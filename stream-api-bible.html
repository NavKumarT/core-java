What is a Stream?

A Stream is a sequence of elements supporting functional-style, declarative operations — you describe WHAT transformation you want, not HOW to loop and accumulate it. Critically, a stream is NOT a data structure: it doesn't store elements, it processes them from a source, on demand.

CollectionStream
Stores data?Yes — data sits in memoryNo — a pipeline of computation over a source
ConsumptionCan be iterated many timesConsumed ONCE — a second terminal op throws IllegalStateException
EvaluationEager — building the collection does the workLazy — nothing runs until a terminal operation
MutationYou mutate it directly (add/remove)Never mutates its source; produces new streams/results
Iteration controlExternal — you write the loopInternal — the Stream API controls the iteration for you
The declarative shift, side by side 
// Imperative — external iteration, you manage state manually
List<String> result = new ArrayList<>();
for (Employee e : employees) {
    if (e.getSalary() > 50000) {
        result.add(e.getName().toUpperCase());
    }
}

// Declarative — internal iteration, you describe the transformation
List<String> result2 = employees.stream()
    .filter(e -> e.getSalary() > 50000)
    .map(e -> e.getName().toUpperCase())
    .collect(Collectors.toList());
// Same result — but the STRUCTURE of the transformation is now explicit,
// composable, and (as covered later) trivially parallelizable via
// .parallelStream() with zero change to the pipeline's logic
💡 Interview one-liner: "A Stream is a view of computation over a source, not a container — it's consumed exactly once, evaluated lazily, and never mutates the underlying data." This single sentence answers a huge fraction of "what is a stream" follow-up questions.
Every Source

Creating Streams

Streams can originate from collections, arrays, individual values, generator functions, or even files — knowing the full menu (not just .stream()) signals real fluency.

From a Collection or array
Stream.of() & Stream.empty()
Stream.iterate() & Stream.generate()
Stream.builder() & Files.lines()
List<String> names = List.of("Ravi", "Sita", "Amit");
Stream<String> s1 = names.stream();          // sequential
Stream<String> s2 = names.parallelStream();  // parallel — covered later

Integer[] arr = {1, 2, 3};
Stream<Integer> s3 = Arrays.stream(arr);
int[] primArr = {1, 2, 3};
IntStream s4 = Arrays.stream(primArr); // primitive array -> IntStream directly, no boxing

Map<String, Integer> map = Map.of("a", 1, "b", 2);
map.entrySet().stream(); // the standard way to stream a Map — via its entry set
Stream<String> s = Stream.of("a", "b", "c"); // varargs — any number of individual values
Stream<Integer> single = Stream.of(42);     // even a single element works
Stream<String> empty = Stream.empty();       // a genuinely empty stream — useful as a safe default return value

IntStream range = IntStream.range(0, 5);        // 0,1,2,3,4 — exclusive upper bound
IntStream rangeClosed = IntStream.rangeClosed(0, 5); // 0,1,2,3,4,5 — INCLUSIVE upper bound
// Stream.iterate(seed, unaryOperator) — each element derived from the previous
Stream<Integer> powers = Stream.iterate(1, n -> n * 2).limit(5);
// [1, 2, 4, 8, 16] — INFINITE without limit()! Always bound it or add a
// predicate-based overload (Java 9+): Stream.iterate(1, n -> n < 100, n -> n * 2)

// Stream.generate(supplier) — each element independently produced, no relation to the last
Stream<Double> randoms = Stream.generate(Math::random).limit(3);
// ALSO infinite without limit() — generate() has no natural termination at all
// Stream.builder() — imperative-style construction when elements come from
// conditional logic rather than an existing source
Stream<String> built = Stream.<String>builder()
    .add("x").add("y").add("z")
    .build();

// Files.lines() — a LAZY stream of a text file's lines, must be closed (try-with-resources)
try (Stream<String> lines = Files.lines(Path.of("data.txt"))) {
    long errorCount = lines.filter(l -> l.contains("ERROR")).count();
} // unlike Files.readAllLines() (eager, loads the whole file), Files.lines() streams
  // line by line — the right choice for files too large to hold entirely in memory
⚠️ Interview trap: Stream.iterate() and Stream.generate() produce INFINITE streams by default. Forgetting .limit() (or, for iterate, the Java 9+ predicate overload) hangs the program — this is one of the most common "gotcha" questions asked specifically to see if you know streams don't self-terminate.
Source → Intermediate → Terminal

The Pipeline Model

Every stream pipeline has exactly three parts: ONE source, ZERO or more intermediate operations, and EXACTLY ONE terminal operation. Understanding this shape is the foundation for nearly every other stream question.

Anatomy of a pipeline 
employees.stream()                              ← SOURCE
    .filter(e -> e.getSalary() > 50000)          ← INTERMEDIATE (returns a Stream)
    .map(Employee::getName)                       ← INTERMEDIATE (returns a Stream)
    .sorted()                                     ← INTERMEDIATE (returns a Stream)
    .collect(Collectors.toList());                ← TERMINAL (returns a result, ends the pipeline)
Intermediate OperationsTerminal Operations
Return typeAnother StreamA concrete result (List, count, boolean, Optional, void...)
EvaluationLAZY — just builds up the pipeline descriptionTriggers actual execution of the WHOLE pipeline
Chainable?Yes — can chain any number of themNo — ends the pipeline; the stream is now consumed
Examplesfilter, map, flatMap, distinct, sorted, limit, skip, peekcollect, forEach, reduce, count, anyMatch, findFirst, toArray
💡 Interview one-liner: "Intermediate operations are lazy and return a Stream, so they can be chained; terminal operations are eager, return a concrete value, and consume the stream. A pipeline with intermediate operations but no terminal operation never actually executes at all — a very common early mistake."
Why Order of Operations Matters

Laziness & Short-Circuiting

Streams don't process elements stage-by-stage across the WHOLE collection — they process ONE ELEMENT AT A TIME through the ENTIRE pipeline, driven by the terminal operation pulling elements as needed. This is a genuinely different execution model than a naive reading suggests, and it's exactly why performance and even correctness questions come up.

Vertical execution, not horizontal
No terminal op = nothing runs
Short-circuiting operations
List<String> names = List.of("Ann", "Bob", "Cal");

names.stream()
    .peek(n -> System.out.println("filter check: " + n))
    .filter(n -> n.startsWith("A") || n.startsWith("B"))
    .peek(n -> System.out.println("map: " + n))
    .map(String::toUpperCase)
    .forEach(System.out::println);

// Output shows each element runs through the WHOLE pipeline before the next starts:
// filter check: Ann
// map: Ann
// ANN
// filter check: Bob
// map: Bob
// BOB
// filter check: Cal    <- filter fails here, map/forEach NEVER run for "Cal"
//
// NOT: "filter check: Ann, Bob, Cal" then "map: Ann, Bob" then "ANN, BOB" —
// that would be the WRONG (horizontal, stage-by-stage) mental model
List<String> names = List.of("a", "b", "c");

names.stream()
    .filter(n -> {
        System.out.println("filtering: " + n); // this NEVER prints anything
        return true;
    });
// No terminal operation -> the WHOLE pipeline is a no-op. Nothing executes.
// This surprises people coming from eager-evaluation languages, and is a
// classic interview trick: "what does this code print?" Answer: nothing.
// SHORT-CIRCUITING operations can stop processing before seeing every element —
// a major efficiency win, and only possible BECAUSE of lazy, per-element evaluation

Optional<Integer> first = Stream.iterate(1, n -> n + 1)  // an INFINITE stream...
    .filter(n -> n % 7 == 0)
    .findFirst();                             // ...but findFirst() stops as soon as ONE match is found — 7
// This WORKS despite the infinite source, precisely because findFirst() is
// short-circuiting and only pulls as many elements as it actually needs

boolean hasNegative = numbers.stream().anyMatch(n -> n < 0); // stops at the FIRST negative found
List<Integer> firstThree = numbers.stream().limit(3).toList(); // stops after 3 elements pulled

// Short-circuiting operations: anyMatch, allMatch, noneMatch, findFirst,
// findAny, limit — all can terminate the pipeline early
🚫 Interview one-liner: "Streams evaluate lazily and per-element, not stage-by-stage — each element flows through the entire pipeline before the next one starts. This is exactly what makes short-circuiting operations like findFirst() or anyMatch() able to work correctly even against an infinite source stream, since they can signal 'stop pulling' partway through."
The #1 Confusion

map() vs flatMap()

Both transform elements — but map() is a strict ONE-TO-ONE transformation, while flatMap() is ONE-TO-MANY, flattening nested structures into a single, flat stream. Confusing the two is one of the most common real interview stumbling blocks.

map(Function<T,R>)
  • Transforms EACH element into exactly ONE new element
  • Stream<T> becomes Stream<R> — same number of elements, different type/value
  • If the mapping function itself returns a Stream, you get a Stream<Stream<X>> — a nested mess you almost never actually want
flatMap(Function<T, Stream<R>>)
  • Transforms each element into a STREAM of zero, one, or many elements, then FLATTENS all those streams into one
  • The element count going IN doesn't have to match the count coming OUT
  • Exactly what you need for nested collections — List<List<X>> → Stream<X>
The Stream<Stream<X>> problem map() creates
flatMap() flattening nested lists
flatMap() with Optional
Classic use: splitting sentences into words
List<List<Integer>> nested = List.of(List.of(1, 2), List.of(3, 4), List.of(5));

// Using map() here gives you a Stream of Streams — NOT what you want
Stream<Stream<Integer>> wrong = nested.stream().map(List::stream);
// You'd need to manually flatten this yourself — awkward and rarely useful as-is
List<List<Integer>> nested = List.of(List.of(1, 2), List.of(3, 4), List.of(5));

List<Integer> flat = nested.stream()
    .flatMap(List::stream) // each inner List becomes a Stream, all merged into ONE flat stream
    .toList();
System.out.println(flat); // [1, 2, 3, 4, 5] — exactly the flattened result

// Real-world: getting every order line item across every order in a list
List<LineItem> allItems = orders.stream()
    .flatMap(order -> order.getLineItems().stream())
    .toList();
// Optional also has flatMap() — same "avoid nesting" principle applied to Optional
Optional<String> name = Optional.of("alice");

// map() with a function returning Optional -> nested Optional<Optional<X>>:
Optional<Optional<String>> nested = name.map(n -> lookupEmail(n)); // lookupEmail returns Optional<String>

// flatMap() unwraps that extra layer automatically:
Optional<String> email = name.flatMap(n -> lookupEmail(n)); // clean Optional<String>, one level
// LeetCode/interview-style classic: count unique words across many sentences
List<String> sentences = List.of("the quick fox", "the lazy dog");

Set<String> uniqueWords = sentences.stream()
    .flatMap(sentence -> Arrays.stream(sentence.split(" "))) // String[] -> Stream<String> per sentence, then flattened
    .collect(Collectors.toSet());
System.out.println(uniqueWords); // [the, quick, fox, lazy, dog] (order not guaranteed — it's a Set)
💡 Interview one-liner: "map() is 1-to-1: same element count, transformed values. flatMap() is 1-to-many-then-flattened: each element becomes a stream of its own, and those sub-streams get merged into one. Reach for flatMap() whenever your mapping function would otherwise itself return a Stream, List, Optional, or array."
Stateless vs Stateful

filter, distinct, sorted, limit/skip

These four intermediate operations look similarly simple, but split cleanly into two categories with VERY different performance and parallelization implications — a distinction senior interviewers specifically probe for.

OperationStateless or Stateful?Why
filter(Predicate)StatelessEach element's fate depends only on itself — no memory of prior elements needed
map(Function)StatelessSame reasoning — a pure per-element transformation
distinct()StatefulMust remember EVERY element seen so far to detect duplicates — needs unbounded memory in the worst case
sorted()StatefulCan't produce the first output element until it has seen and buffered ALL elements — fundamentally can't start emitting early
limit(n) / skip(n)Stateful (but bounded)Needs to track a count/position, though the memory cost is small and fixed, not proportional to stream size
distinct() — uses equals()/hashCode()
sorted() — natural order vs Comparator
limit() / skip() — pagination pattern
Why the distinction matters for parallel streams
List<Integer> nums = List.of(1, 2, 2, 3, 3, 3, 4);
List<Integer> unique = nums.stream().distinct().toList(); // [1, 2, 3, 4]

// distinct() relies on equals()/hashCode() — for custom objects, that
// contract must be correctly implemented, exactly like with a HashSet
record Point(int x, int y) {} // records auto-generate a correct equals()/hashCode() — an easy win here
List<Point> points = List.of(new Point(1,1), new Point(1,1), new Point(2,2));
points.stream().distinct().count(); // 2 — correctly deduplicated by VALUE, thanks to the record's equals()
List<Integer> nums = List.of(5, 2, 8, 1);
nums.stream().sorted().toList(); // [1, 2, 5, 8] — natural order, requires Comparable

List<Employee> employees = getEmployees();
employees.stream()
    .sorted(Comparator.comparingDouble(Employee::getSalary).reversed()
                        .thenComparing(Employee::getName)) // highest salary first, ties by name
    .toList();
// sorted() is STABLE — equal elements retain their original relative order,
// exactly why chaining thenComparing() for tie-breaks works predictably
// The classic pagination pattern: skip N, take the next M
int pageNumber = 2, pageSize = 10; // 0-indexed page

List<Employee> page = employees.stream()
    .sorted(Comparator.comparing(Employee::getName))
    .skip((long) pageNumber * pageSize)  // skip the first 20
    .limit(pageSize)                    // take the next 10
    .toList();

// NOTE: skip() then limit() (in that order) is the correct pattern for
// pagination — reversing the order changes the semantics entirely
// Stateless operations parallelize CLEANLY — each thread can process its
// chunk of the data completely independently, no coordination needed
list.parallelStream().filter(x -> x > 0).map(x -> x * 2); // scales well

// Stateful operations need SYNCHRONIZATION or a full merge step across
// threads — distinct() and sorted() specifically need to see (or at least
// coordinate across) the WHOLE dataset, which limits how well they
// parallelize and can even make a parallel version SLOWER than sequential
// for small-to-medium datasets, due to the coordination overhead
list.parallelStream().sorted().toList(); // correct, but the sort itself doesn't parallelize for free
💡 Interview one-liner: "filter() and map() are stateless — each element is judged in isolation, so they parallelize trivially. distinct() and sorted() are stateful — they need visibility across some or all of the stream, which is exactly why they're more expensive and less parallel-friendly."
Terminal Operation

reduce() — All 3 Overloads

reduce() combines every element into a SINGLE result — sum, product, max, string concatenation, or any custom accumulation. It has three overloads, and knowing exactly when the THIRD one is actually required (not just decorative) is a genuine senior-level distinction.

Optional<T> reduce(BinaryOperator<T>)
T reduce(T identity, BinaryOperator<T>)
U reduce(U identity, BiFunction, BinaryOperator) — the 3-arg form
List<Integer> nums = List.of(3, 7, 2, 9, 4);

Optional<Integer> max = nums.stream().reduce((a, b) -> a > b ? a : b);
// Returns Optional<T> — NOT T directly — because an EMPTY stream has no
// meaningful result to return. This overload has no "identity"/default value
// to fall back on, so Optional.empty() is the only sane answer for empty input

nums.stream().reduce((a, b) -> a + b).ifPresent(System.out::println); // 25
List<Integer> nums = List.of(3, 7, 2, 9, 4);

int sum = nums.stream().reduce(0, (a, b) -> a + b); // 25 — returns T directly, not Optional<T>
// "0" is the IDENTITY value — the safe starting point AND the correct
// result for an EMPTY stream (sum of nothing = 0). This is exactly why
// providing an identity removes the need for Optional

int product = nums.stream().reduce(1, (a, b) -> a * b); // 1512 — identity for multiplication is 1, not 0

// Method reference form, equally common:
int sum2 = nums.stream().reduce(0, Integer::sum);
// The 3-argument form: reduce(identity, accumulator, combiner)
// ONLY relevant for PARALLEL streams — the combiner merges partial results
// computed independently by different threads back into one

List<String> words = List.of("a", "bb", "ccc");

int totalLength = words.parallelStream().reduce(
    0,                                  // identity
    (partialSum, word) -> partialSum + word.length(), // accumulator: T + element -> T (note the TYPE MISMATCH — U vs T)
    (sum1, sum2) -> sum1 + sum2         // combiner: merges two threads' partial sums together
);
// The accumulator's signature is (U, T) -> U — it can reduce a DIFFERENT
// element type T into a result type U (here: String elements -> int result).
// The two single-argument overloads REQUIRE T and the result to be the SAME
// type — this 3-arg form is the only one that lifts that restriction, and
// the combiner is what makes that type-changing reduction safe in parallel
⚠️ Interview trap: "When would you actually need the 3-argument reduce() over collect()?" — in practice, almost NEVER for everyday code; collect() (covered next) is purpose-built for mutable accumulation (building a List, StringBuilder, etc.) and is almost always the better tool. reduce() is for IMMUTABLE combination — a genuinely new value is produced at each step, not a mutated container. Interviewers ask this specifically to see if you understand that distinction, not to see if you've memorized the 3-arg signature.

anyMatch / allMatch / noneMatch on empty streams
findFirst() vs findAny()
toArray() — the generator-function form
List<Integer> empty = List.of();

empty.stream().anyMatch(n -> n > 0);  // false — vacuously, nothing matched
empty.stream().allMatch(n -> n > 0);  // TRUE — vacuously true! No element violates the condition
empty.stream().noneMatch(n -> n > 0); // true — vacuously, nothing failed to avoid matching

// The allMatch() result on an empty stream is the classic trip-up — it
// mirrors formal logic's "vacuous truth" (a universally-quantified statement
// over an empty set is true), not an intuitive "well there's nothing so...false?"
List<Integer> nums = List.of(4, 2, 9, 1, 7);

Optional<Integer> first = nums.stream().filter(n -> n > 3).findFirst(); // ALWAYS 4 — deterministic, respects order
Optional<Integer> any   = nums.stream().filter(n -> n > 3).findAny();   // 4 in SEQUENTIAL streams too, deterministically

// The difference only matters for PARALLEL streams:
Optional<Integer> anyParallel = nums.parallelStream().filter(n -> n > 3).findAny();
// findAny() can return WHICHEVER matching element some thread finds first —
// NOT necessarily 4. findFirst() on a parallel stream still has to coordinate
// to respect encounter order, which costs some parallel performance.
// Use findAny() when you truly don't care WHICH match you get — it's faster in parallel
List<String> names = List.of("a", "b", "c");

Object[] objArr = names.stream().toArray();           // Object[] — loses the specific type
String[] strArr = names.stream().toArray(String[]::new); // typed array — the generator function form
// String[]::new is a constructor reference matching IntFunction<String[]> —
// the stream tells it exactly how many elements it needs, and it builds
// a correctly-sized, correctly-typed array in one step
java.util.stream.Collectors

toList, toSet, toMap & joining

collect() is the workhorse terminal operation for MUTABLE accumulation — building up a result container (List, Set, Map, String) as elements flow through. These four are the ones you'll use daily.

toList() vs .toList() (Java 16+)
toSet()
toMap() — and the duplicate-key crash
joining() — with delimiter/prefix/suffix
List<String> l1 = names.stream().collect(Collectors.toList()); // classic form — mutable, modifiable list

List<String> l2 = names.stream().toList(); // Java 16+ shortcut — returns an UNMODIFIABLE list
// l2.add("x"); // throws UnsupportedOperationException — different contract than Collectors.toList()!

// Explicitly requesting an unmodifiable list pre-Java-16:
List<String> l3 = names.stream().collect(Collectors.toUnmodifiableList());
Set<String> unique = names.stream().collect(Collectors.toSet());
// NO ordering guarantee — backed by a HashSet internally by default
// Need insertion order preserved? Use Collectors.toCollection(LinkedHashSet::new) instead

Set<String> ordered = names.stream()
    .collect(Collectors.toCollection(LinkedHashSet::new)); // toCollection() — plug in ANY collection supplier
List<Employee> employees = getEmployees();

Map<Integer, String> idToName = employees.stream()
    .collect(Collectors.toMap(Employee::getId, Employee::getName)); // (keyFn, valueFn)

// DUPLICATE KEY -> throws IllegalStateException: "Duplicate key ..."
Map<String, Employee> byDept = employees.stream()
    .collect(Collectors.toMap(Employee::getDepartment, e -> e)); // CRASHES if two employees share a department!

// FIX: the 3-arg overload with a MERGE FUNCTION resolves collisions instead of crashing
Map<String, Employee> highestPaidByDept = employees.stream()
    .collect(Collectors.toMap(
        Employee::getDepartment,
        e -> e,
        (existing, incoming) -> existing.getSalary() > incoming.getSalary() ? existing : incoming // keep the higher-paid one on collision
    ));
List<String> names = List.of("Alice", "Bob", "Cara");

names.stream().collect(Collectors.joining());          // "AliceBobCara" — no separator
names.stream().collect(Collectors.joining(", "));    // "Alice, Bob, Cara"
names.stream().collect(Collectors.joining(", ", "[", "]")); // "[Alice, Bob, Cara]" — delimiter, prefix, suffix

// Internally backed by StringBuilder — far more efficient than "+" concatenation
// inside a forEach loop, which would create a new String object every iteration
🚫 Interview trap: the 2-argument Collectors.toMap(keyFn, valueFn) THROWS IllegalStateException the instant two elements produce the same key — it does NOT silently overwrite like a plain HashMap.put() loop would. This is a deliberate safety design, and interviewers use it to check whether you know the 3-argument merge-function overload exists as the fix.
SQL's GROUP BY, In Java

groupingBy & partitioningBy

The single most interview-tested Collector. groupingBy() is the functional equivalent of SQL's GROUP BY — and its real power (and complexity) comes from stacking DOWNSTREAM collectors for multi-level aggregation.

Basic groupingBy — 1 argument
groupingBy + downstream collector
Multi-level (nested) groupingBy
partitioningBy — exactly 2 groups
List<Employee> employees = getEmployees();

// 1-arg groupingBy: classifier only -> Map<K, List<T>> (List is the IMPLICIT default downstream)
Map<String, List<Employee>> byDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment));
// {"Engineering": [emp1, emp3], "Sales": [emp2], ...}
// 2-arg groupingBy: classifier + DOWNSTREAM collector -> transforms each group's List

Map<String, Long> countByDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment, Collectors.counting()));
// {"Engineering": 2, "Sales": 1}  — how many employees per department

Map<String, Double> avgSalaryByDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment, Collectors.averagingDouble(Employee::getSalary)));
// {"Engineering": 95000.0, "Sales": 72000.0}

Map<String, Set<String>> namesByDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment,
                              Collectors.mapping(Employee::getName, Collectors.toSet())));
// mapping() transforms EACH element before it reaches its downstream collector —
// here: extract just the name, THEN collect those names into a Set
// NESTING groupingBy as the downstream of another groupingBy -> multi-level grouping
Map<String, Map<String, List<Employee>>> byDeptThenLevel = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment,
                              Collectors.groupingBy(Employee::getLevel)));
// {"Engineering": {"Senior": [...], "Junior": [...]}, "Sales": {"Senior": [...]}}
// Read it INSIDE-OUT: the innermost groupingBy runs FIRST conceptually per
// department-bucket, producing the nested Map as the "downstream" result

// Combine multi-level grouping WITH a further downstream aggregation:
Map<String, Map<String, Double>> avgSalaryByDeptAndLevel = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment,
                              Collectors.groupingBy(Employee::getLevel,
                                                    Collectors.averagingDouble(Employee::getSalary))));
// partitioningBy: a SPECIAL CASE of grouping — always produces EXACTLY 2
// groups (true/false), keyed by a boolean Predicate, not an arbitrary classifier

Map<Boolean, List<Employee>> partitioned = employees.stream()
    .collect(Collectors.partitioningBy(e -> e.getSalary() > 80000));
List<Employee> highEarners = partitioned.get(true);
List<Employee> others      = partitioned.get(false);

// KEY DIFFERENCE from groupingBy: the resulting Map ALWAYS has BOTH keys
// present (true AND false), even if one group is completely EMPTY — unlike
// groupingBy(), which only creates entries for classifier values that actually occurred
💡 Interview one-liner: "groupingBy() with a downstream collector is how you go from SQL's GROUP BY + aggregate function to Java streams — the classifier is your GROUP BY column, and the downstream collector (counting, averagingDouble, another groupingBy) is your aggregate function. partitioningBy is just groupingBy specialized to a boolean predicate, guaranteed to always produce both true and false keys."
Beyond the Basics

Advanced Collectors

These are the collectors that separate "I know groupingBy" from "I know the whole toolbox" — including teeing() (Java 12+), a genuine favorite for senior-level questions since it's rarely taught but elegantly solves a common problem.

summarizingDouble() — stats in one pass
filtering() as a downstream collector
teeing() — combining two collectors
Custom Collector.of()
collectingAndThen() — post-process the result
DoubleSummaryStatistics stats = employees.stream()
    .collect(Collectors.summarizingDouble(Employee::getSalary));

stats.getMin();     stats.getMax();
stats.getAverage(); stats.getSum();
stats.getCount();

// ONE pass over the data computes min/max/avg/sum/count TOGETHER —
// far more efficient than calling separate min(), max(), average() streams,
// each of which would re-traverse the whole source independently
// Also available: summarizingInt(), summarizingLong()
// filtering() as a DOWNSTREAM collector — different from stream.filter()!
// stream.filter() removes elements BEFORE grouping — an element filtered out
// never even reaches its group, so that GROUP KEY might disappear entirely.
// Collectors.filtering() filters WITHIN each already-formed group instead.

Map<String, List<Employee>> highEarnersByDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment,
                              Collectors.filtering(e -> e.getSalary() > 100000, Collectors.toList())));
// Every department key STILL appears, even ones with ZERO high earners
// (mapping to an empty list) — using stream.filter() BEFORE groupingBy
// would have silently DROPPED any department with no qualifying employees
// teeing() (Java 12+): run TWO downstream collectors over the SAME stream,
// then merge their results with a BiFunction — solves the classic "I need
// two different aggregates from ONE pass" problem elegantly

record MinMax(int min, int max) {}

MinMax range = Stream.of(3, 7, 1, 9, 4)
    .collect(Collectors.teeing(
        Collectors.minBy(Integer::compareTo),  // collector 1
        Collectors.maxBy(Integer::compareTo),  // collector 2, applied to the SAME elements
        (min, max) -> new MinMax(min.get(), max.get()) // merge function — combines both results
    ));
// BEFORE teeing(): you'd have to either stream the data TWICE (wasteful),
// or hand-write a single custom Collector to track both min and max —
// teeing() gives you the "two collectors, one pass" pattern for free
// Collector.of(supplier, accumulator, combiner, [finisher]) — build your own
Collector<String, StringJoiner, String> customJoiner = Collector.of(
    () -> new StringJoiner(", ", "[", "]"), // SUPPLIER: creates the mutable accumulator container
    StringJoiner::add,                     // ACCUMULATOR: folds one element into the container
    StringJoiner::merge                    // COMBINER: merges two containers (for parallel streams)
                                           // no 4th arg -> the container itself IS the final result (Collector.of has a default identity finisher when omitted, or use the 4-arg form)
);
String result = Stream.of("a", "b", "c").collect(customJoiner);

// This is EXACTLY the same shape as collect()'s own 3-arg overload:
// collect(Supplier, BiConsumer, BiConsumer) — Collectors.of() just packages
// that same idea into a reusable, named Collector object
// collectingAndThen(): wraps another collector, then applies a final
// transformation to its result — commonly used to make a result immutable

List<String> immutableNames = names.stream()
    .collect(Collectors.collectingAndThen(
        Collectors.toList(),          // the underlying collector — builds a normal mutable List
        Collections::unmodifiableList // the finishing transformation — wraps it as read-only
    ));
// Also useful as the downstream of a groupingBy, to post-process each group's result
Avoiding Boxing

Primitive Streams — IntStream, LongStream, DoubleStream

A Stream<Integer> boxes every single int into an Integer object — real memory and GC overhead at scale. The JDK ships specialized primitive stream types specifically to avoid this.

The boxing cost, concretely
Converting between Stream<T> and IntStream
Extra methods primitive streams offer
// Pitfall: boxing every element for a purely numeric operation
List<Integer> numbers = IntStream.range(0, 1_000_000)
    .boxed()                          // int -> Integer, for EVERY element — a real allocation each time
    .collect(Collectors.toList());

long sum = numbers.stream()
    .mapToLong(Integer::longValue)         // unboxing again to sum — wasted round-trip
    .sum();

// Better: stay in IntStream the whole time, no boxing at all
long sum2 = IntStream.range(0, 1_000_000).asLongStream().sum();
// or simply: IntStream.range(0, 1_000_000).sum() if int-range is enough
List<Employee> employees = getEmployees();

// Stream<T> -> IntStream: via mapToInt/mapToLong/mapToDouble
IntStream ages = employees.stream().mapToInt(Employee::getAge);
int totalAge = ages.sum();       // primitive streams have sum()/average()/max()/min() DIRECTLY, no Comparator needed

// IntStream -> Stream<Integer>: via boxed(), when you need object semantics
List<Integer> boxedAges = employees.stream()
    .mapToInt(Employee::getAge)
    .boxed()                    // needed because Collectors.toList() requires a reference type, not int
    .toList();
// Primitive streams expose extra methods a Stream<Integer> simply doesn't have:
IntStream nums = IntStream.of(3, 7, 2, 9, 4);

nums.sum();     // int — direct, no reduce() needed
IntStream.of(3, 7, 2, 9, 4).average(); // OptionalDouble — NOT Optional<Double>
IntStream.of(3, 7, 2, 9, 4).max();     // OptionalInt — NOT Optional<Integer>
IntStream.of(3, 7, 2, 9, 4).summaryStatistics(); // IntSummaryStatistics — min/max/avg/sum/count in one pass

// Note the SPECIALIZED Optional types: OptionalInt/OptionalLong/OptionalDouble —
// NOT generic Optional<Integer> — this is itself a common trick question,
// since it's easy to assume Optional<Integer> and get a compile error
💡 Interview one-liner: "IntStream/LongStream/DoubleStream exist purely to avoid autoboxing overhead for numeric-heavy pipelines — sum()/average()/max() are built in directly, and the Optional variants (OptionalInt, etc.) avoid boxing there too. Reach for them whenever a pipeline is doing genuinely numeric work, not just passing objects through."
Streams' Constant Companion

Optional Deep Dive

Optional<T> shows up constantly as a stream result type (findFirst(), min(), reduce() without identity) — a container that may or may not hold a value, designed to make the ABSENCE of a result an explicit, type-checked possibility instead of a silent null.

The anti-pattern: isPresent() + get()
Idiomatic Optional usage
map/filter/flatMap chaining on Optional
Optional<Employee> result = employees.stream()
    .filter(e -> e.getId() == 42)
    .findFirst();

// ANTI-PATTERN — this is just null-checking with extra steps
if (result.isPresent()) {
    System.out.println(result.get().getName());
} else {
    System.out.println("Not found");
}
// Interviewers specifically ask "how would you improve this" — the fix is
// using Optional's own functional-style methods instead, shown next
Optional<Employee> result = employees.stream().filter(e -> e.getId() == 42).findFirst();

result.ifPresent(e -> System.out.println(e.getName())); // runs ONLY if present, no branching needed

String name = result.map(Employee::getName).orElse("Unknown"); // transform + default, one line

String name2 = result.map(Employee::getName)
                       .orElseGet(() -> computeDefaultName()); // LAZY default — only computed if actually needed
// orElse() ALWAYS evaluates its argument eagerly, even when the Optional
// IS present and the fallback is discarded — orElseGet() avoids that waste
// for expensive fallback computations. A genuinely common gotcha.

result.orElseThrow(() -> new NoSuchElementException("Employee not found")); // explicit failure instead of a silent default
// Optional supports the SAME map/filter/flatMap vocabulary as Stream —
// deliberately, since it's conceptually "a stream of 0 or 1 elements"

Optional<Employee> emp = findEmployee(42);

String deptName = emp
    .filter(e -> e.isActive())              // discard if inactive -> becomes empty
    .map(Employee::getDepartment)         // Optional<String> if present
    .orElse("No active department");

// Chaining a call that ITSELF returns Optional -> use flatMap(), same
// principle as flatMap() on Stream avoiding Optional<Optional<X>>
Optional<Manager> manager = emp.flatMap(Employee::getManager); // getManager() returns Optional<Manager>
⚠️ Interview trap: Optional.get() without first checking presence throws NoSuchElementException on an empty Optional — it's just as dangerous as an unchecked null dereference if used carelessly. The entire point of Optional is defeated if you reflexively call .get() everywhere; prefer map/orElse/ifPresent/orElseThrow instead.
Under the Hood

Parallel Streams — Internals

Calling .parallelStream() or .parallel() looks like a free performance switch — understanding what's ACTUALLY happening underneath is exactly what separates a surface-level answer from a senior one.

ForkJoinPool.commonPool()
  • Parallel streams use the shared, JVM-wide ForkJoinPool.commonPool() by default — NOT a pool you create per-call
  • Default parallelism level = Runtime.availableProcessors() - 1 worker threads
  • Because it's SHARED across your entire application, a blocking or long-running task submitted to it from ANYWHERE can starve other unrelated parallel streams running concurrently
Spliterator — the splitting mechanism
  • Every stream source has a Spliterator ("splittable iterator") responsible for dividing the data into chunks for separate threads
  • How WELL a source splits varies enormously: arrays and ArrayList split cheaply and evenly (known size, direct indexing); LinkedList and Stream.iterate() split poorly (must walk element-by-element to even find a split point)
  • This is exactly why the underlying DATA STRUCTURE matters for parallel stream performance, not just the data size
The fork/join work-stealing model
Using a custom ForkJoinPool
// Conceptually, a parallel stream recursively splits the work (FORK),
// processes each piece independently, then combines results (JOIN) —
// exactly the divide-and-conquer pattern ForkJoinPool was built for

List<Integer> bigList = generateMillionNumbers();

long sum = bigList.parallelStream()
    .mapToLong(Integer::longValue)
    .sum();
// Internally: the list is recursively split into halves until chunks are
// small enough to process directly, each chunk is summed independently
// (possibly on a different worker thread), and partial sums are combined —
// this is WORK STEALING: idle threads "steal" pending sub-tasks from busy
// threads' queues, keeping all cores productively busy
// Submitting a parallel stream operation to a CUSTOM pool, isolating it
// from the shared commonPool (useful to avoid starving unrelated app code)
ForkJoinPool customPool = new ForkJoinPool(4); // 4 threads, dedicated to this work

try {
    long sum = customPool.submit(() ->
        bigList.parallelStream().mapToLong(Integer::longValue).sum()
    ).get();
} finally {
    customPool.shutdown(); // always clean up custom pools explicitly
}
// This pattern is exactly what senior interviewers listen for when they
// ask "how would you avoid one slow parallel stream affecting unrelated
// code elsewhere in the application" — the commonPool being SHARED is the crux
💡 Interview one-liner: "Parallel streams split the source via a Spliterator, distribute chunks across ForkJoinPool.commonPool()'s worker threads using work-stealing, and merge partial results back together. It's genuinely powerful for large, CPU-bound, easily-splittable data — and genuinely risky for small datasets, I/O-bound work, or anything that shares the common pool with other blocking operations."
Where It Goes Wrong

Parallel Stream Pitfalls

"Parallel does not always mean faster" is the single sentence interviewers most want to hear you say — followed by a concrete explanation of why. This is consistently cited as the #1 thing separating junior from senior answers on this topic.

Shared mutable state — silent data corruption
Small datasets — overhead exceeds benefit
Blocking I/O starving the common pool
forEachOrdered() negating parallelism
// THE classic parallel stream bug: mutating shared state from a lambda
List<Integer> results = new ArrayList<>(); // NOT thread-safe

numbers.parallelStream().forEach(n -> results.add(n * 2)); // multiple threads calling add() concurrently
// RESULT: unpredictable — lost updates, ArrayIndexOutOfBoundsException, or
// even an infinite loop internally, since ArrayList's internal array-resize
// logic is not designed to survive concurrent mutation

// FIX 1: use a proper collector — thread-safety is handled FOR you
List<Integer> safe = numbers.parallelStream()
    .map(n -> n * 2)
    .collect(Collectors.toList()); // collect() manages merging safely across threads internally
List<Integer> tiny = List.of(1, 2, 3, 4, 5);

int sum = tiny.parallelStream().mapToInt(Integer::intValue).sum();
// LIKELY SLOWER than tiny.stream()...sum() — the overhead of splitting work,
// scheduling across the ForkJoinPool, and merging results FAR exceeds the
// trivial cost of just summing 5 ints sequentially on one thread

// Rule of thumb repeatedly cited by interviewers and JDK docs alike:
// parallel streams only pay off for LARGE datasets (often cited: tens of
// thousands of elements or more) combined with genuinely CPU-intensive
// per-element work — never assume "parallel" is a free upgrade
// Blocking (I/O, network calls, sleep) inside a parallel stream is a serious anti-pattern
urls.parallelStream()
    .map(url -> fetchOverNetwork(url)) // BLOCKS a commonPool worker thread while waiting on the network
    .toList();

// PROBLEM: the commonPool is SHARED across your ENTIRE JVM process. If
// this pipeline ties up most/all of its worker threads waiting on slow
// network calls, ANY OTHER unrelated parallel stream running anywhere else
// in the same application — even in a completely different part of the
// codebase — can be starved of threads to run on

// FIX: use a dedicated ExecutorService + CompletableFuture for I/O-bound
// work instead of parallel streams, which are designed for CPU-bound tasks
List<Integer> nums = generateMillionNumbers();

nums.parallelStream()
    .map(n -> n * 2)
    .forEachOrdered(System.out::println); // forces ENCOUNTER ORDER to be preserved
// This largely NEGATES the parallelism benefit — the whole point of
// parallel execution is that threads finish in whatever order they finish,
// and forcing re-sequencing back into original order adds real coordination cost

// If order doesn't genuinely matter for your use case, use plain forEach()
// instead — it makes NO ordering guarantee and lets threads report results
// as they finish, which is exactly what unlocks full parallel throughput
🚫 The complete "when NOT to use parallel streams" checklist: small datasets, I/O-bound or blocking operations, stateful/shared-mutable-state lambdas, poorly-splitting sources (LinkedList, Stream.iterate()), and anywhere strict encounter order must be preserved throughout. When in doubt: measure with a real benchmark (JMH) rather than assuming — parallel streams are a targeted optimization, not a default.

Real-World Scenarios

The kind of stream pipelines that actually show up in take-home assignments and "design a small feature" interview rounds — not LeetCode puzzles, but everyday business-logic transformations.

record Order(String customerId, String product, int quantity, double price) {}

List<String> top3Products = orders.stream()
    .collect(Collectors.groupingBy(Order::product,
                              Collectors.summingDouble(o -> o.quantity() * o.price())))
    .entrySet().stream()

    .limit(3)
    .map(Map.Entry::getKey)

record LogEntry(String service, String level, String message) {}

List<LogEntry> logs = getLogs();

// Error COUNT per service — a standard groupingBy+filtering+counting combo
Map<String, Long> errorsByService = logs.stream()
    .filter(l -> l.level().equals("ERROR"))
    .collect(Collectors.groupingBy(LogEntry::service, Collectors.counting()));

// ERROR RATE per service (needs the total too — teeing() from earlier fits perfectly)
Map<String, Double> errorRateByService = logs.stream()
    .collect(Collectors.groupingBy(LogEntry::service,
        Collectors.teeing(
            Collectors.counting(),
            Collectors.filtering(l -> l.level().equals("ERROR"), Collectors.counting()),
            (total, errors) -> total == 0 ? 0.0 : (double) errors / total
        )));
// Deduplicate by a BUSINESS KEY (e.g. email), keeping the MOST RECENT record —
// plain distinct() can't do this since it only knows equals()/hashCode()
record User(String email, String name, Instant updatedAt) {}

Collection<User> deduped = users.stream()
    .collect(Collectors.toMap(
        User::email,                                              // dedup key
        u -> u,                                                       // value
        (existing, incoming) -> incoming.updatedAt().isAfter(existing.updatedAt()) ? incoming : existing
    ))
    .values();
// This "toMap with a merge function" pattern is THE standard way to
// deduplicate-by-key-with-a-tiebreak in real code — worth memorizing
// Real form/API validation: collect ALL errors, don't stop at the first —
// a genuinely common "design this small piece" interview ask
record ValidationRule(Predicate<UserForm> check, String errorMessage) {}

List<ValidationRule> rules = List.of(
    new ValidationRule(f -> f.email().contains("@"), "Invalid email"),
    new ValidationRule(f -> f.age() >= 18, "Must be 18+"),
    new ValidationRule(f -> !f.name().isBlank(), "Name required")
);

List<String> errors = rules.stream()
    .filter(rule -> !rule.check().test(userForm)) // keep only FAILED rules
    .map(ValidationRule::errorMessage)

Map<String, Map<String, Double>> report = sales.stream()

Streams vs Loops

Performance Considerations

Streams add a genuine (small) overhead versus a hand-written loop — object allocation for each pipeline stage, virtual method dispatch through lambdas, and boxing where applicable. For 95% of business code this is irrelevant; for hot paths, it's worth knowing where the cost actually comes from.

Where the overhead comes from
  • Each intermediate operation wraps the previous stage — a chain of small objects gets built even before any element is processed
  • Lambda calls go through an invokedynamic-generated functional interface implementation — cheap, but not literally zero-cost like inlined loop body code
  • Boxing for Stream<Integer>-style pipelines over numeric data, as covered in the Primitive Streams section
When to actually care
  • Tight loops executed millions of times per second in a genuine hot path (verified via profiling, not guessed)
  • Very large numeric computations where boxing overhead compounds — prefer primitive streams there
  • For everyday CRUD/business logic, readability and correctness should win — the JIT optimizes stream pipelines quite well in steady state, and premature "loop is faster" rewrites are rarely worth the lost clarity
Redundant chained filters
Underlying data structure matters for parallel
Ordering operations to exploit short-circuiting
// Multiple separate filters CAN be combined into one predicate for one less pass —
// though the JIT often optimizes trivial cases like this away regardless
List<String> words = getWords();

long count1 = words.stream()
    .filter(w -> w.length() > 3)
    .filter(w -> w.startsWith("a"))
    .count();

long count2 = words.stream()
    .filter(w -> w.length() > 3 && w.startsWith("a")) // one combined predicate — marginally leaner pipeline structure
    .count();
// The performance difference here is typically negligible — this is a
// STYLE/readability decision far more than a real optimization in most cases
// For parallel streams specifically, the SOURCE data structure genuinely
// changes performance — not just a micro-detail

ArrayList<Integer> arrayBacked = new ArrayList<>(millionNumbers);
arrayBacked.parallelStream().mapToInt(Integer::intValue).sum(); // splits cheaply — known size, direct index access

LinkedList<Integer> linkedBacked = new LinkedList<>(millionNumbers);
linkedBacked.parallelStream().mapToInt(Integer::intValue).sum(); // splits POORLY — must walk node-by-node to find split points,
                                                          // often ends up SLOWER in parallel than the ArrayList version sequentially
// Prefer ArrayList/arrays as the source whenever parallel streams are on the table
// Put the CHEAPEST and MOST SELECTIVE filter FIRST — laziness means later
// operations never run for elements already excluded, so filtering early saves work

// Less optimal: expensive check runs on elements a cheap check would already exclude
list.stream()
    .filter(x -> expensiveDatabaseCheck(x)) // runs for EVERY element first
    .filter(x -> x.getStatus() == Status.ACTIVE) // a cheap in-memory check, applied second
    .toList();

// Better: cheap, selective filter FIRST — fewer elements ever reach the expensive check
list.stream()
    .filter(x -> x.getStatus() == Status.ACTIVE) // cheap, run first — narrows the set immediately
    .filter(x -> expensiveDatabaseCheck(x))       // only runs for the SURVIVORS of the cheap filter
    .toList();
💡 Interview one-liner: "For everyday code, stream vs loop performance is a non-issue — readability wins. Where it genuinely matters is avoiding boxing in numeric-heavy pipelines, choosing array-backed sources for parallel streams, and ordering filters cheap-and-selective-first to exploit laziness. I'd reach for a profiler before rewriting a stream pipeline 'for performance' on a hunch."

Short-answer FAANG questions

❓ What is a Stream, and how is it different from a Collection?

  • A Stream is a lazy, one-time-use pipeline of computation over a source — it doesn't store data
  • A Collection stores data in memory and can be iterated repeatedly; a Stream is consumed once and throws on reuse

❓ Intermediate vs terminal operations — what's the actual difference?

  • Intermediate: returns another Stream, lazy, chainable (filter, map, sorted)
  • Terminal: returns a concrete result, triggers execution, consumes the stream (collect, forEach, reduce)
  • A pipeline with zero terminal operations never executes at all

❓ map() vs flatMap() — when do you need flatMap specifically?

  • map(): 1-to-1 transformation, same element count
  • flatMap(): 1-to-many, then flattens — needed whenever your mapping function would itself return a Stream/List/Optional, to avoid a nested Stream<Stream<X>>

❓ Why isn't a parallel stream always faster?

  • Overhead of splitting work, scheduling across ForkJoinPool threads, and merging results can exceed the benefit for small datasets
  • Poorly-splitting sources (LinkedList, Stream.iterate) parallelize badly regardless of size
  • Blocking/I/O-bound work starves the shared commonPool, hurting the WHOLE application, not just that pipeline

❓ What makes an operation "stateful" vs "stateless," and why does it matter?

  • Stateless (filter, map): judges/transforms each element independently — parallelizes trivially
  • Stateful (distinct, sorted): needs visibility across some or all prior elements — harder to parallelize, can't emit results early

❓ groupingBy() vs partitioningBy() — when would you use each?

  • groupingBy: arbitrary classifier function, produces however many keys naturally occur in the data
  • partitioningBy: boolean predicate only, ALWAYS produces exactly 2 keys (true/false), even if one group is empty

❓ How would you compute a group's count AND average in a single pass?

  • groupingBy + Collectors.summarizingDouble() gives count/min/max/avg/sum together in one collector
  • Or groupingBy + Collectors.teeing() to combine two independent downstream collectors over the same grouped data

❓ Why does the 2-argument toMap() throw on duplicate keys instead of overwriting?

  • Deliberate safety design — silently overwriting could hide a real data-integrity bug (e.g. two "unique" IDs colliding)
  • The 3-argument overload with an explicit merge function is the intended fix when duplicates are expected and need a defined resolution strategy

❓ orElse() vs orElseGet() on Optional — what's the real difference?

  • orElse(x): argument is ALWAYS evaluated eagerly, even when the Optional is present and the value is discarded
  • orElseGet(supplier): the supplier only runs if the Optional is actually empty — use it whenever the fallback is expensive to compute

❓ Can you use a stream twice? What happens if you try?

  • No — a Stream is single-use. Calling a second terminal operation on an already-consumed stream throws IllegalStateException
  • To traverse the same source twice, create a fresh stream from it each time (e.g. call .stream() again on the underlying List)

❓ Why should you avoid side effects inside map()/filter()?

  • These are meant to be pure functions — the Stream API's internal execution order (including for parallel streams) isn't something you should rely on for correctness
  • Side effects there are fragile sequentially and genuinely dangerous under parallel execution (race conditions on shared state)

❓ What's the purpose of peek(), and why shouldn't you rely on it for logic?

  • Documented purpose: debugging visibility into a pipeline's intermediate state, nothing more
  • The JVM may skip running it for elements whose result turns out to be unused (e.g. with certain short-circuiting terminal ops) — unreliable for anything that MUST happen

❓ How would you find the top N elements by some field, efficiently?

  • sorted(Comparator.comparing(...).reversed()).limit(N) — simple, O(n log n), fine for most cases
  • For very large streams where N is small, a bounded PriorityQueue (from the Collections Bible's Top-K pattern) avoids sorting the entire dataset — O(n log N) instead
Interview Reference

Interview Cheatsheet

One-liners for when you're under pressure. Know these cold.

🌊 What a Stream is

  • A lazy, one-time pipeline of computation over a source — not a data structure
  • Consumed exactly once; a second terminal op throws IllegalStateException
  • Never mutates its source

🏗️ The pipeline shape

  • 1 source → 0+ intermediate ops → exactly 1 terminal op
  • Intermediate: lazy, returns a Stream (filter, map, sorted)
  • Terminal: eager, returns a result, ends the pipeline (collect, forEach, reduce)
  • No terminal op = pipeline never runs at all

⚡ Laziness & short-circuiting

  • Each element flows through the WHOLE pipeline before the next starts (vertical, not horizontal)
  • Short-circuiting: anyMatch, allMatch, noneMatch, findFirst, findAny, limit
  • allMatch() on an empty stream → true (vacuous truth)

🔀 map() vs flatMap()

  • map(): 1-to-1, same element count
  • flatMap(): 1-to-many, then flattens — use when the mapper itself returns a Stream/List/Optional

⚖️ Stateless vs stateful ops

  • Stateless (parallelize easily): filter, map
  • Stateful (need broader visibility): distinct, sorted, limit/skip

➕ reduce() — 3 overloads

  • reduce(BinaryOperator) → Optional<T> (no identity, empty-safe via Optional)
  • reduce(identity, BinaryOperator) → T directly
  • reduce(identity, accumulator, combiner) → only needed for TYPE-CHANGING reduction in parallel

🎯 Terminal ops quick ref

  • findFirst(): deterministic, respects order. findAny(): faster in parallel, no order guarantee
  • Object[] toArray() vs T[] toArray(generator)

📦 Collectors — the basics

  • toList() (Java 16+, unmodifiable) vs Collectors.toList() (mutable)
  • toMap() 2-arg THROWS on duplicate keys — use the 3-arg merge-function overload
  • joining(delim, prefix, suffix)

📊 groupingBy & partitioningBy

  • groupingBy(classifier, downstream) = SQL GROUP BY + aggregate
  • Nest groupingBy as its own downstream for multi-level grouping
  • partitioningBy: boolean only, ALWAYS both true/false keys present

🧰 Advanced Collectors

  • summarizingDouble(): min/max/avg/sum/count in ONE pass
  • filtering(): filters WITHIN a group (unlike stream.filter() before grouping)
  • teeing() (12+): two collectors, one pass, merged with a BiFunction
  • collectingAndThen(): post-process a collector's result (e.g. make it immutable)

🔢 Primitive streams

  • IntStream/LongStream/DoubleStream avoid boxing for numeric work
  • Return OptionalInt/OptionalLong/OptionalDouble — NOT generic Optional<Integer>
  • boxed() to go back to Stream<Integer>

❓ Optional essentials

  • Avoid isPresent()+get() — prefer map/orElse/ifPresent/orElseThrow
  • orElse(): eager. orElseGet(): lazy — use for expensive fallbacks
  • flatMap() to avoid Optional<Optional<X>>

🧵 Parallel streams

  • Use ForkJoinPool.commonPool() by default — SHARED across the whole JVM
  • Spliterator splits the source — ArrayList/arrays split well, LinkedList/iterate() don't
  • "Parallel does not always mean faster" — the #1 thing to say

🚫 When NOT to use parallel streams

  • Small datasets — overhead exceeds benefit
  • I/O-bound or blocking work — starves the shared commonPool
  • Shared mutable state / stateful lambdas — race conditions
  • forEachOrdered() — negates the parallelism benefit

🚨 Top interview traps

  • Reusing an already-consumed stream → IllegalStateException
  • toMap() duplicate key → IllegalStateException (needs a merge function)
  • Forgetting .limit() on Stream.iterate()/generate() → infinite loop
  • Streams don't skip nulls automatically — filter(Objects::nonNull) first
  • Relying on peek() for real logic — it's a debugging tool, not guaranteed to run
