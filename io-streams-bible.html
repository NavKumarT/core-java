java.io

Streams & the Java I/O Model

A stream is a sequential channel of data flowing between your program and a source or destination — a file, a network socket, an in-memory buffer, another process. Java models every I/O source uniformly as a stream so the same read/write vocabulary works everywhere, regardless of what's on the other end.

Why streams, not random blob transfer
  • Data arrives sequentially and often can't fit in memory all at once (a 10GB file, an infinite socket)
  • A stream lets you process data incrementally — read a chunk, act on it, read the next chunk
  • Uniform abstraction: a file, a network connection, and a byte array all expose the same read()/write() contract
Two families: byte streams vs character streams
  • Byte streams (InputStream/OutputStream) — raw 8-bit bytes; used for binary data: images, audio, serialized objects, any non-text file
  • Character streams (Reader/Writer) — 16-bit Unicode characters; used for text, handles character-encoding conversion automatically
  • Character streams exist BECAUSE byte streams alone don't understand multi-byte encodings (UTF-8, UTF-16) — reading text as raw bytes can split a multi-byte character across two reads

💡 Rule of thumb for choosing: reading/writing text meant for humans → character stream. Reading/writing anything else, or when you don't know/care about encoding → byte stream. Mixing them up (e.g. reading a JPEG with a Reader) corrupts the data because Readers apply charset decoding that binary data was never encoded with.
The Big Picture

  • Supports both reading and writing through a single object, plus arbitrary seeking via a file pointer

Design Pattern Tie-In

The Decorator Pattern Behind java.io

This is a favorite LLD-meets-I/O interview question: "Why do you have to write new BufferedReader(new InputStreamReader(new FileInputStream(...))) instead of just one class?" The answer is that java.io is a textbook implementation of the Decorator design pattern.

The problem decorator solves
  • Streams have many optional, combinable features: buffering, typed reads, pushback, line counting
  • Without decorator, you'd need a class for every COMBINATION — BufferedFileInputStream, BufferedDataFileInputStream, and so on — a combinatorial explosion
  • Decorator instead wraps a base stream in layers, each layer adding exactly one capability
How it's structured in java.io
  • FilterInputStream IS-A InputStream (extends it) AND HAS-A InputStream (wraps one in a field)
  • Every method delegates to the wrapped stream by default, with the subclass overriding only the methods it wants to enhance
  • BufferedInputStream, DataInputStream, PushbackInputStream are all concrete decorators built this way
Stacking decorators — each layer adds one capability 
// Base stream: raw byte access to a file
FileInputStream fis = new FileInputStream("data.txt");

// Decorator layer 1: adds buffering for performance
BufferedInputStream bis = new BufferedInputStream(fis);

// Decorator layer 2: adds byte→char conversion (a different family bridge)
InputStreamReader isr = new InputStreamReader(bis, StandardCharsets.UTF_8);

// Decorator layer 3: adds line-based reading on top of the char stream
BufferedReader br = new BufferedReader(isr);

String line = br.readLine(); // the outermost wrapper is what you call — everything underneath does its part

// Fully inlined, this is the classic (and interview-common) one-liner:
try (BufferedReader reader = new BufferedReader(
        new InputStreamReader(
            new FileInputStream("data.txt"), StandardCharsets.UTF_8))) {
    String line2;
    while ((line2 = reader.readLine()) != null) {
        System.out.println(line2);
    }
}
💡 Interview one-liner: "java.io favors composition over a rigid inheritance tree — each wrapper class implements the same stream interface it wraps, so wrappers stack in any order and any combination without an explosion of subclasses." This is precisely the Decorator pattern's textbook definition — same intent as Java's own GoF example.
⚠️ Closing the OUTERMOST wrapper is enough — close() propagates inward through the chain automatically, since each decorator's close() calls the wrapped stream's close(). Closing an inner stream directly while an outer wrapper still references it can cause errors on subsequent use of the outer wrapper.

// read() one byte at a time — returns int, -1 signals EOF
try (FileInputStream fis = new FileInputStream("data.txt")) {
    int b;
    while ((b = fis.read()) != -1) {   // -1 is an int outside byte range (0-255), so it's unambiguous
        System.out.print((char) b);
    }
}

// read(byte[]) — bulk read, far fewer method calls, MUCH faster
try (FileInputStream fis = new FileInputStream("data.txt")) {
    byte[] buffer = new byte[1024];
    int bytesRead;
    while ((bytesRead = fis.read(buffer)) != -1) {
        // IMPORTANT: use only buffer[0..bytesRead), NOT the whole array —
        // the last chunk is usually partial and leaves stale data past bytesRead
        System.out.write(buffer, 0, bytesRead);
    }
}
try (BufferedInputStream bis =
        new BufferedInputStream(new FileInputStream("data.txt"))) {

    System.out.println(bis.markSupported()); // true — BufferedInputStream supports it

    bis.mark(100);            // mark current position; guarantees reset() works for up to 100 bytes read
    int first = bis.read();  // consume a byte
    bis.reset();             // rewind back to the marked position
    int firstAgain = bis.read(); // reads the SAME byte again
    System.out.println(first == firstAgain); // true
}

// Plain FileInputStream: markSupported() returns false —
// calling mark()/reset() on it silently does nothing useful, or throws
// IOException on reset() ("mark/reset not supported")
try (FileOutputStream fos = new FileOutputStream("out.txt")) {
    fos.write(65);                          // writes ONE byte — 'A' (int is truncated to a byte)
    fos.write("Hello".getBytes());        // writes a whole byte array
    fos.write("Hello World".getBytes(), 0, 5); // writes "Hello" only — offset 0, length 5
    fos.flush();                          // forces buffered bytes out — usually a no-op for FileOutputStream, matters for Buffered/network streams
} // close() called automatically — flushes and releases the file handle
🚫 Classic bug: checking read(byte[])'s return value against 0 instead of -1. A return of 0 is legal (some streams may return 0 bytes read without being at EOF); only -1 means "end of stream." And after a partial bulk read, printing the WHOLE buffer array instead of only buffer[0, bytesRead) leaks stale bytes from the previous iteration into the output.
Byte Streams

FileInputStream & FileOutputStream

The most commonly used byte streams — direct byte-level access to a file on disk. Simple, but with a handful of interview-relevant exception and lifecycle details.

FileOutputStream
  • Constructor throws FileNotFoundException — actually thrown if the file can't be CREATED (parent dir missing, no permissions), not literally "file not found"
  • By default, overwrites the file's existing contents from byte 0
  • Second constructor arg boolean append — new FileOutputStream(path, true) appends instead of overwriting
  • write() methods throw IOException
FileInputStream
  • Constructor throws FileNotFoundException if the file genuinely doesn't exist, or is a directory, or can't be opened for reading
  • available() can be used to size a buffer for a one-shot full read, but is unreliable for network-backed streams
  • Does NOT support mark()/reset() — markSupported() returns false

Reading a file — byte by byte
Reading a whole file at once
Append mode
try (FileOutputStream fos = new FileOutputStream("test.txt")) {
    String str = "example";
    byte[] B = str.getBytes();
    for (byte b : B) {
        fos.write(b);   // works, but one syscall-ish operation per byte — inefficient
    }
    // Better: fos.write(B) — writes the whole array in one call
} // try-with-resources calls close() automatically — no need to call it explicitly
try (FileInputStream fis = new FileInputStream("test.txt")) {
    int x;
    while ((x = fis.read()) != -1) {
        System.out.print((char) x);
    }
}
// Note: for character/text data, FileReader is the more appropriate choice —
// it handles multi-byte encodings correctly, this cast-to-char trick only
// works safely for single-byte encodings like ASCII/ISO-8859-1
try (FileInputStream fis = new FileInputStream("test.txt")) {
    byte[] B = new byte[fis.available()]; // sized off available() — OK for small local files, NOT reliable in general
    fis.read(B);
    String str = new String(B);
    System.out.println(str);
}

// Modern equivalent (Java 7+), no manual buffer sizing needed:
byte[] allBytes = Files.readAllBytes(Path.of("test.txt"));
String str2 = new String(allBytes, StandardCharsets.UTF_8);
// Default constructor OVERWRITES the file
try (FileOutputStream fos = new FileOutputStream("log.txt")) {
    fos.write("first line\n".getBytes());
}
try (FileOutputStream fos = new FileOutputStream("log.txt")) { // same call again
    fos.write("second line\n".getBytes());
}
// log.txt now contains ONLY "second line" — "first line" was wiped

// append=true preserves existing content:
try (FileOutputStream fos = new FileOutputStream("log.txt", true)) {
    fos.write("appended line\n".getBytes());
}
⚠️ If a file is marked read-only (file.setReadOnly()) and you open it with FileOutputStream, the CONSTRUCTOR itself throws FileNotFoundException — the OS denies write access, and Java surfaces it through the same exception type used for "doesn't exist." Message text is the only way to distinguish the two causes.
In-Memory I/O

ByteArrayInputStream & ByteArrayOutputStream

Stream I/O without touching disk or network — the source or destination is just a byte array sitting in memory. Useful for testing, buffering data before a real write, or treating in-memory data uniformly with the stream API.

ByteArrayInputStream
  • Wraps an EXISTING byte array as a readable stream source
  • markSupported() returns true — full mark/reset support, unlike FileInputStream
  • Never throws IOException on read — there's no real I/O happening, just array indexing
  • Reading doesn't consume/modify the underlying array — it just moves an internal read pointer
ByteArrayOutputStream
  • Grows its OWN internal byte array as you write — you never provide one
  • Optional constructor arg sets the initial capacity (default 32 bytes), purely a performance hint — it resizes automatically regardless
  • toByteArray() snapshots current contents; toString() converts using the platform default (or specified) charset
  • writeTo(OutputStream) pipes its buffered content into any other stream in one call
ByteArrayInputStream
ByteArrayOutputStream
Common use: unit testing I/O code
byte[] b = {'a', 'b', 'c'};
ByteArrayInputStream bis = new ByteArrayInputStream(b);

System.out.println(bis.markSupported()); // true

int first = bis.read();    // 97 ('a')
bis.mark(0);
bis.read();                // consumes 'b'
bis.reset();               // back to right after 'a'
System.out.println((char) bis.read()); // 'b' again

bos.write('A');
bos.write("BCDE".getBytes());

byte[] result = bos.toByteArray();   // snapshot: [A, B, C, D, E]
String asString = bos.toString();     // "ABCDE" — uses default charset

try (FileOutputStream fos = new FileOutputStream("out.txt")) {
    bos.writeTo(fos); // dumps the whole in-memory buffer straight into a real file stream
}
// Testing a method that reads from an InputStream — no real file needed
public String countLines(InputStream in) throws IOException {

        return String.valueOf(br.lines().count());
    }
}

@Test

    InputStream fake = new ByteArrayInputStream("a\nb\nc\n".getBytes());
    assertEquals("3", countLines(fake)); // no disk I/O anywhere in the test

Performance

Buffered Streams

Every unbuffered read()/write() call on a file or socket stream can trigger an expensive system call. Buffering interposes an in-memory array so most reads/writes touch memory instead of the OS — a difference that can be 10-100x in raw throughput.

How buffering works
  • BufferedInputStream reads a large CHUNK from the underlying stream into an internal array on the first read() call
  • Subsequent read() calls are served from that in-memory array — no syscall — until the buffer is exhausted, then it refills
  • BufferedOutputStream mirrors this: writes accumulate in memory and flush to the underlying stream in one batched syscall once the buffer fills (or on explicit flush()/close())
mark/reset support
  • Buffered streams ADD mark/reset capability that raw FileInputStream/FileOutputStream lack
  • markSupported() returns true for BufferedInputStream and BufferedReader
  • The mark's readLimit parameter matters: if you read past that many bytes without calling reset(), the mark becomes invalid and reset() throws IOException
BufferedInputStream
BufferedOutputStream
BufferedReader — readLine()
// Unbuffered — one syscall PER BYTE if you loop read() naively
try (FileInputStream fis = new FileInputStream("large.dat")) {
    int b;
    while ((b = fis.read()) != -1) { /* slow for large files */ }
}

// Buffered — the FileInputStream is only hit for large chunk reads
try (BufferedInputStream bis =
        new BufferedInputStream(new FileInputStream("large.dat"), 8192)) { // optional buffer size, default 8192
    int b;
    while ((b = bis.read()) != -1) { /* each call is now just an array index bump, mostly */ }
}
try (BufferedOutputStream bos =
        new BufferedOutputStream(new FileOutputStream("out.dat"))) {
    for (int i = 0; i < 100000; i++) {
        bos.write(i % 256); // accumulates in memory, NOT written to disk yet
    }
    // close() (called automatically by try-with-resources) flushes remaining
    // buffered bytes before releasing the file handle
}
// WITHOUT try-with-resources, forgetting flush()/close() can silently lose
// the last partial buffer's worth of data — a classic production bug
try (BufferedReader br = new BufferedReader(new FileReader("data.txt"))) {
    String line;
    while ((line = br.readLine()) != null) { // readLine() ONLY exists on BufferedReader/LineNumberReader,
        System.out.println(line);               // not on the plain Reader base class
    }
}
// readLine() strips the line terminator and returns null at EOF —
// an empty line returns "" (empty string), NOT null — a common trap

// Java 8+ stream-of-lines alternative:
try (Stream<String> lines = Files.lines(Path.of("data.txt"))) {
    lines.filter(l -> !l.isBlank()).forEach(System.out::println);
}
💡 Interview one-liner: "Buffering trades a small amount of memory for a large reduction in system calls — it's a decorator that batches I/O operations rather than changing what data flows through the stream." Always wrap file/network streams in a buffered decorator unless you have a specific reason not to.

Byte ↔ Char

InputStreamReader & OutputStreamWriter — The Bridge Classes

Everything that ultimately touches a disk, socket, or network is byte-based at the OS level. InputStreamReader/OutputStreamWriter are the adapter classes that convert between the byte world and the character world — decoding bytes into chars (or encoding chars into bytes) using a specified charset.

Why they exist
  • A file on disk is just bytes — there's no inherent "this is UTF-8 text" metadata
  • InputStreamReader wraps a byte-based InputStream and decodes its bytes into chars using a Charset
  • OutputStreamWriter does the reverse — encodes chars into bytes for an underlying OutputStream
  • FileReader/FileWriter are just pre-wired convenience subclasses of these two, defaulting to the platform charset (or accepting an explicit one, Java 11+)
Charset matters
  • Always specify the charset explicitly — StandardCharsets.UTF_8 — rather than relying on the platform default
  • Platform default varies by OS/locale — code that "works on my machine" can corrupt text on a server with a different default charset
  • This exact bug (relying on default charset) is a common root cause of "mojibake" / garbled international text in production
The full pipeline: bytes on disk → decoded chars → buffered line reading 
// EXPLICIT charset — the correct, portable way
try (InputStreamReader isr = new InputStreamReader(
        new FileInputStream("data.txt"), StandardCharsets.UTF_8)) {

    char[] buf = new char[1024];
    int n;
    while ((n = isr.read(buf)) != -1) {
        System.out.print(new String(buf, 0, n));
    }
}

// OutputStreamWriter — the reverse direction
try (OutputStreamWriter osw = new OutputStreamWriter(
        new FileOutputStream("out.txt"), StandardCharsets.UTF_8)) {
    osw.write("café — UTF-8 encoded correctly");
}

// FileReader with explicit charset (Java 11+) — equivalent to the InputStreamReader above
try (FileReader fr = new FileReader("data.txt", StandardCharsets.UTF_8)) { /* ... */ }

// Pre-Java-11 FileReader has NO charset parameter — always platform default,
// which is exactly why InputStreamReader was often preferred for portability
⚠️ Interview trap: "What's the difference between FileReader and InputStreamReader?" — FileReader IS an InputStreamReader (it extends it), pre-configured for a File source. The real distinction interviewers want is charset control: historically FileReader offered no way to specify a charset, forcing InputStreamReader(new FileInputStream(...), charset) when portability mattered. Java 11 added charset-aware FileReader constructors, narrowing this gap.
Seek Anywhere

RandomAccessFile

Every stream covered so far is strictly sequential — read forward, or (rarely) mark/reset a limited distance back. RandomAccessFile breaks that model entirely: it maintains a file pointer that can jump to any byte offset, and can both read AND write through the same object.

Key characteristics
  • Does NOT extend InputStream/OutputStream — implements DataInput and DataOutput directly
  • Constructor takes a mode string: "r" (read-only) or "rw" (read+write)
  • Has all the typed read/write methods from DataInputStream/DataOutputStream (readInt(), writeUTF(), etc.)
  • Maintains an internal file pointer that advances after every read/write, and can be repositioned directly
Core methods
  • seek(long pos) — jumps the file pointer to an absolute byte offset
  • getFilePointer() — returns the current offset
  • skipBytes(int n) — advances the pointer by n bytes without reading
  • length() — total file size in bytes; setLength(long) can grow or truncate the file
Basic seek + read/write
Fixed-record-size random access
try (RandomAccessFile rf = new RandomAccessFile("data.bin", "rw")) {

    rf.writeInt(100);
    rf.writeInt(200);
    rf.writeInt(300);              // pointer now at byte 12 (3 ints × 4 bytes)

    rf.seek(0);                    // jump back to the start
    System.out.println(rf.readInt()); // 100

    rf.seek(rf.getFilePointer() + 4); // skip over the 200 entry
    System.out.println(rf.readInt()); // 300

    rf.skipBytes(-8);              // NOTE: skipBytes only supports moving forward per the API contract —
                                    // use seek() for backward movement
}
// Classic RandomAccessFile use case: fixed-size records, jump directly
// to record N without reading everything before it
final int RECORD_SIZE = 20; // bytes per record

try (RandomAccessFile rf = new RandomAccessFile("records.dat", "rw")) {

    void writeRecord(int index, String name, int score) throws IOException {
        rf.seek((long) index * RECORD_SIZE); // jump straight to this record's offset
        rf.writeUTF(name);                   // (simplified — real code pads to a fixed width)
        rf.writeInt(score);
    }

    String readNameAt(int index) throws IOException {
        rf.seek((long) index * RECORD_SIZE);
        return rf.readUTF();
    }
}
// This is how simple fixed-record database/index files work under the hood —
// O(1) access to record N instead of O(N) sequential scanning
💡 Interview one-liner: "RandomAccessFile trades the simplicity of sequential streams for direct positional access — useful when you need to update a specific record in place without rewriting the whole file, like a simple embedded database or a large fixed-format binary file."
Metadata, Not Content

The File Class

java.io.File represents a path in the filesystem and lets you query/manipulate its METADATA — it does not read or write file content itself. Content I/O still goes through a stream/reader/writer constructed from a File (or path string).

Common File usage 
File f = new File("data/records");

if (!f.exists()) {
    f.mkdirs();                     // creates "data" and "records" if either is missing
}

File file = new File(f, "log.txt");   // File(parent, child) — safer than string concatenation for paths
System.out.println(file.getName()); // "log.txt"

    System.out.println(child.getName());
}
⚠️ File is considered legacy — java.nio.file.Path (with the Files utility class) is the modern replacement, offering better error reporting (real exceptions instead of silent boolean-false failures), symbolic link support, and file-attribute views. See the NIO section later in this document.

Convenience Output

PrintStream & PrintWriter

System.out is a PrintStream — the class behind every println() call you've ever written. Its whole purpose is convenience: it converts any Java value to a human-readable String representation and NEVER throws a checked IOException.

PrintStream (byte-based)
  • System.out and System.err are both PrintStream instances
  • Overloaded print()/println() for every primitive type plus Object (via toString())
  • Never throws IOException — instead sets an internal error flag, checkable via checkError()

PrintWriter (character-based)
  • The character-stream equivalent — same convenience methods, wraps a Writer instead of an OutputStream
  • Preferred over PrintStream for text output where proper charset handling matters
  • Adds printf()/format() for formatted output — also available on PrintStream
  • Also swallows IOExceptions internally — check via checkError()

Object Persistence

Object Serialization Fundamentals

Serialization converts an object's in-memory state into a byte stream that can be stored (file, database) or transmitted (network) and later reconstructed via deserialization. This is one of the deepest, most interview-heavy corners of java.io.

Requirements
  • Class must implement Serializable — a MARKER interface with zero methods, purely a compile/runtime flag
  • Every non-transient, non-static field must ALSO be Serializable (or null at write time) — including fields of referenced objects, recursively
  • No constructor is called during deserialization for a Serializable class — the object is built directly from the byte stream, bypassing normal instantiation
What gets excluded automatically
  • static fields — belong to the CLASS, not the instance, so never serialized (they're not object state)
  • transient fields — explicitly opted out by the developer (passwords, caches, non-serializable handles like Threads/Sockets)
  • Transient fields are reset to their type's default value (0, null, false) on deserialization — NOT preserved
Basic write/read
transient & static fields
serialVersionUID
Non-serializable field → error
class Employee implements Serializable {
    private String name;
    private int age;
    Employee(String name, int age) { this.name = name; this.age = age; }
    // getters omitted
}

// Writing (serializing)
try (ObjectOutputStream oos = new ObjectOutputStream(
        new FileOutputStream("employee.ser"))) {
    oos.writeObject(new Employee("Alice", 30));

// Reading (deserializing)

        new FileInputStream("employee.ser"))) {
    Employee e = (Employee) ois.readObject(); // throws ClassNotFoundException + IOException
    System.out.println(e.name + " " + e.age);   // "Alice 30" — no constructor ran, state came straight from the stream
}
class User implements Serializable {
    private String username;
    private transient String password; // deliberately excluded — never persisted or transmitted
    private static int loginAttempts;  // excluded automatically — class-level, not instance state

System.out.println(u2.password); // null — transient fields reset to default, NOT preserved

    private String value;

// java.io.InvalidClassException: local class incompatible: stream classdesc
// serialVersionUID = X, local class serialVersionUID = Y
//
// Declaring it explicitly means YOU control compatibility — bump it only

    private String model;

Beyond the Basics

Custom Serialization & Inheritance Rules

Default serialization works for simple cases, but real interview questions live in the exceptions: custom read/write logic, what happens with inheritance, and the alternative Externalizable contract that hands you full manual control.

Custom writeObject / readObject
  • Declared private void writeObject(ObjectOutputStream out) and private void readObject(ObjectInputStream in) — the JVM finds and calls these via reflection if present, no interface to implement
  • Lets you transform, encrypt, or validate data during (de)serialization — e.g. re-deriving a transient field
  • out.defaultWriteObject() / in.defaultReadObject() handle the normal fields; your custom code runs before/after
Inheritance rules
  • If a superclass is Serializable, ALL subclasses are automatically Serializable too
  • If a superclass is NOT Serializable but the subclass IS, the superclass MUST have an accessible no-arg constructor — it gets called during deserialization to initialize the non-serializable part of the state
  • Superclass fields are only preserved if the superclass itself is Serializable; otherwise they reset to defaults, initialized only via that no-arg constructor

Non-serializable superclass — fails

class Account implements Serializable {
    private String owner;
    private transient String encryptedPin; // custom-handled, not default-serialized

    private void writeObject(ObjectOutputStream out) throws IOException {
        out.defaultWriteObject();               // writes "owner" normally
        out.writeObject(encrypt(encryptedPin));  // custom step for the transient field
    }

    private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
        in.defaultReadObject();                  // restores "owner" normally
        String encrypted = (String) in.readObject();
        encryptedPin = decrypt(encrypted);        // reconstruct the transient field manually
    }

    private String encrypt(String s) { return "enc(" + s + ")"; }
    private String decrypt(String s) { return s.replace("enc(", "").replace(")", ""); }
}

class Report implements Externalizable {
    private String title;
    private int pageCount;

    public Report() {} // PUBLIC no-arg constructor is MANDATORY for Externalizable —
                       // unlike Serializable, the JVM DOES call a real constructor here

    public Report(String title, int pageCount) { this.title = title; this.pageCount = pageCount; }

    @Override
    public void writeExternal(ObjectOutput out) throws IOException {
        out.writeUTF(title);      // YOU write EVERY field — nothing is automatic
        out.writeInt(pageCount);
    }

    @Override
    public void readExternal(ObjectInput in) throws IOException {
        title = in.readUTF();     // YOU read every field, in the exact same order
        pageCount = in.readInt();
    }
}
// Externalizable = full manual control, smaller output (no reflection-based
// field metadata), but far more boilerplate and easier to get wrong

// Lets you "unread" a byte — peek ahead, then push it back if you don't want it yet.
// Classic use: hand-written tokenizers/parsers that need 1-token lookahead
try (PushbackInputStream pis =
        new PushbackInputStream(new ByteArrayInputStream("123+456".getBytes()))) {

    StringBuilder number = new StringBuilder();
    int b;
    while ((b = pis.read()) != -1) {
        if (Character.isDigit(b)) {
            number.append((char) b);
        } else {
            pis.unread(b); // "I read too far" — push this byte back onto the stream
            break;
        }
    }
    System.out.println(number); // "123" — and '+' is still unread, available for the next read()
}

Production Java

Best Practices & Common Pitfalls

The mechanics of any one stream class are rarely where production bugs come from — resource leaks, silent data loss, and encoding mismatches are.

1

Always use try-with-resources

Every class implementing Closeable/AutoCloseable — every stream class covered in this document — should be opened in a try-with-resources block. Manual finally { stream.close(); } is verbose and easy to get subtly wrong (e.g. forgetting a null check if the constructor itself threw).

2

Always wrap raw file/network streams in a buffered decorator

Unbuffered byte-at-a-time I/O against a file or socket is dramatically slower than buffered I/O. Default to BufferedInputStream/BufferedReader/etc. unless you have a specific reason not to (e.g. you're already reading large fixed chunks via DataInputStream against an in-memory ByteArrayInputStream, where buffering adds no value).

3

Always specify charset explicitly for text I/O

Relying on the platform default charset is a portability bug waiting to happen. Use StandardCharsets.UTF_8 (or an explicit charset the format requires) every time you construct an InputStreamReader, OutputStreamWriter, or call String(byte[]) / getBytes().

4

Check bulk-read return values correctly

read(byte[]) may return FEWER bytes than the array length, even mid-stream (not just at EOF) — never assume a single call fills the buffer. Loop until -1, and only use the buffer's [0, bytesRead) range each iteration.

5

Don't serialize what you don't need to

Mark sensitive fields (credentials, cache handles) transient. Always declare an explicit serialVersionUID on any Serializable class you intend to evolve. Prefer modern data formats (JSON, Protobuf) over Java's built-in serialization for anything crossing service or version boundaries — Java serialization is version-fragile and has a well-documented history of deserialization security vulnerabilities.

6

Prefer java.nio.file for path/file operations

Use Files/Path over File for anything beyond the simplest cases — better error reporting, atomic operations, and direct Stream integration.

🚫 Anti-pattern to flag in code review: deserializing data from an untrusted source with ObjectInputStream.readObject(). Java's native deserialization has been the root cause of numerous real-world remote code execution vulnerabilities (a malicious byte stream can trigger arbitrary code during object reconstruction). Never deserialize data you don't fully trust — validate the source, use an allow-list of expected classes, or avoid native Java serialization entirely for external-facing data.

try (BufferedInputStream bis = new BufferedInputStream(

Short-answer FAANG questions

❓ Byte stream vs character stream — when does the distinction actually matter?

  • Byte streams don't understand encoding — reading multi-byte UTF-8 text as raw bytes and truncating mid-character corrupts it
  • Character streams decode/encode via a Charset, always producing valid characters
  • Binary formats (images, serialized objects, ZIPs) have no "characters" — must use byte streams

❓ Why does InputStream.read() return int, not byte?

  • A byte's range is -128 to 127 (signed) or 0-255 unsigned — either way it can't distinguish a real value from an "end of stream" sentinel
  • int has room for 0-255 AND a distinct -1 for EOF, all in one return type
  • Same reasoning applies to Reader.read() returning int for a 0-65535 char range

❓ What design pattern does java.io use, and why?

  • Decorator — FilterInputStream/OutputStream/Reader/Writer wrap another stream of the same type
  • Avoids a combinatorial explosion of classes for every feature combination (buffered+typed+file, etc.)
  • Lets you stack capabilities (buffering, typed reads, encoding) in any order, only paying for what you use

❓ Why does FileInputStream not support mark/reset, but BufferedInputStream does?

  • Supporting reset() requires buffering already-read data somewhere so it can be replayed
  • Raw FileInputStream has no such buffer — it's a thin wrapper over the OS file descriptor
  • BufferedInputStream's whole purpose is holding an in-memory buffer — reset() is a natural extension of that buffer

❓ What's the difference between flush() and close()?

  • flush() pushes any buffered data out immediately, but keeps the stream open for further writes
  • close() flushes AND releases the underlying resource (file handle, socket) — the stream can't be used afterward
  • close() is effectively "flush() + release resources," which is why explicit flush() calls are rarely needed when using try-with-resources

❓ Why are static fields never serialized?

  • Serialization captures INSTANCE state — what makes one object different from another
  • A static field belongs to the class itself, shared by every instance — it isn't "this object's data"
  • Serializing it would also be meaningless on deserialize — which instance's copy would win?

❓ What happens if two subclasses of a Serializable superclass have conflicting field types?

  • Doesn't apply directly — each subclass has its own instance layout; the question usually really means "what if a field's TYPE changes between serialize and deserialize?"
  • Changing a field's type is an INCOMPATIBLE change — deserialization throws InvalidClassException even with a matching serialVersionUID, since the stream format encodes field types
  • Safe evolution: add new fields (default-initialized on old data), never change an existing field's type or remove it if old data must still load

❓ Is Serializable inherited?

  • Yes — if class A implements Serializable, every subclass of A is automatically Serializable too (interfaces are inherited)
  • You cannot "opt out" a subclass from being Serializable once a superclass declares it
  • The reverse isn't automatic: a Serializable subclass of a non-Serializable superclass needs that superclass to have an accessible no-arg constructor

❓ Why can array types and String be serialized without explicitly implementing Serializable?

  • java.lang.String and all array types are treated as implicitly Serializable by the JVM's serialization mechanism
  • This is a special case baked into the serialization spec, not something you can replicate for your own classes

❓ PrintStream vs Writer — why doesn't System.out.println() need a try/catch?

  • PrintStream explicitly overrides the checked-exception-throwing behavior of normal OutputStreams
  • It catches all internal IOExceptions and sets an error flag instead, checkable via checkError()
  • Deliberate design tradeoff: console/log output shouldn't force every calling method to declare "throws IOException"

❓ How would you copy a large file efficiently in Java?

  • Best: Files.copy(source, target) — NIO, can use OS-level optimizations
  • Stream-based: buffered streams + a reused byte[] buffer loop, or InputStream.transferTo(OutputStream) (Java 9+)
  • Avoid: reading the whole file into a byte[]/String first for files that might be large — risks OutOfMemoryError

❓ What's the difference between Reader.read(char[]) and BufferedReader.readLine()?

  • read(char[]) is a low-level bulk fill — returns raw characters, doesn't know or care about line boundaries
  • readLine() is line-aware — strips the line terminator, returns null at EOF, empty string "" for a blank line
  • readLine() only exists on BufferedReader/LineNumberReader, not the base Reader class

Interview Cheatsheet

One-liners for when you're under pressure. Know these cold.

🌊 Byte vs Character streams

  • Byte: InputStream/OutputStream — raw 8-bit, binary data, no encoding awareness
  • Char: Reader/Writer — 16-bit Unicode, charset-aware, for text
  • Bridge: InputStreamReader / OutputStreamWriter convert byte↔char

🎁 Decorator pattern

  • Filter* classes wrap another stream of the same base type
  • Stack capabilities (buffering, typed I/O, encoding) in any combination
  • Close only the OUTERMOST wrapper — close() propagates inward

📖 Core InputStream methods

  • read() → int (0-255), -1 = EOF
  • read(byte[]) → number read, may be < array length even mid-stream
  • mark(limit)/reset() — only if markSupported() is true
  • FileInputStream: markSupported() = false. BufferedInputStream: true

📁 FileInputStream / FileOutputStream

  • Constructors throw FileNotFoundException
  • FileOutputStream default: OVERWRITES. new FileOutputStream(path, true) = append
  • No mark/reset support on either

🚀 Buffered streams

  • Batch syscalls — reads/writes hit an in-memory array first
  • Add mark/reset support that raw file streams lack
  • Default buffer size 8192 bytes unless specified

🗄️ RandomAccessFile

  • Does NOT extend InputStream/OutputStream — implements DataInput/DataOutput
  • Mode: "r" or "rw"; seek(pos), getFilePointer(), skipBytes(n)
  • Enables O(1) access to a specific offset/record

🔢 DataInputStream / DataOutputStream

  • writeInt/readInt, writeUTF/readUTF, etc. — every Java primitive
  • NO type tagging in the format — reader must know the exact schema and order
  • Reading the wrong type/order gives silently WRONG data, not an exception

🖨️ PrintStream / PrintWriter

  • System.out/System.err ARE PrintStreams
  • NEVER throw IOException — check via checkError() instead
  • PrintWriter often needs an explicit flush() — not always auto-flushing

📦 Serialization essentials

  • Serializable = marker interface, no methods
  • static fields: never serialized. transient fields: excluded, reset to default
  • NO constructor runs on deserialize (Serializable) — bypasses normal instantiation
  • Always declare explicit serialVersionUID

🏗️ Serialization + inheritance

  • Superclass Serializable → all subclasses automatically Serializable
  • Non-Serializable superclass needs an accessible no-arg constructor, or deserialize throws InvalidClassException
  • Non-Serializable superclass fields reset via that constructor, NOT preserved

⚙️ Externalizable vs Serializable

  • Externalizable: full manual control (writeExternal/readExternal), needs PUBLIC no-arg constructor, JVM calls it
  • Serializable: automatic via reflection, no constructor called at all
  • Externalizable is faster (no reflection) but far more boilerplate

🆕 java.nio.file (modern API)

  • Path.of() replaces new File()
  • Files.readAllBytes/readAllLines/lines/write — no manual buffer management
  • Throws real exceptions instead of File's silent boolean failures

🚨 Top interview traps

  • Checking read(byte[]) against 0 instead of -1 for EOF
  • Closing an inner stream while an outer wrapper still references it
  • Relying on platform-default charset instead of specifying UTF-8 explicitly
  • Assuming reset() always works if you've read past the declared readLimit
  • Forgetting a field must be Serializable transitively, or marked transient
  • Deserializing untrusted data — a known RCE attack surface
