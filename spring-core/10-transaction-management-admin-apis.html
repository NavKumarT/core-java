@Transactional Demystified — How Spring Really Manages Transactions

Video: @Transactional Demystified - How Spring Really Manages Transactions

Section 4 first introduced @Transactional and its self-invocation limitation; Section 8 explained AOP in full generality and used @Transactional as the worked example of how Spring's own annotations are built. This topic finally delivers the complete, precise mechanics.

@Service ┌──────────────────┐ │ OrderService │ ← the RAW bean, as you wrote it │ @Transactional │ │ createOrder(...) │ └──────────────────┘ │ wrapped at startup by Spring's TransactionInterceptor (an AOP advice, exactly per Section 8's Fundamentals topic) │ ▼ ┌──────────────────┐ │ PROXY │ ← what's ACTUALLY injected everywhere │ │ this bean is used │ 1. begin transaction (via PlatformTransactionManager) │ 2. call the REAL createOrder() (the join point) │ 3a. method returns normally → COMMIT │ 3b. method throws unchecked exception → ROLLBACK └──────────────────┘ Caller (e.g. a Controller) → talks to the PROXY, not the raw bean directly
ComponentRole
@TransactionalThe marker annotation — pure metadata, does nothing by itself
TransactionInterceptorSpring's built-in AOP advice (conceptually an @Around advice, per Section 8) that does the actual begin/commit/rollback work around the annotated method
PlatformTransactionManagerThe abstraction that actually talks to the underlying resource (JDBC connection, JPA EntityManager) to begin/commit/roll back — DataSourceTransactionManager or JpaTransactionManager depending on setup
The proxy (CGLIB or JDK dynamic proxy)What's actually wired into the Spring context and injected into other beans — the exact same proxying mechanism from Section 1 (@Configuration) and Section 8 (AOP generally)
💡 Stating This Precisely in an Interview

"@Transactional is not magic — it's a specific, built-in application of Spring AOP. At startup, any bean containing a @Transactional method gets wrapped in a proxy. The proxy's advice — TransactionInterceptor — begins a transaction before the real method runs, and commits or rolls back after, based on how the method completes. Every consequence and limitation of @Transactional (self-invocation not working, needing a public method, needing the call to go through the proxy) follows directly from this being proxy-based AOP — the exact mechanism explained generically in Section 8."

⚠ @Transactional on a private or self-invoked method silently does nothing

Both failure modes trace to the same root cause established in Section 8: proxies work by wrapping/subclassing a bean and intercepting calls that go through the proxy. A private method can never be overridden by a CGLIB subclass proxy at all — the annotation is silently ignored, no error. A call from within the same class (this.someTransactionalMethod()) bypasses the proxy entirely, going directly through the real object reference — again, the transactional behavior silently doesn't apply. Both are structural consequences of proxy-based AOP, not bugs in your code that are easy to spot by reading it.

FAANGIf @Transactional is AOP-based like Section 8's custom aspects, why does it feel so much more "built-in" and automatic than a custom @LogExecutionTime aspect?

Purely because Spring Boot's auto-configuration (Section 3's philosophy applied here) automatically registers the TransactionInterceptor/PlatformTransactionManager infrastructure and enables @Transactional processing (via @EnableTransactionManagement, implicitly activated by Spring Boot's JPA/JDBC starters) the moment a DataSource is detected on the classpath — you never had to write @Aspect/@Around code yourself, unlike the custom aspects built by hand in Section 8. Mechanically, though, it is exactly the same category of thing: a marker annotation plus a pre-built aspect that Spring ships and wires up for you automatically, rather than one you write from scratch.

Hands-On — Using @Transactional in a Production-Style Backend

Video: Hands-On - Using @Transactional in a Production-Style Backend
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final InventoryRepository inventoryRepository;
    private final PaymentService paymentService;

    @Transactional
    public Order placeOrder(OrderRequest request) {
        // THREE separate write operations, spanning TWO different tables —
        // @Transactional guarantees ALL succeed together or NONE do
        Order order = orderRepository.save(new Order(request));
        inventoryRepository.decrementStock(request.getProductId(), request.getQuantity());
        paymentService.chargeCustomer(request.getPaymentDetails());  // if THIS throws, the
                                                                      // order save AND stock decrement above are BOTH rolled back
        return order;
    }
}
💡 What "Atomicity" Actually Buys You Here, Concretely

Without @Transactional, if chargeCustomer() throws (e.g., the payment gateway is down), the order row and the decremented stock count from the earlier two lines would already be permanently committed to the database — leaving the system in a corrupted state: stock reduced and an order recorded, despite the customer never actually being charged. @Transactional guarantees these three operations behave as a single atomic unit — either every statement's effect is committed, or (on any unchecked exception) every statement's effect is rolled back as if none of them ever ran, leaving the database in its original, consistent state.

Optimizing Database Reads with @Transactional(readOnly = true)

Video: Optimizing Database Reads with @Transactional(readOnly = true)
@Transactional(readOnly = true)
public List<OrderResponseDto> getOrderHistory(Long userId) {
    return orderRepository.findByUserId(userId).stream()
            .map(orderMapper::toDto)
            .toList();
    // this method NEVER writes — readOnly=true tells Hibernate/the driver
    // that upfront, unlocking real optimizations
}
OptimizationMechanism
Hibernate flush modeDisables automatic dirty-checking flushes (Section 4's persistence-context mechanism) since no entity state changes are expected to need flushing — saves the overhead of Hibernate comparing entity snapshots to detect changes
Database-level read-only hintSome JDBC drivers/databases can route a read-only-flagged connection differently — e.g., to a read replica in a primary/replica database architecture, offloading read traffic away from the primary write database entirely
No transaction log overheadSome databases can skip undo/rollback-log bookkeeping for a connection explicitly marked read-only, since there's nothing to potentially need rolling back
⚠ readOnly = true Is a Hint, Not a Hard Enforcement Guarantee

Marking a method readOnly = true does not actually prevent a write statement from executing if one is accidentally present in the method body — most JPA providers/drivers treat it purely as a performance optimization hint, not a database-level enforced constraint (behavior can vary by driver/database, but it should never be relied upon as a safety mechanism). It is a performance annotation, not a correctness/safety one — always still write correct code that doesn't call a repository's write methods inside a method you've marked read-only, rather than relying on the flag to catch that mistake.

FAANGIn a system with a primary/replica database setup, how does readOnly=true concretely help route traffic, and what has to be configured for that to actually work?

readOnly = true alone doesn't automatically route to a replica — it needs to be paired with an actual routing DataSource configuration (e.g., Spring's AbstractRoutingDataSource, or a database driver/proxy purpose-built for primary/replica routing) that inspects the current transaction's read-only flag and picks the replica connection pool for read-only transactions versus the primary connection pool for read-write ones. Without that routing infrastructure wired up, readOnly = true only delivers the Hibernate-level flush-mode optimization — the replica-routing benefit is a separate, additional piece of infrastructure this annotation merely provides the signal for, not something it accomplishes by itself.

Why @Modifying Is Mandatory for Update/Delete Queries

Video: Why @Modifying Is Mandatory for Update/Delete Queries

This extends Section 7's brief mention of @Modifying into full explanation, now that transaction mechanics have been covered in depth.

@Query("UPDATE Job j SET j.status = :status WHERE j.id = :id")
int updateStatus(@Param("id") Long id, @Param("status") String status);
// throws InvalidDataAccessApiUsageException at runtime — Spring Data JPA, by
// default, assumes every @Query is a SELECT and tries to execute it that way
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("UPDATE Job j SET j.status = :status WHERE j.id = :id")
int updateStatus(@Param("id") Long id, @Param("status") String status);
// returns the number of rows affected — the standard bulk-update return type
AttributePurpose
@Modifying (bare)Tells Spring Data JPA this @Query is a data-changing operation — executes via Query.executeUpdate() instead of a result-set-returning execution
clearAutomatically = trueClears the persistence context after the bulk update — necessary because a bulk UPDATE/DELETE bypasses the persistence context entirely (Section 7), so any already-loaded entities in memory would otherwise silently hold stale data
flushAutomatically = trueForces any pending changes already in the persistence context to flush to the database before the bulk operation executes, avoiding ordering inconsistencies between pending entity-level changes and the bulk statement
⚠ The Stale-Data Trap This Directly Connects To

This is the exact mechanism behind the stale-data warning already flagged in Section 7's @Modifying Q&A: a bulk UPDATE query operates directly against the database, entirely bypassing Hibernate's persistence-context/first-level cache (Section 4). If code elsewhere in the same transaction already loaded a Job entity into the persistence context before the bulk update runs, that in-memory entity's fields are now silently out of sync with the database — clearAutomatically = true is the direct fix, forcing Hibernate to discard its now-stale cached entities so any subsequent read within the same transaction re-fetches fresh data from the database rather than returning outdated in-memory state.

FAANGWhy does a bulk @Modifying update bypass entity lifecycle callbacks like @PreUpdate and JPA auditing's @LastModifiedDate (Section 5)?

JPA lifecycle callbacks (@PrePersist, @PreUpdate, and by extension Section 5's AuditingEntityListener, which hooks into exactly those callbacks) only fire when Hibernate manages an entity's state transition through its normal, tracked lifecycle — loading an entity, modifying a field, and letting dirty-checking generate an UPDATE at flush time. A @Modifying bulk query is a direct SQL statement issued straight to the database, entirely outside that entity-lifecycle machinery — no entity is ever loaded, modified, or dirty-checked in the normal sense, so there's no lifecycle event for any listener to hook into. This is a real, easy-to-miss consequence: a bulk status update via @Modifying will not automatically update updatedAt/updatedBy auditing fields the way an entity-level save() would, unless the JPQL update statement explicitly sets those fields itself.

Rollback Rules in Spring — Checked vs Runtime Exceptions

Video: Rollback Rules in Spring - Checked vs Runtime Exceptions

Spring's default rollback policy is precise and frequently misunderstood: a transaction rolls back automatically on any unchecked (RuntimeException or Error) exception, but NOT on a checked exception — this default is the exact opposite of what many developers coming from plain JDBC/try-catch backgrounds intuitively expect.

Exception thrown inside a @Transactional method │ ▼ Is it a checked exception (extends Exception, not RuntimeException)? │ ┌────┴────┐ YES NO (it's a RuntimeException or Error) │ │ ▼ ▼ COMMITS ROLLS BACK anyway! ⚠️ (the default, expected behavior)
@Transactional
public void processPayment(PaymentRequest request) throws PaymentGatewayException {
    orderRepository.save(new Order(request));

    if (!paymentGateway.charge(request)) {
        throw new PaymentGatewayException("Payment failed");
        // IF PaymentGatewayException extends Exception (checked) — Spring's DEFAULT
        // behavior COMMITS the order save above anyway! The order is now recorded
        // despite the payment having failed — a genuine, serious production bug
    }
}
@Transactional(rollbackFor = PaymentGatewayException.class)   // explicit override — now rolls back correctly
public void processPayment(PaymentRequest request) throws PaymentGatewayException {
    orderRepository.save(new Order(request));
    if (!paymentGateway.charge(request)) {
        throw new PaymentGatewayException("Payment failed");   // now correctly rolls back
    }
}

// the inverse also exists, for the rare case you want a RuntimeException NOT to roll back:
@Transactional(noRollbackFor = SomeRecoverableRuntimeException.class)
💡 Why Spring Chose This Default — The Historical/Design Rationale

This traces back to a design philosophy from early J2EE-era EJB conventions that Spring inherited: checked exceptions were originally conceived as representing expected, recoverable business conditions the caller is meant to explicitly handle (the compiler forces you to catch or declare them) — the framework's assumption being that if you're throwing a checked exception, you've presumably already handled the "should this be a database rollback" decision at a business level. Unchecked/runtime exceptions were conceived as representing unexpected, programming-error-like failures where automatic rollback is the safe default. In practice, most modern Spring codebases prefer unchecked exceptions almost universally for exactly this reason — it sidesteps the entire "did I remember to add rollbackFor" trap by making rollback-on-exception the automatic, default-safe behavior for virtually everything thrown.

⚠ This Is One of the Single Most Common Real Production Bugs Involving @Transactional

A developer defines a custom checked exception (perhaps out of habit, or to force callers to explicitly handle a business exception via the compiler), throws it from inside a @Transactional method expecting normal rollback behavior, and is genuinely surprised in production when partial, inconsistent data ends up committed. The fix is either: (1) make custom business exceptions extend RuntimeException instead of Exception — the overwhelmingly preferred modern convention — or (2) explicitly declare rollbackFor if a checked exception type is unavoidable (e.g., required by an external library's API). Interviewers frequently ask this exact scenario specifically because it's such a realistic, high-impact gotcha.

FAANGDoes Spring roll back on an Error (like OutOfMemoryError), and why does that matter?

Yes — Spring's default rollback rule is actually "roll back on any unchecked Throwable," which includes both RuntimeException and Error (both are unchecked; only Exception and its non-RuntimeException subclasses are checked). This matters because a serious JVM-level failure like OutOfMemoryError mid-transaction should absolutely trigger a rollback rather than risk committing a half-completed, inconsistent set of database changes — the default correctly treats catastrophic JVM errors the same as ordinary unchecked application exceptions for rollback purposes, which is the safe, correct behavior for a truly unexpected failure.

Understanding Transaction Propagation Without Confusion

Video: Understanding Transaction Propagation Without Confusion

Propagation answers one specific question: when a @Transactional method calls another @Transactional method, does the inner call join the outer transaction, or start a genuinely separate one?

PropagationBehaviorTypical Use
REQUIRED (default)Joins the existing transaction if one is active; starts a new one if notThe overwhelming default for almost every service method — "just participate in whatever's already happening"
REQUIRES_NEWAlways suspends any existing transaction and starts a genuinely independent new one — the new transaction commits/rolls back entirely on its own, regardless of what happens to the outer transaction afterwardAudit logging that must persist even if the surrounding business operation later fails and rolls back
NESTEDCreates a savepoint within the existing transaction — can roll back to that savepoint independently, but is still fundamentally part of, and bound to, the outer transaction's ultimate commit/rollbackA sub-operation that should be able to fail and be "undone" in isolation without necessarily failing the entire outer operation — less commonly used, and not supported by every transaction manager/database combination
SUPPORTSJoins an existing transaction if one is active; runs non-transactionally if not (no error either way)Rare — a method that can work with or without a surrounding transaction
MANDATORYRequires an existing transaction to already be active; throws an exception if called outside oneEnforcing that a method must never be called except as part of a larger transactional flow
NOT_SUPPORTEDSuspends any existing transaction and runs the method entirely non-transactionallyA read-heavy or long-running operation that should never hold a transaction/lock open
NEVERThrows an exception if called from within an existing transactionExplicitly enforcing a method must only ever run standalone
REQUIRED (default) — the inner call JOINS the outer transaction: @Transactional @Transactional (REQUIRED, default) public void placeOrder() { public void chargeCustomer() { ... ... chargeCustomer(); ──────▶ (throws!) ┌── this exception rolls back │ the ENTIRE combined transaction — (never reached) ◄────────────┘ including placeOrder()'s earlier writes } REQUIRES_NEW — the inner call is GENUINELY INDEPENDENT: @Transactional @Transactional(propagation = REQUIRES_NEW) public void placeOrder() { public void logAuditEntry() { ... ... (its OWN separate transaction) logAuditEntry(); ───────▶ COMMITS independently, right here riskyOperation(); regardless of what happens next (throws!) ┌── } │ the audit log entry SURVIVES even ROLLS BACK ◄─────────────────┘ though placeOrder() itself rolled back
💡 The Single Cleanest Way to Explain REQUIRES_NEW's Value

"REQUIRES_NEW exists specifically for the case where you want an inner operation's outcome to be independent of the outer transaction's fate — the canonical example being audit/compliance logging that must be preserved even if the business operation it's logging ultimately fails and rolls back. Without REQUIRES_NEW, a failed order would also silently erase the audit trail explaining that the order was attempted and why it failed — exactly the evidence you'd want to have preserved."

FAANGWhy does REQUIRES_NEW require suspending the outer transaction, rather than just running two transactions concurrently on the same thread?

A single database connection (and the single thread using it, in Spring's typical synchronous MVC model) can only be bound to one active transaction at a time — a transaction is fundamentally tied to a specific connection's state. To start a genuinely new, independent transaction mid-flow, Spring's transaction manager must first suspend the current transaction (detaching it from the thread/connection, holding its state aside), acquire a separate connection (potentially from the same pool) for the new nested transaction, run it to completion (commit or rollback, entirely independently), and then resume the original suspended transaction on its original connection to continue where it left off. This connection-management overhead is real and worth knowing — REQUIRES_NEW isn't free, and using it excessively can exhaust a connection pool faster than expected under load, since it genuinely requires an additional connection for the nested transaction's duration.

CoreWhat's the practical difference between NESTED and REQUIRES_NEW — they sound similar but aren't?

REQUIRES_NEW creates a completely independent transaction — its commit/rollback has zero effect on the outer transaction's ultimate fate, and vice versa (as shown in the audit-logging example). NESTED instead creates a savepoint within the same outer transaction — the nested portion can roll back to that savepoint on its own (undoing just its own changes) without necessarily failing the whole outer transaction, but if the outer transaction itself ultimately rolls back, the nested portion's changes are rolled back along with it too, since they were never truly independent — the nested savepoint is still fundamentally bound to and dependent on the outer transaction's own commit for its changes to become permanent. NESTED also requires JDBC savepoint support, meaning it isn't available with every transaction manager/database combination, unlike REQUIRES_NEW, which works anywhere ordinary transactions do.

Choosing the Right Isolation Level in Real Applications

Video: Choosing the Right Isolation Level in Real Applications

Isolation answers a different question than propagation: how much can concurrently-running transactions "see" of each other's uncommitted or newly-committed changes? Each isolation level trades consistency guarantees against concurrency/performance.

The Three Classic Concurrency Anomalies, Defined Precisely

AnomalyWhat Happens
Dirty ReadTransaction A reads a row that Transaction B has modified but not yet committed — if B then rolls back, A has read data that never truly existed
Non-Repeatable ReadTransaction A reads the same row twice within one transaction, but Transaction B commits an update to that row in between A's two reads — A gets two different values for what should be a stable read within its own transaction
Phantom ReadTransaction A runs the same range query (e.g., "all orders over $100") twice, but Transaction B commits a new row matching that range in between — A's second query returns an extra "phantom" row that wasn't there the first time
Isolation LevelDirty ReadNon-Repeatable ReadPhantom ReadConcurrency
READ_UNCOMMITTED❌ Possible❌ Possible❌ PossibleHighest — essentially no isolation
READ_COMMITTED✅ Prevented❌ Possible❌ PossibleHigh — most databases' default (PostgreSQL, Oracle, SQL Server)
REPEATABLE_READ✅ Prevented✅ Prevented❌ Possible (varies by DB — MySQL's InnoDB actually also prevents most phantom reads here via gap locking)Medium — MySQL's default
SERIALIZABLE✅ Prevented✅ Prevented✅ PreventedLowest — transactions effectively behave as if executed one at a time, sequentially
@Transactional(isolation = Isolation.SERIALIZABLE)
public void transferFunds(Long fromAccountId, Long toAccountId, BigDecimal amount) {
    // a genuinely high-stakes financial operation where even a rare
    // concurrency anomaly is unacceptable — worth the performance cost
    Account from = accountRepository.findById(fromAccountId).orElseThrow();
    Account to = accountRepository.findById(toAccountId).orElseThrow();
    from.debit(amount);
    to.credit(amount);
}
💡 The Practical Decision Framework

Don't default to SERIALIZABLE "to be safe" — its heavy locking/performance cost is real and unnecessary for the vast majority of operations. The practical approach: (1) leave isolation at the database's own default (READ_COMMITTED for most, which Spring's own default Isolation.DEFAULT simply defers to) for ordinary CRUD operations where occasional non-repeatable/phantom reads genuinely don't matter for correctness, (2) escalate to REPEATABLE_READ or SERIALIZABLE deliberately and narrowly, only for specific operations where a concurrency anomaly would cause genuine business harm — financial transfers, inventory decrements preventing overselling, seat/ticket booking systems — and (3) consider whether optimistic locking (via JPA's @Version field) might solve the same correctness problem with less locking overhead than a blanket isolation-level escalation, since it only blocks/detects conflicts on rows that genuinely experienced concurrent modification, rather than adding locking overhead to every read.

FAANGDesign the concurrency-safety approach for a limited-inventory checkout flow (e.g., only 5 tickets left, many users trying to buy simultaneously) — walk through the trade-offs of your chosen isolation/locking strategy.

The core risk is two concurrent transactions both reading "5 available" before either commits a decrement, both proceeding to sell, resulting in overselling — a classic non-repeatable read-adjacent race condition (technically closer to a lost-update problem). Options, with trade-offs: (1) Pessimistic locking — SELECT ... FOR UPDATE (via JPA's @Lock(LockModeType.PESSIMISTIC_WRITE)) on the inventory row, forcing concurrent transactions to genuinely wait in line — simple to reason about, correctness-guaranteed, but reduces throughput under high contention since transactions serialize on that specific row. (2) Optimistic locking — a @Version field on the inventory entity; concurrent updates detect the version mismatch and one transaction fails with OptimisticLockException, requiring an application-level retry — better throughput under low-to-moderate contention, but adds retry-logic complexity and can itself degrade under very high contention (many wasted, retried attempts). (3) SERIALIZABLE isolation on the whole transaction — correctness-guaranteed but the heaviest-handed, least scalable option. For a real high-traffic ticket-sale scenario, pessimistic locking on the specific hot inventory row (not the whole transaction's isolation level) is usually the pragmatic middle ground — narrow, targeted locking rather than a blanket isolation escalation.

CoreWhy is READ_COMMITTED the default for most production databases rather than something stricter?

It represents the pragmatic sweet spot for the overwhelming majority of application workloads: it eliminates dirty reads (the most dangerous and least defensible anomaly — reading data that was never actually committed and might not even really "exist") while still permitting reasonably high concurrency, since it doesn't hold long-lived locks across an entire transaction's reads the way REPEATABLE_READ/SERIALIZABLE do. Most business operations can tolerate the rarer, more benign possibility of a non-repeatable or phantom read (re-querying mid-transaction and seeing a value change is uncommon and often inconsequential for typical CRUD flows), making the extra locking overhead of stricter isolation levels an unnecessary cost for the common case — exactly why database vendors chose it as a sensible universal default rather than the strictest available option.

Common @Transactional Pitfalls You Must Avoid in Production

Video: Common @Transactional Pitfalls You Must Avoid in Production
PitfallWhy It HappensFix
Self-invocation silently skips the proxyProxy-based AOP (Section 8/174) — calling this.method() bypasses the proxy entirelyCall through a separately-injected self-reference bean, or restructure into two distinct service beans
Checked exception doesn't trigger rollbackSpring's default rollback rule (this section, topic 178)Prefer RuntimeException-derived custom exceptions, or explicit rollbackFor
@Transactional on a private method does nothingCGLIB proxies can't override private methodsAlways make transactional methods public

Swallowing an exception inside the method, defeating rollbackA try/catch inside the transactional method that catches and logs an exception without re-throwing it means the method returns normally from the proxy's perspective — no rollback occurs, even though something clearly went wrongOnly catch exceptions you're genuinely handling (recovering from); let genuine failures propagate so the transaction rolls back correctly
⚠ The Silently-Swallowed-Exception Pitfall Deserves Special Attention

This is subtler and more dangerous than it first appears: a developer adds a try/catch around a risky operation purely to log the error for observability, intending the surrounding transaction to still fail — but since the method then returns normally (no exception propagates out to the proxy), TransactionInterceptor sees a normal return and commits, exactly as if nothing went wrong. The fix requires either re-throwing after logging (catch (Exception ex) { log.error(...); throw ex; }) or explicitly forcing a rollback via TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() if you genuinely need to catch-and-suppress the exception at that point while still ensuring rollback.

FAANGWhy is a @Transactional method making a slow external HTTP call (e.g., to a payment gateway) a real production risk, beyond just "it's slow"?

A @Transactional method holds a database connection checked out from the connection pool for its entire duration — including time spent waiting on a slow, unrelated external HTTP call that has nothing to do with the database at all. Under load, this means database connections sit idle-but-checked-out for however long the external call takes, rapidly exhausting a finite connection pool and causing unrelated requests to fail or queue waiting for a connection — a slow third-party API can cascade into an apparent "database is down" incident, when the actual root cause is connection-pool starvation caused by holding transactions open across slow I/O that should never have been inside the transactional boundary in the first place. The fix is architectural: perform the external call before or after the transactional boundary, only wrapping the actual database operations in @Transactional.

Building & Demoing Company Management Features for Admin Users

An applied capstone bringing together this section's transaction concepts with earlier sections' authorization (Section 9) and JPA relationship mapping (Section 5) — full CRUD admin endpoints for managing Company entities, gated behind hasRole("ADMIN")/appropriate @PreAuthorize authorities.

@RestController
@RequestMapping("/api/v1/admin/companies")
@PreAuthorize("hasRole('ADMIN')")   // Section 9's coarse role gate, applied at the class level
@RequiredArgsConstructor
public class CompanyAdminController {

    private final CompanyService companyService;

    @PostMapping
    public ResponseEntity<CompanyResponseDto> create(@Valid @RequestBody CompanyRequestDto dto) {
        return ResponseEntity.status(HttpStatus.CREATED).body(companyService.create(dto));
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        companyService.delete(id);   // internally @Transactional — cascades to Jobs per Section 5's mapping
        return ResponseEntity.noContent().build();
    }
}

@Service
@RequiredArgsConstructor
public class CompanyService {

    @Transactional   // this section's mechanics — deleting a company + its jobs is ATOMIC
    public void delete(Long id) {
        Company company = companyRepository.findById(id)
                .orElseThrow(() -> new ResourceNotFoundException("Company not found"));
        companyRepository.delete(company);   // CascadeType.ALL from Section 5 handles the Jobs
    }

    @Transactional(readOnly = true)   // this section's read optimization
    public Page<CompanyResponseDto> list(Pageable pageable) {   // Section 9's pagination
        return companyRepository.findAll(pageable).map(companyMapper::toDto);
    }
}

This single controller/service pair exercises: role-based authorization (Section 9), DTO validation and mapping (Sections 4–5), global exception handling for not-found (Section 5), cascading deletes (Section 5), pagination (Section 9), and — the specific new material this section adds — deliberate, correct use of @Transactional (default for the atomic delete) versus @Transactional(readOnly = true) (for the pure-read listing), applied with actual understanding of why each choice is correct rather than copy-pasted habit.

🎯 Rapid-Fire Round

Master Interview Q&A Bank — Section 10

Transaction management is consistently one of the highest-signal topics in senior backend interviews — these questions probe whether a candidate has genuinely internalized the mechanics or just the annotation syntax.

FAANGWalk through, in complete detail, what happens when method A (REQUIRED) calls method B (REQUIRED) which calls method C (REQUIRES_NEW), and C throws an exception that B catches and swallows without re-throwing.

A starts a new transaction (call it T1, since none exists yet). B is called and joins T1 (REQUIRED, existing transaction present). B calls C; because C is REQUIRES_NEW, Spring suspends T1 and starts an entirely independent T2 for C. C throws — assuming an unchecked exception, T2 rolls back and the exception propagates back out of C's call. B catches this exception and does not re-throw it — from the proxy's perspective, B's method then returns normally. Because B returns normally, T1 (still active, now resumed) proceeds to commit when A's method also completes normally — including any writes A or B made before/after the call to C. Net result: whatever C attempted is correctly rolled back (T2's own rollback), but A and B's changes commit as if nothing went wrong, and — critically — nothing signals to A's caller that C's operation actually failed, unless B explicitly surfaces that failure some other way (a return value, re-throwing a different exception, etc.). This scenario combines topics 178, 179, and 181 into one complete trace.

FAANGDesign the transaction and isolation strategy for a bank's fund-transfer system end to end — propagation, isolation, rollback rules, and how you'd prevent double-spending under concurrent requests.

The core transfer operation uses default REQUIRED propagation (it should always run within a single atomic unit — debit and credit must succeed or fail together, the canonical @Transactional atomicity case from topic 175). All business/validation exceptions extend RuntimeException specifically to get automatic rollback without needing to remember rollbackFor everywhere (topic 178's lesson). For the double-spend concern specifically — two concurrent transfer requests debiting the same account simultaneously — pessimistic row-level locking (SELECT ... FOR UPDATE) on the account balance row during the debit is the most defensible, easiest-to-reason-about choice for genuinely high-stakes financial correctness, rather than relying purely on isolation level (topic 180's discussion of pessimistic vs optimistic locking, applied to the exact scenario this topic set up). A separate audit-log entry recording every attempted transfer (successful or failed) is written via REQUIRES_NEW specifically so the audit trail survives even when the underlying transfer itself rolls back — directly reusing topic 179's audit-logging justification for that propagation type. This synthesizes essentially every mechanism covered in this section into one coherent, realistic system design answer.

CoreIs it true that @Transactional guarantees "ACID" properties — what exactly does the annotation provide versus what the underlying database provides?

@Transactional itself is purely an orchestration mechanism — it tells Spring when to begin, commit, or roll back a transaction boundary around your Java method calls. The actual ACID guarantees (Atomicity, Consistency, Isolation, Durability) are provided by the underlying database engine itself once that begin/commit/rollback sequence is correctly issued — Spring doesn't implement transaction semantics from scratch; it delegates to the database's native transaction support via JDBC/the PlatformTransactionManager abstraction. This is a subtle but important distinction: writing @Transactional incorrectly (e.g., missing rollbackFor for a checked exception) doesn't mean "ACID is broken" — it means Spring simply never told the database to roll back at all, and the database faithfully committed exactly what it was told to, exactly as ACID-compliant behavior would predict.

FAANGWhy can't @Transactional alone solve a distributed transaction problem — e.g., updating your own database AND calling an external microservice's API that also needs to "commit" atomically together?

@Transactional (via PlatformTransactionManager) manages a transaction against one specific transactional resource — typically one database connection. An external microservice call over HTTP is not a transactional resource in this sense at all — there's no way to "roll back" an HTTP call that already succeeded on the other side simply because your own local database transaction later fails, and no way for the remote service to participate in your local commit/rollback decision. This is precisely the class of problem that motivates patterns like the Saga pattern (a sequence of local transactions, each with a corresponding compensating action to "undo" it if a later step fails) or genuine distributed-transaction protocols (two-phase commit, rarely used in modern microservices due to their tight-coupling and availability costs) — @Transactional's guarantees stop firmly at the boundary of a single transactional resource, and understanding that boundary precisely is exactly what separates a monolith-only understanding of transactions from a microservices-aware one.

CoreYou inherited a codebase where every single service method is annotated @Transactional, including pure getters that never write anything. What would you change and why?

Every genuinely read-only method should be changed to @Transactional(readOnly = true) at minimum (topic 176's optimization — free performance with no downside for methods that truly never write), and it's worth questioning whether some of those read methods need @Transactional at all if they're simple single-query reads that don't need a consistent multi-statement view of the data (a single JPA repository call is often already implicitly transactional at the JDBC/Hibernate level without needing an explicit annotation, depending on configuration) — blanket-applying @Transactional everywhere "just in case" adds unnecessary proxy overhead and obscures which methods actually have meaningful atomicity requirements versus which don't, making the codebase harder to reason about for anyone auditing where genuine multi-statement atomicity guarantees are actually needed.
