Actuator is Spring Boot's built-in production-readiness toolkit — a set of HTTP endpoints (under /actuator/* by default) exposing the internal state of a running application: health, metrics, configuration, active beans, and more, all without writing a single line of custom monitoring code.

💡 Why This Matters Beyond "It's Convenient"

In any real deployment — a Kubernetes cluster, a load balancer, a CI/CD pipeline — something external needs a reliable, standardized way to answer "is this instance actually healthy and ready to receive traffic?" without guessing. Actuator's /actuator/health endpoint is precisely that standardized signal, and its presence (or absence) is one of the clearest practical differentiators between a toy application and a genuinely production-operable one — which is exactly why this topic sits in a course section explicitly building toward production readiness.

Health Checks Made Easy with Spring Boot Actuator

Video: Health Checks Made Easy with Spring Boot Actuator
{
  "status": "UP",
  "components": {
    "db": { "status": "UP", "details": { "database": "MySQL" } },
    "diskSpace": { "status": "UP", "details": { "free": 42800000000 } },
    "ping": { "status": "UP" }
  }
}
// Actuator auto-detects relevant HealthIndicators based on what's on the
// classpath (a DataSource present -> automatic DB connectivity check —
// the SAME conditional auto-configuration philosophy as Section 3)
@Component
public class PaymentGatewayHealthIndicator implements HealthIndicator {

    @Override
    public Health health() {
        try {
            boolean reachable = paymentGatewayClient.ping();
            return reachable
                ? Health.up().withDetail("gateway", "Stripe").build()
                : Health.down().withDetail("reason", "unreachable").build();
        } catch (Exception ex) {
            return Health.down(ex).build();
        }
    }
}
// now appears automatically as another component under /actuator/health,
// aggregated into the overall UP/DOWN status alongside the built-in ones
ConceptExplanation
Aggregate statusThe top-level status is computed from every individual HealthIndicator — if any component reports DOWN, the overall application status is DOWN, by default (this aggregation strategy is itself configurable)
Liveness vs ReadinessKubernetes-aware Actuator distinguishes /actuator/health/liveness ("is the process alive and not deadlocked — should it be restarted if not?") from /actuator/health/readiness ("is it ready to receive traffic right now — should the load balancer route to it?") — two genuinely different questions Kubernetes probes separately
⚠ Liveness vs Readiness Is a Frequently-Tested, Precise Distinction

Conflating these is a real production risk: a liveness probe failure tells Kubernetes "this process is broken — kill and restart the container." A readiness probe failure tells Kubernetes "this instance is temporarily not able to serve traffic — stop routing to it, but don't restart it" (e.g., during a slow startup warming a cache, or a temporary downstream dependency outage the instance can recover from once the dependency returns). Wiring a downstream dependency's health (like the payment gateway example above) into the liveness probe by mistake would cause Kubernetes to repeatedly restart a perfectly healthy application instance every time an unrelated third-party service has a brief outage — a classic, avoidable self-inflicted incident.

FAANGDesign the liveness and readiness probe strategy for a Spring Boot service with a database dependency and a downstream third-party API dependency.

Liveness should check only whether the application's own internal state is fundamentally healthy — the JVM is responsive, no deadlock, core internal components initialized correctly — deliberately excluding external dependency checks, since a liveness failure triggers a restart, and restarting won't fix a downstream outage (it would just cause unnecessary restart churn while the real problem persists elsewhere). Readiness should include the database connectivity check (the app genuinely cannot serve most requests without it) and, more debatably, the third-party API check — often configured as a degraded but still ready state if the third-party dependency is used by only a subset of endpoints (the app can still serve everything else), rather than marking the whole instance not-ready over one non-critical downstream dependency being temporarily unavailable. This distinction — what belongs in liveness vs readiness — is exactly the kind of precise, practical Kubernetes-operations judgment that separates surface-level Actuator knowledge from real production experience.

Peeking Inside Spring — Beans, Config & Environment with Actuator

Video: Peeking Inside Spring - Beans, Config & Environment with Actuator
EndpointExposesConnects To
/actuator/beansEvery bean currently registered in the ApplicationContext, with its type and dependenciesMakes Section 1–2's abstract IoC container/bean concepts directly, visibly inspectable at runtime — genuinely useful for debugging an unexpected bean-wiring issue
/actuator/configpropsEvery bound @ConfigurationProperties object and its current resolved valuesDirectly visualizes Section 11's @ConfigurationProperties topic — confirms exactly what values actually got bound in this running instance

⚠ These Endpoints Can Leak Sensitive Data — Must Never Be Publicly Exposed Unauthenticated

/actuator/env and /actuator/configprops can reveal database passwords, API keys, and other secrets bound from environment variables (Section 11) — Actuator automatically applies sanitization to common sensitive-sounding key patterns (masking values for keys containing password, secret, token, etc., by default), but this pattern-matching is not foolproof for custom, non-obviously-named secret properties. In any real deployment, these management endpoints must be secured — either via Spring Security rules restricting /actuator/** to admin roles only (Section 9's authorization patterns), or by exposing Actuator on a separate management port not reachable from the public internet at all (a common, more robust production pattern, configurable via management.server.port).

CoreBy default, are all these endpoints even reachable over HTTP without extra configuration?

No — Spring Boot Actuator exposes only /actuator/health and /actuator/info over HTTP by default; every other endpoint (beans, env, configprops, metrics, etc.) must be explicitly opted into via management.endpoints.web.exposure.include=health,info,beans,env,metrics (or =* for everything, generally discouraged in production) in configuration. This "closed by default, opened deliberately" posture directly mirrors Spring Security's own default philosophy from Section 6 — a sensible, security-conscious default that requires an explicit, auditable decision to expose anything beyond the two safest, least-sensitive endpoints.

It's a lightweight, live, ground-truth verification of "the API surface this build actually exposes matches what we expect," distinct from and complementary to functional endpoint testing.

Powerful Actuator Use Cases — Shutdown, Cache & Log Control

Video: Powerful Actuator Use Cases - Shutdown, Cache & Log Control
# management.endpoint.shutdown.enabled=true  (OFF by default — must opt in)
curl -X POST http://localhost:8080/actuator/shutdown
// triggers a GRACEFUL application shutdown — letting in-flight requests
// complete and resources (DB connections, etc.) close cleanly, rather
// than an abrupt kill -9
# GET /actuator/caches — lists every registered cache region (Section 11's
# "companies", "jobs" Caffeine caches) and their current entry counts

# DELETE /actuator/caches/companies — evicts an ENTIRE cache region ON DEMAND,
# without waiting for TTL expiry (Section 11) or writing a one-off @CacheEvict
# endpoint just for this operational need
curl -X DELETE http://localhost:8080/actuator/caches/companies
⚠ The Shutdown Endpoint Is Disabled by Default for an Obvious Reason

An exposed, unauthenticated /actuator/shutdown endpoint would let literally anyone who can reach it remotely terminate the application on demand — a trivial, catastrophic denial-of-service vector. It requires an explicit opt-in (management.endpoint.shutdown.enabled=true) precisely because of this risk, and in any real deployment must additionally be locked down behind authentication/authorization (or, more commonly, simply left disabled entirely and relying on the orchestration platform's own shutdown mechanisms — e.g., Kubernetes sending SIGTERM directly to the container — rather than exposing an HTTP-triggered shutdown at all).

FAANGWhy is the ability to evict a specific cache region on demand via Actuator genuinely valuable in production, beyond just "it's convenient"?

It provides an operational escape hatch for exactly the scenario Section 11's TTL discussion flagged as a real risk: data changed outside the application's own code paths (a direct database edit, a data-fix script, another service writing to a shared table) that @CachePut/@CacheEvict have no way to know about and TTL would only eventually self-correct. Rather than waiting out the TTL window or restarting the entire application (losing the whole cache's warm state, not just the affected entries) just to clear one specific stale cache region, an on-call engineer can surgically evict exactly the affected region via a single authenticated API call — a genuinely practical incident-response tool directly connecting back to the caching correctness concerns raised in the previous section.

Introduction to Observability and OpenTelemetry

Video: Introduction to Observability and OpenTelemetry

Observability is the ability to understand a system's internal state purely from its external outputs — traditionally decomposed into three complementary pillars, each already touched on separately across this course:

PillarAnswersAlready Covered In
Logs"What specifically happened, in detail, at this point in time?"Section 8 — SLF4J/Logback
Metrics"How is the system performing, in aggregate, over time?" (request rate, error rate, latency percentiles)This section's Actuator topics
Traces"What was the full journey of this one specific request as it moved through multiple services/components?"New in this section — the missing third pillar
💡 Why Tracing Specifically Matters in a Microservices World

Logs and metrics answer questions about one service in isolation reasonably well — but in a microservices architecture (which Section 10's Saga-pattern discussion already gestured toward), a single user-facing request might fan out across five different services. When that request is slow or fails, "which of those five services, specifically, was the actual bottleneck or point of failure?" is a question logs and metrics alone cannot answer — each service's logs are isolated, with no inherent way to correlate "this log line in Service A" with "this log line in Service C" as belonging to the same originating request. Distributed tracing exists specifically to solve this: a single trace ID threads through every service a request touches, letting you reconstruct the complete, ordered, cross-service journey of one specific request after the fact.

OpenTelemetry (OTEL) is a vendor-neutral, industry-standard specification and toolset (APIs, SDKs, and a common wire protocol) for generating and exporting exactly these three pillars in a consistent, portable way — instrument your code once against OpenTelemetry's API, and freely swap the backend that actually stores/visualizes the resulting data (Jaeger, Zipkin, Datadog, Grafana, many others) without re-instrumenting anything.

FAANGWhy does OpenTelemetry's vendor-neutrality matter practically, rather than just picking one vendor's proprietary instrumentation SDK directly?

This mirrors precisely the SLF4J-vs-Logback facade/implementation relationship from Section 8, applied to the whole observability domain: instrumenting application code directly against a specific vendor's proprietary SDK (e.g., a specific APM vendor's agent) creates lock-in — migrating to a different observability backend later means re-instrumenting the entire codebase. Instrumenting against OpenTelemetry's vendor-neutral API instead means the backend (where traces/metrics/logs are actually shipped and visualized) becomes a swappable configuration/infrastructure decision, not a pervasive code-level dependency — directly reducing vendor lock-in risk, a real and commonly-cited factor in enterprise observability-tooling decisions.

💡 The Layering, Stated Precisely for an Interview

"Micrometer is the facade my Spring Boot code interacts with directly — I never call OpenTelemetry's API myself. This mirrors, almost annotation-for-annotation, the JPA/Hibernate/Spring-Data-JPA three-layer relationship from Section 4.

CoreIf Micrometer already powered Actuator's /metrics endpoint before OpenTelemetry entered the picture, what specifically does adding OTEL/OTLP contribute?

Micrometer alone (pre-OTEL integration) handled metrics well but had no standardized, vendor-neutral mechanism for distributed tracing across services, nor a universal wire protocol for shipping that data anywhere. Micrometer Tracing is the newer bridge layer that lets Micrometer's existing metrics facade interoperate with OpenTelemetry's trace generation and OTLP export — meaning a Spring Boot application gets both metrics and distributed tracing through one consistent, familiar Micrometer-based API, while the actual trace data itself flows out through the industry-standard, vendor-neutral OTEL/OTLP pipeline rather than a Spring-specific or vendor-specific format.

💡 "Minimal Code" Is the Point — Automatic Instrumentation

This continues the exact auto-configuration philosophy from Section 3, now applied to observability: Spring Boot auto-detects the Micrometer Tracing/OTEL dependencies on the classpath and automatically instruments Spring MVC request handling, JPA/Hibernate database calls, and outgoing HTTP client calls — generating and propagating trace spans without the developer writing any manual tracing code for these common cases. Manual, custom spans (for wrapping a specific piece of business logic you want separately visible in a trace) remain possible via Micrometer's ObservationRegistry API when genuinely needed, but the baseline, automatic coverage is deliberately broad.

FAANGWhy would you set sampling.probability to something less than 1.0 in a real production system, and what's the trade-off?

Tracing every single request (100% sampling) at real production traffic volume generates a substantial volume of trace data — real storage, network, and backend-processing cost that scales linearly with request volume, which can become genuinely expensive or overwhelming at high scale. A lower sampling rate (e.g., 0.1 = trace 10% of requests) trades completeness for cost/overhead — still providing a statistically representative, useful picture of system latency/behavior for most debugging and performance-analysis purposes, without the full cost of universal tracing. A common, more sophisticated pattern is tail-based sampling at the collector level — sampling based on a trace's outcome (always keep traces that ended in an error or were unusually slow, sample normally-completing fast traces at a much lower rate) — getting the debugging value of full coverage for the traces that actually matter most, at a fraction of full-tracing's cost.

💡 Why RestClient Exists at All, Given WebClient Already Covers HTTP Calls

WebClient is reactive (built on Project Reactor's Mono/Flux) — genuinely powerful for non-blocking, high-concurrency scenarios, but it forces reactive-programming concepts onto every caller even when the surrounding application is a perfectly ordinary synchronous Spring MVC app (the kind built throughout this entire course) with no other reactive code anywhere. RestClient was introduced specifically to give synchronous Spring MVC applications a modern, fluent HTTP client API without requiring reactive programming at all — the direct, non-reactive successor RestTemplate's maintenance-mode status was creating a real gap for.

FAANGHow would you add distributed tracing (this section's earlier topics) to outgoing RestClient calls — is any extra work required?

Generally no manual work is required — when Micrometer Tracing/OTEL (topic 222) is on the classpath and configured, Spring Boot's auto-configuration automatically instruments RestClient (and its predecessors) to create a child span for each outgoing HTTP call and correctly propagate the trace context (via standard traceparent-style headers) to the downstream service — meaning a call from Service A to Service B via RestClient automatically appears as a connected span within the same overall trace, exactly as shown in topic 223's example trace tree, with zero explicit tracing code written in the calling service.

// analogous to Section 3's RequestEntity/ResponseEntity on the SERVER side
ResponseEntity<Job> response = jobBoardClient.get()
        .uri("/jobs/{id}", jobId)
        .exchange((req, res) -> {
            if (res.getStatusCode().is2xxSuccessful()) {
                return ResponseEntity.ok(res.bodyTo(Job.class));
            }
            return ResponseEntity.status(res.getStatusCode()).build();
        });
@Bean
public RestClient jobBoardClient(RestClient.Builder builder) {
    return builder
            .baseUrl("https://api.jobboard.com")
            .requestInterceptor((request, body, execution) -> {
                // runs on EVERY outgoing request — analogous to Section 6's JwtAuthFilter,
                // but on the OUTGOING/client side rather than incoming
                log.info("Calling: {} {}", request.getMethod(), request.getURI());
                return execution.execute(request, body);
            })
            .build();
}
💡 Request Interceptors as the Client-Side Mirror of Server-Side Filters

A RestClient request interceptor plays structurally the same role, on the outgoing side, as a Servlet Filter/Spring Security filter (Section 6) plays on the incoming side — a cross-cutting point to inject logic (logging, auth headers, tracing propagation) that applies uniformly to every request passing through, without duplicating that logic at every individual call site. It's the same cross-cutting-concern principle from Section 8's AOP discussion, expressed here via a client-specific interceptor mechanism rather than AOP directly.

FAANGHow would you add automatic retry logic with exponential backoff to a RestClient call to a flaky third-party API?

RestClient itself has no built-in retry mechanism — retries are typically layered on via Spring Retry (@Retryable, itself another AOP-based annotation following the exact pattern from Section 8/10 — a marker annotation plus an interceptor) wrapping the service method that calls RestClient, configured with a backoff policy (e.g., @Backoff(delay = 200, multiplier = 2) for exponential backoff). It's important to combine this thoughtfully with idempotency considerations from Section 3's REST best practices — blindly retrying a non-idempotent POST (like the payment-charge example from topic 226) risks double-processing if the original request actually succeeded but the response was merely lost in transit; retries should generally be reserved for genuinely idempotent operations, or paired with an idempotency key the downstream API can use to safely deduplicate a retried request.

Introducing HTTP Service Client — Declarative REST Calls

Video: Introducing HTTP Service Client - Declarative REST Calls

This is the same declarative-over-imperative leap Spring Data JPA made for database repositories (Section 4) — now applied to outgoing HTTP calls: define an interface describing the desired calls, and Spring generates a working implementation automatically, with zero hand-written client code.

public interface JobBoardClient {

    @GetExchange("/jobs/{id}")
    Job getJob(@PathVariable Long id);

    @GetExchange("/jobs")
    List<Job> searchJobs(@RequestParam String status);

    @PostExchange("/jobs")
    Job createJob(@RequestBody JobRequest request);

    // notice: these are the EXACT SAME annotations (@GetMapping's exchange
    // equivalents) used to DEFINE endpoints in Section 3 — now used to DECLARE
    // a call to someone ELSE's endpoint instead
}
@Configuration
public class JobBoardClientConfig {

    @Bean
    public JobBoardClient jobBoardClient(RestClient.Builder builder) {
        RestClient restClient = builder.baseUrl("https://api.jobboard.com").build();

        HttpServiceProxyFactory factory = HttpServiceProxyFactory
                .builderFor(RestClientAdapter.create(restClient))
                .build();

        return factory.createClient(JobBoardClient.class);   // Spring generates the PROXY implementation —
    }                                                        // no hand-written class implements this interface anywhere
}

// usage — indistinguishable from any other injected service:
@Service @RequiredArgsConstructor
public class JobAggregatorService {
    private final JobBoardClient jobBoardClient;
    public Job fetchExternalJob(Long id) { return jobBoardClient.getJob(id); }
}
💡 The Same "Proxy Implements the Interface at Runtime" Pattern, One More Time

This is worth calling out explicitly for how it rhymes with concepts already deeply covered: exactly like Spring Data JPA generates a working implementation for a bare JpaRepository interface (Section 4) via a runtime proxy, HttpServiceProxyFactory generates a working implementation for this JobBoardClient interface via a runtime proxy — createClient() returns a dynamically-generated object implementing the interface, translating each annotated method call into the appropriate underlying RestClient call. Recognizing this as "the same pattern, a different domain" rather than a brand-new, unrelated mechanism is exactly the kind of cross-topic synthesis that demonstrates deep understanding.

FAANGWhat's the actual trade-off between using RestClient directly versus the declarative HTTP Interface approach — is one strictly better?

Not strictly better — a genuine trade-off, the same one that generally exists between declarative and imperative approaches throughout the course (derived query methods vs @Query, Section 7/9). The HTTP Interface approach is more concise and readable for straightforward request/response calls, and keeps the "contract" of an external API clearly documented as a single, scannable interface. Direct RestClient usage remains necessary/preferable when a call needs genuinely custom logic that doesn't fit the declarative annotation model cleanly — complex conditional request-building, fine-grained per-call error handling beyond what a simple exception-mapping convention supports, or the exchange()-level full request/response control shown in topic 227. Many real applications use both: the HTTP Interface for the majority of simple, standard calls, and direct RestClient usage for the handful of calls with genuinely special requirements.

Organizing REST Calls with HTTP Service Groups

Video: Organizing REST Calls with HTTP Service Groups

For applications consuming multiple external APIs (a payment gateway, a job board partner API, an email service), HTTP Service Groups provide a way to organize related interface-based clients together, sharing common base configuration (base URL, default headers, shared interceptors) without repeating that setup across every individual client's factory bean definition.

@Configuration
@ImportHttpServices(group = "jobboard", types = {JobBoardClient.class, CompanyLookupClient.class})
public class JobBoardApiConfig { }

# application.properties — ONE place to configure everything shared
# across every client interface registered under the "jobboard" group
spring.http.client.jobboard.base-url=https://api.jobboard.com
spring.http.client.jobboard.connect-timeout=5000
spring.http.client.jobboard.read-timeout=10000
💡 Why This Matters as the Section's Closing Lesson

This directly extends Section 11's "grouping cohesive configuration" lesson (@ConfigurationProperties, grouping related properties into one class rather than scattered @Value fields) into the HTTP-client domain: rather than each individual client interface needing its own separately-configured RestClient bean with duplicated base-URL/timeout/header setup (as topic 228's single-client example showed), Service Groups let a whole family of related external-API clients share one coherent configuration block — the same underlying principle (group related concerns together, configure once) recurring in yet another part of the framework.

CoreHow would you apply distributed tracing (this section's earlier topics) consistently across every client in an HTTP Service Group?

Since HTTP Service Groups still build on top of RestClient/WebClient underneath, the same automatic tracing instrumentation from topic 226's Q&A applies uniformly to every client interface registered in the group — Micrometer Tracing/OTEL auto-configuration instruments the underlying HTTP client machinery, not each individual generated interface proxy separately, so every call made through any client in the group automatically gets a properly-propagated trace span with zero additional per-client configuration needed. This is a nice, concrete illustration of why building on a shared, well-instrumented foundation (rather than each client managing its own raw HTTP calls independently) pays off automatically across cross-cutting concerns like tracing.

FAANGDesign the complete production-readiness checklist for a new Spring Boot microservice about to go live, using only concepts from this section.

(1) Actuator enabled with only health/info exposed publicly, everything else (env, beans, configprops, loggers) restricted to an authenticated admin role or a separate internal-only management port (topics 214–216). (2) Kubernetes liveness and readiness probes correctly wired to distinct Actuator health groups, with external dependency checks deliberately excluded from liveness (topic 215's Q&A). (3) The shutdown endpoint left disabled, relying on the orchestrator's native SIGTERM-based graceful shutdown instead (topic 219). (4) Micrometer Tracing/OTEL configured with a production-appropriate sampling rate (well below 100% at real scale, topic 222's Q&A), exporting to the organization's chosen backend. (5) Trace IDs surfaced in error responses for support workflows (topic 224). (6) Every outgoing call to another service or third-party API made via RestClient or an HTTP Interface, not a bare, unmanaged HTTP library call, ensuring automatic tracing propagation and consistent timeout/retry configuration (topics 226–230). This synthesizes essentially the entire section into one coherent go-live checklist.

FAANGA trace shows a request took 800ms, with a 750ms span labeled simply "external-call" and no further breakdown. How would you improve observability here, and what would you check first?

First check whether the external call is going through RestClient/an HTTP Interface (auto-instrumented, topic 226) or some unmanaged raw HTTP client bypassing Spring's observability auto-configuration entirely — a common root cause of exactly this kind of opaque, single-span external call with no further breakdown. If it is properly instrumented and genuinely is one atomic external call, the next step is checking whether the downstream service is itself instrumented and exporting traces to the same backend with proper trace-context propagation (topic 226's Q&A on automatic header propagation) — if so, this trace should actually continue as a connected child trace inside that downstream service, and the investigation moves there. If the downstream service is a third party outside your control and genuinely opaque, the 750ms is likely legitimately attributable to that external dependency's own latency, and the actionable next step becomes considering a timeout/circuit-breaker policy (Section 10's resilience-adjacent thinking) rather than further internal instrumentation.

CoreWhy might a team choose to still use RestTemplate in new code despite it being in maintenance mode?

Legitimate reasons exist beyond simple inertia: an existing, large codebase already has extensive RestTemplate usage and shared interceptor/configuration infrastructure built around it, and the migration cost to RestClient — while mechanically straightforward given their similar underlying capabilities — isn't free at scale across dozens of call sites; a team might reasonably defer that migration to a dedicated effort rather than mixing both clients inconsistently across a codebase mid-transition. That said, for any new code with no existing constraint, RestClient is unambiguously the current recommendation — "maintenance mode, no longer actively enhanced" is a real, forward-looking risk signal worth citing directly when justifying that choice to a team still defaulting to RestTemplate out of habit.

FAANGExplain how Actuator's /actuator/metrics endpoint, Micrometer, and this section's tracing setup relate to each other — are they three separate systems or one?

One underlying system, viewed from different angles. Micrometer is the single facade underneath both — it's what actually collects and holds metric data. Actuator's /actuator/metrics endpoint (topics 214–219) is simply an HTTP-exposed view into Micrometer's collected metrics, letting you query them ad hoc via a browser/curl. Micrometer Tracing (topics 220–224) extends that same Micrometer foundation to also generate and export distributed traces via the OTEL/OTLP pipeline to an external backend, rather than being queryable directly through Actuator itself. So: Micrometer is the common collection layer; Actuator exposes its metrics locally over HTTP for direct inspection; the OTEL/OTLP/LGTM pipeline is where its trace (and, via exporters, metric) data ultimately flows for full cross-service visualization — three complementary views of one coherent observability foundation, not three unrelated systems bolted together.
