Course Introduction & Why Spring Exists

Videos: Course Introduction · Source Code/PDF instructions · Why Core Java Alone Isn't Enough · Meet Spring & Spring Boot

The Problem: Building a Web App with Plain Core Java / Servlets

Before Spring, Java web development was done with raw Servlets and JSPs. This exposed a huge amount of plumbing work that has nothing to do with actual business logic:

  • Object creation & wiring — every class had to manually new up its dependencies (DAOs, services, utility classes), creating tightly coupled, hard-to-test code.
  • Boilerplate infrastructure — manually configuring a servlet container, mapping URLs in web.xml, handling request/response objects directly, manually parsing JSON.
  • Cross-cutting concerns — logging, transaction management, security, and validation had to be hand-rolled or duplicated across classes.
  • Database plumbing — raw JDBC requires manual Connection/Statement/ResultSet handling, try-with-resources everywhere, manual mapping of rows to objects.
  • No standard project structure — every team invents its own conventions, making onboarding and maintenance harder.
⚠ Interview Framing

When asked "why do we need Spring/Spring Boot," don't just say "it makes things easier." Give the specific pain points it solves: tight coupling (solved by DI/IoC), boilerplate config (solved by auto-configuration), cross-cutting concerns (solved by AOP), and lack of convention (solved by Spring Boot starters + opinionated defaults).

Key mental model: Spring Boot is not a replacement for Spring — it is Spring, pre-configured with sane defaults. Every Spring Boot app is still a full Spring application underneath; you can always drop down to raw Spring config when you need to override a default.

💡 The "Superpowers" Spring Gives You
  • IoC/DI — Spring creates and wires your objects; you just declare what you need.
  • AOP — cross-cutting concerns (logging, security, transactions) applied declaratively via annotations, not scattered code.
  • Data access abstraction — Spring Data JPA removes JDBC boilerplate almost entirely.
  • Spring MVC — clean, annotation-driven request handling (@RestController, @GetMapping, etc.).
  • Testing support — DI makes mocking trivial; Spring Boot Test gives you a full test slice ecosystem.
  • Production-readiness — Actuator, externalized config profiles, embedded servers, graceful shutdown.
FAANGWhy did Spring become the de facto standard over raw Java EE / EJB?

Early Java EE (especially EJB 2.x) required heavyweight, verbose component models (remote interfaces, home interfaces, deployment descriptors) and was hard to unit test because EJBs depended on a container to even instantiate. Spring introduced POJO-based programming — your business classes are plain Java objects with no framework interfaces to implement — and let the container inject dependencies instead of the object having to look them up (inversion of control). This made code testable without a container, lightweight, and far less boilerplate-heavy, which is why it displaced EJB as the dominant enterprise Java model.

CoreIs Spring Boot "faster" than Spring at runtime?

No — this is a common misconception. Spring Boot doesn't change runtime performance of the underlying Spring beans/DI machinery; it speeds up developer velocity (setup, configuration, deployment) via auto-configuration and embedded servers. Runtime performance depends on your code, JVM tuning, and how you use Spring's features, not on whether you used Boot.

CoreCan you use Spring Boot without Spring MVC?

Yes. Spring Boot is a general bootstrapping mechanism, not tied to web apps. You can build CLI tools, batch jobs, or messaging consumers with spring-boot-starter alone (no spring-boot-starter-web), using just the core IoC container, DI, and auto-configuration for whatever else you include (e.g. spring-kafka, spring-batch).

Part 1 — What Maven Is and Why We Need It

Maven is a build automation and dependency management tool for Java projects. Before Maven (and its predecessor Ant), developers manually downloaded JAR files, placed them on the classpath, and wrote custom build scripts. This didn't scale and caused "works on my machine" problems.

Maven solves three core problems:

  • Dependency management — declare a library + version in pom.xml; Maven downloads it (and its transitive dependencies) from a remote repository automatically.
  • Standard project structure — every Maven project follows the same folder layout, so any developer/tool immediately knows where source, tests, and resources live.
  • Build lifecycle standardization — compile, test, package, install, deploy are the same commands across every Maven project on earth.

Standard Directory Layout

my-app/ ├── pom.xml ← the heart of the project ├── src/ │ ├── main/ │ │ ├── java/ ← application source code │ │ └── resources/ ← application.properties, static files │ └── test/ │ ├── java/ ← test source code │ └── resources/ ← test-specific config └── target/ ← compiled output (generated, not committed)

Anatomy of pom.xml (Project Object Model)

<!-- POM = Project Object Model: the XML file that describes everything about the project -->

Part 2 — Build Lifecycle, Phases & Plugins

Maven's build process is modeled as a lifecycle, made up of an ordered sequence of phases. Running a phase runs every phase before it too.

Plugins & Goals

A plugin is a collection of goals (a goal = one specific task, e.g. compiler:compile). Phases are bound to plugin goals under the hood — e.g. the compile phase is bound to the maven-compiler-plugin's compile goal. In Spring Boot, the crucial plugin is spring-boot-maven-plugin, which repackages your JAR into an executable "fat/uber JAR" containing all dependencies, so it can be run standalone with java -jar.

# compile the project
mvn compile

# run tests
mvn test

# build the jar (runs test, package)
mvn package

# skip tests during packaging (use sparingly!)
mvn package -DskipTests

# install into local ~/.m2 repo for other local projects
mvn install

# clean target/ directory before rebuilding
mvn clean install

# run a Spring Boot app directly without building a jar first
mvn spring-boot:run

Part 3 — Repositories, Dependency Scopes & Transitive Dependencies

Repository Types

  • Local repository — ~/.m2/repository on your machine; a cache of every artifact you've ever downloaded/installed.
  • Central repository — Maven Central, the default public repo hosting virtually all open-source Java libraries.
  • Remote/private repository — company-internal artifact servers (Nexus, JFrog Artifactory, AWS CodeArtifact) used to host proprietary internal libraries or a mirrored cache of Central.

Resolution order: Maven checks the local repo first → if missing, fetches from configured remote repos (private repo, then Central) → caches it locally for next time.

Transitive Dependencies

If library A depends on library B, and your project depends on A, Maven automatically pulls in B too — that's a transitive dependency. This is why adding one Spring Boot starter can bring in dozens of jars. Run mvn dependency:tree to visualize the full graph and diagnose version conflicts.

⚠ Dependency Conflicts & Mediation

When two different paths in the dependency tree pull in different versions of the same library, Maven uses "nearest wins" resolution (the version declared closest to your project in the tree wins). You can force a version explicitly using <dependencyManagement> — this is exactly what spring-boot-starter-parent does for you across the whole Spring ecosystem, ensuring every starter uses mutually compatible versions.

FAANGWhat's the difference between a Maven "starter" and a normal dependency?

A Spring Boot starter (e.g. spring-boot-starter-data-jpa) is itself just a POM artifact with no code of its own — it's a curated bundle of transitive dependencies (Hibernate, Spring Data, JPA API, connection pool) chosen to work together, plus it triggers relevant auto-configuration classes on the classpath. A normal dependency is a single library. Starters exist purely to reduce the cognitive load of picking compatible versions manually.

CoreWhy does spring-boot-starter-parent matter, and what happens if you don't use it?

It centralizes version numbers for the entire Spring Boot BOM (Bill of Materials) via <dependencyManagement>, sets sensible compiler defaults (Java version, encoding), and configures default plugin behavior (like the Spring Boot Maven plugin). Without it, you must manually pin every dependency version yourself and risk incompatible combinations — a very common source of runtime NoSuchMethodError/ClassNotFoundException bugs in real production incidents.

CoreWhat's the difference between mvn install and mvn deploy?

install copies the built artifact into your local ~/.m2 repo, only usable on your machine. deploy uploads it to a remote/shared repository (Nexus/Artifactory) so other developers and CI/CD pipelines across the org can consume it as a dependency.

FAANGHow would you resolve a version conflict between two transitive dependencies?

First run mvn dependency:tree to see which paths bring in which versions. Then either (a) explicitly declare the desired version directly in your own <dependencies> (direct declarations always win over transitive ones), or (b) use <dependencyManagement> to pin a version project-wide, or (c) use <exclusions> inside the offending dependency to drop the unwanted transitive version entirely.

Spring Core — IoC and DI Explained the Easy Way

Video: Spring Core - IoC and DI Explained the Easy Way

Inversion of Control (IoC) — The Core Idea

Inversion of Control is a design principle where the control of object creation and lifecycle management is transferred from your code to a framework/container. Normally, a class controls its own dependencies by directly instantiating them (new SomeClass()). With IoC, that control is "inverted" — an external container decides what to create, when, and how to wire it together. Your class simply declares what it needs.

TRADITIONAL (you control everything): ┌────────────────────────────┐ │ class OrderService { │ │ PaymentGateway gw │ │ = new StripeGateway(); │ ← YOU decide the implementation │ } │ ← tight coupling, hard to test/swap └────────────────────────────┘ INVERSION OF CONTROL (container controls it): ┌────────────────────────────┐ │ class OrderService { │ │ PaymentGateway gw; │ ← declared, not created │ OrderService(PaymentGateway│ │ gw){this.gw=gw;} │ } │ └────────────────────────────┘ ▲ │ Spring IoC Container decides which │ PaymentGateway implementation to inject [ IoC Container ]
ℹ The "Hollywood Principle"

IoC is often summarized as "Don't call us, we'll call you." Instead of your object reaching out and pulling in its dependencies, the framework pushes the dependencies into your object. This is the defining characteristic that separates a framework (which calls your code) from a library (which your code calls).

Dependency Injection (DI) — IoC's Most Common Implementation

DI is one specific technique for achieving IoC (others include the Service Locator pattern, though Spring favors DI). In DI, dependencies ("collaborators") a class needs are supplied ("injected") from outside rather than the class creating them itself. Spring supports three injection styles:

@Service
public class OrderService {

    private final PaymentGateway paymentGateway;  // final = immutable

    // Spring auto-detects a single constructor and injects dependencies
    // @Autowired is OPTIONAL here since Spring 4.3+ if there's only one constructor
    public OrderService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }
}
@Service
public class OrderService {

    private PaymentGateway paymentGateway;

    @Autowired
    public void setPaymentGateway(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }
}
@Service
public class OrderService {

    @Autowired   // injected directly via reflection — AVOID in production code
    private PaymentGateway paymentGateway;
}
StyleImmutabilityTestabilityCircular Dep DetectionRecommended?
Constructor✅ can use final✅ easy — pass mocks in constructor, no Spring needed✅ fails fast at startup✅ Best practice / Spring team's official recommendation
Setter❌ mutable⚠ ok⚠ can hide problems (partially constructed objects)Only for optional dependencies

💡 Why Constructor Injection Wins in Interviews

Say this confidently: constructor injection lets you (1) mark fields final for true immutability, (2) guarantees the object is never in a partially-initialized state — it either fully constructs or fails at startup, (3) makes unit testing trivial — you can instantiate the class with new OrderService(mockGateway) without needing Spring at all, and (4) surfaces circular dependency errors immediately at application startup rather than a mysterious NPE at runtime.

Benefits of IoC/DI (Why It Actually Matters)

  • Loose coupling — classes depend on abstractions (interfaces), not concrete implementations. Swapping StripeGateway for RazorpayGateway requires zero changes to OrderService.
  • Testability — dependencies can be trivially mocked/stubbed in unit tests since they're passed in, not hard-coded.
  • Centralized configuration — object graph wiring lives in one place (config classes/annotations), not scattered across the codebase.
  • Lifecycle management — the container handles creation order, singleton reuse, and destruction — you don't manage object lifecycles manually.
  • Reduced boilerplate — no manual factory classes or Service Locator lookups needed.
FAANGIs IoC the same thing as DI?

No — this trips up a lot of candidates. IoC is the broader principle (control of object creation is inverted, handed to a framework). DI is one specific way to implement IoC — by injecting dependencies via constructor/setter/field. Other IoC implementations exist, like the Service Locator pattern (where the object still actively "pulls" its dependency from a registry, rather than having it "pushed" in) — Spring deliberately favors DI over Service Locator because DI keeps dependencies explicit and testable.

FAANGHow does Spring resolve constructor injection when there are multiple beans of the same type?

Spring throws a NoUniqueBeanDefinitionException unless you disambiguate. You resolve it using: @Qualifier("beanName") to pick a specific bean by name, marking one implementation @Primary as the default choice, or renaming the constructor parameter to exactly match a bean's name (Spring falls back to name-matching).

FAANGHow does constructor injection help detect circular dependencies, and what happens if you have one?

If Bean A's constructor needs Bean B, and Bean B's constructor needs Bean A, Spring cannot fully construct either — it throws a BeanCurrentlyInCreationException at startup. With field/setter injection, Spring can sometimes work around this by creating a partially-initialized bean first and injecting the field later — which hides a real design flaw. The fact that constructor injection fails loudly is a feature: circular dependencies almost always indicate poor separation of concerns and should be refactored (e.g., extract shared logic into a third bean, or use setter injection deliberately + @Lazy as a last resort).

CoreWhat is "Dependency Inversion Principle" (SOLID's D) vs "Dependency Injection" — are they the same?

Related but distinct. The Dependency Inversion Principle (DIP) is a SOLID design principle stating high-level modules should depend on abstractions, not concrete low-level modules. Dependency Injection is a mechanical technique/pattern for supplying those dependencies from outside. DI is one practical way to honor DIP, but you could follow DIP (code to interfaces) without using a DI framework at all (e.g., manual factory pattern).

Inside Spring — Beans, the IoC Container, and ApplicationContext

Video: Inside Spring - Beans, IoC Container and ApplicationContext

What Is a "Bean"?

A Spring Bean is simply an object whose entire lifecycle — instantiation, dependency wiring, initialization, and destruction — is managed by the Spring IoC Container, rather than by your own code. Not every Java object is a bean — only objects registered with, and controlled by, the container qualify. You register beans via:

  • Stereotype annotations: @Component, @Service, @Repository, @Controller/@RestController (all meta-annotated with @Component).
  • Explicit Java config: @Bean methods inside a @Configuration class (covered in depth in the next topic).
  • XML configuration (legacy, rarely used in modern Spring Boot projects but still testable/interview-relevant).

The IoC Container

The IoC Container is the core engine of Spring — the runtime component responsible for:

  1. Reading configuration metadata (annotations, Java config classes, or XML) to understand what beans need to exist and how they relate.
  2. Instantiating each bean (calling its constructor).
  3. Wiring dependencies — performing dependency injection between beans as needed.
  4. Managing the full bean lifecycle — initialization callbacks, scope management, and eventually destruction callbacks on shutdown.

Spring provides two container implementations, forming a class hierarchy:

InterfaceCapabilitiesUsed In
BeanFactoryThe root/base interface — basic DI container. Lazy initialization by default (beans created only when first requested).Rarely used directly today — mostly historical / memory-constrained environments
ApplicationContextSub-interface of BeanFactory with extra enterprise features: eager singleton initialization by default, event publishing, internationalization (i18n message resolution), AOP integration, and environment/property abstraction.The one you actually use — every Spring Boot app runs on an ApplicationContext

💡 Interview Gold: BeanFactory vs ApplicationContext

This is one of the single most asked Spring Core questions. Key differentiator to state clearly: BeanFactory lazily instantiates beans (only created when getBean() is called), while ApplicationContext eagerly instantiates all singleton beans at startup by default — which is exactly why a Spring Boot app "fails fast" on a misconfiguration at startup rather than deep into runtime. This eager approach trades a slightly longer startup time for much earlier error detection — a deliberate design choice favoring production reliability.

The Bean Lifecycle (Detailed)

1. Container starts up, reads bean definitions (from @Component scan / @Bean methods) 2. Container instantiates the bean (constructor call) 3. Dependencies injected (constructor/setter/field DI happens here) 4. Aware interfaces invoked (BeanNameAware, ApplicationContextAware, etc.) — if implemented 5. BeanPostProcessor#postProcessBeforeInitialization() — for ALL beans 6. @PostConstruct method invoked ─┐ 7. InitializingBean#afterPropertiesSet() │ initialization callbacks 8. custom init-method (if configured) ─┘ 9. BeanPostProcessor#postProcessAfterInitialization() — e.g. proxies created here (AOP!) 10. ── Bean is now fully ready and in active use ── 11. Container shutdown begins 12. @PreDestroy method invoked ─┐ 13. DisposableBean#destroy() │ destruction callbacks (singleton scope only) 14. custom destroy-method (if configured) ─┘
⚠ Important Nuance

Destruction callbacks (@PreDestroy, etc.) only fire automatically for singleton-scoped beans, because the container fully owns their lifecycle. For prototype-scoped beans, Spring hands off the object after creation and does not manage or call destroy methods — you're responsible for cleanup yourself.

ApplicationContext: Ways to Get One in Spring Boot

@SpringBootApplication
public class EazyBankApplication {

    public static void main(String[] args) {
        // SpringApplication.run() bootstraps the container and returns the
        // fully-initialized ApplicationContext
        ApplicationContext context =
                SpringApplication.run(EazyBankApplication.class, args);

        // manually pulling a bean out of the container (rarely done in real
        // app code — DI should handle this — but useful to know for debugging)
        OrderService service = context.getBean(OrderService.class);
    }
}
FAANGWhy does ApplicationContext eagerly create singleton beans, and can this be changed?

Eager instantiation surfaces configuration errors (missing dependencies, bad property values, wiring mistakes) immediately at startup rather than at some unpredictable point in production traffic — a "fail fast" philosophy critical for production reliability. It also front-loads the cost of object creation so the app is warm and ready to serve requests immediately. You CAN opt individual beans into lazy initialization with @Lazy, or set spring.main.lazy-initialization=true globally (mainly useful to speed up local dev startup time), though this is discouraged in production since it defers error detection.

FAANGHow would you inject a prototype-scoped bean into a singleton bean correctly?

This is a classic trap: if you naively @Autowired a prototype bean directly into a singleton, Spring injects it only once at singleton creation time — you'll get the same prototype instance forever, defeating the purpose. Correct solutions: (1) inject an ObjectFactory<T> or ObjectProvider<T> and call .getObject() each time you need a fresh instance, (2) use lookup method injection via @Lookup, or (3) inject a scoped-proxy (proxyMode = ScopedProxyMode.TARGET_CLASS) so every method call is transparently routed to a fresh prototype instance.

CoreWhat's the difference between BeanFactory.getBean() and ApplicationContext's autowiring?

getBean() is imperative/manual bean lookup — you explicitly ask the container for a bean by type or name, which is a Service-Locator-style anti-pattern in application code (though fine for framework/bootstrap code). Autowiring (via @Autowired, constructor params, etc.) is declarative DI — you simply declare what you need and the container injects it without your code ever calling the container directly. Real application code should almost always prefer autowiring; direct getBean() calls are a code smell outside of framework internals or very specific dynamic-lookup scenarios.

FAANGExplain how @PostConstruct differs from a constructor, and why you'd use it.

A constructor runs before dependency injection is guaranteed complete in some injection styles (particularly field/setter injection — fields are null during the constructor call). @PostConstruct runs after all dependency injection is fully complete, making it the safe place to run initialization logic that depends on injected collaborators (e.g., validating configuration, warming a cache, opening a connection pool). With pure constructor injection, this distinction matters less since all dependencies are guaranteed available inside the constructor itself — but @PostConstruct is still useful for logic you don't want mixed into the constructor's job of just assigning fields.

CoreAre Spring singleton beans the same as the Singleton design pattern (GoF)?

No — a common gotcha. The GoF Singleton pattern guarantees one instance per JVM/classloader, typically enforced with a private constructor and static instance field. A Spring singleton-scoped bean guarantees only one instance per IoC container (ApplicationContext). If you spin up two ApplicationContexts in the same JVM (unusual, but possible — e.g. in some test setups or multi-context apps), you'd get two separate instances of the "singleton" bean. Also, nothing prevents you from still calling new MyBean() manually elsewhere and bypassing the container entirely — Spring doesn't enforce true JVM-wide single-instance semantics.

How @Configuration Classes Are Discovered

@SpringBootApplication is itself a composite annotation bundling @Configuration + @EnableAutoConfiguration + @ComponentScan. This means your main application class is already a configuration class, and component scanning automatically discovers any other @Configuration classes (and @Component-annotated classes) sitting in the same package or sub-packages — no manual registration needed in a typical Spring Boot app.

Full Mode vs Lite Mode — CGLIB Proxying

When a class is annotated @Configuration (the default "full" mode), Spring generates a CGLIB subclass proxy of it at runtime. This proxy intercepts calls to @Bean methods so that calling one @Bean method from another within the same class always returns the same singleton instance — rather than creating a brand-new object each time. If you instead use @Component on a class with @Bean methods ("lite" mode, no proxy), inter-bean-method calls do NOT go through the container and create fresh objects each call — a subtle but real production bug source.

@Configuration  // FULL mode — CGLIB proxy applied
public class AppConfig {

    @Bean
    public PaymentGateway paymentGateway() {
        return new StripeGateway();
    }

    @Bean
    public OrderService orderService() {
        // this call is intercepted by the CGLIB proxy and returns
        // the SAME singleton PaymentGateway bean — NOT a new StripeGateway()
        return new OrderService(paymentGateway());
    }
}
⚠ Common Production Bug

If your @Configuration class is declared final, CGLIB proxying fails at startup because CGLIB works by subclassing — you cannot subclass a final class. Spring Boot will throw a BeanDefinitionStoreException. Never mark a @Configuration class final.

FAANGWhen would you choose @Bean over @Component for your own class?

Even for your own classes, prefer @Bean when: (1) you need to run custom construction logic that a no-arg constructor + field injection can't express cleanly (e.g., calling a builder, choosing an implementation conditionally based on a property), (2) you want to register multiple beans of the same type with different configurations (e.g., two different RestTemplate beans with different timeouts), or (3) the class comes from a third-party library you cannot annotate directly. For straightforward, self-owned classes with simple constructor-based dependencies, @Component + stereotype annotations is idiomatic and less verbose.

FAANGExplain exactly why calling one @Bean method from another inside @Configuration doesn't create duplicate beans.

Because @Configuration classes (in "full" mode, the default) are enhanced by Spring at startup using CGLIB byte-code generation to create a runtime subclass proxy. Every call to a @Bean-annotated method on that proxy is intercepted: the proxy first checks the container's bean cache for an existing instance under that bean's name, and returns it if present, only invoking the real method body if the bean hasn't been created yet. This is exactly what guarantees singleton semantics across inter-bean-method calls, even though syntactically it just looks like a plain Java method call.

CoreWhat's the default bean name from a @Bean method, and how do you override it?

By default the bean's name is the method name itself (e.g. a method named paymentGateway() registers a bean named "paymentGateway"). You override it with @Bean(name = "customName") or the shorthand @Bean("customName"); you can also supply multiple aliases via @Bean(name = {"nameA","nameB"}).

FAANGHow do you conditionally register a @Bean, e.g. only when a property is set or a class is on the classpath?

Use Spring Boot's conditional annotations on the @Bean method or the whole @Configuration class: @ConditionalOnProperty (register only if a specific property/value is present), @ConditionalOnMissingBean (register only if no other bean of that type already exists — heavily used internally by Spring Boot's auto-configuration to let user-defined beans override defaults), @ConditionalOnClass (register only if a given class is present on the classpath — this is literally how Spring Boot auto-configuration decides which starters' features to activate).

🎯 Rapid-Fire Round

Master Interview Q&A Bank — Section 1

Quick-fire questions commonly asked at FAANG, fintech (JPMC, Walmart Global Tech) and product-company interviews, condensed for last-minute revision.

FAANGWhat is Spring's "convention over configuration" and how does Spring Boot embody it?

It means the framework assumes sensible defaults so you only write configuration for what deviates from the norm. Spring Boot embodies this via auto-configuration — e.g., if spring-boot-starter-data-jpa and an H2 dependency are on the classpath, Spring Boot auto-configures a DataSource, EntityManagerFactory, and TransactionManager with zero explicit config, based purely on what it detects.

CoreWhat annotation bootstraps a Spring Boot app, and what three annotations does it combine?

@SpringBootApplication combines @Configuration (marks the class as a source of bean definitions), @EnableAutoConfiguration (triggers Spring Boot's classpath-based auto-configuration), and @ComponentScan (scans the current package and sub-packages for components).

FAANGWhat happens internally when you call SpringApplication.run()?

At a high level: (1) it creates the appropriate ApplicationContext type (servlet web context if spring-boot-starter-web is present), (2) loads and processes all @Configuration classes and auto-configuration candidates, (3) triggers component scanning to register bean definitions, (4) instantiates all singleton beans eagerly and performs dependency injection, (5) runs any ApplicationRunner/CommandLineRunner beans, and (6) starts the embedded servlet container (Tomcat by default) to begin accepting HTTP traffic.

CoreWhat's the difference between @Component, @Service, @Repository, and @Controller?

Functionally, all four are meta-annotated with @Component and are treated identically by the container for scanning/registration purposes. They exist for semantic clarity and add specific extra behavior: @Repository enables automatic translation of persistence exceptions into Spring's unified DataAccessException hierarchy; @Controller is recognized by Spring MVC for request-mapping purposes; @Service is purely semantic (marks business-logic layer) with no extra framework behavior beyond @Component.

FAANGHow does Spring decide which bean to inject when multiple implementations of an interface exist?

Resolution order: (1) if only one bean of that type exists, inject it; (2) if multiple exist and one is marked @Primary, that one wins; (3) if a @Qualifier("name") is specified at the injection point, match by that exact bean name/qualifier; (4) if the injection point's variable/parameter name exactly matches a bean's name, Spring falls back to that match; (5) otherwise, Spring throws NoUniqueBeanDefinitionException at startup.

CoreCan a bean depend on another bean that hasn't been created yet? How does Spring handle ordering?

Yes — Spring automatically determines the correct instantiation order by analyzing the dependency graph declared through constructor parameters, @Autowired fields, etc. It creates dependencies before dependents. You rarely need to manage this manually; @DependsOn exists for the rare case where an ordering dependency isn't expressed through normal injection (e.g., a bean that must be initialized first purely for a side effect).

FAANGWhy is field injection considered an anti-pattern despite being the most concise syntax?

Beyond the testability and immutability issues already covered, field injection also hides a class's true dependencies — you can't tell what a class needs just by looking at its public constructor signature; you have to scan every field for @Autowired. It also silently allows a class to accumulate an unreasonable number of dependencies (a code smell suggesting the class violates Single Responsibility) since there's no constructor parameter list to visually "feel" the growing complexity. Constructor injection makes this pain visible early, nudging you toward better design.

CoreWhat is the difference between compile-time and runtime dependency resolution in Maven vs Spring?

Maven's dependency resolution is about which JARs are on the classpath — resolved once when the build runs, based on pom.xml. Spring's dependency injection is about which object instances get wired together at application startup, resolved by the IoC container reading annotations/config — an entirely different (and later) phase of "dependency resolution." Interviewers sometimes ask this to check if candidates conflate build-time and runtime concerns.
