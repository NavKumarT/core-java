Why Spring Gets Confused — NoUniqueBeanDefinitionException

Video: Why Spring Gets Confused - NoUniqueBeanDefinitionException Explained

When two or more beans of the same type exist in the container, and you try to autowire that type without disambiguation, Spring cannot decide which one you mean. It throws:

org.springframework.beans.factory.NoUniqueBeanDefinitionException:
No qualifying bean of type 'com.growthscript.PaymentGateway' available:
expected single matching bean but found 2: stripeGateway,razorpayGateway

This is a startup-time (fail-fast) exception — the app refuses to boot rather than silently guessing, which is exactly the "eager singleton creation" behavior from Section 1's ApplicationContext discussion in action.

Four Ways to Resolve It

  1. Mark one implementation @Primary (sets the default).
  2. Use @Qualifier("beanName") at the injection point to be explicit.
  3. Rename the injection point's variable/parameter to match a bean's name exactly (Spring falls back to name-based matching).
  4. Inject a List<PaymentGateway> or Map<String,PaymentGateway> if you actually want all implementations (common in Strategy-pattern-style designs).
💡 Strategy Pattern Tie-In

A very common real-world/interview scenario: injecting Map<String, PaymentGateway> auto-populates the map with bean name → bean instance for every implementation, letting you dynamically dispatch by a string key (e.g., from a request parameter) without a giant if-else/switch chain. This is a favorite "design this" interview follow-up after explaining NoUniqueBeanDefinitionException.

FAANGIf you inject a List<PaymentGateway> instead of a single PaymentGateway, does Spring still throw NoUniqueBeanDefinitionException?

No. Collection-typed injection points (List<T>, Set<T>, Map<String,T>, arrays) are a special case — Spring recognizes you explicitly want every matching bean, not one, so it collects them all instead of throwing. Ordering in a List can be controlled via @Order or by implementing Ordered on the beans.

CoreDoes @Primary suppress NoUniqueBeanDefinitionException permanently, or only in specific cases?

It resolves ambiguity only when the ambiguity is a "default vs alternative" situation — i.e., when there's no more specific @Qualifier at the injection point. If a @Qualifier is present, it takes precedence over @Primary. If two beans are both marked @Primary, the exception still occurs since Spring can't determine a single default among primaries.

⚠ Uniqueness Requirement

@Primary — Choosing the "Default" Bean

Video: @Primary - Choosing the 'Default' Bean
@Component
@Primary   // this becomes the DEFAULT choice when ambiguous
public class StripeGateway implements PaymentGateway { }

@Component
public class RazorpayGateway implements PaymentGateway { }

@Service
public class OrderService {
    // no @Qualifier needed — Spring picks StripeGateway automatically
    public OrderService(PaymentGateway gateway) { }
}

Precedence rule: @Qualifier at the injection point always overrides @Primary — @Primary is only a fallback default, not a hard override.

💡 When to Use @Primary vs @Qualifier

Use @Primary when there's a genuinely "usual" choice that 90% of injection points want (e.g., a default ObjectMapper or default DataSource). Use @Qualifier everywhere you need to be explicit about a non-default choice. Mixing both is normal and expected in real codebases.

Modular Config Made Easy with @Import

Video: Modular Config Made Easy with @Import

@Import lets one @Configuration class explicitly pull in bean definitions from another @Configuration class (or regular @Component classes) that may live outside the normal component-scan path — useful for modularizing large configuration into focused, single-responsibility config classes.

@Configuration
public class SecurityConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

@Configuration
@Import({SecurityConfig.class, DatabaseConfig.class})  // pulls both in
public class AppConfig {
    // AppConfig's context now also has all beans from SecurityConfig + DatabaseConfig
}
ℹ Real-World Use Case

Large Spring Boot apps often split configuration by concern — SecurityConfig, DatabaseConfig, KafkaConfig, SwaggerConfig — each self-contained. Since @ComponentScan normally picks these up automatically if they're in scanned packages anyway, @Import becomes essential specifically when a config class lives outside the scanned package tree (e.g., a shared config module imported from a separate JAR/library) or when you want to make the composition of a config explicit and traceable rather than implicit via scanning.

CoreWhat's the difference between @Import and @ComponentScan for pulling in configuration?

@ComponentScan is implicit and broad — it scans an entire package tree and registers anything annotated with a stereotype. @Import is explicit and targeted — you name the exact configuration class(es) to bring in, regardless of package location. @Import is preferred when you want traceable, intentional composition rather than "magic" package-based discovery, and it's the only option when the class lives outside your scanned base package.

Bean Creation the Easy Way — @Component

Video: Bean Creation the Easy Way - @Component

@Component is the most generic stereotype annotation — marking a class as a candidate for auto-detection during classpath component scanning. Spring Boot's @ComponentScan (bundled inside @SpringBootApplication) scans the package of your main class and all sub-packages by default, registering every @Component-annotated (and meta-annotated) class it finds as a bean — no manual @Bean method required.

⚠ Package Placement Matters

If a @Component class lives in a package outside the main application class's package tree, it will not be picked up automatically — a very common real bug for beginners restructuring a project. Fix by either moving the class into scope, or explicitly widening scan scope: @ComponentScan(basePackages = {"com.growthscript.app","com.growthscript.shared"}).

Bean Lifecycle Hooks — @PostConstruct & @PreDestroy

Video: Bean Lifecycle Hooks - @PostConstruct & @PreDestroy
@Component
public class CacheWarmerService {

    private Map<String, String> cache;

    @PostConstruct  // runs AFTER constructor + DI is fully complete
    public void init() {
        cache = new HashMap<>();
        cache.put("warmup", "done");
        System.out.println("Cache warmed up at startup");
    }

    @PreDestroy  // runs just before the bean is destroyed (container shutdown)
    public void cleanup() {
        cache.clear();
        System.out.println("Cache cleared on shutdown");
    }
}

These come from JSR-250 (a standard Java annotation set, not Spring-proprietary), which is why they work identically across other Java EE/Jakarta EE-compliant frameworks too. Common use cases: warming caches, validating required configuration is present, opening resources like connection pools/socket connections (@PostConstruct), and flushing buffers, closing connections, deregistering from external systems (@PreDestroy).

⚠ Only Fires for Singleton Beans by Default

@PreDestroy is only guaranteed to run for singleton-scoped beans, since the container owns their full lifecycle including shutdown. For prototype-scoped beans, Spring hands off the instance after creation and never calls destruction callbacks — you must clean those up manually.

Alternative / Equivalent Mechanisms

MechanismHowNotes
@PostConstruct/@PreDestroyAnnotate a method directlyPreferred — clean, standard, no interface coupling
InitializingBean/DisposableBeanImplement Spring interfaces (afterPropertiesSet()/destroy())Couples your class to Spring API directly — avoided in modern code
@Bean(initMethod=..., destroyMethod=...)Specify method names in the @Bean annotationBest for third-party classes you can't annotate directly
FAANGWhat's the exact order if a bean has @PostConstruct, InitializingBean, AND a custom init-method all at once?

The order is fixed: (1) @PostConstruct methods first, (2) InitializingBean.afterPropertiesSet() second, (3) the custom init-method specified via @Bean(initMethod=...) last. In practice, using more than one of these on the same bean is a code smell — pick one consistently, typically @PostConstruct for your own classes.

CoreWhy might @PostConstruct throw an exception, and what happens if it does?

If validation logic inside @PostConstruct fails (e.g., a required external config value is missing, a connection can't be established), throwing an exception there fails the entire application startup — the ApplicationContext refuses to complete initialization. This is intentional and desirable: it's far better to crash loudly at deploy time than to serve traffic with a half-broken dependency.

💡 Persistence Exception Translation, Explained

Without @Repository, a DAO method might leak a driver-specific checked exception like SQLException or a Hibernate-specific ConstraintViolationException straight up to your service layer, tightly coupling business code to a specific persistence technology. @Repository's exception translation converts these into Spring's consistent, technology-agnostic DataAccessException subtypes (e.g. DataIntegrityViolationException), so your service/business layer can catch one consistent exception hierarchy regardless of whether you're using JPA, plain JDBC, or MongoDB underneath.

FAANGIs @Service functionally different from @Component at all?

As of current Spring versions, no — @Service adds zero extra runtime behavior over @Component; it's meta-annotated with @Component and exists purely to communicate architectural intent to developers and tools (some static analysis / AOP pointcuts do target @Service specifically by convention, but that's project-specific usage, not framework-guaranteed behavior). Using the semantically correct stereotype is still considered best practice for code readability and team conventions.

CoreWhy does @RestController exist instead of just always adding @ResponseBody to every method?

Pure convenience/DRY — before @RestController existed (Spring 4.0+), REST API classes had to write @Controller at the class level plus @ResponseBody on every single method, which was repetitive boilerplate for API-only classes where 100% of methods return response bodies rather than view names. @RestController collapses both into one class-level annotation.

Method-Based Bean Wiring — Theory & Hands-On Demo

Videos: Method-Based Bean Wiring - Theory · Hands-On Demo

"Method-based wiring" refers to injecting dependencies directly as parameters of a @Bean factory method — Spring resolves each parameter from the container by type (and name/qualifier if needed) before invoking the method, exactly like constructor injection does for regular components.

@Configuration
public class AppConfig {

    @Bean
    public DataSource dataSource() {
        return new HikariDataSource();
    }

    // Spring resolves 'dataSource' param from the container BEFORE calling this method
    @Bean
    public JdbcTemplate jdbcTemplate(DataSource dataSource) {
        return new JdbcTemplate(dataSource);
    }

    // works across DIFFERENT @Configuration classes too — Spring resolves
    // from the WHOLE container, not just this config class
    @Bean
    public UserRepository userRepository(JdbcTemplate jdbcTemplate,
                                          @Qualifier("auditLogger") Logger logger) {
        return new UserRepository(jdbcTemplate, logger);
    }
}

This is functionally equivalent to calling one @Bean method from inside another (as shown in Section 1's CGLIB discussion) but is generally preferred because it works correctly regardless of which @Configuration class each bean is declared in, and it doesn't rely on the CGLIB proxy interception subtlety — Spring's container simply resolves each parameter the same way it resolves constructor arguments anywhere else.

💡 Method-Parameter Wiring vs Direct Method-Call Wiring

Prefer method-parameter wiring (public Bean method(Dependency d)) over direct method calls (public Bean method() { return new Bean(dependency()); }) inside the same config class. Parameter-based wiring is more explicit, testable, works across configuration classes without depending on CGLIB proxy semantics, and is what most style guides / the Spring team itself recommend.

Autowiring Demo — Field, Setter & Constructor Injection

Videos: Autowiring Demo - Field vs Setter Injection · Autowiring Demo - Constructor Injection

This is a hands-on reinforcement of the three DI styles from Section 1's IoC/DI theory — now with the mechanics of @Autowired itself examined closely.

@Autowired Attributes

AttributePurpose
required (default true)If true and no matching bean exists, throws NoSuchBeanDefinitionException at startup. Set required = false to allow the dependency to remain null if absent (rarely recommended — prefer Optional<T> or ObjectProvider<T> instead for explicit optionality).
@Service
public class NotificationService {
    private final Optional<SmsGateway> smsGateway;  // clean way to express "optional"

    public NotificationService(Optional<SmsGateway> smsGateway) {
        this.smsGateway = smsGateway;
    }

    public void notifyUser(String msg) {
        smsGateway.ifPresent(gw -> gw.send(msg));
    }
}
@Component
public class ReportGenerator {

    // Spring MUST know which constructor to use when there's more than one —
    // mark exactly ONE with @Autowired
    @Autowired
    public ReportGenerator(ReportFormatter formatter) {
        // primary DI-eligible constructor
    }

    public ReportGenerator() {
        // convenience no-arg constructor, NOT used by Spring for autowiring
    }
}
⚠ The "Single Constructor" Rule

If a class has exactly one constructor, Spring implicitly uses it for autowiring — @Autowired is optional there. If a class has multiple constructors, Spring cannot guess which one to use for DI and throws an error at startup unless exactly one constructor is explicitly annotated @Autowired.

FAANGBetween field, setter, and constructor injection, which does Spring resolve first if a bean uses more than one style simultaneously?

Mixing styles on one bean is discouraged, but the underlying order is: the bean is instantiated via its constructor first (constructor-injected dependencies must be available at this exact moment), then field and setter injection are applied via reflection/setter calls as a subsequent step, before @PostConstruct fires. This ordering is exactly why @PostConstruct — not the constructor — is the safe place to rely on field/setter-injected dependencies.

CoreCan @Autowired be used on a static field or method?

No — Spring does not support dependency injection into static members. Static fields belong to the class, not to any bean instance, and DI is fundamentally about wiring instance-level object graphs. Attempting it doesn't throw an error, but the field silently remains unset/null, which is a subtle and confusing bug — a common "gotcha" interview question.

Autowiring with @Primary & Targeting the Right Bean with @Qualifier

Videos: Autowiring with @Primary - Which Bean Wins? · Targeting the Right Bean with @Qualifier

Resolution Priority — Full Order

  1. Only one candidate bean exists → inject it, no ambiguity.
  2. @Qualifier present at injection point → always wins, matched by exact name/qualifier value.
  3. No @Qualifier, but one candidate is @Primary → the primary bean is injected.
  4. No @Qualifier, no @Primary, but injection point's variable name matches a bean name exactly → matched by name as a final fallback.
  5. Still ambiguous → NoUniqueBeanDefinitionException at startup.
@Component @Primary
public class StripeGateway implements PaymentGateway { }

@Component("razorpay")
public class RazorpayGateway implements PaymentGateway { }

@Service
public class InternationalOrderService {
    private final PaymentGateway gateway;

    public InternationalOrderService(
            @Qualifier("razorpay") PaymentGateway gateway) {  // wins over @Primary
        this.gateway = gateway;
    }
}
💡 Custom Qualifier Annotations (Advanced but Interview-Relevant)

Instead of stringly-typed @Qualifier("razorpay"), you can create a custom, type-safe qualifier annotation using meta-annotation with @Qualifier, e.g. @RazorpayPayment. This gives compile-time safety (typos in string qualifiers only fail at runtime) and is a pattern Spring itself uses internally (e.g. @Lazy, @Async follow similar meta-annotation patterns). Worth mentioning if an interviewer pushes on "how would you make this more robust."

Dynamic Bean Registration — Programmatic Style

Video: Dynamic Bean Registration - Programmatic Style

Beyond declarative annotations, Spring allows registering beans imperatively at runtime using the low-level ApplicationContext/BeanFactory APIs — useful when bean definitions depend on values only known at runtime (e.g., dynamically discovered plugins, tenant-specific beans in a multi-tenant system, or beans built from external configuration data).

public static void main(String[] args) {
    GenericApplicationContext context = new GenericApplicationContext();

    // register a bean by supplying a factory lambda — fully programmatic
    context.registerBean("stripeGateway", StripeGateway.class,
            () -> new StripeGateway("sk_live_xxx"));

    context.refresh();  // finalizes and starts the context

    StripeGateway gw = context.getBean(StripeGateway.class);
}
// hooking into the container's bootstrap process itself to register
// beans conditionally, based on runtime-discovered data
@Component
public class DynamicGatewayRegistrar implements BeanDefinitionRegistryPostProcessor {

    @Override
    public void postProcessBeanDefinitionRegistry(BeanDefinitionRegistry registry) {
        // e.g., loop over configured payment providers from a properties file
        // and register one gateway bean per provider dynamically
        BeanDefinitionBuilder builder =
            BeanDefinitionBuilder.genericBeanDefinition(RazorpayGateway.class);
        registry.registerBeanDefinition("razorpayGateway", builder.getBeanDefinition());
    }
}
⚠ Use Sparingly

Programmatic registration bypasses the readability of declarative annotations and is harder to trace/debug (you can't just Ctrl+click to a @Bean definition — it's assembled at runtime). Reserve it genuinely dynamic scenarios: plugin architectures, multi-tenancy, or framework-level infrastructure code — not everyday application beans.

FAANGGive a real production scenario where programmatic bean registration is the right tool.

A multi-tenant SaaS backend where each tenant has its own database connection/schema, and the set of tenants is only known at runtime (loaded from a config table). Rather than hardcoding a fixed number of @Bean methods, a BeanDefinitionRegistryPostProcessor can loop over the discovered tenant list at startup and register one DataSource bean per tenant dynamically. Another common example: a plugin system where JARs are dropped into a directory at runtime and each exposes a service that needs to become a Spring-managed bean.

Singleton Scope & Eager vs Lazy Initialization

Videos: Singleton Scope - One Bean to Rule Them All · Eager vs Lazy - When is Your Singleton Created?

Singleton is Spring's default bean scope — exactly one shared instance per Spring IoC container, reused for every injection point that requests it.

Container starts │ ▼ [ Bean Definition: OrderService, scope=singleton ] │ ▼ One instance created ──────┬──── injected into ControllerA ├──── injected into ControllerB └──── injected into SchedulerJob (ALL THREE share the exact same object reference)
⚠ Thread-Safety Implication

Because a singleton bean is shared across every concurrent HTTP request thread in a web app, mutable instance state on a singleton is a classic concurrency bug. If OrderService has a mutable field like private int requestCount; that's incremented per request, you have a race condition. Singleton beans should be stateless, or use thread-safe constructs (AtomicInteger, ThreadLocal, or externalize state to a database/cache) if state is unavoidable. This is one of the most commonly asked "gotcha" questions for backend interviews.

FAANGWhy is global lazy initialization (spring.main.lazy-initialization=true) discouraged for production?

Two reasons: (1) it defeats the fail-fast principle — a misconfigured bean now fails during live request handling instead of at deploy time, which is far worse for reliability and incident response, and (2) it can introduce unpredictable latency spikes for whichever unlucky request happens to trigger a heavy bean's first-time construction, rather than paying that cost once, upfront, during a controlled startup/readiness-probe window before traffic is routed to the pod.

FAANGHow would you make a singleton service that legitimately needs per-request state, safely?

Options in order of preference: (1) avoid instance state entirely — pass all needed data as method parameters and return values, keeping the bean purely stateless (the ideal and most scalable design); (2) if per-request context truly must be "ambient" (like a request ID for logging), use request-scoped beans with a scoped-proxy, or ThreadLocal storage cleaned up per request (common in tracing/MDC logging setups); (3) for shared mutable counters/caches, use thread-safe types like AtomicInteger, ConcurrentHashMap, or push the state out to an external store (Redis) entirely.

CoreDoes @Lazy affect eager vs lazy for non-singleton scopes too?

The eager-vs-lazy distinction is specifically about singleton creation timing (container startup vs first use), because singletons are the only scope Spring pre-instantiates by default in the first place. Prototype-scoped beans are already inherently "lazy" in the sense that a new instance is only ever created when explicitly requested — @Lazy has no meaningful additional effect there.

Prototype Scope — Fresh Bean Every Time

Video: Prototype Scope - Fresh Bean Every Time
@Component
@Scope("prototype")  // or ConfigurableBeanFactory.SCOPE_PROTOTYPE constant
public class PdfReportGenerator {
    private List<String> entries = new ArrayList<>();  // safe: unique per instance

    public void addEntry(String e) { entries.add(e); }
}

Every call to context.getBean(PdfReportGenerator.class) or every fresh injection returns a brand new instance. Unlike singleton, the container does not manage the full lifecycle after creation — no automatic @PreDestroy calls; you own cleanup.

The Prototype-Injected-Into-Singleton Trap (revisited from Section 1)

@Service  // singleton by default
public class ReportService {
    private final PdfReportGenerator generator;  // injected ONCE, at ReportService creation

    public ReportService(PdfReportGenerator generator) {
        this.generator = generator;  // BUG: same instance reused forever!
    }
}
@Service
public class ReportService {
    private final ObjectProvider<PdfReportGenerator> generatorProvider;

    public ReportService(ObjectProvider<PdfReportGenerator> generatorProvider) {
        this.generatorProvider = generatorProvider;
    }

    public void generate() {
        PdfReportGenerator freshGenerator = generatorProvider.getObject();  // NEW instance every call
        freshGenerator.addEntry("row 1");
    }
}

FAANGWhat are all the correct ways to get a fresh prototype instance inside a singleton, ranked by preference?
  • ObjectProvider<T> (Spring's modern, recommended approach) — inject it, call .getObject() whenever a fresh instance is needed.
  • ObjectFactory<T> — older, more limited predecessor to ObjectProvider (fewer convenience methods like ifAvailable/stream).
  • @Lookup method injection — declare an abstract method annotated @Lookup that Spring overrides at runtime via CGLIB to return a fresh bean each call. More "magic," less explicit.
  • Scoped proxy (@Scope(proxyMode = ScopedProxyMode.TARGET_CLASS) on the prototype bean) — the singleton holds a proxy that transparently delegates each method call to a fresh prototype instance behind the scenes. Powerful but can obscure what's actually happening for newer team members.
  • Directly calling ApplicationContext.getBean() — technically works but couples your class directly to the Spring API (Service Locator anti-pattern) — generally avoided.
CoreIf you don't clean up a prototype bean's resources manually, what happens?

Nothing automatic — the container forgets about the prototype instance entirely once handed off, so if it holds an unmanaged resource (open file handle, socket, thread), you get a resource leak unless you explicitly close/clean it up in your own code, e.g., via try-with-resources if the bean is AutoCloseable, or a manual cleanup call at the end of its use.

An Advice

Video: An Advice
💡 Section Wrap-Up Principles
  • Default to constructor injection and singleton scope unless you have a specific, deliberate reason to deviate — these are the safe, idiomatic defaults for the vast majority of Spring beans.
  • Keep singleton beans stateless. If you catch yourself adding a mutable instance field to a @Service, stop and ask whether that state belongs in a database, cache, request-scoped bean, or method parameter instead.
  • Reach for @Qualifier/@Primary disambiguation before reaching for programmatic bean registration — the declarative tools cover 95% of real-world ambiguity scenarios.
  • Understanding why each annotation exists (not just its syntax) is what separates a candidate who can debug an unfamiliar Spring codebase in an interview/on-call scenario from one who's only memorized flashcards.
🎯 Rapid-Fire Round

Master Interview Q&A Bank — Section 2

Backend-developer-focused rapid-fire questions on beans, autowiring, and scopes — the single most heavily tested area of Spring Core in real interviews.

FAANGA singleton bean depends on a prototype bean. Walk through exactly what goes wrong with naive field injection, and fix it live.

Naive field/constructor injection resolves the prototype dependency once, at the moment the singleton itself is constructed (since the singleton is only built once, dependency resolution for it also only happens once). Every subsequent use of that field returns the same prototype instance forever — defeating "fresh instance every time." Fix: inject ObjectProvider<PrototypeBean> instead of the bean directly, and call .getObject() at the point of actual use inside a method, so a fresh lookup happens on every call.

FAANGExplain the full bean resolution algorithm Spring uses when injecting a type with multiple candidates.

(1) Collect all beans matching the required type. (2) If exactly one, inject it — done. (3) If a @Qualifier is present at the injection point, filter to the bean(s) matching that qualifier value; if exactly one match remains, inject it. (4) If no qualifier and exactly one candidate is marked @Primary, inject that one. (5) If still ambiguous, try matching the injection point's field/parameter name against a bean's registered name. (6) If still ambiguous, throw NoUniqueBeanDefinitionException. For collection types (List/Set/Map), skip all of this and inject every matching bean instead.

CoreWhat's the practical difference between @Component-based beans and @Bean-method beans when it comes to scope?

None — scope (singleton/prototype/request/etc.) is configured identically for both via @Scope, whether it's placed on the @Component class itself or on the @Bean method. The registration mechanism (scanning vs explicit factory method) is orthogonal to scope behavior.

FAANGWhy does Spring make singleton the default scope rather than prototype?

Most application components — services, repositories, controllers — are naturally stateless: their behavior doesn't depend on per-call mutable state, only on the (typically immutable) collaborators injected at construction time. For such components, creating a new instance per use wastes memory and CPU for zero benefit, since there's nothing instance-specific to isolate. Singleton reuse is both a memory/performance optimization and reflects how most well-designed OOP service classes should actually behave. Prototype exists specifically as an escape hatch for the minority of genuinely stateful component types.

CoreHow would you unit test a class using constructor injection versus one using field injection?

Constructor injection: trivial — new MyService(mockDependency) directly in a plain JUnit test, no Spring context, no reflection tricks, fast test execution. Field injection: requires either starting a (slow) Spring test context with @SpringBootTest/@ContextConfiguration, or using Mockito's @InjectMocks which uses reflection to forcibly set private fields — workable, but slower to set up and more fragile (breaks silently if field names change unexpectedly, and can't easily test with final immutable fields). This is the single most concrete, practical argument for constructor injection in an interview.

FAANGYou need a bean whose implementation is chosen at runtime based on a request header (e.g., "region: US" vs "region: EU"). Design this using what you've learned.

Register each regional implementation as a named bean (custom @Component("usGateway"), @Component("euGateway")), then inject a Map<String, PaymentGateway> into the dispatching service — Spring auto-populates it keyed by bean name. At request time, look up gatewayMap.get(region + "Gateway") to dynamically dispatch without hardcoding a switch statement or relying on ApplicationContext.getBean() lookups. This combines the stereotype-naming, multiple-implementation, and collection-injection concepts from this section into one realistic system design answer.

CoreWhat's the risk of overusing @Primary across a large codebase?

It can silently mask ambiguity that should have been made explicit — a new implementation added later might unexpectedly become "the" default for dozens of injection points across the codebase without any of them being touched, since @Primary is a global, implicit default rather than a per-injection-point decision. In large teams, explicit @Qualifier usage at genuinely ambiguous injection points is often safer and more self-documenting than relying heavily on @Primary.
