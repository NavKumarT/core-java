Creating a Cloud Database with AWS RDS (MySQL)

Video: Creating a Cloud Database with AWS RDS (MySQL)

RDS (Relational Database Service) is AWS's managed relational database offering — AWS handles provisioning, patching, backups, and failover, so the team never has to ssh into a box and manually run apt install mysql-server the way Section 4's local Docker MySQL setup worked. This directly parallels Section 4's own "why Docker instead of installing MySQL locally" argument, one layer further up the stack: RDS is to production infrastructure what Docker Compose was to local development.

RDS SETUP CHECKLIST (the moving parts): DB Engine + Version -> MySQL 8.0 (matching what Section 4 used locally) Instance Class -> e.g. db.t3.micro (Free Tier eligible - right-sized for learning/small workloads, NOT production scale) Storage -> allocated GB, with optional auto-scaling VPC + Subnet Group -> WHICH network the database lives inside (see the Networking section below) Security Group -> the FIREWALL rule controlling who can even reach port 3306 at all (see Networking section) Master username/password -> NEVER reused elsewhere, ideally auto-generated and stored in Secrets Manager, not typed by hand Public accessibility -> "No" in any real setup - the database should NEVER be directly reachable from the public internet Multi-AZ deployment -> optional automatic standby replica in a second Availability Zone, for high availability
⚠ "Public Accessibility: No" Is a Critical, Frequently-Tested Security Default

An RDS instance should never be directly reachable from the public internet — it should sit in a private subnet, reachable only from the application's own compute resources (the Elastic Beanstalk-managed EC2 instances, in this section's setup) via a tightly-scoped security group rule, never from 0.0.0.0/0. This is the cloud-infrastructure equivalent of Section 9's "never expose Actuator's sensitive endpoints publicly" principle — the database is the single most sensitive resource in the entire system, and the blast radius of a publicly-reachable, directly-attackable database is enormous compared to almost any other misconfiguration.

ConceptWhat It Means
Multi-AZAWS automatically maintains a synchronously-replicated standby copy of the database in a different Availability Zone (a physically separate data center within the same region) — if the primary fails, AWS automatically fails over to the standby, typically within seconds to low minutes, with no application-level code changes needed
Read ReplicaA separate, asynchronously-replicated copy specifically for offloading read traffic — directly connects to Section 10's readOnly=true transaction discussion, whose real payoff (routing reads to a replica) requires exactly this kind of infrastructure to exist
Automated backupsRDS can automatically take daily snapshots and retain transaction logs, enabling point-in-time recovery to any second within the retention window — infrastructure-level durability beyond what Section 4's local Docker-volume persistence provided
Parameter GroupA named set of database engine configuration values (e.g., MySQL's max_connections) — the RDS equivalent of a my.cnf file, but managed declaratively through AWS rather than edited directly on a server
FAANGMulti-AZ vs Read Replicas — both involve a second copy of the database. What's the fundamental difference in purpose, and could a system need both?

Multi-AZ exists for availability/disaster recovery — its standby is not directly usable for serving any traffic at all (in the classic Multi-AZ model); its sole job is to be ready to instantly become the new primary if the original primary fails, via synchronous replication guaranteeing zero data loss on failover. Read replicas exist for scaling read throughput — they're asynchronously replicated (meaning a small, real replication lag exists, connecting back to Section 10's isolation-level/staleness discussion) and are actively queryable, specifically to offload read-heavy traffic away from the primary. A real production system commonly uses both simultaneously: Multi-AZ for the primary's own failover resilience, plus one or more read replicas (which can themselves be Multi-AZ) to scale read capacity — they solve genuinely different problems and are not substitutes for each other.

CoreWhy would a team choose RDS over simply running MySQL themselves on an EC2 instance, given EC2 is generally cheaper?

RDS's higher cost buys away substantial undifferentiated operational burden: automated backups and point-in-time recovery, automated minor-version patching, Multi-AZ failover, and read-replica management all come essentially "for free" (i.e., without a team having to build and maintain that automation themselves). Self-managing MySQL on EC2 means a team is directly responsible for all of that — writing and testing their own backup scripts, handling patching windows, building their own failover automation — real engineering time that could instead go toward the application itself. The trade-off genuinely favors RDS for the vast majority of teams; self-managed database-on-EC2 is typically only justified by very specific needs RDS doesn't support (an unusual database engine/version, extremely fine-grained OS-level tuning) or extreme cost sensitivity at a scale where the operational trade-off has been carefully re-evaluated.

💡 EB as "Training Wheels" for Understanding the Full AWS Compute Stack

The most valuable way to think about Elastic Beanstalk for interview purposes: it doesn't replace EC2/ALB/Auto Scaling — it automatically provisions and wires them together using sensible defaults. Everything EB does under the hood is a real, individually-inspectable AWS resource (visible and directly editable in the EC2/ELB consoles) — meaning the skills learned deploying via EB (environment variables, health checks, scaling) transfer directly to understanding and eventually hand-configuring the same underlying services without EB's automation layer, which is exactly the trajectory a growing team often takes as its infrastructure needs become more custom than EB's opinionated defaults comfortably support.

FAANGHow does Elastic Beanstalk know whether a deployed instance is healthy enough to receive traffic — does this connect to anything covered earlier in the course?

Directly, yes — EB's Application Load Balancer performs periodic HTTP health checks against a configurable path on each EC2 instance, and Spring Boot Actuator's /actuator/health endpoint (Section 12) is the standard, idiomatic target to point that health check at. If an instance's health check starts failing, the ALB stops routing new traffic to it, and the Auto Scaling Group can be configured to automatically terminate and replace an unhealthy instance — the exact same liveness/readiness philosophy from Section 12's Kubernetes discussion, just implemented through AWS's own load-balancer/Auto-Scaling-Group health-check mechanism rather than Kubernetes probes specifically. This is a genuinely excellent, concrete example of how Section 12's Actuator investment pays off directly in a real cloud deployment.

CoreWhat's the practical trade-off of using Elastic Beanstalk versus manually configuring EC2, an ALB, and an Auto Scaling Group yourself?

EB trades fine-grained control for speed and simplicity — for a standard Spring Boot web application, EB's defaults handle the vast majority of real needs (health-checked instances behind a load balancer, automatic scaling, rolling deployments) with a fraction of the manual setup time, letting a small team or an individual developer get a genuinely production-viable deployment running in minutes rather than hours of manually wiring together individual AWS services and their interconnected configuration. The trade-off appears once an application's infrastructure needs diverge meaningfully from EB's opinionated defaults — highly custom networking topology, non-standard scaling triggers, or infrastructure shared/coordinated tightly with other non-EB-managed services — at which point a team often migrates to hand-configured EC2/ECS/Kubernetes for the additional control, exactly the trajectory the previous tip described.

Deleting Cloud Resources — Avoiding Unnecessary Costs

Video: Deleting Cloud Resources - Avoiding Unnecessary Costs

A genuinely important, frequently-overlooked closing lesson: cloud resources bill continuously for as long as they exist, regardless of whether they're actually being used — an EB environment and an RDS instance left running after a learning exercise will keep generating charges indefinitely.

ResourceWhat to Check Before Deleting
Elastic Beanstalk environmentTerminating the environment automatically tears down its EC2 instances, Auto Scaling Group, and Load Balancer together — but confirm this actually happened in the EC2 console afterward, since orphaned resources can sometimes survive an incomplete termination
RDS instanceBy default, RDS takes a final snapshot on deletion unless explicitly told to skip it — an easily-missed setting that leaves a (billed, if past the free tier) snapshot lingering indefinitely; deliberately decide whether you want that final snapshot or not
Any associated Elastic IP addressesAWS charges for an Elastic IP that is allocated but not currently attached to a running resource — a very easy-to-miss lingering cost specifically because it looks "free" if you don't know this rule
S3 buckets / CloudWatch log groupsStorage-based resources continue billing for their stored data even after the compute resources that created them are gone
⚠ Set a Billing Alarm — The Single Best Piece of Practical Advice Here

Beyond manually remembering to delete resources, configuring an AWS Budgets billing alarm (a free feature) to email/notify if account spending crosses a small threshold (e.g., $5) is the practical safety net every learner and every real production account should have — catching a forgotten resource, a runaway Auto Scaling Group, or a genuine misconfiguration before it becomes a meaningful, surprising bill, rather than discovering it weeks later.

CoreWhy would a real production team NOT simply delete and recreate an RDS instance to save costs when it's not actively needed (e.g., overnight)?

Unlike compute (which can be trivially stopped and restarted, or scaled to zero via Auto Scaling for genuinely idle periods), a database holds stateful, valuable data — deleting and recreating it isn't a cost-neutral, reversible operation the way stopping a stateless EC2 instance is, since every deletion risks permanent data loss unless a careful backup/restore process is followed perfectly. For genuinely non-production, cost-sensitive environments (a demo/staging database used only during business hours), the more common practice is to stop the RDS instance (available for up to 7 consecutive days per stop, after which AWS auto-restarts it) rather than delete it — pausing compute billing while the underlying storage (and its data) persists safely, a meaningfully different and much safer operation than deletion.

⚠ The Precise, Frequently-Tested Security Group Rule for This Course's Architecture

The correct security group configuration for the RDS instance from topic 232 is: allow inbound traffic on port 3306 (MySQL) only from the security group attached to the Elastic Beanstalk EC2 instances — never from 0.0.0.0/0 (meaning "anywhere on the internet"). This is expressible in the AWS console/CLI as a security-group-to-security-group reference rather than an IP range, which is more robust than an IP-based rule since it automatically continues to work correctly even as EB's Auto Scaling Group adds or removes instances with different IP addresses over time.

FAANGWhat's the practical difference between a Security Group and a Network ACL, and why do both exist?

Security Groups are stateful (a rule allowing inbound traffic on a port automatically allows the corresponding outbound response traffic, with no separate outbound rule needed) and apply at the individual instance level — the primary, fine-grained tool for controlling access to a specific resource, exactly as used for the RDS rule above. NACLs are stateless (inbound and outbound rules must both be explicitly defined, since nothing is automatically inferred) and apply at the subnet level, evaluated as an additional, broader layer before traffic even reaches a security group's rules. Both existing together provides defense-in-depth — a NACL can act as a coarse, subnet-wide safety net (e.g., explicitly blocking a known-malicious IP range at the subnet boundary) independent of and prior to whatever fine-grained rules individual security groups define, though in practice most teams rely primarily on security groups and leave NACLs at their permissive defaults unless there's a specific broader-boundary need.

IAM — Users, Roles & Policies

IAM (Identity and Access Management) is AWS's own authentication/authorization system — and the parallel to Section 6/9's Spring Security material is close enough to be genuinely useful for building intuition quickly.

IAM ConceptRoleSpring Security Parallel
IAM UserA long-lived identity representing a specific person or application, with its own credentials (password, access keys)Roughly analogous to a User entity (Section 7)
IAM PolicyA JSON document defining exactly what actions are allowed/denied on which AWS resources — explicit, deny-by-defaultAnalogous to a GrantedAuthority collection (Section 9) — a set of specific permissions
IAM RoleA set of permissions that can be assumed temporarily by a trusted entity (an EC2 instance, a Lambda function, another AWS account) — no long-lived credentials involved at allNo direct Spring Security equivalent — closer to a temporary, scoped JWT (Section 6) issued for a specific purpose and automatically expiring
💡 The Single Most Important IAM Best Practice for a Backend Developer to Know

An EC2 instance (or an Elastic Beanstalk environment) should be given an IAM Role, not hardcoded IAM User access keys — an Instance Profile attaches an IAM Role directly to the EC2 instance, letting the application code call other AWS services (S3, Secrets Manager) using temporary, automatically-rotated credentials that AWS manages entirely behind the scenes, with zero access keys ever appearing in application configuration or source code at all. This is the AWS-native analog of Section 11's entire "never hardcode secrets" externalized-configuration philosophy, applied specifically to AWS-to-AWS authentication rather than application-level secrets like a database password.

FAANGWhy is an IAM Role considered significantly more secure than a hardcoded IAM User access key pair, beyond just "it's the recommended practice"?

A hardcoded access key pair is a long-lived, static secret — if it leaks (accidentally committed to a public repo, exposed in a log, present in a compromised container image), it remains valid and exploitable until someone notices and manually rotates it, potentially a long exposure window. An IAM Role's credentials are automatically generated, short-lived, and continuously rotated by AWS's internal metadata service, and are scoped to a specific instance's lifetime — there is no static secret to ever leak in the first place, since the credentials aren't retrieved via any mechanism an attacker examining application code or config could directly discover; they're fetched dynamically from the instance's own metadata endpoint at runtime by the AWS SDK. This is a structurally stronger security posture, not merely a "best practice by convention" — directly paralleling why Section 6 preferred short-lived JWTs with a refresh mechanism over long-lived static tokens.

Load Balancing & Auto Scaling

ConceptExplanation
Application Load Balancer (ALB)Operates at Layer 7 (HTTP) — can route based on URL path/host header, terminate TLS/HTTPS, and perform the health checks discussed in topic 233's Q&A. The correct choice for a typical REST API like this course's job portal.
Network Load Balancer (NLB)Operates at Layer 4 (TCP) — far higher raw throughput and lower latency, but no HTTP-aware routing/health-check capability. Used for extreme-performance or non-HTTP (raw TCP) workloads — not the typical choice for a Spring Boot REST API.
Auto Scaling Group (ASG)Automatically adds/removes EC2 instances based on a defined scaling policy (e.g., target average CPU utilization, or request count per instance) — directly extends Section 6's "stateless JWT enables horizontal scaling" discussion into concrete, automated infrastructure that acts on that statelessness
⚠ Auto Scaling Genuinely Requires the Statelessness Section 6 Argued For

This is worth stating explicitly as a direct, concrete payoff: an Auto Scaling Group can terminate any instance at any time (scaling down, or replacing an unhealthy one) and start fresh new instances at any time (scaling up) — an application relying on server-side session state (the architecture Section 7's CSRF topic built and explicitly warned doesn't scale horizontally) would silently lose active user sessions every time the ASG scales down an instance holding those sessions, or would need sticky-session load-balancer configuration as an awkward workaround. The stateless JWT architecture built across Sections 6–7 is precisely what makes Auto Scaling behave correctly and transparently — any request can be served by any instance, with zero session-affinity requirements at all.

FAANGDuring a deployment (a new application version rolling out), how does the ALB avoid routing traffic to an instance that's mid-restart or not yet ready?

The ALB continuously health-checks every registered instance (via the Actuator-backed health check from topic 233's Q&A) and only routes traffic to instances currently reporting healthy — an instance being replaced during a rolling deployment is automatically taken out of the routing pool the moment its health check starts failing (or before it's added to the pool at all, if using a "connection draining"/deregistration-delay configuration that waits for in-flight requests to complete before removing an old instance). This is the mechanism underneath Elastic Beanstalk's rolling deployment strategy, covered next.

⚠ Why Local-Disk File Storage Breaks the Moment You Add a Second Instance

This is a very concrete, easy-to-miss consequence of horizontal scaling (this section's Auto Scaling discussion): if Section 11's resume/profile-image upload feature saved files to the EC2 instance's own local disk, a file uploaded while a request happened to land on Instance A would be completely invisible to a later request that the load balancer routes to Instance B — each instance has its own separate, non-shared disk. S3 solves this structurally: every instance in the Auto Scaling Group reads and writes to the exact same shared, durable object store, regardless of which specific instance handled any given request — making file storage genuinely stateless-compatible in the same way the JWT architecture made authentication stateless-compatible.

FAANGDesign the complete, correct file-upload architecture for Section 11's resume-upload feature, now that it needs to run on a horizontally-scaled Elastic Beanstalk environment.

The Spring Boot upload endpoint (Section 11's MultipartFile handling) receives the file, validates it (content-type/size, per Section 11's security warning), then uploads it directly to an S3 bucket via the AWS SDK — using an IAM Role attached to the EB EC2 instances (this section's IAM topic) rather than hardcoded AWS credentials, scoped via an IAM policy to only allow PutObject/GetObject on that specific bucket. The application stores only the resulting S3 object key/URL in the UserProfile entity's resumeUrl field (Section 11's schema) — the actual file bytes never touch the EC2 instance's own persistent disk at all beyond transient in-memory/temp handling during the upload request itself. This answer synthesizes Section 11's upload feature, this section's IAM and S3 material, and the Auto-Scaling-driven statelessness requirement into one complete, correct, production-appropriate design.

Deployment Strategies — Rolling, Blue/Green & Immutable

StrategyHow It WorksTrade-off
All at onceEvery instance updated simultaneouslyFastest, but causes a full outage during the deploy window — never appropriate for a real production system
RollingInstances updated in small batches, one batch at a time, with the ALB routing only to still-healthy instances throughoutZero downtime, but the old and new application versions run simultaneously for the duration of the rollout — requires the new version to be backward-compatible with whatever the old version expects (a real constraint on database schema changes, in particular)
ImmutableAn entirely new, full-size set of instances is provisioned with the new version, health-checked completely, and only then does traffic cut over — the old instances are then terminatedSafest (a bad deploy never touches any traffic at all until proven healthy), but temporarily doubles resource usage/cost during the deployment window
Blue/GreenTwo complete, independent environments ("blue" = current live, "green" = new version) exist simultaneously; traffic is cut over (often instantly, via DNS or load-balancer target swap) once "green" is fully validatedEnables instant, trivial rollback (just cut traffic back to "blue"), but requires maintaining two full environments, and needs careful handling of any shared stateful resources (like the RDS database) between them
💡 Why "Rolling" Deployments Directly Constrain How You Change a Database Schema

This is a genuinely important, often-overlooked connection back to Section 4's Flyway/Liquibase discussion: during a rolling deployment, old and new application code run against the same database simultaneously for some period — meaning a schema migration that renames or removes a column the old version still expects would break every still-running old-version instance mid-rollout. The safe pattern is backward-compatible, multi-step migrations: add a new column alongside the old one (deploy 1), migrate the application to write to both and read from the new one (deploy 2), then finally drop the old column only once every instance is confirmed running the new version (deploy 3) — a direct, practical consequence of choosing rolling deployments that's easy to overlook until it causes a real production incident.

FAANGElastic Beanstalk supports several of these deployment policies out of the box. How would you choose between "Rolling with additional batch" and "Immutable" for a production job-portal API?

"Rolling with additional batch" (EB briefly provisions one extra batch of new-version instances before starting to remove old ones, avoiding the reduced-capacity dip a plain rolling deployment causes mid-rollout) is a reasonable middle ground for most workloads — solid deployment safety without doubling the entire fleet's cost for the deployment window. "Immutable" is the stronger, more conservative choice specifically when a deployment carries genuine risk of being fundamentally broken (a major dependency upgrade, a significant refactor) — its complete test-before-cutover behavior means a catastrophically bad deploy never receives any real user traffic at all, at the cost of temporarily doubling compute spend during the rollout. For routine, low-risk deploys of a well-tested change, the extra cost/complexity of full immutable deployments is usually unnecessary; reserving it for higher-risk releases is the pragmatic, commonly-cited approach.

These questions probe whether a candidate's AWS knowledge is genuinely operational — the kind that shows up in real "tell me about a system you deployed" conversations, not just service-name recall.

FAANGWalk through the complete, secure architecture for deploying this course's job-portal application to AWS production, from a request hitting the internet to the database — naming every component and why it's there.

A request hits a Route 53 DNS record, resolving to an Application Load Balancer in a public subnet (this section's Networking topic), which terminates HTTPS and performs Actuator-backed health checks (Section 12) against instances in an Auto Scaling Group (this section's Scaling topic) running in a private subnet — each instance an EC2 host running the Spring Boot JAR (Section 1) under an Elastic Beanstalk-managed environment (topic 233), authenticating requests via stateless JWTs (Sections 6–7) that require zero server-side session state, making horizontal scaling correct by construction. Each instance carries an IAM Role (this section's IAM topic), not hardcoded credentials, granting scoped access to Secrets Manager (for the DB password and JWT signing key) and S3 (for resume/profile-image uploads, per this section's Secrets & Storage Q&A). Database writes go to RDS MySQL (topic 232) in its own private subnet, reachable only via a security-group-to-security-group rule from the application instances, with Multi-AZ enabled for failover and automated backups for durability. Deploys use a rolling strategy (this section's Deployment Strategies topic) with schema migrations designed to be backward-compatible across the rollout window, per Flyway/Liquibase practices from Section 4. This is the complete, synthesized answer this entire course — and especially this final section — was building toward.

FAANGYour Elastic Beanstalk application intermittently returns 502 Bad Gateway errors under moderate load, though CPU utilization looks normal. Walk through your diagnostic process using this section's concepts.

A 502 from the ALB typically means the ALB couldn't get a valid response from a backend instance in time — normal CPU rules out simple compute exhaustion, so the investigation shifts elsewhere. Check: (1) the ALB's target-group health-check settings — an overly aggressive health-check timeout/interval combined with a slow Actuator health check (e.g., a health indicator that itself makes a slow downstream call, Section 12's health-check design discussion) could be flapping instances in and out of the healthy pool; (2) whether database connection pool exhaustion is occurring — check RDS's DatabaseConnections CloudWatch metric against the configured HikariCP pool size, since a connection-pool bottleneck (possibly from Section 10's "long-running transaction holding a connection open during a slow external call" pitfall) would cause request threads to queue and time out well before CPU utilization rises meaningfully; (3) whether the Auto Scaling Group's scaling policy is too conservative, only reacting after load has already caused timeouts rather than scaling proactively ahead of demand; (4) trace data (Section 12) for the affected time window, to see exactly which span within a slow/failed request is the actual bottleneck rather than guessing. This kind of multi-hypothesis, evidence-driven diagnostic process — rather than jumping to a single guessed fix — is exactly what a strong production-operations answer looks like.

CoreA teammate suggests storing the RDS database password directly as a hardcoded Elastic Beanstalk environment property (typed into the console) rather than referencing Secrets Manager. What's the actual risk, given it's still "externalized" per Section 11's principles?

It's a genuine improvement over hardcoding in source code, but still falls short of best practice in a few concrete ways: (1) EB environment properties are visible in plaintext to anyone with read access to the EB console/API for that environment — broader exposure than Secrets Manager's fine-grained IAM-policy-gated access; (2) there's no automatic rotation — a compromised password requires a manual, coordinated update across every place it's referenced; (3) it isn't centrally audited or versioned the way Secrets Manager tracks secret access and changes. The practical middle ground many teams use is exactly what topic 233 demonstrated — reference the secret's Secrets Manager ARN from within the EB environment property value itself ({{resolve:secretsmanager:...}}), getting environment-variable-based externalization's simplicity while the actual secret value lives in, and is protected by, the purpose-built secrets-management service.

FAANGHow would this entire architecture need to change if the team decided to migrate from Elastic Beanstalk to ECS/Fargate?

The application itself needs almost no code changes — this is the direct payoff of Section 4's Docker containerization work: the same Spring Boot JAR, packaged into a Docker image via a Dockerfile, becomes the deployable artifact instead of a raw JAR uploaded to EB. Infrastructure concepts largely carry over conceptually (an ALB, an Auto-Scaling-equivalent via ECS Service's desired-count and scaling policies, IAM Roles now attached via ECS Task Roles instead of an EC2 Instance Profile) but are configured through ECS task definitions and service definitions rather than EB's more opinionated, automatic wiring. The most significant genuine difference is operational control: ECS/Fargate requires explicitly defining container resource limits (CPU/memory), health-check commands, and networking mode, where EB previously handled sensible defaults automatically — trading EB's convenience for finer-grained control, exactly the trade-off named in topic 233's Q&A about when teams outgrow EB's defaults. Externalized configuration (environment variables, Secrets Manager references) and the stateless-JWT/S3-file-storage architecture remain entirely unchanged, since neither depends on which specific compute platform is running the container.
