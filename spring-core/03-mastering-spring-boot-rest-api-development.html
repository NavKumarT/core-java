First Look at the App UI & Spring Boot — The Hero of Spring

Videos: First Look at Our Application UI · Introduction to Spring Boot - The HERO of Spring Framework

Spring Boot is called the "hero" of the Spring ecosystem because it solves the single biggest historical complaint about Spring: too much configuration overhead to get a working application running. It layers three things on top of core Spring:

  1. Auto-configuration — inspects the classpath and configures beans automatically based on what's present.
  2. Starter dependencies — curated dependency bundles so you never hand-pick 15 individually-versioned JARs.
  3. Embedded servers — Tomcat/Jetty/Undertow bundled in, producing a self-contained executable JAR — no separate application server installation/deployment required.
💡 The Mental Model to State in Interviews

"Spring Boot doesn't replace Spring — every annotation and container concept from Spring Core (IoC, DI, beans, ApplicationContext) still applies underneath. Spring Boot's job is purely to eliminate the configuration ceremony required to get a Spring application running in production, via auto-configuration, starters, and embedded servers."

The Magic of @RestController

Video: The Magic of @RestController

@RestController = @Controller + @ResponseBody. The critical mechanism to understand: without @ResponseBody, Spring MVC treats a controller method's return String as a logical view name to be resolved by a ViewResolver (e.g., a Thymeleaf template named "hello"). With @ResponseBody present, Spring instead passes the return value to an HttpMessageConverter (Jackson, by default, for JSON) which serializes it directly into the HTTP response body.

@RestController
public class UserController {

    @GetMapping("/users/1")
    public User getUser() {
        return new User("Nikhil", "Backend Engineer");
        // Jackson's MappingJackson2HttpMessageConverter automatically
        // serializes this POJO into: {"name":"Nikhil","role":"Backend Engineer"}
    }
}
FAANGHow does Spring know to convert a Java object to JSON specifically, and could it return XML instead?

Spring MVC uses content negotiation — it inspects the request's Accept header (and other factors like URL suffix or a configured default) to decide which registered HttpMessageConverter to use for serialization. Jackson's JSON converter is registered by default when spring-boot-starter-web is on the classpath and is the default choice absent other signals. If jackson-dataformat-xml is also on the classpath and the client sends Accept: application/xml, Spring can serialize the same object as XML instead — no code change to the controller required, since serialization is entirely decoupled from business logic via the message converter abstraction.

Auto-Configuration — Spring Boot Working Behind the Curtain

Video: Auto-Configuration - Spring Boot Working Behind the Curtain

Auto-configuration is Spring Boot's mechanism for automatically registering beans based on what's present on the classpath, what beans already exist in the context, and what properties are set — without you writing any explicit @Bean methods.

How It Actually Works, Step by Step

  1. At startup, Spring Boot scans META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (in modern Boot 3.x; the older mechanism used spring.factories) inside every JAR on the classpath, collecting a list of candidate auto-configuration classes.
  2. Each candidate class is a normal @Configuration class, but annotated with conditional annotations that gate whether it actually activates.
  3. Spring evaluates each condition; only auto-configuration classes whose conditions are satisfied contribute beans to the context.
Conditional AnnotationActivates When...
@ConditionalOnClassA specific class is present on the classpath (e.g., only configure a DataSource if a JDBC driver class exists)
@ConditionalOnMissingBeanNo bean of that type is already defined — this is exactly how your own custom @Bean silently and safely overrides Spring Boot's default
@ConditionalOnPropertyA specific application.properties/.yml key is set to a given value (or just present)
@ConditionalOnWebApplicationThe app is detected as a web application (servlet or reactive)
@ConditionalOnBeanAnother specific bean already exists in the context
spring-boot-starter-data-jpa on classpath? │ ▼ YES @ConditionalOnClass(DataSource.class) — is javax.sql.DataSource on classpath? YES │ ▼ DataSourceAutoConfiguration activates │ ▼ @ConditionalOnMissingBean(DataSource.class) — did YOU define your own DataSource bean? │ ┌────┴─────┐ NO YES │ │ ▼ ▼ Boot creates Boot backs off — YOUR bean wins, default auto-config silently does nothing HikariCP DataSource
💡 The Golden Rule of Auto-Configuration

"You always win." Every Spring Boot default bean is guarded by @ConditionalOnMissingBean, meaning the moment you define your own bean of that type, Boot's auto-configured default silently steps aside. This is precisely why you can override literally any Spring Boot default — ObjectMapper, DataSource, RestTemplate, security filter chains — just by defining your own @Bean.

FAANGHow would you debug why a particular auto-configuration class did or didn't activate?

Set --debug as a startup flag (or debug=true in application.properties) — Spring Boot prints a detailed "Conditions Evaluation Report" on startup, listing every auto-configuration class as either "Positive matches" (activated, with the exact condition that passed) or "Negative matches" (skipped, with the exact condition that failed and why). This is the single most useful real-world debugging tool for auto-configuration mysteries and is worth naming by name in an interview.

FAANGCan you write your own custom auto-configuration? When would that be appropriate?

Yes — this is exactly how third-party Spring Boot starters work (e.g., a company-internal shared library that auto-configures a standard RestTemplate with company-wide interceptors/timeouts for every microservice). You create a @AutoConfiguration-annotated class (Boot 3.x) with the appropriate @Conditional* guards, then register it in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports inside your library JAR. Appropriate when you want to give consuming teams "it just works" defaults for a cross-cutting concern, the same way Spring Boot itself does for DataSource/ObjectMapper/etc.

CoreWhat's the difference between @Conditional, @ConditionalOnBean, and @ConditionalOnMissingBean?

@Conditional is the low-level, general-purpose building block — you supply a custom Condition implementation with arbitrary matching logic. @ConditionalOnBean/@ConditionalOnMissingBean are specific, ready-made conditions built on top of it, checking presence/absence of a bean of a given type in the context at the point of evaluation. Ordering matters for these two — auto-configuration classes are carefully ordered (via @AutoConfigureOrder/@AutoConfigureAfter/@AutoConfigureBefore) so that "on missing bean" checks run after user-defined beans and higher-priority auto-configurations have already been registered.

REST API Best Practices

Video: REST API Best Practices
PracticeWhy It Matters
Use nouns, not verbs, in URIs (/orders, not /getOrders)HTTP methods already express the verb — the URI should identify a resource
Use the correct HTTP method for the operation's semanticsGET=read (safe, idempotent), POST=create, PUT=full update (idempotent), PATCH=partial update, DELETE=remove (idempotent)
Use plural resource names (/users/42, not /user/42)Consistency and convention across the industry
Return correct HTTP status codes200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 500 Internal Server Error — each communicates precise semantic meaning to clients
Version your APIPrevents breaking existing clients when the contract changes (deep dive later in this section)
Use pagination for large collectionsPrevents unbounded response sizes and memory/latency issues at scale
Support filtering, sorting via query params/orders?status=PENDING&sort=createdAt,desc — keeps endpoints flexible without proliferating one-off routes
Use consistent, structured error responsesA standard error body shape (code, message, timestamp, path) makes client-side error handling predictable
Idempotency for PUT/DELETECalling the same request multiple times produces the same end state — critical for safe retries over unreliable networks
HATEOAS (optional, advanced)Responses include hyperlinks to related/next actions, letting clients discover the API dynamically rather than hardcoding URLs
⚠ Common REST Design Mistakes Interviewers Probe For
  • Using GET for state-changing operations (breaks caching/idempotency assumptions and is a CSRF risk).
  • Returning 200 OK for everything, including errors, with the "real" error status buried in the response body.
  • Deeply nested URIs beyond 2–3 levels (/users/1/orders/5/items/3/reviews/9) — usually a sign resources should be flattened or accessed by their own top-level endpoints with filters.
  • Not handling partial failures consistently in batch endpoints.
FAANGWhat's the difference between PUT and PATCH, and why does idempotency matter for each?

PUT replaces the entire resource with the payload provided — calling it twice with the same body leaves the resource in the same final state (idempotent). PATCH applies a partial update (e.g., "increment counter by 1" or "set only the email field") — it is not inherently idempotent unless deliberately designed that way (e.g., "set email to X" is idempotent; "increment counter by 1" is not, since repeating it changes the result each time). This distinction matters heavily for safe client-side retry logic over flaky networks — clients can safely retry idempotent operations blindly, but must be more careful retrying non-idempotent ones (e.g., using idempotency keys).

CoreWhy is GET considered a "safe" method in addition to idempotent?

"Safe" (per the HTTP spec) means the method causes no server-side state change at all — it's purely a read. "Idempotent" is a weaker guarantee — repeating the call produces the same end state, but state may still have changed on the first call (e.g., DELETE is idempotent — deleting an already-deleted resource still leaves it deleted — but not safe, since the first call did change state). GET is both safe and idempotent; DELETE and PUT are idempotent but not safe; POST is neither by default.

💡 401 vs 403 — A Frequently Confused Pair

Mastering @RequestMapping

Video: Mastering @RequestMapping

@RequestMapping is the general-purpose, original mapping annotation — @GetMapping, @PostMapping, @PutMapping, @PatchMapping, and @DeleteMapping are all just method-specific shorthand/meta-annotations built on top of it (e.g., @GetMapping = @RequestMapping(method = RequestMethod.GET)).

@RestController
@RequestMapping("/api/v1/orders")   // class-level base path
public class OrderController {

    @RequestMapping(method = RequestMethod.GET)        // -> GET /api/v1/orders
    public List<Order> getAll() { ... }

    @RequestMapping(value = "/{id}", method = RequestMethod.GET) // -> GET /api/v1/orders/{id}
    public Order getOne(@PathVariable Long id) { ... }
}
@RequestMapping(
    value = "/orders",
    method = RequestMethod.POST,
    consumes = "application/json",   // only matches requests WITH this Content-Type
    produces = "application/json"    // sets the response Content-Type
)
public Order createOrder(@RequestBody Order order) { ... }
💡 Why the Shorthand Annotations Are Preferred Today

Modern Spring code almost universally prefers @GetMapping/@PostMapping/etc. over raw @RequestMapping(method=...) — purely for readability and to reduce boilerplate. Knowing that they're built on top of @RequestMapping (rather than being unrelated) is what interviewers are actually testing when they ask about this.

⚠ @RequestBody Is Fundamentally Different From @ModelAttribute

@RequestBody deserializes the entire request body (typically JSON) into one object using an HttpMessageConverter. @ModelAttribute instead binds individual form fields or query parameters into an object's properties via Spring's data binder — used for traditional HTML form submissions, not JSON APIs. Going Deeper with RequestEntity

Video: Going Deeper with RequestEntity

RequestEntity<T> represents the entire incoming HTTP request — method, URI, headers, AND body — as a single object, giving you full low-level access in one parameter instead of separately injecting @RequestHeader/@RequestBody/etc.

@PostMapping("/orders")
public ResponseEntity<Order> create(RequestEntity<OrderRequest> requestEntity) {
    HttpHeaders headers = requestEntity.getHeaders();
    OrderRequest body = requestEntity.getBody();
    HttpMethod method = requestEntity.getMethod();
    URI uri = requestEntity.getUrl();

    Order order = orderService.create(body);
    return ResponseEntity.ok(order);
}
ℹ Server-Side vs Client-Side Usage

RequestEntity shows up in two very different contexts: (1) as a controller method parameter (server-side, as above — relatively uncommon in practice since individual annotations are usually cleaner), and (2) far more commonly, as something you build yourself when making outgoing HTTP calls with Spring's RestTemplate/RestClient as a client — e.g. RequestEntity.post(uri).header(...).body(...). Knowing both usages shows depth.

Tailored Responses with ResponseEntity

Video: Tailored Responses with ResponseEntity

ResponseEntity<T> gives you full control over the status code, headers, AND body of the HTTP response — unlike returning a plain object (which always returns 200 OK with default headers), or a plain String (ambiguous with view-name resolution outside @RestController).

@GetMapping("/{id}")
public ResponseEntity<Order> getOrder(@PathVariable Long id) {
    return orderService.findById(id)
            .map(ResponseEntity::ok)                       // 200 OK + body
            .orElseGet(() -> ResponseEntity.notFound().build()); // 404, no body
}
@PostMapping
public ResponseEntity<Order> create(@Valid @RequestBody OrderRequest request) {
    Order created = orderService.create(request);
    URI location = ServletUriComponentsBuilder
            .fromCurrentRequest().path("/{id}")
            .buildAndExpand(created.getId()).toUri();

    return ResponseEntity.created(location).body(created);  // 201 + Location header
}
@GetMapping("/export")
public ResponseEntity<Resource> exportCsv() {
    return ResponseEntity.status(HttpStatus.OK)
            .header("Content-Disposition", "attachment; filename=orders.csv")
            .contentType(MediaType.parseMediaType("text/csv"))
            .body(csvResource);
}
Return TypeStatus ControlHeader ControlWhen to Use
Plain object (Order)❌ Always 200 (or 500 on exception)❌ NoSimple, always-200 read endpoints
ResponseEntity<Order>✅ Full control✅ Full controlAnything needing a specific status (201, 404, 204) or custom headers — the production-grade default
FAANGWhy should a POST that creates a resource return ResponseEntity with 201 and a Location header, rather than just 200 with the object?

Per REST/HTTP semantics, 201 Created precisely communicates "a new resource now exists" — distinct from 200 OK's generic "request succeeded." The Location header is the standard, discoverable way to tell the client exactly where the newly created resource can be retrieved (GET'd) going forward, without the client having to guess or parse it out of the response body. This is a textbook REST best-practices question that also validates whether a candidate actually understands HTTP status code semantics versus just returning 200 for everything.

CoreHow would you globally standardize error responses across every controller, instead of building ResponseEntity manually in every catch block?

Use a centralized @ControllerAdvice (or @RestControllerAdvice) class with @ExceptionHandler methods per exception type. This keeps individual controller methods focused purely on business logic — they simply throw meaningful exceptions — while a single, testable, cross-cutting component maps each exception type to a consistent ResponseEntity with the right status code and a standard error body shape (this pattern is covered in depth in later exception-handling sections of the course).

API Versioning — Why It Matters & Every Strategy

Videos: Why API Versioning Matters · API Versioning Strategies · Traditional Methods · ApiVersionConfigurer Parts 1–2

Why Versioning Matters

Once an API is live, external and internal clients build hard dependencies on its exact contract (URL shape, request/response fields, status codes). Any breaking change — renaming a field, changing a type, removing an endpoint — breaks every client still using the old contract. Versioning lets you evolve the API while keeping old clients working until they can migrate, avoiding a "big bang" coordinated release across every consumer simultaneously.

⚠ Breaking vs Non-Breaking Changes

Non-breaking (usually safe without a version bump): adding a new optional field to a response, adding a new endpoint, adding a new optional query param. Breaking (requires a new version): removing/renaming a field, changing a field's type, changing required-ness of a request field, changing URL structure, changing error response shape.

Versioning Strategies — Compared

StrategyExampleProsCons
URI Path Versioning/api/v1/orders, /api/v2/ordersExtremely explicit, cacheable, easy to route/document, easiest for clients to understand"Pollutes" the URI — technically the same resource now has two different identifiers across versions
Query Parameter Versioning/api/orders?version=2Keeps the base URI stableEasy to forget/omit; not RESTfully "clean" — a resource's identity shouldn't depend on an optional param
Custom Header VersioningX-API-Version: 2Keeps URIs completely clean; version is metadata, not identityLess visible/discoverable — can't just paste a URL into a browser and see the version; requires header tooling for testing
Media Type / Accept Header Versioning (Content Negotiation)Accept: application/vnd.growthscript.v2+jsonMost "correct" per REST/HATEOAS purists — versioning is a content-negotiation concernMost complex to implement and document; poor tooling ergonomics; steep learning curve for API consumers
💡 What Real Companies Actually Use

URI path versioning is overwhelmingly the industry default (Stripe, GitHub, Twitter/X APIs, most fintech APIs) specifically because of its simplicity, cacheability at the CDN/proxy level, and ease of routing at the API Gateway/load-balancer layer without needing to inspect headers. Header/media-type versioning shows up more in strict REST/HATEOAS-purist shops or specific enterprise API standards. Know the trade-offs, but default to recommending URI versioning unless asked to defend an alternative.

Traditional (Manual) Implementation

@RestController
@RequestMapping("/api/v1/orders")
public class OrderControllerV1 {
    @GetMapping("/{id}")
    public OrderV1Response getOrder(@PathVariable Long id) { ... }
}

@RestController
@RequestMapping("/api/v2/orders")
public class OrderControllerV2 {
    @GetMapping("/{id}")
    public OrderV2Response getOrder(@PathVariable Long id) {
        // e.g. v2 renames "orderStatus" -> "status", adds a new "currency" field
    }
}
@GetMapping(value = "/orders/{id}", headers = "X-API-Version=1")
public OrderV1Response getOrderV1(@PathVariable Long id) { ... }

@GetMapping(value = "/orders/{id}", headers = "X-API-Version=2")
public OrderV2Response getOrderV2(@PathVariable Long id) { ... }
// Spring MVC routes based on the "headers" attribute matching at request-mapping time

The "traditional" approach works but scales poorly: duplicated controller classes per version, or a proliferation of headers=/params= attributes scattered across method signatures. This motivates a more structured, centralized approach.

Modern Approach — ApiVersionConfigurer

Newer Spring Framework versions (Spring 7 / Spring Boot 4-era) introduce first-class API versioning support via ApiVersionConfigurer, configured centrally in a WebMvcConfigurer, plus a dedicated @RequestMapping(version = "...")-style attribute — removing the need to manually branch on headers/params in every method signature.

@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void configureApiVersioning(ApiVersionConfigurer configurer) {
        configurer
            .useRequestHeader("X-API-Version")  // centralize the versioning STRATEGY here
            .setDefaultVersion("1")
            .addSupportedVersions("1", "2");
    }
}
@RestController
@RequestMapping("/orders")
public class OrderController {

    @GetMapping(value = "/{id}", version = "1")
    public OrderV1Response getOrderV1(@PathVariable Long id) { ... }

    @GetMapping(value = "/{id}", version = "2")
    public OrderV2Response getOrderV2(@PathVariable Long id) { ... }
}
ℹ Why This Matters for Interviews

The key architectural insight to communicate — regardless of which specific API surface a given Spring version exposes — is that the versioning strategy (header vs URI vs param) should be configured in exactly one central place, not scattered as ad-hoc conditionals across every controller method. This is the same "convention over configuration, centralized cross-cutting concern" philosophy that runs through Spring Boot's whole design (compare to how @ControllerAdvice centralizes error handling, or how a single security filter chain centralizes auth rules).

FAANGHow would you deprecate and eventually remove an old API version without breaking existing clients?

A staged rollout: (1) ship the new version alongside the old one (both live simultaneously), (2) communicate a deprecation timeline to consumers, often via a Deprecation/Sunset HTTP response header on the old version's responses so clients can programmatically detect it, (3) monitor actual traffic/usage on the deprecated version to know when it's safe to remove, (4) only remove the old version's routes after usage has dropped to zero (or the deadline passed and consumers were given ample warning) — never remove a version based purely on a calendar date without checking real traffic first.

CoreIs URI path versioning "unRESTful," and does that matter practically?

REST purists argue a resource should have exactly one canonical URI, and encoding a version into the path technically means /v1/orders/5 and /v2/orders/5 are "different resources" by URI identity, even though they represent the same underlying entity. In practice, this theoretical purity rarely outweighs URI versioning's practical benefits (simplicity, cacheability, discoverability, gateway-level routing) — which is exactly why it dominates real-world industry usage despite the objection. Good interview answers acknowledge the theoretical critique while explaining the pragmatic trade-off.

FAANGDesign an API versioning approach for a microservice sitting behind an API Gateway.

URI path versioning is typically the best fit here specifically because API Gateways (Kong, AWS API Gateway, Spring Cloud Gateway) route and cache based on URL path patterns very naturally — a gateway rule like /v1/** → order-service-v1-upstream is trivial to express, monitor, and gradually shift traffic weights on (e.g., canary releasing v2 to 5% of traffic) without needing to inspect and branch on request headers at the gateway layer, which is comparatively more complex to configure and observe.

Master Interview Q&A Bank — Section 3

High-frequency REST API and Spring MVC questions for backend/full-stack interviews at product companies and fintechs.

FAANGWalk through the complete request lifecycle for a Spring Boot REST call, from socket to response.

(1) Embedded Tomcat accepts the TCP connection and parses the raw HTTP request. (2) The request reaches Spring MVC's DispatcherServlet (the Front Controller). (3) DispatcherServlet consults HandlerMapping to find the matching controller method based on URL pattern + HTTP method + content-type/headers. (4) Any registered HandlerInterceptors run their preHandle (e.g., auth checks, logging). (5) Method arguments are resolved via HandlerMethodArgumentResolvers — this is where @PathVariable/@RequestParam/@RequestBody extraction and Bean Validation happen. (6) The controller method executes business logic. (7) The return value is converted by an HttpMessageConverter (e.g., Jackson) into the response body, or resolved as a view if not a @RestController. (8) Interceptors' postHandle/afterCompletion run. (9) The response is written back through Tomcat to the client.

FAANGHow does Spring Boot decide port 8080 and how would you change it, and what happens if the port is already in use?

8080 is the embedded Tomcat's built-in default. Override via server.port=9090 in application.properties, an environment variable (SERVER_PORT), or a command-line arg (--server.port=9090) — externalized configuration always wins over hardcoded defaults, following Spring Boot's property precedence order. If the port is already bound by another process, the embedded server fails to start and throws a BindException/PortInUseException, crashing the application at startup (another example of fail-fast behavior) — setting server.port=0 tells Spring Boot to bind to any available random free port instead, commonly used in integration tests running multiple app instances in parallel.

CoreWhat's the difference between @RequestParam, @PathVariable, @RequestHeader, and @RequestBody at a glance?

@PathVariable — extracts a segment from the URI path, identifying a specific resource. @RequestParam — extracts a query-string parameter, typically optional filters/pagination. @RequestHeader — extracts an HTTP header value. @RequestBody — deserializes the entire request payload (usually JSON) into a Java object. All four can be combined freely on a single controller method, each pulling from its own distinct part of the HTTP request.

FAANGA client reports intermittent 404s on an endpoint that works fine in Postman. What would you check?

Systematic checklist: (1) verify the exact HTTP method matches (GET vs POST mismatches are the most common cause), (2) check for trailing-slash mismatches or case-sensitivity in the path, (3) confirm the Accept/Content-Type headers match what the produces/consumes attributes expect — a mismatched consumes on a POST also yields 404/415 depending on Spring version, (4) check if the request is being intercepted/rewritten by an API Gateway, load balancer, or reverse proxy before it even reaches the app, and (5) confirm the client isn't hitting a stale/cached DNS entry or wrong environment (staging vs prod) entirely.

CoreWhy does Spring Boot prefer returning DTOs (Data Transfer Objects) instead of JPA entities directly from a REST controller?

Several reasons commonly cited: (1) decoupling — the API contract shouldn't be tightly bound to the database schema; they can evolve independently, (2) avoiding lazy-loading serialization issues — serializing a JPA entity with lazy-fetched associations outside a transaction throws LazyInitializationException, (3) security — entities may carry sensitive fields (password hashes, internal flags) that should never be exposed in a response, (4) avoiding infinite recursion in bidirectional JPA relationships during JSON serialization. DTOs give explicit, controlled control over exactly what crosses the API boundary.

FAANGHow would you implement request-level rate limiting information in your API responses?

Use custom response headers via ResponseEntity — conventionally X-RateLimit-Limit (max requests allowed), X-RateLimit-Remaining (requests left in the current window), and X-RateLimit-Reset (when the window resets), returned alongside a 429 Too Many Requests status once the limit is exceeded. The actual limiting logic itself typically lives in a HandlerInterceptor or a Servlet Filter (running before the controller method executes), backed by a shared counter store like Redis for correctness across multiple app instances in a horizontally scaled deployment.
