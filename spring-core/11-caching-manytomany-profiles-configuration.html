Spring Caching Essentials — @Cacheable, @CachePut & @CacheEvict

Video: Spring Caching Essentials - @Cacheable, @CachePut & @CacheEvict

Spring's caching abstraction is another concrete, built-in application of the annotation-based AOP pattern from Section 8 — a marker annotation plus an aspect that intercepts method calls, exactly like @Transactional (Section 10).

@SpringBootApplication
@EnableCaching   // activates Spring's caching AOP infrastructure — required, like Section 6's @EnableMethodSecurity
public class JobPortalApplication { ... }
@Service
public class CompanyService {

    @Cacheable(value = "companies", key = "#id")
    public Company getCompanyById(Long id) {
        // this method body only EVER executes on a cache MISS —
        // a cache HIT returns the cached value directly, never invoking this at all
        return companyRepository.findById(id)
                .orElseThrow(() -> new ResourceNotFoundException("Company not found"));
    }
}
// "companies" = the cache NAME (a named region); key = the SpEL expression
// identifying which specific cache entry this call's result belongs to
@CachePut(value = "companies", key = "#company.id")
public Company updateCompany(Company company) {
    // UNLIKE @Cacheable, this ALWAYS executes the method body —
    // then updates the cache with the fresh result, keeping cache and DB in sync
    return companyRepository.save(company);
}
@CacheEvict(value = "companies", key = "#id")
public void deleteCompany(Long id) {
    // removes the entry from the cache — prevents serving stale data
    // for a company that no longer exists at all
    companyRepository.deleteById(id);
}

// evicting the WHOLE cache region at once — useful after a bulk operation
@CacheEvict(value = "companies", allEntries = true)
public void bulkImportCompanies(List<Company> companies) { ... }
AnnotationMethod Body Executes?Cache EffectTypical Use
@CacheableOnly on a cache missPopulates the cache with the resultReads — getById, expensive lookups
@CachePutAlwaysOverwrites the cache entry with the fresh resultWrites that should keep the cache in sync — update
@CacheEvictAlwaysRemoves the entry (or the whole region) from the cacheDeletes, or any write where the cached value is now invalid
💡 This Is Literally Section 8's @Around "Skip the Method" Example, Made Concrete

Section 8's @Around advice topic used a hypothetical caching aspect as its worked example of "an aspect that can skip proceed() entirely." @Cacheable is that exact hypothetical, now real: Spring's built-in caching interceptor checks the configured cache before deciding whether to invoke the real method at all — a cache hit means the underlying method (and everything inside it, including a database round-trip) never executes. Understanding this connection is exactly the kind of retroactive synthesis that demonstrates genuine understanding rather than memorized annotation syntax.

⚠ Self-Invocation Breaks Caching Too — Same Root Cause as @Transactional

Because Spring's caching annotations are proxy-based AOP (identical mechanism to @Transactional, Section 10), calling a @Cacheable method from within the same class bypasses the proxy and silently skips caching entirely — the exact same self-invocation limitation flagged repeatedly since Section 4. This is worth stating explicitly as a pattern: any Spring annotation implemented via proxy-based AOP (@Transactional, @Cacheable/@CachePut/@CacheEvict, @Async, @PreAuthorize) shares this exact same limitation, for the exact same underlying reason.

FAANGWhy does @CachePut always execute the method body, when the whole point of caching is to AVOID executing the method?

Because @CachePut solves a genuinely different problem than @Cacheable: it's for write operations, where the method's job is precisely to change the underlying data — skipping it would mean the update never actually happens at all. Its purpose isn't to avoid computation; it's to keep the cache synchronized with a write that must happen regardless, ensuring a subsequent @Cacheable read immediately after an update returns the fresh value rather than a now-stale cached one. Using @Cacheable on an update method would be a serious bug — it would skip the actual update entirely whenever a cache entry already exists for that key.

Keeping Cache in Sync — @CachePut & @CacheEvict Demo

⚠ The Bug This Demo Is Specifically Designed to Prevent

If step 3 used @Cacheable instead of @CachePut (a genuine, common mistake), the update method would check the cache first, find the (now-stale) cached value from step 1 already present, and skip executing the update entirely — the database would never actually be updated, while the API would appear to succeed. This is a serious, silent correctness bug precisely analogous to Section 10's "forgot to call proceed()"/swallowed-exception class of AOP mistakes — caching bugs, like transaction bugs, tend to fail silently rather than throwing an obvious exception.

Preventing Stale Data with TTL-Based Caching

Video: Preventing Stale Data with TTL-Based Caching

TTL (Time To Live) is an automatic expiry mechanism — a cache entry is evicted after a configured duration has elapsed, regardless of whether any explicit @CacheEvict/@CachePut call ever happens. This matters because @CachePut/@CacheEvict only keep the cache in sync for changes that go through your own application's code paths — they offer zero protection against staleness caused by data changed some other way (a direct database edit, another service writing to the same table, a batch job).

💡 TTL as a Safety Net, Not a Replacement for Explicit Invalidation

The correct mental model: explicit invalidation (@CachePut/@CacheEvict) should handle every change your own application code is aware of, keeping the cache correct immediately. TTL exists as a backstop for staleness from sources outside your application's control — bounding the maximum possible staleness window to "at most TTL seconds old," even in the worst case where explicit invalidation was somehow missed or bypassed. Relying on TTL alone (with no explicit invalidation at all) is a valid, simpler design choice specifically when your data can tolerate being up to TTL-seconds stale and the read volume justifies caching at all — a real trade-off decision, not a shortcut.

FAANGHow would you choose an appropriate TTL value for a given piece of cached data?

The decision balances two competing costs: a longer TTL means fewer cache misses/database round-trips (better performance, lower database load) but a larger window during which stale data might be served; a shorter TTL means fresher data but more frequent cache misses, reducing the caching benefit. The right value depends on the data's actual volatility and business tolerance for staleness — e.g., a company's name/description (rarely changes) can tolerate a long TTL (hours), while something like a job posting's current application count (changes frequently, and staleness could visibly mislead a user) needs a much shorter TTL (seconds to low minutes) or explicit invalidation instead of relying on TTL at all.

Boosting Cache Performance with Caffeine (TTL Included)

Video: Boosting Cache Performance with Caffeine (TTL Included)

Caffeine is a high-performance, in-memory Java caching library — the modern, actively-maintained successor to Google Guava's cache, and the caching provider Spring Boot auto-configures automatically once detected on the classpath (Section 3's auto-configuration philosophy applying here too), replacing the limited default ConcurrentMapCacheManager with zero code changes to the @Cacheable annotations themselves.

<dependency>
    <groupId>com.github.ben-manes.caffeine</groupId>
    <artifactId>caffeine</artifactId>
</dependency>
<!-- Spring Boot's auto-configuration detects this and automatically swaps in
     CaffeineCacheManager — no other code changes needed -->
@Configuration
public class CacheConfig {

    @Bean
    public CacheManager cacheManager() {
        CaffeineCacheManager cacheManager = new CaffeineCacheManager("companies", "jobs");
        cacheManager.setCaffeine(Caffeine.newBuilder()
                .expireAfterWrite(10, TimeUnit.MINUTES)   // TTL from the previous topic, now REAL
                .maximumSize(500)                       // bounds memory use — evicts LEAST RECENTLY USED entries past this size
                .recordStats());                       // exposes hit/miss metrics — useful for Actuator/monitoring
        return cacheManager;
    }
}
CapabilityDefault ConcurrentMapCacheManagerCaffeine
TTL / expiry❌ None — entries live forever until manually evicted✅ expireAfterWrite / expireAfterAccess
Size-bounded eviction❌ None — genuinely unbounded memory growth risk✅ maximumSize, with a near-optimal LRU-like (Window TinyLFU) eviction policy
Statistics/metrics❌ None✅ Hit rate, eviction count, load time — integrates with Micrometer/Actuator
Production-appropriate?❌ Learning/demo purposes only✅ Yes — widely used in real production Spring Boot applications
⚠ Caffeine Is Still a Local, In-Memory Cache — Not a Distributed One

A critical limitation worth naming proactively: Caffeine's cache lives entirely within a single JVM instance's memory. In a horizontally-scaled deployment with multiple application instances behind a load balancer, each instance maintains its own independent Caffeine cache — a write on instance A that evicts/updates instance A's cache entry has no effect on instance B's still-stale cached copy. For true multi-instance cache consistency, a distributed cache (Redis, Memcached) shared across all instances is required instead — Caffeine remains an excellent choice specifically for single-instance deployments, or as a fast local "L1" cache layered in front of a shared "L2" distributed cache in more sophisticated architectures.

FAANGIn a horizontally-scaled Spring Boot deployment (5 instances behind a load balancer) using Caffeine, describe a concrete cache-staleness bug this architecture can produce, and how you'd fix it.

A user's request to update a company (routed by the load balancer to instance A) correctly invalidates/updates instance A's local Caffeine cache via @CachePut. But instances B through E still hold their own independent, now-stale cached copies of that company — a subsequent GET request from the same user, routed to instance B by the load balancer, returns stale data despite the update having genuinely succeeded moments earlier. The architectural fix is switching to a distributed cache (Redis via spring-boot-starter-data-redis plus Spring's RedisCacheManager) — a single shared cache instance all 5 application instances read from and write to, so an update from any instance is immediately visible to reads from every other instance, eliminating the per-instance staleness entirely. This is a genuinely common, realistic system design question testing whether a candidate understands the difference between local and distributed caching.

Designing the User Profile Database & JPA Entities

@Entity
@Table(name = "user_profiles")
public class UserProfile {
    @Id @GeneratedValue private Long id;

    @OneToOne(fetch = FetchType.LAZY)   // extends Section 5's OneToMany/ManyToOne coverage to a 1:1 case
    @JoinColumn(name = "user_id", unique = true, nullable = false)   // UNIQUE enforces true 1:1, not 1:N
    private User user;

    private String fullName;
    private String headline;
    private String resumeUrl;      // points to uploaded file storage — next topic
    private String profileImageUrl;
}
💡 Why unique = true Is What Makes This Genuinely OneToOne, Not Just a Renamed ManyToOne

Structurally, a @OneToOne mapping with a foreign key looks almost identical to @ManyToOne (Section 5) — the real, enforced difference is the unique constraint on the foreign key column. Without it, nothing in the database actually prevents multiple UserProfile rows from referencing the same user_id, silently turning what's meant to be a strict one-to-one relationship into a de facto one-to-many at the data-integrity level, regardless of what the JPA annotation claims. This is a worthwhile detail to know cold — the annotation name alone (@OneToOne) doesn't enforce true one-to-one cardinality; the database constraint does.

Creating REST APIs for User Profile, Resume & Image Upload

Video: Creating REST APIs for User Profile, Resume & Image Upload
@PostMapping(value = "/resume", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public ResponseEntity<String> uploadResume(
        @RequestParam("file") MultipartFile file,
        @AuthenticationPrincipal UserDetails currentUser) {   // pulls the SecurityContextHolder principal directly as a param

    if (file.isEmpty()) {
        throw new IllegalArgumentException("File must not be empty");
    }
    if (!"application/pdf".equals(file.getContentType())) {   // content-type validation — never trust the client
        throw new InvalidFileTypeException("Only PDF resumes are accepted");
    }
    if (file.getSize() > 5 * 1024 * 1024) {   // 5MB limit — prevents abuse/resource exhaustion
        throw new FileTooLargeException("Resume must not exceed 5MB");
    }

    String storedUrl = fileStorageService.store(file, currentUser.getUsername());
    profileService.updateResumeUrl(currentUser.getUsername(), storedUrl);
    return ResponseEntity.ok(storedUrl);
}
⚠ File Upload Endpoints Are a Real Security Surface — Never Trust Client-Supplied Metadata

A client-supplied Content-Type header or filename extension is trivially spoofable — an attacker can rename a malicious executable to resume.pdf and set Content-Type: application/pdf regardless of the file's actual contents. Production-grade file validation should inspect the file's actual magic bytes/binary signature (not just trust the declared content type), enforce a strict size limit (preventing denial-of-service via oversized uploads), store uploaded files outside the web-servable directory or in dedicated object storage (S3, GCS) rather than directly in a path the application server might execute, and generate a new, non-predictable filename server-side rather than trusting any client-supplied filename directly (preventing path traversal attacks like a filename of ../../etc/passwd).

CoreWhat does @AuthenticationPrincipal do, and how does it connect to Section 6's SecurityContextHolder?

@AuthenticationPrincipal is a Spring Security convenience annotation that automatically injects the current request's authenticated principal directly as a controller method parameter — it's pure syntactic sugar over manually calling SecurityContextHolder.getContext().getAuthentication().getPrincipal() (the exact mechanism established in Section 6). Using it keeps controller code clean and avoids repeating that boilerplate lookup in every method that needs to know "who is making this request" — functionally identical to the manual approach, just more ergonomic.

@Entity
public class User implements UserDetails {
    // ... existing fields from Section 7

    @ManyToMany(fetch = FetchType.LAZY)   // LAZY is the sensible default here — see Section 5's
    @JoinTable(                          // eager-vs-lazy discussion; unlike roles, saved jobs can be UNBOUNDED
        name = "saved_jobs",
        joinColumns = @JoinColumn(name = "user_id"),
        inverseJoinColumns = @JoinColumn(name = "job_id")
    )
    private Set<Job> savedJobs = new HashSet<>();   // Set, not List — avoids duplicate saves, no meaningful order
}
@Entity
public class Job {
    // ... existing fields from Section 5

    @ManyToMany(mappedBy = "savedJobs", fetch = FetchType.LAZY)   // INVERSE side —
    private Set<User> savedByUsers = new HashSet<>();      // mappedBy, exactly like Section 5's @OneToMany
}
💡 The Join Table Is Structurally Identical to Section 7's user_roles Table

This is worth recognizing explicitly: Section 7's users ↔ roles relationship (via the user_roles join table) was already a @ManyToMany — the course simply hadn't named or formally taught the annotation yet at that point. The underlying database pattern (a join table holding two foreign keys, no meaningful identity of its own) is identical; this topic is where the general-purpose JPA annotation for that exact pattern finally gets its full, dedicated treatment.

FAANGIn a @ManyToMany, which side is the "owning" side, given that — unlike @OneToMany/@ManyToOne — there's no natural foreign-key asymmetry to determine it?

Correct observation — unlike @OneToMany/@ManyToOne where the foreign key's physical location on one specific table makes the owning side unambiguous (Section 5), a @ManyToMany join table is symmetric by nature; there's no structural reason either side "must" own it. JPA resolves this by convention: whichever side declares @JoinTable (without mappedBy) is designated the owning side by the developer's explicit choice — it's the side Hibernate consults when deciding what to write to the join table. The other side uses mappedBy to declare itself the inverse/read-only-navigation side, exactly mirroring Section 5's mappedBy mechanics even though the underlying relationship shape is different. This is a deliberate developer decision, not something JPA infers from the schema the way it can for @ManyToOne.

Building Save & Unsave Job APIs (Bookmarking Feature)

Video: Building Save & Unsave Job APIs (Bookmarking Feature)
@Transactional   // Section 10's atomicity — the read-modify-save sequence must be consistent
public void saveJob(String username, Long jobId) {
    User user = userRepository.findByUsername(username).orElseThrow();
    Job job = jobRepository.findById(jobId).orElseThrow();
    user.getSavedJobs().add(job);   // mutating the OWNING side's collection —
    userRepository.save(user);         // dirty checking (Section 4) generates the INSERT into saved_jobs
}

@Transactional
public void unsaveJob(String username, Long jobId) {
    User user = userRepository.findByUsername(username).orElseThrow();
    user.getSavedJobs().removeIf(j -> j.getId().equals(jobId));
    userRepository.save(user);   // generates the corresponding DELETE from saved_jobs
}
⚠ Mutating the Inverse Side Silently Does Nothing — The Bidirectional-Sync Trap, Again

This is the exact same trap flagged for @OneToMany/@ManyToOne in Section 5, reappearing here for @ManyToMany: calling job.getSavedByUsers().add(user) (mutating the inverse, mappedBy side) has zero effect on the actual saved_jobs join table — Hibernate only writes to the join table based on the state of the owning side's collection (User.savedJobs). Always mutate the owning side, exactly as shown above.

When NOT to Use @ManyToMany in JPA

Video: When NOT to Use @ManyToMany in JPA

A genuinely important, often-skipped lesson: @ManyToMany is frequently the wrong choice the moment the relationship needs to carry any data of its own beyond the bare fact that a link exists.

// what if "saving a job" needed to record WHEN it was saved, or a user's
// PRIVATE NOTE about why they saved it? A plain @ManyToMany join table
// has NO clean way to carry that extra data — it's just two foreign keys.
// (Workarounds exist via @ElementCollection/composite keys, but they're
// awkward and don't scale to real additional business logic on the link.)
// Replace @ManyToMany with an explicit ENTITY for the join table itself —
// turning an implicit M:N into two explicit @OneToMany/@ManyToOne relationships
@Entity
@Table(name = "saved_jobs")
public class SavedJob {
    @Id @GeneratedValue private Long id;   // NOW has its own real identity

    @ManyToOne @JoinColumn(name = "user_id") private User user;
    @ManyToOne @JoinColumn(name = "job_id") private Job job;

    private LocalDateTime savedAt;     // NOW trivial to add — it's just a normal entity field
    private String privateNote;
}
// User now has: @OneToMany(mappedBy = "user") List savedJobs;
// Job now has:  @OneToMany(mappedBy = "job")  List savedByEntries;
SituationRecommended Approach
The relationship is purely "does a link exist" — no extra data@ManyToMany is fine, exactly as used for bookmarking above
The relationship needs a timestamp, status, note, or any other field of its ownAn explicit join entity with two @ManyToOne relationships — genuinely simpler to extend, query, and reason about than fighting @ManyToMany's limitations
You need to query/filter/sort by properties of the relationship itself (e.g., "jobs saved in the last 7 days")Explicit join entity — its own queryable fields make this trivial; a plain @ManyToMany join table has no clean JPQL path to filter by
💡 The General Principle This Teaches

"Use @ManyToMany only when the relationship is genuinely just a relationship — no attributes of its own. The moment a many-to-many link needs to carry any additional data, model the join table as its own first-class entity instead." This single sentence is one of the most practically valuable, frequently-tested pieces of JPA design judgment a candidate can demonstrate — many real production bugs and painful refactors trace back to starting with @ManyToMany and later needing to bolt on extra fields.

FAANGYou're asked to add a "date saved" timestamp to an existing @ManyToMany bookmarking feature already in production. Walk through the migration.

This requires converting the implicit @ManyToMany join table into an explicit entity, as shown above — a genuine schema and code migration, not a small tweak. Steps: (1) create the new SavedJob entity and its table (via a proper migration tool — Flyway/Liquibase, per Section 4's ddl-auto production guidance, never relying on Hibernate's auto-DDL for a production schema change), (2) migrate existing saved_jobs join-table rows into the new entity's table structure (a one-time data migration script, since the new table needs a generated primary key the old join table never had), (3) replace the @ManyToMany mappings on both User and Job with the two @OneToMany/@ManyToOne pairs shown above, (4) update every service-layer method that read/wrote user.getSavedJobs() to work with the new entity relationship instead. This real migration cost is exactly the practical argument for choosing the explicit-entity design upfront whenever there's a reasonable chance the relationship might need extra data later — a valuable point to raise proactively in a system design interview.

Implementing Job Application Workflow Using REST APIs

Videos: Implementing Job Application Workflow Using REST APIs · Live Demo - Apply & Withdraw Job APIs

A direct, deliberate application of the previous topic's lesson: a job application (unlike a bare bookmark) genuinely needs its own data — an application status (APPLIED, UNDER_REVIEW, REJECTED, ACCEPTED), an applied-at timestamp, possibly a cover note — so it's modeled from the start as an explicit join entity (JobApplication), not a @ManyToMany, directly reinforcing the "when NOT to use @ManyToMany" lesson in a realistic feature immediately following it.

@Entity
@Table(name = "job_applications",
       uniqueConstraints = @UniqueConstraint(columnNames = {"user_id", "job_id"}))
       // prevents the SAME user applying to the SAME job twice — a real business rule,
       // enforced at the database level exactly per Section 7's duplicate-prevention pattern
public class JobApplication {
    @Id @GeneratedValue private Long id;

    @ManyToOne @JoinColumn(name = "user_id") private User applicant;
    @ManyToOne @JoinColumn(name = "job_id")  private Job job;

    @Enumerated(EnumType.STRING)
    private ApplicationStatus status;   // APPLIED, WITHDRAWN, UNDER_REVIEW, REJECTED, ACCEPTED

    private LocalDateTime appliedAt;
}

@Service
public class ApplicationService {

    @Transactional
    public void withdraw(Long applicationId, String username) {
        JobApplication app = applicationRepository.findById(applicationId).orElseThrow();
        if (!app.getApplicant().getUsername().equals(username)) {
            throw new AccessDeniedException("Cannot withdraw another user's application");
            // resource-ownership check — Section 9's authorization pattern, applied here
        }
        app.setStatus(ApplicationStatus.WITHDRAWN);   // SOFT status change, not a hard delete —
    }                                                     // preserves the application history/audit trail
}
💡 Withdraw as a Status Change, Not a Deletion — Worth Justifying Explicitly

Modeling "withdraw" as setting status = WITHDRAWN rather than deleting the JobApplication row preserves a full, queryable history — an employer can still see that a candidate applied and later withdrew, which is often genuinely valuable business information (and, in regulated industries, sometimes a compliance requirement to retain). This is the same underlying principle as Section 5's JPA auditing philosophy: prefer recording state transitions over destructively losing history, wherever the business domain can reasonably support it.

💡 @Value Is Syntactic Sugar Over Environment

Every @Value("${...}") injection is resolved, under the hood, via Spring's Environment abstraction (specifically a PropertySourcesPlaceholderConfigurer bean processor scanning for ${} placeholders and resolving them against the Environment's aggregated PropertySources). Knowing this — rather than treating @Value as its own independent, unrelated mechanism — is what lets a candidate correctly reason about property resolution precedence questions, since Environment is the single underlying source of truth both mechanisms draw from.

FAANGWhat are the practical downsides of @Value at scale, motivating the next topic's @ConfigurationProperties?

Three real pain points: (1) scattered, repetitive declarations — a related group of properties (e.g., ten different mail settings) ends up as ten separate @Value fields, possibly duplicated across multiple classes that each need a subset, with no single place representing "the mail configuration" as a cohesive unit; (2) no compile-time type safety or validation for the property's structure — a typo in the property key string ("mial.from-address") fails silently at runtime (the field is simply left at its default/null) rather than at compile time; (3) no support for binding nested/structured configuration (a list of objects, a nested map) cleanly — @Value's SpEL workarounds for anything beyond a flat scalar value get unwieldy fast, as hinted at by the CC-list example above already needing SpEL just for a simple comma-split list.

    }
}

FAANGCan you combine @ConfigurationProperties with Bean Validation (Section 5) to fail fast on invalid configuration at startup?

Yes — this is a genuinely valuable, underused pattern. Adding @Validated to the @ConfigurationProperties class alongside standard JSR-380 constraint annotations (@NotBlank, @Min, @Pattern) on its fields causes Spring Boot to validate the bound configuration at application startup, failing fast with a clear error if, say, mail.smtp.port is missing or out of a sane range — directly extending Section 1/2's "fail-fast at startup, not deep into production traffic" philosophy to configuration correctness itself, rather than discovering a bad config value only when the first email send attempt mysteriously fails in production.

Why Externalizing Configuration Matters in Real Projects

This is the conceptual anchor for the rest of the configuration arc — the "why," ahead of several "how" topics.

ReasonExplanation
Different values per environmentA database URL, external API key, or log level is almost never identical between local dev, staging, and production — hardcoding forces a code change (and redeploy) just to point at a different database

⚠ This Precedence Order Is a Frequently-Tested, Precise Detail

The exact ordering matters for real debugging scenarios — "why isn't my application.properties value taking effect" is very often answered by "a command-line argument or environment variable with the same key is overriding it, higher up this precedence chain." Command-line arguments sit at the very top specifically because they represent the most explicit, deliberate, closest-to-the-actual-invocation override — the same "most specific wins" philosophy that governs Spring's bean-resolution precedence (@Qualifier over @Primary, Section 2) and CSS specificity in an entirely different domain.

FAANGWhy does Spring Boot map an environment variable like DB_PASSWORD to the property key db.password automatically — what's the actual rule?

This is Spring Boot's relaxed binding rule, which exists because operating-system environment variable names conventionally can't contain dots or lowercase-sensitive distinctions the way property keys can (shell environment variables are traditionally UPPER_SNAKE_CASE). Spring Boot's relaxed binding automatically considers DB_PASSWORD, db.password, db-password, and DB.PASSWORD as equivalent representations of the same logical property key — letting configuration flow naturally from whatever a given source's native naming convention is (shell env vars, YAML, .properties files) into one consistent internal property namespace, without requiring exact case/separator matching across sources.

}
💡 The Full Mental Model — Property Files vs @Profile on Beans

Profile-specific property files (application-{profile}.properties) override individual property values per environment — same beans exist everywhere, just configured differently. @Profile on a bean definition goes further, controlling whether an entire bean even exists in the context for a given environment — genuinely different beans (or entirely absent ones) per environment, not just different property values for the same bean. Both mechanisms are driven by the exact same spring.profiles.active switch, just operating at different granularities.

FAANGHow do profile-specific property files interact with the property-source precedence order from the previous topic — which wins if application-prod.properties sets a value AND an environment variable also sets it?

The environment variable wins — profile-specific property files sit below environment variables and JVM/command-line arguments in Spring Boot's overall precedence chain (as laid out in the previous topic's diagram). This is a deliberate, useful layering in practice: application-prod.properties establishes sensible, version-controlled defaults for the production profile, while genuinely sensitive or deployment-specific values (database passwords, API keys) are still supplied via environment variables at deploy time — getting the benefit of both mechanisms: checked-in, reviewable baseline config per environment, plus the ability to override specific sensitive or infrastructure-specific values without ever committing them to source control.

CoreWhat happens if a bean is annotated @Profile("prod") but no profile is active at all (spring.profiles.active is unset)?

The bean is not created — with no active profile matching "prod", Spring simply skips registering it, exactly as if the profile condition evaluated to false. If the application genuinely needs a bean to exist even with no explicit profile active, Spring provides @Profile("default") specifically to match the implicit "default" profile that's considered active whenever spring.profiles.active is unset — a detail worth knowing to avoid a surprising "why is this bean missing" debugging session in a misconfigured environment where no profile was ever explicitly activated.

Master Interview Q&A Bank — Section 11

Caching correctness, relationship-design judgment, and externalized configuration are all classic senior-level signals — these synthesize across the full section.

FAANGDesign a complete caching strategy for a product listing page that shows near-real-time inventory counts alongside largely-static product descriptions.

Split the cache strategy by data volatility rather than caching the whole response uniformly: product descriptions/images (rarely change) use @Cacheable with a long TTL via Caffeine (topics 186, 189, 190) — high cache-hit rate, low staleness risk. Inventory counts (change frequently, and staleness directly misleads a purchasing decision) either skip caching entirely, use a very short TTL (seconds), or are fetched live and merged with the cached product data at the service layer rather than cached together as one unit — recognizing that caching an entire composite response at one uniform TTL forces the most volatile field to dictate the cache lifetime for everything, wastefully under-caching the genuinely stable data. If deployed across multiple instances, Redis (not Caffeine) is required for the counts to stay consistent across instances if any caching is applied to them at all (topic 190's distributed-cache discussion).

FAANGA teammate proposes modeling a "user follows user" (social-graph-style) feature as a plain @ManyToMany. Evaluate this design choice.

Apply topic 200's decision framework directly: does "following" need any data of its own? In almost any real product, yes — at minimum a followedAt timestamp (for a "recently followed" feed), and very plausibly a notification-preference flag, a "close friend" tier, or similar metadata down the line. Per this section's explicit guidance, this strongly argues for an explicit join entity (Follow, with follower/followee @ManyToOne relationships and its own fields) from the start, rather than a bare @ManyToMany that would require the exact same painful migration walked through in topic 200's Q&A the moment a single additional field is needed. A candidate correctly identifying this upfront — rather than defaulting to @ManyToMany because "it's two entities pointing at each other" — demonstrates real, applied JPA design judgment rather than surface-level annotation knowledge.

CoreTrace exactly how a database password gets from a Kubernetes Secret into a running Spring Boot pod's DataSource, using every mechanism covered in this section.

A Kubernetes Secret is typically mounted into the pod as an environment variable (e.g. DB_PASSWORD) at container startup — this is the "environment variable" property source from topics 207–208. application-prod.properties (activated via SPRING_PROFILES_ACTIVE=prod, itself another environment variable, topics 209–210) references it as spring.datasource.password=${DB_PASSWORD} — a placeholder resolved against the Environment abstraction (topic 203). Because environment variables sit above profile-specific property files in Spring Boot's precedence chain (topic 207's diagram), this externally-injected secret value is what actually gets bound, and the exact same container image (this section's "build once, deploy everywhere" principle, topic 206) can be deployed to staging or production with entirely different secret values injected at the Kubernetes layer, with zero difference in the application code or even the built JAR itself.

FAANGWhy might @CacheEvict(allEntries = true) after every single write be a worse design than targeted, key-specific eviction — even though it's simpler to write?

Evicting the entire cache region on every write defeats much of caching's benefit for any read traffic touching entries unrelated to what actually changed — every other cached entry in that region is discarded and must be recomputed/re-fetched on its next read, even though nothing about it actually became stale. Under moderate write frequency, this can result in a cache that's almost perpetually cold for practical purposes, especially for a cache region holding many independent entities (e.g., all companies) where updating one shouldn't invalidate every other company's cached data. Targeted eviction (evicting only the specific key affected, as shown in topic 186's demo) preserves the cache's effectiveness for everything unaffected by a given write — the correct default unless there's a specific reason the entire region's data is genuinely interdependent.
