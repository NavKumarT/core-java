The N+1 Problem — The Silent Performance Killer

Video: The N+1 Problem - The Silent Performance Killer

Section 5 briefly named this problem; this topic goes deep. Using the Company/Job relationship from Section 5's JPA relationships deep dive as the running example:

List companies = companyRepository.findAll(); // Query #1: SELECT * FROM companies for (Company c : companies) { c.getJobs().size(); // triggers a LAZY LOAD for EACH company } // Query #2: SELECT * FROM jobs WHERE company_id = 1 // Query #3: SELECT * FROM jobs WHERE company_id = 2 // Query #4: SELECT * FROM jobs WHERE company_id = 3 // ... // Query #(N+1): SELECT * FROM jobs WHERE company_id = N // 1 query for N companies + N additional queries for their jobs = N+1 total queries // 100 companies -> 101 queries, when 2 well-designed queries (or 1 join) would suffice
⚠ Why "Silent" Is the Operative Word

The N+1 problem is uniquely dangerous because it produces entirely correct results — every test passes, every response is accurate — while silently degrading performance in a way that's invisible in code review (nothing about c.getJobs().size() looks wrong) and often invisible in local development (where a handful of test rows make 101 queries feel instant). It typically only becomes visible in production once data volume grows, manifesting as mysteriously slow endpoints that don't obviously correlate with any specific line of business logic — exactly the kind of bug that's expensive to diagnose after the fact and cheap to prevent by understanding the pattern upfront.

How to Detect It

  • spring.jpa.show-sql=true (plus spring.jpa.properties.hibernate.format_sql=true) and manually counting queries for a suspicious endpoint — crude but effective for learning.
  • A datasource proxy library (like p6spy or datasource-proxy) that logs every executed query with a running count — the practical production-debugging approach.
  • Hibernate's built-in statistics (spring.jpa.properties.hibernate.generate_statistics=true), which logs aggregate query counts per session.
  • APM tools (Datadog, New Relic) that flag suspiciously repetitive query patterns automatically in production traces.
FAANGDoes switching the association's fetch type to EAGER "fix" the N+1 problem?

No — and this is a common, incorrect first instinct. Switching @OneToMany to FetchType.EAGER doesn't eliminate the extra queries; it just changes when they happen — Hibernate still typically issues one separate query per parent to fetch each one's associated collection (unless it happens to also use a join, which isn't EAGER's default query strategy for collections), except now they fire immediately during findAll() regardless of whether the caller ever actually needed the jobs data at all. Worse, it makes the problem unconditional and harder to control per-query — every single fetch of a Company, anywhere in the codebase, now always pays this cost, even in code paths that never touch .getJobs(). The correct fixes (covered in the next topic) target the specific query that needs the association, not the association's global default.

Fixing the N+1 Problem with Hibernate Batch Fetching

Video: Fixing the N+1 Problem with Hibernate Batch Fetching
public interface CompanyRepository extends JpaRepository<Company, Long> {

    @Query("SELECT DISTINCT c FROM Company c LEFT JOIN FETCH c.jobs")
    List<Company> findAllWithJobs();
    // generates ONE query with a SQL JOIN — jobs come back already populated,
    // zero additional lazy-load queries triggered later
}
public interface CompanyRepository extends JpaRepository<Company, Long> {

    @EntityGraph(attributePaths = {"jobs"})   // declarative alternative to writing JOIN FETCH by hand
    List<Company> findAll();
    // overrides JpaRepository's default findAll() specifically for this repository,
    // telling Hibernate to eagerly fetch "jobs" for THIS query only
}
@Entity
public class Company {
    @OneToMany(mappedBy = "company")
    @BatchSize(size = 20)   // Hibernate-specific: batches lazy loads in groups of 20
    private List<Job> jobs;
}
// instead of N individual "WHERE company_id = ?" queries, Hibernate issues
// ceil(N/20) queries using "WHERE company_id IN (?, ?, ?, ... up to 20 ids)"
// — dramatically fewer round-trips, though still more than a single JOIN FETCH
ApproachQuery CountBest For
JOIN FETCHExactly 1A specific, known use case where you always need the association — most efficient, but requires a dedicated query method per fetch shape
@EntityGraphExactly 1 (typically)Same effect as JOIN FETCH but more declarative/reusable, and can be applied to override even inherited JpaRepository methods like findAll()
@BatchSizeceil(N / batch size)A general-purpose, global safety net applied at the entity level — helps even in code paths you didn't specifically optimize, at the cost of still being more than 1 query
⚠ The DISTINCT Keyword in JOIN FETCH Isn't Optional

A SQL join between a Company and its multiple Jobs produces one result row per job — meaning a company with 5 jobs appears 5 times in the raw joined result set. Without DISTINCT in the JPQL, Hibernate would return duplicate Company objects in the Java-level result list (technically the same object reference repeated, due to first-level cache identity, but still duplicated entries in the returned List). DISTINCT at the JPQL level deduplicates these before the result is returned — a very common, easy-to-miss bug when first learning JOIN FETCH.

FAANGCan you use JOIN FETCH for more than one collection association on the same entity in a single query?

Technically you can write it, but Hibernate will throw a MultipleBagFetchException if you try to JOIN FETCH two separate List-typed collections in the same query — the Cartesian product of two unbounded collections joined simultaneously produces an explosion of duplicate rows Hibernate can't cleanly deduplicate back into the correct object graph shape. Common workarounds: fetch one collection via JOIN FETCH and let the other remain lazy (or use @BatchSize for it), change one of the collections to a Set instead of a List (which sidesteps the specific "bag" ordering ambiguity that triggers the exception), or split into two separate queries and merge the results in application code.

CoreWhy doesn't @BatchSize get you down to exactly 1 query like JOIN FETCH does?

@BatchSize is a general optimization applied at the entity/association mapping level, not tied to any specific query — it doesn't know in advance which parent IDs will need their lazy collection loaded, so it can only batch together the IDs that happen to already be loaded into the persistence context at the moment a lazy load is triggered, up to the configured batch size. JOIN FETCH is a query-level decision made upfront, explicitly telling Hibernate "I need these specific parents and their children together, right now, in one shot" — a stronger, more specific guarantee that a generic batching heuristic can't match, in exchange for less flexibility (you need a dedicated query method for each distinct fetch shape you require).

Introducing @Query and JPQL — Writing Custom JPA Queries

Videos: Introducing @Query and JPQL - Writing Custom JPA Queries · Hands-On Demo - Writing JPQL Queries Using @Query

JPQL (Java Persistence Query Language) is JPA's own SQL-like query language — but it queries against entities and their fields, not tables and columns directly, making it database-vendor-agnostic (the same query works unchanged against MySQL, PostgreSQL, Oracle — Hibernate's dialect translates it to the actual vendor SQL).

public interface JobRepository extends JpaRepository<Job, Long> {

    @Query("SELECT j FROM Job j WHERE j.minSalary >= :minSalary AND j.company.name = :companyName")
    List<Job> searchJobs(@Param("minSalary") BigDecimal minSalary,
                          @Param("companyName") String companyName);
    // "Job j" refers to the ENTITY CLASS, "j.company.name" navigates the
    // mapped Java object graph — NOT the raw "jobs"/"company_id" table/column names
}
// named parameters (preferred — clearer, order-independent)
@Query("SELECT j FROM Job j WHERE j.status = :status")
List<Job> findByStatus(@Param("status") String status);

// positional parameters (order-dependent, more fragile to reorder)
@Query("SELECT j FROM Job j WHERE j.status = ?1")
List<Job> findByStatusPositional(String status);
// selecting specific fields rather than a full entity — a "projection"
@Query("SELECT new com.growthscript.dto.JobSummaryDto(j.id, j.title, j.company.name) " +
       "FROM Job j WHERE j.status = 'OPEN'")
List<JobSummaryDto> findOpenJobSummaries();
// JobSummaryDto MUST have a matching constructor — this is JPQL's
// "constructor expression" syntax, letting a query return DTOs DIRECTLY,
// skipping the manual entity-to-DTO mapping step from Section 4
Derived Query Method@Query with JPQLNative SQL
Written againstMethod name (parsed)Entity/field namesActual table/column names
Database-portable?✅ Yes✅ Yes❌ No — vendor-specific SQL syntax
Complexity ceilingLowHigh — joins, aggregates, subqueries, projections all supportedUnlimited — anything the database supports
IDE/compile-time safetyChecked at startup (Section 7)Checked at startup, but string-based — no compile-time type checkingNo JPA-level validation at all — pure string, checked only by the database at execution
💡 Constructor Expressions — A Major Practical Win

The projection example above directly addresses a real pain point from Section 4's DTO pattern: instead of fetching full entities and manually mapping them to DTOs in the service layer (extra code, extra memory for unused fields), a JPQL constructor expression lets the database-level query itself select only the needed columns and have Hibernate construct the DTO directly — genuinely more efficient (less data transferred and mapped) and less boilerplate, for read-heavy, DTO-shaped list/summary endpoints specifically.

FAANGDoes JPQL protect against SQL injection the same way derived queries and native parameterized queries do?

Yes, as long as you use named or positional parameters (:status or ?1) rather than string-concatenating user input directly into the JPQL string. Parameters are bound via JDBC's prepared-statement mechanism underneath, exactly like derived queries — user input is always treated as data, never as executable query syntax, regardless of what characters it contains (directly extending Section 7's SQL injection discussion). The vulnerability only reappears if a developer manually concatenates raw user input into the @Query string itself, which defeats the parameterization Spring Data JPA provides — a mistake, not a limitation of JPQL/@Query as a mechanism.

CoreWhy does JPQL use entity/field names instead of table/column names, and what's the practical benefit?

JPQL operates at the object-model level deliberately — it's part of what makes JPA/Hibernate an ORM abstraction rather than a thin SQL wrapper. This means a JPQL query written today continues to work unchanged if the underlying database vendor changes (MySQL to PostgreSQL, say), if a @Column(name=...) mapping is renamed at the database level without touching the Java field name, or across any Hibernate-dialect-specific SQL syntax differences — all of which Hibernate translates transparently underneath. This portability is the direct, practical payoff of JPQL's entity-oriented syntax versus writing native SQL, which ties a query to one specific database's exact schema and syntax.

⚠ When Native SQL Is Genuinely Justified — Not a Default Choice

Native SQL should be the last resort, reached for specifically when: (1) a database-vendor-specific feature has no JPQL equivalent (full-text search functions, window functions, specific date/JSON functions), (2) an existing, already-hand-tuned SQL query needs to be reused as-is (e.g., migrating a legacy stored procedure's logic), or (3) a query needs hand-tuning for performance that JPQL's generated SQL doesn't achieve (verified via EXPLAIN analysis, not just a guess). Reaching for native SQL by default throws away JPQL's database portability and the (admittedly limited) startup-time validation JPQL gets — it should be a deliberate, justified exception, not a habit.

CoreDoes a native query still return managed JPA entities the way a JPQL query does?

Yes, when the repository method's return type is a mapped entity type (as in the example above), Spring Data JPA still maps the native SQL's result set rows back into fully-managed Job entities, tracked by the persistence context exactly like any other JPA-fetched entity — dirty checking, lazy associations, and the full entity lifecycle from Section 4 all still apply normally. This is a genuinely useful property: native SQL is used only to express the query logic itself, while the result still integrates cleanly into the rest of the JPA-managed object graph, rather than returning disconnected raw data.

Understanding & Using @NamedQuery and @NamedNativeQuery

@Entity

@Query@NamedQuery

ℹ Why @Query Has Largely Superseded @NamedQuery in Practice

Putting the query text directly on the repository method (@Query) keeps the query colocated with its one point of use — a developer reading JobRepository sees exactly what SQL/JPQL each method executes without needing to jump to a separate entity class and search for a matching string name. @NamedQuery's entity-level declaration made more sense in the pre-Spring-Data-JPA era, when query reuse across multiple, hand-written DAO classes was a bigger concern than it is now that each repository interface typically has one clear, dedicated purpose.

FAANGWhat's a genuine, still-relevant reason to reach for @NamedQuery over @Query today?

When the exact same query genuinely needs to be reused outside the Spring Data repository abstraction entirely — e.g., called directly via a raw EntityManager.createNamedQuery("Job.findOpenJobsAboveSalary") in some framework-level or legacy integration code that doesn't go through a Spring Data repository interface at all. Since @NamedQuery is validated and compiled once, centrally, at EntityManagerFactory startup regardless of which repository (if any) ends up calling it, it can offer a very marginal startup-time performance edge in very large applications with many query methods — though this is rarely the deciding factor in practice; the "shared across non-Spring-Data callers" scenario is the more commonly cited legitimate justification.

How Spring Security Stores Authorities Internally Using GrantedAuthority

Video: How Spring Security Stores Authorities Internally using GrantedAuthority
GrantedAuthority (interface — ONE method: getAuthority() -> String) ▲ │ implemented by │ SimpleGrantedAuthority (the standard, near-universal implementation — just wraps a single authority string) UserDetails.getAuthorities() returns: Collection │ ▼ [ SimpleGrantedAuthority("ROLE_ADMIN"), SimpleGrantedAuthority("ROLE_USER"), SimpleGrantedAuthority("SCOPE_read") ] │ at authorization-check time, hasRole("ADMIN") checks whether "ROLE_ADMIN" is PRESENT in this collection
@Override
public Collection<? extends GrantedAuthority> getAuthorities() {
    return roles.stream()
            .map(role -> new SimpleGrantedAuthority(role.getName()))  // e.g. "ROLE_ADMIN"
            .collect(Collectors.toSet());
}

The core insight: Spring Security's entire internal authorization model is nothing more than a flat collection of strings attached to the authenticated principal. There's no built-in distinction at the storage level between a "role" and a "permission/authority" — GrantedAuthority is just a single-method wrapper around a string, and any semantic meaning (like the ROLE_ prefix convention) is a layer of convention Spring Security builds on top, not something enforced by the type system itself.

⚠ hasRole() Silently Adds the ROLE_ Prefix — A Frequent Source of Bugs

Because hasRole("ADMIN") internally checks for the string "ROLE_ADMIN", a common bug pattern is storing the authority as "ROLE_ADMIN" but then also writing hasRole("ROLE_ADMIN") at the check site — this silently checks for the (nonexistent) string "ROLE_ROLE_ADMIN", causing every authorization check to fail with no obvious error, just an unexpected 403. Always store the ROLE_ prefix in the database/data model (as done in Section 7's schema) and call hasRole() without repeating the prefix — or use hasAuthority("ROLE_ADMIN") everywhere instead, which never adds any implicit prefix, if you want to eliminate this entire class of bug.

FAANGIf GrantedAuthority is just a string wrapper with no built-in role/permission distinction, how would you model a fine-grained permission system (e.g., "can edit invoices," "can approve refunds") using it?

Simply add more GrantedAuthority strings to the same flat collection — there's nothing structurally different required. A user's getAuthorities() might return ["ROLE_USER", "PERMISSION_EDIT_INVOICES", "PERMISSION_APPROVE_REFUNDS"] all in the same collection — Spring Security doesn't care that some strings follow a "role" naming convention and others follow a "permission" naming convention; both are just strings checked via hasAuthority() (never hasRole(), which specifically adds the ROLE_ prefix and implies the coarser convention). This directly demonstrates the next topic's AUTHORITY-vs-ROLE distinction is purely a naming/usage convention, not a structural capability difference in the framework.

AUTHORITY vs ROLE — Which One Should You Use?

Video: AUTHORITY vs ROLE - Which One Should You Use
ROLE (via hasRole)AUTHORITY (via hasAuthority)
GranularityCoarse — broad user categories (ADMIN, USER, MANAGER)Fine — specific individual permissions (EDIT_INVOICE, APPROVE_REFUND, VIEW_AUDIT_LOG)
Naming conventionROLE_-prefixed by Spring Security conventionNo convention enforced — any string, though a scheme like PERMISSION_X or a resource:action pattern (invoice:edit) is common

💡 The Practical Recommendation — Not Either/Or

Real production systems typically use both, at different layers: coarse-grained role checks (hasRole("ADMIN")) guard broad access at the authorizeHttpRequests/URL level (Section 6) — cheap, simple, and sufficient for "is this general category of user even allowed near this feature area at all." Fine-grained authority/permission checks (hasAuthority("PERMISSION_APPROVE_REFUNDS")) guard specific, business-logic-sensitive operations, typically via @PreAuthorize at the service-method level (Section 6) — expressing exactly the capability that matters for that one specific action, independent of which role(s) happen to currently grant it. This layered approach avoids both the rigidity of pure role-based access control and the verbosity of checking dozens of individual permissions everywhere.

FAANGA product requirement changes: accountants (previously only ROLE_ACCOUNTANT) should now also be able to approve refunds under $500, a capability that used to be ADMIN-only. How does an authority-based design handle this more gracefully than a pure role-based one?

With pure role-based checks (hasRole("ADMIN") scattered across every refund-approval code path), this change requires either granting accountants the full ADMIN role (dangerously over-broad — they'd gain every other admin capability too) or hunting down and modifying every single hasRole("ADMIN") check related to refunds specifically. With an authority-based design, the check is already expressed as hasAuthority("PERMISSION_APPROVE_REFUNDS") — independent of which role(s) currently grant it — so the fix is purely a data-levelROLE_ACCOUNTANT role's grant set (or directly to affected users) in the database, with zero code changes to any authorization check anywhere in the codebase. This is the concrete, practical payoff of designing authorization around fine-grained authorities from the start, even in systems that also expose coarser roles for simpler checks.

Customizing Security Errors in Spring Security

Video: Customizing Security Errors in Spring Security

By default, Spring Security's 401/403 responses are plain, minimal, and inconsistent with the structured ErrorResponse shape established by @RestControllerAdvice in Section 5. Two dedicated interfaces let you customize each case.

@Component
public class CustomAuthenticationEntryPoint implements AuthenticationEntryPoint {

    @Override
    public void commence(HttpServletRequest request, HttpServletResponse response,
                        AuthenticationException authException) throws IOException {
        // invoked whenever an UNAUTHENTICATED request hits a protected endpoint —
        // this is the exact landing spot referenced in Section 6's JWT filter Q&A
        response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
        response.setContentType("application/json");

        ErrorResponse error = ErrorResponse.builder()
                .status(HttpStatus.UNAUTHORIZED.value())
                .message("Authentication required")
                .timestamp(LocalDateTime.now())
                .path(request.getRequestURI())
                .build();

        new ObjectMapper().writeValue(response.getOutputStream(), error);  // consistent with Section 5's shape
    }
}
@Component
public class CustomAccessDeniedHandler implements AccessDeniedHandler {

    @Override
    public void handle(HttpServletRequest request, HttpServletResponse response,
                       AccessDeniedException accessDeniedException) throws IOException {
        // invoked when the user IS authenticated but LACKS the required role/authority
        response.setStatus(HttpServletResponse.SC_FORBIDDEN);
        response.setContentType("application/json");

        ErrorResponse error = ErrorResponse.builder()
                .status(HttpStatus.FORBIDDEN.value())
                .message("You do not have permission to perform this action")
                .timestamp(LocalDateTime.now())
                .path(request.getRequestURI())
                .build();

        new ObjectMapper().writeValue(response.getOutputStream(), error);
    }
}
http.exceptionHandling(exceptions -> exceptions
    .authenticationEntryPoint(customAuthenticationEntryPoint)   // 401 path
    .accessDeniedHandler(customAccessDeniedHandler)             // 403 path
);
💡 Why Two Separate Interfaces, Not One

This mirrors the authentication-vs-authorization distinction from earlier in this section precisely: AuthenticationEntryPoint fires when identity itself couldn't be established (missing/invalid/expired token — a 401 concern), while AccessDeniedHandler fires when identity was established but the now-known principal simply lacks permission (a 403 concern). Keeping them as separate, independently-configurable components reflects that these are genuinely different failure modes needing potentially different handling/logging/messaging — not the same problem seen from two angles.

FAANGWhy can't @RestControllerAdvice alone handle these 401/403 error customizations, requiring these separate Spring Security interfaces instead?

This connects directly to Section 6's filter-chain architecture: @RestControllerAdvice's @ExceptionHandler methods only catch exceptions thrown from within controller method execution, inside DispatcherServlet's processing. Authentication/authorization failures, however, are detected and thrown by Spring Security's filters — AuthorizationFilter, specifically — which run before the request ever reaches DispatcherServlet at all (per Section 6's filter-chain diagram). An exception thrown at the filter level, before Spring MVC's dispatch machinery is even involved, is structurally invisible to @RestControllerAdvice — Spring Security's own ExceptionTranslationFilter catches it instead and delegates to whichever AuthenticationEntryPoint/AccessDeniedHandler is configured, which is exactly why these are the correct, necessary customization point for this specific class of error.

    return jobRepository.findAll(sort).stream()
            .map(jobMapper::toDto)
            .toList();
}
// GET /jobs?sortBy=minSalary&direction=asc
⚠ Never Pass a Client-Supplied Sort Field Directly Without Validation

Accepting an arbitrary sortBy string directly from a request parameter and passing it straight into Sort.by() is a real security/stability risk: it lets a client attempt to sort by any field name, including ones that don't exist on the entity (causing a runtime exception) or, in more sensitive systems, fields that shouldn't be exposed as sortable at all for information-disclosure reasons. Production code should validate sortBy against an explicit allow-list of permitted sortable field names before constructing the Sort object — a direct application of the "never trust client input" principle from Section 5's validation discussion.

CoreHow does Sort.by(...) actually translate into SQL under the hood — does it risk SQL injection like a naively-built dynamic ORDER BY clause might?

Spring Data JPA's Sort object is resolved against the target entity's mapped field metadata — it isn't string-concatenated directly into raw SQL. If a supplied field name doesn't correspond to an actual mapped entity property, Hibernate throws a PropertyReferenceException at query-execution time (not a SQL injection vector, since the field name is validated against known entity metadata before ever reaching the SQL generation stage, similar in spirit to how derived query method names are validated). That said, the earlier allow-list warning still stands — not because of injection risk specifically, but because an unvalidated field name can crash the endpoint with an unhandled exception, or expose sortability on fields that shouldn't be client-controllable for business reasons.

Understanding & Implementing Pagination in Spring Data JPA

Videos: Understanding Pagination in Spring Data JPA · Hands-On Demo - Paginating Data Using JPA

This extends Section 4's brief pagination mention into full working detail — essential given every list endpoint in a real production API needs it.

public interface JobRepository extends JpaRepository<Job, Long> {
    Page<Job> findByStatus(String status, Pageable pageable);
    // JpaRepository ALSO already provides: Page findAll(Pageable pageable)
}
@GetMapping("/jobs")
public Page<JobResponseDto> getJobs(
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "20") int size,
        @RequestParam(defaultValue = "createdAt,desc") String sort) {

    String[] sortParams = sort.split(",");
    Pageable pageable = PageRequest.of(page, size,
            Sort.by(Sort.Direction.fromString(sortParams[1]), sortParams[0]));

    return jobRepository.findAll(pageable).map(jobMapper::toDto);  // Page.map() converts entity -> DTO,
}                                                                // preserving all pagination metadata
// GET /jobs?page=0&size=20&sort=minSalary,asc
// Page's JSON response includes rich metadata alongside the content:
{

  "totalElements": 143,
  "totalPages": 8,
  "number": 0,          // current page (0-indexed)
  "size": 20,

  "last": false,

TypeWhat It ProvidesQuery Cost
List<T>Just the rows — no metadata at all1 query
Slice<T>Content + hasNext()/hasPrevious(), but NOT total count1 query — fetches size + 1 rows to determine if a next page exists, without a separate COUNT
Page<T>Everything Slice has, PLUS totalElements/totalPages2 queries — the content query, plus a separate COUNT(*) query to compute totals
⚠ Page's COUNT Query Is a Real, Often-Overlooked Cost

Returning Page<T> always triggers a second query just to compute totalElements — on a very large table, an unindexed or complex-filtered COUNT(*) can itself become a meaningful performance cost, sometimes even slower than the actual content query it's paired with. If a UI genuinely doesn't need a total-page-count display (e.g., an infinite-scroll feed that just needs "is there more to load"), prefer Slice<T> specifically to avoid this extra COUNT query entirely — a concrete, interview-relevant performance/API-design trade-off most candidates default to Page without considering.

FAANGFor a very large table (tens of millions of rows), why does offset-based pagination (page=500&size=20) get progressively slower for later pages, and what's the alternative?

Offset-based pagination (LIMIT 20 OFFSET 10000, underneath a request for page 500) requires the database to still scan and discard all 10,000 preceding rows before it can return the requested 20 — the further into the dataset a page is, the more wasted scanning work each request costs, even with an index, since the database still has to walk that many index entries to reach the offset. The scalable alternative is keyset (cursor-based) pagination: instead of an offset, the client passes the last seen value of the sort key from the previous page (e.g., WHERE created_at < :lastSeenTimestamp ORDER BY created_at DESC LIMIT 20) — this lets the database jump directly to the right starting point via an index seek, with performance that stays roughly constant regardless of how deep into the dataset the "page" conceptually is. The trade-off: keyset pagination doesn't support jumping to an arbitrary page number directly (only "next"/"previous" relative to a cursor), which is often an acceptable UX trade-off for infinite-scroll-style interfaces but not for a classic numbered-page UI.

CoreWhy does Page's map() method (used above to convert entities to DTOs) preserve pagination metadata rather than needing to be recomputed?

Page<T>.map(Function<T,R>) is specifically designed to transform only the content of the page (each individual element, entity → DTO here) while carrying forward all the pagination metadata (totalElements, totalPages, current page number) unchanged, since that metadata was already correctly computed against the original (pre-mapping) query and has nothing to do with what shape each element is transformed into afterward. This makes it the standard, idiomatic way to expose a paginated DTO response from a repository that naturally returns paginated entities — directly connecting Section 4's DTO-mapping discussion to the pagination machinery here, without manually reconstructing a new Page object and re-deriving its metadata by hand.

The section's capstone — a PATCH-style status-update endpoint on the Contact entity from Section 4's capstone, now layering in this section's concepts: role-gated (only staff, via hasRole/hasAuthority, can transition a contact's status), and demonstrating a targeted, single-field update rather than a full entity replacement.

@PatchMapping("/{id}/status")
@PreAuthorize("hasAuthority('PERMISSION_MANAGE_CONTACTS')")   // this section's fine-grained authority check
public ResponseEntity<ContactResponseDto> updateStatus(
        @PathVariable String id,
        @RequestBody UpdateStatusRequest request) {

    Contact contact = contactRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("Contact not found: " + id));

    // a real state machine would validate the transition here —
    // e.g. NEW -> IN_PROGRESS -> CLOSED, rejecting invalid jumps like NEW -> CLOSED
    contact.setStatus(request.getStatus());
    Contact updated = contactRepository.save(contact);
    // @LastModifiedDate / @LastModifiedBy (Section 5's auditing) fire automatically here

    return ResponseEntity.ok(contactMapper.toDto(updated));
}

Master Interview Q&A Bank — Section 9

JPA query strategy and authorization design are two of the most reliably-tested "does this candidate have real production experience" areas — these synthesize the whole section.

FAANGAn endpoint that lists jobs with their company names is timing out under load. Walk through your full diagnostic and fix process.

(1) Enable query logging/a datasource proxy to confirm the actual query pattern — likely reveals the N+1 signature (1 query for jobs, N queries for each job's company via a lazy @ManyToOne). (2) Confirm via EXPLAIN or Hibernate statistics that query count scales linearly with result size. (3) Fix with a targeted JOIN FETCH or @EntityGraph on the specific repository method powering this endpoint (not a global fetch-type change, which risks the "eager-fixes-nothing" trap). (4) If the endpoint is paginated, verify the fix still works correctly with Pageable — a naive JOIN FETCH combined with pagination on a collection association can produce incorrect, non-paginated-at-the-database-level results (Hibernate historically had to paginate in-memory in some such cases, a known gotcha worth mentioning). (5) Re-measure query count and latency after the fix to confirm the improvement empirically, not just theoretically.

FAANGDesign the full authorization model (roles, authorities, and where each check lives) for a multi-tenant SaaS invoicing platform with Owner, Accountant, and Viewer user types.

Coarse roles (ROLE_OWNER, ROLE_ACCOUNTANT, ROLE_VIEWER) gate broad feature-area access at the authorizeHttpRequests level (e.g., only Owner/Accountant can reach /api/v1/invoices/** write endpoints at all; Viewer is read-only via method-level GET restrictions). Fine-grained authorities (PERMISSION_CREATE_INVOICE, PERMISSION_APPROVE_PAYMENT, PERMISSION_MANAGE_USERS) gate specific business operations via @PreAuthorize at the service layer, mapped from roles in the database so the mapping can evolve without code changes (this section's ROLE-vs-AUTHORITY discussion). On top of both, a tenant-ownership check in the service layer verifies the authenticated user's tenant ID matches the invoice's tenant ID before any operation proceeds — a business-logic-level check no static role/authority system can express, since it depends on the specific resource being accessed, not just the user's general capabilities. This three-layer design (URL-level roles, method-level authorities, data-level ownership checks) is a realistic, complete answer synthesizing this section with general system-design thinking.

CoreWhen would you choose Slice over Page, and what's the concrete cost difference?

Page<T> executes the content query plus a separate COUNT(*) query to populate totalElements/totalPages — two round-trips, and the COUNT can itself be expensive on a large or heavily-filtered table. Slice<T> needs only one query (fetching pageSize + 1 rows to cheaply determine hasNext() without a separate count). Choose Slice whenever the UI only needs "load more" / infinite-scroll semantics and genuinely has no need to display a total count or jump to an arbitrary page number — a common, concrete performance optimization for large-table, infinite-scroll-style endpoints that most candidates don't think to apply, defaulting to Page everywhere out of habit.

FAANGWhy might a well-designed system use @NamedNativeQuery (or plain @Query with nativeQuery=true) even though it sacrifices database portability — isn't portability always worth preserving?

Portability is valuable but not free — it constrains you to whatever subset of functionality JPQL can express across all database vendors uniformly, which sometimes means leaving real performance or functionality on the table. If a specific PostgreSQL feature (e.g., a GIN index-backed JSONB containment query, or a window function for a leaderboard/ranking calculation) has no reasonable JPQL equivalent, and the team has no realistic plan to ever migrate off that specific database vendor, insisting on JPQL-only for theoretical future portability is a real, unnecessary cost paid today for a migration that may never happen. The honest engineering trade-off is: default to JPQL for portability and maintainability, but treat native SQL as a legitimate, deliberate escape hatch — not a failure — when a specific, verified need justifies it, exactly as covered in this section's native SQL topic.

CoreHow do sorting and pagination interact — does adding Sort to a Pageable change the query's correctness or just its ordering?

Sorting and pagination are complementary and, critically, order matters for pagination correctness — without a deterministic ORDER BY, a database offers no guarantee that repeated LIMIT/OFFSET queries return a stable, non-overlapping sequence of rows across separate requests (rows could shift between pages if concurrent writes happen, or if the database's default ordering isn't actually stable). This is precisely why PageRequest.of(page, size, sort) bundles both together — a paginated query without an explicit sort is technically well-formed but semantically risky for a UI that expects consistent, non-duplicated results as a user pages through results.
