Section 6 — Spring Security Internals & JWT Authentication

The single highest-leverage topic for backend interviews: how Spring Security's filter chain actually works under the hood, how passwords are safely stored, how authentication and authorization are genuinely different, and how to build stateless, production-grade JWT authentication from first principles — token generation, signature validation, and a custom filter wired into the security chain.

Hello Spring Security — Your First Handshake with the Framework

Video: Hello Spring Security - Your First Handshake with the Framework
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

The moment this single starter is added — with zero configuration code — every endpoint in the application becomes protected. This is Spring Boot's auto-configuration philosophy (Section 3) applied to security: SecurityAutoConfiguration detects Spring Security on the classpath and activates a fully-functional, secure-by-default setup.

💡 The Philosophy: Secure By Default

Spring Security's defaults are deliberately restrictive — every request requires authentication unless you explicitly say otherwise. This "closed by default, opened deliberately" posture is a foundational security design principle (the opposite of "open by default, restricted as an afterthought," which is how countless real-world vulnerabilities happen when a developer forgets to add a restriction).

Zero Config Magic — What Spring Security Gives You by Default

Video: Zero Config Magic - What Spring Security Gives You by Default

Out of the box, with nothing but the starter on the classpath, Spring Boot auto-configures:

  • A generated default password for a single user named user, printed to the console at startup (a fresh UUID every restart).
  • Every endpoint requires authentication — any unauthenticated request is redirected to a default login form (HTML page) or, for non-browser clients, met with an HTTP Basic Auth challenge.
  • CSRF protection enabled by default for state-changing requests.
  • Sensible default security headers (e.g., X-Content-Type-Options, X-Frame-Options) to guard against common browser-based attacks like clickjacking.
⚠ The Generated Password Is a Dev-Only Convenience

The console-printed password exists purely so a brand-new Spring Boot + Security project is immediately testable without any setup. It's obviously unsuitable for anything beyond initial exploration — the very next videos (static credentials, then real UserDetailsService implementations) exist to replace it.

ℹ Why Disable These at All?

The default HTML login form is meant for traditional server-rendered web apps — irrelevant for a stateless REST API consumed by a separate frontend (or mobile app). HTTP Basic Auth sends credentials in every single request (base64-encoded, not encrypted — trivially decodable), which doesn't fit a token-based (JWT) authentication model at all. Disabling both is the standard first step before building a real, stateless, token-based security configuration.

Demo of permitAll, denyAll and CSRF Disable

Video: Demo of permitAll, denyAll and CSRF disable
http
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/v1/auth/**").permitAll()   // no authentication required at all
        .requestMatchers("/api/v1/admin/**").denyAll()     // blocked for EVERYONE, regardless of auth
        .anyRequest().authenticated()                       // everything else needs a valid principal
    )
    .csrf(csrf -> csrf.disable());   // see explanation below — appropriate for stateless APIs

What Is CSRF, and Why Disable It for a REST API?

CSRF (Cross-Site Request Forgery) exploits the browser's automatic inclusion of cookies on every request to a site — a malicious page can trick a logged-in user's browser into submitting a state-changing request (e.g., a hidden auto-submitting form) to your app, and the browser helpfully attaches the victim's session cookie, making it look legitimate. Spring Security's CSRF protection requires a unique, unguessable token on every state-changing request to defeat this.

💡 Why This Doesn't Apply to Token-Based (JWT) APIs

CSRF is fundamentally a cookie-based session vulnerability — it exploits the browser automatically attaching cookies. A stateless API authenticated via a JWT sent explicitly in the Authorization header (not a cookie) is not vulnerable to CSRF at all: an attacker's malicious page has no way to make the victim's browser automatically attach that header, since headers (unlike cookies) are never auto-attached by the browser to cross-origin requests. This is precisely why disabling CSRF is the correct, safe choice for a stateless JWT-based REST API — not a security shortcut, but a decision matching the actual threat model.

⚠ Never Disable CSRF for a Cookie/Session-Based App

If your app authenticates via a session cookie (the traditional server-rendered or same-origin-cookie-auth model), disabling CSRF genuinely reopens the vulnerability it was designed to close. The safe-to-disable rule applies specifically because JWT-in-header authentication is immune to the attack CSRF protection exists to prevent — not as a blanket rule for all APIs.

Crafting Your Own Rules — Custom Security Configurations

Videos: Crafting Your Own Rules - Custom Security Configurations Parts 1 & 2
@Configuration
@EnableWebSecurity
@EnableMethodSecurity  // enables @PreAuthorize/@PostAuthorize on service/controller methods
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())              // stateless JWT API — safe, per above
            .cors(Customizer.withDefaults())            // picks up the CorsConfigurationSource bean below
            .sessionManagement(sm ->
                sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))  // no HttpSession ever created
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/v1/auth/**", "/swagger-ui/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/v1/jobs/**").permitAll()  // public reads
                .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")          // role-based restriction
                .anyRequest().authenticated()
            )
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)  // custom JWT filter — covered later
            .httpBasic(basic -> basic.disable())
            .formLogin(form -> form.disable());
        return http.build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();   // covered in depth in the Password Encoders topic
    }
}
MethodPurpose
hasRole("ADMIN")Requires the authenticated principal to hold authority ROLE_ADMIN (Spring auto-prefixes ROLE_ — don't include it yourself)
hasAuthority("SCOPE_read")Requires an exact authority string — no auto-prefixing, used for fine-grained permissions/scopes rather than coarse roles
hasAnyRole(...) / hasAnyAuthority(...)Matches if the principal holds any one of several listed roles/authorities
requestMatchers(HttpMethod.GET, "...")Scopes a rule to a specific HTTP method, not just a path — common for "public reads, protected writes" patterns
⚠ Rule Ordering Matters — First Match Wins

authorizeHttpRequests rules are evaluated in the order declared, and the first matching rule applies — later rules for the same path are never reached. A very common real bug: placing .anyRequest().authenticated() before a more specific permitAll() rule for a sub-path, which makes the specific rule unreachable and unintentionally locks down an endpoint meant to be public. Always order rules from most specific to least specific, with anyRequest() last.

FAANGWhy SessionCreationPolicy.STATELESS specifically for a JWT-based API, and what does it actually change?

It instructs Spring Security to never create or use an HttpSession to store the SecurityContext — every single request must independently prove who it is (via the JWT in the Authorization header), rather than relying on server-side session state tied to a JSESSIONID cookie. This is the architectural foundation that makes true horizontal scaling trivial: any server instance can handle any request without needing shared/sticky session state (directly connecting to the session-scope scalability discussion from Section 5) — a load balancer can route requests to any instance in the fleet with zero coordination.

CoreWhat's the difference between hasRole and hasAuthority, precisely?

Both check the principal's granted authorities, but hasRole("ADMIN") is sugar that automatically checks for the authority string "ROLE_ADMIN" — the ROLE_ prefix convention is a Spring Security-specific pattern for coarse-grained roles. hasAuthority("SCOPE_read") checks the exact string with no prefixing magic — used for finer-grained permission/scope-style authorization (common in OAuth2 setups where authorities come from token scopes, not simple roles). Mixing them up (e.g., calling hasRole("ROLE_ADMIN"), double-prefixing) is a very common configuration bug that silently fails all authorization checks.

CORS Configuration via Spring Security

Video: CORs configurations using Spring Security

This revisits Section 4's CORS topic, but configured through Spring Security's CORS integration rather than a plain WebMvcConfigurer — necessary because once Spring Security is on the classpath, its filter chain runs before Spring MVC even sees the request, so a CORS configuration living only in WebMvcConfigurer can be overridden or never even reached for security-protected endpoints.

@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("http://localhost:4200"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    config.setAllowedHeaders(List.of("*"));
    config.setAllowCredentials(true);

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
}

// then in the SecurityFilterChain: .cors(Customizer.withDefaults())
// — this tells Spring Security to USE the CorsConfigurationSource bean above
⚠ Why CORS Must Be Configured Before Security Rejects the Request

Spring Security's CORS integration deliberately runs its own CorsFilter early in the filter chain — before authentication/authorization checks — specifically so that browser preflight OPTIONS requests (which never carry auth credentials, per Section 4's CORS mechanics) aren't rejected with a 401/403 before the browser even gets a chance to see the CORS headers it needs. Without this ordering, every cross-origin request to a secured endpoint would fail at the preflight stage, regardless of how correctly CORS itself was configured.

💡 The Single Most Important Mental Model in This Entire Section

Spring Security is fundamentally a chain of Servlet Filters, not "magic." Every feature — form login, Basic Auth, CSRF, and your own custom JWT validation — is implemented as a filter with a specific, well-defined position in that chain. Once this clicks, the entire framework stops feeling like a black box: adding JWT support is just "insert one more filter, before the point where Spring would otherwise reject an unauthenticated request."

FAANGHow does SecurityContextHolder make the current user available across an entire request without passing it as a parameter everywhere, and what's the catch with async code?

SecurityContextHolder defaults to a ThreadLocal-based storage strategy — the SecurityContext is bound to the thread currently processing the request. Since a typical Spring MVC request is handled start-to-finish on one dedicated thread, any code anywhere in that call stack (controller, service, repository) can call SecurityContextHolder.getContext().getAuthentication() and get the correct current user, with zero explicit parameter-passing — the exact same ThreadLocal mechanism underlying Section 5's request-scoped bean discussion. The catch: if work is handed off to a different thread (a custom thread pool, @Async, or reactive/WebFlux code), that new thread has no ThreadLocal-bound context by default, and getAuthentication() returns null unless the context is explicitly propagated (e.g., via DelegatingSecurityContextRunnable or switching the holder strategy to MODE_INHERITABLETHREADLOCAL).

FAANGWhat's the difference between authentication and authorization, precisely, and where does each happen in the filter chain?

Authentication answers "who are you?" — verifying identity (username/password check, JWT signature validation) — handled by the authentication-related filters (e.g., UsernamePasswordAuthenticationFilter, or a custom JWT filter) earlier in the chain, ultimately populating the SecurityContextHolder. Authorization answers "are you allowed to do this?" — checking the now-known identity's permissions against the requested resource — handled by AuthorizationFilter (formerly FilterSecurityInterceptor) at the end of the chain, evaluating your authorizeHttpRequests rules. This ordering is architecturally necessary: you cannot check permissions before you know who's asking.

CoreWhy does Spring Security use a Filter chain instead of, say, an interceptor or AOP-based approach like @Transactional does?

Servlet Filters operate at the lowest level of the request-processing pipeline — before the request even reaches DispatcherServlet/Spring MVC (as established in Section 3's request lifecycle). This is deliberate: security decisions (rejecting an unauthenticated or unauthorized request) need to happen as early as possible, ideally before any application code, database access, or business logic executes at all — minimizing the attack surface and avoiding wasted work on requests that will ultimately be rejected. An AOP/interceptor-based approach operating deeper inside Spring MVC would mean the request has already partially been processed by the time security is checked — a fundamentally weaker security posture.

Encoding vs Encryption vs Hashing

Video: Encoding Vs Encryption Vs Hashing

Three fundamentally different operations, frequently confused, and a very common interview question in its own right.

EncodingEncryptionHashing
PurposeData format transformation for compatibility (e.g., binary → text)Confidentiality — hide data from unauthorized readersIntegrity/verification — produce a fixed-size fingerprint of data
Reversible?✅ Yes, trivially — no key needed at all✅ Yes, but only with the correct key❌ No — deliberately one-way by design
Needs a key/secret?❌ No✅ Yes (symmetric or asymmetric key)❌ No (though a "salt" is added — not a secret key)
ExampleBase64, URL encodingAES, RSABCrypt, SHA-256, Argon2
Used for passwords?❌ Never — trivially reversible, provides zero security❌ Rarely for passwords specifically — if the encryption key is ever compromised, every password is instantly recoverable✅ Yes — the correct and standard approach
⚠ Why Passwords Are Hashed, Never Encrypted or "Just" Encoded

Encoding (like Base64) provides zero security — it's designed to be reversed by anyone, with no key at all; using it for passwords is equivalent to storing them in plaintext. Encryption is reversible by design for legitimate use (decrypting a message meant to be read again later) — but this reversibility is exactly the wrong property for password storage: if a database breach also exposes the encryption key (a very plausible joint compromise), every single user's plaintext password is immediately recoverable. Hashing is deliberately one-way — there is no key to steal that would let an attacker recover the original password; the system only ever needs to verify a match (hash the login attempt, compare hashes), never to reconstruct the original.

FAANGIf hashing is one-way, how does a login system verify a password without ever "decrypting" the stored hash?

It never needs to — login verification is fundamentally a re-computation and comparison, not a decryption. At signup, the system hashes the raw password once and stores only the hash. At login, it takes the newly submitted password, runs it through the exact same hashing algorithm (with the same salt, extracted from the stored hash itself — covered in the next topic), and checks whether the resulting hash matches the stored one. If both the original and the login attempt are the same string, a deterministic hash function always produces the same output — meaning a match is proof the submitted password is correct, without the system ever needing to know or reconstruct the original plaintext at all.

CoreGive a legitimate real-world use case for each of encoding, encryption, and hashing in a typical Spring Boot application.

Encoding: Base64-encoding a binary file attachment to safely embed it inside a JSON payload, or URL-encoding query parameters with special characters. Encryption: encrypting sensitive data at rest that the application genuinely needs to read back later in its original form — e.g., a stored payment card token, or PII that must be decrypted for display to an authorized user. Hashing: password storage (the topic at hand), but also things like generating a checksum/fingerprint of a file to verify it wasn't tampered with in transit, or as part of a JWT's signature (covered later in this section).

How Passwords Really Stay Safe — Introduction to Password Encoders

Video: How Passwords Really Stay Safe & introduction to Password Encoders

Why Plain Hashing (Even SHA-256) Isn't Enough

A naive approach — SHA-256(password) stored directly — is vulnerable to rainbow table attacks: precomputed lookup tables mapping common password hashes back to their plaintext, built once and reused against any leaked database. Fast, general-purpose hash functions like SHA-256 also make brute-force attacks computationally cheap for an attacker with GPU/ASIC hardware, since SHA-256 was designed to be fast — the opposite of what you want for password hashing specifically.

The Two Properties a Real Password Hashing Algorithm Needs

PropertyWhy It MattersHow It's Achieved
SaltingDefeats rainbow tables — the same password produces a different hash for every user, since each hash incorporates a unique random valueA random salt is generated per password, and (with BCrypt) stored as part of the resulting hash string itself — no separate salt column needed
Deliberate slowness (work factor)Makes brute-force/dictionary attacks computationally expensive even with powerful hardware — milliseconds per guess instead of billions of guesses per secondAn adjustable "cost factor" / number of iterations, tunable to stay slow even as hardware gets faster over time
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();   // default strength/work factor = 10
    // higher strength (e.g. 12) = slower hashing = more resistant to brute-force,
    // but also slower login for legitimate users — a deliberate, tunable trade-off
}

// registration:
String hashed = passwordEncoder.encode(rawPassword);  // a NEW random salt generated every call
userRepository.save(new User(username, hashed));

// login:

// matches() extracts the salt FROM storedHash, re-hashes the attempt with
// that same salt, and compares — never needs a separately stored salt column

💡 Why BCrypt (or Argon2) Over Generic Hashes — Stated Precisely

"BCrypt is a purpose-built password hashing algorithm — it automatically handles per-password salting (defeating rainbow tables) and has a tunable, deliberately slow work factor (defeating brute-force at scale), whereas general-purpose hashes like SHA-256/MD5 are designed to be fast — the exact opposite property you want for password storage." Argon2 (winner of the 2015 Password Hashing Competition) is the more modern, even stronger recommendation for new systems, additionally resistant to GPU/ASIC-based cracking via its memory-hardness — worth mentioning as the current best-practice frontier beyond BCrypt.

FAANGWhy does BCrypt's encode() method produce a DIFFERENT output every time for the same input password, and is that a bug?

Not a bug — this is the entire point of automatic per-call salting. Every call to encode() generates a fresh, cryptographically random salt, incorporates it into the hashing computation, and embeds that salt directly in the returned string. Two users with the identical password "password123" will get two completely different stored hash strings, which is exactly what defeats rainbow-table and cross-user pattern attacks — an attacker who cracks one user's hash learns nothing about any other user, even if they share the same underlying password.

CoreIf BCrypt hashes don't store the salt in a separate column, how does matches() know which salt to use for comparison?

The salt is encoded directly within the stored hash string itself (as shown in the anatomy breakdown above — the second segment). When matches(raw, storedHash) is called, BCrypt parses the stored string, extracts the algorithm version, cost factor, and salt from it, re-runs the exact same hashing computation on the raw input using that extracted salt, and compares the resulting hash segment to the one already stored. This self-contained format is a deliberate design choice that simplifies password storage schemas — no separate salt column is ever needed.

FAANGHow would you safely migrate an existing user base from an old, weak hashing scheme (e.g., unsalted MD5) to BCrypt without forcing every user to reset their password?

DelegatingPasswordEncoder (Spring Security's actual default) is purpose-built for exactly this migration scenario: store existing legacy hashes prefixed with an identifier like {md5}, and configure new hashes to use {bcrypt} going forward. Existing users can still log in — their submitted password is verified against the legacy algorithm identified by the stored prefix. A common production pattern layers on top of this: upon a successful login using a legacy-hashed password, transparently re-hash and re-save that user's password using the new, stronger algorithm at that moment — gradually migrating the entire user base to the stronger scheme over time, purely through normal login activity, with zero forced password resets.

Creating Users with InMemoryUserDetailsManager

Videos: Creating users using InMemoryUserDetailsManager Parts 1 & 2
@Bean
public UserDetailsService userDetailsService(PasswordEncoder encoder) {
    UserDetails admin = User.withUsername("admin")
            .password(encoder.encode("admin123"))
            .roles("ADMIN")         // stored internally as authority "ROLE_ADMIN"
            .build();

    UserDetails user = User.withUsername("nikhil")
            .password(encoder.encode("pass123"))
            .roles("USER")
            .build();

    return new InMemoryUserDetailsManager(admin, user);
}

InMemoryUserDetailsManager is a full UserDetailsService implementation backed purely by an in-memory collection — no database at all. It's an excellent tool for demos, prototyping, and understanding the UserDetailsService contract in isolation, but obviously unsuitable for production (users vanish on every restart, no persistence, no scaling across multiple instances).

⚠ The Production Path: A Custom UserDetailsService

Real applications implement UserDetailsService themselves, backed by a JPA repository (from Section 4) — loadUserByUsername() queries the database for the user, maps the result to a UserDetails implementation (often by having your own User entity implement UserDetails directly, or via a dedicated adapter class), and returns it. Everything else in the authentication flow (password matching, authority checking) works identically to the in-memory version — InMemoryUserDetailsManager exists purely to teach the contract without the added complexity of a real data layer.

Invoking the Spring Security Authentication Flow Manually

Videos: Invoking the Spring Security authentication flow manually Parts 1 & 2
@RestController
@RequestMapping("/api/v1/auth")
@RequiredArgsConstructor
public class AuthController {

    private final AuthenticationManager authenticationManager;

    @PostMapping("/login")
    public ResponseEntity<String> login(@RequestBody LoginRequest request) {

        // step 1: build an UNAUTHENTICATED token from raw credentials
        Authentication authRequest =
            new UsernamePasswordAuthenticationToken(request.getUsername(), request.getPassword());

        // step 2: hand it to the AuthenticationManager — this is where ALL the
        // internal machinery from the "Internals" topic actually executes:
        // UserDetailsService lookup + PasswordEncoder.matches(), end to end
        Authentication authResult = authenticationManager.authenticate(authRequest);
        // throws BadCredentialsException / DisabledException / etc. on failure —
        // caught centrally by @RestControllerAdvice (Section 5)

        // step 3: authentication succeeded — generate and return a JWT
        // (the exact next topic in this section)
        String token = jwtService.generateToken(authResult);
        return ResponseEntity.ok(token);
    }
}

@Bean
public AuthenticationManager authenticationManager(AuthenticationConfiguration config) throws Exception {
    return config.getAuthenticationManager();  // exposes Spring's auto-configured manager as an injectable bean
}
💡 Why This Manual Invocation Matters — The Bridge to JWT

This is the precise architectural seam where a traditional, form-login-based Spring Security app becomes a modern, token-issuing API. Rather than letting Spring Security's own UsernamePasswordAuthenticationFilter handle a login form submission and establish a session, you build a plain @RestController login endpoint that manually drives the exact same underlying AuthenticationManager/UserDetailsService/PasswordEncoder machinery — but on success, instead of creating a session, you issue a stateless JWT that the client will present on every subsequent request. Everything from the internals topic still applies; only the final step (session vs token) changes.

FAANGWhat's the exact difference between the UsernamePasswordAuthenticationToken passed INTO authenticate() versus the one returned FROM it?

The one passed in is unauthenticated — constructed with just the raw username and raw password, and its isAuthenticated() flag is false. Internally, AuthenticationManager (via ProviderManager delegating to DaoAuthenticationProvider) looks up the user via UserDetailsService, verifies the password via PasswordEncoder.matches(), and upon success constructs and returns a new, fully authenticated Authentication object — this one populated with the user's granted authorities and isAuthenticated() returning true. This returned, authenticated object is what gets placed into SecurityContextHolder (in the traditional session-based flow) or, in the JWT flow, is what gets encoded into the token's claims.

⚠ The Single Most Common JWT Misconception

A JWT is signed, not encrypted. Anyone who intercepts a JWT — a network sniffer, a malicious browser extension, or simply pasting it into jwt.io — can trivially read the header and payload; Base64URL encoding is reversible by design, exactly like plain Base64 encoding discussed in the Encoding-vs-Encryption topic. The signature only guarantees the token hasn't been tampered with since it was issued — it does nothing to hide the payload's contents. Never place sensitive data (passwords, SSNs, secret internal flags) in a JWT payload.

FAANGWhy is JWT revocation fundamentally harder than session invalidation, and how would you handle "logout" or a compromised token in a real system?

A session is a server-side record — logging out simply deletes it, instantly and universally invalidating that session everywhere. A JWT, by design, is self-contained and stateless — the server never "remembers" having issued it, so there's no natural place to delete a record from. Practical mitigations: (1) keep access token expiry short (minutes, not hours/days) so a compromised token has a small window of usefulness, (2) maintain a server-side token blocklist/denylist (in Redis, checked on every request) for explicitly revoked tokens before their natural expiry — this reintroduces some server state, a deliberate trade-off, and (3) use a refresh token pattern (a longer-lived, separately-stored token used only to mint new short-lived access tokens) so that revoking the refresh token effectively cuts off a compromised session's ability to get new access tokens, even though already-issued access tokens remain valid until their own short expiry.

CoreWhat are the standard registered claims (iat, exp, sub, etc.) and why use them instead of just custom claim names?

The JWT spec (RFC 7519) defines a small set of standard, reserved claim names with well-understood meaning: sub (subject — typically the username/user ID), iat (issued-at timestamp), exp (expiration timestamp), iss (issuer), aud (intended audience). Using these standard names rather than inventing your own equivalents (e.g., a custom "expiresAt" field) means every general-purpose JWT library across every language/framework understands and correctly validates them automatically (e.g., automatically rejecting an expired token based on exp) — interoperability and correctness for free, rather than reimplementing expiry-checking logic yourself.

💡 Why Asymmetric Signing Matters for Microservices — A Common System Design Follow-Up

In a microservices architecture, distributing a shared HMAC secret to every service that needs to validate tokens means every one of those services could also forge valid tokens — a significant blast radius if any single service is compromised. With RSA/ECDSA, only the central Auth service holds the private signing key; every downstream microservice only needs the (non-secret) public key to verify signatures, and a compromised downstream service gains no ability to mint its own valid tokens. This asymmetry is precisely why RS256 is the standard choice in real-world microservices and OAuth2/OIDC systems (a natural bridge to discuss if asked about scaling this pattern).

FAANGAn attacker intercepts a valid JWT and tries to modify the payload's "role" claim from USER to ADMIN, then re-sends it. Walk through exactly why this fails.

The attacker can trivially Base64URL-decode the payload, edit the role claim, and re-encode it — but the signature segment was computed over the original header+payload bytes using a secret/private key the attacker doesn't possess. When the modified token reaches the server, the server recomputes what the signature should be for the tampered header+payload using its own secret key, and this recomputed signature will not match the (unchanged, now-stale) signature segment still attached to the forged token — the server immediately rejects it with a signature mismatch, before even looking at the claims' business meaning. This is the entire security guarantee JWT signing provides: tamper-evidence, not confidentiality.

FAANGWhat is the "alg: none" JWT vulnerability, and how does a well-implemented validation library defend against it?

A historical class of vulnerability where some poorly-implemented JWT libraries would trust the alg field from the incoming token itself to decide how to validate it — an attacker could craft a token with "alg": "none" and an empty signature, and a naive verifier would skip signature validation entirely, accepting any forged payload. The fix, now standard in every reputable JWT library, is for the server to hardcode/whitelist the expected algorithm (and its own known key) rather than trusting the token's self-declared algorithm — validation should always be "verify this token was signed with algorithm X using key Y," never "trust whatever algorithm the token claims to use." A related variant involves tricking an RS256 verifier into treating the public key as if it were an HMAC secret — also defeated by hardcoding the expected algorithm rather than trusting the token's header.

Generating JWT Tokens in the Backend App

Videos: Generating JWT token in backend app Parts 1 & 2
@Service
public class JwtService {

    @Value("${jwt.secret}")
    private String secretKey;   // externalized — NEVER hardcoded in source

    @Value("${jwt.expiration-ms}")
    private long expirationMs;

    public String generateToken(Authentication authentication) {
        String username = authentication.getName();
        String roles = authentication.getAuthorities().stream()
                .map(GrantedAuthority::getAuthority)
                .collect(Collectors.joining(","));

        Date now = new Date();
        Date expiry = new Date(now.getTime() + expirationMs);

        return Jwts.builder()
                .subject(username)
                .claim("roles", roles)         // custom claim
                .issuedAt(now)
                .expiration(expiry)
                .signWith(getSigningKey())       // HMAC key derived from the secret
                .compact();
    }

    private SecretKey getSigningKey() {
        byte[] keyBytes = Decoders.BASE64.decode(secretKey);
        return Keys.hmacShaKeyFor(keyBytes);
    }
}

⚠ Signing Key Requirements for HS256

The JWT spec's HMAC-SHA256 requires a signing key of at least 256 bits (32 bytes) — a short, weak, or guessable secret string dramatically weakens the entire signature guarantee, since a short key is brute-forceable. Always generate a cryptographically random secret of sufficient length, store it in a proper secrets manager (AWS Secrets Manager, HashiCorp Vault, or at minimum environment variables — never hardcoded or committed to git), and rotate it periodically as a security best practice.

FAANGWhy put roles/authorities directly in the JWT payload instead of looking them up from the database on every request?

This is the entire point of statelessness — embedding the user's authorities directly in the signed token means a downstream request can be fully authorized without any database round-trip, since the token itself is cryptographically trustworthy (its signature guarantees the roles claim hasn't been tampered with since a legitimate login). The trade-off: if a user's role changes mid-session (e.g., an admin is demoted), that change won't take effect until their current token expires and they re-authenticate — a deliberate consequence of statelessness that's usually acceptable given short token expiries, but worth explicitly naming as a trade-off in a system design discussion, since it's a real staleness window some systems mitigate with very short-lived access tokens plus frequent refresh.

Building a Filter to Validate the JWT Token

Videos: Building a filter on the backend to validate the JWT token Parts 1 & 2

This is where the Internals topic's filter-chain diagram becomes real, working code — a custom filter, inserted at exactly the point discussed earlier (.addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)), that runs on every single incoming request to validate any presented JWT and populate SecurityContextHolder accordingly.

@Component
@RequiredArgsConstructor
public class JwtAuthFilter extends OncePerRequestFilter {  // guarantees exactly ONE execution per request

    private final JwtService jwtService;
    private final UserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {

        String authHeader = request.getHeader("Authorization");

        // no token, or wrong format — just pass through; let downstream
        // authorization rules (authorizeHttpRequests) decide if that's OK
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            filterChain.doFilter(request, response);
            return;
        }

        String token = authHeader.substring(7);   // strip "Bearer " prefix

        try {
            String username = jwtService.extractUsername(token);  // parses + validates signature internally

            // only proceed if we have a username AND nothing is already authenticated
            // (avoids redundant work if some earlier mechanism already set it)
            if (username != null && SecurityContextHolder.getContext().getAuthentication() == null) {

                UserDetails userDetails = userDetailsService.loadUserByUsername(username);

                if (jwtService.isTokenValid(token, userDetails)) {  // checks signature + expiry + username match

                    UsernamePasswordAuthenticationToken authToken =
                        new UsernamePasswordAuthenticationToken(
                            userDetails, null, userDetails.getAuthorities());
                    authToken.setDetails(
                        new WebAuthenticationDetailsSource().buildDetails(request));

                    // THIS is the line that makes the request "authenticated" from
                    // here on — everything downstream (controllers, @PreAuthorize) sees
                    // this user as the current principal
                    SecurityContextHolder.getContext().setAuthentication(authToken);
                }
            }
        } catch (JwtException ex) {
            // invalid/expired/tampered token — do NOT throw; simply don't authenticate.
            // downstream authorizeHttpRequests rules will correctly reject as unauthenticated
        }

        filterChain.doFilter(request, response);  // ALWAYS continue the chain — this filter never blocks by itself
    }
}

💡 Why OncePerRequestFilter, Specifically

OncePerRequestFilter is a Spring-provided base class guaranteeing the filter's logic executes exactly once per request, even in scenarios involving internal request forwarding/dispatching within the servlet container where a naive raw Filter might otherwise run multiple times for the same logical request. Since JWT validation involves real computational work (signature verification, a potential database lookup via UserDetailsService), running it more than once per request would be both wasteful and a subtle source of bugs — this is why it's the standard, idiomatic base class for custom Spring Security filters.

⚠ Why the Filter Never Throws on an Invalid Token

Notice the filter catches JwtException and simply continues the chain rather than immediately rejecting the request itself. This is deliberate separation of concerns: this filter's only job is authentication (populating who the user is, if determinable) — authorization (deciding whether the request is allowed to proceed) is left entirely to the later AuthorizationFilter, which evaluates the authorizeHttpRequests rules. This keeps the two concerns cleanly separated exactly as established in the Internals topic, and correctly allows requests to endpoints marked permitAll() to succeed even with no token, an expired token, or a malformed token present.

FAANGWhy does the filter check "if getAuthentication() == null" before setting a new one — what scenario is this actually guarding against?

It's a defensive guard against doing redundant, unnecessary work (like a fresh UserDetailsService database lookup) if the SecurityContext has somehow already been populated earlier in the chain for this same request — for instance, in a hybrid setup supporting both JWT and traditional session-based auth simultaneously, or when a request is internally forwarded/included within the servlet container and passes through the filter chain's context-setting logic more than once at a lower level. While less critical in a purely JWT-only, stateless configuration, this check is a widely-adopted defensive idiom for custom Spring Security filters.

FAANGTrace the complete end-to-end flow: a client logs in, receives a JWT, then calls a protected endpoint. Describe every step across both requests.

Request 1 (login): Client POSTs credentials to /api/v1/auth/login (a permitAll() endpoint) → AuthController builds an unauthenticated UsernamePasswordAuthenticationToken → hands it to AuthenticationManager.authenticate() → internally delegates to DaoAuthenticationProvider → calls UserDetailsService.loadUserByUsername() → verifies the password via PasswordEncoder.matches() → returns a fully authenticated Authentication → controller passes this to JwtService.generateToken() → a signed JWT is built and returned to the client in the response body. Request 2 (protected call): Client sends Authorization: Bearer <token> → request hits JwtAuthFilter (positioned before UsernamePasswordAuthenticationFilter in the chain) → filter extracts and validates the token's signature/expiry → loads the corresponding UserDetails → builds a new authenticated Authentication object and stores it in SecurityContextHolder → request continues down the chain → AuthorizationFilter checks the now-populated SecurityContextHolder against the endpoint's authorizeHttpRequests rule (e.g., hasRole("ADMIN")) → if satisfied, the request finally reaches DispatcherServlet and the controller method executes, with SecurityContextHolder.getContext().getAuthentication() accessible anywhere in that call stack.

FAANGDesign a complete, production-appropriate authentication and authorization architecture for a new Spring Boot microservices system from scratch.

A dedicated Auth service handling login/signup, hashing passwords with BCrypt/Argon2 (never plain hashing), issuing short-lived JWTs signed with RS256 (asymmetric — so downstream services only need the public key, never the ability to forge tokens) plus a separately-stored, longer-lived refresh token for silent re-authentication. Every downstream microservice runs a stateless JwtAuthFilter validating tokens independently (no shared session store, no database round-trip needed for basic auth checks — true horizontal scalability). CORS configured explicitly per allowed frontend origin, CSRF disabled (justified specifically because auth is token-in-header, not cookie-based). Fine-grained authorization via authorizeHttpRequests path/method rules plus @PreAuthorize method-level checks for business-logic-level permission checks. A Redis-backed token denylist for explicit revocation before natural expiry. This ties together nearly every concept from this entire section into one coherent system design answer.

FAANGWhere should a JWT be stored on the client — localStorage, sessionStorage, or a cookie — and what are the security trade-offs of each?

localStorage/sessionStorage: accessible to any JavaScript running on the page, making it vulnerable to XSS (Cross-Site Scripting) — if an attacker injects malicious JS (e.g., via an unsanitized user-generated content field), they can read the token directly and exfiltrate it. Not vulnerable to CSRF, since nothing is auto-attached by the browser. An httpOnly, Secure, SameSite cookie: inaccessible to JavaScript entirely (immune to XSS token theft), but reintroduces CSRF exposure since the browser auto-attaches cookies to requests — which is exactly why CSRF protection would need to be re-enabled (contradicting the earlier "disable CSRF for JWT" guidance, which specifically assumed header-based, non-cookie delivery). Modern best practice for high-security applications often uses httpOnly cookies for the token combined with re-enabled CSRF protection and a SameSite cookie attribute (mitigating most CSRF vectors on its own) — a genuinely nuanced trade-off worth discussing both sides of rather than giving a single "correct" answer.

CoreWhat is @PreAuthorize, and how does it relate to the authorizeHttpRequests rules configured in SecurityFilterChain?

@PreAuthorize("hasRole('ADMIN')") is a method-level authorization annotation (enabled via @EnableMethodSecurity, shown in the Custom Security Configurations topic) implemented via AOP (an interceptor wraps the annotated method, checking the expression against SecurityContextHolder's current authentication before allowing the method body to execute) — conceptually similar to how @Transactional works via proxying. authorizeHttpRequests rules in SecurityFilterChain operate at the HTTP/URL level, checked by the AuthorizationFilter before the request ever reaches a controller. The two are complementary, not competing: URL-level rules give a coarse-grained first line of defense (e.g., "everything under /admin/** requires ADMIN"), while @PreAuthorize allows finer-grained, business-logic-aware checks directly on service methods (e.g., "a user can only edit their own order" — a check that can't be expressed as a simple URL pattern).

FAANGHow would you implement a refresh token flow alongside short-lived access tokens?

At login, issue two tokens: a short-lived access token (minutes, sent on every API request) and a longer-lived refresh token (days/weeks, stored more carefully — often httpOnly cookie or secure storage, and typically also persisted server-side, e.g. in a database table, specifically so it CAN be revoked, unlike a pure stateless access token). A dedicated /api/v1/auth/refresh endpoint accepts a valid, non-expired refresh token and issues a brand-new access token (and often a rotated new refresh token too, invalidating the old one — "refresh token rotation," which limits the damage if a refresh token is ever stolen, since using a stolen-but-already-used refresh token can be detected and the whole token family revoked). This pattern balances the security benefit of short-lived access tokens (limiting the damage window of a leaked token) against the UX cost of forcing frequent full re-logins.

CoreWhat HTTP status code should an expired/invalid JWT produce, and how does that get wired up given the JwtAuthFilter doesn't throw exceptions itself?

The correct status is 401 Unauthorized (unauthenticated — the server doesn't know who's asking, per the 401-vs-403 distinction from Section 3). Since JwtAuthFilter deliberately swallows JwtException and just leaves SecurityContextHolder empty rather than throwing, the actual 401 response is generated later, by ExceptionTranslationFilter — when the downstream AuthorizationFilter subsequently finds no authenticated principal for a protected endpoint, it throws an AuthenticationException, which ExceptionTranslationFilter catches and translates into a 401 response (typically delegating to an AuthenticationEntryPoint bean, which can be customized to return a structured JSON error body consistent with Section 5's global exception handling shape, rather than Spring Security's default plain-text response).

FAANGExplain the complete difference between BCrypt password hashing and JWT signature verification — both use cryptographic algorithms, but for fundamentally different purposes. Don't confuse them.

They solve entirely different problems despite both living in the "security" topic area. BCrypt is about one-way, irreversible transformation — proving a submitted password matches a stored credential, with no way to recover the original from the hash, specifically defending against credential theft from a database breach. JWT signing (HMAC/RSA) is about tamper-evidence on data the server WANTS to be readable (the payload is meant to be decoded and used) — proving the token's contents haven't been altered since a trusted party issued it, not about hiding the contents at all (the payload is only Base64-encoded, fully reversible, as established earlier). Conflating "signing" with "hashing for storage," or assuming a JWT's payload is protected the way a BCrypt hash protects a password, is a common and revealing interview mistake.
