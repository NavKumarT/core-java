Global Exception Handling with @RestControllerAdvice

Videos: Global Exception Handling in Spring Boot using @RestControllerAdvice - Parts 1 & 2

The Problem Without Centralized Handling

Without a global handler, every controller method needs its own try-catch to translate exceptions into proper HTTP responses — duplicated, inconsistent, and easy to forget. A missing catch block means an unhandled exception falls through to Spring Boot's default error handling, which returns a generic, unhelpful 500 Internal Server Error with a raw stack trace (in dev) or a bare-bones error page — neither of which is acceptable for a real API contract.

@RestControllerAdvice  // = @ControllerAdvice + @ResponseBody — applies GLOBALLY, across every @RestController
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(
            ResourceNotFoundException ex, WebRequest request) {
        ErrorResponse error = ErrorResponse.builder()
                .status(HttpStatus.NOT_FOUND.value())
                .message(ex.getMessage())
                .timestamp(LocalDateTime.now())
                .path(request.getDescription(false))
                .build();
        return new ResponseEntity<>(error, HttpStatus.NOT_FOUND);
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)  // thrown by @Valid failures
    public ResponseEntity<Map<String, String>> handleValidation(
            MethodArgumentNotValidException ex) {
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getFieldErrors().forEach(err ->
                errors.put(err.getField(), err.getDefaultMessage()));
        return ResponseEntity.badRequest().body(errors);
    }

    @ExceptionHandler(Exception.class)  // CATCH-ALL — last resort for anything unanticipated
    public ResponseEntity<ErrorResponse> handleGeneric(Exception ex) {
        ErrorResponse error = ErrorResponse.builder()
                .status(HttpStatus.INTERNAL_SERVER_ERROR.value())
                .message("An unexpected error occurred")  // never leak raw ex.getMessage() to clients here!
                .timestamp(LocalDateTime.now())
                .build();
        return new ResponseEntity<>(error, HttpStatus.INTERNAL_SERVER_ERROR);
    }
}
// custom, meaningful exceptions thrown from the SERVICE layer —
// business logic stays clean, translation to HTTP happens centrally
public class ResourceNotFoundException extends RuntimeException {
    public ResourceNotFoundException(String message) {
        super(message);
    }
}

public class DuplicateResourceException extends RuntimeException {
    public DuplicateResourceException(String message) { super(message); }
}

// usage in the service layer:
public Contact getContact(String id) {
    return contactRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("Contact not found: " + id));
}
@Data @Builder
public class ErrorResponse {
    private int status;
    private String message;
    private LocalDateTime timestamp;
    private String path;
    // a CONSISTENT shape across every error response makes client-side
    // error handling predictable — exactly what REST best practices called for
}
Controller/Service throws ResourceNotFoundException │ ▼ DispatcherServlet catches it, checks registered @ExceptionHandler methods │ ▼ Finds handleNotFound() in @RestControllerAdvice — MOST SPECIFIC match wins │ (Spring matches the most specific exception type first — │ e.g. a handler for IllegalArgumentException beats one for Exception) ▼ Builds and returns a proper 404 + structured ErrorResponse body
💡 @ControllerAdvice vs @RestControllerAdvice

Same relationship as @Controller vs @RestController from Section 3: @RestControllerAdvice = @ControllerAdvice + @ResponseBody, meaning every @ExceptionHandler method's return value is serialized straight to the response body (JSON) rather than resolved as a view. For a REST API, always use @RestControllerAdvice.

⚠ Never Leak Internal Exception Details to Clients

The catch-all Exception.class handler should return a generic, safe message — never the raw ex.getMessage() or stack trace, which can leak internal implementation details (SQL fragments, class names, file paths) that aid an attacker in reconnaissance. Log the full exception server-side (with the stack trace) for debugging, but return only a sanitized message to the client — this exact distinction is a common security-review talking point.

FAANGIf two @ExceptionHandler methods in the same @RestControllerAdvice could both match a thrown exception, which one wins?

Spring selects the handler registered for the most specific exception type in the class hierarchy relative to the thrown exception. If a ResourceNotFoundException extends RuntimeException is thrown, and handlers exist for both ResourceNotFoundException and the broader RuntimeException/Exception, the more specific ResourceNotFoundException handler wins. This is exactly why a generic Exception.class catch-all handler should always be defined last conceptually (order in the file doesn't matter — specificity does) — it only fires when nothing more specific matches.

CoreCan @RestControllerAdvice be scoped to only specific packages or controllers, rather than applying globally?

Yes — @RestControllerAdvice(basePackages = "com.growthscript.api") restricts it to controllers within that package, or @RestControllerAdvice(assignableTypes = {OrderController.class}) scopes it to specific controller classes. Omitting these attributes (the common default) applies the advice globally, to every @RestController in the application — the typical choice for a single unified error-handling strategy.

Backend Validation — Your Last Line of Defense

Videos: Dangers of Relying Only on Client-Side Validation · Backend Validations Parts 1–3

Why Client-Side Validation Alone Is Dangerous

Client-side (browser/mobile) validation exists purely for UX — instant feedback without a round trip. It provides zero real security, because a client is entirely under the end user's control: JavaScript validation can be disabled, bypassed by directly crafting HTTP requests with Postman/curl/a script, or defeated by intercepting and modifying requests with a proxy tool. Any validation the server doesn't itself enforce effectively doesn't exist from a security standpoint.

⚠ The Core Principle

Never trust the client. Every constraint that matters for data integrity or security — required fields, format, length, business rules — must be re-validated on the server, regardless of what the frontend already checked. Client-side validation is a convenience layer; backend validation is the actual security/integrity boundary.

Bean Validation (JSR-380) with @Valid

⚠ Forgetting @Valid on Nested Objects Is a Common Bug

Bean Validation does not automatically cascade into nested objects or collection elements — a nested DTO's own constraints are silently skipped unless the containing field is also annotated @Valid. This is one of the most common real-world validation bugs: a nested object's @NotBlank field passes an empty string straight through because the parent field was missing its own @Valid.

FAANGWhat's the difference between @Valid and @Validated, and when would you specifically need @Validated?

@Valid is the standard Bean Validation (JSR-380) annotation, sufficient for the vast majority of cases including @RequestBody validation and cascading into nested objects. @Validated is a Spring-specific annotation that adds two extra capabilities @Valid alone doesn't have: (1) validation groups — applying different subsets of constraints depending on context (e.g., a "create" group requiring all fields vs an "update" group allowing partial data), and (2) enabling method-level parameter validation on service-layer methods (not just @RequestBody DTOs) when placed at the class level combined with constraint annotations directly on method parameters.

FAANGWhere exactly does @Valid validation happen in the request lifecycle, and what exception does a failure produce?

Validation happens during argument resolution — before the controller method body executes — as part of Spring MVC's HandlerMethodArgumentResolver chain (the same phase that deserializes @RequestBody and binds @PathVariable/@RequestParam). A failure throws MethodArgumentNotValidException (for @RequestBody validation) — this is precisely why a global @ExceptionHandler(MethodArgumentNotValidException.class) in @RestControllerAdvice is the standard place to translate validation failures into a structured 400 response listing every failed field, rather than handling it per-controller.

CoreShould validation logic ever live in the entity/JPA layer instead of the DTO?

Both layers can carry validation annotations, and they serve different purposes: DTO-level validation guards the API contract (what a client is allowed to submit), while entity-level validation (via the same JSR-380 annotations) acts as a last-resort database integrity check that Hibernate enforces right before persisting, catching any invalid state that somehow bypassed the DTO layer (e.g., data constructed internally by a batch job, not through the REST API at all). Relying on entity-level validation as the only validation is risky, though, since JPA validation failures throw a less client-friendly ConstraintViolationException deep in the persistence layer rather than a clean, early 400 response.

Tracking Who Did What — Spring JPA Auditing

Videos: Introduction to Spring JPA Auditing Parts 1 & 2

Spring Data JPA Auditing automatically populates standard "who/when" metadata fields — created timestamp, last-modified timestamp, created-by user, last-modified-by user — on every entity, without manually setting them in every service method.

@SpringBootApplication
@EnableJpaAuditing  // the single switch that turns auditing on application-wide
public class JobPortalApplication {
    public static void main(String[] args) {
        SpringApplication.run(JobPortalApplication.class, args);
    }
}
@MappedSuperclass              // NOT an @Entity itself — fields are inherited INTO subclass tables
@EntityListeners(AuditingEntityListener.class)  // hooks lifecycle callbacks that populate these fields
public abstract class BaseEntity {

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;

    @CreatedBy
    @Column(updatable = false)
    private String createdBy;

    @LastModifiedBy
    private String updatedBy;
    // getters/setters omitted
}

// every entity simply extends BaseEntity — fields appear as real columns
@Entity
public class Job extends BaseEntity {
    @Id @GeneratedValue private Long id;
    private String title;
}
// tells Spring HOW to determine "who" the current user is, for @CreatedBy/@LastModifiedBy
@Component
public class SpringSecurityAuditorAware implements AuditorAware<String> {

    @Override
    public Optional<String> getCurrentAuditor() {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        if (auth == null || !auth.isAuthenticated()) {
            return Optional.of("SYSTEM");  // fallback for unauthenticated/system-driven changes
        }
        return Optional.of(auth.getName());
    }
}
AnnotationPopulated When
@CreatedDateOnce, at entity creation (first persist)
@LastModifiedDateEvery time the entity is updated
@CreatedByOnce, at creation — pulled from your AuditorAware implementation
@LastModifiedByEvery update — same AuditorAware source
💡 Why @MappedSuperclass, Not @Entity, for the Base Class

@MappedSuperclass means BaseEntity itself has no corresponding database table — its fields are simply inherited and mapped into each subclass's own table as regular columns (Job's table gets created_at, updated_at columns directly). This is different from JPA inheritance strategies like SINGLE_TABLE/JOINED, which model true polymorphic entity hierarchies — auditing fields are a pure code-reuse/DRY concern, not a real "is-a" domain relationship, so @MappedSuperclass is the correct, lightweight tool.

FAANGHow does AuditingEntityListener actually populate these fields under the hood?

AuditingEntityListener is a JPA entity listener hooked to lifecycle callback events — specifically @PrePersist (fires just before an INSERT) and @PreUpdate (fires just before an UPDATE). On @PrePersist, it sets both @CreatedDate and @CreatedBy (since this is the entity's first save) as well as the "last modified" fields to the same initial values; on @PreUpdate, it only refreshes @LastModifiedDate/@LastModifiedBy, leaving the original creation metadata untouched (reinforced by @Column(updatable = false) on the created fields as a defense-in-depth database-level guarantee).

CoreWhat happens if @EnableJpaAuditing is present but no AuditorAware bean is registered?

@CreatedDate/@LastModifiedDate still work fine, since timestamps don't need an "auditor" source. But @CreatedBy/@LastModifiedBy fields will simply remain null — Spring Data JPA has no way to determine "who" without an AuditorAware<T> bean explicitly telling it how to resolve the current user (typically from Spring Security's SecurityContextHolder, as shown above, though it could just as easily pull from a request-scoped tenant/user-context object in a non-Spring-Security setup).

Request, Session, Application & WebSocket Bean Scopes

Videos: Introduction to Request/Session/Application/Websocket Bean Scopes · Hands-On Request & Session Scopes · Application Scope

Beyond singleton and prototype (Section 2), Spring provides web-aware scopes, only available within a DispatcherServlet/web-application context.

requestOne instance per single HTTP request — created fresh for each request, discarded once the response completesRequest-scoped context objects (correlation IDs, per-request accumulated data used across multiple collaborators within that request)

💡 Why proxyMode Is Required Here — Same Root Cause as Section 2's Prototype Trap

This is the exact same underlying problem covered when injecting a prototype bean into a singleton in Section 2: a request/session-scoped bean's real instance only exists while that request/session is active, but a singleton controller/service (created once, at startup) needs to hold a reference to it. The proxyMode = ScopedProxyMode.TARGET_CLASS setting makes Spring inject a CGLIB proxy instead of a direct reference — every method call on that proxy transparently delegates to whichever request/session's real instance is currently active (resolved from a ThreadLocal behind the scenes), rather than binding to one fixed instance at singleton-construction time.

FAANGWhy is server-side session scope increasingly avoided in modern REST API design?

Session scope requires the server to maintain stateful, in-memory data tied to a specific server instance for each user — this directly conflicts with REST's stateless constraint and makes horizontal scaling harder: a load balancer must route all of a given user's requests back to the exact same server instance (sticky sessions) unless session data is externalized to a shared store (Redis), adding infrastructure complexity. Modern stateless architectures instead encode necessary user context in a self-contained token (JWT) sent with every request, letting any server instance handle any request without shared session state — a foundational scalability principle worth articulating clearly in system design discussions.

CoreWhat's the practical difference between application scope and singleton scope, since both effectively give "one instance"?

They're nearly identical in a typical single-application-context Spring Boot app — application scope ties the bean's lifetime to the ServletContext rather than the Spring ApplicationContext directly. The distinction only matters in more unusual setups, like a single web application composed of multiple Spring ApplicationContexts sharing one ServletContext (rare, historically seen in some multi-module enterprise WAR deployments) — in that scenario, application scope guarantees one shared instance across all those contexts, whereas each context would otherwise get its own separate singleton instance. For nearly all modern Spring Boot apps (one embedded server, one context), singleton is simply the right, simpler default.

JPA Relationships Roadmap & The Foundation

Videos: What You'll Learn - JPA Relationships Roadmap · The Foundation - Understanding Entity Relationships in Spring Data JPA

A relational database expresses relationships between tables using foreign keys. JPA's job is to let you express that same relationship directly between Java objects — one entity holding a reference (or collection of references) to another — while Hibernate translates that object graph into the correct foreign-key-based SQL underneath.

RelationshipReal-World ExampleCardinality
@OneToOneOne User has one UserProfile1 : 1
@OneToMany / @ManyToOneOne Company posts many Jobs; each Job belongs to one Company1 : N (this section's focus)
@ManyToManyMany Jobs require many Skills; each Skill appears on many JobsM : N
💡 The Core Mental Model Before Any Annotation

Always identify which side owns the foreign key column first, independent of annotations — that's always the "many" side in a one-to-many relationship (e.g., the jobs table has a company_id foreign key column; the companies table has no corresponding column at all). The owning side is where @ManyToOne goes; the non-owning/inverse side (@OneToMany) merely describes the relationship from the other direction using mappedBy, without controlling the actual foreign key.

Unpacking JPA Mappings — The Full Story Behind OneToMany & ManyToOne

Video: Unpacking JPA Mappings - The Full Story Behind OneToMany & ManyToOne
@Entity
@Table(name = "companies")
public class Company {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    // INVERSE side — mappedBy points to the FIELD NAME on Job that owns this relationship
    // no "company_id"-style column exists on the companies table — this is purely
    // an object-graph convenience for navigating company.getJobs()
    @OneToMany(mappedBy = "company", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Job> jobs = new ArrayList<>();
}
@Entity
@Table(name = "jobs")
public class Job {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;

    // OWNING side — this is the field JPA maps to the actual "company_id" FK column
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "company_id", nullable = false)
    private Company company;
}
TABLE companies TABLE jobs ┌────┬───────────┐ ┌────┬─────────────┬────────────┐ │ id │ name │ │ id │ title │ company_id │◄── the ONLY actual FK column ├────┼───────────┤ ├────┼─────────────┼────────────┤ exists ONLY on the "many" side │ 1 │ Acme Corp │◄───────────│ 1 │ Backend Eng. │ 1 │ │ │ ├────┼─────────────┼────────────┤ │ │◄───────────│ 2 │ Frontend Eng. │ 1 │ └────┴───────────┘ └────┴─────────────┴────────────┘ Company (ONE side) Job (MANY / OWNING side) @OneToMany(mappedBy="company") @ManyToOne + @JoinColumn(name="company_id") — describes the relationship — ACTUALLY CONTROLS the foreign key
⚠ Bidirectional Consistency — A Very Common Real Bug

Because Job.company owns the FK, simply doing company.getJobs().add(newJob) on the inverse side does not persist the relationship — the jobs.company_id column is never set, because Hibernate only looks at the owning side (Job.company) when generating INSERT/UPDATE SQL. You must explicitly set both sides: newJob.setCompany(company); company.getJobs().add(newJob); — or better, add a convenience helper method on the "one" side that keeps both sides in sync automatically (a common, recommended pattern: addJob(Job job) { jobs.add(job); job.setCompany(this); }).

FAANGWhy does mappedBy exist at all — why can't both sides just independently declare the relationship?

A relational foreign key is inherently a one-directional, single-column fact in the database — only one table can physically hold the FK column. If both @OneToMany and @ManyToOne tried to independently "own" and manage that same column, Hibernate would have two conflicting, potentially out-of-sync sources of truth for the same piece of data, and could generate redundant or even contradictory SQL. mappedBy resolves this ambiguity explicitly: it tells Hibernate "this side is purely a read-only, in-memory navigational convenience — the other side (identified by field name) is the single source of truth that actually controls the column."

CoreWhy is a bidirectional relationship (both @OneToMany and @ManyToOne present) common, rather than just using @ManyToOne alone?

A unidirectional @ManyToOne-only mapping is perfectly valid and simpler when you only ever need to navigate "from job to its company" — and is often the right, more minimal default. A bidirectional mapping is added specifically when you also need convenient navigation "from company to all its jobs" in your object model (e.g., company.getJobs() to display a company's full job listing) — at the cost of the added complexity of keeping both sides in sync (as shown in the box above) and a higher risk of accidentally triggering infinite recursion during JSON serialization if entities are ever returned directly instead of DTOs (tying back to Section 4's DTO-pattern rationale).

FETCH vs CASCADE — The Two JPA Concepts You Must Never Confuse

Video: FETCH vs CASCADE - The Two JPA Concepts You Must Never Confuse

These two concepts are unrelated in purpose despite both being relationship-annotation attributes, and conflating them is one of the most common JPA misunderstandings.

fetchcascade
ControlsWhen associated data is loaded/queried from the database (read direction)Which operations (persist, remove, merge, etc.) automatically propagate from a parent entity to its associated child entities (write direction)
Answers the question"When I load a Company, should its jobs collection be fetched immediately or only on first access?""When I save() or delete() a Company, should that operation automatically also apply to its associated Jobs?"
ValuesFetchType.EAGER (load immediately, via JOIN) / FetchType.LAZY (defer until accessed, via proxy)CascadeType.PERSIST, MERGE, REMOVE, REFRESH, DETACH, or ALL (all of the above)
Default@ManyToOne/@OneToOne default to EAGER; @OneToMany/@ManyToMany default to LAZYNo cascading at all by default — you must explicitly opt in per operation
// FETCH: purely about READ timing — completely independent of cascade
@ManyToOne(fetch = FetchType.LAZY)   // company NOT loaded until job.getCompany() is called
@JoinColumn(name = "company_id")
private Company company;

// company.jobs left at DEFAULT fetch (LAZY for @OneToMany) — jobs only
// queried the first time company.getJobs() is actually accessed
@OneToMany(mappedBy = "company")
private List<Job> jobs;
// CASCADE: purely about WRITE propagation — nothing to do with when reads happen
@OneToMany(mappedBy = "company", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Job> jobs = new ArrayList<>();

// with CascadeType.ALL / PERSIST:
Company company = new Company("Acme");
company.addJob(new Job("Backend Engineer"));  // helper keeps both sides in sync
companyRepository.save(company);
// saving company AUTOMATICALLY persists the new Job too — one save() call,
// two INSERT statements generated. Without cascade, the Job would need
// its own explicit jobRepository.save(job) call.
⚠ orphanRemoval vs CascadeType.REMOVE — A Frequently Confused Pair

CascadeType.REMOVE deletes child entities when the parent itself is explicitly deleted (companyRepository.delete(company) also deletes all its jobs). orphanRemoval = true is stricter and independent — it deletes a child the moment it's removed from the parent's collection, even if the parent itself is never deleted (company.getJobs().remove(someJob) immediately deletes that job from the database on next flush, because it's now an "orphan" with no parent reference). Many real bugs come from expecting one behavior and getting the other.

FAANGWhy does @ManyToOne default to EAGER while @OneToMany defaults to LAZY — is this arbitrary?

Not arbitrary — it reflects the JPA spec's assumption about typical cardinality cost. A @ManyToOne association points to exactly one other row (e.g., one Company per Job) — fetching it eagerly is a cheap, bounded, single-row join. A @OneToMany association can point to an unbounded number of rows (a company could have thousands of jobs) — eagerly loading that by default would be a potentially catastrophic, unpredictable performance cost baked into every single query that touches the "one" side. In practice, though, many teams override @ManyToOne's default to LAZY explicitly anyway (as shown in the example above) to keep fetch behavior consistent and predictable across the whole codebase, and to avoid unexpectedly large eager-join query plans as the object graph grows.

FAANGIs it safe to use CascadeType.ALL on a @ManyToOne (the "many"/owning side) the same way it's used on @OneToMany?

Generally no — this is a subtle but important asymmetry. Cascading from the "many" side toward the "one" side is dangerous: if Job cascades REMOVE to its Company, deleting a single job could unintentionally delete the entire company and, transitively, every other job that company owns — clearly not the intended semantics. Cascade is almost always configured on the parent-owns-children direction (here, Company → Job via @OneToMany), matching the real-world domain semantics of "if the parent goes away, its exclusively-owned children should go too" — not the reverse.

@OnDelete Explained — What Really Happens When the Parent Is Deleted

Video: @OnDelete Explained - What Really Happens When the Parent is Deleted

By default, without any cascade configuration, attempting to delete a Company row that still has Job rows referencing it via foreign key throws a database-level constraint violation (DataIntegrityViolationException in Spring's translated exception hierarchy) — the database itself refuses to leave orphaned foreign key references.

Hibernate's CascadeType.REMOVE (covered above) handles this at the application/ORM level — Hibernate first issues DELETE statements for every child row, then deletes the parent, all orchestrated in Java. Hibernate's @OnDelete annotation takes a fundamentally different approach: it configures the database itself to handle cascading deletes natively, via a ON DELETE CASCADE foreign key constraint.

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "company_id")
@OnDelete(action = OnDeleteAction.CASCADE)  // Hibernate-specific — generates
private Company company;                        // "ON DELETE CASCADE" in the DDL itself

// resulting DDL (when ddl-auto generates the schema):
// ALTER TABLE jobs ADD CONSTRAINT fk_company
//   FOREIGN KEY (company_id) REFERENCES companies(id) ON DELETE CASCADE;
CascadeType.REMOVE (Hibernate/ORM-level)@OnDelete (Database-level)
Who executes the deletesHibernate — issues individual DELETE statements for each child, in Java, then the parentThe database engine itself, atomically, as part of the single DELETE on the parent
PerformanceSlower for large child collections — N+1-style individual DELETEs, and requires loading children into the persistence context firstMuch faster — one database-native cascading operation, no need to load anything into memory first
Only works viaHibernate/JPA — if a child row is deleted through raw SQL/another tool bypassing Hibernate, this cascade never firesEnforced at the schema/constraint level — fires correctly regardless of what deletes the parent row (Hibernate, a raw SQL script, another application entirely)
PortabilityStandard JPA — works identically regardless of the underlying database vendorHibernate-specific annotation (not part of the JPA spec) — though the resulting SQL feature (ON DELETE CASCADE) is itself standard across virtually all relational databases
💡 When to Reach for @OnDelete Instead of CascadeType.REMOVE

@OnDelete(action = OnDeleteAction.CASCADE) is the better choice when deleting a parent with a genuinely large number of children (performance-sensitive bulk-delete scenarios), or when other systems/scripts might delete rows outside of your Hibernate-managed application and you still need referential integrity guaranteed at the database level regardless of the deletion path. CascadeType.REMOVE is preferable when you need Hibernate lifecycle callbacks (@PreRemove, etc.) to fire correctly on each child during the cascade, since database-level cascades bypass the ORM/Java layer entirely and no Java code runs for the cascaded child deletions.

FAANGIf you use both CascadeType.REMOVE and @OnDelete(CASCADE) together, what happens, and is that redundant or dangerous?

It's technically redundant, not dangerous — Hibernate would first delete children individually via its own cascade logic (issuing the DELETE statements itself), and by the time it deletes the parent, the child rows are already gone, so the database-level ON DELETE CASCADE constraint simply has nothing left to cascade. The practical downside is purely wasted clarity/intent — it's unclear to a future reader which mechanism is "actually" responsible for the behavior, and it forfeits the performance benefit that was the whole point of choosing @OnDelete in the first place (since Hibernate is still doing the slower, one-by-one deletion). Pick one mechanism deliberately based on the trade-offs above, not both.

CoreWithout either CascadeType.REMOVE or @OnDelete, what specific error occurs when deleting a Company that still has Jobs, and how would you diagnose it?

The database rejects the DELETE due to the foreign key constraint, and Hibernate throws a ConstraintViolationException, which Spring's @Repository exception translation (from Section 2's stereotype discussion) converts into a DataIntegrityViolationException. Diagnosing it means recognizing the message will typically reference the specific foreign key constraint name and the referencing table — the fix is deciding deliberately whether the intended behavior is cascading deletion (add CascadeType.REMOVE/@OnDelete), reassigning children first, or blocking the deletion entirely with a clear business-level error message (often the safer default in production, especially for irreversible cascading deletes of potentially valuable data).

FAANGDesign a complete, consistent error-response strategy for a public REST API from scratch.

A single @RestControllerAdvice class with targeted @ExceptionHandler methods per meaningful exception type (not-found, validation, duplicate/conflict, unauthorized), each returning a consistent structured shape (status code, human-readable message, timestamp, request path, and ideally a machine-readable error code for programmatic client handling), a catch-all handler for anything unanticipated that logs full details server-side but returns only a sanitized message to the client, custom domain exceptions thrown from the service layer (keeping business logic free of HTTP concerns), and validation failures automatically mapped to a field-by-field error map via MethodArgumentNotValidException handling. This combines the exception-handling and validation topics from this section into one coherent, senior-level system design answer.

FAANGTrace exactly what happens, step by step, when you call company.getJobs() on a lazily-loaded association.

(1) Hibernate initially populated company.jobs with an uninitialized persistent collection proxy (a PersistentBag/PersistentList) rather than the real data, when the Company was first loaded. (2) Calling .getJobs() and then iterating/accessing it triggers the proxy's initialization logic. (3) If the current persistence context/session is still open, Hibernate transparently issues a SELECT * FROM jobs WHERE company_id = ? query at that exact moment, populates the real collection, and returns it. (4) If the session has already closed (e.g., outside the original @Transactional method), this triggers LazyInitializationException instead, since there's no active session to run the query against — directly connecting back to Section 4's lazy-loading discussion.

CoreWhat's the difference between DTO-level @NotNull/@NotBlank validation and JPA entity-level @Column(nullable=false)?

DTO-level Bean Validation runs before the controller method body executes, during argument resolution — it's an API-contract-level check that produces a clean 400 response early, before any database interaction happens at all. @Column(nullable = false) is a database schema constraintDataIntegrityViolationException deep in the persistence layer rather than a clean early validation error.

FAANGHow would you audit not just "who created this row" but a full historical change log — every field value at every point in time?

Spring Data JPA's built-in auditing (@CreatedBy/@LastModifiedBy/@CreatedDate/@LastModifiedDate) only tracks the current state's metadata, not a full history of every change. For genuine historical/versioned auditing, the standard tool is Hibernate Envers, which automatically maintains a parallel "audit" table per entity, recording every INSERT/UPDATE/DELETE as a new revision — letting you query "what did this entity look like at revision N" or "show the full change history." This distinction (current-state metadata vs. full historical versioning) is a strong signal of practical, beyond-tutorial JPA experience.

CoreWhy does SpringDoc OpenAPI need annotations like @Operation at all if it can already infer endpoints from @GetMapping/@RequestBody automatically?

SpringDoc can infer the structural facts automatically — the HTTP method, path, and request/response schema shapes, since those are directly derivable from existing Spring MVC annotations and Java types. What it cannot infer is human intent and business meaning: what a field actually represents, why an endpoint might return a 409, what a parameter's valid range means in business terms. @Operation/@ApiResponse/@Parameter exist purely to layer that human-authored documentation on top of the auto-inferred structure — the combination of "automatically always structurally correct" plus "manually enriched with meaning" is what makes the resulting docs genuinely useful rather than just a dry schema dump.

FAANGA request-scoped bean is injected into a singleton service using a scoped proxy. Under high concurrent load, could two simultaneous requests ever see each other's data?

No, by design — the scoped proxy resolves the "real" request-scoped instance via a ThreadLocal internally, and since each incoming HTTP request in a servlet container is handled on its own dedicated thread (in the traditional Spring MVC/Tomcat thread-per-request model), each thread's ThreadLocal lookup resolves to that specific request's own isolated bean instance — there's no cross-contamination between concurrent requests. The one place this breaks down is if application code manually hands off work to a different thread (e.g., submitting a task to a custom thread pool or using @Async without properly propagating context) — the new thread has no ThreadLocal-bound request context, and attempting to resolve the request-scoped proxy there throws an exception, since there is genuinely no "current request" from that thread's perspective.
