Section 8 · Spring Boot Bible

Service Discovery & Registration in Microservices

Every time Accounts needs to call Loans, it faces a question a monolith never has to ask: "at this exact moment, which network address is a healthy instance of Loans actually running at?" In a cloud-native system where instances scale up and down and get replaced constantly, that address is never fixed. This section covers the standard production answer — a self-updating service registry (Eureka), client-side discovery and load balancing, declarative inter-service calls (Feign), and the failure-detection mechanics (heartbeats, self-preservation) that keep the whole thing correct even when the network itself misbehaves.

How to use this document: Topics 102–106 build the conceptual case for service discovery before any Eureka-specific code appears — worth reading in full even if you're impatient to get to the implementation, since "why client-side discovery over a traditional load balancer" is one of the most common system-design interview questions this section maps directly onto.

Brief Introduction About Microservices Traffic

Two fundamentally different kinds of traffic flow through a microservices system — this section is about only one of them.

Traffic typeAlso calledExampleConcern of this section?
Client-to-serviceNorth-south trafficA mobile app calling POST /api/create on Accounts through a public-facing entry pointNo — covered separately under API Gateway topics
Service-to-serviceEast-west trafficAccounts internally calling Loans and Cards to assemble a "customer summary" responseYes — this entire section

East-west traffic is what makes microservices genuinely different from a monolith at the networking level: in a monolith, one module calling another is just a Java method call, resolved at compile time, with zero network involved. In microservices, that same logical dependency becomes a real network call to a separate, independently-deployed, independently-scaled process — one whose exact network location isn't fixed and can't be assumed.

Why this deserves its own section

Section 4 already containerized these services and Section 6 centralized their configuration, but nothing so far has addressed how one running service instance finds another running service instance's actual network address at the moment it needs to call it. That's the entire subject of this section.

What's the difference between north-south and east-west traffic?

North-south traffic is external client traffic entering the system from outside (a browser or mobile app calling an API). East-west traffic is internal, service-to-service traffic within the system — one microservice calling another to fulfill part of a request.

Why does a monolith not have this problem at all?

In a monolith, one module calling another is an in-process method call resolved at compile/class-load time — there's no network address to discover because both modules run in the same process. Microservices turn that same logical call into a real network call between separately deployed processes, which is exactly what introduces the "where is the other service right now" problem.

Why does the east-west vs north-south distinction matter for how you design security and observability, not just discovery?

North-south traffic crosses a trust boundary (public internet to your system) and typically gets one consistent security/observability treatment at a single choke point — an API Gateway enforcing auth, rate limiting, and centralized logging for every external request. East-west traffic happens between already-trusted internal services, at a much higher volume and much lower per-call latency budget, so applying the same heavyweight gateway-style processing to every internal call would be both a performance problem and often unnecessary given the calls originate from your own trusted services. This is why internal service-to-service auth (e.g. mutual TLS, service-to-service tokens) and internal observability (distributed tracing propagated between services) are typically designed as separate, lighter-weight concerns from north-south API Gateway policy — a distinction interviewers listen for when discussing microservices security architecture.

Introduction to Service Discovery & Registration Inside Microservices

The problem, precisely stated — and the two-part mechanism that solves it.

Why hardcoded addresses stop working

In a traditional, static deployment, a service ran on a fixed server with a fixed IP — hardcoding http://10.0.4.12:8080 as "the Loans service" in Accounts's config was ugly but functional, because that address rarely changed. In a modern cloud-native/containerized deployment, this assumption completely breaks down:

  • Instances are ephemeral — a container restarting (crash, redeploy, node eviction) typically comes back with a different IP address entirely.
  • Auto-scaling constantly changes the instance count — the set of "currently running Loans instances" grows and shrinks based on load, sometimes multiple times an hour.
  • Deployments replace instances wholesale — a rolling deploy doesn't update existing instances in place; it terminates old ones and starts entirely new ones at new addresses.

Any hardcoded address is stale almost immediately in this environment. The system needs a way to answer "who are the currently healthy instances of Loans, right now" as a live query, not a fixed config value.

The two-part solution

Service DiscoveryAny client that needs to call another service queries the Service Registry — "give me all healthy instances of Loans" — and gets back a current, accurate list, resolved at call time rather than assumed from static config.

Why can't microservices just hardcode each other's IP addresses in configuration?

Because instances in a containerized/cloud environment are ephemeral — restarts, auto-scaling, and rolling deployments constantly change which addresses are actually running a given service, so any hardcoded address goes stale almost immediately.

What's the difference between service registration and service discovery?

Registration is a service instance announcing itself to a central registry on startup (and keeping that registration alive via heartbeats). Discovery is a client querying that registry to find the current, healthy instances of a service it needs to call.

Could you solve this problem with DNS alone, without a dedicated service registry like Eureka?

Partially — DNS-based discovery (as used natively by Kubernetes Services, for instance) works by resolving a stable service name to a current set of backing IPs, updated as instances come and go. The gap versus a dedicated registry like Eureka is DNS's typically coarser health-awareness and caching/TTL behavior — DNS resolvers and clients often cache results for some interval, meaning a just-failed instance might still be returned until the cache expires, whereas a registry with active heartbeat-based health tracking (covered in topics 111–112) can reflect instance health changes faster and more precisely. In practice, Kubernetes-native environments do lean on DNS-based discovery successfully (backed by its own controller continuously updating DNS/Endpoints records), while Eureka-style registries remain common specifically in non-Kubernetes or Spring-Cloud-centric deployments — the two represent genuinely different implementations of the same underlying registration/discovery idea.

Why Not Traditional Load Balancers for Microservices

A very common interview question — the precise, technical reasons a conventional LB architecture doesn't fit this problem well.

How a traditional load balancer works

A conventional load balancer (hardware appliance or something like a statically-configured nginx/HAProxy) sits in front of a pool of backend servers whose addresses are configured — usually manually or via a slow-to-update configuration management process — into the LB itself. Every request flows through the LB, which picks a backend and forwards the request.

The interview-ready framing

The precise answer isn't "traditional load balancers are bad" — they're excellent for their actual use case (client-to-service/north-south traffic hitting a relatively stable, centrally-managed entry point). The problem is specifically applying that static, centralized model to dynamic, high-volume, decentralized east-west traffic between constantly-changing microservice instances — a fundamentally different traffic shape that needs a fundamentally different, self-updating, decentralized mechanism.

Name two reasons a traditional load balancer struggles as the sole mechanism for microservices east-west traffic.

Any two of: its backend list is statically/manually configured and goes stale quickly given constant instance churn; it's a single point of failure for all traffic passing through it; it adds a network hop/latency to every internal call; and it doesn't scale operationally when dozens of independently-scaling services each need dynamic backend awareness.

Is a traditional load balancer still useful anywhere in a microservices architecture, given these limitations?

Yes — it remains the right tool for north-south traffic specifically: a comparatively stable, centrally-managed entry point (an API Gateway or a cloud load balancer like an AWS ALB) sitting between external clients and the system is exactly the traffic shape traditional LBs handle well (lower relative volume than aggregate east-west traffic, a natural single well-monitored ingress point where centralizing auth/rate-limiting/TLS termination is actually desirable rather than a bottleneck). The distinction this topic draws isn't "LBs are obsolete," it's "the traditional centralized LB model is the wrong tool specifically for dynamic, high-volume, decentralized east-west traffic" — client-side discovery (covered next) is the purpose-built alternative for that specific traffic shape, while north-south traffic still benefits from a traditional/cloud LB or gateway.

Service Discovery & Registration Inside Microservices — The Two Architectural Patterns

Server-side discovery vs client-side discovery — a foundational distinction, and where each is used in practice.

Pattern 1: Server-side discovery

The client sends its request to a well-known intermediary (a router or load balancer), which itself queries the service registry and forwards the request to a chosen healthy instance. The client is entirely unaware discovery is happening — it just calls one fixed address, and the intermediary does the discovery and routing work.

Real-world examples: AWS Application Load Balancer integrated with ECS Service Discovery; Kubernetes Services (kube-proxy routing to pod IPs behind a stable virtual IP); a dedicated router tier like Netflix's older Zuul-as-router setups.

Pattern 2: Client-side discovery

The client itself directly queries the service registry, receives the full list of healthy instances, and applies its own load-balancing logic to pick one — then calls that instance directly, with no intermediary in the actual request path.

What's the core difference between server-side and client-side service discovery?

In server-side discovery, a central router/load balancer queries the registry and forwards requests — the client just calls one fixed address, unaware discovery happened. In client-side discovery, the calling service itself queries the registry directly and picks an instance to call, with no intermediary in the request path.

Which pattern does Eureka implement?

Client-side discovery — each client embeds a Eureka discovery client and a load balancer (Spring Cloud LoadBalancer) to query the registry and pick an instance itself, calling it directly.

What's the real trade-off between these two patterns beyond "one has an extra hop"?

Client-side discovery avoids the extra hop and the shared-component failure risk, but pushes real complexity into every single client — each service needs a compatible discovery-client library, meaning this pattern couples you somewhat to a specific ecosystem (Eureka has first-class Spring Cloud support; a client written in a different language/stack needs its own compatible Eureka client library, which may be less mature or unavailable). Server-side discovery centralizes that complexity into one well-maintained router/LB tier, making it trivially usable by clients in any language with zero special libraries — a meaningful advantage in a genuinely polyglot organization — at the cost of that tier becoming both a latency addition and an operational dependency for all east-west traffic. This is exactly why Kubernetes-native environments (a genuinely language-agnostic platform) lean toward server-side-style discovery via Services/DNS, while Spring-Cloud-centric, largely-Java shops (like this course's setup) often find client-side discovery via Eureka a natural fit.

How Client-Side Service Discovery & Load Balancing Works

The exact sequence of events, end to end, for a single inter-service call.

Step-by-step mechanics

  1. Registration — On startup, each Loans instance's embedded Eureka Client sends a REGISTER call to the Eureka Server, containing its service ID (`LOANS`), host, port, and health-check URL.
  2. Heartbeats — Every 30 seconds (default), each registered instance sends a RENEW (heartbeat) call to the Eureka Server to confirm it's still alive.
  3. Registry caching (server side) — The Eureka Server maintains an in-memory registry of every currently-known-healthy instance across all registered services.
  4. Registry fetch (client side) — When Accounts starts up, its own embedded Eureka Client fetches a full copy of the registry from the Eureka Server and caches it locally, refreshing this local cache periodically (also every 30 seconds by default) rather than calling the Eureka Server on every single business request.
  5. Instance selection — When Accounts's code needs to call Loans, the client-side load balancer (Spring Cloud LoadBalancer) looks up `LOANS` in the locally-cached registry, gets back a list of currently-healthy instances, and picks one using a load-balancing strategy (round-robin by default).
  6. Direct call — Accounts calls the chosen Loans instance directly over the network — no intermediary router or LB sits in this request's path at all.

Why the local cache matters more than it might seem

Because Accounts's Eureka Client caches the registry locally and refreshes on an interval (rather than querying Eureka Server per-request), a single business request calling Loans never actually depends on Eureka Server being reachable at that exact moment — it depends on the local cache being reasonably fresh. This is a deliberate resilience trade-off: Eureka favors availability over strict consistency (an instance of the AP side of the CAP theorem in practice) — client calls keep working using a slightly-stale cached view even if the Eureka Server itself is temporarily unreachable, rather than every single service-to-service call failing the instant the registry is unavailable.

Does Accounts query Eureka Server on every single call to Loans?

No — Accounts's Eureka Client fetches and locally caches the registry, refreshing on a periodic interval (default 30 seconds), and picks an instance from that local cache for each call. It doesn't hit Eureka Server for every individual business request.

What load-balancing strategy does Spring Cloud LoadBalancer use by default?

Round-robin — distributing calls evenly, in rotation, across the currently-known healthy instances of the target service.

What CAP-theorem trade-off is Eureka making, and why is it the right choice for this specific use case?

Eureka is explicitly designed as an AP system (Availability + Partition tolerance, sacrificing strict Consistency) rather than CP — during a network partition or temporary Eureka Server unavailability, clients keep operating on their last-known-good cached registry rather than refusing to serve any inter-service calls at all. This is the right trade-off for service discovery specifically because a slightly stale registry (occasionally routing to an instance that just went down, caught and retried) is a far smaller problem than every single inter-service call across the entire system failing the moment the registry has a hiccup — availability of the overall system matters more here than perfect real-time accuracy of "which exact instances exist right now." Contrast this with, say, a leader-election or distributed-lock use case, where strict consistency genuinely matters more than availability, and a CP system (like Zookeeper) would be the more appropriate choice.

Since the client's registry view can be stale, what happens if Accounts's load balancer picks an instance that has actually just gone down?

The call fails (typically a connection refused/timeout), and it's the calling application's responsibility to handle that failure gracefully — commonly via a retry against a different instance (Spring Cloud LoadBalancer and Spring Retry can be configured to automatically retry a failed call against another instance from the same cached list), combined with a circuit breaker (covered in later resilience-focused sections) to stop repeatedly hitting a service that's failing broadly rather than just one bad instance. This is precisely why client-side discovery systems are always paired with retry/resilience logic in production — the registry's eventual consistency is an accepted trade-off specifically because the failure mode (an occasional failed call to a just-died instance) is cheap to detect and recover from at the calling layer.

Spring Cloud Support for Service Discovery & Registration

The DiscoveryClient abstraction, and where Eureka fits among the alternatives.

The DiscoveryClient abstraction

Spring Cloud defines a common DiscoveryClient interface that abstracts over the specific service-registry implementation — application code that depends on service discovery (including Feign, covered later in this section) programs against this interface, not against Eureka specifically. This means switching the underlying registry technology is, in principle, a dependency and configuration change rather than an application-code rewrite.

ImplementationBacking technologyNotes
Netflix EurekaPurpose-built AP registry from Netflix OSSThe most common choice in Spring-Cloud-centric systems; what this course uses
HashiCorp ConsulGeneral-purpose service mesh/registry toolAlso provides KV config storage and health checking; popular outside pure-Spring shops
Apache ZookeeperGeneral-purpose distributed coordination service (CP-oriented)Older, more consistency-focused option; also used for leader election, distributed locks
Kubernetes-native discoveryKubernetes Services + built-in DNSWhen deployed on Kubernetes, discovery can be delegated to the platform itself, removing the need for Eureka entirely
Why this course still teaches Eureka even though Kubernetes exists

Kubernetes-native discovery is genuinely the more common production choice today for teams already running on Kubernetes — it needs no extra service to operate, and it's server-side discovery baked into the platform. Eureka remains valuable to learn because (a) many real systems still run on plain VMs/Docker Compose/non-Kubernetes infrastructure where a dedicated registry is necessary, (b) it teaches the underlying concepts (registration, heartbeats, client-side load balancing) explicitly rather than hiding them inside platform magic, and (c) it's still a very live interview topic precisely because of how clearly it illustrates these mechanics.

What is Spring Cloud's DiscoveryClient interface for?

It's a common abstraction for service discovery that application code programs against, independent of the specific registry technology (Eureka, Consul, Zookeeper) — letting the underlying implementation be swapped via dependencies/config rather than requiring application code changes.

Name two alternatives to Eureka for service discovery.

Any two of: HashiCorp Consul, Apache Zookeeper, and Kubernetes-native discovery via Services and built-in DNS.

How consistency-focused is Zookeeper compared to Eureka, and why would that matter for choosing between them?

Zookeeper is fundamentally a CP system (built on a consensus protocol, ZAB, prioritizing strict consistency) — during a network partition, a Zookeeper cluster favors correctness over availability, potentially refusing writes/reads on a minority partition rather than risk inconsistency. This makes Zookeeper an excellent fit for use cases genuinely requiring strong consistency (distributed locks, leader election, where an inconsistent view could cause real correctness bugs like two nodes both believing they're the leader), but a comparatively poor fit for service discovery specifically, where — as discussed in topic 106 — availability during a partition (clients continuing to operate on a stale-but-usable cached registry) matters more than perfect real-time accuracy. This CP-vs-AP distinction is exactly why Eureka, purpose-built as AP, became the more natural default for service discovery in the Spring Cloud ecosystem despite Zookeeper being a capable, earlier-established distributed systems tool.

@EnableEurekaServer

Turns an ordinary Spring Boot application into a Eureka registry server — auto-configures the registration/heartbeat/lookup REST endpoints and the built-in web dashboard.

eureka.client.register-with-eureka

Set to false because, by default, every Eureka-aware Spring Boot app (including the server itself, which also has the Eureka client on its classpath) tries to register itself as a client — this flag prevents the standalone server from trying to register with itself.

eureka.client.fetch-registry

Also set to false for the same reason — the server doesn't need to fetch a copy of the registry from itself, since it is the registry.

Port 8761 is the Eureka convention (not a hard requirement) and serves a built-in web dashboard showing every currently registered instance, its status, and metadata — extremely useful for manually verifying registration during development.

What annotation turns a Spring Boot app into a Eureka Server?

`@EnableEurekaServer`, from the `spring-cloud-starter-netflix-eureka-server` dependency.

Why does the Eureka Server itself set register-with-eureka and fetch-registry to false?

Because the Eureka client machinery is present even on the server (it's built on the same underlying libraries), and without disabling these, the server would attempt to register itself as a client of itself and fetch a registry copy from itself — unnecessary and potentially confusing in a standalone single-server setup.

Is running a single Eureka Server instance appropriate for production, given topic 104 flagged single-points-of-failure as a core problem this whole section is solving?

No — a single Eureka Server instance would itself become exactly the single point of failure this section otherwise avoids by using client-side discovery. Production Eureka deployments run a peer-aware cluster of multiple Eureka Server instances that replicate their registries to each other (each instance both serves clients and registers itself as a "client" of its peers, which is why `register-with-eureka`/`fetch-registry` default to `true` — this course's `false` override is specifically for the simplified single-instance learning setup). Clients are configured with multiple Eureka Server URLs and can reach any available peer, so no single Eureka Server instance being down takes down discovery for the whole system — this is standard, expected production configuration, not an advanced edge case.

Making Code Changes in Accounts Microservice to Connect to Eureka Server

Turning Accounts into a Eureka Client — both a registrant and a discoverer.

pom.xml

    <groupId>org.springframework.cloud</groupId>

  application:

  instance:
    prefer-ip-address: true

      defaultZone: http://localhost:8761/eureka/
spring.application.name

Doubles here as the service ID Accounts registers under in Eureka — every other service discovers this one by exactly this name (uppercased by convention, e.g. `ACCOUNTS`). Getting this consistent across every service is essential, since Feign clients (topic 113) reference this exact name.

eureka.instance.prefer-ip-address

When `true`, the instance registers using its actual IP address rather than its hostname — important in containerized environments where hostnames may not resolve correctly between containers, while IP addresses (on a shared Docker network) reliably do.

eureka.client.service-url.defaultZone

The address of the Eureka Server this client registers with and fetches the registry from. In production with a Eureka cluster, this would be a comma-separated list of every peer's URL for resilience, as discussed in the previous topic's FAANG answer.

No extra annotation typically needed

In modern Spring Cloud versions, simply having `spring-cloud-starter-netflix-eureka-client` on the classpath is enough to auto-configure Accounts as a Eureka client — the older, explicit `@EnableDiscoveryClient` (or `@EnableEurekaClient`) annotation is now optional/implicit in most setups, though you may still see it used explicitly for clarity in some codebases or older Spring Cloud versions.

What name does a service register under in Eureka?

Its `spring.application.name` value — this is the service ID other services use (via Feign or the discovery client directly) to look it up in the registry, so it needs to be consistent and known across the whole system.

Why does prefer-ip-address matter specifically in a Docker/container environment?

Container hostnames may not be reliably resolvable between different containers' network namespaces, whereas IP addresses on a shared Docker network reliably work — registering by IP avoids potential hostname-resolution failures when another service tries to actually call the registered instance.

What happens if two different services accidentally set the same spring.application.name?

Eureka would register both under the same service ID, meaning any client discovering that service ID would receive a mixed pool of instances belonging to two logically different services — a load-balanced call could land on either one unpredictably, almost certainly causing incorrect behavior or errors (mismatched API contracts) at the calling side. This is a genuine production risk worth explicit safeguarding against — e.g. via naming conventions enforced in code review, or automated checks in CI that verify `spring.application.name` uniqueness across a service catalog, since Eureka itself has no built-in mechanism to detect or prevent this collision; it will happily register whatever name it's given.

Making Code Changes in Loans & Cards Microservice to Connect to Eureka Server

The identical treatment, applied to the remaining two services.

Loans and Cards each receive the same three changes as Accounts: add `spring-cloud-starter-netflix-eureka-client`, confirm `spring.application.name` is set correctly (`loans`, `cards`), and point `eureka.client.service-url.defaultZone` at the same Eureka Server. Once all three are running, the Eureka dashboard at http://localhost:8761 shows all three service IDs, each with their currently registered, healthy instances.

This is what makes Feign (topic 113) possible

With all three services registered under consistent, known service IDs, any one of them can now discover and call any other purely by service name — http://LOANS/api/fetch resolves through Eureka to a real instance address, never a hardcoded IP. This is the exact capability the whole section has been building toward.

Once Loans and Cards are also Eureka clients, what can Accounts do that it couldn't before?

Discover Loans and Cards purely by their registered service names, without knowing or hardcoding any specific instance address — enabling dynamic, load-balanced inter-service calls, most conveniently via Feign clients.

Does registering with Eureka alone give Loans and Cards the ability to call each other, or is something else still needed?

Registration and discovery only solve "how do I find a healthy instance's address" — actually making the call still requires an HTTP client (RestTemplate with `@LoadBalanced`, WebClient, or Feign) that integrates with the discovery client to resolve a service name into an actual instance and issue the request. Eureka registration by itself doesn't make any calls happen; it just makes the information needed to make those calls discoverable — which is exactly why the very next topics introduce Feign as the piece that actually issues the calls, built on top of this now-working discovery foundation.

111

De-registration from Eureka Server When Microservices Shutdown

Graceful shutdown vs crash — and why the difference matters for registry accuracy.

Graceful shutdown

When a Spring Boot application shuts down normally (receives SIGTERM, or is stopped via Actuator's shutdown endpoint), its Eureka Client explicitly sends a DEREGISTER call to the Eureka Server as part of the shutdown sequence — immediately removing that instance from the registry. Any client refreshing its local cache after this point will correctly no longer see the shut-down instance as available.

The gap: ungraceful termination

If a process is killed abruptly (kill -9, an out-of-memory kill, a host crash), there's no opportunity for the shutdown hook to run the deregistration call at all — the instance simply stops sending heartbeats, with no explicit notification to the Eureka Server that it's gone. The registry doesn't know immediately; it only finds out indirectly, once the instance's heartbeats stop arriving — which is exactly the subject of the next topic.

Shutdown typeRegistry awarenessWindow of staleness
Graceful (SIGTERM, normal stop)Immediate — explicit DEREGISTER call~None
Ungraceful (kill -9, crash, host failure)Delayed — only detected via missed heartbeatsUp to the heartbeat eviction timeout (default 90s) — covered next
What happens to a service instance's registry entry when it shuts down gracefully?

Its Eureka Client sends an explicit deregistration call to the Eureka Server as part of the shutdown sequence, immediately removing it from the registry.

Why doesn't deregistration happen on an ungraceful crash?

An abrupt kill (kill -9, OOM kill, host crash) gives the process no chance to run its shutdown hooks, including the deregistration call — the Eureka Server only learns the instance is gone indirectly, once it stops receiving that instance's heartbeats.

What's the practical production consequence of the ungraceful-shutdown gap, and how should calling services be designed to tolerate it?

Between an ungraceful crash and the eventual heartbeat-timeout eviction (up to 90 seconds by default), the Eureka registry — and therefore every client's locally cached copy — can still list the dead instance as available, meaning some fraction of load-balanced calls during that window will be routed to an instance that's actually gone and will fail. This is precisely why production services calling other services via Eureka-based discovery must never assume a returned instance is definitely reachable — retry-on-a-different-instance logic (as discussed in topic 106's FAANG answer) is what actually makes this gap tolerable in practice, converting an occasional failed call into an occasional, transparently-retried, slightly-slower successful call rather than a visible failure.

eureka:
  instance:
    lease-renewal-interval-in-seconds: 30
    lease-expiration-duration-in-seconds: 90
PropertyMeaning
lease-renewal-interval-in-secondsHow often the client sends a heartbeat (RENEW call) to the Eureka Server — default 30 seconds
lease-expiration-duration-in-secondsHow long the Eureka Server waits without receiving a heartbeat before considering the instance dead and evicting it from the registry — default 90 seconds

Each heartbeat effectively "renews the lease" an instance holds on its registry entry. If three consecutive heartbeats are missed (90s ÷ 30s), the Eureka Server assumes the instance is no longer alive and removes it — this is exactly the mechanism that eventually closes the staleness window from an ungraceful shutdown, just not instantly.

The direct trade-off in these two numbers

Shortening these intervals (faster heartbeats, shorter expiration) detects failures faster but increases the constant background network/CPU load of heartbeat traffic across potentially hundreds of instances, and increases the risk of false-positive evictions during brief network hiccups. Lengthening them reduces overhead and false positives but widens the staleness window discussed in the previous topic. The defaults (30s/90s) are a deliberately conservative, production-tested balance — and this exact tension is also what motivates the next topic's self-preservation mechanism.

What are the default heartbeat interval and eviction timeout in Eureka?

A heartbeat every 30 seconds (`lease-renewal-interval-in-seconds`), and the server considers an instance dead and evicts it after 90 seconds without a heartbeat (`lease-expiration-duration-in-seconds`) — three missed heartbeats.

What problem does the heartbeat mechanism solve that graceful deregistration doesn't cover?

Detecting instances that disappeared without explicitly deregistering — crashes, kill -9, host failures — where the only signal the Eureka Server has that something is wrong is the absence of expected heartbeats.

Would shortening the heartbeat interval to, say, 5 seconds be a good idea to detect failures faster?

Not without careful consideration — at real scale (hundreds or thousands of instances across many services), a 5-second heartbeat interval multiplies the constant background heartbeat traffic the Eureka Server must process roughly 6x compared to the 30-second default, which can itself become a meaningful load/scaling concern on the registry. It also makes the system more sensitive to brief, non-fatal network blips being misread as instance failure (a single missed heartbeat under a shorter interval represents a much smaller true elapsed time before the server starts suspecting trouble), increasing the risk of unnecessary evictions during transient issues — exactly the "network trap" scenario the next topic's self-preservation mode exists to guard against. In practice, the 30s/90s defaults represent a well-tested balance, and teams needing faster failure detection typically look to complementary mechanisms (client-side circuit breakers reacting to actual call failures in real time) rather than solely tuning heartbeat intervals more aggressively.

Feign Client Code Changes to Invoke Other Microservices

Declarative, interface-based inter-service calls — built directly on top of Eureka discovery and client-side load balancing.

The problem Feign solves

Without Feign, calling Loans from Accounts via discovery still means writing boilerplate: building a `RestTemplate` (annotated `@LoadBalanced` to hook into the discovery-aware load balancer), manually constructing the URL with the service ID, handling serialization, and writing this pattern repeatedly for every inter-service call. OpenFeign (Spring Cloud's integration of Netflix Feign) replaces all of this with a plain Java interface — you declare the shape of the remote API you want to call, and Feign generates a working implementation at runtime that automatically integrates with Eureka discovery and the load balancer.

    @GetMapping(value = "/api/fetch", consumes = "application/json")

Annotation reference

@EnableFeignClients

Placed on the main application class — tells Spring to scan for `@FeignClient`-annotated interfaces and generate proxy implementations for each, registering them as injectable beans.

@FeignClient(name = "loans")

The `name` attribute is the target service's registered Eureka service ID — exactly the `spring.application.name` value Loans registered under back in topic 110. This is the critical link between Feign and Eureka discovery: Feign resolves this name to a real instance address via the discovery client under the hood.

Method signatures

Feign interface methods are annotated with the exact same Spring MVC mapping annotations (`@GetMapping`, `@RequestParam`, `@RequestHeader`) used on the actual controller being called — Feign mirrors the target's real REST contract, so the interface effectively documents "this is what I expect to call, and how."

A real pattern worth noting: correlation ID propagation

The `eazybank-correlation-id` header threaded through both Feign clients is a practical illustration of a production concern flagged back in Section 1's exception-handling notes — propagating a single request-tracing identifier across every hop of a multi-service call chain (Accounts → Loans, Accounts → Cards) so a single customer-facing request can be traced end-to-end in logs across all three services, not just within whichever one happened to log an error.

What is a Feign client, in one sentence?

A plain Java interface, annotated with Spring MVC mapping annotations and `@FeignClient`, for which Spring Cloud OpenFeign generates a working implementation at runtime that calls the named remote service — automatically integrating with Eureka discovery and client-side load balancing.

What does the name attribute in @FeignClient(name = "loans") refer to?

The target service's registered Eureka service ID (its `spring.application.name`) — Feign uses this name to discover and call a real, currently-healthy instance of that service.

What annotation is required on the main application class to enable Feign clients?

`@EnableFeignClients` — it triggers scanning for `@FeignClient`-annotated interfaces and generates their proxy implementations.

In the fetchCustomerDetails method, the two Feign calls (to Loans and Cards) run sequentially — what's the performance implication, and how would you fix it?

Sequential calls mean the total latency for this composite endpoint is roughly the sum of both downstream calls' latencies, when they're actually independent of each other and could run concurrently — the Cards call doesn't need to wait for the Loans call to finish. This is a real, common performance issue in API-composition patterns. Fixes include: wrapping each Feign call in a `CompletableFuture.supplyAsync(...)` and joining both before assembling the response, or — more idiomatically in a reactive stack — using WebClient with reactive composition (`Mono.zip`) instead of blocking Feign calls, letting both downstream calls execute in parallel and reducing the composite endpoint's total latency to roughly the slower of the two calls rather than their sum.

What happens to this composite endpoint if the Loans service is temporarily completely down — not just one bad instance, but the whole service unavailable?

Without any additional resilience configuration, the Feign call to Loans throws an exception (after Eureka-driven retries against different instances are exhausted, if configured, or immediately if no healthy instances are discoverable at all) — and depending on how that exception propagates, the entire composite `fetchCustomerDetails` call likely fails outright, even though the Cards portion might have succeeded fine. This is precisely the motivation for pairing Feign with a circuit breaker and fallback (typically Resilience4j in modern Spring Cloud, configured via `@CircuitBreaker` with a fallback method, or a Feign-specific fallback class) — so a Loans outage degrades this endpoint gracefully (e.g. returning customer + Cards data with a null/placeholder for Loans, rather than a complete 500 error) instead of a single downstream dependency's outage cascading into a hard failure of an otherwise-healthy composite request. This pattern is covered in more depth in dedicated resilience sections, but the seed of "why you need it" is exactly this composite-Feign-call scenario.

Why pass the correlation ID as an explicit method parameter/header rather than relying on some kind of implicit thread-local propagation?

Explicit propagation through method signatures and headers is what actually survives the network boundary — a thread-local value set in Accounts's request-handling thread has no way to automatically appear in Loans's request-handling thread, since they're entirely separate processes/JVMs communicating only via the HTTP request itself. The correlation ID has to be serialized into something that crosses the wire — an HTTP header is the standard mechanism — and explicitly threading it through the Feign interface's method signature (rather than hoping some interceptor magically attaches it) keeps the propagation visible and unambiguous in the code, at the cost of slightly more verbose method signatures. Some teams do automate this via a Feign `RequestInterceptor` that reads a thread-local (populated by an inbound request filter) and attaches it to every outgoing Feign call automatically — trading a bit of implicit "magic" for removing the need to thread the parameter through every single method signature by hand.

Eureka Self-Preservation Mode to Avoid Network Trap Issues

Guarding against mass, false-positive eviction during a network blip — a genuinely important production safety mechanism.

The "network trap" scenario

Imagine a brief network partition or connectivity blip between the Eureka Server and a large fraction of its registered clients — not because those instances actually died, but because of a transient network issue (a router hiccup, a brief DNS problem, a temporary overload). If the Eureka Server naively applies the heartbeat-eviction rule from topic 112 literally, it would see a mass wave of missed heartbeats across many, many instances simultaneously and evict all of them — even though every one of those instances is actually still healthy and serving traffic just fine. This is the "network trap": a transient, non-fatal issue causing the registry to falsely believe most of the system just died.

Network blip
many instances miss heartbeats simultaneously
→
Naive eviction
registry wrongly empties out — mass false-positive

How self-preservation mode prevents this

Eureka Server continuously tracks the ratio of expected heartbeats to actually-received heartbeats across its entire registry. If that ratio drops below a threshold (85% by default) within a rolling window, Eureka concludes it's more likely experiencing a systemic network problem than a genuine mass instance failure, and enters self-preservation mode: it stops evicting instances entirely, preserving the registry in its last-known-good state until heartbeat renewals recover to a healthy ratio.

The core insight

A single instance missing its heartbeats is treated as "that instance probably died" (topic 112's normal eviction logic). But many instances missing heartbeats at the same time is statistically far more likely to be a shared, systemic problem (a network issue, or a problem with the Eureka Server's own connectivity) than every one of those independent instances coincidentally dying simultaneously — self-preservation encodes exactly this statistical reasoning directly into Eureka's eviction logic.

application.yml (dev/testing override only)
eureka:
  server:
    enable-self-preservation: false
    renewal-percent-threshold: 0.85
Disabling this in production is a genuine anti-pattern

enable-self-preservation: false is commonly set during local development/demos specifically because a single-instance, single-Eureka-Server local setup makes eviction timing easy to observe and test without self-preservation's protective delay getting in the way. Leaving it disabled in production removes exactly the safety net that prevents a transient network issue from wrongly emptying out your entire service registry — a real, well-documented cause of production incidents in systems that copy dev-time Eureka config into production without reviewing it. This is a favorite "spot the mistake" interview scenario.

What problem does Eureka's self-preservation mode solve?

It prevents mass, false-positive eviction of healthy instances during a transient network issue — if too many instances miss heartbeats simultaneously, Eureka assumes a systemic network problem rather than genuine mass instance failure, and stops evicting until heartbeat renewals recover.

What's the default renewal threshold that triggers self-preservation mode?

85% — if the ratio of received-to-expected heartbeats across the whole registry drops below this within a rolling window, Eureka enters self-preservation mode and stops evicting instances.

What's the trade-off self-preservation mode accepts, and why is it still the right default?

While in self-preservation mode, Eureka also stops evicting instances that are genuinely dead (not just the ones affected by the network blip) — so the registry can hold onto some truly-dead entries longer than the normal 90-second eviction window would otherwise allow, meaning clients might occasionally route to a dead instance and need to rely on their own retry logic (as discussed in topic 106/111) more than usual during this period. This is an accepted trade-off because the alternative — naive eviction during a network blip — is strictly worse: it would potentially empty out the entire registry of an otherwise fully healthy system, causing every single service-to-service call across the whole platform to fail with "no instances available," a far more severe outage than a temporarily elevated rate of retried calls to a few actually-dead instances. Self-preservation deliberately trades a small amount of registry staleness for avoiding a catastrophic, self-inflicted, false-positive mass outage.

How would you actually detect and respond to a Eureka Server sitting in self-preservation mode in a production monitoring setup?

Eureka Server's own dashboard and Actuator metrics expose whether the server is currently in self-preservation mode (visible via the dashboard UI banner, and programmatically via Eureka's status/info endpoints or exposed metrics), which should be wired into monitoring/alerting — an alert firing when self-preservation activates lets an on-call engineer investigate the underlying network issue causing widespread missed heartbeats, rather than only noticing something's wrong once it manifests as user-facing failures. Response typically involves diagnosing the actual network/connectivity problem (is it isolated to the Eureka Server's own network path, or affecting a broader set of services) rather than trying to "fix" self-preservation mode itself, since it's a symptom being correctly reported, not the underlying problem.

Important Note on GraalVM

A compatibility heads-up worth understanding even briefly — reflection-heavy libraries and native-image compilation don't naturally mix.

What GraalVM native image is, briefly

GraalVM native image ahead-of-time compiles a Spring Boot application into a standalone native executable — no JVM needed at runtime, with dramatically faster startup time and lower memory footprint, which matters a great deal for serverless/fast-autoscaling deployment scenarios. Spring Boot 3+ has first-class support for building native images via `spring-boot-starter-parent`'s native-image plugin support.

Why Eureka specifically is a friction point

GraalVM native-image compilation works by statically analyzing the application's bytecode ahead of time to determine exactly what classes/methods/reflection usage are reachable — anything relying on runtime reflection, dynamic proxies, or dynamic classloading that the static analyzer can't fully see in advance needs to be explicitly declared via reflection configuration hints, or the native image will fail at runtime with a class-not-found-style error that never appears when running normally on the JVM. Netflix Eureka's client libraries (and some other Netflix OSS-era libraries generally) were built well before native-image compilation was a mainstream concern, and rely on exactly this kind of dynamic behavior in ways that aren't automatically native-image-friendly out of the box.

The practical takeaway

If you're planning to compile a Eureka-client-dependent service to a GraalVM native image, expect to need additional reflection configuration (either hand-written `reflect-config.json` hints, or relying on Spring AOT processing plus community-maintained GraalVM reachability metadata for Eureka, where available) — it's not a simple drop-in "just works" situation the way a native-image build of a plain, reflection-light Spring Boot REST service typically is. This is exactly the kind of detail that separates "I've read about GraalVM" from "I've actually tried shipping a Eureka-based service as a native image" in an interview conversation.

What is GraalVM native image, in one sentence?

A GraalVM feature that ahead-of-time compiles a Java application (including Spring Boot apps) into a standalone native executable with no JVM required at runtime, offering much faster startup and lower memory usage.

Why does Eureka client specifically need extra attention for native-image compilation?

Because native-image compilation relies on ahead-of-time static analysis to determine what's reachable, and Eureka's client libraries use runtime reflection/dynamic behavior patterns that predate native-image tooling — this needs to be explicitly declared via reflection configuration for the native image to work correctly, unlike code that avoids reflection and "just works" under native-image compilation automatically.

Why does faster startup time from GraalVM native image matter specifically for a microservices architecture using Eureka-based discovery, beyond generic "faster is better"?

Startup speed directly affects how quickly a newly-scaled instance becomes genuinely useful — from process start, through Spring context initialization, through successful Eureka registration, to actually being discoverable and receiving load-balanced traffic. In an autoscaling scenario reacting to a sudden traffic spike, a JVM-based Spring Boot app might take several seconds to tens of seconds to reach that fully-registered, traffic-ready state, during which the system is still under-provisioned relative to demand; a native-image version reaching the same state in a fraction of the time meaningfully shrinks that under-provisioned window. This is precisely why native image is discussed as particularly valuable for fast-autoscaling and serverless deployment models specifically — the startup-time benefit compounds with exactly the kind of dynamic, elastic infrastructure this whole section's service-discovery mechanics are designed to support.
