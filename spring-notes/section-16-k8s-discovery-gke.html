Kubernetes Service Discovery & Deploying to Google Cloud (GKE)

Eureka solved discovery before Kubernetes; on Kubernetes the platform already registers Pods and load-balances Services. This section replaces client-side discovery with server-side discovery using Kubernetes Services plus the Spring Cloud Kubernetes Discovery Server, updates the microservices and Helm charts, then runs the whole EazyBank platform on a real managed cluster in Google Kubernetes Engine — creation, installation, verification of the Grafana stack, and safe teardown.

How to use this document: every topic has concepts, code and commands, and two interview tabs: Common and FAANG-level. Highest-frequency interview areas: client-side vs server-side discovery (255), how the Discovery Server and RBAC work (256), what changes when removing Eureka (258–260), per-connection load balancing and gRPC caveats (255, 261), managed Kubernetes responsibilities and GKE Autopilot vs Standard (262, 264), and cloud cost hygiene (263, 268). Note: the course’s exact property names and choices (e.g. Feign direct URL vs discovery) should be checked against the videos; this document explains all the options.

So why do we still need something from Spring?

Our code uses Spring Cloud abstractions: the Gateway routes with lb://accounts and Feign clients reference services by name; both rely on a DiscoveryClient bean. Once Eureka is removed, something must implement DiscoveryClient. Spring Cloud Kubernetes provides exactly that: a DiscoveryClient that reads Kubernetes Services/Endpoints. We deploy a small Discovery Server so applications do not each need permission to call the Kubernetes API (topic 256).

Key message

On Kubernetes the platform is the service registry and the load balancer. Eureka becomes an unnecessary second source of truth, so we remove it and keep only what Spring needs to resolve names.

Server-side LB is per connection

kube-proxy balances when a connection is established. HTTP/1.1 clients that reuse keep-alive connections spread load only as connections are created; gRPC/HTTP/2 multiplexes everything on one connection, so a plain ClusterIP Service can send all traffic to one Pod.

What is client-side service discovery?

The calling service obtains the list of available instances from a registry (e.g. Eureka) and selects one itself using a load-balancing algorithm.

What is server-side service discovery and load balancing?

The caller sends requests to a stable address (router/load balancer); infrastructure keeps track of healthy instances and forwards to one. In Kubernetes this is a Service, cluster DNS and kube-proxy.

Why is Eureka unnecessary in Kubernetes?

Kubernetes already registers Pods behind Services when they are Ready, gives each Service a DNS name, and load-balances. Running Eureka duplicates this and adds extra components to operate.

How does a Pod register with a Kubernetes Service?

It does not register itself: the Service’s label selector matches Pods, and the EndpointSlice controller adds Pods once they pass their readiness probe.

Who performs the load balancing in Kubernetes?

kube-proxy (iptables or IPVS rules on every node) or an eBPF dataplane such as Cilium, balancing connections across the Service’s ready endpoints.

What is a DiscoveryClient in Spring Cloud?

An abstraction (org.springframework.cloud.client.discovery.DiscoveryClient) for looking up service instances by name; implementations exist for Eureka, Consul, Kubernetes, etc. Gateway and OpenFeign use it for lb:// resolution.

When would you still prefer client-side load balancing on Kubernetes?

For gRPC/HTTP/2 or other long-lived multiplexed connections (use a headless Service so DNS returns all Pod IPs and balance per request in the client), when you need metadata-aware routing (zone-aware, canary headers) without a mesh, or when the same code must also run outside Kubernetes.

Describe how kube-proxy implements load balancing for a ClusterIP Service.

In iptables mode, rules in the nat table DNAT traffic to the Service’s virtual IP to one of the endpoint Pod IPs chosen randomly, with connection tracking keeping a connection on the same Pod. IPVS mode uses kernel hash tables and supports algorithms like round-robin and least-connections. Newer CNIs (Cilium) replace kube-proxy with eBPF.

How fast does the Service endpoint list reflect a failing Pod compared with Eureka?

Kubernetes removes a Pod from endpoints as soon as readiness fails or deletion starts, and kube-proxy updates rules within a second or two. Eureka depends on heartbeats (default 30 s lease, 90 s expiry) and client cache refresh (30 s), so stale instances can be called for tens of seconds unless tuned. Graceful shutdown and a preStop delay close the remaining gap in both models.

What are the downsides of removing the Spring-level registry?

Loss of portability to non-Kubernetes environments, loss of rich instance metadata used for custom routing, and reliance on Kubernetes DNS/Service semantics (including DNS caching and ndots issues). Mitigate with the Spring Cloud Kubernetes abstractions, a mesh if advanced traffic management is needed, and DNS tuning.

How do headless Services relate to discovery?

A headless Service (clusterIP: None) returns the Pod IPs directly in DNS instead of one virtual IP, letting clients perform their own load balancing or address individual Pods (StatefulSets). It is the Kubernetes-native building block for client-side discovery.

What the Discovery Server is, why it exists, the manifests it needs (ServiceAccount, RBAC, Deployment, Service), and how clients use it.

What is the Spring Cloud Kubernetes Discovery Server?

A ready-made Spring Boot application (published as the container image springcloud/spring-cloud-kubernetes-discoveryserver) that reads Services, Endpoints/EndpointSlices and Pods from the Kubernetes API and exposes them over simple HTTP endpoints. Applications that include the HTTP-based DiscoveryClient starter (spring-cloud-starter-kubernetes-discoveryclient) call it instead of talking to the Kubernetes API.

Why a separate Discovery Server?

  • Security: only one component needs permission to read cluster objects. Otherwise every microservice’s ServiceAccount would require RBAC to the Kubernetes API (get/list/watch services, endpoints, pods).
  • Load: one watcher (with caching) instead of N applications each polling/watching the API server.
  • Simplicity: apps need only an HTTP URL, no Kubernetes client libraries or credentials.
  • Portability of app code: the Spring DiscoveryClient abstraction is retained.

Name alignment rules

The Kubernetes Service name is the service ID. It must equal what callers use in lb://<name> and what the app uses as spring.application.name (the DiscoveryClient also uses it to identify the local instance). Eureka IDs were upper-case; Kubernetes names are lower-case DNS labels. Also, name the Service port http or set primary-port-name so the right port is chosen when a Service exposes several.

Version compatibility

Pin the Discovery Server image to the Spring Cloud Kubernetes version that matches your Spring Cloud release train (e.g. Spring Cloud 2023.x ↔ Spring Cloud Kubernetes 3.1.x). Check the compatibility table in the reference docs.

What is the Spring Cloud Kubernetes Discovery Server?

A Spring Boot application that reads services and endpoints from the Kubernetes API and exposes them via HTTP (/apps, /apps/{name}) for applications using the HTTP-based Kubernetes DiscoveryClient starter.

Why not let each microservice call the Kubernetes API directly?

Each ServiceAccount would need RBAC to read cluster resources, increasing the security surface and API-server load, and apps would need Kubernetes client dependencies. A central Discovery Server concentrates the permission and caching in one place.

Which RBAC objects does the Discovery Server need?

A ServiceAccount, and a (Cluster)RoleBinding to a read-only role such as the built-in view ClusterRole, so it can list/watch services, endpoints and pods.

How do clients know the Discovery Server address?

Through the property spring.cloud.kubernetes.discovery.discovery-server-url, set to the Discovery Server’s Service DNS name, typically injected from the environment ConfigMap.

What is the ClusterRole view?

A default read-only ClusterRole giving get/list/watch on most namespaced resources (excluding Secrets). Bound with a RoleBinding it applies within one namespace; with a ClusterRoleBinding cluster-wide.

Which Kubernetes object name becomes the service id?

The Service’s metadata.name (e.g. accounts), so Gateway routes use lb://accounts.

RoleBinding vs ClusterRoleBinding for the discovery server — what changes?

A RoleBinding referencing a ClusterRole limits permissions to its own namespace; the server then can only discover services in that namespace. To discover across namespaces (all-namespaces=true) bind via ClusterRoleBinding, or create RoleBindings in each target namespace for tighter least-privilege.

How would you make the Discovery Server highly available?

Run ≥2 replicas behind its ClusterIP Service (it is stateless, caching Kubernetes data), add readiness/liveness probes, PodDisruptionBudget and anti-affinity, and ensure clients tolerate transient failures (retry, cache). Also set resource requests/limits.

What happens to callers if the Discovery Server is down?

New lookups fail; callers may serve from the DiscoveryClient’s cache for a while (configurable cache), but instances changing during the outage are not visible. This is a new dependency compared with pure Service DNS, which is why some teams skip it and use plain Service URLs.

Why does the Kubernetes DiscoveryClient return Pod IPs, and is that still server-side LB?

The Discovery Server returns endpoint (Pod) addresses, then Spring Cloud LoadBalancer picks one: this is effectively client-side load balancing with Kubernetes as the registry. To keep true server-side balancing use the Service URL (http://accounts:8080) or the Kubernetes LoadBalancer mode=SERVICE option which resolves to the Service address instead of Pod IPs.

How do you restrict which services are discoverable?

Configure namespaces (spring.cloud.kubernetes.discovery.namespaces), use label/SpEL filters (spring.cloud.kubernetes.discovery.filter), and limit RBAC to the namespaces concerned.

Sanity check mindset

Always test in layers: (1) Service and Pods Ready, (2) discovery server responds with the Service, (3) microservice resolves it, (4) end-to-end through the Gateway.

Don’t expose it publicly

The discovery endpoints reveal your internal topology. Keep it ClusterIP; use NetworkPolicy to allow only app namespaces to call it.

How do you verify the Discovery Server is working?

Port-forward its Service and call /apps and /apps/<service>; check Pod logs and /actuator/health.

How do you test whether its ServiceAccount has permissions?

kubectl auth can-i list services --as=system:serviceaccount:<ns>:<sa-name> (and endpoints, pods).

Why does /apps not list a Pod that is running?

The Pod is not Ready (readiness probe failing), or its Service selector doesn’t match, or it is in a namespace not covered by the server’s configuration.

What port does the Discovery Server listen on, and how is it exposed?

Port 8761 inside the container; typically exposed by a ClusterIP Service on port 80 targeting 8761.

Why use a ClusterIP Service for it?

Only in-cluster apps need it; exposing it externally would leak internal topology.

How would you secure access to the Discovery Server further?

NetworkPolicy allowing only application Pods, mTLS via a service mesh, no public exposure, least-privilege RBAC (namespace-scoped Role listing only services/endpoints/pods), and run it with a restricted securityContext (non-root, read-only filesystem).

How would you monitor the Discovery Server in production?

Expose Actuator/Micrometer metrics to Prometheus (request latency, errors, cache hit), alert on Pod availability and error rates, and log API-server errors; dashboard in Grafana.

What are the failure modes of depending on it and how do you reduce risk?

Single dependency for name resolution: use replicas + PDB, enable DiscoveryClient caching in clients, retries/timeouts, and consider bypassing it by calling Service DNS names for critical paths.

Which Feign option, and why?

  • Option 2 (explicit URL) embraces server-side load balancing: the Feign client calls http://loans:8090, DNS resolves to the Service ClusterIP, and kube-proxy balances. No DiscoveryClient involvement, one less moving part. (The course demonstrates making the calls go through Kubernetes Services; follow the video for the exact choice.)
  • Option 1 keeps Spring Cloud LoadBalancer picking among Pod IPs returned by the DiscoveryClient: more flexible (custom LB, metadata) but it is client-side LB again.
  • The Gateway’s lb:// scheme requires a DiscoveryClient, which is why the Discovery Server remains for the Gateway.
Upper vs lower case

Eureka registered services in upper case by default (ACCOUNTS). Kubernetes Service names must be lower-case DNS labels (accounts). Every lb:// URI, Feign name and circuit-breaker or config key tied to the old names must be updated, or the Gateway returns 503 “Unable to find instance”.

Local development

With the Kubernetes DiscoveryClient on the classpath, running a service locally (outside the cluster) fails to resolve services. Use Spring profiles (default keeps Eureka/direct URLs, k8s enables Kubernetes discovery) or spring.cloud.kubernetes.discovery.enabled=false locally.

What changes in pom.xml when moving from Eureka to Kubernetes discovery?

Remove spring-cloud-starter-netflix-eureka-client and add spring-cloud-starter-kubernetes-discoveryclient.

Which properties are removed and added?

Remove the eureka.* client/instance settings; add spring.cloud.kubernetes.discovery.discovery-server-url pointing to the Discovery Server Service.

What must spring.application.name match?

The Kubernetes Service name for that microservice, because Kubernetes discovery uses the Service name as the service ID.

How do Gateway routes change?

lb://ACCOUNTS becomes lb://accounts — the lower-case Kubernetes Service name.

How can a Feign client use server-side load balancing?

Specify the Service URL: @FeignClient(name="loans", url="http://loans:8090"), so DNS and kube-proxy do the routing.

Do you need @EnableDiscoveryClient?

No, in modern Spring Cloud the DiscoveryClient auto-configures when the starter is present.

Why does Gateway need discovery but Feign does not necessarily?

Gateway’s lb:// URIs are resolved by the Reactive LoadBalancer using a DiscoveryClient. Feign with an explicit url bypasses load balancer lookup entirely and relies on DNS.

Walk through how lb://accounts is resolved at runtime with the Kubernetes DiscoveryClient.

Gateway’s ReactiveLoadBalancerClientFilter asks Spring Cloud LoadBalancer for an instance of service accounts. The load balancer’s ServiceInstanceListSupplier uses the DiscoveryClient (HTTP, calling /apps/accounts on the Discovery Server), caches the list, picks an instance (round-robin) and rewrites the URI to the Pod IP:port.

Is replacing Eureka with the Kubernetes DiscoveryClient truly “server-side discovery”?

Partially: registration is server-side (Kubernetes), but if the app’s LoadBalancer chooses among returned Pod IPs the balancing is still client-side. Pure server-side requires calling the Service name/ClusterIP. Spring Cloud Kubernetes’ LoadBalancer mode=SERVICE returns the Service address, giving kube-proxy the balancing role.

How do you keep one codebase working locally and in Kubernetes?

Profile-specific configuration: local profile disables Kubernetes discovery and points routes/Feign URLs at localhost or uses a local registry; k8s profile enables discovery and injects the Discovery Server URL via ConfigMap. Use @ConditionalOnProperty or spring.cloud.kubernetes.enabled.

Why bump the image tag (s15 → s16)?

  • Kubernetes nodes cache images; with IfNotPresent and an unchanged tag they would reuse the old image and your change would not deploy.

Which parts of the microservices must be updated after moving to Kubernetes discovery?

Dependencies (Eureka → Kubernetes DiscoveryClient), configuration (remove eureka.*, add discovery-server-url), Gateway route URIs, Feign client setup, and the Config Server’s shared properties.

Why change the Docker image tag after code changes?

To force Kubernetes to pull and roll out the new image and to keep deployments immutable and rollback-able.

What happens to the Eureka Server in the new architecture?

It is removed: no Deployment, Service or Helm dependency remains because Kubernetes tracks instances itself.

Where are Eureka properties typically stored in this project?

In the Config Server’s Git repository (shared application*.yml files) and as environment variables in the Kubernetes ConfigMap; both must be cleaned.

How do you build container images for Spring Boot without a Dockerfile?

Jib (mvn jib:dockerBuild) or Cloud Native Buildpacks (mvn spring-boot:build-image), then push to a registry.

How would you perform this migration with zero downtime in a live system?

Run both mechanisms in parallel: first deploy services supporting both (Eureka still registered while Kubernetes discovery and Service URLs are added), switch the Gateway and Feign clients behind a feature flag/profile, verify with canary traffic, then remove Eureka registration and finally the Eureka server. Use backward-compatible config and staged rollouts with automated rollback.

How do you avoid image-tag drift between environments?

One CI-produced immutable tag (or digest) per commit promoted unchanged through dev → qa → prod; environment values only change the tag reference; use digests (image@sha256:…) for strict immutability; admission policy blocking latest.

What testing would you add to catch discovery misconfiguration before production?

Contract tests for Gateway routes, a smoke-test Job (helm test) that calls each route through the Gateway after deploy, integration tests in kind/Testcontainers-K3s with the Discovery Server, and synthetic monitoring after release.

Version the common/library chart with a major bump and changelog, keep a deprecation window supporting both modes via a values toggle (discovery.mode: eureka|kubernetes), test every consumer chart in CI via helm template + kubeconform, and roll out environment by environment with automated smoke tests.

If load looks uneven

Compare to Eureka

How do you demonstrate load balancing in Kubernetes?

Scale a Deployment to several replicas and send repeated requests through the Service/Gateway; observe responses or logs coming from different Pods and check kubectl get endpoints.

How do you see which Pod handled a request?

Include the Pod name/hostname in a response header or log line, or use kubectl logs -l app=accounts --prefix.

What happens to discovery when a Pod is deleted?

The Pod is removed from the Service’s endpoints, the Discovery Server stops returning it, and the ReplicaSet creates a replacement that is added after it becomes Ready.

What does a 503 “Unable to find instance” from Gateway mean?

The load balancer found no instances for that service ID: wrong name, Pods not Ready, Discovery Server cannot see the namespace, or discovery URL misconfigured.

How do you test self-healing together with discovery?

Delete a Pod while generating continuous traffic and watch error rate, endpoints and the replacement Pod’s readiness.

How would you measure the failure window during a Pod termination?

Run a constant-rate load test (k6/hey/wrk) through the Gateway while deleting Pods or doing a rollout; compute error count and latency spikes; compare with and without preStop sleep, graceful shutdown and readiness-probe tuning.

Why might you still see a few failed requests when a Pod terminates despite endpoints updating?

Endpoint removal propagates asynchronously to every node’s kube-proxy and every client cache; the Pod may receive SIGTERM before all clients stop sending. Add a preStop sleep (5–10 s), enable graceful shutdown in Spring, set a sufficient termination grace period, and keep retries on idempotent calls.

How would you tune Spring Cloud LoadBalancer for this setup?

Configure the instance-list cache TTL, use health-check-based suppliers (spring.cloud.loadbalancer.configurations=health-check), zone preference, retries with backoff for idempotent requests and sensible connect/read timeouts, aligned with Resilience4j policies.

What is managed Kubernetes?

A cloud service where the provider operates the Kubernetes control plane (API server, etcd, scheduler, controllers) and often helps manage worker nodes, upgrades and integrations.

Name the managed Kubernetes services of the big three clouds.

Amazon EKS, Azure AKS and Google GKE.

What is the difference between GKE Standard and Autopilot?

Standard: you manage node pools (machine types, scaling) and pay for nodes. Autopilot: Google manages nodes; you define Pods with resource requests and pay per Pod resources, with security/restriction guardrails.

What do you still manage on a managed cluster?

Your workloads, configuration, RBAC and network policies, observability, secrets, scaling settings, cost and application data/backup.

Why do cloud providers integrate LoadBalancer Services?

The cloud-controller-manager creates a cloud load balancer and external IP for Services of type LoadBalancer automatically, which is what makes the Gateway reachable from the internet.

How do you avoid cloud lock-in when using managed Kubernetes?

Use standard Kubernetes APIs, Helm/Kustomize, open observability (Prometheus/OpenTelemetry), external-secrets abstractions, S3-compatible or CSI storage, and keep provider-specific features (IAM bindings, load-balancer annotations) behind values/overlays. Accept that managed databases and identity are the hardest to move.

Compare cost drivers for EKS, AKS and GKE for a small microservice platform.

Compute (nodes or Pod resources) dominates; then load balancers (each LoadBalancer Service costs), persistent disks, NAT/egress traffic, logging/monitoring ingestion, and control-plane fees (varies by provider/tier). Cost control: right-sizing requests, autoscaling, spot nodes, one Ingress/Gateway instead of many LBs, log retention policies, and cleaning unused disks/IPs.

When would you pick Autopilot-style serverless nodes vs managed node pools?

Autopilot/Fargate when you want minimal node operations and workloads fit restrictions with variable load; node pools when you need privileged DaemonSets, specific machine types/GPUs, node-level tuning, or the best price/performance at steady high utilisation.

How do multi-cluster/multi-cloud strategies work with managed Kubernetes?

Standardise delivery with GitOps (Argo CD ApplicationSets/Flux) across clusters, use global load balancing/DNS for traffic steering, replicate data with cloud-agnostic or managed multi-region databases, and standardise observability and policy (OPA/Kyverno). Complexity and cost are high; justify by resilience, regulatory or latency requirements.

Things that need updating for the cloud

Frequent GKE install problems

Pending Pods (insufficient CPU/memory → add nodes or lower requests); Autopilot rejecting privileged/hostPath workloads; PVC stuck Pending (wrong StorageClass/zone); EXTERNAL-IP <pending> (quota/firewall/API issue); image pull errors from Bitnami (topic 237); long --wait timeouts because JVM apps start slowly (raise timeout, tune probes).

Reproducibility win

Because everything is Helm + values files in Git, standing up this whole platform on a new cluster is a script, not a weekend. That is the payoff of Sections 14–15.

How do you deploy the application to GKE?

Connect kubectl with get-credentials, install the supporting components with Helm, then helm install eazybank prod-env. The same charts used locally work, with values adapted for the environment.

How do you get the public address of the Gateway on GKE?

Set the Gateway Service type to LoadBalancer; GKE provisions a load balancer and kubectl get svc gatewayserver shows the EXTERNAL-IP once ready.

What changes for persistent storage in the cloud?

PVCs are fulfilled by cloud persistent disks via the CSI driver and default StorageClass, which are billed and tied to a zone.

Why might Pods stay Pending on a new cluster?

Not enough CPU/memory on the nodes (or Autopilot scaling still provisioning), unsatisfied node selectors/taints, or unbound PVCs.

Why set resource requests in cloud deployments?

They drive scheduling and autoscaling, and on Autopilot they determine what you are billed.

How would you expose the platform securely instead of a raw LoadBalancer IP?

Reserve a static IP, use a GKE Ingress/Gateway API controller with a Google-managed certificate and Cloud DNS hostname, enable Cloud Armor (WAF/rate limiting), keep backend Services ClusterIP, and enforce NetworkPolicies and authentication at the Gateway.

How do you handle stateful components (Kafka, Keycloak DB) on GKE reliably?

Prefer managed services (Cloud SQL, Confluent/Managed Kafka) for production, or operators (Strimzi, CloudNativePG) with regional persistent disks, anti-affinity across zones, backups/snapshots, PDBs and tested restore procedures. A single-replica Helm install with a zonal disk is a lab pattern only.

How would you automate this installation across environments?

GitOps with Argo CD/Flux (app-of-apps/ApplicationSet), Terraform for cluster and cloud resources, Helm charts for apps, environment values in Git, secrets via External Secrets/Secret Manager, and CI checks (lint, template, policy) before promotion.

How do GKE Workload Identity and Secret Manager improve on the lab setup?

Workload Identity binds a Kubernetes ServiceAccount to a Google service account so Pods access Google APIs without key files; the Secret Manager CSI driver/External Secrets sync secrets into Pods, removing plaintext passwords from values and ConfigMaps.

Cloud Logging’s Logs Explorer (GKE ships container logs by default), or kubectl logs.

What does the Gateway LoadBalancer create in Google Cloud?

A forwarding rule/load balancer (network or application depending on configuration) with an external IP routing traffic to node ports/NEGs and then Pods.

Why shouldn’t you use plain HTTP in the cloud for the secured APIs?

Bearer tokens and credentials can be intercepted; terminate TLS at an Ingress/Gateway with a certificate.

Explain the traffic path from a client to a Pod on GKE.

DNS/IP → Google Cloud load balancer (external IP) → node (via NodePort or container-native load balancing with NEGs directly to Pod IPs) → kube-proxy/dataplane → Pod (Gateway) → Gateway uses DiscoveryClient/Service to reach Accounts Pod → returns. With container-native LB the node hop is skipped for better latency and even distribution.

How would you do a canary release for the Gateway on GKE?

Deploy a second Deployment/ReplicaSet (or Argo Rollouts) with the new version and use weighted traffic routing via Gateway API/Ingress (or a service mesh), monitor error/latency SLOs in Prometheus/Grafana, and automatically promote or abort.

How would you ensure the demo environment can’t surprise you with cost?

Budget alerts and quotas, a dedicated project, labels, auto-shutdown/cleanup scripts, small node pools or Autopilot with tight requests, avoiding multiple LoadBalancers, and a documented teardown (topic 268).

Why the order matters

  • LoadBalancer Services first: GKE removes the cloud load balancer when the Service is deleted. Deleting only the cluster usually cleans these, but explicit removal avoids orphaned forwarding rules and IPs.
  • PVCs/PVs: with a Delete reclaim policy disks go with the PVC; with Retain (or manually created disks) they remain and keep billing.
  • Reserved static IPs bill while unattached.
  • Cluster deletion takes a few minutes; confirm with gcloud container clusters list.

How do you delete a GKE cluster?

gcloud container clusters delete <name> --zone <zone> (or --region), after removing workloads/LoadBalancers/PVCs you don’t want to leave behind.

Why delete LoadBalancer Services before the cluster?

To ensure the associated Google Cloud load balancer, forwarding rules and IPs are released cleanly and aren’t left billing.

What resources can remain billing after cluster deletion?

Persistent Disks, reserved static IPs, load balancer forwarding rules, container/Artifact Registry images, snapshots, Cloud NAT and logging storage.

kubectl config delete-context <ctx> (and optionally delete-cluster/unset users.<name>), then switch to another context.

What is the safest way to avoid surprise costs in a learning project?

Use a separate project with budget alerts, delete the whole project when finished (it removes all resources), and verify billing reports.

How would you automate ephemeral cluster environments (create → test → destroy) in CI?

Use Terraform (or Config Connector/Crossplane) to create the cluster and networking, deploy via Helm/GitOps, run integration/e2e tests, always destroy in a finally/post step, tag resources with the run ID, and run a nightly janitor that deletes anything older than N hours.

What are PV reclaim policies and why do they matter at teardown?

Delete removes the cloud disk when the PVC is deleted; Retain keeps the disk (and its data/cost) for manual recovery. Dynamically provisioned classes default to Delete (GKE standard classes), but a class or PV set to Retain will leave billable disks behind.

How do you protect production clusters from accidental deletion?

Enable deletion protection on the cluster (where available), restrict IAM (separate admin roles, no broad Owner), use organisation policies, require approvals in Terraform pipelines, Infrastructure-as-Code with state locking, and backups (Velero/Backup for GKE) with tested restores.

Answer template

Decision → reason → trade-off → example. “We removed Eureka because Kubernetes already registers Ready Pods behind Services; we kept the Spring DiscoveryClient abstraction via the Discovery Server so Gateway’s lb:// routes still work; trade-off: a new component, and client-side balancing over Pod IPs unless we call Service URLs.”

Why remove Eureka when moving to Kubernetes?

Kubernetes provides registration, DNS-based discovery and load balancing natively, so Eureka duplicates functionality and adds operations overhead.

What is the first thing to check if the Gateway cannot route to a service?

The Discovery Server’s /apps/<name> output: is the service listed with Ready instances under the exact name used in the route?

What must you do at the end of a cloud lab?

Uninstall releases, delete PVCs and the cluster, then audit disks, IPs and load balancers so nothing keeps billing.

Defend your choice between Spring Cloud Kubernetes Discovery, plain Service URLs and a service mesh.

Plain Service URLs are simplest and fully server-side but lose Spring’s lb:// abstraction and metadata-aware routing. The Discovery Server preserves the abstraction with minimal code changes but adds a component and client-side balancing. A mesh provides discovery, mTLS, retries and traffic shifting transparently for any language but adds operational complexity and resource overhead. Choose by team skills, language mix, and traffic-management needs.
