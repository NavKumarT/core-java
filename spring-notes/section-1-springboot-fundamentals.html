How to Build Microservices

Conceptual foundation before touching code — what a microservice is, why it exists, and how the 3-service demo (Accounts / Loans / Cards) is structured.

A microservice is a small, independently deployable service that owns a single, well-defined business capability, along with its own data store, and communicates with other services over the network (typically REST/HTTP or messaging). This is the opposite of a monolith, where all capabilities (accounts, loans, cards, notifications…) live in one deployable unit sharing one database.

Why split eazybank into Accounts / Loans / Cards?

  • Independent deployability — a bug fix in the Cards service can ship without redeploying Accounts or Loans.
  • Independent scalability — if Loans gets 10x traffic during a promotional campaign, only that service needs to scale out.
  • Team autonomy — different squads can own different services, choose release cadence independently (Conway's Law in action).
  • Fault isolation — if the Cards service crashes, Accounts and Loans can, in principle, keep serving requests (bulkheading), unlike a monolith where one bad module can bring the whole JVM down.
  • Technology heterogeneity — each service could theoretically use a different language/DB, though in this demo all three use Spring Boot + H2 for consistency.

Where we are

What is a microservice, in one sentence?

An independently deployable service that owns a single business capability and its own data, exposed via a network API (usually REST).

What's the main difference between a monolith and microservices?

A monolith is one deployable unit with all modules sharing a process and typically a database; microservices split those modules into separately deployable, independently scalable units, each with its own datastore, communicating over the network.

Why does each microservice get its own database instead of sharing one?

Sharing a database re-creates tight coupling at the data layer — any schema change risks breaking other services, and it removes the ability to scale or choose storage technology independently. "Database per service" keeps each service's internal data model private, accessible to others only via its API.

If each service has its own DB, how do you handle a transaction that spans Accounts and Loans (e.g. "close account and settle any linked loan")?

You give up traditional ACID distributed transactions and instead reach for the Saga pattern — a sequence of local transactions, each publishing an event/command that triggers the next step, with compensating transactions to undo prior steps on failure (choreography via events, or orchestration via a coordinator service). This trades strong consistency for eventual consistency, which is an explicit, discussable trade-off interviewers want you to articulate, not just name-drop.

How would you decide service boundaries — why is it Accounts/Loans/Cards and not, say, Customer/Transaction?

Boundaries should follow Domain-Driven Design bounded contexts — group by business capability and data ownership, not by technical layer. The test: can this capability change, scale, and fail independently, and does it have a cohesive internal data model that rarely needs to join with another service's data in a single query? Splitting by technical layer (e.g. a "database service" or "validation service") is a classic anti-pattern that just re-creates a distributed monolith with worse latency.

What's the cost of choosing microservices too early, before the domain is well understood?

Premature decomposition freezes boundaries before you understand real coupling, so you end up with chatty inter-service calls, distributed transactions for things that should have been one transaction, and much higher operational overhead (N deployments, N sets of logs/metrics, network failure modes) for a system that didn't need the scaling or team-autonomy benefits yet. Many teams deliberately start with a "modular monolith" and extract services once boundaries and load patterns are proven.

Introduction to Spring Boot Framework

What problem Spring Boot solves on top of the Spring Framework, and the mechanics of auto-configuration & starters.

Spring Framework's problem

The core Spring Framework (IoC container, DI, Spring MVC, Spring Data, Spring Security…) is powerful but historically required heavy manual configuration — XML bean definitions or verbose @Configuration classes, manually wiring a DispatcherServlet, choosing and configuring an embedded server, aligning dozens of library versions by hand. This is exactly what Spring Boot was built to remove.

What Spring Boot adds

Auto-configurationSpring Boot inspects the classpath and beans already defined, and auto-registers sensible default beans (e.g. seeing H2 + spring-boot-starter-data-jpa on the classpath auto-configures a DataSource, EntityManagerFactory, TransactionManager)
Starter dependenciesCurated dependency bundles (e.g. spring-boot-starter-web) that pull in a compatible, version-aligned set of libraries so you never hand-pick versions
Embedded serversTomcat (default), Jetty, or Undertow bundled inside the JAR — no external app server install/deploy step; you run java -jar app.jar

No code generation, no XMLEverything is Java config + annotations; "convention over configuration"

How auto-configuration actually works (mechanics)

The entry point annotation @SpringBootApplication is itself a meta-annotation combining three:

MainApplication.java
@SpringBootApplication
public class AccountsApplication {
    public static void main(String[] args) {
        SpringApplication.run(AccountsApplication.class, args);
    }
}
@SpringBootConfigurationmeta

A specialization of @Configuration — marks this class as a source of bean definitions. Lets Spring Boot treat the main class itself as a config class.

@EnableAutoConfigurationmeta

The real engine. Triggers Spring Boot to scan META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (older versions: spring.factories) inside every JAR on the classpath, and conditionally register the beans found there using @Conditional* annotations (@ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty, etc.), so a bean is only auto-created if its supporting library is present and you haven't already defined your own bean of that type.

@ComponentScanmeta

Scans the package of the annotated class and all sub-packages for @Component-stereotyped classes (@Service, @Repository, @Controller/@RestController) and registers them as beans. This is why the main class conventionally lives in the root package.

Practical implication

If you define your own DataSource bean, Spring Boot's @ConditionalOnMissingBean-guarded auto-configuration for DataSource silently backs off. This "auto-config only fills the gaps you leave" behavior is the single most important mental model for debugging "why isn't my custom bean being used" issues.

What is Spring Boot and how is it different from the Spring Framework?

Spring Framework provides the core IoC container, DI, and modules (MVC, Data, Security…) but requires manual configuration to wire them together. Spring Boot sits on top of it and auto-configures those modules based on the classpath, ships curated "starter" dependencies, embeds a server, and removes boilerplate — so you get a runnable, production-ready app with minimal setup.

What does @SpringBootApplication do?

It's a convenience meta-annotation bundling @SpringBootConfiguration (marks the class as a config/bean source), @EnableAutoConfiguration (turns on classpath-driven auto-configuration), and @ComponentScan (scans the current package and sub-packages for Spring-managed components).

What is a Spring Boot "starter"?

A starter is a single dependency (e.g. spring-boot-starter-web) that transitively pulls in a version-aligned set of libraries needed for a capability, so you don't manually resolve compatible versions of, say, Spring MVC, Jackson, and an embedded Tomcat.

Walk me through what happens, step by step, from `SpringApplication.run()` to the app being ready to serve traffic.

Roughly: (1) Spring Boot creates an ApplicationContext of the appropriate type (e.g. AnnotationConfigServletWebServerApplicationContext for a servlet web app), (2) it loads ApplicationContextInitializers and fires ApplicationListeners for lifecycle events (ApplicationStartingEvent, ApplicationEnvironmentPreparedEvent...), (3) the Environment is prepared — property sources from application.yml, env vars, command-line args are merged with precedence rules, (4) @ComponentScan registers your beans and @EnableAutoConfiguration registers conditional auto-config beans, (5) the BeanFactory instantiates and wires singleton beans (respecting dependency order, @PostConstruct callbacks), (6) the embedded servlet container (Tomcat) is created and started as part of context refresh, and finally (7) ApplicationReadyEvent fires and the app accepts requests.

How does @ConditionalOnMissingBean actually let you override an auto-configured bean, and what ordering guarantee makes that safe?

Auto-configuration classes are processed after user-defined @Configuration classes because Spring Boot places auto-configuration at the end of the configuration-processing order (historically via @AutoConfigureAfter/ordering metadata, and by deferring their import through DeferredImportSelector). By the time an auto-configuration class's @ConditionalOnMissingBean check runs, your own bean definitions are already registered in the BeanFactory, so the condition correctly evaluates to "bean already present" and the auto-configured default backs off.

Why does Spring Boot favor "convention over configuration" via conditional auto-config rather than dependency-injecting a fixed set of defaults?

Because the same jar (spring-boot-autoconfigure) has to support radically different classpaths — an app with only spring-boot-starter-web shouldn't get a DataSource bean, but one that also has spring-boot-starter-data-jpa and an H2 driver should. Conditional annotations let a single autoconfiguration jar declaratively describe "under what classpath/property/bean conditions should this bean exist," which scales to hundreds of optional integrations without runtime reflection hacks or every user writing their own config.

Introduction to REST APIs & Best Practices

REST constraints, HTTP method semantics, status codes, and API design conventions used throughout the CRUD sections.

What REST actually means

REST (Representational State Transfer) is an architectural style (not a protocol) defined by a set of constraints: client-server separation, statelessness (every request contains all info needed; server holds no client session state), cacheability, a uniform interface (resources identified by URIs, manipulated through representations like JSON, self-descriptive messages via HTTP verbs/status codes), a layered system, and optionally HATEOAS (responses include links to related actions/resources).

HTTP method → operation mapping

Idempotent vs Safe

Safe = does not change server state (GET, HEAD, OPTIONS). Idempotent = calling it N times has the same effect as calling it once (GET, PUT, DELETE — but not POST, and not PATCH in general). Every safe method is idempotent, but not every idempotent method is safe (PUT changes state but repeating it doesn't change the outcome further).

REST API design best practices used in this project

  • Nouns, not verbs, in URIs: /api/create is wrong; POST /api/accounts is right — the verb is carried by the HTTP method.
  • Plural resource names: /api/accounts, not /api/account.
  • Version the API: prefix with /api/v1/... so breaking changes can ship as /api/v2/... without breaking existing clients.
  • Use query params for filtering, not new endpoints: GET /api/accounts?mobileNumber=... rather than a bespoke path.
  • Return correct status codes, not always 200 — 201 for create, 400 for validation errors, 404 for not-found, 500 for unhandled server errors (this is what section 23's global exception handler enforces).
  • Never leak internal entities directly — use DTOs (section 16) so your DB schema and your API contract can evolve independently.
  • Stateless requests — no server-side session; auth (later, Spring Security section) is via a token on every request.
What does REST stand for and what makes an API "RESTful"?

Representational State Transfer. An API is RESTful when it follows constraints like statelessness, a uniform resource-based interface (URIs identify resources, HTTP verbs act on them), client-server separation, and cacheable responses.

Difference between PUT and PATCH?

PUT replaces the entire resource with the payload provided (full update, idempotent); PATCH applies a partial modification to specific fields only.

Why use 201 instead of 200 for a successful POST?

201 Created explicitly communicates that a new resource was created as a result of the request, which is more precise than the generic 200 OK and lets clients (and monitoring/logging) distinguish "created" from "read/updated successfully."

Is REST actually stateless if you use JWT-based authentication — doesn't the token represent state?

Statelessness in REST specifically means the server doesn't persist client session context between requests — every request must be self-contained. A JWT is fine because it's carried by the client on every call and the server can validate/derive identity from it without server-side session storage. It would violate statelessness only if the server kept a session store keyed by a token that the client didn't have to keep resending.

Why is PUT required to be idempotent by spec, and what breaks if your implementation doesn't honor that?

Idempotency lets intermediaries (proxies, clients doing automatic retries after a timeout) safely resend a PUT without asking "did the first one actually apply?" If a PUT handler, say, appended to a list instead of replacing it, a network retry after a lost response would silently duplicate data — the client can't tell the difference between "my first request never arrived" and "it arrived but the response was lost," so idempotency is what makes retry-based fault tolerance safe at the HTTP layer.

How would you evolve a public REST API without breaking existing consumers — compare URI versioning vs header versioning vs no versioning with additive changes only?

URI versioning (/v1/, /v2/) is simple and cache-friendly but forces whole-resource duplication for even small breaking changes and pollutes URIs (arguably violating "URI identifies a resource, not a version of an API"). Header/content-negotiation versioning (Accept: application/vnd.myapp.v2+json) keeps URIs clean and resource-identity stable, but is harder to test/debug and less cache-friendly. Additive-only evolution (only ever add optional fields, never remove/rename) avoids versioning entirely but constrains you long-term and doesn't help with genuinely breaking business-logic changes. Most FAANG-scale public APIs pick URI versioning for its operational simplicity, and layer deprecation policies and contract tests on top rather than trying to avoid versioning altogether.

What is Spring Initializr?

A web tool (start.spring.io) and IDE-integrated wizard that scaffolds a Spring Boot project — letting you pick build tool, Spring Boot version, and starter dependencies — and generates a ready-to-run skeleton project with a correctly configured pom.xml/build.gradle.

What does spring-boot-starter-parent give you in the pom.xml?

Centralized, version-compatible dependency management for the whole Spring Boot ecosystem plus default plugin configuration, so individual dependencies don't need explicit version tags.

What if your company's Maven multi-module project already has its own parent POM — how do you still get Spring Boot's version management?

You can't have two <parent> tags, so instead of inheriting from spring-boot-starter-parent, you import spring-boot-dependencies as a BOM inside <dependencyManagement> with <scope>import</scope>. This gives you the same curated version alignment without taking over the parent slot, letting your org's own parent POM remain in control of plugin/build conventions.

Why does Spring Boot produce an executable "fat/uber jar" instead of a thin jar plus a classpath file?

A fat jar bundles the application classes and all dependency jars (nested) into a single artifact with a custom Launcher class (JarLauncher) that knows how to load nested jars via a custom classloader — because the standard JVM classloader can't load classes from jars-within-a-jar directly. This trades a larger artifact size for massively simpler deployment: one file, java -jar app.jar, no separate dependency-resolution step needed at runtime, which matters a lot for container images and CI/CD pipelines.

Hello World REST API using @RestController

First controller, request mapping annotations, and how Spring resolves a request to a method.

SayHelloController.java
@RestController
public class SayHelloController {

    @RequestMapping(value = "/say-hello", method = RequestMethod.GET)
    public String sayHello() {
        return "Hello World";
    }
}
@RestController

Meta-annotation = @Controller + @ResponseBody. @Controller registers the class as a Spring MVC handler (bean, eligible for request mapping); @ResponseBody tells Spring to serialize the method's return value directly into the HTTP response body (via Jackson to JSON) instead of resolving it as a view name.

@RequestMapping

Maps HTTP requests to handler methods/classes. Can specify value (path), method (HTTP verb), consumes/produces (content types). Verbose form — usually replaced by the shorthand verb-specific annotations below.

value = path
method = HTTP verb
produces = response content-type

What's the difference between @Controller and @RestController?

@Controller methods, by default, return a view name to be resolved by a view resolver (server-side rendering). @RestController = @Controller + @ResponseBody, so every method's return value is written directly to the HTTP response body, typically as JSON — used for building REST APIs.

What does @ResponseBody actually do?

It tells Spring MVC to skip view resolution and instead pass the method's return value to an HttpMessageConverter (Jackson's converter, in most Spring Boot apps) which serializes it — typically to JSON — and writes it straight into the response body.

How does Spring MVC route an incoming HTTP request to the correct @RestController method internally?

The embedded Tomcat forwards the request to Spring's front controller, DispatcherServlet. It consults a HandlerMapping (specifically RequestMappingHandlerMapping) which, at startup, built a registry of URL-pattern-to-method mappings by scanning all @RequestMapping-derived annotations. The matched method is wrapped as a HandlerMethod and invoked through a HandlerAdapter, which resolves method arguments (via HandlerMethodArgumentResolvers for things like @PathVariable, @RequestBody) and passes the return value to an appropriate HttpMessageConverter for serialization.

If two controller methods could match the same URL, how does Spring decide which one wins?

Spring uses a specificity-based comparator (PatternComparator / RequestMappingInfo comparison) — more specific patterns win over wildcard ones (e.g. /accounts/123 literal beats /accounts/{id} beats /accounts/**), and mappings that also constrain by HTTP method, content-type (consumes), or Accept header (produces) are preferred over less-constrained ones. Genuinely ambiguous mappings (same path, method, and no differentiating consumes/produces) throw an IllegalStateException at startup rather than silently picking one.

Configuring H2 Database & YAML Properties

Embedded in-memory DB setup, YAML config structure, and the properties that control JPA/Hibernate behavior.

Why H2 for local dev

H2 is a lightweight, pure-Java relational database that can run fully in-memory — no install, no external process, data resets on every restart. It ships with a browser-based console (/h2-console) for inspecting tables during development. It's a stand-in for a real production DB (MySQL/Postgres, configured similarly later) that keeps the local dev loop fast.

Interview pitfall

ddl-auto: update is convenient for demos but never used in production — it can silently make destructive/unexpected schema changes as entities evolve. Production systems use validate (fail fast if entities don't match schema) combined with a migration tool like Flyway or Liquibase to apply versioned, reviewed schema changes.

Why YAML over .properties

YAML supports hierarchical nesting (no repeated prefixes like spring.datasource.url, spring.datasource.username on every line), is more readable for deeply nested config, and supports Spring Profile-specific documents in a single file using --- separators with spring.config.activate.on-profile. Functionally, both are just PropertySources to Spring — it's purely ergonomic, not a capability difference.

What is the H2 database and why is it used in dev/demos?

H2 is a lightweight, embeddable, pure-Java relational database that can run entirely in-memory with zero external setup, making local development and demos fast and self-contained. It's not typically used in production.

What does spring.jpa.hibernate.ddl-auto=update do, and why is it risky?

It tells Hibernate to compare entity mappings against the existing schema at startup and automatically apply additive changes (new tables/columns) to match. It's risky in production because it can make unreviewed, potentially destructive schema changes automatically — teams prefer explicit, version-controlled migrations instead.

How would you manage schema changes safely across environments in production, and why not just use ddl-auto=validate everywhere?

ddl-auto=validate is a safety net (fails fast if entity/schema drift exists) but doesn't create or evolve the schema — you pair it with a migration tool like Flyway or Liquibase that applies versioned, ordered SQL migration scripts checked into source control and run automatically on startup (or via CI/CD) before the app connects. This gives you an auditable, repeatable, rollback-capable history of schema changes across dev/staging/prod, instead of trusting Hibernate's schema inference — which can't express things like data backfills, column renames (it sees a rename as drop+add), or complex constraint changes.

What is Spring's property precedence order — if the same property is set in application.yml, an environment variable, and a command-line argument, which wins?

Spring Boot resolves properties from many PropertySources in a defined precedence, roughly (highest to lowest): command-line arguments → SPRING_APPLICATION_JSON → servlet init params → JNDI → Java System properties → OS environment variables → profile-specific application-{profile}.yml → base application.yml → @PropertySource annotations → default properties. So a command-line arg overrides an env var, which overrides application.yml. This ordering is exactly what enables the 12-factor pattern of overriding config per-environment without touching the packaged artifact.

IMPORTANT: Lombok Issue in IntelliJ IDEA

Why Lombok needs IDE-level support, and the two-step fix.

Lombok works via annotation processing at compile time — it plugs into the Java compiler and injects bytecode (getters, setters, constructors, equals/hashCode, builders) that doesn't exist as visible source code. javac handles this natively, but IntelliJ's own incremental compiler and code-analysis engine need to know how to interpret Lombok annotations too, or the IDE will show false "cannot find symbol" errors for methods like getName() even though the project compiles fine on the command line.

The fix — two parts

  1. Install the Lombok plugin: Settings → Plugins → search "Lombok" → Install — teaches IntelliJ's editor/inspector to understand generated methods.
  2. Enable annotation processing: Settings → Build, Execution, Deployment → Compiler → Annotation Processors → check "Enable annotation processing" — without this, IntelliJ's own build (separate from Maven's) won't run Lombok's processor at all.
Symptom to recognize

Project builds fine via mvn compile on the terminal, but IntelliJ underlines every Lombok-generated getter/setter call in red. That mismatch is the signature of this exact issue — Maven's annotation processing works independently of the IDE's own compiler settings.

Why does IntelliJ sometimes show errors for Lombok-generated methods even though the project compiles?

Because IntelliJ's editor uses its own incremental compiler and code analyzer separate from the actual Maven/Gradle build; without the Lombok plugin and annotation processing enabled in IDE settings, it doesn't know Lombok annotations generate real methods, so it flags them as missing even though `mvn compile` succeeds.

What two settings fix Lombok support in IntelliJ?

Installing the Lombok plugin, and enabling "Annotation Processing" under Build, Execution, Deployment → Compiler → Annotation Processors.

How does Lombok generate code without you ever seeing a generated .java file, unlike tools like MapStruct which produce visible generated sources?

Lombok hooks into the compiler at the AST (Abstract Syntax Tree) level via the pluggable Annotation Processing API (javax.annotation.processing.Processor), but rather than only generating new source files (the API's typical use), it uses internal, version-specific compiler APIs to directly mutate the in-memory AST of the class being compiled during the processing round — inserting method/field nodes before bytecode generation. This is why Lombok is version-coupled to javac/IDE compiler internals and occasionally breaks on new JDK releases, unlike source-generating processors like MapStruct which just emit additional standalone `.java` files through the sanctioned Filer API.

How derived query methods work

Spring Data parses method names like findByMobileNumber at application startup using a naming convention parser: findBy + property path (MobileNumber → maps to the mobileNumber field), builds a corresponding JPQL query, and creates a proxy implementation — no SQL or implementation is written by you. You can combine conditions: findByNameAndEmail, add ordering: findByNameOrderByCreatedAtDesc, etc.

What's the difference between JPA, Hibernate, and Spring Data JPA?

JPA is a specification for ORM in Java. Hibernate is the concrete implementation of that spec that Spring Boot uses by default. Spring Data JPA is an additional abstraction on top of JPA that auto-generates repository implementations, removing DAO boilerplate.

What does @Entity require to work correctly?

A no-argument constructor (JPA instantiates entities via reflection), a field annotated @Id as primary key, and non-final fields/class (Hibernate needs to generate proxies and set fields).

How does a method like findByMobileNumber(String) work without you writing a query?

Spring Data JPA parses the method name against a supported keyword grammar at startup, derives the equivalent JPQL query from the property name, and generates a proxy implementation automatically — this is called a "derived query method."

Explain what happens under the hood when you call jpaRepository.save() on a new entity vs an existing (already-persisted) one.

save() checks whether the entity is "new" (typically: is its @Id field null, or does it implement Persistable with isNew()). If new, Hibernate issues an INSERT (via EntityManager.persist()). If the ID is non-null, Hibernate calls merge(), which first does a SELECT to load the current state into the persistence context if not already managed, copies over the state of the detached entity, and then relies on Hibernate's dirty-checking to issue an UPDATE only for changed fields at flush time — meaning `save()` on an "existing" entity can trigger an extra read you didn't expect if the entity wasn't already attached to the current persistence context.

What is the N+1 select problem and how would you detect/fix it in this codebase?

It happens when fetching a list of N parent entities with a lazily-loaded association triggers 1 query for the parents plus N additional queries — one per parent — to fetch each one's association, instead of a single join. You'd detect it via spring.jpa.show-sql=true or a tool like p6spy/Hibernate statistics showing repeated near-identical SELECTs. Fixes: use JOIN FETCH in a custom JPQL query, an @EntityGraph annotation on the repository method to eagerly fetch specific associations only where needed, or batch fetching (hibernate.default_batch_fetch_size) as a blanket mitigation — while avoiding globally switching associations to `FetchType.EAGER`, which just moves the problem to every query regardless of need.

Why does Spring Data JPA prefer interface-based repositories over you writing a DAO class — how is the implementation actually created at runtime?

At context startup, Spring Data's JpaRepositoryFactoryBean scans for interfaces extending Repository/JpaRepository and, for each, creates a JDK dynamic proxy (or CGLIB where needed) backed by a default implementation class (SimpleJpaRepository) plus method interceptors that route derived-query-method calls through a query-derivation engine and any custom @Query-annotated methods through JPQL/native execution. This means zero hand-written implementation classes, consistent transactional behavior (each method wrapped with `@Transactional` semantics from `SimpleJpaRepository`), and a uniform extension point (custom repository fragments) — at the cost of some "magic" that's harder to step through in a debugger than a plain DAO class.

Introduction to DTO (Data Transfer Object) Pattern

Why entities should never be exposed directly through REST controllers.

The problem DTOs solve

An @Entity class is a persistence artifact — its shape is dictated by database structure (auditing columns, lazy associations, JPA proxy internals). A REST API's request/response shape is a contract with external clients. Coupling these two means:

  • Any schema change (renaming a column, adding an internal field) breaks API consumers.
  • Internal/sensitive fields (audit columns, other linked entities) can leak accidentally into JSON responses.
  • Serializing a lazily-loaded association outside a transaction throws LazyInitializationException.
  • Validation rules that only make sense for input (e.g. "email required on create") get muddled with persistence concerns.
Definition

A DTO is a plain object used purely to carry data between layers/processes — here, between the client and the controller. It has no persistence annotations and no business behavior, just fields (+ validation annotations) shaped exactly as the API contract requires.

What is a DTO and why not just return the @Entity from the controller?

A DTO is a plain data-carrier object shaped for the API contract. Returning entities directly couples your DB schema to your public API, risks leaking internal fields, and can throw LazyInitializationException when serializing associations outside a transaction — DTOs decouple persistence shape from API shape.

What does BeanUtils.copyProperties do?

It uses reflection to copy field values from a source object to a target object where property names (and compatible types) match, saving you from writing manual getter/setter chains for mapping.

What are the risks of using BeanUtils.copyProperties at scale, and when would you switch to MapStruct?

BeanUtils.copyProperties is reflection-based, so it's slower under high-throughput mapping, fails silently on typo'd or type-mismatched field names (no compile-time check), and doesn't handle nested/collection mapping well. MapStruct generates plain Java mapping code at compile time (like Lombok), so mismatches are compile errors, performance is comparable to hand-written code, and nested object graphs are handled cleanly via composed mappers. Teams typically switch once mapping logic grows complex enough that silent reflection failures become a real production risk, or once profiling shows mapping overhead matters.

In a microservices system, should the DTO layer also be the versioning boundary for your public API?

Yes conceptually — DTOs are exactly where you'd introduce a `v2` variant of a response shape without touching the entity or internal service logic at all, which is the whole point of decoupling persistence from contract. In practice, teams often keep one DTO set per API version (`AccountsDtoV1`, `AccountsDtoV2`) or use versioned controller packages, and the mapping layer (MapStruct/manual) becomes the place where backward compatibility logic — defaulting new fields, transforming renamed fields — actually lives, keeping that complexity out of both the entity and the client-facing version-specific model.

Design note

CustomerDto nests AccountsDto with @Valid so that a single POST /api/create can accept customer + initial account details in one payload, and cascaded Bean Validation actually validates the nested object (without @Valid on the field, nested validation annotations are silently skipped).

Why does CustomerDto have a @Valid annotation on the nested AccountsDto field?

Bean Validation does not cascade into nested objects automatically — without `@Valid` on the field, validation annotations inside `AccountsDto` would be silently ignored when validating a `CustomerDto` instance. `@Valid` tells the validator to recurse into that nested object too.

Why have a separate ErrorResponseDto instead of reusing ResponseDto for errors?

Success and error responses carry fundamentally different information (a status code/message vs. an API path, HTTP error status, message, and timestamp for debugging) — separate DTOs keep each response shape precise and self-documenting rather than one shape with a bunch of nullable, situationally-unused fields.

Should request DTOs and response DTOs for the same resource be the same class? What breaks if you reuse one?

Generally no — request and response often diverge (e.g. a create request has no ID yet, a response includes server-generated fields like `accountNumber`, `createdAt`; an update might allow only a subset of fields to change). Reusing one DTO for both forces every field to be optional/nullable to satisfy both directions, which weakens validation precision (you can't mark a field `@NotEmpty` if it's legitimately absent on create but required on response) and makes the contract ambiguous for API consumers reading generated OpenAPI docs. Splitting into `*Request`/`*Response` DTOs (or per-operation DTOs) keeps validation tight and documentation accurate at the cost of some mapping duplication.

Where should cross-field validation live — e.g. "if accountType is SAVINGS, minBalance must be non-null"?

Bean Validation's built-in annotations are per-field; cross-field rules need either a custom class-level constraint annotation (implementing `ConstraintValidator` at the class level, e.g. `@ValidAccountRules` on the DTO) or, for rules that depend on business/DB state (not just the DTO's own fields), explicit checks in the service layer rather than the validation framework, since Bean Validation runs before any service logic and shouldn't reach into repositories. The rule of thumb: pure structural/data-shape rules → Bean Validation (built-in or custom constraint); anything requiring a DB lookup or business context → service-layer validation with a domain-specific exception.

Annotation reference

@RequestBody

Deserializes the incoming HTTP request body (JSON) into the annotated method parameter using an HttpMessageConverter (Jackson).

@Valid

Triggers Bean Validation on the annotated argument before the controller method body runs. On failure, throws MethodArgumentNotValidException — caught by the global exception handler (section 23).

@Service

Stereotype annotation marking a class as a service-layer Spring bean, picked up by @ComponentScan. Semantically signals business-logic layer (functionally identical to @Component, but improves readability and enables layer-specific AOP/exception translation).

@AllArgsConstructor

Lombok — generates a constructor with one parameter per field. Combined with final fields, this is how constructor injection is done without writing the constructor by hand — Spring auto-detects a single constructor and injects dependencies through it (no @Autowired needed since Spring 4.3+ for single-constructor classes).

@Validated

Spring's variant of javax/jakarta.validation.Valid, applied at the class level here to enable validation of path variables/request params (not just @RequestBody) and to support validation groups.

Constructor injection vs field injection

Using @AllArgsConstructor with final fields (constructor injection) over @Autowired on fields directly is the recommended practice: it makes dependencies explicit and immutable, fails fast at startup if a bean is missing, and makes the class trivially unit-testable (just call the constructor with mocks) without needing a Spring context or reflection-based injection.

What does @Valid on a @RequestBody parameter do, and what happens if validation fails?

It runs Bean Validation against the deserialized object using the constraint annotations on its fields before the controller method executes. If any constraint fails, Spring throws `MethodArgumentNotValidException`, which — if you have a `@RestControllerAdvice` — is caught and turned into a structured error response instead of reaching your method body.

Why does the controller depend on an interface (IAccountsService) instead of the implementation class directly?

This follows the Dependency Inversion Principle — the controller is decoupled from a specific implementation, making it easy to swap implementations or, more practically, to mock the service in controller unit tests without spinning up real business logic or a database.

Why prefer constructor injection (via @AllArgsConstructor) over field injection with @Autowired?

Constructor injection allows fields to be `final` (immutable, thread-safe by construction), makes dependencies explicit in the constructor signature, fails fast at context startup if a dependency can't be satisfied, and is much easier to unit test since you can instantiate the class directly with mocks — no Spring context needed.

The createAccount method does a findByMobileNumber check then a save — is this safe under concurrent requests with the same mobile number?

No — this is a classic check-then-act race conditionunique database constraint on `mobile_number` (defense at the data layer, not just application logic), catching the resulting `DataIntegrityViolationException` and translating it into the same `CustomerAlreadyExistsException` for a clean API response — application-level existence checks alone are a UX nicety (fail fast, friendly message) but not a correctness guarantee under concurrency.

This method saves a Customer and then an Accounts row as two separate repository calls — what guarantees they're atomic?

By itself, nothing in this code guarantees atomicity — if the process crashes between the two `save()` calls, you'd get an orphaned customer with no account. In this codebase it's implicitly relying on the service method being wrapped by Spring's declarative transaction management: if `@Transactional` is applied at the service (class or method) level, both `save()` calls participate in a single JPA/JDBC transaction, and either both commit or both roll back on exception. Note: with `spring-boot-starter-data-jpa`, `SimpleJpaRepository`'s own methods are individually transactional by default, but that does NOT make two separate repository calls in your own service method atomic together — you need an explicit `@Transactional` on the service method itself for that.

Why return ResponseEntity instead of just ResponseDto from the controller method?

ResponseEntity gives explicit control over the full HTTP response — status code, headers, and body — rather than always defaulting to 200 OK. Returning a bare DTO forces you to rely on `@ResponseStatus` annotations or exception-driven status codes for anything other than 200, which is less flexible when the same method might need to return 201 on create, or when you want to add response headers (e.g. a `Location` header pointing to the newly created resource, which is itself a REST best practice for 201 responses).

@RequestParam

Binds a query string parameter (?mobileNumber=...) to a method argument. Required by default (throws MissingServletRequestParameterException if absent) unless required = false is set. Contrast with @PathVariable, which binds a URI template segment like /accounts/{id}.

Why Optional + orElseThrow, not null checks

Spring Data JPA's findBy... methods return Optional<T> instead of a nullable T precisely to force explicit handling of the "not found" case at the call site. .orElseThrow(...) is the idiomatic way to convert an absent Optional straight into a meaningful domain exception, rather than risking a `NullPointerException` deeper in the code.

Difference between @RequestParam and @PathVariable?

@RequestParam binds query string parameters (`?key=value`), typically used for optional filters/search criteria. `@PathVariable` binds a segment of the URI path itself (`/accounts/{id}`), typically used to identify a specific resource.

Why does the repository method return Optional instead of Customer?

To force the caller to explicitly handle the "not found" case rather than risking a NullPointerException — `Optional` makes absence part of the type signature, and `.orElseThrow()` cleanly converts that into a meaningful exception.

Should GET /api/fetch?mobileNumber=... really use a query param instead of a path variable like GET /api/customers/{mobileNumber}?

REST convention favors path variables for identifying a specific resource by a stable identifier (`/customers/{mobileNumber}` reads as "the customer resource identified by this mobile number"), and query params for filtering/searching a collection (`/customers?city=...`). Using a query param here for a single-resource lookup is a minor deviation from idiomatic REST design — acceptable in a course/demo, but in a FAANG-style API review this would likely be flagged, especially since mobile number is being used as a de facto resource identifier.

The fetch flow does two separate repository lookups (customer, then account) — how would you avoid the extra round trip at scale?

Options in increasing complexity: (1) a single JPQL query joining `Customer` and `Accounts` on `customerId` and projecting directly into a DTO (constructor expression or `@EntityGraph`), collapsing two round-trips into one; (2) if `Accounts` is a JPA association on `Customer` (e.g. `@OneToOne`), fetch it eagerly via `JOIN FETCH` in a custom query rather than two separate repository calls; (3) at genuinely high scale, consider a read-optimized cache (e.g. Redis) keyed by mobile number holding the pre-joined DTO, invalidated on writes — but that's usually premature for a lookup this cheap unless profiling shows it's a hot path.

@Override
public boolean updateAccount(CustomerDto customerDto) {
    boolean isUpdated = false;
    AccountsDto accountsDto = customerDto.getAccountsDto();
    if (accountsDto != null) {
        Accounts accounts = accountsRepository.findById(accountsDto.getAccountNumber())
            .orElseThrow(() -> new ResourceNotFoundException(
                "Account", "AccountNumber", accountsDto.getAccountNumber().toString()));

        AccountsMapper.mapToAccounts(accountsDto, accounts);
        accounts = accountsRepository.save(accounts);

        Long customerId = accounts.getCustomerId();
        Customer customer = customerRepository.findById(customerId)
            .orElseThrow(() -> new ResourceNotFoundException(
                "Customer", "CustomerID", customerId.toString()));
        BeanUtils.copyProperties(customerDto, customer);
        customerRepository.save(customer);
        isUpdated = true;
    }
    return isUpdated;
}
Why findById → save(), not a raw UPDATE

Because JPA/Hibernate needs the entity to be a managed entity (attached to the persistence context) for its automatic dirty checking to detect field changes and generate the correct UPDATE SQL at flush/commit time. Loading first (rather than constructing a detached entity with just the ID and calling save) also ensures optimistic locking/versioning (if used) sees the correct current state, and avoids accidentally nulling out fields not present in the incoming DTO.

Why does the update flow call findById before save() instead of just calling save() with the new data directly?

Loading the entity first attaches it to Hibernate's persistence context, so subsequent field changes are automatically detected via dirty checking and translated into an UPDATE statement for exactly the changed columns. Constructing a detached entity from scratch and saving it risks overwriting fields not included in the incoming payload with nulls.

Why does this endpoint return HTTP 417 on failure instead of 400 or 404?

It's a design choice in this course to signal "the update could not be completed as expected" distinctly from validation errors (400) — though in stricter REST design, a more conventional choice would be 404 if the account genuinely wasn't found, since 417 (Expectation Failed) is unusual for this scenario and can confuse API consumers.

Is this update endpoint truly idempotent, per PUT's contract?

Yes in effect — calling it repeatedly with the same payload results in the same final state each time (it fully overwrites the targeted fields based on account number), which satisfies PUT's idempotency contract even though the underlying implementation issues an UPDATE each time rather than literally doing nothing on repeat calls. Idempotency is about the *outcome* being the same, not about whether the server does identical work each time.

Two concurrent PUT requests update the same account with different data — what happens, and how would you prevent a lost update?

Without extra protection, this is a classic lost update race: both requests load the same row, both compute an update, and whichever commits last silently overwrites the other's change with no error. The standard JPA fix is optimistic locking — add a `@Version` field to the entity; Hibernate includes it in the `WHERE` clause of the `UPDATE` and increments it on each write, so if a concurrent transaction already bumped the version, the second `UPDATE` affects zero rows and Hibernate throws `OptimisticLockException`, which the controller can translate into a 409 Conflict asking the client to retry with fresh data. Pessimistic locking (`SELECT ... FOR UPDATE` via `@Lock(LockModeType.PESSIMISTIC_WRITE)`) is the alternative when conflicts are expected to be frequent and you'd rather block than retry.

Ordering matters

Accounts must be deleted before the customer if there's a foreign key from accounts.customer_id → customer.customer_id without cascade delete configured at the DB level — deleting the parent first would violate the FK constraint. This method-level ordering is a manual substitute for a DB-level ON DELETE CASCADE or a JPA-level cascade = CascadeType.REMOVE on a mapped relationship.

Why is accountsRepository.deleteByCustomerId called before customerRepository.deleteById?

Because `accounts` has a foreign key referencing `customer`, the child rows must be removed first — otherwise the delete on `customer` would violate the FK constraint (assuming no DB-level cascade delete is configured).

Should DELETE return 200, 204, or something else on success?

Both 200 OK (with a confirmation body) and 204 No Content (empty body, since there's nothing meaningful left to return once a resource is gone) are acceptable REST conventions — 204 is arguably more precise since a deleted resource has no representation to send back.

This delete isn't wrapped visibly in a transaction — what happens if the process crashes between the two delete calls?

Without `@Transactional` on the service method, each repository call commits independently — a crash between the two leaves accounts deleted but the customer row still present, an inconsistent state. Wrapping the method in `@Transactional` ensures both deletes are part of one atomic unit: either both succeed or, on any exception, both roll back, leaving the pre-delete state intact. This is a good example of why "looks like two calls, must need a transaction" should be a reflex when reviewing multi-step write logic.

Is hard-deleting customer/account rows a good idea for a banking-domain system?

Usually not — financial systems typically favor soft deletes (an `active`/`deleted_at` flag, filtered out of normal queries via `@Where` or a query-level filter) to preserve audit trails, satisfy regulatory/compliance retention requirements, and allow account recovery. Hard deletes also complicate any historical reporting or reconciliation that needs to reference a "deleted" account. The trade-off is added query complexity (every query must exclude soft-deleted rows) and eventual data growth, which is typically an acceptable cost in regulated domains like banking.

            webRequest.getDescription(false),
            HttpStatus.INTERNAL_SERVER_ERROR,
            exception.getMessage(),
            LocalDateTime.now());
        return new ResponseEntity<>(errorResponseDto, HttpStatus.INTERNAL_SERVER_ERROR);
    }

    // overridden from ResponseEntityExceptionHandler — handles @Valid failures
    @Override
    public ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {
        Map<String, String> validationErrors = new HashMap<>();
        ex.getBindingResult().getAllErrors().forEach(error -> {
            String fieldName = ((FieldError) error).getField();
            String message = error.getDefaultMessage();
            validationErrors.put(fieldName, message);
        });
        return new ResponseEntity<>(validationErrors, HttpStatus.BAD_REQUEST);
    }

Annotation reference

@RestControllerAdvice

@ControllerAdvice + @ResponseBody — a single class that intercepts exceptions thrown from any @RestController in the application (global scope by default, narrowable via basePackages/annotations attributes), keeping error-handling logic out of individual controllers entirely.

@ExceptionHandler

Declares which exception type a method handles. Spring matches the most specific applicable handler when an exception is thrown — a handler for a subclass wins over a handler for its superclass.

@ResponseStatus

Placed directly on an exception class to declare the default HTTP status it should map to if thrown and not otherwise handled by an explicit `@ExceptionHandler` returning its own status.

ResponseEntityExceptionHandler

Spring MVC base class with pre-built handlers for common framework exceptions (`MethodArgumentNotValidException`, `HttpMessageNotReadableException`, etc.) — extend it and override specific `handleX` methods to customize just the ones you care about, inheriting sane defaults for the rest.

What's the benefit of @RestControllerAdvice over try/catch in every controller method?

It centralizes error-handling logic in one place, keeping controller methods focused purely on the happy path, ensures consistent error response shapes across the whole application, and avoids duplicating the same try/catch boilerplate across every endpoint.

How does Spring decide which @ExceptionHandler method to invoke when an exception is thrown?

It looks for the most specific matching handler for the thrown exception's type — a handler registered for the exact exception class is preferred; if none exists, it walks up the exception's class hierarchy looking for a handler on a superclass, ultimately falling back to a generic `Exception.class` handler if present.

Why have a catch-all @ExceptionHandler(Exception.class)?

To guarantee that any unanticipated exception (a bug, a null pointer, a third-party library error) still results in a clean, structured JSON error response with a 500 status rather than an unhandled exception leaking a raw stack trace or default error page to the client.

Is it safe to return exception.getMessage() directly in the API error response, as this handler does?

Not universally — for domain exceptions you threw yourself with a controlled message (like `ResourceNotFoundException`), it's fine. But for the generic `Exception.class` catch-all, `exception.getMessage()` might leak internal details: SQL fragments from a `DataAccessException`, class/package names, or other implementation details useful to an attacker probing the system. Production-grade global handlers typically return a generic, safe message for unclassified exceptions ("An unexpected error occurred") while logging the real exception (with stack trace) server-side for debugging, and reserve detailed messages for exceptions you've deliberately designed to be user-facing.

How would you add a correlation/trace ID to every error response for debugging distributed requests across microservices?

Generate or propagate a correlation ID (often via a `Filter`/`HandlerInterceptor` that reads an incoming `X-Correlation-Id` header or generates one if absent), store it in a thread-local context — in Spring, typically via MDC (Mapped Diagnostic Context) for logging, or a request-scoped bean — and include it both in the structured log lines for that request and in the `ErrorResponseDto` returned to the client. In a microservices chain, that same header should be forwarded on any downstream calls (e.g. via `RestTemplate`/`WebClient` interceptors or automatically through tools like Spring Cloud Sleuth/Micrometer Tracing) so a single failing request can be traced end-to-end across services in a centralized logging/tracing system.

What's the difference between using @ResponseStatus on the exception class versus handling it explicitly in @RestControllerAdvice — when would you use each?

@ResponseStatus on the exception class is declarative and terse — good for simple cases where you just need a status code and Spring's default error body is acceptable, and it works even without a global handler present. An explicit `@ExceptionHandler` in `@RestControllerAdvice` is needed when you want a custom response body shape (like this `ErrorResponseDto` with path/timestamp), need to log the exception, need conditional status codes based on exception state, or want a uniform error contract across all exception types — which is why production APIs almost always centralize through the advice class rather than relying solely on `@ResponseStatus`.

NotNull vs NotEmpty vs NotBlank — the exact interview trap

@NotNull passes for "". @NotEmpty rejects "" but passes for " " (whitespace). @NotBlank rejects both "" and " " — it trims before checking. For human-entered text fields like name/email, @NotBlank is almost always the semantically correct choice; this course's use of @NotEmpty on `name` would technically still allow a whitespace-only name to pass.

Where enforcement happens

Bean Validation triggers automatically when a @Valid-annotated @RequestBody or @RequestParam/@PathVariable (with class-level @Validated) parameter is bound, via Spring's integration with Hibernate Validator (the reference implementation of Jakarta Bean Validation). This happens before the controller method body executes — invalid requests never reach your business logic.

What's the difference between @NotNull, @NotEmpty, and @NotBlank?

`@NotNull` only rejects null. `@NotEmpty` rejects null and empty (zero-length) values. `@NotBlank` (strings only) rejects null, empty, and whitespace-only strings by trimming before the check — it's the strictest and usually the right choice for user-entered text.

What library actually implements Bean Validation annotations in a Spring Boot app?

Hibernate Validator — the reference implementation of the Jakarta Bean Validation specification, pulled in transitively by `spring-boot-starter-validation`. "Hibernate" here is unrelated to Hibernate ORM; it's a separate project under the same umbrella name.

How would you validate a field only on create but not on update, using the same DTO class?

Bean Validation supports validation groups — define marker interfaces like `OnCreate` and `OnUpdate`, tag each constraint with `groups = OnCreate.class` where relevant, and trigger validation for a specific group via `@Validated(OnCreate.class)` on the controller method parameter instead of a plain `@Valid`. This lets one DTO serve both operations with operation-specific required fields, though many teams find separate request DTOs per operation simpler to reason about than juggling validation groups.

How would you write a custom validation annotation, e.g. @ValidMobileNumber, instead of repeating a @Pattern regex everywhere?

Define an annotation interface (`@ValidMobileNumber`) meta-annotated with `@Constraint(validatedBy = MobileNumberValidator.class)`, specifying `message`, `groups`, and `payload` attributes per the Bean Validation spec, then implement `MobileNumberValidator implements ConstraintValidator<ValidMobileNumber, String>` with an `isValid()` method containing the actual check (which can be richer than a single regex — e.g. also verifying a country-code-specific rule). This centralizes the validation logic and its error message in one reusable, testable place instead of duplicating a regex string (and risking it drifting) across every DTO that needs it.

Where's the line between validation you do with Bean Validation annotations vs. validation you do in the service layer?

Bean Validation is for structural/self-contained checks about a single object's own fields — format, length, required-ness, ranges — that don't need to consult external state. Anything requiring a database lookup or business rule that depends on system state — "this mobile number is already registered," "this account has insufficient balance for this operation" — belongs in the service layer, both because Bean Validation validators shouldn't have repository dependencies injected into them (mixing concerns, harder to test in isolation) and because those checks often need to happen inside the same transaction as the write they're guarding against race conditions.

Annotation reference

@EnableJpaAuditing

Turns on the JPA auditing infrastructure application-wide. auditorAwareRef points to the bean name supplying "who is the current user" for @CreatedBy/@LastModifiedBy.

@EntityListeners

Registers a JPA lifecycle listener class on an entity. AuditingEntityListener hooks into @PrePersist (before insert) and @PreUpdate (before update) callbacks to stamp the audit fields.

@CreatedDate / @LastModifiedDate

Populated automatically with the current timestamp on insert / on every update respectively.

@CreatedBy / @LastModifiedBy

Populated from whatever AuditorAware.getCurrentAuditor() returns — typically wired to the authenticated user once Spring Security is added.

What four annotations enable automatic audit column population, and what does each track?

`@CreatedDate` (insert timestamp), `@CreatedBy` (who created it), `@LastModifiedDate` (last update timestamp), `@LastModifiedBy` (who last updated it) — placed on entity fields, combined with `@EntityListeners(AuditingEntityListener.class)` on the entity/base class and `@EnableJpaAuditing` on the main application class.

What is AuditorAware used for?

It's the interface Spring Data JPA calls to determine "who is the current user" for populating `@CreatedBy`/`@LastModifiedBy` — you implement `getCurrentAuditor()` to return, typically, the authenticated principal's username.

Why does @CreatedDate only fire on insert and not get overwritten on later updates?

`AuditingEntityListener` only sets the `@CreatedDate`/`@CreatedBy` fields during the `@PrePersist` lifecycle callback (fired once, on the initial insert); on subsequent `@PreUpdate` callbacks it only touches `@LastModifiedDate`/`@LastModifiedBy`, leaving the creation fields untouched. This is also why those fields are typically marked `@Column(updatable = false)` as a second line of defense — even a manual/accidental attempt to set them on update won't generate an UPDATE for that column.

Once Spring Security is added, how would AuditorAware get the actual logged-in user instead of a hardcoded string?

getCurrentAuditor() would read from `SecurityContextHolder.getContext().getAuthentication()`, extracting the principal's username (or a custom claim from a JWT if using token-based auth) — with a null-safe fallback (e.g. `"SYSTEM"` or `Optional.empty()`) for contexts where no authenticated user exists yet, such as a scheduled batch job or an anonymous public endpoint, so auditing doesn't throw an NPE outside a request context.

In a microservices architecture, is JPA-level auditing (createdBy/updatedBy on each row) sufficient for a real audit trail?

Usually not for compliance-grade auditing — JPA auditing only records the *current* state's last-touch metadata (who/when the row currently reflects), not a full history of what changed and what the previous values were. For a genuine audit trail (required in regulated domains like banking) you'd typically add an event-sourcing-style audit log table (or use Hibernate Envers, which snapshots every revision of every entity), or emit domain events to an append-only audit log/stream (e.g. Kafka topic consumed into a dedicated audit service) capturing before/after values for every mutating operation — JPA auditing columns are a good baseline, not a substitute for that.

Introduction to REST API Documentation Using springdoc-openapi

Auto-generating interactive Swagger UI documentation directly from controller code.

OpenAPI (formerly Swagger Specification) is a language-agnostic standard for describing REST APIs — endpoints, request/response schemas, auth requirements — in a machine-readable JSON/YAML document, which tools can then render as interactive documentation, generate client SDKs from, or use for contract testing. springdoc-openapi is a library that inspects your Spring MVC controllers, DTOs, and validation annotations at runtime and generates that OpenAPI document automatically, plus serves a ready-to-use Swagger UI web page.

pom.xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>2.x.x</version>
</dependency>

Adding this single dependency, with zero further config, exposes:

  • /v3/api-docs — the raw OpenAPI JSON spec
  • /swagger-ui.html — the interactive Swagger UI, listing every controller/endpoint it discovered, letting you execute requests directly from the browser
Why this matters for microservices

With N independently deployed services, hand-maintained API documentation (a wiki page, a Word doc) drifts out of sync almost immediately. Generating docs directly from the same annotations that drive validation and serialization guarantees the docs can never lie about the actual contract — if a field is `@NotEmpty` in code, Swagger shows it as required, automatically.

What's the difference between OpenAPI and Swagger?

OpenAPI is the current name for the specification itself (the standard for describing REST APIs); "Swagger" was the original name of the spec and is now mainly used for the associated tooling, especially Swagger UI, the interactive documentation renderer.

What does adding springdoc-openapi-starter-webmvc-ui give you out of the box?

Automatic generation of the OpenAPI spec (at `/v3/api-docs`) by scanning your controllers and DTOs at runtime, plus a ready-to-browse Swagger UI page (`/swagger-ui.html`) where you can view and directly test every discovered endpoint.

Should Swagger UI be enabled in production?

It depends on the API's audience — for a public or partner-facing API, exposing docs is often desirable (self-service integration), but for internal-only microservices, many teams disable Swagger UI in production (`springdoc.swagger-ui.enabled=false` per profile) or at minimum put it behind authentication/network restrictions, since a fully interactive "try it out" console against production data is a meaningful attack surface if it's ever left open unintentionally.

How would you use the generated OpenAPI spec beyond just human-readable docs?

The machine-readable `/v3/api-docs` JSON can drive: (1) client SDK generation via `openapi-generator` for consuming teams/languages, (2) contract testing — validating that the actual API responses conform to the published schema, catching accidental breaking changes in CI before deployment, (3) API gateway configuration generation, and (4) mock server generation for frontend teams to develop against before the backend is fully implemented — treating the spec as a build artifact and versioned contract, not just documentation.

@Tag

Groups a controller's endpoints under a named, described section in Swagger UI — the collapsible heading you see when browsing docs (e.g. all Accounts CRUD endpoints grouped together, separate from Loans/Cards).

Per-endpoint summary/description shown in Swagger UI — the human-readable explanation of what a specific method does, beyond what's inferable from the path/HTTP verb alone.

What does @Tag do versus @Operation?

`@Tag` (class-level) groups a whole controller's endpoints under a named section in Swagger UI. `@Operation` (method-level) documents a single endpoint's summary and description.

Why do you need to manually add @ApiResponse for error codes like 500, if springdoc auto-generates docs from the code?

springdoc can automatically infer the success response type from the controller method's return type (e.g. `ResponseEntity<ResponseDto>`), but it has no way to know what error responses an endpoint might produce — those come from exception handlers elsewhere in the code, not the method signature — so they must be documented explicitly via `@ApiResponse`.

If every controller in every microservice repeats similar @ApiResponse blocks for 400/404/500, how would you avoid that duplication?

Define a custom composed annotation (a meta-annotation bundling the repeated `@ApiResponses` set, e.g. `@CommonErrorResponses`) and apply that single annotation to each endpoint instead of repeating the full block — Java annotations can be stacked on custom annotations, and springdoc will still pick up the underlying `@ApiResponse` entries through the meta-annotation. Alternatively, some teams centralize this via a shared library module included across microservices, or via springdoc's `OperationCustomizer`/`GlobalOperationCustomizer` SPI hooks that programmatically inject common response documentation into every operation at spec-generation time, keeping controller code clean of repeated boilerplate.

What does the example attribute on @Schema do?

It provides a sample value shown in the generated docs and pre-fills the "Try it out" request body in Swagger UI, so API consumers see a realistic working payload instead of an empty or generic placeholder.

Can @Schema be used at both the class and field level? What's the difference?

Yes. At the class level it names and describes the DTO as a whole (how it appears in the schema catalog). At the field level it documents and provides an example for that specific property.

Does springdoc auto-infer "required" fields from Bean Validation annotations, or do you always need @Schema(requiredMode)?

springdoc-openapi does inspect Bean Validation annotations like `@NotNull`/`@NotEmpty`/`@NotBlank` on a field and automatically marks the corresponding OpenAPI schema property as required — so in most cases you don't need to duplicate that with an explicit `@Schema(requiredMode = REQUIRED)`. You'd reach for the explicit attribute mainly when a field is required by API contract but for some reason isn't backed by a Bean Validation constraint (uncommon), or to override the inferred value for documentation-only purposes.

How would you keep example values in @Schema annotations from going stale as the DTO evolves, since they're just hardcoded strings?

There's no built-in compile-time guarantee — hardcoded `example` strings are exactly the kind of documentation drift risk this whole approach otherwise avoids for structural fields. Mitigations: (1) contract tests that assert the documented examples themselves are valid against the DTO's own validation rules (a CI check that deserializes/validates every `@Schema(example=...)` value), (2) code review discipline treating `@Schema` changes as part of the DTO's diff, not an afterthought, and (3) for complex objects, using `examples` referencing a shared, versioned example JSON file rather than inline per-field strings, so one source of truth backs both docs and any example-based tests.

Classic interview trap: @Component vs @Service vs @Repository

JPA/Hibernate instantiates entities via reflection and requires a no-arg constructor to do so; `@AllArgsConstructor` is a separate convenience for manually constructing fully-populated instances in application code (e.g. in tests or mapping code), not something JPA itself requires.

How would you enforce, at build time rather than code review, that every JPA repository/service class uses the correct stereotype annotation across a large codebase?

The real lesson of this exercise

Notice that every one of the three services duplicates: the layered package structure, the global exception handler shape, the DTO/entity mapping approach, the OpenAPI annotation style, and even the audit-field mechanism. This is completely normal at this stage — but it's exactly the kind of duplication that, at real FAANG scale, gets factored into a shared internal library (a common `BaseEntity`, a common exception-handling starter, shared validation utilities) versioned and published for all services in the org to depend on. Recognizing "this should eventually become a shared library" is itself a signal of engineering maturity interviewers listen for.

Why do Loans and Cards each get their own H2 database instance instead of sharing one with Accounts?

Following the "database per service" microservices principle — each service should own its data privately so services stay independently deployable and their internal schemas can evolve without risk of breaking another service that happens to query the same shared tables.

What's duplicated across all three microservices in this exercise?

The overall layered structure (entity/repository/DTO/controller/service), the `BaseEntity` audit-field pattern, the global exception handler shape, and the OpenAPI documentation style — each service reimplements the same architectural skeleton around different domain data.

How would you actually share the duplicated boilerplate (BaseEntity, GlobalExceptionHandler shape, common DTOs like ErrorResponseDto) across Accounts, Loans, and Cards without violating microservice independence?

Extract the genuinely generic, non-domain-specific pieces (an abstract `BaseEntity`, a reusable `ErrorResponseDto`, a base exception-handling class or a set of common `@ExceptionHandler` methods, shared validation annotations) into a small internal library (a separate Maven/Gradle module, published to an internal artifact repository like Nexus/Artifactory) that each service depends on as a normal dependency. The key discipline: this shared library should contain only cross-cutting infrastructure code, never business logic or domain models — the moment a shared library starts encoding domain rules ("what counts as a valid loan"), you've silently recreated coupling between otherwise-independent services, which defeats the purpose of splitting them in the first place. Versioning the shared library independently (semantic versioning, each service pins a version) also preserves each service's ability to upgrade on its own schedule.

If a customer's data spans Accounts, Loans, and Cards, how would a single "get customer 360 view" API be built without merging the databases?

This is a classic API composition problem — a higher-level service (or the API Gateway/BFF layer) calls all three microservices' fetch endpoints (potentially in parallel using `WebClient`/reactive calls or `CompletableFuture` for concurrency) and aggregates the responses into one composite DTO for the client. At larger scale, this pattern is formalized as a dedicated aggregation/composition service or a GraphQL federation layer that stitches together sub-graphs from each service, so the composition logic lives in exactly one place instead of being reimplemented by every client that needs a cross-service view — while each underlying service's database remains completely private and untouched.
