Challenges of Container Orchestration

Why running containers by hand — or with Docker Compose — stops scaling the moment you have many services, many machines, and real users.

The starting point: containers solved packaging, not operations

A container packages an application with its runtime and dependencies into one portable, immutable image, so “it works on my machine” becomes “it works the same everywhere”. Docker (Section 13 of this course) gave us that. But running one container on one laptop is a very different problem from running hundreds of containers across dozens of machines, 24×7, while keeping them healthy, updated, and reachable. That operational gap is what container orchestration fills.

The concrete problems an orchestrator must solve

ChallengeWhat goes wrong without orchestration
Scheduling / placementSomeone must decide which machine runs which container based on free CPU/memory. Doing this by hand wastes hardware (poor bin-packing) or overloads some hosts.
Self-healingA container crashes or its host dies at 3 AM. Nobody restarts it, so the service stays down until a human notices.
ScalingTraffic spikes need more copies of a service; quiet hours need fewer. Manual docker run on each host does not scale, and you cannot react in seconds.
Zero-downtime deploymentsUpgrading v1→v2 by stopping and starting containers causes downtime; a bad release needs an instant rollback path.
Service discovery & load balancingContainers get new IPs every restart. Callers need a stable name and traffic spread across healthy replicas.
Networking across hostsContainers on different machines must talk to each other securely, which plain Docker bridge networks do not provide.
Configuration & secretsPer-environment config and credentials must be injected without baking them into images.
StorageStateful workloads need volumes that follow the workload when it moves between hosts.
Observability & governanceCentralised logs, metrics, resource quotas, access control (RBAC) for many teams sharing a platform.

Where Docker Compose falls short

Compose (Section 13) is excellent for local development and small single-host setups: one YAML file starts the whole stack. But it is fundamentally single-host.

The one-line takeaway

An orchestrator lets you say “I want 3 healthy copies of Accounts v2 running, reachable at one stable address” and keeps that statement true — across crashes, node failures, and releases — without you babysitting it.

What is container orchestration?

It is the automated management of the lifecycle of containers at scale: deploying them, placing them on machines, scaling them, networking and load-balancing them, monitoring their health, replacing failed ones, and rolling out updates. Instead of manually starting containers on each host, you declare the desired state and the orchestrator continuously makes reality match it.

Why is Docker Compose not enough for production?

Compose targets a single host. If that host dies, everything dies. It has no native rolling updates or rollbacks, no autoscaling, no cross-host networking and no scheduler that spreads workloads over many machines. It remains great for local development and simple demos, but production needs a cluster-aware orchestrator.

What are the main responsibilities of an orchestrator?

Scheduling containers onto nodes; self-healing (restart/replace failures); scaling up and down; service discovery and load balancing; rolling updates and rollbacks; configuration and secret management; persistent storage orchestration; and resource and access governance.

What is the difference between a container and an orchestrator?

A container is the unit of packaging and execution for one application instance. An orchestrator is the control system that manages many containers across many machines. Docker runs containers; Kubernetes decides where and how many run and keeps them alive.

Name some orchestration platforms.

Kubernetes (the de-facto standard), Docker Swarm, HashiCorp Nomad, AWS ECS/Fargate, and OpenShift (an enterprise Kubernetes distribution). Managed Kubernetes services are EKS (AWS), AKS (Azure) and GKE (Google).

A single-host Docker setup with restart policies seems to “self-heal”. Why isn’t that equivalent to orchestration?

A restart policy only restarts a crashed container on the same host and only reacts to process exit. It knows nothing about the host failing, about application-level health (a hung process that is still “running”), about distributing replicas across failure domains, or about holding a desired replica count. An orchestrator’s control loop compares desired vs actual state cluster-wide and reschedules onto healthy nodes.

Why do containers need an orchestrator even if you use a cloud load balancer in front?

The load balancer only routes traffic to targets you register. It does not create replacement instances, place workloads by resource availability, roll out versions gradually, or inject config. Registration of constantly changing container IPs also needs automation (which Kubernetes Services/EndpointSlices provide).

Explain “pets vs cattle” and how it relates to orchestration.

Pets are named, hand-tended servers you nurse back to health; cattle are interchangeable instances you simply replace. Orchestrators assume cattle: Pods are ephemeral, any can be killed and recreated anywhere, and state/config live outside them. Designing microservices as stateless, disposable units is what makes self-healing and scaling possible.

What trade-offs would make you choose ECS/Fargate over Kubernetes?

If the team is all-in on AWS and wants minimal operational overhead, ECS/Fargate removes cluster management and has simpler concepts. Kubernetes is better when you need portability across clouds/on-prem, a rich ecosystem (Helm, operators, service mesh), custom resources, or fine-grained control, at the price of complexity. The decision is operational maturity and lock-in tolerance rather than raw capability.

Introduction to Kubernetes

What Kubernetes is, where it came from, what it gives you for free, and the vocabulary you need for the rest of this section.

What is Kubernetes?

Kubernetes (Greek for “helmsman/pilot”; abbreviated K8s because there are 8 letters between K and s) is an open-source container orchestration platform that automates deploying, scaling and operating containerised applications across a cluster of machines. It was open-sourced by Google in 2014, based on over a decade of experience running internal systems called Borg (and later Omega), and donated to the Cloud Native Computing Foundation (CNCF) in 2015. It is now the industry standard and supported by every major cloud.

The core philosophy: declarative desired state + control loops

  • You write a manifest (YAML) describing the desired state (“3 replicas of image X exposed on port 8080”).
  • You submit it to the cluster; it is stored in etcd.
  • Controllers run endless reconciliation loops: observe the actual state → compare with desired → take action to close the gap. Crash? Gap detected, Pod recreated. Node lost? Pods rescheduled.

What Kubernetes gives you out of the box

  • Automated scheduling — places Pods on nodes with enough resources.
  • Self-healing — restarts failed containers, replaces Pods, reschedules from dead nodes, kills containers failing health checks.
  • Horizontal scaling — manually or automatically via the Horizontal Pod Autoscaler.
  • Rolling updates & rollbacks — gradual releases with no downtime and instant revert.
  • Service discovery & load balancing — stable DNS names and virtual IPs in front of Pods.
  • Configuration & secret management — ConfigMaps and Secrets decoupled from images.
  • Storage orchestration — mount local, cloud or network storage via PersistentVolumes.
  • Extensibility — Custom Resource Definitions and operators let you teach Kubernetes about new object types.

Managed Kubernetes

Running the control plane yourself is hard, so most companies use managed services: Amazon EKS, Azure AKS, Google GKE. The provider operates the control plane (API server, etcd, upgrades); you manage worker nodes (or use serverless node options) and your workloads.

Mental model

Kubernetes is a distributed operating system for your data centre: you hand it containers and desired state; it handles placement, restarts, networking and scaling.

What is Kubernetes?

An open-source platform, originally from Google and now under the CNCF, that automates the deployment, scaling, networking and management of containerised applications across a cluster of machines using a declarative desired-state model.

Why is it called K8s?

K8s is a numeronym: K, then eight letters (ubernete), then s. The full name comes from the Greek word for helmsman or pilot.

What is the difference between declarative and imperative management?

Imperative commands (kubectl run, kubectl scale) tell Kubernetes what action to take now. Declarative management (kubectl apply -f file.yaml) describes the end state and lets controllers figure out the steps. Declarative is preferred in real projects because the YAML is versioned, reviewable and repeatable.

What is a Pod? A Deployment? A Service?

A Pod is the smallest unit Kubernetes runs; it wraps one or more containers that share an IP and volumes. A Deployment declares how many Pod replicas should exist and manages updates/rollbacks. A Service gives those Pods a stable network identity and load-balances traffic to them.

Name some benefits of Kubernetes.

Self-healing, automatic scaling, rolling updates and rollbacks, built-in service discovery and load balancing, configuration/secret management, portability across clouds and on-prem, and a large ecosystem (Helm, Prometheus, Istio, Argo CD).

What is a Namespace used for?

Logical isolation inside a cluster: separate environments or teams (dev, qa, prod) with their own resource quotas, access policies and name scope. Common built-ins are default, kube-system, kube-public and kube-node-lease.

Kubernetes vs Docker — are they competitors?

No, they operate at different layers. Docker builds images and runs containers on one host. Kubernetes orchestrates containers across many hosts and talks to a container runtime through the Container Runtime Interface (CRI), typically containerd or CRI-O. Kubernetes removed its built-in “dockershim” in v1.24, but images built with Docker keep working because they follow the OCI image standard.

Explain the control-loop (reconciliation) pattern and why it makes Kubernetes robust.

Each controller continuously watches the API server for the desired state of its resource type and the observed state of the world, and acts to reduce the difference. Because it works on levels (current state) rather than events, it is self-correcting: if a notification is missed or a controller restarts, the next loop still converges. This is why Kubernetes recovers from partial failures gracefully.

Why is the Pod, not the container, the unit of scheduling?

Some processes are tightly coupled (an app plus a log-shipper or proxy sidecar) and must share a network namespace and storage, and be scheduled together on the same node. The Pod models that co-location, giving them one IP, localhost communication and shared volumes while keeping each container’s image and lifecycle separate.

When would you NOT use Kubernetes?

For a handful of services on one VM, a small team with no platform expertise, or simple workloads where PaaS (App Service, Cloud Run, Elastic Beanstalk) or Compose suffices. Kubernetes brings real operational complexity; the benefits appear with scale, many services, or a need for portability and fine control.

A cluster has two kinds of machines: the control plane (formerly “master”) which makes global decisions and stores state, and worker nodes which run your application Pods.

  • metrics-server — resource metrics for kubectl top and autoscaling.
  • Ingress controller, Dashboard, logging/monitoring agents.

  • 1. Authenticate & authorise — the API server verifies who you are (kubeconfig credentials) and whether RBAC lets you create a Deployment.
  • 2. Validate & persist — admission controllers mutate/validate the object; it is written to etcd as desired state.
  • 3. Deployment controller sees a new Deployment and creates a ReplicaSet.
  • 4. ReplicaSet controller sees fewer Pods than desired and creates Pod objects (still unscheduled).
  • 5. Scheduler notices Pods with no node, filters and scores nodes, and writes the chosen node into the Pod spec.
  • 6. Kubelet on that node sees a Pod assigned to it, asks the runtime to pull the image and start containers, runs probes, and updates the Pod status.
  • 7. kube-proxy / CNI wire up networking; the Endpoints controller adds the Pod to matching Services once it is Ready.
Key design insight

Components never call each other directly. Everything goes through the API server by watching and updating objects. That decoupling is why any component can crash and restart without breaking the rest.

Pod, not container

The Pod is the smallest deployable unit: one or more containers sharing one network namespace (one IP, localhost between them) and volumes. You normally create Pods indirectly via a Deployment, never as bare Pods, because a bare Pod is not rescheduled if its node dies.

Labels, selectors and spec vs status

  • Labels are key/value pairs on objects (app: accounts). Selectors query them. This loose coupling is how Services find Pods and Deployments find their Pods.
  • Every object has a spec (what you want) and status (what is observed). Controllers drive status toward spec.
What are the main components of Kubernetes architecture?

Control plane: kube-apiserver, etcd, kube-scheduler, kube-controller-manager (and cloud-controller-manager on clouds). Worker nodes: kubelet, kube-proxy and a container runtime. Add-ons like CoreDNS and a CNI network plugin complete the picture.

What does the API server do?

It is the central gateway: it serves the REST API, authenticates and authorises requests, runs admission control, validates objects and persists them to etcd. All other components, and kubectl, communicate only through it.

What is etcd and why is it critical?

A distributed, consistent key-value store (Raft-based) holding the entire cluster state. If it is lost without a backup the cluster loses all knowledge of its objects, so production setups run 3 or 5 members and take regular snapshots.

What does the scheduler do? Does it start Pods?

It only chooses a node for each unscheduled Pod (filter then score based on resources, affinity, taints/tolerations). It does not start anything; the kubelet on the chosen node does.

What does the kubelet do?

It is the node agent: it watches for Pods assigned to its node, instructs the container runtime to run them, executes liveness/readiness probes, and reports Pod and node status to the API server.

What does kube-proxy do?

It implements Services on each node by programming iptables or IPVS rules so connections to a Service’s virtual IP are load-balanced to healthy backing Pods.

What is a Pod and why can it hold multiple containers?

A Pod is the smallest deployable unit. Multiple containers in a Pod share a network namespace and volumes and are co-scheduled, which suits patterns like sidecars (log shipper, proxy) or init containers.

Walk through exactly what happens when you create a Deployment.

kubectl posts the manifest to the API server, which authenticates, authorises and validates it, then stores it in etcd. The Deployment controller creates a ReplicaSet; the ReplicaSet controller creates Pod objects; the scheduler assigns each Pod to a node; that node’s kubelet pulls the image through the container runtime and starts the containers, and reports status. Once Ready, the Endpoints/EndpointSlice controller adds the Pod to the matching Service. At no point do components call each other directly; they watch the API server.

What happens if the control plane goes down?

Existing Pods keep running because kubelets and the runtime operate independently of the control plane, and kube-proxy rules stay in place. But nothing new can be scheduled, no scaling or self-healing occurs, and kubectl fails until it recovers. That is why production uses highly available control planes across zones with an odd-sized etcd quorum.

Why does etcd need an odd number of members?

Raft requires a majority quorum. With 3 members you tolerate 1 failure, with 5 you tolerate 2; adding a 4th member tolerates no more failures than 3 but increases the quorum size, so even numbers add cost without extra resilience.

What is a watch, and why does Kubernetes use it?

Clients open a long-lived watch on the API server for changes to a resource type instead of polling. Controllers and kubelets react to events and also periodically resync, which is how the system stays event-driven yet self-correcting.

What is an admission controller?

A plugin that intercepts API requests after authentication/authorisation but before persistence. Mutating admission can modify objects (inject defaults or sidecars), validating admission can reject them (policy enforcement such as Pod Security or OPA/Gatekeeper).

How do two Pods on different nodes talk to each other?

The CNI plugin builds an overlay or routed network so every Pod gets a unique cluster-wide IP and can reach any other Pod without NAT. Services add a stable virtual IP on top, implemented by kube-proxy.

Setting Up a Local Cluster with Docker Desktop

The fastest way to get a real, single-node Kubernetes cluster on your laptop to practise everything in this section.

Enable Kubernetes in Docker Desktop

  • Open Docker Desktop → Settings → Kubernetes.
  • Tick Enable Kubernetes, then Apply & Restart. Docker downloads the Kubernetes images and starts a single-node cluster (control plane and worker on one machine).
  • Wait for the Kubernetes indicator to turn green.
  • Docker Desktop installs kubectl and adds a docker-desktop context to your kubeconfig automatically.
Verify
kubectl version
kubectl config get-contexts                  # list contexts, * marks current
kubectl config current-context
kubectl config use-context docker-desktop    # switch to local cluster
kubectl get nodes                            # should show 1 node, Ready
kubectl cluster-info                         # API server + CoreDNS endpoints
kubectl get pods -A                          # system pods in kube-system

kubeconfig and contexts explained

kubectl reads ~/.kube/config (override with the KUBECONFIG env var). It holds three lists: clusters (API server address and CA), users (credentials), and contexts (a named pairing of cluster + user + default namespace). The current context decides which cluster every kubectl command targets.

Always check your context

Running kubectl apply or delete against the wrong context (for example production) is a classic outage. Make a habit of kubectl config current-context, or show it in your shell prompt (kube-ps1).

What is kubectl?

The command-line client for Kubernetes. It translates commands into REST calls to the API server to create, inspect, update and delete resources.

How do you enable Kubernetes on Docker Desktop?

Settings → Kubernetes → Enable Kubernetes → Apply & Restart. This creates a single-node cluster and a docker-desktop kubeconfig context.

What is a context in kubeconfig?

A named combination of cluster, user and namespace. Switching context (kubectl config use-context) changes which cluster your commands operate on.

Where is the kubeconfig file?

~/.kube/config by default, or wherever the KUBECONFIG environment variable points.

How do you see all Pods across every namespace?

kubectl get pods -A (equivalent to --all-namespaces).

What is the difference between kubectl create and kubectl apply?

create is imperative and fails if the object exists. apply is declarative: it creates the object if missing or patches it to match the manifest, tracking the last-applied configuration, so it is the standard for repeatable deployments.

When would you prefer kind or minikube over Docker Desktop’s Kubernetes?

kind runs multi-node clusters as containers in seconds and is ideal for CI pipelines and testing multi-node behaviours (scheduling, node failure). minikube offers addons and multiple drivers. Docker Desktop is single node, so it cannot demonstrate scheduling across nodes, but it is the lowest-friction choice for local app development.

How would you safely manage many clusters from one laptop?

Keep separate kubeconfig contexts, merge files via the KUBECONFIG variable, use tools like kubectx/kubens, and make production contexts require explicit confirmation (shell prompt indicators, separate credentials, read-only roles by default).

A node shows NotReady. How do you investigate?

kubectl describe node for conditions (MemoryPressure, DiskPressure, NetworkUnavailable) and recent events, check kubelet and container runtime logs on the node, verify the CNI plugin and connectivity to the API server. Pods on the node are eventually evicted and rescheduled after the toleration timeout (default 5 minutes).

A web-based view of workloads, Pods, logs, and events — useful for learning and light troubleshooting.

What the Dashboard is

The Kubernetes Dashboard is an official add-on web UI. It lets you view workloads (Deployments, Pods, ReplicaSets), Services, ConfigMaps and Secrets, see logs and events, exec into containers, scale or edit resources and deploy YAML. Security warning

Binding to cluster-admin gives full control of the cluster. That is acceptable on a personal laptop. In shared or production clusters use least-privilege roles (e.g. the built-in view ClusterRole), short-lived tokens, and never expose the Dashboard publicly. Several real breaches began with an open Dashboard.

Version note

Newer Dashboard releases (v7+) are installed via Helm and their access URL differs from the older recommended.yaml flow shown in many tutorials. Follow the README of the version you install. Popular alternatives: k9s (terminal UI), Lens (desktop IDE), and cloud-provider consoles.

What is the Kubernetes Dashboard?

A general-purpose web UI for Kubernetes clusters used to view and manage workloads, see logs/events and troubleshoot, deployed as an add-on in the cluster.

How do you log in to the Dashboard?

Create a ServiceAccount, bind it to a ClusterRole via a ClusterRoleBinding, generate a token with kubectl create token, run kubectl proxy, open the proxy URL, and paste the token (or supply a kubeconfig).

What does kubectl proxy do?

It runs a local HTTP proxy that forwards requests to the API server using your kubeconfig credentials, so you can access the API and in-cluster services such as the Dashboard from localhost:8001.

What is a ServiceAccount?

An identity used by Pods and tools to authenticate to the API server. Every Pod runs under a ServiceAccount (default is default).

What is the difference between Role and ClusterRole?

A Role grants permissions within a single namespace; a ClusterRole is cluster-scoped (or can be reused across namespaces via RoleBindings, and is required for cluster-wide resources like Nodes).

Why is giving the Dashboard cluster-admin dangerous?

Anyone who can reach the Dashboard with that token can create privileged Pods, read every Secret, and take over the cluster. Misconfigured, publicly exposed dashboards have been used for crypto-mining and data theft. Least privilege, network restriction and authentication via SSO or short-lived tokens are the mitigation.

How would you give a team read-only access to the Dashboard?

Create a ServiceAccount (or use OIDC groups), bind it with a RoleBinding to the built-in view ClusterRole limited to the team’s namespace, and issue time-bound tokens. Verify with kubectl auth can-i --as=....

What is the difference between kubectl proxy and kubectl port-forward?

Concepts worth explaining aloud

  • Deployment → ReplicaSet → Pod: you create a Deployment; it creates a ReplicaSet (named accounts-deployment-<hash>) which creates Pods. Each version of the Pod template gets its own ReplicaSet — that is how rollback works (topic 231).
  • Labels vs annotations: labels are identifying and selectable (selectors use them); annotations are non-identifying metadata (build info, tool hints) that cannot be selected on.
  • imagePullPolicy: Always, IfNotPresent, Never. The :latest tag defaults to Always; pinned tags default to IfNotPresent. Use immutable version tags, never rely on latest.
  • Requests vs limits: requests are what the scheduler reserves; limits are the cap. Exceeding the memory limit gets the container OOMKilled; exceeding CPU limit causes throttling. CPU unit 250m = 0.25 core.
  • containerPort is informational; the Service’s targetPort is what actually routes.

What are the main sections of a Kubernetes manifest?

apiVersion, kind, metadata (name, labels, namespace) and spec (desired state). Kubernetes adds a status section.

What is the relationship between Deployment, ReplicaSet and Pod?

A Deployment manages ReplicaSets, a ReplicaSet maintains the desired number of identical Pods, and Pods run the containers. You interact with the Deployment; the rest is automatic.

What is the difference between port, targetPort and containerPort?

port is the Service’s own port; targetPort is the Pod/container port the Service forwards to; containerPort merely documents the port the container listens on.

How do labels and selectors work?

Labels are key/value tags on objects. Selectors choose objects by label. A Service uses a selector to find its backing Pods; a Deployment uses one to identify the Pods it owns.

What are resource requests and limits?

A request is the guaranteed minimum used by the scheduler for placement; a limit is the maximum a container may use. Over the memory limit the container is killed (OOMKilled); over the CPU limit it is throttled.

How do you scale a Deployment?

Change spec.replicas and re-apply, or run kubectl scale deployment accounts-deployment --replicas=3, or configure a Horizontal Pod Autoscaler.

Why is a Deployment’s selector immutable?

The selector ties the Deployment to the ReplicaSets and Pods it adopted by label. Changing it would orphan existing ReplicaSets/Pods or cause overlapping ownership, so the API rejects it. You must delete and recreate the Deployment.

Explain QoS classes and why requests/limits matter for eviction.

Pods are classified as Guaranteed (requests = limits for all containers), Burstable (some requests/limits) or BestEffort (none). Under node memory pressure, BestEffort Pods are evicted first, then Burstable, and Guaranteed last. Not setting requests also breaks scheduling accuracy and autoscaling.

Java-specific: how do container memory limits interact with the JVM?

Modern JVMs are container-aware and size the heap as a percentage of the container limit (-XX:MaxRAMPercentage, default 25%). Non-heap memory (metaspace, thread stacks, native) also counts toward the limit, so a limit equal to heap size will OOMKill the container. Set the percentage deliberately (for example 60–75%) and leave headroom.

Why avoid the latest image tag in Deployments?

It is mutable: different nodes may pull different images, rollbacks cannot reproduce a prior state, and Kubernetes will not detect a change because the manifest is unchanged. Use immutable tags or digests, ideally pinned by CI.

kubectl apply vs replace vs server-side apply?

apply does a three-way merge using the last-applied annotation. replace overwrites the whole object. Server-side apply moves merge logic to the API server with field ownership tracking, reducing conflicts when multiple tools or controllers manage the same object.

Why ClusterIP is the right Service type here

Config Server holds internal configuration (sometimes secrets). Only other Pods inside the cluster need it, so a ClusterIP Service (reachable only inside the cluster) is both sufficient and the secure default. Never expose it with NodePort/LoadBalancer.

How Service DNS works

No startup ordering in Kubernetes

Kubernetes starts Pods in parallel. Make clients resilient: Spring Cloud Config spring.cloud.config.fail-fast=true with retry and backoff, readiness probes on Config Server, and optionally an init container that waits until it responds. Why deploy ConfigServer before other microservices?

Because the other services fetch configuration from it at startup. Without it they fail or crash-loop until it is available.

How does the Accounts Pod reach the ConfigServer Pod?

Through the Config Server’s Service name. CoreDNS resolves configserver (or its fully qualified name) to the Service’s stable ClusterIP, and kube-proxy load-balances to a healthy Pod.

It only needs to be reachable by other Pods inside the cluster. ClusterIP is the default internal-only type and avoids exposing sensitive configuration externally.

How do you view the logs of a Pod?

Compose has depends_on. What is the Kubernetes equivalent and why is there no direct one?

There is none by design. Pods are independent and can restart or reschedule at any time, so a one-time ordering guarantee is meaningless. The idiomatic approach is resilience: clients retry with backoff, readiness probes stop traffic to unready Pods, and init containers can gate startup where truly required.

What happens if Config Server is down when Accounts starts?

With fail-fast enabled the app exits, the kubelet restarts it (CrashLoopBackOff with exponential back-off) until Config Server is available. Without fail-fast the app would start with default config, which is dangerous and hard to detect. Retry settings allow a few attempts before failing.

What is the single point of failure risk in a Config Server and how do you mitigate it in Kubernetes?

Run multiple replicas behind the Service, add readiness/liveness probes, and let clients cache config. Beyond that, many teams replace Config Server with ConfigMaps and Secrets in Kubernetes to remove the runtime dependency entirely.

What is an init container?

A container that runs to completion before the app containers start in the same Pod. Common use: wait for a dependency (until nc -z configserver 8071; do sleep 2; done), run migrations or fetch assets.

How this plugs into Spring Boot

Spring Boot’s relaxed binding maps environment variables to properties: SPRING_PROFILES_ACTIVE becomes spring.profiles.active, SPRING_CONFIG_IMPORT becomes spring.config.import, and EUREKA_CLIENT_SERVICEURL_DEFAULTZONE becomes eureka.client.serviceUrl.defaultZone. Facts to remember

Values are stored in plain text and visible to anyone with read access. Credentials go into a Secret. What is a ConfigMap?

A Kubernetes object that holds non-sensitive configuration as key-value pairs, which Pods consume as environment variables, command arguments or files, decoupling configuration from the container image.

How do you inject a ConfigMap into a Pod?

Use env[].valueFrom.configMapKeyRef for one key, envFrom.configMapRef for all keys, or mount it as a volume to get one file per key.

Why use ConfigMaps instead of baking config into the image?

So the same immutable image can be promoted through dev, QA and prod with only the ConfigMap changing, making deployments repeatable and avoiding rebuilds for config changes.

How does Spring Boot read env variables like SPRING_PROFILES_ACTIVE?

Through relaxed binding: uppercase with underscores maps to lowercase dotted property names. Environment variables outrank application.yml so they override it.

Do Pods pick up ConfigMap changes automatically?

Env vars: no, the Pod must restart (kubectl rollout restart). Mounted files: updated eventually, but the application has to reload them (Spring Cloud Kubernetes or Actuator refresh can help).

What is the difference between ConfigMap and Secret?

ConfigMap is for non-sensitive data. Secret is for sensitive data: it is base64-encoded, can be restricted via RBAC, is kept in memory (tmpfs) when mounted, and can be encrypted at rest. Both are consumed the same way.

ConfigMap vs Spring Cloud Config Server — when to use which in Kubernetes?

ConfigMaps/Secrets are native, need no extra infrastructure, and are ideal when everything runs in Kubernetes. Config Server adds Git-backed versioning and history, per-application and per-profile composition, encryption, and dynamic refresh via Spring Cloud Bus, and works outside Kubernetes. A common pragmatic setup keeps Config Server for application properties and uses ConfigMaps for environment wiring such as profile, URLs and ports; fully Kubernetes-native teams often drop Config Server.

Is a Kubernetes Secret really secure?

By default it is only base64, stored unencrypted in etcd. To secure: enable encryption at rest (KMS provider), tight RBAC (who can get secrets), avoid putting them in Git (use Sealed Secrets, SOPS or External Secrets Operator), prefer file mounts over env vars to reduce leakage in logs and crash dumps, and use short-lived credentials.

How would you roll out a config change safely?

Version the ConfigMap (for example a hash suffix in the name, which Helm and Kustomize generate) so changing it changes the Pod template and triggers a normal rolling update with rollback, rather than mutating config in place and restarting blindly.

What does immutable: true do?

It makes the ConfigMap or Secret read-only after creation, preventing accidental changes that would silently break Pods, and lets the kubelet stop watching it, reducing API server load at scale.

Common probe mistakes

What is self-healing in Kubernetes?

The cluster automatically detects failed or missing Pods/containers/nodes and restores the desired state by restarting containers, recreating Pods or rescheduling them onto healthy nodes, without human intervention.

What happens when you delete a Pod managed by a Deployment?

The ReplicaSet notices the actual count is below desired and immediately creates a new Pod, which the scheduler places on a node.

What is the difference between liveness and readiness probes?

Liveness answers “should this container be restarted?”. Readiness answers “should this Pod receive traffic?”. A failing readiness probe removes the Pod from Service endpoints without restarting it.

What is a startup probe?

A probe that holds off liveness and readiness checks until the application has finished starting, protecting slow-starting apps (like large Spring Boot apps) from being killed prematurely.

What is restartPolicy?

A Pod-level setting (Always, OnFailure, Never) that tells the kubelet when to restart containers. Deployments use Always.

What exposes liveness and readiness in Spring Boot?

Actuator health groups: /actuator/health/liveness and /actuator/health/readiness, enabled with management.endpoint.health.probes.enabled=true (automatic when running on Kubernetes).

Why should a liveness probe not check the database or other downstream services?

If the DB goes down, all Pods would fail liveness and be restarted together, producing a restart storm that cannot fix the DB and makes recovery slower. Liveness should only detect that the process itself is deadlocked or unrecoverable. Dependency checks belong in readiness (so traffic stops flowing while still allowing recovery), and even there should be used carefully to avoid cascading removals of all Pods.

How does self-healing relate to the resiliency patterns from Section 10?

They operate at different layers. Kubernetes heals infrastructure/process failures (dead Pods, nodes). Resilience4j patterns (circuit breaker, retry, bulkhead, rate limiter) protect calls between running services from slow or failing dependencies. A complete design needs both: probes and replicas for availability, circuit breakers and timeouts for graceful degradation.

What is a PodDisruptionBudget?

A policy that limits how many replicas of an application may be voluntarily taken down at once (node drains, cluster upgrades). For example minAvailable: 1 prevents a drain from removing all replicas simultaneously.

How are Pods spread across nodes or zones for fault tolerance?

Use topologySpreadConstraints or pod anti-affinity so replicas land on different nodes/zones; otherwise the scheduler may place all replicas on one node and a single node failure takes the service down.

How long until Pods on a failed node are rescheduled?

The node is marked NotReady after the node-monitor grace period (~40 s) and the default taint-based eviction tolerations (300 s) mean Pods are evicted after about 5 minutes. This can be tuned with tolerationSeconds for faster failover.

Changing the Pod template (image tag, env, resources…) makes the Deployment controller create a new ReplicaSet. Rollback caveats

rollout undo reverts only the Pod template. It does not undo database migrations, ConfigMap changes (unless versioned), or external side-effects. Make DB changes backward compatible (expand/contract) so v1 and v2 can both run during the rollout.

Readiness is the safety net

If new Pods never become Ready, the rollout stalls and the old Pods keep serving — the platform protects you. Without a readiness probe Kubernetes assumes a Pod is ready as soon as the container starts and may send traffic too early.

Note on --record

The old --record flag is deprecated; set the kubernetes.io/change-cause annotation instead to label revisions in rollout history.

What is a rolling update?

A deployment strategy where Pods are replaced gradually, so some old and some new Pods serve traffic at the same time and the application stays available throughout.

How do you roll back a deployment?

kubectl rollout undo deployment/<name> for the previous revision, or --to-revision=N for a specific one. Check history with kubectl rollout history.

What do maxSurge and maxUnavailable mean?

maxSurge is how many extra Pods above the desired count may be created during the update; maxUnavailable is how many Pods may be unavailable. Both accept absolute numbers or percentages.

How do you update the image of a running deployment?

Edit the manifest and kubectl apply, or kubectl set image deployment/<name> <container>=<image:tag>.

How does Kubernetes know a new Pod is healthy during a rollout?

Through its readiness probe; a Pod counts as available only after becoming Ready (and optionally minReadySeconds).

What is revisionHistoryLimit?

The number of old ReplicaSets retained for rollback; default 10. Setting it to 0 disables rollback.

Rolling update vs blue/green vs canary — when to pick each?

Rolling is the default, cheap and good for backward-compatible changes. Blue/green gives instant switch and rollback and is good for risky changes or when versions cannot mix, at double the resources. Canary exposes a small slice of real traffic to the new version with automated metric analysis and aborts on regression; best for high-traffic services, usually via a service mesh or Argo Rollouts/Flagger.

A rollout is stuck at “Waiting for rollout to finish: 1 out of 3 new replicas have been updated”. Why?

The new Pod is not becoming Ready: failing readiness probe, ImagePullBackOff, CrashLoopBackOff, or insufficient resources (Pending). Old Pods keep serving. Check kubectl get pods, describe and logs of the new Pod, then fix or rollout undo. After progressDeadlineSeconds the Deployment condition becomes ProgressDeadlineExceeded.

How do you achieve a true zero-downtime deployment for a Spring Boot service?

Readiness probe tied to Actuator readiness; maxUnavailable: 0; at least 2 replicas; graceful shutdown (server.shutdown=graceful with spring.lifecycle.timeout-per-shutdown-phase) with terminationGracePeriodSeconds longer than that; a short preStop sleep so the Pod is removed from endpoints before SIGTERM; and backward-compatible DB changes.

What happens to in-flight requests when a Pod is terminated?

Kubernetes sends SIGTERM and removes the Pod from Service endpoints concurrently. If the app ignores SIGTERM or exits immediately, in-flight requests break, and some requests may still arrive due to endpoint propagation delay. Graceful shutdown, a preStop delay and a sufficient grace period (default 30 s) fix this.

How do you trigger a rolling restart without changing the image?

kubectl rollout restart deployment/<name>; it patches an annotation in the Pod template, causing a normal rolling update. Useful after changing a ConfigMap consumed as env vars.

Pods are ephemeral and change IPs; a Service is the stable front door to them.

Why Services exist

Details worth knowing

  • Types are cumulative: LoadBalancer ⊃ NodePort ⊃ ClusterIP.
  • Only Ready Pods are in the Service’s endpoints; this is how readiness gates traffic.
  • Default load balancing is random/round-robin per connection; sessionAffinity: ClientIP gives stickiness.

Common mistakes

Selector doesn’t match Pod labels (no endpoints); wrong targetPort; exposing every service as LoadBalancer (cost and attack surface); assuming ClusterIP is reachable from your laptop (it is not — use port-forward).

What is a Kubernetes Service?

An abstraction that gives a set of Pods (selected by labels) a stable IP and DNS name and load-balances traffic across them, hiding the fact that Pods come and go.

List the Service types.

ClusterIP, NodePort, LoadBalancer, and ExternalName (plus headless Services using clusterIP: None).

Difference between NodePort and LoadBalancer?

NodePort exposes the Service on a high port (30000–32767) of every node. LoadBalancer builds on that and asks the cloud provider to create an external load balancer with a public IP that forwards to the NodePorts.

Which type would you use for internal microservices and why?

ClusterIP — it is only reachable inside the cluster, which is exactly the isolation wanted for backend services.

How does a Service know which Pods to send traffic to?

Through its label selector. Matching, Ready Pods are recorded as endpoints (EndpointSlices) which kube-proxy uses to route.

What is the default Service type?

ClusterIP.

What is ExternalName used for?

To map an in-cluster DNS name to an external DNS name (CNAME), so applications can refer to an external service by a stable internal name that can later be swapped for an in-cluster one.

Service vs Ingress vs Gateway API?

A Service is layer-4 (TCP/UDP) load balancing to Pods. Ingress is layer-7 HTTP(S) routing (host/path rules, TLS termination) implemented by an ingress controller (NGINX, Traefik, cloud ALB). The Gateway API is the newer, more expressive and role-oriented successor to Ingress. Typically you have one LoadBalancer for the ingress controller, and ClusterIP Services behind it.

How does kube-proxy implement a Service?

In iptables mode it writes NAT rules that DNAT connections to the Service ClusterIP into one of the endpoint Pod IPs (random selection). IPVS mode uses kernel IPVS hash tables for better scale and more algorithms. Newer CNIs such as Cilium can replace kube-proxy with eBPF.

What is a headless Service and when do you need it?

A Service with clusterIP: None: DNS returns the individual Pod IPs (A records) instead of a single virtual IP. Needed for StatefulSets with stable per-Pod DNS (pod-0.svc) and for clients that do their own load balancing or need to reach specific replicas, e.g. databases and Kafka.

Why is LoadBalancer per service a bad idea at scale?

Each creates a separate cloud load balancer with a cost and public IP, increasing attack surface and management overhead. Consolidate through an Ingress/Gateway layer.

What is externalTrafficPolicy: Local?

It preserves the client source IP and avoids an extra hop by routing only to Pods on the node that received the traffic, at the cost of potentially uneven load distribution. The default Cluster balances across all nodes but SNATs the source address.

How do you scale a deployment quickly?

Why does the LoadBalancer EXTERNAL-IP show <pending> on some clusters?

There is no cloud controller to provision a load balancer (bare metal, minikube without tunnel). Use MetalLB on bare metal or minikube tunnel.

How do you change a Service type without editing YAML?

kubectl patch svc <name> -p ... or kubectl edit svc <name>; but the declarative way is to change the manifest and re-apply.

How would you expose only the Gateway securely in production?

Keep all backends as ClusterIP; expose the Gateway through an Ingress or LoadBalancer with TLS termination (cert-manager), apply NetworkPolicies allowing ingress to backends only from the Gateway, enable authentication at the Gateway, and use WAF/rate limiting.

What are NetworkPolicies and why do they matter?

They are firewall rules for Pods (L3/L4): allow or deny ingress/egress by Pod, namespace or CIDR. By default all Pods can talk to all Pods. NetworkPolicies, enforced by CNIs like Calico or Cilium, implement zero-trust and limit blast radius if one service is compromised.

What are the drawbacks of manually written manifests?

Heavy duplication, hard to manage multiple environments, no packaging or versioning, no single-command install/upgrade/rollback of the full application, no templating logic and a high chance of copy-paste errors.

What is Helm?

The package manager for Kubernetes. A chart bundles templated manifests and default values; installing it creates a release that Helm can upgrade, roll back or uninstall as a unit.

What is a Helm chart, values file and release?

A chart is the package (templates + metadata + default values). A values file supplies configuration to fill the templates. A release is a deployed instance of a chart in a cluster with a revision history.

How is Helm different from Kustomize?

Helm uses Go templating and packages applications with release management; Kustomize patches plain YAML using overlays with no templating and is built into kubectl.

Helm vs Kustomize vs GitOps — how do they fit together?

Helm and Kustomize are authoring/templating tools producing manifests; GitOps tools (Argo CD, Flux) are delivery mechanisms that watch Git and apply the result continuously. Many teams render Helm charts or Kustomize overlays via Argo CD, getting templating plus drift detection and audit trails.

What are the downsides of Helm?

Go-template YAML can become hard to read and debug, charts can hide complexity, and helm upgrade failures can leave releases in odd states. Mitigate with helm template and helm lint in CI, --atomic and --wait upgrades, and keeping charts simple.

How would you manage secrets with Helm/GitOps?

Never commit plaintext secrets. Use Sealed Secrets, SOPS-encrypted values (helm-secrets), or External Secrets Operator pulling from Vault/cloud secret managers, so Git contains only encrypted or reference data.

How do you promote the same release from dev to prod safely?

Build one immutable image per commit, deploy the same chart version with environment-specific values files, gate promotion with automated tests and approvals, and use progressive delivery (canary/blue-green) with automatic rollback on SLO breach.
