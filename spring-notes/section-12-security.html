Microservices Security

Section 9 hid every internal service's port behind the Gateway; Section 11 gave you full visibility into what the system is doing. Neither addressed a basic question: right now, anyone who can reach the Gateway can call every route on it. This section closes that gap with OAuth2 and OpenID Connect via Keycloak — covering both machine-to-machine authentication (Client Credentials grant, securing the Gateway itself and inter-service calls) and real end-user authentication (Authorization Code grant, the flow behind virtually every "Sign in" button you've ever clicked) — plus role-based authorization enforced centrally at the Gateway, exactly where Section 9 argued cross-cutting concerns belong.

How to use this document: OAuth2/OIDC terminology gets confused constantly even by experienced engineers — topic 183 and 184 are worth over-preparing, since "explain the difference between OAuth2 and OpenID Connect" and "walk me through the Authorization Code flow, and explain why it isn't simpler" are two of the most consistently asked questions in backend/security-adjacent interviews at any company handling real user data.

Introduction to Microservices Security

What's actually still missing, given everything built in Sections 9 and 11.

The gap this section closes

Recall Section 9's architecture: the Gateway is the sole external entry point, and internal services no longer publish ports at all. This solved routing and topology hiding — but as configured so far, the Gateway will happily route any incoming request to Accounts, Loans, or Cards, with zero verification of who's calling or whether they're allowed to. Anyone who can reach the Gateway's public port can call every route on it.

The two questions security must answer, every request

QuestionConcern
Authentication — "Who are you?"Verifying the identity of the caller (a human user, or another service/application) making the request
Authorization — "What are you allowed to do?"Given a verified identity, determining whether that specific identity is permitted to perform this specific action (e.g. only an ADMIN role can call the delete-account endpoint)
These are two genuinely different concerns — conflating them is a classic interview mistake

A request can be perfectly authenticated (we know exactly who's calling, their identity is cryptographically verified) and still be correctly rejected for lacking authorization (they're not allowed to do this specific thing). Security systems — and interview answers — need to treat these as two separate, sequential checks, not one combined "is this request okay" gate.

Where this needs to be enforced, and why centrally

Consistent with every cross-cutting concern covered since Section 9, authentication/authorization logic duplicated independently inside every microservice is exactly the anti-pattern this course has repeatedly argued against — the Gateway is the natural, single place to enforce it, for the same reasons SSL termination, rate limiting, and correlation ID generation belong there.

What's the difference between authentication and authorization?

Authentication verifies who is making a request (identity). Authorization determines, given a verified identity, whether that identity is permitted to perform the specific requested action — a request can be fully authenticated and still correctly denied for lacking authorization.

Why does it make sense to enforce security centrally at the Gateway rather than in each individual microservice?

It follows the same cross-cutting-concerns argument from Section 9 — centralizing auth avoids duplicating and potentially inconsistently implementing the same logic across every service, and lets unauthenticated/unauthorized requests be rejected at the system's single entry point before they ever reach internal services at all.

If the Gateway already enforces authentication/authorization, is there any reason an internal service would still need its own security checks?

This is a genuine, actively-debated architectural question, not a settled one — a pure "trust the perimeter" model (only the Gateway checks, internal services trust anything reaching them) is simpler but assumes the internal network is fully trusted and the Gateway can never be misconfigured or bypassed. A zero-trust model argues every service should independently validate incoming requests (re-verifying the token, not just trusting an internal network boundary), since a compromised internal service or an internal network misconfiguration could otherwise let an attacker who's gained any foothold inside the network call other services with no further checks at all. In practice, many organizations land on a middle ground: the Gateway does the primary, user-facing authentication/authorization enforcement (rejecting clearly invalid/unauthorized requests early, cheaply, at one place), while individual services still perform lightweight token validation for defense-in-depth — directly paralleling the Section 9 discussion of API Gateway vs Service Mesh responsibilities, where mTLS and service-level policy enforcement inside a mesh provide exactly this kind of additional internal-layer protection beyond the edge.

Problems That OAuth2 Solves

The motivating scenario — why "just check a username and password" isn't sufficient once delegation is involved.

The password anti-pattern

Imagine a third-party budgeting app wants to read a user's transaction history from eazybank. The naive approach — the user gives the budgeting app their actual eazybank username and password — is a real, historically common pattern, and a genuinely serious problem:

  • The third party gets full access, not the narrow "read transaction history" access the user actually intended to grant — the password grants everything the user's account can do.
  • No easy revocation — the only way to cut off the third party's access is to change the actual account password, which also logs out every other legitimate session/device.
  • The user's real credential is now stored by a third party, multiplying the number of places a single leak could compromise the user's actual eazybank account.
  • No audit trail distinguishing the user's own actions from the third party's — everything looks identical, authenticated as the user directly.

What OAuth2 provides instead

Delegated, scoped, revocable access — the user authenticates directly with the trusted authorization server (never handing credentials to the third party at all), explicitly grants a narrow, specific scope of access ("read transaction history only," not full account access), receives a token representing exactly that grant, and can revoke that specific token/grant independently at any time without affecting their actual account credentials or other sessions.

What's the core problem with a third-party app asking users for their actual password?

It grants the third party full account access rather than a narrow, specific scope, requires storing the user's real credential outside the primary account (multiplying leak risk), and offers no way to revoke just that third party's access without changing the password entirely (logging out everything else too).

What does OAuth2 provide instead of password sharing?

Delegated, scoped, and independently revocable access — the user authenticates directly with a trusted authorization server, grants a specific narrow scope, and receives a token representing exactly that grant, which can be revoked on its own without touching the actual account credentials.

Why is "no audit trail distinguishing the user's actions from the third party's" a real security concern, beyond just being inconvenient?

Without a distinguishable identity for the delegated access, any anomaly-detection or forensic investigation after a security incident can't tell whether unusual activity originated from the legitimate user or from a compromised or malicious third-party integration acting under the shared credential — a serious gap for detecting and responding to abuse. OAuth2's token-based model inherently carries information about which client/application a given request is associated with (the token was issued to a specific registered client), enabling exactly this kind of attribution — a genuinely important operational security benefit beyond the more commonly-cited "scoping" and "revocation" advantages.

Introduction to OAuth2

Precisely what OAuth2 is — and, just as importantly, what it explicitly is not.

OAuth2 is an authorization framework, not an authentication protocol

OAuth 2.0 (RFC 6749) is a framework that defines how a client application obtains a limited-scope access token, which it then presents to a resource server to access protected resources — without the client ever needing to handle the resource owner's actual credentials. It is fundamentally about delegated authorization: "this client is allowed to do X, on behalf of this resource owner (or on its own behalf)."

The single most common misconception, worth stating precisely

OAuth2, by itself, says nothing about who the user is — it only establishes that a token grants some specific scope of access. A resource server receiving a valid OAuth2 access token knows the request is authorized for some scope, but OAuth2 alone provides no standardized way to learn the authenticated user's actual identity (name, email, a stable user ID) from that transaction. This exact gap is what topic 184's OpenID Connect exists to fill — and correctly stating "OAuth2 is authorization, not authentication" unprompted is a strong, specific signal in an interview.

Is OAuth2 an authentication protocol or an authorization framework?

An authorization framework — it defines how a client obtains a limited-scope access token to access protected resources, without needing the resource owner's actual credentials. It doesn't, by itself, standardize how to verify or communicate the user's actual identity.

Concretely, what could go wrong if a system used raw OAuth2 access tokens to "authenticate" users, without OpenID Connect?

Since a plain OAuth2 access token's structure and content aren't standardized for identity purposes (its format and claims are entirely up to the specific authorization server's implementation), a resource server trying to infer user identity purely from an access token is relying on implementation-specific, non-standardized behavior rather than a guaranteed contract — different authorization servers might structure tokens completely differently, and there's no standardized claim guaranteed to represent "who is this," no standardized way to verify the token was actually intended for identity purposes (an access token might be scoped for a narrow API purpose, not meant to double as a proof-of-identity), and historically this exact ambiguity led to real, documented security vulnerabilities in systems that tried to use OAuth2 access tokens as a de facto login mechanism before OpenID Connect standardized the correct way to do this (via a distinct ID Token, covered next).

What's the difference between an access token and a refresh token?

An access token is presented on every request to prove authorization and is typically short-lived. A refresh token is longer-lived and used specifically to obtain a new access token once the current one expires, without requiring the resource owner to fully re-authenticate.

In OAuth2 terminology, what role does the Gateway play?

Depending on the flow, the Gateway acts as the Resource Server (validating incoming access tokens before routing requests to backend services) and, in the Client Credentials flow, also as the Client itself when authenticating on its own behalf.

Why are access tokens deliberately kept short-lived, given the added complexity of needing a separate refresh mechanism?

This is a direct security/usability trade-off: a short-lived access token limits the damage window if a token is ever leaked or stolen (an attacker with a stolen access token can only misuse it until it naturally expires, often within minutes), while the longer-lived refresh token — used far less frequently and typically kept more securely (e.g. never exposed to client-side JavaScript in a browser context) — lets the user avoid needing to fully re-authenticate (re-enter credentials) every few minutes. This mirrors a broader security principle seen elsewhere in this course too — Section 10's circuit breaker sliding windows and Section 6's short-lived CI credentials both reflect the same underlying idea: bound the blast radius of any single compromised credential by keeping its useful lifetime short, and pay the complexity cost of a renewal mechanism in exchange.

What Is OpenID Connect & Why It Is Important

The identity layer OAuth2 deliberately doesn't provide — and the exact, precise relationship between the two.

OIDC is a thin identity layer built on top of OAuth2

OpenID Connect (OIDC) extends OAuth2 with exactly what topic 182 flagged as missing: a standardized way to authenticate a user and obtain verified identity information, using the exact same underlying OAuth2 flows and infrastructure. It adds three concrete things on top of plain OAuth2:

AdditionPurpose
ID TokenA JWT — distinct from the access token — containing standardized identity claims about the authenticated user (`sub` = subject/user ID, `name`, `email`, `iss` = issuer, `exp` = expiration)
openid scopeIncluding this specific, reserved scope in the authorization request is what signals "this is an OIDC request, please also issue an ID Token," turning a plain OAuth2 flow into an OIDC-enabled one
UserInfo endpointA standardized endpoint (`/userinfo`) the client can call with a valid access token to retrieve additional user profile claims beyond what's embedded in the ID Token itself
The precise, interview-ready one-liner

OAuth2 answers "is this client authorized to do X?" OpenID Connect answers "who is this user, verified?" — OIDC doesn't replace or compete with OAuth2; it's a standardized identity layer built directly on top of the same OAuth2 protocol flows, adding the ID Token as the concrete mechanism for conveying verified identity. This distinction is worth stating in almost exactly these words if asked directly, since it's precise, correct, and demonstrates the exact nuance many engineers get wrong.

TokenPurposeConsumed by
Access TokenAuthorizes API calls to a resource serverThe resource server, on every API request
ID TokenProves the user's authenticated identity, once, at login timeThe client application itself (not sent on every subsequent API call) — used to establish "who is logged in" client-side
What is OpenID Connect's relationship to OAuth2?

OIDC is a thin identity layer built directly on top of OAuth2, using the same underlying flows, adding a standardized ID Token (a JWT with identity claims about the authenticated user), the reserved `openid` scope, and a UserInfo endpoint.

What's the difference between an access token and an ID token?

An access token authorizes API calls and is sent to the resource server on every request. An ID token proves the user's authenticated identity at login time and is consumed by the client application itself to establish who's logged in, not sent on every subsequent API call.

Why does including the openid scope specifically trigger OIDC behavior — what's actually happening mechanically?

The `openid` scope is a reserved, standardized signal that tells the authorization server "this specific authorization request should also produce an ID Token, per the OIDC specification" — an authorization server that supports OIDC recognizes this scope specifically and, in addition to whatever access token it would normally issue for a plain OAuth2 request, also generates and returns the standardized ID Token alongside it. Without the `openid` scope, the exact same underlying OAuth2 flow (Authorization Code, for instance) still works and issues an access token, but no ID Token is produced — it's a genuinely opt-in extension layered onto the existing protocol, not a separate, parallel mechanism, which is precisely why OIDC is accurately described as being built "on top of" rather than "alongside" OAuth2.

Should a client ever send the ID Token to a resource server as if it were an access token?

No — this is a genuine, documented anti-pattern. The ID Token is specifically intended for the client application's own consumption (to establish and display "who is logged in"), and its claims/audience are typically scoped to the client itself, not to arbitrary resource servers the client might call. Using it as a bearer credential for API authorization conflates two purpose-built, differently-scoped tokens, and can create real security gaps (a resource server might not correctly validate an ID Token's audience/intended-use the way it would for an access token specifically designed for that purpose) — the correct token for authorizing API calls is always the access token, and the ID Token should stay client-side, used only to establish identity information for the application's own UI/session purposes.

Introduction to IAM Products & Why Keycloak

Choosing an actual Authorization Server implementation, rather than building OAuth2/OIDC compliance from scratch.

Why nobody hand-rolls their own Authorization Server

Correctly implementing OAuth2/OIDC — token signing and rotation, session management, secure credential storage, protection against the many well-documented OAuth2-specific attack vectors (covered implicitly throughout this section's flow deep-dives) — is genuinely difficult, security-critical infrastructure. Virtually every organization uses a dedicated IAM (Identity and Access Management) product rather than building this themselves.

ProductNotes
KeycloakOpen-source (originally Red Hat/JBoss, now a CNCF project), self-hostable, fully-featured OAuth2/OIDC/SAML support — what this course uses
Okta / Auth0Popular managed, commercial IAM-as-a-service platforms
AWS Cognito / Azure Entra IDCloud-provider-native IAM offerings, convenient when already committed to that cloud ecosystem

Why Keycloak specifically for this course

  • Free and self-hostable — runs easily in Docker, no external account/billing needed for learning.
  • Fully standards-compliant — genuine OAuth2/OIDC support, so everything learned transfers directly to any other compliant IAM product (the protocol, not the vendor, is what matters most).
  • Real production usage — Keycloak is a legitimate, widely-used production IAM choice at many real organizations, not just a learning-only tool.
  • Realms, clients, and roles map cleanly onto this section's exact needs — everything covered from topic 188 onward.
What is an IAM product, and why do most organizations use one rather than building their own Authorization Server?

Identity and Access Management products (Keycloak, Okta, Auth0, Cognito) implement the security-critical, genuinely difficult-to-get-right details of OAuth2/OIDC compliance — token signing, session management, secure credential handling — so organizations don't need to build and maintain this themselves, which carries significant security risk if done incorrectly.

What's the trade-off between a self-hosted IAM product like Keycloak versus a managed commercial one like Okta/Auth0?

Self-hosting Keycloak gives full control (data residency, no per-user/per-request vendor pricing, ability to customize deeply, no dependency on a third party's uptime) but shifts operational responsibility onto the organization — patching, scaling, securing, and maintaining high availability for what's genuinely critical, security-sensitive infrastructure becomes the organization's own job. A managed service like Okta/Auth0 offloads that operational burden (the vendor handles uptime, security patching, scaling) at the cost of ongoing subscription pricing (often scaling with user count or request volume, which can become significant at scale) and less deep customization flexibility. The decision typically comes down to team size/expertise available to operate identity infrastructure reliably, cost sensitivity at the organization's actual scale, and any regulatory/data-residency requirements that might favor keeping identity data fully in-house — a genuinely "it depends on the organization's specific constraints" answer worth reasoning through explicitly rather than asserting one option as universally correct.

Deep Dive of Client Credentials Grant Type Flow

The machine-to-machine flow — no end user, no browser redirect, no consent screen.

When this flow applies

The Client Credentials grant is used when the client itself is the entity being authorized — not acting on behalf of any human user. Classic use cases: one backend service calling another (service-to-service/machine-to-machine), a scheduled batch job, or — as this course applies it — the Gateway needing its own identity/authorization to operate as a trusted client.

Client
client_id + client_secret
→ direct request →
Authorization Server
Keycloak's /token endpoint
→ access token →
Client
uses token to call Resource Server
  1. The client authenticates directly with the Authorization Server's token endpoint, presenting its own `client_id` and `client_secret` — a simple, direct, back-channel HTTP request, no browser or redirect involved at all.
  2. The Authorization Server validates the client's credentials and, if valid, issues an access token directly in the response.
  3. The client uses that access token (typically as a Bearer token) to call the Resource Server.
Why this flow is so much simpler than Authorization Code (topic 195)

Because there's no human resource owner involved, there's nothing to redirect a browser to, no login page, no consent screen — the client's own credentials are the authorization proof, exchanged directly in one request/response round trip. This flow is only appropriate specifically because the client is trusted to hold and protect a secret credential itself (a backend service can securely store a `client_secret`; a browser-based JavaScript app or a mobile app generally cannot, which is exactly why user-facing applications need the different Authorization Code flow instead).

When is the Client Credentials grant type appropriate to use?

When the client itself is the entity being authorized, not acting on behalf of a human user — machine-to-machine scenarios like service-to-service calls, scheduled jobs, or a Gateway authenticating as itself.

Why doesn't this flow involve a browser redirect or consent screen?

There's no human resource owner involved to authenticate or grant consent — the client directly presents its own credentials (client_id/client_secret) to the Authorization Server's token endpoint in a single back-channel request, and receives a token directly in response.

Why is this flow only safe for confidential clients that can securely store a secret, and what happens if you tried using it from a mobile app or browser SPA?

The entire security of this flow rests on the `client_secret` staying genuinely secret — if a mobile app or browser-based JavaScript application embedded a client secret, any user could extract it from the compiled app binary or browser dev tools/network inspector, since these are fundamentally untrusted, user-controlled execution environments. Once leaked, anyone possessing that secret could impersonate the client and obtain tokens with its full authorized scope — a serious compromise. This is precisely why Client Credentials is reserved for genuinely confidential clients (backend services, server-side applications) that run in environments the organization fully controls and can keep secrets in, and why user-facing public clients need the fundamentally different Authorization Code flow (with PKCE, discussed in topic 195) instead.

Securing Gateway Server Using Client Credentials Grant Type Flow — Theory

Applying the flow concretely to this course's own system.

Any caller wanting to hit the Gateway must first independently obtain an access token from Keycloak using the Client Credentials flow (presenting its own registered client_id/secret), then include that token as a Bearer token on every request to the Gateway. The Gateway, configured as an OAuth2 Resource Server (topics 191-192), validates the token's signature and claims before allowing the request to proceed to routing at all — an unauthenticated or invalid-token request is rejected right at the edge, never reaching Accounts, Loans, or Cards.

Caller
1. get token →
Keycloak
2. token →
Caller
3. Bearer token →
Gateway (Resource Server)
validates before routing
4. only if valid →
Accounts/Loans/Cards
What role does the Gateway play once secured as a Resource Server?

It validates every incoming request's access token (signature and claims) before allowing routing to internal services — an unauthenticated or invalid request is rejected at the Gateway itself, never reaching Accounts, Loans, or Cards.

Does token acquisition and token validation need to happen through the same request path, or are these genuinely separate transactions?

Genuinely separate — token acquisition (the caller obtaining a token from Keycloak) is a completely independent transaction from token usage (the caller presenting that already-obtained token to the Gateway on a subsequent, separate API call). The caller typically acquires a token once and reuses it across many subsequent API calls until it expires, rather than fetching a fresh token before every single request — an important operational detail, since re-authenticating with Keycloak on every API call would add unnecessary latency and load to the Authorization Server for no security benefit, given the token itself already carries verifiable proof of authorization for its full validity window.

Setup of Auth Server Using KeyCloak

Getting Keycloak running, and the concept of a Realm.

docker run — Keycloak
$ docker run -p 7080:8080 \
    -e KEYCLOAK_ADMIN=admin \
    -e KEYCLOAK_ADMIN_PASSWORD=admin \
    quay.io/keycloak/keycloak:latest start-dev

Realms — Keycloak's tenant isolation concept

A Realm is an isolated namespace within Keycloak — its own set of clients, users, roles, and configuration, completely separate from any other realm on the same Keycloak instance. This is directly analogous to a multi-tenant system's tenant isolation: one Keycloak deployment can serve entirely separate applications/organizations (or separate environments — dev/staging/prod) without their clients or users ever mixing. For this course, a dedicated realm (e.g. `eazybank`) is created to hold everything specific to this system.

What is a Keycloak Realm?

An isolated namespace within a Keycloak instance, containing its own set of clients, users, roles, and configuration — completely separate from any other realm on the same instance.

Would you use separate realms for dev/staging/prod, or separate Keycloak deployments entirely?

Both patterns are used in practice, with different trade-offs: separate realms on one shared Keycloak deployment reduce infrastructure overhead (one system to operate) and are simpler for smaller teams, but mean a Keycloak-level outage or misconfiguration risks affecting every environment simultaneously, and it requires careful realm-level access control to prevent, say, a developer with staging-realm access from accidentally touching production realm configuration. Fully separate Keycloak deployments per environment (a common pattern for anything security-sensitive, like a production identity system) provide genuine blast-radius isolation — a staging environment issue can never affect production's actual identity infrastructure at all — at the cost of more infrastructure to operate and keep configuration consistent across. For genuinely production, security-critical identity infrastructure, most mature organizations lean toward separate deployments (or at minimum, very strong access boundaries) for production specifically, even if lower environments share more.

Confidential vs public clients — a distinction worth being precise about

A confidential client can securely store a secret (e.g. a backend service) and is required for flows like Client Credentials. A public client (a browser SPA or mobile app) can't securely hold a secret and needs a different flow — Authorization Code with PKCE — designed for that constraint.

What security practice should govern how a client_secret is actually stored and injected into the calling application, once generated?

Never hardcoded into source code or committed to version control — this is exactly the secrets-management discipline covered back in Section 6 (Spring Cloud Config's encryption support, or an external secrets manager) applied here to an OAuth2 client secret specifically. The secret should be injected at deploy time via an environment variable or a dedicated secrets manager, exactly the same pattern used for database credentials throughout this course, and ideally rotated periodically — a leaked client_secret is functionally equivalent to an attacker being able to impersonate that client and obtain valid, fully-authorized access tokens at will, a serious compromise worth treating with the same operational rigor as any other production credential.

JWT structure — header.payload.signature

The returned access token is a JWT (JSON Web Token): three base64url-encoded segments separated by dots — a header (algorithm/key metadata), a payload (the claims shown above), and a signature (cryptographically signed by Keycloak's private key). Crucially, JWTs are self-contained and independently verifiable — a resource server can validate a JWT's signature (using Keycloak's public key, fetched from a standard JWKS endpoint) entirely on its own, without needing to call back to Keycloak on every single request.

This "stateless validation" property is a genuinely important architectural fact

Unlike an opaque token (a random-looking string with no embedded meaning, which requires the resource server to call an introspection endpoint on the Authorization Server for every single validation), a JWT lets the Gateway validate tokens locally and independently — fast, no extra network round-trip per request, no added load on Keycloak proportional to API traffic. The trade-off: since validation is local and doesn't consult Keycloak live, a JWT can't be instantly revoked before its natural expiration — this specific trade-off is a very common, precise follow-up question.

What are the three parts of a JWT?

Header (algorithm/key metadata), payload (the claims — identity/authorization information), and signature (cryptographic proof the token hasn't been tampered with), each base64url-encoded and separated by dots.

Why can a resource server validate a JWT without calling back to the Authorization Server?

Because a JWT's signature can be independently verified using the Authorization Server's public key (fetched once from a standard JWKS endpoint) — the token is self-contained proof, so validation is a local cryptographic check, not a live network call to Keycloak on every request.

Given that JWTs can't be instantly revoked, how would you handle needing to immediately invalidate a compromised token or a terminated user's access?

Several complementary mitigations, none of which fully restore instant revocation without giving up JWT's stateless-validation benefit entirely: (1) keep access token lifetimes genuinely short (minutes, not hours) so any compromise has a small, bounded window regardless — the primary, simplest mitigation; (2) maintain a server-side token blocklist/denylist for genuinely urgent revocations (a compromised token, an immediately-terminated employee) that the resource server checks in addition to signature validation — this sacrifices some of the "no extra lookup needed" benefit specifically for the rare urgent-revocation case, rather than for every request; (3) for the refresh token specifically (which is typically opaque/checked against the Authorization Server, not a self-contained JWT in many implementations), revoking it prevents obtaining any *new* access tokens going forward, even though already-issued access tokens remain valid until their own natural, short expiry. Explicitly weighing "instant revocability" against "stateless validation performance" as a genuine trade-off — rather than claiming JWTs are either strictly better or strictly worse than opaque tokens — is exactly the kind of nuanced answer that distinguishes strong candidates on this specific, frequently-asked question.

What is a JWKS endpoint, and why does the resource server need to fetch keys from it rather than hardcoding Keycloak's public key?

JWKS (JSON Web Key Set) is a standardized endpoint (part of the OIDC discovery mechanism, typically at `/realms/{realm}/protocol/openid-connect/certs`) exposing the Authorization Server's current public signing key(s) in a standard format. Fetching keys dynamically from this endpoint — rather than hardcoding a specific public key value into the resource server's configuration — allows the Authorization Server to rotate its signing keys periodically (a security best practice, limiting the impact if a private signing key were ever somehow compromised) without requiring every resource server across the organization to be manually reconfigured with a new hardcoded key every time rotation happens; resource servers typically cache the JWKS response but refresh it periodically or when they encounter a token signed with a key ID (`kid` in the JWT header) they don't currently recognize, seamlessly picking up newly-rotated keys.

This is a good example of a security configuration choice that's correct because of specific architectural context (stateless token auth) rather than a universally-safe default, and articulating that reasoning explicitly is a stronger interview answer than just stating the config is fine.

Implementing Authorization Inside Gateway Server Using Roles

@Bean
public SecurityWebFilterChain securityWebFilterChain(
        ServerHttpSecurity serverHttpSecurity) {

        .authorizeExchange(exchange -> exchange

private Converter<Jwt, Mono<AbstractAuthenticationToken>> grantedAuthoritiesExtractor() {
    var jwtAuthenticationConverter = new JwtAuthenticationConverter();
    jwtAuthenticationConverter.setJwtGrantedAuthoritiesConverter(new KeycloakRoleConverter());
    return new ReactiveJwtAuthenticationConverterAdapter(jwtAuthenticationConverter);
}

// KeycloakRoleConverter reads realm_access.roles from the JWT claims
// and maps each role into a Spring Security GrantedAuthority,
// prefixed "ROLE_" so hasRole("ACCOUNTS") correctly matches "ROLE_ACCOUNTS"

Why a custom converter is needed at all

Keycloak embeds roles inside the JWT under a Keycloak-specific claim structure (`realm_access.roles`, an array), which doesn't match Spring Security's default expectation for where authorities live in a JWT. A custom Converter bridges this gap — extracting Keycloak's specific claim structure and mapping each role string into a proper Spring Security GrantedAuthority (conventionally prefixed ROLE_, which is what makes .hasRole("ACCOUNTS") — which implicitly checks for `ROLE_ACCOUNTS` — actually work correctly).

This is genuinely a common, specific integration gotcha worth knowing by name

Spring Security's OAuth2 Resource Server support is written generically to work with any OIDC-compliant provider, but different Authorization Servers structure their role/authority claims differently in the JWT payload — what works out-of-the-box for one IAM provider's token structure often doesn't for another's, and Keycloak's `realm_access.roles` nesting specifically requires this custom converter. Encountering `hasRole(...)` checks silently always failing/denying, despite a token that clearly contains the expected role when manually decoded, is a very plausible real debugging scenario this custom converter directly explains.

Why is a custom JWT authorities converter needed when integrating Keycloak with Spring Security?

Keycloak embeds roles under its own specific claim structure (`realm_access.roles`), which doesn't match Spring Security's default expectations for where authorities live in a JWT — the custom converter extracts Keycloak's claim structure and maps each role into a proper Spring Security GrantedAuthority.

Why does the converter prefix roles with "ROLE_"?

Because Spring Security's `hasRole("ACCOUNTS")` check conventionally looks for an authority named `ROLE_ACCOUNTS` internally — without the prefix being applied during conversion, role checks would silently fail to match even if the underlying role data is otherwise correct.

Should role checks like hasRole("ACCOUNTS") be based on realm-level roles or client-specific roles in Keycloak, and what's the difference?

Keycloak supports both realm roles (global to the whole realm, embedded under `realm_access.roles`, as used in this example) and client roles (scoped to a specific registered client, embedded under `resource_access.{client_id}.roles`) — the choice matters architecturally: realm roles are appropriate for genuinely cross-cutting permission concepts shared meaningfully across multiple clients/applications in the realm, while client roles are better for permissions genuinely specific to one particular application's own authorization model, keeping that application's role vocabulary from polluting the shared realm-wide namespace. For a system like this course's, where roles like ACCOUNTS/LOANS/CARDS are specifically about which Gateway route a caller can access — arguably a Gateway-specific authorization concern rather than a realm-wide identity concept — a case could be made either way depending on whether other clients in the realm would ever meaningfully care about these same role names; this is a genuine design decision worth being able to discuss with reasoning rather than a single universally-correct answer.

Deep Dive of Authorization Code Grant Type Flow

The gold-standard flow for real end users — significantly more involved than Client Credentials, deliberately so.

When this flow applies

Used whenever a real human resource owner is involved — logging into a web application, a mobile app, any user-facing "Sign in" experience. Unlike Client Credentials, this flow requires the user to actively authenticate (and consent) via a browser redirect to the Authorization Server directly — the client application itself never sees the user's actual password.

User's browser
1. redirect to /authorize →
Keycloak login page
User authenticates + consents
2. redirect back with code →
Client's redirect_uri
Client backend
3. exchange code (back-channel) →
Keycloak /token endpoint
4. access + refresh + ID token →
Client backend
  1. The client redirects the user's browser to the Authorization Server's `/authorize` endpoint, including its `client_id`, requested `scope` (including `openid` for OIDC), and a `redirect_uri`.
  2. The user authenticates directly with Keycloak (enters credentials on Keycloak's own login page — the client application never sees the password) and, if required, explicitly consents to the requested scopes.
  3. Keycloak redirects the browser back to the client's `redirect_uri`, appending a short-lived, single-use authorization code as a query parameter.
  4. The client's backend (not the browser) exchanges this code — along with its own `client_id`/`client_secret` — for tokens at Keycloak's `/token` endpoint, a direct back-channel server-to-server request.
  5. Keycloak returns an access token, refresh token, and (since `openid` scope was requested) an ID token.

Why the extra "code" indirection step exists — the single most important nuance of this flow

A simpler-seeming design might have Keycloak redirect the browser directly back with the access token itself attached to the URL. This was actually an earlier, now-deprecated OAuth2 flow (the "Implicit" grant) — and it's insecure specifically because browser URLs are a leaky channel: they can appear in browser history, get logged by web servers/proxies along the redirect chain, leak via the `Referer` header to any third-party resources the page subsequently loads, and are visible to any browser extension. The Authorization Code flow instead puts only a short-lived, single-use code — not the actual token — through this leaky browser channel; the real token exchange happens over a secure, direct back-channel connection between the client's backend and Keycloak, a channel never exposed to the browser or any of those leak vectors at all.

PKCE — the extension that makes this flow safe for public clients too

PKCE (Proof Key for Code Exchange) extends this flow specifically for public clients (mobile apps, browser SPAs) that can't securely hold a `client_secret` at all. The client generates a random secret (`code_verifier`) locally, sends a hashed version (`code_challenge`) with the initial authorization request, and must present the original `code_verifier` when exchanging the authorization code for a token — meaning even if the authorization code itself were somehow intercepted mid-flow, an attacker without the original `code_verifier` (which never left the legitimate client) couldn't complete the exchange. PKCE is now recommended for confidential clients too, as defense-in-depth, not just public ones.

Why does the Authorization Code flow redirect back with a code instead of the access token directly?

Because browser URLs are a leaky channel (browser history, server logs, Referer headers, browser extensions) — putting a short-lived, single-use code through that channel instead of the actual token, then exchanging that code for the real token over a secure server-to-server back-channel, keeps the actual token out of the leaky browser-facing path entirely.

What is PKCE, and why is it needed?

Proof Key for Code Exchange — an extension letting public clients (mobile apps, browser SPAs, which can't securely hold a client secret) safely use the Authorization Code flow, by requiring the client to prove it's the same entity that initiated the flow via a locally-generated secret (code_verifier/code_challenge pair) rather than relying on a client_secret.

Why was the older Implicit grant deprecated, and what specifically made it insecure compared to Authorization Code?

The Implicit grant returned the access token directly in the browser redirect URL fragment, skipping the code-exchange step entirely — meaning the actual, usable access token itself was exposed to every leaky channel a URL passes through (browser history, potentially server/proxy logs depending on configuration, browser extensions with URL access, and in some cases the Referer header if not carefully handled). Beyond exposure risk, the Implicit grant also had no secure mechanism to verify the token wasn't intercepted or substituted in transit, and typically didn't support refresh tokens safely (since a public client receiving a long-lived refresh token directly via a leaky browser channel would compound the exposure risk significantly). The Authorization Code flow (with PKCE for public clients) is now the universally recommended replacement — OAuth2 security best-practice guidance (RFC 8252 and the OAuth 2.0 Security Best Current Practice document) formally deprecates the Implicit grant for exactly these reasons.

Walk through exactly why PKCE's code_verifier/code_challenge mechanism defeats an authorization code interception attack.

Without PKCE, if an attacker could somehow intercept the authorization code as it's redirected back to the client (e.g. via a malicious app registering the same custom URL scheme on a mobile device, a documented real attack vector for mobile OAuth2 flows), they could exchange that intercepted code for a real access token themselves, since the code alone was sufficient. With PKCE: the legitimate client generates a random `code_verifier`, computes a hash of it (`code_challenge`), and sends only the hash with the initial authorization request — Keycloak stores this hash, associated with the eventual authorization code it issues. When exchanging the code for a token, the client must supply the original, unhashed `code_verifier`; Keycloak re-hashes it and confirms it matches the `code_challenge` stored earlier for that specific code. An attacker who intercepted only the authorization code (not the original `code_verifier`, which never left the legitimate client's memory) cannot produce a matching `code_verifier`, so the token exchange fails even with a valid, intercepted code in hand — the code alone is no longer sufficient, which is precisely what closes this specific attack vector.

Securing Gateway Server Using Authorization Code Grant Type Flow — Theory

Applying the flow to a genuine user-facing scenario in this course's system.

For an actual eazybank customer logging into a web or mobile front-end, the Authorization Code flow (not Client Credentials) is the correct choice — a real resource owner is involved, and their credentials must never be handled directly by the client application. The front-end client redirects to Keycloak's login page, the customer authenticates, and the resulting access token (carrying the customer's own identity and role claims) is what gets presented to the Gateway on subsequent API calls — the same Resource Server validation logic from topics 191-194 applies unchanged, since from the Gateway's perspective, a valid JWT is a valid JWT regardless of which grant type originally produced it.

Why the Gateway-side code doesn't need to change between the two flows

This is a genuinely elegant property worth calling out explicitly: the Resource Server configuration built in topics 191-194 validates JWTs based on their signature, issuer, and claims — it has no awareness of, or dependency on, which specific grant type produced the token in the first place. Whether a token arrived via Client Credentials (topic 190) or Authorization Code (this flow), the Gateway's validation and role-based authorization logic works identically, unchanged.

Does the Gateway's Resource Server configuration need to change depending on which grant type produced the token?

No — the Gateway validates JWTs based on signature, issuer, and claims, independent of which grant type originally produced the token; the same Resource Server config works identically for tokens from either Client Credentials or Authorization Code flows.

If both a machine client (via Client Credentials) and a real user (via Authorization Code) can obtain tokens that pass the same Gateway validation, how would the Gateway or downstream services distinguish "this is a service acting on its own behalf" from "this is a request on behalf of a specific user"?

By inspecting specific claims within the validated JWT itself — the `sub` (subject) claim differs meaningfully between the two cases (a service-account identifier like `service-account-eazybank-client` for Client Credentials tokens, versus an actual user ID for Authorization Code tokens), and the `azp` (authorized party) claim identifies which client obtained the token. Downstream business logic that needs to behave differently depending on whether a request is genuinely user-initiated versus system-initiated (e.g. an audit log wanting to record "which human customer initiated this" versus "this was an automated batch process") would inspect these specific claims rather than assuming all validated tokens represent the same kind of caller — a good illustration that "the token is valid" and "who/what does this token actually represent" are related but distinct questions worth answering explicitly in code that cares about the difference.

Why "Valid redirect URIs" being an explicit, tightly-scoped allow-list matters so much

If Keycloak allowed redirecting to any URI a request happened to specify, an attacker could craft a malicious authorization request specifying their own server as the `redirect_uri` — tricking a user into authenticating through a legitimate-looking flow, only for the resulting authorization code (or, in some historical misconfigurations, even the token) to be delivered straight to the attacker's server instead of the legitimate application. This exact class of vulnerability (open redirect in OAuth2 flows) is a real, well-documented attack pattern — configuring a tight, explicit allow-list of legitimate redirect URIs (never a wildcard in production) is a genuinely load-bearing security control, not a minor configuration detail.

What Keycloak setting specifically enables the Authorization Code grant type, distinct from Client Credentials?

"Standard flow enabled" — a different toggle from "Service accounts roles" (which enables Client Credentials), reflecting that these are genuinely different grant types with independently configurable support per client.

Why does this flow require an actual end user to exist in Keycloak, unlike Client Credentials?

Because a real resource owner is involved in this flow — the user must actually authenticate with their own credentials against Keycloak's login page, so a genuine user account (username/password, assigned roles) needs to exist to test and use this flow, unlike Client Credentials which uses an automatically-generated internal service account representing the client itself.

Why is a wildcard or overly permissive redirect_uri configuration considered a serious vulnerability, specifically?

It enables an open-redirect-style attack against the OAuth2 flow itself — an attacker crafts an authorization request specifying their own malicious server as the `redirect_uri`; if Keycloak doesn't strictly validate this against a pre-registered allow-list, it will happily redirect the user's browser (post-authentication) to the attacker's server with the authorization code attached, letting the attacker complete the code-exchange themselves and obtain a valid access token representing the victim's identity — effectively account takeover, despite the user having "correctly" authenticated with their real credentials at the legitimate Keycloak login page the whole time. This is precisely why strict redirect URI validation is called out explicitly in OAuth2 security best-practice guidance as a mandatory control, not an optional hardening step — it's one of the most consequential single misconfigurations possible in an OAuth2 deployment.

What's the purpose of the state parameter in the Authorization Code flow?

A random value generated by the client and verified on the redirect back, protecting against CSRF attacks against the OAuth2 flow itself — ensuring the authorization response actually corresponds to a request this specific client genuinely initiated.

Which three tokens are typically present in the final token response for this flow, and why?

What would go wrong if a client skipped validating the state parameter on the redirect back?
