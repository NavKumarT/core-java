Introduction to Helm & the Problems It Solves

What Helm is, the vocabulary (chart, release, repository, values), how it works internally, and why Section 14’s hand-written manifests needed it.

The problem recap (from Section 14)

To run EazyBank on Kubernetes we wrote a Deployment, Service and ConfigMap entries per microservice — Config Server, Eureka, Accounts, Loans, Cards, Gateway. They were ~90% identical. Now imagine three environments (dev, QA, prod) with different replica counts, image tags, profiles and Service types, plus third-party software (Keycloak, Kafka, Prometheus, Grafana) that you would otherwise have to write hundreds of YAML lines for. Hand-managed YAML does not scale. Helm is the standard answer.

What is Helm?

Helm is the package manager for Kubernetes. Just as apt/yum install software on Linux, npm installs JS libraries and Maven pulls Java dependencies, Helm packages, versions, shares, installs, upgrades and removes Kubernetes applications. It is a CNCF graduated project. It does two jobs: (1) a templating engine that generates Kubernetes YAML from reusable templates plus values, and (2) a release manager that tracks what was installed and enables upgrade, rollback and uninstall as a single unit.

  • Helm 3 is client-only. There is no server component. Helm 2 had Tiller, a privileged in-cluster server that was a security risk and was removed in Helm 3.
  • The CLI renders templates on your machine, then sends the resulting manifests to the Kubernetes API using your kubeconfig and RBAC permissions.

Helm 3 vs Helm 4

Helm 4 was released on 12 Nov 2025 and Helm 3 is on a path to end-of-life. Charts written for Helm 3 (apiVersion: v2) are expected to keep working, and Helm 4 can manage existing Helm 3 releases without a migration step. Notable Helm 4 changes: Server-Side Apply for new releases (existing releases keep their original apply method), a redesigned plugin system (WebAssembly), better readiness/status waiting, and flag renames (--atomic → --rollback-on-failure, --force → --force-replace; old flags still work with a deprecation warning). Everything in this section applies to both; differences are called out where relevant.

Mental model

Chart + Values = Release. A chart is the class; a release is an instance; values are constructor arguments.

What is Helm?

The package manager for Kubernetes. It packages Kubernetes manifests as charts, lets you configure them with values, and manages installs, upgrades, rollbacks and uninstalls as releases.

What is a Helm chart?

A package containing templated Kubernetes manifests, default values and metadata (Chart.yaml) that together describe an application or a component.

What is a release?

A deployed instance of a chart in a cluster, identified by a release name, with a revision history. Installing the same chart twice with different names creates two independent releases.

What problems does Helm solve compared to plain kubectl and YAML?

Eliminates duplicated manifests via templating, handles multiple environments through values, versions and distributes applications as packages, and provides lifecycle commands (upgrade, history, rollback, uninstall) that treat many resources as one unit.

What is Tiller and why was it removed?

Tiller was Helm 2’s in-cluster server component that executed releases with broad privileges, creating a security risk and RBAC complexity. Helm 3 removed it: the client talks directly to the API server with the user’s own permissions.

Where does Helm store release information?

In the cluster, as Kubernetes Secrets (type helm.sh/release.v1) in the release’s namespace, one per revision. (ConfigMap and SQL storage drivers also exist.)

How does Helm differ from just using kubectl apply with templated YAML (envsubst, sed)?

Helm adds a real templating language with functions and control flow, a packaging/versioning/dependency model, and — critically — release tracking: it knows which resources belong to which release, stores history, can diff, upgrade, roll back and cleanly uninstall everything it created. kubectl apply has no notion of “the application as a unit”, so deletions of removed resources and rollbacks are manual.

Explain how Helm computes what to change on helm upgrade.

In Helm 3 it used a three-way strategic merge patch comparing the previous release manifest, the live cluster state and the new manifest, so manual edits to live objects are preserved where not otherwise changed. Helm 4 uses Server-Side Apply for new releases (field-ownership based) while existing Helm 3 releases keep client-side apply on upgrade unless you explicitly opt in.

What are the security implications of Helm?

Charts can create any resource, including RBAC and privileged Pods, so you must treat third-party charts as code: review templates (helm template), pin versions, verify provenance (helm verify with signatures, OCI digests), scan rendered manifests, and install with least-privilege kubeconfig. Release Secrets contain rendered values, which may include sensitive data, so restrict access to them.

When would you choose Kustomize or plain manifests instead of Helm?

For small, internal apps where per-environment changes are a handful of patches; when you want to avoid a templating language; or when the platform already standardises on Kustomize/GitOps. Helm shines when distributing reusable software or when parametrisation is extensive. Many teams combine them (Helm output post-processed by Kustomize, or Argo CD rendering Helm).

Is Helm a deployment orchestrator that waits for dependencies?

Not by default. Helm applies resources and (with --wait) can wait for readiness, but ordering is limited to resource-kind install order and hooks. Application-level dependency ordering must still be handled via readiness probes, retries and init containers, as in Section 14.

Wrong cluster

Because Helm silently follows your current kube context, running helm upgrade on the wrong context is as dangerous as with kubectl. Always check kubectl config current-context, or pass --kube-context explicitly in scripts.

How do you install Helm?

Via a package manager (brew install helm, choco install kubernetes-helm, apt/snap) or the official install script, then verify with helm version.

Does Helm need anything installed in the cluster?

No. Helm 3+ is purely a client binary that talks to the Kubernetes API using your kubeconfig. No Tiller or other server component is needed.

How does Helm know which cluster to deploy to?

It reads the same kubeconfig and current context as kubectl; override with --kube-context, --kubeconfig and -n/--namespace.

What does helm env show?

The environment Helm will use: config/cache/data directories, the default namespace, kube context, storage driver and related settings.

What permissions does Helm need?

Whatever the user’s kubeconfig is allowed to do — Helm creates the resources in the chart and the release Secrets in the target namespace, so the account needs RBAC for those kinds.

How would you run Helm safely in CI/CD?

Use a dedicated ServiceAccount or short-lived OIDC credentials with namespace-scoped RBAC, pin the Helm version, pass explicit --kube-context/--namespace, use helm upgrade --install --atomic/--rollback-on-failure --wait --timeout, store values in Git and secrets in an external manager, and run helm lint and helm template | kubeconform before deploying.

Which release storage backends exist and why would you change the default?

Secrets (default), ConfigMaps, and SQL (PostgreSQL). Secret storage is namespace-local and RBAC-controlled. SQL storage helps when release history exceeds the 1 MiB object limit of etcd objects or for very large clusters, at the cost of an external dependency.

What problems arise from Helm version/Kubernetes version mismatch?

The client may use removed API versions or lack features for newer clusters, causing failures such as “no matches for kind” or deprecated-API warnings. Follow Helm’s version support matrix and test charts against the target Kubernetes version using --kube-version with helm template.

IMPORTANT: Bitnami Images & Helm Charts Change

The course installs several apps (Keycloak, Kafka, etc.) from Bitnami charts. Bitnami’s free distribution changed in 2025; this is what to know and how to keep the labs working.

What happened

  • Background: Bitnami (owned by Broadcom) published a huge catalogue of container images (docker.io/bitnami/*) and Helm charts (charts.bitnami.com/bitnami, and OCI docker.io/bitnamicharts/*) that most tutorials, including this course, relied on.
  • 28 Aug 2025 onward: Bitnami stopped publishing the full free catalogue. A limited set of hardened images stays in the public “mainline” repo (mostly latest only). Production-grade, versioned images and charts moved under the paid Bitnami Secure Images offering.
  • Legacy archive: existing versioned images were copied to docker.io/bitnamilegacy/* and no longer receive updates. Removal from docker.io/bitnami was postponed and completed around 29 Sep 2025.
  • Source code of the charts on GitHub (bitnami/charts) remains open (Apache 2.0); what changed is the free availability of built artifacts and images.
  • Effect: a chart that still points at docker.io/bitnami/<app>:<version> can fail with ImagePullBackOff / “manifest unknown”.
Verify current status

This area is changing. Before relying on any workaround below, check the Bitnami announcement (github.com/bitnami/charts issue #35164) and the chart’s current values.yaml.

The bigger lesson (great interview material)

  • Supply-chain risk: your deployment depended on a third party’s free artifacts. Pin chart and image versions (even digests), and mirror critical images/charts into a registry you control.
  • Never use latest or unpinned dependencies in production.
  • Prefer upstream project-maintained charts/operators for critical infrastructure.
  • Treat third-party charts as code you review: helm template, scan images (Trivy, Grype), review RBAC.
Why do Bitnami charts fail to install in many tutorials now?

Because the versioned images they reference under docker.io/bitnami were moved to bitnamilegacy (or behind the paid Bitnami Secure Images) after Aug–Sep 2025, so the pulls fail.

How can you make a Bitnami chart work for a local lab?

Override the image repository to the bitnamilegacy namespace (and allow it with the chart’s allow-insecure-images global flag where needed). Accept that those images are frozen and unpatched.

Are the Bitnami charts’ source code still open?

Yes, the chart source in the bitnami/charts GitHub repo remains Apache-2.0; what changed is free publication of built images and packaged charts.

What are alternatives to Bitnami charts?

Upstream/vendor charts and operators (Strimzi for Kafka, Keycloak Operator, prometheus-community/*, grafana/*), or self-built mirrored images and charts.

What does this teach about dependency management in Kubernetes platforms?

Public artifact registries can change terms or disappear. Mitigate with version pinning, digest pinning, a private mirror/proxy cache (Harbor, Artifactory, ECR pull-through), SBOMs and image scanning, and by preferring community- or vendor-maintained upstream artifacts over redistributed ones.

How would you migrate a production system off Bitnami charts with minimal risk?

Inventory all charts and images in use; mirror current versions into your registry; switch image references to the mirror (no behaviour change); then plan per-component migration to an upstream chart/operator, testing data migration (backup/restore), values mapping and rollback in staging; do it one component at a time behind change control.

How do you verify what images a chart will deploy before installing?

helm template the chart with your values and grep for image:; or helm show values to see image defaults; scan with Trivy; compare to what is allowed by admission policy (Kyverno/Gatekeeper image allow-lists).

How do you install a chart from a repository?

Add the repo (helm repo add), update (helm repo update), then helm install <release-name> <repo>/<chart>, optionally with -f values.yaml or --set.

How do you see which values a chart supports?

helm show values <chart> (and helm show readme). The default values.yaml documents every option.

How do you override values at install time?

With --set key=value or one or more -f myvalues.yaml files; later files and --set override earlier ones and the chart defaults.

What does helm list show?

Releases in the current namespace with name, namespace, revision, updated time, status and chart/app version. Use -A for all namespaces and --uninstalled/--failed filters.

What is helm search hub vs helm search repo?

hub searches Artifact Hub across public charts without adding a repo; repo searches only repos you added locally.

How do you see exactly what Helm deployed?

helm get manifest <release> for the applied YAML and helm get values for values; helm status for current state and notes.

What is the difference between --dry-run and helm template?

helm template renders locally with no cluster connection (so .Capabilities and lookup are defaults/empty). install --dry-run goes through the install pipeline, optionally contacting the API server (--dry-run=server in newer versions) so it validates against real API versions and can trigger lookups; it also shows hooks and notes.

Why might helm install succeed but the app still be broken?

Helm only confirms the API server accepted the resources unless you pass --wait (and even then only waits for Pod readiness). Misconfigured probes, crashing Pods, bad config or missing dependencies still show up later. Use --wait --timeout and --atomic/--rollback-on-failure in CI to get fail-fast, auto-reverting installs.

How do you pin a chart for reproducible deployments?

Pin --version (or the dependency version in Chart.yaml and commit Chart.lock), pin image tags/digests in values, and for OCI charts reference a digest. Avoid floating ranges and latest.

How do you inspect a third-party chart for risk before installing?

helm pull --untar and read templates; helm template with your values and review RBAC, privileged settings, hostPath, images; scan with kubeconform, Trivy/Checkov/kube-score; verify signature with helm verify if provenance files exist.

Packaging flow

What is the structure of a Helm chart?

Chart.yaml (metadata), values.yaml (defaults), templates/ (manifests and helpers), plus optional charts/ (dependencies), crds/, NOTES.txt, values.schema.json, .helmignore and tests.

What is the difference between version and appVersion in Chart.yaml?

version is the chart’s own SemVer version and must change when the chart changes; appVersion is the version of the packaged application and is informational.

What is _helpers.tpl?

A file for reusable named templates and functions (e.g. labels, resource names). Files beginning with an underscore are not rendered as Kubernetes manifests.

What is NOTES.txt?

A templated text file printed after install/upgrade to show the user instructions such as how to access the app.

What does helm create do?

Scaffolds a new chart with sample Deployment, Service, Ingress, ServiceAccount, helpers and tests that you can adapt.

What does helm lint do?

Statically checks a chart for syntax problems and best-practice violations without installing it.

What is a library chart and when do you use it?

A chart with type: library that exposes named templates but renders no resources itself and cannot be installed. You use it to share boilerplate (Deployment/Service/ConfigMap templates) across many service charts so each service only supplies values.

How does Helm treat CRDs in the crds/ directory?

They are installed before other resources on helm install but are never upgraded or deleted by Helm because that is risky (deleting a CRD deletes all its custom resources). If you need lifecycle management, ship CRDs in a separate chart, via templates with care, or manage them with GitOps.

What is values.schema.json and why use it?

A JSON Schema validating the final merged values (required keys, types, enums, ranges). Helm enforces it on install, upgrade, lint and template, giving early, clear errors instead of cryptic template failures.

Explain Chart.lock and helm dependency build vs update.

update resolves dependency version ranges from Chart.yaml, downloads them into charts/ and rewrites Chart.lock. build rebuilds charts/ from the existing lock file for reproducible builds. Use build in CI.

Helm’s templating language (Go templates + Sprig functions) from first principles, with a real Deployment template.

How rendering works

Each file in templates/ is a Go template. Anything inside {{ … }} is evaluated against a data structure; everything else is copied verbatim. After rendering, the output must be valid Kubernetes YAML. Helm also bundles Sprig (~70 helper functions) and a few Helm-specific ones (include, toYaml, required, tpl, lookup).

include vs template

template is a built-in action whose output goes straight into the document and cannot be piped. include is a Helm function returning a string, so you can pipe it to indent/nindent/quote. Always prefer include.

The classic YAML indentation bugs

1) Forgetting nindent after toYaml, producing mis-indented blocks. 2) Using {{ }} where {{- }} is needed, leaving blank lines or joining lines. 3) Unquoted values that YAML reinterprets ("true", "08080", no) — use quote. 4) Numeric-looking strings passed with --set become numbers. Debug with helm template --debug and helm lint.

Workflow

Scaffold with helm create, delete what you do not need, template only what actually varies, run helm lint and helm template after every change, then install into a scratch namespace.

What templating engine does Helm use?

Go’s text/template extended with the Sprig function library and Helm-specific functions such as include, toYaml, required, tpl and lookup.

What are .Values, .Release and .Chart?

Built-in objects: .Values is the merged configuration; .Release holds release info (name, namespace, revision, install/upgrade flags); .Chart exposes Chart.yaml fields.

What does {{- … -}} do?

The dashes trim whitespace (including newlines) before/after the action, which is essential to produce correctly indented YAML.

How do you set a default value in a template?

Pipe through default: {{ .Values.replicaCount | default 1 }}.

How do you loop over a map or list in a template?

{{ range $key, $value := .Values.env }}…{{ end }} for maps; {{ range .Values.items }} for lists.

How do you make a value mandatory?

required "message" .Values.x aborts rendering with the message if it is empty; or use values.schema.json.

include vs template — why does it matter?

include returns a string that can be piped (e.g. | nindent 4, | sha256sum), while template writes directly to output and cannot be post-processed. Because YAML is indentation-sensitive, include … | nindent is the idiomatic way to embed shared snippets.

How would you roll Pods automatically when a ConfigMap in the chart changes?

Add a Pod-template annotation with the hash of the rendered ConfigMap: checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}. Changing the ConfigMap changes the annotation, which changes the Pod template and triggers a rolling update, solving the “env vars don’t update” issue from Section 14.

What is the scope problem inside range and with and how do you solve it?

Inside those blocks . is rebound to the current element, so .Release or .Values no longer resolve. Use $ (root context) such as $.Release.Name, or assign variables before entering the block.

Why is lookup returning empty with helm template?

helm template runs without a cluster connection, so lookups return empty maps. It works during real install/upgrade (and server-side dry runs). Charts relying on lookup (e.g. reusing an existing Secret to avoid regenerating passwords) must handle the empty case.

How do you generate a random password safely in a chart?

randAlphaNum regenerates on every upgrade, which would rotate the password. Combine with lookup to reuse an existing Secret value if present, or require the user/external secret manager to supply it.

How the pieces connect

  • Named templates are global across a chart and all its dependencies: a template defined in a subchart is callable from the parent with include/template.
  • The caller passes . (its own context), so .Values inside the shared template refers to the calling chart’s values. That is how one template produces different output per service.
  • repository: file://../eazybank-common is a local path dependency; after helm dependency build/update it is vendored into charts/ as a .tgz.
  • Feature switches (config_enabled, if blocks) make one template cover services that differ (Config Server has no config import; Gateway needs a LoadBalancer; Eureka has no Eureka client).
Naming collisions

Named templates share one global namespace. Always prefix names with the chart (common.deployment, not deployment) or two charts defining the same name silently override each other.

Forgot to rebuild

If you change the common chart but don’t re-run helm dependency build/update, each service still bundles the old copy in charts/. CI should always rebuild dependencies before packaging.

Library chart vs normal chart as a dependency

A type: library chart renders nothing on its own; a normal application chart used as a dependency also installs its own resources. For purely shared templates, use library type.

How do you avoid duplicating templates across many microservice charts?

Create a common (library) chart containing named templates (define) and have each service chart declare it as a dependency and call include "common.deployment" ., supplying only its own values.

What is a named template?

A reusable template block declared with {{ define "name" }}…{{ end }}, typically in _helpers.tpl or _*.tpl files, invoked with include or template.

How is a dependency declared and fetched?

In Chart.yaml under dependencies (name, version, repository); fetched with helm dependency update (resolve + lock) or helm dependency build (from lock).

What does file://../eazybank-common mean?

A dependency whose repository is a local directory relative to the chart, handy for monorepos. Helm packages it into the parent’s charts/ directory.

How does the shared template know each service’s values?

Because the service passes its context (.) when including the template, so .Values inside refers to the calling chart’s merged values.

Library chart vs copy-paste vs Kustomize base for sharing — trade-offs?

A library chart gives one versioned source of truth with strong reuse but couples all services to its release cadence and makes debugging indirect. Copy-paste is simple but drifts. Kustomize bases work for plain YAML but lack versioned packaging. Mitigate coupling by semantic-versioning the library, allowing services to pin different versions, and keeping it small and well-tested (helm unittest).

How would you test a common chart that serves many consumers?

Use helm lint and helm template in CI for each consumer with representative values; add unit tests with the helm-unittest plugin asserting rendered fields; validate output with kubeconform; and run a smoke install in a kind cluster.

What breaks if two charts define the same named template?

The last one loaded wins (templates share a global registry), producing confusing behaviour that depends on dependency load order. Avoid by chart-prefixed names and by treating helper names as a public API.

How do you version and release the common chart without breaking services?

SemVer it: backward-compatible template additions bump minor; breaking value/label changes bump major. Services pin a range (~0.1.0), commit Chart.lock, and upgrade deliberately, with changelogs and CI that renders all consumers against the new version before release.

Why StatefulSet?

  • Each broker needs a stable identity (kafka-controller-0, -1…) and its own persistent volume that follows it when rescheduled.
  • A headless Service gives each broker a stable DNS name for advertised listeners and inter-broker traffic.
  • Ordered, graceful rollout and scaling, unlike a Deployment’s interchangeable Pods.
Connection gotchas

Bitnami availability & alternatives

See topic 237. For serious use prefer the Strimzi operator (Kafka as Custom Resources, rolling upgrades, topic/user operators), or a managed service (MSK, Confluent Cloud, Aiven).

Why does Kafka usually run as a StatefulSet?

Brokers need stable identities and dedicated persistent storage; StatefulSets provide stable Pod names/DNS and per-Pod volumes that persist across rescheduling.

How do microservices find the Kafka brokers in Kubernetes?

Through the Kafka Service DNS name and port (e.g. kafka.default.svc.cluster.local:9092), set via Spring Cloud Stream binder properties (broker list) injected from ConfigMap env vars.

What is a partition and a consumer group?

A partition is an ordered log segment of a topic enabling parallelism; a consumer group is a set of consumers sharing a topic’s partitions so each record is processed by one member of the group.

What is KRaft mode?

Kafka’s built-in Raft-based metadata management that removes the need for ZooKeeper, simplifying deployment.

What happens to messages if a broker Pod restarts?

If persistence and replication are configured, the Pod re-attaches its PersistentVolume and rejoins; replicas on other brokers keep partitions available. Without persistence data on that broker is lost.

Explain Kafka’s advertised listeners problem in Kubernetes.

Clients bootstrap to any broker, then receive metadata listing each partition leader’s advertised host:port. If advertised addresses are internal Pod names but the client is outside the cluster (or in another network), connections fail. Solutions: separate internal/external listeners with correct advertised addresses (NodePort/LoadBalancer per broker or Ingress/TLS passthrough) or keep clients in-cluster.

How do you guarantee no message loss and ordering with Kafka?

Producer: acks=all, idempotence, retries; topic: replication factor ≥3, min.insync.replicas=2; consumers commit offsets after processing (at-least-once) and handle duplicates idempotently; ordering is guaranteed only within a partition, so use a key per entity. Exactly-once needs transactions.

How would you scale consumers for the message service?

Increase the number of Pods up to the partition count (extra consumers sit idle), or increase partitions (which changes key-to-partition mapping). Use an HPA on consumer lag via KEDA for event-driven autoscaling.

Operator vs Helm for Kafka?

Strimzi handles rolling broker upgrades in the right order, certificate rotation, rebalancing (Cruise Control), topics/users as CRDs and safe scaling — operational knowledge a chart cannot express. A chart suits dev/test.

Installing Grafana Loki & Tempo in Kubernetes Using Helm

Centralised logs (Loki) and distributed tracing (Tempo), completing the three pillars of observability.

Loki — logs

  • Loki is a log aggregation system from Grafana Labs, described as “Prometheus for logs”: it indexes only labels (app, namespace, pod), not full log text, which makes it cheap and fast to operate.
  • A log collector agent runs on each node (DaemonSet) – Promtail historically, now Grafana Alloy – reads container logs and ships them to Loki with labels.
  • Query with LogQL: {app="accounts"} |= "ERROR".
  • Modes: single-binary (simple), simple-scalable, microservices (large scale). Storage: object store (S3/GCS/MinIO) or filesystem for labs.

Tempo — distributed traces

  • Tempo stores traces (spans) cheaply, indexing by trace ID; it accepts OTLP, Jaeger and Zipkin formats.
  • Spring Boot services emit traces via OpenTelemetry (the OTel Java agent or Micrometer Tracing) to Tempo’s OTLP endpoint (gRPC 4317, HTTP 4318).
  • The trace ID is propagated across HTTP calls (W3C traceparent header) and added to log lines (MDC), so Grafana can jump from a log line to its full trace and back.

What is Loki and how does it differ from Elasticsearch?

Loki stores logs indexed only by labels, keeping the content compressed in chunks, so it is cheaper and simpler than Elasticsearch which full-text indexes everything. Trade-off: filtering inside log text is done at query time (grep-like).

What is Tempo?

A scalable, low-cost distributed tracing backend that stores traces keyed by trace ID and integrates with Grafana, accepting OpenTelemetry, Jaeger and Zipkin data.

How do logs get from Pods into Loki?

A collector agent (Promtail or Grafana Alloy) runs on every node, tails container log files, attaches Kubernetes labels and pushes them to Loki’s API.

What is a trace, a span and a trace ID?

A trace is the end-to-end journey of one request; spans are the timed operations in each service within it; the trace ID is the shared identifier propagated across services so spans can be stitched together.

What is OpenTelemetry?

A vendor-neutral CNCF standard and set of SDKs/agents for generating and exporting telemetry (traces, metrics, logs) via the OTLP protocol.

Why is “index labels, not content” a significant design decision?

It makes ingestion and storage cheap and keeps the index small, but queries must scan chunks matching label selectors, so good label design (low-cardinality: app, namespace, level) is crucial. High-cardinality labels (user ID, trace ID) cause index blow-up and poor performance; put such values in the log line and filter with LogQL.

How does trace context propagation work in a Spring microservice chain through the Gateway?

The W3C traceparent header carries trace ID and parent span ID. Instrumentation (OTel agent or Micrometer Tracing) extracts it from incoming requests, creates child spans, and injects it into outgoing calls (RestTemplate/WebClient/Feign/Kafka headers). Gateway and Feign need instrumentation too, or the chain breaks.

Sampling: what is it and how do you choose a strategy?

Recording every trace is expensive. Head-based sampling decides at the start (probabilistic, e.g. 10%); tail-based sampling (in an OTel Collector) decides after seeing the whole trace and can keep all errors/slow traces. Production commonly uses tail sampling, with 100% sampling in dev.

What is the role of the OpenTelemetry Collector?

An optional vendor-agnostic pipeline (receivers → processors → exporters) between apps and backends: batching, retry, tail sampling, attribute scrubbing, fan-out to multiple backends — decoupling application config from backend choice.

How do you install the whole application with Helm?

Build dependencies of the environment (umbrella) chart with helm dependency build, then run helm install eazybank prod-env. All service charts are deployed together as one release.

What does helm dependency build do?

Reads Chart.lock (or Chart.yaml) and downloads/copies the dependency charts into the chart’s charts/ directory so it can be rendered and installed.

What does --wait do on install?

Makes Helm wait until all Pods, PVCs, Services (and Deployment replicas) reach a ready state or the --timeout expires, so the command succeeds only if the app is actually running.

How do you check the status of a release?

helm list for all releases and status, helm status <release> for detail, helm get manifest/values for contents, and kubectl get pods for Pod state.

How do you install the same chart in two environments?

Use different release names and/or namespaces and environment values: helm install eazybank-dev ./app -n dev -f values-dev.yaml and helm install eazybank-prod ./app -n prod -f values-prod.yaml.

Why do you get “cannot re-use a name that is still in use”?

A release with that name already exists in the namespace (possibly in failed state). Use helm upgrade --install, choose another name, or helm uninstall the failed release first.

In what order does Helm create resources and can you rely on it for dependencies between microservices?

Helm sorts resources by kind (Namespace → … → ConfigMap → Service → Deployment …) but only submits them; it does not wait for one Deployment to be ready before creating the next unless using hooks. Application-level readiness must be handled by probes, retries and init containers. Helm hooks and weights can order Jobs (e.g. migrations).

What are Helm hooks and give use cases.

Resources annotated helm.sh/hook (pre/post-install, pre/post-upgrade, pre/post-delete, pre/post-rollback, test) with hook-weight and hook-delete-policy. Hooks are not part of the release’s managed set, so they are not deleted on uninstall unless a delete policy says so. Uses: DB schema migration Job before upgrade, smoke test after install, cleanup before delete.

How would you adopt existing, kubectl-created resources into a Helm release?

Add the label app.kubernetes.io/managed-by=Helm and annotations meta.helm.sh/release-name and meta.helm.sh/release-namespace to the live objects, then run helm install/upgrade with matching manifests; Helm will take ownership instead of failing with “already exists”.

What is the failure mode when --wait times out and what state is the release left in?

The release is recorded as failed and resources remain in the cluster (unless atomic/rollback-on-failure is set). You then inspect, fix, and helm upgrade (or rollback); to retry an install of a failed first revision you may need helm uninstall first.

Should the whole system really be one Helm release?

It simplifies bootstrapping but couples lifecycles: one failing component fails the entire release, and rollback reverts everything. Mature setups give each microservice its own release/pipeline and use the umbrella only for infra/baseline or demo environments.

Silent reverts

Env vars from a ConfigMap don’t reload (Section 14). With Helm, add the checksum/config annotation (topic 240) so a ConfigMap change modifies the Pod template and triggers a normal rolling update on helm upgrade.

Some fields cannot be changed on live objects (Deployment spec.selector, Job spec.template, Service clusterIP, PVC size in some classes). The upgrade fails with “field is immutable”. Stuck release

What does helm upgrade do?

Applies a new chart version and/or new values to an existing release, updates only the resources that changed, and records a new revision.

How do you upgrade an image version with Helm?

Change image.tag in values (or --set image.tag=…) and run helm upgrade <release> <chart>; Kubernetes then rolls out the new Pods.

What does helm upgrade --install do?

Installs the release if it does not exist, otherwise upgrades it — an idempotent command ideal for CI/CD.

How do you see that an upgrade happened?

helm list shows an incremented REVISION; helm history <release> lists all revisions with status and description.

What does --wait / --atomic do on upgrade?

--wait blocks until resources are Ready; --atomic (Helm 4: --rollback-on-failure) rolls back automatically to the previous revision if the upgrade fails or times out.

What is --reuse-values?

Reuse the previous release’s values instead of resetting to chart defaults; but new default keys added by a newer chart will be missing, which can break rendering.

Explain how a rolling upgrade via Helm relates to a Kubernetes Deployment rollout.

Helm only updates the Deployment object; the Deployment controller performs the rolling update using maxSurge/maxUnavailable and readiness probes (Section 14). Helm’s --wait observes readiness; Helm history tracks the release, while Kubernetes keeps a separate ReplicaSet revision history for the Deployment.

How do you do zero-downtime Helm upgrades?

Multiple replicas, correct readiness probes, maxUnavailable: 0, graceful shutdown + preStop sleep, PodDisruptionBudgets, backward-compatible DB migrations (expand/contract) run as pre-upgrade hooks, and --atomic --wait in the pipeline.

How do you handle database migrations during a Helm upgrade?

Run them as a pre-upgrade hook Job (or use Flyway/Liquibase at app start with leader election), make them backward compatible so old and new versions coexist during the rollout, and never rely on rollback to undo schema changes.

Why is helm upgrade sometimes slow or “stuck”?

--wait waits for readiness; failing probes, image pulls, insufficient cluster resources, long terminationGracePeriodSeconds or PDBs blocking evictions all extend or time out the operation. Use kubectl describe on the new Pods and the Deployment’s conditions.

Helm 3 three-way merge vs Helm 4 server-side apply — why change?

Three-way merge computed patches client-side and could conflict or drop fields managed by other controllers/tools (GitOps, HPA, operators). Server-side apply tracks field ownership on the API server, detects conflicts explicitly and cooperates with multiple managers. Existing Helm 3 releases keep client-side apply on upgrade unless you opt in to avoid surprises.

Key facts

  • A rollback creates a NEW revision (revision 4 = “Rollback to 2”). History is append-only; nothing is rewritten.
  • Rollback re-applies the stored manifest of the target revision (all resources in the release), then Kubernetes performs a normal rolling update back to the old Pod template.
  • History length is limited by --history-max (default 10); old revision Secrets are pruned.
  • Release statuses: deployed (current), superseded (replaced), failed, uninstalled (kept with --keep-history), uninstalling, pending-install, pending-upgrade, pending-rollback.

What rollback does NOT undo

Database schema/data changes, external side-effects, PVC data, CRDs in crds/, Secrets/ConfigMaps modified outside Helm, and resources that Helm hooks created. It also cannot fix a bad chart that deletes a PVC — design stateful resources with helm.sh/resource-policy: keep.

Rollback to a failed state

If revision N was itself a bad config, rolling back to N-1 is right; rolling back to “previous” after a failed upgrade goes to the last deployed revision, not necessarily N-1. Check helm history before choosing.

How do you view the revision history of a release?

helm history <release> shows revision numbers, timestamps, status, chart/app version and description.

How do you roll back a release?

helm rollback <release> <revision>; without a revision it reverts to the previous one.

Does rollback delete the newer revisions?

No. It creates a new revision whose content equals the target revision; history keeps growing (up to --history-max).

How do you inspect what an old revision contained?

helm get values|manifest|all <release> --revision N.

What is the difference between helm rollback and kubectl rollout undo?

Helm rolls back the whole release (all resources and values); kubectl rolls back one Deployment’s Pod template and bypasses Helm’s bookkeeping.

How many revisions does Helm keep?

By default 10 per release; configure with --history-max on upgrade (0 = unlimited).

Why does a Helm rollback increase the revision number instead of reducing it?

History is an immutable audit log of operations. Rolling back is itself a change event, so Helm records revision N+1 whose manifest equals revision M. This preserves traceability (who did what when) and mirrors Git revert semantics.

A rollback succeeded but the application is still broken. What could explain it?

Stateful or external changes were not reverted (DB migration, PVC data, message schema), config changed outside Helm, the old image tag no longer exists or was overwritten (mutable tags), or the failure is in a dependency. Use immutable tags/digests and backward-compatible migrations so rollback is meaningful.

How would you implement automatic rollback in CI/CD?

helm upgrade --install --atomic --wait --timeout X (Helm 4: --rollback-on-failure) for deploy-time failures; plus post-deploy verification (smoke tests, SLO checks via Argo Rollouts/Flagger or pipeline gates) that triggers helm rollback when metrics regress.

Rollback in a GitOps setup (Argo CD/Flux) — how does it differ?

There is typically no Helm release history; the desired state is in Git. Rollback = revert the Git commit (or pin the previous chart/values version) and let the controller sync. Using helm rollback manually would be overwritten by the next sync.

What does helm uninstall do?

Deletes all Kubernetes resources that belong to a release and removes the release record (history), cleaning up the application in one command.

What does --keep-history do?

Retains the release revision records after uninstall (status uninstalled) so you can still view history and even roll back to resurrect the release.

Does helm uninstall delete PersistentVolumeClaims?

Not for those created by StatefulSet volume claim templates; they stay by design to prevent accidental data loss and must be deleted manually. PVCs defined as chart templates are deleted unless protected by helm.sh/resource-policy: keep.

Was the old command helm delete?

Yes; helm delete is an alias of helm uninstall in Helm 3. In Helm 2 delete kept history by default and needed --purge.

How do you remove a release in another namespace?

helm uninstall <release> -n <namespace>; releases are namespace-scoped.

Why does Helm refuse to delete CRDs and how should you handle CRD lifecycle?

Deleting a CRD cascades to deleting every custom resource of that type across the cluster — potentially catastrophic and affecting other releases. Helm therefore installs crds/ once and never upgrades/deletes. Manage CRDs in a dedicated chart or via GitOps/Terraform with explicit review, and document upgrade steps for chart consumers.

How do you protect critical resources from helm uninstall/upgrade deletion?

Annotate with helm.sh/resource-policy: keep (e.g. PVCs, Secrets); use RBAC and admission policies; use --keep-history and backups; for databases prefer managed services or operators with their own deletion protection.

A release is stuck in uninstalling or failed. How do you recover?

Inspect helm status/history and pending finalizers on resources (kubectl get … -o yaml), fix blockers (e.g. namespace finalizers, hooks failing), retry helm uninstall --no-hooks if a hook is the blocker; as a last resort delete the release Secrets (sh.helm.release.v1.<name>.vN) and clean resources manually.

Uninstall ordering: does Helm delete in reverse install order?

Yes, Helm deletes in reverse of its install-order sorting (e.g. Deployments before ConfigMaps, Namespaces last) and waits only if --wait is used; finalizers and Pod termination grace periods can make deletion appear slow.

What are the biggest operational risks with Helm and how do you mitigate them?

Helm vs Operators vs GitOps — summarise how they fit together.

Helm packages and templates manifests and tracks release history. Operators encode ongoing operational logic for complex apps via CRDs (day-2: failover, backup, upgrade). GitOps (Argo CD/Flux) is the delivery model keeping cluster state equal to Git, often by rendering Helm/Kustomize. Typical stack: Git → Argo CD → Helm chart (including operator CRs) → Kubernetes.

What changed in Helm 4 that an experienced engineer should know?

Server-Side Apply by default for new releases (existing releases keep their previous apply method unless you opt in), flag renames (--atomic → --rollback-on-failure, --force → --force-replace) with deprecation warnings for old names, a new WebAssembly-capable plugin system, improved readiness/status waiting, and OCI/registry-login tweaks. Charts with apiVersion: v2 and existing Helm 3 releases continue to work; test pipelines before upgrading the CLI.
