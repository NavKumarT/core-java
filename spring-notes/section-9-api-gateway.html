Gateway, Routing & Cross-Cutting Concerns

Every microservices system eventually has to answer a question Section 8 deliberately left open: if Accounts, Loans, and Cards are internal, dynamically-scaled services discovered via Eureka, what does an external client — a mobile app, a browser — actually talk to? Exposing every microservice directly to the internet is the wrong answer at basically every real company. This section covers the standard fix — an API Gateway / Edge Server as the single, hardened entry point — built with Spring Cloud Gateway's reactive architecture, custom routing, and the cross-cutting concerns (correlation IDs, centralized logging, response headers) that belong at the edge rather than duplicated across every service.

💡
How to use this document: This is one of the most reliably-asked system-design topics in microservices/backend interviews at large-scale product and fintech companies — "design an API Gateway," "how would you centralize auth/rate-limiting," and "Gateway vs Service Mesh" show up constantly. Topic 132 (design patterns) and the FAANG-level Q&A throughout are written with that specifically in mind.

Challenges While Dealing with External Communication in Microservices

Section 8 solved east-west (internal) traffic. This topic is about the other half — north-south traffic — and why it can't be solved the same way.

What happens if external clients call microservices directly

Imagine a mobile app calling Accounts, Loans, and Cards directly, each at its own address, with no intermediary. Every one of the following becomes the client's problem, or gets duplicated N times across N services:

  • Client complexity explodes — the client must know and maintain N different service endpoints, and if it needs data spanning multiple services (a "customer summary" view), it must orchestrate multiple calls and merge results itself.
  • Cross-cutting concerns duplicate across every service — authentication/authorization, rate limiting, CORS handling, SSL/TLS termination, request logging, and IP allow-listing would each need to be implemented and kept consistent inside every single microservice independently.
  • Internal architecture leaks to the outside world — clients become coupled to internal service boundaries (which team owns what, how the system happens to be decomposed today); refactoring internal boundaries later becomes a breaking change for every external consumer.
  • Massively larger attack surface — every microservice becomes a direct, independently-securable target on the public internet, rather than having one hardened, heavily-monitored perimeter.
  • No central point for throttling or abuse protection — a client hammering one service has no system-wide rate-limiting checkpoint to pass through first.
  • Inconsistent versioning and protocol exposure — different teams evolve their services' public contracts independently, with no central point enforcing a consistent external API contract or protocol translation (e.g. exposing REST externally while some internal services use gRPC).
The core realization

Every one of these problems shares the same shape: something that should be handled once, centrally instead gets pushed down into every individual service, or worse, pushed onto every individual client. This is precisely the gap an API Gateway / Edge Server exists to close — and it's why this topic exists as the direct motivation before any Spring Cloud Gateway code appears.

What happens to cross-cutting concerns like authentication and rate limiting if external clients call microservices directly?

Each concern needs to be implemented and kept consistent inside every individual microservice independently, since there's no shared, central point external traffic must pass through first — leading to duplication and drift risk across services.

Why does exposing every microservice directly to the internet increase security risk?

Every service becomes an independently-reachable, independently-securable target, multiplying the attack surface, rather than concentrating external exposure and hardening effort on one well-monitored perimeter.

Beyond security, what's the architectural coupling risk of clients calling microservices directly?

Clients become coupled to the system's current internal service decomposition — if a team later decides to split, merge, or rename a service (a routine internal architecture evolution), every external client integration built against the old direct endpoints breaks. A gateway acts as an anti-corruption layer for the public API surface: internal services can be restructured freely as long as the gateway's externally-facing routes and contracts stay stable, decoupling "how we organize our internal services" from "what our external API looks like" — a genuinely important architectural property at any company operating at real scale, since internal decomposition is expected to evolve continuously while external contracts need much higher stability guarantees.

Why We Need an Edge Server or API Gateway Inside Microservices

The single-entry-point solution, and exactly which responsibilities it centralizes.

What an API Gateway is

An API Gateway (also called an Edge Server) is a single, dedicated service that sits between external clients and the internal microservices ecosystem, acting as the sole entry point for all north-south traffic. Every external request hits the gateway first; the gateway then routes it to the appropriate internal service (using the exact service-discovery mechanics from Section 8) and returns the response.

What a gateway should NOT become

A gateway is meant to handle generic, cross-cutting, infrastructure-level concerns — not business logic. If a gateway starts accumulating service-specific business rules (e.g. "if account type is SAVINGS, apply this discount logic"), it's drifting into becoming exactly the kind of tightly-coupled, hard-to-independently-deploy component microservices were meant to avoid in the first place — sometimes called a "God gateway" anti-pattern. This distinction — infrastructure concerns at the edge, business logic in services — is a very common interview follow-up.

What is an API Gateway / Edge Server, in one sentence?

A single, dedicated service that sits between external clients and internal microservices, serving as the sole entry point for external traffic — routing requests internally and centralizing cross-cutting concerns like auth, rate limiting, and logging.

Name three cross-cutting concerns a gateway centralizes.

Any three of: authentication/authorization, rate limiting, SSL/TLS termination, centralized logging/tracing, request routing, and request/response transformation.

Why is it a mistake for a gateway to contain business logic, beyond just "separation of concerns" as a general principle?

Business logic in the gateway means the gateway now has to be redeployed every time that specific business rule changes, even though the gateway is shared, high-traffic, critical infrastructure that every single request passes through — coupling a comparatively volatile concern (business rules that change often) to a component that should be comparatively stable and rarely-changing (routing and cross-cutting infrastructure). It also reintroduces exactly the kind of tight coupling and single point of ownership microservices are meant to avoid: instead of the Loans team owning loan business logic end-to-end, that logic now lives partly in a shared, centrally-owned gateway, creating a coordination bottleneck and blurring service ownership boundaries — a real anti-pattern flagged in essentially every serious API Gateway design discussion.

Doesn't putting everything through one gateway just recreate the single-point-of-failure problem Section 8 spent an entire topic (104) arguing against for east-west traffic?

It's a fair tension, but the two traffic shapes genuinely differ in a way that changes the calculus: north-south traffic is lower relative volume than aggregate east-west traffic, and centralizing a *stable, well-monitored, horizontally-scalable* entry point for it is a deliberate, accepted trade-off — exactly as argued in topic 104's FAANG answer. In production, this risk is mitigated the same way any critical stateless service's SPOF risk is mitigated: running multiple gateway instances behind a cloud/hardware load balancer (the traditional LB pattern from Section 8 is actually the *right* tool here, since gateway instances are comparatively stable and don't need dynamic per-instance discovery the way internal services do), horizontal autoscaling, and multi-AZ/multi-region deployment for genuinely critical systems. The gateway being a single logical entry point doesn't mean it's a single physical instance.

Introduction to Spring Cloud Gateway

Spring's reactive, non-blocking gateway implementation — and why it replaced Netflix Zuul in the Spring Cloud ecosystem.

What Spring Cloud Gateway is

Spring Cloud Gateway (SCG) is Spring's own API Gateway library, built on Spring WebFlux (Spring's reactive web framework), Project Reactor, and an embedded Netty server — a fully non-blocking, asynchronous stack, deliberately different from the traditional blocking Servlet/Tomcat stack used by regular Spring MVC applications throughout this course so far.

Why not Netflix Zuul

Netflix Zuul (specifically Zuul 1, the version most widely adopted historically) was the earlier standard gateway in the Spring Cloud Netflix ecosystem — but it's built on the traditional blocking Servlet model (one thread per request, blocking I/O). Under high concurrency, a blocking gateway can exhaust its thread pool waiting on slow downstream calls, becoming a bottleneck exactly where the system needs the most headroom (every single external request passes through it). Spring built Spring Cloud Gateway as a reactive, non-blocking replacement specifically to solve this, and it's now the standard recommendation in the Spring Cloud ecosystem — Netflix's own Zuul 2 (an async rewrite) exists but never achieved the same level of Spring Cloud integration or community adoption.

What underlying technology stack is Spring Cloud Gateway built on?

Spring WebFlux, Project Reactor, and an embedded Netty server — a non-blocking, reactive stack, as opposed to the traditional blocking Servlet/Tomcat model used by regular Spring MVC.

Why did Spring Cloud Gateway replace Zuul 1 as the standard recommendation?

Zuul 1 is built on a blocking, thread-per-request Servlet model, which can become a throughput bottleneck under high concurrency — since every external request passes through the gateway, this matters more here than almost anywhere else in the system. Spring Cloud Gateway's non-blocking reactive model handles much higher concurrency with fewer threads.

Why does a reactive, non-blocking model specifically matter more for a gateway than for a typical backend microservice?

A gateway is, structurally, an I/O-bound proxy — for every incoming request, it makes an outbound call to a downstream service and waits for that response, meaning the gateway spends most of its time waiting on network I/O rather than doing CPU-bound work. In a blocking model, each of these waits ties up an entire thread from a finite pool, so gateway throughput is capped by thread pool size divided by average downstream latency. In a reactive model, a thread isn't blocked while waiting — it's freed to handle other requests, and the event loop resumes processing that specific request once the downstream response arrives, meaning a small number of threads can service a very large number of concurrent in-flight requests. This I/O-bound, high-fan-in nature is exactly the profile reactive programming is designed for, and exactly why it matters disproportionately at the gateway layer specifically, versus, say, a CPU-bound internal service where blocking vs reactive matters much less.

Does choosing Spring Cloud Gateway mean the internal microservices behind it also need to be reactive/WebFlux-based?

No — this is a common and important point of clarification. The gateway's own internal implementation being reactive is independent of what protocol/paradigm the services behind it use; Accounts, Loans, and Cards throughout this course remain traditional blocking Spring MVC applications, and the gateway proxies HTTP requests to them without requiring them to also be reactive. The reactive requirement is specifically about the gateway's own request-handling efficiency under its uniquely high-fan-in traffic pattern, not a constraint it imposes on the rest of the architecture.

Pre-filters vs post-filters

A single GatewayFilter can act at two distinct points in the same request's lifecycle, using Reactor's composable stream model: the filter's logic before calling chain.filter(exchange) runs as a pre-filter (on the way in — e.g. adding a correlation ID header, validating auth), and logic attached via .then(...) after that call runs as a post-filter (on the way out — e.g. adding a response header, logging the response status). This is precisely the mechanism topics 129–131 build on.

GatewayFilter

Scoped to a specific route — configured per-route, either declaratively (in YAML) or via the Java route builder DSL. Built-in filters include AddRequestHeader, AddResponseHeader, StripPrefix, RewritePath, and many more.

GlobalFilter

Applies to every route automatically — implemented as a Spring bean implementing the GlobalFilter interface. This is the mechanism used for genuinely cross-cutting concerns like correlation ID generation (topic 130), since it needs to apply uniformly regardless of which specific route handled the request.

How this connects back to Section 8

A route's destination URI using the lb://SERVICE-NAME scheme (e.g. lb://ACCOUNTS) is exactly what tells Spring Cloud Gateway to resolve the target through the Eureka-backed, client-side-discovery-and-load-balancing machinery from Section 8 — the gateway doesn't hardcode a downstream address any more than Feign did; it discovers a healthy instance dynamically for every proxied request.

What are the three core building blocks of Spring Cloud Gateway configuration?

Route (the overall unit: ID, destination, predicates, filters), Predicate (the condition a request must match to use this route), and Filter (logic that modifies the request or response as it passes through).

What's the difference between GatewayFilter and GlobalFilter?

`GatewayFilter` is scoped to a specific route, configured individually per-route. `GlobalFilter` applies automatically to every route in the gateway, making it the right choice for concerns that should apply uniformly regardless of which route handled a request.

How does a filter implement both pre- and post-processing logic within what looks like a single filter definition?

Spring Cloud Gateway filters are built around Reactor's `Mono`/reactive-chain composition model — a filter receives the current `ServerWebExchange` and a `GatewayFilterChain`, and calls `chain.filter(exchange)` to continue processing. Any logic placed before that call executes as the request flows inward (pre-filter behavior — e.g. mutating headers before the proxied call is made), and any logic composed via `.then(Mono.fromRunnable(...))` or similar after that call executes once the downstream response has come back and is flowing outward (post-filter behavior). This single-method, chain-based design is what lets one filter definition cleanly express both "before" and "after" logic without needing two separate filter types.

What's the actual mechanism by which the gateway's route-matching handles a request that could match multiple routes' predicates?

Spring Cloud Gateway evaluates routes in the order they're defined (or, for programmatically-built routes, the order added via the `RouteLocatorBuilder`) and uses the first route whose combined predicates all evaluate to true — so route ordering matters, and more specific routes generally need to be defined before more general/catch-all ones, mirroring the same "most specific match wins" principle discussed for Spring MVC's `@RequestMapping` resolution back in Section 1. This is a genuine, easy-to-hit gotcha when combining the auto-generated discovery-locator routes (topic 126) with hand-written custom routes (topic 128) in the same gateway — if ordering isn't deliberate, a broad auto-generated route can shadow a more specific custom one you actually intended to be used.

Critical constraint: never combine spring-boot-starter-web with spring-cloud-starter-gateway

spring-cloud-starter-gateway pulls in Spring WebFlux, which requires a reactive, non-blocking servlet container model. spring-boot-starter-web pulls in traditional blocking Spring MVC on Tomcat. Having both on the classpath simultaneously creates an ambiguous, broken auto-configuration state — Spring Boot won't know which web stack to actually initialize. This is one of the most common early mistakes when adding a gateway module, especially if it was scaffolded by copy-pasting a `pom.xml` from one of the other (MVC-based) services.

Like every other service in this system, the Gateway is also a Eureka client — not because it needs to be discovered by other services in any meaningful way, but because it needs to discover Accounts, Loans, and Cards to route to them via the lb://SERVICE-NAME mechanism covered in the previous topic.

Why can't you have both spring-boot-starter-web and spring-cloud-starter-gateway on the same classpath?

They represent two fundamentally different, mutually exclusive web stacks — traditional blocking Spring MVC (starter-web) versus reactive Spring WebFlux (required by the gateway) — and having both creates an ambiguous auto-configuration state Spring Boot can't correctly resolve.

Why does the gateway need to be a Eureka client?

To discover the internal microservices (Accounts, Loans, Cards) it needs to route requests to — using the exact client-side discovery mechanics from Section 8, resolved via `lb://SERVICE-NAME` destination URIs.

Does the gateway registering itself with Eureka serve any purpose, given internal services don't call the gateway (traffic flows the other direction)?

In this specific course's architecture, not a strong functional one — you're right that traffic flows client → gateway → services, not the reverse, so internal services have no real need to discover the gateway via Eureka. It's mostly a byproduct of including the Eureka client dependency (needed for the gateway's own outbound discovery) and following the consistent registration pattern established for every service in the system. In more advanced setups, gateway registration can matter for things like a monitoring/ops dashboard that wants a unified view of every registered service including infrastructure components, or if a service mesh/observability tool queries the registry to build a full system topology map — but for the pure routing use case this course focuses on, it's largely incidental rather than load-bearing.

Why this is a demo mechanism, not a production pattern

Auto-generated routes are excellent for quickly verifying the gateway → discovery → downstream chain works end-to-end, but they offer zero control over path structure, filters, or which endpoints are actually meant to be externally exposed — every single endpoint on every registered service becomes reachable through the gateway automatically, including ones that were never intended to be public. Production systems almost always move to explicit, hand-defined routes (topic 128) specifically to control and restrict what's actually exposed externally.

What does spring.cloud.gateway.discovery.locator.enabled=true do?

It tells Spring Cloud Gateway to automatically generate one route per service currently registered in Eureka, with no manual route configuration needed — each route's path is prefixed by the service's registered ID.

What's the specific production risk of relying on discovery-locator auto-generated routes rather than explicit routes?

Every endpoint on every registered service becomes externally reachable through the gateway with zero deliberate curation — including internal-only administrative endpoints, actuator management endpoints (unless separately secured), or endpoints genuinely never meant for external consumption. This directly undermines one of the gateway's core purposes from topic 122 (hiding internal topology and controlling exactly what's exposed) — auto-discovery routes expose the internal API surface 1:1 to the outside world rather than curating a deliberate, minimal, reviewed external contract. This is precisely why explicit route configuration (topic 128) is the production standard: it lets a team consciously decide which specific paths, on which specific services, should be reachable externally at all.

Make Changes Inside Gateway Server to Accept Service Names with Lower Case

A small but real-world-relevant REST convention fix.

application.yml
spring:
  cloud:
    gateway:
      discovery:
        locator:
          enabled: true
          lower-case-service-id: true

By default, the auto-generated route prefix matches Eureka's service ID casing, which is conventionally uppercase (ACCOUNTS). Setting lower-case-service-id: true makes the generated paths lowercase (/accounts/api/fetch) instead — aligning with standard REST URL conventions (lowercase, hyphenated paths) covered back in Section 1's REST best-practices notes, since uppercase segments in a URL path are unconventional and can look unprofessional in a public-facing API.

What does lower-case-service-id: true change?

It makes the gateway's auto-generated discovery routes use lowercase service names in the path (e.g. `/accounts/...`) instead of the uppercase Eureka service ID convention (`/ACCOUNTS/...`), aligning with standard REST URL casing conventions.

Is this purely cosmetic, or does URL casing actually matter functionally for HTTP?

It's largely a convention/professionalism concern rather than a strict functional requirement — URL paths are technically case-sensitive per the HTTP spec, so `/ACCOUNTS/...` and `/accounts/...` are different paths as far as routing is concerned, meaning this setting genuinely changes what the actual externally-callable path is, not just how it displays. The practical reasoning for preferring lowercase is almost entirely about matching REST API convention and consumer expectations (developers instinctively expect lowercase, hyphenated paths) rather than any technical HTTP requirement — but getting API path conventions right and consistent is a real, if understated, part of API design quality that shows up in code review and public API documentation standards at any company maintaining external-facing APIs.

Implementing Custom Routing Using Spring Cloud Gateway

Explicit, hand-curated routes — the production-standard replacement for the discovery-locator demo mechanism.

GatewayRouteConfig.java
@Configuration
public class GatewayRouteConfig {

    @Bean
    public RouteLocator eazyBankRouteConfig(RouteLocatorBuilder routeLocatorBuilder) {
        return routeLocatorBuilder.routes()
            .route(p -> p
                .path("/eazybank/accounts/**")
                .filters(f -> f
                    .rewritePath("/eazybank/accounts/(?<segment>.*)", "/${segment}")
                    .addResponseHeader("X-Response-Time", LocalDateTime.now().toString())
                    .circuitBreaker(config -> config.setName("accountsCircuitBreaker")))
                .uri("lb://ACCOUNTS"))
            .route(p -> p
                .path("/eazybank/loans/**")
                .filters(f -> f
                    .rewritePath("/eazybank/loans/(?<segment>.*)", "/${segment}"))
                .uri("lb://LOANS"))
            .route(p -> p
                .path("/eazybank/cards/**")
                .filters(f -> f
                    .rewritePath("/eazybank/cards/(?<segment>.*)", "/${segment}"))
                .uri("lb://CARDS"))
            .build();
    }
}

Annotation & method reference

RouteLocatorBuilder

Injected builder for programmatically defining routes in Java, offering full control that YAML-based route config can express too, but which many teams find more readable/testable as code — especially once filter chains get non-trivial.

.path(...)

The route's predicate — matches incoming requests whose path fits this pattern. ** matches any remaining path segments.

.rewritePath(...)

A built-in filter that transforms the externally-visible path (/eazybank/accounts/api/fetch) into the path the downstream service actually expects (/api/fetch) — this is exactly how the gateway can present a clean, deliberately-designed external URL structure that's fully decoupled from each service's own internal path conventions.

.circuitBreaker(...)

Wraps this route with a circuit breaker (backed by Resilience4j in modern Spring Cloud Gateway) — if the Accounts service starts failing broadly, the circuit breaker can trip and short-circuit further calls, protecting both the gateway and the struggling downstream service from cascading overload. This is a direct, practical answer to the "what happens when a downstream service is failing" question raised back in Section 8's Feign topic.

Why explicit routes are the production standard

Explicit routing gives full, deliberate control over exactly what's exposed externally (only /eazybank/accounts/**-style paths, never a service's raw internal path structure), lets each route carry its own tailored filter chain (circuit breakers, custom headers, rate limiting configured per-route rather than uniformly), and — critically — decouples the external API's URL design from internal implementation details, satisfying exactly the "hide internal topology" goal from topic 122 that the discovery-locator demo mechanism explicitly fails to provide.

What does the rewritePath filter do?

It transforms the externally-visible request path into whatever path the downstream service actually expects — letting the gateway present a clean, custom external URL structure independent of each internal service's own path conventions.

Why is explicit routing preferred over the discovery-locator auto-generated routes from topic 126 in production?

It gives deliberate control over exactly which paths are externally exposed (rather than every endpoint on every registered service becoming reachable automatically), and lets each route carry its own tailored filter chain — critical for production concerns like circuit breakers, custom headers, and rate limiting configured per-route.

What are the trade-offs between defining routes via the Java RouteLocatorBuilder DSL versus declaratively in application.yml?

YAML-based route definitions are simpler to read for straightforward routes and don't require a recompile/redeploy if paired with an externalized-config mechanism (Spring Cloud Config from Section 6 could, in principle, serve gateway route definitions dynamically) — but complex conditional logic, reusable filter compositions, or programmatically-generated routes (e.g. building routes from a data-driven service catalog) are awkward or impossible to express cleanly in YAML. The Java DSL is fully type-checked at compile time (a typo'd filter name fails to compile rather than silently misbehaving at runtime), supports arbitrary Java logic for route construction, and is generally preferred once route configuration grows beyond simple path-to-service mappings — which is exactly why this course introduces the Java DSL for custom routing rather than staying with YAML-only configuration.

How would you evolve this route configuration to support versioned external APIs, e.g. /eazybank/v1/accounts/** vs /eazybank/v2/accounts/**?

Add version-specific route predicates mapping to potentially different downstream targets or different filter chains — e.g. `/eazybank/v1/accounts/**` routing to the current Accounts service with today's response shape, while `/eazybank/v2/accounts/**` could route to either a newer Accounts version (if the team runs parallel versions during a migration) or the same service with an additional response-transformation filter that reshapes the v1 response into the new v2 contract. This is exactly the kind of protocol/contract-translation responsibility that belongs at the gateway layer rather than duplicated in every client, and ties directly back to the URI-versioning discussion from Section 1's REST best-practices topic — the gateway is a natural, centralized place to implement that versioning strategy without touching the underlying services' own internal APIs at all.

Demo of addResponseHeader Filter

A concrete, minimal filter example before moving to the more involved cross-cutting-concerns implementation.

Adding a response header
.filters(f -> f
    .rewritePath("/eazybank/accounts/(?<segment>.*)", "/${segment}")
    .addResponseHeader("X-Response-Time", LocalDateTime.now().toString())
)

addResponseHeader is one of Spring Cloud Gateway's many built-in filters (alongside `addRequestHeader`, `removeRequestHeader`, `setStatus`, and dozens more) — it injects a custom header into the response the gateway sends back to the client, after the downstream service's response has already come back. This is a deliberately simple example that demonstrates the post-filter half of a route's filter chain (see topic 124) before the section moves to the more substantial, genuinely production-relevant global filter implementation in the next two topics.

A subtle but real gotcha: this specific header value is misleading

Setting X-Response-Time to LocalDateTime.now() evaluated once when the route is defined (or, depending on exact placement, once per request but before the downstream call actually completes) doesn't correctly represent "how long did this request take" — a genuinely useful response-time header needs to be computed as the actual elapsed time between when the request entered the gateway and when the response was ready, typically captured via timestamps stored in the `ServerWebExchange`'s attributes at the pre-filter stage and read back at the post-filter stage. Worth understanding this distinction rather than treating the demo literally.

What does the addResponseHeader filter do?

It adds a custom header to the response the gateway sends back to the client, applied after the downstream service's response has been received — a post-filter operation.

How would you correctly implement a response-time header that reflects actual request latency?

Capture a start timestamp in a pre-filter stage, store it in the `ServerWebExchange`'s attribute map (a per-request, request-scoped storage mechanism Spring WebFlux provides specifically for this kind of cross-filter-stage data passing), and in a post-filter stage — after `chain.filter(exchange)` completes — read that stored start time, compute the elapsed duration against the current time, and set that computed value as the response header. This is a genuinely common pattern for gateway-level latency instrumentation, and the general technique (stash something at the pre-filter stage, retrieve and use it at the post-filter stage via exchange attributes) is exactly how correlation ID propagation is implemented in the very next topic.

public class FilterUtility {

    public static final String CORRELATION_ID = "eazybank-correlation-id";

    public String getCorrelationId(HttpHeaders requestHeaders) {
        if (requestHeaders.get(CORRELATION_ID) != null) {
            List<String> requestHeaderList = requestHeaders.get(CORRELATION_ID);
            return requestHeaderList.stream().findFirst().get();
        } else {
            return null;
        }
    }

    public ServerWebExchange setRequestHeader(
            ServerWebExchange exchange, String name, String value) {
        return exchange.mutate()
            .request(exchange.getRequest().mutate().header(name, value).build())
            .build();
    }
}
@Component
@Order(1)
public class RequestTraceFilter implements GlobalFilter {

    private static final Logger logger =
        LoggerFactory.getLogger(RequestTraceFilter.class);

    @Autowired
    FilterUtility filterUtility;

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        HttpHeaders requestHeaders = exchange.getRequest().getHeaders();

        if (isCorrelationIdPresent(requestHeaders)) {
            logger.debug("eazybank-correlation-id found: {}",
                filterUtility.getCorrelationId(requestHeaders));
        } else {
            String correlationID = generateCorrelationId();
            exchange = filterUtility.setRequestHeader(
                exchange, FilterUtility.CORRELATION_ID, correlationID);
            logger.debug("eazybank-correlation-id generated: {}", correlationID);
        }
        return chain.filter(exchange);
    }

    private boolean isCorrelationIdPresent(HttpHeaders requestHeaders) {
        return filterUtility.getCorrelationId(requestHeaders) != null;
    }

    private String generateCorrelationId() {
        return java.util.UUID.randomUUID().toString();
    }
}

Annotation & concept reference

GlobalFilter

This interface (versus per-route `GatewayFilter`) is exactly why this filter applies uniformly to every request through every route — correlation ID generation is precisely the kind of concern that must never depend on which specific route happened to handle a request.

@Order(1)

Controls this filter's position in the overall filter execution chain relative to other global filters — lower values execute earlier. Correlation ID generation typically needs to run very early, before other filters that might want to log or use that ID.

exchange.mutate()

ServerWebExchange (and its underlying `ServerHttpRequest`) is immutable in the reactive WebFlux model — you can't directly modify request headers in place. `.mutate()` returns a builder for constructing a new, modified exchange/request, which is why the filter must reassign the local `exchange` variable to this new mutated instance before continuing the chain.

Mono<Void>

The reactive return type every `GlobalFilter`/`GatewayFilter` must produce — `Mono` represents an asynchronous computation that will eventually complete (with no meaningful value here, hence `Void`), consistent with the fully non-blocking, reactive nature of the whole gateway request pipeline established in topic 123.

Centralized logging, the other half of this pair of topics

Beyond correlation ID propagation, the same `GlobalFilter` mechanism is the natural place to log every request/response passing through the gateway centrally — method, path, status code, latency — giving one consistent, complete log of all external traffic hitting the system, rather than needing to reconstruct that picture from scattered individual service logs. Combined with the correlation ID now present on every downstream log line too, an engineer investigating an issue can search logs across every service by one shared identifier and see the complete, ordered story of a single external request's full journey through the system — exactly the distributed-tracing capability flagged as a gap back in Section 1's exception-handling notes, now actually closed.

Why is the gateway the right place to generate a correlation ID, rather than each individual service generating its own?

The gateway is the single entry point every external request passes through first — generating the ID there guarantees exactly one ID per external request, consistently propagated to every downstream service call, rather than each service potentially generating its own inconsistent ID or requiring extra coordination to agree on one.

Why must the filter reassign the exchange variable via exchange.mutate() instead of directly setting a header on the existing request object?

`ServerWebExchange` and its request are immutable in Spring WebFlux's reactive model — there's no in-place header setter to call. `.mutate()` builds a new, modified exchange instance reflecting the added header, which must be explicitly passed forward (reassigned to the local variable, then passed into `chain.filter(...)`) for the change to actually take effect on the request as it continues through the chain.

What happens if a malicious or misbehaving external client sends its own eazybank-correlation-id header — does the filter's "use existing if present" logic create any risk?

Potentially yes, in a couple of ways worth understanding: (1) log injection/confusion — an attacker could deliberately set a correlation ID matching a legitimate, unrelated request's ID, muddying log analysis or making malicious traffic harder to distinguish from a genuine request in the same trace; (2) if any downstream logic naively trusts the correlation ID as more than a log-correlation convenience (e.g. using it as a cache key or idempotency key without additional validation), a client-supplied value could enable unintended cache collisions or replay-style issues. Production-grade implementations typically treat a client-supplied correlation ID as advisory at best — either always generating a fresh, server-controlled ID regardless of what the client sent (sacrificing the ability for a client to pre-correlate their own request, which is sometimes a deliberately desired feature for client-side debugging), or validating the format/uniqueness of a client-supplied ID before trusting it, and never using it for anything beyond log correlation without additional safeguards.

How would this correlation-ID pattern relate to, or be replaced by, standardized distributed tracing tools like Micrometer Tracing (Spring's Sleuth successor) or OpenTelemetry?

This hand-rolled correlation ID is functionally a simplified, single-ID version of what dedicated distributed tracing frameworks provide more richly: Micrometer Tracing/OpenTelemetry generate a trace ID (identifying the whole end-to-end request journey, analogous to this correlation ID) plus a unique span ID per individual hop/operation within that trace, automatically propagated via standard headers (W3C Trace Context, or B3 headers), and automatically instrument Spring MVC, WebFlux, Feign, and RestTemplate/WebClient calls without needing hand-written filters like this one at all. These tools also integrate with visualization backends (Zipkin, Jaeger, or cloud-provider tracing services) that render the full multi-service call graph with per-hop latency breakdowns — something a plain correlation ID logged as text can't provide on its own, only enabling manual log correlation via grep/search. Many real production systems use both: a simple business-level correlation ID (sometimes customer-facing, e.g. returned to the client for support-ticket reference) alongside a full distributed tracing system for deep, automatic observability — they solve related but distinct problems.

Design Patterns Around API Gateway

The system-design vocabulary interviewers expect — this topic alone maps directly onto a huge fraction of gateway-related interview questions.

Gateway Offloading

Move cross-cutting, infrastructure-level concerns — SSL termination, authentication, rate limiting, compression, caching — out of every individual service and onto the gateway, so backend services can focus purely on business logic. This is essentially topic 122's core argument, formalized as a named pattern.

Gateway Aggregation (API Composition)

The gateway (or a thin, dedicated layer just behind it) composes a single client-facing response from multiple backend calls — exactly the "customer summary spanning Accounts, Loans, Cards" scenario from Section 8's Feign topic, but potentially handled at the gateway/BFF layer instead of inside one of the domain services. Reduces the number of round-trips a client needs to make, at the cost of introducing some orchestration logic outside the pure domain services.

Backend for Frontend (BFF)

Instead of one single, generic gateway serving every client type identically, run separate gateway instances tailored to each client type — a mobile BFF returning a lean, mobile-optimized payload, a web BFF returning a richer response shape suited to a browser SPA, potentially a partner-API BFF with entirely different auth/rate-limiting rules for third-party integrators. Each BFF is owned by (or closely aligned with) the team building that specific client, letting client-specific response shaping evolve independently without a single shared gateway becoming a bottleneck or a compromise-for-everyone.

API Gateway vs Service Mesh — the other extremely common interview question

These solve different halves of the traffic problem and are complementary, not competing: an API Gateway (this section) handles north-south traffic — external clients entering the system. A Service Mesh (e.g. Istio, Linkerd — typically covered in a dedicated later section, often paired with Kubernetes) handles east-west traffic between internal services via lightweight sidecar proxies attached to every service instance, providing mTLS, fine-grained traffic policies, and observability for internal calls specifically. Larger organizations frequently run both together: a gateway at the edge, a mesh internally — a very common "compare and contrast" question once a candidate has demonstrated gateway fundamentals.

What is the Backend for Frontend (BFF) pattern?

Running separate, client-type-specific gateway instances (e.g. one for mobile, one for web) instead of one generic gateway serving every client identically — letting each BFF shape responses and apply policies optimized for its specific client type, owned independently.

What's the difference between an API Gateway and a Service Mesh?

An API Gateway handles north-south traffic — the entry point for external clients into the system. A Service Mesh handles east-west traffic — communication between internal services — typically via sidecar proxies, providing things like mutual TLS and fine-grained internal traffic policies. They address different traffic shapes and are commonly used together, not as alternatives to each other.

When would you specifically recommend adopting the BFF pattern over a single shared gateway, and what's the tipping point?

BFF becomes worth the added operational cost when client-specific response shaping/optimization needs genuinely diverge — e.g. a mobile client needing a deliberately lean, low-bandwidth payload versus a web dashboard needing a much richer, more complete response, or different clients needing meaningfully different auth flows (a mobile app using OAuth2 device flow versus a web app using a standard authorization code flow) — such that a single shared gateway would otherwise need an increasing amount of conditional, client-type-branching logic to serve everyone reasonably well. The tipping point is usually when that shared-gateway conditional complexity starts to feel like it's fighting the single-responsibility principle, or when different client-facing teams want to iterate on their own gateway-level concerns independently without coordinating through one shared, centrally-owned gateway codebase — at that point, splitting into BFFs restores team autonomy at the cost of some duplicated cross-cutting infrastructure across the BFF instances (often mitigated by extracting genuinely shared logic — auth validation, rate limiting — into a shared library or a thin layer both BFFs sit behind).

In a system using both an API Gateway and a Service Mesh, where does responsibility for something like rate limiting actually live?

Typically split by traffic direction and granularity: the API Gateway enforces coarse-grained, client-facing rate limiting (e.g. "this API key gets 1000 requests/minute total across the whole system") since it's the one place that sees the complete picture of an external client's overall usage. A Service Mesh can additionally enforce fine-grained, service-level traffic policies internally (e.g. "no single caller should exceed X requests/second specifically against the Loans service's `/api/create` endpoint, regardless of which upstream service or gateway route it came through"), which protects individual services from internal traffic spikes (a runaway retry loop in one service hammering another) that never even involve external client behavior at all and therefore wouldn't be visible to gateway-level rate limiting. The two layers are complementary — the gateway protects the system's edge and overall external usage budgets, the mesh protects individual internal services from each other.

How would you design rate limiting at the gateway to be both effective and fair across many API consumers — what algorithm would you pick and why?

The two most common production choices are token bucket and sliding window log/counter. Token bucket (each client has a bucket refilling at a steady rate, each request consumes a token, requests are rejected/queued when the bucket is empty) is popular because it naturally allows short bursts up to the bucket capacity while still enforcing a steady average rate over time — a good fit for typical API traffic that's naturally bursty rather than perfectly uniform. A fixed window counter is simpler to implement but has a well-known edge-case flaw (a client can send double its allowed rate by timing requests around a window boundary — e.g. maxing out the end of one window and the start of the next); a sliding window (log-based or weighted-counter approximation) fixes this at some added implementation/storage cost. Spring Cloud Gateway ships a built-in `RequestRateLimiter` filter backed by Redis implementing a token-bucket-style algorithm out of the box, which is the practical default most teams reach for rather than hand-rolling rate limiting logic themselves.

Generating and Pushing Docker Images with Spring Cloud Gateway Changes

The gateway becomes another containerized service, following the exact Section 4 workflow.

The new Gateway Server module gets its own Docker image, built and pushed to Docker Hub via whichever build approach the team standardized on (Dockerfile/Buildpacks/Jib from Section 4), tagged for this section (e.g. `:s9`). No image-build-specific changes are needed for the reactive WebFlux stack — as established back in Section 4, containerization is orthogonal to the application's internal architecture.

Does the gateway's use of WebFlux instead of traditional Spring MVC change how it needs to be containerized?

No — the same Dockerfile/Buildpacks/Jib approaches from Section 4 work identically regardless of which web stack the application uses internally; containerization packages the JAR and its runtime dependencies, which is orthogonal to whether that JAR happens to be a reactive or blocking application.

Given the gateway's high-throughput, latency-sensitive role, does anything about its container resource allocation deserve special consideration compared to a typical backend service?

Yes, worth thinking about explicitly: since every external request passes through it, the gateway often benefits from being provisioned with headroom for burst traffic and horizontal autoscaling tuned more aggressively than a typical internal service, given it's the first point of contention under a traffic spike. Its reactive, non-blocking nature (topic 123) means it can handle high concurrency with relatively modest CPU/memory footprint per instance compared to a blocking service handling similar request volume, but genuinely CPU-bound work at the gateway (heavy request/response transformation, complex filter logic) can still become a bottleneck even in a non-blocking model — reactive avoids thread-blocking on I/O waits, it doesn't make CPU-bound work free. Production capacity planning for a gateway typically treats it as a distinct tier from regular services, monitored and scaled based on its own specific traffic and latency characteristics rather than assuming it behaves like an average backend service.

The most important production-hygiene change in this file, easy to overlook

Notice accounts (and, equally, loans/cards) no longer publishes a ports: mapping to the host at all. This is exactly topic 121/122's argument made concrete in infrastructure: internal services should only be reachable from other containers on the shared Docker network (via service name, as established since Section 4), never directly from outside Docker entirely. Only gatewayserver exposes a host port — it is now the sole external entry point into the whole system, matching the architecture diagrammed back in topic 122 exactly. Leaving every service's port published, even after adding a gateway, is a real, easy-to-make mistake that quietly defeats the entire point of this section.

Why should accounts, loans, and cards stop publishing their ports to the host once a gateway is in place?

Because the gateway is now meant to be the sole external entry point into the system — internal services should only be reachable from other containers on the shared Docker network (via service name), not directly from outside Docker. Leaving their ports published would let external clients bypass the gateway entirely, undermining every centralized concern (auth, rate limiting, logging) it's meant to enforce.

Does removing published ports for internal services actually provide meaningful security, or is it a superficial fix, given they're still reachable within the Docker network?

It's a meaningful, real layer of defense-in-depth rather than a complete security solution on its own — it eliminates the specific, easy attack vector of a client on the host machine's network (or, in a real cloud deployment, anyone who can reach the host's IP directly) hitting an internal service's port and bypassing the gateway entirely, which is a genuinely common and embarrassingly simple misconfiguration to have in production if overlooked. It does NOT, by itself, protect against a compromised container on the same Docker network calling other internal services directly (lateral movement within the network), which is precisely the gap a Service Mesh's mTLS and fine-grained internal traffic policies (mentioned in topic 132's callout) are designed to close at a deeper layer. In a real production deployment (not just Compose), this same principle scales up via network policies/security groups restricting which internal components can reach which others, with the gateway remaining the only component with an internet-facing load balancer or ingress point in front of it — port-hiding in Compose is a simplified, local-dev-scale illustration of that same production network-segmentation principle.
