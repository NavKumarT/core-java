Quick Introduction to Kubernetes Ingress

The problem with exposing every Service on its own load balancer, and the one-sentence answer: Ingress.

The exposure problem

So far we exposed the Gateway with a LoadBalancer Service. That works for one entry point, but imagine exposing a website, an API, an admin console and Grafana: one cloud load balancer + one public IP per Service, each billed, each needing its own TLS certificate and DNS record, and each only operating at Layer 4 (TCP/UDP) — it cannot route by hostname or URL path.

Ingress in one sentence

Ingress is a Kubernetes API object that defines Layer-7 (HTTP/HTTPS) routing rules — “requests for api.eazybank.com/accounts go to Service accounts” — and an Ingress Controller is the component that reads those rules and implements them with a real reverse proxy/load balancer. Remember

Ingress = rules (API object). Ingress Controller = engine that enforces them. Without a controller installed, an Ingress object does nothing.

What is a Kubernetes Ingress?

An API object defining HTTP/HTTPS routing rules (host and path based) from outside the cluster to Services inside it, typically also handling TLS termination.

Why do we need Ingress when we have LoadBalancer Services?

A LoadBalancer Service creates one external load balancer per Service at Layer 4. Ingress lets many Services share a single entry point and adds Layer-7 routing, TLS termination and virtual hosting, reducing cost and complexity.

Is Ingress enough by itself?

No. You must install an Ingress Controller (NGINX, Traefik, HAProxy, cloud-provided, etc.); the Ingress resource is only configuration it reads.

Which API group and version is Ingress in?

networking.k8s.io/v1 (GA since Kubernetes 1.19).

Does Ingress route traffic between internal microservices?

No; it handles external (north-south) traffic entering the cluster. Internal (east-west) traffic uses Services (or a service mesh).

What is the difference between Ingress and a Service of type LoadBalancer?

LoadBalancer is an L4 construct that provisions an external load balancer for one Service. Ingress is an L7 abstraction implemented by a controller (itself usually exposed via one LoadBalancer Service) that multiplexes many hostnames/paths to many Services. They are complementary.

Why is Ingress often called a “leaky” or limited abstraction?

The spec covers only basic host/path routing and TLS; everything else (rewrites, timeouts, auth, rate limiting, canary) is controller-specific annotations, which makes manifests non-portable and hard to validate. That limitation motivated the Gateway API.

How does a request reach a Pod via Ingress?

DNS resolves the hostname to the load balancer IP; the LB forwards to the Ingress Controller Pods (via NodePort or container-native LB); the controller matches host/path to a backend Service and proxies to one of its Pod endpoints (often directly to Pod IPs from the EndpointSlices, bypassing kube-proxy).

Common Ingress problems

Missing/incorrect ingressClassName (no controller picks it up); path rewrite surprises (/eazybank prefix forwarded to the backend); Service port mismatch; backend Pods not Ready (503/502); TLS Secret in the wrong namespace; DNS not pointing to the controller’s LB IP; annotations specific to a different controller being silently ignored.

What does an Ingress Controller do?

Watches Ingress (and Service/Endpoint/Secret) objects, translates them into proxy configuration, and routes external HTTP(S) traffic to the right Service/Pod, usually terminating TLS.

What are the three pathTypes?

Exact, Prefix and ImplementationSpecific.

How do you enable HTTPS on an Ingress?

Create a TLS Secret (kubernetes.io/tls) with certificate and key, reference it in spec.tls; automate issuance/renewal with cert-manager.

What is an IngressClass?

A cluster resource naming a controller implementation; an Ingress selects it with ingressClassName so multiple controllers can coexist.

How do you route by hostname vs by path?

rules[].host for name-based virtual hosting and paths[] within a rule for URL-path routing.

Why do we use annotations on Ingress?

To configure controller-specific features not covered by the core spec (rewrites, timeouts, rate limiting, auth, canary).

Explain how an Ingress Controller can bypass kube-proxy.

Controllers watch EndpointSlices and route directly to Pod IPs (with their own LB algorithm, keep-alive and health handling), so requests don’t pass through the Service ClusterIP/DNAT. This allows better balancing, sticky sessions, retries and WebSocket handling.

How would you do TLS termination vs passthrough vs re-encryption?

Termination: TLS ends at the controller, plain HTTP to Pods (simplest, cert at the edge). Passthrough: controller forwards the encrypted stream by SNI without decrypting (needs L4 support, app handles TLS). Re-encryption: terminate at the edge and open a new TLS connection to the backend (end-to-end encryption inside the cluster, or use a mesh mTLS).

Why is the Gateway API considered the successor to Ingress?

It separates roles (GatewayClass by infra provider, Gateway by cluster operator, Routes by app developers), supports header/query matching, weighted traffic splitting, TCP/UDP/gRPC/TLS routes, cross-namespace references with explicit grants, and standardises features that used to be annotations. It is the long-term direction, and Ingress is feature-frozen.

How do you do zero-downtime config changes and rollout of the controller itself?

Run multiple controller replicas with PodDisruptionBudgets and anti-affinity, readiness probes, graceful shutdown (connection draining), maxUnavailable: 0 rolling updates, and an external LB health check; controllers hot-reload config rather than restarting processes.

How would you design ingress for multiple teams on one cluster?

Per-team namespaces with IngressClasses or Gateway API Routes attached to a shared Gateway with allowedRoutes restrictions, admission policies that restrict hostnames/annotations (Kyverno/Gatekeeper), quotas, and centrally-managed TLS (cert-manager) and WAF.

Do you need both Ingress and Spring Cloud Gateway?

Often yes: Ingress is the generic, infrastructure-owned front door; Spring Cloud Gateway holds application-level edge logic owned by the dev team. Small systems may expose the Gateway directly via a LoadBalancer; very simple ones may let Ingress route straight to services and skip the Gateway.

Double handling

Duplicating rate limiting, retries or timeouts at Ingress, Gateway and mesh multiplies effective retries (3×3×3 requests on failure) and creates conflicting timeouts. Decide one owner per concern and align timeouts (outer ≥ inner).

List the main benefits of Ingress.

Single entry point and IP, L7 host/path routing, TLS termination, name-based virtual hosting, cost reduction vs many load balancers, centralised edge policies and observability.

What kinds of traffic does Ingress manage?

External HTTP/HTTPS traffic entering the cluster (north-south), including WebSockets and gRPC with a supporting controller. It is not for arbitrary TCP/UDP or internal east-west traffic.

What is north-south vs east-west traffic?

North-south: traffic between external clients and the cluster. East-west: traffic between services inside the cluster.

How does Ingress relate to an API gateway?

Ingress is a generic Kubernetes edge router; an API gateway (Spring Cloud Gateway, Kong) adds application-level concerns like OAuth2 validation, request transformation and aggregation. They are often layered.

Where should TLS be terminated?

Commonly at the Ingress/Gateway edge; add re-encryption or mesh mTLS inside the cluster if end-to-end encryption is required.

Design the edge for a production microservice platform on Kubernetes.

Cloud LB → Ingress/Gateway API with TLS (cert-manager), WAF/DDoS protection (Cloud Armor/Shield), coarse host/path routing → API gateway (auth, rate limit, aggregation) → services with NetworkPolicies and mesh mTLS. Observability at each hop with correlated trace IDs; separate public and internal gateways; HA controllers across zones.

How do you handle non-HTTP traffic such as Kafka or PostgreSQL from outside the cluster?

Avoid exposing them publicly; if needed use a dedicated LoadBalancer Service (with source IP restrictions), a TCP route in Gateway API or controller TCP passthrough, or a private connection (VPN/PrivateLink). Prefer keeping them internal.

How do you implement canary releases at the edge?

Gateway API HTTPRoute weighted backendRefs or controller canary features (header/cookie/weight), combined with metrics-driven promotion (Argo Rollouts/Flagger) and automatic rollback on SLO regression.

What are the security risks at the ingress layer and mitigations?

Exposed admin UIs, missing TLS, request smuggling, oversized bodies, header spoofing (X-Forwarded-*), misrouted hosts and over-permissive annotations (configuration snippets). Mitigate with WAF, strict host rules, trusted proxy settings, disabling snippet annotations, request limits, up-to-date maintained controllers, and policy admission control.

Introduction to Service Mesh & Its Capabilities

The cross-cutting network problems of microservices and the infrastructure layer designed to solve them without touching application code.

The problem: network concerns scattered across every service

In a microservice system every call between services must be secure (encrypt, authenticate), reliable (timeouts, retries, circuit breaking), observable (metrics, traces, access logs), and controllable (canary, routing, access policy). Implementing these in each service means libraries (Resilience4j, Spring Security, Micrometer, Spring Cloud LoadBalancer) in every codebase, every language, every team — with inconsistent versions and behaviour.

What is a service mesh?

A service mesh is a dedicated infrastructure layer that handles service-to-service communication transparently. It deploys a proxy next to every workload (the sidecar pattern) that intercepts all inbound and outbound traffic, plus a control plane that configures those proxies. The application keeps making plain calls like http://loans:8090; the proxy adds the capabilities.

Sidecar vs ambient

Sidecars give strong per-Pod isolation but cost memory/CPU per Pod and require restarts to inject/upgrade. Ambient mode splits L4 (secure overlay, mTLS via ztunnel per node) from L7 (waypoint proxies only where needed), reducing overhead. Both are valid; know the trade-off.

Do you need a mesh?

A mesh pays off with many services, strict zero-trust/compliance needs, polyglot stacks, or demanding traffic management. For a handful of Spring services, Spring Cloud + Kubernetes NetworkPolicies + Ingress may be enough. Don’t adopt a mesh for résumé reasons.

Double resilience

Retries configured in the app (Resilience4j), Gateway and mesh multiply: 3 × 3 × 3 = 27 attempts against a failing dependency, amplifying the outage. Pick one layer for retries/timeouts, keep circuit breakers where fallbacks live, and align timeouts.

What is a service mesh?

A dedicated infrastructure layer, typically sidecar proxies plus a control plane, that manages service-to-service communication — security (mTLS), traffic routing, resilience and observability — without changing application code.

What problems does a service mesh solve?

Consistent encryption/authentication, retries/timeouts/circuit breaking, traffic shaping and observability across all services and languages, without each team re-implementing them.

What is the sidecar pattern?

Running a helper container (the proxy) in the same Pod as the application so it shares the network namespace and transparently intercepts traffic.

What is the difference between data plane and control plane?

The data plane is the proxies that actually carry traffic; the control plane configures them (routes, certificates, policies) and collects telemetry.

Name some service mesh implementations.

Istio, Linkerd, Cilium Service Mesh, Consul Connect, Kuma.

Does a service mesh replace Resilience4j?

Partially. It covers generic retries/timeouts/circuit breaking at network level, but cannot provide business fallbacks (cached data, default responses), so many teams keep Resilience4j for fallbacks and let the mesh handle the rest.

Explain how traffic is transparently intercepted by the sidecar.

An init container (or the CNI plugin) installs iptables/nftables rules in the Pod’s network namespace redirecting all inbound traffic to the proxy’s inbound port and all outbound traffic to its outbound port. The proxy applies policy, then connects to the destination, so the app is unaware. In ambient mode the node’s ztunnel intercepts traffic via redirection instead of per-Pod sidecars.

Compare Istio sidecar mode, ambient mode and Linkerd.

Istio sidecar: Envoy per Pod, richest features, highest overhead/complexity. Istio ambient: per-node ztunnel (L4, mTLS) plus optional per-namespace waypoint proxies (L7), lowering resource cost and removing restarts for onboarding. Linkerd: very light Rust proxy, simple operations, fewer features (less rich traffic management and policy). Choose by feature needs vs operational budget.

What is the performance and operational cost of a mesh?

Extra proxy hops add latency (~ms) and CPU/memory per Pod (Envoy ~50–100 MiB+), control-plane resources, more moving parts to upgrade/debug, certificate and config-propagation failure modes, and complexity in startup/shutdown ordering (app starting before sidecar ready, jobs not terminating because the sidecar keeps running). Measure and budget it.

How do mesh circuit breakers differ from Resilience4j’s?

The mesh implements connection-pool limits and outlier detection (ejecting unhealthy endpoints from the LB pool after consecutive errors) at the proxy for any protocol. Resilience4j wraps individual calls with configurable failure-rate thresholds, half-open states and fallback functions within the application context. They solve overlapping but different layers.

How would you introduce a mesh incrementally?

Install the control plane, onboard one namespace in permissive mode, verify metrics and traffic, enable mTLS permissive → strict gradually, add authorization policies (default-deny with explicit allows), then add traffic management; keep observability dashboards and rollback (remove injection label) ready.

Life of a request through the mesh

  • App in Pod A calls http://loans:8090 → iptables redirects to Pod A’s Envoy.
  • Envoy consults its xDS-delivered config: route (VirtualService), endpoints (service registry), policy; picks a Loans Pod IP (least-request/round-robin).

  • Pod B’s Envoy verifies identity, evaluates AuthorizationPolicy, forwards to the Loans container on localhost.
  • Both proxies emit metrics, access logs and trace spans.
Gotchas

Pods must be restarted after enabling injection; sidecar start-order issues (app calls out before proxy ready: use holdApplicationUntilProxyStarts); Jobs/CronJobs hang because the sidecar never exits; port names/protocol prefixes (http-, grpc-) matter for L7 handling; health probes through STRICT mTLS (Istio rewrites kubelet probes); headless Services and StatefulSets need special handling.

What are the main components of a service mesh?

A data plane of sidecar proxies (e.g. Envoy) and a control plane (e.g. istiod) that distributes configuration and certificates, plus ingress/egress gateways and telemetry tools.

What does istiod do?

It converts routing/policy configuration into proxy configuration (xDS), acts as the certificate authority for workload mTLS identities, injects sidecars via a webhook and validates config.

What is Envoy?

An open-source high-performance L4/L7 proxy used as the data plane in Istio and many other systems; configured dynamically via xDS APIs.

How do you add a Pod to the Istio mesh?

Label the namespace for injection (istio-injection=enabled) and restart the Pods so the sidecar is injected (or use ambient mode labels).

What are VirtualService and DestinationRule?

VirtualService defines how requests are routed (match, weights, retries, timeouts); DestinationRule defines policies for traffic to a destination (subsets, load balancing, outlier detection, TLS settings).

What is Kiali?

A console for Istio that visualises the service graph, traffic, health and validates Istio configuration.

How does Envoy get its configuration and what is xDS?

xDS is the family of discovery APIs (LDS listeners, RDS routes, CDS clusters, EDS endpoints, SDS secrets) over gRPC streams. istiod watches Kubernetes and Istio resources, computes per-proxy config and pushes incremental updates, so routing and endpoints change without restarting proxies.

How do you do a canary rollout with Istio and ensure safe promotion?

Deploy v2 with a distinct version label, define subsets in a DestinationRule, shift VirtualService weights gradually (1% → 10% → 50% → 100%) based on Prometheus SLO metrics, automated by Flagger/Argo Rollouts, with instant rollback by restoring weights. Use header-based routing for internal testers first.

How can the mesh break your application and how do you diagnose it?

Common failures: 503 UC/UF response flags from outlier ejection or mTLS mismatch, protocol sniffing errors, probes failing, connection resets from idle timeouts. Diagnose with istioctl proxy-status, istioctl proxy-config, istioctl x describe pod, Envoy access logs with response flags, and Kiali validations.

How do you secure the mesh control plane?

Restrict access to istio-system and Istio CRDs via RBAC, use admission policies for who may create VirtualServices/AuthorizationPolicies, enable strict mTLS, keep istiod and proxies patched, limit egress, and protect the root CA (plugin your own CA or cert-manager istio-csr).

Where TLS fits in our platform

Edge: TLS terminates at the Ingress/Gateway (public certificate via cert-manager). Inside: plain HTTP is the default on Kubernetes; mTLS (next topic) encrypts and authenticates east-west traffic, usually handled by the service mesh instead of by every Spring app.

Frequent TLS errors

Hostname/SAN mismatch (CN alone is not used), expired certificate, missing intermediate in the chain, client does not trust the private CA (truststore), clock skew (“not yet valid”), protocol/cipher mismatch, SNI missing (wrong certificate served).

What problems does TLS solve?

Confidentiality (encryption), integrity (tamper detection) and authentication (server identity via certificates) of network communication.

Symmetric vs asymmetric encryption — how does TLS use both?

Asymmetric cryptography (certificates, signatures, key exchange) authenticates the server and establishes a shared secret; symmetric encryption with the derived session keys then protects the actual data because it is much faster.

What is a digital certificate?

An X.509 document binding a public key to an identity (hostnames in SAN), signed by a Certificate Authority so others can verify it.

What is a Certificate Authority and chain of trust?

A CA signs certificates. Clients trust a set of root CAs; a server certificate is trusted if a valid chain of signatures leads to one of those roots.

What happens during a TLS handshake (summary)?

Client and server agree on version/cipher, the server proves its identity with a certificate, both derive shared session keys using key exchange, they verify the handshake with Finished messages, then exchange encrypted application data.

What are SNI and ALPN?

SNI (Server Name Indication) tells the server which hostname the client wants so it can present the right certificate; ALPN negotiates the application protocol (h2 or http/1.1).

Why does TLS 1.3 only allow ephemeral key exchange and why is that important?

Because ephemeral (EC)DHE gives forward secrecy: compromise of the server’s long-term private key doesn’t expose past session traffic. TLS 1.3 also removed legacy features that enabled downgrade/padding oracle attacks, shortened the handshake to 1 RTT and encrypts the certificate exchange.

Walk through certificate validation in detail.

Build a path from leaf to a trusted root; verify each signature with the issuer’s public key; check validity period, key usage/extended key usage (serverAuth), basic constraints (CA flag, path length), name constraints; match the requested hostname against SAN entries (wildcards limited to one label); check revocation (OCSP stapling/CRL) if configured; verify the server’s CertificateVerify signature proving possession of the private key.

What is the risk of 0-RTT in TLS 1.3?

Early data is sent in the first flight using a resumption secret and can be replayed by an attacker, so only idempotent, safe requests may be accepted over 0-RTT; many deployments disable it.

How do you rotate certificates without downtime?

Use short-lived certificates with automated issuance (cert-manager, mesh CA, ACME), reload on file change or SDS push (no restart), overlap validity periods, support multiple trusted CAs during CA rotation, and monitor expiry (Prometheus blackbox/cert-manager metrics).

Why is validating only the CN insufficient and what replaced it?

RFC 6125/modern clients ignore CN for hostname validation; they require SAN entries. Mixing identity in CN risks mismatches and wildcard ambiguity.

What is mTLS?

Mutual TLS: both client and server present certificates and verify each other, so each side authenticates the other in addition to encrypting the channel.

How does mTLS differ from regular TLS?

In regular TLS only the server is authenticated; in mTLS the server also requests and validates a client certificate.

Why is mTLS important for microservices?

It encrypts internal traffic and gives each service a verifiable identity, enabling zero-trust and policy such as “only Accounts may call Loans”.

How does a service mesh provide mTLS?

Its CA issues short-lived workload certificates to every proxy, which establish mTLS automatically between sidecars, with automatic rotation, requiring no application changes.

What are PERMISSIVE and STRICT modes?

PERMISSIVE accepts both plaintext and mTLS (for migration); STRICT only accepts mTLS connections.

Does mTLS authenticate end users?

No, it authenticates services (workloads). End-user identity is handled with JWT/OAuth2 tokens.

Explain SPIFFE/SPIRE and why identity is not based on IP addresses.

SPIFFE defines a standard workload identity (a URI like spiffe://trust-domain/ns/x/sa/y) embedded in an X.509 SVID, and SPIRE is a reference implementation issuing them after attesting the workload. IPs are ephemeral and reused in Kubernetes, so identity must be cryptographic and tied to a workload’s properties (ServiceAccount, namespace).

How are workload certificates issued and rotated in Istio?

The sidecar (pilot-agent) generates a private key and CSR, authenticates to istiod with its projected ServiceAccount token, istiod’s CA signs a short-lived certificate containing the SPIFFE URI SAN, and it is delivered to Envoy through SDS in memory. Before expiry (default ~24h lifetime, renewal at ~half) the agent repeats the process, with no disk keys or restarts.

What are the failure modes of mesh-wide mTLS and how do you mitigate them?

CA/istiod outage prevents new/renewed certs (existing ones keep working until expiry): run HA istiod, monitor cert expiry, protect root CA; non-mesh clients break under STRICT: use PERMISSIVE per-port exceptions or gateways; trust-domain mismatches across clusters: federate trust domains; clock skew; protocol sniffing issues. Maintain break-glass procedures and rollout gradually.

How do AuthorizationPolicies use mTLS identity, and what is a sound default?

The proxy exposes the verified peer principal (cluster.local/ns/<ns>/sa/<sa>) to rules. A sound default is deny-all per namespace (empty ALLOW policy) plus explicit ALLOW rules per service pair (principal + method + path), optionally combined with JWT claims from RequestAuthentication for user-level checks.

mTLS at the mesh vs in the application: when would you do both?

For defence in depth in regulated environments (end-to-end encryption inside the Pod boundary, or traffic leaving the mesh), or when workloads span clusters/VMs that the mesh does not cover. Otherwise the mesh layer alone is simpler and less error-prone.

Optimizing Microservices Development with Spring Boot BOM — Part 1

The dependency/version-drift problem across microservices and what a Bill of Materials (BOM) is.

The problem

Our platform has Accounts, Loans, Cards, Gateway, Config Server, Message… each is its own Maven project with its own pom.xml. Each pom repeats: the Spring Boot parent version, the Spring Cloud version, versions of springdoc-openapi, MapStruct, Lombok, Testcontainers, Resilience4j, Micrometer/OTel agents, Jib/plugin versions. Over time this causes version drift (Accounts on 3.3.x, Loans on 3.2.x), incompatible transitive dependencies, security patches applied unevenly, and a painful upgrade (edit N files, N pull requests).

What is a BOM?

A Bill Of Materials is a special pom.xml (packaging pom) that contains only a <dependencyManagement> section listing dependencies with tested, compatible versions. Projects import it and then declare dependencies without versions; Maven resolves the version from the BOM. You already use BOMs every day: spring-boot-dependencies (via spring-boot-starter-parent) and spring-cloud-dependencies.

Goals of this part of the course (the “optimisation”)

  • One place to define versions of third-party libraries and your own internal libraries.
  • Consistency: every microservice builds against the same tested set.

Spring Boot’s own promise

Spring Boot’s BOM pins versions of ~hundreds of libraries (Jackson, Hibernate, Tomcat, Micrometer…) that are tested together; overriding one (via a property like jackson-bom.version) is possible but takes responsibility for compatibility.

What is a BOM in Maven?

A POM with a <dependencyManagement> section listing compatible dependency versions, imported by projects so they can declare dependencies without versions.

What problem does a BOM solve in microservices?

Version drift and inconsistent dependencies across many services; it centralises versions so all services use the same tested set and upgrade together.

Name BOMs you already use with Spring.

spring-boot-dependencies (through the starter parent) and spring-cloud-dependencies.

What is the difference between dependencyManagement and dependencies?

dependencyManagement only declares versions/exclusions and adds nothing to the classpath; dependencies declares what the module actually uses (and inherits versions from management).

How do you import a BOM?

Add it inside <dependencyManagement> with <type>pom</type> and <scope>import</scope>.

Why use a BOM instead of a parent POM?

Maven allows a single parent (already taken by Spring Boot); a BOM can be imported in addition to any parent and is focused purely on version alignment.

How does Maven resolve a version when multiple BOMs and the project declare the same artifact?

Explicit <version> on the dependency wins; then the project’s own dependencyManagement entries; then inherited parent management; among imported BOMs the first declared import wins for a given artifact. Verify with mvn help:effective-pom and mvn dependency:tree -Dverbose.

What are the risks of overriding versions managed by Spring Boot’s BOM?

You leave the tested compatibility matrix: binary incompatibilities between Spring libs and the overridden one (e.g. Jackson, Netty, Hibernate), subtle runtime errors. Prefer upgrading Boot, or override via the BOM property mechanism and run the full test suite and security scans.

Parent POM vs BOM vs Gradle platform — compare.

Maven parent: inheritance of everything (single). BOM import: version alignment only (multiple). Gradle’s platform()/enforcedPlatform() is the equivalent of BOM import; dependencyManagement plugin emulates Maven behaviour; version catalogs (libs.versions.toml) are another centralisation mechanism.

How can the BOM approach support supply-chain security?

A central BOM becomes the single place to bump vulnerable transitive versions (CVE remediation), enforce approved library versions with maven-enforcer-plugin (dependencyConvergence, banned dependencies), generate an SBOM (CycloneDX) per build, and drive automated updates (Renovate/Dependabot) in one repository.

  • Plugin versions can’t be managed by importing a BOM — keep those in a parent POM (if you want an org parent) or in each service.
BOM not found

Services resolving eazybank-bom fail with “Non-resolvable import POM” unless it is in the local repository (mvn install done) or published to a remote repository (Nexus/Artifactory/GitHub Packages) that the build can reach — important for CI and Docker builds.

Alternative: multi-module reactor

If all services live in one repository you can make the BOM (or a parent) the root of a multi-module build: mvn -pl accounts -am clean package builds a module and what it depends on in one reactor, no install step needed.

How do you create your own BOM?

Create a Maven project with packaging pom, define version properties and a <dependencyManagement> section (importing Spring Boot/Cloud BOMs and listing other libraries), then mvn install or publish it.

Why does the BOM have <packaging>pom</packaging>?

Because it produces no jar — it only carries metadata (dependency management) for other projects to import.

Can a BOM import other BOMs?

Yes; our BOM imports spring-boot-dependencies and spring-cloud-dependencies, aggregating everything into one import for the services.

Why put versions into properties?

Single place to change, easier overrides and tooling support (versions-maven-plugin, Renovate, Dependabot).

Where does the BOM have to be available for service builds?

In the local Maven repository (mvn install) or in a remote repository the build can access, e.g. Nexus/Artifactory/GitHub Packages for CI.

How do you choose compatible Spring Boot and Spring Cloud versions?

Use the Spring Cloud “supported versions” table: each release train targets specific Boot lines (e.g. 2023.0.x ↔ Boot 3.2/3.3). Mismatches cause startup failures or subtle bugs; encode the pair in the BOM so services cannot mix them.

How would you structure BOM release management for 30 teams?

Treat the BOM as a product: SemVer with changelog, release candidates validated by building a reference set of services in CI, a compatibility test suite, deprecation notices, a channel/latest vs LTS BOM, and automated PRs (Renovate) to consumer repos when a new BOM is published.

What happens with dependency convergence conflicts despite a BOM?

Managed versions apply only to artifacts declared in management; transitive dependencies not listed may still diverge. Use maven-enforcer-plugin dependencyConvergence/requireUpperBoundDeps and add exclusions or management entries to resolve.

Why import spring-boot-dependencies in the BOM instead of using spring-boot-starter-parent?

The starter parent also configures plugins, resource filtering, Java release and UTF-8; but only one parent is allowed. Importing the BOM keeps the parent slot free (e.g. for a corporate parent) at the cost of configuring plugins yourself.

Shared Libraries in Microservices — Part 1

What belongs in a shared library, what absolutely does not, and creating the eazybank-common module.

The duplication problem

Look at Accounts, Loans and Cards: each has an identical ErrorResponseDto, ResponseDto, GlobalExceptionHandler, AuditAwareImpl, ResourceNotFoundException, constants, base entity with audit columns, Feign/Resilience4j configuration and OpenAPI customisation. Copy-paste means a bug fix or a new field must be repeated in every service, and copies slowly diverge.

What is a shared library?

A separate Maven (or Gradle) module, packaged as a jar and published to a repository, containing technical, cross-cutting code that multiple microservices depend on. Each microservice declares it as a normal dependency (version supplied by the BOM).

  • Transitive dependency pollution: the library drags Spring/Jackson versions that conflict with services.
  • Dependency hell and slow evolution because breaking changes require coordinated releases.

Alternatives to a shared jar

(1) Spring Boot starter + auto-configuration (Part 2) for behaviour; (2) OpenAPI / protobuf contracts generated per consumer instead of sharing DTO classes; (3) a platform service (e.g. audit service) accessed via API; (4) copy when code is tiny and stable — duplication is cheaper than the wrong abstraction.

What is a shared library in a microservices context?

A separately built and versioned jar holding cross-cutting technical code (error DTOs, exception handling, audit config, utilities) that multiple services depend on.

What kind of code should go into a shared library?

Stable, technical, cross-cutting code such as common error response formats, global exception handling, audit support, constants and utilities — not business logic or domain entities.

Why is sharing domain entities across services an anti-pattern?

It couples services at compile time and often at the database level, destroying independent deployability and data ownership.

What is the “distributed monolith”?

A system split into services that cannot be changed or deployed independently because of tight coupling — for example via a big shared domain library or shared database.

How do you avoid breaking all services when the library changes?

SemVer with backward-compatible changes, deprecation periods, extensive tests, and letting each service upgrade the library version on its own schedule through the BOM.

Why shouldn’t the shared library be a Spring Boot fat jar?

A repackaged executable jar nests classes under BOOT-INF, so other projects can’t use them as a dependency; the library should be a plain jar (no repackage goal).

When is duplication better than a shared library?

When the code is small, likely to diverge per service, or when sharing would couple release cycles. “Duplication is far cheaper than the wrong abstraction.” Apply the rule of three and share only stable, truly common technical code.

How would you evolve a shared library without lockstep upgrades?

Keep backward compatibility (additive API, deprecations with @Deprecated(forRemoval) and release notes), run API compatibility checks (japicmp/revapi) in CI, publish new minor versions frequently, support N-1 majors for a window, and use Renovate to propose upgrades. Feature toggles in auto-configuration let services opt into new behaviour.

Shared DTOs between services: contract-first alternatives?

Use OpenAPI/AsyncAPI/protobuf schemas as the contract; each consumer generates its own client models (OpenAPI Generator, Spring Cloud Contract, Pact consumer-driven contracts), so a provider’s model changes don’t force a recompile of consumers and incompatibilities are caught by contract tests.

What governance does a shared library need in a large organisation?

Clear ownership (a platform/enablement team), contribution guidelines, SLAs for fixes, versioning/deprecation policy, documentation and examples, compatibility test harness against reference services, and metrics on adoption/version spread.

Because component scanning is limited to the application’s base package; the library lives in a different package, so its annotated classes aren’t scanned.

How can you make Spring discover the library’s beans?

Either extend component scanning (scanBasePackages), @Import a configuration class, or — best — provide auto-configuration registered in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports.

How do you stop the library from being repackaged as an executable jar?

Do not run the Spring Boot Maven plugin’s repackage goal for the library module (or skip it); keep it a plain jar.

How do services get the library version?

Declare the dependency without a version; the version comes from the BOM’s dependencyManagement.

How do you publish the library?

mvn install for local use and mvn deploy to a repository manager (Nexus, Artifactory, GitHub Packages) for CI and other developers.

What does @ConditionalOnMissingBean achieve?

Lets the service override a library bean by defining its own; the library’s default backs off, giving flexibility.

Explain how Spring Boot 3 discovers auto-configurations.

At startup @EnableAutoConfiguration (inside @SpringBootApplication) uses ImportCandidates to read all META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports files on the classpath, loads the listed classes, sorts them (@AutoConfiguration(before/after)), and processes their @Conditional annotations to decide which beans to register. spring.factories registration was removed for auto-config in Boot 3.

How would you design a starter that supports both servlet and reactive applications?

Separate auto-configuration classes guarded by @ConditionalOnWebApplication(type=SERVLET/REACTIVE) and @ConditionalOnClass, optional dependencies on the respective web stacks, and shared pure-Java core in a separate module; test both with WebApplicationContextRunner and ReactiveWebApplicationContextRunner.

How do you prevent transitive dependency conflicts introduced by a shared library?

Mark framework dependencies provided/optional, import the BOM for managed versions, use the enforcer plugin (dependencyConvergence, banned dependencies) in the library’s CI, avoid shading, and test the library against a matrix of supported Boot versions.

How would you roll out a breaking change in the shared library?

Release a new major (2.0.0) alongside the old line, provide migration docs and OpenRewrite recipes where possible, deprecate old APIs in 1.x with warnings, update the BOM with the new version as opt-in, upgrade services incrementally with feature flags, and retire 1.x after a deadline.

Compare a shared starter to a sidecar or platform service for cross-cutting concerns.

A starter is in-process: fast, language-specific (JVM), version coupling. A sidecar/mesh or platform service is language-agnostic and updated independently, but adds latency/operational complexity. Use starters for JVM-specific cross-cutting code (error format, audit hooks), meshes/platform services for network and capability concerns.

Decision rules

  • Public hostname + TLS + WAF → Ingress/Gateway API. Auth/rate-limit/aggregation for your APIs → Spring Cloud Gateway. Encrypt + authorize internal calls in many languages → mesh mTLS.
  • One owner per resilience concern (retries/timeouts) to avoid retry storms.
  • Align versions with a BOM; share build conventions with a parent; share runtime technical code with a starter; share API shapes with contracts.
  • If a shared change forces all services to redeploy, it’s a distributed monolith smell.

Ingress vs API gateway vs service mesh in one sentence each?

Ingress: generic L7 entry into the cluster. API gateway: application-aware front door for APIs. Service mesh: transparent security and traffic control between services.

BOM vs parent POM?

A BOM only aligns dependency versions and can be imported many times; a parent provides inheritance of build configuration and can be used once.

How do shared libraries’ beans get registered in Spring Boot 3?

Via auto-configuration listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports.

Design the security architecture for the EazyBank platform from edge to database.

Edge: WAF/DDoS + TLS at Ingress/Gateway API; Spring Cloud Gateway validates Keycloak JWTs and applies rate limits; mesh mTLS with default-deny AuthorizationPolicies between services; NetworkPolicies as a second layer; secrets via external manager; least-privilege DB credentials per service with TLS; audit logging and observability; supply-chain controls via BOM, SBOM, image scanning and signed images.

What would make you remove a service mesh after adopting it?

Cost/complexity outweighing benefits: small service count, no multi-language need, operational burden (upgrades, debugging), performance overhead, or capabilities available more simply via ingress, network policies and libraries. Evaluate with metrics on incidents caused by the mesh vs problems solved.
