Configuration Management in Microservices

Almost every real production incident traced back to "config" falls into one of two buckets: a secret leaked because it lived in source control, or a service came up with the wrong value because config drifted silently between environments. This is one of the highest-leverage topics for both real production work and interviews — it's where "I can write a CRUD API" turns into "I understand how a fleet of services stays correctly configured, secured, and updatable without downtime." This section goes from the three ways to read a property inside one Spring Boot app, all the way to a centralized, git-backed, encrypted, runtime-refreshable Spring Cloud Config setup wired into Docker Compose with proper liveness/readiness probes.

Introduction to Configuration Management Challenges Inside Microservices

Why config gets exponentially harder as services and environments multiply.

What counts as "configuration"

Anything that varies by environment or needs to change without a code change: database URLs and credentials, external service endpoints, timeouts/retry counts, feature flags, logging levels, message broker connection details, third-party API keys. In a single monolith, this was already a manageable problem (one `application.properties`, maybe a few environment-specific overrides). In a microservices system, the same problem multiplies along two axes at once.

The concrete problems

  • Config is scattered — bundled inside each service's own JAR/codebase, with no single place to see "what is Accounts's production DB URL right now" without opening that specific service's repo.
  • Changing config requires a redeploy — a property baked into a packaged JAR means "update a timeout value" and "ship new business logic" go through the exact same slow, risky release pipeline, even though they're fundamentally different kinds of change.
  • Secrets in source control — database passwords and API keys committed into `application.yml` are visible to anyone with repo read access, present in git history forever (even if later "removed"), and hard to rotate without a code change.
  • No audit trail dedicated to config changes — "who changed the payment gateway timeout, when, and why" is buried in generic commit history mixed with unrelated code changes, not a first-class, config-specific audit log.
  • Config drift — with no single source of truth, it's easy for QA and production to silently diverge in ways nobody intended, discovered only when something breaks in one environment but not another.
  • No dynamic refresh — even a trivial value change (bump a rate limit) needs a full application restart, causing avoidable downtime/disruption for changes that shouldn't need it.
Where this section is headed

Why is configuration management harder in microservices than in a monolith?

A monolith has one deployable unit and typically one config file per environment. Microservices multiply this: N independently deployed services each need their own config across M environments, so the problem scales as N×M rather than staying constant — and without centralization, keeping all those configs consistent and secure becomes a real operational burden.

Why is committing database passwords into application.yml a problem?

It exposes the secret to anyone with source-control read access, leaves it permanently in git history even after later removal (removing a file doesn't erase prior commits), and makes rotating the secret require a code change and redeploy rather than an independent operational action.

Beyond the operational annoyance, what's the actual production-risk argument for treating config changes and code changes as different classes of deployment?

Code changes carry business-logic risk and typically go through a full test/review/staged-rollout pipeline appropriately. Config changes are often urgent and low-risk-if-correct (bump a connection pool size, flip a feature flag, update a downstream timeout during an incident) — but if the only path to change them is "redeploy the whole service," you either slow down urgent fixes to match the code-release cadence, or you pressure the team into rushing a full redeploy under incident conditions, which is itself a source of new risk (redeploys can fail, cause brief unavailability, or introduce unrelated changes that happened to be sitting in the same branch). Decoupling config changes from code deploys — the core motivation for Spring Cloud Config's dynamic refresh — lets low-risk operational changes ship on their own, faster and safer, timeline.

How Configurations Work in Spring Boot

The Environment abstraction, PropertySources, and the full property-precedence order.

The Environment abstraction

Spring models all configuration through the Environment interface, which is backed internally by an ordered list of PropertySource objects (MutablePropertySources). Each property source represents one origin of key-value configuration — command-line args, system properties, OS environment variables, `application.yml`, and more. When any part of Spring resolves a property, it walks this ordered list and returns the value from the first source that has it — which is exactly the mechanism behind Spring's property precedence.

Full property precedence order (highest to lowest)

  1. Command-line arguments (--server.port=9090)
  2. SPRING_APPLICATION_JSON (properties embedded as inline JSON in an env var)
  3. Servlet init parameters
  4. JNDI attributes
  5. Java System properties (-Dserver.port=9090)
  6. OS environment variables (SERVER_PORT=9090)
  7. RandomValuePropertySource
  8. Profile-specific application config outside the packaged jar (application-{profile}.yml in the current directory)
  9. Profile-specific application config packaged inside the jar
  10. Application config outside the jar (application.yml in the current directory)
  11. Application config packaged inside the jar
  12. @PropertySource annotations on @Configuration classes
  13. Default properties (set via SpringApplication.setDefaultProperties)
The one rule that matters most in practice

Anything set via command-line arguments or environment variables always wins over anything in a packaged `application.yml` — which is precisely what makes "build one immutable image, configure it differently per environment via env vars at deploy time" (the 12-factor app pattern, and exactly what Docker Compose's `environment:` block does) work correctly without ever needing to rebuild the image per environment.

Relaxed binding

Spring's property binding is deliberately lenient about naming convention — server.port, SERVER_PORT, and server-port all bind to the same underlying property. This exists specifically because different sources have different natural naming conventions (YAML favors kebab-case, environment variables are conventionally SCREAMING_SNAKE_CASE, Java fields are camelCase) — relaxed binding means you don't have to manually transliterate between them.

What is a PropertySource in Spring?

An abstraction representing one origin of key-value configuration data (e.g. command-line args, environment variables, `application.yml`). Spring's `Environment` holds an ordered list of these, and resolves a property by checking them in priority order.

What is relaxed binding?

Spring's tolerance for different naming conventions referring to the same property — `server.port`, `SERVER_PORT`, and `server-port` all resolve to the same value — so config doesn't need to be manually reformatted to match each source's natural convention.

If the same property is defined in application.yml and as an environment variable, which wins?

The environment variable — OS environment variables sit higher in Spring's property precedence order than packaged `application.yml` values.

Why does Spring Boot prioritize command-line arguments and environment variables above the packaged application.yml, architecturally?

This ordering is what makes the 12-factor app principle of "build once, configure per environment" achievable: the same immutable artifact (JAR or container image) can be deployed to dev, QA, and prod with environment-specific values supplied externally at launch time (env vars in a container orchestrator, command-line flags in a systemd unit), without ever needing environment-specific builds. If packaged config took precedence, you'd be forced back into building separate artifacts per environment — reintroducing exactly the "environment inconsistency" and "it works in staging but not prod" problems containerization and externalized config are meant to solve.

How would you debug a situation where a property has an unexpected value and you're not sure which PropertySource is actually supplying it?

Spring Boot Actuator's `/actuator/env` endpoint (with `management.endpoints.web.exposure.include=env`) exposes every active `PropertySource` in priority order along with the resolved value for a given key, letting you see exactly which source is "winning" for that property — invaluable for diagnosing precedence surprises without needing to reason through the full ordering manually or add temporary logging. In production, this endpoint is typically restricted/secured given it can expose sensitive configuration, so teams often gate it behind authentication or disable it outside trusted internal networks.

Reading Configurations Using @Value Annotation

The simplest way to inject a single property — and its real limitations.

Usage
@RestController
public class AccountsController {

    @Value("${build.version}")
    private String buildVersion;

    // with a default value if the property is absent
    @Value("${mail.enabled:false}")
    private boolean mailEnabled;

    // SpEL expression, not just a plain property reference
    @Value("#{'${allowed.origins}'.split(',')}")
    private List<String> allowedOrigins;
}
@Value

Field/parameter-level annotation that injects a resolved property value at bean creation time. The ${...} syntax is a property placeholder; Spring also supports full SpEL (Spring Expression Language) via #{...} for more complex expressions (as in the list-splitting example above). Only works on Spring-managed beans — it does nothing on a plain, manually-instantiated object.

Limitations

  • No compile-time safety — a typo'd property key (`${moil.enabled}`) is only caught at runtime (or not at all, if a default value masks the typo).
  • Verbose at scale — injecting 15 related properties means 15 separate `@Value` fields, with no structural grouping.
  • Awkward for nested/complex structures — binding a list works (as shown) but is clunky via SpEL string-splitting; binding a nested object graph isn't practical at all with `@Value`.
  • Hard to validate — no built-in way to apply Bean Validation constraints to an `@Value`-injected field.
  • Not testable in isolation — since it only resolves inside a Spring context, unit-testing a class using `@Value` without spinning up Spring requires manually setting the field via reflection or a constructor workaround.
How do you provide a default value with @Value if the property might be missing?

Using colon syntax inside the placeholder: `@Value("${property.name:defaultValue}")` — if `property.name` isn't found in any property source, `defaultValue` is used instead.

Does @Value work on a plain Java object created with "new"?

No — `@Value` is processed by a Spring `BeanPostProcessor` during bean initialization, so it only resolves on objects that Spring itself creates and manages as beans; manually instantiating a class with `new` bypasses Spring's lifecycle entirely and the field would remain unresolved (null/default).

Why would a team standardize on @ConfigurationProperties over @Value for anything beyond a couple of standalone values, even though @Value is simpler for a single property?

Beyond the structural/type-safety benefits (covered in the next topic), `@Value` usage tends to scatter related configuration across many unrelated classes — each class grabs just the one or two properties it needs via its own `@Value` fields, with no single place that documents "here is the full shape of this feature's configuration." `@ConfigurationProperties` centralizes a cohesive configuration group into one typed class, which is easier to document, test, validate as a unit, and reason about — especially valuable as a codebase grows and the same config surface is referenced from multiple places.

Reading Configurations Using the Environment Interface

Programmatic, dynamic property access — useful when the key isn't known until runtime.

Usage
@Service
@AllArgsConstructor
public class FeatureFlagService {

    private final Environment environment;

    public boolean isFeatureEnabled(String featureName) {
        // property key built dynamically at runtime — @Value can't do this
        String key = "feature." + featureName + ".enabled";
        return environment.getProperty(key, Boolean.class, false);
    }

    public String requiredValue() {
        // throws IllegalStateException if missing — fail fast instead of silently null
        return environment.getRequiredProperty("payment.gateway.url");
    }

    public boolean isProdProfile() {
        return Arrays.asList(environment.getActiveProfiles()).contains("prod");
    }
}
Environmentorg.springframework.core.env

Injectable interface giving programmatic access to properties and active profiles. getProperty(key) returns null if absent; getProperty(key, defaultValue) supplies a fallback; getRequiredProperty(key) throws if the key is missing — useful for "fail fast at startup" semantics on properties that are truly mandatory. getActiveProfiles()/getDefaultProfiles() expose which profiles are currently active.

When Environment is the right tool over @Value or @ConfigurationProperties

  • The property key itself is only known at runtime (built dynamically, as in the feature-flag example above).
  • You need to check active profiles programmatically (`environment.acceptsProfiles(...)`), e.g. for conditional logic beyond what `@Profile` on a bean can express.
  • You're writing infrastructure/framework-level code that needs generic access to configuration without knowing its shape in advance.
What does environment.getRequiredProperty do differently from getProperty?

`getProperty` returns null (or a supplied default) if the key isn't found. `getRequiredProperty` throws an `IllegalStateException` immediately if the key is missing, which is useful for surfacing a missing mandatory configuration value as a fast, clear startup failure rather than a later, harder-to-diagnose null-related bug.

When would you reach for Environment instead of @Value?

When the property key isn't known until runtime (e.g. built dynamically from a variable), or when you need programmatic access to things like the active profiles list, rather than a single statically-known property resolved at bean-creation time.

Both @Value and Environment ultimately read from the same PropertySources — what's the actual mechanical difference in when/how each resolves a value?

`@Value` resolution happens once, at bean instantiation time, via a `BeanPostProcessor` (`AutowiredAnnotationBeanPostProcessor`/`CommonAnnotationBeanPostProcessor`) that evaluates the placeholder and injects the resolved value directly into the field — after that point, the field holds a static, resolved value for the bean's lifetime (unless the bean itself is `@RefreshScope`, covered in the runtime-refresh topics later). `Environment.getProperty()` is a live, on-demand lookup against the current `PropertySources` every single time it's called — meaning if the underlying property source content changes at runtime (e.g. after a Spring Cloud Config refresh event updates the environment), a fresh call to `environment.getProperty()` reflects the new value immediately, without needing any special scope annotation, whereas a plain (non-refresh-scoped) `@Value` field would still hold the stale, originally-injected value.

Type-safe, structured, validated configuration binding — the production-recommended approach for related property groups.

Annotation reference

@ConfigurationProperties

Binds an entire prefixed group of properties into a POJO's fields by name-matching (with relaxed binding — `contact-details` in YAML maps to `contactDetails` in Java). Supports nested objects, `List`, `Map`, and even nested `@ConfigurationProperties` classes for deeper structures.

@EnableConfigurationProperties

Registers a `@ConfigurationProperties`-annotated class as a Spring bean, making it injectable elsewhere. Alternative: annotate the properties class itself with `@Component`, which also registers it via component scanning — either works, `@EnableConfigurationProperties` is more explicit about the wiring.

Adding validation

Validated properties class

@Validated

    @NotEmpty
    private String message;

    @NotEmpty @Size(min = 1)

}

@Validated on a `@ConfigurationProperties` class triggers Bean Validation on the bound values at application startup — meaning a misconfigured or missing required property fails the application fast, at boot, with a clear error, rather than surfacing as a mysterious null-related bug much later at request time.

What does @ConfigurationProperties(prefix = "accounts") do?

It binds every property under the `accounts.*` namespace in your configuration sources into the fields of the annotated class, matching property names to field names using relaxed binding (so `accounts.contact-details.name` maps to a `name` field inside a `contactDetails` nested object).

How do you make a required configuration property fail the application at startup if it's missing?

Annotate the `@ConfigurationProperties` class with `@Validated` and apply Bean Validation constraints (e.g. `@NotEmpty`) on the relevant fields — Spring Boot validates the bound values during startup and fails fast with a clear error if a constraint is violated, rather than allowing the app to start in a misconfigured state.

What's the advantage of constructor binding (immutable @ConfigurationProperties, often via a Java record) over the traditional getter/setter POJO style?

Constructor binding creates the properties object as fully immutable — all fields are set once via the constructor and never exposed via setters — which eliminates an entire class of bugs where some other code accidentally mutates configuration state at runtime (configuration should generally be read-only from the application's perspective). It also plays well with Java records, which are a natural fit for pure data-holding configuration classes, and constructor binding fails fast and clearly if a required constructor parameter can't be bound, rather than silently leaving a setter-based field at its default (often null) value. The trade-off is that a record-based configuration class can't be trivially proxied for something like `@RefreshScope`-style dynamic re-binding, since the whole object needs to be reconstructed rather than having individual fields updated — a nuance relevant when combining `@ConfigurationProperties` with the dynamic refresh mechanisms covered later in this section.

How would you unit test a class that depends on an @ConfigurationProperties bean, without starting a full Spring context?

Since a `@ConfigurationProperties` class is ultimately just a plain POJO once bound, you can construct it directly in a unit test (`new AccountsContactInfoDto()` plus setters, or the constructor directly for constructor-binding style) and inject that manually-built instance into the class under test — no Spring context needed at all for a pure unit test. If you specifically want to test the binding behavior itself (does `accounts.on-call-support` in a test YAML correctly populate the list, including edge cases like relaxed binding or validation failures), Spring provides `@EnableConfigurationProperties` + `@ConfigurationPropertiesScan` friendly test slices, or more narrowly, `ConfigurationPropertiesBindingContext`/`Binder` utilities, letting you test just the binding logic in a lightweight, targeted way rather than a full `@SpringBootTest`.

Introduction to Spring Boot Profiles

Environment-specific configuration sets, and conditionally-registered beans.

A profile is a named, logical grouping of configuration (and optionally, beans) that's only active when explicitly selected. The core file-naming convention: application-{profile}.yml is layered on top of the base application.yml when that profile is active — the base file's values still apply, and the profile-specific file overrides/adds to them for just that environment.

Two valid syntaxes you'll see across courses/codebases — neither is outdated

Some instructors/codebases put profile-specific config in separate files using the application-{profile}.yml naming convention shown below — Spring Boot auto-discovers and loads these purely by filename the moment that profile is active, no extra directive required. Others put everything in one file as multiple YAML documents separated by ---, with each document guarded by spring.config.activate.on-profile: qa — this `on-profile` syntax (replacing the older, now-deprecated `spring.profiles: qa` from Boot 2.3 and earlier) was introduced in Spring Boot 2.4 alongside `spring.config.import`, so it's the newer of the two styles, not a legacy one. You may also see a third, hybrid variant: separate application-{profile}.yml files that also use `on-profile` internally, sometimes paired with an explicit `spring.config.import` in the default file. For conventionally-named files sitting in the default classpath location, that explicit import is redundant — Spring Boot would auto-load them anyway — but it's not wrong; it's often just an explicitness/teaching choice, or becomes genuinely necessary if the files live somewhere Spring wouldn't auto-discover, or if the author wants `optional:`-style control over whether a missing file should fail startup. All three patterns are current, correct Spring Boot 2.4+ configurations — treat this as a style choice, not a version signal.

@Profile

Placed on a `@Bean` method or `@Component`/`@Configuration` class to conditionally register it only when the specified profile(s) are active. Supports boolean expressions: "qa | staging" (either), "!prod" (not prod), "prod & eu" (both active). Real-world use: swap a mock external-service client for the real one, only in production.

What is a Spring profile?

A named grouping of configuration (and optionally beans) that's only applied when explicitly activated — used to vary behavior/config per environment (dev, QA, prod) without maintaining entirely separate codebases.

Does application-qa.yml replace application.yml entirely when the qa profile is active?

No — it's layered on top. Base `application.yml` values still apply; `application-qa.yml` only overrides or adds specific values for that profile, following normal property-source precedence (profile-specific config takes priority over the base file).

What does @Profile("!prod") mean?

The annotated bean is registered whenever the "prod" profile is NOT among the active profiles — i.e., active in every environment except production.

What's the risk of using @Profile-conditional beans heavily to swap real vs fake implementations of external integrations, and how would you mitigate it?

The risk is environment parity drift — if non-prod environments run a meaningfully different implementation (a fake SMS sender, a stubbed payment gateway) than production, you lose confidence that tests passing in QA actually validate production behavior; bugs specific to the real integration (serialization quirks, timeout behavior, error handling) only surface in prod, the worst place to discover them. Mitigations: keep the fake/real split as thin as possible (swap only the actual external network call, not surrounding business logic), maintain a staging environment that uses real integrations (perhaps against a sandbox/test instance of the third-party service) specifically to catch integration-level issues before prod, and treat profile-based swapping as appropriate mainly for genuinely expensive/dangerous-to-call-in-non-prod dependencies (real payment processors, real SMS costs) rather than a general-purpose pattern for all external calls.

Notice what's already different from Section 1

Recall from Section 1's H2/YAML notes that `ddl-auto: update` was flagged as dev-only. Here it's concrete: default/local uses H2 with permissive settings for fast iteration; QA/prod switch to MySQL with `ddl-auto: validate` (schema managed by a migration tool, not Hibernate inference) and credentials pulled from environment variables rather than hardcoded — profiles are exactly the mechanism that makes this environment-appropriate divergence manageable in one codebase.

Why does the qa/prod config use ddl-auto: validate instead of update, unlike the local/default profile?

`update` risks unreviewed, automatic schema changes, which is acceptable for fast local iteration but unacceptable outside dev — QA and prod should have their schema managed by a deliberate, version-controlled migration tool (Flyway/Liquibase), with Hibernate only validating that entities match the existing schema rather than silently altering it.

Why is the database password referenced as ${DB_PASSWORD} instead of a literal string in application-qa.yml?

To avoid committing a real secret into source control — the placeholder is resolved from an environment variable supplied at deploy time (or, as covered later in this section, from an encrypted value fetched from Config Server), keeping the actual credential out of the codebase entirely.

What's the risk of copy-pasting near-identical application-qa.yml and application-prod.yml files as this course does, at real organizational scale?

Duplication means every shared setting (logging format, common timeouts, connection pool sizing) has to be kept manually in sync across every environment-specific file for every service — a change that should apply everywhere requires N edits and is easy to partially miss, causing exactly the "config drift" problem named in topic 67. This is one of the concrete motivations for moving to Spring Cloud Config later in this section: a git-backed config repo can express shared base config once and layer environment-specific overrides via profile-scoped files served centrally, and — more importantly — the config source becomes one team's/one repo's responsibility to keep consistent, rather than duplicated inside every individual service's own codebase.

Externalizing Configurations Using Command-line, JVM & Environment Options

Three ways to override a property outside the packaged JAR — without rebuilding anything.

1. Command-line argument
2. JVM system property
3. OS environment variable
$ java -jar accounts.jar --server.port=9090
# Spring Boot's own argument parsing — highest precedence of the three
$ java -Dserver.port=9090 -jar accounts.jar
# standard JVM system property flag — set BEFORE -jar
$ export SERVER_PORT=9090
$ java -jar accounts.jar
# or inline: SERVER_PORT=9090 java -jar accounts.jar
# relaxed binding translates SERVER_PORT -> server.port automatically

Command-line argument--property.name=valueOne-off manual runs, scripts explicitly invoking the JAR

Why environment variables dominate in containerized deployments

Command-line args and `-D` flags require modifying the container's ENTRYPOINT/CMD — awkward to vary per environment without templating the Dockerfile itself. Environment variables are supplied entirely outside the image (via `docker run -e`, a Compose `environment:` block, or a Kubernetes `ConfigMap`/`Secret`), which is exactly the separation of "immutable image" from "environment-specific config" that containerization is meant to enable — this is why section 68's precedence order deliberately puts env vars above the packaged config file.

Name the three ways to externalize a Spring Boot property without rebuilding the JAR.

Command-line arguments (`--property.name=value`), JVM system properties (`-Dproperty.name=value`), and OS environment variables (`PROPERTY_NAME=value`, translated via relaxed binding).

Why is SERVER_PORT recognized as equivalent to server.port?

Because of Spring's relaxed binding — it tolerates different naming conventions (dot notation, kebab-case, SCREAMING_SNAKE_CASE) referring to the same logical property, since environment variables conventionally can't contain dots or lowercase-with-dashes syntax the way YAML/properties files can.

Why do containerized deployments favor environment variables over command-line arguments for configuration, given both are externalization mechanisms Spring Boot supports equally well?

Environment variables can be injected entirely outside the image definition — via the container runtime/orchestrator (`docker run -e`, Compose `environment:`, Kubernetes `ConfigMap`/`Secret` mounted as env vars) — without touching the image's `ENTRYPOINT`/`CMD` at all. Command-line arguments, by contrast, are typically baked into the image's `CMD`/`ENTRYPOINT` or require the orchestrator to override the container's command array per deployment, which is more awkward to template and vary across environments/replicas. Env vars also integrate naturally with secret-management systems (Kubernetes Secrets, cloud secret managers injecting values as env vars at container start), giving a consistent mechanism for both plain config and sensitive values.

Activating the Profile Using Command-line, JVM & Environment Options

The special property that selects which profile-specific config layer applies.

Command-line
JVM system property
Environment variable
$ java -jar accounts.jar --spring.profiles.active=qa
$ java -Dspring.profiles.active=qa -jar accounts.jar

Multiple profiles can be active simultaneously, comma-separated: SPRING_PROFILES_ACTIVE=qa,eu-region. Spring also supports profile groups (spring.profiles.group.production=prod,logging-verbose,metrics) letting one named group activate several underlying profiles together as a bundle.

Precedence applies here too

The exact same precedence order from topic 68 governs which `spring.profiles.active` value wins if set in multiple places — a command-line `--spring.profiles.active=qa` overrides an environment variable `SPRING_PROFILES_ACTIVE=prod`, which overrides a value hardcoded in `application.yml`. This is a common gotcha: hardcoding `spring.profiles.active: default` in `application.yml` "just to be explicit" can silently prevent easy overriding if the precedence isn't well understood — though externally-supplied values still win, since `application.yml` sits at the bottom of the precedence order.

What property activates a Spring profile, and what are the three ways to set it?

`spring.profiles.active` — set via `--spring.profiles.active=qa` (command-line), `-Dspring.profiles.active=qa` (JVM system property), or `SPRING_PROFILES_ACTIVE=qa` (environment variable).

Can more than one profile be active at once?

Yes — profiles are comma-separated (e.g. `qa,eu-region`), and all of their profile-specific config files/beans apply together, layered in the order they're listed.

What's the practical benefit of Spring's profile groups feature over just listing multiple comma-separated profiles at deploy time everywhere?

Profile groups let you define a reusable, named bundle once (e.g. `spring.profiles.group.production=prod,metrics,audit-logging`) so every deployment pipeline/script only needs to reference the single group name (`SPRING_PROFILES_ACTIVE=production`) rather than every deployment site needing to know and correctly list the full set of underlying profiles individually — reducing the chance that one deployment script activates `prod` but forgets `audit-logging`, a subtle and easy-to-miss drift risk when the full profile list is duplicated across multiple deployment configs/scripts instead of centralized in one group definition.

Assignment & Demo: Profile Changes Inside Loans & Cards Microservices

Applying the exact same profile pattern to the other two services — reinforcing it as a repeatable template.

The assignment: replicate the Accounts service's `application.yml` / `application-qa.yml` / `application-prod.yml` structure for Loans and Cards independently — each service gets its own default/QA/prod configuration set, its own database connection details per environment, and its own `SPRING_PROFILES_ACTIVE` activation at deploy time.

The real lesson, again

Just as in Section 1's Loans & Cards exercise, notice the duplication: three services now each maintain three near-identical profile-config files, with the only real differences being database names/hosts and service-specific values. This is precisely the pain point topic 78 formalizes next — and precisely what centralizing config in a Config Server (topic 79 onward) is designed to eliminate.

What's duplicated across Accounts, Loans, and Cards after this exercise?

The overall profile-file structure and any shared settings (logging patterns, common timeout values, `ddl-auto` strategy per environment) — each service repeats the same pattern independently, even though much of it isn't actually service-specific.

If a new mandatory logging format is rolled out organization-wide, how many files need to change with the current (Spring Boot profiles only, no Config Server) setup, and why is that a scaling problem?

With 3 services × 3 environments each potentially needing the update (9 files, or more precisely wherever the logging config is currently duplicated), every file needs a manual, individually-verified edit — and at real organizational scale with dozens of services, this becomes both slow and error-prone (easy to miss one file, or introduce an inconsistency during manual editing). This is the exact motivating problem for centralizing shared configuration in one place (a Config Server backed by a git repo) where a shared base file can be edited once and picked up by every service on their next config refresh — turning an O(N×M) manual edit problem into an O(1) change.

Name two limitations of relying only on Spring Boot's built-in profiles/externalization for a multi-service system.

Any two of: no central visibility across services, requires a restart for any config change, no dedicated version/audit history for config, duplication of shared settings across services, and no built-in secret encryption.

Of all these drawbacks, which one has the most direct production-availability impact, and why?

The "requires a restart" limitation, because it directly couples an operational necessity (fixing a misconfigured timeout, rotating a credential, adjusting a rate limit during an incident) to an availability-impacting event (a restart, even a graceful one, briefly reduces serving capacity and risks whatever normally goes wrong during a deploy — failed health checks, connection draining issues). In an incident-response context specifically, needing a full restart to apply a config fix means the fix itself introduces risk and delay exactly when speed and low-risk changes matter most — which is why "change config without restarting the process" (the actuator-refresh and Cloud Bus mechanisms covered later in this section) is one of the most operationally valuable capabilities Spring Cloud Config adds.

What is Spring Cloud Config, in one sentence?

A client-server system for centralizing microservices configuration — a Config Server reads config from a backend (typically a git repository) and serves it over HTTP to Config Clients at startup (and on refresh), decoupling configuration from each service's own packaged codebase.

What does the {application} segment in the Config Server's URL pattern refer to?

The requesting client's `spring.application.name` — it tells the Config Server which service's configuration file(s) to look up and return.

Why is a git repository the most common Config Server backend choice over, say, a database?

Git provides version history, diffing, branching, and pull-request-based review for config changes essentially for free — exactly the "dedicated audit trail for config changes" capability identified as missing in topic 78 — without needing to build any of that tooling yourself. It also naturally supports the `{label}` concept (branches/tags mapping to environments or config versions) and integrates with existing developer workflows (the same PR review process used for code can review config changes too). A database backend would require building version history, diffing, and review tooling from scratch to match what git already provides as a side effect of being a version control system.

The single annotation that turns an ordinary Spring Boot application into a Config Server — auto-configures the REST endpoints (`/{application}/{profile}/{label}` and friends) that clients query, and wires up whichever backend (`native`/`git`/`vault`) is configured via `spring.cloud.config.server.*` properties.

What annotation turns a Spring Boot app into a Config Server?

`@EnableConfigServer`, from the `spring-cloud-config-server` dependency — it auto-configures the REST endpoints that expose configuration to clients.

Is the Config Server itself a single point of failure for the whole system? What happens to Accounts/Loans/Cards if the Config Server is down?

This means Config Server downtime mainly threatens new deployments/restarts/scale-out events, not already-running healthy instances — but it's still standard practice to run the Config Server itself with multiple replicas behind a load balancer for high availability, and to use `optional:configserver:` prefix so a client can still start with only its local fallback config if Config Server is genuinely unreachable, rather than failing outright.

What does spring.profiles.active=native mean on the Config Server?

It tells the Config Server to source configuration from local classpath or file system locations rather than a git repository — "native" here refers to the local filesystem backend, not any platform-specific meaning.

What is application.yml inside the config/ folder used for, versus accounts.yml?

Why would you avoid the classpath/native backend for a real production Config Server despite it being the simplest to set up?

Because the config files are baked directly into the Config Server's own JAR, changing any configuration requires rebuilding and redeploying the Config Server itself — reintroducing exactly the "config change requires a redeploy" problem that centralizing config was meant to solve, just moved one level up (now it's the Config Server that needs redeploying instead of each individual client). It also forfeits git's version history/audit trail and branch-based environment separation. The classpath backend is genuinely appropriate only for local development/demos or very simple setups where those trade-offs are acceptable — production setups almost always use the git backend (topic 85) instead.

Updating Accounts Microservice to Read Properties from Config Server

spring.config.import

The modern (Spring Boot 2.4+) way to point a client at a Config Server — added directly to `application.yml`, replacing the older `bootstrap.yml`-based approach from earlier Spring Cloud versions. The optional: prefix means the application will still start (falling back to its own local config) if the Config Server is unreachable, rather than failing hard at startup — an explicit, deliberate resilience choice, not a default.

What actually happens at startup

Before the rest of Accounts's own `ApplicationContext` is fully built, Spring Cloud Config's bootstrap phase makes an HTTP call to http://localhost:8071/accounts/qa, receives back a merged property set, and injects it as an additional, high-priority `PropertySource` into the Environment — meaning by the time your `@Value`/`@ConfigurationProperties`/`Environment` code runs, Config-Server-sourced properties are already available exactly like any other property source, just fetched remotely instead of read from a local file.

What property tells a Spring Boot app to fetch its configuration from a Config Server?

`spring.config.import`, pointing at `configserver:` followed by the Config Server's URL — e.g. `spring.config.import: "optional:configserver:http://localhost:8071"`.

What does the "optional:" prefix change about this behavior?

Without it, the application fails to start if the Config Server is unreachable. With `optional:`, the application still starts, falling back to whatever local configuration it has, if the Config Server can't be reached.

Should a production service use "optional:configserver:..." or the non-optional form — what's the actual trade-off?

It depends on whether the service can safely operate on stale/default local config versus needing to guarantee it never starts with wrong configuration. The non-optional form fails fast and loud if Config Server is unreachable — appropriate when starting with incorrect/incomplete config (e.g. missing a critical downstream URL) is worse than not starting at all. The `optional:` form trades that safety for availability — the service starts even if Config Server is down, which is better for services that can tolerate running on cached/default values temporarily but risks silently running with stale configuration if nobody notices Config Server has been down for a while. Many production setups use `optional:` specifically so that Config Server downtime doesn't cascade into a total outage of dependent services, but pair it with monitoring/alerting on Config Server availability so the "silently running on stale config" risk doesn't go unnoticed.

Updating Loans & Cards Microservice to Read Properties from Config Server

The exact same client-side change, applied to the remaining two services.

Loans and Cards each get the identical treatment as topic 82: add `spring-cloud-starter-config`, set `spring.application.name` to their own service name (`loans`, `cards`), and point `spring.config.import` at the same Config Server. Each service then independently fetches its own `{application}/{profile}` config from the shared server — /loans/qa and /cards/qa respectively — while any properties placed in a shared `application.yml` inside the config repo/backend apply to all three automatically.

This is the payoff moment

Compare this to the duplication problem named at the end of topic 76–77: a shared setting (say, a common logging pattern or a shared external service URL) now lives once, in the Config Server's backend, and all three services pick it up automatically — no more copy-pasting the same value into three separate `application-qa.yml` files.

What determines which config file the Config Server returns to the Loans service versus the Cards service?

Each service's own `spring.application.name` (`loans` vs `cards`) — the Config Server uses this to look up the correspondingly-named config file(s) (`loans.yml`/`loans-{profile}.yml` vs `cards.yml`/`cards-{profile}.yml`) in its backend.

If a property is defined in both the shared application.yml and in loans-specific loans.yml on the Config Server, which one wins for the Loans service?

The application-specific file (`loans.yml` or `loans-{profile}.yml`) takes precedence over the shared `application.yml` — Spring Cloud Config merges them with more-specific-wins semantics, following the same general principle as Spring Boot's own profile-specific-overrides-base-file behavior discussed in topic 72. This lets a service override a shared default for its own specific needs while still inheriting everything it doesn't explicitly override.

application.yml

    active: native

Still the same native profile mechanism as the classpath approach, but pointing at an external directory on the host filesystem rather than files packaged inside the Config Server's JAR. This decouples config from the Config Server's own build/deploy cycle — you can edit files at /opt/config-repo directly without rebuilding the Config Server — but still lacks any built-in versioning/audit trail unless that directory happens to itself be a git working copy checked out separately (which is essentially reinventing the git backend manually, worse).

Where this fits in practice

File system backend is a reasonable middle-ground for specific constrained environments (e.g. an air-gapped network with no git server reachable, or a very simple on-prem setup), but for nearly all cloud-native production systems, the git backend (next topic) is the standard, recommended choice — file system backend mainly appears in this course as a stepping stone to build intuition before introducing git.

How does the file system backend differ from the classpath backend for Config Server?

Both use the same `native` profile mechanism, but file system backend points at an external directory path (`file:///...`) outside the Config Server's own JAR, so config files can be edited without rebuilding/redeploying the Config Server itself — unlike classpath, where files are bundled into the JAR.

What operational gap does the file system backend still have compared to a git backend, even though it decouples config editing from Config Server redeployment?

No built-in version history, diffing, rollback, or review process — editing a file at `/opt/config-repo` directly is an untracked, unaudited change unless you separately layer version control or change-management tooling on top of that directory yourself. It also doesn't naturally support the `{label}` (branch/tag) concept for environment separation the way a git backend does out of the box. It solves "don't need to redeploy Config Server to change config" but not "have a proper audit trail and review process for config changes," which was one of the core motivations from topic 78.

What Config Server property points it at a git repository?

`spring.cloud.config.server.git.uri` — once set, the git backend is used, and no `native` profile is needed (native is only for the classpath/filesystem alternative).

What does the {label} part of the Config Server's URL pattern correspond to when using a git backend?

A git branch, tag, or commit ID — it tells the Config Server which version/ref of the repository to read the requested config file from.

Why is clone-on-start=true generally preferred for production, and what does the Config Server do on subsequent config requests once cloned?

`clone-on-start=true` surfaces connectivity, authentication, or repository-access misconfigurations immediately at Config Server startup — a fast, obvious failure — rather than silently deferring the first clone attempt to whenever the first client happens to request config (which could be moments after a deploy, under production load, a much worse time to discover a broken git credential). After the initial clone, the Config Server maintains a local working copy and, by default, performs a `git pull` before serving each request's underlying data lookup (or on a configurable refresh interval) to pick up new commits — meaning the "source of truth" is genuinely the git repository's current state, not a stale one-time snapshot, without needing to restart the Config Server itself when the repo changes.

What's a stronger alternative to storing a raw git username/password in the Config Server's own application.yml for accessing a private repo?

Use a scoped, revocable personal access token (or a dedicated machine/service account's token) instead of a real user's password — narrower permissions (read-only, repo-scoped) and independently revocable without affecting a human's account. Better still, avoid embedding even the token directly in `application.yml`: inject it via an environment variable at Config Server deploy time (exactly the externalization pattern from topic 74), or — going further, tying back into topic 86 — use the Config Server's own encryption support, or an external secrets manager (Vault, AWS Secrets Manager) to supply the git credential at runtime, so the credential never appears in any config file, encrypted or not.

Encryption & Decryption of Properties Inside Config Server

Storing sensitive values safely in a git-backed config repo — a very common interview topic on its own.

The problem

Even with git as the backend, storing a plaintext database password or API key directly in a git repository — even a private one — is a security risk: it's readable by anyone with repo access, remains in git history indefinitely, and duplicates the exact secrets-in-source-control problem from topic 67, just relocated to a different repository. Spring Cloud Config Server has built-in symmetric or asymmetric encryption support specifically for this.

Config Server: symmetric key setup
Encrypt / decrypt via REST
Storing the encrypted value
encrypt:
  key: "${CONFIG_SERVER_ENCRYPT_KEY}"  # the symmetric key — never hardcoded
$ curl -X POST http://localhost:8071/encrypt -d "mySecretPassword"
686f2b3f...c9f1  # the ciphertext returned

$ curl -X POST http://localhost:8071/decrypt -d "686f2b3f...c9f1"
mySecretPassword
# in accounts-prod.yml, stored inside the git repo:
spring:
  datasource:
    password: "{cipher}686f2b3f...c9f1"

# the {cipher} prefix tells Config Server to auto-decrypt this specific
# value before serving it to a requesting client — the client receives
# the plaintext password, never the ciphertext

How it fits together

  1. An operator calls the Config Server's /encrypt endpoint with the plaintext secret, getting back ciphertext.
  2. That ciphertext, prefixed with {cipher}, is what actually gets committed to the git config repo — never the plaintext.
  3. When a client requests its config, the Config Server automatically detects the {cipher} prefix, decrypts the value using its configured key, and returns the plaintext value to the client — decryption is transparent to the client, which never even knows the value was encrypted at rest.
Symmetric key management is itself a real production concern

The `encrypt.key` used above is a single shared secret — if it leaks, every encrypted value in the repo (past and present) is trivially decryptable. Production-grade setups typically prefer an asymmetric keystore (a public/private key pair, where encryption uses the public key and only the Config Server holds the private key) or, increasingly, delegate secret storage entirely to a dedicated secrets manager (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault) rather than managing encryption keys inside the Config Server's own configuration at all — the symmetric-key approach shown here is a solid learning example but a meaningfully weaker security posture than what most FAANG-level production systems actually run.

What does the {cipher} prefix on a property value in the config repo mean?

It signals to the Config Server that this value is encrypted ciphertext and should be automatically decrypted (using the server's configured encryption key) before being served to a requesting client — the client always receives the plaintext value.

Where should the plaintext secret ever appear — in the git repo, or only transiently?

Only transiently — a human/operator supplies the plaintext once to the `/encrypt` endpoint to obtain ciphertext, and only the ciphertext (prefixed `{cipher}`) is ever committed to the git repository. The plaintext itself should never be committed anywhere.

What's the practical weakness of symmetric-key encryption for this use case, and how does an asymmetric keystore address it?

With a symmetric key, the exact same key both encrypts and decrypts, so anyone (or any system, or any leaked config value/environment variable) with access to that one key can decrypt every secret ever encrypted with it — a single point of compromise with broad blast radius, and rotating the key requires re-encrypting every existing secret. An asymmetric keystore uses a public/private key pair: encryption (which might happen from various operator machines/CI systems) only requires the public key, which is safe to distribute more broadly, while decryption requires the private key, which stays exclusively on the Config Server itself and never needs to be shared with whoever is doing the encrypting. This significantly narrows the set of places a compromise could occur to just wherever the private key lives, and cleanly separates "who can encrypt new secrets" from "who/what can decrypt existing ones."

Why might a team choose an external secrets manager (Vault, AWS Secrets Manager) over Config Server's built-in encryption entirely?

Dedicated secrets managers provide capabilities Config Server's built-in encryption doesn't attempt to: automatic secret rotation on a schedule, fine-grained per-secret access policies (which services/roles can read which specific secrets), detailed audit logging of every secret access (not just config changes, but every read), dynamic/short-lived credentials (e.g. Vault issuing a database credential valid for a few hours rather than a long-lived static password), and a security model where secrets never need to be committed to git at all — even as ciphertext — since the secrets manager is the actual source of truth, with Config Server (or the application directly) fetching secrets from it at runtime rather than storing them, even encrypted, in the config repo. Config Server's built-in `{cipher}` mechanism remains a reasonable middle ground for teams not ready to operate a full secrets-manager deployment, but it's explicitly a lighter-weight solution with a smaller feature set.

Refresh Configurations at Runtime Using the Refresh Actuator Path

The first, most manual mechanism for applying config changes without a restart.

The pieces involved

pom.xml (actuator)
application.yml (expose refresh endpoint)
@RefreshScope usage
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
management:
  endpoints:
    web:
      exposure:
        include: "refresh,health,info"
@RestController
@RefreshScope
public class AccountsController {

    @Value("${build.version}")
    private String buildVersion;
    // this field is re-resolved after a refresh event — a plain @Value
    // field on a NON-@RefreshScope bean would keep its stale, original value
}

The mechanism

  1. The config repo is updated (a new value committed and pushed).
  2. An operator issues POST http://accounts-instance:8080/actuator/refresh — actuator's refresh endpoint.
  3. The client re-fetches its configuration from the Config Server (same as it did at startup) and updates its Environment's property sources with any changed values.
  4. Any bean annotated @RefreshScope is destroyed and lazily recreated on its next use — meaning its `@Value`/`@ConfigurationProperties`-injected fields are re-resolved against the now-updated Environment, picking up the new values without a full application restart.
@RefreshScope

Marks a bean as belonging to the special "refresh" scope — instead of being a normal eager singleton, Spring wraps it in a proxy that can be told to discard its current instance and lazily rebuild it on next access. This is precisely what makes runtime property updates actually visible in application code — beans NOT marked `@RefreshScope` keep whatever values they were originally created with, even after a refresh event fires.

The scalability gap this topic deliberately leaves open

Calling /actuator/refresh only refreshes the one instance you called it on. With 3 replicas of Accounts running behind a load balancer, you'd need to call this endpoint on all 3 individually, and that number only grows as you scale out. This exact limitation is what the next two topics (Spring Cloud Bus, then Bus + Config Monitor) solve — this topic is intentionally the "manual, doesn't scale" baseline to make that motivation concrete.

What does @RefreshScope do?

It marks a bean so that, when a refresh event occurs, the bean is discarded and lazily rebuilt on next access — re-resolving any `@Value` or `@ConfigurationProperties`-injected fields against the updated configuration, instead of retaining stale values from when the bean was first created.

What triggers a refresh via this mechanism?

An HTTP POST to that specific instance's `/actuator/refresh` endpoint, which causes it to re-fetch config from the Config Server and refresh any `@RefreshScope` beans.

What's the main limitation of this approach?

It only refreshes the single instance you call it on — with multiple replicas of a service, you'd need to call the endpoint on every instance individually, which doesn't scale as replica count grows.

Why does @RefreshScope work by destroying and recreating the bean rather than just re-injecting new values into the existing instance's fields?

Directly mutating a running bean's fields via reflection would be fragile and unsafe — it wouldn't re-run any constructor logic, wouldn't correctly handle beans with complex initialization (`@PostConstruct` logic, derived/computed fields based on the config), and could leave the bean in an inconsistent state if only some fields were updated mid-use by a concurrent request. Discarding and lazily recreating the bean via its normal Spring lifecycle (constructor, dependency injection, `@PostConstruct`) guarantees the new instance is fully, correctly initialized exactly as if the application had just started fresh with the new config — a much safer and more predictable guarantee than partial in-place field mutation.

Is exposing /actuator/refresh publicly a security concern, and how would you secure it in production?

Yes — an unauthenticated, exposed refresh endpoint could let anyone trigger a wave of bean recreation across your fleet (a mild denial-of-service/resource-churn vector) or, combined with a compromised Config Server, be part of a chain propagating malicious config changes into running instances quickly. Production practice: restrict actuator's management endpoints to a separate management port not exposed on the public network (`management.server.port`), require authentication specifically for sensitive actuator endpoints (Spring Security config scoped to `/actuator/**`), and expose only the specific endpoints actually needed (`management.endpoints.web.exposure.include` explicitly listing endpoints, never `include: "*"` in production) rather than defaulting to exposing everything actuator offers.

What problem does Spring Cloud Bus solve compared to calling /actuator/refresh directly?

It removes the need to call the refresh endpoint on every individual instance — instead, calling `/actuator/busrefresh` on just one instance broadcasts the refresh event to every connected instance across the fleet via a shared message broker, so refreshing scales to any number of replicas with one call.

What extra infrastructure does Spring Cloud Bus require?

A message broker — commonly RabbitMQ (via `spring-cloud-starter-bus-amqp`) or Kafka — that every service instance connects to, forming the broadcast channel refresh events travel over.

What happens if a service instance is temporarily disconnected from the message broker when a busrefresh event is published — does it miss the update permanently?

For genuinely mission-critical refresh delivery guarantees, some teams pair this with periodic scheduled refreshes as a safety net, ensuring an instance never drifts indefinitely even if it missed a specific bus event.

Why might a team choose Kafka over RabbitMQ as the Cloud Bus transport, or vice versa?

RabbitMQ is often simpler to operate for this specific use case — a broadcast/fanout messaging pattern for relatively low-volume, low-latency-sensitive refresh events is exactly what RabbitMQ's exchange/queue model handles well with minimal configuration. Kafka is generally chosen when the organization already runs Kafka for other purposes (event streaming, inter-service async communication) and prefers not to operate two different messaging systems, or when they want Cloud Bus events to flow through the same durable, replayable log infrastructure as their other event-driven architecture — Kafka's stronger durability/replay guarantees are generally more capability than a config-refresh broadcast strictly needs, but reusing existing infrastructure is often the deciding factor over the specific technical merits for this one narrow use case.

What does Spring Cloud Config Monitor add on top of Spring Cloud Bus?

Full automation — a git webhook calls the Config Server's `/monitor` endpoint on every push, and Config Monitor automatically publishes the refresh event onto the bus, removing the need for anyone to manually call `/actuator/busrefresh` after a config change.

What triggers the /monitor endpoint?

A webhook configured on the git repository (GitHub/GitLab) that sends an HTTP POST to the Config Server whenever a push event occurs.

Config Monitor "determines which applications' config actually changed" from the webhook payload — why does that matter instead of just refreshing everything on every push?

A monorepo-style config repository typically holds config for every service (`accounts.yml`, `loans.yml`, `cards.yml`, shared `application.yml`); a single commit might only touch `loans.yml`. What security consideration applies specifically to exposing a public /monitor webhook endpoint on the Config Server?

An unauthenticated `/monitor` endpoint is a public trigger for fleet-wide refresh events — while triggering an unwanted refresh isn't as severe as a genuine secret leak, a malicious or misconfigured actor spamming it could cause repeated unnecessary bean-recreation churn across the fleet (a resource-exhaustion/availability concern) or be used to probe which applications exist/are configured. Git providers support webhook payload signing (e.g. GitHub's `X-Hub-Signature-256` header, an HMAC of the payload using a shared secret configured on both the webhook and the Config Server) — Config Server should validate this signature and reject unsigned or incorrectly-signed requests, ensuring only genuine, authorized webhook deliveries from the configured repository can trigger a refresh, rather than trusting any POST request that happens to hit the endpoint.

Introduction to Liveness and Readiness Probes

Two different questions an orchestrator needs answered — "is it alive?" vs "is it ready for traffic?" — and why they're not the same question.

Why one health check isn't enough

A naive single /health endpoint conflates two genuinely different questions:

ProbeQuestion it answersWhat the orchestrator does on failure
Liveness"Is this process alive, or is it stuck/deadlocked and needs to be killed and restarted?"Restarts the container
Readiness"Is this instance currently able to correctly serve traffic right now?"Temporarily removes it from load-balancer rotation (does NOT restart it)

These genuinely diverge in important cases: a service that's still fetching its initial config from Config Server, or still warming up a cache, or momentarily unable to reach a downstream dependency it needs — is alive (the process is healthy, not stuck) but not yet ready to correctly handle requests. Treating these identically means either killing/restarting a perfectly healthy process unnecessarily (if you only have a strict "readiness-style" check wired to restart behavior), or routing live traffic to an instance that isn't actually ready to serve it correctly (if you only have a loose "liveness-style" check wired to traffic routing).

application.yml

      probes:
        enabled: true
  health:
    livenessState:
      enabled: true
    readinessState:
      enabled: true

With this enabled, Spring Boot Actuator exposes two dedicated endpoints:

EndpointPurpose
/actuator/health/livenessReports whether the internal application state is broken beyond recovery — Spring Boot's LivenessState (`CORRECT`/`BROKEN`)
/actuator/health/readinessReports whether the application is currently ready to accept traffic — Spring Boot's ReadinessState (`ACCEPTING_TRAFFIC`/`REFUSING_TRAFFIC`), automatically tied to the application lifecycle (e.g. becomes `ACCEPTING_TRAFFIC` only after the context fully starts, and can be flipped to `REFUSING_TRAFFIC` during graceful shutdown)
Where this fits with Docker Compose vs Kubernetes

Docker Compose's `healthcheck:` (used in the previous topic) is a single, generic mechanism — Compose alone doesn't have a first-class distinction between "liveness" and "readiness" the way Kubernetes does (`livenessProbe` and `readinessProbe` as genuinely separate, independently configurable checks). In this course's Compose setup, the healthcheck is typically pointed at the readiness endpoint specifically, since "can this service correctly serve requests" is usually the more relevant question for gating dependent services' startup — the distinction becomes fully operative once you move to a real orchestrator like Kubernetes (a later section), where both probes get used for their genuinely different purposes.

What's the difference between a liveness probe and a readiness probe?

Liveness answers "is this process alive and not stuck" — failing it typically causes a restart. Readiness answers "is this instance currently able to correctly serve traffic" — failing it removes the instance from load-balancer rotation without restarting it.

What Spring Boot Actuator endpoints expose these two checks?

`/actuator/health/liveness` and `/actuator/health/readiness`, enabled via `management.endpoint.health.probes.enabled=true`.

Give a concrete scenario where a service should report itself alive but not ready.

Right at startup, while the service is still fetching its initial configuration from Config Server (a required, non-optional dependency in this section's setup) — the JVM process itself is running fine (liveness: healthy), but the application isn't yet in a state to correctly handle a real business request (readiness: not ready) until that config fetch completes and the application context fully initializes. Another example: a temporary, self-healing loss of connectivity to a critical downstream dependency — you don't want the orchestrator to kill and restart a perfectly healthy process just because a downstream call is failing (restarting won't fix a downstream outage), but you do want the load balancer to stop sending it traffic until connectivity recovers, which is exactly the readiness-without-liveness-failure case.

What's a risky misconfiguration involving liveness probes specifically, and why is it worse than a readiness misconfiguration?

A liveness probe that's too aggressive or checks the wrong thing (e.g. checking a downstream dependency's health as part of liveness, rather than just "is this process itself functioning") can cause an orchestrator to repeatedly kill and restart a perfectly fine process because of an unrelated external outage — potentially creating a restart loop that never resolves the actual problem (the downstream outage) while adding the instability of constant restarts on top of it. This is strictly worse than a readiness misconfiguration, because a bad readiness check just removes an instance from traffic (a safe, reversible, no-data-loss-risk action), whereas a bad liveness check actively destroys and recreates the process — potentially interrupting in-flight work and adding operational churn without addressing the root cause. The general rule: liveness checks should verify only the process's own internal health (not deadlocked, JVM responsive), while readiness checks are the appropriate place to factor in dependency health.

The gotcha that trips people up: extends doesn't merge lists

If common-config.yml's base service declared depends_on: [rabbit] and the extending service also needs to depend on configserver, the extending service's own depends_on block completely replaces the base one rather than merging with it — you'd need to list both dependencies explicitly in the extending service, not just the new one. This is exactly why the example above declares depends_on directly on accounts/loans rather than inside the shared base file — list-type Compose keys are generally kept out of the shared/extended base and declared per-service instead, precisely to avoid this silent-overwrite trap.

Why this matters beyond tidiness

This is the exact same "duplication → drift" concern raised throughout this section (topics 76–78) — just applied to the Compose file itself now instead of application config. A shared setting defined once via an anchor and reused across services can't silently diverge the way three independently-typed copies could.

What does the x- prefix mean on a top-level key in a Compose file?

It marks the key as an extension field, explicitly ignored by Compose's schema validation — a safe place to define reusable YAML content (like a shared block of environment variables) that isn't itself interpreted as a service, network, or volume definition.

What do the & and * symbols do in this YAML?

`&name` defines a YAML anchor — a named, reusable reference to that block of content. `*name` is an alias that inserts a copy of the anchored content wherever it's used, avoiding the need to retype the same block repeatedly.

What does the extends field do in a Compose file?

It lets a service inherit its configuration from a named service defined in a separate Compose file — specified via `file:` (the other file's path) and `service:` (the base service's name within it) — merging that base configuration into the current service before any locally-declared keys are applied.

Does extends merge list-type fields like depends_on from the base file?

No — scalar and map-type keys (like `environment`) merge/deep-merge as expected, but list-type keys such as `depends_on` and `volumes` are replaced entirely by whatever the extending service declares locally, not merged with the base file's list. Any dependencies needed from both the base and the extending service must be listed in full on the extending service itself.

Is YAML anchor/merge-key reuse a good long-term strategy for a Compose file that keeps growing, or does it have limits?

It helps meaningfully at moderate scale (a handful of services sharing a handful of common settings, as in this course), but it's still a fairly blunt, all-or-nothing text-reuse mechanism — nested overrides can get visually hard to follow, and YAML anchors don't support any kind of parameterization (you can't anchor a block and substitute just one field per usage without additional merge-key gymnastics). At real organizational scale with many more services, teams typically move beyond hand-maintained Compose files with anchors entirely, toward templating tools (e.g. generating Compose or Kubernetes manifests from a higher-level tool like Helm, Kustomize, or an internal templating layer) that offer genuine parameterization, validation, and reuse across many more services than YAML anchors comfortably support by themselves.

Why might a team choose extends over YAML anchors, given anchors can express the same "shared config" idea within one file?

Once the shared configuration itself grows substantial (a full base service shape — networks, resource limits, common env vars, restart policy) it becomes a readability and ownership win to give it a genuinely separate file rather than an `x-` block buried at the top of an already-large `docker-compose.yml` — separate files can be reviewed, diffed, and reasoned about independently, and `extends` is a Compose-native, schema-validated way to express "this service is built on top of that one" versus anchors, which are a generic YAML trick the Compose spec doesn't have any first-class awareness of (Compose just sees the fully-resolved YAML after your editor/parser expands the anchors). The trade-off is the list-merging gotcha covered above, and that `extends` only lets you extend a whole service, not an arbitrary fragment the way an anchor can reuse just a `healthcheck:` block or just a few env vars.

Compose also has an "include:" top-level directive for pulling in another compose file — how is that different from extends?

include: (added in newer Compose Specification versions) pulls in an entire separate Compose file's services as-is, wholesale, into the current project — useful for composing genuinely independent sub-projects together (e.g. a shared "infrastructure" compose file defining the database/broker services, included by several different applications' own compose files). extends operates at the single-service level — one service inherits from one named base service in another file, then adds/overrides its own keys — which is the right granularity for "these three application services all share 90% of their shape but need their own image/port/name," exactly this course's use case. `include` is the right tool for "reuse this whole set of infrastructure services across multiple independent projects," a different, coarser-grained problem than what topic 93 is solving.

Testing Config Server Changes End to End Using Docker Compose & Default Profile

Validating the whole chain actually works together, not just each piece in isolation.

The end-to-end checklist

  1. docker compose up -d — confirm every service (Config Server, RabbitMQ, 3 databases, 3 application services) reaches a healthy state, in the correct dependency order.
  2. Hit a business endpoint on Accounts (e.g. the contact-info endpoint from topic 71) and confirm the value returned matches what's configured in the Config Server's backend — proving the client genuinely fetched its config remotely, not from a bundled local fallback.
  3. Change a value in the config repo, push it, and confirm — depending on which refresh mechanism is wired up — either a manual `/actuator/busrefresh` call or (with Config Monitor) the webhook alone propagates the new value to a running instance without any restart.
  4. Re-verify the business endpoint reflects the updated value, confirming the full refresh chain (git → Config Server → Cloud Bus → `@RefreshScope` bean) genuinely works, not just each individual piece in isolation.
Why end-to-end testing catches things unit/component testing won't

Each individual piece (Config Server serving a value, a client's `@RefreshScope` bean re-resolving on a direct actuator call, RabbitMQ delivering a message) can work correctly in isolation while the full chain still fails — e.g. a Compose networking misconfiguration where `SPRING_RABBITMQ_HOST` doesn't actually resolve to the right container, or a webhook secret mismatch that silently drops Config Monitor events. Only an actual end-to-end run through Compose, from a real git push to a verified updated response, proves the whole system genuinely works together.

Why is it not enough to just confirm each service individually reports "healthy" in Compose?

A healthcheck passing only confirms a narrow condition (usually that the process/HTTP endpoint responds) — it doesn't prove the full functional chain (config actually being correctly fetched, refresh events actually propagating end-to-end) works as intended. Only exercising the real behavior — checking an actual returned config value, then changing it and confirming the update propagates — validates the system is functioning correctly as a whole.

How would you turn this manual end-to-end verification checklist into an automated test that runs in CI?

Use a tool like Testcontainers to programmatically spin up the same multi-container stack (Config Server, RabbitMQ, application services, using the same images or even the same Compose file via Testcontainers' Compose module) inside a CI pipeline, then write an integration test that: starts the stack, calls the business endpoint to assert the initial config value, programmatically modifies the config source (e.g. writing directly to a test git repo or the classpath/file-system backend used in the test environment), triggers the refresh (calling `/actuator/busrefresh` directly, or simulating the webhook call to `/monitor`), and asserts the business endpoint now returns the updated value — all within an automated, repeatable CI run rather than a manual click-through, catching regressions in the refresh chain automatically on every change to the Config Server or client setup.

What's the only meaningful difference between the QA and prod Compose files for the accounts service?

The `SPRING_PROFILES_ACTIVE` environment variable — everything else, including the Docker image itself, stays the same. The active profile determines which profile-specific config file (`accounts-qa.yml` vs `accounts-prod.yml`) the Config Server returns to that instance.

Why is "same image, different SPRING_PROFILES_ACTIVE per environment" considered a best practice, rather than building separate images per environment?

Building a separate image per environment means you're never actually testing the exact artifact that will run in production — the QA image and prod image, even if built from identical source, are technically different artifacts (different build timestamps, potentially different dependency resolution if built at different times), reintroducing a subtle version of "works in QA, might not work in prod" risk. Using one immutable image across all environments and varying only externalized configuration (profile selection, env vars) guarantees you're testing the literal bytes that will run in production at every earlier stage — this is a core tenet of modern CI/CD practice (build once, promote the same artifact through environments) and is precisely what this section's entire arc — profiles, externalized config, and a centralized Config Server — was built to enable cleanly.

Looking back across this whole section, what's the single biggest production-readiness gap that remains even after topics 67–96?

Everything here still assumes a single-host Docker Compose deployment — there's no multi-host scheduling, no automatic instance replacement on host failure, no rolling updates with health-gated rollout, and no real horizontal autoscaling, all of which were flagged as Compose's limitations back in Section 4's Docker Compose topic. The configuration-management architecture built in this section (Config Server, Cloud Bus, profiles, encrypted secrets) is fully orchestrator-agnostic and carries forward cleanly — but the actual deployment/scheduling layer is the next major gap, which is exactly what a proper container orchestrator (Kubernetes, covered in a later section) is built to close.
