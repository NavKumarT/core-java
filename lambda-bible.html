Java 8+

What is a Lambda Expression?

A lambda expression is an anonymous, nameless block of code that can be passed around as a value — a way of writing an implementation of a single-method interface inline, without a class declaration. It's Java's syntax for "here's a function, treat it like data."

Core characteristics
  • Nameless — no method name, no class name required at the call site
  • Anonymous — creates an implementation without a named class
  • Defined against an interface — specifically, one with exactly one abstract method
  • Can be assigned to a variable, passed as an argument, or returned from a method
  • Enables functional-style programming — behavior as a first-class value
What problem it solves
  • Before Java 8, passing behavior meant an anonymous inner class — 5+ lines of ceremony for one line of logic
  • Lambdas collapse that ceremony to (params) -> expression
  • Enabled the Stream API, Comparator chaining, and functional-style collection processing
  • Under the hood, still compiles down to implementing a functional interface — no new bytecode-level construct
The progression: interface → concrete class → anonymous class → lambda 
@FunctionalInterface
interface MyLambda {
    void display();
}

// 1) Traditional — a separate named concrete class
class ConcreteClass implements MyLambda {
    @Override
    public void display() { System.out.print("Hello world"); }
}
MyLambda ml = new ConcreteClass();
ml.display();

// 2) Anonymous inner class — no separate named class, but still verbose
MyLambda mlNested = new MyLambda() {
    @Override
    public void display() { System.out.print("Inner nested method"); }
};
mlNested.display();

// 3) Lambda expression — same result, minimal syntax
MyLambda ml2 = () -> { System.out.println("Lambda"); };
ml2.display();
💡 Mental model: a lambda is compiler sugar for "implement this one abstract method, right here, right now." The variable's declared type (MyLambda) tells the compiler which interface's method the lambda's parameter list and body must match — this is called target typing.
The Contract

Functional Interfaces & @FunctionalInterface

A lambda can only be assigned to a variable of a functional interface type — an interface with exactly one abstract method (a "SAM," Single Abstract Method). This is the mechanism that makes lambdas type-safe: the compiler always knows exactly which method signature the lambda must implement.

What counts toward "single abstract method"
  • Exactly ONE abstract (unimplemented) method — the requirement
  • default methods — allowed, don't count toward the limit
  • static methods — allowed, don't count toward the limit
  • Methods that override an Object method (equals, hashCode, toString) — allowed as abstract, don't count, since every class inherits an implementation from Object anyway
@FunctionalInterface annotation
  • Optional — an interface with one abstract method IS a functional interface with or without it
  • Its only job: tells the compiler to error if a second abstract method is later added
  • A documentation + safety-net annotation, not a magic enabler
  • Best practice: always add it — catches accidental interface-breaking edits at compile time instead of at every lambda call site
Valid functional interface
Invalid — 2 abstract methods
Object methods don't count
@FunctionalInterface
interface Calculator {
    int calculate(int a, int b);      // the ONE abstract method

    default int calculateTwice(int a, int b) {  // default — doesn't count
        return calculate(a, b) * 2;
    }

    static Calculator identity() {           // static — doesn't count
        return (a, b) -> a;
    }
}
Calculator add = (a, b) -> a + b; // compiles — exactly 1 abstract method to satisfy
@FunctionalInterface
interface Broken {
    void methodOne();
    void methodTwo(); // SECOND abstract method
}
// COMPILE ERROR: "Broken is not a functional interface"
// "multiple non-overriding abstract methods found"
// A lambda has ONE body — it can only ever implement ONE method
@FunctionalInterface
interface Comparer<T> {
    int compareTo(T other);

    boolean equals(Object obj); // re-declares Object's equals() — STILL VALID
    String toString();             // re-declares Object's toString() — STILL VALID
}
// Still counts as exactly 1 abstract method (compareTo). Every class already
// implements equals()/toString()/hashCode() by inheriting from Object, so
// re-declaring them here adds no NEW obligation for implementers
// (this is literally how java.util.Comparator is designed)
⚠️ An interface with ZERO abstract methods is not a functional interface either — there's nothing for a lambda to implement. And a lambda can never target a class or an abstract class, only an interface.

The #1 Trap

Lambda vs Anonymous Inner Class

They look interchangeable and often are — until this enters the picture, or someone asks how each compiles. This distinction is one of the most common "gotcha" questions in senior Java interviews.

this — the classic trap
Variable shadowing
public class Widget {
    private String name = "Widget-A";

    void testAnonymous() {
        Runnable r = new Runnable() {
            @Override
            public void run() {
                System.out.println(this); // prints Widget$1@<hash> — the ANONYMOUS CLASS instance
            }
        };
        r.run();
    }

    void testLambda() {
        Runnable r = () -> System.out.println(this); // prints Widget@<hash> — the ENCLOSING Widget instance
        r.run();
    }
}
// A lambda does NOT create a new "this" scope — it captures the enclosing
// instance's "this" exactly like any other local code in that method would
void demo() {
    int count = 5;

    Runnable anon = new Runnable() {
        @Override
        public void run() {
            int count = 10; // ✓ COMPILES — anonymous class has its OWN scope, shadowing is fine
            System.out.println(count);
        }
    };

    Runnable lam = () -> {
        int count = 10; // ✗ COMPILE ERROR — "variable count is already defined in the scope"
        System.out.println(count); // lambda shares the ENCLOSING method's scope, not a new one
    };
}
💡 Interview one-liner: "A lambda is lexically scoped — it borrows the enclosing scope's this and can't shadow enclosing locals. An anonymous class introduces a real new scope with its own this."
Closures

Variable Capture in Lambda Expressions

A lambda can reference variables from its enclosing scope — this is what makes it a closure. But local variables and instance/static fields follow completely different rules once captured, and that asymmetry is a favorite interview probe.

Local variables — effectively final
  • Must be final or effectively final (never reassigned after initialization) to be captured
  • Captured by value — the lambda gets a copy taken at creation time, not a live reference
  • Reassigning a captured local anywhere in the enclosing scope is a compile error — not just inside the lambda
Instance / static fields — no restriction
  • No effectively-final requirement — fields can be freely read AND reassigned inside a lambda
  • Captured by reference — the lambda goes through the enclosing object (or class, for static), not a value snapshot
  • Changes made inside the lambda are visible outside it, and vice versa
Local variable — must be effectively final
Instance field — freely mutable
Classic loop-variable trap
void demo() {
    int count = 5;           // never reassigned below → effectively final, OK to capture
    Runnable r = () -> System.out.println(count); // ✓ compiles

    int counter = 0;
    Runnable bad = () -> System.out.println(counter); // this line alone would compile...
    counter++; // ...but THIS reassignment makes "counter" NOT effectively final
    // → COMPILE ERROR on the lambda: "local variables referenced from a
    // lambda expression must be final or effectively final"
}
public class Counter {
    private int count = 0; // instance field

    public Runnable increment() {
        return () -> count++; // ✓ COMPILES — fields have NO effectively-final requirement
    }

    void demo() {
        Runnable r = increment();
        r.run(); r.run(); r.run();
        System.out.println(count); // 3 — mutations through the lambda ARE visible on the object
    }
}
// This is exactly how a lambda-based counter/accumulator pattern works —
// wrap the mutable state in a field (or an AtomicInteger for thread-safety)
// The classic "why did every lambda print the same value" bug
List<Runnable> tasks = new ArrayList<>();

for (int i = 0; i < 3; i++) {
    int current = i; // NEW effectively-final local created FRESH each iteration
    tasks.add(() -> System.out.println(current)); // each lambda captures its OWN "current"
}
tasks.forEach(Runnable::run); // prints 0, 1, 2 — correct

// Enhanced for-loop variables are ALSO effectively final per-iteration,
// so "for (int x : list) { tasks.add(() -> print(x)); }" works correctly too —
// each iteration gets its own binding of x, unlike languages with one
// shared loop variable across all iterations (classic pre-ES6 JavaScript var trap)
🚫 Why capture-by-value for locals exists: a local variable lives on the stack frame of its enclosing method, which may be gone by the time the lambda actually runs (e.g. a lambda returned from a method, or handed to another thread). Copying the value at creation time avoids a dangling reference to a stack frame that no longer exists. Instance fields don't have this problem — they live on the heap as long as the object does, so the lambda can safely hold a live reference to the object and read the field whenever it runs.

Default Methods

Composing Functions — andThen, compose, and, or, negate

The built-in functional interfaces ship default methods for chaining lambdas together — this is where the "functional interfaces can have default methods" rule from earlier actually pays off in real code.

andThen vs compose
Predicate: and / or / negate
Function<Integer, Integer> addTwo   = x -> x + 2;
Function<Integer, Integer> multiply3 = x -> x * 3;

// andThen — run THIS first, then feed the result into the argument
Function<Integer, Integer> f1 = addTwo.andThen(multiply3);
System.out.println(f1.apply(5)); // (5+2)=7, then 7*3 = 21

// compose — run the ARGUMENT first, then feed its result into THIS
Function<Integer, Integer> f2 = addTwo.compose(multiply3);
System.out.println(f2.apply(5)); // (5*3)=15, then 15+2 = 17

// Consumer has andThen too (runs both, no value passed between them):
Consumer<String> log   = s -> System.out.println("LOG: " + s);
Consumer<String> audit = s -> System.out.println("AUDIT: " + s);
log.andThen(audit).accept("event"); // prints both, log's output first
Predicate<Integer> isPositive = n -> n > 0;
Predicate<Integer> isEven     = n -> n % 2 == 0;

Predicate<Integer> positiveAndEven = isPositive.and(isEven);
Predicate<Integer> positiveOrEven  = isPositive.or(isEven);
Predicate<Integer> isNegative      = isPositive.negate();

System.out.println(positiveAndEven.test(4));  // true
System.out.println(positiveAndEven.test(-4)); // false
System.out.println(isNegative.test(-4));      // true

// Short-circuits exactly like && and || — and() won't call the second
// predicate if the first already returns false
Passing Behavior

Using Lambdas as Method Parameters

The real payoff of lambdas: a method can accept a functional interface parameter and let the caller supply the behavior — this is how Stream.filter, Comparator.comparing, and every callback-style API in modern Java works.

A custom functional interface accepted as a parameter 
@FunctionalInterface
interface Addition {
    int add(int a, int b);
}

public class Main {
    // addWrapper doesn't care HOW the two ints are combined — just that
    // something matching Addition's signature is supplied
    static int addWrapper(Addition a) {
        return a.add(5, 9);
    }

    public static void main(String[] args) {
        System.out.println(addWrapper((a, b) -> a + b + 1)); // 5+9+1 = 15
        System.out.println(addWrapper((a, b) -> a * b));     // 5*9 = 45 — swap behavior with zero changes to addWrapper
    }
}
💡 This is strategy pattern without the boilerplate. Before lambdas, "pluggable behavior" meant defining a Strategy interface plus one concrete class per strategy. A lambda IS the concrete implementation, written inline at the call site — same design pattern, far less ceremony.

Method References

When a lambda's entire body is just "call this existing method," a method reference (::) says the same thing more directly. There are exactly four kinds — knowing which is which is a standard interview check.

Instance method of an arbitrary object of a type (unbound)ClassName::instanceMethod(obj, args) -> obj.instanceMethod(args)
Constructor referenceClassName::new(args) -> new ClassName(args)

@FunctionalInterface
interface Addition {
    int add(int a, int b);
}

public class Main {
    static int multiplyThemInstead(int a, int b) { return a * b; }

    public static void main(String[] args) {
        Addition ad = Main::multiplyThemInstead; // static method reference
        System.out.println(ad.add(1, 4)); // 4 — "add" is just the FI's method name; the actual logic is multiplyThemInstead's
    }
}
// Compiler matches signatures structurally: Addition.add(int,int) → int must
// line up with multiplyThemInstead(int,int) → int. Method NAMES don't need to match.
String greeting = "hello world";

Supplier<String> upper = greeting::toUpperCase; // bound to THIS specific "greeting" object
System.out.println(upper.get()); // "HELLO WORLD"
// Equivalent lambda: () -> greeting.toUpperCase()

List<String> items = new ArrayList<>();
Consumer<String> addToList = items::add; // bound to the "items" instance
addToList.accept("x"); // items now contains "x"
// No specific object yet — the object becomes the FIRST parameter at call time
Function<String, String> upper = String::toUpperCase; // UNBOUND — no particular String chosen
System.out.println(upper.apply("hello")); // "HELLO" — "hello" fills the "this" slot
// Equivalent lambda: s -> s.toUpperCase()

// This is exactly what Comparator.comparing / sorting uses under the hood:
List<String> names = new ArrayList<>(List.of("Charlie", "alice", "Bob"));
names.sort(String::compareToIgnoreCase); // (a, b) -> a.compareToIgnoreCase(b)
class Point {
    int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
}

BiFunction<Integer, Integer, Point> factory = Point::new; // constructor reference
Point p = factory.apply(3, 4); // equivalent to (x, y) -> new Point(x, y)

// Very common with Streams / Collectors:
List<String> names = List.of("a", "b", "c");
List<StringBuilder> builders = names.stream()
    .map(StringBuilder::new) // String -> new StringBuilder(String)
    .toList();

// Array constructor reference — a special extra form
IntFunction<int[]> arrayMaker = int[]::new;
int[] arr = arrayMaker.apply(5); // new int[5]
⚠️ Bound vs unbound is a common trip-up: greeting::toUpperCase (a variable) is bound — the object is fixed. String::toUpperCase (the class name) is unbound — an object of that type must be supplied at call time as the first argument. Same :: syntax, very different resulting functional signature.

Lambdas & Checked Exceptions

None of the built-in functional interfaces declare throws on their abstract method, so a checked exception cannot be thrown directly from a lambda body targeting Function, Consumer, Predicate, etc. This trips people up constantly with I/O and reflection code inside streams.

Won't compile
Fix: catch inside, wrap unchecked
Fix: custom throwing functional interface
List<String> paths = List.of("a.txt", "b.txt");

paths.forEach(p -> {
    Files.readAllLines(Path.of(p)); // COMPILE ERROR — "Unhandled exception: IOException"
});
// Consumer.accept(T) does not declare "throws" — a lambda targeting it
// can't add one either. The checked exception has nowhere to legally go.
// Catch it locally and convert to an unchecked exception
paths.forEach(p -> {
    try {
        Files.readAllLines(Path.of(p));
    } catch (IOException e) {
        throw new UncheckedIOException(e); // purpose-built JDK wrapper for exactly this case
    }
});
@FunctionalInterface
interface ThrowingConsumer<T, E extends Exception> {
    void accept(T t) throws E; // this ONE declares throws — the escape hatch
}

static <T> Consumer<T> wrap(ThrowingConsumer<T, Exception> f) {
    return t -> {
        try { f.accept(t); }
        catch (Exception e) { throw new RuntimeException(e); }
    };
}
paths.forEach(wrap(p -> Files.readAllLines(Path.of(p)))); // compiles cleanly, checked exception preserved as the cause

Where They Shine

Lambdas in the Stream API

The Stream API is the single biggest reason lambdas exist in modern Java code — nearly every intermediate and terminal stream operation takes a functional interface parameter.

A typical stream pipeline, annotated with which functional interface each stage expects 
List<String> names = List.of("Alice", "bob", "Charlie", "dave", "Eve");

List<String> result = names.stream()
    .filter(n -> n.length() > 3)          // filter(Predicate<T>)
    .map(String::toUpperCase)             // map(Function<T,R>) — unbound method reference
    .sorted((a, b) -> a.compareTo(b))      // sorted(Comparator<T>)
    .peek(n -> System.out.println("peek: " + n)) // peek(Consumer<T>) — debugging hook
    .toList();

Optional<String> longest = names.stream()
    .reduce(BinaryOperator.maxBy(Comparator.comparingInt(String::length))); // reduce(BinaryOperator<T>)

double avgLength = names.stream()
    .mapToInt(String::length)             // mapToInt(ToIntFunction<T>)
    .average().orElse(0);
💡 Interview framing: streams don't add any new lambda mechanics — every single stage is just "here's a functional interface parameter, here's a lambda or method reference satisfying it." Understanding lambdas fully means the Stream API's method signatures stop needing memorization.

Short-answer FAANG questions

❓ What makes an interface "functional"?

  • Exactly one abstract method (SAM — Single Abstract Method)
  • default and static methods don't count toward that limit
  • Methods re-declaring an Object method (equals/hashCode/toString) don't count either
  • @FunctionalInterface is optional but enforces the rule at compile time

❓ Why must captured locals be effectively final?

  • Locals live on the stack frame, which may be gone by the time the lambda runs
  • The lambda captures a VALUE COPY at creation time, not a live reference
  • Allowing mutation would create a disconnect between the copy and any "current" value — Java disallows it outright rather than define confusing semantics

❓ Does a lambda create a new class file?

  • No separate .class file at compile time, unlike anonymous inner classes
  • Compiled to an invokedynamic instruction
  • The actual implementation class is generated at runtime by LambdaMetafactory, often cached

❓ Can lambdas be serialized?

  • Only if the target functional interface extends Serializable
  • Not recommended for general use — the serialized form is JVM-implementation-specific and fragile across JDK versions
  • Comparator.comparing(...) chains sometimes need this for distributed sort scenarios

❓ Bound vs unbound method reference — what's the difference?

  • Bound: obj::method — object already fixed, only the remaining args are supplied
  • Unbound: ClassName::method — the object itself becomes the first parameter at call time
  • Static: ClassName::staticMethod — no object involved at all

❓ Can a lambda implement an abstract class?

  • No — only interfaces, and only functional (single-abstract-method) ones
  • An abstract class can have constructors and instance state — a lambda has neither
  • If you need that, you still need an anonymous inner class or subclass

❓ Do lambdas support overloading like normal methods?

  • No — a lambda has no name of its own, so there's nothing to overload
  • What IS possible: overloading a method that accepts different functional interface parameter types, and letting the compiler pick based on the lambda's inferred shape
  • Ambiguous cases (same param count on two different FIs) may need an explicit cast

❓ Function vs UnaryOperator — when does it matter?

  • UnaryOperator<T> IS-A Function<T,T>, just narrower typing
  • APIs like List.replaceAll(UnaryOperator<E>) specifically require the narrower type
  • Prefer UnaryOperator/BinaryOperator whenever input and output types match — signals intent

❓ Runnable vs Callable — when to use which?

  • Runnable: no return value, cannot throw a checked exception
  • Callable<V>: returns a value, CAN throw checked Exception
  • ExecutorService.submit() is overloaded for both — Callable when you need a result or need to propagate a checked exception
Interview Reference

Interview Cheatsheet

One-liners for when you're under pressure. Know these cold.

λ What a lambda is

  • Nameless, anonymous implementation of a functional interface's single method
  • Target-typed — the variable's declared interface type tells the compiler what to expect
  • No new bytecode construct — compiled via invokedynamic + LambdaMetafactory

🎯 Functional interface rule

  • Exactly ONE abstract method (SAM)
  • default/static methods don't count
  • Re-declared Object methods (equals/hashCode/toString) don't count
  • @FunctionalInterface is optional, but enforces the rule at compile time

✍️ Syntax quick ref

  • () mandatory for zero params
  • Parens optional for exactly ONE untyped param
  • Parens mandatory for 2+ params, or any typed param
  • Expression body: no braces, no return, no semicolon
  • Block body: braces + explicit return required

⚖️ Lambda vs anonymous class

  • Lambda's "this" = enclosing instance; anon class's "this" = itself
  • Lambda can't shadow enclosing local variable names; anon class can
  • Lambda: no separate .class file. Anon class: Outer$N.class
  • Lambda: only functional interfaces. Anon class: any interface/abstract class

🔒 Variable capture

  • Local variables: must be final or effectively final; captured BY VALUE
  • Instance/static fields: no restriction, freely mutable, captured BY REFERENCE
  • Loop variables get a fresh binding per iteration — safe to capture

📚 java.util.function core 4

  • Function<T,R> — apply(T) → R
  • Supplier<T> — get() → T
  • Consumer<T> — accept(T) → void
  • Predicate<T> — test(T) → boolean
  • + Bi- variants for 2 inputs, Unary/BinaryOperator for same-type in/out

🔗 Composition defaults

  • Function: andThen (this→arg), compose (arg→this)
  • Predicate: and, or, negate — short-circuiting like &&/||
  • Consumer: andThen — runs both, no value passed between

🔖 Method reference — 4 kinds

  • Static: ClassName::staticMethod
  • Bound instance: obj::instanceMethod
  • Unbound instance: ClassName::instanceMethod (obj becomes 1st param)
  • Constructor: ClassName::new

🚨 Top interview traps

  • Captured local reassigned anywhere in scope → compile error
  • 2 abstract methods + @FunctionalInterface → compile error
  • Checked exception thrown directly from a standard-FI lambda → compile error
  • Lambda shadowing an enclosing local name → compile error
  • Bound vs unbound method reference confused → wrong parameter count assumed

💥 Checked exceptions in lambdas

  • Built-in FIs don't declare throws — checked exceptions can't cross directly
  • Fix 1: try-catch inside, rethrow as UncheckedIOException/RuntimeException
  • Fix 2: define a custom FI with `throws E` on its method
