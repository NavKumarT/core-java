Backend Engineering Fundamentals

The vocabulary everything else in this document assumes.

ConceptDefinition

Stateless serviceEach request contains everything needed to process it — no server-side session memory between requests. HTTP Deep Dive

Fast, dense reference — the mechanics every FastAPI route sits on top of.

MethodSemanticsIdempotent?
GETRetrieve a resource, no side effectsYes
POSTCreate a resource, or trigger a non-idempotent actionNo
PUTReplace a resource entirelyYes
PATCHPartially update a resourceNot necessarily
DELETERemove a resourceYes (deleting twice = same end state)
Status codeMeaning
400Bad request — malformed input, client's fault
401Unauthenticated — no valid credentials provided at all
403Unauthorized — credentials valid, but lack permission for this specific action
422Validation error — FastAPI's default for a Pydantic validation failure
429Rate limited — tied directly to Section 15
502Bad gateway — an upstream service (e.g. the LLM provider) returned an invalid response
503Service unavailable — the server itself is overloaded or down, often temporary
Idempotency, precisely — and why it matters more here than in typical REST APIs

An idempotent operation produces the same end state no matter how many times it's applied. This is the exact same concept as Topic 7's idempotency-key material for tool calls — a POST /agent/refund endpoint retried by a flaky client (or an agent's own retry logic) must not double-refund, which means the endpoint needs an idempotency key even though POST is not idempotent by HTTP's own definition.

REST API Design

The design decisions that separate a usable API from an unusable one.

PrincipleApplied
Resource-oriented namingPOST /conversations/{id}/messages, not POST /sendMessage — nouns, not verbs, in the URL
PaginationCursor-based (opaque token pointing to "next page") over offset-based for any dataset that mutates while being paginated — offset pagination silently skips or duplicates rows under concurrent writes
Versioning/v1/... in the URL path is the simplest, most explicit approach — critical for an AI API specifically, since prompt/model changes behind an endpoint are real behavioral changes (Topic 7's canary deployment material) that consumers need a stable contract to depend on across
Consistent error schemaEvery error response, across every endpoint, should share one shape (Section 08) — inconsistent error formats are one of the most common real API usability complaints

FastAPI Fundamentals

The framework's core value proposition: your Pydantic models (Doc 18 §05) become your request validation, your response schema, AND your auto-generated API documentation, from one source of truth.

main.py — a real minimal AI service route
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI(title="Agent Service", version="1.0.0")

class ChatRequest(BaseModel):
    message: str = Field(min_length=1, max_length=4000)
    thread_id: str | None = None       # maps directly to LangGraph's thread_id

class ChatResponse(BaseModel):
    reply: str
    thread_id: str

@app.post("/v1/chat", response_model=ChatResponse)      # response_model both validates AND filters the output
async def chat(req: ChatRequest) -> ChatResponse:
    thread_id = req.thread_id or new_thread_id()
    result = await agent_graph.ainvoke(
        {"messages": [{"role": "user", "content": req.message}]},
        {"configurable": {"thread_id": thread_id}},
    )
    return ChatResponse(reply=result["messages"][-1].content, thread_id=thread_id)

Every FastAPI app automatically serves an OpenAPI schema (/openapi.json) generated directly from your route type hints and Pydantic models, plus interactive docs at /docs (Swagger UI) and /redoc — zero extra code required. This is the same core insight as Topic 12's tool schemas: type hints and Pydantic models aren't decoration, they're the literal source of a machine-readable contract, whether that contract is consumed by an LLM (a tool schema) or by API clients (an OpenAPI spec).

response_model does two jobs at once — a subtle, important point

response_model both validates your return value against the schema (catching a bug where your handler accidentally returns an extra internal field) and filters the output to exactly that schema's fields — meaning even if your handler's returned object has extra attributes (e.g. an internal debug field), only the declared fields are ever serialized to the client. This is a real security-relevant behavior, not just a convenience: it's your last line of defense against accidentally leaking an internal field to an external caller.

Dependency Injection

FastAPI's Depends system is the direct application-layer parallel to Pydantic AI's RunContext from Topic 12 — shared resources, injected, never global state.

dependencies.py
from fastapi import Depends, HTTPException, Header

# a shared, connection-pooled resource -- constructed once per request, injected everywhere it's needed
async def get_db_session():
    async with async_session_factory() as session:
        yield session                     # yield-based dependency: cleanup runs after the request, like a context manager

# authentication as a dependency -- reusable across every protected route
async def get_current_user(authorization: str = Header(...)) -> User:
    token = authorization.removeprefix("Bearer ")
    user = await verify_jwt(token)
    if not user:
        raise HTTPException(status_code=401, detail="Invalid or expired token")
    return user

# composing dependencies -- this route gets a validated user AND a DB session, for free
@app.get("/v1/conversations")
async def list_conversations(
    user: User = Depends(get_current_user),
    db = Depends(get_db_session),
):
    return await db.get_conversations(user.id)
Why this matters for testing (ties directly to Section 19)

FastAPI lets you override any dependency in tests via app.dependency_overrides[get_current_user] = lambda: fake_user — swap in a fake authenticated user or a fake DB session without touching route code at all. This is the same "mock the boundary" discipline as Doc 18's testing section, applied at the API layer instead of the model-client layer.

06 ★★

Async FastAPI

This section exists to answer one specific, near-universal interview question with total confidence.

"What happens if you call a blocking function inside an async FastAPI endpoint?" — the complete answer

FastAPI runs each async def endpoint as a coroutine on the single event loop. If that coroutine calls a blocking (synchronous, CPU- or I/O-blocking) function directly — a synchronous DB driver call, a synchronous requests.get(), time.sleep() — that call blocks the entire event loop for its duration, not just the current request. Every other concurrent request being served by that worker process stalls until the blocking call finishes, silently destroying the concurrency the async model was supposed to provide. The server doesn't crash and no error is raised — it just gets quietly, catastrophically slower under load, which is exactly what makes this bug dangerous: it's invisible in local single-request testing and only shows up under real concurrent traffic.

FixWhen to use it
Use an async-native libraryAlways the first choice — async DB drivers (asyncpg via SQLAlchemy's async engine), httpx/aiohttp instead of requests, async model clients (model.ainvoke from Topic 12/Doc 18)
Run the blocking call in a thread poolWhen no async version exists — await run_in_threadpool(blocking_fn, *args) (FastAPI's built-in helper) offloads it to a worker thread so the event loop keeps serving other requests
Define the route as plain def, not async defFastAPI automatically runs synchronous (def) route handlers in a thread pool already — a legitimate option specifically for routes that are inherently CPU-bound or fully synchronous, but it forfeits the concurrency benefit for anything that could otherwise be async
the_bug_and_the_fix.py
# WRONG -- blocks the entire event loop for every concurrent request during this call
@app.post("/v1/legacy-lookup")
async def legacy_lookup(query: str):
    result = requests.get(f"https://legacy-api/search?q={query}")   # sync call inside async def!
    return result.json()

# FIX 1 -- use the async client (Doc 18 §11)
@app.post("/v1/lookup")
async def lookup(query: str):
    resp = await http_client.get(f"https://api/search?q={query}")   # httpx.AsyncClient
    return resp.json()

# FIX 2 -- no async version exists, offload to a thread instead
from fastapi.concurrency import run_in_threadpool

@app.post("/v1/legacy-lookup")
async def legacy_lookup(query: str):
    result = await run_in_threadpool(requests.get, f"https://legacy-api/search?q={query}")
    return result.json()

Middleware & Request Lifecycle

Code that runs around every request, regardless of which route handles it — the natural home for cross-cutting concerns.

middleware.py
import time, uuid
from starlette.middleware.base import BaseHTTPMiddleware

class RequestContextMiddleware(BaseHTTPMiddleware):
    """Attaches a request ID and timing to every request -- feeds Doc 18 §13's
    structured logging and Section 17's tracing directly."""
    async def dispatch(self, request, call_next):
        request_id = str(uuid.uuid4())
        request_id_var.set(request_id)               # the contextvar from Doc 18 §13
        start = time.monotonic()
        response = await call_next(request)
        response.headers["X-Request-ID"] = request_id
        response.headers["X-Response-Time"] = f"{time.monotonic() - start:.3f}"
        return response

app.add_middleware(RequestContextMiddleware)

Error Handling

Consistent error shape everywhere, and never leak internals to the client.

error_handlers.py
from fastapi import Request
from fastapi.responses import JSONResponse

class AgentError(Exception):                     # from Doc 18 §06's exception hierarchy
    def __init__(self, message: str, code: str):
        self.message, self.code = message, code

@app.exception_handler(AgentError)
async def handle_agent_error(request: Request, exc: AgentError):
    logger.error(f"AgentError: {exc.code}", extra={"request_id": request_id_var.get()})
    return JSONResponse(status_code=502, content={
        "error": {"code": exc.code, "message": exc.message, "request_id": request_id_var.get()}
    })

@app.exception_handler(Exception)      # catch-all: NEVER return a raw traceback/exception string to the client
async def handle_unexpected(request: Request, exc: Exception):
    logger.exception("Unhandled exception")
    return JSONResponse(status_code=500, content={
        "error": {"code": "internal_error", "message": "An unexpected error occurred."}
    })
Information leakage — a real, common vulnerability class

Returning a raw stack trace, an internal exception message, or a database error string to an external client leaks implementation details an attacker can use (library versions, internal file paths, query structure). Always map internal exceptions to a small, deliberate set of external-facing error codes and generic messages — log the full detail server-side, return the minimum necessary externally. This is a direct instance of Topic 6's least-privilege principle applied to error responses.

Authentication & Authorization

Who are you (authentication) vs what are you allowed to do (authorization) — the same distinction from Topic 6's OWASP material, now at the API layer.

MechanismBest for
API keysService-to-service auth, simple B2B integrations — easy to issue/revoke, no built-in expiry semantics
JWT (JSON Web Tokens)Stateless user sessions — the token itself carries claims (user ID, roles), verifiable without a DB round-trip; use short-lived access tokens plus a longer-lived refresh token
OAuth2Delegated authorization — "let this app act on my behalf" — the standard for third-party integrations
RBAC (Role-Based Access Control)Coarse-grained authorization — a user's role (admin, member, viewer) determines what endpoints/actions they can reach
The direct link to Topic 6's Excessive Agency material

An agent backend introduces a specific authorization wrinkle beyond typical CRUD APIs: the agent acts on behalf of a user, and its tool calls need to inherit that user's actual permission scope — not a blanket service-level credential. This is Topic 6's least-privilege principle applied concretely: a support agent's refund tool should be scoped to the authenticated user's own account/permissions, not a superuser API key the agent process happens to hold.

Databases & FastAPI

SQLAlchemy's async engine, and the one query-pattern bug that shows up in nearly every real backend eventually.

async_sqlalchemy.py
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
from sqlalchemy.orm import selectinload

engine = create_async_engine("postgresql+asyncpg://...", pool_size=20, max_overflow=10)
async_session_factory = async_sessionmaker(engine, expire_on_commit=False)

# N+1 query problem: looping and querying per-item instead of one batched query
# BAD:
for conv in conversations:
    messages = await db.execute(select(Message).where(Message.conv_id == conv.id))  # N extra queries!

# GOOD -- eager-load the relationship in the original query
result = await db.execute(
    select(Conversation).options(selectinload(Conversation.messages))
)
Connection pooling, sized correctly

The pool must be sized against your actual concurrency, not guessed — too small and requests queue waiting for a connection under load; too large and you can exhaust the database's own max-connections limit. Since agent requests can be long-running (a multi-step trajectory holding a connection across several LLM calls), size pools conservatively and prefer opening a connection only for the specific DB operation, not for the full duration of an agent run.

semantic_cache_redis.py
import redis.asyncio as redis, hashlib, json

r = redis.Redis(host="localhost", decode_responses=True)

async def cache_aside_get_or_generate(prompt: str, ttl_seconds: int = 3600) -> str:
    """Cache-aside pattern: check cache, miss -> generate, then populate cache."""
    key = f"llm:exact:{hashlib.sha256(prompt.encode()).hexdigest()}"
    cached = await r.get(key)
    if cached:
        return cached
    result = await model.ainvoke(prompt)
    await r.set(key, result.content, ex=ttl_seconds)     # ex= sets TTL directly
    return result.content

agent_endpoint.py
class AgentRunRequest(BaseModel):
    task: str
    thread_id: str | None = None
    tool_allowlist: list[str] | None = None    # Topic 6: least-privilege, scoped per-request

class AgentRunResponse(BaseModel):
    run_id: str
    status: Literal["completed", "requires_approval"]
    result: str | None = None
    pending_action: dict | None = None          # foundational bible: interrupt_before payload

@app.post("/v1/agent", response_model=AgentRunResponse)
async def run_agent(req: AgentRunRequest, user: User = Depends(get_current_user)):
    thread_id = req.thread_id or str(uuid.uuid4())
    thread = {"configurable": {"thread_id": thread_id}}
    result = await agent_graph.ainvoke(
        {"messages": [{"role": "user", "content": req.task}], "user_id": user.id},
        thread,
    )
    state = await agent_graph.aget_state(thread)
    if state.next:                              # graph paused -- interrupt_before fired, needs human approval
        return AgentRunResponse(run_id=thread_id, status="requires_approval",
                                pending_action=state.values["messages"][-1].tool_calls[0])
    return AgentRunResponse(run_id=thread_id, status="completed",
                            result=result["messages"][-1].content)

Streaming AI Responses

Directly implementing the foundational bible's streaming chapter and Topic 7's TTFT material as real HTTP endpoints.

Server-Sent Events (SSE)WebSockets
DirectionOne-way, server → clientBidirectional
ProtocolPlain HTTP, works through most proxies/load balancers without special configA protocol upgrade from HTTP — needs explicit infra support (proxies, load balancers must support the upgrade)

sse_streaming_endpoint.py
from fastapi.responses import StreamingResponse
import json

async def event_generator(task: str, thread: dict):
    try:
        async for event in agent_graph.astream_events(
            {"messages": [{"role": "user", "content": task}]}, thread, version="v1"
        ):
            if event["event"] == "on_chat_model_stream":
                content = event["data"]["chunk"].content
                if content:                            # the foundational bible's empty-content gotcha
                    yield f"data: {json.dumps({'type': 'token', 'content': content})}\n\n"
            elif event["event"] == "on_tool_start":
                yield f"data: {json.dumps({'type': 'tool_call', 'name': event['name']})}\n\n"
    except asyncio.CancelledError:
        # client disconnected mid-stream -- clean up, don't let the agent run orphaned
        logger.info("Client disconnected, stopping stream")
        raise
    finally:
        yield f"data: {json.dumps({'type': 'done'})}\n\n"

@app.post("/v1/agent/stream")
async def stream_agent(req: AgentRunRequest):
    thread = {"configurable": {"thread_id": req.thread_id or str(uuid.uuid4())}}
    return StreamingResponse(event_generator(req.task, thread), media_type="text/event-stream")
Client disconnects — the failure mode most streaming endpoints get wrong

If a client closes the connection mid-stream (closed browser tab, network drop) and your generator doesn't handle asyncio.CancelledError, the underlying agent run can keep executing tool calls and burning tokens for a response nobody will ever receive. Always catch cancellation explicitly and stop the underlying agent invocation — this is a real, silent cost leak in production streaming endpoints that don't handle it.

Background Tasks & Job Queues

The pattern for anything too slow to hold an HTTP connection open for — exactly Topic 3's deep-research-agent latency profile.

ToolWhen it's enough / not enough
FastAPI BackgroundTasksFine for lightweight, fire-and-forget work within the same process (send a notification email after responding) — insufficient for anything long-running, since it dies with the worker process and has no retry/persistence

@app.post("/v1/research", status_code=202)     # 202 Accepted -- work queued, not yet done
async def start_research(req: ResearchRequest) -> dict:

    await job_store.create(job_id, status="queued")
    await queue.enqueue("run_research_agent", job_id=job_id, query=req.query)

        raise HTTPException(404, "job not found")
    return {"status": job.status, "result": job.result if job.status == "completed" else None}

Rate Limiting & Quotas

Doc 18's token-bucket limiter, now made distributed via Redis so it works correctly across multiple server processes.

redis_rate_limit_dependency.py
async def rate_limit(user: User = Depends(get_current_user)):
    key = f"ratelimit:{user.id}"
    # atomic INCR + conditional EXPIRE -- correct even under concurrent requests
    # from the SAME user hitting DIFFERENT server processes simultaneously
    count = await r.incr(key)
    if count == 1:
        await r.expire(key, 60)              # 60-second window
    if count > user.rate_limit_per_minute:
        raise HTTPException(429, detail="Rate limit exceeded")

@app.post("/v1/chat", dependencies=[Depends(rate_limit)])   # applied as a dependency -- composes with auth cleanly
async def chat(req: ChatRequest): ...

Per-user request limits are only half the picture for an AI API specifically — token-based limits matter just as much, since a single request's cost varies enormously with output length and context size (Topic 7's token economics). Production AI gateways typically enforce both a requests/minute cap and a tokens/minute cap simultaneously.

Observability

Wiring Topic 7's OTel GenAI material into an actual FastAPI app.

otel_instrumentation.py
from opentelemetry.instrumentation.fastapi import FastAPIInstrumentor

FastAPIInstrumentor.instrument_app(app)   # auto-instruments every route as a span, zero manual wiring

# health vs readiness -- a real, commonly-tested distinction
@app.get("/healthz")                        # liveness: is the process alive at all?
async def healthz():
    return {"status": "ok"}

@app.get("/readyz")                        # readiness: can it actually SERVE traffic right now?
async def readyz():
    try:
        await db.execute(select(1))
        await r.ping()
        return {"status": "ready"}
    except Exception:
        raise HTTPException(503, "dependencies unavailable")
Liveness vs readiness, precisely — a real orchestrator (Kubernetes) distinction

Liveness answers "should the orchestrator restart this process" — a failing liveness check means the process itself is stuck/deadlocked. Readiness answers "should the load balancer send this instance traffic right now" — a process can be alive but not ready (e.g. its DB connection pool hasn't finished initializing, or a downstream dependency is temporarily down) without needing a restart, just a temporary traffic pause.

Security

This section is deliberately a bridge, not a repeat — Topic 6 is the canonical source; here's exactly how those concepts land at the API layer.

RiskAPI-layer manifestation
Prompt injection / indirect injectionAny endpoint accepting user text that flows into an agent's context (Topic 6's lethal trifecta) — validate/sanitize at the boundary, but remember detection alone doesn't close the trifecta; architectural controls (Topic 6 §05-06) still apply
SSRF (Server-Side Request Forgery)An agent tool that fetches a URL supplied by user input can be tricked into making the server request internal/forbidden addresses — validate and allowlist outbound destinations, never pass raw user-supplied URLs to an unrestricted fetch
Excessive Agency / tool authorizationDirectly Topic 6 §07 — every tool endpoint scoped to least privilege, checked against the authenticated user's actual permissions, not a blanket service credential
File-upload securityAny /v1/upload endpoint feeding a RAG pipeline — validate file type/size server-side (never trust the client-reported content-type), scan for malicious content, and isolate processing (never execute uploaded content)
PII handlingStructured logging (Section 17) must not log full prompt/response bodies by default in a way that captures PII — redact or hash sensitive fields before they hit a log aggregator
Interview framing

"How do you secure a file-upload endpoint that feeds a RAG pipeline?" — Validate file type and size server-side using the actual file content (magic bytes), not the client-supplied content-type header, which is trivially spoofable. Process uploads in an isolated environment (Topic 6's sandboxing principle) rather than the main API process. Scan for malicious content before ingestion. And treat the uploaded document's text exactly like any other untrusted content once it enters the RAG pipeline — Topic 6's lethal trifecta framing applies directly, since a malicious document is a textbook indirect-prompt-injection vector.

Production Architecture

Where a real AI backend lands on the monolith-to-microservices spectrum in practice.

PatternWhen it's the right call
Modular monolithThe honest default for most teams starting out — one deployable, but internally organized into clear service-layer modules (AI service, RAG service, tool service as separate internal packages) so a future split to real microservices is a refactor, not a rewrite
AI gateway / model gatewayA dedicated service in front of all LLM calls — centralizes routing (Topic 7), rate limiting (Section 15), caching, and provider fallback, so every other service calls one internal gateway instead of each independently wiring provider SDKs
Separate RAG / tool / worker servicesJustified once one component's scaling needs diverge sharply from the rest — e.g. the embedding/retrieval service needs GPU-backed infrastructure while the API layer doesn't, making a shared deployable wasteful
The same discipline as Topic 3's multi-agent economics

Splitting into microservices prematurely adds real operational overhead (network calls where function calls used to suffice, distributed tracing complexity, more deployment surface) for a scaling problem you may not actually have yet. Default to a modular monolith; split specific components out only once you have a measured, specific reason — the same "prove you need the complexity first" discipline that runs through this entire series.

Interview Cheat-Sheet

The generic backend comparisons the outline calls for, plus AI-specific system design prompts.

REST vs GraphQL — when would you choose each for an AI API?core

REST's resource-oriented, cacheable-by-URL model fits most AI API shapes well (chat, embed, retrieve are naturally distinct resources/actions), and its simplicity matches most client needs. GraphQL earns its complexity when clients have highly variable data needs from the same underlying resources (e.g. a dashboard needing different slices of conversation/agent-run data per view) and over-fetching with REST would be a real problem — less common for AI-specific endpoints, more common for a broader product surface built around the same data.

PUT vs PATCH, and GET vs POST — the precise distinctions.core

PUT replaces a resource entirely (idempotent — sending the same PUT twice yields the same end state); PATCH applies a partial update (idempotency depends on the specific patch semantics). GET retrieves without side effects and is safely cacheable/idempotent; POST typically creates a resource or triggers a non-idempotent action and should never be used for a pure read, both for caching correctness and because some infrastructure (browsers, proxies) treats GET and POST very differently around retries and caching.

WebSockets vs SSE — which would you choose for streaming agent tokens, and why?core

SSE, for the large majority of LLM token-streaming use cases — it's plain HTTP (simpler infrastructure, works through most proxies without special configuration) and the communication is inherently one-directional (server streams tokens to the client; the client doesn't need to send data mid-stream). Choose WebSockets specifically when the interaction is genuinely bidirectional in real time — a voice agent with simultaneous audio in and out is the clearest example.

Design a streaming AI API end to end.design

SSE endpoint (Section 13) wrapping graph.astream_events, filtering for on_chat_model_stream token events and on_tool_start events, formatted as typed JSON events over the SSE wire format. Explicitly handle client disconnection via asyncio.CancelledError to stop the underlying agent run rather than letting it execute orphaned. Layer rate limiting (Section 15) and auth (Section 09) as FastAPI dependencies ahead of the streaming handler. Instrument with request-ID correlation (Section 07) so a slow or failed stream is traceable end-to-end in observability tooling (Section 17).

Design an async agent API that supports human-in-the-loop approval.design

Exactly Section 12's worked endpoint: compile the LangGraph agent with interrupt_before on any sensitive tool node (foundational bible). The POST /v1/agent endpoint invokes the graph, then checks graph.aget_state(thread) — if state.next is non-empty, the graph paused and the response returns status="requires_approval" with the pending tool call's details instead of a final result. A separate POST /v1/agent/{thread_id}/approve endpoint calls graph.astream(None, thread) to resume, or a /reject endpoint that ends the thread without resuming. Idempotency keys (Section 01/16) on the approve endpoint specifically, since a duplicated approval request must not execute the sensitive action twice.

How would you design an LLM gateway sitting in front of multiple internal services?design

A dedicated FastAPI service (Section 22's AI gateway pattern) that every internal service calls instead of talking to LLM providers directly — centralizing model routing/cascades (Topic 7), per-service and per-token rate limiting (Section 15), prompt/semantic caching (Section 11), provider fallback (Doc 18 §17's RobustLLMClient pattern), and unified observability (Section 17) in one place rather than duplicated across every service that needs model access. This also makes a provider outage or a model deprecation a one-service change instead of a scattered migration across the whole backend.

Glossary

Every term used in this document.

ASGI
Asynchronous Server Gateway Interface — the async successor to WSGI; Uvicorn is an ASGI server, FastAPI is an ASGI framework.
response_model
FastAPI parameter both validating and filtering a route's output to a declared Pydantic schema.
Depends
FastAPI's dependency injection mechanism for shared, composable, overridable resources.
run_in_threadpool
FastAPI helper offloading a blocking call to a thread so the event loop isn't stalled.
N+1 query problem
Issuing one query per item in a loop instead of one batched/eager-loaded query.
Cache-aside pattern
Check cache first, generate and populate on miss.
SSE (Server-Sent Events)
One-way HTTP streaming protocol from server to client.
202 Accepted
HTTP status indicating work was queued, not yet completed — the background-job pattern's response.
Liveness vs readiness
Is the process alive (restart if not) vs is it ready to serve traffic (pause routing if not).
P95 / P99 latency
Tail-latency percentiles; the metric SLAs are typically written against, unlike averages.
Modular monolith
A single deployable internally organized into clearly separated service modules.
AI gateway / model gateway
A dedicated internal service centralizing all LLM provider calls, routing, caching, and rate limiting.
