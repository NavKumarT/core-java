How Tool Calling Actually Works, Under the Hood

Building directly on Topic 11: the model is still just predicting tokens. "Calling a tool" is a specific, structured shape those tokens are trained to take.

Recall from Topic 11 that a model only ever does one thing: predict a probability distribution over its next token, repeatedly. Tool calling doesn't add a new capability to the model architecture — it's a training and prompting convention. During SFT and preference alignment, models are specifically trained on examples where, instead of producing plain text, the "correct" continuation is a structured, machine-parseable object naming a function and its arguments. Nothing about the transformer changes; what changes is that the model has learned when that structured shape is the right continuation, and how to fill in valid arguments for it.

The three-part contract

  1. You describe the tools. Every tool is turned into a JSON Schema — name, description, and a typed parameter list — and sent to the model alongside your prompt on every single call. The model does not "remember" tools between calls; you resend the schema every time.
  2. The model emits a structured call instead of text. If the model decides a tool is the right next step, instead of (or alongside) plain text, it emits a JSON object matching one of the schemas you provided — a name and an arguments object.
  3. You execute it and send the result back. The model itself never runs any code — your application code reads the emitted tool call, executes the real function, and sends the result back into the conversation as a new message, so the model can use it to decide what happens next.
ProviderWire format quirk worth knowing
OpenAITool calls appear as a tool_calls array on the assistant message; each call has an id used to match a later tool-role message back to it.
AnthropicTool use appears as a tool_use content block (alongside possible text blocks in the same message); results are returned as a tool_result content block referencing the same id.
BothNeither provider "remembers" a tool across calls — every request resends the full tool schema list, which is exactly why Topic 7's prompt caching applies directly to tool definitions: a stable, unchanging tool schema block is prime cacheable content.
The direct link back to the foundational agent loop

This is precisely the mechanism behind model.bind_tools([...]) and exists_action from the foundational LangGraph bible — bind_tools is what attaches the JSON schemas to every request, and len(result.tool_calls) > 0 is literally checking whether the model's last message contained one of these structured objects instead of (or alongside) plain text.

01

Defining Tools in LangChain

Three ways to define a tool, from simplest to most explicit — know when to reach for each.

The simplest form — @tool with a docstring

simple_tool.py
from langchain_core.tools import tool

@tool
def get_order_status(order_id: str) -> str:
    """Look up the current status of a customer order by its order ID."""
    # the docstring above becomes the tool's "description" field
    # the type hint (str) becomes the JSON schema type for order_id
    order = db.get_order(order_id)
    return f"Order {order_id} is currently: {order.status}"

The docstring is not a comment — it's sent directly to the model as the tool's description, and is exactly what the model uses to decide whether this tool is relevant to the current task. A vague docstring produces unreliable tool selection; a precise one (what it does, when to use it, what it returns) measurably improves tool-choice accuracy.

Explicit schema with Pydantic — when types alone aren't enough

pydantic_tool_schema.py
from pydantic import BaseModel, Field
from langchain_core.tools import StructuredTool

class RefundInput(BaseModel):
    order_id: str = Field(description="The order ID to refund, e.g. 'ORD-4471'")
    amount_usd: float = Field(description="Refund amount in USD, must be positive", gt=0)
    reason: str = Field(description="Short reason for the refund, shown in the audit log")

def issue_refund(order_id: str, amount_usd: float, reason: str) -> str:
    # gt=0 above is enforced BEFORE this function body ever runs --
    # an invalid amount never reaches your business logic at all
    result = payments.refund(order_id, amount_usd, reason)
    return f"Refunded ${amount_usd} for {order_id}"

refund_tool = StructuredTool.from_function(
    func=issue_refund,
    name="issue_refund",
    description="Issue a refund for a customer order. Requires human approval above $100.",
    args_schema=RefundInput,
)
Why bother with the Pydantic version

Field-level validation (gt=0, string patterns, enums) is enforced automatically before your function body ever executes — the model can still try to call the tool with a negative refund amount, but LangChain's argument validation rejects it and returns a validation error back to the model as an observation, exactly like the "bad tool name, retry" self-correction pattern from the foundational bible, just for arguments instead of tool names.

02

The Execution Loop in LangGraph

A tightened, production-ready version of the foundational bible's take_action node — now with validation and error recovery made explicit.

robust_take_action.py
from langchain_core.messages import ToolMessage
from pydantic import ValidationError

def take_action(state: AgentState) -> dict:
    tool_calls = state["messages"][-1].tool_calls
    results = []
    for call in tool_calls:
        name, args, call_id = call["name"], call["args"], call["id"]
        if name not in tools_by_name:
            content = f"Error: no tool named '{name}'. Available tools: {list(tools_by_name)}"
        else:
            try:
                content = str(tools_by_name[name].invoke(args))   # Pydantic validation happens here
            except ValidationError as e:
                # feed the validation error back as the observation -- the model sees
                # exactly what was wrong with its own arguments and can self-correct
                content = f"Error: invalid arguments for {name}: {e}"
            except Exception as e:
                content = f"Error: {name} failed during execution: {e}"
        results.append(ToolMessage(tool_call_id=call_id, name=name, content=content))
    return {"messages": results}
Never let a tool exception kill the graph run

An unhandled exception inside a tool call, if not caught, propagates up and crashes the entire LangGraph run — losing the whole conversation's progress for what might be a single bad argument. The try/except shown above is not optional defensive style; it's the difference between "the agent recovers and tries again" and "the whole run dies," and it's exactly the same discipline as Topic 7's retry/circuit-breaker material, applied at the individual tool-call level.

03

Parallel vs Sequential Tool Calls

A single model turn can request several tool calls at once — most agent code executes them sequentially by default, leaving real latency on the table.

When a model decides it needs multiple independent pieces of information (e.g., "check the weather in SF and LA"), it can emit multiple tool calls in a single tool_calls array on one message, rather than calling one, waiting, then calling the next. Your execution code decides whether to run them sequentially or concurrently — the model has no opinion on this, it only decided what to call, not how you execute it.

parallel_execution.py
import asyncio
from langchain_core.messages import ToolMessage

async def take_action_parallel(state: AgentState) -> dict:
    tool_calls = state["messages"][-1].tool_calls

    async def run_one(call):
        name, args, call_id = call["name"], call["args"], call["id"]
        try:
            content = str(await tools_by_name[name].ainvoke(args))
        except Exception as e:
            content = f"Error: {name} failed: {e}"
        return ToolMessage(tool_call_id=call_id, name=name, content=content)

    # independent tool calls run concurrently instead of one-by-one
    results = await asyncio.gather(*[run_one(c) for c in tool_calls])
    return {"messages": list(results)}
Execute in parallel when...Execute sequentially when...
The calls are genuinely independent (two separate lookups with no shared dependency) — direct latency winA later call's arguments depend on an earlier call's result within the same batch (rare — the model usually won't request this shape, since it can't know the result yet)
The tools are read-only or otherwise safe to run concurrentlyTools have side effects that must not race — e.g., two calls that both modify the same record
Interview framing

"How would you speed up an agent that frequently needs to call 3-4 independent APIs per turn?" — Check whether the tool-call executor is currently sequential; if so, switch to concurrent execution via asyncio.gather (or your framework's async tool-call primitive) for calls within the same model turn, since the model already batches independent calls into one tool_calls array — most of the available speedup is simply not being captured by naive sequential execution code.

04 ★

Structured Outputs, Two Ways

Getting an LLM to reliably return JSON matching a schema — not for calling a real tool, but for extracting or formatting data — uses the exact same underlying mechanism as tool calling.

Mechanism 1 — structured output via a "fake" tool call

The oldest and most portable trick: define a Pydantic schema, present it to the model as if it were a tool to call, but never actually execute anything — you just read the arguments the model generated as your structured result. This is exactly what LangChain's with_structured_output() does under the hood on many providers.

with_structured_output.py
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI

class TicketClassification(BaseModel):
    category: Literal["billing", "technical", "account"] = Field(description="Primary ticket category")
    urgency: Literal["low", "medium", "high"] = Field(description="How urgent this ticket is")
    summary: str = Field(description="One-sentence summary of the customer's issue")

model = ChatOpenAI(model="gpt-4o")
classifier = model.with_structured_output(TicketClassification)

result = classifier.invoke("My card was charged twice for the same order, please help ASAP")
# result is a REAL TicketClassification instance, already validated -- not a string to parse
print(result.category)   # "billing"
print(result.urgency)    # "high"

Mechanism 2 — native JSON-schema / structured-output modes

Newer provider APIs (OpenAI's response_format with a JSON schema, Anthropic's structured output support) can constrain generation directly at decoding time — the model is prevented from generating any token that would violate the schema, rather than being asked nicely via a tool-call convention. This is a stronger guarantee: with true constrained decoding, invalid JSON is architecturally impossible, not just unlikely.

Tool-call-based structured outputNative constrained decoding
Guarantee strengthVery high, but not absolute — determined by training, not decoding constraintsAbsolute for schema shape — invalid JSON structure is impossible
PortabilityWorks across nearly every tool-calling-capable model, older and newerRequires explicit provider support for the feature
What it can't guaranteeSemantic correctness — a validly-shaped but factually wrong answer, or a value that's schema-valid but business-logic-invalid, still requires the retry loop belowSame limitation — shape is guaranteed, correctness of content is not
The gap neither mechanism closes

Both mechanisms guarantee shape — you will get valid JSON matching your schema's types. Neither guarantees correctness — a validly-typed urgency: "low" on a ticket that's actually urgent is a perfectly schema-valid, completely wrong output. Structured output solves a parsing problem, not an accuracy problem — accuracy is still Topic 5's territory entirely.

05

Validation & Retry-on-Invalid-Schema

The pattern that turns "usually correct" into "correct or explicitly failed after N attempts" — essential for any pipeline that can't tolerate silent bad data.

validate_and_retry.py
from pydantic import BaseModel, ValidationError, field_validator

class ExtractedInvoice(BaseModel):
    invoice_number: str
    total_usd: float
    line_items: list[str]

    @field_validator("total_usd")
    @classmethod
    def total_must_be_positive(cls, v):
        if v <= 0:
            raise ValueError("total_usd must be positive -- got a non-positive value")
        return v

def extract_with_retry(model, text: str, max_attempts: int = 3) -> ExtractedInvoice:
    structured_model = model.with_structured_output(ExtractedInvoice, include_raw=True)
    error_context = ""
    for attempt in range(max_attempts):
        try:
            result = structured_model.invoke(text + error_context)
            if result["parsing_error"] is None:
                return result["parsed"]
            raise result["parsing_error"]
        except (ValidationError, Exception) as e:
            # feed the EXACT validation error back to the model -- this is the whole trick
            error_context = f"\n\nYour previous attempt failed validation: {e}\nPlease correct it."
    raise RuntimeError(f"Failed to extract valid invoice after {max_attempts} attempts")

The core trick, worth naming explicitly: don't just retry blindly — feed the exact validation error message back into the next attempt's context. The model can usually self-correct a specific, named failure ("total_usd must be positive, got -50") far more reliably than it can guess what you wanted on a second blind attempt with no feedback.

Pydantic AI does this automatically — a preview of Section 06

This exact retry-with-error-feedback loop is precisely what Pydantic AI's ModelRetry mechanism automates natively — raise ModelRetry("reason") inside a validator or tool, and the framework handles resending it to the model for you, with a configurable retry budget. It's worth understanding the manual version above first, so the framework doesn't feel like magic.

06 ★

Pydantic AI, In Depth

A minimal, type-safe agent framework built by the Pydantic team, with a fundamentally different design philosophy than LangGraph — worth understanding on its own terms, not just as "LangGraph but smaller."

Pydantic AI is an agent framework built around three ideas: type-safe structured outputs via Pydantic models, dependency injection via a typed RunContext, and model-agnostic agents defined as plain Python. Where LangChain composes chains of abstractions (runnables, LCEL), Pydantic AI keeps you close to plain Python — an agent is a class, a tool is a function, an output is a Pydantic model.

Core concepts, in one example

pydantic_ai_full_example.py
from dataclasses import dataclass
from pydantic import BaseModel, Field
from pydantic_ai import Agent, RunContext, ModelRetry

# 1. Dependencies -- injected at runtime, no global state, fully type-checked
@dataclass
class SupportDeps:
    customer_id: str
    db: DatabaseConn

# 2. Output type -- the schema the agent MUST return, validated automatically
class SupportOutput(BaseModel):
    response: str = Field(description="Reply to send the customer")
    risk_level: Literal["low", "medium", "high"]

# 3. The agent itself -- model, deps type, output type, instructions
support_agent = Agent(
    "anthropic:claude-sonnet-4-6",
    deps_type=SupportDeps,
    output_type=SupportOutput,        # validation failure -> auto-retry against the model
    instructions="You are a bank support agent. Judge the risk level of every query.",
)

# 4. Dynamic instructions via dependency injection
@support_agent.instructions
async def add_customer_name(ctx: RunContext[SupportDeps]) -> str:
    name = await ctx.deps.db.customer_name(ctx.deps.customer_id)
    return f"The customer's name is {name!r}."

# 5. Tools -- plain functions, docstring becomes the description automatically
@support_agent.tool
async def get_account_balance(ctx: RunContext[SupportDeps], account_type: str) -> float:
    """Get the current balance for a given account type (checking/savings)."""
    balance = await ctx.deps.db.query_balance(ctx.deps.customer_id, account_type)
    if balance is None:
        # ModelRetry sends this message back to the model and lets it try again --
        # the same "feed the error back" trick from Section 05, now framework-native
        raise ModelRetry(f"No {account_type} account found for this customer.")
    return balance

# 6. Run it
result = await support_agent.run(
    "What's my checking balance and is anything unusual?",
    deps=SupportDeps(customer_id="cust_123", db=db_connection),
)
print(result.output.response)      # guaranteed to be a valid SupportOutput instance
print(result.output.risk_level)
ConceptWhat it does
deps_type / RunContextType-safe dependency injection — database connections, API clients, and session data are passed in at run time via ctx.deps, never global state, which makes agents genuinely easy to unit test (swap in a fake db for tests).
output_typeA Pydantic model the agent is guaranteed to return — if validation fails, the framework automatically re-prompts the model to try again, up to a configurable retry budget, with zero manual retry code required.
@agent.tool / @agent.tool_plainRegister a plain Python function as a tool; use @agent.tool (not tool_plain) specifically when the function needs RunContext access. Docstring and type hints become the tool's schema automatically.
ModelRetryRaise it inside a tool or validator to send a specific error message back to the model and force another attempt — the framework-native version of Section 05's manual retry loop.
Durable execution integrationNative TemporalAgent / DBOSAgent wrappers exist for production resilience — directly the durable-execution material from Topic 7, available as a drop-in integration rather than something you wire up yourself.
API naming has changed — know the current names

Pydantic AI's 2.0 release (June 2026) renamed key parameters — result_type became output_type, and system_prompt is now generally instructions. Older tutorials and blog posts online commonly still show the pre-2.0 names — if you see result_type in a code sample, mentally translate it, since that's stale API surface as of the current release.

07

Pydantic AI vs LangGraph

Not competitors so much as complements — they optimize for different things, and the honest answer to "which one" is "it depends what you're building."

Pydantic AILangGraph
Design centerType safety, validation, plain Python, minimal abstractionExplicit control flow as a graph — cycles, branching, checkpointing, human-in-the-loop
State / control flowSimpler, largely linear agent runs; no first-class graph/cycle abstractionFull StateGraph — nodes, conditional edges, cycles — built exactly for the multi-step, branching control flow covered in the foundational bible and Topic 1
EcosystemLean by design — model-agnostic core, growing but smaller integration surfaceLarge ecosystem — hundreds of integrations (retrievers, vector stores, document loaders) via the broader LangChain project
Best fitType-safe, testable services with structured outputs and tool calls as the core need — data extraction pipelines, typed API-backed assistantsComplex multi-step or multi-agent workflows needing explicit state machines, persistence, and human approval steps — everything in Topics 1, 3, and the foundational bible
Interview framing

"How does Pydantic AI compare to LangChain/LangGraph, and when would you pick each?" — Pydantic AI is a minimal agent framework focused on three things: type-safe structured outputs via Pydantic models, dependency injection via RunContext, and model-agnostic agents defined as plain Python, with a lean, un-opinionated core. LangGraph is the graph-based orchestration layer built for genuinely complex control flow — cycles, conditional branching, checkpointed persistence, multi-agent topologies — with a much larger surrounding ecosystem. Pick Pydantic AI when the core need is a reliable, typed, testable agent with tool calls and structured output; pick LangGraph when the workflow itself has real branching, looping, or multi-agent structure that needs to be explicit and inspectable. They can also be combined — nothing stops a LangGraph node from internally using Pydantic AI's typed output guarantees.

08

Production Failure Modes

What actually goes wrong with tool calling in production, tied back to earlier topics.

  • Vague tool descriptions causing wrong tool selection. The model chooses tools based entirely on the description text you provide — a generic docstring produces unreliable selection among similar tools, directly measurable via Topic 5's tool-selection-accuracy trajectory metric.
  • Too many tools degrading selection accuracy. As the tool list grows (the foundational bible's "single-agent ceiling" from the multi-agent doc), the model has more chances to pick wrong — this is one of the concrete reasons Topic 3's multi-agent specialization pattern exists, scoping each agent to a small, focused tool set.
  • Hallucinated arguments that are schema-valid but factually wrong. A syntactically perfect tool call with a made-up order ID passes validation but fails at execution — this is exactly why the try/except pattern in Section 02 returns the execution error as an observation rather than crashing, letting the model see and correct its own hallucination.
  • Unhandled tool exceptions crashing the entire agent run. Covered directly in Section 02 — always wrap tool execution, never let a single bad call kill the whole trajectory.
  • Treating structured-output shape validity as correctness. Covered in Section 04 — a schema-valid response can still be substantively wrong; only Topic 5's evaluation discipline catches that gap.
  • Not caching stable tool schemas. Every call resends the full tool schema list — if it's static across calls, it's exactly the kind of content Topic 7's prompt caching is built for, and skipping that caching wastes a nearly-free cost optimization.

Interview Cheat-Sheet

Grouped by depth.

Explain what actually happens when a model "calls a tool" — mechanically.core

Every tool is converted to a JSON Schema and sent with every request. Instead of (or alongside) plain text, the model can emit a structured object naming a tool and its arguments — this is a learned behavior from training (Topic 11's SFT/preference-alignment stages), not a new architectural capability. The model never executes anything itself; your application code reads the emitted call, runs the real function, and sends the result back as a new message for the model to continue reasoning from.

What's the difference between the two mechanisms for getting structured output from an LLM?core

One presents your schema as a fake tool call and reads the arguments the model generates as the result — portable across most tool-calling-capable models, a strong but not absolute guarantee. The other uses native constrained decoding (e.g. OpenAI's JSON schema response format) that makes the model architecturally incapable of producing invalid-shaped output during generation itself. Neither guarantees the content is factually correct — both only guarantee the shape matches your schema.

Why should you always feed a validation error back to the model rather than just retrying blindly?core

A blind retry gives the model no new information — it's likely to make a similar mistake again. Feeding back the specific validation failure ("total_usd must be positive, got -50") gives the model a targeted, actionable correction, which measurably improves retry success rates over blind re-attempts. This is the core mechanism behind both a manual retry loop and Pydantic AI's native ModelRetry.

How would you speed up an agent making several independent tool calls per turn?execution

Check whether the executor runs tool calls sequentially by default — most naive implementations do, even though the model already batches independent calls into one tool_calls array per turn. Switch to concurrent execution (asyncio.gather in Python) for calls within the same turn when they're safe to run in parallel (read-only, no shared side effects), capturing latency that's already available rather than architecturally unlocked by anything new.

Compare Pydantic AI's dependency injection model to how you'd typically pass shared resources in a LangGraph agent.framework

Pydantic AI's RunContext gives compile-time-checked, explicit dependency injection — a typed dataclass passed into agent.run(), accessed in tools via ctx.deps, with static type checkers catching mismatches. LangGraph doesn't have an equivalent first-class DI primitive — shared resources are typically threaded through as closures, class attributes on a wrapping Agent class (as in the foundational bible's Agent.__init__), or via LangGraph's config/configurable parameter, none of which get the same static type-checking guarantee Pydantic AI's RunContext provides.

When would you reach for Pydantic AI instead of LangGraph for a new agent project?framework

When the core requirement is a reliably typed, testable, tool-using agent without complex branching control flow — a data-extraction service, a typed API assistant, anything where dependency injection and guaranteed structured output matter more than explicit multi-step graph orchestration. Reach for LangGraph instead once the workflow needs real cycles, conditional branching, checkpointed persistence, or multi-agent coordination — the graph abstraction is solving a different problem than Pydantic AI's type-safety-first design center.

An agent's tool-selection accuracy has dropped as you've added more tools to it. What do you check first?production

First, whether tool descriptions are specific and distinguishable enough for the model to reliably choose between similar-sounding tools — vague docstrings are the most common cause. Second, whether the tool count itself has grown past what a single agent can reliably discriminate between, which is exactly the signal from Topic 3 that argues for splitting into multiple specialized agents each with a smaller, focused tool set rather than one agent with an ever-growing list.

Glossary

Every term used in this document.

Tool / function calling
A trained model behavior: emitting a structured object naming a function and arguments instead of plain text.
JSON Schema
The typed description format tools and structured outputs are both expressed as, sent to the model every call.
@tool / StructuredTool
LangChain primitives for registering a Python function as a model-callable tool.
args_schema
A Pydantic model defining and validating a tool's expected arguments.

LangChain method forcing a model call to return a validated instance of a given Pydantic schema.
Constrained decoding
Native provider mechanism restricting token generation itself to only produce schema-valid output.
Validation-and-retry loop
Feeding a specific validation error back to the model to prompt a targeted correction on the next attempt.

A minimal, type-safe agent framework centered on structured outputs, dependency injection, and plain Python.
RunContext
Pydantic AI's typed dependency-injection carrier, passed into tools and dynamic instructions.
