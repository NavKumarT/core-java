RAG Is a Pipeline, Not a Technique

The gap between a RAG demo and a RAG system that survives production is entirely in this section's framing.

44%
factual accuracy for naive retrieval, no advanced techniques
63%
factual accuracy for state-of-the-art RAG with advanced techniques
+17.4%
Recall@5 gain from adding reranking on top of hybrid RRF alone

A comprehensive RAG benchmark found that state-of-the-art RAG systems answer only 63% of factual questions correctly, while straightforward retrieval without advanced techniques scores just 44%. Every technique in this document exists to close some specific slice of that 19-point gap — chunking fixes context loss at boundaries, hybrid search fixes vocabulary mismatch, reranking fixes coarse ranking precision, self-correction fixes retrieval failures the pipeline can detect and recover from.

The upstream truth that outranks every technique below

The choice of chunking strategy matters — but most teams discover that chunk size is not the binding constraint. Production RAG failures usually trace back to stale, ungoverned, or semantically thin source data rather than suboptimal boundary placement. Every technique in this document assumes your source corpus is accurate and current — no retrieval technique fixes a knowledge base that's wrong or stale, and that's worth saying explicitly in an interview before diving into technique details.

01 ★

Chunking Strategies, All Nine

The most over-discussed, under-decisive lever in RAG — know all nine, know the real numbers, know that it's rarely the actual bottleneck.

StrategyHow it worksCost / speed
Fixed-size / characterSplit every N characters, often with overlapFastest, simplest — the 5-minute baseline
Recursive (token-based)Splits recursively along a hierarchy of separators, respecting sentence/paragraph boundaries where possible; the pragmatic 2026 default4.82 MB/s (Chonkie benchmark)
Semantic chunkingUses embedding similarity to detect topic shifts, grouping sentences whose embeddings are similar and starting a new chunk when embedding distance jumps above a threshold~0.33 MB/s — roughly 14x slower than token-based; improves recall up to 9% over simpler methods
Document-structure-awareSplits along native document structure (headers, sections) rather than arbitrary token countsLow overhead if structure metadata already exists
Parent-child / sentence windowRetrieve a small precise chunk, but pass its larger parent context to the generator — decouples retrieval precision from generation completenessStorage overhead for maintaining both granularities
Agentic chunkingUses an LLM to propose chunk boundaries based on semantic logic — e.g. LumberChunker for narrative long-form documentsHighest cost — an LLM call per boundary decision
Late chunkingEmbeds the entire document first to capture global context, then splits into chunks afterward — improves retrieval by emphasizing document-level coherenceCheaper than contextual retrieval — uses only the embedding model, no LLM cost
Contextual retrieval (chunking + enrichment)Covered in full in the next section — prepend LLM-generated context to each chunk before embeddingHighest quality gain, LLM cost per chunk at indexing time
Metadata-enriched retrieval unitsChunks with ownership, freshness, lineage, and policy context attached — less about boundary placement, more about governanceEngineering overhead, pays off at enterprise scale/compliance

Chunk size & overlap — the numbers to actually cite

Parameter2026 guidance
Chunk size512–1024 tokens is a defensible starting point — a February 2026 vendor benchmark ranked recursive 512-token splitting first across seven strategies; an earlier LlamaIndex study found 1024 tokens near peak faithfulness.
OverlapIndustry best practice historically recommended 10-20% overlap — but a January 2026 systematic analysis using SPLADE retrieval and Mistral-8B on Natural Questions found that overlap provided no measurable benefit and only increased indexing cost. Treat the 10-20% figure as a legacy default worth re-testing on your own corpus, not a settled fact.
Interview framing

"How do you choose a chunking strategy for a new RAG system?" — Start with recursive token-based splitting at 512-1024 tokens as the pragmatic default; it's the top-ranked strategy in recent benchmarks and costs almost nothing to implement. Only escalate to semantic or agentic chunking if your eval (Topic 5's context recall/precision metrics) shows chunking-boundary losses specifically — semantic chunking is ~14x slower to index, so it should be a measured decision, not a default. And always check your source data quality before tuning chunking further — most production RAG failures are upstream of the chunker entirely.

02 ★

Contextual Retrieval & Late Chunking

The single highest-ROI technique in this entire document — and the exact mechanism behind why it works.

A chunk saying "revenue grew 3% last quarter" is useless without knowing which company, which quarter, or which document it came from. The embedding model faithfully encodes the fragment but misses the context that makes it meaningful — when a user asks "What was Acme Corp's Q2 2023 revenue growth?", the retriever may not find this chunk because the embedding has no signal for "Acme Corp" or "Q2 2023."

Contextual retrieval (Anthropic, 2024)

Prepends a short LLM-generated context summary to each chunk before embedding — the summary explains where the chunk sits within its source document, so the embedding carries document-level context rather than just the chunk's local text.

"This chunk is from Acme Corp's Q2 2023 earnings report, in the
revenue summary section. Revenue grew 3% last quarter."

49%

67%

Anthropic's contextual retrieval research demonstrated that adding context to chunks before embedding reduces retrieval failures by 49%, and by 67% when combined with reranking — a bigger improvement than switching from a cheap embedding model to an expensive one.

Late chunking (Jina AI) — the cheaper alternative solving the same problem

Late chunking uses the embedding model only, cheaper than contextual retrieval's LLM + embedding pipeline. Best for long documents with cross-references — technical docs, research papers, legal documents where entities are introduced once and referenced throughout.

When they converge — a genuinely interesting nuance

A 2025 arXiv paper comparing late chunking and contextual retrieval found results depend heavily on the embedding model used — with Jina-V3, fixed-window chunking and semantic chunking "do not differ much in terms of performance" when late chunking is applied, because the full-document context already captures the cross-references. This is a good "I know the nuance, not just the headline number" fact to have ready.

Interview framing

"Your RAG system misses queries that reference an entity only named once, early in a long document. What do you do?" — This is the canonical contextual-retrieval failure mode. Either prepend LLM-generated context to each chunk before embedding (Anthropic's approach, ~49% failure reduction, ~67% with reranking) or use late chunking with a long-context embedding model that embeds the full document before splitting (cheaper, no LLM cost, particularly strong when entities are introduced once and referenced throughout — legal/technical docs). Choose late chunking first if cost is a concern; escalate to full contextual retrieval if late chunking's gains plateau on your eval set.

03

Hybrid Search & Reciprocal Rank Fusion

Dense and sparse retrieval fail on opposite query types. Fusing them is close to a free lunch.

MethodWins onLoses on
Dense (embeddings)Paraphrasing, synonyms, conceptual/semantic matchingExact-match terms — identifiers, names, domain jargon — because embedding models compress semantics and lose token-level precision
Sparse (BM25)SKUs, product codes, exact tokens, rare termsSemantic synonyms and paraphrased queries
Hybrid (fused)Both — the standard implementation is BM25 plus an off-the-shelf dense encoder plus RRF or weighted scoringAdded latency and infra complexity relative to either alone

Reciprocal Rank Fusion merges the two ranked result sets by rank position rather than raw score, making it robust to the different score scales of the two systems — no need to normalize BM25 scores against cosine similarities, which live on entirely different numeric ranges.

The real cost/benefit trade, quantified

Moving from dense-only to hybrid retrieval elevated Mean Reciprocal Rank from 0.410 to 0.486 — an 18.5% improvement in the likelihood of the correct answer appearing in the top position. This accuracy lift came with a 24.5% increase in query latency (an additional 201ms), largely due to the overhead of generating both dense and sparse vectors.

Interview framing

"When would you skip hybrid search and use dense retrieval alone?" — When the corpus is clean and single-topic with no exact-match requirement — e.g. a narrow FAQ knowledge base where every query is naturally conceptual. Skip it also when the added ~200ms latency genuinely doesn't fit the budget and your query distribution is dominated by paraphrase-style questions rather than exact lookups. Add it back the moment identifiers, product codes, names, or rare technical terms appear in real query logs.

04

Reranking: Cross-Encoders & ColBERT

The single biggest precision lever in the entire pipeline — and the most expensive per-candidate.

A cross-encoder model reads both the user query and each retrieved chunk as a single input, producing a precise relevance score for each pair — unlike bi-encoders (used for the initial dense retrieval pass), which encode query and document independently and can only be compared via a cheap vector operation afterward.

Recall@5 gain: hybrid+rerank (0.816) vs hybrid RRF alone (0.695)
+39.7%

5,000x

The two-stage pipeline of hybrid retrieval followed by neural reranking dominates all single-stage methods by a wide margin — Recall@5 of 0.816 compared to 0.695 for hybrid RRF alone, 0.644 for BM25 alone, and 0.587 for dense retrieval alone. While bi-encoders provide low-latency retrieval, cross-encoder rerankers can be 5,000x more expensive in terms of compute-per-query — which is exactly why reranking is always a second-stage refinement over a small candidate set, never the primary retrieval mechanism.

ParameterGuidance
Retrieve-then-rerank candidate countReranking the top-50 candidates is considered the "sweet spot" for most production use cases
Latency addedTypically 150-300ms for 20 candidates
When to skip itReal-time applications with strict latency budgets, or when initial retrieval candidates are already clean (small, low-noise corpus)

ColBERT sits between bi-encoders and cross-encoders: a multi-vector (token-level) retrieval model that's more precise than a single-vector bi-encoder but cheaper than a full cross-encoder, often used as a coarse reranking pass before a final cross-encoder stage in the most demanding pipelines.

05

Query Transformation: HyDE & Multi-Query

Techniques that rewrite or expand the query before retrieval — with an honest, benchmark-backed caveat on the most famous one.

HyDE (Hypothetical Document Embeddings)

HyDE addresses the asymmetry between short queries and long documents by generating a hypothetical answer passage at query time and retrieving with its embedding rather than the original query's embedding — the intuition being that a hypothetical answer is closer in embedding space to a real answer passage than a short question is.

The honest benchmark result — say this to sound current, not textbook

HyDE underperforms vanilla dense retrieval in a recent controlled benchmark, with all pairwise differences between adjacent methods statistically significant (p < 0.001). HyDE is a genuinely clever idea that doesn't reliably beat the simple baseline in practice — a hypothetical passage generated by the LLM can just as easily hallucinate content that pulls retrieval toward the wrong documents. Test it on your own eval set before trusting the theory; don't cite it as an automatic win in an interview.

Multi-query / RAG-Fusion

Generate several reformulations of the original query (different phrasings, different angles), retrieve for each independently, then fuse the results (typically via RRF) — broadens recall by covering vocabulary and framing the original single query might miss, at the cost of N retrieval calls instead of one.

Query rewriting

A lighter-weight transformation: clean up, disambiguate, or expand the raw user query (resolve pronouns, add implied context from conversation history) before it ever hits the retriever — cheap, and often catches a meaningful share of retrieval misses caused by ambiguous or underspecified queries rather than genuine retrieval-system limitations.

06

Self-RAG, CRAG & Adaptive RAG

The family of techniques that let the pipeline notice its own retrieval failures and do something about it — directly related to the Reflexion/Self-Refine patterns from Topic 1.

TechniqueMechanism
Self-RAGOn-demand retrieval with built-in output critique — the model signals when to retrieve and whether the retrieved context actually supports the generated answer, using special reflection tokens rather than always retrieving unconditionally on every query
CRAG (Corrective RAG)Retrieval evaluation with web search fallback — a fallback path that triggers when retrieved documents look weak, grading retrieved documents and either using them, refining them, or escalating to an external search when confidence is low
Adaptive RAGQuery routing to right-sized retrieval pipelines — simple factual queries get lightweight single-pass retrieval, complex multi-hop queries get the full agentic treatment, avoiding paying agentic-RAG overhead on queries that don't need it
Where CRAG actually lands in the benchmark hierarchy

Cross-encoder reranking dominates all methods; contextual hybrid outperforms vanilla hybrid RRF; CRAG provides moderate gains through adaptive query correction; HyDE underperforms vanilla dense retrieval. This ranking is worth memorizing directly — it tells you where to actually invest engineering effort first (reranking, then contextual/hybrid) versus where the marginal gain is smaller (CRAG) or negative in practice (HyDE).

Interview framing

"Explain the difference between CRAG and Self-RAG." — Self-RAG decides whether to retrieve at all and critiques whether retrieved context supports its own answer, using the model's own reflection tokens — it's a decision layer wrapped around a single retrieval pass. CRAG assumes retrieval already happened and grades the quality of what came back, with an explicit fallback (often web search) when the retrieved documents are judged weak — it's a quality-control layer sitting after retrieval, not a decision about whether to retrieve. They're complementary, not competing.

07

GraphRAG & RAPTOR

For questions a flat vector store structurally cannot answer well — multi-hop relationships and whole-corpus synthesis.

GraphRAG

Knowledge graph RAG augments vector retrieval with a structured knowledge graph representing entities and their relationships, using graph traversal at retrieval time to assemble context a flat vector store cannot. Microsoft's GraphRAG paper showed that local-question performance is comparable to vector RAG, but global questions — the kind asking about themes or relationships spanning the whole corpus — are where GraphRAG earns its keep, since flat retrieval is ineffective for holistic questions like "what are the main themes across all these documents?"

RAPTOR

Recursive tree indexing for long-document reasoning — builds a hierarchical tree of recursive summaries over a document (clustering and summarizing chunks bottom-up), so retrieval can pull from the right level of abstraction: a fine-grained leaf chunk for a specific fact, or a higher-level summary node for a broad thematic question.

Use whenSkip when
Multi-hop questions requiring explicit entity/relationship traversal, or whole-corpus synthesis questions a single retrieval pass structurally can't answerMost queries are simple fact lookups answerable from a single chunk — graph construction and maintenance overhead isn't repaid

Agentic RAG, Revisited

Ties every technique above back to the reasoning patterns from Topic 1 — this is where retrieval stops being a single pipeline stage and becomes something an agent plans and adapts.

Every technique in this document so far assumes a largely fixed pipeline shape (retrieve → maybe rerank → generate). Agentic RAG is what happens when an LLM plans the retrieval strategy itself, mid-task — deciding whether to retrieve (Self-RAG's core question), how many times, with what reformulated sub-queries (Topic 1's Self-Ask pattern), and whether the results are good enough to stop or need another pass (CRAG's grading step, generalized into a full agentic loop rather than a single fallback branch).

The direct connection to Topic 1

The "query → subquery → retrieve → rank" diagram from Topic 1's agentic search section is the same shape as CRAG's grade-and-correct loop and Self-RAG's retrieve-and-critique loop, generalized. The reasoning patterns you already know — ReAct for step-by-step adaptive retrieval, Plan-and-Execute for a fixed multi-hop retrieval plan, Reflexion for improving retrieval strategy across attempts — are directly applicable to building an agentic RAG system; this topic is Topic 1's patterns applied specifically to the retrieval domain.

Interview framing

"When does agentic RAG earn its added latency and cost over a fixed pipeline?" — Same criteria as Topic 1's decision framework: when the right retrieval strategy can only be determined after seeing intermediate results (a fixed ReWOO-style plan would be wrong), when questions are genuinely multi-hop with dependent sub-queries, or when self-correction (noticing weak retrieved context and retrying differently) measurably improves your eval numbers over a static pipeline. For single-hop factual lookups, a fixed hybrid-search-plus-rerank pipeline is both cheaper and more predictable.

Production Architecture, End to End

Every technique above, assembled into one reference pipeline.

Ingestion: normalize sources, strip boilerplate, attach metadata for filtered retrieval. Chunking: semantic or recursive splits, parent/child IDs for hierarchy. Embed & index: batch embed with a domain-aligned model, incremental upserts. Query understanding: rewriting, HyDE (with the caveat above), multi-query for recall. Retrieve & rerank: hybrid search, wide candidate set (e.g. 20-50), rerank to a tight set (e.g. 5). Prompting: answer only from context, cite sources, low temperature for factual tasks. Validation: faithfulness checks, safety filters, tracing IDs.

Embedding model choice, briefly

Dense embeddings via current MTEB leaderboard top picks (Voyage-3, OpenAI text-embedding-3-large, BGE-M3, Cohere Embed v4). Model choice matters less than the contextual-retrieval and reranking decisions above it in this pipeline — per the earlier stat, contextual retrieval alone beats switching to a more expensive embedding model.

Production Pitfalls

What actually goes wrong.

  • Obsessing over chunk size while source data is stale. Chunking is rarely the binding constraint — check data governance first.
  • Adding overlap by default without testing it. A recent systematic analysis found no measurable benefit from overlap on some retrieval setups — it's a legacy default, not a law.
  • Trusting HyDE without testing on your own corpus. It underperforms vanilla dense retrieval in controlled benchmarks — a plausible idea that doesn't always pay off.
  • Using a cross-encoder as the primary retrieval mechanism. 5,000x more expensive per-candidate than a bi-encoder — always a second-stage refinement over a small candidate set, never the first pass.
  • Skipping hybrid search on a corpus full of identifiers/codes/names. Dense-only retrieval structurally misses exact-match terms — this is the most common "why can't it find the SKU" bug report.
  • Reaching for GraphRAG or agentic RAG before checking if a simpler pipeline already clears your eval bar. Same discipline as Topic 3's multi-agent decision framework — measure the baseline first.
  • Adopting a technique because a blog post cited a benchmark number, without validating it on your own eval set. Every number in this document is corpus- and query-distribution-specific.

Interview Cheat-Sheet

Grouped by depth.

Core concepts

Walk through why naive RAG underperforms and where the 44%→63% gap actually comes from.core

Naive RAG (single dense retrieval pass, no reranking, no context enrichment, fixed-size chunking) fails in specific, well-understood ways: chunks lose document-level context, dense-only retrieval misses exact-match terms, and coarse initial ranking surfaces noisy candidates the generator can't distinguish from genuinely relevant ones. Each advanced technique — hybrid search, reranking, contextual retrieval — closes one specific slice of that gap, which is why they compound rather than substitute for each other.

Why does contextual retrieval outperform just switching to a better embedding model?core

A better embedding model still embeds the same context-poor chunk text — it can't recover information that was never in the chunk to begin with (e.g., which company or quarter a revenue figure refers to). Contextual retrieval fixes the actual root cause by enriching the chunk's content before embedding, so the improvement isn't bounded by embedding model quality the way a model swap is.

Explain Reciprocal Rank Fusion and why it's preferred over combining raw scores.core

BM25 scores and cosine-similarity scores live on entirely different, incompatible numeric scales, so combining them directly requires careful normalization that's fragile across corpora. RRF sidesteps this by fusing based on each result's rank position in its own list rather than its raw score, making fusion robust regardless of how the underlying scores are distributed.

Technique trade-offs

When would you choose late chunking over contextual retrieval, and vice versa?tradeoffs

Late chunking uses only the embedding model (no LLM cost) and is a strong fit for long documents with cross-references — technical docs, legal documents where entities are introduced once. Contextual retrieval requires an LLM call per chunk at indexing time but has a stronger track record (49-67% failure reduction) and works well even when late chunking's long-context embedding requirement isn't met by your chosen embedding model. Start with late chunking for cost reasons; escalate to full contextual retrieval if gains plateau.

Why is a cross-encoder never used as the primary retrieval mechanism?tradeoffs

A cross-encoder must jointly process the query and each candidate document together, which is roughly 5,000x more compute-per-query than a bi-encoder's independent-encoding-plus-vector-comparison approach. Running that over an entire corpus per query is computationally infeasible at any real scale — it only becomes viable as a second-stage reranker over a small candidate set (the "top-50" sweet spot) already narrowed by a cheap first-pass retriever.

Your team wants to add HyDE because a well-known blog post recommends it. How do you respond?tradeoffs

HyDE is a legitimate, clever idea — generating a hypothetical answer passage to retrieve against rather than the raw short query — but recent controlled benchmarking found it underperforms vanilla dense retrieval, likely because the LLM's hypothetical passage can hallucinate content that pulls retrieval toward the wrong documents. Recommend an A/B test against your own eval set before adopting it; don't take a technique's reputation as a substitute for measuring it on your actual corpus and query distribution.

What's the actual difference between CRAG and Self-RAG, precisely?tradeoffs

Self-RAG decides whether retrieval is needed at all for a given query, and after generating, critiques whether its own answer is actually supported by the retrieved context — both decisions live inside the generation model via reflection tokens. CRAG assumes retrieval has already happened and specifically grades the quality of what came back, triggering a fallback (often external web search) when confidence in the retrieved documents is low. Self-RAG is a decision-and-critique wrapper; CRAG is a post-retrieval quality gate.

System design

Design a RAG system for an internal legal document search tool with entities (client names, case numbers) introduced once and referenced throughout long documents.design

This is the canonical late-chunking / contextual-retrieval use case. Use a long-context embedding model with late chunking (embed the full document first, split after) to preserve cross-reference context cheaply, layered with hybrid search since case numbers and client names are exact-match terms dense retrieval alone would miss. Add reranking over the top-50 hybrid candidates for final precision. Validate on an eval set specifically containing "entity introduced once, referenced later" queries, since that's the exact failure mode being targeted.

Your RAG system handles both simple FAQ lookups and complex multi-document comparison questions. How do you architect for both without over-paying on the simple case?design

Adaptive RAG — route simple factual queries to a lightweight single-pass hybrid-search-plus-rerank pipeline, and route queries classified as complex/comparative/multi-hop to a heavier agentic RAG loop (query decomposition, multiple retrieval rounds, CRAG-style grading between rounds). The routing decision itself can be a cheap classifier or even a simple heuristic on query structure, avoiding the cost of running every query through the expensive path.

Users report your RAG system confidently answers questions with wrong information rather than saying "I don't know." How do you diagnose and fix this?design

Check faithfulness and context recall separately (Topic 5's RAGAS metrics) — if faithfulness is high but the underlying retrieved context was actually insufficient or wrong, the generator is being faithfully wrong, and the fix belongs upstream in retrieval quality (hybrid search, reranking, contextual retrieval), not in the generation prompt. If faithfulness itself is low despite good context recall, add a CRAG-style grading step or Self-RAG-style critique that can trigger a "insufficient evidence" response instead of a confident hallucination when retrieved context doesn't actually support an answer.

A stakeholder asks why you're not using GraphRAG for a customer support knowledge base of short, mostly independent articles.design

GraphRAG earns its complexity on multi-hop relationship questions and whole-corpus synthesis questions — a support KB of short, mostly independent articles rarely has either property; most queries are single-hop fact lookups a flat hybrid-search-plus-rerank pipeline already handles well. Recommend measuring against the eval set first: if global/thematic questions are a real, frequent part of the query distribution, GraphRAG is worth the graph-construction and maintenance overhead; if not, it's added complexity without a corresponding accuracy gain.

Glossary

Every term used in this document.

Semantic chunking
Splitting text at points where embedding similarity between sentences drops, rather than fixed character/token counts.
Late chunking
Embedding a full document first for global context, then splitting into chunks afterward.
Contextual retrieval
Prepending LLM-generated document-context summaries to chunks before embedding.
Hybrid search
Combining sparse (BM25) and dense (embedding) retrieval, typically fused via RRF.
Reciprocal Rank Fusion (RRF)
Merging ranked result lists by rank position rather than raw score, robust to differing score scales.
Cross-encoder reranking
Jointly scoring a query-document pair for precise relevance, applied as a second-stage refinement over a small candidate set.
Bi-encoder
Independently encodes query and document, compared via cheap vector similarity — used for initial retrieval, not reranking.
ColBERT
Multi-vector (token-level) retrieval model, precision/cost between bi-encoders and cross-encoders.
HyDE
Retrieving using the embedding of a generated hypothetical answer passage instead of the raw query.
Self-RAG
Model decides when to retrieve and critiques whether retrieved context supports its own generated answer.
CRAG (Corrective RAG)
Grades retrieved document quality and triggers a fallback (e.g. web search) when confidence is low.
Adaptive RAG
Routes queries to a right-sized retrieval pipeline based on estimated complexity.
GraphRAG
Augments vector retrieval with a structured entity-relationship knowledge graph for multi-hop and global questions.
RAPTOR
Recursive hierarchical tree of document summaries, enabling retrieval at variable levels of abstraction.
Agentic RAG
An LLM plans and adapts the retrieval strategy itself mid-task, rather than following a fixed pipeline.
