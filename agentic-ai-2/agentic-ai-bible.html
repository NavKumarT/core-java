Agentic Foundations — What Makes Something "Agentic"

Your notes jump straight into ReAct and LangGraph — this is the ten‑second definition that ties it all together, because every interviewer opens with it.

A plain LLM call is one shot: prompt in, text out. An agent is an LLM wrapped in a loop that lets it decide, on its own, what to do next — call a tool, read the result, and decide again — until it thinks it has enough to answer. The loop is the whole idea. Everything else (tools, state, memory, graphs) exists to make that loop reliable, inspectable, and steerable.

Your note captured this precisely: "LLM + everything around it is called the runtime." The model itself never changes at inference time — its weights are frozen. What makes it "agentic" is the scaffolding: the system prompt, the tools it can call, the state it can read and write, and the control flow that decides when to stop.

LayerJobTypical tool
ReasoningDecide what to do next given the conversation so farThe LLM itself (GPT‑4o, Claude, etc.)
ActingExecute a decision against the real worldTools / function calls (search, code exec, APIs)
MemoryCarry information across turns and across sessionsAgentState + Checkpointer
Control flowRoute between reasoning, acting, and stoppingLangGraph's StateGraph
OversightLet a human approve, edit, or rewind a stepinterrupt_before / update_state
Likely interview framing

"What's the difference between a chatbot and an agent?" — A chatbot maps input → output through the model once per turn. An agent can take zero, one, or many actions per turn, inspecting the result of each action before deciding on the next, and it stops only when a condition (like "no more tool calls") is met.

02

ReAct — Reasoning + Acting

Straight from your notes: the LLM first "thinks," then takes an action; the action runs in an environment and returns an observation; the LLM looks at the observation and repeats.

ReAct (Yao et al., 2022) is the pattern almost every agent framework — LangGraph included — is built on top of. It interleaves two things the model was previously asked to do separately:

  • Reasoning traces — free‑text "thoughts" that let the model plan, decompose the task, and notice when a previous action failed.
  • Actions — structured calls into an environment (a search API, a calculator, a database) that ground the model's reasoning in real, current information instead of its frozen training data.
prompt / observation control flow decision terminal state

Read the loop as: User prompt → LLM → (Thought + Action) → does the action need a tool? If yes, call the tool, get an Observation, append it back into the prompt, and go around again. If no — the model produced a final answer with no tool calls — return it to the user. That "does the action need a tool" diamond is, in LangGraph terms, a conditional edge, and it's the single most important piece of control flow in the whole framework.

Why ReAct over plain chain-of-thought

Chain-of-thought alone lets a model reason step by step, but every fact it uses still comes from frozen training data — it can hallucinate a statistic and reason flawlessly from the wrong number. ReAct grounds each reasoning step in a real, freshly-fetched observation, so errors get corrected mid-trajectory instead of compounding.

LangChain Primitives

Prompt templates, the LangChain Hub, and tools — the three building blocks your notes call out before graphs enter the picture.

Prompt Templates

A PromptTemplate turns a plain string with placeholders into a reusable, parameterized prompt object — separating the fixed wording (the prompt engineer's job) from the runtime values (filled in per‑call).

prompt_template.py
from langchain.prompts import PromptTemplate

prompt_template = PromptTemplate.from_template(
    "Tell me about {subject}"
)

# Or pull a battle-tested prompt from the community hub
from langchain import hub
prompt = hub.pull("hwchase17/react")

The LangChain Hub (hub.pull(...)) is a registry of shared, versioned prompts — pulling hwchase17/react gets you the canonical ReAct prompt template so you don't hand‑roll the "Thought / Action / Observation" formatting yourself.

Tools

A tool is just a function the model is allowed to call, described to it in a schema (name, description, argument types) so the model can decide when and how to invoke it. TavilySearchResults from langchain-community is the search tool your notes reach for repeatedly.

tools.py
from langchain_community.tools.tavily_search import TavilySearchResults

tool = TavilySearchResults(max_results=2)

# Registering tools on an agent: name -> tool lookup table
self.tools = {t.name: t for t in tools}

# Binding tells the LLM what functions it may call and their schemas
self.model = model.bind_tools(tools)
bind_tools, demystified

model.bind_tools([...]) doesn't change the model — it attaches a JSON‑schema description of each tool to every request, so the provider's API can return a structured tool_calls field instead of (or alongside) plain text. Your agent code then reads message.tool_calls to decide what to execute.

LangChain vs LangGraph — when your notes shift gears

Your notes flag this transition explicitly: "New in LangGraph → cyclic graphs, persistence, human in the loop — an extension of LangChain that supports graphs." LangChain's original agent abstraction (AgentExecutor) is a fixed loop you can't easily customize. LangGraph replaces it with an explicit, inspectable graph.

LangGraph Anatomy — Nodes, Edges, Conditional Edges

Your notes summarize it in three lines. Here's what each line actually compiles to.

ConceptYour noteWhat it is
Nodes"Agents or functions"A Python function (state) -> dict — receives the current state, returns a partial update to merge in.
Edges"Connect nodes"An unconditional hop: after node A finishes, always run node B.
Conditional edges"Decisions"A router function reads the state and returns a key; that key is looked up in a dict mapping to the next node (or END).
graph_skeleton.py
from langgraph.graph import StateGraph, END

graph = StateGraph(AgentState)
graph.add_node("llm", self.call_openai)
graph.add_node("action", self.take_action)

graph.add_conditional_edges(
    "llm",
    self.exists_action,               # router function
    {True: "action", False: END}
)
graph.add_edge("action", "llm")   # unconditional edge back = the loop
graph.set_entry_point("llm")

self.graph = graph.compile()

Notice the cycle: llm → action → llm → action → … This is exactly what a plain function‑call chain can't express cleanly — LangGraph's whole reason to exist is making that back‑edge a first‑class, compileable thing instead of a manually written while loop.

Interview trap

"Why not just write a while loop calling the LLM and a tool?" — You can, for a toy agent. It stops scaling once you need persistence across process restarts, mid‑run human approval, replaying from an arbitrary past step, or parallel branches — all of which require the run to be a graph of discrete, resumable steps rather than one live Python call stack.

Agent State

"Accessible to all parts of the graph. Local to the graph. Can be stored in a persistence layer." — your three-line definition, unpacked.

State is a typed dictionary (TypedDict) that every node reads from and writes back to. It's the single shared blackboard the whole graph works against — nodes never talk to each other directly, only through state.

Simple state

state_simple.py
class AgentState(TypedDict):
    messages: Annotated[Sequence[BaseMessage], operator.add]

Annotated[..., operator.add] is the key idea: it's a reducer. Without it, a node returning {"messages": [...]} would overwrite the whole messages list. With operator.add, LangGraph appends the new messages to the existing list instead — so every node's output accumulates rather than replaces.

Complex state

state_complex.py
class AgentState(TypedDict):
    input: str                                              # overwrites
    chat_history: list[BaseMessage]                         # overwrites
    agent_outcome: Union[AgentAction, AgentOutcome, None]  # overwrites
    intermediate_steps: Annotated[
        list[tuple[AgentAction, str]], operator.add
    ]                                                        # adds / appends

Every field without an Annotated reducer simply gets overwritten on each update (your notes label this "overrides"); every field wrapped with a reducer like operator.add gets merged (your notes label this "adds a new update"). Choosing the wrong one is a classic bug: overwrite a running message history and you silently lose context every step.

Real bug from the later lesson

The default operator.add reducer always appends. That breaks the moment you want to replace a message with the same id (e.g. after a human edits one mid-run). The fix in your notes is a custom reducer, reduce_messages, that assigns each message a uuid, then merges by id — replacing on match, appending otherwise:

custom_reducer.py
def reduce_messages(left: list[AnyMessage], right: list[AnyMessage]) -> list[AnyMessage]:
    for message in right:
        if not message.id:
            message.id = str(uuid4())
    merged = left.copy()
    for message in right:
        for i, existing in enumerate(merged):
            if existing.id == message.id:
                merged[i] = message
                break
        else:
            merged.append(message)
    return merged

class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], reduce_messages]

Building the Agent — Full Walkthrough

The exact Agent class from your notebook, annotated line by line.

agent.py — full class
class Agent:
    def __init__(self, model, tools, system=""):
        self.system = system
        graph = StateGraph(AgentState)
        graph.add_node("llm", self.call_openai)
        graph.add_node("action", self.take_action)
        graph.add_conditional_edges(
            "llm", self.exists_action, {True: "action", False: END}
        )
        graph.add_edge("action", "llm")
        graph.set_entry_point("llm")
        self.graph = graph.compile()
        self.tools = {t.name: t for t in tools}
        self.model = model.bind_tools(tools)

    def exists_action(self, state: AgentState):
        result = state['messages'][-1]
        return len(result.tool_calls) > 0

    def call_openai(self, state: AgentState):
        messages = state['messages']
        if self.system:
            messages = [SystemMessage(content=self.system)] + messages
        message = self.model.invoke(messages)
        return {'messages': [message]}

    def take_action(self, state: AgentState):
        tool_calls = state['messages'][-1].tool_calls
        results = []
        for t in tool_calls:
            if not t['name'] in self.tools:
                result = "bad tool name, retry"   # self-correcting loop
            else:
                result = self.tools[t['name']].invoke(t['args'])
            results.append(ToolMessage(tool_call_id=t['id'], name=t['name'], content=str(result)))
        return {'messages': results}

Three functions, three jobs:

  • exists_action — the router for the conditional edge. It looks at the last message only and checks whether the model asked for a tool call.
  • call_openai — the "llm" node. Prepends the system prompt (if any), invokes the model on the full message history, and returns the new AI message wrapped in a list so the operator.add reducer appends it.
  • take_action — the "action" node. Loops over every tool call the model requested (a single turn can request several in parallel), executes each, and wraps each result in a ToolMessage tied back to its tool_call_id so the model can match observations to the calls that produced them.
Notice the self-correction

"bad tool name, retry" isn't an exception — it's fed back to the model as if it were a normal observation. The next LLM turn sees its own mistake and can retry with a corrected tool name. This is a small but real example of an agent recovering from its own error without any human intervening.

run.py
prompt = """You are a smart research assistant. Use the search engine to look up information.
You are allowed to make multiple calls (either together or in sequence).
Only look up information when you are sure of what you want."""

model = ChatOpenAI(model="gpt-4o")
abot = Agent(model, [tool], system=prompt)

messages = [HumanMessage(content="What is the weather in sf?")]
result = abot.graph.invoke({"messages": messages})
result['messages'][-1].content

Model choice matters for tool-use quality. Your notes flag this directly: a multi-hop question ("who won the Super Bowl, what state is the team from, what's that state's GDP") needed gpt-4o instead of gpt-3.5-turbo — weaker models plan multi-step tool chains less reliably.

Persistence & Checkpointing

"Checkpoints — a concept from LangGraph." This is what turns a stateless function call into a resumable, multi-day conversation.

A checkpointer saves a snapshot of the full AgentState after every node executes. Snapshots are keyed by a thread_id — think of a thread as one persistent conversation. Reuse the same thread_id and the graph picks up exactly where it left off; use a new one and you start clean.

persistence.py
from langgraph.checkpoint.sqlite import SqliteSaver
memory = SqliteSaver.from_conn_string(":memory:")

# compiled with a checkpointer
self.graph = graph.compile(checkpointer=checkpointer)

thread = {"configurable": {"thread_id": "1"}}
for event in abot.graph.stream({"messages": messages}, thread):
    for v in event.values():
        print(v['messages'])
BackendWhen to use it
MemorySaver / ":memory:"Local dev, notebooks, unit tests — gone on process exit
SqliteSaverSingle-process apps, prototypes, small deployments
AsyncSqliteSaverSame, but for async/streaming code paths
PostgresSaverProduction — multi-process, durable, concurrent threads
Interview framing

"How does LangGraph give an agent memory across sessions?" — Not via a vector store by default (that's semantic memory for RAG). Short-term conversational memory is the checkpointer: every super-step's state is persisted keyed by thread_id, so graph.invoke(None, thread) — passing no new input — resumes exactly where the last run stopped.

Streaming

Two different things people mean by "streaming" — your notes cover both.

Streaming graph steps

graph.stream(...) yields one event per node completion — useful for showing "🔍 searching…" / "🤖 thinking…" progress in a UI.

Streaming model tokens

graph.astream_events(..., version="v1") goes one level deeper and yields individual LLM tokens as they're generated, via the on_chat_model_stream event kind:

token_stream.py
from langgraph.checkpoint.aiosqlite import AsyncSqliteSaver

memory = AsyncSqliteSaver.from_conn_string(":memory:")
abot = Agent(model, [tool], system=prompt, checkpointer=memory)

thread = {"configurable": {"thread_id": "4"}}
async for event in abot.graph.astream_events({"messages": messages}, thread, version="v1"):
    kind = event["event"]
    if kind == "on_chat_model_stream":
        content = event["data"]["chunk"].content
        if content:   # empty content = model is requesting a tool call, not text
            print(content, end="|")

Your note nails the gotcha: empty content in a chunk means the model is mid‑way through requesting a tool call, not producing user‑facing text — filter those out or the UI flickers with blank tokens.

Human‑in‑the‑Loop

"Add a break before a node takes place — humans can approve or deny specific actions." The mechanism is interrupt_before + get_state + update_state.

Pause before a risky node

interrupt.py
self.graph = graph.compile(
    checkpointer=checkpointer,
    interrupt_before=["action"]   # pause right before tool execution
)

Run the graph and it will execute the "llm" node, then stop before "action" ever runs — nothing has actually been executed yet. Inspect what it's about to do:

inspect_and_approve.py
state = abot.graph.get_state(thread)
state.values['messages'][-1].tool_calls   # see the pending tool call(s)
state.next                                    # -> ('action',) what runs next

# approve: resume with no new input
for event in abot.graph.stream(None, thread):
    print(event)

Edit state before resuming

You're not limited to yes/no — update_state lets you rewrite the pending action entirely (e.g. correct a search query) before letting it run:

edit_before_resume.py
current_values = abot.graph.get_state(thread)
_id = current_values.values['messages'][-1].tool_calls[0]['id']
current_values.values['messages'][-1].tool_calls = [{
    'name': 'tavily_search_results_json',
    'args': {'query': 'current weather in Louisiana'},  # edited
    'id': _id
}]
abot.graph.update_state(thread, current_values.values)
MethodPurpose
interrupt_before=[node]Pause the graph right before a specific node runs
graph.get_state(thread)Read the current snapshot + what node runs next
graph.get_state_history(thread)Every past snapshot for the thread, newest first
graph.update_state(thread, values)Overwrite part of the state, then continue from there
graph.stream(None, thread)Resume from wherever the thread paused (no new input)
Interview framing

"How would you build an approval step before an agent sends an email / runs a payment / deletes something?" — Compile with interrupt_before=["that_node"], surface get_state(thread).values to a human reviewer UI, and only call stream(None, thread) once they click approve. Deny → don't resume, or update_state to redirect the graph elsewhere entirely.

Time Travel

Because every super-step is checkpointed, "go back in time" is just: pick an old checkpoint, optionally edit it, and invoke from there.

time_travel.py
states = []
for state in abot.graph.get_state_history(thread):
    states.append(state)

to_replay = states[-3]   # an arbitrary earlier snapshot

# A) replay unchanged — deterministic re-run from that point
for event in abot.graph.stream(None, to_replay.config):
    print(event)

# B) branch — edit the snapshot, then continue down a new path
to_replay.values['messages'][-1].tool_calls = [{
    'name': 'tavily_search_results_json',
    'args': {'query': 'current weather in LA, accuweather'},
    'id': _id
}]
branch_state = abot.graph.update_state(to_replay.config, to_replay.values)
for event in abot.graph.stream(None, branch_state):
    print(event)

# C) inject a fabricated observation at a past point, as if a node produced it
state_update = {"messages": [ToolMessage(tool_call_id=_id, name="tavily_search_results_json", content="54 degree celcius")]}
branch_and_add = abot.graph.update_state(to_replay.config, state_update, as_node="action")

Three distinct capabilities, easy to blur together — keep them separate for an interview answer:

  1. Replay — re-run a past checkpoint exactly as it happened (deterministic debugging: "what did the agent see at step 3?").
  2. Branch — edit the snapshot's values and continue from there, creating a new path in state history without touching the original run ("what if it had searched a different query?").
  3. Inject as a node — as_node="action" tells LangGraph to treat your manually-written update as if that node produced it, so the graph correctly computes what runs next (usually back to "llm").
operator.add gotcha, revisited

Your note about count fields: because count used operator.add, setting save_state.values["count"] = -3 and calling update_state doesn't set count to -3 — it adds -3 to whatever the current value already is. Reducers apply on every write, including the writes you make by hand during time travel.

Agentic Search & Multi‑Hop RAG

"In a two-shot [zero-shot] setting, an agent will receive a prompt and produce an answer based on static weights of the model." Your diagram of query → subquery → retrieve → rank is agentic RAG in miniature.

Plain RAG is a single retrieve‑then‑generate hop: embed the query, pull the top‑k chunks, stuff them in context, answer. It breaks on questions that need multiple, dependent lookups — the Super Bowl example from your notes ("who won → what state is that team from → what's that state's GDP") needs three sequential facts, each depending on the last.

Zero/one-shot RAGAgentic RAG
Retrieval stepsExactly oneAs many as the agent decides it needs
QueryUsed verbatimDecomposed into subqueries the model plans itself
Self-correctionNone — bad retrieval = bad answerAgent can notice weak results and retrieve again differently
Cost / latencyLow, predictableHigher, variable — worth it for genuinely multi-hop questions
Interview framing

"When would you reach for agentic RAG instead of plain RAG?" — When a single query can't be answered by one retrieval pass: comparisons across sources, chained facts, or questions where the right search terms only become clear after seeing the first result. If one embed-and-retrieve reliably answers the question, agentic RAG is pure overhead.

Production Pitfalls

Things that go wrong the first time you take this off a notebook and onto a server — mostly implicit in your notes, made explicit here.

  • Infinite loops. A conditional edge that never resolves to END (e.g. a tool that always fails and always triggers a retry) will loop forever. Cap it with a step counter in state and a max-steps check in the router.
  • Unbounded tool_calls. Nothing in the base pattern stops a model from requesting 20 parallel tool calls. Validate/limit them in take_action before executing.
  • Reducer mismatch. Forgetting operator.add on a messages field silently drops history every turn instead of erroring loudly — always test state growth, not just the final answer.
  • SqliteSaver in production. Fine for a demo; a single-writer SQLite file will bottleneck or corrupt under concurrent threads. Move to PostgresSaver once you have real traffic.
  • Weaker models on multi-hop tasks. Your own notebook hit this — gpt-3.5-turbo handled single-hop weather lookups but needed gpt-4o for the three-hop Super Bowl question. Benchmark tool-planning quality per model, not just cost.
  • Silent tool failures. A tool that raises inside take_action without a try/except kills the whole run. Catch exceptions and feed the error back as an observation, the same way the "bad tool name, retry" pattern does.
  • No human checkpoint on irreversible actions. Anything that sends, deletes, pays, or publishes should sit behind interrupt_before until you trust the agent's track record.

Interview Cheat‑Sheet

Grouped by theme. Tap to expand — answer out loud before reading the model answer.

Concepts

What is ReAct and why interleave reasoning with acting?core

ReAct interleaves free-text reasoning ("thoughts") with structured tool calls ("actions"), feeding each tool's result back as an "observation" before the next reasoning step. Interleaving matters because it grounds each reasoning step in fresh, real information rather than letting the model reason for many steps purely from its frozen training data, where early errors compound unchecked.

What's the difference between an agent and a workflow/chain?core

A chain has a fixed, developer-defined sequence of steps. An agent has the model itself decide, at runtime, which steps to take and in what order — including whether to loop, which tool to call, and when to stop. The control flow is data (the model's output), not code.

Explain LangGraph's state, nodes, and edges in one breath.core

State is a typed shared blackboard every node reads and writes. Nodes are functions that take state and return a partial update. Edges connect nodes — unconditional edges always route the same way, conditional edges call a router function on the current state to pick the next node dynamically, including possibly looping back to a node already visited.

State & reducers

What does Annotated[list, operator.add] actually change?state

Without it, a node's returned value for that key overwrites the field entirely. With it, LangGraph merges the new value into the existing one using the given reducer function — operator.add concatenates lists (or adds numbers), so successive node outputs accumulate instead of replacing each other.

When would you write a custom reducer instead of operator.add?state

When "append everything" is wrong for your use case — e.g. you need to replace a message by id (after a human edits it) rather than duplicate it. A custom reducer like reduce_messages merges by identity: replace on matching id, append otherwise.

Persistence & resumability

How does a checkpointer give an agent memory?persistence

It snapshots the full AgentState after every super-step, keyed by thread_id. Resuming a thread — even in a new process — is just invoking the graph with the same thread_id and no new input; LangGraph loads the last snapshot and continues from there.

SqliteSaver vs PostgresSaver — how do you choose?persistence

SqliteSaver is fine for single-process prototypes and local dev. Once you have concurrent users/threads and need durability across deploys, PostgresSaver is the production choice — SQLite's single-writer model doesn't hold up under real concurrent load.

Human‑in‑the‑loop & time travel

Walk through adding an approval step before a risky tool call.hitl

Compile the graph with interrupt_before=["action"]. The run stops right before that node executes. Call get_state(thread) to show the pending tool call to a human. On approval, call stream(None, thread) to resume unchanged; to modify it first, call update_state(thread, edited_values) before resuming.

What's the difference between replaying and branching a past state?hitl

Replaying re-runs a past checkpoint unchanged — deterministic, for debugging. Branching edits the snapshot's values (or injects one via update_state(..., as_node=...)) before continuing, producing a new path in state history that diverges from the original run without altering it.

Why does update_state on a reducer-backed field sometimes not do what you expect?hitl

Because reducers apply on every write, including manual ones. Setting a field to a value doesn't set it — the reducer combines it with the existing value. For operator.add on a counter, "setting" it to -3 actually subtracts 3 from whatever it already was.

Tools & models

What does model.bind_tools() actually send to the API?tools

A JSON-schema description of each tool's name, description, and parameters, attached to every request. The provider's API can then return a structured tool_calls field pointing at one of those schemas instead of only free text, which your code reads to decide what to execute.

How would you make an agent recover from calling a tool that doesn't exist?tools

Don't crash — return a ToolMessage observation like "bad tool name, retry" from the action node. The model sees that as normal feedback on its next turn and can self-correct, the same way it would react to any other observation.

Why might a multi-hop tool-use task fail on a cheaper model but pass on a stronger one?tools

Multi-hop tasks require planning a chain of dependent tool calls and correctly using each result to form the next query. Weaker models are more prone to skipping steps, misreading intermediate results, or terminating early — tool-planning quality scales with model capability more than single-hop retrieval does.

System design

Design an agent that drafts an email and requires human approval before sending.design

Nodes: llm (drafts) → conditional edge to "send" if the model calls the send-tool. Compile with interrupt_before=["send"] and a checkpointer so the paused thread survives a page reload. Surface the draft via get_state; on edit, update_state with the corrected body; on approve, stream(None, thread); on reject, end the thread without resuming.

How would you prevent an agent from looping forever?design

Add a step counter to state (a plain int field, overwritten each time with the incremented value). The router function checks it against a max before routing back into the loop, forcing END once the limit is hit — independent of whether the model "thinks" it still needs another tool call.

Every term from your notes, one line each.

Runtime
The LLM plus everything wrapped around it — prompts, tools, state, control flow.
Observation
The result returned to the model after it executes an action / tool call.
StateGraph
LangGraph's core object: a graph of nodes and edges operating over a shared typed state.
Node
A function (state) -> partial update, representing one agent or one step.

An unconditional connection: after node A, always run node B.

One persistent, resumable conversation/run, identified by thread_id.
interrupt_before
Compile-time option that pauses execution just before a named node runs.

Replaying or branching from any past checkpoint in a thread's history.

PromptTemplate
A parameterized prompt string with placeholders filled in at call time.

A registry of shared, versioned community prompts (hub.pull(...)).

The TypedDict schema describing everything the graph tracks across steps.

Weeks 3–4 — Add persistence and streaming

Swap in SqliteSaver, run the same thread across two separate script invocations, then add astream_events token streaming to a tiny CLI or Flask endpoint.

Weeks 5–6 — Human-in-the-loop

Add interrupt_before on your tool node. Build a minimal approve/edit/deny flow — even just a CLI prompt — before the tool actually executes.

Weeks 7–8 — Time travel & debugging

Practice get_state_history, replay an old checkpoint, and branch it with a modified tool call. This is the part almost no candidate can speak to fluently — it's a strong differentiator.

Weeks 9–10 — Multi-tool, multi-hop agent

Add a second and third tool (calculator, a second API). Ask it a genuinely multi-hop question and compare gpt-3.5 vs gpt-4-class model behavior directly, like your notes did.

Weeks 11–12 — Ship one end-to-end project

Wrap everything into one real project with a UI, persistence, and a human-approval step on at least one irreversible action. This is your portfolio piece and your best interview story.
