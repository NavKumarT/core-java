Why Multi-Agent At All — The Single-Agent Ceiling

Every multi-agent system exists to escape one specific limitation of a single agent. Name the limitation before you name the topology.

A lone ReAct agent handles small tasks fine — search the web, sum up the results, easy. Real work is rarely that small. As you keep adding tools and responsibilities to one agent, three things degrade together: the system prompt grows until the model starts forgetting its own rules, the tool list grows until the agent starts picking the wrong tool, and the context window fills with irrelevant history from unrelated sub-tasks. This is the single-agent ceiling, and it's the actual justification for going multi-agent — not "multi-agent sounds more sophisticated."

A multi-agent system consists of multiple agents — LLMs autonomously using tools in a loop — working together. Anthropic's Research feature involves an agent that plans a research process based on user queries, then uses tools to create parallel agents that search for information simultaneously. The essence of it: breadth-first research questions where the answer requires exploring many independent paths at once and the total information exceeds a single context window.

The real reason it wins on research specifically

The essence of search is compression: distilling insights from a vast corpus. Subagents facilitate compression by operating in parallel with their own context windows, exploring different aspects of the question simultaneously before condensing the most important tokens for the lead researcher. A single agent doing this sequentially can't hold five independent research threads in one context window without them interfering with each other.

The honest counter-lesson

Today, multi-agent systems are often applied in situations where a single agent would perform better — Anthropic has seen teams invest months building elaborate multi-agent architectures only to discover that improved prompting on a single agent achieved equal or better results. The ceiling is real, but it's specific — verify you've actually hit it (via eval, not vibes) before reaching for multiple agents.

Anthropic's Orchestrator-Worker System, In Full

Claude's Research feature is the most thoroughly documented production multi-agent system in the industry. Know it well enough to describe every stage from memory.

Anthropic's Research system employs an orchestrator-worker pattern where a lead agent coordinates the overall process while delegating specialized tasks to subagents operating in parallel.

The stages, in order

  1. Lead Researcher analyzes and plans. The Lead Researcher analyzes the query, decides on an overall strategy, and records the plan in memory — because large research tasks can easily exceed the model's context window, saving the plan avoids losing track when tokens run out.
  2. Subagents spawn and work in parallel. Each subagent is given a specific task — exploring a certain company, checking a particular time period, looking into a technical detail. Each subagent independently performs web searches, evaluates tool results using interleaved thinking, and returns findings to the LeadResearcher.
  3. Lead synthesizes and decides whether to continue. The LeadResearcher synthesizes results and decides whether more research is needed — if so, it can create additional subagents or refine its strategy.
  4. Citation pass. Once sufficient information is gathered, the system exits the research loop and passes all findings to a CitationAgent, which processes the documents and research report to identify specific locations for citations, ensuring all claims are properly attributed to their sources.

The isolation boundary — the single most important design decision

The decision that matters in any multi-agent design is the isolation boundary: what does each subagent need to know about what the others are doing? Anthropic's bet for research is: almost nothing. Each subagent gets a self-contained task description, an output format, and a fresh context window. It doesn't know the other subagents exist. It cannot coordinate with them mid-task. Orchestrator-worker constrains the topology deliberately — workers never talk to each other; every decision about what comes next lives in the orchestrator.

Hard-won prompt engineering lessons

LessonWhat went wrong without it
Teach the orchestrator to delegate explicitlyThe lead agent decomposes queries into subtasks; each subagent needs an objective, output format, guidance on tools/sources, and clear task boundaries — without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information. One subagent explored the 2021 automotive chip crisis while 2 others duplicated work investigating current 2025 supply chains, without an effective division of labor — from an early version that just said "research the semiconductor shortage."
Scale effort to query complexity, explicitly, in the promptAnthropic's prompts embed concrete rules: 1 agent for simple fact-finding, 2 to 4 subagents for direct comparisons, and more than 10 subagents for complex research — without rules like these, the lead agent over-scales, spinning up subagents for problems a single call could answer.
Think like your agents — build simulationsAnthropic built simulations using their Console with exact prompts and tools from their production system, watching agents work step by step — this immediately revealed failure modes like continuing after sufficient results were obtained, overly verbose search queries, and selecting incorrect tools.
Persist context explicitlyStandard context windows become insufficient for conversations spanning hundreds of turns — patterns were implemented where agents summarize completed work phases and store essential information in external memory before proceeding, so a fresh subagent spawned near a context limit can retrieve the stored research plan rather than losing previous work.

Evaluation methodology

Evaluate agents with LLM-as-judge rubrics — factual and citation accuracy, completeness, source quality, tool efficiency — plus human testing, instead of rigid golden answers, because research is inherently open-ended and different valid research paths can reach the same correct conclusion.

Variance analysis — the number worth memorizing

Analysis of the BrowseComp evaluation revealed three factors explaining 95% of variance: token usage (80% of variance), tool calls (parallel execution enabling breadth-first exploration), and model choice — with upgrading to Sonnet 4 outperforming doubling the token budget on Sonnet 3.7. The architecture's win comes overwhelmingly from letting the system spend more total tokens in parallel, not from clever prompt tricks.

When verification subagents are worth it

Verification subagents remain valuable when using less capable orchestrators, when verification requires specialized tools, or when you want to enforce explicit verification checkpoints. Verification subagents succeed because they sidestep the telephone game problem — verification requires minimal context transfer by nature, so a verifier can blackbox-test a system without needing the full history of how it was built. The main agent completes a unit of work, then spawns a verification subagent with the artifact to verify, clear success criteria, and tools to perform verification — the verifier doesn't need to understand why the artifact was built as it was, only whether it's correct.

Supervisor Pattern, In Depth

The pattern most teams should actually start with — and the one you'll be asked to defend most often.

A supervisor agent receives all user queries, determines which specialized agent should handle the task, delegates the work, and then translates the response back to the user. It sits between the network pattern (every agent can call every other — chaos) and the hierarchical pattern (supervisor of supervisors — overkill for most teams).

supervisor_langgraph.py
from langgraph_supervisor import create_supervisor
from langgraph.prebuilt import create_react_agent

research_agent = create_react_agent(model, tools=[search_tool], name="research_agent")
math_agent = create_react_agent(model, tools=[calculator_tool], name="math_agent")

workflow = create_supervisor(
    agents=[research_agent, math_agent],
    model=supervisor_model,
    prompt="You route between a research specialist and a math specialist. Route each turn to exactly one.",
)
app = workflow.compile()
StrengthWeakness
Easier to reason about — one routing node, clear control flow, every decision visible in traces.Slower — every handoff passes through the supervisor, adding an intermediary round trip and doubling token spend on routing calls.
Clean single point for guardrails, logging, and policy enforcementSingle point of failure — in hub-and-spoke topology, coordinator failure halts the entire system.
Work stays hidden from the user until the supervisor is ready to respondContext window saturation — the supervisor accumulates full message history from all sub-agent interactions; routing accuracy drops noticeably after 8-12 sub-agent round trips as historical messages crowd out current task state.
Mitigations for the two real weaknesses

For context saturation: CrewAI addresses this with automatic summarization (respect_context_window=True); LangGraph's subgraphs isolate graph state per agent or team so the supervisor doesn't accumulate every sub-agent's full internal reasoning. For the serial-execution bottleneck: the supervisor's synchronous routing loop forces serial execution even when sub-tasks are logically independent — true parallel dispatch requires explicitly fanning out to multiple workers at once (the orchestrator-worker pattern) rather than routing one at a time.

04

Swarm / Handoff Pattern, In Depth

Remove the middleman. Agents hand the user directly to each other.

The swarm eliminates the supervisor. Agents hand off directly to each other using Command objects returned from handoff tools — when an agent calls a handoff tool, Command(goto=..., graph=Command.PARENT) tells LangGraph to navigate to a different node in the parent graph. Each agent gets handoff tools for the agents it can transfer to.

swarm_langgraph.py
from langgraph_swarm import create_handoff_tool, create_swarm
from langgraph.prebuilt import create_react_agent

billing_agent = create_react_agent(
    model, name="billing_agent",
    tools=[refund_tool, create_handoff_tool(agent_name="tech_agent",
        description="Transfer to tech support for non-billing issues.")],
)
tech_agent = create_react_agent(
    model, name="tech_agent",
    tools=[diagnostics_tool, create_handoff_tool(agent_name="billing_agent",
        description="Transfer to billing for payment/refund issues.")],
)
swarm = create_swarm([billing_agent, tech_agent], default_active_agent="triage_agent").compile()
StrengthWeakness
Faster — no intermediary, direct agent-to-agent handoffs, fewer LLM calls. Measured in one production migration: roughly a 40% reduction in end-to-end response time and fewer LLM calls per query switching from supervisor to swarm.Routing decisions are distributed across every agent's own prompt instead of one place — shared rules must be duplicated across every agent's system prompt; change one rule and you're updating it in every agent that needs it, and the risk of inconsistency grows with every agent added.
Every agent can interact directly with the user and hand off to one another — ideal when the user benefits from staying with the active specialist across turns.Handoff chains can run long — if triage → tech → billing runs longer than roughly 3 hops, that's usually a sign of a routing problem, not genuine task complexity.
When production teams actually reach for swarm over supervisor

Use a swarm when the application has real specialists that need to take turns being directly responsible for the conversation: each agent has distinct tools/instructions/success criteria, the user benefits from staying with the active specialist across turns, the workflow is mostly sequential rather than parallel, the handoff topology can stay sparse and understandable, and the application can persist thread state with a checkpointer. Practical rule of thumb: start with the supervisor — it's simpler to build and debug, and routing accuracy matters more than the latency penalty in most early deployments. Graduate to swarm only once you have data showing latency is the actual bottleneck and your agents rarely misroute.

Non-negotiable safety net

A multi-agent system without a recursion guard is a production incident waiting to happen — cap total handoffs per conversation and alert when the cap is hit, regardless of topology.

05

Network (Mesh) Pattern

Know it exists, know why almost nobody should default to it.

In the network (or mesh) pattern, any agent can reach any other agent at any time. There is no set order and no set chain — an agent decides mid-task that it needs help and calls for it. This is the most free-form pattern, and the hardest to trace. For a small number of specialists, network is anarchy — hierarchy or supervisor is almost always the right answer instead.

Why this is a trap in interviews

Network topology sounds maximally flexible, which makes it tempting to propose as "the general solution." In practice it removes the one thing that makes multi-agent systems debuggable: a predictable, traceable path through the system. Proposing network topology without a specific reason (genuine unpredictable peer-to-peer collaboration needs, not just "more flexibility") reads as a junior mistake in a system design interview.

Blackboard, Debate & Voting

Two more named patterns worth recognizing, less common in production but real interview material.

Blackboard

Agents don't message each other at all — they read from and write to a shared workspace ("the blackboard": a document, a data structure, a scratchpad) independently, and act whenever they notice something relevant has changed. This decouples agents completely: no agent needs to know which other agents exist, only what shape of data to watch for and produce. Good for loosely-coupled contributions where strict ordering doesn't matter — e.g., several specialist agents annotating the same shared document with their own type of finding.

Debate / Voting / Ensemble

Multiple agents (often the same model, sometimes different models) independently attempt the same task, then either critique each other's answers in a structured back-and-forth (debate) or a final answer is chosen by majority/weighted vote (ensemble). This is the multi-agent generalization of Self-Consistency (see Topic 1) — instead of sampling one model multiple times, you're sampling potentially different agents/models/prompts and using disagreement itself as a signal.

Use whenSkip when
A single agent's mistake is costly and diverse perspectives measurably reduce error (e.g. content moderation edge cases, high-stakes classification)The task has one clearly correct approach — debate just multiplies cost for no accuracy gain
You have budget for N× the LLM calls of a single passLatency-sensitive, real-time user-facing paths

State Sharing & the Telephone Game Problem

The question every multi-agent design must answer explicitly: what does each agent actually need to know about what the others are doing?

ModelHow it worksTrade-off
Full shared stateAll agents read/write the same state object (e.g. one LangGraph AgentState)Simple, but context grows unbounded as more agents contribute — the supervisor context-saturation problem
Isolated context, condensed handoffEach agent gets a fresh context window and a self-contained task description; it returns only distilled findings, not its full working processScales far better, but loses nuance — the receiving agent only sees the conclusion, not the reasoning behind it
Explicit artifact passingAgents exchange a defined schema/document (a plan, a code diff, a report draft) rather than raw conversation historyForces clarity about the interface between agents; brittle if the schema doesn't capture something a downstream agent needed
The "telephone game" problem, named precisely

Verification subagents succeed because they sidestep the telephone game problem — verification requires minimal context transfer by nature. The telephone game problem is what happens when information passes through several agents' summaries in sequence: each summarization step loses a little fidelity, and by the third or fourth hand-off, the original nuance is gone or subtly distorted — exactly like the children's game. The fix isn't "share more context" (that reintroduces the saturation problem) — it's designing hand-offs that need minimal context transfer in the first place, which is why verification, scoped sub-tasks, and condensed artifacts all work better than passing raw history downstream.

Interview framing

"How do you decide how much context to pass between agents in a multi-agent system?" — Start from the isolation boundary question: does the downstream agent need to know how the upstream agent reached its conclusion, or just what the conclusion was? Verification, formatting, and narrowly-scoped execution tasks usually need only the latter — pass a condensed artifact. Tasks requiring the downstream agent to build on or challenge the upstream reasoning need more context, at the cost of window space and the telephone-game risk.

08

Failure Isolation & Recursion Guards

More moving parts means more ways to fail. Design for it explicitly, per topology.

  • Supervisor single point of failure. Coordinator failure halts the entire system in hub-and-spoke topology. Mitigate with checkpoint persistence so a crashed supervisor can resume from the last checkpoint rather than restarting the whole task.
  • Runaway handoff loops in swarm. Two agents that keep handing off to each other (A thinks it's a billing issue, hands to tech; tech thinks it's billing, hands back) will loop forever without a cap. Track handoff count per conversation and force a fallback (e.g., escalate to a human, or a designated tie-breaker agent) past a threshold.
  • One bad subagent poisoning the synthesis. In orchestrator-worker, a single subagent returning a confidently wrong finding can corrupt the lead's final synthesis if there's no cross-check. This is exactly the case for verification subagents or citation passes — a dedicated check step that doesn't just trust every worker's output at face value.
  • Partial failure in parallel fan-out. If 4 of 5 parallel subagents return successfully and one times out or errors, decide up front: does the orchestrator proceed with partial results, retry just the failed one, or fail the whole task? Silently proceeding with partial results without flagging the gap is a common, hard-to-catch bug.
  • Cascading retries. A failure at the leaf level (a tool call inside a subagent) shouldn't automatically retry the entire multi-agent run from the top — scope retries to the smallest failed unit possible.

Token Economics — the 15x Problem

The number every multi-agent design conversation eventually has to justify.

Agents use roughly 4x more tokens than chat interactions, and multi-agent systems use about 15x more tokens than chats. For economic viability, multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance.

Task profileMulti-agent economically justified?
High-value, breadth-first research where a wrong or incomplete answer is costlyYes — the 90.2% accuracy gain typically outweighs a 15x token multiplier
High-volume, low-value, simple lookupsNo — the multiplier dominates; a single well-prompted agent is the economically correct choice
Tightly interdependent tasks (e.g. coding, where each step depends closely on the last)Generally no — multi-agent systems excel at problems that can be divided into parallel, independent strands but are less effective for tightly interdependent tasks such as coding.
Interview framing

"Your PM wants a multi-agent system for every feature because it sounds more advanced. How do you push back?" — Frame it as an economics problem, not a technology preference: multi-agent systems run at roughly 15x the token cost of a normal chat interaction, and the accuracy gain (Anthropic's own eval: 90.2%) only shows up on breadth-first, high-value, parallelizable tasks. For anything narrow, sequential, or low-value, a single well-prompted agent is both cheaper and easier to debug — propose measuring against a strong single-agent baseline before committing to the multi-agent build.

Evaluating Multi-Agent Systems

You can't tune what you don't measure — and multi-agent systems need metrics single-agent evals don't capture.

MetricWhat it catches
Routing / delegation accuracyDid the supervisor/swarm send the task to the right specialist? (Independent of whether the specialist then did a good job.)
Resolution completenessWere all parts of a multi-domain request actually handled, or did routing to one specialist silently drop a sub-request that belonged to another?
Handoff / hop countHow many agent-to-agent transitions did this task take? Rising hop counts over time signal routing drift or a growing need for a tie-breaker.
Token cost per resolved taskThe economic viability check from the previous section, tracked per topology so you can compare supervisor vs swarm costs directly.
LLM-as-judge rubric scoresFor open-ended tasks without a single golden answer: factual accuracy, citation accuracy, completeness, source quality, tool efficiency — scored by a separate judge model against a rubric, not a string match.
Practical advice from production teams

Write the routing_accuracy eval before you write the second agent — decide how you'll measure whether delegation is working correctly before you have two agents to delegate between, so you're not retrofitting evaluation onto a system that's already grown complex.

The Decision Framework

One decision tree, from "should I even go multi-agent" down to "which topology."

QuestionIf yes →
Does a single, well-prompted agent already clear your accuracy bar?Stop here. Rule of thumb: if a single agent with all the tools is hitting ≥85% on your eval and tasks are reasonably homogeneous, stay single.
Is the task decomposable into independent parallel sub-tasks (breadth-first)?Orchestrator-worker
Are there distinct task types you don't want exposed directly to the user, needing central control?Supervisor
Do users benefit from staying with one active specialist across multiple turns, and is the flow mostly sequential?Swarm / handoff

Production Pitfalls

What actually breaks the first time a multi-agent design leaves the whiteboard.

  • Vague delegation instructions. "Research the semiconductor shortage" produced duplicated work across subagents — one explored a 2021 crisis while two others redundantly investigated 2025 supply chains. Every sub-task needs an objective, output format, tool guidance, and explicit boundaries.
  • No effort-scaling rule. Without explicit guidance, orchestrators over-scale — spinning up many subagents for a problem a single call could have answered — silently multiplying cost.
  • Context saturation in supervisor topologies. Routing accuracy measurably degrades after ~8-12 round trips as accumulated history crowds out current task state — use subgraph isolation or summarization before that point, not after you notice the degradation in production.
  • Missing recursion/hop guards. Any topology with cyclic handoff potential (swarm especially) needs a hard cap and a designed fallback, not an assumption that agents will "figure out" not to loop.
  • Jumping to multi-agent without a single-agent baseline. Teams have spent months building elaborate multi-agent architectures only to discover improved prompting on a single agent achieved equal or better results — always measure the baseline first.
  • Treating multi-agent as free. The 15x token multiplier is real and compounds with every additional agent layer — cost-model the design before building it, not after the first invoice.
  • No verification step on high-stakes synthesis. A single subagent's confidently wrong finding can silently corrupt a final answer with no cross-check in place.

Interview Cheat-Sheet

Grouped by depth — definitions, trade-offs, and the system-design prompts you'll actually be handed.

Definitions & core mechanics

What's the difference between orchestrator-worker and supervisor?core

Orchestrator-worker fans out to multiple workers in parallel for independent sub-tasks, and workers never talk to each other or the user — everything routes through the lead. Supervisor routes one turn at a time to a single specialist based on task type; it's typically sequential rather than parallel, and is about picking the right specialist rather than decomposing one task into many parallel pieces.

What's the "isolation boundary" and why does Anthropic call it the most important design decision?core

It's the question of what one agent needs to know about what other agents are doing. Anthropic's research subagents get almost nothing — a self-contained task and a fresh context window, no awareness of siblings. Tightening or loosening this boundary is the single biggest lever over both cost (more shared context = more tokens) and coordination quality (less shared context = more risk of duplicated or conflicting work).

Explain the "telephone game problem" in multi-agent handoffs.core

Information passed through a chain of agent summaries loses fidelity at each hop, the way a message degrades passed verbally down a line of people. The fix isn't passing more raw context (which reintroduces context saturation) — it's designing handoffs, like verification tasks, that inherently need minimal context transfer, so there's less to lose in translation.

Trade-offs

Why would you choose swarm over supervisor even though supervisor is "easier to reason about"?tradeoffs

Latency and cost: every supervisor handoff adds an intermediary round trip and roughly doubles token spend on routing calls specifically. One production migration reported a ~40% latency reduction switching supervisor to swarm. You'd make the switch once you have data showing latency is the actual bottleneck and misrouting is rare — not by default, since supervisor's simpler debugging and routing accuracy matter more early on.

When is a 15x token cost actually worth paying?tradeoffs

When the task is high-value, breadth-first, and decomposes into genuinely independent sub-tasks where a single agent's sequential search would miss things a single context window can't hold. Anthropic's own bar: the accuracy improvement (90.2% in their eval) needs to be worth the cost multiplier for the specific task — high-volume, low-value, or tightly sequential tasks (like most coding tasks) don't clear that bar.

Why do multi-agent systems perform worse on coding tasks than on research tasks?tradeoffs

Coding tasks are tightly interdependent — each step depends closely on the exact state left by the last (a specific function signature, a specific file's current content), which resists clean parallel decomposition and punishes information loss between agents far more than breadth-first research, where sub-tasks are genuinely independent and only need to be combined at the end.

System design

Design a customer support system that needs to route between billing, technical, and account-management specialists.design

Swarm is the natural fit: the user benefits from staying with one active specialist across the conversation rather than seeing routing overhead, the workflow is mostly sequential (rarely needs true parallel work across specialists), and each specialist has clearly distinct tools. Add a triage agent as the default active agent, cap handoff chains at ~3 hops with a fallback to human escalation, and log the active agent to the UI so users see who's responding. Track routing accuracy and resolution completeness as core evals from day one.

Design a deep-research agent that investigates a broad business question across many sources.design

Orchestrator-worker, modeled directly on Anthropic's Research system: a lead agent plans and persists its strategy to memory, spawns 2-10 subagents scaled to query complexity (explicit rules in the prompt, not left to the model's judgment), each subagent gets a self-contained task with clear boundaries and returns condensed findings only, and a dedicated citation/verification pass runs before the final synthesis reaches the user. Budget for ~15x the token cost of a single-agent chat and justify it against the value of the research.

Your multi-agent system's accuracy has plateaued and costs keep climbing. Where do you look first?design

Check whether the delegation instructions are specific enough (vague task descriptions cause duplicated work, which burns tokens without improving accuracy) and whether you have an effort-scaling rule (an orchestrator without explicit scaling guidance over-spawns subagents for simple queries). Also verify against a single-agent baseline — plateaued multi-agent accuracy sometimes means the added complexity was never buying anything and better single-agent prompting would match it at a fraction of the cost.

How would you prevent one bad subagent from corrupting the final answer in an orchestrator-worker system?design

Add a verification subagent as a distinct stage after synthesis but before returning to the user — give it the artifact to check, explicit success criteria, and verification tools, without needing to understand the full history of how the artifact was produced (the same "sidesteps the telephone game" property that makes verification cheap to bolt on). This is cheaper than trying to make every worker perfectly reliable, and catches errors a single confidently-wrong subagent would otherwise silently propagate.

A stakeholder wants every feature built as a multi-agent system because it "sounds more advanced." How do you respond?design

Reframe it as an economics and reliability question, not a sophistication contest: multi-agent systems cost roughly 15x a single chat call in tokens, and Anthropic's own data shows teams repeatedly discovering that improved single-agent prompting matches multi-agent performance on tasks that don't genuinely need parallel decomposition. Propose measuring a strong single-agent baseline first, and reserve multi-agent architecture for tasks that demonstrably hit the single-agent ceiling — long context needs, need for real specialization, or genuine parallel independent sub-tasks.

How do you evaluate whether a supervisor is routing correctly, separately from whether the specialists themselves are doing good work?design

Build a routing-accuracy eval independent of task completion — a labeled set of queries with the "correct" specialist for each, scored purely on whether the supervisor picked the right one, regardless of what that specialist then produced. This isolates routing failures from execution failures, which otherwise get conflated in an end-to-end success metric and make debugging much harder.

Glossary

Every term used in this document.

Orchestrator-worker
One lead agent plans and delegates; workers execute independently in parallel and never communicate with each other.
Supervisor
A central router agent that decides which specialist acts next; specialists report back to the supervisor, not directly to the user.
Swarm / handoff
Peer agents transfer control (and the user-facing conversation) directly to each other via handoff tools, no central router.
Network / mesh
Any agent can call any other agent at any time with no fixed order — most flexible, hardest to trace.
Blackboard
Agents read/write a shared workspace independently, with no direct agent-to-agent messaging.
Isolation boundary
The deliberate limit on what one agent knows about other agents' work — Anthropic's term for the key multi-agent design decision.
Telephone game problem
Progressive loss of fidelity as information passes through a chain of agent summaries/handoffs.
Verification subagent
A dedicated agent spawned to check a completed artifact against success criteria, without needing the full history of how it was built.
Context saturation
Supervisor-pattern degradation as accumulated sub-agent history crowds out current task state in the context window.
Handoff / hop count
Number of agent-to-agent transitions in a conversation; a rising count signals routing drift.
Recursion guard
A hard cap on handoffs/loops with a designed fallback, preventing infinite agent-to-agent cycling.
Effort-scaling rule
Explicit prompt guidance mapping query complexity to number of subagents spawned, preventing over-scaling.
Routing accuracy
Eval metric measuring whether a supervisor/swarm delegated to the correct specialist, independent of that specialist's output quality.
