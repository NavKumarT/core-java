1. null vs undefined

  • undefined: the engine's "no value assigned yet". Seen on uninitialised variables, missing properties, missing arguments, functions with no return.
  • null: a value you assign to mean "intentionally empty".
  • Both are primitives and falsy.
let a; console.log(a);            // undefined
const o = {}; console.log(o.x);   // undefined
console.log(typeof undefined, typeof null); // "undefined" "object" (historic bug)
console.log(null == undefined, null === undefined); // true false
console.log(Number(null), Number(undefined));       // 0 NaN
console.log(null + 1, undefined + 1);               // 1 NaN
JSON.stringify({a:undefined,b:null});               // '{"b":null}'

Where they behave differently

  • Default parameters and destructuring defaults fire only for undefined, not null.
  • ?? treats both as "missing"; || treats every falsy value (0, "", false) as missing.
  • Check both with x == null (the one accepted use of loose equality).
function f(x = 10){ return x }
f(undefined); // 10
f(null);      // null
0 ?? 5; // 0     0 || 5; // 5
Trap: an undeclared variable throws ReferenceError, but typeof undeclared returns "undefined" safely. Check null properly with x === null, never typeof.
Why is typeof null "object"?

A bug from the first JS version, where values were tagged by type bits and null's all-zero pointer matched the object tag. It was never fixed to avoid breaking the web.

How do you test for both null and undefined?

x == null, or x ?? fallback, or x?.prop to read safely.

  • Hoisting: declarations are registered before code runs. Function declarations are hoisted with their body; function expressions and arrows are not (only the variable is).
  • TDZ (temporal dead zone): the time between entering a scope and the let/const line. Access throws ReferenceError, even typeof.
console.log(a); var a = 1;   // undefined
console.log(b); let b = 1;   // ReferenceError
hi(); function hi(){}        // works
bye(); var bye = () => {};   // TypeError: bye is not a function

for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)); // 3 3 3
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j)); // 0 1 2
Trap: let in a for loop creates a fresh binding per iteration, which is why it fixes the timer output. Old fix: wrap in an IIFE.
var x = 1; function f(){ console.log(x); var x = 2 } f() prints undefined: the local x is hoisted and shadows the outer one.
Is let hoisted?

Yes. The binding exists from the start of the block, but is uninitialised until the declaration runs. That is the TDZ, and it proves hoisting: otherwise the outer variable would be read instead of throwing.

Does const make a value immutable?

No, it prevents reassignment of the binding. const a=[]; a.push(1) works. Use Object.freeze for shallow immutability.

What is lexical scope?

Scope is decided by where code is written, not where it is called. A function looks up variables through its definition-time chain of enclosing scopes (the scope chain).

Going deeper

  • DOM APIs return null for "not found" (getElementById, regex.exec); plain property access returns undefined.
  • void 0 always yields undefined (safe even if a local variable is named undefined). Object.create(null) makes a prototype-less object.
  • Optional chaining stops at either: user?.address?.city gives undefined if any link is null/undefined.
  • delete obj.a removes the key; obj.a = undefined keeps the key ("a" in obj stays true).
console.log(typeof typeof null);  // "string"
let x = null; x?.a;               // undefined, no error
({}).a === undefined;             // true
"a" in {a: undefined};            // true
When would you return null vs undefined from your own API?

Return null for "looked, found nothing / intentionally empty"; leave undefined for "not provided/not set". Pick one convention per codebase, since JSON keeps null but drops undefined.

3. Automatic Semicolon Insertion (ASI)

The parser inserts ; when it hits a token that is illegal and (a) a newline precedes it, (b) it is }, or (c) the input ends. It also inserts after a "restricted production" line break.

  • Restricted: return, break, continue, throw, yield, and postfix ++ --. A newline right after them ends the statement.
  • No insertion when the next line can continue the expression. Lines starting with (, [, a backtick, +, - or / are the danger.
function f(){
  return
  { ok: true }
}
f(); // undefined, not the object

const a = 1
const b = a
(function(){ console.log("hi") })()  // TypeError: 1 is not a function
// parsed as: const b = a(function(){...})()

let x = 1, y = 2
;[x, y] = [y, x]   // leading semicolon protects the line
Trap: ASI does not insert inside a for(;;) header, and does not "fix" a line starting with ( or [. Write return { on the same line.
Should you use semicolons?

Either style works if you know the rules. Most teams use semicolons plus Prettier or ESLint (semi rule) to avoid the edge cases above.

More ASI cases

  • No line break is allowed before => and none after return/throw.
  • a newline ++b is parsed as a; ++b (postfix ++ cannot start a line).
  • A line starting with a template literal continues the previous expression (tagged template).
const a = 1
[1, 2].forEach(n => n)   // TypeError: parsed as 1[1, 2].forEach(...)

const t = 'x'
`y`.length               // TypeError: 'x' is called as a tag function

function g(){ return (
  1 + 2
) }                       // 3: parenthesis on the same line keeps it safe
Which tokens at the start of a line are dangerous?

(, [, `, +, -, /. If you skip semicolons, prefix these lines with ;.

4. Rest vs Spread (...)

  • Rest collects many into one. Used in parameters and destructuring; must be the last element; gives a real array.
  • Spread expands one into many. Used in calls, array literals and object literals.
const sum = (...nums) => nums.reduce((a, b) => a + b, 0); // rest
sum(1, 2, 3);                  // 6
Math.max(...[4, 9, 2]);        // 9  (spread into call)
const [first, ...others] = [1, 2, 3];   // rest in destructuring
const { a, ...remaining } = { a: 1, b: 2, c: 3 }; // remaining = {b:2,c:3}
const merged = { ...{x:1,y:2}, ...{y:9} };  // {x:1, y:9} later wins
[..."hey"];                    // ["h","e","y"]
  • Spread makes a shallow copy. Nested objects are still shared; use structuredClone for deep copies.
  • Array spread needs an iterable; object spread works on any object (and ignores null/undefined).
  • Rest beats arguments: real array, works in arrows, can follow named params.
Trap: [...{a:1}] throws (not iterable) but ({...[1,2]}) gives {0:1,1:2}. {...null} is {}.
const b = {...a}; b.nested.x = 1 also changes a.nested.x.
Difference between rest and spread in one line?

Same syntax, opposite direction: rest gathers values into an array/object on the left side of an assignment or parameter list, spread unpacks on the right side or in call arguments.

More depth

  • fn.length counts params before the first default or rest.
  • Spread of a Map/Set works ([...map] gives entries); spreading huge arrays into a call (Math.max(...big)) can hit the argument limit and throw RangeError. Use reduce there.
  • {...obj} copies own enumerable props and defines them; Object.assign sets them (triggers setters). Neither copies prototypes or non-enumerable props.
const [a, , b, ...c] = [1, 2, 3, 4, 5];  // a=1 b=3 c=[4,5]
const f = (x, y = 2, ...z) => 0;  f.length;  // 1
const { p: { q }, ...rest } = { p: { q: 1 }, r: 2, s: 3 }; // q=1 rest={r:2,s:3}
const arr2 = [...arr, 4];   // immutable add (used constantly in React state)
const upd = { ...state, count: state.count + 1 };
Spread vs slice/concat/Object.assign?

Spread is the concise, readable equivalent for shallow copies; it also works with any iterable and inside literals. All are shallow.

5. When do you get Infinity / -Infinity?

  • Division of a non-zero number by zero: 1/0 is Infinity, -1/0 is -Infinity. Note 1/-0 is -Infinity too.
  • Overflow beyond Number.MAX_VALUE (about 1.79e308): 2**1024, Number.MAX_VALUE*2.
  • Math.log(0) is -Infinity. Math.max() (no args) is -Infinity; Math.min() is Infinity.
  • Number("Infinity"), parseFloat("Infinity"), -Number.MAX_VALUE*2.
Infinity - Infinity;   // NaN
Infinity * 0;          // NaN
5 / Infinity;          // 0
Number.isFinite(1/0);  // false
Number.isFinite("5");  // false (no coercion) vs isFinite("5") true
1n / 0n;               // RangeError: BigInt never gives Infinity
Why doesn't JS throw on divide by zero?

JS Numbers follow IEEE 754 doubles, which define Infinity and NaN as valid results. Only BigInt division by zero throws.

Why does Math.max() return -Infinity?

It is the identity element for max (every number is larger), the same logic as an empty sum being 0.

More depth

  • Number.MAX_SAFE_INTEGER is 9007199254740991 (253-1); beyond it integers lose precision (MAX_SAFE_INTEGER + 2 is wrong). Use BigInt.
  • Number.MIN_VALUE (5e-324) is the smallest positive number, not the most negative. MIN_VALUE / 2 underflows to 0. Most negative is -Number.MAX_VALUE.
  • JS has -0: Object.is(0, -0) is false, 0 === -0 is true, and 1/-0 is -Infinity.
  • JSON.stringify(Infinity) gives "null". isFinite(null) is true (null becomes 0).
Infinity === Infinity;        // true
typeof Infinity;              // "number"
parseInt("Infinity");         // NaN (parseInt reads digits only)
10 ** 309;                    // Infinity
Number.POSITIVE_INFINITY === Infinity; // true
Infinity > Number.MAX_VALUE;  // true
Practical use of Infinity?

As a neutral starting value: let min = Infinity for a minimum search, -Infinity for a maximum, and as an unbounded limit in algorithms (Dijkstra distances).

6. When do you get NaN?

NaN means "invalid numeric result". It is of type number.

  • Failed conversion: Number("abc"), parseInt("abc"), Number(undefined), +{}.
  • Impossible maths: 0/0, Math.sqrt(-1), Infinity - Infinity, Infinity * 0.
  • Arithmetic with undefined or non-numeric strings: undefined + 1, "a" * 2.
NaN === NaN;               // false (only value not equal to itself)
typeof NaN;                // "number"
isNaN("hello");           // true  (coerces first: misleading)
Number.isNaN("hello");    // false (no coercion: correct)
Object.is(NaN, NaN);      // true
[NaN].includes(NaN);      // true
[NaN].indexOf(NaN);       // -1 (uses ===)
NaN ** 0;                 // 1   (special case)
"5" - 2; "5" + 2;         // 3  "52"
Trap: null + 1 is 1 (null becomes 0) but undefined + 1 is NaN. [] + {} is "[object Object]", and parseInt(null) is NaN because it parses the string "null".
How do you reliably check for NaN?

Number.isNaN(x), or Object.is(x, NaN), or the old trick x !== x.

Why is 0.1 + 0.2 !== 0.3?

Binary floating point cannot represent 0.1 exactly; the sum is 0.30000000000000004. Compare with a tolerance (Math.abs(a-b) < Number.EPSILON) or use integer cents/BigInt/decimal libraries.

Trap: NaN spreads: any arithmetic with NaN is NaN, so a single bad input silently poisons a whole total. Validate inputs early with Number.isNaN.
Why does ["1","2","3"].map(parseInt) fail?

map calls parseInt(value, index). Radix 0 is treated as 10, radix 1 is invalid (NaN), radix 2 cannot parse "3" (NaN).

7. Arrow functions: must-know points

  • No own this: captures this lexically from the enclosing scope. call/apply/bind cannot change it.
  • No arguments object (use rest). No own super/new.target.
  • Not constructors: new throws TypeError; no prototype.
  • Cannot be generators. Duplicate parameter names are not allowed.
  • Implicit return for expression bodies; wrap object literals in parentheses.
const sq = x => x * x;
const mk = () => ({ id: 1 });      // () needed for object
const bad = () => { id: 1 };       // undefined: braces are a block, id: is a label

const user = {
  name: "Asha",
  regular() { return this.name },        // "Asha"
  arrow: () => this.name,                // undefined (this = outer/global)
  later() { setTimeout(() => console.log(this.name)) } // "Asha" via lexical this
};
const Foo = () => {}; new Foo();      // TypeError

When not to use

  • Object methods and prototype methods that need their own this.
  • Constructors, and callbacks where the library sets this (e.g. jQuery handlers, DOM this as element).
Trap: class field arrows (handle = () => {...}) bind this per instance. Handy for callbacks, but each instance gets its own copy instead of sharing one prototype method.
Output: const o = { v: 1, f: () => this.v }; o.f()

The arrow uses the outer this, not o. In a classic browser script that is window, so you get undefined. In Node CommonJS it is module.exports ({}), also undefined. In an ES module top-level this is undefined, so it throws a TypeError. Rule: arrow = outer this.

Can you bind an arrow function?

bind works without error but cannot change this; it only pre-fills arguments.

8. Closures

Definition: a closure is a function bundled with references to the variables of the scope where it was created (its lexical environment). The function keeps those variables alive even after the outer function has returned.

function counter(){
  let n = 0;                    // private, survives after counter() returns
  return { inc: () => ++n, get: () => n };
}
const c = counter(); c.inc(); c.inc(); c.get(); // 2

const once = fn => { let done = false, r; return (...a) => done ? r : (done = true, r = fn(...a)) };

function debounce(fn, ms){ let t; return (...a) => { clearTimeout(t); t = setTimeout(() => fn(...a), ms) } }

Uses

  • Data privacy / module pattern, factories, memoization, once, debounce/throttle, partial application and currying, event handlers with state, React hooks (state lives in a closure).

Pitfalls

  • Closures capture variables, not values: with var in a loop, all callbacks see the final value.
  • Can retain large objects and cause memory leaks if the closure is long-lived. Stale closures in React: a callback captures old state.
Trap: for(var i=0;i<3;i++){ fns.push(()=>i) } fns.map(f=>f()) gives [3,3,3]; with let it gives [0,1,2].
Explain a closure in one sentence

A function that remembers and can access variables from its birthplace scope even when executed elsewhere.

Do closures cause memory leaks?

Not by themselves. They keep referenced variables alive for as long as the closure is reachable; engines usually keep only variables that are actually used, but one live closure can pin a shared scope. Release by removing listeners/timers or nulling references.

9. How can sum(5)(6) return 11? (Currying)

sum(5) returns a function that remembers 5 (closure), and that function receives 6.

const sum = a => b => a + b;
sum(5)(6); // 11

// Infinite chaining, ends on empty call: sum(1)(2)(3)()
function add(a){ return b => b === undefined ? a : add(a + b) }
add(1)(2)(3)(); // 6

// Chain ending without () using valueOf
function s(a){ const f = b => s(a + b); f.valueOf = () => a; return f }
s(1)(2)(3) + 0; // 6 (coerced)

// Generic curry using fn.length
const curry = fn => function c(...a){ return a.length >= fn.length ? fn(...a) : (...b) => c(...a, ...b) };
curry((a, b, c) => a + b + c)(1)(2, 3); // 6
  • Currying: f(a,b,c) becomes f(a)(b)(c). Partial application: fix some args now, rest later.
  • Why useful: reusable specialised functions (const add5 = sum(5)), composition, configuration.
Trap: fn.length ignores default and rest params, so a generic curry breaks on them.
Difference between currying and partial application?

Currying turns an n-ary function into n unary functions chained. Partial application pre-fills any number of args and returns a function that takes the rest.

10. Iterables and Iterators

  • Iterable: object with a [Symbol.iterator]() method that returns an iterator.
  • Iterator: object with next() returning { value, done }.
  • Built-in iterables: Array, String, Map, Set, TypedArray, arguments, NodeList, generators. Plain objects are not iterable.
  • Consumers: for...of, spread, array destructuring, Array.from, new Map/Set, Promise.all, yield*.
const range = {
  from: 1, to: 3,
  [Symbol.iterator]() {
    let cur = this.from, end = this.to;
    return { next: () => cur <= end ? { value: cur++, done: false } : { value: undefined, done: true } };
  }
};
[...range];                 // [1,2,3]
for (const x of range) {}   // works

const it = [10, 20][Symbol.iterator]();
it.next(); // {value:10, done:false}
it.next(); it.next(); // {value:undefined, done:true}
  • for...in loops over enumerable keys (including inherited); for...of loops over values of an iterable.
  • Iteration is lazy and pull-based. break in for...of calls the iterator's optional return() for cleanup.
  • Async version: Symbol.asyncIterator with for await...of (streams, paginated APIs).
  • Array-likes (have length and indexes) are not necessarily iterable; convert with Array.from.
Trap: for (const x of {a:1}) throws TypeError (not iterable). An iterator that returns itself ([Symbol.iterator](){return this}) can only be consumed once.
Is an iterator also iterable?

Built-in iterators (array iterators, generator objects) are, because they return themselves from [Symbol.iterator]. A bare { next(){} } object is not.

More depth

  • Protocol: next(v) required; return() and throw() optional (cleanup on early exit).
  • Iterating objects: Object.keys / values / entries return arrays, which are iterable. map.entries(), array.entries(), keys(), values() return iterators.
  • A generator makes custom iterables short: *[Symbol.iterator]() { yield* this.items }.
  • Modern engines add iterator helpers (.map .filter .take .toArray directly on iterators), lazy like generators. Check browser support before relying on them.
for (const [i, v] of ["a","b"].entries()) {}      // 0 "a", 1 "b"
for (const [k, v] of Object.entries({x:1})) {}    // "x" 1
Array.from({ length: 3 }, (_, i) => i * 2);       // [0,2,4]
class Bag { items=[1,2]; *[Symbol.iterator](){ yield* this.items } }
[...new Bag()];  // [1,2]
Array-like vs iterable?

Array-like has length and index keys ({0:"a",length:1}); iterable has Symbol.iterator. Strings and arrays are both; the example object is only array-like. Array.from accepts either.

11. Generators

A function* returns a generator object (an iterator) and can pause at yield and resume later, keeping its local state.

function* ids(){ let i = 1; while (true) yield i++; }  // infinite, lazy
const g = ids(); g.next().value; g.next().value;       // 1, 2

function* talk(){
  const name = yield "Name?";       // value passed IN by next(arg)
  const age  = yield `Hi ${name}, age?`;
  return `${name}:${age}`;
}
const t = talk();
t.next();        // {value:"Name?", done:false}  (first next(arg) is ignored)
t.next("Ravi");  // {value:"Hi Ravi, age?", done:false}
t.next(30);      // {value:"Ravi:30", done:true}

function* all(){ yield 1; yield* [2, 3]; yield* other(); } // delegate
  • Methods: next(v), return(v) (finish early, runs finally), throw(e) (raise error at the paused yield).
  • Generators are iterable, so work with spread and for...of. A return value is not included in iteration.
  • Use cases: lazy/infinite sequences, custom iterables with less code, state machines, pagination, ID generation, redux-saga, and the idea behind async/await (coroutines).
  • Cannot be arrow functions; calling a generator does not run any of its body until the first next().
Trap: [...gen()] on an infinite generator hangs. A finished generator stays finished: next() returns {value:undefined, done:true} forever. yield is an expression: const x = yield 1 gets whatever is passed to the following next.
Generator vs normal function?

Normal functions run to completion once. Generators can suspend and resume, return multiple values over time, and accept values back through next(arg).

How do generators relate to async/await?

async/await behaves like a generator driven by a runner that resumes it when each promise settles (await ≈ yield). Libraries like co did this before ES2017.

12. Memory management & garbage collection

  • Lifecycle: allocate (automatic on creating values) → use → release (garbage collector).
  • Stack holds primitives and references; heap holds objects, arrays, functions.
  • Reachability: a value is kept if it can be reached from roots (globals, current call stack, active closures). Unreachable values are collected.
  • Mark-and-sweep: mark everything reachable from roots, sweep the rest. Handles circular references. The old reference counting approach leaked cycles (old IE).
  • V8 is generational: short-lived objects in the young generation (fast Scavenge), survivors promoted to the old generation (Mark-Compact, incremental/concurrent to avoid long pauses).

Common leaks

  • Accidental globals (x = 5 without declaration).
  • Uncleared setInterval / event listeners (React: no cleanup in useEffect).
  • Closures holding big data; unbounded caches/Maps; detached DOM nodes still referenced.
const cache = new WeakMap();      // keys held weakly: entry vanishes with the key object
function meta(el){ if(!cache.has(el)) cache.set(el, { clicks: 0 }); return cache.get(el) }

const id = setInterval(tick, 1000);
clearInterval(id);                // release
btn.removeEventListener("click", handler);
  • WeakMap/WeakSet: keys must be objects, not enumerable, no size. WeakRef/FinalizationRegistry exist but are unreliable for logic.
  • Find leaks: DevTools Memory tab: heap snapshots, allocation timeline; look for ever-growing retained size.
Trap: setting obj = null does not free memory by itself; it only removes one reference. And you cannot force GC from code.
Map vs WeakMap?

Map holds strong references and is iterable, so keys never get collected while in the map. WeakMap holds keys weakly, so it can't leak the keys, but you cannot iterate or count it.

How do you debug a memory leak?

Take heap snapshots before and after repeating an action, compare, and trace the retainer path of objects that keep growing (listeners, timers, detached DOM, closures).

More depth

// Leak 1: forgotten interval keeps the closure (and bigData) alive
function start(){ const bigData = new Array(1e6).fill(0);
  setInterval(() => console.log(bigData.length), 1000); }
// Leak 2: detached DOM kept in an array
const nodes = []; nodes.push(document.getElementById("row")); row.remove(); // still referenced
// React-style fix: always clean up
useEffect(() => { const id = setInterval(tick, 1000); return () => clearInterval(id) }, []);
// WeakRef: reference that does not block collection
const ref = new WeakRef(obj); ref.deref()?.method();
  • Symptoms of a leak: heap grows after every GC cycle, rising tab memory, jank, eventual crash.
  • Stack: fixed-size, LIFO call frames (stack overflow on deep recursion). Heap: dynamic, GC-managed.
  • GC runs automatically and non-deterministically; large heaps cause pauses, which V8 reduces with incremental, concurrent and parallel marking.
How does GC handle circular references?

Mark-and-sweep only asks "is it reachable from a root?". A cycle with no path from a root is unreachable and collected, unlike reference counting.

13. Error handling

try {
  JSON.parse("{bad");
} catch (e) {                    // catch binding optional: catch { }
  console.log(e.name, e.message); // SyntaxError ...
} finally {
  cleanup();                     // always runs, even after return/throw
}

class ValidationError extends Error {
  constructor(msg, field){ super(msg); this.name = "ValidationError"; this.field = field }
}
throw new ValidationError("Required", "email");

try { await fetch(u) } catch (e) { throw new Error("Load failed", { cause: e }) }
  • Built-in types: Error, TypeError, ReferenceError, SyntaxError, RangeError, URIError, EvalError, AggregateError. Always throw Error objects (they carry a stack), not strings.
  • Rethrow errors you can't handle; check with e instanceof X.
  • Async: use try/catch around await, or .catch() on promises. Promise.allSettled collects failures without rejecting.
  • Global nets: window.onerror, unhandledrejection event (browser); process.on("uncaughtException" / "unhandledRejection") (Node). Send to a logging service.
  • fetch does not reject on HTTP 404/500; check res.ok.
Trap 1: try { setTimeout(() => { throw 1 }) } catch{} does NOT catch: the callback runs later, outside the try. Same for un-awaited promises.
Trap 2: function f(){ try { return 1 } finally { return 2 } } returns 2; finally overrides.
Trap 3: new Promise(()=>{ throw 1 }) becomes a rejection, not a sync throw. A return promise inside try without await bypasses the catch.
Difference between throw Error and throw "text"?

Error objects have name, message and stack, work with instanceof, and show up properly in tools. Strings lose all that.

How do you handle errors globally in a real app?

Local try/catch for expected failures, a centralised handler/logger, global unhandledrejection and onerror listeners, user-friendly messages, and (in React) error boundaries.

More depth

async function load(){ throw new Error("x") }   // returns a rejected promise
load().catch(e => console.log(e.message));
Promise.any([Promise.reject(1)]).catch(e => e instanceof AggregateError); // true

async function retry(fn, n = 3){            // retry pattern
  for (let i = 0; i < n; i++){
    try { return await fn() } catch (e) { if (i === n - 1) throw e;
      await new Promise(r => setTimeout(r, 2 ** i * 200)) } } }
  • e.stack shows the call trace; e.cause chains the original error. Error objects don't JSON-serialise well (no enumerable props), so log message and stack explicitly.
  • try/catch catches sync errors and awaited rejections only; .catch() handles a promise chain. return fn() inside try (no await) will not catch its rejection; return await fn() will.
  • Operational vs programmer errors: handle expected failures (network, validation); let bugs (TypeError) surface and be logged.
Promise.all vs allSettled vs any vs race for errors?

all rejects on the first failure; allSettled never rejects and reports each outcome; any resolves with the first success (AggregateError if all fail); race settles with the first result, success or failure.
