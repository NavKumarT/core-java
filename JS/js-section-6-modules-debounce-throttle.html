1. What is a module?

A module is a single JavaScript file with its own private scope that explicitly exports what others may use and imports what it needs from other modules. ES modules (ESM, ES2015) are the language standard, replacing older patterns: IIFE/revealing-module pattern, CommonJS (require, Node), AMD and UMD.

  • Why modules: no global namespace pollution, encapsulation, reuse, explicit dependencies, maintainability, lazy loading, tree-shaking (bundlers drop unused exports).
  • Properties of an ES module: always strict mode; top-level variables are module-scoped (not window properties); top-level this is undefined; evaluated once and cached (a singleton shared by all importers); imports/exports are static (must be at top level, analysable before running); supports top-level await; loaded with CORS rules.
// math.js
export const PI = 3.14159;
export function add(a, b) { return a + b }

// app.js
import { PI, add } from "./math.js";     // path + extension required in browsers
console.log(add(2, 3), PI);

Using modules in a browser

<!-- type="module" is REQUIRED to use import/export -->
<script type="module" src="app.js"></script>

<script type="module">                 <!-- inline module also works -->
  import { add } from "./math.js";
  console.log(add(1, 2));
</script>

<script src="app.js"></script>         <!-- classic script containing import/export: -->
// SyntaxError: Cannot use import statement outside a module

<script nomodule src="legacy.js"></script>   <!-- fallback for browsers without module support -->

// dynamic import() works even in classic scripts
button.onclick = async () => { const m = await import("./heavy.js"); m.run() };
  • Module scripts are deferred by default (run after HTML is parsed, in order), so no need for defer. async makes them run as soon as loaded.
  • Browser specifiers must be a URL or relative path ("./a.js", "/a.js", "https://..."). Bare names like "lodash" need a bundler or an import map (<script type="importmap">).
  • onclick="..." inline handlers can't see module-scoped functions; attach with addEventListener or assign to window.

Running import/export on your local machine

  • Browser: opening index.html via file:// fails with a CORS error ("origin null") because module scripts are fetched with CORS. Serve over HTTP: VS Code Live Server, npx serve, python3 -m http.server, or a dev server like npm create vite@latest.
  • Node.js: either name files .mjs, or add "type": "module" to package.json (then .js is ESM). Then node app.js. Relative imports need the extension. No __dirname/__filename; use import.meta.url.
// Node ESM replacement for __dirname
import { fileURLToPath } from "node:url"; import path from "node:path";
const __dirname = path.dirname(fileURLToPath(import.meta.url));
Traps: import in a plain <script> is a SyntaxError. A module's top-level var x does not create window.x. Forgetting the .js extension in the browser gives a 404. Import and export statements cannot be inside if, functions or try blocks (use import()). Opening via file:// is the #1 "my modules don't work" problem.
What is a module?

A file (unit of code) with its own scope that shares functionality through export and consumes it through import, helping organise and reuse code without global variables.

Can you import a module inside a normal script tag?

Only if the tag is <script type="module"> (inline or src). In a classic script, static import/export throws a SyntaxError; the dynamic import("./x.js") expression is the exception and works anywhere.

How do you run import/export locally?

Use type="module" and serve the files over HTTP (Live Server, http-server, Vite) instead of opening with file://. In Node use .mjs or "type":"module".

Benefits of modules? Does a module run more than once if imported in many files?

Encapsulation, reuse, dependency clarity, tree-shaking and lazy loading. No: a module is fetched and evaluated once; every importer gets the same instance (so module-level state is shared, which is how singletons work).

2. Named export and import

A module may have many named exports. Importers must use the exported name (inside { }), though they can alias it.

// utils.js: three equivalent ways to export
export const PI = 3.14;                       // inline
export function add(a, b) { return a + b }
export class Counter {}
const sub = (a, b) => a - b, mul = (a, b) => a * b;
export { sub, mul as multiply };              // list at the bottom, with alias

// app.js
import { PI, add } from "./utils.js";         // names must match the exports
import { multiply as times, sub } from "./utils.js";   // alias with `as`
import * as utils from "./utils.js";          // namespace import: ALL named exports as one object
utils.add(1, 2); utils.PI; Object.keys(utils);
import { add as add2, add as add3 } from "./utils.js";  // same export twice: fine

import { missing } from "./utils.js";         // SyntaxError: module does not provide an export named 'missing'
  • Braces are mandatory for named imports. Without braces you are asking for the default export. import add from "./utils.js" fails if there is no default.
  • Rename on import with as (and on export). The local name can differ; the name in braces must match the exported name.
  • Namespace import (import * as ns) gives a read-only module namespace object (also contains default if present).
  • Hoisting: import declarations are hoisted: all imports are resolved and the imported modules are executed before the importing module's own code, wherever the import line is written. Exports are also declared up front. But let/const/class exports are still in the TDZ until their line runs (matters in circular imports).
console.log(add(1, 2));              // 3: works even though the import is below
import { add } from "./utils.js";    // hoisted (convention: keep imports at top)

import { x } from "./a.js";   // a.js imports b.js which imports a.js (circular):
// x may be in TDZ at that moment -> ReferenceError: Cannot access 'x' before initialization
Traps: a typo in a named import is a parse-time SyntaxError (not undefined like in CommonJS). Imported bindings are read-only: add = 5 throws TypeError. You cannot export a destructuring that is not declared (export { a } needs a in scope). Importing names inside braces is not destructuring (you cannot nest or default them), even though it looks similar.
What is a named export and import?

Exporting one or more bindings by name (export const a, export { a, b }) and importing them by those names in braces. A file can have any number of them.

Can you avoid {} while importing a named module?

No, braces are the syntax for named imports. The alternatives are a namespace import (import * as m) or a default import (no braces) when the module has a default export.

How do you import all named exports? Is it good practice?

import * as utils from "./utils.js". It is handy to avoid name clashes and for small utility modules, and modern bundlers can still tree-shake when you access members statically (utils.add). But importing everything by habit hides dependencies, hampers tree-shaking if members are accessed dynamically (utils[name]), and makes code less clear; prefer importing just what you need.

Do modules hoist?

Yes: static imports are hoisted and executed before the module body, regardless of position. Exported function declarations are usable early; let/const/class exports stay in the TDZ until initialised.

Must the name be the same on import?

For named imports the name in braces must match the export, but you may rename locally with as. (Default imports can use any name.)

3. Default export and import

Each module can have at most one default export, the module's "main thing". It is imported without braces and with any name you like.

// ways to default-export (only ONE per file)
export default function greet() {}            // 1. named or anonymous function
export default class User {}                  // 2. class
export default 42;                            // 3. any expression/value
export default { api: "/v1", retries: 3 };    // 4. object literal
export default () => "hi";                    // 5. anonymous arrow
const store = {}; export default store;       // 6. declare first, then export the identifier
export { store as default };                  // 7. equivalent alias form
export default const x = 1;                   // SyntaxError: use `const x = 1; export default x`

// importing
import greet from "./greet.js";               // any local name
import hello from "./greet.js";               // same module, different name: fine
import { default as sayHi } from "./greet.js";// explicit form
import greet2, { helper, VERSION } from "./lib.js";   // default + named together (React: import React, { useState } from "react")
import * as lib from "./lib.js"; lib.default; // default lives under the key "default"

Traps: export default exports the value (the binding is not live under a new name for expressions). export default function(){} is a declaration (hoisted), whereas export default (function(){}) is an expression. You cannot write import { default } from (default is a reserved word, so alias it: { default as x }). Mixing both in a file is allowed but keep it consistent.
What is default export/import? Difference between named and default?

Default: one main export per module, imported without braces under any name. Named: many exports, imported with braces by exact name (aliasable). See the table above.

Various ways to implement default export/import?

Export: export default followed by a function, class, value, object or arrow; or export { x as default }; or declare then export default x. Import: import x from, import { default as x } from, import x, { named } from and import * as ns (then ns.default).

Default vs named: which should you prefer?

Many style guides prefer named exports for consistent names, safer refactoring, easy auto-imports and tree-shaking; defaults remain common for components and for frameworks that require them (Next.js pages, lazy-loaded components with React.lazy).

4. Re-exports, dynamic import, live bindings

// Re-exports and barrel files (components/index.js)
export { Button } from "./Button.js";          // re-export a named export
export { default as Modal } from "./Modal.js"; // re-export a default under a name
export * from "./helpers.js";                  // re-export all named (NOT default)
export * as math from "./math.js";             // re-export namespace
import "./polyfills.js";                       // side-effect only import (runs the file)

// Dynamic import(): returns a Promise of the module namespace; can be anywhere, path can be computed
const { add, default: Main } = await import("./math.js");
if (isAdmin) { const m = await import("./admin.js"); m.init() }
const lang = await import(`./i18n/${locale}.js`);       // conditional / computed loading, code splitting
button.onclick = () => import("./chart.js").then(m => m.draw());   // lazy-load on demand

// JSON modules (modern engines, with import attributes; check support)
import data from "./data.json" with { type: "json" };

// live bindings: imports are READ-ONLY VIEWS of the exporter's variables
// counter.js
export let count = 0;
export function inc() { count++ }
// main.js
import { count, inc } from "./counter.js";
console.log(count); inc(); console.log(count);   // 0 then 1 (live!)
count = 10;                                      // TypeError: Assignment to constant variable

// import.meta and top-level await (modules only)
import.meta.url;                                 // URL of the current module
const config = await fetch("/config.json").then(r => r.json());
  • Dynamic import enables code splitting and lazy loading: the code downloads only when needed (React React.lazy(() => import("./Page")), route-based splitting).
  • Circular dependencies work in ESM thanks to live bindings, but accessing a binding before its module has run gives TDZ ReferenceError (or undefined for var/functions hoisted). Avoid by restructuring.
  • Import maps let browsers map bare specifiers: { "imports": { "lodash": "/vendor/lodash.js" } }.
Trap: export * does not re-export the default. Barrel files can defeat tree-shaking and slow dev servers in huge projects. import() is an expression returning a promise, so await it. Static import paths can't be variables or template strings.
What are live bindings?

An import is a read-only reference to the original exported variable, not a copy. If the exporting module changes the variable, importers see the new value, though they can't assign to it themselves. (CommonJS exports copies of values at require time.)

What is dynamic import and when to use it?

import(path) loads a module on demand and returns a promise. Use it for lazy loading routes/components, heavy libraries, feature flags, and locale files, improving initial load time.

What is a barrel file?

An index.js that re-exports from several modules so consumers can import from one path (import { Button, Modal } from "./components").

ESM vs CommonJS: key differences?

ESM is the standard: static, async, live bindings, tree-shakable, in browsers and Node; CommonJS is Node's older synchronous require system with value copies and dynamic loading. ESM is preferred in new code.

Why can bundlers tree-shake ESM but not CJS?

ESM imports/exports are static, so tools know at build time which exports are used and can drop the rest; require can be dynamic (require(name)), defeating analysis.

6. Debounce vs throttle: the concept

Some events fire at a very high rate: mousemove, scroll, resize, input/keyup, rapid clicks. Running an expensive handler (API call, layout work, re-render) on every event wastes CPU and network and makes the UI janky. Debounce and throttle are two ways to control how often the handler really runs.

What is throttling and debouncing?

Both limit how often a function runs in response to rapid events. Throttling guarantees at most one execution per time window (regular cadence). Debouncing delays execution until the events have stopped for a set time, collapsing a burst into one call.

When would you choose one over the other?

Use throttle when you need regular updates during continuous activity (scroll position, resize, mouse tracking, preventing click spam). Use debounce when only the final value matters (search box, validation, autosave, "resize ended").

7. Throttling: implementation

// A) Course approach: a flag + setTimeout (runs the handler AFTER each window: "trailing")
let normalCount = 0, throttledCount = 0, throttleWait = false;
document.addEventListener("mousemove", () => {
  normalCount++;                                  // every event
  if (throttleWait) return;                       // ignore events while the timer is running
  throttleWait = true;
  setTimeout(() => { throttledCount++; throttleWait = false }, 500);   // runs once per 500ms
});

// B) Reusable throttle: leading edge (runs immediately, then ignores for `ms`)
function throttle(fn, ms) {
  let wait = false;
  return function (...args) {
    if (wait) return;
    fn.apply(this, args);                         // preserve `this` and arguments
    wait = true;
    setTimeout(() => (wait = false), ms);
  };
}

// C) Timestamp version (no timers)
function throttleTs(fn, ms) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= ms) { last = now; return fn.apply(this, args) }
  };
}

// D) Leading + trailing (last event is not lost): what lodash does by default
function throttleFull(fn, ms) {
  let last = 0, timer = null, lastArgs, lastThis;
  return function (...args) {
    const now = Date.now(); lastArgs = args; lastThis = this;
    const remaining = ms - (now - last);
    if (remaining <= 0) { clearTimeout(timer); timer = null; last = now; fn.apply(this, args) }
    else if (!timer) timer = setTimeout(() => { last = Date.now(); timer = null; fn.apply(lastThis, lastArgs) }, remaining);
  };
}

window.addEventListener("scroll", throttle(updateProgressBar, 200));
// 10 events, one every 100ms (0..900ms), throttle(300) leading-only runs at 0, 300, 600, 900 -> 4 calls
Traps: an arrow function as the returned wrapper loses the caller's this (use function + apply). Plain leading-only throttle drops the last event, so the UI can end on a stale value (e.g. last scroll position); add trailing execution. Don't create the throttled function inside the event handler (a new closure each time resets the state): create it once outside. For visual updates, requestAnimationFrame throttling syncs to the screen refresh. Throttled functions return undefined when skipped.
How do you implement throttling?

Keep a flag (or last-run timestamp) in a closure. If the flag is set, ignore the call; otherwise run (or schedule) the function and set the flag, clearing it with setTimeout after the interval.

Leading vs trailing edge?

Leading: run on the first event of a window, then ignore the rest. Trailing: run once at the end of the window with the latest data. Lodash lets you choose both: _.throttle(fn, ms, { leading, trailing }).

8. Debouncing: implementation

// Course approach: a bounce timer that is reset on every event
let normalCount = 0, debouncedCount = 0, bounceTimer;
document.addEventListener("mousemove", () => {
  normalCount++;
  clearTimeout(bounceTimer);                       // cancel the previous pending run
  bounceTimer = setTimeout(() => { debouncedCount++ }, 500);   // runs only after 500ms of inactivity
});

// Reusable debounce
function debounce(fn, ms) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), ms);   // arrow inside keeps outer `this`
  };
}

// With leading option, cancel() and flush()
function debounceFull(fn, ms, { leading = false } = {}) {
  let timer, lastArgs, lastThis;
  function debounced(...args) {
    lastArgs = args; lastThis = this;
    const callNow = leading && !timer;
    clearTimeout(timer);
    timer = setTimeout(() => { timer = null; if (!leading) fn.apply(lastThis, lastArgs) }, ms);
    if (callNow) fn.apply(this, args);
  }
  debounced.cancel = () => { clearTimeout(timer); timer = null };
  debounced.flush = () => { if (timer) { clearTimeout(timer); timer = null; fn.apply(lastThis, lastArgs) } };
  return debounced;
}

input.addEventListener("input", debounce(e => search(e.target.value), 300));
// typing "javascript" fast (10 keystrokes, gaps < 300ms) -> 1 API call after you pause
Traps: create the debounced function once; input.oninput = e => debounce(fn, 300)(e) makes a new timer every time, so nothing is ever debounced. A debounced handler gets the last event object; read e.target.value at call time (events are not reused in modern browsers, but copy values if needed). Constant events with gaps always below N never fire a debounced function (e.g. continuous scroll): use throttle, or maxWait in lodash. Debounced results arrive asynchronously, so return values are not available.
How do you implement debouncing?

Store a timer id in a closure; on every call clear the existing timer and start a new setTimeout that will run the function after the delay. Only the last call in a burst survives.

Why does it use closures, and what about this and arguments?

The closure holds timer (or wait) between calls. Use a regular function wrapper with fn.apply(this, args) (or an arrow inside) to forward the original this and arguments.

Give a practical example of throttling and of debouncing.

Throttling: a button or scroll handler that must fire at most once per second even when the user clicks/scrolls rapidly. Debouncing: a search box that calls the API only after the user pauses typing.

Debounce vs throttle for a scroll event or a resize event?

Scroll: throttle (continuous feedback needed). Resize: debounce if you only need the final size, throttle if the layout must follow along.

10. React usage and advanced points

// React: a component re-renders, so a debounce created in the body is re-created each time and never works.
// 1) useDebounce value hook (most common)
function useDebounce(value, ms = 300) {
  const [v, setV] = useState(value);
  useEffect(() => { const t = setTimeout(() => setV(value), ms); return () => clearTimeout(t) }, [value, ms]);
  return v;
}
const debouncedQuery = useDebounce(query, 400);
useEffect(() => { if (debouncedQuery) fetchResults(debouncedQuery) }, [debouncedQuery]);

// 2) debounced callback: keep ONE instance across renders
const debouncedSave = useMemo(() => debounce(save, 500), []);     // or useRef / useCallback
useEffect(() => () => debouncedSave.cancel?.(), [debouncedSave]); // cleanup on unmount
// Wrong: onChange={debounce(handle, 300)} creates a NEW debounced function each render

// Lodash
import debounce from "lodash/debounce"; import throttle from "lodash/throttle";
debounce(fn, 300, { leading: false, trailing: true, maxWait: 1000 });   // maxWait guarantees a run
throttle(fn, 300, { leading: true, trailing: true });

// Alternatives for high-frequency work
requestAnimationFrame(update);                          // sync to display refresh (~60fps)
window.addEventListener("scroll", fn, { passive: true });   // passive: browser doesn't wait for preventDefault
new IntersectionObserver(cb).observe(el);               // visibility instead of scroll math
  • Debounce vs throttle vs rAF: rAF = at most once per frame, great for visual updates.
  • Always cancel pending timers on unmount (memory leak and state-update-after-unmount).
  • Stale closure: a debounced function created once captures the props/state of that render; read latest values via a ref.
  • Throttle = rate limiting, which also appears server-side (API rate limits, token bucket); debounce is mostly a client concept.
Why doesn't debounce work inside a React component by default?

The component function runs on every render, creating a new debounced function and a new timer closure each time, so previous timers are never cleared. Memoise the debounced function (useMemo/useRef) or debounce the value with a hook.

Write debounce / throttle from scratch (most asked)

See sections 7 and 8: closure holding a timer (debounce) or a flag/timestamp (throttle), apply(this, args), optional leading/trailing and cancel.
