1. What is asynchronous? The event loop (read this first)

  • Synchronous: statements run one after another; each waits for the previous one to finish. Asynchronous: a long-running task (timer, network call, file read) is started, the program keeps going, and the result is handled later when it is ready.
  • JavaScript has one thread (one call stack). It stays responsive because slow work is handed to the environment (browser Web APIs / Node libuv), and the finished callbacks are queued and run by the event loop when the stack is empty.
             +-----------------+      Web APIs (timers, fetch, DOM events) run outside the stack
  code  -->  |   Call Stack    |  <-- runs one function at a time
             +-----------------+
                    ^   when the stack is EMPTY, the event loop picks the next job:
                    |
   1) Microtask queue  : promise .then/.catch/.finally, await continuations, queueMicrotask, MutationObserver
                         -> ALL of it is drained (including newly added microtasks) before anything else
   2) (browser may render here)
   3) Macrotask queue  : setTimeout, setInterval, DOM events, I/O, MessageChannel  -> ONE task per loop turn

Golden rule: run all synchronous code → drain every microtask → (render) → take one macrotask → drain microtasks again → repeat. That is why a resolved promise's .then beats setTimeout(fn, 0).

console.log("A");
setTimeout(() => console.log("B"), 0);          // macrotask
Promise.resolve().then(() => console.log("C")); // microtask
console.log("D");
// A D C B
Traps: setTimeout(fn, 0) does not run immediately: it runs after the current script and all microtasks. A never-ending microtask chain (function f(){ Promise.resolve().then(f) }) freezes the page because macrotasks and rendering never get a turn. Heavy synchronous loops block everything, including timers and clicks. Async does not mean multi-threaded; use Web Workers for CPU-heavy work.
What is an asynchronous process?

A task that is started now and completes later without blocking the main thread. The engine continues executing other code, then runs the task's callback (or resolves its promise) via the event loop once the result is ready, e.g. HTTP requests, timers, file/database access.

Is JavaScript single-threaded? How then is it asynchronous?

Yes, one call stack. Asynchrony comes from the host environment doing the waiting (timers, network) and the event loop feeding completed callbacks back onto the stack one at a time.

Microtask vs macrotask?

Microtasks (promise reactions, await continuations, queueMicrotask) run right after the current task and before the next macrotask; macrotasks (setTimeout, events, I/O) are processed one per loop turn. Microtasks always have priority.

2. Callbacks and callback hell

A callback is a function passed as an argument to another function, to be called later. Callbacks can be synchronous (arr.map(cb), forEach, sort) or asynchronous (setTimeout(cb), event handlers, old Node APIs). Functions are first-class values in JS, which makes this possible.

function greet(name, cb) { cb(`Hello ${name}`) }
greet("Asha", msg => console.log(msg));          // synchronous callback

setTimeout(() => console.log("later"), 1000);    // asynchronous callback

// Node style: error-first callback
fs.readFile("a.txt", (err, data) => { if (err) return handle(err); use(data) });

// CALLBACK HELL / pyramid of doom: each step depends on the previous, nesting grows rightwards
getUser(1, (err, user) => {
  if (err) return handle(err);
  getOrders(user.id, (err, orders) => {
    if (err) return handle(err);
    getItems(orders[0].id, (err, items) => {
      if (err) return handle(err);
      console.log(items);              // hard to read, repeated error handling, hard to extend
    });
  });
});

// Fixed with promises / async-await
getUser(1).then(u => getOrders(u.id)).then(o => getItems(o[0].id)).then(console.log).catch(handle);
try { const u = await getUser(1); const o = await getOrders(u.id); console.log(await getItems(o[0].id)) } catch (e) { handle(e) }
  • Problems with callbacks: deep nesting, duplicated error handling, no return values or try/catch across async boundaries, inversion of control (you trust a third-party function to call your callback once, with the right args), hard to run in parallel.
  • Ways out: name and flatten functions, promises, async/await, modularise.
Trap: try { setTimeout(() => { throw new Error("x") }, 0) } catch (e) {} does not catch: the callback runs later on a fresh stack. A callback invoked both synchronously and asynchronously in different branches ("Zalgo") creates unpredictable order; always be consistently async.
What is a callback function?

A function passed into another function as an argument, which the receiving function invokes later (immediately or after an async operation completes).

What is callback hell / pyramid of doom?

Deeply nested callbacks used to sequence dependent async steps, forming a rightward pyramid that is hard to read, debug and handle errors in. Promises and async/await flatten it.

3. Promise basics

A Promise is an object representing the eventual result of an async operation: a placeholder for a value that will arrive later (or an error).

StateMeaningHow you get there
pending (default)initial, not finishednew Promise(...) just created
fulfilled (resolved successfully)completed with a valueresolve(value)
rejectedfailed with a reasonreject(err) or a thrown error in the executor

Fulfilled or rejected = settled. A promise settles only once; its state and value are then immutable. Further resolve/reject calls are silently ignored.

const p = new Promise((resolve, reject) => {   // executor runs SYNCHRONOUSLY
  setTimeout(() => {
    Math.random() > 0.5 ? resolve("ok") : reject(new Error("fail"));
  }, 1000);
});
console.log(p);                 // Promise { <pending> }

p.then(value => console.log(value))             // runs on fulfil
 .catch(err => console.log(err.message))        // runs on reject (or an error in earlier .then)
 .finally(() => console.log("cleanup"));        // runs either way, receives NO argument

p.then(onFulfilled, onRejected);                // two-arg form: onRejected does NOT catch errors thrown in onFulfilled

Promise.resolve(42);   Promise.reject(new Error("x"));   // already-settled promises
Promise.resolve(somePromise) === somePromise;            // returns the same promise
const sleep = ms => new Promise(r => setTimeout(r, ms)); // promisify a timer
const { promise, resolve, reject } = Promise.withResolvers();   // ES2024: expose resolvers (check support)

How finally behaves

  • Runs on both outcomes for cleanup (hide spinner, close connection). Gets no arguments.
  • Passes the original value/reason through; its return value is ignored. If it throws or returns a rejected promise, that new rejection replaces the result.
Promise.resolve(1).finally(() => 2).then(v => console.log(v));            // 1
Promise.reject("e").finally(() => {}).catch(e => console.log(e));         // "e"
Promise.resolve(1).finally(() => { throw "boom" }).catch(e => console.log(e)); // "boom"
Traps: the executor runs immediately, only then callbacks are async. resolve(x) does not stop the executor (code after it still runs). A promise rejected with no handler triggers unhandledrejection (browser event) / process warning or crash (Node 15+). "Resolved" is not the same as "fulfilled": a promise resolved with another pending promise is "resolved" but still pending. A thenable is any object with a then method, and promises adopt it.
What is a Promise?

An object representing the eventual completion (value) or failure (reason) of an async operation, with then/catch/finally to attach handlers, avoiding callback nesting.

What is the default status? What status after resolve or reject?

Default pending. resolve(v) makes it fulfilled; reject(e) makes it rejected. After that it can never change.

How do you run code at the end of resolve OR reject?

promise.finally(callback). It runs regardless of the outcome and is ideal for cleanup.

What happens if you throw inside the executor or a then?

The promise is rejected with the thrown value; thrown errors inside then reject the promise returned by that then. Errors thrown later in async callbacks (a setTimeout inside the executor) are NOT converted; they become uncaught exceptions.

4. Promise chaining

Every .then() / .catch() / .finally() returns a new promise, so calls can be chained so each step receives the previous step's result. Rules for what the next promise does:

Handler...Next promise
returns a plain valuefulfilled with that value
returns a promiseadopts it (waits, then takes its result or error)
returns nothingfulfilled with undefined
throwsrejected with the error
no handler for that state (e.g. no .catch)passes the value/error along unchanged
fetchUser(1)                          // promise
  .then(user => fetchOrders(user.id)) // return a promise: next step waits for it
  .then(orders => orders.length)      // return a value
  .then(count => { console.log(count) })   // returns undefined
  .catch(err => { console.error(err); return 0 })   // catches ANY earlier failure, then chain continues fulfilled with 0
  .finally(() => hideSpinner());

// common mistakes
p.then(v => { doAsync(v) });          // forgot return: next then gets undefined and doesn't wait
p.then(v => { return doAsync(v) });   // correct
p.then(a => { p2.then(b => use(a, b)) });   // nested again: flatten with return or async/await

Promise.resolve(1).then(2).then(v => console.log(v));   // 1 (non-function arg is ignored; value passes through)

The course output question (traced step by step)

const pr = new Promise((resolve, reject) => {
  resolve("Over");                       // 1. fulfils pr with "Over" immediately
  setTimeout(() => { resolve("Again") }, 2000);   // 4. later: ignored, pr is already settled
});

pr.then(msg => {
  console.log(msg);                      // 2. prints "Over"
  return pr;                             // returns the same, already-fulfilled promise
}).then(msg => {
  console.log(msg);                      // 3. receives "Over" again, prints "Over"
});
// Output:
// Over
// Over

Why: a promise can be settled only once, so resolve("Again") after two seconds does nothing. The second then gets the value of the returned pr, which is still "Over". The two logs appear immediately (microtasks), not after 2 seconds. The timer still runs but has no visible effect.

Trap: a .catch in the middle recovers the chain: later .then handlers run with the catch's return value. To keep failing, rethrow: .catch(e => { log(e); throw e }). Returning a promise from inside then costs extra microtask ticks, which affects ordering puzzles.
What is promise chaining? Syntax?

Sequencing async steps by chaining .then().then().catch().finally(); each returns a new promise whose result is whatever the previous handler returned (or the error it threw). Return a promise from a handler to make the next step wait.

then(a, b) vs then(a).catch(b)?

With then(a, b), b handles only rejections of the original promise, not errors thrown inside a. .then(a).catch(b) also catches errors from a, so it is usually preferred.

5. Promise.all, allSettled, race, any

MethodResolves whenResultRejects when
Promise.allALL fulfilarray of values, in input orderFIRST rejection (fail-fast)
Promise.allSettledALL settle (never rejects)array of {status:"fulfilled", value} or {status:"rejected", reason}never
Promise.raceFIRST settles (win or lose)that valueif the first to settle is a rejection
Promise.anyFIRST fulfilsthat valueALL reject: AggregateError with .errors
const p1 = new Promise(r => setTimeout(() => r("Promise1"), 2000));
const p2 = "Normal string";                       // not a promise
const p3 = new Promise(r => setTimeout(() => r("Promise3"), 2000));

Promise.all([p1, p2, p3]).then(console.log).catch(console.log);
// after ~2s: ["Promise1", "Normal string", "Promise3"]
// Non-promise values are wrapped with Promise.resolve(), so they count as already fulfilled. Order matches input order, not finish order.

Promise.all([]);            // resolves immediately with []
Promise.race([]);           // pending FOREVER
Promise.any([]);            // rejects with AggregateError
Promise.allSettled([]);     // resolves with []

const r = await Promise.allSettled([Promise.resolve(1), Promise.reject("x")]);
// [{status:"fulfilled", value:1}, {status:"rejected", reason:"x"}]
const ok = r.filter(x => x.status === "fulfilled").map(x => x.value);

const obj = Promise.race([]);
console.log(obj);                     // Promise { <pending> }
setTimeout(() => console.log(obj), 2000);   // Promise { <pending> } again: nothing can ever settle it

Handling several promises that may reject

// 1) Need every outcome (batch jobs, dashboard widgets): allSettled
const results = await Promise.allSettled(urls.map(u => fetch(u).then(r => r.json())));

// 2) Want all-or-nothing but with fallbacks: catch per promise so one failure doesn't reject all
const safe = p => p.catch(e => ({ error: e }));
const out = await Promise.all(tasks.map(t => safe(t())));

// 3) Need only the first success (mirrors/CDNs): any
const fastest = await Promise.any([fetch(a), fetch(b)]);

// 4) Fail-fast is fine: all (the others keep running, their results are just ignored; they are not cancelled)
// race for a timeout
const withTimeout = (p, ms) => Promise.race([p, new Promise((_, rej) => setTimeout(() => rej(new Error("Timeout")), ms))]);
Traps: Promise.all rejects with only the first error; later rejections are handled silently (no unhandled warning) but lost. Passing functions or an array of already-started work does not run them in parallel any differently: promises begin when created, all only waits. Promise.race does not cancel the losers. Input must be iterable; passing a non-iterable rejects with TypeError.
Promise.all vs allSettled vs race?

all: waits for all, returns values array, rejects on first failure. allSettled: waits for all, returns status objects, never rejects. race: settles as soon as the first promise settles, with its outcome. (any: first fulfilment.)

What if an element in all() isn't a promise?

It's treated as an already-resolved value, so the code above prints ["Promise1","Normal string","Promise3"] after about 2 seconds.

What is the purpose of race()? What for an empty iterable?

Take whichever settles first: request timeouts, fastest-server selection, cancelling UI waits. Promise.race([]) stays pending forever, so both logs print Promise { <pending> }.

Most efficient way to handle multiple rejected promises?

Use Promise.allSettled to inspect every outcome in one go, or attach .catch to each promise when you want per-item fallbacks while still using Promise.all. For "first success", use Promise.any.

6. async / await

Syntactic sugar over promises that lets async code read like synchronous code.

  • async function always returns a promise. A returned value is wrapped with Promise.resolve; a thrown error becomes a rejection. You do not need to return a promise explicitly.
  • await promise pauses only that function (not the thread), unwraps the fulfilled value, or throws the rejection reason. The rest of the function resumes as a microtask. Awaiting a non-promise just waits one microtask tick.
  • await is only valid inside an async function or at the top level of an ES module (top-level await). Elsewhere it is a SyntaxError.
async function getData() { return 5 }          // same as: return Promise.resolve(5)
getData().then(console.log);                    // 5
async function bad() { throw new Error("x") }   // returns a rejected promise, doesn't throw synchronously

function f() { const x = await g() }            // SyntaxError: await is only valid in async functions
// top-level await: only in <script type="module"> / .mjs
const data = await fetch(url).then(r => r.json());

// async IIFE (the way to use await in a script / immediately)
(async () => {
  const user = await getUser();
  console.log(user);
})();
(async function () { /* ... */ })();           // also fine; ends the same way

// error handling: try/catch/finally
async function load() {
  try {
    const res = await fetch(url);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();                    // `return await` so a rejection is caught HERE
  } catch (err) {
    console.error(err); return null;
  } finally { hideSpinner() }
}
load().catch(handle);                           // alternatively catch on the caller side

// Go-style helper, avoids try/catch blocks everywhere
const to = p => p.then(v => [null, v], e => [e, undefined]);
const [err, user] = await to(getUser());

// parallel with Promise.all + await
const [user2, posts] = await Promise.all([getUser(), getPosts()]);   // both start immediately
const results = await Promise.all(ids.map(id => fetchItem(id)));     // array in parallel

Sequential vs parallel (very common interview trap)

// SLOW: sequential, total = a + b
const a = await fetchA(); const b = await fetchB();
// FAST: start both, then await
const pa = fetchA(), pb = fetchB(); const [a2, b2] = [await pa, await pb];
// or: await Promise.all([fetchA(), fetchB()])

ids.forEach(async id => { await save(id) });     // BUG: forEach ignores the promises, doesn't wait, errors unhandled
for (const id of ids) { await save(id) }          // sequential, waits correctly
await Promise.all(ids.map(save));                 // parallel, waits correctly
for await (const x of asyncIterable) {}           // consuming async iterables (section 10)
Traps: an async function never throws synchronously, it rejects. Forgetting await gives you a pending promise (if (checkUser()) is always truthy). await in a loop is sequential. Without try/catch or .catch, a rejection becomes an unhandled rejection. return promise inside try without await skips the local catch. Awaiting makes the code after it run in a microtask, so it runs after the synchronous code that follows the call.
Explain the functionality of async/await.

async marks a function that returns a promise and allows await; await suspends that function until the promise settles, giving the fulfilled value or throwing the rejection. It makes promise chains read like sequential code and works with try/catch.

Can you write await without async? Do you need to return a promise from an async function?

No to the first (SyntaxError), except top-level await in ES modules. No to the second: return any value and it is auto-wrapped in a promise.

Can you have an async IIFE?

Yes: (async () => { await ...; })();, useful in scripts without top-level await.

Best way to handle errors with await? Promise.all with async/await syntax?

try/catch/finally around the awaits (or .catch() on the async call, or a to() helper). For parallel work: const [a, b] = await Promise.all([p1, p2]), wrapped in try/catch because it rejects if any promise rejects.

How is async/await implemented / what is it equivalent to?

It behaves like a generator driven by promises: each await is like yield and the runner resumes the function with the settled result via .then.

7. Output puzzles (trace like the engine)

Method: (1) run all sync code top to bottom, noting what is queued; (2) run the microtask queue until empty; (3) run one macrotask, then microtasks again.

// Puzzle 1
console.log("1");
setTimeout(() => console.log("2"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("4");
// 1 4 3 2

// Puzzle 2: async/await ordering
async function a() { console.log("a1"); await b(); console.log("a2") }
async function b() { console.log("b") }
console.log("s");
a();
new Promise(r => { console.log("p"); r() }).then(() => console.log("then"));
console.log("e");
// s a1 b p e a2 then
// a() runs synchronously until the first await (a1, b); its continuation (a2) is queued first, "then" second.

// Puzzle 3: two chains interleave
Promise.resolve().then(() => console.log(1)).then(() => console.log(2));
Promise.resolve().then(() => console.log(3)).then(() => console.log(4));
// 1 3 2 4

// Puzzle 4: timers created inside microtasks
setTimeout(() => console.log("timeout1"), 0);
Promise.resolve().then(() => { console.log("micro1"); setTimeout(() => console.log("timeout2"), 0) }).then(() => console.log("micro2"));
// micro1 micro2 timeout1 timeout2

// Puzzle 5: catch recovers
Promise.reject("e").then(() => console.log("a")).catch(e => { console.log(e); return "r" }).then(v => console.log(v));
// e r

// Puzzle 6: executor is synchronous
new Promise(res => { console.log("exec"); res() }); console.log("after");
// exec after

// Puzzle 7: throw in async callback inside executor is NOT caught
new Promise(() => { setTimeout(() => { throw new Error("x") }, 0) }).catch(() => console.log("caught?"));
// Uncaught Error: x   (the promise stays pending; catch never runs)

// Puzzle 8: finally passes through
Promise.resolve("v").finally(() => "ignored").then(console.log);   // v

// Puzzle 9: setTimeout vs setImmediate vs nextTick (Node)
// process.nextTick runs before promise microtasks; setImmediate after I/O phase
Trap: the "extra ticks" rule: returning a promise from a then handler (or async function returning a promise) adds about two extra microtask ticks, so chains that look equal can interleave unexpectedly in puzzles that mix them. Interviewers mostly test the sync → microtask → macrotask order, so master that.

8. AJAX and XMLHttpRequest (XHR)

AJAX = Asynchronous JavaScript And XML: a technique (not a library) for sending requests and receiving data from a server in the background without reloading the page. XML is historical; JSON is the norm. Implemented with XMLHttpRequest (older) or fetch (modern).

const xhr = new XMLHttpRequest();
xhr.open("GET", "https://api.example.com/users/1", true);   // (method, url, async=true); readyState becomes 1
xhr.timeout = 5000;                       // ms, set BEFORE send(); ontimeout fires when exceeded
xhr.responseType = "json";                // "" | "text" | "json" | "blob" | "arraybuffer" | "document" (set before send)
xhr.setRequestHeader("Accept", "application/json");   // after open(), before send()

xhr.onreadystatechange = () => {          // fires on EVERY readyState change
  if (xhr.readyState === 4) {             // DONE
    if (xhr.status >= 200 && xhr.status < 300) console.log(xhr.response);
    else console.error(xhr.status, xhr.statusText);
  }
};
xhr.onload = () => console.log("done", xhr.status, xhr.response);   // request COMPLETED (any HTTP status incl. 404/500)
xhr.onerror = () => console.log("network error");                   // network failure / CORS block
xhr.ontimeout = () => console.log("timed out");
xhr.onabort = () => console.log("aborted");
xhr.onprogress = e => e.lengthComputable && console.log(e.loaded / e.total);
xhr.upload.onprogress = e => {};          // upload progress (fetch can't do this easily)
xhr.send();                               // GET: no body

// POST JSON
const x = new XMLHttpRequest();
x.open("POST", "/api/users");             // 1. open
x.setRequestHeader("Content-Type", "application/json");   // 2. headers
x.send(JSON.stringify({ name: "Asha" })); // 3. send

xhr.abort();                              // force stop: readyState 0, fires "abort" (and "loadend")

// response headers (available from readyState 2)
xhr.getResponseHeader("Content-Type");    // one header, case-insensitive, null if missing
xhr.getAllResponseHeaders();              // one string "name: value\r\n..." (parse by splitting)

readyState values

ValueNameMeaning
0UNSENTobject created, open() not called yet
1OPENEDopen() called, can set headers
2HEADERS_RECEIVEDsend() called, status and headers available
3LOADINGresponse body downloading (responseText partial)
4DONEoperation complete (success or failure)
Traps: setRequestHeader before open() throws InvalidStateError; after send() also throws. "Forbidden" headers (Host, Cookie, Content-Length, Origin...) can't be set by script. load is an event (use onload), and it fires even for 404/500; check status. xhr.readyState === 4 is also reached on errors, with status 0. responseText throws if responseType isn't "" or "text"; use xhr.response. Synchronous XHR (open(..., false)) freezes the UI and is deprecated. Calling abort() after completion does nothing.
What is AJAX?

A technique that lets a page exchange data with a server asynchronously in the background and update parts of the DOM without a full reload, using XHR or fetch (JSON/XML/text payloads).

How do you set a timeout, response format, and force stop?

xhr.timeout = ms (+ ontimeout) before send; xhr.responseType = "json" etc.; xhr.abort() to cancel.

Explain readyState and onreadystatechange.

readyState (0-4) tracks the request lifecycle. onreadystatechange is called every time it changes; typically you act when it is 4 and status is 2xx.

When is the "load" event called?

When the request has completed successfully at the network level and the response has fully arrived (readyState 4), regardless of HTTP status. Failures trigger error, timeout or abort instead; loadend fires after any of them.

How do you set HTTP headers (sequence)? How do you read response headers?

Order: new XMLHttpRequest() → open() → setRequestHeader() (one or more) → send(). Read with getResponseHeader(name) for one or getAllResponseHeaders() for all, once readyState is at least 2.

9. Fetch API

fetch(url, options) is the modern, promise-based replacement for XHR. It returns a Promise<Response> that resolves once headers arrive; the body is read with a second promise-returning method.

// GET
const res = await fetch("/api/users");
if (!res.ok) throw new Error(`HTTP ${res.status}`);   // fetch does NOT reject on 404/500!
const users = await res.json();                       // .text() .blob() .arrayBuffer() .formData() .json()

// POST JSON
await fetch("/api/users", {
  method: "POST",
  headers: { "Content-Type": "application/json", Authorization: `Bearer ${token}` },
  body: JSON.stringify({ name: "Asha" })              // body must be a string / FormData / Blob / URLSearchParams
});

// DELETE
const del = await fetch(`/api/users/${id}`, { method: "DELETE" });
if (del.status === 204 || del.ok) console.log("deleted");   // often 204 No Content: don't call .json() on an empty body
// PUT / PATCH are the same with method and body

// FormData upload (do NOT set Content-Type; the browser adds the multipart boundary)
const fd = new FormData(); fd.append("file", input.files[0]);
await fetch("/upload", { method: "POST", body: fd });

// cancel and timeout
const ctrl = new AbortController();
fetch(url, { signal: ctrl.signal }).catch(e => e.name === "AbortError" && console.log("aborted"));
ctrl.abort();
fetch(url, { signal: AbortSignal.timeout(5000) });    // reject with TimeoutError after 5s

// cookies / CORS options
fetch(url, { credentials: "include", mode: "cors", cache: "no-store" });

// Response details
res.status; res.statusText; res.ok; res.headers.get("content-type"); res.url; res.redirected;
const copy = res.clone();                             // a body can be read only ONCE

// reusable wrapper
async function api(path, opts = {}) {
  const r = await fetch(path, { headers: { "Content-Type": "application/json" }, ...opts });
  if (!r.ok) { const e = new Error(r.statusText); e.status = r.status; e.body = await r.text(); throw e }
  return r.status === 204 ? null : r.json();
}

Explain the functionality of the fetch API.

It performs network requests and returns a promise that resolves with a Response object once headers arrive (even for HTTP error statuses). You check ok/status and then read the body with json()/text()/blob(), each of which returns another promise. It supports options for method, headers, body, credentials, CORS, caching and cancellation via AbortController.

How do you make a DELETE request?

fetch(url, { method: "DELETE" }), optionally with headers; check res.ok (often status 204 with no body).

Why doesn't fetch reject on 404?

Because the request itself succeeded at the HTTP level: the server answered. Only network-level failures reject, so you must test response.ok yourself.

fetch vs axios?

Axios auto-parses JSON, rejects on non-2xx, has interceptors, timeouts, upload progress and works in Node/older browsers; fetch is built in, zero dependency, streams, but needs a small wrapper for the same conveniences.

10. Async iterators and async generators

  • Iterable (sync) has [Symbol.iterator]() returning { next() } with { value, done }.
  • Async iterable has [Symbol.asyncIterator]() returning an iterator whose next() returns a Promise of { value, done }. Consume it with for await...of (inside an async function or module top level).
  • Symbol.asyncIterator is the well-known symbol that tells the language "this object can be iterated asynchronously", for data that arrives over time: paginated APIs, streams, WebSocket messages, file chunks.
// manual async iterable
const feed = {
  from: 1, to: 3,
  [Symbol.asyncIterator]() {
    let cur = this.from, end = this.to;
    return {
      async next() {
        await new Promise(r => setTimeout(r, 500));                 // simulate async wait
        return cur <= end ? { value: cur++, done: false } : { value: undefined, done: true };
      }
    };
  }
};
(async () => { for await (const n of feed) console.log(n) })();      // 1, 2, 3 (each after 500ms)

// the same with an ASYNC GENERATOR: far shorter
async function* feed2(from, to) {
  for (let i = from; i <= to; i++) { await sleep(500); yield i }
}
for await (const n of feed2(1, 3)) console.log(n);
const gen = feed2(1, 3); await gen.next();   // {value:1, done:false}  (Promise-returning)

// as an object method
const obj = { async *[Symbol.asyncIterator]() { yield 1; yield 2 } };

// paginated API
async function* pages(url) {
  while (url) {
    const r = await fetch(url).then(r => r.json());
    yield* r.items;                  // yield* works with (async) iterables
    url = r.next;
  }
}
for await (const item of pages("/api/items?page=1")) { if (item.id === 42) break }  // break stops fetching more pages (calls return())

// streams
for await (const chunk of response.body) { /* Uint8Array chunks (supported in modern browsers; Node streams too) */ }

// spread does NOT work with async iterables
[...obj];                            // TypeError: obj is not iterable (spread looks for Symbol.iterator only)
const out = []; for await (const v of obj) out.push(v);   // collect manually
const arr = await Array.fromAsync(obj);                    // newer engines; check support
// for await also accepts sync iterables of promises:
for await (const v of [Promise.resolve(1), 2]) console.log(v);   // 1, 2
Traps: for...of over an async iterable throws "not iterable"; use for await. for await processes items one at a time (sequential); use Promise.all for parallel work on known promises. An async generator's next() calls are queued, so concurrent calls are served in order. A break/return/throw inside for await triggers the iterator's return() for cleanup. Use try/finally inside generators to release resources.
What is Symbol.asyncIterator?

A built-in symbol identifying the method that returns an async iterator; objects having it can be consumed with for await...of. Its iterator's next() returns a promise resolving to { value, done }.

Can we use the spread operator with an async iterator, e.g. [...obj]?

No. Spread and array destructuring use Symbol.iterator synchronously and will throw a TypeError. Use for await to collect into an array (or Array.fromAsync where supported).

How do you handle an async iterator using generator syntax?

Declare async function* (or async *[Symbol.asyncIterator]()), use await and yield inside, and consume with for await...of. The generator automatically implements the async iterator protocol.

11. Coding patterns interviewers ask you to write

// 1) Promise.all polyfill
function myAll(promises) {
  return new Promise((resolve, reject) => {
    const results = []; let done = 0;
    if (!promises.length) return resolve(results);
    promises.forEach((p, i) => {
      Promise.resolve(p).then(v => { results[i] = v; if (++done === promises.length) resolve(results) }, reject);
    });
  });
}

// 2) Promise.race / allSettled sketches
const myRace = ps => new Promise((res, rej) => ps.forEach(p => Promise.resolve(p).then(res, rej)));
const mySettled = ps => Promise.all(ps.map(p => Promise.resolve(p).then(value => ({ status: "fulfilled", value }), reason => ({ status: "rejected", reason }))));

// 3) Retry with backoff
async function retry(fn, tries = 3, delay = 300) {
  for (let i = 0; i < tries; i++) {
    try { return await fn() } catch (e) { if (i === tries - 1) throw e; await sleep(delay * 2 ** i) }
  }
}

// 4) Timeout wrapper (race) and promisify
const timeout = (p, ms) => Promise.race([p, new Promise((_, r) => setTimeout(() => r(new Error("timeout")), ms))]);
const promisify = fn => (...args) => new Promise((res, rej) => fn(...args, (err, data) => err ? rej(err) : res(data)));

// 5) Run promises sequentially
async function sequence(tasks) { const out = []; for (const t of tasks) out.push(await t()); return out }
tasks.reduce((chain, t) => chain.then(t), Promise.resolve());   // reduce version

// 6) Concurrency limit (pool of N)
async function pool(tasks, limit) {
  const results = []; let i = 0;
  const worker = async () => { while (i < tasks.length) { const idx = i++; results[idx] = await tasks[idx]() } };
  await Promise.all(Array.from({ length: limit }, worker));
  return results;
}

// 7) Debounced async search that ignores stale responses
let latest = 0;
async function search(q) { const id = ++latest; const r = await fetch(`/s?q=${q}`).then(r => r.json()); if (id === latest) render(r) }

// 8) Cancel previous request
let ctrl; async function load(q) { ctrl?.abort(); ctrl = new AbortController(); return fetch(`/s?q=${q}`, { signal: ctrl.signal }) }

// 9) Implement a mini Promise (core idea): state, value, handlers[], then returns new Promise, handlers run via queueMicrotask
const sleep = ms => new Promise(r => setTimeout(r, ms));
How do you run tasks one by one vs in parallel vs with a limit?

Sequential: for...of with await (or reduce chain). Parallel: Promise.all(tasks.map(fn)). Limited concurrency: a worker pool pulling from a shared index (pattern 6) or a library like p-limit.

How do you avoid race conditions in async UI code?

Cancel the previous request (AbortController) or tag each request with an id and ignore responses that are not the latest; debounce user input.

What is an unhandled promise rejection?

A rejected promise without any handler by the time the microtask queue drains. Browsers fire unhandledrejection on window; Node 15+ terminates the process by default. Always end chains with .catch or use try/catch around await.
