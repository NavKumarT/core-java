Foundations

Process vs Thread — The Foundation

Understanding the difference between a process and a thread is where every concurrency interview starts. Get this framing wrong and everything downstream suffers.

AspectProcessThread
DefinitionIndependent program in execution with its own memory spaceLightweight unit of execution within a process
MemoryOwn heap, stack, code, data segments — fully isolatedShares heap & code with other threads; own stack only
CommunicationIPC — pipes, sockets, shared memory (expensive)Shared memory directly — fast but needs synchronization
Context switchExpensive — full memory map switchCheap — only stack & registers change
Creation costHigh — OS allocates full address spaceLow — shares parent process resources
Failure isolationStrong — one crash doesn't kill othersWeak — one thread crash can kill the JVM
ExampleChrome browser (each tab is a process)Chrome tab (JS engine, renderer, network — threads)

Why Multithreading?

Benefits
  • Better CPU utilisation — don't waste cores while I/O waits
  • Responsiveness — UI thread stays alive while background work runs
  • Throughput — multiple requests handled simultaneously (web servers)
  • Resource sharing — threads share heap, reducing memory overhead
Risks
  • Race conditions — unsynchronised access to shared data
  • Deadlock — threads waiting for each other's locks forever
  • Complexity — hard to debug, reproduce, and test
  • Overhead — context switching, synchronization cost

JVM Memory Model (JMM) — why it matters

The Java Memory Model defines how threads interact through memory. Each thread has its own working copy of shared variables (in CPU cache). Without proper synchronization, one thread's changes may never be visible to another — leading to bugs that don't reproduce easily.

JMM visibility problem — and the fix 
// WITHOUT synchronization — flag may stay true in thread's local cache
class UnsafeStop {
    static boolean flag = false; // shared variable — NOT volatile

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            while (!flag) { // may NEVER see flag=true — reading stale cache value
                // spin
            }
            System.out.println("Stopped");
        });
        worker.start();
        Thread.sleep(100);
        flag = true; // main thread writes — worker may never see it
    }
}

// FIX: declare flag as volatile — forces reads/writes to main memory
static volatile boolean flag = false; // now guaranteed visible across threads
💡 Interview answer: "The JMM guarantees happens-before relationships. A write to a volatile variable happens-before every subsequent read of that variable. synchronized blocks also establish happens-before — exit of a synchronized block happens-before entry of any subsequent synchronized block on the same monitor."

Thread States — All 6

Java defines 6 thread states in Thread.State. Knowing the exact transitions and what causes each state is a guaranteed interview question at every product company.

⚠️
Critical interview distinction — BLOCKED vs WAITING: BLOCKED means waiting for a lock (synchronized keyword). WAITING means voluntarily pausing execution via wait() or join(). BLOCKED is about lock contention; WAITING is about inter-thread coordination. This distinction separates candidates who've just read about threading from those who've used it.
💡 Interview answer: "A thread in BLOCKED state is held outside a synchronized block because another thread owns the monitor. A thread in WAITING state has voluntarily given up the CPU and is waiting for an explicit notification — it called wait() and is inside a synchronized block, which it has temporarily released."

class JoinDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            System.out.println("T1 start");
            try { Thread.sleep(500); } catch (InterruptedException e) {}
            System.out.println("T1 done");
        });
        Thread t2 = new Thread(() -> System.out.println("T2 done"));

        t1.start();
        t2.start();
        t1.join(); // main thread waits for T1 to finish
        t2.join(); // then waits for T2
        System.out.println("Both threads done — main continues");
    }
}
// Output guaranteed: T1 start, T1 done, then "Both threads done"
// T2 may interleave with T1, but main always waits for both
// Proper interrupt handling pattern — cooperative cancellation
class CancellableTask implements Runnable {
    @Override
    public void run() {
        while (!Thread.currentThread().isInterrupted()) {
            try {
                System.out.println("Working...");
                Thread.sleep(100); // InterruptedException if interrupted during sleep
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt(); // RESTORE interrupted flag
                System.out.println("Task cancelled cleanly");
                break; // exit loop
            }
        }
    }
}

Thread t = new Thread(new CancellableTask());
t.start();
Thread.sleep(350);
t.interrupt(); // signal thread to stop

// RULE: When you catch InterruptedException, always restore the flag:
// Thread.currentThread().interrupt();
// Otherwise the interrupt signal is SWALLOWED and callers can't detect it
// Daemon threads — background service threads that die when ALL non-daemon threads end
class LogFlusher implements Runnable {
    public void run() {
        while (true) {
            System.out.println("Flushing logs...");
            try { Thread.sleep(1000); } catch (InterruptedException e) { break; }
        }
    }
}

Thread logger = new Thread(new LogFlusher());
logger.setDaemon(true); // MUST set before start()
logger.start();          // runs in background

System.out.println("Main work done");
// When main exits: logger daemon thread AUTOMATICALLY KILLED
// No need to join() or stop() daemon threads

// Trap: logger.setDaemon(true) AFTER logger.start() → IllegalThreadStateException
System.out.println(logger.isDaemon()); // true
Scheduling

Thread Priority

Thread priority is a hint to the OS scheduler — not a guarantee. Understand what it means and exactly what it doesn't mean.

Priority Rules
  • Range: 1 (MIN) to 10 (MAX), default 5 (NORM)
  • Child thread inherits parent's priority
  • setPriority() must be valid 1–10 else IllegalArgumentException
  • Higher priority threads get more CPU time — not exclusive CPU
  • Priority is OS/JVM dependent — not portable across platforms
  • Never use priority for correctness — only for performance tuning hints
Constants
  • Thread.MIN_PRIORITY = 1
  • Thread.NORM_PRIORITY = 5 (default)
  • Thread.MAX_PRIORITY = 10
  • Main thread: NORM_PRIORITY (5)
  • GC thread: typically low priority
Thread priority complete demo 
Thread low  = new Thread(() -> System.out.println("Low priority"));
Thread high = new Thread(() -> System.out.println("High priority"));

low.setPriority(Thread.MIN_PRIORITY);  // 1
high.setPriority(Thread.MAX_PRIORITY); // 10

System.out.println(low.getPriority());  // 1
System.out.println(high.getPriority()); // 10

low.start();
high.start();
// Output order NOT guaranteed — priority is only a hint to scheduler

// Get current thread priority
Thread.currentThread().getPriority();  // 5 in main thread

// setPriority(0) or setPriority(11) → IllegalArgumentException at runtime
💡 Interview answer: "Thread priority is a hint to the thread scheduler, not a guarantee. On Linux, Java thread priorities may be ignored entirely. Never write code that depends on priority for correctness — use proper synchronization instead. Priority is only appropriate for performance tuning where you want background tasks to yield CPU to foreground work."
Synchronization

Race Conditions, Mutex & Synchronization

The most critical concurrency topic. A race condition happens when the correctness of a program depends on the relative timing of thread execution. Synchronization enforces mutual exclusion to prevent it.

Race Condition — demonstrated

❌ Race Condition
✅ Synchronized Fix
class Counter {
    private int count = 0;
    public void increment() { count++; } // NOT atomic! 3 steps: read → modify → write
    public int  getCount()  { return count; }
}

Counter c = new Counter();
Runnable task = () -> { for (int i = 0; i < 1000; i++) c.increment(); };

Thread t1 = new Thread(task);
Thread t2 = new Thread(task);
t1.start(); t2.start();
t1.join();  t2.join();

System.out.println(c.getCount()); // Expected 2000 — actual: 1847 or 1923 or...
// T1 reads count=500, T2 reads count=500 simultaneously
// Both write 501 — one increment is LOST
class Counter {
    private int count = 0;

    // synchronized method — only ONE thread can execute this at a time
    public synchronized void increment() { count++; }
    public synchronized int  getCount()  { return count; }
}

// OR: synchronized block — finer-grained, preferred
class Counter {
    private int count = 0;
    private final Object lock = new Object(); // dedicated lock object

    public void increment() {
        synchronized (lock) { count++; } // lock scope is minimal — better performance
    }
    public int getCount() {
        synchronized (lock) { return count; }
    }
}
// Now: always prints 2000 — atomic read-modify-write guaranteed

synchronized — block vs method vs static

All forms of synchronized 
class SyncForms {
    private int instanceCount = 0;
    private static int staticCount = 0;

    // 1. Synchronized instance method — locks on 'this' (the instance)
    public synchronized void instanceMethod() {
        instanceCount++; // lock: this object
    }

    // 2. Synchronized block — same as above but with explicit scope control
    public void instanceBlock() {
        // non-critical code here (runs without lock)
        synchronized (this) {
            instanceCount++; // only critical section is locked
        }
        // non-critical code here (runs without lock)
    }

    // 3. Static synchronized method — locks on CLASS object (SyncForms.class)
    public static synchronized void staticMethod() {
        staticCount++; // lock: SyncForms.class — shared across ALL instances
    }

    // 4. Synchronized block on class — equivalent to static synchronized method
    public static void staticBlock() {
        synchronized (SyncForms.class) {
            staticCount++;
        }
    }

    // 5. Synchronized on different object — different lock, independent
    private final Object lock1 = new Object();
    private final Object lock2 = new Object();
    public void methodA() { synchronized(lock1) { /* ... */ } }
    public void methodB() { synchronized(lock2) { /* ... */ } }
    // methodA and methodB can run concurrently — different locks!
}

Monitor — the Java synchronization model

1
Every Java object has a built-in monitor (also called intrinsic lock or mutex). When a thread enters a synchronized block/method, it acquires the monitor of the lock object.
2
While a thread holds the monitor, no other thread can enter any synchronized block/method that uses the same monitor — they become BLOCKED.
3
Java monitors are reentrant — a thread that already holds a lock can re-enter synchronized methods on the same object without deadlocking itself.
4
When the synchronized block exits (normally or via exception), the lock is automatically released — guaranteed, even if an exception is thrown.
Reentrant locking — monitors are reentrant by design 
class ReentrantDemo {
    public synchronized void outer() {
        System.out.println("outer — holds lock");
        inner(); // calls another synchronized method on same object
    }
    public synchronized void inner() {
        System.out.println("inner — re-acquires same lock"); // no deadlock
    }
}
// Works fine — the thread already owns the lock, so it can re-enter
// Lock count: outer() increments to 1, inner() increments to 2
// inner() returns → count back to 1; outer() returns → count 0 → released
⚠️
Interview trap — synchronizing on wrong object: Synchronizing on a String literal is dangerous because string literals are interned — two completely unrelated classes synchronizing on "lock" would block each other. Always use a dedicated private final Object lock = new Object(). Similarly, never synchronize on an Integer or autoboxed value — the cached Integer objects (-128 to 127) are shared!
Memory Visibility

volatile keyword

volatile is the lightweight synchronization tool — it guarantees visibility but NOT atomicity. Understanding this distinction is a FAANG-level question.

What volatile guarantees
  • Visibility — writes to volatile variable are immediately visible to all threads (flushes to main memory)
  • No caching — threads always read from main memory, not CPU cache
  • Prevents instruction reordering around the volatile access
  • Reading/writing a long or double is atomic when volatile
What volatile does NOT guarantee
  • Atomicity of compound operations — count++ is still 3 steps
  • Mutual exclusion — multiple threads can execute concurrently
  • Cannot replace synchronized for read-modify-write operations
Stop flag (correct use)
Wrong use — count++ trap
DCL Singleton (volatile)
// CORRECT: volatile for a simple flag that one thread writes, others read
class Worker implements Runnable {
    private volatile boolean running = true; // volatile: guaranteed visible

    public void stop() { running = false; } // called by another thread

    public void run() {
        while (running) {        // always reads from main memory — sees stop()
            doWork();
        }
        System.out.println("Stopped cleanly");
    }
}

// If multiple threads wrote 'running', you'd need synchronized
// WRONG: volatile does NOT fix the race in count++
class BrokenCounter {
    volatile int count = 0;

                                  // volatile ensures each step sees latest value
                                  // but steps are NOT atomic as a unit
}

// T1: READ count=5, T2: READ count=5 (both see same value due to volatile)
// T1: WRITE 6,      T2: WRITE 6  — one increment STILL LOST

// volatile is CRITICAL in Double-Checked Locking Singleton
class Singleton {
    private static volatile Singleton instance; // volatile REQUIRED

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {           // 1st check — no lock
            synchronized (Singleton.class) {
                if (instance == null) {   // 2nd check — inside lock
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
// WHY volatile here:
// new Singleton() = 3 steps: allocate memory → initialise fields → assign to instance
// JVM can reorder to: allocate → assign → initialise (steps 2 and 3 swapped)
// Without volatile: Thread 2 sees non-null instance but uninitialised object
// volatile prevents this reordering → safe publication of the object
💡 Interview answer — volatile vs synchronized: "volatile guarantees visibility and prevents reordering — it's cheap (no locking). synchronized guarantees visibility AND atomicity (mutual exclusion) — it's heavier. Use volatile for simple flags with single writer. Use synchronized or AtomicXxx for compound operations like increment. Never use volatile as a replacement for synchronized when you need read-modify-write atomicity."
Coordination

Inter-Thread Communication

wait(), notify(), and notifyAll() are the primitive tools for threads to coordinate. They only work inside synchronized blocks — calling them outside throws IllegalMonitorStateException.

wait / notify rules — critical

wait() behaviour
  • Must be called from inside synchronized block on the same object
  • Releases the monitor lock and suspends the thread (→ WAITING state)
  • Thread is placed in the object's wait set
  • Re-acquires the lock before returning from wait()
  • Always call wait() inside a while loop — not if — (spurious wakeups)
notify() vs notifyAll()
  • notify() — wakes ONE arbitrary waiting thread
  • notifyAll() — wakes ALL waiting threads; they compete for the lock
  • Woken thread re-checks condition in the while loop
  • Prefer notifyAll() unless you know exactly which thread to wake
  • notify() risks leaving threads stuck if wrong thread wakes

Producer-Consumer — the classic example

Using wait/notify
Using BlockingQueue (preferred)
Using ReentrantLock + Condition
class SharedBuffer {
    private Queue<Integer> buffer = new LinkedList<>();
    private final int CAPACITY = 5;

    public synchronized void produce(int item) throws InterruptedException {
        while (buffer.size() == CAPACITY) { // while NOT if — spurious wakeup safe
            System.out.println("Buffer full — producer waiting");
            wait(); // releases lock; consumer can now enter
        }
        buffer.add(item);
        System.out.println("Produced: " + item);
        notifyAll(); // wake all — consumers and other producers check condition
    }

    public synchronized int consume() throws InterruptedException {
        while (buffer.isEmpty()) {     // while NOT if
            System.out.println("Buffer empty — consumer waiting");
            wait(); // releases lock; producer can now enter
        }
        int item = buffer.poll();
        System.out.println("Consumed: " + item);
        notifyAll(); // wake producers waiting on full buffer
        return item;
    }
}
// BlockingQueue — the production way; handles wait/notify internally
import java.util.concurrent.*;

class ProducerConsumerWithQueue {
    private final BlockingQueue<Integer> queue =
        new ArrayBlockingQueue<>(5); // bounded — blocks on full/empty

    class Producer implements Runnable {
        public void run() {
            try {
                for (int i = 0; i < 10; i++) {
                    queue.put(i); // BLOCKS if queue full — no manual wait() needed
                    System.out.println("Produced: " + i);
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }
    }

    class Consumer implements Runnable {
        public void run() {
            try {
                for (int i = 0; i < 10; i++) {
                    int item = queue.take(); // BLOCKS if queue empty — no manual wait()
                    System.out.println("Consumed: " + item);
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }
    }
}
// Other BlockingQueue implementations:
// LinkedBlockingQueue — optionally bounded, higher throughput
// PriorityBlockingQueue — elements ordered by priority
// SynchronousQueue — zero capacity; each put() blocks until take()
// ReentrantLock + Condition — more flexible than synchronized + wait/notify
import java.util.concurrent.locks.*;

class BoundedBuffer<T> {
    private final Queue<T> items = new LinkedList<>();
    private final int capacity;
    private final Lock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition(); // separate conditions
    private final Condition notEmpty = lock.newCondition(); // precise wakeup

    BoundedBuffer(int capacity) { this.capacity = capacity; }

    public void put(T item) throws InterruptedException {
        lock.lock();
        try {
            while (items.size() == capacity) notFull.await();
            items.add(item);
            notEmpty.signal(); // wake ONLY consumers — precise, unlike notifyAll()
        } finally { lock.unlock(); } // always unlock in finally
    }

    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (items.isEmpty()) notEmpty.await();
            T item = items.poll();
            notFull.signal(); // wake ONLY producers
            return item;
        } finally { lock.unlock(); }
    }
}
⚠️
Spurious wakeup — always use while, never if: The JVM spec allows threads to wake from wait() without being notified — called a spurious wakeup. If you use if (!condition) wait() and a spurious wakeup occurs, the thread proceeds without the condition being true. Always use while (!condition) wait().

import java.util.concurrent.locks.*;

class SafeCounter {
    private int count = 0;
    private final ReentrantLock lock = new ReentrantLock();

    public void increment() {
        lock.lock();              // acquire — blocks until available
        try {
            count++;
        } finally {
            lock.unlock();       // ALWAYS in finally — ensures release on exception
        }
    }

    public int getCount() {
        lock.lock();
        try { return count; }
        finally { lock.unlock(); }
    }

    // Reentrant — same thread can lock again without deadlocking
    public void doubleIncrement() {
        lock.lock();
        try {
            increment(); // inner lock.lock() — count is now 2 (reentrant)
            increment();
        } finally { lock.unlock(); }
    }

    public int getHoldCount() { return lock.getHoldCount(); } // how deep we're nested
}

class AccountTransfer {
    private final ReentrantLock lock = new ReentrantLock();
    private double balance;

    public boolean transfer(AccountTransfer target, double amount)
            throws InterruptedException {

        // Try to acquire both locks with timeout — avoids deadlock
        boolean gotThis   = this.lock.tryLock(50, TimeUnit.MILLISECONDS);
        boolean gotTarget = false;
        if (gotThis) {
            try {
                gotTarget = target.lock.tryLock(50, TimeUnit.MILLISECONDS);
                if (gotTarget) {
                    try {
                        this.balance   -= amount;
                        target.balance += amount;
                        return true;
                    } finally { target.lock.unlock(); }
                }
            } finally { this.lock.unlock(); }
        }
        return false; // couldn't get both locks — retry later
    }
}

// lockInterruptibly() — can be cancelled via thread.interrupt()
try {
    lock.lockInterruptibly(); // throws InterruptedException if interrupted while waiting
    try { /* critical section */ }

    Thread.currentThread().interrupt(); // restore flag

// ReadWriteLock — multiple readers OR one writer; readers don't block each other
class CachedData {
    private Map<String, String> cache = new HashMap<>();
    private final ReadWriteLock rwLock = new ReentrantReadWriteLock();
    private final Lock readLock  = rwLock.readLock();
    private final Lock writeLock = rwLock.writeLock();

    public String get(String key) {
        readLock.lock();              // many readers can hold simultaneously
        try { return cache.get(key); }
        finally { readLock.unlock(); }
    }

    public void put(String key, String value) {
        writeLock.lock();             // exclusive — blocks ALL readers and writers
        try { cache.put(key, value); }
        finally { writeLock.unlock(); }
    }
}
// Read/Write lock rules:
// Multiple threads can hold readLock simultaneously
// writeLock is exclusive — no readers or other writers
// Perfect for: read-heavy caches, config stores, lookup tables
// StampedLock (Java 8+) — adds optimistic read mode for even better performance
import java.util.concurrent.locks.StampedLock;

class Point {
    private double x, y;
    private final StampedLock sl = new StampedLock();

    void move(double dx, double dy) {
        long stamp = sl.writeLock();
        try { x += dx; y += dy; }
        finally { sl.unlockWrite(stamp); }
    }

    double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead(); // NO lock acquired — very fast
        double curX = x, curY = y;
        if (!sl.validate(stamp)) {            // check if write happened during our read
            stamp = sl.readLock();            // fall back to real read lock
            try { curX = x; curY = y; }
            finally { sl.unlockRead(stamp); }
        }
        return Math.sqrt(curX*curX + curY*curY);
    }
}
// Optimistic read: try without lock → if no write, use values directly (fastest)
// If write detected: fall back to readLock → safe but slower
// Note: StampedLock is NOT reentrant — causes deadlock if same thread tries to reacquire

Atomic Classes & CAS

Atomic classes in java.util.concurrent.atomic provide thread-safe operations without locks, using Compare-And-Swap (CAS) hardware instructions. Faster than synchronized for simple counters and flags.

How CAS works

1
Read the current value V from memory
2
Compute new value N based on V
3
Atomically: if memory still == V, write N; else retry from step 1 — this is the CAS operation, done in hardware in a single CPU instruction

// ABA Problem — CAS weakness
// Thread 1 reads value A
// Thread 2 changes A → B → A  (back to original value)
// Thread 1 does CAS: sees A, thinks nothing changed → WRONG

// Example: lock-free stack
// T1 reads top=Node(A) → next=Node(B)
// T2 pops A, pops B, pushes A back (A is now recycled/reused)
// T1 CAS succeeds: top still looks like A, but B is GONE from the list
// T1 sets top.next to old B → memory corruption

// CountDownLatch — one or more threads WAIT until N countdowns happen
import java.util.concurrent.CountDownLatch;

class ServiceStartup {
    public static void main(String[] args) throws InterruptedException {
        CountDownLatch latch = new CountDownLatch(3); // wait for 3 services

        for (String service : new String[]{"DB", "Cache", "MQ"}) {
            new Thread(() -> {
                System.out.println(service + " starting...");
                try { Thread.sleep((long)(Math.random()*1000)); }
                catch (InterruptedException e) {}
                System.out.println(service + " ready");
                latch.countDown(); // decrement counter by 1
            }).start();
        }

        System.out.println("App waiting for all services...");
        latch.await();              // BLOCKS until count reaches 0
        // latch.await(5, TimeUnit.SECONDS); // with timeout
        System.out.println("All services ready — starting app server");
    }
}
// CANNOT be reset — single use only
// countDown() never blocks — just decrements
// await() blocks until count == 0
// Multiple threads can await() simultaneously
// CyclicBarrier — ALL N threads wait at the barrier before any proceeds
import java.util.concurrent.CyclicBarrier;

class ParallelMergeSort {
    static CyclicBarrier barrier = new CyclicBarrier(3,
        () -> System.out.println("=== All workers done phase — merging ===")
        // barrierAction runs once all threads arrive (on last arriving thread)
    );

    static void worker(int id) throws Exception {
        for (int phase = 1; phase <= 3; phase++) {
            System.out.println("Worker "+id+" doing phase "+phase);
            Thread.sleep((long)(Math.random() * 500));
            barrier.await(); // wait for ALL workers to finish this phase
            // After all arrive: barrier resets, ALL proceed to next phase
        }
    }

    public static void main(String[] args) throws Exception {
        for (int i = 1; i <= 3; i++) {
            final int id = i;
            new Thread(() -> {
                try { worker(id); } catch (Exception e) {}
            }).start();
        }
    }
}

import java.util.concurrent.Exchanger;

class PipelineDemo {
    public static void main(String[] args) {
        Exchanger<String> exchanger = new Exchanger<>();

        Thread producer = new Thread(() -> {
            try {
                String data = "batch-1";
                System.out.println("Producer sending: " + data);
                String ack = exchanger.exchange(data); // blocks until consumer arrives
                System.out.println("Producer received ack: " + ack);
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });

        Thread consumer = new Thread(() -> {
            try {
                String received = exchanger.exchange("ack-ok"); // blocks until producer arrives
                System.out.println("Consumer got: " + received);
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });

        producer.start(); consumer.start();
    }
}
// Both threads block at exchange() until both arrive → swap happens → both continue
// CountDownLatch vs CyclicBarrier — key differences
//
// CountDownLatch:
// - count() calls and await() callers are DIFFERENT threads (usually)
// - Main thread awaits; worker threads countDown()
// - Non-reusable — once count reaches 0, stays 0
// - countDown() NEVER blocks
// - Use: wait for N events (service startups, test setup, async results)
//
// CyclicBarrier:
// - ALL threads call await() and ALL wait for each other
// - Reusable — auto-resets after all arrive
// - Optional barrierAction runs when all arrive
// - BrokenBarrierException if any thread is interrupted
// - Use: divide work into parallel phases (MapReduce, parallel simulations)
//
// Semaphore:
// - Not a barrier — controls concurrent ACCESS count
// - Can be released by different thread than acquired
// - Use: rate limiting, resource pools, throttling concurrent operations

Concurrency Problems

Deadlock, Livelock & Starvation

The three cardinal sins of concurrent programming. Interviewers at FAANG companies will ask you to identify, explain, and fix all three — often with code.

Deadlock — 4 Coffman Conditions

A deadlock requires ALL four conditions simultaneously. Remove any one and deadlock cannot occur.

4 Coffman Conditions
  • Mutual Exclusion — at least one resource is held exclusively
  • Hold and Wait — threads hold some resources while waiting for others
  • No Preemption — resources can't be forcibly taken; must be released voluntarily
  • Circular Wait — T1 waits for T2, T2 waits for T1 (cycle in wait graph)
Prevention strategies
  • Lock ordering — always acquire locks in the same global order (breaks circular wait)
  • tryLock with timeout — if can't get all locks, release all and retry (breaks hold-and-wait)
  • Lock all at once — acquire all needed locks atomically if possible
  • Use higher-level abstractions — BlockingQueue, Semaphore eliminate manual locking

These are the questions that separate candidates who've read about threading from those who've thought deeply about it. Every one has appeared in product company interviews.

class MyThread extends Thread {
    public void run() {
        System.out.println(Thread.currentThread().getName());
    }
}
MyThread t = new MyThread();
t.run();   // prints: "main"   ← runs on CURRENT thread, no new thread
t.start(); // prints: "Thread-0" ← new OS thread created, run() on it

// ANSWER: run() is just a normal method call. start() is the magic.
// The JVM creates a new thread stack only when start() is called.
class Demo {
    public synchronized void        instanceMethod() { sleep(1000); }
    public static synchronized void staticMethod()   { sleep(1000); }
}
Demo d = new Demo();

// Q: Can instanceMethod() and staticMethod() run concurrently?
// A: YES! They use DIFFERENT locks.
//    instanceMethod() locks on: d (the instance)
//    staticMethod()   locks on: Demo.class (the Class object)
// These are completely independent monitors → no mutual exclusion between them

// Q: Can TWO instances' instanceMethods run concurrently?
// A: YES! Each instance has its own monitor.
// Demo d1 = new Demo(); Demo d2 = new Demo();
// d1.instanceMethod() and d2.instanceMethod() run concurrently (different locks)
// Q: What happens when you call wait() outside synchronized?
class Test {
    public static void main(String[] args) throws InterruptedException {
        Object obj = new Object();
        obj.wait(); // ← runtime exception, not compile error!
    }
}
// A: Throws IllegalMonitorStateException at RUNTIME
// wait(), notify(), notifyAll() MUST be called on an object while
// holding that object's monitor (inside synchronized block on same object)

// Same for notify() outside synchronized → IllegalMonitorStateException

// CORRECT pattern:
synchronized (obj) {
    obj.wait();    // ✓ holding obj's monitor
    obj.notify(); // ✓ same
}
// Q: Does sleep() release the lock?
// A: NO — this is one of the most asked interview questions
class LockTest {
    synchronized void method() throws InterruptedException {
        System.out.println(Thread.currentThread().getName() + " sleeping");
        Thread.sleep(2000); // HOLDS LOCK for 2 seconds while sleeping
        System.out.println(Thread.currentThread().getName() + " done");
    }
}
LockTest obj = new LockTest();
new Thread(() -> { try { obj.method(); } catch(Exception e){} }).start();
new Thread(() -> { try { obj.method(); } catch(Exception e){} }).start();

// Output: T1 sleeping → (2s wait) → T1 done → T2 sleeping → T2 done
// T2 is BLOCKED for 2s because T1 holds lock while sleeping
// wait() releases the lock — sleep() does NOT
// Q: What happens if you call start() twice on the same thread?
Thread t = new Thread(() -> System.out.println("Running"));
t.start(); // ✓ works — creates new thread
t.start(); // ✗ IllegalThreadStateException!

// A thread object can only be started once.
// After start(), thread moves to RUNNABLE state.
// After run() completes, thread moves to TERMINATED state.
// Calling start() on a TERMINATED or already-STARTED thread = exception

// Q: Can you restart a terminated thread?
// A: NO — once TERMINATED, cannot be restarted. Create a new Thread.
// Use Executor framework to avoid managing thread lifecycle manually.

Short-answer FAANG questions

🔄 What is thread safety?

  • A class is thread-safe if it behaves correctly when accessed from multiple threads simultaneously, regardless of scheduling or interleaving, without additional synchronization from the caller.
  • String, Integer, StringBuilder (not!) are examples.
  • Thread-safety is about correctness, not performance.

⚡ volatile vs synchronized

  • volatile: visibility only, no atomicity
  • synchronized: visibility + atomicity (mutual exclusion)
  • volatile is cheaper — no lock/unlock overhead
  • Use volatile for flags (single writer); synchronized for compound ops
  • volatile cannot replace synchronized for check-then-act

🔒 What is a monitor?

  • Every Java object has a built-in monitor (intrinsic lock)
  • synchronized acquires the monitor of the lock object
  • Java monitors are reentrant — same thread can reacquire
  • Monitor has: entry set (BLOCKED threads) + wait set (WAITING threads)
  • notify() moves one thread from wait set to entry set

🧵 Can two threads run same method?

  • Yes — if the method is not synchronized, any number of threads can execute it concurrently
  • Each thread has its own stack frame with local variables
  • Only shared mutable state (heap objects, static fields) needs protection
  • Local variables are always thread-safe — on thread's own stack

🏊 What is thread pool? Why use?

  • Pre-created set of reusable threads
  • Avoids cost of creating/destroying thread per task (expensive OS operation)
  • Limits total thread count — prevents OOM from unbounded threads
  • Queues tasks when all threads busy — provides backpressure
  • Always prefer ExecutorService over raw Thread creation

🎯 What is happens-before?

  • JMM relationship: if A happens-before B, A's effects are visible to B
  • Established by: volatile write/read, synchronized exit/entry, thread.start(), thread.join()
  • Without happens-before: no visibility guarantee — stale values possible
  • Key for reasoning about correctness across threads

🔑 Difference: notify() vs notifyAll()

  • notify(): wakes ONE arbitrary waiting thread
  • notifyAll(): wakes ALL waiting threads
  • Woken threads compete for the lock — only one wins
  • notify() risk: wrong thread wakes and re-waits → missed signal
  • Prefer notifyAll() unless exactly one thread type waits

💀 How to detect deadlock?

  • jstack <pid> — prints thread dump with "Found N deadlock(s)"
  • ThreadMXBean.findDeadlockedThreads() — programmatic
  • VisualVM / JConsole — visual deadlock detection
  • Prevention > detection — use lock ordering and tryLock

⚠️ What is spurious wakeup?

  • A thread wakes from wait() without being notified
  • Allowed by POSIX and Java specs — rare but real
  • Fix: always use while(!condition) wait() — not if
  • Re-check condition after every wakeup

🧪 What is CAS?

  • Compare-And-Swap — hardware-level atomic instruction
  • If memory == expected, swap to new value; else retry
  • Used by AtomicInteger, ConcurrentHashMap, CopyOnWriteArrayList
  • Lock-free but not wait-free (can spin)
  • ABA problem — solved by AtomicStampedReference

🌊 ThreadLocal — what and when?

  • Thread-local variable — each thread has its own independent copy
  • No synchronization needed — no sharing
  • Use: user context per request (web frameworks), SimpleDateFormat instances, DB connections
  • Trap: memory leak in thread pools — must call remove() when done

🏎️ AtomicInteger vs synchronized

  • Both thread-safe for counter operations
  • AtomicInteger: lock-free CAS, lower overhead, faster at low-medium contention
  • synchronized: simpler for complex compound logic
  • At very high contention: LongAdder beats AtomicLong
  • For simple increment: AtomicInteger > synchronized

ThreadLocal — a must-know topic

ThreadLocal — per-thread isolated variables 
// ThreadLocal gives each thread its own independent variable copy
class RequestContext {
    // Each thread gets its own String value — no sharing, no sync needed
    private static final ThreadLocal<String> userId =
        ThreadLocal.withInitial(() -> "anonymous");

    public static void setUser(String id) { userId.set(id); }
    public static String getUser()        { return userId.get(); }
    public static void clear()            { userId.remove(); } // critical in thread pools
}

// Web request handler — each request thread has own userId
Runnable handler = () -> {
    RequestContext.setUser("user_" + Thread.currentThread().getId());
    try {
        processRequest(); // can call getUser() anywhere down the call stack
    } finally {
        RequestContext.clear(); // MUST remove — thread goes back to pool with stale value otherwise
    }
};

// InheritableThreadLocal — child thread inherits parent's values
static final InheritableThreadLocal<String> traceId = new InheritableThreadLocal<>();
// Parent sets traceId → child threads automatically inherit it (for distributed tracing)
Interview Reference

Interview Cheatsheet

One-liners for when you're under pressure. Know these cold before any Java concurrency interview.

🧵 Thread creation one-liners

  • extends Thread: wastes inheritance; use only for Thread overrides
  • implements Runnable: preferred; clean separation of task from thread
  • Callable: returns value + throws checked exceptions
  • run() = method call on current thread; start() = new OS thread
  • start() twice = IllegalThreadStateException

🔄 Thread states

  • NEW → RUNNABLE via start()
  • BLOCKED = waiting for synchronized lock
  • WAITING = wait() / join() — indefinite
  • TIMED_WAITING = sleep() / wait(ms) / join(ms)
  • TERMINATED = run() completed; cannot restart
  • BLOCKED is about locks; WAITING is about coordination

⚡ sleep vs wait

  • sleep(): Thread class, static, does NOT release lock
  • wait(): Object class, releases lock, must be in synchronized
  • sleep(): woken by timeout only
  • wait(): woken by notify()/notifyAll()
  • Both throw InterruptedException

🔒 synchronized rules

  • Instance method: locks on 'this'
  • Static method: locks on ClassName.class
  • Block: locks on specified object
  • Reentrant: same thread can re-enter
  • Lock auto-released on block exit (even on exception)
  • Does NOT prevent access via different lock object

⚡ volatile rules

  • Guarantees visibility — flushes to main memory
  • Does NOT guarantee atomicity
  • count++ is NOT atomic even with volatile
  • Good for: stop flags, state flags, DCL singleton
  • Prevents instruction reordering around the variable

🤝 wait/notify rules

  • Must be inside synchronized on same object
  • wait() releases lock; re-acquires before returning
  • Always use while(!cond) wait() — not if
  • notify(): wakes 1 arbitrary thread
  • notifyAll(): wakes all; they compete for lock
  • Outside synchronized → IllegalMonitorStateException

🔑 ReentrantLock vs synchronized

  • tryLock(), tryLock(timeout): ReentrantLock only
  • lockInterruptibly(): ReentrantLock only
  • Fair mode: new ReentrantLock(true)
  • Multiple conditions: lock.newCondition()
  • Always unlock() in finally block
  • synchronized: simpler, JVM-optimised

🏊 Thread pool types

  • fixedThreadPool(n): bounded threads, unbounded queue
  • cachedThreadPool(): grows on demand, 60s idle TTL
  • singleThreadExecutor(): sequential, one thread
  • scheduledThreadPool(n): delayed/periodic tasks
  • Always shutdown() the pool when done
  • shutdown() waits; shutdownNow() interrupts

💀 Deadlock prevention

  • Lock ordering: always acquire in same order
  • tryLock(timeout): release all and retry
  • Avoid nested locks where possible
  • Detect: jstack, ThreadMXBean.findDeadlockedThreads()
  • Livelock: active but no progress → add randomness
  • Starvation: ReentrantLock(true) for fair access

🔢 Atomic / CAS

  • AtomicInteger.incrementAndGet(): lock-free counter
  • compareAndSet(expect, update): the CAS operation
  • ABA problem: use AtomicStampedReference
  • High contention: LongAdder beats AtomicLong
  • LongAdder has no compareAndSet — use AtomicLong if needed

🚦 Synchronizers

  • CountDownLatch: wait for N events (one-shot)
  • CyclicBarrier: N threads meet at point (reusable)
  • Semaphore: limit concurrent access to N
  • Semaphore can be released by different thread
  • Locks must be released by same thread

🗂️ Concurrent collections

  • ConcurrentHashMap: no null keys/values; CHM.putIfAbsent is atomic
  • CopyOnWriteArrayList: safe iteration; expensive writes
  • Collections.synchronizedList: iteration needs manual lock
  • BlockingQueue.put()/take(): blocks on full/empty
  • ConcurrentLinkedQueue: lock-free, non-blocking

🚨 Top interview traps

  • run() instead of start() — no new thread created
  • sleep() does NOT release lock
  • volatile does NOT make count++ atomic
  • wait() outside synchronized = IllegalMonitorStateException
  • if(!cond) wait() — should be while
  • Missing volatile in DCL Singleton
  • ThreadLocal memory leak in pools — must call remove()
  • synchronized on String literal or Integer — shared pool!

🌟 Design principles

  • Immutable objects are always thread-safe
  • Prefer higher-level abstractions over raw synchronized
  • Minimise lock scope — lock only what you must
  • Never call alien methods while holding a lock
  • Document thread-safety guarantees in your classes
  • Prefer BlockingQueue over wait/notify for producer-consumer
