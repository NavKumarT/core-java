Java 5+

Why Generics Exist

Before generics, any container that needed to hold "some type" simply held Object. That worked, but it silently threw away type safety — the compiler had no way to stop you putting the wrong thing in, and every read required an unchecked, runtime-risky cast.

The problem generics solve — pre-generics, Object-based "polymorphism" 
String s = new String("Hello world");
Object obj = s;              // widening — always safe, always allowed

obj = new Integer(1);        // ALSO compiles — obj is just an Object reference,
                             // the compiler has no idea it was "supposed to" hold a String

s = (String) obj;            // compiles fine... then throws ClassCastException AT RUNTIME
                             // because obj actually holds an Integer right now

// So by default we don't have type safety and compile-time checking —
// the mistake (storing an Integer where a String was expected) is only
// caught when the bad cast actually executes, potentially deep in production
What generics add
  • Compile-time type checking — the wrong type is rejected at compile time, not discovered via a runtime ClassCastException
  • No explicit casts needed on retrieval — the compiler inserts them for you, and only where it's already proven safe
  • Self-documenting APIs — List<String> tells you exactly what's inside, unlike a raw List
The core idea
  • A generic class/method is parameterized over a TYPE, the same way a regular method is parameterized over VALUES
  • class Box<T> — T is a placeholder, filled in with a real type (Box<String>, Box<Integer>) at the point of use
  • Enforced entirely by the COMPILER — this matters enormously for what generics can and can't do at runtime, covered next in Type Erasure
💡 Interview framing: "Generics move a category of bugs from runtime (ClassCastException, often far from the actual mistake) to compile time (a red squiggle exactly where the wrong type was used)." That's the entire value proposition in one sentence.
The Core Mechanism

Type Erasure

This is the single most important mechanic behind Java generics, and the source of nearly every "why can't I do X with generics" interview question. Generic type information exists ONLY at compile time — the compiler checks it, then erases it, replacing type parameters with their bound (or Object) in the compiled bytecode.

Why erasure was chosen
  • Backward compatibility — generics were added in Java 5; erasure lets generic code interoperate with pre-generics bytecode and libraries
  • No JVM changes required — the bytecode format itself didn't need to change to support generics
  • Cost: no reified generics — unlike C#/.NET, Java generics carry no type information at runtime
What actually happens at compile time
  • List<String> and List<Integer> compile down to the exact same bytecode — plain List
  • The compiler inserts casts automatically at extraction points (e.g. after list.get(0)) so your code doesn't need to
  • Unbounded T erases to Object; T extends Number erases to Number
Same class at runtime
Why T[] needs an unchecked cast
instanceof / new T() forbidden
List<String> strings = new ArrayList<>();
List<Integer> ints    = new ArrayList<>();

System.out.println(strings.getClass() == ints.getClass()); // true!
// Both are literally java.util.ArrayList at runtime — the /
// type argument only ever existed in the SOURCE CODE and compiled .class
// file's metadata for the compiler's own use; the runtime object has no idea
class GenericDemo<T> {
    T genericArray[] = (T[]) new Object[5]; // unchecked cast warning, but this is the standard pattern
}
// WHY the cast is required: "new T[5]" does NOT compile at all.
// After erasure, T is just Object — the JVM would need to create an array
// of a type that no longer exists by the time bytecode runs. So Java forces
// you to allocate an Object[] and cast it, which is technically a LIE to the
// compiler (the array's real runtime component type is Object, not T) —
// which is exactly why the compiler flags it as "unchecked"

GenericDemo<String> gd = new GenericDemo<>();
gd.genericArray[0] = "Hello"; // fine
// gd.genericArray[1] = 10;   // COMPILE ERROR — the compiler DOES still enforce
// this at the assignment site, even though the array itself is really an Object[]
// underneath. Type safety is enforced by the COMPILER, not by the array's real type
class Box<T> {
    private T value;

    boolean isStringBox() {
        // return value instanceof T; // COMPILE ERROR — "T" doesn't exist at runtime
        return false; // no way to ask "is T String?" — the information is erased
    }

    T createDefault() {
        // return new T(); // COMPILE ERROR — same root cause: the JVM has no
        // class named "T" to instantiate; erasure means it doesn't exist by runtime
        return null;
    }
}
// Workaround for both: pass a Class<T> token explicitly, e.g.
// T createDefault(Class<T> clazz) { return clazz.getDeclaredConstructor().newInstance(); }
🚫 The single fact that answers most "why can't generics do X" questions: at runtime, all generic type information is gone. T effectively doesn't exist in the compiled class — it's compiled AS IF it were Object (or its bound). Every restriction covered later in this document (no new T(), no T[], no instanceof T, no static fields of type T) traces back directly to this one fact.
Building Blocks

Defining a Generic Class

A generic class declares one or more type parameters in angle brackets after the class name. Every field, method parameter, and return type inside the class can then reference that placeholder type, and the compiler substitutes the real type at every call site.

A complete generic container — fields, a constrained-capacity array, append/display 
class GenericDemo<T> {
    private T genericArray[] = (T[]) new Object[5]; // unchecked cast — see Type Erasure section
    private int length = 0;

    public void display() {
        for (int i = 0; i < length; i++) {
            System.out.println(genericArray[i]);
        }
    }

    public void append(T v) {
        if (length == 5) return;
        genericArray[length++] = v;
    }
}

public class Main {
    public static void main(String[] args) {
        GenericDemo<String> gds = new GenericDemo<>(); // diamond operator — infers 
        gds.append("Hello");
        gds.append("World");
        // gds.append(10); // COMPILE ERROR — T is bound to String for this instance
        gds.display();
    }
}
Naming convention
  • T — Type (general purpose)
  • E — Element (used heavily in the Collections framework — List<E>)
  • K, V — Key, Value (Map-style generics)
  • N — Number; R — Return type; S, U — additional types when T is taken
  • Single uppercase letters by convention, purely readability — the compiler treats T and MyType identically
The diamond operator (Java 7+)
  • new GenericDemo<>() — empty angle brackets, type inferred from the declared variable type on the left
  • Before Java 7, you had to repeat it: GenericDemo<String> gd = new GenericDemo<String>();
  • Purely a compile-time convenience — has zero effect on the erased bytecode
Legacy Interop

Raw Types — What Happens Without a Type Parameter

You CAN use a generic class without supplying a type argument at all — this is called a raw type. It exists purely for backward compatibility with pre-Java-5 code, and it throws away every compile-time safety guarantee generics normally provide.

Raw type — behaves like Object
Unchecked warning & mixed usage danger
GenericDemo gds = new GenericDemo(); // RAW TYPE — no  supplied at all
// T is effectively treated as Object here — no compile-time type checking
// applies to values passed to append(), and display() gives no type guarantee

gds.append("Hello"); // compiles
gds.append(10);        // ALSO compiles — no error, because with a raw type the
                       // compiler falls all the way back to pre-generics behavior
// This is exactly the type-unsafety problem generics were built to prevent —
// using a raw type opts you OUT of that protection entirely
List rawList = new ArrayList(); // raw — compiler emits "uses unchecked or unsafe operations"
rawList.add("a string");
rawList.add(42);              // compiles — raw type accepts anything

List<String> strings = rawList;  // UNCHECKED WARNING, but compiles — assigning raw to parameterized
String s = strings.get(1);     // compiles fine... ClassCastException AT RUNTIME (Integer -> String)
// The compiler trusted the raw-to-parameterized assignment and inserted
// a cast at get(), which then blows up because the actual element is an Integer
Raw type: GenericDemo gdParameterized: GenericDemo<String> gd
Compile-time type checkingNone — behaves like pre-Java-5 codeFull — wrong-type arguments rejected
Unchecked warningsGenerated liberallyNone, when used correctly
Use caseLegacy code interop onlyAll new code, always
⚠️ Raw types are a legacy escape hatch, not a feature to reach for. Modern Java code should never declare a raw type deliberately — if you see one in a codebase, it's almost always either very old code or an accidental omission of the type argument.
Beyond a Single T

Multiple Type Parameters

A generic class isn't limited to one placeholder — you can declare as many as the design needs, comma-separated. The most common real-world example is a key/value pair, exactly how Map<K,V> is built.

Two type parameters — a simple key/value pair, mirroring Map.Entry 
class Pair<K, V> {
    private K key;
    private V value;

    Pair(K key, V value) {
        this.key = key;
        this.value = value;
    }

    public K getKey()   { return key; }
    public V getValue() { return value; }

    @Override
    public String toString() { return key + " -> " + value; }
}

Pair<String, Integer> ageEntry = new Pair<>("Alice", 30);
System.out.println(ageEntry); // "Alice -> 30"

// This is exactly the shape java.util.Map<K,V> and Map.Entry<K,V> use —
// HashMap<String, List<Integer>> is the same idea with a more complex V
💡 Type parameters are completely independent of each other — Pair<String, Integer> and Pair<Integer, String> are different, incompatible parameterizations of the same class. Order matters exactly like it does for regular method parameters.
Inheritance

Subclassing a Generic Class

A subclass of a generic class has three options: stay generic and pass the type parameter through, fix the type parameter to something concrete, or extend the raw type. Each has different implications for what the subclass can promise its own callers.

Pass the type parameter through
Fix the type parameter
Subclass introduces its OWN parameter
class Container<T> {
    protected T value;
    public void set(T value) { this.value = value; }
    public T get() { return value; }
}

// Subclass stays generic — "class Sub<T> extends Super<T>" from your notes
class LoggingContainer<T> extends Container<T> {
    @Override
    public void set(T value) {
        System.out.println("Setting: " + value);
        super.set(value);
    }
}
LoggingContainer<String> lc = new LoggingContainer<>(); // still flexible — caller picks T
// Subclass FIXES the type parameter to something concrete — no longer generic itself
class StringContainer extends Container<String> {
    public int length() { return get().length(); } // get() is known to return String here — no cast needed
}
StringContainer sc = new StringContainer(); // no  at all — it's baked in as String
sc.set("hello");
System.out.println(sc.length()); // 5
// sc.set(42); // COMPILE ERROR — set(T) is set(String) for this subclass
// Subclass adds an ADDITIONAL type parameter of its own
class KeyedContainer<T, K> extends Container<T> {
    private K key;
    public void setKey(K key) { this.key = key; }
    public K getKey()   { return key; }
}
KeyedContainer<String, Integer> kc = new KeyedContainer<>();
kc.set("value");   // T = String, inherited from Container
kc.setKey(101);   // K = Integer, this class's own parameter
💡 Interfaces follow the exact same rules — class Repo<T> implements Dao<T> passes the parameter through, and class UserRepo implements Dao<User> fixes it, identical to the extends cases above.
Constraining T

Bounded Type Parameters

By default, T can be ANY reference type — the compiler assumes nothing about it beyond what Object offers. A bounded type parameter narrows that: T extends Number restricts T to Number and its subtypes, and — critically — lets you call Number's methods directly on a T value.

Single bound — extends Number
Bound is an interface — still "extends"
Multiple bounds — class & interfaces
class NumericBox<T extends Number> { // only Number and its subtypes allowed
    private T value;
    NumericBox(T value) { this.value = value; }

    public double doubleValue() {
        return value.doubleValue(); // callable because the compiler KNOWS T is at least a Number —
    }                            // without the bound, T would only offer Object's methods
}

NumericBox<Integer> ib = new NumericBox<>(42);   // OK — Integer extends Number
NumericBox<Double>  db = new NumericBox<>(3.14); // OK — Double extends Number
// NumericBox<String> sb = new NumericBox<>("x"); // COMPILE ERROR —
// String does not extend Number
// Even when the bound is an INTERFACE, the keyword is still "extends" — never "implements"
class SortedBox<T extends Comparable<T>> { // Comparable is an interface
    private List<T> items = new ArrayList<>();

    public void add(T item) {
        items.add(item);
        Collections.sort(items); // legal because T is guaranteed Comparable<T>
    }
}
// Why "extends" for interfaces too: in the context of a type parameter
// bound, "extends" simply means "is-a" / "is a subtype of" — it doesn't
// carry class-vs-interface baggage the way it does for normal class
// declarations. This is a very common interview trick question.
// Multiple bounds: AT MOST one class, plus any number of interfaces, joined with &
interface Auditable { String auditId(); }
interface Taggable  { String tag(); }

class Record<T extends Number & Auditable & Taggable> {
    // T must be a Number (the ONE class bound) AND implement BOTH interfaces
    private T value;
    public void describe() {
        System.out.println(value.auditId() + " / " + value.tag() + " = " + value.doubleValue());
    }
}
// RULE: if a class bound is present, it MUST come first, before any interfaces —
//  would be a COMPILE ERROR (class must lead)
// You can have zero or one class bound, but as many interface bounds as needed
Why only ONE class bound is allowed
  • Java doesn't support multiple class inheritance — a type parameter's bound follows the same rule any class declaration does
  • A type can only ever extend one concrete class, so the bound mirrors that: at most one class, but unlimited interfaces (since a class CAN implement many interfaces)
Bounded types & wildcards preview
  • Bounded type PARAMETERS (T extends Number) constrain what T can be declared as, at the class/method definition site
  • Bounded WILDCARDS (? extends Number) constrain what a caller can pass at the USE site — a related but distinct concept, covered in the Wildcards section
Method-Level Generics

Generic Methods

A method can declare its own type parameter, independent of whether its enclosing class is generic at all. The type parameter is declared in angle brackets BEFORE the return type — this is what makes a method generic, not merely using a type that happens to be a class-level parameter.

A static generic method operating on any GenericDemo<T> 
static <T> void display(GenericDemo<T> array) {
    //     ^^^ this angle-bracket declaration is what makes display() generic —
    // it introduces T fresh, for THIS method call, independent of any class-level T
    for (T element : array) {
        System.out.print(element);
    }
}

// Callable with ANY GenericDemo<T>, T inferred per-call:
display(new GenericDemo<String>());   // T inferred as String for this call
display(new GenericDemo<Integer>());  // T inferred as Integer for this call — a DIFFERENT, independent T
Generic methods in a non-generic class
  • The class itself doesn't need any type parameter — the method introduces and scopes its own T
  • Static generic methods (like Collections.sort, Arrays.asList) are extremely common in the JDK for exactly this reason — utility methods that work across any type
Type inference
  • You almost never need to specify the type argument explicitly — the compiler infers it from the arguments passed
  • Explicit form when needed: Main.<String>display(gd) — rarely necessary, useful when inference is ambiguous
Bounded generic method
Multiple type parameters on a method
JDK examples you already use
// A method's own type parameter can be bounded exactly like a class's can
static <T extends Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b; // compareTo() callable because of the bound
}
System.out.println(max(3, 7));           // 7 — T = Integer
System.out.println(max("apple", "banana")); // "banana" — T = String
static <K, V> Pair<K, V> of(K key, V value) { // factory method with 2 method-level type params
    return new Pair<>(key, value);
}
Pair<String, Integer> p = Pair.of("age", 30); // K, V both inferred from the arguments

// This "static factory method with inference" pattern predates the diamond
// operator and is still common for readability — e.g. Map.entry(k, v)
// You've been calling generic methods all along without necessarily noticing:
List<Integer> nums = Arrays.<Integer>asList(1, 2, 3); // explicit type witness (rarely needed)
List<Integer> nums2 = Arrays.asList(1, 2, 3);         // normal — inferred

Collections.<String>sort(myList);  // Collections.sort's signature:
                                // static <T extends Comparable<? super T>> void sort(List<T> list)

// Every one of these is a STATIC GENERIC METHOD — none of Arrays, Collections,
// or List are themselves generic classes for these particular methods
💡 Interview trap to watch for: static methods CANNOT reference a class-level type parameter — a static context has no particular instance, so there's no concrete binding of the class's T to use. A static method that needs generics must declare its OWN type parameter, exactly as shown above.
Flexible Call Sites

Wildcards — ?, ? extends T, ? super T

Generics are invariant by default: List<Integer> is NOT a List<Number>, even though Integer IS a Number. Wildcards exist to relax that rigidity at specific use sites, without breaking type safety.

Why invariance exists in the first place
  • If List<Integer> WERE a List<Number>, you could do List<Number> ln = someListOfIntegers; ln.add(3.14); — adding a Double into what's really a List<Integer> at runtime
  • Invariance prevents exactly that hole — it's a deliberate safety choice, not an oversight
  • Wildcards let you opt into read-only or write-only flexibility instead, safely
The three wildcard forms
  • ? — unbounded, "some unknown type"
  • ? extends T — upper-bounded, "T or any subtype" — READ-friendly
  • ? super T — lower-bounded, "T or any supertype" — WRITE-friendly
Unbounded ?
? extends T (upper bound)
? super T (lower bound)
super only works on methods, not classes
static void printAll(List<?> list) { // accepts List<String>, List<Integer>, List<AnyType> — all of them
    for (Object o : list) {  // elements only guaranteed to be Object — the exact type is unknown
        System.out.println(o);
    }
    // list.add("x"); // COMPILE ERROR — can't add ANYTHING except null;
    // the compiler doesn't know what type this list REALLY holds
}
printAll(List.of("a", "b"));  // works
printAll(List.of(1, 2, 3));   // also works — that's the whole point of ?
// "? extends T" — accepts T or any SUBTYPE of T. Great for READING.
static double sumAll(List<? extends Number> list) {
    double sum = 0;
    for (Number n : list) { // safe to read as Number — every element IS-A Number, guaranteed
        sum += n.doubleValue();
    }
    return sum;
    // list.add(5); // COMPILE ERROR — can't add. The list might really be a
    // List<Integer>, or List<Double>, or List<Long> — the compiler can't verify
    // an int/Integer literal is safe to insert into whichever ONE of those it is
}
sumAll(List.of(1, 2, 3));       // List<Integer> — Integer extends Number, OK
sumAll(List.of(1.5, 2.5));    // List<Double> — Double extends Number, OK
// "? super T" — accepts T or any SUPERTYPE of T. Great for WRITING.
static void addNumbers(List<? super Integer> list) {
    list.add(1);  // SAFE — whatever the list really is (List<Integer>, List<Number>,
    list.add(2);  // List<Object>), an Integer is guaranteed assignable into it
    // Number n = list.get(0); // COMPILE ERROR — can't assume the return type is
    // more specific than Object; the list might really hold Objects
    Object o = list.get(0); // only Object is guaranteed on read
}
List<Number> numbers = new ArrayList<>();
addNumbers(numbers); // OK — Number is a supertype of Integer
List<Object> objects = new ArrayList<>();
addNumbers(objects); // also OK — Object is a supertype of Integer too
// "super" is a WILDCARD-BOUND keyword only — it works on method/variable
// declarations using "?", but is NOT valid for bounding a type PARAMETER
// on a class or method declaration:

static void addNumbers(List<? super Integer> list) { /* ... */ } // ✓ VALID — wildcard bound

// class Box<T super Integer> { }  // ✗ COMPILE ERROR — "super" is not
// allowed here. Type parameter declarations only support "extends"
// (which, as covered earlier, is also used for interface bounds).
// There is no way to say "T must be Integer or a supertype of Integer"
// as a class-level type parameter bound — only as a wildcard bound.
The Mnemonic That Sticks

PECS — Producer Extends, Consumer Super

Deciding between ? extends T and ? super T is confusing until you frame it around what the parameter DOES: does your method read FROM it (a producer of values), or write INTO it (a consumer of values)?

RoleWildcardYou can...You cannot...
Producer — you READ from it? extends TRead elements out, safely typed as TAdd elements in (except null)
Consumer — you WRITE to it? super TAdd elements of type T inRead elements out as anything more specific than Object
Both produce AND consumeNo wildcard — exact type TBoth read and write, fully typedAccept a broader range of caller-supplied list types
PECS in action — Collections.copy's actual real-world signature 
// The real JDK signature: java.util.Collections.copy
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    for (int i = 0; i < src.size(); i++) {
        dest.set(i, src.get(i)); // READ from src (a Producer of T -> "extends"),
    }                                // WRITE into dest (a Consumer of T -> "super")
}

List<Integer> ints    = List.of(1, 2, 3);
List<Number>  numbers = new ArrayList<>(List.of(0, 0, 0));

Collections.copy(numbers, ints);
// dest = List<Number>  — Number is a supertype of Integer -> matches "? super T" where T=Integer
// src  = List<Integer> — matches "? extends T" exactly where T=Integer
// Without wildcards, copy() could ONLY accept List<Integer> dest and
// List<Integer> src — far too restrictive for a general-purpose utility
💡 Interview one-liner: "PECS — Producer Extends, Consumer Super. If the parameterized type only ever GIVES you values, bound it with extends. If it only ever TAKES values from you, bound it with super. If it does both, don't use a wildcard at all — use the exact type."
A Classic Clash

Generics & Arrays

Arrays and generics have fundamentally incompatible design philosophies — arrays are covariant and reified (they know their element type at runtime), while generics are invariant and erased (type info vanishes at runtime). Mixing them is where some of the trickiest generics questions live.

Arrays are covariant (and reified)
  • Integer[] IS-A Number[] IS-A Object[] — array types follow the same subtype relationship as their elements
  • Arrays carry their actual component type at runtime — arr.getClass() tells you exactly what it is
  • This covariance is UNSAFE and enforced only at runtime via ArrayStoreException
Generics are invariant (and erased)
  • List<Integer> is NOT a List<Number> — no automatic subtyping between different parameterizations
  • This invariance is enforced entirely at COMPILE time, with no runtime type info to fall back on
  • Because of erasure, there IS no runtime component type for a generic array to carry — this is the root incompatibility
Array covariance — a real runtime bug
Why "new T[]" doesn't compile
Generic varargs — heap pollution warning
Integer[] ints = {1, 2, 3};
Object[] objs = ints;         // legal — arrays ARE covariant
objs[0] = "not an integer"; // compiles fine (objs is declared Object[])...
                             // ...but throws ArrayStoreException AT RUNTIME, because the array
                             // object underneath is REALLY an Integer[], and it remembers that

// Contrast: the generics equivalent doesn't even COMPILE, catching the
// same class of mistake much earlier —
List<Integer> intList = List.of(1, 2, 3);
// List<Object> objList = intList; // COMPILE ERROR — invariance blocks this outright
class Box<T> {
    // T[] arr = new T[10]; // COMPILE ERROR — "generic array creation"
    //
    // WHY: arrays need to know their component type at runtime to enforce
    // covariance checks (ArrayStoreException). After erasure, T is just
    // Object — creating "new T[10]" would really create an Object[], but
    // claim to be a T[], silently breaking the runtime type-safety guarantee
    // arrays are supposed to provide. Java refuses to let you create that lie.

    private T[] arr = (T[]) new Object[10]; // the standard, unchecked-warning workaround
    // You're explicitly telling the compiler "trust me" — and it's YOUR job
    // as the class author to never let this array escape as a T[] to outside
    // code, since doing so risks a ClassCastException down the line
}
// Varargs are secretly arrays — combining them with generics triggers the same issue
@SafeVarargs // suppresses the warning WHEN you've verified the method is actually safe
static <T> List<T> listOf(T... elements) { // compiler creates a T[] under the hood — "heap pollution" warning
    return Arrays.asList(elements);
}
List<String> l = listOf("a", "b", "c"); // fine to call — the warning is about the METHOD's internals, not call sites

// @SafeVarargs is a promise from the method author: "I don't store anything
// unsafe into this array or let it escape" — only legal on static/final/
// private methods or constructors, since it requires the method can't be
// overridden with a version that breaks the promise
🚫 Interview one-liner: "Arrays check element types at runtime because they're reified; generics check element types at compile time because they're erased. new T[] would need runtime type info generics don't have — that mismatch is exactly why the JDK's own generic containers (ArrayList, HashMap) store an Object[] internally and cast on retrieval, rather than ever creating a true generic array."
The Full List

Restrictions on Generics

Every restriction below traces back to type erasure — T genuinely does not exist as a distinct type at runtime, so anything requiring runtime type knowledge of T is off the table.

RestrictionWhy (traces back to erasure)
Cannot instantiate T — new T()No class named "T" exists at runtime to instantiate
Cannot create a generic array — new T[]Arrays need a real runtime component type to enforce store-checks; T has none
Cannot use primitives as a type argument — List<int>Generics are erased to Object/bound; a primitive can't be stored where a reference is expected — use wrapper types (List<Integer>)
Cannot create static fields of type TA static field is shared across ALL instantiations (Box<String>, Box<Integer>) — but after erasure there's only ONE class, so which T would it hold?
Cannot use instanceof with a parameterized type — obj instanceof List<String>At runtime, all List<X> are just List — there's no way to check the erased type argument
Cannot catch a generic exception type — catch (T e)The JVM's exception dispatch mechanism relies on the exact runtime class of the exception; T has none
Cannot overload two methods that erase to the same signaturevoid m(List<String> l) and void m(List<Integer> l) both erase to void m(List l) — a compile-time "clashing" error

No static fields of type T
No instanceof with parameterized type
No catch(T e)
No clashing overloads
// List<int> list = new ArrayList<>(); // COMPILE ERROR — type arguments must be reference types
List<Integer> list = new ArrayList<>(); // use the wrapper class instead
list.add(5); // autoboxing converts int -> Integer transparently at the call site

int x = list.get(0); // auto-unboxing converts Integer -> int on retrieval
// This autoboxing/unboxing convenience is exactly why generics never NEEDED
// primitive support directly, at the cost of some boxing overhead
class Box<T> {
    // private static T defaultValue; // COMPILE ERROR — "non-static type variable T
    // cannot be referenced from a static context"
    //
    // WHY: Box<String> and Box<Integer> are literally the SAME class after
    // erasure. A static field is ONE field, shared class-wide — but which type
    // would "defaultValue" hold — the String use's value, or the Integer use's?
    // There's no coherent answer, so the compiler forbids it entirely.

    private static int instanceCount; // FINE — doesn't involve T at all
}
List<String> list = new ArrayList<>();

// if (list instanceof List<String>) { } // COMPILE ERROR — "illegal generic type for instanceof"
// The erased runtime type of list is just List — there's no  left to check against

if (list instanceof List<?>) { // ✓ VALID — unbounded wildcard IS allowed, since it asks
    System.out.println("is some kind of List"); // nothing about the erased type argument
}
if (list instanceof ArrayList) { /* ... */ } // ✓ VALID — checking the raw class itself is always fine
class Processor<T extends Exception> {
    void process() {
        try {
            doWork();
        // } catch (T e) { } // COMPILE ERROR — "cannot catch type parameter T"
        //
        // WHY: the JVM's catch-clause matching works by inspecting the actual
        // runtime class of the thrown exception against the catch clause's type.
        // After erasure, T has no distinct runtime class to match against.
        } catch (Exception e) { // have to catch a real, erasure-safe type instead
            // handle generically here
        }
    }
    void doWork() throws Exception {}
}
// Note: you CAN still declare "void m() throws T" (throwing IS allowed) —
// it's specifically CATCHING a type parameter that's forbidden
class Printer {
    void print(List<String> list)  { /* ... */ }
    // void print(List<Integer> list) { } // COMPILE ERROR — "print(List<Integer>)
    // clashes with print(List<String>); both methods have the same erasure"
    //
    // WHY: after erasure, BOTH signatures become "void print(List list)" —
    // literally identical bytecode signatures, an illegal duplicate method
}
Erasure's Side Effect

Bridge Methods

A subtle consequence of type erasure surfaces when a generic class or interface is overridden with a concrete type: the compiler silently generates an extra bridge method to preserve polymorphism. Most Java developers never see this directly, but it's a genuine "deep knowledge" interview question.

Why a bridge method is needed 
interface Container<T> {
    void set(T value);
}

class StringContainer implements Container<String> {
    @Override
    public void set(String value) { // looks like it overrides Container.set(T), but...
        System.out.println(value);
    }
}

// After erasure, Container<T>'s method is really: void set(Object value)
// But StringContainer declares: void set(String value)
// These are DIFFERENT erased signatures — set(Object) vs set(String) — so
// technically StringContainer.set(String) does NOT override Container.set(Object)
// by normal JVM override rules. Polymorphism would silently break.

// THE FIX: the compiler auto-generates a synthetic BRIDGE method behind the scenes:
//   public void set(Object value) { set((String) value); }  // compiler-generated
// This bridge method DOES have the erased signature the interface expects,
// and simply delegates to your real, more specific set(String) method
What this means in practice
  • You never write bridge methods yourself — the compiler generates them automatically whenever needed
  • They're marked with the synthetic + bridge flags in the bytecode — invisible to normal source-level code and reflection unless you specifically ask for synthetic methods
  • StringContainer.class.getDeclaredMethods() will actually show TWO set methods if you inspect it — your real one, and the compiler-generated bridge
Why interviewers ask this
  • It demonstrates real understanding of erasure's consequences, beyond just memorizing "T becomes Object"
  • It explains otherwise-confusing reflection output (extra synthetic methods) that engineers sometimes stumble into
  • It reinforces WHY erasure needed careful compiler engineering to preserve normal OOP behavior seamlessly
💡 Interview one-liner: "Bridge methods are the compiler's way of reconciling erasure with polymorphism — when a generic method is overridden with a more specific parameter type, the compiler generates an invisible forwarding method with the erased signature so the JVM's normal virtual-dispatch rules still work correctly."

Short-answer FAANG questions

❓ What is type erasure and why does it exist?

  • Generic type information is checked at compile time, then stripped from the bytecode
  • Exists for backward compatibility — generic code interoperates with pre-Java-5 bytecode and libraries with zero JVM changes
  • Trade-off: no reified generics at runtime, unlike C#

❓ Are generics covariant or invariant? What about arrays?

  • Generics: invariant by default — List<Integer> is not a List<Number>
  • Arrays: covariant — Integer[] IS an Object[]
  • Wildcards (? extends/? super) let you opt into controlled, safe variance for generics

❓ What's the difference between List<Object> and a raw List?

  • List<Object>: fully type-checked — every element is guaranteed to be an Object (anything really, since everything IS an Object), full compiler protection
  • Raw List: NO type checking at all — compiler falls back to pre-generics behavior entirely, unchecked warnings everywhere
  • List<?> (unbounded wildcard) sits in between — read-only unknown type, safer than raw but not writable

❓ Explain PECS in one sentence.

  • Producer Extends — if you only read from it, use ? extends T
  • Consumer Super — if you only write to it, use ? super T
  • Both? Use the exact type T, no wildcard

❓ Why can't you create a generic array directly?

  • Arrays need a real runtime component type to enforce covariance's ArrayStoreException checks
  • After erasure, T has no distinct runtime type — creating "new T[]" would be a lie about the array's real element type
  • Workaround: create an Object[] (or array of the erasure bound) and unchecked-cast it

❓ Why must a class bound come before interface bounds in T extends A & B & C?

  • Java allows at most ONE class bound (no multiple class inheritance) but unlimited interface bounds
  • The class bound, if present, must be listed FIRST — a syntax rule enforced by the compiler
  • "extends" is reused for both class and interface bounds in this context — no separate "implements" keyword for type parameters

❓ Can a static method use its enclosing class's type parameter?

  • No — a class-level T is bound per-instance (Box<String> vs Box<Integer>); a static context has no particular instance
  • A static method needing generics must declare its OWN type parameter: static <T> void method(...)
  • This applies to static fields of type T too — forbidden for the same reason

❓ What is a bridge method?

  • A compiler-generated synthetic method reconciling a generic interface/superclass method with a subclass's more specific override
  • Needed because erasure can make an "obvious" override technically mismatch at the erased-signature level
  • Invisible in normal source code — only visible via reflection (getDeclaredMethods shows extra synthetic entries)

❓ Why does List<String>.class not compile?

  • .class literals require a real runtime Class object — but List<String> and List<Integer> share ONE Class object (List.class) after erasure
  • There is no distinct List<String>.class to reference — only the raw List.class exists at runtime

❓ Bounded type parameter vs bounded wildcard — what's the actual difference?

  • Bounded type PARAMETER (T extends Number): constrains what T can be at the DEFINITION site (class/method declaration)
  • Bounded WILDCARD (? extends Number): constrains what can be passed at the USE/call site, without needing to name a type parameter at all
  • Wildcards are for call-site flexibility; type parameter bounds are for definition-site guarantees you can rely on inside the class/method body

❓ Why does Comparable use <T> but Comparator often uses wildcards?

  • Comparable<T>.compareTo(T o) — an object compares itself to exactly one type, T is fixed per-class
  • Comparator<T> methods like Collections.sort accept Comparator<? super T> — allowing a comparator written for a SUPERTYPE to sort a list of a subtype (PECS: comparator CONSUMES T values to compare, so super applies)

❓ What happens if you don't supply a type argument at all?

  • The class is used as a RAW TYPE — T is effectively treated as Object throughout
  • All compile-time type checking for that variable is lost — compiler emits unchecked warnings
  • Purely a legacy-compatibility feature, never intentional in new code
Interview Reference

Interview Cheatsheet

One-liners for when you're under pressure. Know these cold.

🎯 Why generics exist

  • Move type errors from runtime (ClassCastException) to compile time
  • No explicit casts needed — compiler inserts them where already proven safe
  • Self-documenting APIs — List<String> vs raw List

🧹 Type erasure — the master rule

  • Generic type info exists ONLY at compile time, erased from bytecode
  • List<String> and List<Integer> are the SAME class at runtime
  • Unbounded T erases to Object; T extends Number erases to Number

📦 Raw types

  • No type argument supplied → T treated as Object, zero compile-time checking
  • Legacy-compatibility escape hatch only — never intentional in new code
  • Raw-to-parameterized assignment compiles with an unchecked warning

🔗 Multiple type params & subclassing

  • Pair<K,V> — independent params, order matters (K,V ≠ V,K)
  • Subclass can pass T through, fix it concrete, or add its own new param
  • Interfaces follow identical rules to extends

🔒 Bounded type parameters

  • T extends Number — restricts T, unlocks Number's methods on T
  • "extends" used even for interface bounds — never "implements"
  • T extends A & B & C — at most ONE class (must be first), any number of interfaces

🛠️ Generic methods

  • <T> declared BEFORE the return type — introduces its own T, independent of class-level T
  • Static methods MUST use their own type parameter — can't reference class-level T
  • Type inference handles almost all cases — explicit witness rarely needed

🃏 Wildcards

  • ? — unbounded, read-only as Object, can't add (except null)
  • ? extends T — upper bound, read as T, can't add
  • ? super T — lower bound, can add T, read only as Object
  • "super" only valid on wildcards — NOT on type parameter declarations

🎓 PECS

  • Producer Extends — only reading from it → ? extends T
  • Consumer Super — only writing to it → ? super T
  • Both → exact type T, no wildcard at all

📐 Generics vs Arrays

  • Arrays: covariant + reified — Integer[] IS Object[], checked at runtime (ArrayStoreException)
  • Generics: invariant + erased — List<Integer> is NOT List<Object>, checked at compile time
  • new T[] doesn't compile — no runtime component type to give the array

🚫 The 6 core restrictions

  • No new T(), no new T[], no primitives as type args
  • No static fields of type T
  • No instanceof with a parameterized type (unbounded ? is OK)
  • No catch(T e); no overloads that erase to the same signature

🌉 Bridge methods

  • Compiler-generated synthetic methods reconciling erasure with polymorphism
  • Generated when a generic method is overridden with a more specific parameter type
  • Invisible in source, visible via reflection (getDeclaredMethods)

🚨 Top interview traps

  • Assuming List<Integer> is a List<Number> (it's not — invariance)
  • Forgetting class bound must come FIRST in T extends A & B & C
  • Trying static <class-level T> usage in a static method
  • Confusing PECS direction — remember: extends=read, super=write
  • Assuming a raw-to-parameterized assignment is fully safe (it isn't — deferred ClassCastException risk)
