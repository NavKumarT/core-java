Foundations

Errors vs Exceptions — What's the Difference?

Java distinguishes between three categories of problems. Knowing which is which — and which you should handle — is the first question in every exception interview.

3 Types of Problems
  • Syntax Errors — detected by the compiler during compilation. Code never becomes bytecode. Example: missing semicolon, wrong type.
  • Logical Errors — program compiles and runs but produces wrong output. No exception thrown. Must be found via testing/debugging.
  • Runtime Errors (Exceptions) — program compiles fine but crashes during execution due to bad input, missing resources, or illegal state.
Why Exceptions Happen
  • Bad user input — parsing "abc" as an integer
  • Resource unavailability — file not found, DB down
  • Programming mistakes — null access, array overflow
  • Network failures — connection timeout, refused
  • JVM resource exhaustion — OutOfMemoryError, StackOverflow

The Throwable Hierarchy — the complete tree

💡 Interview one-liner: "Object → Throwable → (Error | Exception). Error is for JVM-level problems you usually can't recover from. Exception splits into RuntimeException (unchecked) and everything else (checked). RuntimeException and its subclasses are unchecked — all others are checked."

Exception Handling

try-catch-finally — Complete Rules

The core exception handling mechanism. Every rule here has been tested in FAANG interviews — especially finally behaviour, return in finally, and catch ordering.

Syntax variations

All valid forms of try blocks 
// 1. try + catch (most common)
try {
    int result = 10 / 0;
} catch (ArithmeticException e) {
    System.out.println("Caught: " + e.getMessage()); // "/ by zero"
}

// 2. try + catch + finally
try {
    riskyOperation();
} catch (IOException e) {
    handleError(e);
} finally {
    cleanup(); // ALWAYS runs — exception or not, return or not
}

// 3. try + finally (NO catch) — valid! exception propagates but finally still runs
try {
    acquireResource();
    doWork();
} finally {
    releaseResource(); // guaranteed to run even if doWork() throws
}

// 4. Multiple catch blocks
try {
    operation();
} catch (FileNotFoundException e) { // more specific FIRST
    System.out.println("File not found");
} catch (IOException e) {           // less specific AFTER
    System.out.println("IO error");
} catch (Exception e) {             // most general LAST
    System.out.println("Something else");
}

Catch ordering — subclass before superclass

❌ Wrong order — compile error
✅ Correct order
try {
    readFile();
} catch (IOException e) {         // SUPERCLASS first — WRONG
    System.out.println("IO");
} catch (FileNotFoundException e) { // SUBCLASS after — COMPILE ERROR
    System.out.println("File");
    // Error: "exception FileNotFoundException has already been caught"
    // FileNotFoundException IS-A IOException — the first catch catches it too
    // Second catch is unreachable — compiler rejects it
}
try {
    readFile();
} catch (FileNotFoundException e) { // SUBCLASS first — correct
    System.out.println("Specific: file not found");
} catch (IOException e) {           // SUPERCLASS after — catches other IOExceptions
    System.out.println("General IO error");
} catch (Exception e) {             // Most general last
    System.out.println("Unexpected error: " + e.getMessage());
}
// Rule: always order catches from MOST SPECIFIC to LEAST SPECIFIC

// finally runs in ALL scenarios: normal exit, exception, and return
static int test(int x) {
    try {
        System.out.println("try");
        if (x == 0) throw new RuntimeException("zero");
        return x * 2;           // finally runs BEFORE this return executes
    } catch (RuntimeException e) {
        System.out.println("catch: " + e.getMessage());
        return -1;              // finally runs BEFORE this return too
    } finally {
        System.out.println("finally always"); // ALWAYS prints
    }
}
test(5);  // try → finally → returns 10
test(0);  // try → catch → finally → returns -1

// Classic use: resource cleanup
Connection conn = null;
try {
    conn = getConnection();
    doDbWork(conn);
} catch (SQLException e) {
    logError(e);
} finally {
    if (conn != null) conn.close(); // guaranteed cleanup
}
// TRICKY: return inside finally OVERRIDES return from try or catch
static int trickyReturn() {
    try {
        return 1;         // value 1 is staged for return...
    } finally {
        return 2;         // ...but finally's return WINS. Returns 2.
    }
}
System.out.println(trickyReturn()); // 2 — NOT 1!

// Same with exception + return in finally:
static int suppressesException() {
    try {
        throw new RuntimeException("error"); // exception thrown...
    } finally {
        return 42; // ...but return in finally SUPPRESSES the exception!
    }
}
System.out.println(suppressesException()); // 42, NO exception thrown
// Rule: NEVER put return in finally — it silently swallows exceptions
// Exception thrown from finally replaces the original exception
static void doubleException() {
    try {
        throw new RuntimeException("original"); // thrown first...
    } finally {
        throw new RuntimeException("from finally"); // ...REPLACES original
    }
}
try {
    doubleException();
} catch (RuntimeException e) {
    System.out.println(e.getMessage()); // "from finally" — original is LOST!
}
// Original exception is swallowed — very dangerous
// try-with-resources solves this via Suppressed exceptions
// Three cases where finally does NOT run:

// 1. System.exit() called inside try or catch
try {
    System.exit(0);       // JVM terminates — finally skipped
} finally {
    System.out.println("This NEVER prints");
}

// 2. JVM crashes (OutOfMemoryError during finally, kill -9, power failure)

// 3. Infinite loop or deadlock in try block
try {
    while(true) {} // finally never reached
} finally {
    System.out.println("Never runs");
}

// Rule: finally "always" runs in normal circumstances
// Exception: JVM-level kill, System.exit(), or thread death
Java 7+

Multi-catch — catch (A | B e)

Java 7 introduced the ability to catch multiple unrelated exception types in a single catch block, eliminating duplicate error-handling code. Know the rules and restrictions.

Before Java 7 — repetitive
Java 7+ — multi-catch
// Pre-Java 7: same handler duplicated for each exception type
try {
    operation();
} catch (IOException e) {
    log(e); sendAlert(e); throw new ServiceException(e);
} catch (SQLException e) {
    log(e); sendAlert(e); throw new ServiceException(e); // exact duplicate
} catch (ClassNotFoundException e) {
    log(e); sendAlert(e); throw new ServiceException(e); // exact duplicate
}
// Java 7+: multi-catch eliminates duplication
try {
    operation();
} catch (IOException | SQLException | ClassNotFoundException e) {
    log(e); sendAlert(e); throw new ServiceException(e); // one block
}

// RULES for multi-catch:
// 1. Types must be UNRELATED (no superclass-subclass between them)
// catch (IOException | FileNotFoundException e)  ← COMPILE ERROR
// FileNotFoundException IS-A IOException — redundant/unreachable

// 2. The catch variable 'e' is implicitly final — cannot reassign
catch (IOException | SQLException e) {
    e = new IOException(); // COMPILE ERROR — e is effectively final
}

// 3. Can still have separate catch blocks for different handling
try {
    operation();
} catch (FileNotFoundException e) {
    System.out.println("File missing: " + e.getMessage());
} catch (IOException | SQLException e) { // multi-catch for rest
    System.out.println("Resource error: " + e.getMessage());
}
💡 Interview answer: "Multi-catch (Java 7) lets you handle multiple unrelated exception types in one block, eliminating code duplication. The types must not have a superclass-subclass relationship between them, and the variable is implicitly final — you can't reassign it inside the block."

// Child method CAN: throw fewer exceptions, throw narrower checked exceptions
// Child method CANNOT: throw new/broader checked exceptions than parent

// Pattern 1: catch, log, re-throw same exception
try {
    riskyOperation();
} catch (IOException e) {
    log.error("IO failed", e);
    throw e;  // re-throw the SAME exception — stack trace preserved
}

// Pattern 2: wrap in different exception (exception translation)
try {
    dbOperation();
} catch (SQLException e) {
    // Translate low-level to domain exception
    throw new DataAccessException("DB error", e); // e is the 'cause'
}

// Pattern 3: catch checked, throw unchecked (common in frameworks)
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt(); // restore flag
    throw new RuntimeException("Interrupted", e); // wrap as unchecked
}

// Java 7+: more precise rethrow — compiler knows exact type
void rethrowExample() throws FileNotFoundException, IOException {
    try { riskyOp(); }
    catch (Exception e) { throw e; } // Java 7 knows this can only be FNFE or IOE
}
// try + finally WITHOUT catch — valid and useful
// Exception propagates to caller, but finally still runs

void doWork() throws IOException {
    FileReader f = new FileReader("data.txt");
    try {
        processFile(f); // may throw IOException
        // no catch — we don't handle it here, just clean up
    } finally {
        f.close(); // always close, even if processFile() throws
    }    // IOException from processFile() propagates to caller
}

// Use case: lock pattern without try-with-resources
Lock lock = new ReentrantLock();
lock.lock();
try {
    criticalSection(); // exception propagates to caller
} finally {
    lock.unlock(); // ALWAYS released, even if criticalSection() throws
}
Call Stack

Exception Propagation

When an exception isn't caught in the method where it occurs, it travels up the call stack until it finds a matching catch block — or reaches the JVM, which terminates the program.

1
Exception thrown in a method — JVM creates an exception object and looks for a matching catch in the current method.
2
No match found — method terminates abnormally, its stack frame is popped. The exception propagates to the calling method.
3
Propagation continues up the call stack until a matching catch block is found or main() is reached.
4
If no handler anywhere — the JVM's default exception handler catches it, prints the stack trace, and terminates the thread (or the entire program for the main thread).
Propagation demo
Checked propagation (throws chain)
Reaching the JVM
// Call chain: main() → method1() → method2() → method3()
// Exception thrown in method3(), not caught until main()

class PropagationDemo {
    static void method3() {
        int[] arr = {1, 2, 3};
        System.out.println(arr[10]); // ArrayIndexOutOfBoundsException thrown here
    }
    static void method2() { method3(); } // no catch — propagates up
    static void method1() { method2(); } // no catch — propagates up

    public static void main(String[] args) {
        try {
            method1(); // finally caught here
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("Caught in main: " + e.getMessage());
        }
    }
}
// Stack trace shows the full path: method3 → method2 → method1 → main
// That's WHY stack traces are valuable — they show you exactly how you got there
// Checked exceptions MUST be declared at every level they propagate through
class CheckedPropagation {

    static void method3() throws IOException {
        throw new IOException("file missing");
    }

    static void method2() throws IOException { // must declare — it propagates
        method3();
    }

    static void method1() throws IOException { // must declare
        method2();
    }

    public static void main(String[] args) {
        try {
            method1(); // main HANDLES it — no throws needed on main
        } catch (IOException e) {
            System.out.println("Handled: " + e.getMessage());
        }
    }
}
// If method2 doesn't declare throws IOException → COMPILE ERROR
// The compiler enforces the checked exception "declaration chain"
// Unchecked exceptions propagate silently — no declaration required
// When exception reaches JVM without being caught:
// 1. Thread's uncaught exception handler is invoked
// 2. Default: prints stack trace to stderr and terminates the thread
// 3. If main thread: whole program terminates

// You can set a custom uncaught exception handler:
Thread.setDefaultUncaughtExceptionHandler((thread, throwable) -> {
    System.err.println("Unhandled in thread " + thread.getName()
        + ": " + throwable.getMessage());
    // send alert, log to monitoring system, etc.
});

// Per-thread handler:
Thread t = new Thread(() -> { throw new RuntimeException("boom"); });
t.setUncaughtExceptionHandler((thread, ex) -> {
    System.out.println("Caught unhandled: " + ex.getMessage());
});
t.start(); // prints "Caught unhandled: boom" — thread terminates gracefully

// Note: main() can declare throws Exception
public static void main(String[] args) throws Exception {
    throw new Exception("uncaught"); // JVM handles it, prints stack trace
}
Custom Exceptions

Creating Custom Exceptions

Real applications use domain-specific exceptions. Know how to create both checked and unchecked custom exceptions, when to use which, and how to structure them for maximum clarity.

Checked custom (extends Exception)
  • Use when caller is expected to handle it
  • Recoverable: low balance, invalid input that user can fix
  • Forces callers to acknowledge the exception exists
  • Example: InsufficientFundsException
Unchecked custom (extends RuntimeException)
  • Use for programming errors or unrecoverable states
  • Caller usually can't meaningfully handle them
  • Preferred in modern Java / Spring ecosystem
  • Example: UserNotFoundException, ConfigurationException

// Checked custom exception — extends Exception
public class InsufficientFundsException extends Exception {
    private final double requested;
    private final double available;

    // No-arg constructor
    public InsufficientFundsException() {
        super("Insufficient funds");
        this.requested = 0;
        this.available = 0;
    }

    // Message constructor
    public InsufficientFundsException(String message) {
        super(message);
        this.requested = 0;
        this.available = 0;
    }

    // Domain-specific constructor
    public InsufficientFundsException(double requested, double available) {
        super(String.format("Requested %.2f but only %.2f available", requested, available));
        this.requested = requested;
        this.available = available;
    }

    // Cause constructor — for exception chaining
    public InsufficientFundsException(String message, Throwable cause) {
        super(message, cause);
        this.requested = 0;
        this.available = 0;
    }

    // Domain-specific getters
    public double getRequested() { return requested; }
    public double getAvailable() { return available; }

    @Override
    public String toString() {
        return "InsufficientFundsException: " + getMessage();
    }
}
// Unchecked custom exception — extends RuntimeException
public class UserNotFoundException extends RuntimeException {
    private final String userId;

    public UserNotFoundException(String userId) {
        super("User not found with ID: " + userId);
        this.userId = userId;
    }

    public UserNotFoundException(String userId, Throwable cause) {
        super("User not found with ID: " + userId, cause);
        this.userId = userId;
    }

    public String getUserId() { return userId; }
}

// Minimum viable custom exception (just message + cause constructors)
public class MinimumBalanceException extends Exception {
    public MinimumBalanceException() {
        super("Balance is below minimum required of ₹5000");
    }
    public MinimumBalanceException(String msg) { super(msg); }
    public MinimumBalanceException(String msg, Throwable cause) { super(msg, cause); }
    public MinimumBalanceException(Throwable cause) { super(cause); }

    @Override
    public String toString() {
        return "MinimumBalanceException: " + getMessage();
    }
}
// Design: build a domain exception hierarchy
// Base domain exception — all app exceptions extend this
public class AppException extends RuntimeException {
    private final String errorCode;

    public AppException(String errorCode, String message) {
        super(message);
        this.errorCode = errorCode;
    }
    public AppException(String errorCode, String message, Throwable cause) {
        super(message, cause);
        this.errorCode = errorCode;
    }
    public String getErrorCode() { return errorCode; }
}

// Domain-specific exceptions extend AppException
public class ValidationException extends AppException {
    public ValidationException(String field, String reason) {
        super("VALIDATION_ERROR", "Validation failed on '" + field + "': " + reason);
    }
}
public class ResourceNotFoundException extends AppException {
    public ResourceNotFoundException(String resource, Object id) {
        super("NOT_FOUND", resource + " with id=" + id + " not found");
    }
}
// Global handler can catch AppException — handles all app errors in one place
class BankAccount {
    private double balance;
    private static final double MIN_BALANCE = 5000;

    public BankAccount(double initialBalance) throws MinimumBalanceException {
        if (initialBalance < MIN_BALANCE)
            throw new MinimumBalanceException();
        this.balance = initialBalance;
    }

    public void withdraw(double amount) throws InsufficientFundsException {
        if (amount <= 0)
            throw new IllegalArgumentException("Amount must be positive");
        if (balance - amount < MIN_BALANCE)
            throw new InsufficientFundsException(amount, balance - MIN_BALANCE);
        balance -= amount;
    }
}

// Usage
try {
    BankAccount acc = new BankAccount(10000);
    acc.withdraw(8000);
} catch (MinimumBalanceException e) {
    System.out.println(e);
} catch (InsufficientFundsException e) {
    System.out.println("Need: "+e.getRequested()+" Available: "+e.getAvailable());
}
💡 Best practice — 4 constructor rule: Always provide all 4 constructors in a custom exception: (), (String message), (String message, Throwable cause), (Throwable cause). This is what Exception itself provides and makes your exception maximally usable by callers.
Java 7+

try-with-resources

Java 7's answer to the verbose finally-based cleanup pattern. Resources are closed automatically in reverse order of declaration — and suppressed exceptions mean the original exception is never lost.

What qualifies as a resource?
  • Must implement AutoCloseable — single method: void close() throws Exception
  • Closeable extends AutoCloseable — close() throws IOException
  • JDK examples: FileReader, BufferedReader, InputStream, Connection, PreparedStatement, ResultSet, Scanner
  • Any custom class implementing AutoCloseable works
Guarantees
  • close() called automatically when try block exits
  • close() called even if exception thrown in try block
  • Multiple resources closed in REVERSE order of declaration
  • close() exceptions stored as suppressed — original preserved
  • Without TWR: close() exception replaces original — root cause lost

Multiple resources + close order
Custom AutoCloseable
Suppressed exceptions

// Basic try-with-resources — resource declared in parentheses
try (FileReader fr = new FileReader("data.txt")) {
    int ch;
    while ((ch = fr.read()) != -1)
        System.out.print((char) ch);
    // fr.close() called automatically here — even if read() throws
} catch (IOException e) {
    System.out.println("Error: " + e.getMessage());
}
// fr is out of scope after the block — already closed

// Java 9+: use effectively-final variable declared outside
FileReader fr = new FileReader("data.txt");
try (fr) {      // no re-declaration needed
    process(fr);
} catch (IOException e) { handle(e); }
// Multiple resources — semicolon separated; closed in REVERSE order
try (
    FileReader     fr = new FileReader("input.txt");   // opened 1st
    BufferedReader br = new BufferedReader(fr);         // opened 2nd
    FileWriter     fw = new FileWriter("output.txt")   // opened 3rd
) {
    String line;
    while ((line = br.readLine()) != null)
        fw.write(line.toUpperCase() + "\n");
    // Close order: fw.close() → br.close() → fr.close()
    // Reverse matters: br wraps fr; br must close before fr
} catch (IOException e) { e.printStackTrace(); }
// Any class implementing AutoCloseable works in try-with-resources
class DBConnection implements AutoCloseable {
    DBConnection() { System.out.println("DB: connected"); }
    void query(String sql) { System.out.println("Running: " + sql); }
    @Override
    public void close() { System.out.println("DB: closed"); }
}

class Transaction implements AutoCloseable {
    Transaction() { System.out.println("TX: begin"); }
    @Override
    public void close() { System.out.println("TX: commit/rollback"); }
}

try (
    DBConnection conn = new DBConnection();
    Transaction  tx   = new Transaction()
) {
    conn.query("SELECT * FROM users");
}
// Output:
// DB: connected
// TX: begin
// Running: SELECT * FROM users
// TX: commit/rollback   ← tx closed first (reverse)
// DB: closed            ← conn closed second
// What happens when BOTH try body AND close() throw exceptions?
class BrokenResource implements AutoCloseable {
    void use()   { throw new RuntimeException("use() failed");   }
    public void close() { throw new RuntimeException("close() failed"); }
}

try (BrokenResource r = new BrokenResource()) {
    r.use(); // throws "use() failed"
    // TWR calls r.close() → throws "close() failed"
    // "close() failed" is SUPPRESSED — attached to "use() failed"
} catch (RuntimeException e) {
    System.out.println("Primary:    " + e.getMessage());         // "use() failed"
    for (Throwable s : e.getSuppressed())
        System.out.println("Suppressed: " + s.getMessage());    // "close() failed"
}

// With manual finally: close() exception REPLACES original — root cause LOST
// TWR: primary exception preserved; close() exception stored as suppressed
// Always check getSuppressed() when debugging resource-related issues
// JDBC example: manual finally (messy) vs try-with-resources (clean)

// BEFORE — 18 lines of boilerplate, easy to miss null checks
Connection conn = null; PreparedStatement ps = null; ResultSet rs = null;
try {
    conn = ds.getConnection();
    ps   = conn.prepareStatement("SELECT * FROM users");
    rs   = ps.executeQuery();
    while (rs.next()) process(rs);
} catch (SQLException e) { handle(e); }
finally {
    if (rs   != null) try { rs.close();   } catch(SQLException x){log(x);}
    if (ps   != null) try { ps.close();   } catch(SQLException x){log(x);}
    if (conn != null) try { conn.close(); } catch(SQLException x){log(x);}
}

// AFTER — 6 lines, guaranteed correct close order, suppressed exceptions handled
try (
    Connection        conn = ds.getConnection();
    PreparedStatement ps   = conn.prepareStatement("SELECT * FROM users");
    ResultSet         rs   = ps.executeQuery()
) {
    while (rs.next()) process(rs);
} catch (SQLException e) { handle(e); }

Exception Chaining — Cause & Effect

Exception chaining preserves the root cause when translating between abstraction layers. Without it, you get "User not found" with no idea why. With it, the full chain — from SQL error to domain exception — is visible in the stack trace.

Basic chaining
Walking the chain
initCause()
// Exception translation — wrap low-level in domain exception, preserve cause
class UserService {
    public User findUser(int id) {
        try {
            return db.query("SELECT * FROM users WHERE id=" + id);
        } catch (SQLException e) {
            // BAD: throw e;                        → leaks DB layer to caller
            // BAD: throw new RuntimeException(e);   → loses message context
            // GOOD: translate + preserve cause
            throw new UserNotFoundException("User not found: id=" + id, e);
        }
    }
}

// Throwable cause constructors (all Exception subclasses should have these):
new Exception(String message, Throwable cause)
new Exception(Throwable cause)               // message auto-set from cause.toString()

// Retrieving the chain
try {
    userService.findUser(99);
} catch (UserNotFoundException e) {
    System.out.println(e.getMessage());              // "User not found: id=99"
    System.out.println(e.getCause().getMessage());  // "Table 'users' doesn't exist"
    e.printStackTrace();
    // UserNotFoundException: User not found: id=99
    //   at UserService.findUser(...)...
    // Caused by: SQLException: Table 'users' doesn't exist
}
// Walking the full exception chain programmatically
void printChain(Throwable t) {
    System.out.println("Exception chain:");
    Throwable current = t;
    int depth = 0;
    while (current != null) {
        System.out.println("  ".repeat(depth)
            + current.getClass().getSimpleName()
            + ": " + current.getMessage());
        current = current.getCause(); // null terminates the chain
        depth++;
    }
}

// Example output for a 3-layer chain:
// Exception chain:
// ServiceException: Order processing failed
//   UserNotFoundException: User not found: id=42
//     SQLException: Connection timed out

// Find root cause utility:
Throwable getRootCause(Throwable t) {
    Throwable cause = t;
    while (cause.getCause() != null) cause = cause.getCause();
    return cause;
}
// initCause() — for legacy exceptions without cause constructor
class OldException extends Exception {
    public OldException(String msg) { super(msg); } // no cause constructor
}

try { doWork(); }
catch (SQLException e) {
    OldException oe = new OldException("DB failure");
    oe.initCause(e); // set cause after construction
    throw oe;
}

// initCause() rules:
// Can only be called ONCE — throws IllegalStateException on second call
// Cannot call if constructor already set cause (via super(msg, cause))
// Always prefer the cause constructor over initCause() in new code

// Printing suppressed + cause together:
void fullDump(Throwable t) {
    t.printStackTrace();           // shows cause chain
    for (Throwable s : t.getSuppressed())
        System.err.println("Suppressed: " + s);

    Integer.parseInt("abc");

    // getMessage() — just the message string
    System.out.println(e.getMessage());      // For input string: "abc"

    // toString() — ClassName: message

    // getSuppressed() — empty array (not a TWR scenario)
    System.out.println(e.getSuppressed().length); // 0

Production Code

Best Practices & Anti-patterns

Exception handling is where junior vs senior code is most visible. These are the patterns interviewers look for — and the anti-patterns that fail interviews.

✓ Best Practices — Do These

1
Catch specific, not general. Catch FileNotFoundException, not Exception. Specific catches allow targeted recovery and prevent accidentally hiding unrelated exceptions.
2
Always preserve the cause. throw new ServiceException("msg", originalException) — without the cause, root-cause debugging is impossible in production.
3
Use try-with-resources for any AutoCloseable. It handles suppressed exceptions correctly, is less verbose, and eliminates the null-check boilerplate.
4
Include context in messages. "User not found: id=42, tenant=acme" vs "User not found" — context is priceless at 2 AM debugging production.
5
Log once, at the boundary. Log the exception where you stop propagating it — not at every intermediate level. Logging and re-throwing creates duplicate noise in logs.
6
Restore interrupted flag after catching InterruptedException: Thread.currentThread().interrupt(). Without this, the interrupt signal is permanently swallowed.

✗ Anti-patterns — Never Do These

Empty catch block
catch(Exception e)
Exceptions for flow
Log and rethrow
return in finally
// ANTI-PATTERN: Empty catch — the silent killer
try {
    importantOperation();
} catch (Exception e) {
    // Completely empty — exception silently swallowed
    // Program continues in unknown/corrupt state
    // No trace — impossible to debug
}

// Also bad: print and swallow
catch (Exception e) {
    e.printStackTrace(); // printed to stderr... nobody reads it in production
    // still swallowed — execution continues in broken state
}

// CORRECT: either handle meaningfully or rethrow
catch (IOException e) {
    log.error("File processing failed for path={}", filePath, e); // real logger
    throw new ProcessingException("Failed to process: " + filePath, e);
}
// ANTI-PATTERN: Pokémon catch — "gotta catch 'em all"
try {
    parseDate(input);
    connectToDatabase();
    executeQuery();
    processResults();
} catch (Exception e) { // catches EVERYTHING including NullPointer = programming bug
    System.out.println("Something went wrong"); // all diagnostic info lost
}

// CORRECT: catch what you expect and know how to handle
try {
    parseDate(input);
} catch (ParseException e) {
    throw new ValidationException("date", "Invalid format", e);
}
try {
    connectToDatabase();
    executeQuery();
} catch (SQLException e) {
    throw new DataAccessException("Query failed", e);
}
// ANTI-PATTERN: Using exceptions for normal control flow
// Creating an exception captures the full stack trace — ~50-1000x slower

// BAD: null check via exception
try {
    String val = map.get("key").toUpperCase(); // NullPointerException if absent
} catch (NullPointerException e) { // using exception as if-statement
    val = "DEFAULT";
}

// CORRECT: guard with a check
String raw = map.get("key");
String val = (raw != null) ? raw.toUpperCase() : "DEFAULT";
// Java 8+: map.getOrDefault("key", "DEFAULT").toUpperCase();

// BAD: parsing with exception as type check
try {
    Integer.parseInt(input); // expect this to throw sometimes — bad design
    return true;
} catch (NumberFormatException e) { return false; }

// CORRECT: use Pattern matching or a library method
return input.matches("-?\\d+");
// ANTI-PATTERN: Log and rethrow at every level — log spam
void method3() throws Exception {
    try { dbOp(); }
    catch (Exception e) { log.error("m3", e); throw e; } // logged here...
}
void method2() throws Exception {
    try { method3(); }
    catch (Exception e) { log.error("m2", e); throw e; } // ...and here...
}
// Same stack trace printed 3 times — log noise, not signal

// CORRECT: let it propagate; log once at the top boundary
void method3() throws Exception { dbOp(); }           // no catch
void method2() throws Exception { method3(); }        // no catch
void boundary() {
    try { method2(); }
    catch (Exception e) { log.error("Operation failed", e); sendError(e); }
} // logged ONCE — clean
// ANTI-PATTERN: return or throw in finally — suppresses original exception
static int bad1() {
    try     { return 1; }    // would return 1...
    finally { return 2; }    // ...finally return WINS. Always returns 2.
}

static void bad2() {
    try     { throw new RuntimeException("original"); }
    finally { throw new RuntimeException("in finally"); } // "original" silently LOST
}

System.out.println(bad1()); // 2 — NOT 1. Confusing, silent.

// CORRECT: finally is for cleanup ONLY — never control flow
try {
    doWork();
} finally {
    if (resource != null) {
        try { resource.close(); }
        catch (Exception e) { log.warn("close failed", e); } // log but don't throw
    }
    // never return; never throw — just clean up
}

Short-answer FAANG questions

❓ Can finally NOT execute?

  • Yes — three cases: System.exit() terminates JVM before finally runs
  • JVM crash (kill -9, power failure, OutOfMemoryError during finally)
  • Infinite loop or deadlock inside the try block
  • In all other cases: finally always executes

❓ Can we have try without catch?

  • Yes — try { } finally { } is valid (no catch block)
  • Exception propagates to caller; finally still runs
  • Common for lock/resource cleanup without handling the exception
  • try alone with no catch and no finally = compile error

❓ catch(Exception e) catches Error?

  • No — Exception and Error are siblings under Throwable
  • catch(Exception e) does NOT catch OutOfMemoryError
  • Use catch(Throwable t) to catch both — almost always a mistake
  • Errors should not be caught; they signal unrecoverable JVM issues

❓ Is NumberFormatException checked?

  • No — NumberFormatException extends IllegalArgumentException extends RuntimeException
  • Unchecked — compiler doesn't force you to handle it
  • Common trap: beginners think parsing exceptions are checked
  • Only ParseException (SimpleDateFormat) is checked

❓ Can you re-throw the same exception?

  • Yes — throw e inside a catch block re-throws the same object
  • Stack trace is PRESERVED (unlike creating a new exception)
  • Original creation point remains in the trace — no information lost
  • Use when you want to log/inspect but not actually handle

❓ What is a suppressed exception?

  • An exception thrown during close() in try-with-resources
  • Attached to the primary exception via addSuppressed()
  • Retrieved via e.getSuppressed() — never null, may be empty
  • With manual finally: close() exception replaces original (information loss)
  • TWR solves this — both exceptions preserved

❓ throw vs throws — one line each

  • throw — inside method body, throws a specific exception instance
  • throws — in method signature, declares what may be thrown
  • throw = action; throws = declaration
  • throw takes ONE object; throws declares ONE OR MORE types

❓ What is exception propagation?

  • Uncaught exception travels up the call stack to the caller
  • Each frame is popped until a matching catch is found
  • Checked exceptions must be declared (throws) at every propagation level
  • If nothing catches it, JVM's default handler prints stack trace and terminates

❓ When to use checked vs unchecked?

  • Checked: recoverable conditions caller should handle (file missing, network down)
  • Unchecked: programming bugs or unrecoverable states
  • Modern Java/Spring: prefer unchecked — avoids polluting method signatures
  • Joshua Bloch (Effective Java): "When in doubt, throw unchecked"

❓ Can a constructor throw an exception?

  • Yes — constructors can throw both checked and unchecked exceptions
  • If constructor throws, the object is NOT created (no partial object returned)
  • Declare checked: MyClass() throws IOException {}
  • Useful for enforcing invariants at construction time

❓ What is NoClassDefFoundError vs ClassNotFoundException?

  • ClassNotFoundException: checked; thrown by Class.forName() — class not in classpath
  • NoClassDefFoundError: unchecked Error; class existed at compile but missing at runtime
  • CNFE: explicit dynamic class loading failed
  • NCDFE: JVM can't find class during normal loading

❓ Multi-catch variable is effectively final?

  • Yes — in catch (A | B e), variable e is implicitly final
  • Cannot reassign: e = new A() inside the block = compile error
  • Types in multi-catch must be unrelated (no IS-A between them)
  • Single-catch variable is NOT final — can be reassigned
Interview Reference

Interview Cheatsheet

One-liners for when you're under pressure. Know these cold.

🏛️ Throwable hierarchy

  • Object → Throwable → Exception + Error
  • Exception → RuntimeException (unchecked) + others (checked)
  • Error: JVM-level, don't catch (OOM, StackOverflow)
  • catch(Exception) does NOT catch Error
  • catch(Throwable) catches both — almost never do this

✅ Checked vs Unchecked

  • Checked: extends Exception (not RuntimeException) — compiler enforces
  • Unchecked: extends RuntimeException — optional to handle
  • Checked: IOException, SQLException, InterruptedException
  • Unchecked: NPE, ArrayIndexOOB, ArithmeticException, ClassCastException
  • Prefer unchecked in modern code

🔀 throw vs throws

  • throw: inside body, throws instance — throw new X()
  • throws: in signature, declares types — void m() throws X, Y
  • throw = action; throws = declaration
  • Code after throw is unreachable

⚡ finally rules

  • Always runs: normal exit, exception, return
  • Does NOT run: System.exit(), JVM crash, infinite loop
  • return in finally OVERRIDES try/catch return
  • throw in finally REPLACES original exception
  • Never put return or throw in finally

🎯 catch ordering

  • Subclass BEFORE superclass — compiler enforces
  • Superclass first = compile error (unreachable catch)
  • Multi-catch (A | B): types must be unrelated
  • Multi-catch variable is implicitly final
  • Exception last (if at all — prefer specific)

♻️ try-with-resources

  • Requires AutoCloseable or Closeable
  • close() called automatically — even if exception thrown
  • Multiple: closed in REVERSE order of declaration
  • TWR suppresses close() exception — original preserved
  • Always prefer over manual finally for resources

🔗 Exception chaining

  • Always pass cause: throw new MyEx("msg", e)
  • getCause() — retrieves the wrapped exception
  • printStackTrace() shows full chain with "Caused by:"
  • Without cause: root-cause debugging is impossible
  • initCause() — legacy; prefer cause constructor

🏗️ Custom exception recipe

  • Checked: extends Exception; Unchecked: extends RuntimeException
  • Provide 4 constructors: (), (msg), (msg, cause), (cause)
  • Add domain-specific fields + getters
  • Override toString() for readable output
  • Build hierarchy: AppException → specific exceptions

📋 Propagation rules

  • Unchecked: propagates silently, no declaration needed
  • Checked: every intermediate method must catch or declare throws
  • Unhandled: JVM default handler prints stack trace + kills thread
  • Set Thread.setUncaughtExceptionHandler() for global fallback

🚨 Top interview traps

  • finally return OVERRIDES try return
  • System.exit() — finally does NOT run
  • Superclass catch before subclass = compile error
  • Multi-catch variable is final — can't reassign
  • catch(Exception) does NOT catch Error
  • Empty catch = silent failure — always log or rethrow
  • return in finally swallows original exception
  • InterruptedException: always restore the flag

  • Catch specific, not general

  • Use try-with-resources for AutoCloseable
  • Include context in exception messages
  • Log once at the boundary — not at every level
  • Never use exceptions for control flow
