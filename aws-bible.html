Cloud Computing & AWS Basics

If you've never touched AWS, start here — everything else in this document is really just "here's a specific tool that solves one piece of the puzzle below." Get this mental model solid first.

What "the cloud" actually means
  • Instead of buying, racking, and maintaining physical servers, you RENT compute/storage/networking from a provider (AWS, Azure, GCP) who owns and runs massive data centers
  • You pay for what you use (pay-as-you-go), and capacity can scale up or down in minutes instead of the weeks/months a physical server purchase would take
  • AWS (Amazon Web Services) is the largest cloud provider — launched 2006, originally built to run Amazon's own e-commerce infrastructure
The three service models — IaaS, PaaS, SaaS
  • IaaS (Infrastructure as a Service) — you get raw virtual machines, storage, and networking; YOU manage the OS, runtime, and app (e.g. EC2 — a virtual server you fully configure)
  • PaaS (Platform as a Service) — AWS manages the OS/runtime; you just deploy your code (e.g. Elastic Beanstalk, Lambda)
  • SaaS (Software as a Service) — a fully finished application you just use (e.g. Gmail, Salesforce — not something you build ON, but might integrate WITH)
AWS Global Infrastructure — Regions, Availability Zones, Edge Locations

Why Region/AZ choice is a genuine interview topic
  • "Design a highly-available app" ALWAYS means "deploy across multiple AZs" — one AZ is a single point of failure
  • Some services are REGIONAL (S3 buckets, most managed services), others are tied to a specific AZ (an EC2 instance, an EBS volume)
  • Cross-region data transfer costs money and adds latency — a real factor in "why did you pick this Region" questions
The Shared Responsibility Model
  • AWS is responsible for security OF the cloud — physical data centers, hardware, the underlying network
  • YOU are responsible for security IN the cloud — your data, IAM configuration, OS patching (for EC2), network configuration (security groups, VPC), application-level security
  • This split SHIFTS depending on the service — for Lambda (serverless), AWS manages far more (no OS to patch); for EC2, you manage far more
💡 Interview framing: a huge fraction of "what AWS services have you used" answers, even from people with real experience, are really just naming services. What actually impresses an interviewer when you have LIMITED hands-on time is being able to explain the SHAPE of a typical deployment — "a Spring Boot app running on [compute service], talking to [database service], behind a [load balancer], with [storage service] for files, secured by [IAM roles + security groups]." This document is built to give you exactly that shape, service by service.
The Foundation of AWS Security

IAM — Identity and Access Management

IAM controls WHO (or WHAT) can do WHAT in your AWS account. It's free, it's the very first thing every AWS account has, and it underlies literally every other security question you'll be asked — "how would you secure X" almost always has "with an IAM policy" as part of the answer.

Users, Groups, Roles — the core entities
  • IAM User — represents a PERSON (or an application with long-term credentials) — has a permanent username/password and/or access keys
  • IAM Group — a collection of users, for attaching the same permissions to many people at once (e.g. a "Developers" group)
  • IAM Role — a set of permissions ASSUMED TEMPORARILY, not tied to one specific person — the critical mechanism for letting AWS SERVICES (EC2, Lambda) securely act on your behalf
Policies — the actual permission documents
  • A JSON document specifying WHO can do WHAT to WHICH resources, and under what conditions
  • Attached to Users, Groups, or Roles — the entity's EFFECTIVE permissions are the union of everything attached to it
  • Principle of Least Privilege — grant ONLY the specific permissions needed, nothing broader — the single most repeated AWS security best practice in every interview guide

Amazon Elastic Compute Cloud

EC2 — Virtual Servers

EC2 gives you a virtual machine ("instance") in the cloud — the closest thing to "just a server," and historically the most common place to run a Java/Spring Boot application before container-based approaches became popular.

Core concepts
  • AMI (Amazon Machine Image) — the template an instance boots from: OS + any pre-installed software (Amazon Linux, Ubuntu, Windows, or a custom AMI you've baked yourself)
  • Instance Type — the hardware profile: CPU/memory/network ratio. Families: t (burstable, cheap, general purpose), m (balanced), c (compute-optimized), r (memory-optimized) — e.g. t3.medium, m5.large
  • Key Pair — SSH public/private key for secure login — AWS keeps the public key, you keep the private key (never uploaded, never recoverable if lost)
Stop vs Terminate — a classic interview distinction
  • Stop — instance shuts down gracefully; EBS root volume is PRESERVED; you're NOT billed for compute while stopped (still billed for the attached EBS storage); can be restarted later with the same data
  • Terminate — instance is permanently destroyed; by default the root EBS volume is DELETED too (unless "delete on termination" is disabled); cannot be undone

Launching a Spring Boot app on EC2 — the manual flow
User Data — bootstrapping on first launch
// The classic (pre-container) way to run a Java app on EC2 — conceptually:
// 1. Launch an EC2 instance from an Amazon Linux AMI
// 2. SSH in using your key pair
// 3. Install a JDK (e.g. via yum/apt or a pre-baked custom AMI)
// 4. Copy your Spring Boot .jar onto the instance (via scp, S3 download, or CI/CD)
// 5. Run it, typically as a systemd service so it restarts automatically on reboot/crash:

// /etc/systemd/system/myapp.service
[Unit]
Description=My Spring Boot App
After=network.target

[Service]
User=ec2-user
ExecStart=/usr/bin/java -jar /opt/myapp/myapp.jar
Restart=always
SuccessExitStatus=143

[Install]
WantedBy=multi-user.target

// sudo systemctl enable myapp && sudo systemctl start myapp
// EC2 "User Data" — a shell script you attach at LAUNCH time, run ONCE
// automatically on first boot — the standard way to bootstrap an instance
// without manual SSH steps, and the basis for Auto Scaling Group instances
// (covered in the Load Balancing & Auto Scaling section) configuring themselves identically

#!/bin/bash
yum update -y
yum install -y java-17-amazon-corretto
aws s3 cp s3://my-deployment-bucket/myapp.jar /opt/myapp/myapp.jar // pull the latest build from S3
systemctl enable myapp
systemctl start myapp

// This is exactly the mechanism that lets an Auto Scaling Group spin up a
// brand new, fully-configured, running instance with ZERO manual steps —
// every new instance runs this same script on boot
💡 Interview framing: if asked "how would you run a Spring Boot app on AWS," EC2-with-systemd is the most fundamental answer — but be ready to immediately follow up with "though in practice I'd lean toward Elastic Beanstalk or ECS/Fargate for easier scaling and deployment automation" (covered in the Deployment Strategies section) — showing you know the manual approach exists AND why production teams usually reach for something higher-level.

// 3. Use THIS custom AMI (instead of a bare Amazon Linux AMI) in your Auto

//    almost immediately, a meaningfully faster and more reliable pattern
//    than "boot bare OS, then run a big install script every time"
💡 Interview one-liner: "EBS is a persistent, single-instance network disk — the default choice for a root volume or a database. Instance Store is fast but ephemeral — fine for scratch space, never for anything you need to survive a stop/terminate. EFS is the one to reach for when MULTIPLE instances need to share the same files, like a common uploads directory across an Auto Scaling fleet."
Simple Storage Service

S3 — Object Storage

The single most-used AWS service across the entire industry, and one of the most likely to have a genuinely detailed follow-up question — especially "how would a Java app let users upload a file to S3."

Core concepts
  • Bucket — a globally-unique-named container for objects (files) — think of it as a top-level "drive"
  • Object — a file plus metadata, identified by a KEY (its full "path" within the bucket, e.g. uploads/2024/receipt.pdf) — S3 is technically a flat key-value store; "folders" are a UI convenience, not a real filesystem hierarchy
  • Effectively unlimited storage, 11 nines of durability (99.999999999%) — achieved by redundantly storing objects across multiple AZs automatically
Storage Classes — the same durability, different cost/access trade-offs
  • S3 Standard — frequently accessed data, higher cost, millisecond access
  • S3 Standard-IA (Infrequent Access) — cheaper storage, small retrieval fee — for data accessed occasionally
  • S3 Glacier / Glacier Deep Archive — very cheap, but retrieval takes minutes to HOURS — for long-term archives/compliance data
  • Lifecycle Policies automate moving objects between classes over time (e.g. "move to Glacier after 90 days") — a real cost-optimization talking point
Presigned URLs — the standard file-upload pattern
Direct upload/download from Java (server-side)
Versioning & MFA Delete
// PROBLEM: you want users to upload files (e.g. profile photos) DIRECTLY to
// S3 from the browser — but you don't want to hand out real AWS credentials
// to every client, and routing large file bytes THROUGH your Spring Boot
// server first wastes bandwidth and server resources

// SOLUTION: a PRESIGNED URL — your backend (which HAS legitimate AWS
// credentials, via its IAM role) generates a temporary, cryptographically-
// signed URL that grants time-limited access to ONE specific S3 operation —
// then hands that URL to the client, who uploads/downloads directly

S3Presigner presigner = S3Presigner.create();

PutObjectRequest objectRequest = PutObjectRequest.builder()
    .bucket("my-app-uploads")
    .key("profile-photos/" + userId + ".jpg")
    .build();

PutObjectPresignRequest presignRequest = PutObjectPresignRequest.builder()
    .signatureDuration(Duration.ofMinutes(15)) // SHORT-lived — expires quickly, limiting exposure
    .putObjectRequest(objectRequest)
    .build();

PresignedPutObjectRequest presignedRequest = presigner.presignPutObject(presignRequest);
String uploadUrl = presignedRequest.url().toString(); // hand THIS to the frontend — it PUTs the file bytes directly to this URL

// The URL grants access ONLY to that exact operation on that exact key,
// only for the duration specified — never broader than that
// When the SERVER itself needs to read/write S3 (e.g. generating a report
// and storing it, or processing an uploaded file server-side)

S3Client s3 = S3Client.builder().region(Region.US_EAST_1).build(); // picks up the instance/task IAM role automatically

// Upload
s3.putObject(
    PutObjectRequest.builder().bucket("my-bucket").key("reports/summary.pdf").build(),
    RequestBody.fromFile(Paths.get("/tmp/summary.pdf"))
);

// Download
ResponseBytes<GetObjectResponse> object = s3.getObjectAsBytes(
    GetObjectRequest.builder().bucket("my-bucket").key("reports/summary.pdf").build()
);
byte[] fileBytes = object.asByteArray();
// VERSIONING — when enabled on a bucket, every overwrite/delete keeps the
// PREVIOUS version instead of destroying it — protects against accidental
// overwrite or deletion, at the cost of storing every version (real $ impact)

// A "delete" on a versioned bucket doesn't actually remove the object —
// it adds a "delete marker" as the latest version; the old versions remain
// recoverable until explicitly purged (often via a lifecycle rule)

// MFA DELETE — an extra layer specifically for versioned buckets: requires
// multi-factor auth to PERMANENTLY delete a version or to disable
// versioning itself — protects against a compromised/mistaken single credential
// causing irreversible data loss on business-critical buckets
💡 Interview one-liner: "For user file uploads, I'd avoid routing bytes through the Spring Boot server entirely — instead, generate a short-lived presigned URL server-side (using the app's IAM role, never a hardcoded credential) and let the client upload directly to S3. It's more scalable, and the app never needs to see or hold the raw file data at all." This is consistently the answer interviewers are fishing for on file-upload design questions.
Your Private Network in AWS

VPC — Virtual Private Cloud

A VPC is your own logically isolated slice of the AWS network — like having your own private data center network, but software-defined. This is consistently the topic where "no hands-on experience" shows most obviously, so it's worth extra attention here.

The anatomy of a typical production VPC 
VPC (e.g. 10.0.0.0/16 — up to ~65,000 IP addresses)
│
├─ PUBLIC SUBNET (e.g. 10.0.1.0/24) — in Availability Zone A
│    Contains: Load Balancer, NAT Gateway
│    Route table sends 0.0.0.0/0 traffic -> Internet Gateway (direct internet access)
│
├─ PRIVATE SUBNET (e.g. 10.0.2.0/24) — in Availability Zone A
│    Contains: EC2 instances / ECS tasks running your Spring Boot app
│    Route table sends 0.0.0.0/0 traffic -> NAT Gateway (OUTBOUND internet only,
│    e.g. to call a 3rd-party API — nothing can initiate a connection INTO this subnet from the internet)
│
└─ PRIVATE SUBNET (e.g. 10.0.3.0/24) — in Availability Zone B
     Contains: RDS database — typically has NO internet route at all, reachable
     only from within the VPC
The core building blocks
  • CIDR block — the IP address range for the VPC (e.g. 10.0.0.0/16), subdivided into smaller ranges for each subnet
  • Subnet — a slice of the VPC tied to ONE specific AZ; marked "public" or "private" based on its ROUTE TABLE, not any inherent property
  • Internet Gateway (IGW) — attached to the VPC, provides the path for PUBLIC subnets to reach (and be reached from) the internet
  • NAT Gateway — sits in a public subnet, lets PRIVATE subnet resources initiate OUTBOUND internet connections (e.g. downloading a package, calling an external API) WITHOUT being reachable from the internet themselves
Why the app server usually goes in a PRIVATE subnet
  • Nothing on the public internet can directly initiate a connection to it — all inbound traffic is forced through the Load Balancer first
  • The database goes in an even MORE restricted private subnet — often with no internet route at all, reachable only from the app tier
  • This "public subnet has only the load balancer, everything else is private" layout is THE standard reference architecture — describing it, even without having built it, demonstrates real understanding

🚫 The single most-asked VPC interview distinction: "Security Groups are STATEFUL, NACLs are STATELESS." Concretely: if you allow inbound port 443 on a Security Group, the response traffic going back out is automatically permitted — you don't need a matching outbound rule. With a NACL, you'd need BOTH an inbound rule allowing 443 in AND an outbound rule allowing the ephemeral return ports out, or the connection breaks. Being able to state this crisply, unprompted, is one of the highest-value single facts in this entire document.
Distributing Traffic, Handling Growth

Load Balancing & Auto Scaling

These two services are almost always discussed together — a Load Balancer distributes incoming traffic across multiple instances; an Auto Scaling Group automatically adjusts HOW MANY instances exist based on demand. Together, they're the standard answer to "how does your app handle traffic spikes and stay available."

Types of Load Balancer
  • ALB (Application Load Balancer) — operates at Layer 7 (HTTP/HTTPS) — can route based on URL path, hostname, headers; the standard choice for a REST API/web app
  • NLB (Network Load Balancer) — operates at Layer 4 (TCP/UDP) — ultra-high performance, static IP support; used for extreme throughput or non-HTTP protocols
  • CLB (Classic Load Balancer) — the legacy, original ELB — largely superseded by ALB/NLB for new workloads
Health Checks — how the LB knows an instance is alive
  • The LB periodically pings a configured endpoint (e.g. /actuator/health — Spring Boot Actuator's standard health endpoint) on each registered instance
  • Instances failing health checks are automatically taken OUT of rotation — no traffic routed to them — until they recover
  • This is exactly why every production Spring Boot app should expose a real health endpoint, not just rely on "the process is running"

Scaling policies
Min / Max / Desired capacity
// TARGET TRACKING — the simplest, most common: "keep average CPU near 50%"
// AWS automatically adds/removes instances to maintain that target — similar
// to a thermostat

// STEP SCALING — more granular control: define specific actions for specific
// metric thresholds, e.g. "CPU > 70% for 5 min -> add 2 instances", "CPU > 90% -> add 4"

// SCHEDULED SCALING — for predictable traffic patterns, e.g. "scale up to
// 10 instances every weekday at 8am, scale down to 2 at 8pm" — common for
// business apps with well-known usage patterns
// Every Auto Scaling Group is configured with three numbers:
// MIN     — the floor; ASG never scales below this, even at zero load
//           (typically >= 2, spread across different AZs, for high availability)
// MAX      — the ceiling; a safety limit against runaway scaling (and runaway cost)
// DESIRED  — the current TARGET the ASG is actively trying to maintain,
//            adjusted automatically by scaling policies within [MIN, MAX]

// Example: min=2, max=10, desired=2 at idle. A traffic spike triggers a
// scaling policy that raises "desired" to 5 -> ASG launches 3 more instances
// automatically to match, registers them with the target group once their
// health checks pass, and they start receiving traffic
💡 Interview one-liner: "A Load Balancer distributes traffic and hides HOW MANY instances exist behind one stable endpoint; an Auto Scaling Group changes how many instances actually exist, based on real-time metrics. Together they mean the app can absorb a traffic spike by adding capacity automatically, and the Load Balancer's health checks ensure traffic only ever reaches instances that are actually healthy."
Relational Database Service

RDS — Managed Relational Databases

RDS runs a real relational database (MySQL, PostgreSQL, MariaDB, Oracle, SQL Server) for you — AWS handles patching, backups, and failover, while you connect exactly like you would to any JDBC-compatible database. This is what almost every Spring Boot + AWS shop uses for its primary datastore.

What RDS manages FOR you
  • Automated backups and point-in-time recovery (restore to any second within your retention window)
  • OS and database engine patching (with a configurable maintenance window)
  • Automated failover for high availability (Multi-AZ, next tab)
  • Storage auto-scaling as your data grows
What it DOESN'T change for your app code
  • It's still just MySQL/Postgres under the hood — your Spring Boot application.properties JDBC URL, Hibernate dialect, and JPA repositories work exactly as if it were a local database
  • The ONLY real difference from a Java code perspective is the connection endpoint (an RDS DNS name) and network/security configuration (VPC, security groups)
Multi-AZ — high availability
Read Replicas — read scalability
Connecting from Spring Boot
// MULTI-AZ: a SYNCHRONOUS standby replica in a DIFFERENT Availability Zone —
// purely for DISASTER RECOVERY / HIGH AVAILABILITY, not for extra read capacity

// - Your app connects to ONE endpoint (the primary) — you never talk to
//   the standby directly
// - Every write is synchronously replicated to the standby BEFORE being
//   acknowledged — guarantees zero data loss on failover, at a small
//   latency cost per write
// - If the primary AZ has an outage, RDS AUTOMATICALLY fails over to the
//   standby (typically 60-120 seconds) and updates the DNS endpoint to
//   point at it — your app just sees a brief connection blip, then
//   traffic resumes against the (now-primary) standby

// THIS IS THE KEY DISTINCTION interviewers check for: Multi-AZ is about
// AVAILABILITY (surviving an outage), NOT about scaling read throughput
// READ REPLICAS: ASYNCHRONOUS copies used to OFFLOAD READ traffic from the
// primary — for SCALING, not disaster recovery

// - You can create MULTIPLE read replicas (unlike Multi-AZ's single standby)
// - Your APPLICATION CODE must explicitly route read-only queries to a
//   replica's endpoint — RDS does NOT do this automatically like Multi-AZ failover does
// - Replication is ASYNCHRONOUS -> replicas can lag slightly behind the
//   primary (usually milliseconds, but under heavy load it can grow) —
//   a real consideration for "read your own write" consistency requirements
// - Can even be promoted to a STANDALONE writable database if needed

🚫 The #1 RDS interview trap: confusing Multi-AZ with Read Replicas. Multi-AZ = ONE synchronous standby, for AVAILABILITY, automatic failover, same endpoint. You can — and in serious production systems often DO — use both together: Multi-AZ for the primary's resilience, plus read replicas for scaling reads.

Serverless Compute

Lambda & Serverless

Lambda runs your code in response to an event, WITHOUT you provisioning or managing any server at all — you upload code (or a container image), AWS handles everything else, and you pay only for the milliseconds your code actually executes.

The core model
  • A Lambda function is TRIGGERED by an event: an API Gateway HTTP request, a new file landing in S3, a message arriving in SQS, a scheduled CloudWatch Event, and many more
  • Each invocation runs in an isolated, ephemeral environment — no server to patch, no OS to manage, scales automatically from zero to thousands of concurrent invocations
  • Billing is per-invocation and per-millisecond of execution time — genuinely $0 when nothing is happening, unlike an always-running EC2 instance
The Java-specific catch: COLD STARTS
  • When a NEW execution environment is needed (first invocation, or after scaling up), AWS must initialize the runtime AND your code before it can run — this is a "cold start"
  • Java's JVM startup + classloading + (for Spring apps) full application context initialization makes Java's cold start noticeably SLOWER than lighter runtimes (Node.js, Python, Go) — often 1-5+ seconds for a Spring Boot app vs tens of milliseconds for Node
  • "Warm" invocations (reusing an already-initialized environment) are fast — the cold start penalty only hits the FIRST request to a fresh environment

// Gateway route — this IS a complete, deployable REST endpoint, no server involved
// Real, commonly-cited mitigation strategies for Java cold starts:

// 1. PROVISIONED CONCURRENCY — pay AWS to keep N execution environments
//    pre-initialized and warm at all times, eliminating cold starts for
//    that reserved capacity (at an ongoing cost, even when idle)

// 2. Use a LIGHTER framework than full Spring Boot for latency-sensitive
//    Lambdas — e.g. plain Java, Micronaut, or Quarkus, which have
//    dramatically faster startup than a full Spring ApplicationContext

// 3. GraalVM NATIVE IMAGE — compile the Java app AHEAD OF TIME into a
//    native binary — near-instant startup, no JVM warm-up at all (Spring
//    Boot 3+ has first-class GraalVM native image support for exactly this reason)

// 4. Minimize dependencies and avoid heavy static initialization in the
//    Lambda's init phase — every unnecessary class loaded adds to cold-start time
// Lambda / serverless fits well:
// - Event-driven, sporadic, or unpredictable workloads (image processing
//   on S3 upload, scheduled cleanup jobs, webhook handlers)
// - Workloads where "pay $0 when idle" genuinely matters
// - Simple, focused, stateless functions

// A traditional server (EC2/ECS) fits better:
// - Consistently high, steady traffic (Lambda's per-invocation cost can
//   exceed a running server's cost at high, sustained volume)
// - Latency-critical APIs where cold starts are unacceptable (unless
//   paying for provisioned concurrency)
// - Long-running processes (Lambda has a hard 15-minute MAXIMUM execution
//   time per invocation)
// - A full, complex Spring Boot monolith — usually a more natural fit as a
//   traditional deployment than shoehorned into Lambda's execution model
💡 Interview one-liner: "Lambda is great for event-driven, bursty, or infrequent workloads where paying $0 at idle matters — but Java's JVM startup means cold starts are a real, well-known trade-off, mitigated with provisioned concurrency, lighter frameworks, or GraalVM native images. For a steady-traffic Spring Boot REST API, I'd more likely reach for ECS/Fargate or EC2 first." Naming the cold-start trade-off unprompted is exactly the kind of production-awareness interviewers are listening for.
The Front Door for APIs

API Gateway

A fully managed service for creating, publishing, and securing APIs — most commonly paired with Lambda for a fully serverless backend, but can also route to EC2, ECS, or any HTTP endpoint.

What it handles for you
  • Request routing — maps HTTP methods + paths (e.g. GET /orders/{id}) to a backend (typically a Lambda function)
  • Authentication/authorization — integrates with IAM, Cognito, or custom Lambda authorizers to gate access before a request ever reaches your code
  • Throttling & rate limiting — protects backends from being overwhelmed, configurable per API key/client
  • Request/response transformation, caching, and automatic API documentation generation
REST API vs HTTP API — the two flavors
  • REST API — the original, more feature-rich option (request validation, more auth options, usage plans) — higher cost, slightly higher latency
  • HTTP API — newer, leaner, cheaper, lower latency — covers the common cases (Lambda/HTTP proxy integration, JWT auth) without the extra features most simple APIs never use
  • Default recommendation for a new, simple serverless API today: HTTP API, unless you specifically need a REST API feature

Why decoupling matters (the actual interview point)
  • Without a queue: if the Inventory Service is down, the Order Service's direct call fails, and the whole order might fail too — a tightly-coupled failure
  • With SQS in between: the message just waits in the queue until Inventory Service is back up and processes it — the Order Service never even notices the outage
  • This is the standard answer to "how would you make Service A resilient to Service B being temporarily unavailable"
Dead Letter Queues (DLQ)
  • A message that repeatedly FAILS processing (consumer keeps throwing an error) is moved to a separate DLQ after a configured number of retries, instead of endlessly retrying or being silently dropped
  • Lets you inspect/alert on poison messages without blocking the main queue — a genuine production-hardening detail worth mentioning

Docker on AWS

Containers — ECS, Fargate & ECR

Containerizing a Spring Boot app (packaging it with Docker) has become the dominant modern deployment pattern — consistent behavior from a developer's laptop through to production, and AWS has purpose-built services for running containers at scale.

The core pieces
  • ECR (Elastic Container Registry) — AWS's private Docker image registry — you push your built image here, ECS/EKS pulls from it
  • ECS (Elastic Container Service) — AWS's own container ORCHESTRATOR — schedules containers ("tasks") onto compute, handles restarts, integrates natively with ALB/CloudWatch/IAM
  • Task Definition — the blueprint for a container: which image, how much CPU/memory, environment variables, port mappings — analogous to a Kubernetes Pod spec, but ECS-specific
ECS Launch Types: EC2 vs Fargate
  • ECS on EC2 — YOU manage a fleet of EC2 instances that ECS schedules containers onto; more control, can use Spot/Reserved instances for cost savings, but you patch the underlying hosts
  • ECS on Fargate — fully SERVERLESS containers — no EC2 instances to manage at all, AWS handles the underlying compute; simpler operations, typically higher $/vCPU cost than well-utilized EC2

Automating Deployment

CI/CD Pipelines on AWS

Manually building and uploading a jar every time doesn't scale to a real team — AWS's native CI/CD services automate the build → test → deploy pipeline, though many teams also use GitHub Actions/Jenkins/GitLab CI that simply CALL these same AWS services.

The standard AWS-native pipeline 
Git push (CodeCommit / GitHub)
   │
   ▼
CodePipeline  (orchestrates the whole flow, triggers on each commit)
   │
   ├─▶ CodeBuild   — runs `mvn clean package`, runs tests, builds a Docker image, pushes to ECR
   │
   └─▶ CodeDeploy  — deploys the new version to EC2 / ECS / Lambda, following a
                      configured deployment strategy (see below)
The three services, briefly
  • CodePipeline — the overall orchestrator: defines STAGES (source → build → test → deploy) and triggers automatically on a new commit
  • CodeBuild — a managed build environment: compiles code, runs tests, produces build artifacts (a jar, or a Docker image) — think "Jenkins build agent, but managed"
  • CodeDeploy — automates the actual deployment to EC2, ECS, or Lambda, including the rollout STRATEGY
Deployment strategies — how the new version rolls out
  • In-place / rolling — update instances one batch at a time; simple, but a brief mixed-version state during rollout
  • Blue/Green — deploy the NEW version to entirely separate infrastructure, then SWITCH traffic over once healthy — near-zero downtime, and instant ROLLBACK is just switching traffic back
  • Canary — shift a small percentage of traffic (e.g. 10%) to the new version first, monitor for errors, then gradually increase — limits the "blast radius" of a bad deploy
💡 Interview one-liner: "For zero-downtime deploys, I'd favor a blue/green strategy — spin up the new version alongside the old one, run health checks against it, then cut the load balancer over. If something's wrong, rolling back is just switching traffic back to the known-good environment, rather than trying to undo a partially-completed rolling update." Naming blue/green specifically (not just "I'd use CI/CD") is a strong, concrete signal.
Infrastructure as Code

CloudFormation & Infrastructure as Code

Manually clicking through the AWS Console to create a VPC, EC2 instances, an RDS database, and IAM roles is slow, error-prone, and impossible to reliably reproduce. Infrastructure as Code (IaC) defines all of that infrastructure in a text file, version-controlled just like application code.

Why IaC matters (the real interview point)
  • Reproducibility — spin up an identical staging environment from the same template used for production
  • Version control — infrastructure changes go through the same code review / git history as application code
  • Disaster recovery — if a whole environment is lost, re-running the template rebuilds it, rather than hoping someone remembers every manual click that was ever made
CloudFormation vs CDK vs Terraform
  • CloudFormation — AWS's native IaC service; templates in YAML/JSON; AWS-only
  • AWS CDK (Cloud Development Kit) — define infrastructure using REAL programming languages (Java, TypeScript, Python) that COMPILE DOWN to a CloudFormation template — lets Java developers define infra in Java itself, a genuinely relevant tool to mention
  • Terraform — a third-party (HashiCorp) tool, multi-cloud (works across AWS/Azure/GCP), extremely widely adopted in the industry — often the answer when a company isn't AWS-exclusive

Seeing What's Actually Happening

CloudWatch & Observability

AWS's native monitoring service — metrics, logs, and alarms across virtually every AWS resource, plus your own application's custom metrics and logs.

The three pillars
  • Metrics — numeric time-series data: CPU utilization, request count, latency, custom application metrics (e.g. "orders processed per minute")
  • Logs — CloudWatch Logs collects application/system log output (e.g. everything your Spring Boot app writes to stdout when running on ECS/Lambda) into searchable log groups
  • Alarms — trigger an action (SNS notification, Auto Scaling action, or a Lambda function) when a metric crosses a defined threshold — this is exactly what feeds Auto Scaling's scaling policies
CloudWatch vs CloudTrail — a common mix-up
  • CloudWatch — monitors PERFORMANCE and OPERATIONAL health: "is CPU high, are there errors, is latency spiking"
  • CloudTrail — logs API-level AUDIT activity: "WHO made WHAT change to WHICH resource, and WHEN" — critical for security investigations and compliance, not performance monitoring
  • Interview shorthand: CloudWatch = "is it working right now," CloudTrail = "who did what, historically"
Spring Boot Actuator → CloudWatch — the standard observability pairing

// CloudWatch automatically, with almost no custom code

// application.properties
management.metrics.export.cloudwatch.namespace=MyApp
management.metrics.export.cloudwatch.step=1m
management.endpoints.web.exposure.include=health,info,metrics

// This is exactly the "health,info,metrics" endpoint the Load Balancer's
// health check (from the Load Balancing section) and CloudWatch dashboards
// both plug into — the same Actuator setup does double duty
💡 Interview one-liner: "I'd expose Spring Boot Actuator's health and metrics endpoints, feed them into CloudWatch via Micrometer, and set alarms on key thresholds — error rate, p99 latency, CPU — that notify via SNS and feed the Auto Scaling Group's scaling policies. For anything security or audit-related — who changed a security group, who deleted a resource — that's CloudTrail, not CloudWatch."
DNS & Content Delivery

Route 53 & CloudFront

Two services that usually sit at the very FRONT of a user's request — before it ever reaches your Load Balancer or app servers.

Route 53 — DNS as a service
  • Translates a domain name (api.myapp.com) into an IP address / resource — the entry point for literally every request
  • Supports advanced ROUTING POLICIES beyond simple DNS: Weighted (split traffic by percentage, e.g. for A/B testing or gradual rollout), Latency-based (route to the Region closest to the user), Failover (route to a backup Region if the primary is unhealthy), Geolocation (route based on the user's location)
  • Also functions as a domain registrar (you can buy domains directly through it)
CloudFront — AWS's CDN
  • Caches content at Edge Locations physically close to users worldwide — dramatically reduces latency for static assets (JS/CSS/images) and can also cache/accelerate dynamic API responses
  • Sits in front of S3 (for static frontend hosting — a very common React/Angular deployment pattern) or in front of an ALB (for a full application, including API responses)
  • Reduces load on your actual origin servers — repeat requests for the same content are served straight from the edge cache, never reaching your backend at all
The classic "React frontend + Spring Boot API" deployment shape 
User
   │

   │
   ▼

   └─▶ /api/* requests ───────────────▶ Application Load Balancer ──▶ Spring Boot app (ECS/EC2)

AWS SDK for Java & Spring Cloud AWS

Everything covered so far is "what the services do" — this section is specifically "how your Java code actually talks to them," tying the whole document back to code you could plausibly write.

AWS SDK for Java v2
  • The official, low-level Java client library for every AWS service — S3Client, SqsClient, DynamoDbClient, etc., all seen in earlier sections

Short-answer conceptual questions

❓ Security Groups vs NACLs — what's the actual difference?

  • Security Groups: instance-level, STATEFUL (return traffic auto-allowed), ALLOW rules only
  • NACLs: subnet-level, STATELESS (must explicitly allow both directions), supports ALLOW and DENY

❓ Multi-AZ RDS vs Read Replicas — when would you use each?

  • Multi-AZ: synchronous standby, for AVAILABILITY/disaster recovery, automatic failover, same endpoint
  • Read Replicas: asynchronous copies, for READ SCALING, app must route reads explicitly, can lag

❓ Why would you use an IAM Role instead of an IAM User's access keys?

  • Roles issue short-lived, auto-rotating credentials — no static secret to leak or manage
  • The AWS SDK's default credential chain picks up an attached instance/task role automatically

❓ SQS vs SNS — what's the core difference?

  • SQS: point-to-point queue — one message, consumed by exactly one worker
  • SNS: pub/sub fan-out — every subscriber gets a copy of every message

❓ What's a cold start, and why does it matter specifically for Java on Lambda?

  • The delay when a fresh execution environment must initialize the runtime + your code before running
  • Java's JVM startup + classloading (and Spring's full context init) makes it notably slower than Node/Python — mitigated with provisioned concurrency, lighter frameworks, or GraalVM native images

❓ What does "the app runs in a private subnet" actually mean, and why do it?

  • The subnet's route table has no path to an Internet Gateway — nothing on the public internet can initiate a connection directly to resources there
  • All inbound traffic is forced through the Load Balancer in the public subnet first — a real reduction in attack surface

❓ How does Auto Scaling actually decide to add/remove instances?

  • Watches a CloudWatch metric (e.g. average CPU) against a target-tracking, step, or scheduled scaling policy
  • Adjusts the ASG's "desired capacity" within its configured min/max bounds; new instances register with the target group once they pass health checks

❓ What's the difference between CloudWatch and CloudTrail?

  • CloudWatch: operational monitoring — metrics, logs, alarms — "is it healthy right now"
  • CloudTrail: API-level audit log — "who did what, to which resource, and when" — for security/compliance

❓ RDS vs DynamoDB — how would you decide?

  • RDS: relational data, complex queries/joins, strong ACID transactions, a typical CRUD business app
  • DynamoDB: known, simple key-based access patterns at massive scale, flexible schema, horizontal scaling by design

❓ Why containerize with ECS/Fargate instead of deploying directly to EC2?

  • Consistent behavior from local dev through production (the same Docker image everywhere)
  • Fargate removes EC2 patching/management entirely; each service scales independently
  • Easier to run multiple isolated microservices on shared infrastructure without manual instance juggling

❓ What is Infrastructure as Code, and why does it matter?

  • Defining infrastructure (VPCs, EC2, RDS, IAM) in version-controlled text/code rather than manual console clicks
  • Enables reproducible environments, code review for infra changes, and reliable disaster recovery

❓ What's a blue/green deployment, and why prefer it over a rolling update?

  • Deploy the new version to entirely separate infrastructure, verify it's healthy, then cut traffic over
  • Rollback is instant (switch traffic back) versus trying to undo a partially-completed rolling update

Interview Cheatsheet

☁️ Cloud basics

  • IaaS (EC2) — you manage OS/runtime. PaaS (Beanstalk/Lambda) — AWS manages more
  • Region = geographic area. AZ = independent data center within a Region
  • Shared Responsibility: AWS secures the cloud, YOU secure what's IN it

  • Users = people/long-term creds. Roles = temporary, assumed permissions
  • EC2/Lambda/ECS → always use a ROLE, never hardcoded access keys
  • Least privilege — grant only what's needed, nothing broader

🖥️ EC2 quick facts

  • Stop = EBS preserved, no compute billing. Terminate = permanently destroyed
  • On-Demand (flexible) / Reserved (steady, discount) / Spot (interruptible, cheap)
  • EBS = persistent single-instance disk. EFS = shared across many instances

🪣 S3 essentials

  • Flat key-value store — "folders" are a UI convenience only
  • Presigned URL = client uploads directly to S3, server never touches the bytes
  • Lifecycle policies auto-transition objects to cheaper storage classes over time

🌐 VPC — the #1 fact

  • Security Groups: instance-level, STATEFUL, allow-only
  • NACLs: subnet-level, STATELESS, allow + deny
  • Public subnet → has an Internet Gateway route. Private → doesn't (may use NAT for outbound)

⚖️ Load Balancing & Auto Scaling

  • ALB = Layer 7 (HTTP). NLB = Layer 4 (TCP), extreme throughput
  • Health checks pull unhealthy instances out of rotation automatically
  • ASG: min/max/desired capacity, driven by CloudWatch-metric-based scaling policies

🗄️ RDS — the #1 fact

  • Multi-AZ = synchronous standby, for AVAILABILITY, automatic failover
  • Read Replica = asynchronous copy, for READ SCALING, app must route explicitly
  • Can — and often should — use both together

📊 DynamoDB vs RDS

  • RDS: relational, joins, ACID — typical business CRUD
  • DynamoDB: known key-based access patterns, massive horizontal scale, flexible schema

⚡ Lambda essentials

  • Event-driven, pay-per-invocation, scales to zero
  • Java cold starts are real — mitigate with provisioned concurrency, lighter frameworks, or GraalVM native image
  • 15-minute max execution time per invocation

📨 SQS vs SNS

  • SQS: point-to-point queue, one consumer per message
  • SNS: pub/sub fan-out, every subscriber gets a copy

🚀 Deploying Spring Boot
