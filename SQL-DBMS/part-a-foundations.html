1 · DBMS core concepts

A DBMS is software that lets you create, query, update and administer data while enforcing rules about its shape and integrity. An RDBMS (PostgreSQL, MySQL, Oracle, SQL Server) is a DBMS built around the relational model: data lives in tables (relations), rows are tuples, and relationships are expressed through shared key values rather than physical pointers.

The interview-relevant question is rarely "what is a DBMS" — it's why relational, and when not. Be ready to argue both directions.

Relational (SQL)Non-relational (NoSQL)
SchemaFixed, enforced at write timeFlexible / schema-on-read
Consistency modelStrong, ACID by defaultOften tunable — eventual to strong
RelationshipsFirst-class (joins, FKs)Denormalized / embedded, app-managed
Scale patternVertical first, horizontal via shardingHorizontal by design (partition-native)
Best fitTransactional systems, financial data, anything needing multi-row invariantsHigh write throughput, flexible/evolving schema, huge single-key lookups
Interview framing that scores well: "I'd reach for Postgres when the data has strong relationships and I need transactional guarantees — orders, ledgers, inventory. I'd reach for a document or wide-column store when access patterns are simple key lookups at massive scale, like a session store or activity feed, and I'm willing to denormalize." This is almost verbatim what gets asked in the DB-choice portion of "Design X" system-design rounds.

CAP theorem gets name-dropped constantly but is usually mis-explained. It only applies during a network partition: you must choose between Consistency (every read sees the latest write) and Availability (every request gets a response). Outside of a partition, you can have both. A single-node Postgres instance is CA in practice — the tradeoff becomes real once you replicate across nodes.

2 · ER modeling & schema design

An Entity-Relationship diagram is the design step before tables exist. Interviewers use it to see whether you can translate a fuzzy business description into a clean structure before you touch SQL.

Vocabulary you must use precisely:

  • Entity — a thing with independent existence (Student, Order, Book).
  • Weak entity — cannot be uniquely identified without its owning entity (an OrderLineItem only makes sense tied to an Order; its key is a composite of the owner's key + a discriminator).
  • Attribute — simple, composite, derived, or multi-valued (multi-valued attributes signal you need a separate table, not a comma-separated column).
  • Cardinality — 1:1, 1:N, M:N. M:N always resolves into a junction/associative table with two FKs.

Worked example — "Design a schema for a library system" (a real recurring prompt):

Book (1) ────── (N) BookCopy ────── (N) Loan ────── (N) ────── (1) Member book_id PK copy_id PK loan_id PK member_id PK title book_id FK copy_id FK isbn status member_id FK checkout_date due_date return_date (nullable) Book ── (N) ── BookAuthor ── (N) ── Author <-- resolves the M:N book_id FK book_id author_id FK ─── Author.author_id PK

Notice the reasoning, which is what's actually being graded: a Book (the title, "Dune") is distinct from a BookCopy (a specific physical copy that can be checked out) — collapsing these is the single most common mistake candidates make, and it's exactly the kind of subtlety that separates a 1:1-thinking SDE1 answer from an SDE2 one. Loan is a genuine entity (not just a join table) because it carries its own attributes (dates) that don't belong to either Member or BookCopy.

Common trap: modeling a many-to-many relationship as two foreign keys jammed into one of the two tables instead of a junction table. If you find yourself repeating rows to represent multiple associations, you're missing a table.

When asked to "design a schema" cold, narrate this order out loud — it reads as structured thinking rather than guessing:

  1. List the core entities (nouns in the prompt).
  2. For each pair of entities, state the cardinality and whether the relationship itself needs attributes.
  3. Resolve every M:N into a junction table.
  4. Assign primary keys (prefer surrogate keys for anything mutable — see Module 3).
  5. Only then write CREATE TABLE.

3 · Keys & constraints

Constraints are the database's way of refusing to store nonsense, regardless of what your application code does or forgets to do. Interviewers probe this because ORM-shaped developers sometimes think validation belongs only in the app layer.

Key typeDefinitionNotes
Primary key (PK)Uniquely identifies a row; implies NOT NULL + UNIQUEExactly one per table. Prefer a surrogate (auto-increment / UUID) over a natural key that might legitimately change (email, SSN).
Candidate keyAny column set that could serve as PKThe one you don't pick becomes a...
Unique key / alternate keyEnforces uniqueness, allows NULLse.g. email when the surrogate id is the PK.
Foreign key (FK)References a PK/unique key in another tableEnforces referential integrity — you cannot insert an order for a customer_id that doesn't exist.
Composite keyPK made of >1 columnCommon in junction tables: (book_id, author_id).
Super keyAny superset of a candidate key that's still uniqueMostly a normalization-theory term (see Part B, BCNF).

Constraint types beyond keys:

CREATE TABLE loan (
  loan_id       BIGSERIAL PRIMARY KEY,
  copy_id       BIGINT NOT NULL REFERENCES book_copy(copy_id),
  member_id     BIGINT NOT NULL REFERENCES member(member_id),
  checkout_date DATE NOT NULL DEFAULT CURRENT_DATE,
  due_date      DATE NOT NULL,
  return_date   DATE,
  CHECK (due_date > checkout_date),
  CHECK (return_date IS NULL OR return_date >= checkout_date)
);
  • NOT NULL — domain integrity; a due date must exist.
  • CHECK — arbitrary boolean invariant on a row (or, in Postgres, across columns).
  • UNIQUE — no two rows share a value (or tuple of values).
  • FOREIGN KEY ... ON DELETE — decide the behavior explicitly: CASCADE (delete children too), RESTRICT/NO ACTION (block the delete), SET NULL (orphan gracefully). Interviewers like asking which you'd pick for a specific relationship — e.g. deleting a Member who still has an open Loan should be RESTRICT, not CASCADE, because silently deleting loan history is a data-integrity bug waiting to happen.
A strong interview answer, condensed: "Entity integrity is enforced by the primary key, referential integrity by foreign keys, and domain integrity by CHECK/NOT NULL/data types. I push as many of these into the schema as possible — application-level validation can be bypassed by a bad migration, a second service, or a manual psql session; a CHECK constraint can't."

NULL semantics deserve their own paragraph because they trip people up in both DBMS theory and SQL practice: NULL means "unknown," not zero or empty string. This is why NULL = NULL evaluates to NULL (not true), why you need IS NULL instead of = NULL, and why a NULL in a UNIQUE column doesn't collide with another NULL (per SQL standard — Postgres follows this).

Popular interview questions — Foundations

Asked almost verbatim across Amazon, Google, Uber and Flipkart-style loops. Try answering out loud before opening each one.

When would you choose a relational database over a NoSQL store, concretely?

When the data has real relationships that must stay consistent across multiple rows/tables — orders touching inventory and payments — and you need multi-row transactional guarantees. Pick NoSQL when the access pattern is simple key-based lookups at very high write throughput and the schema will keep evolving (activity feeds, session stores, product catalogs with wildly varying attributes).

Explain CAP theorem without hand-waving.

CAP only bites during a network partition between nodes. You then choose Consistency (every node returns the latest write, at the cost of refusing some requests) or Availability (every node answers, possibly with stale data). Outside a partition you can have both — a single-node Postgres is not "sacrificing" anything; CAP is irrelevant until you replicate across a network boundary.

Weak entity vs strong entity — give a concrete example.

A strong entity has its own primary key and independent existence (Book). A weak entity has no independent identity — it's identified only via its owner's key plus a discriminator (an OrderLineItem is meaningless without its Order; its key is (order_id, line_number)).

How do you model a many-to-many relationship?

Introduce a junction (associative) table with a foreign key to each side, and a composite primary key of both foreign keys (or a surrogate key plus a unique constraint on the pair). If the relationship itself has attributes — like a Loan having checkout/due dates between Member and BookCopy — that table is a genuine entity, not just a join table.

Primary key vs unique key — what's the actual difference?

Both enforce uniqueness. A primary key additionally forbids NULLs and there can only be one per table (it's the canonical identity). A table can have several unique keys/constraints, and unique columns (other than the PK) may allow a NULL, per the SQL standard.

Candidate key vs super key vs primary key?

A super key is any column set that uniquely identifies a row (possibly with redundant extra columns). A candidate key is a minimal super key — remove any column and uniqueness breaks. The primary key is the one candidate key you choose to be the table's official identity; the rest become alternate/unique keys.

What does ON DELETE CASCADE do, and when should you avoid it?

It automatically deletes child rows when the referenced parent row is deleted. Avoid it whenever the child rows are historical or audit-relevant — e.g. deleting a Member should not silently cascade-delete their Loan history; use RESTRICT there and force an explicit, intentional cleanup path instead.

Why doesn't NULL = NULL evaluate to TRUE?

NULL represents "unknown," not a value. Comparing two unknowns can't logically resolve to true or false, so SQL returns NULL (which is treated as not-true in a WHERE clause). This is why you must use IS NULL / IS NOT NULL rather than =.
