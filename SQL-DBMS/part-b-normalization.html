4a · Update, insert & delete anomalies

Anomalies are the actual problem that normalization solves — if you can't name them concretely, "normalize this table" answers come out as memorized rules with no motivation. All three anomalies come from the same root cause: one fact is stored redundantly, in multiple rows, instead of once.

Use one deliberately bad table as the running example for the rest of this part:

-- Denormalized "orders" table (the starting point)
order_id | customer_name | customer_email | product_name | product_price | qty | supplier_name | supplier_country
   1     | Asha Rao      | asha@x.com     | USB-C Cable  | 499           |  2  | Anker         | China
   2     | Asha Rao      | asha@x.com     | USB-C Cable  | 499           |  1  | Anker         | China
   3     | Ravi Iyer     | ravi@x.com     | Mechanical KB| 3499          |  1  | Keychron      | China
AnomalyWhat it meansConcrete failure in the table above
Insert anomalyYou cannot record fact A without also being forced to record unrelated fact B, because they live in the same row.You cannot add a new product ("Wireless Mouse") to the catalog until someone places an order for it — product_name/product_price only exist attached to an order_id. A product with zero orders has no row to live in.
Update anomalyA single real-world fact is duplicated across many rows, so changing it means updating N rows — miss one and the data is now internally inconsistent.Anker raises the price of the USB-C Cable to ₹599. You must update it in every order row that mentions that product (rows 1 and 2). Update only row 1 and the table now asserts the same product had two different prices at the same time — a silent correctness bug, not a crash.
Delete anomalyDeleting one fact accidentally erases a second, unrelated fact that happened to be riding along in the same row.Delete order 3 (a return/cancellation) and you lose all knowledge that "Mechanical KB" exists, that it costs 3499, and that Keychron (based in China) supplies it — because that product's only row was that one order.
The mental model interviewers are checking for: anomalies aren't three unrelated rules to memorize — they're three symptoms of the same disease (a fact that should be atomic and singular is instead smeared across many rows). Normalization is the cure: move each fact to the one table where it belongs, referenced by key rather than repeated by value.

4b · Normalization: 1NF → BCNF → 4NF

Normalization is the discipline of structuring tables so that each fact is stored in exactly one place. Each normal form is a progressively stricter rule, and each one happens to eliminate a specific anomaly from the list above as a side effect — that mapping, explicitly, is below.

FormRuleWhat it removes
1NFEvery column holds a single atomic value; no repeating groups.If a "products" column held a comma-separated list, that violates 1NF — split into a line-items table.
2NF1NF, and every non-key attribute depends on the whole composite key, not part of it.Only matters with composite PKs. Here, product_price depends only on product_name, not on order_id — a partial dependency. Move product data to its own table.
3NF2NF, and no transitive dependency (non-key attribute depending on another non-key attribute).supplier_country depends on supplier_name, not on the order or the product directly. Split suppliers out.
BCNFFor every functional dependency X → Y, X must be a superkey.Catches edge cases 3NF misses when a table has multiple overlapping candidate keys (classic example below).
4NFNo multi-valued dependencies independent of each other in the same table.e.g. a table of (employee, skill, language) where skills and languages are independent — split into two tables, not one cross-product.

Now the mapping interviewers actually want you to say out loud — which step fixes which anomaly from 4a, and why:

Anomaly (from 4a)Fixed byMechanism
Insert anomaly — can't add a product without an order2NF splitProduct becomes its own table with its own PK (product_id). It can now be inserted independent of whether any order references it yet.
Update anomaly — price duplicated across every order row2NF split (removing the partial dependency of price on product_name alone, not the whole order key)Price is stored exactly once, in the product row. Every order references it by product_id; changing the price is a single-row UPDATE.
Delete anomaly — deleting the only order erases the product/supplier facts2NF (product table) + 3NF (supplier table)Product and supplier rows exist independently of any order row, so deleting an order (or even all orders for that product) leaves catalog and supplier data intact.
Repeating/non-atomic groups (e.g. a comma-separated tags column)1NFSplit into a child table with one tag per row — this is a prerequisite fix, enabling the rest of the pipeline; it doesn't by itself remove update/delete anomalies.

Applying 1NF→3NF to the orders table above gives:

customer(customer_id PK, name, email)
product(product_id PK, name, price, supplier_id FK)
supplier(supplier_id PK, name, country)
order_header(order_id PK, customer_id FK, order_date)
order_line(order_id FK, product_id FK, qty, PRIMARY KEY(order_id, product_id))

3NF vs BCNF — the answer that's actually being tested. The textbook counter-example: a table (student, course, instructor) where each course can have several instructors, but each instructor teaches only one course, and a student can take a course from multiple instructors. Functional dependency: (student, course) → instructor and also instructor → course. This is in 3NF (every non-key attribute is on a candidate key), but violates BCNF, because instructor is not a superkey yet determines course. The fix is splitting into (instructor, course) and (student, instructor).

The one-sentence answer that satisfies most interviewers: "3NF allows a non-prime attribute to determine another non-prime attribute as long as the determinant is part of a candidate key; BCNF is stricter — every determinant must be a candidate key on its own. BCNF can occasionally sacrifice a dependency that 3NF preserved, which is why 3NF is the pragmatic industry default and BCNF is mostly an academic ceiling."

5 · Denormalization: when product companies break the rules on purpose

Normalization optimizes for write integrity and storage. It does not optimize for read latency — a fully 3NF schema for a social feed might need 6 joins to render one screen. Product companies denormalize deliberately, and being able to argue the tradeoff is exactly what separates a bookish answer from an SDE2 answer.

Signal favoring normalizationSignal favoring denormalization
Write-heavy, correctness-critical (ledgers, inventory, billing)Read-heavy, latency-sensitive (feeds, product pages, dashboards)
Data changes often and must stay consistent everywhereData is written once, read millions of times (comment_count, order snapshot)
Storage cost matters more than CPU-at-query-timeYou can tolerate slightly stale derived data

Common, interview-safe denormalization patterns:

  • Precomputed counters — storing like_count directly on a post row instead of running COUNT(*) over a likes table on every read, updated via trigger or async job.
  • Snapshotting — an order_line storing the product's price_at_purchase and product_name at time of sale, even though that duplicates the product table — because a later price change must never retroactively alter historical invoices. This is not sloppiness; normalizing this away would be a bug.
  • Materialized views (see Part E) — get the query performance of a denormalized table while keeping the source tables normalized; the tradeoff shifts from "duplicated, always in sync" to "duplicated, refreshed on a schedule."
Interview line worth memorizing: "I normalize by default for correctness, then denormalize surgically at proven hot paths — usually by adding a derived column or a materialized view rather than restructuring the source-of-truth tables. I try to keep exactly one normalized source of truth and treat every denormalized copy as a cache with an explicit invalidation or refresh strategy."

Popular interview questions — Normalization

Name the three anomalies in an unnormalized table, with a one-line example each.

Insert: can't add a product to the catalog without an order to attach it to. Update: a price change must be applied to every row that repeats it, or the data goes inconsistent. Delete: removing the only order for a product wipes out that product's catalog data entirely.

Difference between 3NF and BCNF, precisely?

3NF forbids a non-key attribute from determining another non-key attribute, but allows a determinant that's only part of a candidate key if it's still "prime." BCNF is stricter: every determinant in any functional dependency must be a candidate key on its own, full stop. The classic separating example is a (student, course, instructor) table where instructor → course but instructor alone isn't a candidate key — 3NF-compliant, BCNF-violating.

Can a table be in BCNF but not 4NF?

Yes. BCNF only concerns single-valued functional dependencies. A table like (employee, skill, language) — where an employee's skills and languages are independent lists — can satisfy BCNF (no non-trivial FDs beyond the whole key) while still needing to be split for 4NF, because it has two independent multi-valued dependencies forced into one cross-product table.

Is normalization always good? When would you deliberately break it?

No — normalization optimizes for write integrity and storage, not read latency. Product companies denormalize deliberately for read-heavy, latency-sensitive paths (precomputed counters, materialized views) or for correctness-preserving snapshots (storing the price at time of purchase on an order line, so a later catalog price change doesn't rewrite history).

What does 1NF actually fix, versus what does it merely enable?

1NF removes repeating groups / non-atomic values (a comma-separated column becomes its own child table). By itself it doesn't remove update or delete anomalies — it's a prerequisite that makes the table row-per-fact enough for 2NF/3NF to do that work.

What's a transitive dependency, in one sentence?

A non-key attribute depends on another non-key attribute rather than directly on the primary key — e.g. supplier_country depends on supplier_name, which depends on the key, rather than depending on the key itself; 3NF removes this by moving supplier facts to their own table.

Give a real product-company example of intentional denormalization and justify it.

Storing comment_count directly on a post row instead of computing COUNT(*) from a comments table on every page render. Justification: the read path (viewing a post) vastly outnumbers the write path (adding a comment), and a small, well-defined staleness window (updated via trigger or async job) is an acceptable tradeoff for avoiding a full table scan/aggregate on every view.
