25 · SQL injection & access control

SQL injection happens when untrusted input is concatenated directly into a query string, letting an attacker change the query's structure, not just its data:

-- Vulnerable: string concatenation
String query = "SELECT * FROM users WHERE username = '" + input + "'";
-- input = "' OR '1'='1"  turns the query into:
-- SELECT * FROM users WHERE username = '' OR '1'='1'   -- returns every row

The fix is always parameterized queries / prepared statements — input is sent to the database separately from the query structure, so it's bound as a literal value and can never be interpreted as SQL:

-- Safe: parameterized
PreparedStatement stmt = conn.prepareStatement("SELECT * FROM users WHERE username = ?");
stmt.setString(1, input);
Interview trap: "escaping quotes" (manually replacing ' with '') is a legacy, error-prone mitigation, not the answer to give first — there are always encoding edge cases it misses. Lead with parameterized queries/ORMs that parameterize by default; mention escaping only as the historical alternative.

Defense in depth beyond parameterization: least-privilege database accounts (the application's DB user shouldn't have DROP/ALTER rights it never needs), input validation as a second layer (not a replacement), and never building dynamic SQL by interpolating identifiers (table/column names) from user input at all if avoidable — parameterization doesn't cover identifiers, only values.

Access control (DCL — Data Control Language):

CREATE ROLE app_readonly;
GRANT SELECT ON orders, customer TO app_readonly;

CREATE ROLE app_writer;
GRANT SELECT, INSERT, UPDATE ON orders TO app_writer;
REVOKE DELETE ON orders FROM app_writer;   -- explicit even if never granted, for clarity in review

Standard pattern: define roles by function (read-only reporting user, application writer, migration/admin user) rather than granting broad permissions to a single shared credential — this limits blast radius if any one credential leaks, and makes an audit ("what can this service actually do") answerable at a glance.

26 · Zero-downtime migrations & production failure patterns

The core problem: a naive schema change (add a NOT NULL column, rename a column, change a type) can lock the table for the duration of a full table rewrite, or briefly break every running application instance that hasn't deployed the matching code yet. The standard technique is the expand-contract pattern, splitting one "migration" into several small, individually safe deploys:

  1. Expand — add the new column/table as nullable (or with a cheap default), without removing or renaming anything old. Old code keeps working untouched.
  2. Migrate/backfill — populate the new column in batches (never one giant UPDATE locking the whole table), and start dual-writing from the application (write to both old and new) once code supports it.
  3. Cut over — deploy application code that reads from the new column/table, once backfill is confirmed complete and dual-writes are flowing.
  4. Contract — once nothing reads the old column, drop it in a separate, later deploy.
Concretely, for "add a NOT NULL column with a default" on a large table: older Postgres versions had to rewrite every row to backfill the default, taking an exclusive lock for the duration. Modern Postgres (11+) can add a column with a constant default without a full rewrite, but a NOT NULL constraint still requires validating existing rows — for a genuinely huge table, add the column nullable, backfill in batches, then add the NOT NULL constraint with NOT VALID followed by a separate, non-blocking VALIDATE CONSTRAINT pass.

Common production failure patterns worth naming proactively in an interview:

  • Connection pool exhaustion — every connection to Postgres is a full OS process with real memory overhead; an application opening unbounded connections (or a leaked-connection bug) starves the database. Fix with an external pooler (PgBouncer) and bounded pool sizes in the app.
  • Long-running transaction blocking VACUUM — an old open transaction prevents MVCC from reclaiming dead row versions system-wide, not just in its own table, causing gradual bloat and slowdown across the database.
  • Missing index discovered only in production — a query that was fast on a small staging dataset does a sequential scan at production scale; caught via slow-query logs or pg_stat_statements, fixed via CREATE INDEX CONCURRENTLY so the index build doesn't lock writes.
  • Replication lag spikes under write bursts, causing stale reads on followers (Part F) — often surfaces as "it worked when I tested it, then broke under load."
  • Thundering herd on cache expiry — a hot key's cache entry expires and every concurrent request falls through to the database at once; mitigated with jittered TTLs or a lock/single-flight pattern around the recompute.

Popular interview questions — Security & Ops

How exactly does a parameterized query prevent SQL injection?

The query structure is sent to the database separately from the input values, and compiled/planned before the values are bound. The database therefore treats the input strictly as a literal value, never as part of the SQL syntax — there's no string concatenation step for an attacker to exploit, regardless of what characters the input contains.

Why is "escaping quotes" not considered a sufficient defense?

It's a manual, error-prone blocklist approach — different encodings, character sets, or context (e.g. inside a LIKE pattern, or a dynamically built identifier) all have their own escaping rules, and missing one reopens the hole. Parameterized queries eliminate the entire class of bug rather than trying to sanitize around it.

Why use separate database roles instead of one shared application credential?

Least privilege — if a credential leaks or a bug executes unexpected SQL, the blast radius is limited to whatever that specific role can do. A reporting/read-only service should never hold DELETE or DDL rights it doesn't need.

What's the expand-contract pattern and why is it necessary?

It splits a risky schema change into safe incremental steps — add new structure without touching old (expand), backfill and dual-write, cut application code over once verified, then remove the old structure later (contract). It's necessary because a rolling deployment means old and new application code run simultaneously against the same database for a period, and a naive one-shot migration can break whichever version is running at the wrong moment, or lock the table outright.

How would you add an index to a large production table without blocking writes?

CREATE INDEX CONCURRENTLY — it builds the index without holding the exclusive lock a normal CREATE INDEX takes, at the cost of taking longer and needing a retry if it fails partway (it can leave behind an invalid index that must be dropped and retried).

What causes connection pool exhaustion, and how do you prevent it?

Each database connection carries real server-side overhead (a full backend process in Postgres), so an application opening too many connections, or leaking connections it forgets to close, can starve the database of capacity. Prevent it with a bounded connection pool in the application and/or an external pooler like PgBouncer sitting between the app and the database.
