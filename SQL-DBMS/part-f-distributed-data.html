21 · Replication & CAP in practice

Leader-follower (primary-replica) replication is the default pattern: all writes go to one leader, which streams changes to one or more followers. Followers serve reads, spreading read load and providing failover targets.

ModeBehaviorTradeoff
SynchronousLeader waits for at least one follower to confirm the write before acknowledging the client.Zero data loss on failover, but higher write latency, and the leader can stall if a follower is slow/down.
AsynchronousLeader acknowledges the write immediately; followers catch up afterward.Lower latency, but a leader crash before replication completes loses the unreplicated writes — this is replication lag, and it's the direct cause of "I just wrote something and immediately can't see it" bugs when a read hits a lagging follower.

Multi-leader / leaderless replication (accepting writes on multiple nodes) trades simplicity for availability and geographic write locality, at the cost of needing conflict resolution (last-write-wins, vector clocks, CRDTs) when the same key is written on two nodes concurrently.

CAP theorem, applied — revisit Part A's definition with an actual replicated system: during a network partition between the leader and a follower's data center, you must choose: serve reads/writes from the isolated follower anyway (Availability, but it may be stale or diverge — AP) or refuse to serve from that side until the partition heals (Consistency, but reduced availability — CP). Postgres streaming replication in synchronous mode leans CP; most default async setups lean AP for reads from followers.

Interview-safe line: "I think of CAP less as 'pick two forever' and more as a per-request policy — a payment write might need strict consistency (CP), while a 'likes' counter read on the same system can tolerate a stale replica (AP). Modern systems often mix both within one architecture rather than picking one label for the whole system."

22 · Sharding & partitioning

Partitioning splits one logical table into smaller physical pieces, typically still on one node (e.g. Postgres native partitioning by range or list) — mainly a manageability/query-pruning win. Sharding specifically means splitting data across multiple nodes, so it also solves the "the data doesn't fit on one machine" problem.

StrategyHow it worksTradeoff
Range-basedShard by a value range (user_id 1–1M on shard A, 1M–2M on shard B)Great for range queries, but prone to hotspots if data/traffic isn't uniform across ranges (e.g. newest users all landing on the last shard).
Hash-basedShard = hash(key) mod NEven distribution, kills hotspots, but range queries now have to fan out to every shard.
Directory-basedA lookup service maps each key (or key range) to its shard explicitlyMost flexible (arbitrary rebalancing), but the directory service itself becomes a critical dependency.
Consistent hashingHash both keys and nodes onto a ring; a key belongs to the next node clockwiseAdding/removing a node only reshuffles a small fraction of keys, instead of nearly all of them as with plain hash-mod-N — the standard answer to "how do you reshard without moving everything."

Resharding pain points to name proactively: cross-shard joins and transactions become expensive or impossible without a coordination layer (see 2PC/Sagas, Part D); auto-incrementing IDs no longer work globally (switch to UUIDs or a coordinated ID-generation service like Snowflake IDs); and a single "celebrity" key (a viral post, a huge customer) can overload one shard no matter how good the strategy is — often handled with an explicit hot-key split as a special case.

23 · SQL vs NoSQL decision framework

Question to askLeans SQLLeans NoSQL
Do multiple entities need to stay consistent together?Yes — multi-row/table transactions matter (orders + inventory + payment)No — each document/item mostly stands alone
How stable is the schema?Well-understood, slowly evolvingRapidly evolving, heterogeneous records
Access pattern?Ad-hoc queries, joins, reportingSimple key-based lookups at very high scale
Write volume?Moderate, correctness-criticalExtremely high (telemetry, logs, event streams)
ExampleOrders, ledgers, user accounts, inventorySession store, activity feed, product catalog with variable attributes, time-series metrics

Polyglot persistence — most real product systems at scale use several stores simultaneously, each for what it's good at: Postgres for the transactional core, Redis for hot caches/sessions, Elasticsearch for full-text/faceted search, a wide-column store (Cassandra/DynamoDB) for massive write-heavy time-series or feeds, S3/blob storage for large binary objects. Naming this explicitly in a system-design round signals you're not treating "pick one database" as the only lever.

24 · Worked schema-design case studies

The DB sub-section of a "Design X" round, done the way a strong SDE2 answer actually flows: entities → cardinality → key schema decisions → index choices → consistency tradeoffs.

Design the database for a ride-sharing app (Uber-style) 
rider(rider_id PK, name, ...)
driver(driver_id PK, name, vehicle_info, current_status)
ride(ride_id PK, rider_id FK, driver_id FK, status, requested_at,
     pickup_geo, dropoff_geo, fare, started_at, completed_at)
driver_location(driver_id FK, geo_point, updated_at)   -- extremely hot, high write rate
  • Key decision: driver_location is write-heavy and latency-critical (location pings every few seconds per active driver) — this table does not belong in the same durability/consistency tier as ride. Route it to an in-memory geo-indexed store (Redis with geospatial commands, or a dedicated location service) rather than the transactional Postgres core; only the ride's final route/fare needs strong durability.
  • Indexing: a geospatial index (GiST in Postgres, or a specialized geo-index) on driver location for "nearest N drivers" queries — a plain B-tree can't do proximity search.
  • Consistency: matching a rider to a driver is the one step that needs a strong consistency guarantee (never double-assign the same driver) — a good place to mention row-level locking or a compare-and-swap on driver.current_status inside a short transaction.
Design the database for a photo-sharing app (Instagram-style) 
user(user_id PK, username, ...)
post(post_id PK, user_id FK, image_url, caption, created_at)
follow(follower_id FK, followee_id FK, PRIMARY KEY(follower_id, followee_id))
like(user_id FK, post_id FK, created_at, PRIMARY KEY(user_id, post_id))
comment(comment_id PK, post_id FK, user_id FK, text, created_at)
  • Key decision — the feed itself is the hard part, not the schema above. A normalized "join follow to posts of everyone I follow, ORDER BY created_at" query is fine at small scale but collapses for a celebrity account with millions of followers (fan-out-on-read gets expensive; fan-out-on-write — pushing a new post into every follower's precomputed feed — gets expensive the other direction). Real systems use a hybrid: fan-out-on-write for normal accounts, fan-out-on-read for celebrity accounts, exactly the kind of nuance that separates a strong answer.
  • Denormalization: like_count and comment_count precomputed on post, updated async — see Part B, Module 5.
  • Indexing: composite index on (user_id, created_at DESC) for a profile grid; the follow and like tables use composite PKs directly as their access-pattern index.
Design the database for an event-ticketing system (high-contention checkout) 
event(event_id PK, name, venue_id FK, starts_at)
seat(seat_id PK, event_id FK, section, row, seat_number, status)  -- status: available/held/sold
reservation(reservation_id PK, seat_id FK, user_id FK, expires_at, status)
  • Key decision — this is fundamentally a concurrency-control problem, not a schema problem. Two users must never both successfully book the same seat. Use a short transaction with SELECT ... FOR UPDATE on the seat row (pessimistic lock) or an atomic conditional update (UPDATE seat SET status='held' WHERE seat_id=? AND status='available', checking rows-affected) — directly exercises Part D's locking module.
  • Reservation TTL: a held seat that isn't paid within N minutes must revert to available — either an expiring lock, a scheduled job scanning for expired holds, or a TTL-capable store (Redis) fronting the hold state before it's finalized in Postgres.
  • Why not just rely on a UNIQUE constraint? A unique constraint on (seat_id) in a "sold seats" table does prevent double-selling at the database level as a last line of defense — worth mentioning alongside the application-level lock, not instead of it.

Popular interview questions — Distributed Data

What causes "read your own write" bugs in a replicated system?

Asynchronous replication lag — the write lands on the leader and is acknowledged immediately, but a subsequent read gets routed to a follower that hasn't caught up yet. Fixes: read-your-writes consistency (route a user's reads to the leader for a short window after their own write), or synchronous replication for that path.

Why is consistent hashing preferred over plain hash-mod-N for sharding?

With hash-mod-N, adding or removing a single node changes the modulus, remapping nearly every key — a massive, disruptive data migration. Consistent hashing places nodes and keys on a ring so only the keys between the changed node and its neighbor need to move, making scaling in/out far cheaper.

What breaks when you shard a previously single-node relational database?

Cross-shard joins and transactions become expensive or need a coordination layer (2PC/Sagas); auto-increment primary keys stop being globally unique (move to UUIDs or a distributed ID generator); and any single very hot key can overload one shard regardless of the sharding strategy.

How would you design a social feed for both normal users and a celebrity with 50M followers?

Fan-out-on-write (push new posts into each follower's precomputed feed at write time) works well for normal accounts but is prohibitively expensive for a celebrity's massive follower count. A hybrid is standard: fan-out-on-write for most accounts, fan-out-on-read (merge celebrity posts into the feed at read time) for accounts above a follower threshold.

In the ticket-checkout problem, why use SELECT ... FOR UPDATE instead of just a UNIQUE constraint?

A UNIQUE constraint only rejects the second conflicting write after the fact — it's a correct last line of defense but doesn't prevent two requests from both doing wasted work (charging a card, say) before one fails. Locking the seat row (or an atomic conditional UPDATE) at the start of the critical section prevents the conflict from happening at all, and the constraint remains as a safety net underneath it.
