17 · Indexing deep dive

An index is a separate, ordered data structure that lets the engine find rows without scanning the whole table — the tradeoff is always faster reads, slower/heavier writes, extra storage.

Index typeStructureGood forBad for
B-tree (default, almost everywhere)Balanced tree, sorted keys, O(log n) lookupEquality, range queries (>, <, BETWEEN), ORDER BY, prefix matches (LIKE 'abc%')Nothing much — it's the safe general default
HashHash table of key → row pointerPure equality lookups onlyAny range query, ORDER BY — no notion of "nearby" keys
BitmapA bitmap per distinct value, marking which rows have itLow-cardinality columns (status: active/inactive/pending) combined with AND/OR across several such columnsHigh-cardinality columns (user_id) — bitmap per value becomes as large as the table
GIN / GiST (Postgres-specific)Inverted index / generalized search treeFull-text search, array containment, JSONB, geospatialNot a general substitute for B-tree on scalar columns

Composite indexes — an index on (a, b, c) is usable for filters on a alone, a AND b, or a AND b AND c (leftmost-prefix rule), but generally not usable for a filter on b alone. Column order should follow: equality columns first, then the range/sort column last.

Covering index — an index that includes every column the query needs, so the engine never touches the base table (heap) at all ("index-only scan"):

CREATE INDEX idx_orders_covering ON orders (customer_id) INCLUDE (order_date, total);
-- SELECT order_date, total FROM orders WHERE customer_id = 42;  -- never reads the heap
When an index hurts: every index must be updated on every INSERT/UPDATE/DELETE that touches an indexed column — a table with 8 indexes pays that cost 8 times per write. High-write, low-read tables (an events/audit log) often intentionally carry few or no secondary indexes. Also watch for indexes that never get used because the planner decides a sequential scan is cheaper anyway — small tables, or filters matching a large fraction of rows, often make an index scan slower than a seq scan due to random I/O.

18 · Reading EXPLAIN & the optimizer

The optimizer is cost-based: it estimates the cost of several candidate plans (using table statistics — row counts, value distribution) and picks the cheapest one. EXPLAIN ANALYZE actually runs the query and shows real vs estimated numbers — always prefer it over plain EXPLAIN when debugging, since estimates can be badly wrong on stale statistics.

EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42 ORDER BY order_date DESC LIMIT 10;

-- Limit  (cost=0.42..8.89 rows=10 width=64) (actual time=0.03..0.05 rows=10 loops=1)
--   ->  Index Scan Backward using idx_orders_customer_date on orders
--         (cost=0.42..423.10 rows=500 width=64) (actual time=0.03..0.04 rows=10 loops=1)
--         Index Cond: (customer_id = 42)
Plan nodeMeaning
Seq ScanReads the entire table. Fine for small tables or when most rows match; a red flag on a large table with a selective filter and no matching index.
Index ScanUses an index to find matching rows, then fetches each from the heap.
Index Only ScanSatisfies the query entirely from the index (covering index) — no heap access.
Bitmap Heap Scan / Bitmap Index ScanBuilds an in-memory bitmap of matching row locations first, then fetches them in physical order — used when many (but not almost-all) rows match.
Nested LoopFor each outer row, scan/probe the inner side. Cheap when the outer side is small.
Hash JoinBuild a hash table from the smaller side, probe it with the larger side. Good for large, unsorted equi-joins.
Merge JoinBoth sides pre-sorted (or sorted by the planner), then merged in one pass. Good when both sides are already ordered by the join key.
The debugging habit worth stating out loud in an interview: "If actual rows is wildly different from the planner's rows estimate, statistics are stale — I'd run ANALYZE on the table before trusting the plan further. If a query is slow and I see a Seq Scan on a large table with a highly selective WHERE clause, that's my first candidate for a missing index."

19 · Storage engine internals (practical depth)

You don't need to reimplement Postgres to answer this well — you need the mental model of how a write actually becomes durable and how reads avoid re-reading disk every time.

  • Pages — the unit of I/O (typically 8KB in Postgres). Rows are packed into pages; the engine always reads/writes whole pages, never individual rows, from disk.
  • Buffer pool / shared buffers — an in-memory cache of recently used pages. A read that hits the buffer pool skips disk entirely; this is why "working set fits in RAM" is such a common performance heuristic.
  • Write-Ahead Log (WAL) — before a change is applied to the actual data pages, it's appended to a sequential log file. COMMIT only returns success once the WAL record is flushed to durable storage — sequential log writes are far cheaper than random writes to data pages, which is why this design is faster and crash-safe: on restart, the engine replays the WAL to reconstruct any changes that hadn't made it to the data pages yet.
  • MVCC row versions & VACUUM — Postgres never overwrites a row in place on UPDATE; it writes a new row version and marks the old one dead. This is what makes non-blocking MVCC reads possible (Part D), but dead versions accumulate and must be reclaimed — that's VACUUM's job; a table under heavy UPDATE/DELETE churn that isn't vacuumed enough will bloat.
One sentence that ties it together: "A write goes: WAL record appended and flushed (durability), then the actual data page is updated in the buffer pool and written back to disk later (lazily, via checkpoints) — separating 'durable' from 'applied to the data file' is exactly what makes crash recovery possible."

20 · Views, materialized views, procedures, triggers, cursors

ObjectWhat it isInterview trap
ViewA saved query, no separate storage — re-executed against live data every time it's queried.People sometimes assume a view is a performance optimization. It isn't — it's a naming/security convenience. It can even be slower if it wraps an expensive query used repeatedly.
Materialized viewA view whose result is physically stored, refreshed on a schedule or on demand (REFRESH MATERIALIZED VIEW).Data can be stale between refreshes — you're trading freshness for read speed. Know whether your use case (a nightly analytics dashboard) can tolerate that or not (a live balance).
Stored procedure / functionPrecompiled logic stored and executed inside the database.Great for reducing network round-trips and centralizing business rules that must never be bypassed; the tradeoff is business logic split across the app layer and the DB layer, harder to version-control/test/deploy uniformly, and a form of vendor lock-in.
TriggerA function that fires automatically on INSERT/UPDATE/DELETE.Useful for invariants that must never be skipped (audit logging, denormalized counter maintenance), but overuse makes the system's actual behavior invisible from application code — a classic "spooky action at a distance" complaint from teams that inherit a trigger-heavy schema.
CursorA handle for iterating a result set row-by-row inside procedural code.Row-by-row processing is almost always slower than a set-based query — reach for a cursor only when you genuinely can't express the logic as one query (e.g., calling an external API per row inside a procedure).
A strong, differentiated answer on "view vs materialized view": "I'd use a view purely for readability/security — hiding a complex join behind a simple name, or restricting which columns a role can see. I'd only reach for a materialized view once I've measured that the underlying query is genuinely expensive and re-run often, and I'm willing to accept a defined staleness window — it's a deliberate caching decision, not a default."

Popular interview questions — Storage, Indexing & Performance

When would an index actually make a query slower, or not get used at all?

Indexes add write overhead on every INSERT/UPDATE/DELETE touching indexed columns, so a write-heavy, rarely-queried table can be net-slower with more indexes. Even when it exists, the planner may skip an index if the filter matches a large fraction of the table — random-access index lookups can cost more than one sequential scan in that case.

What's the leftmost-prefix rule for composite indexes?

A composite index on (a, b, c) can serve queries filtering on a, on (a,b), or on (a,b,c), but not on b or c alone — the engine can only use the index by matching from its leftmost column inward.

What is a covering index / index-only scan?

An index that includes every column a query needs (via the key columns or an INCLUDE clause), so the engine can answer the query from the index alone without touching the underlying table (heap) at all — the fastest possible read path.

What does EXPLAIN ANALYZE give you that plain EXPLAIN doesn't?

Plain EXPLAIN shows the planner's cost estimates without running the query. EXPLAIN ANALYZE actually executes it and reports real elapsed time and real row counts alongside the estimates — letting you spot cases where stale statistics caused the planner to pick a bad plan.

Hash join vs nested loop vs merge join — how does the optimizer choose?

Based on estimated cost given table sizes and existing sort order: nested loop wins when one side is small; hash join wins for large, unsorted equi-joins (build a hash table on the smaller side); merge join wins when both sides are already sorted on the join key, avoiding an extra sort step.

Why does Postgres need VACUUM?

Because MVCC never updates a row in place — an UPDATE writes a new row version and marks the old one dead rather than overwriting it, so old versions accumulate. VACUUM reclaims that dead space; without it, a heavily updated table bloats and both storage and scan performance degrade.

Is a view a performance optimization?

No — a regular view is just a saved query, re-executed against live data every time. It's a naming/security abstraction, not a cache. A materialized view is the one that actually stores results and can improve read performance, at the cost of staleness between refreshes.
