1 WHERE vs HAVING — what's the difference?

WHERE filters individual rows before grouping happens; HAVING filters entire groups after aggregation. You cannot use an aggregate function in WHERE (WHERE COUNT(*) > 1 is a syntax error) because aggregates don't exist until GROUP BY has run. Full execution-order breakdown: Part C, Module 6.

2 DELETE vs TRUNCATE vs DROP

DELETE removes rows one at a time (can be filtered with WHERE, is logged row-by-row, triggers fire, fully rollback-able). TRUNCATE deallocates the table's data pages wholesale — faster, minimally logged, resets identity/auto-increment counters, cannot be filtered, and in most engines can't be rolled back as cheaply as DELETE (Postgres is an exception: it's transactional there too). DROP removes the table definition itself, including its schema, indexes, and constraints — nothing is left to query.

3 CHAR vs VARCHAR vs TEXT

CHAR(n) is fixed-length, space-padded to n — predictable storage, marginal speed benefit, wastes space on variable-length data. VARCHAR(n) is variable-length up to a cap n — the common default. TEXT is variable-length with no practical cap. In Postgres specifically, all three actually use the same underlying storage mechanism and have near-identical performance — the choice there is really about whether you want a length constraint documented/enforced (VARCHAR(n)) versus none (TEXT), not a performance decision like it can be in some other engines.

4 Primary key vs unique key vs foreign key vs composite key

Primary key: the table's one official identity, NOT NULL + unique. Unique key: also enforces uniqueness, but a table can have several, and (per the SQL standard) they can allow one NULL. Foreign key: references a primary/unique key in another table, enforcing referential integrity. Composite key: any of the above spanning more than one column together — common on junction tables, e.g. PRIMARY KEY (student_id, course_id). Full treatment: Part A, Module 3.

5 What are constraints, and why put them in the database instead of the app layer?

NOT NULL, CHECK, UNIQUE, PRIMARY/FOREIGN KEY — they enforce domain, entity, and referential integrity regardless of which application, script, or manual session touches the data. App-layer validation can be bypassed by a second service, a bad migration, or a direct DB session; a CHECK constraint cannot.

6 Walk through all JOIN types with an example.

INNER (only matches on both sides), LEFT (all left rows, NULLs for unmatched right), RIGHT (mirror of LEFT), FULL OUTER (union of LEFT and RIGHT), CROSS (Cartesian product — every row × every row). Full table with examples and the two most common join bugs (fan-out, WHERE-turns-LEFT-into-INNER): Part C, Module 7.

7 What is a self-join, and when would you use one?

A table joined to itself via two aliases, used to compare rows within the same table — the standard example is comparing an employee's salary to their manager's, where both are rows in the same employee table linked by manager_id.

8 IN vs EXISTS vs JOIN for filtering — which do you pick, and why?

All three can express "rows that have a match elsewhere," but they behave differently on NULLs and scale differently. EXISTS (and NOT EXISTS) short-circuits on the first match and is NULL-safe. IN is fine for filtering against a small, NULL-free literal list, but NOT IN silently returns zero rows if the subquery result contains even one NULL — a very commonly asked trap. A JOIN is the right call when you also need columns from the other table in the output, not just a filter; a plain existence check that discards the other table's columns is better expressed as EXISTS to avoid accidental row duplication from a one-to-many join.

9 What is an index, how does it work, and what's the tradeoff?

A separate, ordered structure (commonly a B-tree) that lets the engine locate rows without a full table scan — faster reads, at the cost of extra storage and slower writes (every index must be updated on every INSERT/UPDATE/DELETE touching its columns). Full type-by-type breakdown (B-tree/hash/bitmap/GIN-GiST) and when an index actually hurts: Part E, Module 17.

10 Clustered vs non-clustered index — what's the difference?

A clustered index determines the physical storage order of the table's rows — there can only be one per table (in Postgres, this isn't maintained automatically like in SQL Server/MySQL InnoDB; Postgres's CLUSTER command physically reorders once but doesn't keep it clustered on future writes). A non-clustered (secondary) index is a separate structure of pointers back to the table's rows — a table can have many. Interviewers most often want you to know: clustered = physical row order (one only), non-clustered = extra lookup structure (many allowed).

11 What is a covering index?

An index that contains every column a query needs, so the engine can answer entirely from the index without touching the table itself — an "index-only scan," the fastest possible read path. See the worked CREATE INDEX ... INCLUDE (...) example: Part E, Module 17.

12 RANK vs DENSE_RANK vs ROW_NUMBER — differences, with ties.

ROW_NUMBER() always gives unique sequential numbers, even on ties (arbitrary tiebreak). RANK() gives tied rows the same rank, then skips the next rank by the tie count (1,1,3). DENSE_RANK() gives tied rows the same rank with no gap (1,1,2). Pick DENSE_RANK when "2nd highest" must not disappear because two rows tied for 1st.

13 How do you find the Nth highest salary?

SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employee
) t WHERE rnk = :N;

The single most-repeated live-coding SQL question across almost every product-company loop. Full problem bank with 9 more of these solved: Part C, Module 12.

14 How do you calculate a rolling average / running total?

SELECT day, revenue,
       AVG(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS moving_avg_7d,
       SUM(revenue) OVER (ORDER BY day) AS running_total
FROM daily_revenue;

Window frame clauses (ROWS BETWEEN ... AND ...) are the mechanism — full walkthrough: Part C, Module 9.

15 Subquery vs CTE — when do you use which?

A CTE (WITH) is named and readable, and in modern Postgres (12+) is inlined into the plan at the same cost as an equivalent subquery when it has no side effects — so the choice is mostly about readability and reuse (referencing the same intermediate result more than once) rather than performance. Reach for a plain subquery for a simple, one-off, single-use filter where a full CTE header feels like overhead. Recursive CTEs are the one case with no subquery equivalent — required for hierarchical data. Details: Part C, Module 8.

16 Explain normalization. When would you intentionally denormalize?

Normalization eliminates insert/update/delete anomalies by ensuring each fact is stored exactly once (1NF→BCNF). You'd deliberately denormalize for proven, read-heavy hot paths (precomputed counters, materialized views) or for correctness-preserving snapshots (locking in a price at time of purchase so a later catalog change doesn't rewrite history). Full anomaly-by-anomaly mapping: Part B, Module 4a.

17 What are the ACID properties, and why do they matter?

Atomicity (all-or-nothing), Consistency (invariants always hold), Isolation (concurrent transactions don't see each other's half-done state), Durability (a commit survives a crash). They matter because without them, a crash or a concurrent request mid-transaction can leave the database in a state that's internally contradictory — money debited but never credited, for example. Worked bank-transfer example: Part D, Module 13.

18 What is a deadlock, and how do you prevent one?

Two transactions each hold a lock the other is waiting for — a cycle in the wait-for graph. The database detects the cycle and aborts one transaction (the victim) to break it. Prevent it proactively by always acquiring/updating rows in a consistent global order across every transaction, so a circular wait can never form. Full section: Part D, Module 15.

19 UNION vs UNION ALL

UNION combines two result sets and removes duplicates (an implicit sort/hash dedup pass). UNION ALL combines and keeps everything, with no dedup cost. Default to UNION ALL unless you specifically need distinct rows across the combined sets — using UNION out of habit is a common, avoidable performance regression.

20 Why does NOT IN sometimes return zero rows unexpectedly?

If the subquery behind NOT IN returns even a single NULL, every comparison evaluates to NULL rather than true/false, because x NOT IN (a, NULL) expands to x != a AND x != NULL — and that last term is always NULL, which poisons the whole AND for every row. The NULL-safe fix is NOT EXISTS or a LEFT JOIN ... WHERE ... IS NULL. This exact trap shows up disguised inside "find customers who never ordered"-style questions across almost every SQL round — see it solved both ways: Part C, Module 12.

Write-a-query drill: 20 implementation problems

Pure "give me a SQL query to get X" prompts, the way they actually get read out loud in a live-coding round. Distinct from Part C's problem bank — no overlap, so drill both. Solutions assume Postgres.

21 Write a query to find duplicate email addresses in a users table. 
SELECT email, COUNT(*) AS cnt
FROM person
GROUP BY email
HAVING COUNT(*) > 1;
22 Write a query to swap seat assignments in pairs (odd/even id, last odd stays put if count is odd) — the classic "Exchange Seats" problem. 
SELECT
  CASE
    WHEN id % 2 = 1 AND id = (SELECT MAX(id) FROM seat) THEN id   -- last odd seat unchanged
    WHEN id % 2 = 1 THEN id + 1
    ELSE id - 1
  END AS id,
  student
FROM seat
ORDER BY id;
23 Write a query to find the department with the highest average salary. 
SELECT department_id, AVG(salary) AS avg_salary
FROM employee
GROUP BY department_id
ORDER BY avg_salary DESC
LIMIT 1;
24 Write a query to list employees hired in the last 90 days. 
SELECT * FROM employee
WHERE hire_date >= CURRENT_DATE - INTERVAL '90 days';
25 Write a query to find categories that have zero products in them. 
SELECT c.category_id, c.name
FROM category c
LEFT JOIN product p ON p.category_id = c.category_id
WHERE p.product_id IS NULL;
26 Write a query to calculate each product's percentage contribution to total revenue. 
SELECT product_id,
       SUM(revenue) AS product_revenue,
       ROUND(100.0 * SUM(revenue) / SUM(SUM(revenue)) OVER (), 2) AS pct_of_total
FROM sales
GROUP BY product_id;

The trick: SUM(SUM(revenue)) OVER () — an aggregate wrapped in a window function with no PARTITION BY gives the grand total alongside each group's own subtotal.

27 Write a query to get each customer's first and last order date. 
SELECT customer_id, MIN(order_date) AS first_order, MAX(order_date) AS last_order
FROM orders
GROUP BY customer_id;
28 Write a query to find customers who placed at least one order in every month of 2026. 
SELECT customer_id
FROM orders
WHERE EXTRACT(YEAR FROM order_date) = 2026
GROUP BY customer_id
HAVING COUNT(DISTINCT EXTRACT(MONTH FROM order_date)) = 12;
29 Write a query to find the most frequently ordered product within each category. 
SELECT category_id, product_id, order_count FROM (
  SELECT p.category_id, p.product_id, COUNT(*) AS order_count,
         ROW_NUMBER() OVER (PARTITION BY p.category_id ORDER BY COUNT(*) DESC) AS rn
  FROM order_items oi JOIN product p ON p.product_id = oi.product_id
  GROUP BY p.category_id, p.product_id
) t WHERE rn = 1;
30 Write a query to detect overlapping bookings for the same resource (e.g. a meeting room double-booked). 
SELECT a.booking_id, b.booking_id
FROM booking a
JOIN booking b ON a.resource_id = b.resource_id
  AND a.booking_id < b.booking_id
  AND a.start_time < b.end_time
  AND b.start_time < a.end_time;

The overlap condition — a.start < b.end AND b.start < a.end — is the general-purpose pattern for any interval-overlap check; memorize it as a unit rather than re-deriving it live.

31 Write a query to compute the running (cumulative) count of distinct users active-to-date, by day. 
WITH first_seen AS (
  SELECT user_id, MIN(activity_date) AS first_date
  FROM activity
  GROUP BY user_id
)
SELECT first_date,
       SUM(COUNT(*)) OVER (ORDER BY first_date) AS cumulative_unique_users
FROM first_seen
GROUP BY first_date
ORDER BY first_date;

Key idea: a running count of distinct users equals a running total of each user's first-seen date — reduces an otherwise awkward "distinct within a window" problem to a plain running SUM.

32 Write a query to produce a comma-separated list of employee names per department. 
SELECT department_id, STRING_AGG(name, ', ' ORDER BY name) AS employees
FROM employee
GROUP BY department_id;
33 Write a query to show each employee's salary alongside the difference from their department's average. 
SELECT employee_id, name, salary,
       ROUND(salary - AVG(salary) OVER (PARTITION BY department_id), 2) AS diff_from_dept_avg
FROM employee;
34 Write a query to find the percentage of users whose first purchase happened on their signup day. 
WITH first_order AS (
  SELECT user_id, MIN(order_date) AS first_order_date FROM orders GROUP BY user_id
)
SELECT ROUND(100.0 * COUNT(*) FILTER (WHERE f.first_order_date = u.signup_date) / COUNT(*), 2) AS same_day_pct
FROM users u JOIN first_order f ON f.user_id = u.user_id;
35 Write a query to find the longest streak of consecutive days a stock's closing price increased. 
WITH flagged AS (
  SELECT trade_date, close_price,
         CASE WHEN close_price > LAG(close_price) OVER (ORDER BY trade_date) THEN 1 ELSE 0 END AS is_up
  FROM stock_price
),
grouped AS (
  SELECT trade_date,
         trade_date - (ROW_NUMBER() OVER (ORDER BY trade_date))::int AS grp
  FROM flagged WHERE is_up = 1
)
SELECT COUNT(*) AS streak_len, MIN(trade_date) AS streak_start, MAX(trade_date) AS streak_end
FROM grouped
GROUP BY grp
ORDER BY streak_len DESC
LIMIT 1;

Same gaps-and-islands mechanics as Part C, Module 10 — applied to "up days" instead of login days.

36 Write a query to find the manager with the most direct reports. 
SELECT manager_id, COUNT(*) AS direct_reports
FROM employee
WHERE manager_id IS NOT NULL
GROUP BY manager_id
ORDER BY direct_reports DESC
LIMIT 1;
37 Write a query to pivot monthly revenue into one column per month, for each product. 
SELECT product_id,
  SUM(CASE WHEN EXTRACT(MONTH FROM sale_date) = 1 THEN revenue ELSE 0 END) AS jan,
  SUM(CASE WHEN EXTRACT(MONTH FROM sale_date) = 2 THEN revenue ELSE 0 END) AS feb,
  SUM(CASE WHEN EXTRACT(MONTH FROM sale_date) = 3 THEN revenue ELSE 0 END) AS mar
  -- ... repeat the same CASE pattern through month 12
FROM sales
GROUP BY product_id;

Postgres has no native PIVOT keyword (unlike SQL Server) — conditional aggregation is the portable answer every time.

38 Write a query to find the customer with the highest total lifetime spend. 
SELECT customer_id, SUM(total) AS lifetime_spend
FROM orders
GROUP BY customer_id
ORDER BY lifetime_spend DESC
LIMIT 1;
39 Write a query to find the average number of days between consecutive orders, per customer. 
WITH gaps AS (
  SELECT customer_id, order_date,
         order_date - LAG(order_date) OVER (PARTITION BY customer_id ORDER BY order_date) AS gap
  FROM orders
)
SELECT customer_id, AVG(gap) AS avg_days_between_orders
FROM gaps
WHERE gap IS NOT NULL
GROUP BY customer_id;
40 Write a query to flag potential fraud: users with more than 5 transactions within any 5-minute window. 
SELECT user_id, txn_time, txn_count_in_window
FROM (
  SELECT user_id, txn_time,
         COUNT(*) OVER (
           PARTITION BY user_id ORDER BY txn_time
           RANGE BETWEEN INTERVAL '5 minutes' PRECEDING AND CURRENT ROW
         ) AS txn_count_in_window
  FROM transactions
) t
WHERE txn_count_in_window > 5;

A RANGE frame (time-based) rather than ROWS (row-count-based) is what makes this a true sliding time window instead of a fixed number of preceding rows — a distinction worth naming explicitly if asked.
