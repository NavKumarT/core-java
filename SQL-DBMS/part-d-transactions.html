13 · ACID, with a worked example

Use one example for all four properties — a bank transfer — because interviewers usually ask you to "explain ACID with an example" directly:

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- debit Asha
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- credit Ravi
COMMIT;
PropertyGuaranteeIn this example
AtomicityAll statements in the transaction succeed, or none do.If the credit to Ravi fails (constraint violation, crash), the debit from Asha is rolled back too — money never vanishes mid-transfer.
ConsistencyThe database moves from one valid state to another — all constraints/invariants hold before and after.A CHECK constraint (balance >= 0) prevents the transaction from ever leaving an account negative; this is a joint responsibility of the engine (enforcing constraints) and the application (writing correct logic).
IsolationConcurrent transactions don't see each other's uncommitted intermediate state.A second transaction reading Asha's balance mid-transfer shouldn't see the post-debit, pre-credit "money is gone" state — governed by isolation level, see Module 14.
DurabilityOnce committed, the change survives a crash immediately after.Achieved via a write-ahead log (WAL) — the commit is only acknowledged once the log record is flushed to durable storage, so a crash right after COMMIT doesn't lose the transfer.
Interview framing: "Atomicity and durability are mechanisms the engine gives you almost for free via the transaction log. Isolation is a dial you actively choose (isolation level). Consistency is the one I have to earn myself — the engine only enforces the constraints I actually declared."

14 · Isolation levels & anomalies

Isolation levels exist because full serial execution (one transaction at a time) is correct but too slow. Each weaker level allows a specific anomaly in exchange for concurrency.

AnomalyWhat happens
Dirty readTransaction A reads a row that transaction B has modified but not yet committed. If B rolls back, A used data that never officially existed.
Non-repeatable readA reads a row twice in the same transaction and gets different values, because B committed an update to that row in between.
Phantom readA re-runs the same range query twice and gets a different set of rows, because B inserted/deleted a row matching the range in between.
Lost updateA and B both read the same row, both compute a new value based on that read, and whichever writes second silently overwrites the other's update.

-- ... statements ...

The follow-up question that catches people: "Why does Postgres's Repeatable Read already prevent phantoms, when the SQL standard says it doesn't have to?" Postgres implements isolation via MVCC snapshots rather than the pessimistic locking the standard was originally written around — a Repeatable Read transaction sees one consistent snapshot of the whole database for its entire duration, so a concurrent insert simply isn't visible at all, phantom or otherwise. At Serializable, Postgres adds runtime dependency-cycle detection (SSI — Serializable Snapshot Isolation) on top of that snapshot to catch write skew, the one anomaly snapshotting alone can't prevent.
Write skew — the anomaly Serializable specifically exists to catch, and a good one to bring up unprompted: two transactions each read overlapping data, each independently satisfy a constraint based on that read, and both commit — but the constraint is violated once both changes are combined. Classic example: a hospital rule "at least one doctor must be on call"; two of the two on-call doctors each independently check "is someone else covering" and both go off-call, leaving zero — each transaction was individually valid against what it read.

15 · Locking, deadlocks, 2PL vs MVCC

Lock types: shared (S) locks for reads, exclusive (X) locks for writes. Two-Phase Locking (2PL) is the classical concurrency-control protocol: a transaction acquires all the locks it needs (growing phase) before releasing any (shrinking phase), guaranteeing serializability.

MVCC (Multi-Version Concurrency Control) — what Postgres actually uses day to day — takes a different approach: writers don't block readers and readers don't block writers. Instead of locking rows for reads, each row keeps enough version history that a transaction can see the snapshot as it existed when its transaction started. Locks are still used, but mainly to serialize concurrent writes to the same row, not to protect reads.

The line that shows real understanding: "2PL is pessimistic and lock-based — correct, but a reader can block a writer and vice versa. MVCC is optimistic about reads — a reader never blocks a writer because it's reading an older, consistent version, at the cost of extra storage (old row versions) that needs to be cleaned up — which is exactly what Postgres's VACUUM process does."

Deadlocks happen when transaction A holds a lock B wants, and B holds a lock A wants — a cycle in the wait-for graph. Databases don't avoid this proactively by default; they detect it: Postgres periodically checks for a cycle in the wait-for graph and aborts one transaction (the "victim") with an error, letting the other proceed.

-- Classic deadlock: two transactions update the same two rows in opposite order
-- Txn A:                          Txn B:
UPDATE accounts SET ... WHERE id=1;  UPDATE accounts SET ... WHERE id=2;
UPDATE accounts SET ... WHERE id=2;  UPDATE accounts SET ... WHERE id=1;
-- A waits on B's lock on row 2, B waits on A's lock on row 1 -- cycle

Prevention in application code: always acquire locks (update rows) in a consistent global order — e.g. always update the lower account id first, regardless of which side of the transfer it's on. This eliminates the cycle by construction rather than relying on the database's detector-and-abort fallback.

16 · Savepoints & distributed transactions

Savepoints allow a partial rollback inside one transaction, without aborting the whole thing:

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SAVEPOINT before_credit;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
-- suppose a business-rule check fails here
ROLLBACK TO SAVEPOINT before_credit;   -- undo just the credit, keep the debit pending
-- ... try an alternate credit target, then COMMIT or ROLLBACK the whole txn

Distributed transactions span more than one database/service — e.g. a payment DB and an inventory DB owned by different services. The classical protocol is Two-Phase Commit (2PC):

  1. Prepare phase — the coordinator asks every participant "can you commit?"; each participant does all the work, writes it durably, and replies yes/no, but does not yet finalize.
  2. Commit phase — if every participant said yes, the coordinator tells everyone to commit for real; if any said no, it tells everyone to abort.
Why 2PC is unpopular at product-company scale: the coordinator is a single point of blocking — if it crashes after some participants are prepared but before the final decision is sent, those participants sit holding locks indefinitely. Modern systems usually prefer the Saga pattern instead: break the distributed operation into a sequence of local transactions, each with a defined compensating action, and run compensations in reverse order if a later step fails, trading strict atomicity for availability and explicit, application-level error handling.

Popular interview questions — Transactions & Concurrency

Explain the four ACID properties with an example.

Use a bank transfer: Atomicity means both the debit and credit happen or neither does; Consistency means declared invariants (balance ≥ 0) always hold; Isolation means a concurrent transaction never sees the momentary "debited but not yet credited" state; Durability means once COMMIT returns, the transfer survives a crash, because it's been flushed to the write-ahead log.

What's the difference between a non-repeatable read and a phantom read?

A non-repeatable read is about re-reading the same row and getting a different value because it was updated. A phantom read is about re-running the same range query and getting a different set of rows because a matching row was inserted or deleted in between.

What is a lost update, and which isolation level prevents it?

Two transactions read the same row, each compute a new value from that read, and the second write silently clobbers the first's update. Read Committed does not prevent it (each individual statement is committed-consistent, but the read-then-write sequence isn't atomic); Repeatable Read and Serializable do, since Postgres detects the conflicting concurrent update and forces one transaction to retry.

2PL vs MVCC — what's the practical tradeoff?

2PL is lock-based and pessimistic: correctness is enforced by blocking, so readers and writers can block each other. MVCC lets readers see a consistent snapshot of old row versions without blocking writers (and vice versa), at the cost of keeping multiple row versions around, which is why Postgres needs VACUUM to reclaim dead versions.

How does a database detect a deadlock, and what does it do about it?

It periodically checks the wait-for graph between blocked transactions for a cycle. If found, it aborts one transaction (the "victim," often the one that would be cheapest to roll back) with an explicit deadlock error, releasing its locks so the other can proceed. The application is expected to retry the aborted transaction.

How would you prevent deadlocks at the application level, proactively?

Always acquire/update rows in a fixed, consistent global order across all transactions (e.g., always the lower primary key first) so a circular wait can never form, rather than relying on the database's detect-and-abort fallback.

Why is Two-Phase Commit rarely used across microservices at scale, and what replaces it?

2PC's coordinator is a blocking single point of failure — if it dies mid-protocol, participants can be left holding locks indefinitely, hurting availability. The Saga pattern is the common replacement: a sequence of local transactions each with a compensating action, run in reverse to "undo" a partially completed distributed operation if a later step fails.
