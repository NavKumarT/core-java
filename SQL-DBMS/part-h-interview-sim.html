27 · Rapid-fire cheat sheet

One line each, for the last-night skim. If any line doesn't fully make sense, that's your signal to jump back into that part.

ACID — Atomic (all-or-nothing), Consistent (invariants hold), Isolated (concurrent txns don't see each other's half-done work), Durable (survives a crash post-commit).
Isolation anomalies, weakest→strongest prevented: Read Uncommitted (none) → Read Committed (dirty read) → Repeatable Read (+ non-repeatable read) → Serializable (+ phantom + write skew).
Normal forms: 1NF atomic values → 2NF no partial dependency (whole key) → 3NF no transitive dependency → BCNF every determinant is a candidate key.
Anomalies fixed: insert & delete (splitting into own tables), update (removing duplication of a fact across rows).
Index default: B-tree for equality + range + sort. Hash only for pure equality. Bitmap for low-cardinality AND/OR. GIN/GiST for full-text/JSON/geo.
Composite index rule: leftmost-prefix — usable left-to-right, not from the middle.
View vs materialized view: view = saved query, re-run live every time; materialized view = physically stored, refreshed on a schedule — a real caching decision.
2PL vs MVCC: 2PL blocks readers/writers with locks; MVCC lets readers see an old snapshot without blocking writers, at the cost of VACUUM cleanup.
CAP: only matters during a network partition — pick Consistency (refuse/delay) or Availability (serve possibly-stale) per request, not once for the whole system.
Sharding: range (hotspot risk) vs hash (even, kills range queries) vs consistent hashing (minimal reshuffle on scale in/out).
WHERE vs HAVING: WHERE filters rows before GROUP BY; HAVING filters groups after aggregation.
NOT IN vs NOT EXISTS: NOT IN silently breaks (returns zero rows) if the subquery contains a NULL; NOT EXISTS/LEFT JOIN+IS NULL are NULL-safe.
UNION vs UNION ALL: UNION dedups (costs a sort/hash pass); UNION ALL doesn't — default to ALL unless you need distinct rows.
SQL injection fix: parameterized queries/prepared statements — never string concatenation, and escaping alone isn't sufficient.
Zero-downtime schema change: expand (add nullable) → backfill/dual-write → cut over → contract (drop old) — never one big destructive step.
2PC vs Saga: 2PC = blocking coordinator, strict atomicity across services; Saga = sequence of local transactions with compensating rollbacks, favors availability.

28 · Company-pattern notes

General shape drawn from recent candidate-reported experiences — treat as tendencies to prepare for, not guarantees of any specific loop.

PatternWhat tends to show up
Amazon-style (Leadership-Principles-driven bar raisers)SQL asked as a practical mid-round exercise (write a query live), DBMS theory folded into system-design ("Design an inventory system") rather than asked standalone — expect the interviewer to push on why a design choice after you make it.
Google/large-search-styleHeavier on algorithmic reasoning about data structures behind indexes (why B-tree, complexity arguments) and distributed-systems tradeoffs (CAP, replication) over raw SQL syntax.
Uber/Lyft/ride-and-delivery-styleGeospatial and high-write-throughput scenarios recur heavily (see Part F's ride-sharing case study) — location data, matching under contention, and consistency-vs-latency tradeoffs are a near-guaranteed sub-topic.
Fintech/payments-styleTransactions and isolation levels get disproportionate depth — expect a "walk me through what could go wrong with this transfer code" style probe, and questions about idempotency for retried payment requests.
High-growth product/e-commerce-style (Flipkart, DoorDash-style)Schema design for catalogs/orders/inventory is common, plus a strong emphasis on the SQL problem bank (Part C, Module 12) as a timed, live-coding segment.
Universal pattern across all of them: the first answer you give is rarely the whole test — the follow-up ("why not X instead," "what if this got 100x bigger," "how would you know this was slow in production") is where SDE2-level signal actually gets collected. Prepare to defend, not just state, every design choice.

29 · Mock interview drilling script

Read the interviewer prompts, answer out loud before reading the notes, then check yourself against the "what a strong answer covers" line. This mirrors how a real follow-up chain actually runs.

"Design a schema for an e-commerce order system."
→ what a strong answer covers: entities (customer, product, order, order_line, payment), M:N resolved via order_line, price snapshotted on order_line not referenced live from product (Part B, Module 5).
"Why did you snapshot the price instead of just joining to the product table?"
→ tests whether you understand denormalization is a deliberate correctness choice, not laziness — a later price change must never rewrite a historical invoice.
"Now this table has 500 million rows and reads are slow. What do you do?"
→ expects: check EXPLAIN ANALYZE first, don't guess; look for a missing/unused index; consider whether the access pattern needs partitioning (by date range, likely, for an orders table) before jumping to sharding.
"Two customers are checking out the last unit of the same product at the same time. Walk me through what happens."
→ expects: name the race condition explicitly, then the fix — a transaction with either row-level locking (SELECT ... FOR UPDATE) or an atomic conditional decrement (UPDATE ... WHERE stock > 0), not just "wrap it in a transaction" without saying what isolation/locking actually does the work.
"Now the checkout service and the inventory service are two separate databases owned by two teams. Does your answer change?"
→ expects: recognize this is now a distributed transaction problem, name 2PC's blocking-coordinator downside, and propose a Saga with an explicit compensating action (release the reservation) if payment fails after inventory was decremented.
"A teammate wants to add 12 indexes to this table to speed up every dashboard query. Any concerns?"
→ expects: push back constructively — every index taxes every write; ask about the actual write volume and query patterns before agreeing, and suggest consolidating into fewer, well-chosen composite/covering indexes instead.
The meta-skill being tested across all of this: narrate your reasoning, not just your conclusion. "I'd check X before assuming Y" reads as production experience; a confident final answer with no diagnostic step in front of it reads as memorized theory.
