6 · Query anatomy & execution order

You write a query in this order:

SELECT ... FROM ... JOIN ... ON ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT ...

The engine evaluates it in a completely different order — and almost every "why doesn't my alias work" bug traces back to not knowing this:

StepClauseWhat happens
1FROM / JOINBuild the working row set from all source tables.
2WHEREFilter individual rows. Aggregates don't exist yet — you cannot reference a SELECT alias or an aggregate here.
3GROUP BYCollapse rows into groups.
4HAVINGFilter groups, now that aggregates exist.
5SELECTCompute output expressions/aliases.
6DISTINCTDe-duplicate the projected rows.
7ORDER BYSort — SELECT aliases are visible here.
8LIMIT / OFFSETTrim the final row count.
This is why: WHERE total_price > 100 fails if total_price is a SELECT alias for price*qty — WHERE runs before SELECT computes it. You must repeat the expression, or move the filter to HAVING if it's post-aggregation, or wrap in a CTE/subquery. It's also why WHERE COUNT(*) > 1 is always a syntax error and HAVING COUNT(*) > 1 is correct — aggregates only exist after GROUP BY.

7 · Joins, deeply

JoinReturns
INNER JOINOnly rows with a match on both sides.
LEFT JOINAll left rows; unmatched right columns are NULL.
RIGHT JOINMirror of LEFT — rarely used, most people rewrite as LEFT by swapping table order.
FULL OUTER JOINUnion of LEFT and RIGHT — all rows from both sides, NULLs where unmatched.
CROSS JOINCartesian product — every row of A with every row of B. Rare on purpose; common by accident (forgotten ON clause).
Self joinA table joined to itself via two aliases — the standard way to compare rows within one table (employee ↔ manager).

Semi-join and anti-join are patterns, not keywords, but interviewers expect the vocabulary:

-- Semi-join: customers who have placed at least one order (no duplication even if they have many orders)
SELECT c.* FROM customer c WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);

-- Anti-join: customers who have never ordered
SELECT c.* FROM customer c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
-- Equivalent LEFT JOIN / IS NULL form (watch for NULLs with NOT IN — see FAQ):
SELECT c.* FROM customer c LEFT JOIN orders o ON o.customer_id = c.customer_id WHERE o.customer_id IS NULL;
Bug #1 — the fan-out trap. Joining orders to order_items (one-to-many) and then SUM(orders.total) in the same query double-counts the order total once per line item. Fix: aggregate order_items down to one row per order in a subquery/CTE before joining, or use a separate scalar subquery for each metric instead of joining everything into one flat row set.
Bug #2 — WHERE silently turns a LEFT JOIN into an INNER JOIN. LEFT JOIN orders o ON ... WHERE o.status = 'shipped' drops every customer with no matching order, because NULL fails the WHERE filter. If you want to keep all customers but filter which orders count, move the condition into the ON clause: LEFT JOIN orders o ON o.customer_id = c.customer_id AND o.status = 'shipped'.

8 · Subqueries vs CTEs vs derived tables

Scalar subquery — returns one value, used where a single value is expected: SELECT name, (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) AS order_count FROM customer c;

Correlated subquery — references the outer query's row, so conceptually re-runs once per outer row. This is the performance trap: a correlated subquery in the SELECT list or WHERE clause can turn an O(N) query into O(N·M) unless the optimizer can rewrite it into a join/semi-join (modern Postgres often can, but don't assume it always will — profile with EXPLAIN, see Part E).

CTE (WITH) — a named, readable subquery. In Postgres 12+, a non-recursive CTE is inlined into the main query by the planner (same performance as an equivalent subquery) unless it has side effects (a data-modifying CTE) or you force materialization with MATERIALIZED. Pre-12 Postgres always materialized CTEs as an optimization fence — worth knowing the version-dependent behavior exists, even if you don't memorize the exact cutoff.

Recursive CTE — the standard tool for hierarchical/graph-shaped data (org charts, category trees, bill-of-materials):

WITH RECURSIVE org_chart AS (
  SELECT employee_id, name, manager_id, 1 AS depth
  FROM employee WHERE manager_id IS NULL         -- anchor: the CEO
  UNION ALL
  SELECT e.employee_id, e.name, e.manager_id, oc.depth + 1
  FROM employee e
  JOIN org_chart oc ON e.manager_id = oc.employee_id  -- recursive step
)
SELECT * FROM org_chart ORDER BY depth;

Two-part structure every time: an anchor query (base case) UNION ALL'd with a recursive query that joins the CTE to itself, terminating when the recursive step returns no new rows.

9 · Window functions

The single highest-leverage SQL topic for interviews — almost every "hard" SQL problem in a real loop reduces to picking the right window function. The shape is always:

function() OVER (PARTITION BY col ORDER BY col [ROWS/RANGE BETWEEN ... AND ...])

PARTITION BY resets the calculation per group (like a per-group GROUP BY, but rows aren't collapsed). ORDER BY inside OVER defines the row sequence for ranking/running calculations.

FunctionBehavior on tiesTypical use
ROW_NUMBER()Always unique, arbitrary tiebreakDedup rows, pick "the first N per group"
RANK()Ties share a rank, next rank skips"Nth highest salary" when ties should share a place
DENSE_RANK()Ties share a rank, no gap"Nth distinct highest value"
LAG(col, n) / LEAD(col, n)—Compare a row to the previous/next row (day-over-day delta)
NTILE(n)—Split ordered rows into n roughly-equal buckets (quartiles)
SUM()/AVG() OVER (...ROWS BETWEEN ...)—Running total, moving average
-- Nth highest salary per department (N=2), ties handled with DENSE_RANK
SELECT * FROM (
  SELECT employee_id, department_id, salary,
         DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk
  FROM employee
) ranked WHERE rnk = 2;

-- 7-day moving average of daily revenue
SELECT day, revenue,
       AVG(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS moving_avg_7d
FROM daily_revenue;

-- Running cumulative total
SELECT day, revenue, SUM(revenue) OVER (ORDER BY day) AS running_total
FROM daily_revenue;
Postgres shortcut worth knowing: SELECT DISTINCT ON (department_id) * ... ORDER BY department_id, salary DESC is Postgres-specific sugar for "top 1 row per group" that avoids the ROW_NUMBER-subquery dance entirely. Mention it, but default to ROW_NUMBER() in an interview since it's portable across engines.

10 · Aggregate patterns

WHERE vs HAVING — the most-asked one-liner in every list: WHERE filters rows before grouping; HAVING filters groups after aggregation. WHERE dept = 'eng' GROUP BY manager HAVING COUNT(*) > 5 — WHERE removes non-eng rows first, HAVING then keeps only managers with more than 5 remaining reports.

Gaps-and-islands — detecting runs of consecutive values (consecutive login days, consecutive price increases). The standard trick: subtract a row-number from a date/sequence — rows in the same "island" produce the same difference:

SELECT user_id, login_date,
       login_date - (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date))::int AS grp
FROM logins;
-- rows sharing the same (user_id, grp) are one unbroken streak of consecutive days

Deduplication — keep one row per key, discard the rest. Standard pattern:

DELETE FROM employee e
USING (
  SELECT ctid, ROW_NUMBER() OVER (PARTITION BY email ORDER BY employee_id) AS rn
  FROM employee
) d
WHERE e.ctid = d.ctid AND d.rn > 1;

Pivoting without a PIVOT keyword (Postgres has none built in) — conditional aggregation:

SELECT department_id,
       SUM(CASE WHEN gender = 'F' THEN 1 ELSE 0 END) AS female_count,
       SUM(CASE WHEN gender = 'M' THEN 1 ELSE 0 END) AS male_count
FROM employee GROUP BY department_id;

11 · Set operations

OperatorBehaviorCost note
UNIONCombines and removes duplicate rowsImplies a dedup pass (sort or hash) over the combined set — costs more.
UNION ALLCombines, keeps duplicatesNo dedup pass — always prefer this when you already know the sets are disjoint or duplicates are acceptable/desired.
INTERSECTRows present in both setsAlso dedups implicitly.
EXCEPTRows in the first set, not the secondOrder matters — not symmetric.
Interview one-liner: "I default to UNION ALL and only pay for UNION's dedup when I actually need distinct rows — using UNION out of habit is a common accidental performance regression."

12 · Real-interview problem bank

Each of these has shown up, close to verbatim, in product-company SQL rounds. Solutions assume Postgres.

Find the Nth highest salary without LIMIT/OFFSET (portable across engines) 
SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employee
) t WHERE rnk = :N;

DENSE_RANK avoids skipping a place on ties, so "2nd highest" doesn't disappear if two people tie for 1st.

Second highest salary per department 
SELECT department_id, salary FROM (
  SELECT department_id, salary,
         DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk
  FROM employee
) t WHERE rnk = 2;
Employees who earn more than their manager 
SELECT e.name AS employee, e.salary, m.name AS manager, m.salary AS manager_salary
FROM employee e
JOIN employee m ON e.manager_id = m.employee_id
WHERE e.salary > m.salary;

A textbook self-join — the same table plays two roles via two aliases.

Users active on 3+ consecutive days 
WITH islands AS (
  SELECT user_id, login_date,
         login_date - (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date))::int AS grp
  FROM logins
)
SELECT user_id, grp, COUNT(*) AS streak_len, MIN(login_date) AS streak_start, MAX(login_date) AS streak_end
FROM islands GROUP BY user_id, grp HAVING COUNT(*) >= 3;
Remove duplicate rows, keep the earliest by id 
DELETE FROM t a USING t b
WHERE a.id > b.id AND a.dedup_key = b.dedup_key;

Self-anti-join on the natural key, keeping the smaller id.

Top 3 highest-paid employees in each department 
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rn
  FROM employee
) t WHERE rn <= 3;
Month-over-month revenue growth % 
SELECT month, revenue,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month)) / LAG(revenue) OVER (ORDER BY month), 2) AS growth_pct
FROM monthly_revenue;
Find customers who never placed an order 
SELECT c.* FROM customer c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;

Avoid NOT IN (SELECT customer_id FROM orders) here — if a single NULL sneaks into orders.customer_id, NOT IN silently returns zero rows for the entire query. LEFT JOIN/IS NULL or NOT EXISTS are both NULL-safe.

Median salary per department (no MEDIAN() function in Postgres) 
SELECT department_id, PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY salary) AS median_salary
FROM employee GROUP BY department_id;

Popular interview questions — SQL Mastery

Why does NOT IN with a subquery sometimes return zero rows unexpectedly?

If the subquery's result set contains even one NULL, NOT IN evaluates to NULL (not true) for every comparison, because x NOT IN (a, b, NULL) expands to x!=a AND x!=b AND x!=NULL, and the last term is always NULL, poisoning the whole AND. Use NOT EXISTS or a LEFT JOIN/IS NULL instead — both are NULL-safe.

Difference between RANK, DENSE_RANK and ROW_NUMBER?

ROW_NUMBER always assigns unique, sequential numbers even on ties. RANK gives tied rows the same rank but skips the next rank by the count of ties (1,1,3). DENSE_RANK gives tied rows the same rank with no gap (1,1,2).

When would a correlated subquery be slower than a join, and how would you detect it?

When the planner can't rewrite the correlated subquery into a semi-join, it effectively re-executes the inner query per outer row, turning a linear scan into a nested-loop-like cost. Detect it with EXPLAIN ANALYZE — look for a large "loops" count on the inner plan node relative to outer rows (see Part E for the full EXPLAIN walkthrough).

What causes duplicate rows to appear after a JOIN that "shouldn't" have duplicates?

Almost always a fan-out: joining a one-to-many relationship (orders → order_items) without pre-aggregating the many side first. Every matching child row multiplies the parent row in the output.

UNION vs UNION ALL — which do you default to, and why?

UNION ALL, because it skips the implicit dedup (sort/hash) pass. Only use UNION when you specifically need distinct rows across the combined sets — treating UNION as the "safe default" is a common unnecessary performance cost.

How do you get the "top N per group" — walk through it.

Wrap a ROW_NUMBER() OVER (PARTITION BY group_col ORDER BY sort_col DESC) in a subquery or CTE, then filter the outer query on rn <= N. RANK/DENSE_RANK instead of ROW_NUMBER if ties should be allowed to tie for the Nth spot.

What's a CTE's actual runtime behavior in modern Postgres — is it always materialized?

No — since Postgres 12, a non-recursive CTE with no side effects is inlined into the main query plan by default (same cost as an equivalent subquery), unless you explicitly force materialization with the MATERIALIZED keyword or the CTE has side effects (e.g. it's a data-modifying statement).
