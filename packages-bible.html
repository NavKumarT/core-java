Java Packages

What is a Package?

A package is Java's namespace mechanism — a way of organizing related classes, interfaces, enums, and annotations into a single logical unit, backed by an actual directory on disk. Think of it as a folder for your code that also becomes part of every class's fully qualified name.

Why packages exist
  • Avoid naming collisions — two classes named List can coexist in java.util and java.awt
  • Namespace management for large codebases with thousands of classes
  • An access-control boundary — default (package-private) visibility only makes sense because packages exist
  • Logical grouping — related classes live together (all JDBC classes in java.sql)
  • Easier maintenance, discovery, and reuse across teams/modules
A package is, mechanically
  • A directory on disk whose name matches the package name
  • A namespace prefix baked into every class's fully qualified name
  • Declared via a package statement at the top of a .java file
  • NOT a physical container at runtime — the JVM just resolves classes by their FQN and classpath
A package's fully qualified name uniquely identifies every class 
// Without packages — collision, can't have two classes named "List" in one namespace
class List { /* which one?? */ }

// With packages — fully qualified names disambiguate completely
java.util.List<String> l1;   // java.util's List — an interface
java.awt.List l2;                // java.awt's List — a GUI component, totally different class

// This is the actual reason both can exist in the JDK without conflict
💡 Mental model: a package is to classes what a folder is to files — except the "folder path" is also baked directly into the language as part of every class's real name.
Built-in vs Custom

Java packages split into two categories: the ones shipped with the JDK, and the ones you write. Knowing the common built-in packages cold is a baseline interview expectation.

User-defined packages

Any package you create yourself — com.growthscript.service, com.walmart.inventory.dao. Structured identically to built-in packages: a directory tree matching dotted names, with a package statement in every source file inside it.

Using Packages

The import Statement

import is purely a compile-time convenience — it lets you refer to a class by its short name instead of typing the fully qualified name every time. It has zero runtime cost and zero effect on the compiled bytecode's size or behavior.

Single-type import
Wildcard import
Static import
No import — FQN
import java.util.ArrayList;   // imports exactly ONE class
import java.util.List;

public class Demo {
    List<String> names = new ArrayList<>(); // short names now usable
}
import java.util.*;  // imports ALL top-level classes/interfaces DIRECTLY in java.util

public class Demo {
    List<String> names = new ArrayList<>();
    Map<String, Integer> counts = new HashMap<>();
}

// IMPORTANT: java.util.* does NOT import java.util.concurrent.* —
// wildcard import is NOT recursive into sub-packages
ExecutorService ex; // COMPILE ERROR even with "import java.util.*;" — needs its own import
// Static import — brings in STATIC members so you can drop the class prefix
import static java.lang.Math.*;

public class Demo {
    double hyp = sqrt(pow(3, 2) + pow(4, 2)); // Math.sqrt / Math.pow without the "Math." prefix
    double circumference = 2 * PI * radius;          // Math.PI, also static-imported
}

// import static java.util.Collections.emptyList; — imports ONE static member
// Overuse hurts readability — reviewers flag "where did this come from" static imports
// No import needed at all — just spell out the fully qualified name inline
public class Demo {
    java.util.List<String> names = new java.util.ArrayList<>();
    // Verbose, but zero ambiguity — this is the escape hatch when two
    // wildcard-imported packages both define a class with the same name
}
⚠️ Ambiguity trap: if you import java.util.*; and import java.awt.*; and then write List l;, that's a compile error — "reference to List is ambiguous." The compiler won't guess. Fix: use a single-type import for the one you actually want, or the fully qualified name.
💡 java.lang is the one exception: every class in java.lang (String, Object, Math, System, the whole exception hierarchy) is implicitly imported into every Java file — you never write import java.lang.String;, though it's legal to.
Hands-On

Creating a Package & Compiling It

Three rules govern every source file that belongs to a package: the package statement must be the first statement in the file, the directory structure must exactly mirror the package name, and the compiler needs to be told to build that structure for you.

1
Declare the package as the very first line — only comments or blank lines may precede it. Nothing else, not even an import, can come before it.
2
Write the class normally below the package statement.
3
Compile with -d — this tells javac to create the matching directory structure and place the .class file inside it automatically.
4
Run using the fully qualified class name from the directory that contains the top-level package folder — not from inside the package directory itself.
File.java
Compile command
Resulting directory
Run it
// File: File.java  (can be saved anywhere before compiling)
package mypack1; // ← MUST be the first statement in the file

public class File {
    public void show() {
        System.out.println("Hello from mypack1.File");
    }
}
$ javac -d . File.java

// -d .    → generate the package directory structure STARTING at "."
//           (current directory); use -d /some/path for a specific target
// javac reads "package mypack1;" from the source and creates:
//   ./mypack1/File.class

// Without -d: javac just drops File.class next to File.java —
// no package directory is created, and it WON'T run correctly as a package member
.
├── File.java
└── mypack1/
    └── File.class      // javac -d created this folder + placed the class inside

// The folder name "mypack1" MUST exactly match the package name (case-sensitive)
// This is not a convention — the JVM's classloader relies on it to locate classes
// Run from the directory that CONTAINS mypack1/ (i.e. the parent, not inside it)
$ java mypack1.File   // note: dotted fully-qualified name, NOT mypack1/File or mypack1.File.class

// Common mistake: cd into mypack1/ and run "java File" — this FAILS
// with NoClassDefFoundError because the classloader expects the package
// structure to be visible from the classpath root
Nesting

Creating a Sub-package

A sub-package is just a package whose name has more dot-separated segments — declared the same way, compiled the same way. The interview trap is assuming this nesting grants some kind of special access relationship. It doesn't.

package packageName.subPackageName; 
package mypack1.subpack1; // dot-separated — this IS the entire package name

public class Helper {
    public void assist() { System.out.println("in subpack1"); }
}

// Directory structure MUST nest to match:
// mypack1/
//   subpack1/
//     Helper.class
// Compile from the source root: javac -d . mypack1/subpack1/Helper.java
// Run:                          java mypack1.subpack1.Helper
🚫 Critical interview point — packages are NOT hierarchical for access control. mypack1.subpack1 is a completely independent, unrelated package as far as the compiler and access modifiers are concerned. A class in mypack1 has zero special access to default (package-private) members in mypack1.subpack1, and vice versa. import mypack1.*; does NOT pull in mypack1.subpack1 either — the "sub" in "sub-package" describes the naming convention and directory nesting only, not a parent-child access relationship.
Access Control

Access Modifiers in Java

Four levels of visibility, from most to least restrictive: private → default (no keyword) → protected → public. Every one of these is a favorite whiteboard question because the middle two are easy to mix up.

// private — accessible ONLY inside the same class (not even subclasses)
package com.growthscript.model;

public class Account {
    private double balance; // hidden from EVERY other class, including subclasses

    private void auditLog() { /* internal-only helper */ }
}

class SavingsAccount extends Account {
    void test() {
        balance = 100; // COMPILE ERROR — even a subclass can't see a private field
    }
}
// default (package-private) — no keyword at all, just omit the modifier
package com.growthscript.model;

class InternalHelper { // no modifier → default access
    void assist() { /* also default — package-private method */ }
}

// From ANOTHER class in com.growthscript.model → fully accessible
class Service {
    void use() { new InternalHelper().assist(); } // works — same package
}

// From com.growthscript.other (a DIFFERENT package) → invisible entirely
package com.growthscript.other;
import com.growthscript.model.InternalHelper; // COMPILE ERROR — can't even import it
// protected — package access PLUS subclasses anywhere, with a catch (see below)
package com.growthscript.model;

public class Account {
    protected double balance;
    protected void applyInterest() { /* ... */ }
}

// From a DIFFERENT package, subclassing IS allowed to use protected members —
// but only through "this" / a reference of the SUBCLASS's own type
package com.growthscript.other;
class SavingsAccount extends com.growthscript.model.Account {
    void grow() {
        this.balance += 10;   // ✓ works — accessed via inherited "this"
        applyInterest();      // ✓ works — inherited protected method
    }
}
// public — accessible from absolutely anywhere, no restrictions
package com.growthscript.model;

public class Account {
    public String accountId;
    public double getBalance() { return balance; }
}

// From literally any package, any class, any relationship (or none at all)
package com.walmart.billing;
import com.growthscript.model.Account;
class Invoice {
    void charge(Account a) { a.getBalance(); } // fully accessible, no relationship needed
}
The Trap

protected — The Rule Nobody Remembers Correctly

protected is "accessible everywhere except by non-subclasses in a different package" — but there's a sharper rule hiding inside that: from a different package, you can only reach a protected member through a reference of your own subclass type, never through a reference typed as the superclass.

The reference-type restriction — a very common FAANG trap 
package com.growthscript.model;
public class Account {
    protected double balance;
}
package com.growthscript.other; // different package — subclass relationship exists
import com.growthscript.model.Account;

class SavingsAccount extends Account {

    void ok() {
        this.balance = 100;          // ✓ COMPILES — "this" is typed as SavingsAccount
    }

    void alsoOk(SavingsAccount other) {
        other.balance = 100;         // ✓ COMPILES — reference typed as SavingsAccount (the subclass)
    }

    void fails(Account acc) {
        acc.balance = 100;           // ✗ COMPILE ERROR — reference typed as Account (the SUPERCLASS)
    }                                 // even though acc might hold a SavingsAccount object at runtime!
}
💡 Why this rule exists: the compiler can't know at compile time that an Account-typed parameter actually points to a SavingsAccount — it could be a totally unrelated CheckingAccount instance from the same package with no relationship to SavingsAccount at all. Restricting access to your own subclass's type (or subtypes of it) is how Java keeps this check sound at compile time.
⚠️ Note: this restriction only applies across packages. Within the SAME package, protected behaves exactly like default — any class can access it through any reference type, subclass or not, since package access already covers that case.
Class Declarations

Top-Level Class Modifier Rules

A top-level (outer) class can only ever be public or default (package-private) — private and protected are illegal on it. Those two only make sense on members (fields, methods, constructors, and nested classes), which live inside a class and can be scoped tighter than the class itself.

Valid top-level declarations
Illegal top-level declarations
Nested classes — all 4 allowed
public class Account { }     // ✓ public — visible everywhere

class InternalHelper { }    // ✓ default (no modifier) — package-private, visible only in this package
private class Broken { }    // ✗ COMPILE ERROR — "modifier private not allowed here"

protected class AlsoBroken { } // ✗ COMPILE ERROR — "modifier protected not allowed here"

// Reasoning: "private" would mean "visible only inside itself" — meaningless
// for a top-level type with nothing enclosing it. Same logic kills protected:
// there's no enclosing class to inherit access relative to.
// Nested (inner) classes ARE members of the enclosing class — so all 4 apply
public class Outer {
    public class    PublicInner    { }  // ✓ visible everywhere
    protected class ProtectedInner { }  // ✓ package + subclasses
    class           DefaultInner   { }  // ✓ package-private
    private class  PrivateInner   { }  // ✓ visible only inside Outer
}
🚫 One public top-level class per file, and it must match the filename. Account.java can contain at most one public class Account — plus as many default-access top-level classes as you want. Two public top-level classes in one file, or a public class whose name doesn't match the filename, is a compile error.
Conventions

Package Naming Conventions & CLASSPATH

Package names follow the reverse-domain-name convention specifically to guarantee global uniqueness — two companies can't accidentally publish colliding package names if both are rooted in their own domains.

Reverse domain convention 
// Domain: citi.com  →  package root: com.citi
package com.citi.academic.account;

// Domain: growthscript.com  →  package root: com.growthscript
package com.growthscript.youtube.analytics;

// Rules:
// - all lowercase (avoids clashes on case-insensitive filesystems like Windows/macOS,
//   and avoids confusion with class names, which are conventionally PascalCase)
// - segments separated by dots, matching nested folders exactly
// - avoid Java reserved words as segments (no "com.citi.class.account")
// - avoid starting a segment with a digit (illegal identifier)

CLASSPATH — how the JVM finds your packages

The classpath is the set of root directories (and/or JARs) the JVM searches when resolving a fully qualified class name. When you run java mypack1.File from a directory containing mypack1/, that directory is implicitly on the classpath. For anything beyond the current directory — external JARs, other source roots — use java -cp path1:path2 mypack1.File (semicolon-separated on Windows). A JAR file is simply a zipped bundle of compiled packages plus a manifest; it's how packages get distributed and depended on (Maven/Gradle dependencies are ultimately JARs full of packages).

FAANG Rapid-Fire Q&A — Tricky Questions

Packages sound simple, which is exactly why interviewers use them to check whether you actually understand Java's compilation and access model, or just memorized "public means everyone can see it."

Output / compile-error prediction

package statement order
Multiple public classes
Extending a default class
Does import cost anything?
// Q: Does this compile?
import java.util.List;
package com.growthscript.model; // package statement AFTER an import

public class Account { }

// A: NO — COMPILE ERROR: "package statement must be the only statement
// on this line" / must appear before any import or type declaration.
// Only comments and blank lines are allowed before "package".
// Q: Does Account.java compile with this content?
package com.growthscript.model;

public class Account { }
public class AccountHistory { } // a SECOND public top-level class, same file

// A: NO — COMPILE ERROR: a .java file can have at most ONE public
// top-level type, and its name must match the filename (Account.java).
// Fix: move AccountHistory to its own AccountHistory.java, OR make it
// default-access (drop "public") if it's only meant to be used in-package.
// Q: Can you extend this class from a different package?
package com.growthscript.model;
class InternalBase { } // default access — no modifier
package com.growthscript.other;
import com.growthscript.model.InternalBase; // COMPILE ERROR right here
class Derived extends InternalBase { }

// A: You can't even IMPORT it, let alone extend it. Default-access classes
// are invisible outside their package — there's no special "I'm extending it"
// exemption. The class itself must be public for cross-package subclassing.
// Q: Does "import java.util.*;" make the compiled program bigger or slower?

// A: No — imports are a PURE COMPILE-TIME convenience. The compiler resolves
// every short name to its fully qualified name and bakes THAT into the
// bytecode (the constant pool references FQNs). Whether you write:
List<String> a;                  // with "import java.util.*;"
java.util.List<String> b;        // with no import at all
// ...both compile to IDENTICAL bytecode. Zero runtime difference, zero
// difference in .class file size from importing "too much."

Short-answer FAANG questions

❓ Can two classes share a name in different packages?

  • Yes — java.util.List and java.awt.List both exist
  • The package prefix is part of the real, unique identity of the class
  • Only becomes a problem if you wildcard-import both into the same file

❓ Is java.lang imported automatically?

  • Yes — every class in java.lang is implicitly available
  • String, Object, Math, System, Thread, and the exception hierarchy need no import
  • Explicitly writing import java.lang.String; is legal but pointless

❓ Does a wildcard import include sub-packages?

  • No — import java.util.*; does NOT pull in java.util.concurrent.*
  • Each sub-package needs its own explicit or wildcard import
  • Same non-hierarchy rule that applies to access control also applies to imports

❓ Can a top-level class be private or protected?

  • No — only public or default (no modifier) are legal on top-level classes
  • private/protected are only meaningful on members of an enclosing class
  • Nested/inner classes CAN be private, protected, default, or public

❓ Do sub-packages inherit parent package access?

  • No — com.x and com.x.y are entirely independent packages
  • Default-access members in one are invisible in the other, despite the dotted naming
  • The "sub" relationship is a naming/folder convention only, not an access grant

❓ protected across packages — what's the catch?

  • Accessible in a subclass in another package, but only via a reference typed as that subclass (or narrower)
  • Access through a reference typed as the superclass fails to compile, even cross-package
  • Within the SAME package, protected behaves just like default — no restriction

❓ What exactly does javac -d do?

  • Reads the package statement and builds matching directories automatically
  • Without -d, the .class file lands next to the .java file with no package folder
  • -d . roots the generated structure at the current directory

❓ Why the reverse-domain naming convention?

  • Guarantees global uniqueness — domains are already globally unique
  • Prevents two companies from ever publishing colliding package names
  • All lowercase avoids case-sensitivity issues across filesystems

❓ What is a package-private constructor used for?

  • Forces object creation through a factory method or builder in the same package
  • Common in framework internals — prevents external code from instantiating directly
  • Class can still be public; only the constructor is restricted
Interview Reference

Interview Cheatsheet

One-liners for when you're under pressure. Know these cold.

📦 What a package is

  • Namespace + directory that groups related classes/interfaces/enums
  • Avoids naming collisions, adds an access-control layer
  • Directory name must match package name exactly (case-sensitive)
  • Not a runtime container — just a naming/classloading mechanism

📥 import rules

  • Compile-time only — zero runtime cost, zero bytecode size difference
  • Wildcard (*) imports one level only — NOT recursive into sub-packages
  • Two wildcard imports with a name clash → ambiguity compile error
  • java.lang.* is always implicitly imported — never needs importing
  • static import brings in static members, drops the class-name prefix

🏗️ Creating a package

  • package name; must be the first statement in the file
  • Only comments/blank lines may precede it — not even imports
  • Compile: javac -d . File.java — builds matching directories
  • Run: java pkg.name.ClassName from the classpath root

🔗 Sub-packages

  • package parent.child; — just a longer dotted name
  • NOT hierarchical for access — parent and child are fully independent
  • Default-access members aren't shared between parent and sub-package
  • Wildcard import of parent does NOT pull in the sub-package

🔐 Access modifiers

  • private: same class only
  • default (no keyword): same class + same package
  • protected: same package + subclasses anywhere (via subclass-typed reference)
  • public: everywhere, no restriction

⚠️ protected across packages

  • Cross-package access only works through a subclass-typed reference
  • Access via a superclass-typed reference fails to compile, even in a subclass
  • Same-package protected access has no such restriction — acts like default

🏛️ Top-level class rules

  • Only public or default allowed — never private, never protected
  • At most ONE public top-level class per .java file
  • Public class name must match the filename exactly
  • Nested/inner classes CAN use all 4 modifiers — they're members

🌐 Naming convention

  • Reverse domain name: com.company.module
  • All lowercase, dot-separated, matches folder nesting exactly
  • Avoid Java reserved words and digit-first segments
  • Guarantees global uniqueness across organizations

🚨 Top interview traps

  • package statement not first line → compile error
  • Two public top-level classes in one file → compile error
  • Private/protected top-level class → compile error
  • Wildcard import ≠ recursive into sub-packages
  • protected via superclass reference (cross-package) → compile error
  • Sub-packages have NO special access to their "parent" package
  • Default-access class can't even be imported cross-package, let alone extended

🗂️ CLASSPATH quick ref

  • Set of roots (dirs/JARs) the JVM searches for FQN class resolution
  • Current dir is implicitly on the classpath when running java
  • -cp path1:path2 (or ; on Windows) adds more roots
  • A JAR = zipped compiled packages + manifest — how dependencies are shipped
