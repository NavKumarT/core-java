1. Transactional outbox (fixing the dual write)

Problem: "save to DB and publish to Kafka" cannot be atomic. Crash between the two and you either lose the event or publish one for data that was rolled back.

@Transactional                                   // one DB transaction
public void placeOrder(OrderDto dto) {
  Order order = orderRepo.save(Order.from(dto));
  outboxRepo.save(new OutboxEvent(UUID.randomUUID(), "order", order.getId().toString(),   // aggregate key
                                  "OrderPlaced", toJson(order), Instant.now()));
}

@Scheduled(fixedDelay = 500)                     // relay (or use Debezium CDC instead of polling)
public void publish() {
  for (OutboxEvent e : outboxRepo.findTop100ByPublishedFalseOrderById()) {
    kafkaTemplate.send("orders", e.getAggregateId(), e.getPayload()).get(5, TimeUnit.SECONDS);
    e.markPublished();                           // crash before this line → re-publish → duplicates
    outboxRepo.save(e);
  }
}
  • Delivery is at-least-once: consumers must be idempotent, and the event id doubles as the dedupe key.
  • Key by aggregate id to keep per-entity ordering. Run one relay per shard or use SELECT ... FOR UPDATE SKIP LOCKED to avoid double-sending across instances.
  • Polling vs CDC: polling is simple but adds DB load and latency; Debezium tails the DB log (near real-time, no polling), often with the outbox event router SMT. Clean up published rows on a schedule.

2. Idempotent consumer implementations

With at-least-once delivery, processing the same record twice must have the same effect as once.

@Transactional
public void handle(PaymentEvent e) {
  try {
    processedRepo.saveAndFlush(new ProcessedEvent(e.eventId()));   // PK/unique on event_id
  } catch (DataIntegrityViolationException dup) {
    return;                                                         // already processed → ack and skip
  }
  ledgerService.apply(e);                                           // business write in the same transaction
}
TechniqueNotes
Processed-events table, same DB transactionStrongest for DB sinks; needs cleanup (TTL) and an event id from the producer
Upsert / natural idempotencyINSERT ... ON CONFLICT DO UPDATE, "set status = X"; no extra table
Version checkApply only if event.version > stored.version; also drops stale out-of-order events
Cache-based dedupe (Redis SETNX + TTL)Fast, but not atomic with the DB write; a crash between them still needs a safe retry
Downstream idempotency keyPass the event id to the external API (payments) so the remote side dedupes
Payments angle: the client sends an idempotency key on the REST call; the service stores key → result; the event carries a unique id; every consumer dedupes on it. Duplicates from retries, rebalances and DLT replays then become harmless.

3. Saga for distributed transactions

  • No 2PC across microservices. A saga is a sequence of local transactions with compensating actions on failure (e.g. order → reserve stock → charge payment; if payment fails, release stock, cancel order).
  • Choreography: services react to each other's events. Simple, decoupled, but the flow is implicit and hard to trace as it grows.
  • Orchestration: a coordinator (state machine) sends commands and tracks state. Explicit flow, easier to monitor and reason about, one more component.
  • Requirements: a correlation id on every event, idempotent handlers and compensations, timeouts for missing replies, persisted saga state, and compensations that cannot fail permanently (retry, then alert).
  • Combine with the outbox so each step's state change and event are atomic.

4. CQRS, event sourcing, event-carried state

  • CQRS: separate write model and read model; Kafka carries changes to build read-optimized views (search index, cache). Read side is eventually consistent.
  • Event sourcing: store the sequence of events as the source of truth and derive state by replay. Powerful audit and time travel; costs: schema evolution, snapshots, harder queries.
  • Event-carried state transfer: events include enough data that consumers need not call back the producer, at the cost of larger events and duplicated data.

5. Backpressure, pause/resume, slow downstream

Kafka is pull-based, so a slow consumer simply polls less and data waits in the log (until retention). The danger is exceeding max.poll.interval.ms or overloading a fragile downstream.

@Autowired KafkaListenerEndpointRegistry registry;

// circuit breaker opened → stop polling but stay in the group (heartbeats continue)
registry.getListenerContainer("libraryListener").pause();
// ... downstream recovered
registry.getListenerContainer("libraryListener").resume();

@KafkaListener(id = "libraryListener", topics = "library-events")
public void onMessage(ConsumerRecord<Integer,String> r) { ... }
  • pause() keeps the consumer in the group without triggering a rebalance (unlike stopping it). Pair with Resilience4j circuit breaker events, rate limiters and bulkheads on downstream calls.
  • Lower max.poll.records, batch DB writes, use bounded queues and timeouts. Unbounded in-memory queues turn backpressure into OOM.

6. Parallelism without breaking order

  • One partition = one thread by default. To go faster: more partitions and consumers; batch processing; or key-sharded executors (hash key → one of N single-thread executors) so per-key order holds while different keys run in parallel. Commit offsets only up to the lowest completed offset per partition.
  • Libraries such as Confluent's Parallel Consumer implement this. Simpler alternative: raise partitions and replicas × concurrency.

7. Kafka Connect and Debezium

  • Connect is the integration framework: source connectors pull from systems into topics, sink connectors push topics to systems (JDBC, S3, Elasticsearch). Runs as a scalable cluster of workers with tasks; config via REST; offsets and configs stored in internal Kafka topics. Converters (Avro/JSON) and SMTs transform records.
  • Debezium = CDC source connector: reads the database transaction log (Postgres WAL, MySQL binlog) and emits change events (before/after, op type). No dual write, near real-time; use for the outbox, cache/search sync, and data lake feeds.
  • Error handling: errors.tolerance=all with errors.deadletterqueue.topic.name (sink connectors) routes bad records aside. Watch for schema changes and initial-snapshot load.
  • Prefer Connect over hand-written consumers for standard data movement: fewer bugs, built-in scaling and offset handling.

8. Kafka Streams basics

StreamsBuilder b = new StreamsBuilder();
b.stream("orders", Consumed.with(Serdes.String(), orderSerde))
 .filter((k, o) -> o.amount() > 0)
 .groupByKey()
 .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5)))
 .count(Materialized.as("orders-per-5min"))
 .toStream().to("order-counts");
  • A client library (no separate cluster): the app is the stream processor. KStream = record stream, KTable = latest value per key (changelog), GlobalKTable = full copy on each instance.
  • State lives in local RocksDB stores backed by changelog topics, so state is rebuilt after a failure; num.standby.replicas speeds failover.
  • Scaling = partitions (tasks) spread over instances. Joins require co-partitioned topics (same key, same partition count).
  • Exactly-once: processing.guarantee=exactly_once_v2. Windowing, grace periods and late events are the usual tricky part.
  • Streams vs plain consumer vs Flink: Streams for Kafka-to-Kafka stateful processing in JVM services; plain consumers for simple side effects; Flink for large, complex, multi-source streaming jobs.

9. Multi-cluster and disaster recovery

  • MirrorMaker 2 (Connect-based) replicates topics, configs and consumer-group offsets between clusters; remote topics are prefixed with the source cluster alias. Replication is asynchronous, so RPO > 0.
  • Active-passive: simplest; fail over consumers to the DR cluster using translated offsets; expect some duplicates, so idempotency again.
  • Active-active: each region writes its own topics; consumers read both; watch for loops and conflicts.
  • Stretch cluster across 3 AZs/regions (rack-aware, RF 3, min.insync.replicas=2): RPO near zero but needs low inter-site latency; a 2-site stretch cannot survive site loss with quorum.
  • Define RPO/RTO first, rehearse failover, and test consumer offset translation.

12. Capacity planning quick rules

  • Disk ≈ ingest rate × retention × replication factor × (1 + ~20–30% overhead/headroom). Keep disks below roughly 60–70% used.
  • Network: broker egress = consumers × ingest + replication traffic ((RF−1) × ingest). Check NIC capacity, especially with many consumer groups.
  • Memory: modest JVM heap (~6 GB), the rest for page cache. CPU matters for TLS and compression.
  • Broker count: enough for RF, throughput and partition limits, plus capacity to lose one broker (N−1) without breaching limits. Use SSD/NVMe or well-provisioned JBOD; XFS or ext4.

Interview Q&A

Tap a question to expand.

★ Explain the dual-write problem and the outbox pattern.
DB and Kafka writes are not atomic. Outbox: write business data and an outbox row in one DB transaction, and a relay (poller or Debezium CDC) publishes to Kafka. Delivery becomes at-least-once, so consumers dedupe by event id.
★ How do you implement an idempotent consumer?
Unique event id stored in a processed-events table inside the same DB transaction as the business write (or natural idempotency by upsert/version check). On duplicate key, skip and acknowledge.
★ Design payment processing with Kafka so nothing is lost or double-charged.
Client idempotency key → API stores key/result → outbox → topic keyed by account/payment id → idempotent consumers with processed-event table → idempotent call to the payment provider with the same key → retries with backoff, DLT and reconciliation job for unknowns. Producer: acks=all, idempotence, RF 3, min ISR 2.
★ Saga: choreography or orchestration?
Choreography for few steps and loose coupling; orchestration when the flow is long, needs timeouts, visibility and compensation logic in one place. Both need correlation ids, idempotent handlers and compensations.
How do you pause a consumer without a rebalance?
container.pause() (or consumer.pause(partitions)) stops fetching while polling continues and the member stays in the group. Stopping the container leaves the group and triggers a rebalance.
Can you process records in parallel and still keep per-key order?
Yes: shard by key hash onto single-threaded executors and commit only contiguous completed offsets. Or scale partitions and consumers instead.
★ Kafka Connect vs writing your own consumer?
Connect for standard source/sink movement (scaling, offsets, retries, DLQ built in). Custom consumer for business logic and side effects.
What is CDC and why Debezium over polling?
CDC streams committed DB changes from the transaction log: low latency, no load from polling queries, captures deletes and ordering per row; needs log access and careful snapshot and schema handling.
KStream vs KTable? Why must join topics be co-partitioned?
KStream is an event stream, KTable is latest-state per key. A join needs matching keys in the same partition number so a task can hold both sides locally.
★ How would you do disaster recovery across regions?
Define RPO/RTO. MirrorMaker 2 active-passive (async, offset translation, expect duplicates) or a stretch cluster across 3 sites for near-zero RPO with low latency. Automate and rehearse failover; keep consumers idempotent.
★ Which metrics do you alert on?
Broker: under-replicated/under-min-ISR/offline partitions, controller count, disk. Producer: error/retry rate, latency. Consumer: lag (offset and time), rebalance rate. App: DLT depth and end-to-end latency.
How do you do a zero-downtime rolling upgrade of brokers?
One broker at a time with controlled shutdown, wait for URP = 0, follow the documented version/metadata upgrade order, and test client compatibility first.
How do you size disk for a topic?
Ingest rate × retention × RF, plus headroom (say 30%), and keep utilization under ~70%. Check replication and consumer egress against the network too.
Event sourcing pitfalls?
Schema evolution of stored events, replay time (need snapshots), eventual consistency of read models, and harder ad-hoc queries.
