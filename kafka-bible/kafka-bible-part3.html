1. Unit vs integration testing

Video 49

Unit testIntegration test
ScopeOne class or slice; collaborators mockedReal Spring context; real (embedded or containerized) Kafka
Tools@WebMvcTest, MockMvc, Mockito@SpringBootTest, @EmbeddedKafka or Testcontainers, TestRestTemplate
SpeedMilliseconds to secondsSeconds; needs a broker
ProvesLogic, validation, status codesWiring, config, serialization, and that a record really reaches a topic
  • Testing pyramid: many unit tests, fewer integration tests, very few end-to-end tests.
  • Structure each test as given / when / then; one behavior per test; name tests by behavior (postLibraryEvent_invalidBook_returns400).

2. Unit testing POST and PUT with MockMvc

Videos 50–51

@WebMvcTest loads only the web layer (controllers, advice, Jackson). No Kafka, no full context. Mock the producer.

@WebMvcTest(LibraryEventsController.class)
class LibraryEventsControllerUnitTest {
  @Autowired MockMvc mockMvc;
  @Autowired ObjectMapper objectMapper;
  @MockitoBean LibraryEventProducer producer;     // @MockBean before Spring Boot 3.4

  static LibraryEvent event(Integer id, LibraryEventType type, Book book) { return new LibraryEvent(id, type, book); }
  static final Book BOOK = new Book(123, "Kafka Guide", "Dilip");

  @Test
  void post_valid_returns201() throws Exception {
    when(producer.sendLibraryEvent(any())).thenReturn(CompletableFuture.completedFuture(null));

    mockMvc.perform(post("/libraryevents")
            .contentType(MediaType.APPLICATION_JSON)
            .content(objectMapper.writeValueAsString(event(null, LibraryEventType.NEW, BOOK))))
        .andExpect(status().isCreated());
    verify(producer, times(1)).sendLibraryEvent(any());
  }

  @Test
  void post_invalidBook_returns400() throws Exception {
    var bad = event(null, LibraryEventType.NEW, new Book(null, "", ""));
    mockMvc.perform(post("/libraryevents").contentType(MediaType.APPLICATION_JSON)
            .content(objectMapper.writeValueAsString(bad)))
        .andExpect(status().isBadRequest())
        .andExpect(jsonPath("$['book.bookId']").exists());     // from RestControllerAdvice
    verifyNoInteractions(producer);
  }

  @Test
  void put_missingId_returns400() throws Exception {
    mockMvc.perform(put("/libraryevents").contentType(MediaType.APPLICATION_JSON)
            .content(objectMapper.writeValueAsString(event(null, LibraryEventType.UPDATE, BOOK))))
        .andExpect(status().isBadRequest());
  }
}
  • Test the negative paths: missing fields, wrong type, missing id on PUT. Assert the producer is never called on invalid input.
  • Use @Import(GlobalExceptionHandler.class) if the advice is not picked up in your slice.

3. Integration testing POST and PUT

Videos 52–53

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@EmbeddedKafka(topics = "library-events", partitions = 3,
                bootstrapServersProperty = "spring.kafka.bootstrap-servers")   // overrides app config
class LibraryEventsControllerIntegrationTest {
  @Autowired TestRestTemplate restTemplate;
  @Autowired EmbeddedKafkaBroker embeddedKafka;
  @Autowired ObjectMapper objectMapper;
  Consumer<Integer,String> consumer;

  @BeforeEach void setUp() {
    var props = new HashMap<>(KafkaTestUtils.consumerProps("test-group", "true", embeddedKafka));
    props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
    consumer = new DefaultKafkaConsumerFactory<>(props, new IntegerDeserializer(), new StringDeserializer()).createConsumer();
    embeddedKafka.consumeFromAllEmbeddedTopics(consumer);
  }
  @AfterEach void tearDown() { consumer.close(); }

  @Test
  void post_publishesToKafka() throws Exception {
    var event = new LibraryEvent(null, LibraryEventType.NEW, new Book(123, "Kafka Guide", "Dilip"));
    var res = restTemplate.exchange("/libraryevents", HttpMethod.POST, new HttpEntity<>(event), LibraryEvent.class);

    assertEquals(HttpStatus.CREATED, res.getStatusCode());
    ConsumerRecord<Integer,String> rec = KafkaTestUtils.getSingleRecord(consumer, "library-events");
    assertEquals(objectMapper.writeValueAsString(event), rec.value());
  }

  @Test
  void put_sendsKeyedEvent() {
    var event = new LibraryEvent(999, LibraryEventType.UPDATE, new Book(123, "Kafka Guide 2", "Dilip"));
    restTemplate.exchange("/libraryevents", HttpMethod.PUT, new HttpEntity<>(event), LibraryEvent.class);
    var rec = KafkaTestUtils.getSingleRecord(consumer, "library-events");
    assertEquals(999, rec.key());
  }
}
  • The real flow runs: HTTP → controller → KafkaTemplate → embedded broker → a test consumer reads it back and asserts key and value.
  • Embedded Kafka: in-JVM, fast to start, not identical to a real broker. Testcontainers (KafkaContainer + @ServiceConnection, Boot 3.1+) uses a real Kafka image, closest to production but needs Docker.
  • Avoid flakiness: unique consumer group per test, close consumers, use earliest, prefer Awaitility over Thread.sleep, keep a timeout on reads.

4. Unit testing the producer (KafkaTemplate mocked)

Video 54

@ExtendWith(MockitoExtension.class)
class LibraryEventProducerUnitTest {
  @Mock KafkaTemplate<Integer,String> kafkaTemplate;
  @Spy ObjectMapper objectMapper = new ObjectMapper();
  @InjectMocks LibraryEventProducer producer;

  LibraryEvent event = new LibraryEvent(1, LibraryEventType.NEW, new Book(1, "Book", "Author"));

  @BeforeEach void init() { ReflectionTestUtils.setField(producer, "topic", "library-events"); }

  @Test
  void send_success() throws Exception {
    var record = new ProducerRecord<Integer,String>("library-events", 1, "json");
    var meta = new RecordMetadata(new TopicPartition("library-events", 1), 1, 0, System.currentTimeMillis(), 1, 2);
    when(kafkaTemplate.send(eq("library-events"), eq(1), anyString()))
        .thenReturn(CompletableFuture.completedFuture(new SendResult<>(record, meta)));

    var result = producer.sendLibraryEvent(event).get();
    assertEquals(1, result.getRecordMetadata().partition());
  }

  @Test
  void send_failure() {
    when(kafkaTemplate.send(anyString(), any(), anyString()))
        .thenReturn(CompletableFuture.failedFuture(new RuntimeException("Kafka unavailable")));

    assertThrows(ExecutionException.class, () -> producer.sendLibraryEvent(event).get());
  }
}
  • Stub send() with completedFuture for success and failedFuture for the failure path, so the callback logic is exercised without a broker.
  • Field injection with @Value is awkward to unit test (needs ReflectionTestUtils). Constructor-injecting the topic makes tests simpler.

5. OpenAPI and Swagger

Videos 55–56

  • OpenAPI is the vendor-neutral spec (YAML/JSON) that describes a REST API: paths, methods, schemas, status codes, auth. Swagger UI is a tool that renders it.
  • Why it matters: one contract for consumers and producers, always-current docs, client and server code generation, contract testing, API gateway and governance integration, and easier onboarding.
  • Spring Boot 3: add org.springdoc:springdoc-openapi-starter-webmvc-ui. Spec at /v3/api-docs, UI at /swagger-ui.html.
  • Code-first (generate spec from annotated controllers, what springdoc does) vs contract-first (write spec, generate stubs; better for cross-team APIs).
@Bean OpenAPI api() {
  return new OpenAPI().info(new Info().title("Library Events Producer").version("v1")
      .description("Publishes library events to Kafka"));
}

@Tag(name = "Library Events")
@Operation(summary = "Publish a NEW library event")
@ApiResponses({
  @ApiResponse(responseCode = "201", description = "Accepted and sent"),
  @ApiResponse(responseCode = "400", description = "Validation failed")})
@PostMapping
public ResponseEntity<LibraryEvent> post(@RequestBody @Valid LibraryEvent e) { ... }
Production note: disable or protect Swagger UI in prod (springdoc.swagger-ui.enabled=false under the prod profile), since it exposes your API surface.

6. AGENTS.md

Video 57

  • A markdown file in the repo root that gives AI coding agents standing instructions about the project (a README for agents). Tools read it automatically; some use their own name (e.g. CLAUDE.md, Copilot instructions file).
  • Put in it: what the project is, tech stack and versions, exact build/test commands, package layout, coding conventions, testing rules, and explicit do/don't lists (e.g. "never commit secrets", "always add a unit test").
  • Keep it short, concrete, and versioned in git. Nested files in subfolders can specialize instructions. It is loaded into context every time, so bloat costs tokens.
# Library Events Producer
Spring Boot 3.3, Java 21, Spring Kafka, Maven.

## Commands
- Build: `./mvnw clean verify`
- Test:  `./mvnw test`

## Rules
- Controllers are thin: validate with `@Valid`, delegate to a service/producer.
- Errors go through `GlobalExceptionHandler`; never return stack traces.
- Every new endpoint needs a MockMvc test and an integration test.
- Kafka key is always `libraryEventId`.

7. Skills for coding agents

Videos 58–60

  • A skill is a packaged, reusable set of instructions (a folder with a SKILL.md containing a name and description, plus optional scripts and templates) that an agent loads only when the task matches.
  • AGENTS.md vs skill: AGENTS.md is always in context (project-wide rules); a skill is loaded on demand (task-specific playbook), which keeps context small. Skills are reusable across projects and shareable with a team.
  • The description is what the agent uses to decide when to load it, so write it as "use when the user asks to write tests for X".
---
name: testing-skill
description: Use when writing or reviewing unit and integration tests for this Spring Boot Kafka service.
---
# Testing skill
1. Controllers: `@WebMvcTest` + `MockMvc`, mock the producer with `@MockitoBean`.
2. Producer: mock `KafkaTemplate`; cover `completedFuture` and `failedFuture`.
3. Integration: `@SpringBootTest` + `@EmbeddedKafka`; read back with `KafkaTestUtils`.
4. Always test the invalid-input path and assert no Kafka call happens.
5. Name tests `method_condition_expectedResult`; use given/when/then.
  • Controller skill (video 60) encodes controller conventions: thin controllers, @Valid on bodies, correct status codes, OpenAPI annotations, errors via the advice, and delegating to the producer.
  • Good skills are specific, include examples, and are reviewed like code. Treat generated output as a draft: run the tests.

Interview Q&A

Tap a question to expand.

Testing

★ @WebMvcTest vs @SpringBootTest?
@WebMvcTest loads only the web slice (controllers, advice, converters), fast, needs mocks for services. @SpringBootTest loads the full context, use it for integration tests with real wiring and Kafka.
★ @Mock vs @MockBean/@MockitoBean?
@Mock (Mockito) creates a plain mock, no Spring involved. @MockBean (now @MockitoBean from Boot 3.4) replaces a bean in the Spring context with a mock.
★ How do you test code that publishes to Kafka?
Unit: mock KafkaTemplate and stub the future (success and failure). Integration: @EmbeddedKafka or Testcontainers, call the endpoint, read the record back with a test consumer, assert topic, key, value, headers.
★ Embedded Kafka vs Testcontainers?
Embedded: no Docker, fast, in-JVM, but not the real broker distribution. Testcontainers: real Kafka in Docker, more faithful (also for KRaft/security configs), slower and requires Docker in CI. Reuse a container across tests for speed.
How do you assert that a message went to the right partition with the right key?
Read the ConsumerRecord in the test and assert key(), partition() (same key must always yield the same partition), and headers().
How do you test failure handling when Kafka is unavailable?
Unit: stub failedFuture. Integration: point at a bad bootstrap server with small max.block.ms/delivery.timeout.ms and assert the error response or persisted-failure behavior.
What should you not mock?
The thing under test, value objects, and simple data holders. Prefer real objects unless slow, non-deterministic or external. Over-mocking makes tests pass while production breaks.
What is contract testing and why use it for Kafka?
Verifies that producer and consumer agree on message shape without running both (Pact, Spring Cloud Contract, or schema compatibility checks in a Schema Registry). It catches breaking payload changes early.

Situational

★ Your integration tests are flaky. What do you check?
Shared consumer groups or topics between tests, missing earliest offset reset, fixed sleeps instead of Awaitility, unclosed consumers, port clashes, ordering assumptions across partitions, and test-time metadata delay on the first send.
The test suite takes 15 minutes. How do you speed it up?
Push logic into unit and slice tests, share one Spring context and one Kafka container across classes, avoid @DirtiesContext, run tests in parallel where safe, and keep the integration tests to the critical paths.
How do you keep test data and topics isolated?
Unique group ids and topic names per test class, delete or recreate topics in @AfterEach when needed, or seek to the end before each test.

OpenAPI and AI tooling

★ Why use OpenAPI? Code-first or contract-first?
It gives a machine-readable contract for docs, client generation, validation and governance. Code-first is quick for one team; contract-first is better when several teams agree on the API before implementation.
How do you document errors and security in OpenAPI?
@ApiResponse per status with schemas, a shared error model, and a SecurityScheme (bearer/OAuth2) applied globally or per operation.
How do you version an API?
URI (/v1/...), header or media type. Keep changes backward compatible, deprecate with notice, publish a separate OpenAPI doc per version.
★ How do you use AI coding assistants responsibly?
Spec first, small tasks, standing rules in AGENTS.md, task playbooks as skills, review every diff, rely on tests and CI as the gate, and never share secrets or proprietary data with unapproved tools.
AGENTS.md vs a skill: what goes where?
Project-wide facts and rules that always apply go in AGENTS.md. Focused, occasionally needed procedures (how to write tests, how to add an endpoint) go in skills so they load only when relevant.
