1. Why partitions exist, throughput factors, and sizing

Why partitions: (1) parallel writes and reads across brokers and consumers, (2) horizontal storage scaling beyond one machine, (3) a defined scope for ordering. One log on one machine would cap throughput and size.

What limits throughput

LayerLevers
ProducerBatching (linger.ms, batch.size), compression, acks, async vs sync sends, message size, serialization cost, partition count, network
BrokerDisk (sequential write speed), page cache size, network bandwidth, replication factor (each write is copied RF times), number of partitions per broker, num.network.threads / num.io.threads, TLS overhead
ConsumerPartitions ≥ consumers, per-record processing time (usually the real bottleneck: DB or API calls), max.poll.records, fetch sizes, batch writes downstream
Partition sizing rule: partitions ≥ max(T / Tp, T / Tc) where T is target throughput, Tp what one partition sustains on the producer side, Tc what one consumer sustains. Example (illustrative): target 100 MB/s, producer measured at 10 MB/s per partition, consumer at 5 MB/s per partition → at least 20 partitions. Add headroom (1.5–2×) because partitions can be added but never removed, and adding them remaps keys.
  • Consumers vs partitions: throughput scales with consumers only up to the partition count. Beyond that extra consumers are idle. More partitions do not help if the bottleneck is a slow downstream.
  • Too many partitions cost: file handles and memory per partition, slower controller work and leader election after failures, more replication traffic and end-to-end latency, longer recovery. Traditional guidance was a few thousand partitions per broker; KRaft raises the cluster ceiling, but per-broker cost remains.
  • Measure, do not guess: kafka-producer-perf-test.sh and kafka-consumer-perf-test.sh against a production-like cluster, then size from real numbers.

2. Broker internals

  • Request path (produce): network thread reads the request → request queue → I/O thread appends to the partition log (into the OS page cache) → for acks=all the request waits in purgatory until followers catch up → response. Fetches work similarly.
  • Storage: each partition = segments (.log, sparse .index, .timeindex). Lookup: find the segment by base offset, binary-search the sparse index, scan forward. Reads and writes are sequential.
  • Page cache, not fsync: Kafka writes to the OS cache and lets the OS flush. Durability comes from replication, not per-message fsync. Keep the JVM heap modest (around 6 GB) and leave RAM for the page cache; consumers reading recent data are served from memory.
  • Zero-copy: sendfile moves bytes page cache → socket without copying through user space. With TLS the broker must encrypt in user space, so zero-copy is lost and CPU and latency rise.
  • Replication: followers fetch from the leader like consumers. The leader tracks each follower's log end offset (LEO). High watermark (HW) = the smallest LEO across the ISR; consumers only read below it. Followers learn the HW from fetch responses.
  • Leader epoch: a counter incremented at every leader change. After a crash, a follower asks the new leader for the end offset of its last epoch and truncates to that, avoiding the old HW-based truncation bug that could cause divergent or lost data.
  • ISR dynamics: a follower lagging longer than replica.lag.time.max.ms leaves the ISR and rejoins when caught up. Flapping ISR usually means slow disks, network or GC.
  • Controller (KRaft): one active controller from the quorum manages broker registration, leader election and metadata, writing everything to __cluster_metadata. Brokers replicate that log. Clients learn changes via metadata requests, and a NotLeaderOrFollower error triggers a refresh.
  • Rack awareness and follower fetching: broker.rack spreads replicas across racks/AZs; with replica.selector.class consumers can fetch from the closest replica (KIP-392) to cut cross-AZ traffic.
  • Tiered storage (KIP-405, production-ready since 3.9): older segments move to object storage, so local disks hold only hot data.

3. Group protocol, offsets, lag

  • Coordinator: for each group, the leader of partition hash(group.id) % 50 of __consumer_offsets is the group coordinator.
  • Classic protocol: members send JoinGroup; the coordinator picks a group leader (a consumer) which computes assignments and returns them via SyncGroup. Each rebalance bumps the generation id; commits from an old generation fail with CommitFailedException. Eager assignors stop everyone; cooperative ones revoke only moved partitions.
  • New protocol (KIP-848, GA in Kafka 4.0): assignment moves to the broker-side coordinator, members reconcile incrementally, no global stop-the-world barrier.
  • Offset expiry gotcha: committed offsets of a group with no active members are deleted after offsets.retention.minutes (default 7 days). A service that was down for longer restarts and falls back to auto.offset.reset: earliest reprocesses everything, latest silently skips backlog.
  • Lag = log-end offset − committed offset, per partition. Track offset lag and, for SLAs, time lag (age of the oldest unprocessed record).

5. Log compaction and retention details

  • Compaction (cleanup.policy=compact): a cleaner thread keeps the latest value per key in the closed segments. The active segment is never compacted. Offsets are preserved (gaps appear). A tombstone (key with null value) deletes the key and is itself removed after delete.retention.ms (24 h). Trigger tuned by min.cleanable.dirty.ratio (0.5). Consumers near the head still see every update.
  • Use for: latest-state topics (inventory per SKU, customer profile), changelogs, __consumer_offsets. Not for event history you must keep whole.
  • Retention gotcha: deletion works on closed segments only. A low-traffic topic with a 1 GB segment may keep data far longer than retention.ms because the segment never rolls. Set segment.ms (and check log.retention.check.interval.ms).
  • Retention by time or bytes applies per partition. Slow consumers whose lag exceeds retention lose data permanently (offset out of range → reset policy applies).

  • Pulsar: separates serving (brokers) from storage (BookKeeper), native multi-tenancy and geo-replication, both queue and stream semantics; smaller ecosystem.
  • Do not use Kafka when: you need per-message TTL, priority queues, complex routing, request/response, or tiny volume where operating a cluster outweighs the benefit. Kafka is also not a general database; it is a log.

7. Security (essential for fintech interviews)

  • In transit: TLS on client and inter-broker listeners. Authentication: mTLS, SASL/SCRAM-SHA-512, SASL/OAUTHBEARER, SASL/GSSAPI (Kerberos), SASL/PLAIN (only over TLS). Authorization: ACLs per principal on topics, groups and cluster.
  • At rest: Kafka does not encrypt log files; use disk or volume encryption. For sensitive fields (PII, card data) encrypt or tokenize before publishing, and treat topics as long-lived copies of data (retention, right-to-erasure, compaction with tombstones).
  • Multi-tenancy: topic naming conventions, ACLs, and quotas (producer_byte_rate, consumer_byte_rate, request_percentage) so one noisy client cannot starve others.

8. Schemas, Avro and Schema Registry

  • JSON is easy but untyped and verbose. Avro/Protobuf give compact binary, explicit schemas and enforced evolution.
  • Schema Registry stores versioned schemas per subject (default <topic>-value). Each message carries a magic byte plus a 4-byte schema id; the deserializer fetches and caches the schema.
  • Compatibility modes: BACKWARD (default; new schema can read old data: add fields with defaults, remove fields; upgrade consumers first), FORWARD (old readers can read new data; upgrade producers first), FULL (both), NONE; the _TRANSITIVE variants check against all versions, not just the last.
  • Safe changes: add optional field with default. Breaking: rename or retype a field, add required field with no default. For a truly breaking change, publish a new topic/version and migrate consumers.
  • Spring config: value-serializer: io.confluent.kafka.serializers.KafkaAvroSerializer, properties: schema.registry.url, and specific.avro.reader=true on the consumer.

9. Large messages

  • Preferred: claim check: store the payload in object storage or a DB, send the reference plus metadata. Also compress; avoid chunking unless unavoidable.
  • If you must raise limits, change the whole chain or it fails somewhere: producer max.request.size, broker message.max.bytes (or topic max.message.bytes), replica.fetch.max.bytes, consumer max.partition.fetch.bytes and fetch.max.bytes. Large records also hurt batching, memory and rebalances.

Interview Q&A

Tap a question to expand.

★ Why do partitions exist? What happens if you use one big partition?
Partitions give parallelism, scale-out storage and an ordering scope. One partition caps throughput at one broker's disk and one consumer, and you lose the ability to scale consumers.
★ What factors affect Kafka throughput? How do consumers and partitions play in?
Producer batching/compression/acks, broker disk, network, replication factor and partition count, and consumer processing speed. Consumer parallelism is capped by the partition count; adding consumers past that does nothing, and adding partitions does not help if the downstream call is the bottleneck.
★ How would you decide the number of partitions for a new topic?
Measure per-partition producer and consumer throughput, compute max(T/Tp, T/Tc), add headroom, consider key cardinality, ordering needs and per-broker partition limits, then load test.
★ How does Kafka provide durability without fsyncing every message?
Replication. A write is acknowledged after the ISR has it in memory/page cache; with RF ≥ 3 and min.insync.replicas=2 a single node crash cannot lose it. Simultaneous loss of all replicas before flush is the residual risk.
★ Why is Kafka fast, and why does TLS slow it down?
Sequential I/O, page cache, batching, compression, zero-copy. TLS forces user-space encryption, so sendfile zero-copy no longer applies and CPU cost increases.
★ High watermark vs log end offset vs last stable offset?
LEO: next offset to be written on a replica. HW: highest offset replicated to all ISR; consumers read below it. LSO: with transactions, the offset before the first open transaction; read_committed consumers read up to it.
What problem do leader epochs solve?
Safe truncation after leader changes. Followers truncate to the end offset of the last epoch they share with the new leader, preventing log divergence and data loss seen with HW-only truncation.
★ Our service was down for 10 days, restarted, and reprocessed the entire topic. Why?
Committed offsets of an empty group expire after 7 days (offsets.retention.minutes), so auto.offset.reset=earliest kicked in. Fix: raise offset retention for critical groups, keep consumers running or use static membership, choose the reset policy deliberately, and make consumers idempotent.
How does the group coordinator get chosen and what does it do?
Leader of the __consumer_offsets partition for the hashed group id. It manages membership, heartbeats, rebalances and offset commits for that group.
★ Kafka vs RabbitMQ: which and why?
Kafka for high-throughput event streaming, replay, multiple independent consumers and audit. RabbitMQ for task queues, flexible routing, priorities, TTL and request/response. Kafka consumers pull and messages persist; RabbitMQ pushes and removes on ack.
★ When is compaction appropriate, and what are its traps?
For latest-state per key. Traps: it is not immediate, the active segment is not compacted, consumers can still see older values near the head, tombstones linger for delete.retention.ms, and keys must be non-null.
Data is older than retention.ms but still on disk. Why?
Only closed segments are deleted. On a quiet topic the active segment may not have rolled; set segment.ms.
★ How do you evolve an event schema without breaking consumers?
Schema Registry with BACKWARD (or FULL) compatibility; add optional fields with defaults; never rename or retype; for breaking changes create a new versioned topic and migrate.
★ How do you secure a Kafka platform for a bank?
TLS everywhere, SASL/mTLS authentication, least-privilege ACLs, quotas, disk encryption, field-level encryption or tokenization for PII, secrets from a vault, audit logging, network isolation, and retention/erasure policy for regulated data.
How do you send a 20 MB payload through Kafka?
Do not; use claim check (object store reference). If unavoidable, raise limits end to end (producer, broker/topic, replica fetch, consumer) and accept the batching and memory cost.
Can consumers read from a follower? Why?
Yes, with rack-aware follower fetching (KIP-392). It cuts cross-AZ network cost and latency at the price of slightly higher end-to-end lag.
