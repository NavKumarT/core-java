1. Topics and partitions

Video 9

  • Topic: a named, logical stream of records. Partition: an ordered, immutable, append-only log that makes up a topic.
  • Offset: a record's sequence number within one partition. Offsets are unique per partition, not per topic.
  • Ordering is guaranteed only inside a partition, never across partitions.
  • Partitions are the unit of parallelism (max active consumers in a group = partition count) and of storage distribution.
  • You can increase partitions but never decrease them. Increasing changes hash(key) % N, so the same key may land on a different partition afterwards.
  • Records are not deleted on consumption; they are removed by the retention policy.

2. Local broker with KRaft

Video 10

  • KRaft replaces ZooKeeper (removed entirely in Kafka 4.0). Cluster metadata lives in an internal Raft-replicated log, __cluster_metadata.
  • A node can be a broker, a controller, or both (process.roles=broker,controller, fine for local use).
  • Controllers form a quorum and elect one active controller via the Raft consensus protocol. It handles leader election, topic creation and metadata changes.
  • Benefits: no second system to run, faster controller failover, and metadata scales to more partitions.
KAFKA_CLUSTER_ID=$(bin/kafka-storage.sh random-uuid)
bin/kafka-storage.sh format -t $KAFKA_CLUSTER_ID -c config/server.properties   # config path varies by version

  • Same key → same partition (murmur2 hash of key bytes mod partition count), so per-key ordering holds.
  • Null key: the default partitioner is sticky. It fills a batch for one partition, then switches, for better batching than pure round robin.
  • Pick keys with high cardinality and even distribution (orderId, userId). A skewed key (e.g. country) creates a hot partition.

5. Consumer offsets

Video 14

  • A committed offset is the next offset to read, stored per (group, topic, partition) in the internal topic __consumer_offsets.
  • auto.offset.reset applies only when the group has no committed offset (or it is out of range): earliest, latest (default), none (throws).
  • enable.auto.commit=true commits every auto.commit.interval.ms (5s) inside poll(). It can lose or duplicate work on a crash.
Commit strategyResult
Commit before processingAt-most-once (a crash loses messages)
Commit after processingAt-least-once (a crash causes duplicates; make consumers idempotent)
Transactions / read_committed, or offsets stored with the result in one DB transactionExactly-once effect

6. Consumer groups and consumer internals

Videos 15–16

  • Within a group, each partition goes to exactly one consumer. Different groups each get every message independently (pub-sub across groups, queue inside a group).
  • More consumers than partitions means the extras sit idle.
  • A broker acts as group coordinator; one consumer is the group leader and computes the assignment.
  • Rebalance triggers: consumer joins or leaves, missed heartbeats (session.timeout.ms), slow processing (max.poll.interval.ms exceeded), or partition count change.
  • Assignors: Range, RoundRobin, Sticky, CooperativeSticky (incremental, avoids stop-the-world). Static membership (group.instance.id) avoids rebalances on quick restarts. Kafka 4.0 adds the new server-side protocol (KIP-848).

Poll loop: poll() fetches batches (tuned by fetch.min.bytes, fetch.max.wait.ms, max.poll.records), deserializes, and returns. A separate heartbeat thread keeps the session alive. The consumer must call poll() again within max.poll.interval.ms or it is kicked out of the group.

7. Commit log and retention

Video 17

  • Each partition is a directory of segments (.log, .index, .timeindex). Writes go to the active segment only. Segment rolls at segment.bytes (1 GB) or segment.ms.
  • Retention deletes whole old segments: retention.ms (default 7 days) and/or retention.bytes. Deletion is per segment, not per record.
  • cleanup.policy=compact keeps the latest value per key (changelog and state use cases; a null value is a tombstone).
  • Why it is fast: sequential disk writes, OS page cache, batching, and zero-copy (sendfile) from disk to network.

8. Distributed cluster, replication, leader election, ISR

Videos 18–23

  • Distributed system: independent nodes that cooperate and appear as one. Kafka scales by partitioning and survives failures by replicating.
  • Replication factor (RF): copies per partition, spread across brokers. One replica is the leader (handles all produce and, by default, fetch); the rest are followers that pull from the leader.
  • ISR (in-sync replicas): the leader plus followers that are caught up (within replica.lag.time.max.ms, 30s). Slow followers are dropped from the ISR and re-added when caught up.
  • High watermark: the offset replicated to all ISR members. Consumers only see records below it.
  • Leader election: when a leader dies, the controller picks a new leader from the ISR. unclean.leader.election.enable=false (default) prefers unavailability over data loss. Leader epochs prevent stale leaders from truncating wrongly.
  • Preferred leader: the first replica in the assignment; auto leader rebalance moves leadership back after recovery.
  • Partition distribution: replicas are spread across brokers round-robin (rack-aware if broker.rack is set), so leaders and load are balanced.
Zero-loss recipe: replication.factor=3, min.insync.replicas=2, producer acks=all + idempotence, unclean election off, and commit consumer offsets after processing. Tolerates one broker down while still accepting writes. If ISR < 2, producers get NotEnoughReplicasException instead of silently losing data.
bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic pay --partitions 3 --replication-factor 3 \
  --config min.insync.replicas=2
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic pay
# Topic: pay  Partition: 0  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
# Stop broker 2 -> new leader elected from Isr; Isr shrinks to 3,1

Demo scenarios from the videos: kill the leader broker and watch a follower become leader; stop two of three brokers with acks=all and min.insync.replicas=2 and watch produce fail while consume still works.

Interview Q&A

Tap a question to expand.

Fundamentals

★ What is Kafka and why is it fast?
A distributed, durable, partitioned commit-log platform for streaming and messaging. Speed comes from sequential I/O, page cache, batching and compression, zero-copy transfer, and parallelism through partitions.
★ Topic vs partition vs offset?
Topic is the logical stream; partitions are its ordered logs (parallelism and distribution); offset is a record's position within one partition.
★ How is ordering guaranteed?
Only per partition. Give related events the same key so they hit the same partition; keep idempotence on and max.in.flight ≤ 5 so retries do not reorder. Global ordering needs a single partition, which limits throughput.
Kafka vs RabbitMQ?
Kafka: retained log, consumers pull and can replay, very high throughput, partition-ordered. RabbitMQ: smart broker with push routing, messages removed after ack, richer routing (exchanges), lower throughput. Use Kafka for event streaming and replay, RabbitMQ for task queues and complex routing.
Why did Kafka drop ZooKeeper (KRaft)?
Two systems to operate, slow controller failover (metadata reloaded from ZK), and a scaling ceiling on partitions. KRaft stores metadata in a Raft log inside Kafka, so failover is fast and the operational surface is smaller.

Producer

★ Explain acks 0 / 1 / all.
0: no wait, can lose data. 1: leader ack; data can be lost if the leader dies before replication. all: waits for all ISR, and with min.insync.replicas gives the strongest durability.
★ How does the idempotent producer prevent duplicates?
The broker assigns a producer id; each batch carries a per-partition sequence number. The broker rejects sequence numbers it has already written, so retries do not duplicate. Scope: one producer session and one partition.
What do linger.ms and batch.size do? How would you tune for throughput?
Raise linger.ms (e.g. 10–20 ms), raise batch.size (e.g. 64–128 KB), and enable compression (lz4/zstd). Trade-off: added latency.
How does the partitioner choose a partition?
Explicit partition if given; else murmur2(key) mod partitions; else sticky batching for null keys. A custom Partitioner can be plugged in.

Consumer and groups

★ What triggers a rebalance and how do you minimise it?
Members joining or leaving, heartbeat or poll timeouts, and partition changes. Minimise with CooperativeSticky, static membership, sensible session.timeout.ms, smaller max.poll.records or a larger max.poll.interval.ms so processing fits in the poll window, and graceful shutdown.
★ Difference between session.timeout.ms and max.poll.interval.ms?
Session timeout: heartbeat liveness (background thread). Max poll interval: the maximum gap between poll() calls, detecting a stuck processing loop. Either breach removes the consumer and triggers a rebalance.
What happens if consumers outnumber partitions?
The extra consumers are idle (standbys). Parallelism is capped by partition count.
★ At-most-once, at-least-once, exactly-once: how do you achieve each?
See the commit table: commit before processing, commit after processing, and for exactly-once use idempotent producer + transactions with isolation.level=read_committed (Kafka to Kafka), or an idempotent sink / offsets committed in the same DB transaction.
What is auto.offset.reset?
Where a group starts when it has no valid committed offset: earliest from the beginning, latest only new records, none throws an exception.

Storage and cluster

★ What is ISR and what is min.insync.replicas?
ISR is the set of replicas caught up with the leader. min.insync.replicas is the minimum ISR size required for an acks=all write to succeed; below it, the producer gets an exception. RF=3, min ISR=2 tolerates one failure.
★ How does leader election work when a broker dies?
The active controller detects the failure, chooses a new leader from the partition's ISR, and publishes the metadata change. Clients refresh metadata and reconnect. Unclean election (out-of-sync replica) is off by default to avoid data loss.
What is the high watermark?
The highest offset replicated to all ISR members; consumers can read only up to it, so they never see data that could be lost on a leader failover.
How does retention work? Delete vs compact?
Delete removes whole segments older than retention.ms or beyond retention.bytes. Compact keeps the latest record per key (tombstones delete keys). Both can be combined.
How are partitions and replicas distributed across brokers?
Round-robin from a random start broker, followers offset from the leader, and rack-aware when broker.rack is set so replicas land in different racks or AZs.
How many partitions should a topic have?
Target throughput / per-partition throughput, at least the peak consumer count you want, with headroom (cannot shrink; increasing breaks key mapping). Too many partitions cost memory, file handles and longer failovers.

Situational and performance

★ Consumer lag keeps growing. How do you diagnose and fix it?
Check lag per partition (kafka-consumer-groups.sh --describe). If all partitions lag: consumers are too slow. Profile processing (DB or API calls), batch or parallelise inside the consumer, tune max.poll.records and fetch sizes, and add consumers up to the partition count; add partitions if you are at the cap. If one partition lags: hot key or stuck message; fix key distribution or skip a poison message via DLT.
★ Downstream is receiving duplicate messages. Why, and how do you fix it?
Causes: producer retries without idempotence, consumer crash after processing but before commit, rebalances mid-batch. Fixes: idempotent producer, idempotent consumers (dedupe by unique event id or upsert), commit after processing, transactions where applicable.
★ How do you guarantee no message loss end to end?
Producer: acks=all, idempotence, handle send failures. Broker: RF ≥ 3, min.insync.replicas=2, unclean election off. Consumer: manual commit after successful processing, plus a DLT for failures.
One partition is getting most of the traffic. What do you do?
Hot key. Choose a better key, add a salt or suffix to spread heavy keys (accepting weaker per-key ordering), or use a custom partitioner.
Frequent rebalance storms in production. Steps?
Check logs for poll-interval or session timeout breaches, reduce per-poll work, raise max.poll.interval.ms, switch to CooperativeSticky, enable static membership for rolling deploys, and avoid long GC pauses.
A broker went down in a 3-broker cluster (RF=3, min ISR=2). What happens to producers and consumers?
Leaders on that broker fail over to followers in the ISR; producers with acks=all keep working because ISR is still 2. If a second broker goes down, produces fail with NotEnoughReplicas while consumers can keep reading committed data.
