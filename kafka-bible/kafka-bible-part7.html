1. Containers: why and what

Video 120

  • Problem: "works on my machine". Apps depend on OS libraries, runtime versions and config. A container packages the app with everything it needs and runs the same everywhere.
  • A container is an isolated process on the host kernel: namespaces isolate what it sees (processes, network, mounts) and cgroups limit what it can use (CPU, memory).

2. Docker basics

Video 121

  • Image: immutable, layered, read-only template. Container: a running instance of an image. Registry: stores images (Docker Hub, ECR, private Artifactory).
  • Architecture: docker CLI → Docker daemon → containerd → runc. Layers are cached; unchanged layers are reused on rebuild, so order Dockerfile steps from least to most frequently changing.
docker build -t dilip/library-events-producer:1.0 .
docker run -d --name producer -p 8080:8080 -e SPRING_PROFILES_ACTIVE=local dilip/library-events-producer:1.0
docker ps            # running containers        docker ps -a   # all
docker logs -f producer
docker exec -it producer sh
docker stop producer && docker rm producer
docker images        docker rmi IMAGE
docker volume ls     docker network ls
  • -p host:container publishes a port. Data inside a container is lost on removal; use volumes for persistence. Containers on the same user-defined network reach each other by container name.

3. Dockerfile for the producer, and running per environment

Videos 122–124, 126

# Dockerfile (multi-stage)
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -q dependency:go-offline            # cached until pom.xml changes
COPY src ./src
RUN mvn -q clean package -DskipTests

FROM eclipse-temurin:21-jre
RUN useradd -r -u 1001 app
WORKDIR /app
COPY --from=build /src/target/*.jar app.jar
USER app
EXPOSE 8080
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75"
ENTRYPOINT ["sh","-c","java $JAVA_OPTS -jar app.jar"]
  • Best practices: multi-stage (small runtime image, no build tools), JRE base, non-root user, .dockerignore, pinned base tags, one process per container, container-aware JVM flags (MaxRAMPercentage).
  • Same image, different environments (video 124): build once; vary behavior by env vars or profiles only.
docker run -p 8080:8080 -e SPRING_PROFILES_ACTIVE=dev  -e SPRING_KAFKA_BOOTSTRAP_SERVERS=kafka-dev:9092  IMAGE
docker run -p 8080:8080 -e SPRING_PROFILES_ACTIVE=prod -e SPRING_KAFKA_BOOTSTRAP_SERVERS=kafka-prod:9092 IMAGE
Networking gotcha: inside a container, localhost is the container itself, not your laptop or the Kafka container. Use a shared Docker network and the service name (kafka:9092) or host.docker.internal. Kafka's advertised.listeners must return an address the client can actually reach, otherwise the client connects to the bootstrap address and then fails on the advertised one. Use separate internal and external listeners.
  • Consumer (video 126): same build. It also needs Postgres and Kafka: run them on one Docker network (or Docker Compose) and pass SPRING_DATASOURCE_URL, SPRING_KAFKA_BOOTSTRAP_SERVERS and the DB credentials as env vars.

  • Tag with immutable versions (semver or git SHA). Avoid latest in deployments: it is mutable and makes rollbacks and audits unreliable.

5. Why Kubernetes, and its architecture

Videos 127–131

  • Docker alone cannot: spread containers across many machines, restart failed ones automatically, scale on demand, do rolling updates with zero downtime, load balance and discover services, or manage config and secrets centrally.
  • Kubernetes is a declarative orchestrator: you describe the desired state (3 replicas of this image) and controllers continuously reconcile actual state toward it.
ComponentRole
kube-apiserverFront door; every request and component talks through it
etcdConsistent key-value store holding all cluster state
schedulerChooses a node for each new Pod (resources, affinity, taints)
controller-managerRuns reconcile loops (Deployment, ReplicaSet, Node controllers)
kubelet (each node)Runs and monitors the Pods assigned to its node
kube-proxy (each node)Implements Service networking rules
Container runtimecontainerd / CRI-O actually runs containers

Flow of kubectl apply: API server validates and stores in etcd → Deployment controller creates a ReplicaSet → it creates Pods → scheduler assigns nodes → kubelets pull the image and start containers → status flows back to the API server.

minikube start --driver=docker         # local single-node cluster
kubectl get nodes                      kubectl config get-contexts
kubectl apply -f deployment.yaml       kubectl get pods -o wide
kubectl describe pod POD               kubectl logs -f POD [--previous]
kubectl exec -it POD -- sh             kubectl delete -f deployment.yaml
kubectl rollout status|history|undo deployment/NAME
kubectl scale deployment NAME --replicas=3

6. Deployment and Pods

Video 132

  • Pod: smallest deployable unit; one or more containers sharing network (one IP) and volumes. Pods are ephemeral; never rely on a Pod's IP.
  • Deployment → manages a ReplicaSet → keeps N Pods running; provides self-healing, rolling updates, and rollback.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: library-events-producer
spec:
  replicas: 2
  strategy: { type: RollingUpdate, rollingUpdate: { maxSurge: 1, maxUnavailable: 0 } }
  selector:
    matchLabels: { app: library-events-producer }
  template:
    metadata:
      labels: { app: library-events-producer }
    spec:
      containers:
        - name: producer
          image: dilip/library-events-producer:1.0
          ports: [ { containerPort: 8080 } ]
          resources:
            requests: { cpu: 250m, memory: 512Mi }
            limits:   { memory: 768Mi }
  • requests = what the scheduler reserves; limits = hard cap. Exceeding the memory limit gets the container OOMKilled; CPU over the limit is throttled. Size the JVM heap below the memory limit.
  • Rolling update replaces Pods gradually; maxUnavailable: 0 keeps full capacity during a deploy.

8. Scaling to multiple replicas

Video 136

kubectl scale deployment library-events-producer --replicas=3
kubectl autoscale deployment library-events-producer --min=2 --max=10 --cpu-percent=70    # HPA
  • Replicas give throughput and availability; the Service spreads traffic across ready Pods. The producer is stateless, so it scales freely.
  • Consumer + Kafka rule: total consumer threads = replicas × listener concurrency must be ≤ topic partitions, or extra Pods sit idle. Scaling or restarting Pods triggers rebalances.
  • CPU-based HPA is a poor fit for consumers; scale on consumer lag (e.g. KEDA Kafka scaler), capped at the partition count.

9. Externalizing config with ConfigMap

Video 137

apiVersion: v1
kind: ConfigMap
metadata: { name: producer-config }
data:
  SPRING_PROFILES_ACTIVE: "prod"
  SPRING_KAFKA_BOOTSTRAP_SERVERS: "kafka:9092"
---
# in the container spec
          envFrom:
            - configMapRef: { name: producer-config }
  • Config lives outside the image: same image in dev/QA/prod, different ConfigMaps. Use it for non-sensitive settings only.
  • Env vars are read at container start, so changing a ConfigMap needs a Pod restart (kubectl rollout restart deployment/NAME). ConfigMaps mounted as files update eventually, but Spring will not reload them unless you build for it.

10. Liveness and readiness in Kubernetes

Video 138

          startupProbe:                     # protects slow JVM starts
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            failureThreshold: 30
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            periodSeconds: 10
            failureThreshold: 3
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            periodSeconds: 5
  • Liveness failure → kubelet restarts the container. Readiness failure → Pod is removed from Service endpoints (no traffic, no restart). Startup probe delays the other two until the app has booted.
  • Actuator probe endpoints come from Part 6. Keep Kafka and DB in readiness only, not liveness.
  • Graceful shutdown: Kubernetes sends SIGTERM, then SIGKILL after terminationGracePeriodSeconds (30 s). Set server.shutdown=graceful so in-flight requests finish and consumers stop polling and commit cleanly.

11. Consumer on Kubernetes

Video 139

  • Same pattern as the producer: Deployment + ConfigMap + probes, plus a Service if it exposes REST (Book CRUD, GET events).
  • Kafka and Postgres addresses come from config (SPRING_KAFKA_BOOTSTRAP_SERVERS, SPRING_DATASOURCE_URL). Inside the cluster use Service DNS names (e.g. postgres:5432), never localhost.
  • Stateful systems (Postgres, Kafka brokers) need StatefulSets with persistent volumes; in production use managed services or operators (e.g. Strimzi for Kafka). Flyway runs at app start, so several replicas must tolerate a concurrent migration (Flyway locks the schema history table).

12. Secrets: env vars and volume mounts

Videos 140–141

apiVersion: v1
kind: Secret
metadata: { name: db-secret }
type: Opaque
stringData:
  DB_USER: library
  DB_PASSWORD: change-me
---
# option 1: environment variable
          env:
            - name: SPRING_DATASOURCE_PASSWORD
              valueFrom: { secretKeyRef: { name: db-secret, key: DB_PASSWORD } }
# option 2: volume mount (each key becomes a file)
          volumeMounts:
            - { name: db-secret, mountPath: /etc/secrets, readOnly: true }
      volumes:
        - name: db-secret
          secret: { secretName: db-secret }
# Spring Boot reads mounted files as properties
spring:
  config:
    import: "optional:configtree:/etc/secrets/"
  • Secrets are base64-encoded, not encrypted. Protect them with RBAC, enable etcd encryption at rest, and keep them out of Git.
  • Volume mount vs env var: files can be updated in a running Pod, are not visible in kubectl describe, and are less likely to leak through logs, crash dumps or child processes. Env vars are simpler but static until restart.
  • For stronger control use an external manager (Vault, AWS Secrets Manager, Azure Key Vault) synced by External Secrets Operator or the CSI Secrets Store driver.

Interview Q&A

Tap a question to expand.

Docker

★ Container vs VM? Image vs container?
Containers share the host kernel and isolate with namespaces and cgroups, so they are light and fast; VMs bring a full guest OS. An image is the immutable layered template, a container is a running instance with a writable layer on top.
★ How does Docker layer caching work, and how do you use it?
Each instruction creates a layer; unchanged layers up to the first change are reused. Copy pom.xml and resolve dependencies before copying source so dependency layers stay cached.
CMD vs ENTRYPOINT? COPY vs ADD?
ENTRYPOINT is the fixed executable; CMD supplies default arguments that docker run can override. COPY just copies files; ADD also extracts archives and fetches URLs, so prefer COPY.
★ Why multi-stage builds and non-root users?
Multi-stage keeps compilers and source out of the runtime image (smaller, fewer vulnerabilities). Non-root limits damage if the process is compromised.
★ My containerized app cannot connect to Kafka on localhost:9092. Why?
localhost is the container itself. Put both on one Docker network and use the broker's service name; configure Kafka's advertised.listeners with separate internal (container-to-container) and external (host) listeners.
How do you run the same image in dev and prod?
Build once, inject environment-specific config at runtime (env vars, profiles, ConfigMaps, secrets). No rebuild per environment.
How do you reduce image size and build time?
Slim/JRE base, multi-stage, .dockerignore, ordered layers, layered Spring Boot jars, and build cache reuse in CI.

Kubernetes core

★ Explain Kubernetes architecture and what happens on kubectl apply.
API server stores desired state in etcd; controllers create ReplicaSet and Pods; the scheduler assigns nodes; each node's kubelet pulls images and starts containers via the runtime; kube-proxy wires Service networking. Everything talks through the API server.
★ Pod vs Deployment vs ReplicaSet?
Pod runs containers. ReplicaSet keeps N identical Pods. Deployment manages ReplicaSets to give rolling updates and rollbacks. You almost always create Deployments.
★ Service types and Service vs Ingress?
ClusterIP (internal), NodePort, LoadBalancer (cloud LB), plus headless for direct Pod DNS (StatefulSets). A Service is L4 load balancing to Pods; Ingress is L7 host/path routing and TLS for many Services via an Ingress controller.
How does a Service know which Pods to route to?
Label selector → matching Pods that are Ready become its endpoints. Failing readiness removes a Pod from the endpoints.
★ How does a rolling update work? How do you roll back?
New ReplicaSet scales up while the old scales down, controlled by maxSurge/maxUnavailable, gated by readiness. Roll back with kubectl rollout undo.
★ Liveness vs readiness vs startup probes?
Liveness restarts a stuck container; readiness controls whether it receives traffic; startup gives slow apps time to boot before liveness starts. Do not put external dependencies in liveness.
★ Resource requests vs limits? Why was my Java pod OOMKilled?
Requests drive scheduling; limits are caps. The container exceeded the memory limit (heap plus metaspace, threads, direct buffers). Set heap via MaxRAMPercentage well below the limit and check with kubectl describe pod (reason OOMKilled).
★ ConfigMap vs Secret? Are Secrets secure?
ConfigMap for plain config, Secret for sensitive values. Secrets are only base64-encoded by default; secure them with RBAC, etcd encryption, and optionally an external secret manager.
Env var vs volume-mounted secret?
Env vars are simple but static and easier to leak; mounted files are refreshable, hidden from describe, and can be read via Spring's configtree.

Kafka on Kubernetes and operations

★ How do you scale a Kafka consumer deployment?
Replicas × concurrency ≤ partitions. Scale on consumer lag (KEDA) rather than CPU, expect rebalances, and use cooperative rebalancing and static membership to soften them during rollouts.
★ Pods keep restarting during a Kafka outage. Why, and how do you fix it?
Kafka health is in the liveness probe, so failures cause restarts. Move dependency checks to readiness and keep liveness about the process only.
★ How do you gracefully shut down a consumer during a deployment?
Handle SIGTERM: stop polling, finish or abandon the current batch, commit offsets, leave the group (server.shutdown=graceful, adequate terminationGracePeriodSeconds). Otherwise the group waits for the session timeout before rebalancing.
How do you debug CrashLoopBackOff and ImagePullBackOff?
CrashLoopBackOff: kubectl logs --previous, describe pod (exit code, OOM, bad config, failing probe). ImagePullBackOff: wrong image/tag, missing registry credentials (imagePullSecrets), or network to the registry.
Should you run Kafka itself on Kubernetes?
Possible with StatefulSets, persistent volumes and an operator (Strimzi), but operationally demanding. Many teams use managed Kafka (MSK, Confluent Cloud) and run only apps on Kubernetes.
Where does the Library Events consumer reach Postgres from inside the cluster?
Through a Service DNS name (e.g. postgres.default.svc.cluster.local) provided via config, never localhost, with credentials from a Secret.
