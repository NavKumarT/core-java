1. Producer reliability: acks, retries, idempotence, in-flight

Videos 85–88

acks and min.insync.replicas

SettingMeaningRisk
acks=0No ackSilent loss
acks=1Leader wrote itLost if leader dies before followers copy
acks=allAll in-sync replicas wrote itSafe, if ISR is large enough
  • acks=all alone is not enough: if the ISR shrinks to just the leader, "all" means one. min.insync.replicas (topic or broker) sets the minimum ISR for a write to succeed; otherwise the producer gets NotEnoughReplicasException (retriable).
  • Rule: RF=3, min.insync.replicas=2, acks=all survives 1 broker failure with no loss and keeps accepting writes. Writes tolerate RF − minISR failures; data survives minISR − 1.
  • Higher durability costs latency, and a smaller ISR costs availability (CAP-style trade-off).

Retries and backoff

  • retries defaults to a huge number; the real bound is delivery.timeout.ms (120 s). Tune the deadline, not the count. retry.backoff.ms (100 ms) with exponential growth up to retry.backoff.max.ms (1 s).
  • Retriable: NotEnoughReplicas, NotLeaderOrFollower, network/timeouts. Non-retriable: RecordTooLarge, SerializationException, auth errors.
  • Danger: retries without idempotence can duplicate (ack lost, resend) and reorder (batch 2 succeeds while batch 1 retries).

Idempotent producer and max.in.flight

  • enable.idempotence=true (default since Kafka 3.0): broker assigns a producer id (PID) + epoch; each batch carries a per-partition sequence number; the broker drops duplicates and rejects gaps. Requires acks=all, retries > 0, max.in.flight ≤ 5.
  • Limits: dedup holds within one producer session and partition. A restarted app gets a new PID, and app-level resends are not detected. For atomic multi-partition or read-process-write use transactions (transactional.id).
  • max.in.flight.requests.per.connection: unacked requests per broker connection. Without idempotence, >1 risks reordering on retry (use 1 for strict order). With idempotence, up to 5 keeps order because the broker uses sequence numbers, and gives better throughput.

3. Consumer error handling: behavior and internals

Videos 92–97

  • Current default (video 93): when the listener throws, DefaultErrorHandler retries the same record up to 9 more times with no delay (FixedBackOff(0, 9)), then logs and skips it, and the offset is committed. That is silent data loss for a business-critical event, so you must configure recovery.
  • Under the hood (video 94): on exception the container does not poll past the failed record: DefaultErrorHandler seeks the partition back to the failed offset, sleeps for the back-off in the consumer thread, and redelivers. When the back-off is exhausted it calls the ConsumerRecordRecoverer, then commits and continues. This is a blocking retry: the partition is stalled during retries.
  • The total back-off time must stay well below max.poll.interval.ms, or the consumer is evicted mid-retry and a rebalance follows.
  • Spring Boot auto-registers a CommonErrorHandler bean on the listener container factory.
@Bean
DefaultErrorHandler errorHandler(ConsumerRecordRecoverer recoverer) {
  var backOff = new ExponentialBackOffWithMaxRetries(3);        // 3 retries after the first attempt
  backOff.setInitialInterval(1_000L);
  backOff.setMultiplier(2.0);                                   // 1s, 2s, 4s
  backOff.setMaxInterval(10_000L);

  var handler = new DefaultErrorHandler(recoverer, backOff);
  handler.addNotRetryableExceptions(IllegalArgumentException.class, JsonProcessingException.class);
  handler.addRetryableExceptions(RecoverableDataAccessException.class);
  handler.setRetryListeners(new RetryListener() {               // video 96
    public void failedDelivery(ConsumerRecord<?,?> r, Exception ex, int attempt) {
      log.warn("attempt {} failed for key={} offset={}: {}", attempt, r.key(), r.offset(), ex.getMessage());
    }
    public void recovered(ConsumerRecord<?,?> r, Exception ex) { log.error("recovered (gave up) key={}", r.key()); }
  });
  return handler;
}
  • Retryable vs non-retryable (video 97): by default these skip retries and go straight to the recoverer: DeserializationException, MessageConversionException, ConversionException, MethodArgumentResolutionException, NoSuchMethodException, ClassCastException. Retry only transient failures (DB down, timeout, downstream 503). Do not retry validation or business-rule violations: they will fail every time.

4. Recovery strategies

Videos 98–102

StrategyHowTrade-off
Log and skipDefault recovererSimplest; data is lost, only a log line remains
Dead-letter topicDeadLetterPublishingRecovererPreserves the record and exception headers; needs a DLT consumer or replay process
Save to DBCustom recoverer writes a failure recordQueryable, easy to build retry jobs and dashboards; DB becomes a dependency
HybridRetryable failures → DB (status RETRY) for a scheduler; non-retryable → DLT (status DEAD)Most flexible; most moving parts
@Bean
DeadLetterPublishingRecoverer dltRecoverer(KafkaTemplate<Object,Object> template) {
  return new DeadLetterPublishingRecoverer(template,
      (record, ex) -> new TopicPartition(record.topic() + ".DLT", record.partition()));
}

// DB variant
@Bean
ConsumerRecordRecoverer dbRecoverer(FailureRecordService svc) {
  return (rec, ex) -> svc.save(new FailureRecord(rec.topic(), rec.partition(), rec.offset(),
                                                   (Integer) rec.key(), (String) rec.value(),
                                                   ex.getMessage(), "RETRY"));
}

// Hybrid
@Bean
ConsumerRecordRecoverer hybrid(DeadLetterPublishingRecoverer dlt, FailureRecordService svc) {
  return (rec, ex) -> {
    Throwable cause = ex.getCause() != null ? ex.getCause() : ex;
    if (cause instanceof RecoverableDataAccessException) svc.save(rec, ex, "RETRY");   // scheduler retries later
    else { dlt.accept(rec, ex); svc.save(rec, ex, "DEAD"); }
  };
}
  • The DLT default destination is <topic>.DLT on the same partition number, so the DLT needs at least as many partitions (or return -1 to let Kafka choose). Headers carry original topic, partition, offset, exception class, message and stack trace.
  • Undeserializable payloads arrive as byte[]: the DLT template needs a byte-array serializer (use the recoverer's map-of-templates constructor).
  • Unwrap the exception (ex.getCause()): listener exceptions are wrapped in ListenerExecutionFailedException.
  • A DB recoverer that itself fails causes the record to be retried again, so keep it simple and monitor it.
  • DLT is not the end: monitor and alert on DLT depth, and build a replay path (a job or admin endpoint that republishes to the main topic once fixed).
Non-blocking alternative: @RetryableTopic retries via separate retry topics (-retry-0, -retry-1, -dlt) so the main partition keeps moving. Trade-off: ordering for that key is no longer guaranteed. Use blocking retries when order matters, retry topics when throughput matters.
@RetryableTopic(attempts = "4", backoff = @Backoff(delay = 1000, multiplier = 2.0),
                dltStrategy = DltStrategy.FAIL_ON_ERROR,
                exclude = {IllegalArgumentException.class})
@KafkaListener(topics = "library-events") void onMessage(ConsumerRecord<Integer,String> r) { ... }
@DltHandler void dlt(ConsumerRecord<Integer,String> r) { /* alert, persist */ }

@Test void retryable_isRetriedThenRecovered() throws Exception {
  doThrow(new RecoverableDataAccessException("db down")).when(serviceSpy).processLibraryEvent(any());
  kafkaTemplate.send("library-events", 1, json);
  verify(serviceSpy, timeout(10000).times(4)).processLibraryEvent(any());          // 1 + 3 retries
}
  • Use a tiny back-off in test properties so tests stay fast. Cover: retried N times, non-retryable not retried, record lands in DLT/DB, and a subsequent good message is still processed.

Interview Q&A

Tap a question to expand.

Producer reliability

★ Configure Kafka so no message is lost. Explain each piece.
Producer: acks=all, idempotence on, handle failures from the future. Topic: RF 3, min.insync.replicas=2, unclean election off. Consumer: manual or after-processing commit, retries with recovery to DLT so failures are not skipped silently. Add monitoring for ISR shrink, under-replicated partitions, and DLT depth.
★ Why is acks=all not enough without min.insync.replicas?
If followers fall out of the ISR, "all in-sync replicas" can be just the leader, so a leader crash loses data. min.insync.replicas=2 forces writes to fail when redundancy is gone.
★ With RF=3 and min ISR=2, what if two brokers fail?
ISR drops below 2: acks=all writes fail with NotEnoughReplicasException, but reads of committed data continue. That is by design: it prefers consistency over availability.
★ How does the idempotent producer work? What are its limits?
PID + epoch + per-partition sequence numbers; the broker rejects duplicates and out-of-order sequences. Limits: single producer session, single partition scope; not protection against app-level double-sends or across restarts. Use transactions or idempotent consumers for those.
★ How is ordering preserved when retries are enabled?
Idempotence with max.in.flight ≤ 5 (broker resequences by sequence number), or max.in.flight=1 without idempotence. Otherwise a retried batch can land after a later batch.
Relationship between delivery.timeout.ms, request.timeout.ms, linger.ms?
delivery.timeout.ms ≥ linger.ms + request.timeout.ms. Delivery timeout is the overall deadline including retries, while request timeout is one attempt. Prefer tuning the deadline over a retry count.
Idempotent producer vs transactions?
Idempotence: exactly-once per partition per session. Transactions add atomic writes across partitions/topics and consumed-offset commits (sendOffsetsToTransaction), so consumers with read_committed see all or nothing.

Consumer retry and recovery

★ What does Spring Kafka do by default when a listener throws?
DefaultErrorHandler retries up to 9 more times immediately, then logs and skips the record and commits the offset. Data is lost silently unless you add a recoverer.
★ How would you design retry and failure handling for a payments consumer?
Classify errors. Transient: bounded exponential back-off. Permanent: no retry, straight to DLT with exception headers. Persist failure metadata to a table, alert on DLT growth, provide replay tooling, keep the consumer idempotent, and keep total back-off below max.poll.interval.ms.
★ Blocking retries vs retry topics (@RetryableTopic)?
Blocking: preserves order, stalls the partition (throughput and lag hit), simple. Retry topics: partition keeps flowing, delayed retries via tiers, but breaks per-key ordering and adds topics and operational complexity.
★ Downstream DB is down for 30 minutes. What happens with your setup?
In-memory back-off exhausts in seconds, and records go to the recoverer (DLT/DB) in bulk. Better: pause the container on a circuit breaker, use longer back-off within poll limits, or route to retry topics with longer delays, then replay the failures after recovery.
What happens to a record that fails in the DLT publisher itself?
The recovery fails, the error handler treats it as an error again and the record is redelivered (with back-off). Use a reliable DLT setup, monitor recoveryFailed, and fall back to logging or DB.
How do you replay messages from the DLT?
A controlled job or endpoint reads the DLT (or DB failure table), fixes or validates the payload, republishes to the original topic (keeping the key), and marks the failure record resolved. Avoid automatic infinite loops.
What is in the DLT record headers?
Original topic, partition, offset, timestamp, plus exception class, message and stack trace (kafka_dlt-* headers), useful for triage.
Which exceptions are non-retryable by default and why?
Deserialization, conversion, and method-resolution errors, since retrying cannot change the outcome. Add your business exceptions with addNotRetryableExceptions.

Timings and situational

★ session.timeout.ms vs heartbeat.interval.ms vs max.poll.interval.ms?
Session: how long without heartbeats before eviction. Heartbeat: how often the background thread signals liveness (≤ ⅓ of session). Max poll interval: max time between polls, which protects against a stuck processing loop.
★ A consumer is repeatedly kicked out and rebalances. Diagnose.
Look for "poll interval exceeded" (slow processing or long back-off: reduce max.poll.records, raise interval), missed heartbeats (GC pauses, network: raise session timeout), frequent deployments (use static membership and cooperative assignor), or bad pods restarting.
How do fetch.min.bytes and fetch.max.wait.ms trade latency for throughput?
The broker holds the fetch until it has fetch.min.bytes or the wait expires. Higher values batch more per request (throughput, lower broker load), lower values respond faster.
What is max.poll.records for?
Caps records per poll so processing per batch fits within max.poll.interval.ms; smaller values also shrink the replay window after failure.
Kafka consumer commit throws timeout errors. What do you check?
Broker or coordinator health, network latency, default.api.timeout.ms, group coordinator moves, and whether the consumer was already evicted (CommitFailedException).
