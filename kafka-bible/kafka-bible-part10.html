Kafka Bible · Part 10

Production scenario playbook, design prompts, hiring-manager prep, rapid-fire revision

Reported interview loops (Walmart, JPMC) lean on "how would you handle this in production?" and on real incidents. Each scenario: Symptom → Diagnose → Fix → Prevent. Answer in that order out loud.

Universal answer frame: (1) state the symptom and impact, (2) confirm with metrics/CLI before guessing, (3) mitigate first (stop the bleeding), (4) fix root cause, (5) prevent recurrence (alerts, config, tests). Interviewers reward this order more than a single clever fix.

A. Consumer-side incidents

★ 1. Lag is growing steadily on every partition

DiagnoseCompare records-consumed-rate vs produce rate; check per-partition lag, processing time per record, downstream (DB/API) latency, GC, CPU, thread dumps; check recent deploys or traffic spikes.

FixRemove the slow step (batch DB writes, add indexes, cache, async where safe), tune max.poll.records/fetch, scale consumers up to partition count, add partitions if capped (mind key remap).

PreventAlert on time lag, load test at 2× peak, partition headroom, autoscale on lag (KEDA).

★ 2. Lag is high on only one partition

DiagnoseDoes it follow the partition or the consumer instance across rebalances? Partition: hot key or poison record retrying. Instance: bad node, GC, noisy neighbor.

FixHot key: salt or change key, custom partitioner. Poison: DLT and skip. Instance: replace the pod.

PreventHigh-cardinality keys, per-partition lag alerts, key-skew dashboards.

★ 3. Constant rebalancing; throughput collapses

DiagnoseLogs for "max.poll.interval exceeded" (slow processing/long retry back-off), heartbeat timeouts (GC, network), pods restarting (liveness misconfigured, OOMKilled, frequent deploys), autoscaler flapping.

FixReduce max.poll.records or raise max.poll.interval.ms; shorten retry back-off; CooperativeSticky assignor; static membership (group.instance.id) with a longer session timeout; fix probes; stabilize autoscaling.

PreventAlert on rebalance rate; graceful shutdown; rolling-deploy surge limits.

★ 4. Duplicate processing after a deployment

DiagnoseOffsets committed after processing plus rebalance/crash mid-batch means redelivery is expected; check for producer retries without idempotence.

FixIdempotent consumer (processed-event table / upsert / version), idempotent producer, graceful shutdown so in-flight batches finish and commit.

PreventDesign for at-least-once from day one; chaos test with kills mid-batch.

★ 5. Events processed out of order

DiagnoseDifferent partitions for related events, retries without idempotence, thread-pool handoff in the listener, retry topics/DLT reprocessing, partition count changed.

FixKey by entity id, idempotence on, sequential per-partition processing, version check to drop stale events.

★ 6. One bad message blocks the whole partition (poison pill)

DiagnoseSame offset failing repeatedly in logs; lag flat on one partition; deserialization exception inside poll.

FixMitigate: DLT it or seek past it. Root cause: ErrorHandlingDeserializer, non-retryable classification, DLT recoverer, alert on DLT.

PreventSchema Registry compatibility checks and producer-side validation.

★ 7. After a long outage the service reprocessed everything (or skipped everything)

DiagnoseGroup had no members longer than offsets.retention.minutes (7 days), so committed offsets expired and auto.offset.reset applied.

FixReset offsets deliberately to a timestamp (--reset-offsets --to-datetime) with consumers stopped; ensure idempotent handlers.

PreventRaise offset retention for critical groups; alert if a group has no members; explicit reset policy.

★ 8. Downstream DB was down 20 minutes; thousands of messages ended up in the DLT

DiagnoseShort in-memory back-off exhausted, all records reached the recoverer.

FixReplay the DLT after the DB recovers (controlled job, idempotent). Longer-term: circuit breaker that pauses the container during outages, retry topics with longer delays, separate transient from permanent errors.

PreventHealth-gated consumption, DLT depth alert, replay tooling tested in advance.

9. A bad deploy produced wrong events and downstream data is corrupted

FixStop the bad producer; fix and redeploy. For consumers: stop the group, fix logic, reset offsets to before the bad window (--to-datetime) and reprocess with idempotent, overwrite-safe handlers; for compacted topics publish corrected values with the same key.

PreventCanary releases, schema validation, contract tests, retention long enough to allow replay.

10. Consumer slower than producer; retention might delete unread data

DiagnoseCompare lag growth against remaining retention window.

MitigateTemporarily raise retention (kafka-configs.sh --alter ... retention.ms), scale consumers/partitions, shed non-critical work. If data is already gone, offset-out-of-range triggers the reset policy: reconcile from the source of truth.

11. Consumer OOM

DiagnoseHeap dump; large max.poll.records × big messages; unbounded internal queue; batch listener accumulating.

FixLower max.poll.records and fetch sizes, bound queues, stream processing, correct container memory/heap ratio.

12. CommitFailedException / "consumer is not part of the group"

CauseThe consumer was evicted (poll interval or session timeout) and a rebalance happened before it committed.

FixShorten work per poll, raise the interval, ensure the heartbeat thread is not starved; make processing idempotent because the batch will be redelivered.

B. Producer-side incidents

★ 13. Producers throw NotEnoughReplicasException after a broker went down

Diagnose--describe the topic: ISR size below min.insync.replicas (e.g. RF 3, min ISR 2, two brokers gone or a follower lagging).

FixBring brokers back or fix the slow follower. Do not lower min ISR or enable unclean election as a quick fix for critical data. If availability must win, that is a deliberate trade-off (per topic).

PreventRF 3 across racks, alerts on under-min-ISR, capacity for N−1.

★ 14. "TimeoutException: Expiring N records" / delivery timeout

DiagnoseBroker unavailable or slow, leader election in progress, network, batches sitting in the accumulator longer than delivery.timeout.ms (large linger.ms, saturated sender, buffer contention).

FixFix broker/network; verify delivery.timeout.ms ≥ linger + request.timeout; handle the failed future (retry, persist for replay); reduce batch stalls.

15. RecordTooLargeException / MESSAGE_TOO_LARGE

FixClaim check (payload in object storage). Otherwise raise the entire chain: producer max.request.size, broker/topic max.message.bytes, replica.fetch.max.bytes, consumer fetch limits. Compress first.

★ 16. Produce latency spiked

DiagnoseProducer metrics (request-latency, batch-size, buffer available); broker request time breakdown, disk latency, ISR shrink (acks=all waits on slow follower), GC, network saturation, leader imbalance, TLS CPU.

FixAddress the slow replica/disk, rebalance leaders, tune batching/compression, spread load.

★ 17. Duplicate events published (client retries, double click, retry after timeout)

FixIdempotent producer covers broker-level retries only. Add an API idempotency key, unique event id, and consumer-side dedupe. Timeout after send does not mean failure: the write may have succeeded, so retries must be safe.

★ 18. "We think messages are being lost"

DiagnoseReproduce by counting: producer success callbacks vs topic end offsets vs consumer processed count; audit ids per stage. Check acks, unhandled failed futures, unclean elections, retention deleting early, consumer committing before processing, DLT skipping, wrong group id or offset reset.

FixZero-loss recipe (acks=all, idempotence, RF 3, min ISR 2, unclean off, commit after processing, DLT not skip). Add reconciliation counters.

19. send() blocks under load / buffer exhausted

CauseProducer outruns the brokers; buffer.memory full; blocks up to max.block.ms, then throws.

FixBatching + compression, more partitions/brokers, bounded intake with 429 back-pressure at the API, handle the exception. Do not just raise buffer size.

20. One partition receives most of the traffic

FixRebalance the key space (compound key, salting with reduced ordering scope), custom partitioner for known heavy keys, or split hot entities into sub-keys.

C. Broker and cluster incidents

★ 21. A broker's disk is full

MitigateFree space safely: lower retention on the biggest topics or delete old segments via config (not by hand-deleting files), add disk/volume, move partitions off the broker (throttled reassignment).

PreventAlert at 70/80%, right-size retention, tiered storage, capacity planning per topic.

★ 22. Under-replicated partitions and ISR flapping

DiagnoseWhich broker is the common member? Check disk latency, GC pauses, network, CPU, oversized fetches, reassignment in progress, replica.lag.time.max.ms too tight.

FixFix the slow node; throttle heavy jobs; tune fetch/replica threads only after finding the cause.

23. Leaders keep moving; cluster unstable

ImpactClients must refresh metadata and retry, so latency rises and throughput drops.

DiagnoseBroker restarts/crashes, controller flapping, session timeouts to the controller, GC, auto leader rebalance thrashing. FixStabilize the broker; run preferred-leader election once things settle.

24. Lag spikes right after a partition reassignment

CauseReassignment copies log segments between brokers, competing for disk and network with client traffic.

FixUse replication throttles, run off-peak, move in small batches, use Cruise Control.

25. Added brokers but the old topics did not speed up

WhyExisting partitions stay where they are. Run a reassignment (or Cruise Control) to move partitions onto new brokers; new topics distribute automatically.

26. Controller quorum lost / cluster metadata unavailable (KRaft)

DiagnoseMajority of controllers down or partitioned; existing partition leaders may continue serving while metadata changes (topic creation, elections) fail.

FixRestore a controller majority (odd count: 3 or 5), check disks and network. PreventDedicated controller nodes in production across AZs.

27. We need fewer partitions (or a different key)

Partitions cannot be reduced. Create a new topic with the right settings, dual-publish or mirror, migrate consumers, then retire the old topic (checking ordering and offsets during cutover).

28. __consumer_offsets huge or group coordinator slow

DiagnoseVery many commits (commit per record with tiny intervals), stale groups, huge number of groups on one coordinator broker.

FixCommit less often (batch/time), clean up dead groups, verify compaction of the offsets topic, balance coordinators across brokers.

D. System design prompts (outline answers)

★ Payments pipeline: no loss, no double charge

Idempotency key at the API; outbox to payments topic keyed by account id (per-account ordering); acks=all, RF 3, min ISR 2; idempotent consumers with processed-event table; idempotent call to the payment provider; retries with back-off, DLT, reconciliation job for unknown outcomes; audit topic (compacted or long retention); encryption and ACLs; lag and DLT alerts.

★ Order processing across services (saga)

Order service emits OrderPlaced via outbox; inventory reserves and emits result; payment charges; orchestrator or choreography with correlation id; compensations (release stock, refund); timeouts and DLT; idempotency everywhere; order status read model built from events.

★ Real-time inventory across thousands of stores

Events keyed by storeId:sku; compacted topic for latest stock levels plus an event topic for history; consumers upsert with version check; partition count from SKU throughput; hot SKUs handled by sub-keys; Streams or a materialized store for read APIs; cache with TTL; monitor lag per store group.

Notification service with retries and priorities

Separate topics per priority (avoid head-of-line blocking), consumers with more capacity on high priority; retry topics with increasing delays; DLT and manual review; dedupe id per notification; provider rate limiting via pause/resume; user preference checks in the consumer.

CDC pipeline to search index and data lake

Debezium reads the DB log → topics per table (Avro + Schema Registry) → Connect sinks to Elasticsearch and S3; use tombstones for deletes; handle snapshot, schema changes and ordering per key; monitor connector lag and tasks; idempotent sinks.

High-volume telemetry from a streaming service (loss-tolerant)

Favor throughput: acks=1 or all with large batches, lz4/zstd, many partitions keyed by device or session, short retention, sampling, consumers batch to a lake. State the trade-off: some loss acceptable here, unlike payments.

Multi-tenant Kafka for many teams

Topic naming and ownership, ACLs per team, quotas, schema governance, self-service provisioning with defaults (RF 3, min ISR 2), cost and usage dashboards, separate clusters for regulated or noisy workloads.

E. Hiring-manager round: project and depth questions

Expect "why" after every answer, line-by-line resume probing, and monolith vs microservices, plus performance testing.

★ Questions to prepare with real numbers from your own project
  • Why Kafka and not REST, RabbitMQ or SQS here? What did you give up?
  • How many topics, partitions, replicas? How did you choose them? Peak messages/sec and message size?
  • What are your delivery guarantees, and where can duplicates or loss still occur?
  • How do you handle failures: retries, DLT, replay? Show an incident you debugged (use Symptom → Diagnose → Fix → Prevent).
  • How do you monitor it and what do you alert on? What is your lag SLA?
  • How do you performance test (tools, environment, targets, bottleneck found), and what other tests before go-live (integration, contract, failure/chaos, soak)?
  • Monolith vs microservices: when each fits, and how would you migrate (strangler pattern, events as the seam, data ownership first)?
  • What would you change if traffic grew 10×?

F. Rapid-fire revision (one-liners)

Open the flash list
  • Ordering only per partition; same key → same partition (murmur2 % N).
  • Partitions: parallelism ceiling = consumers in group; add ok, remove never; adding remaps keys.
  • Durability: acks=all + RF 3 + min.insync.replicas=2 + unclean election off.
  • Idempotent producer: PID + epoch + per-partition sequence; default on since 3.0; needs acks=all, in-flight ≤ 5.
  • Transactions: atomic multi-partition writes + offsets; read_committed reads to LSO; Kafka-only scope.
  • Commit after processing = at-least-once; make consumers idempotent.
  • Spring default error handler: ~10 quick attempts, then skip. Configure back-off + recoverer (DLT/DB).
  • Deserialization errors: ErrorHandlingDeserializer; non-retryable exceptions go straight to recovery.
  • Rebalance triggers: join/leave, heartbeat (session) timeout, poll interval exceeded, partition change. Mitigate with cooperative + static membership.
  • max.poll.interval.ms (5 min) = max gap between polls; session.timeout.ms (45 s) = heartbeat liveness.
  • HW = min LEO of ISR; consumers read below HW; leader epoch fixes truncation.
  • Offsets of empty groups expire after 7 days; reset only with consumers stopped.
  • Retention deletes closed segments only; compaction keeps latest per key, tombstone deletes.
  • TLS disables zero-copy; durability is replication, not fsync.
  • Outbox fixes dual write (at-least-once); saga fixes cross-service transactions with compensations.
  • Liveness ≠ readiness: keep Kafka/DB out of liveness.
  • Replicas × concurrency ≤ partitions; scale consumers on lag.
  • Schema: Avro + Registry, BACKWARD compatible by default, add optional fields only.
  • Large payloads: claim check; raise limits across the whole chain if forced.
  • KRaft replaced ZooKeeper (removed in 4.0); new group protocol KIP-848 in 4.0.
