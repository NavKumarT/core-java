1. Architecture, PRD, project setup

Videos 61–63

  • Flow: client → Producer service (REST) → Kafka topic library-events → Consumer service (@KafkaListener) → Postgres. Producer and consumer are decoupled and scale independently.
  • Consumer PRD: consume events, deserialize, apply NEW (insert) and UPDATE (validate exists, then update) rules, persist, expose read and CRUD APIs, migrations via Flyway.
  • Dependencies: spring-kafka, spring-boot-starter-data-jpa, postgresql, flyway-core (+ flyway-database-postgresql on Flyway 10+), spring-boot-starter-web, validation, springdoc, spring-kafka-test, Testcontainers.

2. Building the consumer with @KafkaListener

Videos 64–66

@Component @Slf4j
public class LibraryEventsConsumer {
  private final ObjectMapper objectMapper;
  private final LibraryEventService service;
  // constructor omitted

  @KafkaListener(topics = "${app.topic:library-events}", groupId = "library-events-group")
  public void onMessage(ConsumerRecord<Integer,String> record) throws JsonProcessingException {
    log.info("key={} partition={} offset={}", record.key(), record.partition(), record.offset());
    LibraryEventDto dto = objectMapper.readValue(record.value(), LibraryEventDto.class);
    service.processLibraryEvent(dto);
  }
}
spring:
  kafka:
    bootstrap-servers: localhost:9092
    consumer:
      group-id: library-events-group
      auto-offset-reset: earliest
      key-deserializer: org.apache.kafka.common.serialization.IntegerDeserializer
      value-deserializer: org.apache.kafka.common.serialization.StringDeserializer
    listener:
      ack-mode: batch          # default
      concurrency: 1
  • Listener signatures can take the payload, ConsumerRecord, @Header values, Acknowledgment, or Consumer. Use ConsumerRecord when you need key, partition, offset and headers.
  • Test manually: run the producer, POST an event, watch the consumer log the record (video 65).

3. StringDeserializer vs JsonDeserializer

String + ObjectMapperJsonDeserializer
ParsingYou parse in the listener; failures are visible in your codeFramework converts to the target type
ConfigSimplespring.json.trusted.packages, spring.json.value.default.type, spring.json.use.type.headers=false when producer and consumer classes differ
RiskBad JSON throws inside listener (handled by the error handler)Bad JSON fails inside the consumer's poll, so the same record is retried forever unless wrapped
Poison pill: wrap the real deserializer with ErrorHandlingDeserializer (value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer, spring.deserializer.value.delegate.class: ...JsonDeserializer). The failure becomes a handled exception (retry/DLT) instead of an endless poll loop.
  • Use a separate LibraryEventDto for the wire contract; the DB entity stays internal so the two can evolve independently.

4. How the Spring Kafka consumer works, and autoconfiguration

Videos 68–69

  • KafkaListenerAnnotationBeanPostProcessor finds @KafkaListener methods and registers them in the KafkaListenerEndpointRegistry.
  • The ConcurrentKafkaListenerContainerFactory builds a ConcurrentMessageListenerContainer, which spawns N KafkaMessageListenerContainers. Each has its own KafkaConsumer and its own thread running the poll loop.
  • Loop: poll() → batch of records → call your listener one record at a time → commit offsets per ack mode → poll again. A single consumer thread processes sequentially, and KafkaConsumer itself is not thread-safe.
  • Autoconfig (KafkaAutoConfiguration + KafkaAnnotationDrivenConfiguration): creates ConsumerFactory, the container factory and @EnableKafka behavior from spring.kafka.consumer.* and spring.kafka.listener.*. Boot sets enable.auto.commit=false, so the container manages commits. Define your own factory bean to customize (error handler, batch mode, per-listener settings).
  • Default error handling: DefaultErrorHandler retries a failing record (default 10 attempts total, no delay), then logs and moves on. Configure back-off and a dead-letter recoverer for real systems.

5. Consumer groups and rebalance (hands-on)

Video 70

  • Run two instances (--server.port=8081/8082) with the same group-id: the 3 partitions split between them. Stop one: its partitions are revoked and reassigned (visible in logs as "partitions revoked / assigned").
  • A different group-id receives all messages independently (fan-out). Same group load-balances (competing consumers).
  • Inspect: kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group library-events-group shows partition assignment, current offset, log-end offset, and lag.
  • Hook rebalance events with ConsumerAwareRebalanceListener or ConsumerRebalanceListener (e.g. flush state before partitions are revoked).

6. Offset management: default and manual

Videos 71–72

AckModeCommit happens
BATCH (default)After all records from one poll() were processed
RECORDAfter each record's listener returns
TIME / COUNT / COUNT_TIMEAfter a period / number of records
MANUALQueued on ack.acknowledge(), committed with the batch
MANUAL_IMMEDIATECommitted immediately on acknowledge()
// spring.kafka.listener.ack-mode: manual_immediate
@KafkaListener(topics = "library-events")
public void onMessage(ConsumerRecord<Integer,String> record, Acknowledgment ack) throws Exception {
  service.processLibraryEvent(objectMapper.readValue(record.value(), LibraryEventDto.class));
  ack.acknowledge();      // only after the DB commit succeeded
}
  • If the listener throws, the offset is not committed for that record; the error handler decides retry vs. skip vs. DLT.
  • Commit after successful processing gives at-least-once: a crash between DB commit and offset commit causes redelivery, so the consumer must be idempotent.

7. Concurrent consumers

Video 73

@KafkaListener(topics = "library-events", concurrency = "3")     // or spring.kafka.listener.concurrency: 3
  • Creates 3 consumer threads in one JVM, each with its own consumer in the same group. Partitions are spread across them.
  • Ceiling: total active consumers (all threads on all instances) ≤ partition count. Extra threads sit idle.
  • Ordering is still per partition, because each partition is handled by exactly one thread.
  • Threads share the JVM: listener code and services must be thread-safe. Scale by threads for CPU or DB-bound work per JVM; scale by instances for resilience and capacity.

-- src/main/resources/db/migration/V1__create_library_tables.sql
CREATE TABLE library_event (
  library_event_id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  event_type       VARCHAR(20) NOT NULL
);
CREATE TABLE book (
  book_id          INT PRIMARY KEY,
  book_name        VARCHAR(255) NOT NULL,
  book_author      VARCHAR(255) NOT NULL,
  library_event_id INT REFERENCES library_event(library_event_id)
);
  • Flyway applies versioned scripts V{n}__description.sql in order and records them with checksums in flyway_schema_history. Never edit an applied migration (checksum mismatch fails startup); add V2__... instead. R__ scripts are repeatable (views, procs).
  • Why Flyway over ddl-auto=update: repeatable, reviewed, versioned, safe across environments; update is unpredictable and never drops or renames correctly.

9. Entities, repository, service

Videos 76–78

@Entity @Getter @Setter @NoArgsConstructor
public class LibraryEvent {
  @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Integer libraryEventId;
  @Enumerated(EnumType.STRING) private LibraryEventType eventType;
  @OneToOne(mappedBy = "libraryEvent", cascade = CascadeType.ALL) private Book book;
}
@Entity @Getter @Setter @NoArgsConstructor
public class Book {
  @Id private Integer bookId; private String bookName; private String bookAuthor;
  @OneToOne @JoinColumn(name = "library_event_id") private LibraryEvent libraryEvent;
}
public interface LibraryEventRepository extends JpaRepository<LibraryEvent, Integer> {}

@Service @Transactional
public class LibraryEventService {
  private final LibraryEventRepository repo;
  public void processLibraryEvent(LibraryEventDto dto) {
    switch (dto.type()) {
      case NEW    -> save(dto);
      case UPDATE -> { validate(dto); save(dto); }
    }
  }
  private void validate(LibraryEventDto dto) {
    if (dto.libraryEventId() == null) throw new IllegalArgumentException("libraryEventId required for UPDATE");
    repo.findById(dto.libraryEventId()).orElseThrow(() -> new IllegalArgumentException("Unknown library event"));
  }
  private void save(LibraryEventDto dto) { /* map DTO to entity, set book.libraryEvent, repo.save(entity) */ }
}
  • Business rules live in the service, not the listener. The listener only deserializes and delegates.
  • Set the back-reference (book.setLibraryEvent(event)) before saving, or the FK stays null.
  • Idempotency: UPDATE is naturally idempotent. NEW is not: redelivery creates a duplicate unless you enforce a unique business key (e.g. unique book_id) or a processed-event table.

Interview Q&A

Tap a question to expand.

Consumer fundamentals

★ How does @KafkaListener work internally?
A bean post-processor registers each listener with the endpoint registry; the container factory creates a concurrent container that starts N message-listener containers, each running a KafkaConsumer poll loop on its own thread and calling your method for each record, then committing offsets per ack mode.
★ When are offsets committed by default in Spring Kafka?
enable.auto.commit is false; the container commits with AckMode.BATCH, after all records from the last poll were processed successfully.
★ AckMode RECORD vs BATCH vs MANUAL: trade-offs?
RECORD: more commits, less reprocessing after failure. BATCH: fewer commits, larger replay window. MANUAL/MANUAL_IMMEDIATE: you control exactly when (e.g. after DB commit or async work completes) at the cost of complexity.
★ A consumer crashes after saving to DB but before committing the offset. What happens?
The record is redelivered and processed again (at-least-once). Make the handler idempotent: upsert, unique constraint, or a processed-event-id table checked in the same DB transaction.
How do you get exactly-once effect end to end?
Kafka-to-Kafka: idempotent producer + transactions + read_committed. Kafka-to-DB: at-least-once delivery + idempotent write (or store the offset in the same DB transaction and seek on startup).
★ What is concurrency in @KafkaListener? What limits it?
Number of consumer threads per container. Total active consumers across the group cannot exceed partitions; each partition still has one owner, so per-partition ordering holds.
Can one consumer instance handle multiple topics or partitions?
Yes. topics = {"a","b"} or a pattern; a consumer gets one or more partitions and processes them in a single thread, interleaving partitions.
What is a batch listener?
spring.kafka.listener.type=batch hands the listener a List of records per poll, useful for bulk DB inserts. Failure handling is more complex (BatchListenerFailedException to mark the failing index).

Deserialization and errors

★ What is a poison pill and how do you handle it?
A record that always fails (e.g. undeserializable). With JsonDeserializer directly, the poll loop keeps failing on that offset. Use ErrorHandlingDeserializer plus DefaultErrorHandler with a DeadLetterPublishingRecoverer to send it to a DLT and move on.
Why did JsonDeserializer throw "class not in trusted packages"?
It only instantiates trusted types. Set spring.json.trusted.packages (or the specific package), or use a default type and disable type headers when producer and consumer DTO classes differ.
Which exceptions should be retried vs sent straight to the DLT?
Retry transient ones (DB down, timeouts) with back-off. Do not retry non-retryable ones (deserialization, validation, IllegalArgumentException); classify them with addNotRetryableExceptions.

Groups, rebalance, scaling

★ Two instances with the same group id and 3 partitions. What happens when one dies?
The coordinator detects missed heartbeats or session timeout, triggers a rebalance, and the survivor gets the orphaned partitions. Uncommitted records are re-read from the last committed offset.
★ Consumer lag is growing. What do you do?
Check lag per partition. Find the bottleneck (usually the DB or downstream call), batch writes, raise concurrency up to partitions, add instances, add partitions if capped, check for a stuck or poison record on one partition, and check rebalance storms.
Processing sometimes takes 10 minutes and the consumer keeps getting kicked out. Fix?
It exceeds max.poll.interval.ms. Reduce max.poll.records, raise the interval, or hand long work to an executor and pause/resume the partition; better, make the work shorter or asynchronous.
How do you preserve ordering with concurrency?
Key by entity id so its events share a partition; one partition is handled by one thread. Do not hand records to a free thread pool inside the listener unless you partition the work by key yourself.

Data layer and APIs

★ Why Flyway (or Liquibase) instead of ddl-auto=update?
Versioned, reviewable, repeatable migrations with history and checksums across all environments. ddl-auto is nondeterministic and unsafe in production; use validate to catch drift.
What happens if you edit an already-applied Flyway migration?
Checksum validation fails on startup. Fix by adding a new migration, or flyway repair only when you understand the impact.
Entity vs DTO: why not expose entities?
Entities are persistence models: lazy relations, internal fields, and schema coupling. DTOs give a stable API contract and avoid serialization problems and N+1 surprises.
What is the N+1 problem and how do you fix it?
One query for the parent list plus one per child. Fix with fetch joins, @EntityGraph, batch fetching, or projections.
Why @Transactional on the service and not the listener?
Keeps the transaction boundary around business logic and DB work, and lets you commit the offset only after the transaction completes. Note that a DB transaction and Kafka offset commit are not atomic, hence idempotency.
How would you test the consumer end to end?
Embedded Kafka or Testcontainers Kafka + Testcontainers Postgres, wait for partition assignment, publish a record, assert DB state with Awaitility, and separately test failure and DLT behavior.
