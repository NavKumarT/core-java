2. Domain and POST endpoint

Videos 33–35

public record Book(@NotNull Integer bookId, @NotBlank String bookName, @NotBlank String bookAuthor) {}
public enum LibraryEventType { NEW, UPDATE }
public record LibraryEvent(Integer libraryEventId, @NotNull LibraryEventType type, @NotNull @Valid Book book) {}

@RestController @RequestMapping("/libraryevents")
public class LibraryEventsController {
  private final LibraryEventProducer producer;
  public LibraryEventsController(LibraryEventProducer p){ this.producer = p; }

  @PostMapping
  public ResponseEntity<LibraryEvent> post(@RequestBody @Valid LibraryEvent event) throws JsonProcessingException {
    producer.sendLibraryEvent(event);                       // async
    return ResponseEntity.status(HttpStatus.CREATED).body(event);
  }
}
  • Controller only validates and delegates. Producer logic lives in its own @Component.
  • Async send means 201 confirms the request was accepted, not that Kafka acknowledged it. 202 Accepted is arguably more accurate; know this trade-off.

3. KafkaTemplate: introduction and usage

Videos 36–37

KafkaTemplate<K,V> is Spring's high-level wrapper over the Kafka Producer: it handles creation, send, callbacks, and shutdown.

@Component @Slf4j
public class LibraryEventProducer {
  private final KafkaTemplate<Integer,String> kafkaTemplate;
  private final ObjectMapper objectMapper;
  @Value("${spring.kafka.template.default-topic}") private String topic;

  public CompletableFuture<SendResult<Integer,String>> sendLibraryEvent(LibraryEvent e) throws JsonProcessingException {
    Integer key = e.libraryEventId();
    String value = objectMapper.writeValueAsString(e);
    return kafkaTemplate.send(topic, key, value)                       // returns immediately
        .whenComplete((result, ex) -> {
          if (ex != null) log.error("send failed key={} : {}", key, ex.getMessage());
          else log.info("sent key={} partition={} offset={}", key,
                        result.getRecordMetadata().partition(), result.getRecordMetadata().offset());
        });
  }
}
MethodUse
send(topic, value) / send(topic, key, value)Simple sends
send(topic, partition, key, value)Force a partition
send(ProducerRecord)Full control: headers, timestamp (e.g. trace id, event type)
sendDefault(...)Uses spring.kafka.template.default-topic
  • In Spring Kafka 3.x send returns CompletableFuture<SendResult> (it was ListenableFuture in 2.x). SendResult holds the ProducerRecord and RecordMetadata (topic, partition, offset, timestamp).

5. KafkaTemplate under the hood and threading model

Videos 39, 45

  • KafkaTemplate → ProducerFactory (DefaultKafkaProducerFactory) → a single, shared, thread-safe KafkaProducer instance, created lazily on first send and reused by all request threads.
  • send() (on the caller's thread): serialize key and value, fetch metadata if needed (blocks up to max.block.ms), choose partition, append to the RecordAccumulator, return the future.
  • A dedicated Sender (I/O) thread drains batches, sends them to leader brokers, handles retries and acks, and completes the future. Callbacks run on the producer's I/O thread, so keep them fast and non-blocking.
  • Sharing one producer is faster than one per request because it maximizes batching and reuses connections. (Transactional producers are the exception: the factory keeps a pool keyed by transaction id prefix.)
  • First send is slower: it includes metadata fetch and connection setup. Warm up on startup if latency matters.

6. Batching and buffering deep dive

Video 40

  • Records are grouped per partition into batches in the accumulator. A batch is sent when it reaches batch.size (bytes, default 16 KB) or linger.ms expires (default 0, meaning send immediately, though records arriving together still batch).
  • buffer.memory (default 32 MB) caps unsent data. When full, send() blocks up to max.block.ms (60s), then throws TimeoutException. This is the back-pressure mechanism.
  • Compression is applied per batch, so larger batches compress better.
  • delivery.timeout.ms (2 min) bounds the total time from send to ack, including retries; request.timeout.ms bounds each attempt.

7. How KafkaTemplate autoconfiguration works

Video 41

  • KafkaAutoConfiguration (activated when KafkaTemplate is on the classpath) binds spring.kafka.* to KafkaProperties.
  • It registers ProducerFactory, KafkaTemplate, ConsumerFactory, listener container factory, KafkaAdmin and more, each @ConditionalOnMissingBean. Define your own bean and Boot backs off.
  • spring.kafka.producer.* maps to producer configs; anything else goes under spring.kafka.producer.properties.*. spring.kafka.template.default-topic feeds sendDefault.
  • A KafkaAdmin bean creates topics declared as NewTopic beans on startup (TopicBuilder.name("library-events").partitions(3).replicas(1).build()). Fine for dev; in prod, topics are usually provisioned by platform tooling.

  kafka:

        enable.idempotence: true

8. StringSerializer vs JsonSerializer

Video 42

StringSerializer + own ObjectMapperJsonSerializer (Spring Kafka)
ControlFull: you control the JSON and errorsConvenient: serializes the object directly
Type infoNone in headersAdds __TypeId__ header (class name) by default; set spring.json.add.type.headers=false for non-Spring consumers
CouplingLoose, consumer parses itselfConsumer needs JsonDeserializer + trusted packages
  • Serialization failure surfaces as SerializationException inside send(), before anything reaches the broker.
  • For production with several teams and schema evolution, prefer Avro/Protobuf + Schema Registry (compatibility rules, compact payloads) over free-form JSON.
  • Key serializer must match the key type (IntegerSerializer for an Integer id). Mismatch throws ClassCastException.

9. RestControllerAdvice and exception handling

Videos 43, 47

@RestControllerAdvice @Slf4j
public class GlobalExceptionHandler {

  @ExceptionHandler(MethodArgumentNotValidException.class)          // @Valid failures
  public ResponseEntity<Map<String,String>> validation(MethodArgumentNotValidException ex) {
    Map<String,String> errors = new TreeMap<>();
    ex.getBindingResult().getFieldErrors().forEach(f -> errors.put(f.getField(), f.getDefaultMessage()));
    return ResponseEntity.badRequest().body(errors);                 // 400
  }

  @ExceptionHandler(JsonProcessingException.class)
  public ResponseEntity<String> json(JsonProcessingException ex) { return ResponseEntity.unprocessableEntity().body(ex.getOriginalMessage()); }

  @ExceptionHandler(Exception.class)                                 // catch-all
  public ResponseEntity<String> any(Exception ex) {
    log.error("unhandled", ex);
    return ResponseEntity.internalServerError().body("Something went wrong");   // never leak internals
  }
}
  • Most specific handler wins. Keep the catch-all last in spirit and always log the stack trace.
  • Async send failures do not reach the advice, because the request thread has already returned. They arrive in the whenComplete callback, where you log, retry, or persist the event for reprocessing.

10. Synchronous sending

Video 44

try {
  SendResult<Integer,String> r = kafkaTemplate.send(topic, key, value).get(3, TimeUnit.SECONDS);
} catch (ExecutionException e) { /* real cause: e.getCause() (e.g. RecordTooLargeException) */ }
  catch (TimeoutException e)   { /* no ack in time */ }
  catch (InterruptedException e) { Thread.currentThread().interrupt(); }
  • Blocks the request thread until the broker acks, so it is much lower throughput but the API can return a truthful result.
  • Use it when the caller must know the write succeeded (critical or low-volume events); use async plus callback for high volume.
  • Always use a timeout on get(). Unwrap ExecutionException to find the actual Kafka error.

11. PUT endpoint and keys

Video 46

@PutMapping
public ResponseEntity<?> put(@RequestBody @Valid LibraryEvent event) throws JsonProcessingException {
  if (event.libraryEventId() == null)
    return ResponseEntity.badRequest().body("libraryEventId is required for UPDATE");
  if (event.type() != LibraryEventType.UPDATE)
    return ResponseEntity.badRequest().body("Only UPDATE events are supported");
  producer.sendLibraryEvent(event);                    // key = libraryEventId
  return ResponseEntity.ok(event);
}
  • Key = entity id so all events for one book go to the same partition and are consumed in order (NEW then UPDATE never swap).
  • Validate business rules at the edge (missing id, wrong type) and return 4xx before touching Kafka.
  • POST creates (server-generated or supplied id), PUT updates an existing id and is idempotent by intent.

Interview Q&A

Tap a question to expand.

KafkaTemplate and sending

★ What is KafkaTemplate and what does send() return?
Spring's thread-safe abstraction over KafkaProducer. send() is asynchronous and returns a CompletableFuture<SendResult> (topic, partition, offset, timestamp on success).
★ Is KafkaTemplate thread-safe? Should each request get its own producer?
Yes, thread-safe. One shared producer per factory is recommended: it batches records from many threads and reuses connections. Creating producers per request is slow and wasteful.
★ Sync vs async send: when do you use each?
Async plus callback for throughput; sync (get(timeout)) when the caller needs certainty before responding. Sync blocks a thread per request, lowering throughput.
★ What happens if the broker is down when you call send()?
If metadata cannot be fetched, send() blocks up to max.block.ms, then throws TimeoutException. If the send is accepted but the broker later fails, the future completes exceptionally after retries within delivery.timeout.ms. Handle both: catch at the call site and in the callback.
How do you add headers such as a trace id or event type?
Build a ProducerRecord with RecordHeaders (or use MessageBuilder with KafkaHeaders) and call send(record).
How do you know which partition and offset a message landed on?
From SendResult.getRecordMetadata() in the callback or get().
What is sendDefault?
Sends to spring.kafka.template.default-topic (or template.setDefaultTopic).

Under the hood and config

★ Walk me through what happens between send() and the broker ack.
Serialize → resolve metadata (partition leader) → partitioner → append to per-partition batch in the RecordAccumulator → Sender thread groups batches by broker and sends → leader appends, replicates per acks → response → future completes and the callback runs.
★ What are linger.ms, batch.size, buffer.memory? What if the buffer fills?
See section 6. When the buffer is full, send() blocks up to max.block.ms and then throws, which is the producer's back-pressure. Fix by raising throughput (batching, compression), scaling out, or slowing the source.
How does Spring Boot autoconfigure Kafka? How do you override it?
KafkaAutoConfiguration binds spring.kafka.* and creates beans with @ConditionalOnMissingBean. Override with properties, or define your own ProducerFactory/KafkaTemplate beans.
How do you create a second KafkaTemplate with a different serializer (e.g. JSON for one topic)?
Define another ProducerFactory with its own config map and a second KafkaTemplate bean, then inject by qualifier. Or use a RoutingKafkaTemplate.
★ StringSerializer vs JsonSerializer vs Avro?
String plus ObjectMapper gives full control and no type headers. JsonSerializer is convenient but adds type headers and couples consumers. Avro/Protobuf with Schema Registry gives compact, versioned, compatibility-checked contracts, best for multi-team production.

Reliability and design

★ How do you configure the Spring Kafka producer for no data loss and no duplicates?
acks=all, enable.idempotence=true, sensible retries and delivery.timeout.ms, with topic RF 3 and min.insync.replicas=2. Handle failed futures (log, retry, or park the event).
★ The REST call succeeded but the Kafka send failed. What do you do?
Do not return success blindly. Options: sync send and return 5xx on failure; async with callback that persists failures for retry or DLQ; or the transactional outbox pattern (below).
★ Dual-write problem: save to DB and publish to Kafka atomically?
A DB transaction and a Kafka send cannot be one atomic operation. Use the outbox pattern: write the event to an outbox table in the same DB transaction; a relay (poller or CDC such as Debezium) publishes it to Kafka. Consumers must be idempotent (at-least-once).
Kafka transactions with Spring?
Set spring.kafka.producer.transaction-id-prefix; use @Transactional or kafkaTemplate.executeInTransaction. Sends become atomic across topics/partitions; consumers use isolation.level=read_committed. It covers Kafka-to-Kafka only, not your DB.
How do you preserve ordering of updates for one entity?
Use the entity id as the key so they share a partition; keep idempotence on with max.in.flight ≤ 5; avoid multiple producers racing for the same key without coordination.
Why validate before sending to Kafka?
Kafka topics are shared contracts; bad data poisons every consumer and cannot be edited (log is immutable). Reject at the edge with 400.

Situational

★ Your producer service's latency spiked. Where do you look?
Metadata fetch or blocked send() (buffer full, broker unavailable), acks=all with a slow follower (ISR shrink), tiny batches (linger.ms=0), no compression on large payloads, sync get() on the request thread, or GC pauses. Check producer metrics: record-send-rate, request-latency-avg, buffer-available-bytes, batch-size-avg.
★ You must support 10× traffic. What do you change in the producer?
Async sends, larger batches with linger.ms 5–20, compression, enough partitions, scale service instances, tune buffer size, and check broker capacity and network.
Message larger than 1 MB fails. What now?
RecordTooLargeException. Prefer storing the payload in object storage and sending a reference (claim check). Otherwise raise max.request.size (producer), message.max.bytes/max.message.bytes (broker/topic), and consumer max.partition.fetch.bytes.
How do you test the producer?
Unit: mock KafkaTemplate. Integration: @EmbeddedKafka or Testcontainers Kafka with a test consumer asserting topic, key, value and headers. Also test the @RestControllerAdvice with MockMvc for 400/500 cases.
How do you manage different Kafka settings across dev, QA and prod?
Spring profiles with per-profile YAML, secrets injected from environment or a secrets manager, and topic provisioning via infrastructure tooling rather than autoconfigured creation in prod.
