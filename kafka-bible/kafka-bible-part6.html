1. Kafka transactions and exactly-once semantics

Video 107

SemanticsHow
At-most-onceCommit before processing; may lose
At-least-onceCommit after processing; may duplicate
Exactly-once (Kafka)Idempotent producer + transactions + read_committed consumers
  • A transaction makes writes to multiple partitions/topics (and consumed-offset commits) atomic: all become visible or none do.
  • Mechanics: the producer has a transactional.id; a transaction coordinator broker tracks state in the internal __transaction_state topic; on commit/abort it writes commit/abort markers into the partitions. A new producer with the same id bumps the epoch and fences zombie producers.
  • Consumers choose isolation.level: read_uncommitted (default, sees aborted data) or read_committed (only committed data, reads up to the last stable offset, so an open transaction delays visibility of later records).
  • Requirements: acks=all, idempotence on, and a healthy __transaction_state (RF and transaction.state.log.min.isr ≥ 2 in prod). transaction.timeout.ms (default 60 s) aborts stuck transactions.
  • Scope: exactly-once holds inside Kafka (Kafka → process → Kafka). A DB or REST call is not part of the Kafka transaction.

2. Approach 1: declarative with @Transactional

Videos 108–109

spring:
  kafka:
    producer:
      transaction-id-prefix: tx-library-       # enables transactions; Boot creates KafkaTransactionManager
      acks: all
    consumer:
      properties:
        isolation.level: read_committed
@Service
public class LibraryEventPublisher {
  @Transactional("kafkaTransactionManager")               // needed if another TM (JPA) exists
  public void publishAll(List<LibraryEvent> events) {
    for (var e : events) {
      kafkaTemplate.send("library-events", e.libraryEventId(), toJson(e));
    }
    // returning normally commits; a RuntimeException aborts all sends
  }
}
  • With a transactional producer factory, calling send() outside a transaction throws IllegalStateException (no transaction in progress) unless allowNonTransactional is set.
  • Rollback rules: Spring rolls back on RuntimeException/Error only. A checked exception commits unless you add rollbackFor = Exception.class.
  • Self-invocation trap: calling a @Transactional method from the same class bypasses the proxy, so no transaction starts.
  • Publishing multiple messages as one transaction (video 109): a partial failure mid-loop must leave zero visible messages when read with read_committed.
  • DB + Kafka: with JPA as primary TM the Kafka transaction is synchronized on a best-effort basis (commit order, not two-phase commit). It is not atomic; use the outbox pattern or idempotent consumers for correctness.

4. Transactions in the consumer (read-process-write)

Video 112

  • When the producer factory has a transaction-id-prefix, Boot wires the KafkaTransactionManager into the listener container. The container begins a transaction per record (or batch), runs your listener, then calls sendOffsetsToTransaction and commits, so produced records and consumed offsets commit atomically.
  • If the listener throws, the transaction aborts: output records are discarded, offsets are not committed, and the record is redelivered (subject to the error handler). Downstream consumers must use read_committed.
@KafkaListener(topics = "library-events", groupId = "enricher")
public void process(ConsumerRecord<Integer,String> r) {         // already inside a Kafka transaction
  kafkaTemplate.send("library-events-enriched", r.key(), enrich(r.value()));
}
Caveat: if your listener writes to a database, the DB commit is outside the Kafka transaction. A crash between the two still causes redelivery, so keep the DB write idempotent. True exactly-once to an external store needs idempotency or storing offsets with the data.

5. Testing transactions

Video 111

@EmbeddedKafka(topics = "library-events", partitions = 3,
    bootstrapServersProperty = "spring.kafka.bootstrap-servers",
    brokerProperties = {"transaction.state.log.replication.factor=1", "transaction.state.log.min.isr=1"})
class TransactionalPublishTest {
  // test consumer: props.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");

  @Test void failure_midway_leavesNoRecords() {
    assertThrows(RuntimeException.class, () -> publisher.publishAll(List.of(good, badThatThrows)));
    var records = KafkaTestUtils.getRecords(consumer, Duration.ofSeconds(3));
    assertEquals(0, records.count());                       // aborted transaction is invisible
  }
  @Test void success_publishesAll() { publisher.publishAll(List.of(a, b)); assertEquals(2, KafkaTestUtils.getRecords(consumer).count()); }
}
  • Embedded brokers need the transaction-log properties above (single broker), or the transaction coordinator never becomes available.
  • The test consumer must be read_committed; with the default level you would still see aborted records and the test would mislead you.

6. Spring Boot Actuator

Videos 113–114

  • spring-boot-starter-actuator adds production endpoints: /actuator/health, info, metrics, loggers, env, prometheus (with Micrometer registry).
  • Only health is exposed over HTTP by default; expose more explicitly and secure them (Spring Security, separate management port, never expose env/heapdump publicly).
  • Health aggregates HealthIndicators (db, diskSpace, ping, custom). Overall status is the worst of all components.
  • Probes: management.endpoint.health.probes.enabled=true gives /actuator/health/liveness and /readiness for Kubernetes.
management:
  endpoints.web.exposure.include: health,info,metrics,prometheus
  endpoint.health:
    show-details: when-authorized
    probes.enabled: true
    group:
      readiness.include: readinessState,db,kafka      # dependencies gate traffic
      liveness.include: livenessState                 # keep dependencies OUT of liveness
Liveness vs readiness: liveness = "is the process broken? restart it". Readiness = "can it serve traffic now? route around it". If liveness includes Kafka or the DB, a broker outage makes Kubernetes restart every pod in a loop and makes things worse.

7. Kafka readiness health indicator

Videos 115–116

Boot has no built-in Kafka health indicator, so write one that asks the cluster for its nodes with a short timeout.

@Component("kafka")
public class KafkaHealthIndicator implements HealthIndicator {
  private final AdminClient admin;                                   // one shared client, not one per call
  public KafkaHealthIndicator(KafkaAdmin kafkaAdmin) { this.admin = AdminClient.create(kafkaAdmin.getConfigurationProperties()); }

  @Override public Health health() {
    try {
      var cluster = admin.describeCluster(new DescribeClusterOptions().timeoutMs(2000));
      int brokers = cluster.nodes().get(2, TimeUnit.SECONDS).size();
      return Health.up().withDetail("brokers", brokers).withDetail("clusterId", cluster.clusterId().get()).build();
    } catch (Exception e) { return Health.down(e).build(); }
  }
  @PreDestroy void close() { admin.close(Duration.ofSeconds(2)); }
}
  • Producer: readiness = can reach Kafka. Consumer: readiness = Kafka reachable and listener containers running (registry.getListenerContainers().stream().allMatch(MessageListenerContainer::isRunning)) and DB healthy.
  • Keep checks fast and cheap with tight timeouts; health endpoints are hit every few seconds by every pod.
  • Also useful: Micrometer Kafka metrics (consumer records-lag-max, producer record-error-rate) exposed at /actuator/prometheus for alerting.

8. Executable jars and environment variables

Videos 117–119

# build (spring-boot-maven-plugin repackages into a runnable "fat" jar)
./mvnw clean package -DskipTests

# run producer
SPRING_PROFILES_ACTIVE=prod \
SPRING_KAFKA_BOOTSTRAP_SERVERS=broker1:9092,broker2:9092 \
SERVER_PORT=8080 \
java -jar target/library-events-producer.jar

# run consumer (different port), override via arguments
java -jar target/library-events-consumer.jar --server.port=8081 --spring.profiles.active=prod \
     --spring.datasource.url=jdbc:postgresql://db:5432/library

# yaml placeholders with defaults
#   bootstrap-servers: ${KAFKA_BROKERS:localhost:9092}
#   password: ${DB_PASSWORD}          # no default for secrets
  • Executable jar: the Boot loader runs nested jars from BOOT-INF/lib and your classes from BOOT-INF/classes, so java -jar needs no app server or classpath setup.
  • Relaxed binding: spring.kafka.bootstrap-servers ↔ env var SPRING_KAFKA_BOOTSTRAP_SERVERS (uppercase, dots and dashes become underscores).
  • Precedence (high → low): command-line args, JVM -D properties, OS environment variables, profile-specific files (application-prod.yml), application.yml, defaults in code.
  • Secrets come from env vars or a secrets manager, never from the repo. Twelve-factor: same artifact everywhere, config differs by environment.
  • In containers set memory explicitly (-XX:MaxRAMPercentage=75) and prefer layered images or spring-boot:build-image.

Interview Q&A

Tap a question to expand.

Transactions and exactly-once

★ What does "exactly-once" mean in Kafka? What does it not cover?
Idempotent producer + transactions + read_committed consumers give exactly-once for consume-process-produce within Kafka. It does not cover side effects in databases or external APIs; those need idempotent operations.
★ How do Kafka transactions work internally?
A transactional.id maps to a producer id and epoch. The transaction coordinator records state in __transaction_state; on commit/abort it writes markers to every partition involved. Consumers using read_committed skip aborted records and stop at the last stable offset.
★ What is zombie fencing?
When an instance restarts or a rebalance hands its work to another, the new producer with the same transactional.id gets a higher epoch; the broker rejects writes from the old (zombie) producer.
★ Idempotent producer vs transaction: when do you need which?
Idempotence removes duplicates from retries on one partition in one session. Transactions are needed for atomic multi-partition/topic writes and to commit consumed offsets together with produced output.
What is isolation.level and what is the last stable offset?
read_committed hides uncommitted and aborted records. The LSO is the offset before the first still-open transaction, so a long-running transaction delays consumers reading beyond it.
Downsides of transactions?
Higher latency (commit round-trips and markers), more broker load, transactional consumers wait for commits, need proper RF/ISR on the transaction log, and stuck transactions block visibility until timeout.
★ @Transactional on a method that sends to Kafka and saves to a DB: is it atomic?
No. Two independent systems, no two-phase commit. Commit order is best effort, so a crash between them leaves inconsistency. Use the outbox pattern (write event to a table in the same DB transaction, relay to Kafka) or make consumers idempotent.
Why did my @Transactional method not roll back the Kafka sends?
Common causes: a checked exception (add rollbackFor), self-invocation bypassing the proxy, wrong transaction manager chosen when both JPA and Kafka exist, or catching the exception inside the method.
How do transactions work with a Spring Kafka listener?
The container starts a Kafka transaction per record/batch, sends consumed offsets to the transaction and commits with any records you produced. On exception it aborts, offsets stay uncommitted, and the record is redelivered.
Situational: you must publish three related events atomically. How?
Enable transaction-id-prefix, wrap the three sends in @Transactional("kafkaTransactionManager") (or executeInTransaction), and ensure downstream consumers use read_committed. Test that a failure on the third leaves none visible.
Situational: duplicates still appear downstream even with transactions. Why?
Consumers still on read_uncommitted, side effects outside Kafka (DB/API) replayed after redelivery, or producers without a stable transactional.id across restarts. Fix isolation level and make sinks idempotent.

Actuator and operations

★ Liveness vs readiness probes? What goes in each?
Liveness detects a broken process (restart); readiness gates traffic. Put dependencies (DB, Kafka) in readiness, not liveness, so an outage removes pods from rotation instead of triggering restart storms.
★ How do you monitor a Kafka consumer in production?
Health/readiness endpoints, Micrometer metrics to Prometheus/Grafana (consumer lag, poll rate, error rate, rebalances), lag alerts from kafka-consumer-groups or Burrow/exporters, DLT depth alerts, and structured logs with topic/partition/offset.
How do you write a custom HealthIndicator? What to watch out for?
Implement HealthIndicator, return Health.up()/down() with details. Keep it fast with timeouts, reuse clients, avoid heavy calls, and do not leak sensitive details publicly.
How do you secure Actuator endpoints?
Expose only what you need, put them on a separate management port or behind Spring Security roles, restrict show-details, and never expose env, heapdump or loggers (write) to the internet.
Situational: health says UP but Kafka is down. Why?
No Kafka indicator exists by default, so nothing checks it. Add a custom indicator (AdminClient describeCluster with timeout) and include it in the readiness group.
Situational: after a Kafka outage all pods restart repeatedly. Cause?
Kafka health is wired into liveness. Move it to readiness only.

Packaging and configuration

★ How does a Spring Boot executable jar work?
The Maven/Gradle plugin repackages the app with a launcher; nested dependency jars live in BOOT-INF/lib and the Boot loader builds the classpath at start, so java -jar works with an embedded server.
★ Configuration precedence in Spring Boot?
Command-line args, then system properties, then OS env vars, then profile-specific files, then application.yml, then defaults. Higher sources override lower ones.
How do you pass Kafka brokers and secrets to the app in prod?
Environment variables or arguments (SPRING_KAFKA_BOOTSTRAP_SERVERS), secrets from a manager (Vault, AWS Secrets Manager, Kubernetes Secrets), profile files only for non-secret differences.
How do you run the producer and consumer on one machine?
Different ports (server.port), same Kafka, distinct application names; for multiple consumers use the same group-id to share partitions.
