What is Kafka & Why It Exists

Kafka is a distributed, append-only, partitioned, replicated commit LOG — not a traditional message queue with a different UI. Every architectural decision in Kafka flows from that one sentence, and truly internalizing it is what separates a candidate who's "used Kafka" from one who genuinely understands it.

Traditional Message Queue vs Kafka
  • A traditional MQ (RabbitMQ, ActiveMQ, SQS) typically DELETES a message once it's been consumed/acknowledged — it's a transient handoff mechanism
  • Kafka RETAINS messages for a configured period (or forever, with compaction) regardless of whether they've been read — consuming a message does NOT remove it
  • This means MULTIPLE independent consumers (or consumer groups) can read the SAME data, at their own pace, and you can REPLAY history — rewind a consumer to an earlier offset and reprocess
Why this design — the original problem Kafka solved
  • Built at LinkedIn to handle massive-scale EVENT streams (user activity, metrics) that needed to flow to many downstream systems (analytics, search indexing, monitoring) without those systems tightly coupling to each other
  • A log-based design gives high THROUGHPUT (sequential disk I/O is fast, and Kafka leans on this heavily) and DECOUPLING (producers and consumers never talk to each other directly, only through the log)
  • Core use cases: event-driven microservices, activity tracking, log aggregation, stream processing, Change Data Capture (CDC), and as the backbone of real-time data pipelines
The mental model that unlocks everything else

   │
   ├─ Partition 0: [msg0][msg1][msg2][msg3][msg4]...  ← append-only, ordered, immutable
   ├─ Partition 1: [msg0][msg1][msg2]...
   └─ Partition 2: [msg0][msg1][msg2][msg3]...

// records are appended to, in order, forever incrementing an OFFSET

// remembered offset backward, and re-reads history it already saw before
💡 Interview one-liner: "Kafka is a distributed commit log, not a queue — messages persist after consumption, multiple consumer groups can independently read the same topic at their own pace, and offsets are just a client-tracked position, which is exactly what makes replay possible. Nearly every Kafka behavior I know traces back to this log-based, pull-based design."

The Unit of Everything

Topics, Partitions & Offsets

The partition — not the topic — is Kafka's real unit of parallelism, ordering, and storage. A huge fraction of "how does Kafka guarantee X" interview answers reduce to "only within a single partition."

What a partition guarantees
  • Strict ordering WITHIN a partition — records are appended and read in the exact order written
  • NO ordering guarantee ACROSS partitions — two records in different partitions of the same topic can be read in any relative order
  • Each partition is consumed by AT MOST ONE consumer within a given consumer group at a time — this is literally how Kafka achieves parallel consumption
Offsets — the coordinate system
  • A monotonically increasing integer, UNIQUE PER PARTITION (not global across the topic) — offset 5 in Partition 0 and offset 5 in Partition 1 are two completely different records
  • Immutable once assigned — a record's offset never changes, even under log compaction (compaction removes records, it doesn't renumber survivors)
  • Tracked by the CONSUMER (committed to an internal Kafka topic, __consumer_offsets) — the broker doesn't track "what has been read," only what exists
Why ordering is per-partition, concretely
Creating a topic — key configs
// Topic "orders" with 3 partitions. Producer sends events for order #42:
// CREATED, PAID, SHIPPED — in that order, from the SAME producer thread

// If all three go to the SAME partition (because they share a key — see the
// Partitioning Strategy section), ordering IS guaranteed:
// Partition 1: [..., CREATED(order42), PAID(order42), SHIPPED(order42), ...]
// A consumer reading Partition 1 sees them in exactly this order — always.

// If they land on DIFFERENT partitions (e.g. no key, round-robin), a
// consumer group with 3 consumers might process SHIPPED before PAID —
// genuinely unordered relative to each other. THIS is exactly why any
// event stream that needs ordering for a given ENTITY must key by that
// entity's ID (orderId here) — covered fully in the next section

    --partitions 6 \                 # parallelism ceiling — see Partitioning Strategy for how to choose this

    --config retention.ms=604800000 \  # 7 days — how long records are kept
    --config cleanup.policy=delete     # "delete" (time/size based) vs "compact" (per-key latest-value) — see Log Internals section

// later BREAKS key-based ordering guarantees for existing keys (the
// key-to-partition mapping changes once the partition count changes) —
// choosing partition count thoughtfully UP FRONT is a real production concern

An enormous fraction of downstream interview questions — partitioning strategy, why keys matter, consumer group parallelism limits, rebalancing implications — are direct consequences of this one sentence.
Choosing Where a Record Goes

Partitioning Strategy & Hot Partitions

How a producer decides WHICH partition a record lands in is one of the most consequential design decisions in a Kafka-based system — get it wrong and you either lose ordering guarantees you needed, or create a crippling hot-partition bottleneck.

How many partitions should a topic have?
// Kafka's built-in default partitioner:

// 1. If a KEY is provided: partition = hash(key) % numPartitions
//    (technically murmur2 hash — but "consistent hash of the key" is the
//    concept that matters) -> the SAME key ALWAYS maps to the SAME
//    partition, which is EXACTLY what gives per-key ordering

// 2. If NO key is provided: since Kafka 2.4+, records are batched using
//    the "sticky partitioner" — stick to ONE partition for a batch's worth
//    of records, then switch — this improves BATCHING EFFICIENCY over the
//    old pure round-robin approach, at the cost of no ordering guarantee at all

producer.send(new ProducerRecord<>("orders", orderId, orderEvent)); // orderId as KEY -> same order's events always co-located
public class VipCustomerPartitioner implements Partitioner {

    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        int numPartitions = cluster.partitionCountForTopic(topic);

        if (isVipCustomer((String) key)) {
            return 0; // route ALL VIP traffic to a dedicated partition —
        }                // e.g. consumed by a higher-priority/faster consumer instance

        return Math.abs(key.hashCode()) % (numPartitions - 1) + 1; // everyone else spread across the rest
    }
}
// Real interview-relevant use case: priority routing, or steering data with
// a known skewed key distribution more evenly than the default hash would
// A HOT PARTITION: one partition receives disproportionately more traffic
// than others — e.g. keying by "tenantId" when one tenant is 1000x bigger
// than the rest. That ONE partition's single leader broker becomes a
// bottleneck — adding MORE partitions/consumers doesn't help, since a
// single key always maps to the same partition

// FIXES, roughly in order of preference:
// 1. Salt the key: combine the natural key with a random/rotating suffix
//    (e.g. "tenantId-" + (eventId.hashCode() % 4)) to SPREAD one logical
//    entity's traffic across several partitions — at the cost of losing
//    strict ordering for that WHOLE entity (only sub-ranges stay ordered)
// 2. Use a custom partitioner with explicit logic for known "big" keys
//    (like the VIP example above, inverted — spread the BIG key, not isolate it)
// 3. Reconsider whether that entity truly NEEDS cross-event ordering at all —
//    if not, drop the key requirement and let records spread naturally
// A genuinely common senior-level question — there's no single right
// number, but the REASONING matters:

// - Partition count sets your MAX consumer parallelism within one group —
//   more partitions than consumers = some consumers handle multiple
//   partitions; more CONSUMERS than partitions = the extra consumers sit idle
// - Rule of thumb: partitions >= max number of consumer instances you
//   ever expect to run concurrently for that topic
// - More partitions = more open file handles per broker, longer leader
//   election time during failover, more memory/replication overhead —
//   NOT a free "more is always better" dial
// - A commonly cited practical starting point for moderate throughput:
//   somewhere in the 6-12 partition range, scaled up based on measured
//   target throughput per partition (often cited around tens of MB/s per
//   partition as a rough single-partition ceiling) and expected consumer count
💡 Interview one-liner: "I key by whatever entity needs ordered processing — typically the aggregate ID, like orderId or userId — so all events for that entity land in the same partition and are processed in order by one consumer. Partition count is set based on the max parallelism I need and expected throughput per partition, keeping in mind it can only go UP, never down, and increasing it later reshuffles the key-to-partition mapping."
Fault Tolerance

Replication, ISR & Leader Election

Every partition has multiple copies (replicas) spread across different brokers — if the broker holding the "authoritative" copy dies, another takes over automatically. This is THE mechanism behind "how does Kafka survive a broker failure," asked in some form in nearly every Kafka interview.

Leader & Followers
  • Each partition has exactly ONE LEADER replica at a time — ALL reads and writes for that partition go through the leader, exclusively
  • Every other replica is a FOLLOWER — it continuously fetches (replicates) new records from the leader, but serves no client traffic by default
  • replication.factor=3 means 3 total copies of each partition (1 leader + 2 followers), typically spread across 3 different brokers (ideally 3 different AZs/racks too, for real fault tolerance)
ISR — In-Sync Replicas
  • The ISR is the subset of replicas that are "caught up" with the leader — specifically, that have fetched within replica.lag.time.max.ms (default 30s)
  • ONLY a replica in the ISR is eligible to be elected the new leader if the current leader fails — this is what prevents data loss on failover
  • A slow or network-partitioned follower falls OUT of the ISR — it still exists as a replica, but is excluded from leader-election eligibility and from acks=all acknowledgment until it catches back up
Leader failure — the failover sequence
Unclean Leader Election — the availability/consistency trade-off
min.insync.replicas — the durability floor
// Partition "orders-2" — Leader on Broker 1, Followers on Broker 2 and Broker 3, all in ISR

// Broker 1 crashes:
// 1. The Controller detects the failure (heartbeat/session timeout)
// 2. Controller picks a NEW leader from the remaining ISR members for
//    every partition that WAS led by Broker 1 — here, Broker 2 or Broker 3
// 3. Controller updates cluster metadata (via KRaft, or historically ZooKeeper)
//    with the new leader assignment
// 4. Producers/consumers, whose metadata is now STALE, get a
//    NotLeaderForPartitionException on their next request -> they refresh
//    metadata automatically and retry against the NEW leader — the client-side
//    SDK handles this transparently, no application code changes needed

// Net effect: a brief availability blip for THAT partition during election
// (typically sub-second to a few seconds), zero data loss (the new leader
// was fully caught up, by definition of being in the ISR)
// What if EVERY replica in the ISR is also down (a rare but real multi-broker
// outage)? Kafka faces a genuine choice:

// unclean.leader.election.enable = false (the SAFE default, recommended
// for production): Kafka REFUSES to elect a non-ISR (out-of-sync,
// "dirty") replica — the partition becomes UNAVAILABLE (offline) until an
// ISR member recovers. Prioritizes CONSISTENCY over availability — you
// will NEVER silently lose already-acknowledged data this way

// unclean.leader.election.enable = true: Kafka WILL elect an out-of-sync
// replica as leader to restore AVAILABILITY — but that replica may be
// missing some of the most recent records, meaning DATA LOSS for anything
// it hadn't yet replicated. Prioritizes AVAILABILITY over consistency

// This is a textbook, concrete instance of the CAP theorem trade-off —
// interviewers love this question specifically because it's a REAL,
// configurable dial, not just abstract theory
// min.insync.replicas works TOGETHER with the producer's acks=all setting
// (fully covered in the Producer Acknowledgments section) to define the
// actual durability floor:

// replication.factor=3, min.insync.replicas=2, producer acks=all:
// -> a write is acknowledged ONLY once at least 2 of the 3 replicas
//    (including the leader) have it — tolerates ONE broker failure with
//    ZERO data loss and ZERO availability loss
// -> if the ISR shrinks below min.insync.replicas (e.g. 2 brokers down at
//    once), the PRODUCER gets a NotEnoughReplicasException — Kafka refuses
//    the write entirely rather than accept it with insufficient durability

// This is THE standard production configuration combo for "don't lose data" —
// replication.factor=3 + min.insync.replicas=2 + acks=all
💡 Interview one-liner: "Only ISR members are eligible for leader election, which is exactly why acknowledged data survives a leader failure by default. The unclean leader election flag is a direct, explicit CAP-theorem trade-off — I'd leave it disabled in production for any data where correctness matters more than a few seconds of availability during a rare multi-broker outage."
Cluster Coordination

Controller, ZooKeeper vs KRaft

Someone has to track "which broker leads which partition," detect failures, and coordinate metadata changes across the whole cluster — that's the Controller's job, and HOW it's implemented has fundamentally changed in modern Kafka.

ZooKeeper mode (legacy)KRaft mode (modern, Kafka 3.3+ default, 4.0+ only option)
Metadata storageAn EXTERNAL ZooKeeper ensemble — a separate distributed system you deploy and operate alongside KafkaAn INTERNAL Kafka topic (the metadata log) — no external system at all
Controller electionVia ZooKeeper — brokers race to create an ephemeral znode, the winner is ControllerA dedicated quorum of Controller nodes elects an active controller via the RAFT consensus protocol, same family of algorithm as etcd/Consul
Operational complexityHigher — two distributed systems to run, monitor, and keep in version lockstepLower — one system, Kafka manages its own metadata natively
Failover speedSlower — ZooKeeper session timeouts, broker re-registration overheadFaster — Raft-based leader election is significantly quicker
Scalability ceilingZooKeeper itself becomes a bottleneck at very large partition counts (hundreds of thousands+)Designed to scale to millions of partitions
What the Controller actually DOES, regardless of which mode 
// - Watches for broker failures (via heartbeats/session mechanisms)
// - Elects a new leader (from the ISR) for every partition that loses its leader
// - Propagates metadata changes (new topics, partition reassignments,
//   config changes) to every broker in the cluster
// - Handles administrative operations: topic creation/deletion, partition
//   reassignment during rebalancing of the CLUSTER itself (not to be
//   confused with CONSUMER GROUP rebalancing, a completely different concept covered later)

// There is exactly ONE active controller in the cluster at any time —
// this is itself a leader-election problem, solved via ZooKeeper OR
// KRaft's Raft quorum, depending on mode
💡 Interview one-liner: "KRaft removes the ZooKeeper dependency by having Kafka manage its own cluster metadata internally, as a replicated log, using the Raft consensus protocol among a dedicated set of controller nodes. It's simpler operationally — one system instead of two — and scales further. As of Kafka 4.0, KRaft is the only supported mode; ZooKeeper support has been fully removed." Being current on this transition (a genuinely recent, actively-discussed architectural shift) is a strong signal you follow the ecosystem, not just a textbook from several years ago.
What's Actually on Disk

Log Segments, Retention & Compaction

A partition isn't one giant file — understanding the segment structure explains both HOW Kafka achieves its legendary throughput and HOW old data actually gets cleaned up.

Segments — why a partition is split into files
  • A partition's log is broken into SEGMENT files (default rolls over at 1GB, or a time interval via segment.ms) — only the ACTIVE (newest) segment is open for writes at any time
  • Retention and compaction operate on WHOLE segments, not individual records — Kafka deletes/compacts an entire closed segment file at once, which is far cheaper than record-by-record deletion
  • Each segment has an accompanying INDEX file, mapping offsets to physical byte positions — this is what makes seeking to an arbitrary offset fast (binary search on the index, not a linear scan of the log)
Zero-Copy — the throughput secret
  • When serving a consumer FETCH request, Kafka uses the OS's sendfile() system call to transfer data DIRECTLY from the page cache to the network socket — bypassing the JVM heap entirely
  • Normally, data would copy: disk → OS buffer → application buffer (JVM heap) → socket buffer — Kafka's zero-copy path skips the application-buffer hop completely
  • This is a genuinely cited, real reason Kafka achieves such high throughput despite being written in Java/Scala — worth naming specifically if asked "why is Kafka so fast"
Retention: cleanup.policy=delete
Compaction: cleanup.policy=compact
Combining both: compact,delete
// The DEFAULT policy — deletes whole segments once they age out or the
// partition exceeds a size limit, regardless of key or content

retention.ms=604800000       // 7 days (default) — delete segments older than this
retention.bytes=-1           // -1 = unlimited by size; set a value to cap partition size instead/also

// Used for: event streams, logs, metrics — anything where you only care
// about a recent WINDOW of history, and old data genuinely has no further value
// COMPACTION retains only the LATEST record for each KEY, regardless of age —
// a background "log cleaner" thread periodically rewrites segments,
// dropping older records whose key has since been superseded

// Before compaction (key: value pairs, in write order):
// [user1: {name: "Alice", city: "NYC"}]
// [user2: {name: "Bob"}]
// [user1: {name: "Alice", city: "SF"}]   ← a newer update for user1
// [user1: {name: "Alice", city: "SF", verified: true}] ← even newer

// After compaction:
// [user2: {name: "Bob"}]
// [user1: {name: "Alice", city: "SF", verified: true}] ← only the LATEST survives

// USE CASE: maintaining a changelog of "current state" per key — exactly
// what Kafka Streams uses internally for its state store changelogs, and
// what CDC (Change Data Capture) pipelines commonly rely on

// TOMBSTONES: a record with a NULL value for a key signals "delete this
// key entirely" — the tombstone itself is eventually removed too, after a
// configurable delay (delete.retention.ms), giving consumers time to see it first
// cleanup.policy=compact,delete — BOTH policies applied together:
// compaction keeps the latest value per key, AND time/size-based deletion
// still removes segments past the retention window regardless

// Useful when you want "latest state per key" behavior, but ALSO have a
// hard compliance/cost requirement to never keep ANY data past N days,
// even a compacted "latest" record
💡 Interview one-liner: "Deletion is coarse — time or size based, whole segments at once. Compaction is fine-grained — per-key, always keeping the latest value regardless of age, which is exactly the semantic you want for a changelog or 'current state' topic rather than a pure event stream." Also worth having ready: "Kafka's throughput comes partly from sequential disk I/O and partly from zero-copy transfer via sendfile(), skipping the JVM heap entirely when serving fetch requests."
What send() Actually Does

Producer Internals

producer.send() looks like a simple synchronous call — it's actually asynchronous, batched, and buffered under the hood. Understanding this pipeline explains most producer tuning knobs.

The send() pipeline, step by step 
producer.send(record)
   │
   ▼
1. SERIALIZE key/value (via configured Serializer — String, Avro, JSON, etc.)
   │
   ▼
2. PARTITIONER decides which partition (key hash, sticky default, or custom — see Partitioning Strategy)
   │
   ▼
3. Record appended to an in-memory BATCH for that specific topic-partition
   (accumulating in the "RecordAccumulator") — send() returns IMMEDIATELY
   here with a Future, NOT after the record actually reaches the broker
   │
   ▼
4. A background I/O thread (the "Sender") flushes a batch to the broker when:
   EITHER the batch reaches batch.size bytes, OR linger.ms elapses since
   the first record was added to it — whichever happens FIRST
   │
   ▼
5. Broker (partition leader) appends to its log, replicates per acks setting
   (see next section), and responds — Future completes, triggering any
   registered callback
The key batching knobs
  • batch.size (default 16KB) — max bytes per batch PER PARTITION before it's sent — bigger batches = better throughput/compression, at the cost of more memory and slightly higher per-record latency
  • linger.ms (default 0) — how long to WAIT for a batch to fill before sending anyway — setting this above 0 (e.g. 5-20ms) deliberately trades a small latency cost for meaningfully better throughput via larger batches
  • compression.type (none/gzip/snappy/lz4/zstd) — compresses whole BATCHES (not individual records) — a real, often-overlooked throughput and cost lever, since it directly reduces both network and disk I/O
send() is asynchronous — a real footgun
  • send() returns a Future<RecordMetadata> immediately — it does NOT mean the record safely reached Kafka
  • Calling .get() on that Future BLOCKS until the broker actually responds — turns it into a synchronous call, useful for correctness-critical paths, at a real throughput cost if overused
  • The idiomatic pattern for high-throughput async code is a CALLBACK, not blocking .get() on every single send
The correct async pattern — callback
The anti-pattern — synchronous send in a loop
producer.send(new ProducerRecord<>("orders", orderId, orderEvent), (metadata, exception) -> {
    if (exception != null) {
        log.error("Failed to send order event: {}", orderId, exception); // handle/alert/retry logic here
    } else {
        log.debug("Sent to partition {} offset {}", metadata.partition(), metadata.offset());
    }
});
// This lets the Sender thread keep batching and sending at full throughput —
// the callback fires asynchronously once the broker actually responds
// ANTI-PATTERN: defeats batching almost entirely — each send() effectively
// becomes synchronous, one round-trip at a time
for (OrderEvent event : events) {
    producer.send(new ProducerRecord<>("orders", event.getOrderId(), event)).get(); // blocks EVERY iteration
}
// Throughput here is bounded by network round-trip latency, not by batch
// efficiency — often 10-100x slower than the callback pattern for bulk sends
💡 Interview one-liner: "send() is async by default — it accumulates records into per-partition batches and a background Sender thread flushes them based on batch.size or linger.ms, whichever hits first. I'd use a callback for high-throughput paths and reserve blocking .get() for cases where I genuinely need to confirm a write before proceeding, like right before returning a success response to a client."
How Sure Do You Need to Be?

Acknowledgments & Durability

The acks setting is the single most important producer durability knob — and a virtually guaranteed interview question, often phrased as "what acks setting would you use for X."

Choosing acks by use case
Retries — and the ordering danger they introduce
// acks=0 — metrics/telemetry pings where occasional loss is a total non-issue,
// and shaving every microsecond of latency actually matters

// acks=1 — a reasonable middle ground for moderately important data where
// losing a handful of records during a rare leader crash is tolerable

// acks=all — financial transactions, order events, anything where losing
// even one record is a genuine business problem. Standard production combo:
producerProps.put("acks", "all");
producerProps.put("retries", Integer.MAX_VALUE);  // retry indefinitely on retriable errors (bounded by delivery.timeout.ms)
producerProps.put("enable.idempotence", true); // see the next section — required to make retries SAFE
// A naive retry, WITHOUT idempotence, can silently REORDER records:

// Producer sends batch A, then batch B (both to the same partition)
// Batch A's response is delayed/lost -> producer retries batch A
// Meanwhile batch B already succeeded and was written FIRST
// Batch A's retry now arrives and is appended AFTER B
// Result: B ends up BEFORE A in the log, even though A was sent first —
// a genuine, historically real Kafka correctness gotcha

// THE FIX: enable.idempotence=true (covered in depth next section) makes
// the broker deduplicate AND preserve ordering across retries automatically —
// as of Kafka 3.0, acks=all and enable.idempotence=true are BOTH the
// default producer configuration, precisely because this combination is
// considered the correct, safe baseline for nearly all production use
🚫 Interview trap to watch for: before Kafka 3.0, the DEFAULT was acks=1 and idempotence OFF — meaning plenty of legacy production systems and older interview prep material assume weaker defaults than modern Kafka actually ships with. Know both: what the CURRENT defaults are (acks=all + idempotence on, since 3.0), and what to explicitly set if you're on, or being asked about, an older cluster.
Exactly-Once, Part 1

Idempotent Producers

Idempotence solves EXACTLY ONE problem — duplicate writes caused by producer RETRIES — and it's the foundational building block that transactions (next section) are built on top of.

How it works — PID + sequence numbers
  • When enable.idempotence=true, the broker assigns the producer a unique Producer ID (PID) at session start
  • Every batch sent to a specific topic-partition gets a monotonically increasing SEQUENCE NUMBER, tracked per (PID, partition)
  • If the broker receives a batch with a sequence number it has ALREADY seen and appended (i.e., a retried duplicate), it silently DISCARDS the duplicate and returns success — without appending it again
  • If a batch arrives out of expected sequence, the broker detects it and rejects it, preserving ORDER as well as preventing duplicates
What it does and does NOT guarantee
  • DOES guarantee: exactly-once, in-order delivery for writes to a SINGLE partition, from a SINGLE producer session — this is genuinely "exactly once" at that narrow scope
  • Does NOT guarantee: atomicity across MULTIPLE partitions or topics (e.g. "write to both the orders topic AND the inventory topic, both or neither") — that needs full TRANSACTIONS, covered next
  • Does NOT protect against APPLICATION-level duplicates — if your app code calls send() twice for what is logically the same business event, idempotence can't detect that; it only dedupes broker-level RETRIES of the exact same batch
Enabling it — as of Kafka 3.0, this is already the default 
producerProps.put("enable.idempotence", true); // forces acks=all and retries>0 automatically as a side effect —
                                          // Kafka enforces the settings idempotence actually needs internally

// The overhead is genuinely tiny — just a few extra numeric fields per
// batch (PID + sequence number) — this is a very commonly cited, close-to-free
// correctness upgrade, which is exactly why it's the modern default
💡 Interview one-liner: "Idempotent producers solve duplicate writes from retries by having the broker deduplicate based on a producer ID and per-partition sequence number — it's exactly-once, but scoped to a single partition and a single producer session. For atomicity across multiple partitions, or a true consume-process-produce exactly-once pipeline, you need transactions, which are built on top of this same idempotence mechanism."
Exactly-Once, Part 2

Kafka Transactions

Transactions extend idempotence to guarantee ATOMICITY across multiple partitions/topics, AND — critically for stream processing — let a consume-process-produce pipeline commit its input offset and output records as one atomic unit.

A basic multi-partition transaction
transactional.id — identity across restarts
Consume-Process-Produce EOS pattern
Consumer isolation.level — read_committed
producer.initTransactions(); // once, at startup — registers with the transaction coordinator

try {
    producer.beginTransaction();

    producer.send(new ProducerRecord<>("orders", orderId, orderEvent));
    producer.send(new ProducerRecord<>("inventory", sku, inventoryUpdate));

    producer.commitTransaction(); // BOTH records become visible to read_committed consumers atomically —
                                  // either BOTH show up, or (on abort/failure) NEITHER does, ever
} catch (KafkaException e) {
    producer.abortTransaction(); // rolls back — downstream read_committed consumers never see either record
}
// transactional.id uniquely identifies a LOGICAL producer across restarts —
// critical for FENCING zombie producer instances (e.g. an old app instance
// that hung and is still alive, unaware a newer instance has taken over)

producerProps.put("transactional.id", "order-service-1");

// When a producer with the SAME transactional.id reconnects (e.g. after a
// restart), it gets the SAME PID but an INCREMENTED epoch. Any OLDER
// instance still trying to write with the previous (lower) epoch is
// immediately FENCED OFF by the broker — its writes are rejected — this
// is what prevents a "zombie" old instance from corrupting data after a
// new instance has already taken over the same logical role
// The classic "read from topic A, transform, write to topic B" pattern —
// wants the CONSUMED OFFSET and the PRODUCED RECORD committed atomically,
// so a crash mid-processing never causes a message to be "lost" (offset
// committed but output never written) or "duplicated" (output written but
// offset never committed, so it's reprocessed on restart)

producer.initTransactions();
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    if (records.isEmpty()) continue;

    producer.beginTransaction();
    try {
        for (ConsumerRecord<String, String> record : records) {
            String transformed = transform(record.value());
            producer.send(new ProducerRecord<>("output-topic", record.key(), transformed));
        }
        // send the CONSUMED offsets to the transaction too — this is the key API
        // that makes "commit offset + commit output" ONE atomic operation
        producer.sendOffsetsToTransaction(
            currentOffsets(records), consumer.groupMetadata());
        producer.commitTransaction();
    } catch (Exception e) {
        producer.abortTransaction(); // neither the output NOR the offset commit takes effect
    }
} // This exact pattern is what Kafka Streams uses internally under the hood
  // for its own exactly-once processing guarantee
// Transactions alone don't help unless CONSUMERS opt into respecting them:

consumerProps.put("isolation.level", "read_committed");
// read_committed: the consumer NEVER sees records from an aborted
// transaction, and only sees committed records once the transaction
// actually commits (records are buffered/hidden by the broker until then)

// read_uncommitted (the DEFAULT!): consumer sees ALL records immediately,
// including ones from transactions that later get ABORTED — a genuinely
// easy-to-miss gotcha: producing transactionally does NOTHING for a
// consumer that hasn't explicitly opted into read_committed
🚫 The #1 transactions interview trap: forgetting that isolation.level=read_committed must be set EXPLICITLY on the consumer — it defaults to read_uncommitted. A producer can be doing everything correctly with transactions, and a consumer will still see uncommitted, potentially-aborted data if this isn't set. Also worth having ready: "exactly-once end-to-end in Kafka specifically means Kafka-to-Kafka — if the pipeline writes to an EXTERNAL system (a database, an API call) inside that transaction, Kafka's exactly-once guarantee doesn't extend there; you need idempotent writes or your own deduplication logic on that external side."
Parallel Consumption

Consumer Groups & Partition Assignment

A Consumer Group is how Kafka achieves parallel, load-balanced consumption while still letting multiple independent applications read the same topic separately.

The core rule
  • Each partition is assigned to AT MOST ONE consumer WITHIN a given group at a time — this is what prevents the same record from being processed twice by the same logical application
  • DIFFERENT consumer groups are completely independent — each group tracks its OWN offsets and can read the same topic at its own pace, from the beginning if needed
  • If consumers > partitions, the extras sit COMPLETELY IDLE — a partition can't be split across two consumers in the same group
Partition Assignment Strategies
  • Range — assigns contiguous partition ranges per topic; can lead to UNEVEN load if a consumer ends up with more partitions across several topics
  • RoundRobin — spreads partitions across ALL consumers as evenly as possible, across ALL subscribed topics together
  • Sticky / CooperativeSticky — aims to minimize the number of partition MOVEMENTS during a rebalance (keep prior assignments where possible), while still balancing load — the modern recommended default, covered fully next section

The Most-Tested Consumer Topic

Rebalancing Protocols

When group membership changes (a consumer joins, leaves, or is considered dead), partitions must be REASSIGNED — this is a "rebalance," and the mechanics of HOW it happens (and how disruptive it is) is one of the most consistently asked deep-dive topics in senior Kafka interviews.

What triggers a rebalance
  • A new consumer JOINS the group
  • A consumer LEAVES gracefully (clean shutdown)
  • A consumer is considered DEAD — no heartbeat within session.timeout.ms, or no poll() call within max.poll.interval.ms (the latter usually means your processing is taking too long — a very common real-world cause)
  • The topic's partition count changes (an admin adds partitions)
The Group Coordinator
  • One broker acts as the Group Coordinator for a given consumer group — handles heartbeats, membership, and triggers/orchestrates rebalances
  • One consumer in the group is elected the "group LEADER" (a client-side role, distinct from a partition leader) — it computes the actual new assignment using the configured assignor strategy, and sends it back to the coordinator to distribute
Eager Rebalancing (legacy default)Cooperative Sticky (modern, recommended)
MechanismSTOP-THE-WORLD: every consumer revokes ALL its partitions, THEN a full new assignment is computed and handed outINCREMENTAL: consumers keep any partition they're still assigned; only the specific partitions that actually need to MOVE are revoked and reassigned
DisruptionALL consumption pauses across the ENTIRE group during every rebalance, even for partitions whose assignment doesn't actually changeOnly the moving partitions pause — everything else keeps processing uninterrupted
Rebalance roundsOne roundMay take 2 rounds (revoke only what must move, then reassign) — more protocol complexity, but far less disruption
Configpartition.assignment.strategy=RangeAssignor (or RoundRobin)partition.assignment.strategy=CooperativeStickyAssignor
Static Membership — avoiding rebalances on restart
max.poll.interval.ms — the silent rebalance trigger

I'd default to CooperativeStickyAssignor in any production system, and use static group membership to avoid unnecessary rebalances entirely during routine rolling restarts."
Remembering Where You Left Off

Offset Management

How and WHEN a consumer commits its offset is the single biggest lever controlling delivery semantics — the difference between at-least-once, at-most-once, and building toward exactly-once all comes down to commit timing relative to processing.

Where offsets actually live
  • Committed offsets are stored in an internal Kafka topic, __consumer_offsets — itself a compacted topic, keyed by (group, topic, partition), so it only ever keeps the LATEST committed offset per key
  • This means offset storage is just as durable/replicated as any other Kafka data — no separate external system needed (a real architectural improvement over Kafka's much older ZooKeeper-based offset storage)
Auto-commit vs Manual commit
  • enable.auto.commit=true (default) — offsets committed automatically in the background every auto.commit.interval.ms (default 5s), regardless of whether processing actually finished — simple, but a real correctness risk
  • Manual commit (enable.auto.commit=false) — YOUR code decides exactly when to commit, typically AFTER successfully processing a batch — the standard production pattern for anything correctness-sensitive
Why auto-commit is risky
commitSync() vs commitAsync()
Resetting position manually — seek()

// whether your processing actually succeeded:

    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        processOrder(record.value()); // if this THROWS partway through the batch, but the
    }                                 // 5-second auto-commit timer already fired for an EARLIER
}                                     // offset in this poll — that record is now considered "done"
                                      // even though processing it actually failed -> SILENT DATA LOSS
                                      // from the application's point of view
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        processOrder(record.value()); // process FIRST
    }

    try {
        consumer.commitSync(); // BLOCKS until the broker confirms — safest, but adds latency per batch.
    } catch (CommitFailedException e) {  // The standard choice right before shutdown, or wherever correctness
        log.error("Commit failed", e);       // matters more than shaving off latency
    }

    // commitAsync() — non-blocking, higher throughput, but a failed async
    // commit is easy to silently miss without a callback:
    consumer.commitAsync((offsets, exception) -> {
        if (exception != null) log.error("Async commit failed for {}", offsets, exception);
    });
    // Common production pattern: commitAsync() in the main loop for
    // throughput, with a FINAL commitSync() in a finally block on shutdown to
    // guarantee the last offset is definitely persisted before exiting
// Manually rewinding/fast-forwarding a consumer's position — the actual
// mechanism behind "replay" and behind recovering from a bad deployment

consumer.seekToBeginning(consumer.assignment()); // reprocess EVERYTHING from the start — e.g. rebuilding a cache

consumer.seek(new TopicPartition("orders", 0), 15000L); // jump to a SPECIFIC offset — e.g. skip a known-bad record range

// Time-based seeking — "give me the offset as of this timestamp," genuinely useful
// for "replay everything since the incident started at 14:32 yesterday":

💡 Interview one-liner: "I'd disable auto-commit for anything correctness-sensitive and commit manually AFTER processing succeeds — commitAsync in the steady-state loop for throughput, with a final commitSync on shutdown to guarantee the last offset lands. Committing BEFORE processing risks silent message loss on failure; committing only after is what gets you at-least-once delivery, which combined with idempotent processing logic is usually the practical target."
What poll() Actually Does

Consumer Internals — The Poll Loop

Kafka consumers are fundamentally PULL-based — the client repeatedly asks the broker "give me more records," rather than the broker pushing data at it. This single design choice explains several consumer configuration knobs at once.

ConfigControls
fetch.min.bytesBroker won't respond to a fetch request until at least this much data is available (or fetch.max.wait.ms elapses) — bigger values improve throughput/batching at a latency cost
fetch.max.wait.msMax time the broker waits to accumulate fetch.min.bytes before responding anyway — caps the latency trade-off above
max.poll.recordsMax records returned by a SINGLE poll() call — smaller values mean more frequent poll() calls, which helps avoid the max.poll.interval.ms timeout for slow per-record processing
session.timeout.msHow long the broker waits without a heartbeat before considering the consumer dead
heartbeat.interval.msHow often the client sends heartbeats — typically 1/3 of session.timeout.ms
max.poll.interval.msMax time allowed BETWEEN poll() calls before the consumer is considered stuck and removed from the group (separate from the heartbeat mechanism, sent on a background thread since Kafka 0.10.1+)
Why heartbeats run on a SEPARATE thread from poll() 
// Pre-0.10.1, heartbeats were sent only as a SIDE EFFECT of calling poll() —
// meaning slow message PROCESSING (which happens between poll() calls in
// a typical loop) could starve heartbeats and falsely trigger a rebalance

// Modern Kafka runs heartbeats on a DEDICATED background thread, decoupled
// from the application's processing loop — this is exactly why there are
// now TWO separate liveness signals with different meanings:
// - session.timeout.ms / heartbeat.interval.ms: "is the consumer PROCESS still alive"
// - max.poll.interval.ms: "is the consumer's MAIN LOOP still making progress"
// A consumer can be heartbeating fine (process alive) while still being
// kicked out for not calling poll() often enough (stuck processing) —
// these are genuinely independent failure modes, a real distinction interviewers probe
💡 Interview one-liner: "Kafka consumers pull, they're not pushed to — poll() is the heartbeat of the whole consumption loop. There are actually two independent liveness checks: heartbeats (is the process alive) on a background thread, and max.poll.interval.ms (is the main loop making progress) tied to actually calling poll() — a consumer stuck in a slow processing loop can fail the second even while passing the first, which is one of the most common real-world causes of an unexpected rebalance."

At-Most-Once, At-Least-Once & Exactly-Once — End-to-End

This section is the synthesis of everything covered so far — acks, idempotence, transactions, and offset commit timing all combine to determine which delivery guarantee your pipeline actually has, end to end.

// The overwhelming majority of real production systems target AT-LEAST-ONCE,
// not full exactly-once — it's simpler, faster, and "good enough" IF your
// downstream processing is made idempotent (next tab) to safely absorb duplicates

while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        processOrder(record.value()); // process FIRST
    }
    consumer.commitSync();      // commit AFTER — a crash here means reprocessing on restart, by design
}
// The genuinely practical answer to "how do you achieve exactly-once
// processing" in most REAL systems isn't Kafka transactions at all — it's
// making the CONSUMER'S SIDE EFFECT idempotent, so at-least-once + a
// duplicate-safe operation together BEHAVE like exactly-once

// Pattern 1: a database UPSERT/UNIQUE CONSTRAINT keyed by a business ID
void processOrder(OrderEvent event) {
    // INSERT ... ON CONFLICT (order_id) DO NOTHING — reprocessing the same
    // orderId a second time is a harmless no-op, not a duplicate charge
    orderRepository.upsert(event);
}

// Pattern 2: an explicit "processed events" dedup table/cache, checked
// before applying any side effect — necessary when the operation ISN'T
// naturally idempotent (e.g. "send an email" has no natural upsert)
void processOrder(OrderEvent event) {
    if (processedEventStore.alreadyProcessed(event.getEventId())) return; // skip — already handled
    sendConfirmationEmail(event);
    processedEventStore.markProcessed(event.getEventId());
}
💡 Interview one-liner — this is a genuinely great answer to close with on this topic: "In practice, I lean on at-least-once delivery plus idempotent processing on the consumer side — an upsert keyed by business ID, or an explicit dedup check — rather than reaching for full Kafka transactions everywhere. Transactions are the right tool for atomic multi-topic writes or Streams-style consume-transform-produce pipelines specifically, but for a typical 'consume and update a database' service, idempotent consumption is simpler, faster, and just as correct."

Error Handling, Retry & Dead Letter Topics

A message that repeatedly fails processing shouldn't block the whole partition forever, or be silently dropped — Spring Kafka's error handling machinery, built on DefaultErrorHandler, is a very commonly probed production-readiness topic.

DefaultErrorHandler with retry backoff

@Bean
public DefaultErrorHandler errorHandler() {
    BackOff backOff = new ExponentialBackOff(1000L, 2.0); // start at 1s, double each retry
    ((ExponentialBackOff) backOff).setMaxInterval(30000L);       // cap at 30s between retries
    DefaultErrorHandler handler = new DefaultErrorHandler(backOff);
    return handler;
}
// On an exception, Spring Kafka automatically SEEKS BACK to the failed
// record's offset and retries it after the backoff delay — the consumer
// effectively pauses/retries that specific record, without you writing any
// manual seek()/retry loop code yourself
// After exhausting retries, route the poison record to a DEAD LETTER TOPIC
// instead of endlessly retrying or silently dropping it — lets you inspect,
// alert, and manually reprocess later without blocking the main partition

@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(template,
        (record, ex) -> new TopicPartition(record.topic() + ".DLT", record.partition()));
        // convention: "orders" -> "orders.DLT", same partition count preserved

    DefaultErrorHandler handler = new DefaultErrorHandler(
        recoverer,
        new FixedBackOff(1000L, 3) // retry 3 times, 1s apart, THEN send to DLT
    );
    return handler;
}

// A separate listener/dashboard on the DLT lets ops/on-call engineers
// inspect failed messages, fix the root cause, and republish manually —
// this exact pattern is what real production Kafka consumers are expected to have
// Not every failure is worth retrying — a malformed JSON payload will
// NEVER succeed no matter how many times you retry it, so retrying wastes
// time before the inevitable DLT trip. Classify exceptions explicitly:

@Bean
public DefaultErrorHandler errorHandler(DeadLetterPublishingRecoverer recoverer) {
    DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 3));

    handler.addNotRetryableExceptions(
        DeserializationException.class,   // malformed message — retrying changes nothing
        IllegalArgumentException.class // a genuine data/business validation failure
    ); // these skip straight to the DLT recoverer, no wasted retry attempts

    return handler;
}
// TRANSIENT failures (a downstream service timeout, a temporary DB
// connection blip) are exactly what SHOULD be retried — the classification
// itself is the real design decision interviewers want you to reason about
💡 Interview one-liner: "I'd configure a DefaultErrorHandler with exponential backoff for transient failures, and explicitly classify permanent failures — bad deserialization, validation errors — as non-retryable so they skip straight to a Dead Letter Topic instead of wasting retry attempts. The DLT gets its own monitoring and alerting, so a poison message becomes a visible, actionable incident instead of either blocking the partition forever or silently vanishing."

Spring Kafka Transactions

Spring wraps the raw transactional producer API (from the Kafka Transactions section) in its familiar @Transactional declarative style — and, notably, can even span a Kafka transaction and a DATABASE transaction together via ChainedKafkaTransactionManager.

Consume-transform-produce, Spring-style
Kafka + DB transaction together
# application.yml
spring.kafka.producer.transaction-id-prefix: order-service-tx-

@Service
public class OrderService {

    private final KafkaTemplate<String, Object> kafkaTemplate;

    @Transactional("kafkaTransactionManager")
    public void placeOrder(Order order) {
        kafkaTemplate.send("orders", order.getId(), order);
        kafkaTemplate.send("inventory", order.getSku(), new InventoryUpdate(order));

        // an exception anywhere in this method rolls BOTH back, exactly like
        // the manual beginTransaction()/commitTransaction() pattern shown earlier
    }
}
// Spring's version of the raw consume-process-produce EOS pattern —
// listener container + KafkaTemplate share the SAME transaction automatically
// when both are configured with a transaction manager

@KafkaListener(topics = "raw-events", containerFactory = "transactionalContainerFactory")
@Transactional("kafkaTransactionManager")
public void transform(RawEvent event) {
    EnrichedEvent enriched = enrich(event);
    kafkaTemplate.send("enriched-events", enriched.getId(), enriched);
    // the CONSUMED offset and the PRODUCED record commit together as one unit —
    // Spring handles the sendOffsetsToTransaction() call internally, so you
    // never write it by hand the way the raw API requires
}
// A genuinely advanced, senior-level scenario: writing to a database AND
// publishing a Kafka event ATOMICALLY — the classic "dual write" problem

@Bean
public ChainedKafkaTransactionManager<?, ?> chainedTransactionManager(
        KafkaTransactionManager kafkaTM, JpaTransactionManager jpaTM) {
    return new ChainedKafkaTransactionManager<>(kafkaTM, jpaTM);
}

public void placeOrder(Order order) {

    kafkaTemplate.send("orders", order.getId(), order); // Kafka write

// effort chaining of two SEPARATE transaction managers. A failure between
// the two commits is still theoretically possible (a narrow window). Many
// senior engineers instead prefer the TRANSACTIONAL OUTBOX pattern — write
// to the DB and an "outbox" table in ONE local DB transaction, then a
// separate process (often Kafka Connect / Debezium via CDC) reliably
// publishes from the outbox to Kafka — genuinely worth naming as the more
// robust alternative if this topic comes up
💡 Interview one-liner: "For atomic Kafka-only operations, @Transactional with a KafkaTransactionManager works well. For the dual-write problem — DB plus Kafka together — ChainedKafkaTransactionManager exists but isn't true 2PC, so for anything genuinely critical I'd lean toward the transactional outbox pattern: write to the database and an outbox table in one local transaction, then let a CDC process like Debezium reliably publish to Kafka from there." Naming the outbox pattern specifically is a strong senior-level signal.
Stream Processing on Kafka

Kafka Streams Fundamentals

A client library (not a separate cluster to deploy — it runs INSIDE your own application) for building stream-processing applications directly on top of Kafka topics. Worth knowing conceptually even if you've mostly used plain producers/consumers.

Core abstractions
  • KStream — an unbounded stream of independent events (a record stream — think "INSERT-only")
  • KTable — a changelog / current-state view, keyed, where a new record UPDATES the existing value for that key (think "UPSERT," backed by log compaction under the hood)
  • State Stores — local, embedded storage (RocksDB by default) for stateful operations like aggregations and joins — backed by a compacted CHANGELOG TOPIC in Kafka for fault-tolerant recovery if the app instance dies and restarts elsewhere
Why it matters even without hands-on use
  • Kafka Streams' exactly-once guarantee is built directly on the transactions mechanism from earlier — it's the "worked example" of that pattern at scale
  • KStream-KTable joins are a genuinely common real interview whiteboard question — "how would you enrich an order event stream with current customer data"
  • It's a legitimate alternative to spinning up Flink/Spark Streaming for many use cases — worth knowing WHEN to reach for it
A stream-table join — the classic "enrich an event" pattern 
StreamsBuilder builder = new StreamsBuilder();

KStream<String, OrderEvent> orders = builder.stream("orders");        // unbounded event stream
KTable<String, Customer> customers = builder.table("customers");   // current-state view, keyed by customerId

KStream<String, EnrichedOrder> enriched = orders
    .selectKey((orderId, order) -> order.getCustomerId()) // re-key to join on customerId
    .join(customers, (order, customer) -> new EnrichedOrder(order, customer));

enriched.to("enriched-orders");

// Every incoming order event is joined against the LATEST known state of
// that customer, maintained automatically in a local state store kept up
// to date by consuming the "customers" topic's changelog continuously
💡 Interview one-liner: "Kafka Streams is a library, not a cluster — it runs embedded in your own JVM app, scales by running more instances (each picks up a subset of partitions, exactly like a consumer group), and its state stores are backed by changelog topics so state survives a crash and restart. I'd reach for it over a heavier framework like Flink when the processing logic is Kafka-to-Kafka and doesn't need Flink's more advanced windowing/watermarking capabilities."
Contracts Between Producers & Consumers

Schema Registry & Avro

Kafka itself is schema-agnostic — it stores bytes, full stop. Without a shared contract, a producer changing its JSON structure can silently break every downstream consumer. Schema Registry (a Confluent-originated but now widely adopted component) solves exactly this.

Why not just use JSON everywhere
  • JSON has NO enforced schema — a typo'd field name or a silently dropped field is a runtime surprise for every consumer, discovered only in production
  • Avro (or Protobuf) records carry a compact SCHEMA ID instead of embedding a verbose schema in every message — Schema Registry resolves that ID to the full schema, keeping messages small AND type-safe
  • Also meaningfully more compact on the wire than JSON — a real throughput/storage win at scale, on top of the safety benefit
Schema Evolution & Compatibility Modes
  • BACKWARD — a new schema can read data written with the OLD schema (new consumers work with old data) — the most common default
  • FORWARD — old schema can read data written with the NEW schema (old consumers survive a producer upgrade)
  • FULL — both backward AND forward compatible simultaneously — the strictest, safest option for a topic with many independent consumer teams
  • Schema Registry REJECTS a schema change that violates the configured compatibility mode — this is what actually enforces the contract, not just documentation
Spring Boot + Avro producer/consumer configuration 
# application.yml
spring:
  kafka:
    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
      properties:
        schema.registry.url: http://schema-registry:8081
    consumer:
      value-deserializer: io.confluent.kafka.serializers.KafkaAvroDeserializer
      properties:
        schema.registry.url: http://schema-registry:8081
        specific.avro.reader: true  # deserialize into your generated Avro POJO, not a generic record

// Adding a new OPTIONAL field with a default value is a safe, BACKWARD-
// compatible change. Renaming or removing a field, or adding a REQUIRED
// field with no default, breaks compatibility — Schema Registry will
// reject that registration outright under BACKWARD mode
💡 Interview one-liner: "I'd use Avro with Schema Registry over raw JSON for any topic with multiple independent consumer teams — it enforces a real contract at write time, and the compatibility mode (BACKWARD is the sane default) means a schema change that would break an existing consumer gets rejected at registration time, not discovered as a production incident weeks later."
Integration Without Custom Code

Kafka Connect

A framework for moving data INTO and OUT OF Kafka from external systems (databases, S3, Elasticsearch) using pre-built, configuration-only CONNECTORS — no custom producer/consumer code needed for common integration patterns.

Source vs Sink connectors
  • Source Connector — pulls data FROM an external system INTO Kafka (e.g. a database's change stream, via Debezium)
  • Sink Connector — pushes data FROM Kafka OUT TO an external system (e.g. writing every event to Elasticsearch for search indexing)
  • Runs as its own cluster of "Connect workers" — a genuinely separate deployment from your application code
Debezium & Change Data Capture (CDC) — a very real, common pattern
  • Debezium is a source connector that reads a database's TRANSACTION LOG (e.g. MySQL's binlog, Postgres's WAL) directly, streaming every insert/update/delete as a Kafka event — without adding any load to the actual application queries
  • This is exactly the mechanism a real transactional-outbox implementation (mentioned in the Spring Kafka Transactions section) typically uses under the hood — reliably publishing DB changes to Kafka without a fragile dual-write
A Debezium source connector config, conceptually 
{

    "connector.class": "io.debezium.connector.mysql.MySqlConnector",

💡 Interview one-liner: "For getting data out of a legacy database into an event-driven pipeline without touching application code, I'd reach for Kafka Connect with a Debezium CDC source connector — it reads the database's transaction log directly, so there's no dual-write risk and no added load on the actual application queries. It's also the standard, production-proven way to implement a transactional outbox reliably."
Locking It Down

Security — SSL, SASL & ACLs

Kafka ships with NO security enabled by default — anyone who can reach the broker port can produce/consume anything. Production clusters layer on encryption, authentication, and authorization explicitly.

EncryptionSSL/TLS between clients and brokers, and broker-to-broker"Can traffic be read/tampered with in transit?"

A concrete ACL example
Spring Boot client security config
# Grant the "order-service" principal permission to WRITE to the "orders" topic only
kafka-acls.sh --add --allow-principal User:order-service \
    --operation Write --topic orders

# Grant "order-processing-service" READ access to "orders", scoped to its own consumer group
kafka-acls.sh --add --allow-principal User:order-processing-service \
    --operation Read --topic orders --group order-processing-service

// This is the DIRECT Kafka analogue of the least-privilege principle from
// IAM policies (see the AWS Bible) — grant only the specific topic +
// operation combination a service genuinely needs, nothing broader
# application.yml — SASL_SSL with SCRAM, a common production combination
spring:
  kafka:
    bootstrap-servers: broker1:9093
    security:
      protocol: SASL_SSL
    properties:
      sasl.mechanism: SCRAM-SHA-512
      sasl.jaas.config: >
        org.apache.kafka.common.security.scram.ScramLoginModule required
        username="order-service"
        password="${KAFKA_PASSWORD}";  # injected via Secrets Manager/Vault, never hardcoded —
      ssl.truststore.location: /etc/kafka/secrets/truststore.jks  # same principle as the AWS Bible's secrets guidance
💡 Interview one-liner: "Encryption, authentication, and authorization are three separate layers — TLS answers 'is this connection secure,' SASL answers 'who is this client,' and ACLs answer 'what is this authenticated identity allowed to do.' I'd scope ACLs per-service to the specific topics and operations actually needed — a producer service gets Write on its topic, a consumer service gets Read scoped to its own consumer group — the same least-privilege principle as IAM."

Knowing Something's Wrong Before Users Do

Monitoring & Consumer Lag

Consumer lag — the gap between the latest produced offset and a consumer group's committed offset — is THE single most important operational metric in any Kafka-based system, and "how would you monitor a Kafka pipeline" is an extremely common senior interview question.

Consumer Lag — what it actually means
  • lag = latest offset in the partition − consumer's last committed offset
  • Growing lag means the consumer is falling BEHIND production rate — either it needs more parallelism (more consumers, up to the partition count ceiling), or per-record processing needs to get faster
  • Checked via kafka-consumer-groups.sh --describe --group X, or programmatically/via monitoring tools (Burrow, Prometheus + kafka-lag-exporter, Confluent Control Center)
Key broker-side metrics to watch (JMX)
  • UnderReplicatedPartitions — partitions where a follower has fallen out of the ISR — a leading indicator of broker or network trouble, BEFORE it becomes an outage
  • OfflinePartitionsCount — partitions with NO available leader at all — a genuine, active outage for that data
  • RequestHandlerAvgIdlePercent / NetworkProcessorAvgIdlePercent — low idle % means the broker's thread pools are saturated, a capacity signal
Reading a lag report

💡 Interview one-liner: "I'd alert on consumer lag trending upward over time, not just an absolute threshold — a temporary spike during a traffic burst is normal, but lag that keeps growing means the consumer group is structurally behind. On the broker side, UnderReplicatedPartitions is my earliest warning signal — it usually means trouble before anything is actually down yet, giving time to react before OfflinePartitionsCount turns into a real incident."

// Q: "Broker 2 crashes. Walk me through exactly what happens."

// A: 1. Controller detects the failure (session/heartbeat timeout)
// 2. For every partition where Broker 2 was LEADER, controller elects a
//    new leader from the remaining ISR members
// 3. For partitions where Broker 2 was a FOLLOWER, nothing changes except
//    the ISR shrinks by one until it recovers or is replaced
// 4. Producers/consumers get a stale-metadata error on next request,
//    refresh cluster metadata automatically, and continue against the new leader
// 5. IF replication.factor=3 and min.insync.replicas=2: zero data loss,
//    brief availability blip only for partitions that needed re-election
// 6. IF min.insync.replicas isn't met for some partition (e.g. TWO brokers
//    down simultaneously): producers get NotEnoughReplicasException on
//    acks=all writes to that partition until it recovers
// Q: "A consumer crashes after processing 3 of 10 records in a poll()
// batch, before committing. What happens on restart?"

// A: Depends ENTIRELY on commit strategy (see Offset Management):
// - If offsets commit per-record or per-batch AFTER processing (the
//   correct at-least-once pattern): NONE of the 10 were committed yet —
//   all 10 get reprocessed from the last committed offset on restart.
//   Records 1-3 are now DUPLICATES — this is exactly why idempotent
//   processing (upsert / dedup check) matters, covered in Delivery Semantics
// - If auto-commit happened to fire mid-batch on its timer: some of those
//   10 might be considered "committed" without having been fully
//   processed — genuine silent data loss risk, exactly why manual commit
//   after processing is the safer production pattern
// - Additionally: this crash likely triggers a REBALANCE (session/poll-interval
//   timeout), so the partition may get picked up by a DIFFERENT consumer instance
// Q: "A producer can't reach the partition leader due to a network issue.
// What does it do?"

// A: 1. The send() call's underlying request times out (request.timeout.ms)
// 2. If it's a RETRIABLE error (network timeout counts), the producer
//    retries automatically, up to "retries" attempts, bounded overall by
//    delivery.timeout.ms (the TOTAL time budget across all retries)
// 3. Before retrying, the producer refreshes its metadata — if the
//    partition leader actually CHANGED during the outage (e.g. failover
//    happened), it automatically retries against the NEW leader
// 4. If delivery.timeout.ms is exceeded entirely, the send() Future/
//    callback completes with a TimeoutException — the APPLICATION must
//    decide what to do (log, alert, dead-letter the failed record locally,
//    or propagate the failure to whatever triggered the send in the first place)
// Q: "One consumer instance in a group of 5 is processing much slower than
// the others — its partitions' lag keeps growing while the rest are fine.
// How would you diagnose and fix this?"

// A: DIAGNOSE:
// - Check if it's a HOT PARTITION issue — does that consumer happen to own
//   a partition with disproportionate traffic (skewed key distribution)?
// - Check that instance's OWN resource metrics — CPU throttling, GC pauses
//   (a long GC pause can look identical to "slow processing" from the
//   outside, and can even approach max.poll.interval.ms and trigger a rebalance)
// - Check for a downstream dependency that specific instance calls being
//   slow (e.g. hitting a different DB replica or AZ with worse latency)

// FIX options: rebalance partition assignment (sometimes just restarting
// triggers a fresh, more even assignment), fix the underlying key skew
// (see Partitioning Strategy's hot-partition fixes), scale that consumer's
// resources, or split slow per-record work onto a separate thread pool so
// the poll loop itself stays fast and lag catches up
// Q: "A producer team deploys a change that breaks deserialization for
// every downstream consumer. How would this have been PREVENTED, and how
// do you recover NOW that it's already happened?"

// A: PREVENTION: Schema Registry with an enforced compatibility mode
// (BACKWARD, typically) would have REJECTED this schema registration
// before it could ever be produced — this is precisely why Schema
// Registry exists, and naming it here is the strongest possible answer

// RECOVERY, given it already happened:
// 1. Classify DeserializationException as non-retryable in the error
//    handler (see Spring Kafka Error Handling) so poison messages route
//    to the DLT instead of blocking the partition indefinitely
// 2. Roll back the producer's bad deploy
// 3. Once fixed, reprocess the DLT messages (or seek() consumers back to
//    before the bad deploy's offset, per the Offset Management section's
//    seek()/offsetsForTimes() tools, if replaying from source is preferable
//    to replaying from the DLT)

FAANG Rapid Fire

FAANG Rapid-Fire Q&A

Based on current interview patterns at top product companies for backend Java + Kafka roles, these are the questions that come up again and again — organized to reinforce the reasoning chains from earlier sections, not just isolated facts.

Short-answer conceptual questions

❓ Why is Kafka so much faster than a traditional message broker?

  • Sequential disk I/O (append-only log) instead of random-access indexed storage
  • Zero-copy transfer (sendfile()) straight from page cache to network socket, bypassing the JVM heap
  • Batching at every layer — producer batches, broker writes batches, consumer fetches batches

❓ How does Kafka guarantee ordering?

  • Only WITHIN a single partition — never across partitions of the same topic
  • Achieved by keying related records (e.g. same orderId) so they always hash to the same partition

❓ What's the difference between acks=1 and acks=all?

  • acks=1: only the leader confirms — data can be lost if the leader fails before followers replicate it
  • acks=all: all current ISR members confirm, governed by min.insync.replicas — the strong-durability choice

❓ How do idempotent producers actually prevent duplicates?

  • Each producer session gets a PID; every batch to a partition gets a monotonic sequence number
  • The broker discards a batch whose sequence number it's already seen and appended — deduping retries at the source

❓ What's the actual difference between idempotence and transactions?

  • Idempotence: exactly-once for a single partition, single producer session — dedupes retries
  • Transactions: atomicity across MULTIPLE partitions/topics, and atomic consume-offset+produce for stream pipelines

❓ Why does isolation.level=read_committed matter, and what's the default?

  • Default is read_uncommitted — consumers see records from transactions that later get ABORTED
  • Producing transactionally accomplishes nothing for correctness unless the consumer explicitly opts into read_committed

❓ Eager vs cooperative-sticky rebalancing — what's the real difference?

  • Eager: ALL consumers revoke ALL partitions before reassignment — full stop-the-world pause
  • Cooperative-sticky: only partitions that genuinely need to move are revoked — everything else keeps processing

❓ What are the two independent liveness signals for a consumer, and why does it matter?

  • Heartbeats (background thread) — "is the process alive"
  • max.poll.interval.ms — "is the main loop making progress" — a consumer stuck in slow processing can fail this while heartbeating fine, triggering an unexpected rebalance

❓ How would you achieve exactly-once processing in a real system?

  • Most practical answer: at-least-once delivery + idempotent consumer-side processing (DB upsert keyed by business ID, or an explicit dedup check)
  • Full Kafka transactions are the right tool specifically for atomic multi-topic writes or Streams-style consume-transform-produce pipelines

❓ Compaction vs retention — when would you use each?

  • Retention (delete): time/size-based, whole segments — for event streams where only recent history matters
  • Compaction: keeps the latest value per key regardless of age — for changelog/current-state topics (e.g. Kafka Streams state store changelogs, CDC)

❓ What's a hot partition, and how do you fix it?

  • One partition receives disproportionate traffic due to key skew — adding more partitions/consumers doesn't help since one key always maps to the same partition
  • Fix: salt the key to spread load, use a custom partitioner, or reconsider whether that entity truly needs strict ordering

❓ What replaced ZooKeeper, and why does it matter?

  • KRaft — Kafka manages its own metadata internally via a Raft-consensus quorum of controller nodes, no external system
  • Simpler operations, faster failover, better scalability; the only supported mode as of Kafka 4.0

❓ How would you handle a "poison message" that keeps failing?

  • Classify the exception: transient (retry with backoff) vs permanent (skip straight to Dead Letter Topic)
  • Route unrecoverable failures to a DLT after N retries so they're visible/actionable, not silently dropped or blocking the partition forever

❓ Why avoid a naive "dual write" to a database and Kafka?

  • Writing to the DB and publishing to Kafka as two separate operations risks one succeeding while the other fails — no atomicity
  • Prefer the transactional outbox pattern: write to DB + an outbox table in one local transaction, then a CDC tool (Debezium) reliably publishes to Kafka from there

❓ What would you monitor to know a Kafka pipeline is healthy?

  • Consumer lag trend (not just absolute value) — a group falling steadily behind production rate
  • UnderReplicatedPartitions (early warning) and OfflinePartitionsCount (active outage) on the broker side

Interview Cheatsheet

One-liners for when you're under pressure. Know these cold.

📜 What Kafka actually is

  • A distributed, append-only, partitioned, replicated commit LOG — not a queue
  • Consuming doesn't delete — multiple groups read independently, replay is possible
  • Fast via sequential disk I/O, zero-copy (sendfile), and batching everywhere

🧩 Partitions — the core unit

  • Ordering guaranteed WITHIN a partition only, never across partitions
  • Offsets are per-partition, monotonic, tracked by the consumer (not the broker)
  • Key by whatever entity needs ordered processing (e.g. orderId)

🔥 Hot partitions

  • Caused by key skew — one key always maps to the same partition
  • Fix: salt the key, custom partitioner, or drop the ordering requirement

🛡️ Replication & ISR

  • One leader per partition, all reads/writes go through it; followers replicate
  • Only ISR members are eligible for leader election — this is what prevents data loss on failover
  • unclean.leader.election.enable — a direct CAP trade-off (off = safe default)

🗳️ Controller & KRaft

  • Controller: elects leaders, detects failures, propagates metadata
  • KRaft replaced ZooKeeper — Raft consensus, internal to Kafka, only supported mode since 4.0

🗑️ Retention vs Compaction

  • Retention (delete): time/size-based, whole segments — event streams
  • Compaction: latest value per key, regardless of age — changelogs, CDC, Streams state stores

📤 Producer essentials

  • send() is async — batches by batch.size/linger.ms, flushed by a background Sender thread
  • acks=0 (none) / acks=1 (leader only) / acks=all (full ISR, governed by min.insync.replicas)
  • Since Kafka 3.0: acks=all + idempotence are the DEFAULT

✅ Exactly-once building blocks

  • Idempotent producer: PID + sequence number — dedupes retries, single partition/session scope
  • Transactions: atomic multi-partition writes + sendOffsetsToTransaction for consume-produce
  • Consumer MUST set isolation.level=read_committed (default is read_uncommitted!)

👥 Consumer groups & rebalancing

  • A partition → at most one consumer per group at a time; extra consumers sit idle
  • Eager rebalance: stop-the-world. Cooperative-sticky: only moving partitions pause
  • Static membership (group.instance.id) avoids rebalances on routine restarts

📍 Offset commit timing

  • Commit BEFORE processing → at-most-once (risk: silent loss)
  • Commit AFTER processing → at-least-once (risk: duplicates — make processing idempotent)
  • commitSync (safe, blocking) vs commitAsync (fast, needs a failure callback)

🔁 Two independent consumer liveness checks

  • Heartbeats (background thread) — is the process alive
  • max.poll.interval.ms — is the main loop making progress (tied to calling poll())

🌱 Spring Kafka mapping

  • KafkaTemplate = producer. @KafkaListener = consumer (concurrency ≤ partition count)
  • Acknowledgment.acknowledge() = manual commit. DefaultErrorHandler + DeadLetterPublishingRecoverer = DLT
  • @Transactional("kafkaTransactionManager") = the transactional producer API, declaratively

🏗️ The dual-write problem

  • Writing to DB + Kafka as two separate ops risks partial failure
  • Fix: transactional outbox — write DB + outbox table in one local tx, CDC (Debezium) publishes reliably

📐 Schema Registry

  • Enforces a real contract — rejects incompatible schema changes at registration time
  • BACKWARD (new reads old), FORWARD (old reads new), FULL (both) — BACKWARD is the common default

📊 Monitoring essentials

  • Consumer lag = latest offset − committed offset; watch the TREND, not just the value
  • UnderReplicatedPartitions = early warning. OfflinePartitionsCount = active outage

🚨 Top interview traps

  • Assuming ordering across partitions (it's per-partition only)
  • Forgetting isolation.level=read_committed on the consumer
  • Auto-commit firing before processing actually completes
  • Confusing idempotence (single partition/session) with transactions (cross-partition atomicity)
  • concurrency/consumer count exceeding partition count — wasted, idle consumers
