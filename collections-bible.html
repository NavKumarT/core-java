java.util

Why the Collections Framework Exists

A plain Java array has a fatal limitation for real-world data structures: its size is FIXED at creation and can never change.

The core problem — arrays can't grow 
int[] A = new int[10]; // exactly 10 slots, forever — no resize(), no push_back()
// Need an 11th element? You must allocate a NEW array and copy everything over.
// The Collections Framework automates exactly this "allocate bigger, copy, replace"
// dance behind a clean, standard API — plus adds sets, maps, queues, sorted
// structures, and a common set of interfaces so algorithms can work generically
// across any of them
What the framework provides beyond "resizable arrays"
  • Dynamic collections — ArrayList, LinkedList: grow and shrink automatically
  • Distinct collections — Set: automatically rejects duplicates
  • Distinct + sorted collections — SortedSet/TreeSet: duplicates rejected AND elements kept in order
  • Key-value storage — Map: the one branch NOT part of the Collection hierarchy, covered separately
  • A common set of interfaces (Collection, List, Set, Queue) so code can be written against the ABSTRACTION, swapping implementations freely
"Collection" vs "Collections" — a classic interview trip-up
  • Collection (singular) — the root INTERFACE: List, Set, Queue all extend it
  • Collections (plural) — a UTILITY CLASS full of static helper methods: Collections.sort(), Collections.reverse(), Collections.unmodifiableList()
  • Same relationship as Arrays (utility class) to array types themselves
💡 Coming from C++: think of the Collections Framework as Java's answer to the STL containers — ArrayList ≈ vector, HashMap ≈ unordered_map, TreeMap ≈ map. A dedicated side-by-side translation table is in the C++ → Java Rosetta Stone section below — bookmark it for your LeetCode transition.
The Big Picture

The Complete Collections Hierarchy

Every collection class implements a chain of interfaces rooted at Iterable. Map is deliberately NOT part of this hierarchy — it doesn't extend Collection at all, since a Map's fundamental unit is a key-value PAIR, not a single element.

Reading the tree
  • Iterable — the root; anything Iterable can be used in a for-each loop
  • Collection — adds add/remove/size/contains-style bulk operations
  • List — ordered, allows duplicates, index-based access
  • Set — no duplicates; SortedSet/TreeSet additionally keeps elements sorted
  • Queue — designed for FIFO processing; Deque extends it for double-ended access; PriorityQueue extends it for heap-ordered access
Why Map is separate
  • Collection's core contract is "a bag of single elements" — add(E), iterator() over E
  • Map's core contract is "a set of key→value associations" — put(K,V), get(K) — a fundamentally different shape
  • Map DOES integrate with Collection indirectly: map.keySet() returns a Set<K>, map.values() returns a Collection<V>, map.entrySet() returns a Set<Map.Entry<K,V>>
⚠️ Interview trap: "Does Map extend Collection?" — NO. This is asked constantly and the naive assumption (everything in java.util must be a Collection) is wrong. Map is a first-class citizen of the Collections FRAMEWORK, but not of the Collection INTERFACE hierarchy.
The Contracts

Collection, List & Queue Interfaces

Every concrete class you'll use (ArrayList, HashSet, ArrayDeque...) implements one of these interfaces. Knowing exactly which methods live where — and their return-value contracts — is baseline interview material.

  • add(int index, E e) / remove(int index) — positional insert/delete
  • get(int index) / set(int index, E e) — positional read/overwrite
  • subList(int from, int to) — a VIEW backed by the original list, not a copy

  • listIterator() / listIterator(int index) — a bidirectional iterator, covered in the Iterators section
Set interface — deliberately minimal

  • Everything else (iteration, removal, bulk ops) is inherited as-is from Collection
Queue interface — the null vs exception split
Queue methods in action
// Queue offers TWO parallel method families for the same operations —
// one returns a sentinel value on failure, the other throws

//  Operation      Throws on failure        Returns special value
//  Insert         add(e)                   offer(e)  -> false
//  Remove         remove()                 poll()    -> null
//  Examine        element()                peek()    -> null

// poll()    -> null on empty queue, NO exception
// remove()  -> throws NoSuchElementException on empty queue
// peek()    -> null on empty queue, NO exception
// element() -> throws NoSuchElementException on empty queue
Queue<Integer> q = new LinkedList<>();

q.offer(1); q.offer(2);

System.out.println(q.poll());   // 1 — removes and returns head
System.out.println(q.peek());   // 2 — returns head WITHOUT removing

q.poll(); // queue now empty
System.out.println(q.poll());   // null — empty queue, no exception
// q.remove();  // would throw NoSuchElementException instead

// PREFER offer()/poll()/peek() in almost all production and interview code —
// they let you check for "empty" with a simple null check instead of a try/catch

The Default List

ArrayList

Backed by a resizable array under the hood — the workhorse List implementation, and your default choice unless you have a specific reason not to use it.

How growth works internally
  • Backed by an Object[] that starts at a small default capacity (10, if unspecified)
  • When full, a new array of ~1.5x the current capacity is allocated and all elements are copied over — an O(n) operation, but AMORTIZED O(1) per add() across many calls
  • Supplying an initial capacity when you know the approximate size avoids repeated resize-and-copy cycles
Time complexity
  • get(i) / set(i, v) — O(1), direct array indexing
  • add(v) (at end) — amortized O(1)
  • add(i, v) / remove(i) (middle) — O(n), shifts all subsequent elements
  • contains(v) / indexOf(v) — O(n), linear scan

Doubly-Linked

LinkedList

Java implements LinkedList as a genuine doubly linked list — every node holds references to both its previous and next node. It implements both List and Deque, so it can serve as a list, a stack, or a queue.

AspectArrayListLinkedList
Backing structureResizable arrayDoubly linked nodes
get(i) / random accessO(1)O(n) — must walk from head or tail
Insert/delete at head or tailO(n) at head, amortized O(1) at tailO(1) — no shifting, just re-link pointers
Insert/delete in the middleO(n) — must shift elementsO(n) to FIND the position, then O(1) to splice
Memory overheadLower — just the array + unused capacityHigher — each node stores 2 extra references (prev/next)
Initial capacity constructorYes — new ArrayList<>(20)No — nodes are allocated one at a time, no notion of "capacity"
LinkedList used as List, Stack, and Queue — all via the same class 
LinkedList<Integer> ll = new LinkedList<>();

// As a List
ll.add(1); ll.add(2); ll.add(0, 0); // insert at index 0

// As a Deque (Stack-style, via push/pop on the head)
ll.push(99);  // insert at head
ll.pop();    // remove from head

// As a Queue (via offer/poll)
ll.offer(5); // insert at tail
ll.poll();   // remove from head — FIFO order

// Direct head/tail access without removal
ll.getFirst(); ll.getLast();
ll.peekFirst(); ll.peekLast(); // null-safe versions
⚠️ Interview reality check: despite the theoretical O(1) insert/delete, ArrayList outperforms LinkedList in most practical benchmarks due to CPU cache locality — array elements sit contiguously in memory, while linked-list nodes are scattered and require pointer-chasing. Default to ArrayList unless you specifically need frequent head/tail operations or are implementing something like an LRU cache's internal list.
Know Them, Avoid Them

Vector & Stack (Legacy)

Both predate the Collections Framework (Java 1.0) and were retrofitted to implement its interfaces. Both are still around and interview-relevant to RECOGNIZE, but neither should be your first choice in new code.

Vector
  • Essentially a synchronized ArrayList — every method is synchronized, adding locking overhead even in single-threaded code
  • Grows by DOUBLING its capacity by default (vs ArrayList's ~1.5x)
  • Modern replacement: ArrayList, or Collections.synchronizedList(new ArrayList<>()) / CopyOnWriteArrayList if you actually need thread safety
Stack
  • Extends Vector — inherits ALL of Vector's baggage (synchronized, doubling growth) just to add push/pop/peek
  • Also technically lets you call List methods like add(int, E) on it, which can silently break stack discipline — a real design wart
  • Modern replacement: Deque<T> stack = new ArrayDeque<>(); using push()/pop()/peek() — faster, no synchronization overhead, and the JDK docs themselves recommend this
Legacy vs modern stack — side by side 
// Legacy — works, but avoid in new code
Stack<Integer> legacyStack = new Stack<>();
legacyStack.push(1);
legacyStack.pop();

// Modern — preferred for interviews and production alike
Deque<Integer> modernStack = new ArrayDeque<>();
modernStack.push(1);
modernStack.pop();
💡 Interview one-liner: "Vector and Stack are legacy, synchronized classes retrofitted into the Collections Framework. ArrayList/ArrayDeque are their unsynchronized, faster modern replacements — I use java.util.Stack only when reading legacy code, never when writing new code."
Double-Ended

ArrayDeque — The Modern Swiss Army Knife

ArrayDeque ("Array Double Ended Queue") is backed by a resizable array and can efficiently insert/remove from BOTH ends — making it the go-to implementation for stacks, queues, and sliding-window problems alike.

Key characteristics
  • Backed by a resizable array (specifically a circular buffer), NOT a linked list
  • All core operations — offerFirst/offerLast/pollFirst/pollLast — are amortized O(1)
  • Faster than LinkedList for stack/queue use in nearly all real benchmarks, due to array cache-locality
  • Does NOT permit null elements — offering null throws NullPointerException (unlike LinkedList)
Three roles, one class
  • As a Queue (FIFO): offer() adds to tail, poll() removes from head
  • As a Stack (LIFO): push() adds to head, pop() removes from head
  • As a Deque: explicit offerFirst/offerLast/pollFirst/pollLast for direct double-ended control — the classic sliding-window-maximum tool
Basic operations
Traversal
Classic use: sliding window maximum
Deque<Integer> dq = new ArrayDeque<>();

dq.offerLast(10);   // insert at end — [10]
dq.offerFirst(5);   // insert at beginning — [5, 10]
dq.offerLast(20);   // [5, 10, 20]

System.out.println(dq.peekFirst()); // 5 — no removal
System.out.println(dq.peekLast());  // 20 — no removal

dq.pollFirst();  // removes 5 -> [10, 20]
dq.pollLast();   // removes 20 -> [10]
dq.forEach((x) -> System.out.println(x)); // head-to-tail order

// Reverse traversal — a Deque-exclusive convenience:
Iterator<Integer> descIt = dq.descendingIterator();
while (descIt.hasNext()) {
    System.out.println(descIt.next()); // tail-to-head order
}
// LeetCode 239 "Sliding Window Maximum" — the textbook ArrayDeque application.
// Maintain a deque of INDICES, keeping it in decreasing order of VALUE.
int[] maxSlidingWindow(int[] nums, int k) {
    Deque<Integer> deque = new ArrayDeque<>(); // stores INDICES
    int[] result = new int[nums.length - k + 1];

    for (int i = 0; i < nums.length; i++) {
        while (!deque.isEmpty() && deque.peekFirst() <= i - k) {
            deque.pollFirst(); // drop indices that fell out of the window
        }
        while (!deque.isEmpty() && nums[deque.peekLast()] < nums[i]) {
            deque.pollLast(); // drop smaller values — they can never be the max again
        }
        deque.offerLast(i);
        if (i >= k - 1) {
            result[i - k + 1] = nums[deque.peekFirst()]; // front of deque = current window max
        }
    }
    return result;
} // O(n) overall — each index is pushed and popped at most once
Heap-Backed

PriorityQueue

Implemented as a binary heap, backed by a resizable array (not actual tree nodes — just clever index arithmetic: for index i, children live at 2i+1 and 2i+2). Min-heap by default — the SMALLEST element always sits at the head.

Complexity
  • offer() / poll() — O(log n), sift up/down to restore heap order
  • peek() — O(1), always the root
  • contains() / arbitrary remove(Object) — O(n), no shortcut for finding an arbitrary element in a heap
  • Iteration order (forEach, the iterator) is NOT sorted — only poll() repeatedly gives you sorted output
Core operations
  • offer(e) — insert, restoring heap property
  • poll() — remove and return the smallest (or highest-priority) element
  • peek() — view the smallest without removing
  • forEach() — visits every element, but in internal array order, NOT priority order
Default min-heap
Max-heap via a Comparator class
Max-heap via lambda (modern, preferred)
Classic use: Top-K elements
PriorityQueue<Integer> p = new PriorityQueue<>(); // min-heap by default

p.offer(5); p.offer(1); p.offer(3);

p.peek();  // 1 — smallest
p.poll();  // removes and returns 1
p.poll();  // removes and returns 3
p.poll();  // removes and returns 5
// From your notes — a custom Comparator class that flips the natural order
class MyComp implements Comparator<Integer> {
    @Override
    public int compare(Integer o1, Integer o2) {
        if (o1 < o2) return 1;   // "o1 is bigger" in heap-order terms — flips the usual convention
        if (o1 > o2) return -1;
        return 0;
    }
}
// Above comparator creates a MAX HEAP — PriorityQueue always puts the
// element the Comparator treats as "smallest" (negative compare result) at
// the head; by inverting the sign, the LARGEST value ends up "smallest"

PriorityQueue<Integer> maxHeap = new PriorityQueue<>(new MyComp());
maxHeap.offer(5); maxHeap.offer(1); maxHeap.offer(3);
maxHeap.peek(); // 5 — largest on top now
// The modern, terser equivalent of the MyComp class above
PriorityQueue<Integer> maxHeap = new PriorityQueue<>((a, b) -> b - a); // reversed subtraction
// CAUTION: (a, b) -> b - a can silently overflow for values near
// Integer.MIN_VALUE/MAX_VALUE — safer in interviews to write:
PriorityQueue<Integer> maxHeapSafe = new PriorityQueue<>(Collections.reverseOrder());

// Custom objects, ordered by a specific field — very common in LeetCode:
PriorityQueue<int[]> pq = new PriorityQueue<>((a, b) -> a[1] - b[1]); // min-heap ordered by index 1
// LeetCode 215 "Kth Largest Element" — maintain a min-heap of size K.
// The SMALLEST of the K largest-seen elements sits at the head — evict it
// whenever the heap grows past K, and whatever survives IS the top K.
int findKthLargest(int[] nums, int k) {
    PriorityQueue<Integer> minHeap = new PriorityQueue<>(); // plain min-heap — no comparator needed
    for (int n : nums) {
        minHeap.offer(n);
        if (minHeap.size() > k) {
            minHeap.poll(); // evict the smallest — keeps only the K largest seen so far
        }
    }
    return minHeap.peek(); // the smallest of the K largest = the Kth largest overall
} // O(n log k) — much better than sorting the whole array (O(n log n)) when k << n
🚫 Interview trap: iterating a PriorityQueue with a for-each loop or forEach() does NOT visit elements in priority order — it walks the internal array in whatever order the heap happens to store them. Only repeated poll() calls guarantee sorted output.
No Duplicates, No Order

HashSet

Internally, HashSet is just a thin wrapper around a HashMap — every element you add becomes a KEY in a backing map, with a shared dummy constant as the value. Understanding HashMap's internals (covered in depth later) tells you everything about HashSet's behavior.

Key characteristics
  • No duplicate elements — determined via hashCode() + equals()
  • No ordering guarantee whatsoever — iteration order can even change between runs
  • Average O(1) for add/remove/contains; worst case O(n) with severe hash collisions (or O(log n) since Java 8's bucket treeification, covered in the HashMap section)
  • Allows a single null element
Constructor tuning
  • new HashSet<>(initialCapacity, loadFactor) — pre-size to avoid rehashing if you know the approximate element count
  • loadFactor controls the fill-ratio threshold that triggers a resize (default 0.75) — lower = more memory, fewer collisions; higher = less memory, more collisions
Basic operations 
HashSet<Integer> hs = new HashSet<>(20, 0.5f); // capacity hint 20, resize at 50% full

hs.add(5);
hs.add(5);   // no-op — add() returns false, set unchanged
hs.remove(5);

// Classic LeetCode use: O(1) duplicate/membership check
boolean hasDuplicate(int[] nums) {
    Set<Integer> seen = new HashSet<>();
    for (int n : nums) {
        if (!seen.add(n)) return true; // add() returns false if n was already present
    }
    return false;
} // O(n) time, O(n) space — the standard "seen set" pattern
⚠️ Storing a mutable custom object in a HashSet and then mutating a field that affects hashCode() AFTER insertion corrupts the set — the element becomes unfindable, stuck in the wrong bucket. Only use immutable keys, or keys whose hashCode-affecting fields never change post-insertion.

// To store custom objects in a TreeSet, the class MUST implement Comparable —
// otherwise TreeSet has no way to decide ordering, and throws ClassCastException
// the moment you try to add a second element
class Point implements Comparable<Point> { // generic form — modern, type-safe
    private int x;
    private int y;

    @Override

The Deepest Dive

HashMap — Internal Working

HashMap is the single most interview-tested collection in Java. Understanding its bucket-array-plus-collision-chain design — and how it changed in Java 8 — separates "I use HashMap" from "I understand HashMap."

The core data structure
  • Backed by an array of "buckets" (Node[] table), default initial size 16
  • A key's bucket index is computed from its hashCode(), further mixed and masked against the array length
  • Multiple keys CAN land in the same bucket (a "collision") — each bucket holds a chain of entries for that index
load factor & resizing
  • Default load factor: 0.75 — when the map is 75% full (size > capacity × 0.75), it RESIZES
  • Resize doubles the bucket array size and re-buckets every existing entry — an expensive O(n) operation, amortized across many inserts
  • Pre-sizing with a known capacity (new HashMap<>(expectedSize)) avoids repeated resizes, exactly like ArrayList's initial capacity
Step by step: put() and get()
Java 8+: bucket treeification
Why hashCode() + equals() must agree
// put(key, value):
// 1. Compute hash = key.hashCode(), then mix bits (HashMap applies
//    "hash ^ (hash >>> 16)" to spread high bits into low bits, reducing
//    collisions for keys whose low bits alone are similar)
// 2. bucketIndex = hash & (table.length - 1)   // fast modulo via bitmask,
//    only works because table.length is always a power of 2
// 3. If the bucket is empty, place the new Node there directly
// 4. If the bucket already has entries, walk the chain:
//    - if a key.equals() an existing entry's key, OVERWRITE its value
//    - otherwise, append a new Node to the chain (or tree, see next tab)

// get(key): same hash + bucketIndex computation, then walk the bucket's
// chain comparing equals() until a match is found, or return null

Map<String, Integer> map = new HashMap<>();
map.put("apple", 1);   // hashCode() computed, bucket found, Node inserted
map.put("apple", 2);   // same key -> same bucket -> equals() match -> VALUE OVERWRITTEN, not duplicated
map.get("apple");      // 2
// PRE-Java 8: every bucket was a plain LINKED LIST of colliding entries.
// Worst case (all keys collide into one bucket): O(n) lookup — a
// pathological but real DENIAL-OF-SERVICE vector if an attacker can craft
// keys with identical hashCode()s (this was a real historical CVE class)

// Java 8+ FIX: if a single bucket's chain grows past TREEIFY_THRESHOLD (8),
// AND the table itself has at least 64 buckets, that bucket's linked list
// is converted into a balanced RED-BLACK TREE instead — worst-case lookup
// within that bucket drops from O(n) to O(log n)

// It converts BACK to a linked list if the bucket shrinks below
// UNTREEIFY_THRESHOLD (6) after removals — hysteresis avoids thrashing
// back and forth right at the boundary

// This is entirely an INTERNAL optimization — HashMap's public API and
// Big-O contract (average O(1)) are unaffected; it only improves the
// WORST case from O(n) to O(log n) per bucket
// The contract: if a.equals(b) is true, then a.hashCode() MUST equal b.hashCode()
// (the reverse isn't required — different objects CAN share a hashCode; that's
// just a collision, handled by the bucket chain)

class BadKey {
    int id;
    @Override
    public boolean equals(Object o) {
        return o instanceof BadKey && ((BadKey) o).id == this.id;
    }
    // NO hashCode() override — inherits Object's IDENTITY-based hashCode()
    // Two BadKey objects with the same id are equals()-equal, but almost
    // certainly land in DIFFERENT buckets (different default hashCodes) —
    // map.get(new BadKey(5)) will NEVER find an entry put with a different
    // BadKey(5) instance, even though they're "equal." A silent, brutal bug.
}
// RULE: whenever you override equals(), you MUST override hashCode() too —
// most IDEs and records (Java 16+) generate both together automatically

Order-Preserving

LinkedHashMap & the LRU Cache Pattern

LinkedHashMap combines a hash table (for O(1) lookup) with a doubly linked list threading through all entries (for predictable iteration order) — and with one constructor flag, becomes a complete, interview-famous LRU cache implementation.

How it maintains order internally
  • Every entry is ALSO a node in a doubly linked list — each holds before/after references to its neighbors in iteration order
  • The hash table portion is used for O(1) key lookup, exactly like HashMap
  • The linked list portion is used purely for iteration order — get()/put() still go through hashing, not list traversal
Insertion order example (from your notes)
  • Inserting key 12 then key 17 links them: [12,A] <-> [17,B]
  • The hash bucket for each key still points directly to its node for O(1) access
  • Iterating the map walks the LINKED LIST, not the buckets — which is exactly why iteration order matches insertion order, unlike plain HashMap
Insertion-order iteration — the default mode 
LinkedHashMap<Integer, String> lhm = new LinkedHashMap<>();
lhm.put(12, "A");
lhm.put(17, "B");
lhm.put(3, "C");

for (Map.Entry<Integer, String> e : lhm.entrySet()) {
    System.out.println(e.getKey() + "=" + e.getValue());
}
// Prints in the EXACT order inserted: 12=A, 17=B, 3=C
// A plain HashMap makes NO such guarantee — same puts, unpredictable order
The access-order constructor
Complete LRU Cache implementation
LinkedHashMap<Integer, String> lhm = new LinkedHashMap<>(
    initialCapacity, // e.g. 5
    loadFactor,       // e.g. 0.75f
    accessOrder        // true = order by LAST ACCESS, not insertion
);

// When accessOrder = true:
// - Every get() call MOVES that entry to the END of the iteration order
// - The entry at the START (front) of the iteration is therefore always
//   the LEAST recently used one — exactly the property an LRU cache needs
LinkedHashMap<Integer, String> accessOrdered = new LinkedHashMap<>(5, 0.75f, true);
// The classic "Design an LRU Cache" interview question, solved in ~15 lines
class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LRUCache(int capacity) {
        super(capacity, 0.75f, true); // accessOrder = true is the key ingredient
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity; // hook called automatically after every put() —
    }                                // returning true auto-evicts the LEAST recently used entry
}

LRUCache<Integer, String> cache = new LRUCache<>(3);
cache.put(1, "a"); cache.put(2, "b"); cache.put(3, "c");
cache.get(1);              // touches key 1 -> moves it to "most recently used"
cache.put(4, "d");        // exceeds capacity -> evicts key 2 (the actual least recently used)
System.out.println(cache.containsKey(2)); // false — evicted
💡 Why this is a favorite interview question: it tests whether you know LinkedHashMap has BOTH an access-order mode AND a protected override hook (removeEldestEntry) specifically designed for cache eviction — turning a ~100-line hand-rolled doubly-linked-list-plus-hashmap solution into a ~15-line subclass.

Hashtable predates the Collections Framework, same story as Vector/Stack. Meanwhile, understanding exactly how iteration works — and why concurrent modification breaks it — is a recurring "explain what happens" interview question.

Iterable, Iterator, ListIterator — three related but distinct things
  • Iterable<T> — the interface that makes a for-each loop possible; declares iterator()
  • Iterator<T> — one-directional cursor: hasNext(), next(), remove()
  • ListIterator<T> (List only) — BIDIRECTIONAL: adds hasPrevious(), previous(), plus set() and add() during traversal
Fail-fast vs fail-safe iterators
  • Fail-fast (ArrayList, HashMap, HashSet, ...): detects structural modification during iteration via an internal modCount counter, throws ConcurrentModificationException
  • Fail-safe (ConcurrentHashMap, CopyOnWriteArrayList): iterates over a snapshot or tolerates concurrent changes, never throws — but may not reflect the very latest modifications
ListIterator — bidirectional
ConcurrentModificationException — why it happens
Safe removal patterns
List<Integer> list = new ArrayList<>(List.of(1, 2, 3));
ListIterator<Integer> lit = list.listIterator();

while (lit.hasNext()) {
    int val = lit.next();
    if (val == 2) lit.set(20); // in-place replace during traversal — plain Iterator can't do this
}

while (lit.hasPrevious()) { // walk BACKWARD from wherever next() left off
    System.out.println(lit.previous());
}
// list is now [1, 20, 3]
List<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4));

for (Integer x : list) {
    if (x == 2) list.remove(x); // modifying the list WHILE the for-each loop's hidden
}                                // Iterator is still using it -> ConcurrentModificationException

// WHY: the for-each loop desugars to using list.iterator() internally.
// Every structural modification (add/remove) increments an internal
// modCount field. Each call to it.next() checks "does modCount still
// match what I saw when I was created?" — if not, it throws immediately,
// rather than risk silently corrupted/undefined iteration behavior
// FIX 1: use the Iterator's OWN remove() — it updates modCount correctly
Iterator<Integer> it = list.iterator();
while (it.hasNext()) {
    if (it.next() == 2) it.remove(); // SAFE — the only removal the iterator itself sanctions
}

// FIX 2 (Java 8+): removeIf() — cleanest for simple predicate-based removal
list.removeIf(x -> x == 2);

// FIX 3: iterate over a COPY if you need to modify the original freely
for (Integer x : new ArrayList<>(list)) {
    if (x == 2) list.remove(x);
}

// LeetCode 1 "Two Sum" — the canonical HashMap pattern
int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> seen = new HashMap<>(); // value -> index
    for (int i = 0; i < nums.length; i++) {
        int complement = target - nums[i];
        if (seen.containsKey(complement)) {
            return new int[]{seen.get(complement), i};
        }
        seen.put(nums[i], i);
    }
    return new int[]{};
} // O(n) time, O(n) space — one pass instead of the naive O(n²)

// LeetCode 242 "Valid Anagram" — frequency map comparison
boolean isAnagram(String s, String t) {
    if (s.length() != t.length()) return false;
    Map<Character, Integer> count = new HashMap<>();
    for (char c : s.toCharArray()) count.merge(c, 1, Integer::sum);
    for (char c : t.toCharArray()) count.merge(c, -1, Integer::sum);
    return count.values().stream().allMatch(v -> v == 0);
}
// LeetCode 496 "Next Greater Element" — the monotonic (decreasing) stack pattern
int[] nextGreaterElement(int[] nums) {
    int[] result = new int[nums.length];
    Arrays.fill(result, -1);
    Deque<Integer> stack = new ArrayDeque<>(); // stores INDICES, kept in decreasing value order

    for (int i = 0; i < nums.length; i++) {
        while (!stack.isEmpty() && nums[stack.peek()] < nums[i]) {
            result[stack.pop()] = nums[i]; // found the "next greater" for whatever's on top
        }
        stack.push(i);
    }
    return result;
} // O(n) — each index is pushed and popped at most once, despite the nested loop look
// Building a graph and running BFS — the standard Map<Integer, List<Integer>> adjacency list
Map<Integer, List<Integer>> graph = new HashMap<>();

void addEdge(int u, int v) {
    graph.computeIfAbsent(u, k -> new ArrayList<>()).add(v); // auto-creates the list on first edge from u
    graph.computeIfAbsent(v, k -> new ArrayList<>()).add(u); // undirected — add both directions
}

List<Integer> bfs(int start) {
    List<Integer> order = new ArrayList<>();
    Set<Integer> visited = new HashSet<>();
    Queue<Integer> queue = new ArrayDeque<>();

    queue.offer(start);
    visited.add(start);

    while (!queue.isEmpty()) {
        int node = queue.poll();
        order.add(node);
        for (int neighbor : graph.getOrDefault(node, List.of())) {
            if (visited.add(neighbor)) { // add() returns false if already visited — a neat one-liner combo
                queue.offer(neighbor);
            }
        }
    }
    return order;
}
// LeetCode 347 "Top K Frequent Elements" — HashMap + PriorityQueue combo,
// one of the most common two-collection combos in interviews
int[] topKFrequent(int[] nums, int k) {
    Map<Integer, Integer> freq = new HashMap<>();
    for (int n : nums) freq.merge(n, 1, Integer::sum);

    // min-heap of size k, ordered by FREQUENCY (ascending) — smallest freq evicted first
    PriorityQueue<Map.Entry<Integer, Integer>> heap =
        new PriorityQueue<>((a, b) -> a.getValue() - b.getValue());

    for (Map.Entry<Integer, Integer> entry : freq.entrySet()) {
        heap.offer(entry);
        if (heap.size() > k) heap.poll();
    }

    int[] result = new int[k];
    for (int i = k - 1; i >= 0; i--) result[i] = heap.poll().getKey();
    return result;
} // O(n log k) — the HashMap+PriorityQueue combo generalizes to countless
  // "top K by some computed metric" problems
💡 Transition tip: the biggest mental shift from C++ isn't syntax, it's that Java has NO operator overloading — map[key]++ becomes map.merge(key, 1, Integer::sum), and container comparisons/output need explicit methods (.equals(), Arrays.toString()) instead of == or cout <<. Once merge()/getOrDefault()/computeIfAbsent() feel natural, the rest of the transition is just renaming methods.

List<Integer> list = new ArrayList<>(List.of(10, 20, 30));
list.remove(1);         // Q: what does the list contain after this?
// A: [10, 30] — remove(int) is INDEX-based; removed the element AT index 1 (value 20)

list.remove(Integer.valueOf(10)); // removes the VALUE 10 (via the Object overload) -> [30]
// The overload resolution is based on the STATIC type of the argument —
// an int literal picks remove(int), an Integer object picks remove(Object)
Map<String, Integer> hm = new HashMap<>();
hm.put(null, 1);      // Q: does this compile / work?
hm.put("a", null);   // Q: what about this?
// A: BOTH work fine on HashMap — exactly ONE null key is allowed (stored
// in bucket 0, special-cased), and any number of null VALUES are allowed.
// Hashtable and ConcurrentHashMap, by contrast, allow NEITHER —
// throwing NullPointerException immediately on either
List<Integer> mutable = new ArrayList<>(List.of(1, 2, 3));
List<Integer> readOnly = Collections.unmodifiableList(mutable);

mutable.add(4);
System.out.println(readOnly.size()); // Q: what does this print?
// A: 4 — NOT 3! unmodifiableList() wraps the SAME underlying list; it only
// blocks mutation calls made THROUGH the wrapper. Changes to the original
// still show through. This is "read-only," not truly "immutable" — a very
// commonly misunderstood distinction
PriorityQueue<Integer> pq = new PriorityQueue<>(List.of(5, 1, 8, 2));
for (int x : pq) System.out.print(x + " "); // Q: does this print "1 2 5 8"?
// A: NOT guaranteed! for-each / iterator() on a PriorityQueue visits the
// internal array in whatever order the heap happens to store elements —
// only sorted by the heap PROPERTY (each parent <= its children), not
// fully sorted. Only repeated poll() calls guarantee ascending output.

Short-answer FAANG questions

❓ ArrayList vs LinkedList — when would you actually choose each?

  • ArrayList: default choice — O(1) random access, better cache locality, most real workloads favor it
  • LinkedList: frequent insert/delete at both ends with rare random access — e.g. implementing a Deque manually (though ArrayDeque usually wins even there)
  • In practice, ArrayList wins most benchmarks even for "LinkedList's strong suit" due to cache effects

❓ How does HashMap handle collisions, and how did that change in Java 8?

  • Colliding keys land in the same bucket, stored as a linked list of entries pre-Java 8
  • Java 8+: a bucket converts to a red-black tree once it exceeds 8 entries (with table size ≥ 64) — worst-case O(n) becomes O(log n)
  • Requires hashCode()/equals() to be correctly implemented for correctness at all

❓ Why is HashMap's default initial capacity always a power of 2?

  • Bucket index is computed via hash & (capacity - 1) — a bitmask trick that's only equivalent to modulo when capacity is a power of 2
  • Bitwise AND is significantly cheaper than the % operator — a deliberate performance optimization

❓ HashSet vs TreeSet vs LinkedHashSet — pick one for each scenario?

  • Just need fast membership, don't care about order → HashSet
  • Need sorted iteration or nearest-value queries → TreeSet
  • Need insertion-order iteration with fast lookup → LinkedHashSet

❓ Why does PriorityQueue default to a min-heap?

  • Pure JDK design convention — matches natural ordering (Comparable's compareTo), where "smallest first" is the default sense of "least"
  • C++'s priority_queue defaults the opposite way (max-heap) — a common source of ported-bug in cross-language interviews
  • Both directions are one line away via a Comparator either way

❓ What makes an iterator "fail-fast," and why design it that way?

  • Detects concurrent structural modification via a modCount check, throws ConcurrentModificationException rather than risk silently wrong/corrupted iteration
  • It's a best-effort DEBUGGING aid, not a hard concurrency guarantee — not reliably thrown in all cases, and never rely on it for actual thread-safety
  • Fail-safe alternatives (ConcurrentHashMap) trade this detection for lock-free concurrent iteration instead

❓ Why can't you just use a HashMap when order matters?

  • HashMap gives NO ordering guarantee at all — bucket layout depends on hash values and internal resizing history, not insertion sequence
  • LinkedHashMap (insertion or access order) or TreeMap (sorted order) are the correct tools depending on which "order" you actually need

❓ Explain how you'd implement an LRU cache, and why LinkedHashMap fits.

  • Need O(1) get/put AND O(1) "move to most-recent" AND O(1) eviction of least-recent — a hand-rolled HashMap + doubly linked list combo
  • LinkedHashMap with accessOrder=true already threads a doubly linked list through its entries in access order — override removeEldestEntry() and you get the whole thing "for free"

❓ What's the time complexity difference between TreeMap and HashMap, and when do you accept the tradeoff?

  • HashMap: O(1) average for get/put/remove. TreeMap: O(log n) for the same operations
  • Accept TreeMap's overhead whenever you need sorted iteration, range queries, or nearest-key lookups — capabilities HashMap simply cannot provide

❓ Comparable vs Comparator — which would you use to sort Employees by salary, then by name?

  • Comparable if "by salary" is genuinely the class's ONE natural, canonical order
  • Comparator (with thenComparing for the name tie-break) for anything else — especially since you likely want MULTIPLE different sort orders for the same Employee class across your codebase

❓ Why is Vector/Stack/Hashtable considered legacy, and what replaces each?

  • All three predate the Collections Framework and are unconditionally synchronized — a real performance cost even single-threaded
  • Vector → ArrayList. Stack → Deque (ArrayDeque). Hashtable → HashMap (single-threaded) or ConcurrentHashMap (multi-threaded)

❓ What's the actual difference between Collection and Collections?

  • Collection (singular): the root INTERFACE — List, Set, Queue all extend it
  • Collections (plural): a static UTILITY CLASS of helper methods operating on collections — sort, reverse, unmodifiableList, etc.

❓ Design a data structure with O(1) insert, delete, AND getRandom() — which collections would you combine?

  • ArrayList for O(1) getRandom() (index-based) and O(1) amortized insert (append)
  • HashMap<value, index> to locate any value's position in O(1)
  • Delete trick: swap the target with the LAST array element, update the map, then remove the last element in O(1) — avoids the O(n) shift a naive middle-removal would cost
Interview Reference

Interview Cheatsheet

One-liners for when you're under pressure. Know these cold.

🗂️ The hierarchy essentials

  • Iterable → Collection → {List, Queue, Set}
  • Map is SEPARATE — does not extend Collection
  • Collection (interface) ≠ Collections (utility class)

📋 ArrayList vs LinkedList

  • ArrayList: O(1) get/set, amortized O(1) end-insert, O(n) middle insert/delete
  • LinkedList: O(1) head/tail insert/delete, O(n) random access
  • ArrayList wins most real benchmarks — default to it

🧱 Queue method families

  • Throws: add() / remove() / element()
  • Returns sentinel: offer() / poll() / peek()
  • Prefer the offer/poll/peek family — null-checkable, no try/catch

🔀 ArrayDeque as stack/queue

  • Stack: push()/pop()/peek() on the head
  • Queue: offer() tail, poll() head
  • Prefer over legacy Stack/LinkedList — faster, cache-friendly

⛰️ PriorityQueue

  • MIN-heap by default (opposite of C++!)
  • Max-heap: new PriorityQueue<>(Collections.reverseOrder())
  • Iteration order ≠ sorted order — only poll() guarantees it

🧮 HashMap internals

  • Array of buckets; index = hash(key) & (capacity - 1)
  • Collisions → linked list, treeified to red-black tree past 8 entries (Java 8+)
  • equals()-equal objects MUST share hashCode(), or lookups silently fail

🔗 LinkedHashMap & LRU

  • Hash table + doubly linked list for order
  • accessOrder=true → order by last access, not insertion
  • Override removeEldestEntry() for automatic LRU eviction

🌳 TreeMap / TreeSet

  • Red-Black Tree — O(log n) everything, always sorted
  • ceiling/floor/higher/lower — nearest-value queries HashMap can't do
  • Custom objects need Comparable<T> or an explicit Comparator

⚖️ Comparable vs Comparator

  • Comparable: ONE natural order, defined INSIDE the class (compareTo)
  • Comparator: MANY external orders (compare), as many as needed
  • Comparator.comparing().thenComparing() for multi-key sorts

🚫 Legacy classes to avoid

  • Vector → use ArrayList
  • Stack → use Deque (ArrayDeque)
  • Hashtable → use HashMap or ConcurrentHashMap

🔁 Iterators

  • Iterator: one-directional; ListIterator: bidirectional + set()/add()
  • Fail-fast: throws ConcurrentModificationException (ArrayList, HashMap)
  • Safe removal: it.remove(), or list.removeIf(predicate)

🧰 Arrays vs Collections (utility classes)

  • Arrays.sort/binarySearch/fill/copyOf — operate on raw arrays
  • Collections.sort/max/min/unmodifiableList — operate on Collection objects
  • Arrays.asList() is a FIXED-SIZE view, not a resizable list

🌉 C++ → Java quick map

  • vector→ArrayList, unordered_map→HashMap, map→TreeMap
  • priority_queue (max default) → PriorityQueue (MIN default!)
  • stack→Deque, pair→Map.Entry or int[]/custom class

🎯 DSA pattern → collection

  • Frequency count → HashMap<T,Integer> + merge()
  • Top-K → PriorityQueue, size-capped at k
  • Sliding window / monotonic stack → ArrayDeque
  • Graph adjacency → Map<Integer,List<Integer>> + computeIfAbsent()

🚨 Top interview traps

  • list.remove(int) is index-based; remove(Integer) is value-based
  • Arrays.asList() throws on add()/remove() — fixed-size view
  • Collections.unmodifiableList() is a VIEW, not a true immutable copy
  • PriorityQueue iteration order ≠ sorted order
  • Java's PriorityQueue min-heap default is OPPOSITE of C++'s priority_queue
