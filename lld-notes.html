Foundations

What is LLD?

LLD bridges the gap between a high-level architecture and actual code. It focuses on classes, objects, and their relationships — the skeleton an engineer designs before implementation begins.

HLD
System components, APIs, databases, infrastructure
→
LLD
Classes · Objects · Interfaces · Design Patterns
→
Code
Actual implementation in Java / Python / etc.

The goal of LLD is to produce code that is:

🧹 Clean

  • Readable by another engineer without explanation
  • Minimal duplication (DRY)

🔄 Flexible

  • Open for extension, closed for modification
  • Behaviour changes don't cascade into unrelated classes

🧪 Testable

  • Dependencies can be swapped or mocked
  • Each class has a single, verifiable job
SOLID Principles

SOLID Principles

The 5 foundational rules for writing object-oriented code that won't collapse under change. Every FAANG LLD round tests these — knowingly or not.

S
Single Responsibility Principle
A class should have only one reason to change

Every class or module should do one thing and do it well. If a class handles both invoice generation and email sending, a change in email logic forces you to touch the invoice class — a recipe for silent bugs.

Analogy: A restaurant chef cooks. A waiter serves. If the chef also takes orders, the kitchen gets chaotic when the order system changes.

❌ Violation
✅ Correct
class Invoice {
  // Reason 1: business logic
  void calculateTotal() { ... }
  // Reason 2: persistence — SRP violation!
  void saveToDatabase() { ... }
  // Reason 3: output — another violation!
  void printInvoice() { ... }
}
class Invoice          { void calculateTotal() {...} }
class InvoiceRepository { void save(Invoice i) {...} }
class InvoicePrinter    { void print(Invoice i) {...} }
// Each class has exactly one reason to change
💡 Interview answer: "I'd check if I can describe what the class does without using the word 'and'. If I need 'and', it has multiple responsibilities."
O
Open / Closed Principle
Open for extension, closed for modification

Once a class is tested and deployed, modifying it introduces risk. Instead, extend behaviour by adding new classes or implementations — not by editing proven code. Reduces risk, supports polymorphism, and enables dynamic behaviour through inheritance and interfaces.

Analogy: A power socket is closed for modification. A new appliance extends it via a plug — it doesn't rewire the socket.

❌ Violation
✅ Correct
class DiscountCalculator {
  double calculate(String type, double price) {
    if (type.equals("STUDENT"))  return price * 0.8;
    if (type.equals("SENIOR"))   return price * 0.7;
    // Adding EMPLOYEE forces editing this class!
  }
}
interface DiscountStrategy {
  double apply(double price);
}
class StudentDiscount  implements DiscountStrategy {
  public double apply(double p) { return p * 0.8; }
}
class EmployeeDiscount implements DiscountStrategy {
  public double apply(double p) { return p * 0.6; }
}
// New discount = new class. Zero existing code touched.
💡 Interview answer: "I'd use the Strategy pattern. Adding a new payment method means adding a new class, not modifying PaymentProcessor."
L
Liskov Substitution Principle
Subclasses must be substitutable for their superclass

If class B extends class A, then anywhere A is used, B must work without breaking the application. A subclass extends the parent's capabilities — it never narrows them.

Analogy: If you order a "vehicle" and receive a car — you should be able to drive it. A car that can't go in reverse violates this principle.

⚠️
Classic LSP trap — Square extends Rectangle: Setting width on a Rectangle should not change its height. But a Square must keep them equal — so swapping a Rectangle for a Square breaks calling code. They should both implement a common Shape interface instead.
❌ Violation
✅ Correct
class Bird    { void fly() { /* flaps wings */ } }
class Ostrich extends Bird {
  void fly() {
    throw new UnsupportedOperationException("Can't fly!");
    // Breaks any code that calls fly() on a Bird
  }
}
interface Bird      { void eat(); }
interface FlyingBird extends Bird { void fly(); }
class Eagle   implements FlyingBird { ... }
class Ostrich implements Bird       { ... }
// Ostrich is never passed where FlyingBird is expected
💡 Interview test: "Can I use this subclass everywhere the parent is used without reading the subclass's code?" If no — it violates LSP.
I
Interface Segregation Principle
No client should implement methods it doesn't use

A "fat" interface forces implementing classes to provide empty or irrelevant method stubs — coupling them to things they don't need. Break large interfaces into smaller, role-specific ones. Prevents bloated classes, no forced dependencies, cleaner more maintainable code.

Analogy: A printer interface with print(), scan(), and fax() — a basic printer shouldn't have to implement fax().

❌ Violation
✅ Correct
interface Worker {
  void work();
  void eat();   // Robots don't eat!
  void sleep();  // Robots don't sleep!
}
class Robot implements Worker {
  public void eat()   { /* forced empty impl */ }
  public void sleep() { /* forced empty impl */ }
}
interface Workable  { void work(); }
interface Feedable  { void eat(); }
interface Sleepable { void sleep(); }

class Human implements Workable, Feedable, Sleepable {...}
class Robot implements Workable {
  public void work() { ... } // only what it needs
}
💡 Interview answer: "I'd look for any UnsupportedOperationException or empty method body — those are red flags the interface is too fat."
D
Dependency Inversion Principle
Depend on abstractions, not concretions

High-level modules (business logic) should not depend on low-level modules (databases, email clients). Both should depend on abstractions (interfaces). This decouples layers and makes the system swappable and testable without touching production code.

Analogy: A TV remote doesn't depend on a specific TV model. It depends on an IR protocol (abstraction). You can change the TV without changing the remote.

❌ Violation
✅ Correct
class OrderService {
  // Hardcoded to MySQL — impossible to test or swap
  private MySQLOrderRepository repo =
              new MySQLOrderRepository();
  void placeOrder(Order o) { repo.save(o); }
}
interface OrderRepository { void save(Order o); }

class OrderService {
  private final OrderRepository repo;
  OrderService(OrderRepository repo) { this.repo = repo; }
  void placeOrder(Order o) { repo.save(o); }
}
// Prod: inject MySQLRepo. Tests: inject MockRepo.
💡 Interview answer: "I'd use constructor injection — pass in an interface, not a concrete class. In production inject MySQL, in tests inject a mock. Same service, no code change."
Design Patterns

Design Pattern Categories

Design patterns are reusable solutions to recurring OOP problems. The Gang of Four (GoF) categorised them into three families based on what problem they solve.

Creational

Controls how objects are created. Decouples creation logic from calling code — caller doesn't need to know which concrete class is instantiated.

Singleton Builder Factory Abstract Factory Object Pool Prototype
💡 Example: LoggerFactory.getLogger() returns a Logger — you never call new Logger(). The factory decides FileLogger vs ConsoleLogger.

Structural

Controls how classes and objects are composed so larger structures can solve problems in a flexible, decoupled way.

Decorator Proxy Composite Adapter Bridge Facade Flyweight
💡 Example: Java's BufferedInputStream wraps an InputStream (Decorator) — adds buffering without touching the original class.

Behavioural

Controls how objects communicate and distribute responsibility. Concerned with algorithms and assignment of duties between objects.

State Strategy Observer Chain of Resp. Template Command Iterator
💡 Example: A Kafka consumer uses Observer — multiple subscribers react to the same event without the publisher knowing who they are.
Pattern memory aid

Creational asks:

"Who builds the object, and how do I hide that from the caller?"

Structural asks:

"How do I assemble objects into a larger, flexible structure?"

Behavioural asks:

"Who is responsible for what, and how do objects talk to each other?"

Behavioural Patterns — Deep Dive

Behavioural Design Patterns

Behavioural patterns define how objects communicate and share responsibility. They are the most commonly tested patterns in FAANG LLD rounds because they directly reflect real-world system design decisions.

Behavioural — Pattern 01
♟️

Strategy Pattern

Define a family of algorithms, encapsulate each one, and make them interchangeable at runtime
Category Behavioural
Core Idea Swap algorithms without changing the class that uses them
SOLID Link Open/Closed · Single Responsibility

Problem & Solution

Without Strategy
  • Behaviour controlled by if/else chains
  • Code duplication across similar algorithms
  • Tight coupling — adding new behaviour means editing the class
  • Impossible to swap behaviour at runtime
With Strategy
  • Each algorithm lives in its own dedicated class
  • The context holds a reference to a strategy interface
  • Behaviour swapped by injecting a different concrete strategy
  • New algorithms added without touching existing code

When to Use

Multiple sorting algorithms Payment methods (UPI, Card, Wallet) Discount / pricing rules Compression formats (ZIP, RAR, LZ4) Navigation routes (fastest, shortest, scenic) Auth strategies (OAuth, JWT, API Key)

Generic UML Structure

Strategy Pattern — Generic UML. Context has-a Strategy interface; Concrete strategies implement it.

How It Works — Step by Step

1
Define a Strategy interface with a single method (e.g. execute()). This is the contract every algorithm must fulfil.
2
Create Concrete Strategy classes — one per algorithm. Each implements the interface with its own logic. No shared state between strategies.
3
The Context class holds a reference to the Strategy interface (not a concrete class — this is DIP in action). It delegates execution to whichever strategy is currently set.
4
At runtime, inject or swap the strategy via a setter or constructor. The context's behaviour changes without a single line of its own code being modified.

Deep Dive Example — Payment Gateway

An e-commerce checkout needs to support UPI, Credit Card, and Wallet payments. Each has completely different processing logic. New methods (e.g. BNPL) will be added in future.

// Strategy Interface — the contract every algorithm must implement
public interface PaymentStrategy {
    void pay(double amount);
}
// Concrete Strategy A
public class UPIPayment implements PaymentStrategy {
    private final String upiId;

    public UPIPayment(String upiId) {
        this.upiId = upiId;
    }

    @Override
    public void pay(double amount) {
        System.out.println("Paid ₹" + amount + " via UPI → " + upiId);
        // Real impl: call UPI gateway API
    }
}
// Concrete Strategy B
public class CreditCardPayment implements PaymentStrategy {
    private final String cardNumber;
    private final String cvv;

    public CreditCardPayment(String cardNumber, String cvv) {
        this.cardNumber = cardNumber;
        this.cvv = cvv;
    }

    @Override
    public void pay(double amount) {
        System.out.println("Paid ₹" + amount + " via Credit Card ****"
            + cardNumber.substring(cardNumber.length() - 4));
        // Real impl: call card network (Visa/Mastercard)
    }
}
// Concrete Strategy C
public class WalletPayment implements PaymentStrategy {
    private final String walletId;

    public WalletPayment(String walletId) {
        this.walletId = walletId;
    }

    @Override
    public void pay(double amount) {
        System.out.println("Paid ₹" + amount + " from Wallet → " + walletId);
        // Real impl: debit from wallet balance
    }
}
// Context — holds a reference to the strategy, delegates to it
public class PaymentContext {
    private PaymentStrategy strategy; // depends on abstraction (DIP)

    // Inject at construction time...
    public PaymentContext(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

    // ...or swap at runtime
    public void setStrategy(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

    public void pay(double amount) {
        // Context has NO idea which algorithm runs — pure delegation
        strategy.pay(amount);
    }
}
public class Main {
    public static void main(String[] args) {

        PaymentContext checkout = new PaymentContext(
            new UPIPayment("user@okaxis")
        );
        checkout.pay(1500.0);
        // → Paid ₹1500.0 via UPI → user@okaxis

        // User switches to card — no change to PaymentContext code
        checkout.setStrategy(new CreditCardPayment("4111111111111111", "123"));
        checkout.pay(3200.0);
        // → Paid ₹3200.0 via Credit Card ****1111

        // Adding BNPL tomorrow = new class. Zero existing code changes.
    }
}
💡 Interview answer: "I'd identify that the varying behaviour — payment method, sort algorithm, discount rule — belongs in its own interface. The context delegates entirely. Adding new behaviour is a new file, never an edit to existing ones. This honours both OCP and SRP."
Behavioural — Pattern 02
👁️

Observer Pattern

An object (Observable/Publisher) maintains a list of dependents (Observers) and notifies them automatically on state change
Category Behavioural
Core Idea One-to-many dependency — publisher notifies all subscribers automatically
Also Known As Publish-Subscribe · Event-Listener · Dependents
Without Observer
  • Publisher must know every subscriber class
  • Adding a new subscriber means editing publisher
  • Polling-based solutions waste resources
  • Tight coupling between data source and consumers
With Observer
  • Publisher only knows the Observer interface
  • Any number of observers can subscribe/unsubscribe at runtime
  • Publishers push notifications — no polling
  • Open/Closed — add subscribers without changing publisher

When to Use

Stock price trackers Notification / push systems Weather apps Event-driven architectures UI frameworks (MVC) Kafka consumers Subscription services

Generic UML Structure

Observer Pattern — Generic UML. Observable maintains list of Observers and calls update() on each.

Push Model vs Pull Model

Push — How it works
  • Observable decides what data observers get
  • Passes data as argument to update(ObservableData)
  • Observer is passive — receives exactly what publisher sends
  • Simpler observer implementation
Push — Watch out
  • Observer may receive data it doesn't need
  • Coupling grows if ObservableData structure changes
  • Less flexible — observer can't ask for more

// Observer interface — receives data pushed by the publisher
public interface Observer {
    void update(ObservableData data); // publisher pushes data object
}

// Data transfer object carrying the state change
public class ObservableData {
    public final String stockSymbol;
    public final double price;
    public ObservableData(String s, double p) {
        this.stockSymbol = s; this.price = p;
    }
}
// Observable interface — publisher contract
public interface Observable {
    void add(Observer o);
    void remove(Observer o);
    void notifyObservers();
    void setState(ObservableData data);
}
public class StockMarket implements Observable {
    private final List<Observer> observers = new ArrayList<>();
    private ObservableData latestData;

    @Override public void add(Observer o)    { observers.add(o); }
    @Override public void remove(Observer o) { observers.remove(o); }

    @Override
    public void setState(ObservableData data) {
        this.latestData = data;
        notifyObservers(); // auto-notify on every state change
    }

    @Override
    public void notifyObservers() {
        // PUSH: publisher decides what data observers see
        for (Observer o : observers) {
            o.update(latestData);
        }
    }
}
public class MobileAlertObserver implements Observer {
    private final String userId;

    public MobileAlertObserver(String userId) {
        this.userId = userId;
    }

    @Override
    public void update(ObservableData data) {
        // Receives data pushed by StockMarket — no need to ask for it
        System.out.println("[ALERT → " + userId + "] "
            + data.stockSymbol + " is now ₹" + data.price);
    }
}

// Usage
StockMarket market = new StockMarket();
market.add(new MobileAlertObserver("user_001"));
market.add(new MobileAlertObserver("user_002"));
market.setState(new ObservableData("INFY", 1842.50));
// → [ALERT → user_001] INFY is now ₹1842.5
// → [ALERT → user_002] INFY is now ₹1842.5
Pull — How it works
  • Observer holds a reference to the Observable object
  • update() takes no parameters — just a signal
  • Observer calls getters on Observable to fetch what it needs
  • Observer controls exactly what data it reads
Pull — Watch out
  • Observer is tightly coupled to Observable's API
  • Observer must know which getters to call
  • Slightly more complex observer code

// Pull model — update() has NO parameters
// Observer only knows something changed; it pulls what it needs
public interface Observer {
    void update(); // no args — just a "something changed" signal
}
public class StockMarket implements Observable {
    private final List<Observer> observers = new ArrayList<>();
    private ObservableData latestData;

    // Observers pull this data themselves via the getter
    public ObservableData getLatestData() { return latestData; }

    public void setState(ObservableData data) {
        this.latestData = data;
        notifyObservers();
    }

    public void notifyObservers() {
        // PULL: just signal — no data passed
        for (Observer o : observers) o.update();
    }
    // add/remove omitted for brevity
}
public class PortfolioObserver implements Observer {
    private final StockMarket market; // holds reference to observable
    private final String trackedSymbol;

    public PortfolioObserver(StockMarket market, String symbol) {
        this.market = market;
        this.trackedSymbol = symbol;
    }

    @Override
    public void update() {
        // PULLS only what it needs from the observable
        ObservableData data = market.getLatestData();
        if (data.stockSymbol.equals(trackedSymbol)) {
            System.out.println("Portfolio update: "
                + trackedSymbol + " → ₹" + data.price);
        }
    }
}
💡 Push vs Pull decision: Use Push when all observers need the same data and you want simpler observer code. Use Pull when different observers care about different parts of the state and you want observer autonomy over what they fetch.
💡 Interview answer: "I'd define an Observable interface with add/remove/notify and an Observer interface with update(). The concrete Observable holds the list and calls notify() on setState(). New subscribers just implement Observer — the publisher never changes."
Behavioural — Pattern 03
🔄

State Pattern

An object changes its behaviour dynamically when its internal state changes — as if it changed its class at runtime
Category Behavioural
Core Idea Each state is its own class. The context delegates behaviour to the current state object.
Signature use-case Vending Machine · Traffic Light · Order Lifecycle
Without State Pattern
  • State managed via enums + giant if/switch blocks
  • Adding a new state means editing the context class
  • Transition logic scattered across methods
  • Impossible to test each state in isolation
With State Pattern
  • Each state is an encapsulated class with its own behaviour
  • Context delegates all operations to current state
  • Transitions are explicit — state sets the next state
  • New states added without touching existing ones

When to Use

Vending machines Traffic signals Order lifecycle (Placed → Shipped → Delivered) ATM flow Game characters (idle / running / jumping) TCP connections Document workflows (Draft → Review → Published)

Generic UML Structure

State Pattern — Generic UML. Context has-a State interface. Each concrete state implements behaviour and can trigger transitions.

How It Works — Step by Step

1
Define a State interface with all operations the context supports. Each operation receives the context object as a parameter so the state can trigger transitions.
2
Create Concrete State classes — one per state. Each implements the full interface. If an operation is invalid in that state, throw an exception or log a warning.
3
The Context class has-a State field. All operations delegate directly to the current state — no if/switch logic in the context.
4
Transitions are handled by the state itself — when an operation changes the machine's state, the state calls context.setState(new NextState()). The context never decides transitions.

Deep Dive Example — Vending Machine

A vending machine has four states: Idle (waiting), HasMoney (coin inserted), Dispensing (releasing product), and OutOfStock. Each state permits only certain operations — inserting a coin when it's already dispensing must throw an error, not silently corrupt state.

// State interface — context object passed in so state can trigger transitions
public interface VendingMachineState {
    void insertCoin(VendingMachine ctx);
    void selectProduct(VendingMachine ctx);
    void dispense(VendingMachine ctx);
    void refund(VendingMachine ctx);
}
// Context — has-a State; delegates ALL operations to it
public class VendingMachine {
    private VendingMachineState currentState;
    private int stock;

    public VendingMachine(int stock) {
        this.stock = stock;
        // Start in the right state based on stock
        this.currentState = (stock > 0)
            ? new IdleState()
            : new OutOfStockState();
    }

    // Called by state classes to trigger transitions
    public void setState(VendingMachineState state) {
        this.currentState = state;
    }

    public int  getStock()             { return stock; }
    public void decrementStock()        { stock--; }

    // All public operations delegate to currentState — ZERO if/switch
    public void insertCoin()   { currentState.insertCoin(this); }
    public void selectProduct(){ currentState.selectProduct(this); }
    public void dispense()     { currentState.dispense(this); }
    public void refund()       { currentState.refund(this); }
}
// IdleState — machine is waiting for a coin
public class IdleState implements VendingMachineState {

    @Override
    public void insertCoin(VendingMachine ctx) {
        System.out.println("Coin accepted.");
        ctx.setState(new HasMoneyState()); // ← transition
    }

    @Override
    public void selectProduct(VendingMachine ctx) {
        System.out.println("Please insert a coin first.");
    }

    @Override
    public void dispense(VendingMachine ctx) {
        System.out.println("Cannot dispense. No payment received.");
    }

    @Override
    public void refund(VendingMachine ctx) {
        System.out.println("Nothing to refund.");
    }
}
// HasMoneyState — coin inserted, waiting for product selection
public class HasMoneyState implements VendingMachineState {

    @Override
    public void insertCoin(VendingMachine ctx) {
        System.out.println("Coin already inserted. Select a product.");
    }

    @Override
    public void selectProduct(VendingMachine ctx) {
        System.out.println("Product selected. Dispensing...");
        ctx.setState(new DispensingState()); // ← transition
    }

    @Override
    public void dispense(VendingMachine ctx) {
        System.out.println("Select a product before dispensing.");
    }

    @Override
    public void refund(VendingMachine ctx) {
        System.out.println("Coin refunded.");
        ctx.setState(new IdleState()); // ← back to idle
    }
}
// DispensingState — product is being released
public class DispensingState implements VendingMachineState {

    @Override
    public void insertCoin(VendingMachine ctx) {
        System.out.println("Please wait — dispensing in progress.");
    }

    @Override
    public void selectProduct(VendingMachine ctx) {
        System.out.println("Already dispensing.");
    }

    @Override
    public void dispense(VendingMachine ctx) {
        System.out.println("Product dispensed. Enjoy!");
        ctx.decrementStock();

        // Transition: stock decides next state
        if (ctx.getStock() > 0) {
            ctx.setState(new IdleState());
        } else {
            System.out.println("Machine is now out of stock.");
            ctx.setState(new OutOfStockState());
        }
    }

    @Override
    public void refund(VendingMachine ctx) {
        System.out.println("Cannot refund — already dispensing.");
    }
}
// OutOfStockState — machine is empty; rejects all operations
public class OutOfStockState implements VendingMachineState {

    @Override
    public void insertCoin(VendingMachine ctx) {
        System.out.println("Out of stock. Coin returned.");
    }

    @Override
    public void selectProduct(VendingMachine ctx) {
        System.out.println("Out of stock. Cannot select product.");
    }

    @Override
    public void dispense(VendingMachine ctx) {
        System.out.println("Out of stock. Nothing to dispense.");
    }

    @Override
    public void refund(VendingMachine ctx) {
        System.out.println("Nothing to refund.");
    }
}
public class Main {
    public static void main(String[] args) {

        VendingMachine vm = new VendingMachine(2); // 2 items in stock

        vm.insertCoin();      // → Coin accepted. [Idle → HasMoney]
        vm.insertCoin();      // → Coin already inserted.
        vm.selectProduct();   // → Product selected. [HasMoney → Dispensing]
        vm.dispense();        // → Product dispensed. [Dispensing → Idle]

        vm.insertCoin();      // → Coin accepted. [Idle → HasMoney]
        vm.refund();          // → Coin refunded. [HasMoney → Idle]

        vm.insertCoin();      // → Coin accepted.
        vm.selectProduct();   // → Product selected.
        vm.dispense();        // → Product dispensed. Machine is now out of stock.
                               //   [Dispensing → OutOfStock]

        vm.insertCoin();      // → Out of stock. Coin returned.
    }
}
💡 Key insight: Notice that VendingMachine.insertCoin() has zero if/switch logic. It just calls currentState.insertCoin(this). All decision-making lives in the state classes. Adding a "Maintenance" state tomorrow means one new file — nothing else changes.
💡 Strategy vs State: They look structurally similar but solve different problems. Strategy changes how an operation is performed (algorithm selection). State changes what operations are valid (behaviour based on current lifecycle stage). Strategy is typically set externally; State transitions happen internally.
💡 Interview answer: "I'd model each state as a class implementing a State interface. The context delegates all operations to currentState and exposes setState() for transitions. No if/switch in the context — adding a new state is a new file."
Object Relationships

Has-A vs Is-A

The most misused concept in OOP design. Getting this right is the difference between a flexible system and an inheritance nightmare that collapses on the first requirement change.

Is-A Relationship

→ Inheritance

Class B is a type of class A. B inherits all properties and behaviours of A. Use sparingly — inheritance is the tightest coupling in OOP.

Only use when you can truthfully say the subclass IS the parent — not just shares some behaviour with it.

Dog extends Animal    // ✅ Dog IS an Animal
Car extends Vehicle   // ✅ Car IS a Vehicle
Stack extends Vector  // ❌ Stack is NOT a Vector

Has-A Relationship

→ Composition / Aggregation

Class A contains or uses an instance of class B. This is the preferred relationship — loosely coupled, easily swappable, and mockable in tests.

"Favour composition over inheritance." — Gang of Four

Car has Engine        // ✅ Car HAS-A Engine
Employee has Address  // ✅ Employee HAS-A Address

Has-A comes in two strengths:

🔗
Aggregation — Weak relationship
The contained object can exist independently. If the parent is destroyed, the child lives on.
Department HAS-A Professor — Delete the Department; the Professor still exists and can join another.
🔒
Composition — Strong relationship
The contained object cannot exist without the parent. If the parent is destroyed, the child is too.
House HAS-A Room — Destroy the House; all Rooms cease to exist.
⚠️
Classic interview mistake: Inheriting purely for code reuse — e.g., Stack extends Vector in Java. A Stack should HAVE-A Vector internally, not inherit from one. Otherwise callers can invoke vector.add(0, element) and bypass the Stack's push/pop contract entirely.

🧬 Inheritance vs Composition

  • Is-A (inheritance) → tight coupling, use rarely
  • Has-A (composition) → loose coupling, prefer this
  • Aggregation = parts survive the whole
  • Composition = parts die with the whole

🚨 Red flags to call out

  • Class description needs "and" → SRP violation
  • Editing proven code to add features → OCP
  • Empty or throw-stub method → LSP or ISP
  • new ConcreteClass() inside a service → DIP

🎯 Most asked patterns

  • Singleton, Factory, Builder — Creational
  • Proxy, Decorator, Adapter — Structural
  • Observer, Strategy, State — Behavioural

📝 LLD round structure

  • Clarify requirements (2 min)
  • Identify entities and classes
  • Define relationships (Has-A / Is-A)
  • Apply patterns where appropriate
  • Validate every class against SOLID
