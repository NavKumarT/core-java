Vector Databases & Context Engineering

Two topics that turn out to be one discipline: how retrieval infrastructure actually works under the hood (HNSW, IVF, quantization, the recall-latency-memory triangle), and how to deliberately manage everything an agent sees at the moment it acts — the practice that's replaced "prompt engineering" as the real job in 2026.

00

Why a Vector Database At All

Building directly on Topic 11's embeddings — once meaning is a coordinate, retrieval becomes a search problem, and search problems have known hard tradeoffs.

Topic 11 established that embeddings place semantically similar content near each other in a high-dimensional space. Finding "the most similar passages to this query" is therefore a nearest-neighbor search problem: given a query vector, find the k stored vectors closest to it. The naive approach — compare the query against every single stored vector — is brute-force / exact k-NN search: perfectly accurate, and computationally fine at small scale, but its cost grows linearly with the number of stored vectors. At a few thousand vectors this is instant; at tens of millions it's too slow for an interactive application.

A vector database is purpose-built infrastructure for storing embeddings and answering nearest-neighbor queries fast, at scale — the core value it adds over "just loop through every vector" is an index: a data structure built ahead of time that lets a query skip comparing against most of the stored vectors, at the cost of occasionally missing the true best answer. This trade — approximate but fast, instead of exact but slow — is called Approximate Nearest Neighbor (ANN) search, and it's the single concept every indexing algorithm in this document exists to implement well.

01

Similarity Metrics

Before indexing, you need a precise definition of "close" — three metrics dominate, and the choice isn't arbitrary.

MetricWhat it measuresWhen it's the right choice
Cosine similarityThe angle between two vectors, ignoring their magnitudeThe default for text embeddings — most embedding models are trained such that direction, not magnitude, carries meaning; robust to differences in text length
Dot productCosine similarity scaled by both vectors' magnitudesEquivalent to cosine similarity if all vectors are pre-normalized to unit length (common in modern embedding models) — often faster to compute since it skips the normalization step at query time
Euclidean (L2) distanceStraight-line distance between two pointsCommon for image/audio embeddings and some non-text domains where absolute magnitude carries real signal, not just direction
The mismatch that silently ruins retrieval quality

Using the wrong metric for how an embedding model was trained produces a working-but-degraded system — nothing crashes, results just quietly rank worse than they should. Always check your embedding provider's documentation for the metric they trained and optimized for (nearly always cosine or dot product for text) rather than defaulting to whatever your vector database ships with.

02

The ANN Recall-Latency-Memory Triangle

Every indexing algorithm in this document is a different point in the same three-way trade. Hold this frame before the specifics.

Every ANN index makes a deliberate trade among three properties: recall (what fraction of the true nearest neighbors did the search actually find), latency (how fast is each query), and memory (how much RAM/disk does the index consume). No algorithm wins on all three simultaneously — HNSW leans toward recall and latency at the cost of memory; IVF with quantization leans toward memory efficiency at some cost to recall; the specific parameters you tune (covered per-algorithm below) slide your deployment along these tradeoffs.

How recall is actually measured

Recall@k is computed by comparing an approximate search's top-k results against a ground-truth exact (brute-force) search's top-k results on the same query — the fraction that overlap is your recall score. This is the concrete metric behind every tuning decision in this document, and it's the same underlying idea as Topic 5's evaluation discipline, applied specifically to retrieval infrastructure rather than end-to-end agent behavior.

03 ★

HNSW, Fully Explained

Hierarchical Navigable Small World — the default index for most production vector search in 2026. Worth understanding structurally, not just by name.

HNSW builds a multi-layer graph over your vectors, where each vector is a node connected to its approximate nearest neighbors. The "hierarchical" part is the key trick: the top layer has very few nodes with long-range connections (for fast, coarse jumps across the whole space), and each layer below has progressively more nodes with shorter-range connections (for fine-grained local refinement) — search starts at the sparse top layer, takes big jumps toward the right neighborhood, then descends layer by layer, refining its position, until it reaches the bottom layer for a precise local search.

ParameterWhat it controls
MMax connections per node — higher M means denser graph, better recall, more memory
efConstructionCandidate list size during index build — higher values build a higher-quality graph, at the cost of slower indexing
efSearchCandidate pool size during query time — the main lever for trading query latency against recall, tunable per-query without rebuilding the index

HNSW's real strength: excellent recall even at small efSearch values, sub-millisecond query latency at million-scale, graceful scaling to billions of vectors, and no separate training/clustering phase required before you can start inserting vectors — which is exactly why it's the default choice for most production vector search under roughly 10 million vectors with active writes.

The real weakness

HNSW's memory overhead from storing graph edges is its main cost, and its tail latency spikes when metadata filters are applied at query time, since filtering can force the graph traversal to lose its pruning power (covered in Section 06). The good news: this memory disadvantage is shrinking — techniques like binary quantization (Section 05) combined with HNSW now keep the graph small enough to fit in RAM at scales where unquantized HNSW would not.

04 ★

IVF, Fully Explained

Inverted File Index — older than HNSW, simpler conceptually, and still the right choice under specific, real conditions.

IVF's core idea is clustering: run k-means on your embeddings to find nlist cluster centers ("centroids"). Every stored vector gets assigned to its nearest centroid, producing a set of inverted lists — buckets of vector IDs grouped by which cluster they belong to. At query time, instead of searching the whole dataset, IVF only searches the nprobe clusters whose centroids are closest to the query vector — directly limiting how much of the dataset gets scanned, and giving you an explicit, tunable knob on the recall/latency trade.

ParameterWhat it controls
nlistNumber of clusters — for roughly 10M vectors, a reasonable starting point is around 3,000, tuned experimentally from there based on measured recall and latency
nprobeHow many clusters to search per query — the main recall/latency lever; higher nprobe means searching more of the dataset, better recall, higher latency
When IVF genuinely beats HNSW

IVFFlat is the right call when memory is tight, the dataset is very large (50M+) and mostly static, or index build time matters more than query latency. IVF's latency curve is also smoother under metadata filtering — HNSW's graph traversal loses pruning power when filters are applied, while IVF's cluster-scan structure degrades more gracefully. Choose IVF for tens-to-hundreds of millions of vectors under memory constraints or with heavy filtering; choose HNSW as the default otherwise.

05

Quantization: PQ, SQ, Binary

Compressing vectors to fit more of them in memory — the third lever alongside index choice.

TechniqueHow it worksCompression / recall cost
Scalar Quantization (SQ8)Each float becomes 8 bits instead of the usual 32~4x memory reduction, minimal geometry distortion
Product Quantization (PQ)Split each vector into sub-vectors, encode each sub-vector with a small learned codebookVery high compression (e.g. 64x) at the cost of more meaningful recall loss than SQ
Binary quantizationCollapse each dimension to a single bitExtreme compression, enabling HNSW graphs to fit in RAM at scales where the unquantized version would not, with a modest, often acceptable recall cost for RAG workloads
The two-stage search pattern that makes quantization safe to use

When using quantization, the standard production pattern is a final re-rank step on higher-precision (unquantized) data — search the compressed index to quickly narrow to a candidate set, then re-score that small candidate set using the full-precision vectors for the final top-k. This preserves the speed benefit of compressed search while protecting the quality of what's actually returned — directly the same "cheap-first-pass, expensive-precise-second-pass" structure as Topic 8's reranking, applied to vector compression instead of retrieval-vs-reranking.

IVF-PQ combines both techniques — IVF's clustering narrows the search scope, PQ compresses the vectors within each cluster, delivering both faster search and lower memory than either technique alone. This combination is common at billion-scale deployments where neither pure HNSW nor pure IVF's memory footprint is viable.

06

Filtered Vector Search

Almost every real production query is "find similar vectors WHERE tenant_id = X" — combining ANN search with metadata filtering is a genuinely hard, actively-researched problem, not a solved afterthought.

ApproachTradeoff
Pre-filteringFilter the metadata first, then run exact/brute-force search only within the filtered subset — accurate but loses the ANN speed advantage entirely if the filtered subset is still large
Post-filteringRun ANN search first, then discard results that don't match the filter — fast, but can return too few (or zero) results if the filter is restrictive and the true matches weren't in the initial candidate set
In-graph / integrated filtering (e.g. ACORN-family)The filter is applied during graph traversal itself, so the search only explores nodes that satisfy the filter — the modern, actively-researched approach specifically because pre- and post-filtering both degrade badly at low selectivity (a filter matching a small fraction of the dataset)
Why this specifically breaks at low selectivity

At low selectivity (a filter matching, say, 0.3% of the dataset — common for per-tenant filtering in a large shared index), naive filtered HNSW search can see dramatic recall collapse, because the graph's pruning heuristics were built assuming an unfiltered search space, and most of the nodes the traversal would naturally visit get discarded by the filter. This is an active research area (e.g. RACORN-style adaptive methods reporting large recall recovery and latency improvements over naive filtered HNSW in the low-selectivity regime specifically) — not a solved, boring problem, and worth knowing by name if a system design question raises multi-tenant vector search.

Interview framing

"You're building a multi-tenant RAG system where each query must only search one tenant's data. What goes wrong with a naive implementation?" — If tenants share one HNSW index and you apply the tenant filter as a post-filter, recall can collapse badly for tenants with a small fraction of the total data, since the graph traversal's pruning assumed an unfiltered search space. Mitigations: use a vector database with native multi-tenancy that applies filters during traversal (Qdrant's indexed payload fields, Weaviate's tenant model), or consider separate indexes/namespaces per tenant (Pinecone's namespace model) when tenant counts are manageable, trading some index-management overhead for guaranteed filter correctness.

07 ★

Vector DB Comparison, 2026

Five options cover the large majority of production RAG deployments. Know the honest tradeoffs, not the marketing copy.

Database2026 positioning
pgvectorThe 2026 default for most RAG apps under ~10M vectors: zero new infrastructure if you're already on Postgres, transactional consistency, and — with HNSW indexes, half-precision storage, and binary quantization — roughly 90% of dedicated-vector-DB performance. pgvector 0.8.2 (Feb 2026) supports HNSW, IVFFlat, halfvec, sparsevec, and binary quantization on one SQL surface.
QdrantThe performance-focused open-source choice — its Rust implementation gives a measurable latency edge (roughly 10-25% faster than Weaviate/Milvus on common workloads in one benchmark, p99 ~12ms vs ~16-18ms at 10M vectors). Strong native multi-tenancy via indexed payload fields.
WeaviateThe strongest choice specifically for hybrid search — built-in BM25 is a genuine, real advantage over competitors requiring you to bolt on lexical search separately. Native multi-tenancy is built into its data model.
PineconeZero-ops, fully managed, predictable serverless pricing — the right choice when you have budget and no appetite for infrastructure management. Becomes expensive enough at scale ($5,000+/month territory) that self-hosting's ops cost is often justified for teams with the capability.
MilvusJustified only at 100M+ vectors with a dedicated ops team — its tiered storage (RAM/NVMe/S3 with automatic promotion/demotion) is a genuine advantage at that scale, but its operational complexity exceeds Qdrant's for typical workloads and isn't worth adopting below that scale threshold.
ChromaExcellent for prototyping — runs in-process in Python with zero external service and zero configuration. Lacks the production operational tooling (HA, snapshots, monitoring integrations) of the dedicated options above; not a production recommendation at meaningful scale.
The advice that matters more than the whole table

For most workloads, the vector store is the least interesting engineering problem — retrieval quality, chunking strategy (Topic 8), metadata schema, and the evaluation pipeline (Topic 5) matter far more than whether you chose Qdrant over Weaviate. Start with pgvector; migrate only when you have a measured reason to, and always benchmark with your own data and query patterns rather than trusting published synthetic benchmarks.

Context Engineering, Defined

The discipline that's absorbed "prompt engineering" as one of its sub-parts. Know its origin and its precise scope.

The term was given its clearest articulation by Andrej Karpathy in June 2025, who argued "prompt engineering" understates the actual work — prompt engineering suggests crafting a single instruction, while context engineering describes the broader discipline of filling the entire context window with the right information: instructions, retrieved knowledge, memory, tool descriptions, and prior outputs, all structured so the model can actually use them effectively.

Prompt engineeringContext engineering
ScopeA static artifact — the system prompt text a developer writes, reviews, and commitsA runtime pipeline — retrieval, reranking, summarization, schema injection, token budget management, and assembly logic, executing before every model call
OwnershipTypically owned by whoever writes the system promptTypically owned by platform teams, living alongside API servers, data pipelines, and observability tooling
Question it answers"How do I ask?""What does the agent know, see, and remember at the moment of action?"

This is exactly a superset relationship: prompt engineering happens within the context window, while context engineering determines what fills that window in the first place. Prompt engineering isn't obsolete — it's one tool inside the larger context-engineering toolkit.

Why this discipline exists at all — the actual production data

According to LangChain's 2026 State of AI Agents report, 57% of organizations now have agents in production, and quality remains the top barrier to deployment — and most quality failures trace not to model capability but to poor context management: the model had the wrong information, too much information, or stale information at the moment it needed to decide. Context engineering is the direct response to that finding.

10 ★

Write / Select / Compress / Isolate

LangChain's Lance Martin formalized the discipline into this four-verb taxonomy — the framework with the most staying power, and the one worth having ready in an interview.

Write — persist context outside the window so it survives

A model is stateless; every call starts from nothing unless you explicitly carry information forward. "Write" covers everything baked into the system before a user interaction happens — system prompts, persona instructions, rules, guardrails — the "constitution" of the system, unchanging per request. This is the layer that overlaps most with traditional prompt engineering, and it directly connects to Topic 9's working/episodic memory writing.

Select — retrieve only what's relevant, on demand

Retrieval-augmented generation is context engineering in its purest form — you're not changing the prompt, you're changing what knowledge the model has access to when it generates. The engineering challenge isn't writing the query; it's the pipeline that retrieves the right documents, ranks them, filters noise, and fits the result within budget — precisely Topic 8's entire subject, reframed as one pillar of a larger discipline. "Select" also covers tool descriptions and memory retrieval (Topic 9) — loading information on demand rather than upfront.

Compress — reduce tokens while retaining what matters

Summarization, trimming old messages, chunk deduplication, LLMLingua-style compression — techniques that reduce token volume without discarding signal. This is precisely Topic 7's context compaction material and Topic 9's memory consolidation, viewed through the context-engineering lens: both exist because an ever-growing context degrades reasoning accuracy and inflates cost even when it technically still fits.

Isolate — keep unrelated context separate

Split context across separate agents or components so each gets only what it needs, rather than dumping everything into one shared window — precisely Topic 3's isolation boundary concept (Anthropic's orchestrator-worker subagents getting fresh, self-contained context) and the same principle behind sandboxing raw tool output into structured, filtered results instead of injecting everything a tool returns directly into the agent's context.

four_pillars_in_one_langgraph_node.py
def assemble_context(state: AgentState) -> dict:
    # WRITE: static system instructions, unchanging per request
    system = load_system_prompt()

    # SELECT: retrieve only what's relevant to the current turn (Topic 8's pipeline)
    query = state["messages"][-1].content
    retrieved_docs = hybrid_retriever.invoke(query, top_k=5)

    # COMPRESS: summarize older turns instead of keeping full history verbatim
    history = state["messages"]
    if count_tokens(history) > COMPACTION_THRESHOLD:
        history = compact_history(history)   # Topic 7 / Topic 9's consolidation

    # ISOLATE: pass a sub-agent only its own scoped slice, not the full state
    subagent_context = {"task": state["current_subtask"], "docs": retrieved_docs}

    return {"assembled_context": build_prompt(system, history, retrieved_docs)}
Interview framing

"Walk me through the Write/Select/Compress/Isolate framework and map each pillar onto something we've already discussed." — Write is the static system prompt layer, overlapping with traditional prompt engineering and Topic 9's memory-writing. Select is retrieval — Topic 8's entire RAG pipeline, plus tool and memory selection. Compress is Topic 7's context compaction and Topic 9's memory consolidation — reducing tokens without losing signal. Isolate is Topic 3's isolation-boundary principle for multi-agent systems, and the same logic behind sandboxing raw tool output before it enters context. A production AI agent typically uses all four simultaneously, not just one.

Production Pitfalls

What actually goes wrong.

  • Mismatched similarity metric. Using Euclidean distance on an embedding model trained/optimized for cosine similarity degrades results silently — nothing errors, ranking just gets quietly worse.
  • Choosing a dedicated vector DB before you need one. Under ~10M vectors, pgvector with modern quantization closes most of the performance gap — a separate vector database adds real operational overhead most teams don't need yet.
  • Naive post-filtering on a multi-tenant HNSW index. Recall can collapse badly for tenants with a small slice of a shared index — use native multi-tenancy features or separate indexes instead of filtering after the fact.
  • Quantizing without a re-rank stage. Compressed search alone trades away real accuracy — always re-score the narrowed candidate set against full-precision vectors before returning final results.
  • Treating "prompt engineering" as the whole job. A well-crafted system prompt with an unmanaged, ever-growing, unfiltered context window will still degrade — context engineering's Select/Compress/Isolate pillars aren't optional extras once an agent runs multi-step.
  • Dumping raw tool output directly into context. Violates the Isolate principle — sandbox tool execution and return structured, filtered results, not an entire raw API response.
  • Benchmarking a vector DB choice on synthetic data. Published benchmarks routinely mislead — always validate index/DB choice against your own embeddings, query patterns, and filter conditions.

Interview Cheat-Sheet

Grouped by depth.

Explain HNSW well enough to draw it on a whiteboard.core

A multi-layer graph where the top layer is sparse with long-range connections for fast coarse navigation, and each layer below is progressively denser with shorter connections for local refinement. Search starts at the top layer, greedily jumps toward the query's neighborhood, then descends layer by layer refining position, ending with a precise search at the dense bottom layer containing every vector. Key parameters: M (connections per node, trades memory for recall), efConstruction (build-time quality), efSearch (query-time recall/latency knob, tunable without rebuilding).

When would you choose IVF over HNSW?core

When memory is tight, the dataset is very large (50M+) and mostly static, or build time matters more than query latency — IVF's cluster-based structure is more memory-efficient than HNSW's graph edges, and combines more gracefully with quantization for extreme compression. It's also the safer choice under heavy metadata filtering, since HNSW's tail latency spikes when filters reduce the graph's effective pruning power.

Explain the two-stage search pattern used with quantized indexes.core

Quantization compresses vectors for fast, memory-efficient search but introduces some accuracy loss. Production systems address this with a re-rank stage: run the fast approximate search over compressed vectors to narrow to a small candidate set, then re-score just that candidate set using full-precision vectors for the final top-k. This preserves most of quantization's speed and memory benefit while protecting the accuracy of what's actually returned to the user.

Why does filtered vector search break down at low selectivity, and how would you fix it for a multi-tenant system?architecture

Naive filtering (pre- or post-) assumes the underlying ANN index's pruning heuristics still work correctly once most candidates are excluded by the filter — at low selectivity (a filter matching a small fraction of the dataset, e.g. one tenant's slice of a large shared index), this breaks down and recall can collapse. Fixes: use a vector database with native multi-tenancy applying filters during graph traversal itself (Qdrant's indexed payload fields, Weaviate's tenant model), or maintain separate indexes/namespaces per tenant when tenant count is manageable, accepting more index-management overhead for guaranteed correctness.

A team wants to adopt Milvus for a new RAG project with 2 million documents. What's your recommendation?design

Push back — Milvus earns its operational complexity only at 100M+ vectors with a dedicated platform team; at 2 million vectors, pgvector (if already on Postgres) or a lighter dedicated option like Qdrant will deliver comparable retrieval quality with far less operational overhead. The vector store is rarely the interesting engineering problem at this scale — retrieval quality, chunking, and evaluation infrastructure matter far more, and over-engineering the storage layer early is a common, avoidable mistake.

What's the actual difference between prompt engineering and context engineering?context-eng

Prompt engineering is a static artifact — the wording of a system prompt, reviewed and committed like code. Context engineering is a runtime pipeline — retrieval, reranking, summarization, memory selection, tool output filtering, and token budget management, executing before every model call to determine everything the model sees at the moment it acts. It's a superset relationship: prompt engineering happens within the context window; context engineering determines what fills that window.

Map the Write/Select/Compress/Isolate framework onto a real multi-agent RAG system you'd design.context-eng

Write: a lean, versioned system prompt per agent role, not a single bloated shared prompt. Select: a hybrid-search-plus-reranking retrieval pipeline (Topic 8) feeding only the top few relevant chunks, not a full document dump. Compress: conversation history summarized past a token threshold before it crowds out current task state (Topic 7), and episodic memory consolidated into semantic facts over time (Topic 9). Isolate: each subagent in an orchestrator-worker topology (Topic 3) gets a fresh, scoped context containing only its specific task — not the full shared history — and raw tool outputs are filtered into structured summaries before entering any agent's context at all.

Why might an agent's quality degrade even though you haven't changed the system prompt or the model?context-eng

Because prompt engineering alone doesn't control the rest of what fills the context window — a growing conversation history without compaction, a retrieval pipeline degrading due to stale data or index drift, or an increasingly cluttered tool-output stream can each independently erode quality with zero prompt changes. This is precisely why context engineering treats context assembly as its own runtime pipeline requiring its own observability and testing, not something a static, unchanging system prompt can account for on its own.

Glossary

Every term used in this document.

ANN (Approximate Nearest Neighbor)
Search that trades perfect accuracy for speed via an index, as opposed to exact brute-force k-NN.
Recall@k
Fraction of true top-k nearest neighbors an approximate search actually finds, vs. exact search.
HNSW
Hierarchical Navigable Small World — a multi-layer graph ANN index, the 2026 production default under ~10M vectors.
M / efConstruction / efSearch
HNSW's core tuning parameters, controlling graph density, build quality, and query-time recall/latency respectively.
IVF (Inverted File Index)
Clustering-based ANN index; searches only the nearest clusters (nprobe of nlist) to a query.
Product Quantization (PQ)
Vector compression via sub-vector codebooks; high compression, moderate recall cost.
Scalar / Binary Quantization
Simpler compression reducing per-dimension precision; less aggressive than PQ, lower recall cost.
Filtered vector search
Combining ANN search with metadata filters; degrades badly at low selectivity without integrated (in-graph) filtering.
Context engineering
The discipline of managing everything an agent sees at the moment of action — instructions, memory, retrieved knowledge, tool outputs.
Write / Select / Compress / Isolate
LangChain's four-pillar taxonomy for context engineering strategies.
