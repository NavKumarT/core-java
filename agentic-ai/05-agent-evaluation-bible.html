Why Agent Evaluation Is a Different Problem

The single distinction every eval conversation in an interview comes back to. Get this exactly right before anything else.

An LLM eval is a function from (input, output) to a score. An agent eval is a function from trajectory to a score, where the trajectory is the ordered sequence of system prompt, user input, agent reasoning, tool calls (name plus arguments plus return value), retrieval results, intermediate LLM calls, final response, and outcome metadata. Two runs of the same task can take completely different paths and both be correct, or both be wrong for different reasons — that changes what "good" means.

The example every senior interviewer uses

Picture a support agent that gives a polite, accurate answer at every step but never actually resolves the ticket. Turn-level scoring says it is great. The user says it failed. A held-out benchmark and a final-answer pass/fail tells you almost nothing about whether the agent looped before answering, called the wrong tool and recovered, leaked its reasoning, or left the user frustrated three turns in.

According to LangChain's 2026 State of AI Agents report, 57% of organizations now have agents in production, and quality is the #1 barrier to deployment. This is not a niche concern — it is the current bottleneck of the entire field, which is exactly why it's the round interviewers weight most heavily.

The Diagnostic Stack — Outcome, Trajectory, Component

Three layers, used as a funnel: cheap and blunt at the top, expensive and precise at the bottom.

LayerQuestion it answersCost
OutcomeDid the agent's full run actually accomplish the user's goal? — simple, but blunt: tells you something went wrong, not whereLowest
TrajectoryLooks at the plan, reasoning steps, tool calls, retries, and handoffs that produced the result — this is where the real diagnostic signal livesMedium
ComponentTests individual components — retrievers, models, sub-agents, tool calls, RAG pipelines — to identify exactly where failures or bottlenecks occurHighest (most granular)

Use these levels as a diagnostic stack: outcome first, then path, then failing component — don't jump straight to expensive component-level testing on every case; reserve it for the failures outcome and trajectory eval flag as worth digging into.

02

Outcome / Task Completion Evaluation

The blunt, cheap, non-negotiable first layer.

Task Completion, also known as task success or goal accuracy, measures whether an agent completed a user-given task. The definition of "done" depends on the task; for tool-calling, planning, and autonomous agents this metric is often the clearest end-to-end signal of whether the agent actually worked. Grading methods: exact or rule-based matching for deterministic outputs, code-based assertions and schema checks, model-based grading where an LLM judges the output against criteria, and human review for the cases automation cannot cover — most production suites combine all of these, using cheap deterministic checks where possible and LLM-as-judge only where nuance is required.

Practical stance

Use outcome metrics for initial validation and continuous monitoring due to lower computational cost; use trajectory metrics for debugging and process improvement, showing how agents work rather than just whether they achieve business goals.

Trajectory Evaluation — Where the Real Signal Lives

Five categories, and the flat-metric trap that makes teams think they're done when they aren't.

CategoryWhat it checks
Goal completionDid the agent finish the user's task? The outcome metric, and the only one users directly care about.
Tool selection accuracyDid it pick the right tool at each step?
Tool argument correctnessDid it pass the right parameters?
Trajectory efficiencyHow many redundant steps, retries, and loops occurred?
Final answer qualityGroundedness, factuality, safety of the final response.
The flat-metric trap

A flat metric like AnswerRelevancy on the final response misses the eight retries, three retrieval misses, and one wrong tool call that produced the right-looking answer. An agent that scores perfectly on outcome but wandered wildly to get there will keep wandering on harder inputs where it doesn't get lucky — trajectory eval is what catches that before it becomes a production incident.

trajectory_eval_shape.py
trajectory = {
    "system_prompt": ...,
    "user_input": ...,
    "steps": [
        {"reasoning": ..., "tool_call": {"name": ..., "args": {...}}, "observation": ...},
        # ... every intermediate step, in order
    ],
    "final_response": ...,
    "outcome_metadata": {"success": True, "tokens_used": 4210, "latency_ms": 3800},
}
# an agent eval scores THIS whole object, not just final_response
04

LLM-as-Judge Techniques

Three shapes of judging, and when to reach for each.

LLM-as-a-Judge uses an LLM to score, classify, or compare another LLM's outputs — you define what "good" means for your application, then run that judgement repeatedly across datasets, CI/CD pipelines, and production traces.

TechniqueShapeBest for
Pointwise / G-EvalScore one output against a custom rubric, aloneCustom quality criteria specific to your application
Pairwise / ArenaGEvalCompare two outputs, pick a winner (or tie)Prompt or model comparisons, A/B testing changes
DAG-based / DAGMetricStrict multi-step scoring logic, deterministic branches with LLM judgment at leavesComplex pass/fail criteria that need auditable step-by-step logic, not a single freeform score
Reliability lift from technique, not just prompt wording

Design judge prompts with explicit rubrics, few-shot examples, and structured JSON outputs requiring evidence before scoring; chain-of-thought prompting and few-shot examples improve scoring reliability by over 85%. Validate reliability by measuring Cronbach's alpha across multiple independent runs to assess internal consistency, and calibrate against human expert evaluation, targeting 0.80+ Spearman correlation for production deployment alignment.

Give the judge an escape hatch

Agent-grade judges often show inconsistent strictness and overconfidence when evaluation rubrics are underspecified — a simple reliability trick is to give the judge an explicit "Unknown" option when evidence is insufficient, reducing hallucinated verdicts.

LLM-as-Judge Biases, Fully Mapped

Position bias

A systematic preference for the response appearing in a particular position (first or last), as large as 10–15 percentage points. Mitigation: swap augmentation — evaluate each pair in both orders, accept a consistent judgment, record an inconsistent one as a tie; calibration prompting explicitly instructing the judge not to be influenced by presentation order; ensemble judging across multiple position orderings; and chain-of-thought forcing, requiring a detailed rationale before the verdict, which reduces reliance on superficial positional cues. Note: position-neutrality language in the prompt alone has near-zero effect — the bias lives in the decode, not the rubric, which is why swap augmentation (an architectural fix) beats prompt wording (a rubric fix) for this specific bias.

Verbosity bias

Longer responses are systematically preferred even when the additional content is irrelevant or repetitive. Mitigation: instruct the judge explicitly to penalize unnecessary length and focus on information quality over quantity, or truncate responses to a fixed length before judging. Length-neutrality language in the prompt reduces this bias by roughly half — unlike position bias, prompt wording actually helps here. Note this bias is heterogeneous across models when measured length-aware: some models show it strongly, one major lab's model shows the opposite tendency, and others are close to neutral — worth checking empirically for your specific judge model rather than assuming.

Self-enhancement / self-preference bias

Judges rate their own model's outputs higher — a special risk in automated training loops where a model's judgments feed back into training itself. Mitigation: use an independent model — from a different provider or lineage — as the judge whenever evaluating that same model's outputs; ensemble evaluation using multiple models from different families reduces reliance on any single model's self-preference.

Format / "beauty" bias

Privileging superficial features like formality or stylistic polish over deeper content quality. Mitigation: explicitly separate correctness criteria from style criteria in the rubric — score them as distinct dimensions rather than one blended "quality" score, so polish can't substitute for accuracy in the aggregate.

Bandwagon / authority / compassion-fade biases

Bandwagon-effect bias: judgments skew toward stated majority opinions in the system instruction. Authority bias: undue weight given to claims that cite an authoritative-sounding source. Compassion-fade: judgments shift when identifiable names are attached vs anonymized outputs. Mitigation: anonymize model/source identifiers before judging, and never embed claimed consensus ("most experts agree...") in the judge's input context.

Calibration drift

A judge model version bump can shift the mean score and narrow the distribution while your CI gate keeps passing — the judge changed, the rubric didn't, and the signal stops meaning what you thought it meant the day the model rolled. Mitigation: pin judge model versions explicitly, re-run your human-calibration check whenever the judge model changes, and monitor score distribution shape (not just the mean) over time for unexplained narrowing or shifting.

The aggregate reliability number worth knowing

Zheng et al. show that LLM judges can achieve over 80% agreement with humans, and analysis of over 150,000 evaluation instances across 22 tasks with 15 LLM judges found strong average consensus — more than 80% of cases yield agreement from at least 2 of 3 judges, with full unanimity in about 23%; models sharing architecture and training lineage tend to exhibit higher internal agreement, indicating shared systematic bias patterns, and high-disagreement "hard cases" are strongly associated with minimal answer-quality gaps. The practical takeaway: majority voting or aggregation across diverse model families mitigates idiosyncratic and familial biases in single-model judgments — an ensemble of judges from different labs is measurably more reliable than one judge, however strong.

The question every eval-focused interview asks

"How would you validate that your LLM judge is trustworthy before relying on it?" — Full answer: (1) calibrate against a human-labeled golden set, targeting ≥0.80 Spearman correlation; (2) run swap augmentation to detect and correct position bias; (3) test length-neutrality by comparing scores on paraphrased responses of different lengths; (4) use a judge from a different model family than the system under test to avoid self-preference; (5) re-validate whenever you change the judge model version; (6) for high-stakes decisions, ensemble multiple judges and treat disagreement itself as a signal for human review, not just noise to average away.

Benchmarks: tau-bench, SWE-bench, GAIA & More

Know exactly what each measures, how it's scored, and — critically — where it stops telling you anything about your own agent.

BenchmarkDomainScoring method
τ-bench / τ²-benchRealistic customer-service dialogue (retail, airline, telecom) with an LLM-simulated user, domain APIs, and policy guidelinesCompares final database state against an annotated goal state; introduces pass^k to measure reliability across repeated trials, not just one-shot success
SWE-bench (Verified)Real GitHub issues and associated pull requests across popular Python repositoriesWhether the patch resolves the issue and passes the repository's hidden unit test suite
GAIA466 human-designed, real-world questions requiring web browsing, multi-modal, and multi-file handlingExact match against a single reference answer; graded across three escalating difficulty levels
AgentBenchMultiple interactive environments — OS commands, databases, knowledge graphs, web browsing — assessing cross-domain generalizationPer-environment task success; best used to compare architectures and identify where capability transfer breaks down, not to predict production performance directly
WebArena / OSWorldAutonomous web navigation / general real-desktop computer useTask-specific success criteria checked against final browser or OS state
METR HCAST / Time HorizonsLong-horizon autonomyThe longest task an agent can finish 50% of the time — a direct measure of how far autonomous execution holds up before failing
The pattern across every serious benchmark

The pattern across the serious benchmarks is execution-based verification: tau-bench checks the database state, SWE-Bench runs the test suite, tau2-bench's pass^k measures whether the agent succeeds reliably across attempts rather than once. A benchmark that only checks tool-call syntax or final text would pass agents that look right and do the wrong thing. The same standard should apply to your own eval harness: verify the actual end state, not just the last message.

The gap that trips people up

Public benchmark scores serve two valid purposes: coarse model shortlisting and regression detection. They do not predict production performance — a 20-40 percentage point drop from public benchmark to real task distribution is routinely observed. Private evals on your own task samples are the actual production-readiness signal. Agent scores are also the most harness-sensitive numbers in AI — the same model can score very differently under different scaffolds, so treat a small point gap as noise and only compare scores measured within the same harness.

Interview framing

"How do benchmarks differ from an evaluation framework, and how do you use them together?" — Benchmarks (tau-bench, SWE-bench, GAIA) are fixed, standardized task sets with public leaderboards, used for coarse model comparison and regression detection. Frameworks (LangSmith, DeepEval, Ragas) are tooling you point at your own agent and your own task distribution. Benchmarks tell you which base model or scaffold is roughly in the right range; they don't replace running your own private eval set on your actual production task mix, where the real go/no-go decision has to be made.

RAG-Specific Evaluation (RAGAS)

Four metrics, two axes — retrieval quality and generation quality — and the exact formulas behind each.

MetricAxisDefinition
FaithfulnessGenerationFraction of claims in the answer that can be inferred from the retrieved context — computed by extracting statements from the answer via an LLM, then verifying each against the context: F = |supported statements| / |total statements|
Answer RelevancyGenerationSemantic similarity between the answer and the question — computed by generating several questions the answer could plausibly address, then averaging their embedding similarity to the original query
Context PrecisionRetrievalWhether the relevant context chunks are ranked higher — high values indicate the retrieved set is well focused with little irrelevant material
Context RecallRetrievalFraction of the ground truth that is covered by retrieved context — compares each statement in a ground-truth answer against the retrieved context to check presence
The production incident this exact split explains

A legal research RAG ships and scores 0.91 faithfulness on the offline eval set. Three weeks into production, customers complain that 1 in 6 responses misses a key statute. The team checks faithfulness in the dashboard: still 0.91. They check context recall: 0.62. The retriever was missing a second statute on multi-hop questions; the generator was answering coherently from the partial context it did have, so faithfulness stayed high. No retrieval-stage metric on the dashboard surfaced the regression. Faithfulness alone cannot catch a retrieval problem — you need both retrieval-side and generation-side metrics on the same dashboard, always, because a generator can be perfectly faithful to incomplete evidence.

Beyond the core four, Ragas also ships context entities recall, noise sensitivity, answer semantic similarity, answer correctness, tool call accuracy, and agent goal accuracy — the last two specifically extending RAGAS-style evaluation into agentic (not just retrieval) workflows.

ragas_eval.py
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall

result = evaluate(
    dataset=eval_dataset,   # question, contexts, answer, ground_truth per row
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
)
The blind spot even RAGAS doesn't cover

Standard eval metrics assume a trustworthy index — a system can score 0.95 on faithfulness and still return wrong business answers if the retrieved content is stale, unowned, or misaligned with the canonical source. Context trustworthiness — freshness, ownership, lineage — sits upstream of every RAGAS metric and needs its own governance check, not just retrieval scoring.

Interview framing

"Your RAG system's faithfulness score looks great but users are complaining about incomplete answers. What do you check?" — Context recall specifically, not faithfulness. High faithfulness with low context recall is the exact signature of a retrieval gap: the generator is being perfectly honest about incomplete evidence. Faithfulness measures whether the answer respects what was retrieved; it says nothing about whether what was retrieved was enough.

Building Eval Datasets

The most underrated engineering effort in the entire eval pipeline.

The most underrated engineering challenge in agent evaluation is actually building the test data. Unlike image classification where you can label a photo in 10 seconds, a single agent eval case — with its full task description, tool environment, expected trajectory, and gold output — can take hours to construct correctly.

SourceDescriptionVolume target
Hand-crafted goldensExperts write tasks and validate expected trajectories manually — highest quality, but expensive50–100 as your anchor set, covering your most critical user scenarios
Production trace miningCollect real user interactions, filter for interesting or failing cases, add ground-truth labels — high ecological validity since these are real problems real users hit≥500 cases before trusting aggregate metrics
Synthetic generationUse a strong LLM to generate task variations from a seed setScale up coverage of edge cases the first two sources under-represent
Practical sizing rule for RAG specifically

Start with 100 to 200 queries, then add batches of 25 until your key metrics (faithfulness, retrieval recall, answer accuracy) change by less than 2 points across two consecutive runs — a defensible stopping rule, not just a fixed range. Use stratified sampling from real traffic so coverage matches production mix: factual lookup, multi-hop reasoning, policy or compliance questions, and ambiguous cases.

Eval-Driven Development & the Closed Loop

The idea that separates teams that ship reliable agents from teams stuck in a debugging cycle.

Treat the eval as the static endpoint and your agent drifts. Treat it as a loop and the agent compounds. An agent eval guide is incomplete without the closed-loop pattern: offline eval feeds the CI gate, the CI gate feeds production trace eval, trace eval feeds an error feed, the error feed feeds optimization, and optimization ships back through CI.

Every release ages your eval set the day it lands — new intents, new prompt revisions, new tool schemas, new retrieval indexes, new traffic shapes. A static offline pass is a necessary condition; it is never sufficient.

CI gating in practice

Integrate evaluation into CI/CD with progressive canary deployment patterns — run the offline eval suite pre-merge as a hard gate (block on regressions and safety violations), then run the same rubric against a sample of live production traffic post-deploy, and route any drift or new failure clusters back into the eval dataset as new golden cases, so the suite itself grows in step with what production actually throws at the agent.

Online / Production Evaluation

LLM-as-judge is the wrong tool for evaluating every single production turn. Know why, and what replaces it.

Each LLM-as-judge call is a full model call, so it's too expensive to run on every production turn, and the same trajectory can score differently across runs. LLM-as-judge is fine for offline scoring on a held-out sample, where cost and variance are bounded and you can ensemble or human-review the edge cases — it is the wrong tool for the per-turn job.

The right shape for per-turn production labels

Per-turn evaluation is a classification problem: take one turn, return a label — not a full LLM-judge call. A small, cheap, fast classifier (fine-tuned or distilled specifically for your failure taxonomy) can label every production turn in milliseconds, feeding those labels into your eval set, fine-tuning data, and monitoring dashboards, while full LLM-as-judge stays reserved for offline batch scoring on a sampled subset.

SignalWhat it catches
Topic relevancyWhether questions and responses stay within the application's intended domain
Negative sentiment detectionUser frustration — often indicates task failure even when the response was technically accurate
Policy violation / safety monitoringToxicity in inputs and outputs, prompt injection attempts, domain-specific policy violations
Human annotation queuesStructured expert review of sampled or flagged traces, building the next round of golden eval cases

Statistical Rigor

Numbers to actually cite when asked "how do you know your eval is trustworthy."

MetricWhat it validatesTarget
Spearman correlation (judge vs human)Judge alignment with expert human judgment≥0.80 for production deployment alignment
Cronbach's alphaInternal consistency of the judge across repeated independent runsHigher is more consistent; run multiple passes and check variance before trusting a single score
pass^kReliability of agent behavior across multiple trials of the same task, not just one-shot successReport alongside pass@1 — a large gap between the two signals inconsistency, not just capability
Inter-rater reliability (Cohen's kappa)Agreement between human reviewers on high-stakes manual audits≥0.60 in enterprise legal/medical audit workflows, with two independent reviewers
The pass^k reveal

Even state-of-the-art function-calling agents (gpt-4o) succeed on under 50% of tau-bench tasks and are terribly inconsistent — pass^8 under 25% in the retail domain. A model that looks strong on pass@1 can be dramatically less reliable across repeated attempts at the identical task — this is exactly the gap outcome-only, single-run evaluation hides.

13

Failure Modes & Anti-Patterns

What actually goes wrong when evaluation is treated as a checkbox instead of infrastructure.

  • Scoring only the final message. Misses the entire trajectory — an agent can accumulate retries, wrong tool calls, and loops while still landing on a correct-looking final answer.
  • Trusting a single LLM judge run. No swap augmentation, no ensemble, no human calibration check — a single unvalidated judge call is exactly as unreliable as the documented bias magnitudes above.
  • Treating a static offline eval set as permanently sufficient. Every release ages your eval set — new intents, prompt revisions, tool schemas, and traffic shapes all erode a static suite's coverage over time.
  • Confusing faithfulness with retrieval completeness in RAG. The legal-research incident above — high faithfulness, silently low context recall — is one of the most common production surprises in RAG systems specifically.
  • Reporting only pass@1 on a reliability-sensitive task. Hides the pass^k gap that reveals whether an agent is actually consistent or just got lucky once.
  • Relying on public benchmark scores as a production-readiness signal. A 20-40 percentage point drop from public benchmark to real task distribution is routinely observed — private evals on your own data are the actual signal.
  • No per-turn production monitoring, only periodic offline batch eval. Misses drift and emerging failure clusters between eval runs — the closed-loop pattern exists specifically to prevent this gap.

Decision Framework

What to build, in what order, for a new agent with no eval infrastructure yet.

StepWhat to build
1Deterministic outcome check (schema validation, exact match, code assertion) for anything that can be checked without an LLM — cheapest, run it first and always
250–100 hand-crafted golden trajectories covering your most critical scenarios, with expected tool calls annotated, not just expected final answers
3LLM-as-judge for what can't be checked deterministically — with explicit rubric, few-shot examples, structured output, and an "Unknown" escape hatch

Interview Cheat-Sheet

Every question grouped by depth — this is the round that fails most candidates, so this section is deliberately the longest in the document.

Core distinctions

Why is evaluating an agent fundamentally different from evaluating a single LLM call?core

An LLM eval is a function from (input, output) to a score. An agent eval is a function from a full trajectory — reasoning, tool calls with arguments and results, retrieval, intermediate LLM calls, and final outcome — to a score. Two agent runs can reach the same correct final answer through completely different, differently-flawed paths, so scoring only the final output is blind to how the agent actually behaved.

Walk through the diagnostic stack: outcome, trajectory, component.core

Outcome eval is cheap and blunt — did the task succeed, yes or no. Trajectory eval looks at the full path — tool selection, argument correctness, efficiency, reasoning quality — and is where the real diagnostic signal lives. Component eval tests individual pieces (a retriever, a specific sub-agent, a tool) in isolation to pinpoint exactly where a trajectory-level failure originated. Use them as a funnel: outcome first to detect a problem exists, trajectory to localize it to a phase, component to pin the exact cause.

Give a concrete example of an agent that passes turn-level evaluation but fails the user.core

A support agent that gives a polite, accurate, well-formatted answer at every single turn but never actually resolves the underlying ticket. Turn-level scoring rates every message highly; the user still walks away with an unresolved problem. This is exactly why agent evaluation needs goal-level, trajectory-spanning metrics rather than per-message scoring alone.

LLM-as-judge

Name three documented LLM-judge biases and a specific mitigation for each.judge

Position bias (10-15 point winrate swing on close calls) — mitigate with swap augmentation, evaluating both orderings and treating an inconsistent result as a tie. Verbosity bias (15-30 point inflation for longer outputs) — mitigate with explicit length-neutrality instructions in the rubric, which measurably cuts the effect roughly in half. Self-preference bias (10-25% inflated self-scoring) — mitigate by always using a judge from a different model family than the system under test.

Why does prompt wording fix verbosity bias but not position bias?judge

Verbosity bias responds to explicit instructions because it's a content-level heuristic the model can consciously override when told to. Position bias lives deeper in how the model attends to input order during decoding — telling it not to be influenced by position has near-zero measured effect. Position bias needs an architectural fix (swap the order and compare, or ensemble across orderings), not a rubric fix.

How do you validate that your LLM judge is actually trustworthy before shipping it?judge

Calibrate against a human-labeled golden set targeting at least 0.80 Spearman correlation. Check internal consistency across repeated runs (Cronbach's alpha). Run swap augmentation to catch position bias. Confirm the judge model is a different family than the system under test to avoid self-preference. Re-validate every time the judge model version changes, since calibration drift is real and a CI gate can silently keep passing while the judge's meaning shifts underneath it.

When is LLM-as-judge the wrong tool entirely?judge

For per-turn production evaluation at scale — it's too expensive to run on every live turn and too variance-prone (the same trajectory can score differently across runs) to trust as a real-time signal. The right tool for that job is a cheap, fast, purpose-built classifier trained on your specific failure taxonomy; reserve full LLM-as-judge for offline batch scoring on a bounded, sampled dataset where cost and variance are controlled.

Benchmarks

What does tau-bench measure that SWE-bench and GAIA don't?benchmarks

Reliability across repeated attempts at the same task, via its pass^k metric, and realistic multi-turn dialogue with a simulated user under written policy constraints — closer to production customer-service agent behavior than a single-shot task. SWE-bench and GAIA are largely single-attempt, single-turn task-resolution benchmarks; tau-bench specifically targets the gap between "can solve it once" and "solves it reliably while following rules and talking to a user."

Your agent scores well on GAIA. Can you conclude it will perform well in your production environment?benchmarks

No — a 20-40 percentage point drop from public benchmark score to real task distribution performance is routinely observed, and benchmark scores are highly sensitive to the specific agent harness/scaffold used, which likely differs from your production setup. GAIA is useful for coarse model shortlisting and detecting regressions, not as a substitute for evaluating on your own private task distribution.

Why does pass^k matter more than pass@1 for a production agent?benchmarks

Pass@1 only tells you whether the agent can succeed once, possibly by luck. Pass^k measures success rate across repeated attempts at the identical task, revealing consistency. A documented example: GPT-4o scores under 50% pass@1 on tau-bench but drops to under 25% pass^8 in retail — meaning it's dramatically less reliable across repeated attempts than a single success rate suggests, which matters enormously for a production agent serving the same type of request many times over.

RAG evaluation

Explain faithfulness vs context recall, and why you need both.rag

Faithfulness measures whether the generated answer's claims are actually supported by the retrieved context — it catches hallucination relative to what was retrieved. Context recall measures whether the retrieved context actually contains everything needed to answer correctly — it catches retrieval gaps. A system can score high faithfulness while still giving an incomplete or wrong-feeling answer, because the generator is being perfectly honest about partial evidence the retriever failed to surface. You need both metrics on the same dashboard, always — faithfulness alone can't distinguish a generation problem from a retrieval problem.

Walk through the legal-research RAG incident and what it teaches about metric selection.rag

A system shipped with a 0.91 faithfulness score. Weeks later, users reported answers missing a key statute roughly one in six times. Faithfulness stayed at 0.91 the whole time because the generator was faithfully summarizing whatever partial context it received — the actual regression was in context recall (dropped to 0.62), invisible on a dashboard that only tracked generation-side metrics. The lesson: always pair generation metrics with retrieval metrics; a healthy generation score can mask a badly broken retriever.

How large should your RAG eval dataset be before you trust the aggregate score?rag

Start around 100-200 queries, then add batches of roughly 25 more until key metrics (faithfulness, retrieval recall, answer accuracy) stop moving by more than about 2 points across two consecutive runs — that stability threshold is a defensible, principled stopping rule rather than an arbitrary fixed number. Sample should be stratified from real traffic patterns: factual lookup, multi-hop reasoning, policy/compliance questions, and ambiguous cases specifically, not just easy queries.

System design & production

Design an evaluation pipeline for a customer-support agent from scratch.design

Start with deterministic checks wherever possible (was a ticket actually closed in the system of record — schema/state check, no LLM needed). Build 50-100 hand-crafted golden trajectories covering critical scenarios with expected tool calls annotated. Add LLM-as-judge with an explicit rubric for what can't be checked deterministically (tone, resolution quality), validated against human labels at ≥0.80 Spearman correlation and checked for position/verbosity/self-preference bias. Wire the golden set into a CI gate blocking regressions pre-merge. Add a cheap per-turn classifier in production for negative-sentiment and policy-violation detection, feeding an error queue that routes real failures back into the golden set — closing the loop rather than treating eval as a one-time setup task.

Your team wants to skip building an eval set and just "eyeball" outputs during development. How do you push back?design

LLM outputs are non-deterministic — a change that looks fine on the handful of examples you eyeballed can regress on dozens of cases you didn't happen to check, silently, with no way to detect it before a user does. Manual spot-checking doesn't scale and isn't repeatable across prompt/model changes. Frame it in cost terms: building even a 50-case golden set is a one-time investment that turns every future change into a fast, automated, repeatable pass/fail check instead of a fresh round of manual review each time.

How do you decide what goes in the CI gate versus what's monitored only in production?design

CI gate: your curated golden set plus any known regression cases — bounded, fast enough to run pre-merge, and directly tied to a merge/no-merge decision. Production monitoring: cheap per-turn classifiers for drift and safety signals across all live traffic, plus periodic LLM-as-judge sampling on a bounded batch of production traces for deeper quality checks the fast classifiers can't do. The failures production monitoring surfaces should routinely get promoted into the CI golden set — that promotion path is what keeps the gate meaningful over time instead of stale.

How would you catch the fact that your agent has gotten quietly worse after a prompt change, before users notice?design

This is precisely what the CI gate exists to prevent — run the full golden trajectory set (not just final-answer checks) against the new prompt before merge, comparing trajectory-level metrics (tool selection accuracy, efficiency, not just outcome) against the previous baseline, and block the merge on any statistically meaningful regression. If the regression is subtle enough to slip past a bounded golden set, production trace monitoring with per-turn classifiers and periodic sampled LLM-judge review is the second line of defense, feeding newly discovered failure patterns back into the golden set.

Glossary

Every term used in this document.

Trajectory
The full ordered sequence of prompts, reasoning, tool calls, observations, and final response an agent produces for one task.
Outcome eval
Binary/scalar scoring of whether the final task goal was achieved, independent of path taken.
Component eval
Testing an individual piece (retriever, sub-agent, tool) of the system in isolation.
LLM-as-judge
Using an LLM to score, classify, or compare another system's outputs against a rubric.
Pointwise / pairwise judging
Scoring one output alone vs. comparing two outputs to pick a winner.
Position bias
Judge preference for a response based on its presentation order, not its quality.
Verbosity bias
Judge preference for longer responses regardless of added value.
Self-preference / self-enhancement bias
Judge tendency to rate its own model family's outputs more favorably.
Swap augmentation
Evaluating a pairwise comparison in both orderings to detect and correct position bias.
Spearman correlation
Statistical measure of judge-vs-human ranking agreement; ≥0.80 is a common production target.
pass^k
Reliability metric measuring success rate across k repeated attempts at the same task, not just one.
Faithfulness
RAGAS metric: fraction of an answer's claims supported by the retrieved context.
Context recall
RAGAS metric: fraction of ground-truth information actually present in retrieved context.
Context precision
RAGAS metric: whether relevant retrieved chunks are ranked highly.
Golden dataset
A curated, expert-validated set of eval cases with known-correct expected trajectories/outputs.
Eval-driven development
Treating evaluation as a continuous closed loop (offline → CI → production → error feed → optimization) rather than a one-time gate.
Calibration drift
Silent change in a judge's effective scoring behavior after a model version update, undetected by an unchanged rubric.
