Agent Reasoning Patterns Beyond ReAct

ReAct is the pattern everyone learns first and the pattern almost every interviewer expects you to move past. This is every reasoning/control-flow pattern that matters in 2026 — what problem each one solves, exactly how it works, when it beats ReAct, when it's worse, its actual paper results, and LangGraph-style pseudocode you could defend on a whiteboard.

00

The Landscape — One Map for Eleven Patterns

Every pattern below is answering one of three questions differently: how much do you plan before acting, how many paths do you explore, and how do you learn from failure. Hold this map in your head before the details.

Almost every "new" agent pattern you'll be asked about is a variation on three axes. Get these three axes solid and you can place any pattern — including ones invented after this document was written — without memorizing a taxonomy.

AxisQuestion it answersLow endHigh end
Planning horizonHow far ahead does the agent commit before acting?One step at a time (ReAct)Full plan up front (Plan-and-Execute, ReWOO)
Search breadthHow many candidate paths does it consider per decision?One path, no backtracking (ReAct, CoT)Many paths explored & compared (ToT, GoT, LATS)
Learning loopDoes it use its own past failures to improve?No memory of past attempts (ReAct, CoT)Explicit critique + retry (Reflexion, Self-Refine, LATS)

Every pattern in this doc is a specific point in that three-dimensional space, chosen to trade off token cost, latency, and accuracy differently. That trade-off — not the name of the pattern — is what interviewers actually want you to reason about.

single-path, cheap plan-first self-critique loop multi-path search search + critique combined
The single most important interview instinct

Never answer "which pattern is best" — answer "best for what constraint." Every pattern here is strictly more expensive than ReAct in tokens or latency; each one is buying something specific (recoverability, parallelism, exploration, self-correction) in exchange. State the trade explicitly and you sound like someone who has shipped these, not read about them.

01

ReAct, Recapped as the Baseline

Every pattern below is defined relative to this one. Thirty seconds, then we move on.

ReAct (Yao et al., 2022) interleaves reasoning ("Thought") and acting ("Action") one step at a time: think, act, observe, think again. It's cheap, adaptive to whatever the last observation was, and has zero planning overhead. Its weakness is exactly its strength: because it only ever looks one step ahead, it can wander — take a locally-reasonable action that turns out to be globally wrong, with no mechanism to notice until much later, and no way to compare it against an alternative it never considered.

PropertyValue
LLM calls per task~1 per step (no separate planning pass)
BacktrackingNone — committed to each action once taken
Best forTasks where the right next step depends heavily on the last observation (open-ended search, exploratory debugging)
Worst forLong-horizon tasks with a definable success criterion, where a wrong early step is expensive to discover late
02

Self-Consistency (CoT-SC)

Wang et al., 2022. The simplest way to trade tokens for accuracy: stop trusting a single reasoning chain.

Standard chain-of-thought samples one reasoning path and takes its answer. Self-Consistency samples multiple independent reasoning paths (via temperature > 0) for the same question, then takes a majority vote over the final answers — discarding the reasoning text itself. The insight: correct reasoning paths tend to agree with each other on the answer even when worded differently; wrong paths scatter more randomly. It's not really an "agent" pattern — there's no tool use or environment — but it's the ancestor of every "try N times and pick the best" pattern that follows, and it's frequently the cheapest lever for boosting a plain LLM call before you reach for anything agentic.

self_consistency.py
answers = []
for _ in range(5):                              # sample N independent chains
    resp = model.invoke(prompt, temperature=0.7)
    answers.append(extract_final_answer(resp))

final = majority_vote(answers)                     # most common answer wins
When it's worth it

Self-Consistency is cheap to bolt onto anything — arithmetic, multiple-choice, classification, any task with a clean final answer to vote over. It's a poor fit for open-ended generation (there's no clean way to "vote" over five different essays) — that's where Self-Refine and Reflexion take over instead.

Interview framing

"How would you improve accuracy on a math word-problem agent without changing the model?" — Self-Consistency: sample k reasoning paths at temperature > 0, extract each final answer, majority vote. It's model-agnostic, requires zero architecture change, and the accuracy gain is well-documented on arithmetic and commonsense reasoning benchmarks.

03

Self-Ask

Press et al., 2022. Decompose the question before you try to answer it — the pattern hiding inside every "agentic search" pipeline.

Self-Ask has the model explicitly decide "are follow-up questions needed here?", and if so, generate and answer each sub-question (optionally via a search tool) before composing the final answer. It's structurally close to ReAct but the loop is organized around question decomposition specifically rather than open-ended thought — which makes it easier to prompt reliably for multi-hop QA and easier to force citation of intermediate facts.

self_ask_trace.txt
Question: Who was president when the designer of the Eiffel Tower was born?
Are follow up questions needed here: Yes.
Follow up: Who designed the Eiffel Tower?
Intermediate answer: Gustave Eiffel.
Follow up: When was Gustave Eiffel born?
Intermediate answer: 1832.
Follow up: Who was the U.S. president in 1832?
Intermediate answer: Andrew Jackson.
So the final answer is: Andrew Jackson.

This is exactly the "query → subquery → retrieve" shape from agentic RAG — Self-Ask is the reasoning pattern underneath it, generalized past just retrieval to any sub-question a tool can answer.

04

Plan-and-Execute

Wang et al.'s Plan-and-Solve prompting, popularized as an agent architecture by LangChain in 2023. Separate the planner from the doer.

Instead of deciding one step at a time, a planner LLM call produces a complete, ordered, multi-step plan for the whole task up front. An executor then works through the plan step by step, invoking tools as needed for each step. After execution (or after each step, in stricter variants), a re-planner checks whether the original plan still makes sense given what's been learned — and either continues, revises the remaining plan, or declares the task done.

plan_execute_langgraph.py
class Plan(BaseModel):
    steps: list[str]

async def plan_step(state):
    plan = await planner.ainvoke({"objective": state["input"]})
    return {"plan": plan.steps}

async def execute_step(state):
    task = state["plan"][0]                       # next step, could be a mini ReAct agent
    result = await executor.ainvoke({"input": task})
    return {"past_steps": (task, result), "plan": state["plan"][1:]}

async def replan_step(state):
    output = await replanner.ainvoke(state)  # sees past_steps + original objective
    if isinstance(output, Response):
        return {"response": output.response}     # done
    return {"plan": output.steps}              # revised remaining plan
AdvantageWhy it matters
Explicit long-horizon planningEven very strong LLMs struggle to hold a long plan in their head implicitly while also executing step by step — writing it down first offloads that working memory.
Model mixingUse an expensive, strong model only for the planner call; cheaper/smaller models can execute each already-scoped step.
Inspectable checkpointThe plan is a structured artifact a human can review/approve before any tool actually runs — a natural human-in-the-loop point.
Narrower executor contextEach executor call sees one step, not the whole task — this measurably reduces hallucinated tool arguments compared to a planner that also executes.
Known weaknesses

A plan made with zero information about what tools will actually return is a guess. If step 2 depends on a fact step 1 hasn't fetched yet, the plan can be wrong in ways only visible at execution time — which is exactly why the re-planner exists, and why Plan-and-Execute is strictly more complex to implement correctly than ReAct.

05

ReWOO — Reasoning WithOut Observation

Xu et al., 2023. Plan-and-Execute's leaner, faster sibling — plan the entire tool itinerary in one shot, with variable placeholders instead of real results.

ReAct re-invokes the LLM after every single observation, re-sending the whole growing transcript each time — expensive and slow. ReWOO's insight: for many tasks, you can generate the entire tool-call plan in a single LLM call, using symbolic placeholders (#E1, #E2...) for results you don't have yet, then execute every tool call — substituting placeholders as results arrive — without calling the LLM again until a final "Solver" pass synthesizes the answer.

ComponentJobUses LLM?
PlannerEmits the full plan with #E variable placeholders in one passYes — once
WorkerExecutes each tool call, substituting resolved #E variables into later steps' argumentsNo — pure execution
SolverReads all resolved observations and produces the final answerYes — once
rewoo_plan_example.txt
Plan: Find who won the 2024 Super Bowl.
#E1 = Search[2024 Super Bowl winner]
Plan: Find what state that team's headquarters is in, using #E1.
#E2 = Search[headquarters state of #E1]
Plan: Find the GDP of that state, using #E2.
#E3 = Search[GDP of #E2]

Notice: the LLM never sees the actual search results while planning — it only reasons about the shape of the dependency chain (this needs that). Execution then runs all three searches with real substituted values, and only the final Solver call sees the actual text. ReWOO cuts token usage by 30–50% compared to ReAct on equivalent multi-step tasks, and reduces the number of LLM calls to as few as two — planner and solver — with tool execution running in between (and, when steps are independent, in parallel).

Where it breaks

ReWOO is more efficient with fewer model invocations, but it struggles with complex, observation-requiring planning tasks — if step 2's search query genuinely depends on the content of step 1's result (not just its existence), a plan written before seeing that content can be wrong in ways ReWOO has no mechanism to catch mid-flight. It trades adaptability for speed.

Interview framing

"How would you cut latency/cost on a multi-hop search agent that's currently ReAct?" — If the dependency structure between steps is predictable (you usually know you'll need "team → state → GDP" without needing to see the team name first), switch to ReWOO: one planning call, parallel tool execution via variable substitution, one solver call. If steps are only knowable after seeing prior results, stay with ReAct or use Plan-and-Execute with a re-planner.

06

Reflexion — Verbal Reinforcement Learning

Shinn et al., 2023. Instead of updating weights, update a memory of what went wrong in your own words.

Reflexion uses verbal reinforcement to help agents learn from prior failings, converting binary or scalar feedback from the environment into a textual summary that's added as additional context for the next attempt — a paradigm shift from traditional RL's numerical reward signals to natural-language reflections, avoiding the prohibitive compute cost of gradient-based fine-tuning entirely.

The three-model architecture

Reflexion is built from three distinct models: an Actor that generates text and actions (often a Chain-of-Thought or ReAct policy), an Evaluator that scores the Actor's output trajectory, and a Self-Reflection model that generates verbal reinforcement cues to help the Actor improve.

The loop, step by step

  1. Actor attempts the task, producing a full trajectory (a sequence of actions/thoughts, possibly a ReAct run).
  2. Evaluator scores the trajectory — a hard signal when available (unit tests passing/failing, a binary success flag) or an LLM-based judge when not.
  3. If the score is below threshold, the Self-Reflection model reads the trajectory + score and writes a short natural-language diagnosis: what went wrong, what to try differently.
  4. That reflection is appended to an episodic memory buffer.
  5. The Actor retries the task, now prompted with its own past reflections as extra context.
  6. Repeat for a fixed number of trials or until the score clears the threshold.
The headline result

Reflexion achieves a 91% pass@1 accuracy on the HumanEval coding benchmark, surpassing the previous state-of-the-art GPT-4 result of 80% — and the gain came entirely from the reflection loop, not a stronger base model. Reflexion agents verbally reflect on task feedback signals, then maintain their own reflective text in an episodic memory buffer to induce better decision-making in subsequent trials.

reflexion_loop.py
memory = []
for trial in range(max_trials):
    trajectory = actor.run(task, reflections=memory)     # Actor sees past reflections
    score = evaluator.score(trajectory)                  # unit tests, binary success, or LLM judge
    if score >= threshold:
        break
    reflection = self_reflect_model.generate(trajectory, score)
    memory.append(reflection)                             # episodic memory buffer
Real limitation

Reflexion relies on the LLM's own self-evaluation capability (or a heuristic evaluator) to generate useful verbal feedback, and without formal convergence guarantees, there's no assurance the iterative process consistently steers the Actor toward correct outcomes — a bad Evaluator or vague reflections can make the loop spin without actually improving.

Interview framing

"Design a coding agent that gets better across attempts on the same failing test." — Reflexion: Actor writes code, Evaluator runs the test suite (a hard signal, not an LLM judge — much more reliable), on failure a Self-Reflection pass reads the stack trace and writes a targeted diagnosis, which is prepended to context on the next attempt. Cap trials at 3-5 to bound cost, and always prefer an executable/hard evaluator over an LLM judge when one is available.

07

Self-Refine

Madaan et al., 2023. Reflexion's simpler cousin — no environment, no episodic memory across tasks, just "critique your own output and rewrite it," in a single sitting.

Self-Refine is the pattern to reach for when there's no external environment to give you ground-truth feedback — no unit tests, no task success signal — just a piece of generated text (an essay, an email, a summary) that could plausibly be better. The same LLM plays two roles in sequence: generate an output, then critique that exact output against a rubric, then revise based on the critique. Repeat for a fixed number of rounds or until the critique says "no further changes needed."

self_refine.py
output = model.invoke(f"Write: {task}")
for _ in range(3):
    critique = model.invoke(f"Critique this against the goal:\n{output}")
    if "no changes needed" in critique.lower():
        break
    output = model.invoke(f"Revise using this critique:\n{output}\n\n{critique}")
Self-RefineReflexion
Feedback sourceThe model critiquing itself, same sessionAn environment/evaluator with (ideally) ground truth, across trials
MemoryNone persisted — each task starts freshEpisodic memory buffer persists across trials
Best forOpen-ended generation: writing, summarization, code styleTasks with a checkable success criterion: tests passing, a game won
Interview trap

"Won't the model's critique just be the same biases as its generation?" — Yes, partially. Self-Refine has no access to ground truth, so it can polish style and catch surface errors but can't reliably catch factual mistakes the model itself doesn't know are wrong. That's exactly why Reflexion insists on an external, ideally hard, Evaluator wherever one is available.

Tree of Thoughts (ToT)

Yao et al., 2023. Chain-of-thought is a single path through the woods. ToT lets the model explore several paths and prune the bad ones before committing.

ToT organises inference as a search over intermediate thoughts rather than a single left-to-right pass: the agent expands a tree whose nodes are candidate partial solutions, a scorer evaluates each node, and a controller decides which branches to expand or backtrack — trading tokens for look-ahead and the ability to recover from an early wrong turn that a single chain would be stuck with.

The four operations

  • Thought decomposition — define what counts as one "step" or partial solution for this task.
  • Thought generation — at each node, sample several candidate next thoughts (not just one).
  • State evaluation — score each candidate (the model itself, or a separate scorer/critic) — "is this partial solution promising?"
  • Search algorithm — BFS (keep the top-k candidates at each depth) or DFS (commit to the best-looking branch, backtrack on dead ends).
The headline result

On the Game of 24 benchmark, GPT-4 achieves 4% with standard prompting and 74% with Tree of Thoughts — an 18.5x improvement — because Game of 24 has exactly the property ToT needs: a hard, checkable success criterion and a search space small enough to explore several branches cheaply.

Use ToT whenSkip ToT when
The task has a definable, checkable success criterion to score partial solutions againstThere's no good way to score a partial (unfinished) solution — you only know quality at the very end
The cost of a wrong plan is high relative to a few extra LLM callsLatency budget doesn't allow multiple LLM calls per decision point (N=3 branches × 10 decision points = 30+ calls minimum)
ReAct/CoT has repeatedly failed on this task class specificallyReAct already solves the task reliably — ToT only adds cost from here
Interview framing

"When would you NOT reach for Tree of Thoughts even though it clearly outperforms CoT on paper?" — ToT costs 10 to 100 times more tokens than CoT depending on branching factor and depth, and it needs a working scorer for partial solutions, which many real tasks don't have (you can't score "half a customer support reply" the way you can score "half a sudoku"). Default to ReAct/CoT; add ToT only for a specific task class with repeated failures and a definable evaluation criterion.

Graph of Thoughts (GoT)

Besta et al., 2024. ToT's tree can't merge two good partial ideas into one better one. GoT can.

Graph of Thoughts generalises ToT from trees to arbitrary dependency graphs: thoughts become vertices and edges record informational dependencies, allowing recombination, summarisation, or refinement of subgraphs and feedback loops across them — which matters for tasks where sub-problems interlock, like sorting with constraints or multi-step data transformations. A tree structure forces every idea to have exactly one parent; a graph lets you take the best parts of two different branches and merge them into a new node, or refine one thought using another as input.

Tree of ThoughtsGraph of Thoughts
StructureStrict tree — each thought has one parentArbitrary DAG — thoughts can merge, reference, and refine each other
Merging ideasNot possible — you must pick one branchNative operation — combine two promising thoughts into a stronger one
Cost vs ToTBaselineOften lower — sharing and distilling subgraphs instead of re-deriving from scratch reduces both cost and improves quality
Reality check for interviews

GoT is much rarer in production than ToT — its implementation complexity (defining merge/refine operations per task) is high relative to the marginal gain over ToT for most business problems. Know it conceptually and be ready to explain the tree-vs-graph distinction; don't expect to be asked to implement it live.

LATS — Language Agent Tree Search

Zhou et al., 2023. The "if you had to pick just one advanced pattern" answer — ReAct's tool use, ToT's search, and Reflexion's self-critique, fused with Monte Carlo Tree Search.

LATS is a general LLM agent search algorithm that combines reflection/evaluation and search — specifically Monte Carlo Tree Search — to achieve better overall task performance compared to similar techniques like ReAct, Reflexion, or Tree of Thoughts individually. Where ToT searches over pure reasoning, LATS searches over actual action trajectories in a real environment (tool calls, code execution), scoring and reflecting on each branch as it goes.

The MCTS-style loop

Select the best next actions based on aggregate rewards from prior exploration; expand and simulate by picking the most promising candidate actions and executing them in parallel; reflect and evaluate by observing outcomes and scoring the decisions (using reflection, and external feedback where available); backpropagate by updating the scores of ancestor nodes based on the new outcomes — repeating until a solution is found or a max search depth is reached.

ReActReflexionTree of ThoughtsLATS
BacktrackingNoNo (within a trial)YesYes (via MCTS)
Real environment actionsYesYesUsually mental simulation onlyYes
Self-critique between attemptsNoYesOnly via node scoringYes — built in
CostLowestMedium (trials × 1 path)High (branches × depth)Highest
The honest trade-off

LATS is the strongest single-agent pattern on hard benchmarks precisely because it does the most work per task. That's also disqualifying for latency-sensitive, high-volume, or cost-constrained production paths. Reserve it for the highest-value, most failure-prone task classes — not as your default agent loop.

Interview framing

"You've tried ReAct and Reflexion on a hard task and both plateau below your accuracy bar — what next?" — LATS: combine tree search (explore multiple action branches, not just multiple reasoning branches) with reflection (critique and score each expanded branch) using MCTS-style selection to focus compute on the most promising parts of the tree. Flag the cost trade-off unprompted — it's the answer the interviewer is listening for.

Self-Discovery & STORM — Composable and Research Patterns

Two more patterns worth recognizing by name even if you'll implement them less often.

Self-Discovery

Instead of hand-picking a reasoning pattern (CoT vs. step-back vs. decomposition) for a task ahead of time, Self-Discovery has the model compose its own reasoning structure from a set of atomic reasoning modules ("break the problem into subproblems," "think step by step," "consider constraints first"...) selected and adapted specifically for the task at hand, before actually solving it. It's a meta-pattern: a plan for how to reason, generated before the reasoning itself.

STORM

STORM is an outline-driven research-and-writing pattern: generate a topic outline, research each section via multiple simulated "perspectives" asking questions of a retrieval tool, then synthesize a long-form article section by section. It's the closest named pattern to a full "deep research" agent pipeline, and a good one to mention if asked to design a research-report-generating agent.

Where these fit

Self-Discovery is useful when you're building a general-purpose reasoning agent across wildly different task types and don't want to hand-pick a pattern per task. STORM is useful specifically for long-form research writing where an outline-first, multi-perspective research pass measurably improves depth and citation coverage over a single-pass RAG answer.

The meta-question every senior interview asks

"Walk me through how you'd pick a reasoning pattern for a new agent." Answer in this order: (1) does it have a hard, checkable success signal? (2) is the tool-dependency chain predictable or does each step depend on the last observation's content? (3) what's the latency/cost budget per request? (4) is a single wrong step catastrophic or cheaply recoverable? The answers to those four questions, not familiarity with pattern names, determine the right pick.

Production Hybrids — What Ships, Not What's in the Paper

Almost nobody runs a pure pattern in production. Here's what actually gets combined and why.

ReAct + Reflexion (the most common hybrid)

Run a ReAct loop for step-by-step adaptation on the common case; if the result fails validation, enter a Reflexion retry cycle for self-correction on the hard cases. You get ReAct's low cost on the 90% of requests that succeed first try, and Reflexion's recovery on the 10% that don't.

Plan-and-Execute with a ReAct fallback per step

Plan upfront; if a step returns something unexpected and the re-planner can't handle it, drop into a ReAct loop for that specific step — plan-level structure with step-level adaptability where it's actually needed.

ReWOO fast path, Plan-and-Execute fallback

Try ReWOO first for its speed; if any tool call returns an error or an empty result, fall back to Plan-and-Execute's re-planning to recover — a conditional edge in LangGraph routes between the two based on tool call success.

The framing that separates senior candidates

"Agent patterns" and "agent frameworks" are different things — ReAct/Reflexion/ToT are architectural patterns, while LangGraph/CrewAI/AutoGen are the plumbing you implement them in. You can build a ReAct+Reflexion hybrid in LangGraph, in raw Python, or in any other framework — knowing the pattern is framework-independent knowledge, and interviewers specifically probe for whether you understand that distinction.

Interview Cheat-Sheet

Every question grouped by depth. Answer out loud before revealing.

Definitions & core mechanics

What problem does Self-Consistency solve, and why isn't it enough on its own?core

It reduces variance from sampling a single reasoning chain by sampling several independently and majority-voting the final answers. It only works cleanly when there's a discrete final answer to vote over — it can't meaningfully "vote" across five different pieces of open-ended prose, which is why it doesn't help with generation quality the way Self-Refine does.

Explain ReWOO's two-call trick and what it costs you.core

The planner emits the full tool-call plan in one pass using symbolic placeholders (#E1, #E2...) for results it doesn't have yet; a non-LLM worker executes every call, substituting real values as they resolve; a solver makes one final LLM call over all resolved results. It costs adaptability — because the plan is made without seeing any actual tool output, it can't adjust its query strategy based on what a tool actually returned.

What are the three models in Reflexion and what does each do?core

Actor (generates the trajectory), Evaluator (scores it — ideally against a hard signal like passing tests), Self-Reflection model (writes a natural-language diagnosis of failure that's appended to episodic memory and fed into the Actor's next attempt). None of them update model weights — the "learning" is entirely in the growing text context.

Tree of Thoughts vs Graph of Thoughts — what's the actual structural difference?core

ToT restricts the search to a strict tree — every partial solution has exactly one parent, so you must fully commit to one branch over another. GoT allows arbitrary dependency graphs, so two promising partial solutions from different branches can be merged, refined together, or reference each other — better suited to tasks where sub-problems interlock rather than decompose cleanly.

Trade-offs & selection

When would ReAct actually beat every "smarter" pattern on this list?tradeoffs

When the task is genuinely exploratory — the right next step can only be known after seeing the last observation, so a pre-made plan (Plan-and-Execute, ReWOO) would be wrong, and there's no clean way to score a "partial solution" for a tree search (ToT, LATS) to prune against. Debugging an unfamiliar codebase or exploratory web research are good examples.

Why might Tree of Thoughts fail to beat ReAct even though the paper shows an 18x gain on Game of 24?tradeoffs

Game of 24 has an unusually clean, checkable partial-solution scorer — most real tasks don't. Without a reliable way to score whether a half-finished plan is "promising," ToT's search degrades to expensive random exploration instead of informed pruning, and you pay 10-100x the tokens for little or no accuracy gain.

Reflexion vs Self-Refine — how do you decide which one a task needs?tradeoffs

Check whether ground-truth feedback exists outside the model's own judgment. If there's a hard signal — unit tests, a game's win condition, a validator — use Reflexion, because its Evaluator can be that hard signal instead of the model grading its own homework. If there's no such signal (an essay, an email, a summary), Self-Refine is the honest option — you're improving surface quality, not correctness, and you should say so explicitly.

Your agent is too slow and expensive on a multi-hop research task using ReAct. What do you check before switching patterns?tradeoffs

First: is the tool-dependency chain actually predictable ahead of time, or does step 2's query genuinely depend on step 1's content? If predictable, ReWOO cuts LLM calls dramatically. If not predictable but the task is long-horizon, Plan-and-Execute at least front-loads the planning cost into one call and lets you use a cheaper model for execution steps. Don't reach for ToT/LATS for a latency problem — they make latency and cost worse, not better.

System design

Design a customer-support agent that drafts replies and improves when a human rejects a draft.design

ReAct or Plan-and-Execute for the initial draft (pull ticket context, relevant KB articles, draft a reply). Wrap it in a Reflexion-style loop where "human rejects with a reason" is the Evaluator's feedback signal instead of an automated one; the reason becomes the verbal reflection fed into the next draft attempt for that ticket. Cap retries at 2-3 before escalating to a human writing it from scratch.

Design a coding agent that fixes a failing CI pipeline.design

Reflexion is the natural fit: Actor proposes a code change, Evaluator is literally the CI pipeline (a hard, unambiguous signal), Self-Reflection reads the failing test output and writes a targeted diagnosis for the next attempt. For a genuinely hard bug where straightforward reflection stalls, escalate to LATS to explore multiple candidate fixes as branches and use MCTS-style selection to focus compute on the most promising one.

Design a long-form research report generator on a topic with no single canonical source.design

STORM-style: generate a topic outline first, then research each section using multiple simulated perspectives that each ask the retrieval tool different questions (surfacing information a single-angle query would miss), then synthesize section by section. This beats single-pass agentic RAG specifically on breadth and citation diversity for open-ended topics.

You've been asked to reduce a ToT-based agent's cost by 70% without losing accuracy. What do you do first?design

Before touching the pattern, check whether the branching factor and depth are actually tuned to the task — most ToT implementations over-explore by default. Second, check whether cheaper models can serve as the node scorer while a stronger model only generates the final chosen path. Third, consider whether the task even needs ToT's full search — if failures cluster on a specific sub-task, a narrower Reflexion loop scoped to just that sub-task is often cheaper than blanket tree search.

Reflexion's three roles: generate, score, and diagnose failure respectively.
Verbal reinforcement learning
Reflexion's term for improving behavior via natural-language feedback instead of gradient updates.
Thought decomposition
ToT's step of defining what counts as one discrete "step" in the search space for a given task.
BFS / DFS search
Breadth-first (keep top-k candidates per depth) vs depth-first (commit and backtrack) strategies for exploring a ToT search tree.
MCTS (Monte Carlo Tree Search)
Select/Expand/Simulate/Backpropagate search algorithm; LATS applies it to real agent action trajectories.
UCT
Upper Confidence bound applied to Trees — the formula MCTS uses to balance exploring new branches vs exploiting known-good ones.
Node scorer / critic
The component (model or heuristic) that assigns a "how promising is this" score to a partial solution in ToT/GoT/LATS.
Self-Discovery
Meta-pattern where the model composes its own reasoning structure from atomic modules before solving the task.
STORM
Outline-first, multi-perspective research pattern for long-form report generation.

How to actually study these before an interview

Don't read them front to back. For each: read the abstract, then find the one diagram that shows the architecture, then read only the method section long enough to draw that diagram from memory and explain it out loud in under 90 seconds. That's the depth interviewers are actually testing for.
