The 2026 Framework Landscape

Six frameworks dominate production agent deployments right now. Know the philosophy behind each, not just the name.

By mid-2026, six SDKs dominate production agent deployments: LangGraph, CrewAI, OpenAI Agents SDK, Claude Agent SDK, Google ADK, and Microsoft Agent Framework — each takes a different approach to the same underlying problem: how to build agents that work reliably in production.

A name that will trip you up

As of April 2026, Microsoft merged AutoGen with Semantic Kernel into the Microsoft Agent Framework 1.0, which reached general availability that month — AutoGen is now in maintenance mode, receiving bug fixes but no major new feature development. If you have AutoGen in production, LangGraph is the closest architectural fit for migration, while CrewAI is the easiest transition if your agents follow role-based patterns. Do not recommend starting a new project on AutoGen in an interview — it reads as stale knowledge.

Token cost is a real, cited differentiator

Benchmarks show LangGraph runs roughly 47% lower token costs than CrewAI, attributed to explicit edge transitions instead of LLM-driven task routing — CrewAI's role-based delegation asks an LLM to decide routing, which LangGraph's conditional edges do in code for free. Conversely, AutoGen-style multi-agent conversation is reported to consume 3-5x more tokens than LangGraph for equivalent tasks because agents "talk" through several conversational turns to coordinate.

The senior-level framing

There is no single best framework — your choice depends on use case, team size, and existing tech stack, and many production systems combine frameworks: you might use LangGraph for orchestration while plugging in specialist agents built on other frameworks. Naming a framework as universally "best" is a junior answer; describing the trade you're making is the senior one. And increasingly the interoperability question — "can these talk to each other at all" — matters more than which single framework wins, which is exactly what A2A solves.

02

MCP vs A2A — Two Different Problems

The single most-tested distinction in this whole topic area. Get this exactly right.

MCP (Model Context Protocol) connects agents to tools and data. A2A connects agents to other agents — enabling them to discover each other's capabilities, delegate tasks, and collaborate across frameworks and organizations. They are complementary layers, not competitors: a retail store's inventory agent might use MCP to interact with its own product database, and when stock runs low, notify an internal order agent that uses A2A to communicate with an external supplier's agent.

MCPA2A
ConnectsAgent → tool / data sourceAgent → agent
Created byAnthropic, 2024Google, April 2025 — now housed by the Linux Foundation as an open-source project
What the counterpart looks like to youA stateless function with a fixed schemaA full agent that can reason, maintain state, and handle multi-turn interactions like negotiation or clarification — it retains its full capabilities rather than being reduced to a function call
Discovery mechanismTool schema listing on the MCP serverAgent Card at a well-known URL
TransportTypically stdio or HTTP+SSEJSON-RPC 2.0 over HTTP(S)
Interview framing

"When would you wrap a service as an MCP tool vs expose it as an A2A agent?" — If the counterpart is stateless and performs a single function, wrap it as an MCP tool. If it needs to reason, hold state across a multi-turn interaction, or make its own decisions about how to fulfill your request, expose it as an A2A agent instead — collapsing a reasoning agent into a single MCP tool call throws away everything that made it an agent.

A2A Protocol — Core Concepts

Five vocabulary terms that show up in every A2A conversation, interview or production.

TermWhat it is
Agent CardA JSON document describing what an agent does, its skills, and its endpoint — including name, description, version, service endpoint URL, transports, and authentication requirements, published at /.well-known/agent-card.json (or the legacy /.well-known/agent.json).
AgentSkillDeclaration of one capability the agent exposes, with a unique id, name, description, and usage examples — an agent's card can list several skills.
A2A Server (remote agent)Takes requests, processes tasks, and responds with status updates or results, exposing an HTTP endpoint compatible with the A2A protocol.
A2A Client (client agent)An app, service, or other AI agent that delegates requests to remote agents, using A2A to initiate communication.
TaskA2A is task-based: client requests are treated as stateful tasks with the goal of completion, each initiating a task with a unique ID and lifecycle (submitted, working, etc.).

04

Task Lifecycle & Wire Format

Three interaction modes, one underlying transport.

ModeHow it works
SynchronousSingle request/response over JSON-RPC — send a message, block for the task result.
StreamingServer-Sent Events (SSE) deliver incremental updates as the remote agent works — TaskStatusUpdateEvent and TaskArtifactUpdateEvent events stream intermediate progress, e.g. while the remote agent is calling its own tools.
Asynchronous / pushWebhook-based push notifications for long-running tasks the client doesn't want to hold a connection open for.

A typical sequence: the client requests the agent card, the server returns it; the client sends message/send (or message/sendStream for streaming); the request routes through a RequestHandler to an AgentExecutor, which invokes the actual underlying agent (LangGraph graph, ADK agent, whatever); the executor returns a response, the handler updates the Task and enqueues an event, and the server relays it back to the client.

The architectural pattern underneath every framework's A2A integration

Every framework's A2A integration follows the same shape: an AgentExecutor abstract class handles request processing, a DefaultRequestHandler manages protocol-level concerns and task lifecycle, an EventQueue delivers streaming updates, a TaskStore persists state across interactions, and an A2AStarletteApplication provides the HTTP server. The separation between protocol handling and agent logic is what lets you drop any framework's agent behind the same A2A server shell.

05 ★

LangGraph ↔ Google ADK — The Architecture

Your actual production setup: a LangGraph-based agent repo and a Google ADK-based agent repo, talking over A2A. Here's the shape of it end to end.

There are two independent decisions to make, and interviewers expect you to separate them: (1) which side hosts the orchestrator/host agent, and (2) which direction the A2A calls flow. In practice both repos can be both a client and a server simultaneously — each specialized agent operates as both client and server, with the A2A Client initiating requests while the A2A Server processes incoming tasks, enabling bidirectional communication.

The reference pattern most teams land on: ADK on the orchestrator/host side (it's built for hierarchical delegation and has first-class RemoteA2aAgent tooling for consuming remote agents as if they were sub-agents), LangGraph on the specialist side (its graph model and checkpointing shine for a complex, stateful, long-running specialist task — currency conversion, document analysis, a multi-step research flow). This mirrors the official reference sample: a currency conversion agent built with LangGraph, exposed through A2A, using LangGraph's ReAct pattern with streaming support and checkpoint-backed conversation memory.

Why this direction, specifically

A2A is the right tool exactly when the agent you need to talk to is a separate, standalone service, when you want to enforce a formal contract between system components, or when you're bridging different languages/frameworks across a microservices-style architecture — all three apply to a LangGraph repo and an ADK repo maintained as separate deployables, likely by different teams, with different release cadences.

06 ★

Exposing a LangGraph Agent via A2A

The LangGraph side becomes an A2A server by wrapping its graph in an AgentExecutor and standing up an A2AStarletteApplication.

Option A — the official a2a-sdk pattern (most control)

agent_executor.py
from a2a.server.agent_execution import AgentExecutor, RequestContext
from a2a.server.events import EventQueue
from a2a.utils import new_agent_text_message

class LangGraphAgentExecutor(AgentExecutor):
    def __init__(self, graph):
        self.graph = graph                        # your compiled StateGraph

    async def execute(self, context: RequestContext, event_queue: EventQueue):
        user_input = context.get_user_input()
        thread = {"configurable": {"thread_id": context.context_id}}  # map A2A contextId -> LangGraph thread
        result = await self.graph.ainvoke(
            {"messages": [{"role": "user", "content": user_input}]}, thread
        )
        text = result["messages"][-1].content
        await event_queue.enqueue_event(new_agent_text_message(text))

    async def cancel(self, context, event_queue):
        raise Exception("cancel not supported")
main.py — stand up the server
from a2a.server.apps import A2AStarletteApplication
from a2a.server.request_handlers import DefaultRequestHandler
from a2a.server.tasks import InMemoryTaskStore
from a2a.types import AgentCard, AgentSkill, AgentCapabilities

skill = AgentSkill(
    id="research", name="Research Agent",
    description="Multi-hop research using search tools", tags=["research"]
)
card = AgentCard(
    name="langgraph-research-agent",
    description="LangGraph ReAct agent exposed via A2A",
    url="http://localhost:9999/",
    version="1.0.0",
    default_input_modes=["text"], default_output_modes=["text"],
    capabilities=AgentCapabilities(streaming=True),
    skills=[skill],
)
handler = DefaultRequestHandler(
    agent_executor=LangGraphAgentExecutor(compiled_graph),
    task_store=InMemoryTaskStore(),
)
app = A2AStarletteApplication(agent_card=card, http_handler=handler)

import uvicorn
uvicorn.run(app.build(), host="0.0.0.0", port=9999)

The official reference sample supports multi-turn dialogue and streaming responses using this exact pattern, with checkpoint-backed memory maintaining conversation state between turns.

Option B — a thin community wrapper (fastest to stand up)

quick_server.py
# pip install langgraph-a2a-server
from langgraph_a2a_server import A2AServer
from your_langgraph_app import your_graph

server = A2AServer(
    graph=your_graph,
    name="My LangGraph Agent",

Which option to actually use

langgraph-a2a-server gives you an A2A endpoint in about five lines — great for a prototype or an internal demo. For anything with SLAs, custom streaming behavior, or auth requirements, the official a2a-sdk AgentExecutor pattern is what production LangGraph↔ADK integrations actually use, because you control every part of the request/response mapping. LangGraph's own team has an open, in-progress issue to add first-class declarative A2A agent-card support directly to core — Pregel.with_agent_card() and Pregel.serve_a2a() — worth checking the current release notes for, since this may already be native by the time you read this.

07 ★

Consuming the LangGraph Agent from ADK

On the ADK side, a remote LangGraph agent looks and acts exactly like a local sub-agent — that's the entire point of RemoteA2aAgent.

RemoteA2aAgent is ADK's component for connecting to an accessible remote agent — running in a separate agent (same machine or different), you use RemoteA2aAgent, and from the root agent's perspective it can be composed alongside local sub-agents with no special-casing.

root_agent.py — ADK host consuming a LangGraph specialist
from google.adk.agents import Agent
from google.adk.agents.remote_a2a_agent import RemoteA2aAgent

research_agent = RemoteA2aAgent(
    name="langgraph_research_agent",
    description="Delegates multi-hop research questions to a remote LangGraph agent",
    agent_card="http://langgraph-repo.internal:9999/.well-known/agent-card.json",
)

root_agent = Agent(
    name="orchestrator",
    model="gemini-2.5-pro",
    instruction="Route research questions to langgraph_research_agent; handle everything else yourself.",
    sub_agents=[research_agent],   # remote agent slots in exactly like a local sub-agent
)

Two ways to run this in local dev, per ADK's own quickstart guides:

MethodWhen to use
to_a2a() + uvicornThe most direct method for productionizing an agent — wraps an existing Agent instance into a Starlette app and auto-generates the Agent Card in-memory from the agent's skills, tools, and metadata.
adk api_server --a2aCLI-based, ideal for local development and hosting multiple agents at once — scans a directory for agents with an agent.json Agent Card file and serves each automatically.
The classic local-dev footgun

When testing locally, both agents run on localhost, so the A2A server port for the exposed agent must be different from the consuming agent's port — e.g. LangGraph server on :9999, ADK's own dev UI (adk web) on :8000. Mixing these up produces confusing "connection refused" errors that look like an A2A protocol bug but are just a port collision.

The Reverse Direction — ADK as Server, LangGraph as Client

Just as common in practice: the ADK repo owns a specialist capability and the LangGraph repo's graph needs to call out to it mid-run.

Exposing the ADK agent

adk_agent/agent.py
from google.adk.a2a.utils.agent_to_a2a import to_a2a
from your_adk_app import root_agent

a2a_app = to_a2a(root_agent)          # auto-builds the Agent Card from the agent's own metadata
# uvicorn adk_agent.agent:a2a_app --port=8000
# curl http://localhost:8000/.well-known/agent-card.json  <- verify it's live

Calling it as a tool node inside a LangGraph graph

There's no ADK-specific client object needed on the LangGraph side — any A2A-compliant server looks the same to a client. Wrap a standard A2A client call as a LangGraph tool, and the routing/conditional-edge logic you already know handles the rest.

a2a_tool.py — LangGraph node calling a remote ADK agent
import httpx
from langchain_core.tools import tool

@tool
async def call_adk_pricing_agent(question: str, context_id: str | None = None) -> str:
    """Delegate a pricing question to the remote ADK pricing agent via A2A."""
    payload = {
        "jsonrpc": "2.0", "method": "message/send",
        "params": {
            "message": {"role": "user", "parts": [{"text": question}]},
            **({"contextId": context_id} if context_id else {}),
        },
    }
    async with httpx.AsyncClient() as client:
        resp = await client.post("http://adk-repo.internal:8000/", json=payload)
        return resp.json()["result"]["parts"][0]["text"]

Register call_adk_pricing_agent on your LangGraph agent exactly like any other tool via bind_tools — from the graph's perspective, "call the remote ADK agent" and "call the Tavily search tool" are the same shape of thing: a tool call, an observation, back to the LLM node.

09 ★

State, Context & Thread Sync — The Part That Actually Breaks

Every A2A/LangGraph interop bug report you'll ever file traces back to this section.

Both sides have their own notion of "this is one ongoing conversation" — A2A calls it contextId, LangGraph calls it thread_id. If you don't deliberately map one to the other, every turn of a multi-turn A2A conversation looks like a brand-new LangGraph thread with no memory of the last turn.

ConceptOwned byPurpose
contextIdA2A protocolGenerated by the server on the first message of a conversation and returned to the client; the client includes it on every follow-up message to associate turns with the ongoing conversation.
taskIdA2A protocolIdentifies one discrete unit of work (a single task) within a context — a context can span multiple tasks.
thread_idLangGraph checkpointerKeys the persisted AgentState snapshot for one resumable run.
The correct mapping pattern

Include contextId and taskId inside the message object on follow-up turns so the server can associate them with the ongoing conversation, but omit them on the first message — the server generates a contextId and returns it in the response. Set thread_id in the top-level metadata field of the JSON-RPC payload, not inside params. Generate a random thread_id before the first message; once the server returns a contextId, use it as the thread_id for all subsequent requests, keeping the A2A conversation context and any tracing (e.g. LangSmith) thread in sync. Pass the same thread_id to every agent in the chain so all traces group into one thread.

executor_with_context_mapping.py
async def execute(self, context: RequestContext, event_queue: EventQueue):
    # A2A's contextId IS the LangGraph thread_id -- one deliberate mapping, everywhere
    lg_thread = {"configurable": {"thread_id": context.context_id}}
    result = await self.graph.ainvoke(
        {"messages": [{"role": "user", "content": context.get_user_input()}]},
        lg_thread,
    )
    # the checkpointer now has full history under context_id -- next A2A turn
    # with the same contextId resumes it exactly like a returning LangGraph thread
If the counterpart agent isn't on LangGraph

If one of your agents is not built on LangGraph, it needs its own equivalent mapping — the A2A contextId still needs to be threaded through to whatever memory/session mechanism that framework uses. On the ADK side, this means mapping contextId to ADK's own session_id in its Session Service — the same discipline, different vocabulary.

10 ★

Trust Boundaries & Security

The moment your LangGraph repo starts accepting requests from a repo your team doesn't control end-to-end, the security model changes.

Treat any agent operating outside your direct control as a potentially untrusted entity. All data received from an external agent — including its AgentCard, messages, artifacts, and task status — should be handled with the same caution you'd apply to any other untrusted network input. This is true even between two repos on the same team, once they deploy and scale independently — a bad deploy on one side shouldn't be able to compromise the other through the A2A channel.

  • Validate the Agent Card, don't just trust it — a skill list and description are just JSON a remote party controls; don't let them silently expand what tools/permissions your host grants that agent.
  • Authenticate every request — A2A supports authentication requirements declared right in the Agent Card; enforce them rather than treating the internal network as an implicit trust boundary.
  • Scope what a remote agent can trigger — a LangGraph agent receiving A2A-delegated tasks from ADK should not have more tool access than the task genuinely requires, exactly like the least-privilege principle for any other external caller.
  • Don't blindly execute instructions embedded in returned artifacts — if the remote agent's response contains something that looks like a new instruction, that's a potential injection vector, not a command to follow.
  • Log and trace across the boundary — thread the same trace/thread id (see previous section) into your observability stack on both sides so a cross-repo failure is debuggable as one incident, not two disconnected logs.
Interview framing

"You're exposing a LangGraph agent to be called by other teams' agents via A2A — what do you check before shipping it?" — Authentication on the Agent Card, least-privilege tool scoping for A2A-originated tasks specifically (don't give a remote caller the same tool access a trusted internal user gets), treating anything in the returned artifacts as untrusted content rather than instructions, and making sure contextId/thread_id are logged consistently so a bad interaction is traceable across both repos, not just yours.

Multi-Agent Orchestration Patterns over A2A

Once you have two repos talking, the natural next question is how many, and who's in charge.

Supervisor / host pattern

A Supervisor agent starts up, fetches each sub-agent's agent-card.json to discover their capabilities, then assigns tasks to the appropriate sub-agent based on the user's question and returns results — this is the LangGraph-supervisor-style pattern, extended across process/repo boundaries via A2A instead of in-process function calls.

Hierarchical agent tree (ADK's native model)

ADK's root agent composes local sub-agents and remote A2A agents in the same tree — local sub-agents communicate in-memory with no network overhead, while remote agents communicate over A2A — letting you mix cheap in-process specialists with expensive cross-repo ones in one coherent orchestration.

Cross-framework mesh

A production reference architecture: a Purchasing Concierge (ADK, A2A client) orchestrating a Burger agent (CrewAI) and a Pizza agent (LangGraph), each independently deployed with its own environment — proof that A2A genuinely doesn't care what built the agent on the other end, only that it speaks the protocol.

When NOT to reach for A2A

Because A2A typically wraps your agent in a separate process and exposes it externally, it should be used only when necessary — two agents in the same LangGraph graph, in the same process, coordinating tightly, are almost always better served as two nodes sharing one AgentState than as two A2A services paying network and serialization overhead for no isolation benefit.

Production Pitfalls

What actually goes wrong the first time LangGraph and ADK repos try to talk in production.

  • SDK version mismatch. ADK's A2A integration works with both a2a-sdk 0.3.x (compatibility mode) and 1.x.x, auto-detected — but hand-constructed AgentCard/Executor code written against 0.3.x types may need the v1.0 migration guide when the other side upgrades. Pin and coordinate SDK versions across the two repos explicitly; don't assume compatibility.
  • Hostname mismatches in containerized/cloud deploys. If you're deploying to an environment where the hostname is defined differently outside the container, use a HOST_OVERRIDE-style environment variable to set the expected hostname on the Agent Card — otherwise the card advertises an unreachable internal address.
  • contextId/thread_id drift (covered above) — the single most common source of "the agent forgot what we were just talking about" bugs in cross-framework setups.
  • Streaming half-implemented on one side. If the LangGraph server advertises capabilities.streaming: true in its Agent Card but the executor doesn't actually enqueue incremental events, ADK's streaming client will hang waiting for updates that never come — keep the advertised capabilities honest.
  • No circuit breaker / timeout on the remote call. A LangGraph tool node calling out to a remote ADK agent needs a timeout and a fallback path — an unreachable remote agent shouldn't hang the entire graph run.
  • Treating A2A traffic as implicitly trusted because it's "internal." See the security section — two independently-deployed repos are a real trust boundary even on the same private network.

Interview Cheat-Sheet

Framework-choice questions first, then A2A-specific questions weighted toward your actual LangGraph↔ADK experience.

Framework choice

Why would you pick LangGraph over CrewAI for a production system, specifically?framework

Explicit conditional edges instead of LLM-driven routing means deterministic, auditable control flow and lower token cost — benchmarks show roughly 47% lower token spend than CrewAI on comparable tasks. LangGraph also has built-in checkpointing with time-travel debugging, which matters for anything needing human approval steps or post-incident replay. CrewAI wins on speed to a working prototype, not on production control.

Your team has AutoGen in production. What do you tell them?framework

AutoGen is in maintenance mode as of 2026 — Microsoft merged it with Semantic Kernel into the Microsoft Agent Framework, which reached GA in April 2026. Existing AutoGen code keeps receiving critical fixes, but new feature work goes to Agent Framework. Plan a migration; LangGraph is the closest architectural fit, CrewAI the easiest if the agents are already role-based.

MCP vs A2A

Explain the difference between MCP and A2A in one breath.protocols

MCP standardizes agent-to-tool connections — the counterpart is a stateless function with a fixed schema. A2A standardizes agent-to-agent connections — the counterpart is a full agent that can reason, hold state across a multi-turn interaction, and retains its full capabilities rather than being reduced to a function call. They're complementary layers, commonly used together in the same system.

When would collapsing a remote agent into an MCP tool be the wrong call?protocols

When the remote side needs to negotiate, ask a clarifying question, or maintain state across several exchanges rather than answer one self-contained function call — that behavior is exactly what MCP's stateless tool model throws away and A2A's task/message model preserves.

A2A protocol mechanics

Walk through what happens from cold start when Agent A wants to delegate a task to Agent B over A2A.a2a

Agent A fetches Agent B's Agent Card from its well-known URL to discover its skills and endpoint. Agent A sends a message/send (or message/sendStream) JSON-RPC request, creating a Task with a unique id and an initial "submitted" status. Agent B's request handler routes it to an AgentExecutor, which invokes the actual underlying agent logic. Results are enqueued as events, the task status updates (e.g., to "working" then "completed"), and the response streams or returns synchronously back to Agent A.

What's the actual purpose of the AgentExecutor abstraction that every framework's A2A integration uses?a2a

It cleanly separates protocol handling (JSON-RPC parsing, task lifecycle, streaming) from agent logic (what your LangGraph graph or ADK agent actually does). That separation is exactly what lets any framework's agent sit behind the same A2A server shell — you implement execute() and cancel(), the framework-agnostic plumbing does the rest.

LangGraph ↔ ADK specifically

Design a system where an ADK orchestrator delegates research questions to a LangGraph specialist agent.design

Expose the LangGraph agent as an A2A server via the a2a-sdk AgentExecutor pattern (or to_a2a()-equivalent), publishing an Agent Card describing its research skill. On the ADK side, wrap it with RemoteA2aAgent pointed at that card's URL, and add it to the root agent's sub_agents list — from the orchestrator's perspective it's indistinguishable from a local sub-agent except for network latency. Map A2A's contextId to the LangGraph thread_id in the executor so multi-turn conversations retain memory across calls.

A multi-turn conversation with your LangGraph specialist keeps losing context on the second and later A2A calls. What's your first suspicion?design

Context/thread mapping. Check whether the executor is generating a fresh LangGraph thread_id on every call instead of reusing A2A's contextId — if the client isn't passing contextId back on follow-up messages, or the server isn't mapping it consistently to thread_id, every "turn" looks like the first turn of a brand-new conversation to the checkpointer.

Should you treat the ADK repo's requests to your LangGraph agent as trusted, since it's your own company's system?design

No — independently deployed and independently released services are a real trust boundary regardless of internal network location. Authenticate requests per the Agent Card's declared requirements, scope tool access for A2A-originated tasks to least privilege, and treat content coming back in artifacts as untrusted data rather than instructions to follow.

When would you NOT use A2A between two agents on your own team?design

When they run in the same process and coordinate tightly — two nodes in one LangGraph graph sharing an AgentState is simpler, faster, and has none of A2A's network/serialization overhead. Reach for A2A specifically when the agents are independently deployed, built on different frameworks, or owned by different teams — the isolation and formal contract are the entire value proposition, and they cost something.
