00 ★

The Memory-Bandwidth Problem — Start Here

Every optimization in this document exists to fix the same root cause. Understand this once and everything else becomes obvious.

Modern LLM inference runs on GPUs built for massively parallel matrix multiplication — but decoding one token at a time, for one request, uses almost none of that parallelism. At batch size 1, 16-bit precision decoding has an arithmetic intensity of roughly 1 — meaning the GPU spends nearly all its time waiting on memory bandwidth to load weights, not actually computing. A reference GPT-2 Large inference on a quiesced RTX 4090 achieves only about 150 tokens/second, for a compute utilization of roughly 0.13% — the GPU's raw compute power is almost entirely wasted, governed instead by the memory-bandwidth roofline.

The one sentence that explains this entire document

The raw mathematics of model serving dictate that memory bandwidth, rather than pure compute power, is the primary bottleneck for inference speed. Every technique in this document — batching, paging, quantization, speculative decoding — is a different strategy for getting more useful work done per byte of memory bandwidth consumed, because that bandwidth, not FLOPs, is the actual scarce resource.

The fix for low arithmetic intensity at batch size 1 is obvious once framed this way: serve many requests at once, so the same weight-loading cost is amortized across many tokens being generated in parallel. That's exactly what batching solves — and naive batching has its own problems, which is where continuous batching and PagedAttention come in.

01 ★

Continuous Batching

The single biggest throughput lever in modern LLM serving — and the reason naive batching leaves most of the gain on the table.

Naive ("static") batching waits until a fixed-size batch of requests has arrived, processes all of them together, and only starts the next batch once every request in the current batch has finished generating — meaning a batch is only as fast as its slowest (longest-output) request, and the GPU sits partially idle waiting for short requests to finish alongside long ones. Continuous batching dynamically groups requests as they arrive, rather than waiting for a full batch — as soon as any request in a running batch finishes, a new request from the queue is immediately spliced in to take its slot, keeping the GPU busy on bursty, variable-length, real-world traffic without manual batching logic.

The measured impact

The difference between a purpose-built inference server and a naive deployment can be up to 24x throughput on identical hardware — continuous batching combined with the memory-management techniques below is where nearly all of that gap comes from. A server that handles 4x more requests on the same GPU means you need 4x fewer GPUs for the same traffic — this is a direct, measurable cost lever, not a marginal tuning knob.

02 ★

PagedAttention & vLLM

vLLM's core innovation, and the reason it became the default 2026 choice for production LLM serving.

Every request being decoded needs its own growing KV cache (recall Topic 13's vector-search KV-cache concept — this is the analogous idea inside the serving engine itself: cached key/value tensors from every previous token, needed so attention doesn't have to recompute from scratch each step). Traditional inference engines allocate one contiguous memory block per request for this cache, sized for the maximum possible sequence length — this wastes 60-80% of KV cache memory through fragmentation, since most requests never reach that maximum length, and the unused reserved space can't be given to other requests.

PagedAttention, vLLM's core design, borrows virtual memory concepts directly from operating systems: it breaks the KV cache into small, non-contiguous "pages" and maps them dynamically, rather than reserving one large contiguous block per request upfront. This lets vLLM serve many concurrent requests without reserving per-request memory upfront — previous systems wasted 60-80% of KV cache memory; vLLM wastes under 4%.

Where this concept is heading

PagedAttention now ships natively in Hugging Face Transformers itself, achieving roughly 84% of vLLM's throughput on a single GPU without any extra runtime — a sign the inference stack is converging, and today's performance gaps between engines may narrow over time as core techniques get absorbed into the broader ecosystem rather than staying engine-specific advantages.

03

RadixAttention & SGLang

SGLang's answer to the same memory problem, optimized for a different traffic shape — directly relevant to agentic and RAG workloads specifically.

SGLang's signature technique is RadixAttention: automatic prefix caching via a radix tree data structure, which detects and reuses shared prefixes across different requests — exactly the same insight as Topic 7's prompt caching, but implemented at the serving-engine level across concurrent requests from potentially different users, not just within one repeated call from the same client.

Interview framing

"You're serving a RAG-based agentic pipeline with heavy prompt reuse across users. Which serving engine would you evaluate first, and why?" — SGLang, specifically because RadixAttention's prefix caching is built exactly for this traffic shape — shared system prompts, shared retrieved-context prefixes, and multi-turn conversation history all benefit from automatic cross-request prefix reuse. The 29% throughput advantage measured on smaller models narrows significantly at 70B+ scale, so this recommendation is model-size-dependent — always validate against your own traffic pattern rather than trusting a single benchmark number in isolation.

05

KV Cache Memory Math

The formula behind why KV cache, not model weights, is often the real constraint on how many concurrent users a GPU can serve.

kv_cache_size_formula.txt
KV cache size (bytes) =
    2                       # K and V, both cached
    × num_layers
    × num_attention_heads × head_dim   # = hidden_size, typically
    × sequence_length
    × batch_size (concurrent sequences)
    × bytes_per_element     # 2 for FP16/BF16

Notice this scales linearly with both sequence length and concurrent batch size — doubling either one doubles KV cache memory demand. This is precisely why leaving ample VRAM headroom after loading model weights matters so much for concurrency: quantizing a 70B model from ~140GB (FP16) down to ~35GB (4-bit) doesn't just fit the model on smaller hardware, it frees dramatically more room for the KV cache, which is essential to handle high-concurrency requests in production — directly connecting Section 06's quantization formats back to this section's memory math.

Why this is the real bottleneck at scale, not raw model size

Once a model's weights fit comfortably in VRAM, the actual limit on how many concurrent users a single GPU can serve is almost always KV cache capacity, not weight storage — this is exactly the constraint PagedAttention (Section 02) is built to use as efficiently as possible, and exactly why quantization's VRAM savings compound directly into concurrency gains, not just "the model fits."

06 ★

Deployment Quantization: GGUF, AWQ, GPTQ

Distinct from Topic 13's vector-search quantization — this is compressing the model's own weights for deployment. Three formats, each optimized for a different serving context.

Quantization compresses weights from 16-bit floats to 4-bit integers, shrinking models by roughly 75% with surprisingly little quality loss. A Llama 3 70B model needing ~140GB of VRAM in FP16 drops to roughly 35-40GB at 4-bit — the difference between requiring multiple A100s and fitting on a single high-end consumer or prosumer GPU.

FormatApproachBest for
GGUFK-quants — mixed bit-depth per layer type (e.g. attention layers at 6-bit, feed-forward at 4-bit), giving better quality-per-bit than naive uniform quantizationCPU inference and Ollama-style local deployment — retains roughly 92% quality at Q4_K_M
AWQActivation-aware — observes model activations during a calibration phase to identify "salient" weights that matter most for output quality, protecting those with higher precision while aggressively quantizing the restProduction GPU serving — the 2026 default for that use case, particularly strong for instruction-tuned models; fastest on vLLM with the Marlin kernel
GPTQA mature, purely weight-based (not activation-aware) GPU quantization approach with an extensive pre-quantized model library already availableGPU serving where a pre-quantized checkpoint already exists for your target model — a practical, adoption-driven reason to prefer it over AWQ in specific cases
bitsandbytesThe only one of these four that supports training directlyQLoRA fine-tuning (Doc 15) specifically — train adapters on a 4-bit base model, then merge back or keep separate
A precise, useful fact: you cannot directly fine-tune the other three formats

GGUF, AWQ, and GPTQ are deployment-time formats — you can't directly fine-tune pre-quantized weights in these formats. The correct workflow is either bitsandbytes with QLoRA to train adapters on a 4-bit base model, then merge and optionally re-export to a deployment format, or fine-tune in full precision first and quantize to GGUF/AWQ/GPTQ afterward purely for serving. Conflating "quantization for training" (bitsandbytes/QLoRA) with "quantization for serving" (GGUF/AWQ/GPTQ) is a common, avoidable confusion.

Interview framing

"You need to deploy a 70B model for production GPU serving with high concurrency. Which quantization format?" — AWQ, as the 2026 default for GPU production serving specifically — its activation-aware calibration protects the weights that matter most for output quality while aggressively compressing the rest, it's the fastest on vLLM with the Marlin kernel, and it consistently outperforms GGUF in concurrent-throughput benchmarks due to optimized integer matrix multiplication kernels. GGUF would be the better choice specifically for CPU-bound or Ollama-style local/edge deployment instead, where its K-quant mixed-precision approach and broader hardware compatibility matter more than raw GPU-concurrent throughput.

07 ★

Speculative Decoding

A genuinely clever trick for the batch-size-1 memory-bandwidth problem from Section 00 — generate more, verify cheaply.

Speculative decoding uses a small, fast "draft" model to generate several candidate next tokens speculatively, then has the large target model verify all of them in a single forward pass — because verifying multiple tokens in parallel costs roughly the same memory-bandwidth budget as generating one token normally (per Section 00's roofline problem), any correctly-guessed draft tokens are essentially "free," accepted without the large model needing a separate full decoding step for each.

VariantWhat's different
Classic speculative decodingA separate, smaller model from the same family serves as the draft model
MedusaAdds multiple extra decoding heads directly to the target model itself, predicting several future positions at once, avoiding the need for a wholly separate draft model
EAGLESpeculates in feature space rather than token space, specifically addressing feature uncertainty in the draft process for improved acceptance rates
Self-speculative decodingUses a subset of the target model's own layers as the draft, avoiding a separate model entirely
Why this isn't free — the real tradeoff

Speculative decoding is lossless (the target model always verifies, so output distribution is unchanged) but not free — it requires either a separate draft model (extra memory and complexity) or extra heads/layers on the target model, and the speedup is entirely dependent on the draft's acceptance rate: if the draft model rarely guesses correctly, verification overhead can erode or even negate the benefit. It composes with the other techniques in this document (quantized draft models, batched speculative verification) rather than replacing them.

Interview framing

"Explain speculative decoding and why it speeds up inference without changing output quality." — A small draft model generates several candidate tokens quickly; the large target model verifies all of them in a single forward pass rather than one sequential pass per token. Because that verification pass costs roughly the same memory-bandwidth budget as generating just one token normally (the batch-1 memory-bandwidth bottleneck from earlier), correctly-guessed draft tokens are accepted essentially for free. It's lossless because the target model still makes the final accept/reject decision on every token — the output distribution exactly matches what the target model alone would have produced, just computed faster.

08

GPU Memory Math, Worked Example

The exact calculation to answer "will this model fit" — walk this out loud in an interview.

gpu_memory_worked_example.txt
# Scenario: serve a 70B parameter model, want to know if it fits on a single 80GB GPU
# with room for reasonable concurrency

Step 1 -- model weight memory:
  70B params × 2 bytes (FP16)               = 140 GB   # doesn't fit on one 80GB GPU
  70B params × 0.5 bytes (4-bit quantized)  = 35 GB    # fits, with 45GB left over

Step 2 -- KV cache memory (per the formula in Section 05), example config:
  num_layers = 80, hidden_size = 8192, 2 bytes/elem
  sequence_length = 4096, batch_size (concurrent seqs) = 32

  KV cache = 2 × 80 × 8192 × 4096 × 32 × 2 bytes
           ≈ 344 GB   # !! this alone exceeds the entire GPU's memory

Step 3 -- the real lesson:
  At meaningful concurrency and sequence length, KV cache -- not model
  weights -- is almost always the binding constraint. Quantizing the
  MODEL frees VRAM, but the KV CACHE itself is usually the thing you
  actually need to manage carefully (via PagedAttention-style paging,
  shorter max sequence length, lower concurrency, or KV cache quantization).
The insight this worked example is built to produce

Quantizing the model's weights is necessary but not sufficient — the KV cache scales with concurrency and sequence length independently of model quantization, and at real production concurrency levels it routinely dwarfs the model weights themselves. This is exactly why PagedAttention (Section 02) matters as much as or more than weight quantization for serving many concurrent users, and it's the calculation that separates a candidate who's actually done GPU capacity planning from one who's only memorized "quantize the model."

10

Production Pitfalls

What actually goes wrong.

  • Deploying with naive/static batching. Leaves most of the available throughput on the table — up to 24x on identical hardware versus a purpose-built continuous-batching engine.
  • Only accounting for model weight memory, not KV cache. Per Section 08's worked example, KV cache at real concurrency routinely exceeds model weight memory by a wide margin — a capacity plan that ignores this will hit OOM errors in production that never showed up in single-request testing.
  • Recommending TGI for a new 2026 deployment without flagging its maintenance-mode status. A visible stale-knowledge signal in an infra-focused interview.
  • Conflating deployment quantization (GGUF/AWQ/GPTQ) with training quantization (bitsandbytes/QLoRA). You cannot directly fine-tune pre-quantized GGUF/AWQ/GPTQ weights — this is a common, avoidable confusion between Doc 15's training-time quantization and this document's serving-time quantization.
  • Choosing an engine based on published benchmarks alone. Numbers swing 2-3x depending on sequence length distribution, prefix overlap, and quantization — always validate against your own actual traffic before committing.
  • Ignoring draft-model acceptance rate when adopting speculative decoding. A poorly matched draft model can erode or negate the speedup entirely — the technique's benefit is not guaranteed, it's conditional on draft quality.
  • Treating engine choice as fixed regardless of model scale. The SGLang-vs-vLLM performance gap narrows sharply from ~29% at 7-8B to 3-5% at 70B+ — a recommendation validated at one model size doesn't automatically transfer to another.

Interview Cheat-Sheet

Grouped by depth.

Why is single-request LLM decoding memory-bandwidth-bound rather than compute-bound, and why does this matter for serving design?core

At batch size 1, generating one token requires loading the entire model's weights from GPU memory but only performing a comparatively tiny amount of computation per token — arithmetic intensity is roughly 1, meaning the GPU spends nearly all its time waiting on memory bandwidth rather than computing, achieving well under 1% compute utilization in practice. This matters because it means the fix isn't "make the GPU compute faster" — it's "amortize that same memory-bandwidth cost across more useful work," which is exactly what batching, paging, and speculative decoding all do in different ways.

Explain continuous batching and quantify why it matters.core

Static batching waits for a fixed batch to fill and finishes only when every request in it completes, wasting GPU capacity on short requests stuck waiting alongside long ones. Continuous batching dynamically splices new requests into a running batch's slots as soon as any request finishes, keeping the GPU consistently busy on bursty, variable-length traffic. The measured impact is large — up to 24x throughput versus a naive deployment on identical hardware, which translates directly into needing far fewer GPUs for the same traffic volume.

Explain PagedAttention and the specific problem it solves.core

Traditional serving engines reserve one contiguous memory block per request for its KV cache, sized for the maximum possible sequence length — since most requests never reach that maximum, this wastes 60-80% of KV cache memory through fragmentation. PagedAttention borrows virtual-memory paging from operating systems, breaking the KV cache into small, dynamically-mapped, non-contiguous pages instead of one large reserved block — reducing that waste to under 4% and letting far more concurrent requests fit in the same GPU memory.

When would you choose SGLang over vLLM, and when does that choice stop mattering?architecture

Choose SGLang for prefix-heavy workloads — RAG, agentic pipelines, multi-turn conversation, structured output — where RadixAttention's automatic cross-request prefix caching measurably helps, roughly a 29% throughput advantage on 7-8B models in published H100 benchmarks. That advantage narrows to 3-5% at 70B+ scale, where the workload becomes more compute-bound than memory-bound and PagedAttention/RadixAttention converge — at that scale, operational maturity and ecosystem support (favoring vLLM) matter more than the raw engine choice.

Walk through the GPU memory math for serving a 70B model: does it fit, and what's the real constraint?architecture

At FP16, 70B parameters need roughly 140GB — doesn't fit on a single 80GB GPU. Quantized to 4-bit, that drops to roughly 35GB, comfortably fitting with room to spare. But the KV cache scales independently with concurrency and sequence length — at realistic production concurrency (dozens of concurrent sequences, several-thousand-token context), KV cache memory can easily exceed the entire GPU's capacity on its own, becoming the actual binding constraint rather than model weights. Managing this requires PagedAttention-style paging, careful concurrency/sequence-length limits, or KV cache quantization — quantizing the model alone is necessary but not sufficient for real production capacity planning.

Compare AWQ and GGUF and explain when you'd pick each.quantization

AWQ uses activation-aware calibration to identify and protect "salient" weights that matter most for output quality, and is the 2026 default for production GPU serving — fastest on vLLM, strong quality retention, particularly for instruction-tuned models. GGUF uses K-quants (mixed bit-depth per layer type) and is optimized for CPU inference and local/edge deployment (Ollama-style) rather than raw GPU-concurrent throughput. Quality differences between the two at 4-bit are minor (roughly 92-95% of FP16 quality for both) — the real deciding factor is your inference stack and target hardware, not quality expectations.

Why is speculative decoding lossless despite using a smaller, less capable draft model?optimization

The draft model only proposes candidate tokens — the large target model always verifies every proposed token in a single forward pass and rejects (and corrects) anything the draft got wrong. Because the final accept/reject decision always rests with the target model, the output distribution exactly matches what the target model alone would have produced; the draft model only affects how many tokens get generated per expensive verification pass, not what tokens are ultimately accepted. The speedup comes entirely from the fact that verifying several tokens in one pass costs roughly the same memory-bandwidth budget as generating a single token normally.

Design the serving infrastructure for a production coding-agent product needing low-latency, high-concurrency inference on a 70B model.design

Start with vLLM or SGLang (evaluate both on real traffic given the coding-agent's likely prefix-heavy pattern from repeated system prompts and shared code context — SGLang is worth a real look here) with AWQ 4-bit quantization to fit comfortably on available GPUs with headroom for KV cache. Explicitly capacity-plan the KV cache separately from model weights using the formula from this document, sized against your real expected concurrency and context length, since that — not model weight size — is the likely binding constraint at production scale. Layer speculative decoding on top if latency-critical, using a smaller model from the same family as the draft, and validate the acceptance rate on real coding-task traffic before committing to it in production.

Glossary

Every term used in this document.

Arithmetic intensity
Ratio of compute operations to memory operations; low at batch-1 decoding, making inference memory-bandwidth-bound.
Continuous batching
Dynamically splicing new requests into a running batch's freed slots, rather than waiting for a fixed batch to complete.
PagedAttention
vLLM's KV cache memory manager using OS-style paging instead of contiguous per-request allocation.
RadixAttention
SGLang's automatic cross-request prefix caching via a radix tree, optimized for prefix-heavy workloads.
KV cache
Cached key/value attention tensors from previous tokens, avoiding recomputation each decoding step; scales with sequence length × batch size.
GGUF
Quantization format using mixed-precision K-quants; optimized for CPU/local/Ollama deployment.
AWQ
Activation-aware weight quantization protecting salient weights; 2026 default for production GPU serving.
GPTQ
Mature weight-based GPU quantization format with an extensive pre-quantized model library.
bitsandbytes
The quantization library that supports training (QLoRA); distinct from deployment-only formats.
Speculative decoding
Using a fast draft model to propose tokens, verified in one batched pass by the target model, for lossless speedup.
Draft model / target model
The small proposer and large verifier models in speculative decoding.
Medusa / EAGLE
Speculative decoding variants using extra decoding heads or feature-space speculation instead of a separate draft model.
