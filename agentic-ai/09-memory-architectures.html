Memory Architectures for AI Agents

The full cognitive-science-grounded taxonomy (working, episodic, semantic, procedural), each type explored in real depth — implementation form, storage mechanics, decay and consolidation — plus the production architectures that implement them (MemGPT/Letta, Mem0, Zep/Graphiti, LangMem), real benchmark numbers, and the failure modes every "agent that remembers you" system eventually hits.

00 ★

The CoALA Taxonomy — Four Types, Not a Vendor Invention

The single framework every serious memory conversation is organized around. It comes from cognitive science, not a product team, and knowing that lineage is worth citing directly.

The four standard types are in-context memory (the active context window), episodic memory (records of past interactions), semantic memory (factual world knowledge), and procedural memory (rules and skills). The CoALA paper (Princeton, 2023) formalised this taxonomy from cognitive science for language model agents.

TypeCognitive science originImplementation form
Working memoryBaddeley & Hitch, 1974The active context window — everything the model can see this turn
Episodic memoryTulving, 1972 — episodic/semantic split within declarative memorySession logs, conversation transcripts, structured "episodes"
Semantic memoryTulving, 1972Distilled facts, user preferences, entity relationships — vector store or knowledge graph
Procedural memorySquire, 1987 — declarative/procedural distinctionSystem prompts, playbooks, skills, validated runbooks
Why the lineage matters in an interview

These are not vendor-invented categories — LangChain's LangGraph documentation adopts the same semantic/episodic/procedural classification for long-term memory and explicitly cites CoALA as the source of the mapping. Being able to say "this maps to Tulving's 1972 episodic/semantic distinction and Squire's 1987 procedural addition, formalized for LLM agents by the CoALA paper" is a genuine signal that you understand the taxonomy is principled, not marketing — most candidates can name the four types; fewer can explain where they came from.

Two more types show up in the more advanced 2026 literature:

  • Organizational / context memory — a fifth type identified in "Governed Memory: A Production Architecture for Multi-Agent Workflows" (arXiv:2603.17787, March 2026), covered in its own section below.
01

Working / In-Context Memory

The tier you already know deeply from earlier topics — this section is deliberately short and exists mainly to connect it to the taxonomy.

Working memory is the active context window — everything the model can directly attend to this turn, with no retrieval step required. This is exactly the LangGraph thread/checkpointer state from the foundational bible, and the context-compaction techniques (sliding window, summarization, subgraph isolation) from Topic 7's production system-design doc. It's fast, direct, but strictly bounded by context window size and, per Topic 7, interacts with prompt caching in ways that need deliberate coordination.

The architectural relationship to everything else in this document

Every long-term memory type below exists specifically because working memory is too small and too ephemeral to hold everything an agent might eventually need — long-term memory's entire job is deciding what's worth promoting out of a session's working memory before that session ends and the context is gone.

02 ★

Episodic Memory, In Depth

Records of specific past experiences — what happened, when, with what outcome. The "diary" layer.

Episodic memory records specific past experiences: what happened, when, in which session, with what outcome. Implemented as a time-series store with full-text and embedding-based retrieval, temporally indexed interaction histories — what happened, when, with whom, and with what outcome.

Why a monolithic store fails here

Episodic memory has fundamentally different access patterns than semantic memory: queries are often temporal ("what did we discuss last Tuesday," "what was the outcome of the last three support tickets from this user") rather than purely similarity-based, which is exactly why the required storage and query mechanics differ by memory type, and monolithic storage approaches often fail — a pure vector store with no temporal indexing structurally can't answer "what happened most recently" as a first-class query.

Importance scoring — not every episode deserves to be kept

Not every interaction deserves preservation. Production systems implement importance scoring based on recency, frequency, Bayesian surprise, entity salience, and outcome signals. The top twenty percent of events by composite score are promoted to long-term storage; the bottom twenty percent are pruned.

The forgetting-curve connection

MemoryBank dynamically adjusts memory strength according to the Ebbinghaus forgetting curve, and supports continual memory updating and user profile construction — episodic memories decay in retrieval priority over time unless reinforced by repeated relevance, directly modeling the human forgetting curve rather than using a flat TTL.

03 ★

Semantic Memory, In Depth

Distilled, generalized facts — not "what happened," but "what is true." The layer that makes an agent informed rather than merely experienced.

Semantic memory contains distilled facts and preferences extracted from raw episodes — user profiles, entity relationships, and reusable knowledge. This requires vector stores or knowledge graphs with conflict resolution. Implemented as a knowledge graph storing facts, concepts, and relationships with temporal validity bounds, supporting multi-hop graph traversal and hybrid vector-graph retrieval.

The critical distinction from episodic memory: semantic memory is derived, not raw. "User prefers window seats" is a semantic fact; "on March 3rd, the user asked for a window seat and confirmed satisfaction" is the episodic record that fact was extracted from. This derivation step is memory consolidation, covered in its own section below.

Where semantic memory actually breaks in production

Failures include stale facts, contradictory entries, and progressive corruption. Unlike episodic memory (where an old record is just an old record — still true that it happened), a stale semantic fact is actively wrong and will be presented to the user or used in reasoning as if current. This is why semantic memory specifically needs conflict resolution and staleness management, covered in their own sections below — episodic memory doesn't have the same acute failure mode.

Beyond pure vector similarity — the 2026 shift

Graph memory in AI agents was largely experimental in 2024. By 2026, the production pattern has changed — memory systems are moving beyond pure vector similarity. Vector memory retrieves semantically similar facts; graph-style memory retrieves facts through entities and relationships. Both are useful; neither is sufficient alone.

04

Procedural Memory — the Immature, Highest-Leverage Frontier

"Knowing how" rather than "knowing that" — and, per the most current sources, the layer the ecosystem has invested in least.

Procedural memory in AI agents represents "knowing how" to perform tasks, focusing on execution rather than facts or past events. It governs how agents carry out workflows, use tools, coordinate sub-agents, and make decisions. It captures learned workflows, decision rules, and behavioral patterns, and lives in configuration files, prompt templates, or versioned stores.

The honest state of the field — say this to sound current

Amazon Bedrock AgentCore Memory has built-in strategies for preferences, facts, summaries, and episodes, but nothing labeled procedural — the closest functional neighbor is the episodic strategy's reflection capability, which consolidates lessons across episodes, useful raw material for procedures but not a managed procedure store. mem0's State of AI Agent Memory 2026 report describes the tooling for managing procedural memory specifically as "still early-stage." That immaturity is exactly why procedural memory is the highest-leverage layer to design deliberately — it is where an agent's performance compounds, and where the ecosystem gives you the least off-the-shelf help.

Semantic memory makes an agent informed; procedural memory makes it better at its job. A support agent with rich semantic memory knows the customer's order history; a support agent with rich procedural memory has learned, across thousands of tickets, which troubleshooting sequence actually resolves this class of issue fastest — that's a categorically different, compounding kind of improvement.

Interview framing

"Why is procedural memory harder to build than semantic memory?" — Semantic memory has converged tooling (vector stores, knowledge graphs, well-studied extraction pipelines). Procedural memory requires identifying which action sequences actually caused good outcomes — a credit-assignment problem closer to reinforcement learning than to fact extraction — and the field genuinely lacks mature off-the-shelf tooling for it as of 2026. Most production systems approximate it today with versioned prompt/playbook updates driven by manual review of failure patterns, not automated procedural learning.

05

Memory Consolidation — Episodic Becomes Semantic

The single most important cross-cutting mechanism in this entire document.

A crucial part of building intelligent agents is converting episodic memory into semantic memory. This process involves identifying patterns across past interactions and distilling them into reusable knowledge. Inspired by human cognition, this "memory consolidation" ensures agents can generalize, reduce redundancy, and improve efficiency over time. Without this step, agents remain limited to recalling past events rather than truly learning from them.

Concretely: dozens of episodic records of "user asked to reschedule a meeting" over months consolidate into a single semantic fact like "user frequently has scheduling conflicts on Mondays" — a generalization no single episode contains on its own, only visible once patterns across many episodes are distilled. This is the mechanism that turns an agent from "remembers what happened" into "has learned something."

06

The 5-Stage Memory Pipeline

Every production memory system, regardless of vendor, implements some version of this same pipeline.

The five-stage pipeline — extraction, integration, storage, retrieval, and forgetting — provides the structural foundation for production deployments.

StageWhat happens
ExtractionAn LLM extracts salient memory candidates from conversation contexts — deciding what in a raw session is even worth remembering
IntegrationAdaptive operations (addition, update, or deletion) based on semantic similarity matching against existing memory — new information gets merged with, or flagged against, what's already stored
StoragePersisted to the appropriate backend — vector store, knowledge graph, key-value store — matched to the memory type's access pattern
RetrievalMulti-signal search at query time (covered in its own section below)
ForgettingDecay, pruning, or supersession of memories that are stale, low-importance, or contradicted (covered next)
07

Forgetting & Staleness Management

Deliberately forgetting is a feature, not a bug — an agent that never forgets accumulates noise and stale facts at the same rate it accumulates useful memory.

MechanismDescription
Ebbinghaus-curve decayDynamically adjusts memory strength according to the forgetting curve — unreinforced memories fade in retrieval priority gradually, not via a hard cutoff
Composite importance scoringRecency, frequency, Bayesian surprise, entity salience, and outcome signals combined into one score, with top/bottom quintile promotion/pruning
Supersede detectionA-MEM introduces dynamic links between memory entries with supersede detection, addressing memory staleness directly — a new fact explicitly marks an old one as outdated rather than the two coexisting ambiguously
Tiered decay (short/mid/long-term)MemoryOS imposes a three-tier storage architecture with different management strategies per tier — memory migrates between tiers based on reinforcement, not a single global decay rate
Interview framing

"Why would you deliberately design an agent to forget things?" — Unbounded memory retention has two costs: retrieval quality degrades as the store fills with low-value or contradicted entries competing for relevance at query time, and stale facts actively mislead reasoning if presented as current. Forgetting mechanisms — decay curves, importance-based pruning, explicit supersession — are how a memory system stays useful rather than becoming an ever-growing liability; this is directly analogous to why Topic 7's context compaction exists for working memory, applied to the long-term tier instead.

08

Conflict Resolution

What happens when new information contradicts something already stored.

When new information conflicts with stored memories, systems must handle contradictions gracefully. The three broad strategies:

  • Overwrite — the new fact simply replaces the old one, appropriate when the new information is clearly more recent and the fact type is inherently single-valued (e.g., "current job title").
  • Supersede with history — the old fact is marked outdated but retained for audit/temporal-reasoning purposes rather than deleted, exactly what A-MEM's supersede detection and Zep's bi-temporal modeling (below) are built for.
  • Flag for review — genuinely ambiguous contradictions (not simply "old vs new," but conflicting simultaneous claims) get surfaced rather than silently resolved either way, appropriate for high-stakes semantic facts.
The assumption that quietly breaks production systems

These systems share a common assumption: the LLM will honor retrieved memory once it is injected into the context. This is not guaranteed — a model can retrieve a correct, current memory and still generate a response inconsistent with it, especially under conflicting signals elsewhere in the prompt. Memory correctness at the storage layer does not guarantee behavioral correctness at generation time; this gap is exactly what recent "persona drift" detection research is starting to measure.

09

Multi-Signal Memory Retrieval

Pure vector similarity is no longer the production default for memory retrieval — direct continuity with Topic 8's hybrid-search argument, applied to memory instead of documents.

Multi-signal retrieval runs three scoring passes in parallel — semantic similarity, keyword matching, and entity matching — and fuses the results. The biggest gains are on temporal queries (+29.6 points) and multi-hop reasoning (+23.1 points), the two categories that most directly reflect how agents handle real user histories.

mem0_entity_linking.txt
# Mem0's entity-linking mechanism
during add():
    entities = extract_entities(memory_text)
    store(entities, collection=f"{collection}_entities")

during search(query):
    query_entities = extract_entities(query)
    entity_matches = match(query_entities, f"{collection}_entities")
    # entity matches BOOST relevant memories inside the combined score
    final_score = combine(semantic_score, bm25_score, entity_boost)

Vector memory retrieves semantically similar facts; graph-style memory retrieves facts through entities and relationships. Both are useful; neither is sufficient alone. The direct parallel to Topic 8: exactly as dense embeddings miss exact-match terms that BM25 catches, pure semantic-similarity memory retrieval misses entity-anchored and temporal queries that keyword and graph-traversal signals catch — the fix is the same fusion principle applied to a different data type.

Reference Architectures: MemGPT/Letta, Mem0, Zep/Graphiti

Three genuinely different architectural philosophies for the same problem — know all three well enough to compare them unprompted.

MemGPT / Letta — the operating-system model

Introduces a virtual memory abstraction inspired by operating systems, in which information is dynamically paged between context and external storage. Letta extends the core architecture with filesystem-based memory storage, PostgreSQL persistence, and enhanced tool integration — the agent itself decides, via explicit tool calls, what to page in and out of its own limited context window, treating the LLM's context exactly like a CPU's fast-but-small RAM and external storage as a large-but-slow disk. This approach relies on recursive summarization and hierarchical compression, which can introduce latency variability and loss of information fidelity, particularly when precise textual recall is required.

Mem0 — the production extraction pipeline

Adopts a two-stage pipeline of memory extraction and update — an LLM extracts salient memory candidates from conversation contexts, then performs adaptive operations (addition, update, or deletion) based on semantic similarity matching. Implements a three-tier memory hierarchy spanning user, session, and agent scopes, combining vector retrieval, graph-based relational storage, and key-value indexing. Reports retrieval Recall@5 in the 0.5–0.6 range on LongMemEval-S — a useful concrete benchmark number to cite directly.

Zep / Graphiti — the temporal knowledge graph

Zep's core component Graphiti is a temporally-aware knowledge graph engine that dynamically synthesizes both unstructured conversational data and structured business data while maintaining historical relationships. Employs a three-tiered subgraph structure comprising episodic, semantic entity, and community layers, using bi-temporal modeling for data integration and hybrid search with multi-strategy reranking. Bi-temporal modeling specifically tracks both when a fact was true in the world and when the system learned it — the mechanism that makes "what did we believe about X as of last month, even though we've since learned it was wrong" queries answerable.

Interview framing

"Compare MemGPT/Letta's approach to Mem0's." — Letta treats memory management as the agent's own responsibility, via explicit paging tool calls modeled on OS virtual memory — powerful and self-directed, but recursive summarization can lose fidelity on precise recall. Mem0 treats memory management as an external pipeline the agent doesn't control directly — an LLM extracts and integrates memories automatically after each conversation, optimized for production reliability and cost rather than agent autonomy over its own memory. The choice is really: do you want the agent deciding what to remember (Letta) or a managed pipeline deciding for it (Mem0)?

Organizational / Governed Memory — the Emerging Fifth Type

What enterprise teams discover is missing after they've already built episodic, semantic, and procedural memory correctly.

"We started to realize we were missing this translation layer." The missing layer was organisational context, not conversation history. No upgrade to episodic or semantic memory would have fixed it. Snowflake's internal research, adding an ontology layer (a form of organisational context memory) to their agents, produced a 20% improvement in agent answer accuracy and a 39% reduction in tool calls. The ontology is entity identity mapping across systems — a component of organisational context memory that does not exist in any standard memory type.

Why this is genuinely a distinct type, not just more semantic memory

Semantic memory answers "what facts does this specific user/agent know." Organizational memory answers a different question: "does 'Acme Corp' in this system refer to the same entity as 'ACME-001' in that system" — cross-system identity resolution that no individual agent's personal semantic memory naturally accumulates, because it's a property of the organization's data landscape, not of any one conversation history.

Interview framing

"Your enterprise agent has solid episodic and semantic memory but still gives inconsistent answers across teams. What's missing?" — Likely an organizational/context memory gap — entity identity isn't unified across the systems the agent touches, so the same real-world entity looks like different things depending on which system's data the agent last queried. The fix is an ontology or entity-resolution layer, not more conversation memory — this is precisely the failure Snowflake's internal research identified, with a measured 20% accuracy and 39% tool-call-reduction improvement once added.

14

Production Pitfalls

What actually goes wrong.

  • Assuming retrieved memory is honored by the model. Injecting a correct, current memory into context doesn't guarantee the generated response is consistent with it — this gap is an active research area (persona drift detection), not a solved problem.
  • Treating memory as write-once, never-forget. Unbounded retention degrades retrieval quality and lets stale facts actively mislead reasoning — forgetting mechanisms are a feature, not a missing optimization.
  • Pure vector similarity retrieval for memory. Misses temporal queries and entity-anchored lookups exactly as pure dense retrieval misses exact-match terms in RAG (Topic 8) — multi-signal fusion is the 2026 production default.
  • Conflating episodic and semantic memory in one undifferentiated store. Different access patterns (temporal vs similarity-based) and different failure modes (an old episode is still true it happened; a stale semantic fact is actively wrong) — monolithic storage structurally can't serve both well.
  • No consolidation step. An agent that only accumulates raw episodes never generalizes — it remembers everything and learns nothing, since the pattern-distillation step from episodic to semantic memory is what produces reusable knowledge.
  • Framework lock-in from LangMem-style tightly-coupled memory tooling. If there's any real chance of switching agent frameworks later, a standalone memory system avoids an expensive re-platform.
  • Assuming paid-tier features are available on the free/open-source tier. Graph capabilities are commonly gated behind commercial tiers across the ecosystem — verify before architecting around a specific capability.
  • No organizational/entity-resolution layer in enterprise deployments. Solid personal memory per agent doesn't fix cross-system entity identity — a distinct problem requiring its own architecture.

Interview Cheat-Sheet

Grouped by depth.

Core taxonomy

Name and define the four CoALA memory types, and their cognitive-science origins.core

Working memory (Baddeley & Hitch, 1974) — the active context window. Episodic memory (Tulving, 1972) — records of specific past experiences with a "what happened, when" structure. Semantic memory (Tulving, 1972) — distilled, generalized facts. Procedural memory (Squire, 1987) — learned rules and skills governing how to execute tasks. The CoALA paper (Princeton, 2023) formalized this cognitive-science taxonomy specifically for LLM agents, and it's now the standard reference — LangGraph's own documentation cites it directly.

What's the structural difference between episodic and semantic memory that determines their storage architecture?core

Episodic memory is raw and temporally anchored — queries are often "what happened when," requiring time-series-aware storage with full-text and embedding retrieval. Semantic memory is derived and generalized — a distilled fact with no inherent timestamp of "when it happened," better served by a vector store or knowledge graph with conflict-resolution logic, since (unlike an old episode, which is still true that it occurred) a stale semantic fact is actively wrong if presented as current.

Explain memory consolidation and why it matters.core

Consolidation is the process of distilling patterns across many raw episodic records into generalized semantic facts — e.g., dozens of individual scheduling-conflict episodes consolidating into "user frequently has Monday conflicts." Without this step, an agent only ever recalls discrete past events; it never generalizes or learns from them, which is the actual difference between an agent that remembers and one that improves.

Architecture comparison

Compare MemGPT/Letta's memory model to Mem0's.architecture

Letta models the LLM's context window as an operating system's fast memory and external storage as disk, with the agent itself issuing explicit paging operations to move information in and out — self-directed, but reliant on recursive summarization that can lose fidelity for precise recall. Mem0 is an external, automated pipeline: an LLM extracts salient facts from a conversation after the fact and integrates them via similarity-matched add/update/delete operations, without the agent directly managing its own memory. The core trade-off is agent autonomy over memory (Letta) versus a managed, production-optimized pipeline (Mem0).

What does Zep's bi-temporal modeling actually solve that a standard knowledge graph doesn't?architecture

A standard knowledge graph typically tracks one timeline — when a fact is true. Bi-temporal modeling tracks two independent timelines: when a fact was true in the world, and when the system learned or recorded it. This makes it possible to correctly answer questions like "what did we believe as of last month" even after that belief has since been corrected — critical for enterprise temporal reasoning and audit trails, and the reason Zep specifically targets that use case over general-purpose semantic memory.

Why is pure vector similarity retrieval increasingly considered insufficient for memory in 2026 production systems?architecture

Vector similarity misses temporal queries ("what happened most recently") and entity-anchored lookups (exact name/identifier matches) — the same structural gap dense-only retrieval has in RAG generally. Production systems now fuse semantic similarity with keyword/BM25 matching and entity matching, with documented gains concentrated specifically on temporal queries (+29.6 points) and multi-hop reasoning (+23.1 points) in at least one reported benchmark — exactly the query types pure similarity search structurally can't serve well.

System design

Design the memory architecture for a personal assistant agent that should get noticeably better at helping a specific user over months of use.design

Working memory for the active conversation (thread state). Episodic memory logging each session with importance scoring (recency, frequency, outcome signals) so only meaningfully important sessions get promoted to long-term storage rather than everything indiscriminately. A consolidation step that periodically distills patterns across episodes into semantic memory — preferences, recurring needs. Procedural memory, even if lightweight, capturing which response strategies have worked well for this user specifically — versioned prompt adjustments driven by observed outcomes, since fully automated procedural learning tooling remains immature. Multi-signal retrieval (semantic + entity + temporal) at query time, since a personal assistant will field both "what do I usually order" (semantic) and "what did we decide last Tuesday" (temporal/episodic) query types.

A user reports your agent gave them outdated information it should have already learned was wrong. How do you diagnose this?design

Two distinct possible failures to separate: either the stale fact is still present in semantic memory because conflict resolution/supersede detection didn't fire when the correction was learned (a storage-layer bug), or the correct fact was retrieved and injected into context but the model didn't honor it during generation (a behavioral-layer failure many current memory systems simply assume away). Check the memory store directly first — if the current fact is there and correct, the bug is downstream in how the model uses retrieved memory, not in the memory system itself, and needs a different fix (e.g., stronger prompt-level emphasis on retrieved memory, or a verification pass).

Your enterprise agent's answers are inconsistent depending on which internal system it queries data from, even though its personal memory is accurate. What's the likely gap?design

An organizational/context memory gap — entity identity isn't resolved across the systems the agent touches, so the same real-world entity (a customer, a product) looks like a different entity depending on the source system's naming/ID conventions. The fix is an ontology or entity-resolution layer mapping identities across systems, not an upgrade to episodic or semantic memory — this is a distinct memory type from the standard CoALA four, and Snowflake's internal research found it produced a 20% accuracy improvement and 39% reduction in redundant tool calls once added.

How would you decide between building on Mem0 versus rolling your own memory pipeline?design

Default to a managed system (Mem0, Zep) unless you have a specific, demonstrated need the managed options don't meet — the five-stage pipeline (extraction, integration, storage, retrieval, forgetting) is genuinely hard to get right, and reinventing memory conflict resolution and staleness management from scratch is rarely where a team's differentiation should live. Roll your own primarily when you need tight control over data residency/compliance that hosted options can't meet, or when your access patterns are unusual enough (e.g., extremely high write volume, highly specialized entity types) that general-purpose tooling underperforms — validate that with your own benchmark before committing, exactly as Topic 5 argues for any infrastructure decision.
