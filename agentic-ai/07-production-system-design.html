00

Why This Is a Different Systems-Design Problem

Three properties of agents break assumptions that traditional backend system design takes for granted.

Agents are probabilistic — the same prompt can produce different responses across calls, so a retry might not produce an equivalent result, making idempotency more complex than a simple cache lookup. Agents are compositional — a single user request might trigger a planning phase, multiple tool calls, memory retrieval, and a synthesis step, and each component can fail independently with failure modes that compound. Agents are stateful — the context window accumulates information across the workflow, and losing that state mid-execution means losing the reasoning chain, the intermediate results, and the plan the agent was following.

The multiplicative failure math, spelled out

If you have five steps with 99% reliability each, your overall success rate drops to 95%. With ten steps, you're at 90%. Real-world agents often involve dozens of operations — at 20 steps and 99% per-step reliability, that's roughly 82%; a genuinely long-running research or coding agent with 50+ operations can fall well below 60% end-to-end success purely from compounding per-step failure, with zero additional bugs anywhere. This single piece of arithmetic is the entire justification for everything in this document.

The Cost Stack: Cache → Route → Compress

The three-pillar framework production teams actually converge on, in the order you should implement them.

The most effective 2026 LLM cost strategies share a common structure regardless of provider, model family, or use case, organized around three pillars: Cache, Route, and Compress. The combination of prompt caching, semantic caching, and model routing delivers 47–80% cost reduction with relatively low implementation effort, and it is where every production optimization programme should start.

02

Prompt / Prefix Caching

The single highest-leverage, lowest-risk lever available — and the first thing to implement, full stop.

Prompt caching reuses the computed key-value tensors behind a repeated prompt prefix, so the static portion of every request — tool definitions, system prompt, and stable context — bills at up to 90% off with no change to model output. Anthropic's prompt caching reduces costs by up to 90% and latency by up to 85% for long prompts; OpenAI achieves 50% cost reduction with automatic caching enabled by default.

Provider parameterValue
Cache write cost25% premium over base input price (Anthropic)
Cache read cost90% discount — 10% of base price (Anthropic)
Break-even point2+ cache hits per cached prefix
Minimum cacheable unit1,024 tokens per cache checkpoint, up to 4 checkpoints per request
Cache lifetime5 minutes from last access, extendable to 1 hour with regular hits
Documented production outcomes — cite these directly

A customer support application with a 4,000-token system prompt and 6,000-token RAG context achieved a 76% total API cost reduction at a 95% cache hit rate, from $10,000/month to $2,361/month. ProjectDiscovery raised their cache hit rate from 7% to 84%, cutting total LLM spend by 59-70% with a single architectural change.

The ordering rule that makes or breaks your hit rate

Cache hit rate is almost entirely a function of prompt structure: static content (system prompt, tool schemas, few-shot examples) must come first, in identical order, every single call — any variation in the prefix (even reordering unrelated fields) invalidates the cache. Naive caching can paradoxically increase latency if cache blocks are positioned poorly — test your caching strategy carefully. Put the volatile part (the actual user query, current turn) last, always.

Interview framing

"How would you cut costs on an agent whose system prompt and tool definitions are 5,000 tokens, called on every turn?" — Prompt caching first: structure every request with the static system prompt and tool schemas as an identical, unchanging prefix, and put the dynamic user turn last. At Anthropic's pricing this turns a 5,000-token static prefix from full price into ~10% price on every call after the first, with breakeven at just 2 hits — for a chat agent with any real conversation length, that's an immediate, close to risk-free win before touching anything else.

03

Semantic Caching (and Its Trap)

Goes further than prefix caching — and is exactly where naive implementations quietly start returning wrong answers.

Semantic caching returns a stored response for any query semantically similar to a previously answered one, skipping the model entirely. Production deployments hit 20-45% of traffic without touching the model — not the 95% vendor materials sometimes suggest, but still material cost reduction for high-volume workloads, since 31% of LLM queries in production exhibit semantic similarity sufficient to return a cached response.

semantic_cache_flow.txt
Query: "What's the refund policy?"
  -> Embed query
  -> Search cache for similar embeddings
  -> If similarity > threshold: return cached response
  -> Else: generate new response, store in cache
The CVA desk incident — why similarity thresholds are a data-quality control, not just a cost lever

A financial risk platform's semantic cache returned hits with similarity scores of 0.87 on queries that sounded similar but were contextually dangerous — a credit-desk analyst's question was answered from a cached response meant for a different, semantically-adjacent-but-substantively-different query. In domains where a wrong-but-plausible-sounding cached answer is worse than a slow correct one (finance, legal, medical, safety-critical support), semantic caching without domain-aware thresholds, metadata scoping (e.g. an as_of_date or desk/tenant field), and event-driven invalidation on underlying data changes is a liability, not an optimization.

Mitigation

Scope the cache by tenant/domain/context, not just embedding similarity alone; set the similarity threshold per risk tier (looser for FAQ-style consumer chat, much tighter or disabled entirely for anything with compliance exposure); and invalidate on underlying data changes rather than relying purely on TTL expiry.

04

Model Routing & Cascades

A 2026 application doesn't talk to one model — it talks to a menu of them.

A 2026 application talks to a menu of models spanning frontier, mid-tier, cheap, and self-hosted. Routing is the policy that picks one per request, navigating three goals that pull against each other: cost, latency, and quality. In 2026 a flagship model can cost 30x+ more per token than a small model, so capability mismatch is the biggest single source of waste.

StrategyHow it works
Static rulesHand-written rules route by request type (e.g. classification → cheap model, open-ended reasoning → frontier model)
Learned routerA trained classifier maps queries to a small or large model, jointly optimizing cost and quality — e.g. RouteLLM's matrix-factorization or causal-LLM-classifier routers trained on preference data
Cascade / escalationOperates sequentially — escalate to a larger model only when the initial (cheap) response is insufficient, judged via confidence, semantic agreement across a small-model ensemble, or a difficulty estimate
The semantic-agreement cascade trick

An ensemble of small models generates responses to a query; semantic similarity metrics assess agreement among the outputs. High agreement indicates reliability — return the highest-scoring ensemble response. Low agreement signals uncertainty — defer to the larger target model, ensuring the expensive model is called only when necessary. This avoids needing a trained difficulty classifier at all — disagreement among cheap models is itself the escalation signal.

The hidden cost of cascading — say this unprompted in an interview

A cascade also adds the cheap model's latency to every escalated request — you pay the cheap call's time, then the frontier call's time. For interactive, latency-sensitive paths that double hop can be the wrong tradeoff; cascades shine on asynchronous or latency-tolerant workloads, not on a live chat turn where the user is watching a spinner.

Interview framing

"Design a routing strategy for a support agent handling both simple FAQ lookups and complex multi-step troubleshooting." — Static rule as the first pass (classification-style queries with a clear intent match go to a cheap/small model), cascade for the ambiguous middle (try cheap first, escalate to frontier on low confidence or ensemble disagreement), and route straight to frontier for anything already flagged high-stakes (e.g. billing disputes, safety-relevant issues) — skip the cascade there since the added latency of a failed cheap attempt isn't worth it when you already know escalation is near-certain.

05

Batching

The lever most teams forget because it only applies to a slice of their workload — but it's a clean 50% for that slice.

Request batching trades individual latency for throughput; OpenAI's Batch API gives 50% savings for async work. Any workload that doesn't need a real-time response — nightly report generation, bulk document classification, offline eval runs — should default to a batch endpoint rather than the synchronous API, purely for the cost difference, with zero quality tradeoff.

Latency Budgets & Streaming

Cost optimization and latency optimization sometimes pull in the same direction (caching helps both) and sometimes fight each other (cascades help cost, hurt latency).

MetricWhat it measuresWhy it matters separately from total latency
TTFT (time to first token)Delay before the user sees anythingDominates perceived responsiveness — streaming makes a 10s total response feel instant if TTFT is 300ms
Total completion latencyFull response timeMatters for synchronous, non-streamed integrations and for total workflow duration in multi-step agents
Per-step latency in a trajectoryTime for each individual tool call / LLM callThe compounding factor in a long agent run — 20 steps at 2s each is 40s even before any retries

Streaming (both graph-level events and token-level via astream_events, covered in the LangGraph bible) is the standard mitigation for perceived latency in interactive agents — show progress ("searching…", "reading document…") rather than a blank wait, especially critical once you're chaining several tool calls per turn.

07 ★

Durable Execution — the Reliability Core

The single most important reliability concept for anything beyond a toy agent. This is the answer to the 90%-at-10-steps problem from Section 00.

Durable execution is the property that an agent workflow — a sequence of LLM calls, tool invocations, and human-in-the-loop pauses — survives a process crash, a redeploy, or an indefinite wait. If the enrichment API rate-limits on the 15th of 20 contacts a lead-scouting agent is processing, the workflow pauses, waits according to the backoff schedule, and retries — the first 14 enrichments don't re-run because their results are already persisted. The durable execution engine ensures each step executes exactly once, even if the workflow function itself runs multiple times.

The orchestrator never directly calls the LLM. Instead, it calls the durability layer, which records the intent, calls the LLM, records the result, and returns the response. If the process crashes between recording the intent and receiving the result, the next recovery discovers the pending call and retries it, with an idempotency key to avoid duplicates.

The economics, so you can cite a real number

Durable execution carries roughly 5–20% overhead at a 100k-runs/day reference workload — a real but modest tax relative to the failure rate it eliminates, and it's this overhead-vs-reliability trade that any "do we need Temporal" conversation should be framed around, not gut feeling.

What durable execution does NOT fix — say this to sound senior

Durable execution guarantees a workflow resumes correctly after infrastructure failure. It does not fix hallucinations, runaway reasoning loops, eval drift, or store-level disaster recovery — those are separate concerns (covered in Topics 5 and 6) that durable execution has no opinion on. Conflating "my agent is reliable" with "my agent is durable" is a common and costly mistake.

08

Temporal & the Replay-Safety Contract

The dominant durable-execution engine for agent workflows, and the specific rules its programming model imposes on your code.

Our non-deterministic, potentially fallible LLM call becomes a Temporal Activity. Temporal's retry policies automatically handle transient failures. If the worker running the workflow crashes after processing 5,000 of 10,000 documents, a new worker picks up, is given the state (the first 5,000 results), and seamlessly resumes execution from document 5,001.

The replay-safety contract

Temporal records non-deterministic side effects into workflow history so replay can reuse the recorded result instead of re-running the non-deterministic operation. Agent workflows are packed with non-determinism — LLM outputs, timestamps, randomness, retrieval results, network responses, policy decisions, tool results. You cannot replay an LLM call and pretend it is the same event; the output must be recorded the first time and reused during recovery. Same for tool responses, policy decisions, and side effects.

RuleWhy
No Date.now() / wall-clock calls in workflow codeReplay must reproduce identical decisions — non-deterministic timestamps break that guarantee unless routed through the framework's deterministic time API
Deterministic branching only in workflow codeAny branch decision based on non-deterministic input (a raw LLM call, a random number) must happen inside an Activity, whose recorded result the workflow then branches on deterministically
Workflow versioningChanging workflow code while in-flight executions exist requires explicit version gating, or replay of old history against new code silently diverges
Idempotency keys derived from (workflow_id, step_id)Guarantees a retried non-idempotent tool call (e.g., "charge card") executes exactly once even across process crashes

Best practices from production Temporal+LLM deployments

  • Idempotency is non-negotiable — if your activity is "create user account," ensure running it twice doesn't create two accounts; design external systems to be idempotent.
  • Configure timeouts intelligently — an LLM call might take 2 minutes; a 1-minute start-to-close timeout causes unnecessary failures and retries. Match timeouts to the actual task, and set retry policies to avoid excessive cost on expensive activities.
  • For workflows running longer than a few seconds, invoke asynchronously — start the workflow, get a handle, and query it for status or receive completion via webhook/message queue later, rather than blocking a request thread.

Alternatives at different weight classes

ToolFit
Temporal / AWS Step Functions / Restate / DBOS / Inngest / Cloudflare WorkflowsFull durable-execution platforms — general-purpose, provide durability and retries but don't gate external-effect settlement on per-resource progress by default.
LangGraph checkpointer (PostgresSaver, RedisSaver)Lightweight alternative when you're already on LangGraph and don't need cross-language workflow orchestration — covered in depth in the LangGraph bible's persistence chapter
Interview framing

"When do you reach for Temporal instead of a LangGraph checkpointer?" — LangGraph's checkpointer gives you resumability within LangGraph's own execution model, which is enough for most single-service agents. Temporal (or an equivalent durable-execution engine) earns its complexity when you need cross-service orchestration spanning multiple languages/frameworks, workflows genuinely running for hours or days, or the stricter replay-safety and exactly-once guarantees Temporal's activity model provides — the honest rule of thumb is if you're spending more than ~20% of engineering time on hand-rolled reliability plumbing (retries, dedup, state tracking), it's time.

Retries, Idempotency & Circuit Breakers

The three defenses against transient failure, and where each one applies specifically to agent workloads.

PatternAgent-specific nuance
Retry with exponential backoffStandard for rate-limited LLM API calls — but remember an LLM retry can return a different response, so retrying a non-idempotent downstream action based on that response needs its own dedup, not just retrying the LLM call
Idempotency keysDerived from a stable identifier (workflow_id + step_id, not a timestamp) so a retried "send email" or "charge card" tool call executes exactly once even if the orchestrating call itself gets retried
Circuit breakersTrip on a downstream tool/API repeatedly failing, so the agent stops hammering a dead dependency and instead fails fast or falls back — critical when a tool failure would otherwise cause the agent to loop retrying it indefinitely
Timeout matchingSet per-activity timeouts to match the actual expected duration of that specific call — a fast tool call and a 2-minute LLM generation should not share the same timeout budget.
The retry-the-whole-thing anti-pattern

The most common naive failure-handling approach — wrapping an entire multi-step agent run in a top-level try/except and retrying the whole thing on any failure — re-executes every already-successful step, multiplying cost and risking duplicate side effects on any non-idempotent action along the way. Scope retries to the smallest failed unit, exactly as durable execution's per-step persistence is designed to enable.

Observability: OTel GenAI & OpenInference

A 47-internal-step agent trace that shows up as two spans in a generic APM tool is a production incident waiting to happen. This section is how you fix that.

The two-span trace, illustrated

A platform engineer shipped a customer-onboarding agent: LangChain plus four tools plus retrieval plus an OpenAI fallback. The trace pane showed exactly two spans per request — one HTTP span into the agent endpoint, one HTTP span out to OpenAI. Forty-seven internal steps lived inside those two spans, invisible. By Friday the agent had three incidents: a hallucinated routing number that nearly triggered a wire transfer, a tool call that retried itself in a loop for ninety seconds, and a token spike from a retrieval prompt that ran 14 times in one conversation. None were visible in the trace tool, because the trace tool didn't know about LLMs.

OpenTelemetry instruments LLM applications by wrapping API calls in spans with standardized gen_ai.* attributes — model name, token counts, finish reason. For agents, each tool call, LLM invocation, and retrieval step becomes a child span, producing a full trace of the reasoning chain. Auto-instrumentation packages exist for OpenAI, Anthropic, LangChain, and LlamaIndex.

StandardGovernanceNotes
OpenTelemetry GenAI Semantic ConventionsOpenTelemetry projectThe OTel GenAI SIG is actively developing conventions for multi-agent systems specifically — tasks, actions, agent teams, memory, artifact tracking.
OpenInferenceApache 2.0, originally from Arize, now adopted across the ecosystemMost 2026 stacks emit OpenInference instrumentation and export via OTLP.

Traditional APM assumes the same input reliably produces the same output; LLM systems break this assumption in several ways: non-determinism (you can't reproduce an issue without capturing the exact input, model parameters, and temperature at call time), a token-based cost model (latency and cost correlate with token counts, not request count), and prompt sensitivity (prompts often contain PII or confidential data, so sending them to observability backends without sanitization creates compliance risk).

What to actually capture, span by span

Every prompt, completion, tool call, retrieval, and agent step as a structured span, with token counts, dollar cost, latency, and evaluation scores attached as first-class span attributes, exported via OTLP to a backend supporting span-tree visualization, per-tenant cost attribution, drift detection on quality, and correlation between offline evaluation runs and production traces via span_id. Note the direct link back to Topic 5 — production trace evaluation depends entirely on this instrumentation existing in the first place.

Interview framing

"Your agent has an intermittent latency spike in production and generic APM shows nothing unusual. What's missing?" — Almost certainly span-level LLM/tool instrumentation. Generic APM sees the outer HTTP request and outer LLM API call; it has no visibility into the internal reasoning loop — retries, redundant retrieval calls, or a tool stuck in a retry loop are invisible unless every internal step is its own span with gen_ai.* attributes. This is the two-span trace failure mode, and the fix is OTel GenAI or OpenInference instrumentation wired through the entire agent, not just at the request boundary.

Context Window Management at Scale

Ties directly to the multi-agent "context saturation" problem from Topic 3 — here's the production mitigation toolkit.

TechniqueWhen to use it
Sliding windowDrop oldest turns once history exceeds a token budget — simple, loses old context entirely
Summarization / compactionPeriodically collapse older turns into a condensed summary, preserving gist at the cost of detail — the standard approach for long-running conversational agents
External memory + retrievalPersist full history outside the context window (a store), retrieve only what's relevant to the current turn — scales furthest, adds retrieval-quality dependency
Subgraph isolation (multi-agent)As covered in Topic 3 — give each sub-agent its own scoped context rather than accumulating everything in one shared state
The trap: compaction interacting badly with prompt caching

Summarizing or compacting history changes the prompt's content, which invalidates any cached prefix built on the old, longer history — a naive "compact every N turns" policy can silently tank your cache hit rate exactly when the conversation gets long enough to need caching most. Coordinate compaction points with cache-checkpoint boundaries rather than triggering them independently.

Rate Limiting & Capacity Planning

Provider rate limits are a real, load-bearing constraint on agent system design, not an afterthought.

  • Token-per-minute and request-per-minute limits are provider- and tier-specific and often the actual bottleneck on agent throughput, not compute or your own infrastructure.
  • Backpressure — queue incoming agent requests rather than firing them all at the provider simultaneously; a durable-execution layer's built-in retry/backoff (see Temporal section) is a natural place to absorb rate-limit backpressure gracefully instead of erroring out.
  • Multi-provider fallback — routing to a secondary provider/model when the primary is rate-limited or down trades consistency for availability; decide deliberately whether that trade is acceptable for your use case (a coding agent probably can tolerate a model swap mid-task worse than a simple classification agent can).
  • Capacity planning for agentic workloads is fundamentally token-based, not request-based — a single agent "request" can burn 10-50x the tokens of a simple chat turn due to tool-call round trips, so provision and forecast against token throughput, not request counts.

Deployment Patterns

Canary and blue-green deployment apply to agents too — with one extra dimension traditional software doesn't have.

Beyond standard canary/blue-green code deployment, agent systems need a prompt and model version rollout strategy — a system prompt change or model version bump is a behavioral change exactly like a code change, and should go through the same staged rollout: canary a small percentage of traffic on the new prompt/model, compare quality and cost metrics (tying back to Topic 5's eval infrastructure) against the baseline, then progressively increase traffic.

Ties directly to Topic 5's closed loop

Integrate evaluation into CI/CD with progressive canary deployment patterns — this is the exact mechanism: a prompt/model change is gated by the offline eval suite pre-merge, then canaried against a live traffic sample with the same eval rubric before full rollout, with automatic rollback if quality or cost metrics regress past a threshold.

Anti-Patterns

What actually breaks in production, ranked roughly by how often teams hit it.

  • No prompt caching structure. Putting the dynamic user query before the static system prompt/tools in the request destroys cache hit rate for zero benefit.
  • Semantic caching without domain-aware thresholds. The CVA-desk-style failure — a plausible-sounding wrong cached answer is worse than a slow correct one in any compliance-sensitive domain.
  • Retry-the-whole-thing error handling. Re-executes every already-successful step on any failure, multiplying cost and risking duplicate non-idempotent side effects.
  • Cascading in a latency-sensitive interactive path. Adds the cheap model's full latency on top of the frontier model's latency for every escalated request — fine for async work, often wrong for live chat.
  • Two-span traces. Generic APM with no LLM-aware instrumentation makes internal agent failures (retry loops, redundant retrieval, token spikes) completely invisible until a user or an invoice notices.
  • Confusing durable execution with correctness. A workflow can resume perfectly after a crash and still hallucinate, loop pointlessly, or drift on quality — durability and reliability-of-output are separate axes.
  • Compaction that ignores cache boundaries. Silently destroys prompt-cache hit rate right when a long conversation needs it most.
  • Provisioning against request count instead of token throughput. Agent workloads burn wildly variable token counts per request due to tool round-trips; request-count-based capacity planning under-provisions for token-heavy workflows.

Interview Cheat-Sheet

Grouped by depth.

Core concepts

Why does a 20-step agent fail so much more often than a single API call, even if every step is individually reliable?core

Failure compounds multiplicatively across independent steps. At 99% per-step reliability, 5 steps yields ~95% end-to-end success, 10 steps yields ~90%, and 20 steps drops to roughly 82% — with zero additional bugs anywhere, purely from the arithmetic of chained probability. This is the core justification for durable execution: it's not about making any single step more reliable, it's about ensuring a failure in one step doesn't force re-running all the others.

Explain the difference between durable execution and reliability/accuracy.core

Durable execution guarantees a workflow's progress survives infrastructure failure — a crash, a redeploy, a long wait — resuming from the last completed step rather than losing all prior work. It says nothing about whether the agent's actual outputs are correct; a perfectly durable workflow can still hallucinate, loop unproductively, or drift on quality. Those are evaluation and prompt-engineering concerns (Topic 5), a separate axis entirely.

What is the replay-safety contract in a Temporal-style durable execution engine?core

Workflow code must be deterministic so that replaying its history reproduces identical decisions — meaning no wall-clock calls, no raw randomness, and no branching directly on a non-deterministic result (an LLM call, a random number) inside workflow code itself. Non-deterministic operations happen inside Activities, whose results get recorded on first execution and reused during replay, so recovery never re-runs (and potentially gets a different result from) an LLM call or tool invocation that already succeeded.

Cost optimization

Walk through the Cache → Route → Compress framework and roughly what each buys you.cost

Cache: prompt/prefix caching for repeated static content (50-90% cost reduction, near-zero implementation effort) plus semantic caching for repeated-meaning queries (20-45% of traffic served without touching the model). Route: send each query to the cheapest model capable of handling it well, via static rules or a cascade with escalation (40-70% savings, since a flagship model can cost 30x+ more per token than a small one). Compress: batching for async work (50% via provider Batch APIs) and context management to avoid paying for redundant or bloated history. Combined, these routinely deliver 70-90% total cost reduction, and should be implemented roughly in that order since caching is the highest-leverage, lowest-risk lever.

Why can naive prompt caching sometimes make latency worse instead of better?cost

If cache blocks are positioned poorly — e.g. splitting the cacheable content awkwardly or invalidating the cache on nearly every call due to volatile content appearing early in the prompt — you pay the cache-write overhead (a 25% premium on Anthropic) without ever reaching the break-even of 2+ hits, and may add processing overhead for a cache that rarely actually hits. The fix is structuring the prompt with all static content first, in identical order every call, and the dynamic content last.

When is a model cascade the wrong choice even though it clearly saves money?cost

In latency-sensitive interactive paths — a cascade adds the cheap model's full latency on top of the frontier model's latency for every request that ends up escalating, a double-hop cost that can make total response time worse than just calling the frontier model directly. Cascades are the right choice for asynchronous or latency-tolerant workloads where the escalation rate is low enough that the average latency gain from cheap-model hits outweighs the double-hop cost on the escalated minority.

Your semantic cache is saving 40% on API costs but a compliance team just flagged a wrong answer that came from a cache hit. What do you check?cost

The similarity threshold and whether the cache is scoped by domain/tenant/context or purely by embedding distance. A generic semantic cache with a loose threshold will conflate semantically-similar-but-substantively-different queries (the CVA desk failure pattern) — the fix is domain-aware thresholds set per risk tier, explicit scoping metadata (jurisdiction, desk, as-of-date), and event-driven invalidation tied to underlying data changes, tightened or disabled entirely for compliance-sensitive query classes even at the cost of some savings.

System design

Design the reliability architecture for an agent that processes a 10,000-document batch job over several hours.design

Durable execution is non-negotiable at this scale — wrap the per-document processing as individually retryable, idempotent activities under a durable-execution engine (Temporal or equivalent), so a worker crash after document 5,000 resumes from 5,001 rather than restarting. Match per-activity timeouts to actual expected duration (an LLM call needs a multi-minute budget, not a generic 30s default). Invoke the overall job asynchronously with a status-queryable handle rather than blocking a request thread. Instrument every step with OTel GenAI spans so a stuck or looping document is visible in trace data, not discovered via a token-spend anomaly days later.

Design cost controls for an agent whose usage just 10x'd unexpectedly.design

First, verify instrumentation exists to even diagnose it — per-span token/cost attribution via OTel GenAI, so you can see whether the spike is more requests, more tokens per request (e.g. a retrieval prompt looping, per the two-span-trace incident), or a routing regression sending traffic to a more expensive model than intended. Then apply the cost stack: confirm prompt caching is structured correctly (a broken cache silently reverting to full-price calls is a common silent regression), check whether a cascade's escalation rate has drifted upward, and add cost anomaly alerting so the next 10x spike triggers a page rather than a surprise invoice.

How would you decide whether a given agent needs a full durable-execution engine like Temporal, versus a lighter option?design

Ask whether workflows genuinely run long enough or span enough independent services/languages that hand-rolled retry/state-tracking logic becomes its own maintenance burden — the rule of thumb is if more than roughly 20% of engineering time goes into reliability plumbing (retries, dedup, state tracking, failure recovery), a dedicated engine pays for itself. For a single-service agent built entirely on LangGraph with workflows measured in seconds-to-minutes, the built-in checkpointer is usually sufficient; for cross-service orchestration or hours-to-days workflows, escalate to Temporal or an equivalent.

An agent's tool call to charge a customer's card is retried after a network timeout, and the customer is charged twice. What went wrong and how do you fix it?design

The retry logic treated the charge-card call as safely retryable without an idempotency key — the original request may have actually succeeded server-side even though the response was lost to the timeout, and a naive retry re-executes the charge rather than discovering the original succeeded. Fix: every non-idempotent tool action needs an idempotency key derived from a stable identifier (not a timestamp), passed through to the downstream API so it can recognize and deduplicate a retried request server-side — exactly the discipline Temporal's activity model enforces by design.

Prompt / prefix caching
Reusing computed KV tensors for a repeated prompt prefix, billed at a steep discount on cache hits.
Semantic caching
Returning a stored response for a semantically similar (not identical) query, skipping the model entirely.
Model routing
Policy selecting which model handles a given request, balancing cost, latency, and quality.
Model cascade
Sequential routing strategy: try a cheap model first, escalate to a larger one only when needed.
Durable execution
Property that a multi-step workflow survives process crashes, redeploys, and long waits without losing progress.
Replay-safety contract
The determinism rules durable-execution engines impose on workflow code so history replay reproduces identical decisions.
Activity (Temporal)
A unit of potentially non-deterministic, retryable work (an LLM call, a tool call) whose result is recorded for replay.
Idempotency key
A stable identifier ensuring a retried non-idempotent action executes exactly once.
Circuit breaker
Pattern that stops calling a repeatedly-failing dependency, failing fast instead of retrying indefinitely.
TTFT (time to first token)
Latency before the first output token appears, dominating perceived responsiveness in streamed responses.
OTel GenAI Semantic Conventions
OpenTelemetry's standardized gen_ai.* span attributes for LLM/agent instrumentation.
OpenInference
Apache-2.0 tracing specification for LLM applications, originally from Arize.
Context compaction
Summarizing or condensing older conversation history to stay within a token budget.
Backpressure
Queuing/throttling incoming requests to stay within downstream capacity or rate limits rather than failing outright.

How to actually get interview-ready on this topic

Take an agent you've built, add OTel/OpenInference span instrumentation, and look at the actual trace tree — you will almost certainly find at least one redundant call, one poorly-scoped timeout, or one cache-invalidating prompt structure you didn't know about. Fixing one real inefficiency you found yourself is worth more in an interview than reciting these benchmark numbers secondhand.
