The Landscape, Recapped

Topic 8 built each of these individually. This document is about choosing between them under a real, specific scenario — the skill, not the technique list.

Quick refresher of what Topic 8 covered in depth: naive single-pass dense retrieval, hybrid search (BM25 + dense + RRF), cross-encoder reranking, contextual retrieval and late chunking, HyDE and multi-query, Self-RAG and CRAG, GraphRAG, and RAPTOR. This document adds one more architecture (KAG) and, more importantly, builds the actual decision-making skill for choosing between all of them — which is a different, harder skill than knowing what each one does.

Why this document exists as its own topic

Almost every candidate who's studied RAG can define GraphRAG. Far fewer can explain when it's the wrong choice, or defend a decision not to use it under interviewer pushback. That specific skill — architecture selection under scrutiny, not architecture recall — is what senior RAG interviews actually probe, and it's the entire subject of this document.

01 ★

GraphRAG Often Loses to Vanilla RAG — Say This Directly

The single most valuable, least-known fact to bring into a RAG architecture interview. Most candidates assume "more structure = better" and never question it.

Despite its conceptual promise, recent studies report that GraphRAG frequently underperforms vanilla RAG on many real-world tasks — a finding significant enough that a dedicated 2026 benchmark, GraphRAG-Bench, was built specifically to answer "is GraphRAG really effective, and in which scenarios do graph structures provide measurable benefits?"

Why this happens, mechanically

Graph construction itself introduces a real failure mode: many GraphRAG pipelines build their knowledge graph using OpenIE (Open Information Extraction) — an automated process for pulling entities and relationships out of raw text — which is inherently noisy. Ambiguous entity resolution, spurious relationship extraction, and inconsistent granularity in the extracted triples all directly degrade retrieval quality, and that noise compounds through every downstream graph traversal. A flat vector index has no equivalent construction-time noise source — this is a structural, not incidental, disadvantage of naive graph-based RAG.

Interview framing — the single highest-value line in this document

"Would you recommend GraphRAG for this system?" — Don't answer with GraphRAG's theoretical benefits by default. Answer: "GraphRAG frequently underperforms vanilla RAG in practice — recent benchmarking (GraphRAG-Bench, 2026) found its advantage is concentrated in specific task types, not universal. I'd want to know the task distribution first." Then walk into Section 02's taxonomy. This single response — leading with the caveat instead of the pitch — is a strong, memorable signal of real, current knowledge rather than recall of a popular technique's marketing.

The actual takeaway to internalize

Graph structure's value is not a fixed property of GraphRAG as a technique — it's a function of task type. The correct question is never "is GraphRAG good," it's "what fraction of my query distribution is Level 2-3, versus Level 1 fact lookups a flat index already handles well." This reframing — from technique quality to task-distribution fit — is exactly the diagnostic instinct Topic 5's evaluation discipline trained you to apply everywhere else, now applied specifically to architecture choice.

03 ★

KAG (Knowledge-Augmented Generation), Fully Explained

Ant Group's logical-form-guided RAG framework — built specifically as a response to GraphRAG's noise problem, and the architecture most candidates have simply never encountered.

KAG (arXiv:2409.13731, ACM Web Conference 2025) is a knowledge-enhanced generation framework built on Ant Group's open-source OpenSPG knowledge graph engine. Its explicit design goal: attack the noise problem that OpenIE-based approaches like GraphRAG and HippoRAG introduce, by using a schema-constrained knowledge graph with semantic alignment instead of unconstrained automated extraction.

The three-part architecture

ComponentJob
KAG-BuilderConstructs the knowledge graph — critically, against a defined schema rather than pure unconstrained OpenIE, directly reducing the entity-ambiguity and spurious-relationship noise that degrades naive GraphRAG.
KAG-SolverThe reasoning engine — translates a natural-language question into a logical form over the schema-constrained graph, and orchestrates a hybrid reasoning process combining retrieval, KG reasoning, language reasoning, and numerical calculation as distinct operator types.
KAG-ModelOptimizations improving the efficiency of both knowledge-graph construction and the question-answering process itself.

Two mechanisms worth naming precisely

  • Mutual indexing — knowledge graph nodes and their originating source text chunks are cross-indexed, so the system can move fluidly between structured graph facts and the full original context those facts were extracted from, rather than losing that connection once extraction happens (a real information-loss problem in many GraphRAG implementations).
  • Logical-form-guided reasoning — rather than a single embedding-similarity retrieval pass, KAG translates the question itself into a structured logical form, then executes reasoning against the graph using that form — enabling genuine multi-step logical inference (connecting facts A→B→C to answer a question none of them individually answers) rather than just retrieving topically-related passages.

The honest cost of KAG's precision

KAG's schema-constrained graph construction is precisely what fixes GraphRAG's noise problem — and it's also KAG's biggest adoption cost. Unlike GraphRAG's largely automated, unconstrained extraction, KAG needs an explicit domain schema defined up front, which is real modeling effort a general-purpose OpenIE pipeline doesn't require. This is exactly why KAG targets professional, high-stakes domains (Ant Group's own production use is e-government and e-health) rather than general open-domain question answering — the schema investment pays off specifically where rigorous, auditable fact-grounding matters enough to justify it.

Interview framing

"When would you pick KAG over GraphRAG?" — When the domain is professional/high-stakes enough to justify defining an explicit schema up front (e-government, healthcare, financial compliance, legal), and the query distribution genuinely needs rigorous multi-hop logical inference rather than thematic summarization. When the domain is more general-purpose, the corpus is large and heterogeneous, and standing up a rigorous schema isn't worth the effort relative to the task's stakes, GraphRAG's lighter-weight automated construction is the more practical choice — accepting its noise tradeoff as the cost of faster setup.

Cost and architectural sophistication increase roughly top-to-bottom in this table — and accuracy does not increase monotonically alongside them. Matching the row to your actual task distribution, not defaulting to the most sophisticated-sounding row, is the entire skill this document is teaching.

06

Architecture-Selection Pitfalls

Distinct from Topic 8's implementation pitfalls — these are mistakes in choosing between architectures, not in building any one of them correctly.

  • Assuming "more sophisticated" means "more accurate." The core finding of this entire document — GraphRAG-Bench found GraphRAG frequently underperforms vanilla RAG specifically because task-architecture mismatch is common, not because graphs are bad.
  • Skipping the naive baseline entirely. Same discipline as Topic 3's multi-agent economics argument and Topic 1's pattern-selection framework — measure a simple hybrid-search-plus-rerank baseline before reaching for GraphRAG, KAG, or Agentic RAG, so any added complexity has to earn its keep against a real number.
  • Choosing GraphRAG without checking the actual query distribution. If most real queries are Level 1 fact retrieval, graph structure is mostly wasted cost — profile the query distribution (exactly Topic 5's evaluation discipline) before committing to an architecture.
  • Underestimating OpenIE noise in automated graph construction. A GraphRAG pipeline's accuracy ceiling is bounded by the quality of its automated entity/relationship extraction — this is a structural property, not a tuning problem you can fully engineer around without moving toward KAG's schema-constrained approach.
  • Choosing KAG for a domain that doesn't justify the schema investment. KAG's precision comes directly from upfront schema definition — applying it to a broad, heterogeneous, low-stakes corpus spends real modeling effort for a gain the task doesn't need.
  • Treating architecture choice as permanent. Query distributions and corpora both drift over time (the same lesson as Topic 5's closed-loop eval argument) — an architecture that was right at launch can become the wrong choice as usage patterns shift, and re-evaluating periodically is part of the job, not a one-time decision.

08

Interview Cheat-Sheet

Grouped by depth — this section is deliberately weighted toward defending a decision under pushback, since that's the actual skill this document teaches.

"Wouldn't GraphRAG obviously give better answers since it understands relationships?" How do you respond to this pushback?core

Not necessarily — GraphRAG-Bench, a 2026 benchmark built specifically to test this assumption, found GraphRAG frequently underperforms vanilla RAG on real-world tasks. The advantage is concentrated in specific task types (complex multi-hop reasoning and corpus-wide contextual summarization) and doesn't reliably hold for simpler fact-retrieval queries, which most production query distributions are dominated by. The right move is checking the actual task distribution against GraphRAG-Bench's four-level taxonomy before assuming the "understands relationships" pitch translates into measured accuracy gains.

Explain KAG's core mechanism and what specific problem it was built to solve.core

KAG was built specifically to fix the noise problem in OpenIE-based graph construction that affects GraphRAG and similar approaches — automated entity/relationship extraction from raw text is inherently noisy (ambiguous entities, spurious relationships). KAG uses a schema-constrained knowledge graph with semantic alignment instead, plus logical-form-guided reasoning: the question itself gets translated into a structured logical form, and a hybrid reasoning engine (retrieval, KG reasoning, language reasoning, numerical calculation as distinct operators) executes genuine multi-step inference against the graph, rather than relying on embedding-similarity retrieval alone.

What's the actual mechanism by which OpenIE-based graph construction hurts retrieval quality?core

OpenIE automatically extracts entities and relationships from raw text with no schema constraining what's valid — this produces ambiguous entity resolution (is "Apple" the company or the fruit in this context), spurious or overly generic relationship extraction, and inconsistent granularity across extracted triples. This noise doesn't stay contained — it compounds through every downstream graph traversal that touches a noisy node or edge, degrading retrieval quality in ways a flat vector index, which has no equivalent construction-time extraction step, doesn't suffer from.

Design the RAG architecture for a healthcare decision-support system requiring auditable, rigorous fact-grounding across multi-hop clinical reasoning.design

This is close to a textbook KAG use case — professional, regulated domain, genuine need for multi-hop logical inference, and auditability requirements that favor KAG's explicit logical-form reasoning over black-box embedding similarity. Justify the upfront schema-definition cost against the domain's stakes (this is exactly the kind of domain, like Ant Group's own e-health deployment, KAG was built for) rather than defaulting to GraphRAG's faster but noisier automated construction, given the accuracy and auditability requirements at hand.

Design the RAG architecture for an internal company wiki search tool, mostly single-topic articles, occasional cross-referencing.design

Start with hybrid search plus reranking as the baseline — most wiki queries are Level 1 fact retrieval, exactly where flat retrieval already performs well per GraphRAG-Bench's taxonomy, and graph construction overhead isn't justified by the task profile. Only escalate toward GraphRAG if evaluation specifically surfaces a meaningful fraction of Level 3 "summarize across many articles" queries in real usage — don't build graph infrastructure preemptively for a query type that may not actually be common in this corpus.

How would you communicate to a non-technical stakeholder why you're not using the "more advanced" GraphRAG for their project?design

Frame it around evidence, not opinion: recent research specifically built to test this question found GraphRAG often performs worse than simpler retrieval on typical queries, with its real advantage concentrated in a narrow set of complex, corpus-wide summarization questions. Offer to measure the actual query distribution against a simpler baseline first — if the numbers show a real gap on the tasks that matter to them, escalating to GraphRAG becomes an evidence-backed decision instead of a default; if not, the simpler system is genuinely the better choice, not a shortcut.

You've measured your query distribution and it's roughly 70% fact lookup, 30% complex multi-hop reasoning. What architecture do you recommend?design

A hybrid architecture rather than a single global choice: route via query classification (similar to Topic 8's Adaptive RAG pattern) — simple fact-lookup queries go through the cheap hybrid-search-plus-rerank pipeline, while queries classified as complex/multi-hop route to GraphRAG or an agentic RAG loop depending on whether the multi-hop structure is more thematic (favoring GraphRAG) or genuinely dependent on intermediate results (favoring an agentic approach). Paying the graph/agentic cost only on the 30% that needs it, rather than applying it universally, is both cheaper and avoids GraphRAG's demonstrated weakness on the 70% fact-lookup majority.

Glossary

Terms new to this document (see Topic 8 for the broader RAG glossary).

GraphRAG-Bench
2026 benchmark (ICLR'26) specifically testing when graph structures measurably help RAG, across a four-level task taxonomy.
Four-level task taxonomy
Fact retrieval, complex reasoning, contextual summarization, creative generation — GraphRAG-Bench's framework for where graph structure helps.
OpenIE
Open Information Extraction — automated, schema-free entity/relationship extraction; the noise source in naive GraphRAG construction.
KAG
Knowledge-Augmented Generation — Ant Group's schema-constrained, logical-form-guided RAG framework built on OpenSPG.
OpenSPG
The open-source knowledge graph engine KAG is built on.
KAG-Builder / Solver / Model
KAG's three components: schema-constrained graph construction, logical-form reasoning engine, and efficiency optimizations respectively.
Mutual indexing
KAG's cross-indexing between knowledge graph nodes and their originating source text chunks.
Logical-form-guided reasoning
Translating a natural-language question into a structured logical form before executing graph reasoning against it.
Hybrid reasoning engine (KAG)
Orchestration across four operator types: retrieval, KG reasoning, language reasoning, numerical calculation.
