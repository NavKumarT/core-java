Foundations

The 4 Pillars of OOP

Every OOP interview starts here. Know the definition, a real-world analogy, and exactly how Java implements each one. Critically — know how they relate: Encapsulation enables Abstraction; Inheritance enables Runtime Polymorphism.

🎭
Abstraction
Hide the how, expose the what

Definition: Show only essential features; hide internal complexity. Users interact with a simplified interface without needing to know the implementation.

Analogy: You press a car's brake pedal — you don't know about hydraulic lines, brake pads, or callipers. The car exposes brake() and hides everything underneath.

In Java: Achieved via abstract classes and interfaces. Method signatures define the contract; implementations are hidden in concrete classes.

Abstraction via interface 
interface PaymentGateway {
    void pay(double amount);  // WHAT — caller only needs this
}                               // HOW is hidden in each impl

class UPIGateway implements PaymentGateway {
    public void pay(double amt) {
        // connect to UPI server, validate VPA, debit — hidden
        System.out.println("Paid via UPI: " + amt);
    }
}

// Caller doesn't know it's UPI — just uses PaymentGateway
PaymentGateway gw = new UPIGateway();
gw.pay(500.0);
🔒
Encapsulation
Bundle data + behaviour; guard state with access modifiers

Definition: Wrap data (fields) and methods that operate on it inside a class. Use private to restrict direct access and expose controlled access via getters/setters.

Analogy: A medicine capsule — the drug is sealed inside; you can't touch it directly. You interact only through the defined interface (swallow it).

Key nuance: Constructors can also be private — used in Singleton and Factory patterns to control instantiation completely.

Encapsulation with validation guard 
class BankAccount {
    private double balance; // hidden — cannot be set directly

    public void deposit(double amount) {
        if (amount <= 0)
            throw new IllegalArgumentException("Invalid amount");
        balance += amount; // only valid ops modify state
    }
    public double getBalance() { return balance; }
}

// account.balance = -9999; ← compile error, field is private
// account.deposit(-100);   ← throws exception, logic is guarded
🧬
Inheritance
Acquire parent properties via IS-A relationship

Definition: A child class inherits all non-private fields and methods of a parent class. Supports code reuse and establishes an IS-A relationship. Every class implicitly extends Object.

Analogy: A SavingsAccount IS-A BankAccount. It inherits deposit/withdraw logic and adds interest calculation on top.

Java rules: Single class inheritance (extends one class only). Multiple inheritance via interfaces. Cannot inherit constructors — but they chain via super().

Inheritance + specialisation 
class Vehicle {
    int speed;
    void move() { System.out.println("Vehicle moves at " + speed); }
}

class Car extends Vehicle {  // Car IS-A Vehicle
    int doors;
    void honk() { System.out.println("Beep!"); }
    void move() {  // overrides parent
        System.out.println("Car drives at " + speed);
    }
}

Car c = new Car();
c.speed = 100;
c.move();  // Car drives at 100  (overridden)
c.honk();  // Beep!              (Car-specific)
🎨
Polymorphism
One interface, many forms — compile-time & runtime

Compile-time (static): Method overloading — same method name, different parameter lists. Resolved by the compiler based on argument types.

Runtime (dynamic): Method overriding — subclass replaces parent method. Which version runs is decided at runtime based on the actual object type, not the reference type.

Both types side by side 
// COMPILE-TIME: overloading — same name, different signatures
class Printer {
    void print(String s)  { System.out.println("String: " + s); }
    void print(int n)     { System.out.println("Int: "    + n); }
    void print(double d)  { System.out.println("Double: " + d); }
}

// RUNTIME: overriding — actual object determines which method runs
class Shape     { void draw() { System.out.println("Shape");     } }
class Circle    extends Shape { void draw() { System.out.println("Circle");  } }
class Triangle  extends Shape { void draw() { System.out.println("Triangle");} }

Shape[] shapes = { new Circle(), new Triangle(), new Circle() };
for (Shape s : shapes) s.draw(); // Circle, Triangle, Circle
💡 Interview: "How do the 4 pillars relate to each other?" Encapsulation protects data so Abstraction (hiding internals) is safe. Inheritance establishes IS-A relationships that Polymorphism operates on — without inheritance, runtime polymorphism through method overriding can't exist.
Inheritance Deep Dive

Inheritance in Java

The most nuanced OOP topic in interviews. Knowing the mechanics isn't enough — you need to know constructor chaining rules, super/this, exactly what can and can't be overridden, and how dynamic dispatch actually works at runtime.

Generalisation vs Specialisation

Generalisation (bottom-up)
  • Extract common behaviour from multiple classes into a parent
  • Dog and Cat both have eat() → pull up into Animal
  • Reduces duplication; creates a reusable base
Specialisation (top-down)
  • Start with a general class; extend with specific children
  • Animal → Dog, Cat, Bird each add unique behaviour
  • Child extends the parent's capability — never narrows it (LSP)

Constructor Chaining — what actually happens

When you create a child object, Java automatically calls every constructor in the hierarchy from the top ancestor down. This is constructor chaining — enforced by the compiler.

1
The first line of every constructor is an implicit super() call unless you explicitly write super(...) or this(...).
2
If the parent has no zero-arg constructor and the child doesn't explicitly call super(args), the code won't compile.
3
Execution order is always top-down: grandparent body → parent body → child body. Never the other way.
Constructor chaining
super() with params
this() — overload chaining
class A {

class B extends A {
    B() {
        // implicit super() — calls A() first
        System.out.println("B constructor");

class C extends B {
    C() {

class Vehicle {
    private String brand;
    Vehicle(String brand) {  // NO zero-arg constructor
        this.brand = brand;
        System.out.println("Vehicle: " + brand);
    }
}
class Car extends Vehicle {
    private int seats;
    Car(String brand, int seats) {

    }

new Car("Toyota", 5);

// Car: 5 seats

class Employee {
    String name; int age; String dept;

    Employee(String name) {
        this(name, 25);            // delegates to (String, int)
    }
    Employee(String name, int age) {
        this(name, age, "General"); // delegates to (String, int, String)
    }
    Employee(String name, int age, String dept) {
        this.name = name; this.age = age; this.dept = dept;
    }

Method Overriding — Rules

Valid overriding
  • Same method name and parameter list
  • Same or covariant return type (subtype for reference types only)
  • Same or less restrictive access (protected → public is fine)
  • Can throw fewer or narrower checked exceptions
  • Always annotate with @Override — compiler verifies it
Cannot override
  • final methods — sealed
  • static methods — method hiding, not overriding
  • private methods — not inherited, invisible to child
  • More restrictive access (public → protected is a compile error)
  • Broader or new checked exceptions than parent throws
⚠️
Static methods are hidden, not overridden. If both parent and child define a static method with the same signature, which one runs depends on the reference type, not the object type — this is method hiding. It does NOT participate in dynamic dispatch. This is a common interview trap.

Dynamic Method Dispatch — how runtime polymorphism works

When a parent reference holds a child object and both have a method with the same signature, the JVM calls the child's version. The reference type (compile-time type) controls what methods are visible. The object type (runtime type) controls which implementation runs.

Dynamic dispatch — the full picture 
class Animal  { void sound() { System.out.println("..."); }   }
class Dog     extends Animal {
    void sound() { System.out.println("Woof"); }
    void fetch() { System.out.println("Fetching!"); } // Dog-only method
}

Animal a = new Dog();  // Animal ref, Dog object
a.sound();              // → "Woof"  (Dog's version — dynamic dispatch)
// a.fetch();           → compile error: Animal ref doesn't know about fetch()
((Dog) a).fetch();      // → "Fetching!" — cast to Dog ref to access Dog methods

// Practical use: polymorphic collections
Animal[] zoo = { new Dog(), new Cat(), new Dog() };
for (Animal x : zoo) x.sound(); // Woof, Meow, Woof — correct class method each time
💡 Interview answer — "What is dynamic dispatch?" "The JVM resolves which overridden method to call at runtime based on the actual object type, not the reference type. The reference type determines which methods are visible at compile time; the actual object type determines which implementation runs. This is the mechanism behind runtime polymorphism — it lets you write code against a parent type and have the right child behaviour execute automatically."
Abstraction

Abstract Classes

Abstract classes sit between interfaces and concrete classes. They can have both abstract methods (no body — must be overridden) and concrete methods (with body — inherited). They're the right tool when subclasses share some implementation but must define their own version of certain behaviours.

Abstract Class — rules
  • Can have abstract methods (no body)
  • Can have concrete methods (with body)
  • Can have constructors (called via super() from child)
  • Can have instance variables of any access level
  • Abstract reference CAN hold a concrete subclass object
  • Subclass MUST implement all abstract methods, or be abstract itself
  • Cannot be instantiated — new AbstractClass() is a compile error
  • Cannot be final — final prevents extending, abstract requires it
  • Abstract method cannot be final, private, or static
Abstract vs Concrete — when to use
  • Use abstract when subclasses share common logic but must define their own version of some operations
  • Use concrete when the class is a complete, usable implementation on its own
  • Abstract = partial template + contract; concrete = full implementation
  • If a class has even one abstract method, the class MUST be declared abstract
  • A class can be declared abstract even with zero abstract methods (prevents direct instantiation)

abstract class DataExporter {
    // Concrete — shared logic all exporters reuse
    final void export() {         // final: subclasses cannot override the flow
        String data = fetchData();
        String formatted = format(data);
        write(formatted);
    }
    private String fetchData() { return "raw_data"; } // shared impl

    // Abstract — each exporter defines its own format and write logic
    abstract String format(String data);
    abstract void   write(String formatted);
}

class CSVExporter extends DataExporter {
    String format(String d) { return d.replace(" ", ","); }
    void   write(String d)  { System.out.println("CSV: " + d); }
}
class JSONExporter extends DataExporter {
    String format(String d) { return "{\"data\":\"" + d + "\"}"; }
    void   write(String d)  { System.out.println("JSON: " + d); }
}

new CSVExporter().export();  // CSV: raw_data
new JSONExporter().export(); // JSON: {"data":"raw_data"}

// Abstract classes CAN have constructors — used for shared initialisation
abstract class Shape {
    private String color;
    private String createdBy;

    Shape(String color) {          // constructor in abstract class
        this.color = color;
        this.createdBy = "system";
        System.out.println("Shape init: " + color);
    }

    abstract double area();
    String getColor() { return color; }
}

class Circle extends Shape {
    double radius;
    Circle(String color, double r) {
        super(color); // calls abstract class constructor — must be first
        this.radius = r;
    }
    double area() { return Math.PI * radius * radius; }
}

Circle c = new Circle("Red", 5.0);
// → Shape init: Red
System.out.println(c.getColor());   // Red
System.out.println(c.area());       // 78.539...
// A subclass can itself be abstract — defers some methods further down the chain
abstract class Vehicle {
    abstract void fuelType();  // must be implemented somewhere below
    abstract void move();
}

abstract class LandVehicle extends Vehicle {
    void move() { System.out.println("Moves on road"); } // implements move()
    // fuelType() still abstract — deferred to concrete child
}

class ElectricCar extends LandVehicle {
    void fuelType() { System.out.println("Electric"); } // finally implemented
}

ElectricCar e = new ElectricCar();
e.fuelType(); // Electric
e.move();     // Moves on road (from LandVehicle)
💡 Interview: Abstract class vs Interface — when to use which? Use abstract class when subclasses share real state (fields) or common implementation, or when you need constructors or non-public methods. Use an interface when you want a pure contract, need multiple inheritance, or want to define capability across unrelated classes (e.g., Comparable, Serializable).

Interfaces

Use an interface when you want polymorphism without borrowing implementation. An interface is a pure contract — it defines what a class can do, not how. In Java 8+, default and private methods made interfaces significantly more powerful.

// Default methods — added Java 8 to evolve interfaces without breaking implementors
interface Logger {
    void log(String message);  // abstract — must implement

    // Default — inherited automatically; classes can override or not
    default void logInfo(String msg) {
        log("[INFO] " + msg);
    }
    default void logError(String msg) {
        log("[ERROR] " + msg);
    }
}

class ConsoleLogger implements Logger {
    public void log(String msg) { System.out.println(msg); }
    // logInfo and logError are FREE — inherited from interface
}

class FileLogger implements Logger {
    public void log(String msg) { /* write to file */ }

    // Override the default — custom prefix for file logs
    public void logError(String msg) {
        log("[FILE-ERROR]["+System.currentTimeMillis()+"] "+msg);
    }
}

Logger l = new ConsoleLogger();
l.logInfo("App started");  // [INFO] App started — used default method
// Private methods (Java 9+) — shared helper logic for default methods
interface Validator {
    boolean isValid(String input);

    default boolean validateAndLog(String input) {
        boolean result = isValid(input);
        logResult(input, result);  // calls private helper
        return result;
    }
    default boolean validateOrThrow(String input) {
        boolean result = isValid(input);
        logResult(input, result);  // same private helper reused
        if (!result) throw new IllegalArgumentException("Invalid: "+input);
        return true;
    }

    // Private — ONLY callable within this interface; not visible to implementing classes
    private void logResult(String input, boolean r) {
        System.out.printf("Validated '%s': %s%n", input, r ? "PASS" : "FAIL");
    }
}
// Multiple inheritance via interfaces — impossible with classes
interface Flyable   { void fly();  }
interface Swimmable { void swim(); }
interface Runnable  { void run();  }

class Duck implements Flyable, Swimmable, Runnable {
    public void fly()  { System.out.println("Duck flying");   }
    public void swim() { System.out.println("Duck swimming"); }
    public void run()  { System.out.println("Duck running");  }
}

// Polymorphism — same object, different reference type
Flyable   f = new Duck(); f.fly();
Swimmable s = new Duck(); s.swim();

// Interface extending multiple interfaces
interface Amphibious extends Flyable, Swimmable {
    void switchMode(); // adds its own method on top
}
// Diamond problem: two interfaces have the same default method name
interface A { default void greet() { System.out.println("Hello from A"); } }
interface B { default void greet() { System.out.println("Hello from B"); } }

// Without resolution → compile error: "greet() is inherited from A and B"
class C implements A, B {
    public void greet() {
        A.super.greet(); // explicitly choose A's default
        // or: B.super.greet();
        // or: write your own logic entirely
    }
}
new C().greet(); // Hello from A

// Rule: if a CLASS also provides the method, class takes priority over interface default
// Rule: a more specific interface default overrides a less specific one in the hierarchy
💡 Interview: Why were default methods added in Java 8? To evolve existing interfaces without breaking all their implementing classes. When Java 8 added stream() and forEach() to Collection and Iterable, they used default methods so existing code — including third-party libraries with millions of Collection implementations — didn't need to change. This is the Open/Closed Principle applied to the Java standard library itself.

// Real-world: Builder pattern uses static nested class
class HttpRequest {
    private final String url;
    private final int timeout;
    private HttpRequest(Builder b) { url = b.url; timeout = b.timeout; }

    static class Builder {
        private String url; private int timeout = 30;
        Builder url(String u)   { this.url = u;      return this; }
        Builder timeout(int t) { this.timeout = t;  return this; }
        HttpRequest build()    { return new HttpRequest(this); }
    }
}
HttpRequest req = new HttpRequest.Builder()

    .timeout(60)
    .build();
// Why anonymous/local classes require effectively final local variables
class Demo {
    int instanceVar = 50;  // instance variables — always accessible, no restriction

    void run() {
        int x = 10;   // effectively final — never reassigned below ✓
        int y = 20;   // will be modified — NOT effectively final ✗

        Runnable r = new Runnable() {
            public void run() {
                System.out.println(instanceVar); // ✓ instance var — no restriction
                System.out.println(x);           // ✓ effectively final local
                // System.out.println(y);          ← compile error — y is modified after
            }
        };

        y++;  // this makes y non-effectively-final — causes compile error above
        r.run();
    }
}

// WHY this rule exists:
// Local vars live on the stack and are destroyed when the method returns.
// The anonymous class object may outlive the method (e.g. passed to a thread).
// Java captures a COPY of the local var at the time of capture.
// If the var could change after capture, the copy would become stale — inconsistency.
// Forcing effectively-final ensures the captured copy is always accurate.
💡 Interview answer — "Difference between inner class and static nested class?" A regular inner class holds an implicit reference to the outer class instance — it can access all outer members but requires an outer instance to be created. A static nested class has no reference to the outer instance — it can only access static outer members but can be created independently. In practice, use static nested classes by default (no hidden coupling); use regular inner only when you genuinely need access to the outer instance's state.
Keywords

static & final

Two of the most tested keywords. Know the execution order of static blocks vs constructors cold — interviewers love asking you to trace output. Know the three ways to initialize a final variable and the final-reference trap.

static — complete rules

static members
  • Shared across ALL instances — one copy per class in Method Area
  • Accessible without object: ClassName.field
  • static methods can only directly access static members
  • Cannot use this or super — no instance context
  • Static methods cannot be overridden — only hidden (method hiding ≠ polymorphism)
  • Only inner classes can be static — top-level classes cannot
  • Useful for shared counters, caches, constants, utility methods
static blocks
  • Run automatically when JVM loads the class into memory
  • Run exactly ONCE per class lifecycle
  • Run BEFORE any constructor or main()
  • Multiple static blocks run in top-to-bottom declaration order
  • Used for complex static variable initialisation (reading config, loading drivers)
  • Cannot access instance variables or methods
  • Cannot use this or super

Execution Order — must know for output-tracing questions

Complete execution order — trace this output 
class Parent {
    static int p = initP();
    static { System.out.println("② Parent static block"); }
    Parent()  { System.out.println("⑤ Parent constructor"); }
    static int initP() { System.out.println("① Parent static var"); return 1; }
}

class Child extends Parent {
    static { System.out.println("③ Child static block"); }
    int c = initC();
    Child()   { System.out.println("⑦ Child constructor"); }
    int initC() { System.out.println("⑥ Child instance var"); return 2; }
}

new Child();

// OUTPUT — always this order:
// ① Parent static var      ← parent static fields initialised
// ② Parent static block    ← parent static blocks run
// ③ Child static block     ← child static blocks run
// [static phase ends here — class is now loaded]
// ⑤ Parent constructor     ← super() called by Child constructor
// ⑥ Child instance var     ← child instance fields initialised
// ⑦ Child constructor      ← child constructor body

final — complete rules

final variable
  • Value cannot be changed after initialisation
  • Convention: ALL_CAPS naming — final int MAX_SIZE = 100;
  • 3 valid ways to initialise: directly, in static block, in constructor
  • Cannot leave a final instance field uninitialised — must assign in every constructor path
  • final reference ≠ immutable object — the reference can't change, the object's internals CAN

  • final methods cannot be overridden in subclasses
  • final classes cannot be extended — String, Integer, Math are final
  • Cannot have both abstract and final — they contradict each other
  • final + static = compile-time constant — stored in constant pool, inlined by compiler
  • Useful for security (no malicious subclassing) and performance (JVM inlines final methods)

Singleton Pattern

Ensure exactly one instance of a class exists throughout the application lifecycle. The concept is simple — private constructor + static instance + static accessor. The interview follow-up is always: "Is it thread-safe?" Know all four variants cold.

The 4 Core Ingredients

1
Private constructor — blocks new Singleton() from any external class
2
Private static instance field — the single object, held at the class level
3
Public static getInstance() — the global access point; creates once, always returns the same reference
4
Thread safety — without it, two threads calling getInstance() simultaneously can each pass the null check and create two separate instances, breaking the guarantee entirely

// Basic Singleton — NOT thread-safe
// Race: two threads can both see instance==null and each create an object
class CoffeeMachine {
    private float coffeeQty;
    private float waterQty;

    private static CoffeeMachine instance = null; // lazy — null until first call

    private CoffeeMachine() {      // private: blocks new CoffeeMachine() from outside
        coffeeQty = 10;
        waterQty  = 10;
    }

    public static CoffeeMachine getInstance() {
        if (instance == null)             // ← RACE CONDITION: both threads reach here
            instance = new CoffeeMachine();
        return instance;
    }
}

// Works fine in single-threaded code:
CoffeeMachine m1 = CoffeeMachine.getInstance();
CoffeeMachine m2 = CoffeeMachine.getInstance();
System.out.println(m1 == m2); // true
// Synchronized — thread-safe but SLOW
// Every single call to getInstance() acquires a lock,
// even after the instance is already created — unnecessary overhead
class CoffeeMachine {
    private static CoffeeMachine instance = null;
    private CoffeeMachine() {}

    public static synchronized CoffeeMachine getInstance() {
        // synchronized: only one thread enters at a time
        // Problem: lock acquired on EVERY call — ~100x slower than needed
        if (instance == null)
            instance = new CoffeeMachine();
        return instance;
    }
}
// Thread-safe: YES. Recommended: NO — DCL or Enum is better
// Double-Checked Locking — production-grade answer ★
// Locks ONLY during first creation; all subsequent calls are lock-free
class CoffeeMachine {
    // volatile: prevents JVM instruction reordering during object construction
    // Without volatile: another thread might see a non-null but partially-constructed object
    private static volatile CoffeeMachine instance = null;

    private float coffeeQty;
    private CoffeeMachine() { coffeeQty = 10; }

    public static CoffeeMachine getInstance() {
        if (instance == null) {                    // 1st check — no lock, fast path
            synchronized (CoffeeMachine.class) {
                if (instance == null) {            // 2nd check — inside lock, prevents race
                    instance = new CoffeeMachine();
                }
            }
        }
        return instance;
    }
    public void brew() { System.out.println("Brewing! qty=" + coffeeQty); }
}

// volatile is CRITICAL — without it the JVM may reorder the 3 steps of object creation:
// 1. allocate memory  2. initialise fields  3. assign reference to instance
// JVM may do 1→3→2: another thread sees non-null instance but uninitialised fields
// Eager initialisation — simplest thread-safe approach
// Instance created when class loads, before any getInstance() call
class CoffeeMachine {
    // JVM guarantees static final initialisation is thread-safe (happens once during class loading)
    private static final CoffeeMachine INSTANCE = new CoffeeMachine();

    private CoffeeMachine() {}

    public static CoffeeMachine getInstance() {
        return INSTANCE;  // no null check needed — always exists
    }
}

// Pros: simplest, no synchronisation needed, always thread-safe
// Cons: instance created even if it is NEVER used — wastes memory if heavyweight
// Use when: the singleton is lightweight and always needed by the application
// Enum Singleton — Josh Bloch's "Effective Java" recommendation
// JVM guarantees exactly one instance per enum constant — natively
enum CoffeeMachine {
    INSTANCE;  // the single instance

    private float coffeeQty = 10;
    private float waterQty  = 10;

    public void brew() {
        System.out.println("Brewing! coffee=" + coffeeQty);
        coffeeQty -= 1;
    }
    public float getCoffeeQty() { return coffeeQty; }
}

// Usage — no getInstance(), just access INSTANCE directly
CoffeeMachine.INSTANCE.brew();
CoffeeMachine.INSTANCE.brew();
System.out.println(CoffeeMachine.INSTANCE.getCoffeeQty()); // 8.0

// Why it is the best:
// ✓ Thread-safe — JVM handles enum constant initialisation
// ✓ Serialisation-safe — enums are naturally serialisable; no readResolve() needed
// ✓ Reflection-safe — Constructor.newInstance() throws for enums; can't break it
// ✓ Simplest code — no boilerplate

The volatile is critical — without it, the JVM can reorder object construction steps and a second thread may see a non-null reference to a partially-initialised object. ⚠️
When NOT to use Singleton: Singletons are global state — they make unit testing hard (difficult to mock), hide dependencies (classes reach for the global rather than declaring what they need), and can cause issues in multi-classloader environments. In real applications, DI frameworks (Spring @Bean, Guice) handle singleton scope for you. Know the pattern deeply, but know when to reach for DI instead.

⚠️
Contract: If a.equals(b) is true, then a.hashCode() == b.hashCode() MUST be true. The reverse is not required (hash collisions are allowed). Breaking this contract causes objects to "disappear" in HashMaps and HashSets — one of the most notorious Java bugs.

class Employee {
    private String id;
    private String name;

    Employee(String id, String name) { this.id = id; this.name = name; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;          // same reference shortcut
        if (o == null) return false;         // null check
        if (getClass() != o.getClass()) return false; // type check
        Employee e = (Employee) o;
        return Objects.equals(id, e.id);    // compare defining fields
    }

    @Override
    public int hashCode() {
        return Objects.hash(id);            // same field(s) as equals()
    }

    @Override
    public String toString() {
        return "Employee{id='" + id + "', name='" + name + "'}";
    }
}

Employee e1 = new Employee("E001", "Alice");
Employee e2 = new Employee("E001", "Alice Updated");
System.out.println(e1.equals(e2));   // true  — same id
System.out.println(e1.hashCode() == e2.hashCode()); // true — contract honoured
System.out.println(e1);             // Employee{id='E001', name='Alice'}
// BROKEN: overrides equals() but NOT hashCode() — classic bug
class BrokenKey {
    int value;
    BrokenKey(int v) { this.value = v; }

    @Override
    public boolean equals(Object o) {
        return o instanceof BrokenKey && ((BrokenKey)o).value == this.value;
    }
    // hashCode() NOT overridden — uses Object's memory-address based hash
}

Map<BrokenKey, String> map = new HashMap<>();
BrokenKey k1 = new BrokenKey(42);
map.put(k1, "found me");

BrokenKey k2 = new BrokenKey(42);
System.out.println(k1.equals(k2));       // true  — equals() says same
System.out.println(map.get(k2));          // null  — OBJECT LOST! different hashCode
// HashMap looks in bucket: hash(k2) → different bucket → not found
// This is the single most common hashCode contract violation bug
// Shallow copy: copies field values — reference fields point to SAME objects
class Address { String city; Address(String c){ city = c; } }

class Person implements Cloneable {
    String  name;
    Address address;   // reference field

    Person(String n, Address a){ name=n; address=a; }

    @Override
    protected Object clone() throws CloneNotSupportedException {
        return super.clone(); // SHALLOW — address reference is copied, not the object
    }
}

Person p1 = new Person("Alice", new Address("Delhi"));
Person p2 = (Person) p1.clone();
p2.address.city = "Mumbai";
System.out.println(p1.address.city); // Mumbai! — p1 and p2 share the same Address

// DEEP copy — clone the reference fields too
protected Object clone() throws CloneNotSupportedException {
    Person copy = (Person) super.clone();
    copy.address = new Address(this.address.city); // clone the Address too
    return copy;
}

// Person(Person other) { this.name = other.name; this.address = new Address(other.address.city); }

// 1. Exact match  2. Widening  3. Autoboxing  4. Varargs
class Test {

    static void print(long x)   { System.out.println("long");   }
    static void print(double x) { System.out.println("double"); }

Test.print(5);     // "int"   — exact match
Test.print(5L);    // "long"  — exact match
Test.print(5.0f);  // "double"— float widens to double (no float overload)

// Widening chain: byte → short → int → long → float → double
// char → int → long → float → double
// These promotions happen AUTOMATICALLY and silently — easy to miss
// Autoboxing is chosen AFTER widening — surprising results
class Test {
    static void print(Integer x) { System.out.println("Integer"); }
    static void print(long x)    { System.out.println("long"); }
}
Test.print(5); // "long" — widening (int→long) beats autoboxing (int→Integer)

Can you instantiate an abstract class? The real answer.

Abstract class instantiation — the anonymous class trick 
abstract class Shape {
    abstract double area();
    void describe() { System.out.println("I am a shape"); }
}

// Direct instantiation: NO
// Shape s = new Shape(); ← COMPILE ERROR

// BUT — you CAN create an object via anonymous class syntax:
Shape s = new Shape() {           // anonymous subclass of Shape

// instantiates THAT — you never directly instantiated Shape itself.

System.out.println(s.getClass().getSimpleName()); // "" (anonymous, no name)

Method hiding vs Method overriding — output prediction

Static method hiding — no dynamic dispatch

Immutable Class — how to create one correctly

Truly immutable class — 5 rules 
// Rule 1: declare class final (prevents subclass from breaking immutability)
public final class ImmutablePoint {
    // Rule 2: all fields private and final
    private final int x;
    private final int y;
    private final List<String> tags;  // mutable reference field — needs extra care

    // Rule 3: initialise all fields in constructor only
    public ImmutablePoint(int x, int y, List<String> tags) {
        this.x = x;
        this.y = y;
        // Rule 4: defensive copy of mutable inputs
        this.tags = List.copyOf(tags);  // unmodifiable copy
    }

    // Rule 5: no setters; getters return primitives or defensive copies
    public int getX()               { return x; }
    public int getY()               { return y; }
    public List<String> getTags()  { return tags; } // List.copyOf is already unmodifiable
}

// Java 16+ Records give you immutability automatically:
record Point(int x, int y) {}  // final, private fields, getters, equals/hashCode/toString — free
Point p = new Point(3, 4);
System.out.println(p.x());  // 3

Types of Inheritance & Why Java Forbids Multiple Class Inheritance

Types Java supports
  • Single: A extends B
  • Multilevel: A extends B, B extends C
  • Hierarchical: B extends A, C extends A (multiple children, one parent)
  • Multiple via Interface: class A implements B, C
  • Multiple class inheritance: NOT supported
Why no multiple class inheritance?
  • The Diamond Problem — if B and C both extend A and both override method(), which version does D (extending B and C) inherit? Ambiguous.
  • Interfaces solve this: if two interfaces provide the same default method, the implementing class is forced to resolve the conflict explicitly — compiler error if you don't.
  • This is a design decision — C++ allows multiple class inheritance but requires complex resolution rules.

💡 Is Java purely OOP? No — Java is not a pure OOP language for two reasons: (1) primitive types (int, boolean, double etc.) are not objects, they bypass the object model entirely; (2) static methods and static fields belong to classes, not objects — they violate the "everything is an object" principle. Languages like Smalltalk and Ruby are considered pure OOP because everything is an object.

Enums — Beyond the Singleton

Enums in Java are far more powerful than most candidates know. They can have fields, constructors, methods, and even abstract methods per-constant. This is frequently tested at senior level.

Fields & methods
Abstract methods per-constant
Enum implementing interface
// Enum with fields, constructor, methods
enum Planet {
    MERCURY(3.303e+23, 2.4397e6),
    VENUS  (4.869e+24, 6.0518e6),
    EARTH  (5.976e+24, 6.37814e6);

    private final double mass;    // in kilograms
    private final double radius;  // in metres

    Planet(double mass, double radius) {  // constructor is implicitly private
        this.mass = mass;
        this.radius = radius;
    }

    double surfaceGravity() {
        final double G = 6.67300E-11;
        return G * mass / (radius * radius);
    }
}

System.out.println(Planet.EARTH.surfaceGravity()); // 9.80
System.out.println(Planet.MERCURY.name());          // MERCURY
System.out.println(Planet.VENUS.ordinal());        // 1 (zero-indexed)
Planet p = Planet.valueOf("EARTH");               // get by name
// Abstract method in enum — each constant provides its own implementation
enum Operation {
    PLUS  { public double apply(double x, double y){ return x + y; } },
    MINUS { public double apply(double x, double y){ return x - y; } },
    TIMES { public double apply(double x, double y){ return x * y; } },
    DIVIDE{ public double apply(double x, double y){ return x / y; } };

    public abstract double apply(double x, double y);
}

for (Operation op : Operation.values()) {
    System.out.printf("%.1f %s %.1f = %.1f%n", 3.0, op, 2.0, op.apply(3.0, 2.0));
}
// 3.0 PLUS 2.0 = 5.0  →  3.0 MINUS 2.0 = 1.0  → etc.
// This replaces an entire if/switch chain — OCP in action
// Enum implementing interface — polymorphism with enum
interface Printable { void print(); }

enum Status implements Printable {
    PENDING, ACTIVE, CLOSED;

    public void print() {
        System.out.println("Status: " + this.name());
    }
}
Status.ACTIVE.print(); // Status: ACTIVE

// EnumSet and EnumMap — high-performance for enums
EnumSet<Status>  active = EnumSet.of(Status.PENDING, Status.ACTIVE);
EnumMap<Status, String> labels = new EnumMap<>(Status.class);
labels.put(Status.ACTIVE, "Currently Running");
// EnumSet is backed by a bit vector — O(1) contains(), extremely fast
// EnumMap uses array indexed by ordinal — faster than HashMap for enum keys
Interview Rapid Fire

FAANG Rapid-Fire Q&A

Short, sharp answers to the most frequently asked OOP short-answer questions. These appear in screening rounds and written tests.

Quick-fire answers

Can constructor be inherited?

  • No. Constructors are not inherited.
  • They can only be called via super() — not inherited as members.
  • A child class always needs its own constructor (implicit no-arg is provided only if no constructor is defined).

Can constructor be overridden?

  • No — constructors are not inherited, so they cannot be overridden.
  • You can overload constructors within the same class.

Can we have try-catch in constructor?

  • Yes — a constructor is a method body; any valid Java code can go inside.
  • Can also declare checked exceptions in constructor signature: MyClass() throws IOException {}

Can abstract class have main()?

  • Yes — main() is a static method; static methods are allowed in abstract classes.
  • The JVM can execute it without instantiating the class.

Can interface extend a class?

  • No — an interface can only extend another interface (one or more).
  • A class can implement an interface.
  • An abstract class can implement an interface without implementing all methods.

Can abstract class be final?

  • No — abstract requires extending; final forbids extending. They directly contradict each other.
  • Compiler error: illegal combination of modifiers: abstract and final

What if child doesn't implement all abstract methods?

  • The child class must also be declared abstract.
  • If not declared abstract, the compiler forces you to implement all abstract methods.
  • This allows chains of partial abstract implementations.

Can we override equals() but not hashCode()?

  • Technically yes — it compiles. But it breaks the equals/hashCode contract.
  • Objects will be "lost" in HashMaps/HashSets.
  • Always override both together. IDEs auto-generate both.

Can static method be abstract?

  • No — abstract means "subclass must implement"; static means "belongs to class, not inherited".
  • These contradict — a static method cannot be overridden, so making it abstract is meaningless.

Can private method be abstract?

  • No — private methods are not inherited or visible to subclasses.
  • Abstract means "override in subclass" — impossible if the method is private.
  • Java 9 allows private methods in interfaces — but they cannot be abstract.

Can a class implement two interfaces with same method?

  • Yes — if both have the same abstract method signature, one implementation satisfies both.
  • If both have conflicting default methods → must override to resolve (compile error otherwise).

What is object interning?

  • Reusing objects instead of creating new ones — String pool is the most common example.
  • "hello".intern() returns the pool reference.
  • Integer cache (-128 to 127) is another example of interning.

FAANG Design Nuggets

★
Favour composition over inheritance — GoF. Inheritance creates tight coupling; composition lets you change behaviour by swapping components. Ask: is this truly IS-A, or am I just trying to reuse code? If the latter, use HAS-A.
★
Program to interfaces, not implementations — declare variables as List not ArrayList, Map not HashMap. This decouples callers from concrete classes and makes swapping implementations trivial.
★
Encapsulation = the only OOP principle you can't work around — once you expose a public field, you can't add validation logic without breaking all callers. Always start private, expose only through methods.
★
The equals/hashCode contract is the most common real-world OOP bug — override both or neither. The symptom is objects "disappearing" from HashMaps. IDEs generate both in one shot (Alt+Insert in IntelliJ).
★
Immutability is your default target — prefer final fields, Records (Java 16+), and unmodifiable collections. Immutable objects are thread-safe by definition, safe to share, and easier to reason about.
★
Never call overridable methods from a constructor — if a subclass overrides the method, it will run before the subclass's own fields are initialised, producing null/0/false default values and deeply confusing bugs.
★
Use @Override always — without it, a typo in an override silently becomes a new method (overload), not an override. The bug is invisible at compile time; behaviours just don't work as expected at runtime. @Override catches this immediately.
Interview Reference

Interview Quick Reference

One-liners for when you're under pressure. Know these cold before any Java interview.

🏛️ 4 Pillars one-liners

  • Abstraction — hide how, show what
  • Encapsulation — bundle data + methods, guard with private
  • Inheritance — IS-A, code reuse via extends
  • Polymorphism — one name, many forms (overload/override)
  • Pillars link: Encapsulation → Abstraction; Inheritance → Polymorphism

🧬 Inheritance rules

  • super() must be first line; this() also must be first — can't use both
  • Static methods are hidden, not overridden — no dynamic dispatch
  • Private methods not inherited at all
  • final methods cannot be overridden
  • Covariant return: child can return subtype of parent's return type (reference only)

🎭 Abstract vs Interface

  • Abstract: shared state + code + constructors
  • Interface: pure contract, no instance state
  • Abstract = partial implementation + contract
  • Interface = multiple inheritance mechanism
  • Java 8+: interfaces can have default + static methods
  • Java 9+: interfaces can have private methods

🏗️ Inner class access rules

  • Regular inner: ALL outer members (even private)
  • Static nested: ONLY static outer members
  • Anonymous/Local: effectively final locals only
  • Only inner classes can be declared static
  • Regular inner needs outer instance; static nested does not

⚡ Execution order

  • 1. Parent static vars & blocks (top-to-bottom)
  • 2. Child static vars & blocks (top-to-bottom)
  • 3. Parent constructor body
  • 4. Child instance var initialisers
  • 5. Child constructor body
  • Static phase always runs before any constructor

🔒 final rules

  • final variable = value can't change after init
  • final reference ≠ immutable object (contents can mutate)
  • final method = can't override in child
  • final class = can't extend (String, Integer, Math)
  • abstract + final = compile error (contradictory)
  • 3 ways to init: direct, static block, constructor

🔁 Singleton variants

  • Basic = not thread-safe
  • Synchronized = safe, every call locks (slow)
  • DCL + volatile = production choice
  • Eager init = safe, not lazy
  • Enum = best practice (Effective Java)
  • volatile prevents partial-construction visibility bug

🚨 Top interview traps

  • Missing volatile in DCL Singleton
  • Static method "override" = hiding, not polymorphism
  • final reference is not immutable (contents CAN mutate)
  • Modifying local var captured by anonymous class
  • Missing super() when parent has no default constructor
  • Abstract + final = compile error
  • Interface fields = always public static final
  • Calling overridden method from constructor = subfield is still 0/null
  • Override equals() without hashCode() = HashMap loses objects
  • Integer cache: == works for -128..127, fails beyond

⚖️ equals() rules

  • == on objects = reference equality (same memory)
  • equals() = logical equality (content)
  • String literals share pool: "a"=="a" is true
  • new String("a")==new String("a") is false
  • Always override hashCode() when overriding equals()
  • equals() contract: reflexive, symmetric, transitive, consistent, non-null

🏗️ Immutable class recipe

  • Declare class final
  • All fields private + final
  • No setters
  • Initialise in constructor only
  • Defensive copy of mutable inputs/outputs
  • Java 16+: use records for free immutability

🧵 Memory quick ref

  • Local primitives → Stack
  • Local references → Stack (object on Heap)
  • All objects → Heap
  • Static variables → Method Area (Heap in Java 8+)
  • Stack = per-thread; Heap = shared across threads
  • String pool = special area in Heap

🔤 String one-liners

  • String = immutable, thread-safe, pool-backed
  • StringBuilder = mutable, fast, NOT thread-safe
  • StringBuffer = mutable, thread-safe (synchronized)
  • + on strings creates new objects each time
  • Use StringBuilder in loops, never + in loops
  • intern() forces string into pool

🎭 Overloading resolution order

  • 1st: Exact match
  • 2nd: Widening (byte→short→int→long→float→double)
  • 3rd: Autoboxing (int → Integer)
  • 4th: Varargs (int...)
  • null fits any reference — ambiguity = compile error
  • Static methods: resolved by REFERENCE type, not object type

📦 Enum power features

  • Enums can have fields, constructors, and methods
  • Enum constructor is always implicitly private
  • Enums can implement interfaces
  • Each constant can have its own method body (abstract enum methods)
  • EnumSet / EnumMap = fastest collection for enum keys
  • Enum = best Singleton implementation

🌟 FAANG design principles

  • Favour composition over inheritance
  • Program to interfaces, not implementations
  • Encapsulate what varies
  • Depend on abstractions, not concretions (DIP)
  • Immutability = thread-safe by default
  • Never call overridable method from constructor
  • Always use @Override annotation
